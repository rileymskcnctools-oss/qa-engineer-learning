## 一、分层的价值与三层架构

### 知识点 1：为什么分层 + Controller/Service/DAO

【课程原话/定义】
代码分层是按功能和责任把系统划分成多个层次，实现模块化，提高可读性、可维护性、可扩展性。

不分层的问题：耦合性增加、难维护、测试困难。
分层的价值：可扩展、可维护、可测试。

经典三层架构：
- **Controller（web 层）**：处理用户请求、访问控制、基本参数校验、简单业务逻辑
- **Service 层**：具体业务逻辑服务层
- **DAO 层**：数据访问层，与底层存储（MySQL 等）交互

（中间还有 Manager 层：封装第三方调用、下沉通用能力、组合多个 DAO）

【为什么？】
为什么要分层？核心是"职责分离"。如果一个文件里既写 HTTP 请求处理、又写业务逻辑、又写 SQL，那改一处会牵动全局，测也难测。分层后：Controller 只管"接收请求、校验参数、返回响应"，Service 管"业务逻辑"，DAO 管"数据库操作"。每层职责单一，可以独立测试（Service 层单独测业务逻辑，不用起 HTTP 服务），也便于替换（比如换数据库，只改 DAO 层）。这是从"能跑"到"可维护"的关键一步，也是面试考察"工程能力"的重点。

【必须掌握】
- 分层核心：职责分离（Controller 请求 / Service 业务 / DAO 数据）
- 不分层：耦合高、难维护、难测试
- 分层：可扩展、可维护、可测试
- Controller 管请求和参数校验，Service 管业务，DAO 管数据库

【企业场景】
你在公司测试平台，如果所有代码写在一个文件（路由 + 逻辑 + SQL 混一起），加个功能要小心翼翼怕改坏别的。分层后：改数据库操作只动 DAO 层，改业务只动 Service 层，改接口只动 Controller 层，互不影响。团队协作也清晰——每人负责一层。

【面试考察】
面试官（高频）：「后端为什么要分层？各层职责是什么？」

参考回答框架：
1. 分层实现职责分离，降低耦合
2. Controller：请求处理 + 参数校验
3. Service：业务逻辑
4. DAO：数据库访问
5. 价值：可维护、可扩展、可测试

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 所有代码写一个文件 | 耦合高、难维护，要分层 |
| Controller 里写复杂业务 | Controller 只做请求处理和校验，业务下沉 Service |
| 分层越细越好 | 分层提高复杂度，要结合项目实际权衡 |

【我的理解】

## 二、分层领域模型与目录结构

### 知识点 2：DO / DAO / DTO / Service / Controller 五层

【课程原话/定义】
基于三层架构的分层领域模型：
- **DO**（Data Object）：与数据库表结构一一对应（ORM 模型）
- **DAO**（Data Access Object）：数据访问，负责 CRUD
- **DTO**（Data Transfer Object）：数据传输对象（pydantic 校验）
- **Service**：业务逻辑层
- **Controller**：HTTP 请求处理

目录结构：
```
src/
├── server.py          # 入口（Base、engine、app）
├── do/                # ORM 模型
├── dao/               # 数据访问（CRUD）
├── dto/               # 数据传输对象（pydantic）
├── service/           # 业务逻辑
├── controller/        # 接口（蓝图）
└── tests/             # 测试
```

数据流：Controller（收请求）→ DTO 校验 → Service（业务）→ DAO（CRUD）→ DO（ORM 映射表）

【为什么？】
为什么要拆出 DO/DAO/DTO 三个"数据对象"？因为它们分别解决不同的问题：DO 是"数据库长什么样"（ORM 模型，对应表结构）；DAO 是"怎么操作数据库"（CRUD 封装）；DTO 是"接口传什么数据"（pydantic 校验 + 序列化）。三者分离后，数据库表结构变了只改 DO、数据库操作变了只改 DAO、接口数据格式变了只改 DTO，互不影响。而 Service（业务）和 Controller（接口）的分离，让"业务逻辑"可以脱离 HTTP 独立测试。这套五层结构是"测试平台后端"的标准工程化范式。

【必须掌握】
- 五层：DO（表结构）、DAO（CRUD）、DTO（数据校验）、Service（业务）、Controller（接口）
- 数据流：Controller → DTO 校验 → Service → DAO → DO
- 目录：do/dao/dto/service/controller/tests
- DO 不包含数据库操作（只定义结构）
- Service 可独立单元测试，Controller 用 requests 做接口测试

【企业场景】
你在公司测试平台按五层分层：do 定义用例表结构、dao 封装用例 CRUD、dto 校验用例数据、service 实现用例业务、controller 暴露 /case 接口。加新功能时各层各改各的，Service 层跑 pytest 单测，Controller 层用 requests 做接口测试。这是"可维护、可测试"的真实落地。

【面试考察】
面试官：「说说你项目的分层结构，DO/DAO/DTO 有什么区别？」

参考回答框架：
1. 五层：DO/DAO/DTO/Service/Controller
2. DO 对应表结构（ORM 模型）
3. DAO 封装 CRUD
4. DTO 用 pydantic 做数据校验
5. Service 业务、Controller 接口

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| DO 里写数据库操作 | DO 只定义表结构，操作在 DAO |
| DTO 和 DO 混为一谈 | DO 是表结构，DTO 是接口数据传输（校验） |
| Controller 写业务逻辑 | 业务下沉 Service，Controller 只转发 |

【扩展知识】
分层是"可测试性"的落地。分层后，Service 层可以脱离 HTTP 用 pytest 直接单测（不启动服务），Controller 层用 requests 发 HTTP 做接口测试。这正好呼应了 Ch19 讲的"可测性"——分层让"可独立测试"成为可能，是测试工程师设计后端时的核心考量。

【我的理解】
> （DO、DAO、DTO 都带一个"D"（Data），它们分别代表数据的哪个形态？为什么"数据库结构"和"接口数据"要分成 DO 和 DTO 两个对象？）
