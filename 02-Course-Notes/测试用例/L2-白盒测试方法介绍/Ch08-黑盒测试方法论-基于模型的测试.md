## 一、基于模型的测试（MBT）是什么

### 知识点1：MBT 的定义与本质

【课程原话/定义】
> Model-based Testing is an application of model-based design for designing and optionally also executing artifacts to perform software testing or system testing.
> 基于模型的测试（MBT）是基于模型的设计的应用，用于设计和（可选地）执行工件，以执行软件测试或系统测试。模型可用于表示被测系统（SUT, System Under Test）的期望行为，或表示测试策略和测试环境。

【为什么？】
前面学的等价类、边界值、判定表、因果图、场景法、正交法，本质都是在"建模"——只不过模型存在于测试工程师的脑子里和纸上，没有显式化、也没法被机器直接消费。MBT 把"模型"这个隐式的东西显式化、可机器处理化。

关键在定义里那个"或"字：模型有**两种完全不同的用途**——① 描述 SUT 的期望行为（系统应该怎样），② 描述测试策略和测试环境（这次该怎么测）。同一份模型既刻画"被测对象"，又刻画"测试手段"，这是它"一物两用"的根源。测试用例从模型自动/半自动生成，而不是工程师手动一条条写。

【必须掌握】
- MBT 全称 Model-based Testing，是"基于模型的设计"在测试领域的应用
- 模型的两种用途：表示 SUT 期望行为 / 表示测试策略与测试环境
- 核心主张：测试用例从模型（自动/半自动）生成

【企业场景】
> 你负责一个"订单状态流转"系统，状态有十几种、迁移规则几十条，产品文档是一大段文字。你按传统方法一条条设计用例，改了需求又要人工找哪些用例受影响。改用 MBT 的思路：把"状态 + 迁移"画成一张模型图，改需求只改图上的迁移规则，用例由工具从新图上重新生成——回归范围一目了然，漏测的概率大幅下降。

【面试考察】
面试官："什么是基于模型的测试？它和前面学的等价类、边界值这些方法有什么本质区别？"
参考回答框架：
1. 一句话定义：测试用例从"被测系统的模型"自动/半自动生成，而不是手动设计
2. 本质区别：等价类/边界值等是"人的头脑里建模、手工产出用例"，MBT 是"显式建模 + 工具生成用例"
3. 模型的两种用途（描述 SUT 行为 / 描述测试策略）
4. 落一个例子收尾（订单状态机、登录态机等）

【易错点】

| ❌ 错误理解 | ✅ 正确理解 |
|------------|------------|
| MBT 是一种"黑盒设计方法"（并列于等价类/边界值） | MBT 是一套"范式"——把建模显式化，工具从模型生成用例，它高于单一设计方法 |
| 模型只能描述"被测系统长什么样" | 模型还能描述"测试策略/测试环境"，两种用途都要知道 |
| MBT = 完全不用人写用例 | 很多场景仍要人工建模、人工做映射，自动化程度视工具和模型信息量而定 |

【我的理解】
> （用自己的话解释：MBT 里的"模型"和等价类/边界值里的"头脑模型"到底差在哪？为什么说"显式化"是 MBT 的关键一跃？）

### 知识点2：抽象测试套件与"映射问题"

【课程原话/定义】
> 描述 SUT 的模型通常是对 SUT 期望行为的抽象、部分表示。从这种模型派生的测试用例，是与模型处于同一抽象级别的功能测试，统称为**抽象测试套件（abstract test suite）**。抽象测试套件不能直接针对 SUT 执行，因为它处于错误的抽象级别。可执行测试套件需要从抽象测试套件派生而来——通过把抽象测试用例映射到适合执行的具体测试用例实现，这被称为解决"**映射问题（mapping problem）**"。

【为什么？】
这是 MBT 最核心、也最容易卡住新手的机制。模型是抽象的——"用户登录成功"这句话没法直接跑；系统只能执行具体的——"输入 user=xxx、pwd=xxx，点击登录按钮，断言返回 200 并拿到 cookie"。抽象层与执行层之间的鸿沟，就是"映射问题"。

为什么有些 MBT 环境能直接生成可执行套件？因为它的模型里带的信息足够多（元素定位、接口参数、断言字段），能自动落到具体语句/方法调用；否则抽象测试套件里的元素必须人工映射成软件里的具体语句/方法。**"映射问题"解决得好不好，决定了 MBT 的自动化程度能到多高。**

【必须掌握】
- 抽象测试套件 vs 可执行测试套件：前者与模型同抽象级别、不可直接执行；后者可直接与 SUT 通信
- "映射问题"的定义：把抽象测试用例落到具体可执行语句/方法调用的过程

【企业场景】
> 你给登录功能建了一个 MBT 模型，工具从模型生成了一堆"抽象路径"：未登录→登录→登出、登录失败→重试→登录成功……这些路径跑不了，因为里面只有"登录"这个词，没有账号、密码、按钮定位。你的下一步工作就是"做映射"：把"登录"这条边绑到真实的 `driver.find_element(...).send_keys(...)` 上。这一步做完，测试才真正能跑——这就是"映射问题"在真实项目里的样子。

【面试考察】
面试官："抽象测试套件为什么不能直接跑？"
参考回答框架：
1. 抽象级别不一致：模型只说"做什么"，没说"怎么在系统上做"
2. 抽象测试套件是"与模型同级别的功能测试"，缺少具体输入、定位、断言
3. 需要"映射"把抽象用例绑定到具体语句/方法，产出可执行测试套件
4. 映射的自动化程度取决于模型信息量（有些环境能直接生成，有些要人工补）

【易错点】

| 维度 | 抽象测试套件 | 可执行测试套件 |
|------|--------------|----------------|
| 抽象级别 | 与模型同级（"登录成功"） | 与 SUT 同级（具体输入/断言） |
| 能否直接执行 | ❌ 不能 | ✅ 能 |
| 由谁派生 | 从模型直接生成 | 由抽象套件经"映射"而来 |
| 依赖信息 | 模型本身 | 模型 + 元素定位/接口/断言等实现细节 |

> （用自己的话，举一个你自己能想到的"抽象→具体"映射例子：模型里的一条边，映射成真实代码后长什么样？）

### 知识点3：MBT 与黑盒测试的关系

【课程原话/定义】
> Because test suites are derived from models and not from source code, model-based testing is usually seen as one form of black-box testing.
> 因为测试套件源自模型而不是源代码，基于模型的测试通常被视为一种黑盒测试形式。但百度百科补充：这并不十分准确——毕竟 MBT 与源代码级的测试覆盖率、以及对代码的功能测试都有着很大的关系。复杂软件系统的 MBT 仍然是一个不断发展的领域。

【为什么？】
"MBT 算不算黑盒"是个经典认知考点，也是这章最容易在面试里被追问的地方。表面看：用例从模型（而非源码）生成 → 黑盒。但模型往往是从需求/规格、甚至源码结构里提炼出来的；而且 MBT 的覆盖度指标（edge_coverage、vertex_coverage）能映射到代码路径的覆盖 → 又沾白盒。

正确的理解是：MBT 是一种把"黑盒的输入视角"和"白盒的覆盖度量"融合起来的方法论，不能简单二分。这也是为什么课程原文最后补一句"复杂系统的 MBT 仍是不断发展的领域"——它的边界还在演进。

【必须掌握】
- 为什么 MBT 通常被归为黑盒：用例源自模型而非源码
- 为什么又不完全准确：模型可能与源码结构相关，覆盖度能映射到代码路径
- 结论：MBT 是"黑盒视角 + 白盒度量"的融合

【企业场景】
> 你在评审会上被开发问："你们测的是不是都不看代码？"你可以这样答：我们用模型生成用例时，模型是从需求规格提炼的，这是黑盒视角；但生成器的 edge_coverage/vertex_coverage 能告诉我们哪些迁移没覆盖，这些路径又能反推回代码的哪些分支没走到。所以 MBT 既能从用户视角保证功能，又能给出接近白盒的覆盖证据——这正是它比纯手工黑盒更有说服力的地方。

【面试考察】
面试官："MBT 是黑盒还是白盒测试？"
参考回答框架：
1. 通常归为黑盒：用例源自模型（需求/规格的抽象），不看源码
2. 但不完全准确：模型常与源码结构相关，覆盖度指标可映射到代码路径
3. 定论：是"黑盒输入视角 + 白盒覆盖度量"的融合，不要非黑即白
4. 可补一句：该领域仍在演进，尤其针对复杂系统

【易错点】

| 视角 | 支持"黑盒"的证据 | 支持"白盒"的证据 |
|------|------------------|------------------|
| 用例来源 | 从模型生成，非源码 | 模型可能由源码结构/规格提炼 |
| 覆盖度量 | 关注功能/状态/迁移 | edge/vertex coverage 能映射到代码路径 |
| 结论 | 通常被视为黑盒 | 但不完全准确，是两者的融合 |

【我的理解】
> （用自己的话说明：为什么"从模型生成"会被归为黑盒？又是什么让它"不完全算黑盒"？你面试时打算怎么一句话定性？）

## 二、模型的构建方法

### 知识点4：四种建模方法

【课程原话/定义】
> 模型构建方法：**有限状态机**、**UML**、**编程语言**、**数学方法**。

【为什么？】
四种方法对应不同的抽象层次、工具链和严谨程度，选型取决于系统复杂度 + 团队技能 + 工具生态：

1. **有限状态机（FSM）**：适合"状态 + 迁移"明确的系统（订单状态、登录态、网络协议状态机）。它最贴近 MBT 的"图"直觉，GraphWalker 就是 FSM 思路的可执行化。
2. **UML**：适合从需求文档到模型的标准化过渡（状态图/活动图/用例图）。企业里需求文档常带 UML，能直接复用，沟通成本低。
3. **编程语言**：用代码直接描述模型（GraphWalker 的 Java API、ModelJUnit 就是这种）。优点是模型可版本化、可复用代码资产，缺点是门槛高。
4. **数学方法**（形式化规约，如 Z、B 方法、Petri 网）：最严谨，能数学证明某些性质，但学习成本高、工程落地少。

【必须掌握】
- 四种方法的名称，各适合什么场景
- 有限状态机与 GraphWalker 的对应关系（最常用）

【企业场景】
> 你接到一个"电子合同签署"系统，状态流转复杂（草稿→待签→已签→作废→归档…）。选建模方法时你判断：这是典型的"状态 + 迁移"问题，用有限状态机最合适；团队里没有形式化方法储备，用数学方法不现实；需求文档里已经有 UML 状态图，可以直接改造成 FSM 模型。这就是"按场景选方法"的决策过程。

【面试考察】
面试官："给系统建模有哪几种方法？你怎么选？"
参考回答框架：
1. 先报四种：有限状态机 / UML / 编程语言 / 数学方法
2. 选型三要素：系统复杂度、团队技能、工具生态
3. 落地判断：状态/迁移明确 → FSM；需求带 UML → 复用；要形式化证明 → 数学方法；要代码资产 → 编程语言

【易错点】

| 建模方法 | 抽象/严谨度 | 典型场景 | 落地门槛 |
|----------|-------------|----------|----------|
| 有限状态机 | 中 | 状态/迁移明确的系统（订单、协议） | 低，工具成熟（GraphWalker） |
| UML | 中低 | 需求已带 UML 的标准化过渡 | 低，沟通成本低 |
| 编程语言 | 中 | 想复用代码资产、可版本化 | 中高，要会写模型代码 |
| 数学方法 | 高（可形式化证明） | 安全攸关、需严格证明 | 高，工程落地少 |

【我的理解】
> （用一个你熟悉的业务（登录、购物车、审批流……），判断它最适合用哪种建模方法，并说一句理由。）

## 三、从模型导出测试

### 知识点5：测试导出与"测试需求包"

【课程原话/定义】
> 测试可以通过不同的方式从模型导出。因为测试通常是实验性的、基于启发式的，没有已知的单一最优的测试导出方法。通常把所有与测试导出相关的参数合并到一个包中，称为"**测试需求**"、"**测试目的**"甚至"**用例（use case）**"。这个包可以包含：模型中应该关注的部分，或完成测试的条件（测试停止标准）。

【为什么？】
这是 MBT "可工程化"的关键。从同一个模型出发，你可以导出完全不同的测试——是全覆盖所有迁移？还是只验证某条关键路径？还是跑到某个状态就停？"测试需求包"就是把这些意图显式表达出来，告诉工具"这次测到什么程度、什么时候停"。

最关键的一点是**停止标准**：状态机图会无限展开路径（环形的迁移可以走无穷多圈），没有停止标准测试永远跑不完。所以"没有唯一最优导出方法"不是缺点，而是特征——测试的"目的"本身就是输入的一部分。

【必须掌握】
- 测试需求包 = 关注点（测哪些部分）+ 停止标准（何时算测完）
- 同一模型可导出不同目的的测试；没有唯一最优导出方法

【企业场景】
> 你手上有一个电商下单模型。发版前冒烟，你只关心"浏览→加购→下单→支付"这条主路径，就把"测试目的"设成"覆盖这条边序列"；而做完整回归时，你把"停止标准"设成"edge_coverage(100)"——所有迁移都走到才算完。同一个模型，两次导出，测试范围和耗时完全不同，这就是"测试需求包"在实战里的用法。

【面试考察】
面试官："从同一个模型，怎么生成不同目的的测试？"
参考回答框架：
1. 测试需求包 = 关注点 + 停止标准，是导出的"输入参数"
2. 冒烟 → 指定关键路径；回归 → 全覆盖（edge/vertex coverage 100%）
3. 针对性验证 → 定向走到某个状态/边（a_star）
4. 没有唯一最优方法，测到什么程度取决于你声明的"目的"

【易错点】

| ❌ 错误理解 | ✅ 正确理解 |
|------------|------------|
| 模型建好就自动得到"唯一正确"的测试集 | 模型是"原料"，测试集随"测试需求包"（目的+停止标准）而变 |
| 测试从模型生成，所以一定能穷尽所有路径 | 停止标准恰恰是为了防止无限展开；没有它测试跑不完 |
| 停止标准可有可无 | 停止标准是"测试需求包"的必备组成，决定测试何时收口 |

【我的理解】
> （同一张订单状态图：冒烟测试和完整回归，你的"测试需求包"分别会写成什么？停止标准各是什么？）

## 四、行业案例

### 知识点6：微软 MBT 实践与 Spec Explorer

【课程原话/定义】
> 十多年来，Microsoft 已成功地将基于模型的测试（MBT）应用到其内部开发过程中，适用于各种内部和外部软件产品，多年来采用率稳步上升，在测试界很受欢迎。**Spec Explorer** 是一个微软 MBT 工具，它扩展了 Visual Studio，为创建行为模型提供了一个高度集成的开发环境，以及一个用于检查模型有效性并从中生成测试用例的图形分析工具。

【为什么？】
微软是 MBT 工业化的标杆案例——它证明了 MBT 不是学术玩具，而能在大厂真实产品（协议栈、编译器、SDK 这类"规格明确、状态复杂"的软件）上稳定落地十年以上。这给了 MBT "可信度背书"。

Spec Explorer 的价值点在于集成：把"建模 + 模型检查 + 用例生成"放进一个 Visual Studio 环境里，显著降低自然学习曲线。它特别强调"检查模型有效性"——模型本身可能写错，先校验模型再生成用例，避免"垃圾进垃圾出"。

【必须掌握】
- 微软 MBT 落地范围：内部开发流程，十年+，内外部产品
- Spec Explorer 定位：Visual Studio 扩展 = 行为模型 IDE + 模型检查 + 用例生成

【企业场景】
> 你在面试里被问到"MBT 有工业落地吗"，如果只会背概念就会显得虚。你可以举微软：它用 MBT 测协议实现、SDK 这类状态复杂的软件，工具是 Spec Explorer，把建模、模型校验、用例生成集成在 Visual Studio 里。这个例子能证明你了解 MBT 不只是理论，还有成熟工业实践。

【面试考察】
面试官："工业界谁在用 MBT？有什么代表工具？"
参考回答框架：
1. 微软：十多年把 MBT 用在内部开发，测协议/SDK 等状态复杂的产品
2. Spec Explorer：微软 MBT 工具，Visual Studio 扩展，集成"建模 + 模型检查 + 用例生成"
3. 开源侧：GraphWalker（下一知识点展开）
4. 选型：闭源+VS 绑定（Spec Explorer）vs 开源+跨平台（GraphWalker）

【易错点】

| ❌ 错误理解 | ✅ 正确理解 |
|------------|------------|

### 知识点7：GraphWalker 开源工具

【课程原话/定义】
> **GraphWalker** 是一个开源的基于模型的测试工具，提供 Editor（图形编辑器）、Command line tools（命令行工具）、并可集成到 Java 项目（Integrate GraphWalker in your java project）。

【为什么？】
Spec Explorer 闭源 + 绑定 Visual Studio，学习成本高、且不面向测试工程师普及；GraphWalker 开源 + 跨平台（一个 jar）+ 可集成 Maven/Java 项目，是测试工程师能真正上手跑起来的 MBT 工具。这正是课程选它做实战的原因。

它把"模型 = 图"这个抽象概念落成可执行文件：Studio（画图/Editor）→ CLI（生成/执行）→ Maven 插件（集成到 Java 项目）。三个形态覆盖了从"手动建模"到"CI 里自动跑"的完整链路。

【必须掌握】
- GraphWalker 三大形态：Editor（画图）/ CLI（命令行）/ Java 项目集成（Maven 插件）
- 定位：开源的 MBT 工具，Spec Explorer 的开源替代

【企业场景】
> 你想在团队里引入 MBT，但公司不给买 Visual Studio 的企业授权，Spec Explorer 用不起来。你用 GraphWalker 替代：Studio 画模型图，Maven 插件把模型集成进 Java 测试项目，最后挂到 Jenkins 里自动跑。零授权成本 + 开源可改，这就是企业选型时 GraphWalker 的现实意义。

【面试考察】
面试官："MBT 有什么能上手的开源工具？"
参考回答框架：
1. GraphWalker：开源 MBT 工具，跨平台 jar
2. 三个形态：Editor（画图）/ CLI（命令行生成与执行）/ Maven 插件（集成 Java 项目）
3. 与 Spec Explorer 对比：开源 vs 闭源、跨平台 vs 绑 VS、易上手 vs 门槛高
4. 一句话：它把"模型=图"落成可执行的工具链

【易错点】

## 五、GraphWalker 实战

### 知识点8：GraphWalker 核心概念（edge / vertex / model）

【课程原话/定义】
> An edge represents an action, a transition.（边代表一个动作、一次迁移）
> A vertex represents verification, an assertion.（顶点代表一次验证、一个断言）
> A model is a graph, which is a set of vertices and edges.（模型是一张图，是顶点和边的集合）

【为什么？】
这是 GraphWalker 世界观的最小单元，也是 MBT "状态/迁移"思想的可执行化：

- **vertex（顶点）= 状态**：在这里做"验证/断言"，确认系统当前状态对不对（比如断言"当前在登录页"）。
- **edge（边）= 动作**：执行一个操作，让系统从一个状态迁到另一个状态（比如"点击登录按钮"）。
- **model（模型）= 图**：一堆顶点 + 边的集合，外加一个起始元素（startElementId）。

测试用例 = 图上的一条**路径**（顶点和边交替的序列）。理解这三个词，才能读懂后面 JSON 里的 `vertices`、`edges`、`startElementId`——它们不是随便的字段，而是这个世界观的结构化表达。

【必须掌握】
- edge = 动作/迁移，vertex = 验证/断言，model = 图（顶点+边集合）
- 测试用例 = 图上的一条路径

【企业场景】
> 你把登录流程建模：三个顶点——「初始页」「已登录页」「登录失败页」，三条边——「输入正确密码」「输入错误密码」「点击登出」。跑测试时，工具沿着边在顶点间走，每到一个顶点就执行你绑定的断言。哪个断言挂了，就说明系统在这个"状态"上不符合预期——比"一条条写用例"更直观地定位到状态级的问题。

【面试考察】
面试官："GraphWalker 里 vertex 和 edge 分别代表什么？"
参考回答框架：
1. vertex = 验证/断言（系统状态检查点）
2. edge = 动作/迁移（驱动状态变化的操作）
3. model = 顶点+边的图，加一个起始元素
4. 用例 = 图上的路径（顶点与边交替）

【易错点】

| 概念 | 代表什么 | 在测试里做什么 |
|------|----------|----------------|
| vertex（顶点） | 状态 | 验证/断言：确认当前状态是否符合预期 |
| edge（边） | 动作/迁移 | 执行操作：驱动系统从一状态迁到另一状态 |
| model（模型） | 图 | 顶点+边的集合，外加起始元素（startElementId） |

【我的理解】
> （用自己的话：为什么"断言放在顶点、动作放在边"这个分工是合理的？如果把断言放在边上会有什么问题？）

### 知识点9：安装部署与工作流程

【课程原话/定义】
> GraphWalker 提供 `graphwalker-cli-4.3.1.jar`（命令行）、`graphwalker-studio-4.3.1.jar`（Studio 设计器）、graphwalker player（可视化播放器）。工作流程四步：① 创建模型 → ② 生成抽象测试套件 → ③ 映射可执行测试套件 → ④ 执行测试。启动 Studio 设计模型：`java -jar graphwalker-studio-4.3.1.jar`。

【为什么？】
这四步**完整复刻了知识点2 的"抽象测试套件 → 映射 → 可执行测试套件"理论**——前面是抽象概念，这里是落地的每一步：

1. Studio 里画的图 = 模型（抽象层）
2. CLI 的 generator 从图生成路径 = 抽象测试套件
3. Maven 插件把抽象路径映射成 Java 测试代码 = 可执行测试套件
4. `mvn test` 跑起来 = 执行测试

前后一对照，MBT 的全链路就串起来了：不是"先讲理论再讲工具"两套东西，而是同一套思想的"定义版"和"落地版"。

【必须掌握】
- 四步流程能默写：创建模型 → 生成抽象测试套件 → 映射可执行测试套件 → 执行测试
- 三个 jar 的用途：cli（命令行）/ studio（画图）/ player（可视化回放）
- 启动 Studio 命令：`java -jar graphwalker-studio-4.3.1.jar`

【企业场景】
> 你在本地跑通一条 MBT 用例的完整链路：先 `java -jar graphwalker-studio-4.3.1.jar` 打开 Studio 画登录模型并保存成 JSON；再用 Maven 插件生成测试源码；最后 `mvn test` 跑起来看到结果。这四步走一遍，你就拥有了一个"能写进简历、能被追问"的 MBT 动手成果。

【面试考察】
面试官："GraphWalker 的工作流程是怎样的？"
参考回答框架：
1. 四步：创建模型 → 生成抽象测试套件 → 映射可执行测试套件 → 执行测试
2. 每一步对应什么工具：Studio 画图 / CLI 生成 / Maven 插件映射 / mvn 执行
3. 点一句：这四步就是"抽象→映射→可执行"理论的工程落地

【易错点】

| ❌ 错误理解 | ✅ 正确理解 |
|------------|------------|
| 画完图就能直接跑测试 | 画图只是第①步，还要生成、映射、执行三步 |
| 三个 jar 是同一功能的三个版本 | cli 跑命令、studio 画图、player 可视化回放，职责不同 |
| 四步流程和知识点2 的理论是两回事 | 四步流程就是"抽象套件→映射→可执行套件"理论的落地版 |

【我的理解】
> （把 GraphWalker 四步流程的每一步，对应到知识点2 的"抽象测试套件 / 可执行测试套件 / 映射问题"，画一条对应线。）

### 知识点10：测试套件生成器算法（generator）

【课程原话/定义】
> 测试套件生成器算法分三类：
> - **路径覆盖**：`random(edge_coverage(100))` / `random(edge_coverage(50))`
> - **状态覆盖**：`random(vertex_coverage(100))` / `random(vertex_coverage(50))`
> - **达到特定状态**：`a_star(reached_vertex(v_VerifyFirstAction))` / `a_star(reached_edge(e_SomeAction))`

【为什么？】
这直接对应知识点5 的"测试需求包"——你选不同的 generator，就是在声明"这次测到什么程度"：

- `edge_coverage(100)`：覆盖所有边（所有迁移都走到），最全的路径覆盖；
- `edge_coverage(50)`：覆盖 50% 的边，用于快速冒烟；
- `vertex_coverage(100)`：覆盖所有顶点（所有状态都到达），但不保证每条边都走到；
- `a_star(reached_vertex(...))` / `a_star(reached_edge(...))`：定向寻路，只求"走到某个状态/某条边"，用于针对性验证。

括号里的 100 / 50 是覆盖率参数，直接回答"测试什么时候算测完"。`random` 表示随机游走、`a_star` 是最短路径寻路算法，两者是两种不同的生成策略。

【必须掌握】
- 三类 generator：路径覆盖（edge_coverage）、状态覆盖（vertex_coverage）、定向（a_star）
- 覆盖率参数含义：100 = 全覆盖，50 = 一半（冒烟）
- edge_coverage vs vertex_coverage 的区别

【企业场景】
> 你的订单模型有 20 个状态、40 条迁移。发版前只跑冒烟，你设 `random(edge_coverage(30))`——覆盖 30% 的边，几分钟跑完，堵住主路径；做完整回归设 `edge_coverage(100)`——所有迁移都走到，跑得久但覆盖全。某个线上 bug 复现时，你只关心"从待支付走到已退款"这条路径，就用 `a_star(reached_vertex(v_已退款))` 定向跑。三种 generator 对应三种测试节奏。

【面试考察】
面试官："edge_coverage(100) 和 vertex_coverage(100) 有什么区别？"
参考回答框架：
1. edge_coverage 按"边（迁移/动作）"计覆盖，100 = 所有迁移都走到
2. vertex_coverage 按"顶点（状态）"计覆盖，100 = 所有状态都到达
3. 区别：走到所有顶点 ≠ 走完所有边（有些边可能被跳过）；edge_coverage(100) 通常比 vertex_coverage(100) 更严格（因为路径覆盖了边必经过顶点）
4. a_star 是第三种：不追求覆盖，只求定向到达某个状态/边

【易错点】

| 生成器 | 覆盖对象 | 参数含义 | 典型用途 |
|--------|----------|----------|----------|
| random(edge_coverage(N)) | 边（动作/迁移） | 覆盖 N% 的边 | 路径覆盖/完整回归(N=100)、冒烟(N 小) |
| random(vertex_coverage(N)) | 顶点（状态） | 覆盖 N% 的顶点 | 状态覆盖/确保每个状态都到过 |
| a_star(reached_vertex/edge(X)) | 指定目标 | 定向走到 X | 复现 bug、验证特定路径 |

【我的理解】
> （为什么"覆盖了所有顶点"不等于"覆盖了所有边"？举一个只有 3 个顶点的小图，说明这种差异。）

### 知识点11：保存模型与生成可执行测试

【课程原话/定义】
> **保存模型**：模型以 JSON 保存，含 `models` 数组，每个模型有 `name`、`id`、`generator`、`vertices`（顶点，含 `x`/`y` 坐标）、`edges`（边，含 `sourceVertexId`/`targetVertexId`）、`startElementId`。
> **生成可执行测试**：`mvn archetype:generate -B`（graphwalker-maven-archetype）生成样本项目 → 把模型文件放到 `src/main/resources/.../xxx.json` → `mvn graphwalker:generate-sources` 生成测试源码 → `mvn graphwalker:test` 运行。
> **GraphWalker Player 可视化**：浏览器打开 `index.html?wsURI=127.0.0.1:8887`，代码里开启 websocket server（`new WebSocketServer(8887, executor.getMachine())`）。

【为什么？】
JSON 是模型的**可持久化形态**，几个字段各有含义：

- `vertices` 带 `x`/`y` 坐标——那是 Studio 画布上的位置，说明"图"里既存了拓扑也存了布局；
- `edges` 的 `sourceVertexId`/`targetVertexId`——图的拓扑结构（从哪个顶点迁到哪个顶点）；
- `generator` 内嵌在模型里——"用哪个算法生成测试"和模型绑定（知识点10 的算法在这里落成字段）；
- `startElementId`——起始元素，测试从哪个顶点/边出发。

Maven 插件是"映射问题"的**自动化解法**：`generate-sources` 把抽象路径映射成具体的 Java 测试方法。Player 用 websocket 让浏览器**实时看到机器人走到图上哪一步**——这是 MBT 的调试/演示利器，也是面试时能"亮出来"的东西。

【必须掌握】
- JSON 关键字段：vertices（含 x/y）、edges（sourceVertexId/targetVertexId）、startElementId、generator
- 三条 mvn 命令：archetype:generate（建项目）→ graphwalker:generate-sources（生成测试）→ graphwalker:test（运行）
- Player 通过 websocket（`new WebSocketServer(8887, ...)`）让浏览器可视化回放

【企业场景】
> 你要把 MBT 用例接入 CI：把画好的 JSON 模型提交到代码仓库，CI 里执行 `mvn graphwalker:generate-sources` 生成测试源码、再 `mvn test` 跑。为了给团队演示"测试到底怎么在图上走"，你启动 Player，用浏览器打开 websocket 地址，机器人每走一步都能看到它停在了哪个状态——这在测试评审里比一堆日志更有说服力。

【面试考察】
面试官："MBT 生成的测试怎么变成可执行的 Java 代码？"
参考回答框架：
1. 模型存成 JSON（含 vertices/edges/startElementId/generator）
2. Maven 插件：`archetype:generate` 建项目 → 放 JSON 到 resources → `graphwalker:generate-sources` 生成测试源码
3. `graphwalker:test` 执行
4. 这一步本质是"映射问题"的自动化解法

【易错点】

| 易混淆点 | 正确理解 |
|----------|----------|
| JSON 里 x/y 是测试逻辑 | 是 Studio 画布坐标（布局信息），拓扑靠 edges 的 source/targetVertexId |
| generator 是运行时才选的参数 | 内嵌在模型的 JSON 里，和模型绑定 |
| `generate-sources` 是执行测试 | 是"生成测试源码"；执行是 `graphwalker:test` |
| Player 只是看日志回放 | 通过 websocket 实时显示机器人当前所在状态，用于调试/演示 |

【我的理解】
> （从 JSON 里挑出 `generator` 和 `startElementId` 两个字段，分别说清它们"决定测试的什么"。）
