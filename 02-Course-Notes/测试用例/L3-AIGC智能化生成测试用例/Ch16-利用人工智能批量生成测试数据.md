## 一、测试数据为什么难搞

【课程原话/定义】
> 测试数据是软件测试过程中用于验证系统功能的数据集合。常见测试数据包括：用户数据、订单数据、交易数据、接口请求数据、边界值数据。测试数据通常用于：功能测试、接口测试、自动化测试、性能测试。测试数据直接影响：测试覆盖率、测试结果准确性、自动化测试执行效果。如果测试数据不足，可能导致：边界场景未被测试、异常情况无法验证、自动化测试无法稳定执行。传统生成测试数据的痛点：手工编写数据效率低、难以覆盖各种测试场景、大规模数据生成困难、数据格式复杂、自动化测试依赖大量数据。

【为什么？】
测试数据是测试工作的隐性成本大头，因为它存在一个"数量尴尬"：1 条不够（测不出边界和异常）、10 条太多（手工造累死人）、100 条造不动（大规模场景比如分页、性能压测，手工根本造不出来）。这个尴尬来自三个矛盾：**手工效率低**（一条条编）、**覆盖难**（边界值/异常值/特殊字符这些"故意造坏"的数据，手工会下意识漏）、**规模难**（性能测试要几万条，手工无解）。所以数据准备常常是"看得见、但没人愿意花时间做"的脏活累活，AI 恰恰是解这个的最佳工具。

【必须掌握】
- 测试数据定义：用于验证系统功能的数据集合
- 5 类常见数据：用户 / 订单 / 交易 / 接口请求 / 边界值
- 4 类用途：功能 / 接口 / 自动化 / 性能
- 数据不足的 3 个后果：边界未测 / 异常无法验证 / 自动化无法稳定执行
- 传统 5 痛点：效率低 / 难覆盖 / 大规模难 / 格式复杂 / 依赖量大

【企业场景】
> 你要测一个"用户列表分页"功能，需求是每页 20 条。只造 5 条数据，你永远测不出"翻到第 2 页"和"最后一页不足 20 条"的边界；手工造 100 条，光编手机号邮箱就耗掉半小时。更别说性能测试要 10 万条用户——手工造是天方夜谭。这就是"数据难搞"的真实写照：不是不会造，是造不动、造不全。

【面试考察】
> 面试官："测试数据怎么准备？有什么工具？"
参考回答框架：
1. 分类准备：功能测试手工造少量、接口/自动化用脚本或 AI 批量、性能测试用造数工具大规模生成
2. 工具：AI（ChatGPT 等）生成结构化数据、Python 脚本、数据库造数、Faker 等库
3. 关键点：数据要覆盖边界/异常/特殊字符，不是只造"正常值"
4. 配合校验：生成后要校验格式正确性（本节第三部分）

【易错点】

| ❌ 错误理解 | ✅ 正确理解 |
|------------|------------|
| 测试数据造几条正常值就够了 | 要覆盖边界/异常/特殊字符，只造正常值测不出问题 |
| 测试数据 = 测试用例 | 数据是测试的"输入"，用例是测试的"设计"，两者不同 |
| 性能测试数据手工慢慢造 | 大规模数据必须靠 AI/脚本/造数工具批量生成 |

【我的理解】
> （"1 条不够、10 条太多、100 条造不动"——以分页功能为例，说明这三个数量分别卡在哪个测试目标上。）

## 二、AI 批量生成测试数据的方法

【课程原话/定义】
> AI 在测试数据生成中的作用：自动生成测试数据、批量生成不同格式数据、生成边界数据、生成异常测试数据、快速构造复杂数据结构。典型场景：① 接口自动化（批量生成接口请求数据、构造不同参数组合）② 性能测试（大量用户/订单/交易记录）③ 边界与异常测试（最大/最小长度、特殊字符、非法输入）④ 自动化测试（用户账号、商品信息、地址信息）。示例提示词（节选）："你是一名资深的测试工程师。请生成 100 条用户测试数据，包含字段：用户ID、用户名、手机号、邮箱、注册时间。要求：1 手机号符合中国手机号格式 2 邮箱格式正确 3 数据格式为 JSON。"

【为什么？】
用 AI 生成数据最大的风险是"**看起来像真的 ≠ 测得出问题**"。AI 默认倾向于生成"正常、合理、规整"的数据——但它要测的场景恰恰是"极端值、脏数据、边界长度、重复值"这些"故意不正常"的数据。所以 prompt 必须显式要求：字段、格式（JSON）、数量、以及**校验规则**（手机号符合中国格式、邮箱正确）。更关键的是——AI 生成的数据要**再喂给校验程序**验一遍（本节第三部分），因为 AI 批量输出时经常"前几条合规、后几条就偷懒变格式"。总结一句：AI 能解决"规模和速度"，但"数据质量"要靠 prompt 约束 + 程序校验双重把关。

【必须掌握】
- AI 生成数据的 5 能力：自动生成 / 批量不同格式 / 边界数据 / 异常数据 / 复杂结构
- 4 个典型场景：接口自动化 / 性能测试 / 边界异常 / 自动化测试
- prompt 要点：字段 + 格式（JSON）+ 数量 + 校验规则（手机号/邮箱格式）
- 核心风险："看起来像真的" ≠ "测得出问题"，要主动造边界/异常/脏数据

【企业场景】
> 你要给接口自动化准备 100 条用户数据。prompt 里你明确写"100 条、JSON 格式、手机号符合中国格式、邮箱正确"。AI 秒出 100 条 JSON。但你没直接用——你注意到 AI 造的手机号全是"13800138000 递增"这种规整序列，缺了"非法手机号、空值、超长邮箱"这些异常数据。于是你补了一批异常/边界数据进去，再跑一遍校验脚本，才敢用于测试。

【面试考察】
> 面试官："你用 AI 生成过测试数据吗？"
参考回答框架：
1. 用过：prompt 里指定字段、格式、数量、校验规则，让 AI 批量出 JSON
2. 效果：规模（100/10000 条）和速度（秒级）远超手工
3. 局限：AI 偏向"正常规整"数据，边界/异常/脏数据要主动补
4. 把关：生成后跑校验脚本验格式，必要时人工补异常数据

【易错点】

| ❌ 错误理解 | ✅ 正确理解 |
|------------|------------|
| AI 生成的数据直接就能用 | 要再喂校验程序验格式，AI 批量输出常"后几条变格式" |
| AI 会主动造边界/异常数据 | AI 偏向"正常规整"，边界/脏数据要 prompt 显式要求或人工补 |
| "看起来像真的"数据就够测了 | 要的是"测得出问题"的极端/脏数据，两者不同 |

【我的理解】
> （AI 生成的一批"13800138000、13800138001…"这种规整数据，为什么不能直接拿去测？你会补哪些"故意不正常"的数据？）

## 三、数据的校验、清理与隔离

【课程原话/定义】
> 使用 AI 的注意事项：① 数据格式必须正确 ② 数据要符合业务规则 ③ 避免生成真实敏感数据 ④ 必要时进行自动校验。自动校验数据格式示例：用 Python 正则校验手机号（`^1[3-9]\d{9}$`）、邮箱（`^[\w\.-]+@[\w\.-]+\.\w+$`）、注册时间（`datetime.fromisoformat`），并逐条统计"总数据量 / 错误数据 / 有效数据"。

【为什么？】
"用完必须删"和数据隔离，比"生成"本身更重要，因为**测试环境数据污染会造成连锁误判**：脏数据混在库里，会让下次回归的断言莫名失败、让开发误以为有 bug、让性能测试的基线失真。同样重要的还有"避免生成真实敏感数据"——AI 如果生成了一批"真实手机号/真实身份证"，一旦进了测试库又同步到生产或日志，就是隐私泄露事故。所以数据治理是"质量（校验）+ 卫生（清理隔离）"一体两面：**校验保证数据"能用"，清理隔离保证数据"不害人"**。这也是为什么注意事项里既有"格式正确"又有"避免敏感数据"。

【必须掌握】
- 4 条注意事项：格式正确 / 符合业务规则 / 避免真实敏感数据 / 必要时自动校验
- 自动校验思路：正则验手机号/邮箱、类型验时间，逐条统计错误率
- 数据治理两面：校验（质量，保证能用）+ 清理隔离（卫生，保证不害人）
- 数据污染后果：回归误判、基线失真、隐私泄露

【企业场景】
> 你用 AI 批量造了 1 万条用户数据灌进测试库。测完必须清库——不然下次回归时，这 1 万条脏数据会让"用户列表总数"断言莫名其妙失败，开发还跑来问你"是不是又出新 bug 了"。另外你在 prompt 里特意要求"手机号用 138 开头的虚拟号段，不要用真实号段"，避免生成的"真实号码"泄露隐私。这两件事，比"生成 1 万条"本身更考验一个测试工程师的素养。

【面试考察】
> 面试官："批量造的测试数据怎么管理？会不会污染环境？"
参考回答框架：
1. 两条线：质量（校验）+ 卫生（清理隔离）
2. 质量：生成后用正则/脚本自动校验格式，统计错误率
3. 卫生：用完清库/隔离在独立测试库，避免脏数据污染回归和基线
4. 安全：避免生成真实敏感数据，用虚拟号段/脱敏数据
5. 结论：生成是手段，治理才是重点

【易错点】

| ❌ 错误理解 | ✅ 正确理解 |
|------------|------------|
| 造完数据灌进去就完事 | 用完必须清库/隔离，否则污染环境导致回归误判 |
| 让 AI 生成"看起来真实"的手机号身份证 | 要避免真实敏感数据，用虚拟号段 + 脱敏 |
| 生成完不校验直接用 | 要跑正则/脚本自动校验格式，统计错误数据 |

【我的理解】
> （"校验保证数据能用，清理隔离保证数据不害人"——这两句话各对应什么具体动作？为什么后者比"生成"本身更重要？）
