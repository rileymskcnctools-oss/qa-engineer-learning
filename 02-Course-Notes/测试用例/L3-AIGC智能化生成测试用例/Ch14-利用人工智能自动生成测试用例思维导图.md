## 一、思维导图与用例表格的定位差异

【课程原话/定义】
> 测试用例思维导图是一种结构化的测试设计方法。思维导图在测试中的价值：梳理系统功能结构、拆解测试模块、提高测试覆盖率、避免遗漏测试场景、提升测试设计效率。因此在很多测试团队中，思维导图是测试设计的重要工具。

【为什么？】
思维导图管"**设计评审不遗漏**"，表格管"**执行记录可追溯**"。导图是"树"，从根（功能）一层层拆到叶（测试点/子场景），评审会上大家一眼就能看出"这个功能拆全了没、哪个分支没拆到"——它回答的是"**我考虑了哪些场景**"。表格是"清单"，每行一条可执行用例（前置条件、步骤、预期结果）——它回答的是"**这条具体怎么测、测了没**"。AI 生成导图的核心价值在"设计"这一层：快速把需求拆成结构化测试点树，供人评审和查漏，而不是直接产出可执行用例。

【必须掌握】
- 导图 = 结构化测试点树（评审用），表格 = 可执行用例清单（执行用）
- 导图 5 价值：梳理结构 / 拆模块 / 提覆盖率 / 避免遗漏 / 提效率
- 评审会优先看导图的原因：一眼看清覆盖度，方便查漏补缺

【企业场景】
> 你负责"用户登录"的用例设计。先用 AI 生成一张思维导图：根节点"用户登录"，下面分"功能模块 / 测试场景 / 异常场景 / 边界场景"四大枝，每枝再拆叶子（用户名输入、密码输入、登录成功响应、错误密码提示、用户名为空……）。你把这张图拿到评审会上，产品和开发一眼就能看出"边界场景里漏了用户名最大长度""异常场景漏了数据库连接失败"，当场补上。这就是导图"防遗漏"的价值。

【面试考察】
> 面试官："为什么要先出思维导图，不能直接生成用例表格吗？"
参考回答框架：
1. 导图管"设计不遗漏"（树结构看覆盖），表格管"执行可追溯"（清单看结果）
2. 评审会上导图一眼看出哪个分支没拆到，表格做不到
3. 正确顺序：导图评审通过 → 再转可执行用例表
4. 一句话：先确保"想全了"，再确保"能执行"

【易错点】

| ❌ 错误理解 | ✅ 正确理解 |
|------------|------------|
| 思维导图就是"AI 生成的草稿" | 导图是"结构化测试点树"，用于设计评审与查漏，不是废草稿 |
| 有导图就不用写用例表格了 | 导图管"想全没想全"，表格管"具体怎么测"，两者都要 |
| 导图越细越好，拆到叶子就完事 | 导图拆到"测试点"层即可，再往下是可执行用例（交给表格） |

【我的理解】
> （一句话说清：思维导图和用例表格各自回答什么问题？为什么评审会看导图、执行看表格？）

## 二、AI 生成思维导图的方法

【课程原话/定义】
> AI 在测试思维导图中的作用：自动分析需求、自动拆解功能模块、自动生成测试点、自动生成思维导图结构、自动补充异常场景。示例提示词（节选）："你是一名经验丰富的软件测试工程师。请根据以下需求生成测试思维导图结构……请输出：1 功能模块 2 测试场景 3 异常场景 4 边界场景。请以 plantuml 思维导图结构输出。"

【为什么？】
AI 生成导图时，提示词必须交代清楚三件事：**角色**（测试工程师视角）、**需求原文**、**输出结构**（要拆成哪几类）。而"功能模块 → 测试场景 → 异常场景 → 边界场景"这个分类之所以是固定的，是因为它对应了黑盒测试设计的基本盘：功能模块（正常路径拆解）、测试场景（正常/异常分支）、异常场景（系统级错误）、边界场景（等价类边界值思想）。四类合起来，正好覆盖了"正常流 + 异常流 + 边界"的完整测试面——少了任何一类都会漏测。要求 AI 输出 plantuml，是为了让结果能直接渲染成图。

【必须掌握】
- AI 生成导图的 5 能力：分析需求 / 拆模块 / 生成测试点 / 生成结构 / 补异常场景
- 四类输出结构：功能模块 / 测试场景 / 异常场景 / 边界场景
- 为什么是这四类：对应"正常流 + 异常流 + 边界"的完整测试面
- plantuml 语法：`@startmindmap` / `@endmindmap`，`*` 数量表示层级

【企业场景】
> 你让 AI 给"用户登录"生成测试导图，prompt 里明确要求输出"功能模块 / 测试场景 / 异常场景 / 边界场景"四类，并指定用 plantuml。AI 输出一棵四枝的树：测试场景下拆出"正确用户名密码→登录成功、错误用户名→失败提示……"，边界场景下拆出"用户名最大/最小长度、密码最大/最小长度"。你拿到 plantuml 代码，粘贴到支持 PlantUML 的工具里就渲染成一张可评审的图。

【面试考察】
> 面试官："你用 AI 生成过测试导图吗？效果如何？"
参考回答框架：
1. 用过：让 AI 按"功能/测试场景/异常/边界"四类输出 plantuml 导图
2. 效果：功能拆解和正常/异常场景覆盖快，节省手工拆解时间
3. 局限：业务特有的坑（并发、降级、权限）仍需人工补
4. 结论：AI 出骨架，人做查漏补缺

【易错点】

| ❌ 错误理解 | ✅ 正确理解 |
|------------|------------|
| 让 AI 随便生成导图，不指定分类 | 必须指定"功能/测试场景/异常/边界"四类，否则结构散、易漏测 |
| plantuml 的 `*` 只是格式符号 | `*` 数量表示层级，是导图"树"的深度 |
| AI 生成的导图直接交评审 | 还要人工补业务特有的异常/边界/权限场景 |

【我的理解】
> （为什么 prompt 里要写死"功能模块 / 测试场景 / 异常场景 / 边界场景"这四类？如果漏掉"边界场景"，你会漏掉哪类测试？）

## 三、导图格式与导出

【课程原话/定义】
> 示例中 AI 以 plantuml 语法输出思维导图（`@startmindmap` … `@endmindmap`），并说明：将代码复制到支持 PlantUML 的工具中进行可视化展示。

【为什么？】
导图生成后要能"落地"成可用的格式，格式决定了它能不能继续流转。plantuml 是"文本即图"的中间格式——好处是可版本管理、可被 AI 直接生成、可渲染成图片；但它不能直接转成用例表格。要转成可执行用例，得把导图的"叶子测试点"进一步展开成"前置条件 + 步骤 + 预期结果"的表格（这就是 Ch15 干的活）。其他常见落地格式：Markdown 列表（可直接转 xmind/OPML）、xmind 原文件（团队评审常用）。核心思路是：**导图是中间产物，格式选对才能顺畅流转到下一步**。

【必须掌握】
- plantuml 是"文本即图"的中间格式，AI 可直接生成、可渲染、可版本管理
- 导图 → 用例表：要把叶子测试点展开成"前置条件+步骤+预期结果"
- 常见落地格式：plantuml / Markdown / xmind / OPML

【企业场景】
> AI 给你生成了登录功能的 plantuml 导图代码。你把它粘贴到支持 PlantUML 的工具（如 VS Code 插件、在线渲染）里出一张图，发到群里评审。评审通过后，你拿着导图里的叶子测试点（如"用户名最大长度"），去 Ch15 的 AI 流程里把这些点逐一展开成带步骤和预期结果的可执行用例表。导图是"想全"，用例表是"能测"。

【面试考察】
> 面试官："AI 生成的导图你怎么转成可执行的用例？"
参考回答框架：
1. 导图先渲染成图评审（plantuml / xmind）
2. 评审通过后，取叶子测试点
3. 每个测试点展开成"前置条件 + 测试步骤 + 预期结果"
4. 落到用例表格，进入可执行状态

【易错点】

| ❌ 错误理解 | ✅ 正确理解 |
|------------|------------|
| 导图能直接当用例表格用 | 导图是"测试点树"，要展开成带步骤/预期结果的表格才能执行 |
| 导图格式无所谓，能看就行 | 格式决定流转：plantuml/Markdown 可版本化，xmind 便于团队评审 |
| plantuml 只是 AI 随便选的格式 | plantuml 是"文本即图"的中间格式，AI 能直接生成、可渲染 |

【我的理解】
> （导图里的一个叶子测试点"用户名最大长度"，要变成可执行用例，还需要补上哪几样东西？）

## 四、导图的漏测检查

【课程原话/定义】
> 示例中 AI 生成的登录功能导图，四类下包含：测试场景（正确/错误用户名、正确/错误密码、用户名为空、密码为空）、异常场景（用户名格式不正确、密码格式不正确、数据库连接失败、服务器错误、登录请求超时）、边界场景（用户名/密码最大、最小长度）。

【为什么？】
怎么判断 AI 生成的导图有没有漏测点？人工 review 时按四根检查线逐条过：**正常流**（主流程能不能走通）、**异常流**（系统级错误：数据库挂了、服务器错、超时）、**边界**（字段最大/最小长度、特殊字符）、**权限**（不同角色能看到什么、能不能越权）。AI 最容易漏的是"权限"和"业务特有的异常"（比如登录失败 N 次锁定账户），因为这两类需要业务知识，AI 从需求文本里读不出来。review 的核心不是看格式，是"**对照这四根线，找 AI 没拆到的分支**"。

【必须掌握】
- 四条 review 检查线：正常流 / 异常流 / 边界 / 权限
- AI 最易漏：权限类 + 业务特有异常（如连续失败锁定）
- review 目的：对照四根线找 AI 没拆到的分支，不是改格式

【企业场景】
> 你 review AI 生成的登录导图，发现它拆得很全，但"异常场景"里只有"数据库连接失败、服务器错误、超时"，没有"连续 5 次登录失败锁定账户"这条（这是业务规则，需求文档里没写）。你在导图上补了这一枝。这就是人工 review 导图的价值——AI 拆显式的，你补隐式的业务规则和权限场景。

【面试考察】
> 面试官："AI 生成的测试导图你会怎么 review？"
参考回答框架：
1. 按四根线对照：正常流 / 异常流 / 边界 / 权限
2. 重点找 AI 漏的分支：权限类、业务特有异常（锁定、降级、并发）
3. 补上后重新评审
4. 结论：AI 拆显式场景，人补隐式业务规则

【易错点】

| ❌ 错误理解 | ✅ 正确理解 |
|------------|------------|
| review 导图 = 改格式、调措辞 | review 的核心是"对照四根线找漏测分支" |
| AI 拆得全就不用 review 了 | 权限类和业务特有异常，AI 读不出来，必须人补 |
| 只看"场景数量多不多" | 要看"四根线有没有覆盖全"，数量多 ≠ 覆盖全 |

【我的理解】
> （review AI 生成的登录导图，你会在哪根检查线上补一个 AI 大概率漏掉的测试点？具体补什么？）
