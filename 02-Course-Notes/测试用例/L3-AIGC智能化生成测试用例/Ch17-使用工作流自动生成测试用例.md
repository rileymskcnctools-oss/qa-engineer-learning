## 一、从人工调用到工作流编排

【课程原话/定义】
> AI 工作流（AI Workflow）是一种通过多个步骤自动完成任务的流程，典型步骤包括：输入数据、AI 解析、数据处理、结果生成。通过工作流，可以将复杂任务拆解为多个自动化步骤。Dify 是一个开源的 LLM 应用开发平台，提供可视化 AI 工作流、知识库管理、Prompt 管理、API 集成。

【为什么？】
前面 Ch10-Ch16 是"人调 AI"：需求分析、写计划、写用例……每一步都要人重新写一次提示词、复制粘贴一次结果。工作流把这几步串成一条流水线，效率倍增的原因在于**瓶颈从"人"转移到"流程"**：手动做时瓶颈是"人每次都要重新组织提示词、搬运上一步的输出"；工作流做时瓶颈是"节点间的数据传参"。提示词写 6 次 → 变成"写好一次、传参调 6 次"。但代价是：一旦流程固定，就失去了单次调用时的灵活性——这正是它和智能体（下一节）的分界点。

【必须掌握】
- AI 工作流 = 把复杂任务拆成多个自动化步骤串起来
- 工作流四步：输入数据 → AI 解析 → 数据处理 → 结果生成
- 效率倍增的本质：从"提示词写 6 次"变成"写好一次、传参调 6 次"
- Dify 定位：开源 LLM 应用平台（可视化工作流 / 知识库 / Prompt 管理 / API 集成）

【企业场景】
> 你把"需求分析 → 测试点生成 → 用例生成"三步在 Dify 里连成一条工作流：开始节点输入需求，节点一分析需求出 JSON，节点二按 JSON 生成测试点列表，节点三按测试点生成用例表，结束节点输出。以后任何人只要在入口贴一段需求，几秒就能得到一份完整用例，不再需要每次都重新写三段提示词。这就是"从人工调用到工作流编排"的提效。

【面试考察】
> 面试官："你说用工作流做自动化用例生成，具体是怎么串的？"
参考回答框架：
1. 用 Dify 搭建工作流：开始节点 → LLM 需求分析 → LLM 测试点生成 → LLM 用例生成 → 结束节点
2. 每个节点用结构化输出（JSON/列表/Markdown 表格）衔接下一节点
3. 入口只需贴需求，自动产出用例表
4. 提效点：提示词写一次，传参调多次

【易错点】

| ❌ 错误理解 | ✅ 正确理解 |
|------------|------------|
| 工作流 = 把多个提示词拼一起 | 工作流关键是"节点间数据传参"，上一步输出喂下一步输入 |
| 工作流和智能体是一回事 | 工作流步骤人写死，智能体步骤 AI 自决（下一节） |
| 工作流建好就一劳永逸 | 需求一变，节点提示词要跟着维护，见本节第三部分 |

【我的理解】
> （手动调 6 次 AI vs 用工作流跑 6 个节点，瓶颈分别卡在哪？为什么工作流能效率倍增？）

## 二、工作流的节点划分

【课程原话/定义】
> Dify 工作流节点示例：输入节点 → LLM 节点（需求分析）→ LLM 节点（测试点生成）→ LLM 节点（测试用例生成）→ 输出节点。节点一输出 JSON（`{"功能":"","业务流程":[],"输入":[],"输出":[],"异常场景":[]}`），节点二输出列表（`[{"类型":"功能","测试点":""}]`），节点三输出 Markdown 表格（`| 用例标题 | 前置条件 | 测试步骤 | 预期结果 |`）。

【为什么？】
工作流设计的成败在"**节点切得对不对**"，不在"提示词写得好不好"。原因是：每个节点的输出必须能被下一个节点"结构化地吃掉"——如果节点一输出一段自然语言长文，节点二就很难稳定地从里面提取测试点；而如果节点一输出固定字段的 JSON，节点二就能精准取到"业务流程""异常场景"这些字段。所以正确切法是一个节点只干一件事、输出一种结构化格式（JSON/列表/表格），节点之间靠"字段"衔接，而不是靠"重新阅读理解"。

【必须掌握】
- 节点划分原则：一个节点只干一件事，输出一种结构化格式
- 节点衔接靠"字段"而非"重新阅读理解"
- 三段式切分：需求分析（JSON）→ 测试点生成（列表）→ 用例生成（表格）

【企业场景】
> 你在 Dify 里搭登录用例工作流时，节点一切成"需求分析"并强制输出 JSON（功能/业务流程/输入/输出/异常场景五个字段），节点二"测试点生成"直接引用节点一的 JSON 字段生成测试点列表，节点三"用例生成"再引用测试点列表生成 Markdown 表格。每个节点只做一件事、输出一种格式，链条清晰，哪个节点出错也能单独定位。

【面试考察】
> 面试官："工作流某个节点失败了怎么办？"
参考回答框架：
1. 先定位是哪个节点失败（工作流可单独查看每个节点的输入/输出）
2. 检查该节点的输入是否拿到上一步的结构化字段（字段名对不对、格式对不对）
3. 检查该节点的输出格式是否符合下游预期
4. 修复后单节点重跑，不必重跑整条链路

【易错点】

| ❌ 错误理解 | ✅ 正确理解 |
|------------|------------|
| 节点越多越细越好 | 节点切分以"一件事 + 一种结构化输出"为准，过细反而难维护 |
| 节点间传自然语言就行 | 必须传结构化字段（JSON/列表/表格），否则下游拿不稳 |
| 失败就整条重跑 | 定位到单节点重跑，工作流支持逐节点查看输入输出 |

【我的理解】
> （节点一输出"自然语言长文"和输出"固定字段 JSON"，对节点二有什么不同影响？为什么结构化输出是工作流的命脉？）

## 三、工作流的可复用性与维护成本

【课程原话/定义】
> 使用 Dify 的优势：可视化流程设计、快速搭建 AI 工具、支持多模型、易于扩展。

【为什么？】
工作流跑通了不等于能长期用下去。需求一变，工作流最容易崩的地方是**提示词里硬编码的业务规则**——比如节点一的分析 prompt 里写死了"提取功能/业务流程/输入/输出/异常场景"，某天需求新增了"权限场景"这个维度，这条 prompt 就得改，改完还要回归验证整条链路。所以可复用性的关键在"**参数化 vs 硬编码**"：把会变的业务要求抽成可配置的输入（比如把"输出维度"做成开始节点的选项），把不变的结构（三段式流程）固定下来。维护成本的高低的本质，是"当初把多少可变的东西写死进了提示词"。

【必须掌握】
- 工作流易崩点：提示词里硬编码的业务规则
- 可复用性关键：参数化（可变项抽成配置）vs 硬编码（写死进提示词）
- 维护成本的本质：当初写死了多少可变的东西

【企业场景】
> 你的登录用例工作流跑了两个月，需求突然新增"要覆盖权限场景（不同角色看到不同功能）"。你发现节点一的 prompt 里把输出维度写死成了"功能/业务流程/输入/输出/异常场景"五个字段，得改 prompt 加一个"权限场景"，改完还要重跑几十条用例回归。吃一堑后，你把"输出维度"抽成了开始节点的一个配置项，以后再新增维度只需改配置，不用动 prompt。

【面试考察】
> 面试官："这个工作流你怎么保证它一直有效？"
参考回答框架：
1. 把会变的业务要求抽成参数/配置，不写死进提示词
2. 需求变更时改配置 + 回归验证，而非重写整条链路
3. 定期用新需求样例回归，发现漂移及时修
4. 结论：可复用性的关键是"参数化"，维护成本取决于"写死了多少"

【易错点】

| ❌ 错误理解 | ✅ 正确理解 |
|------------|------------|
| 工作流跑通 = 永久有效 | 需求一变就可能崩，要持续维护 + 回归 |
| 业务规则写死进提示词没关系 | 写死的可变项越多，维护成本越高，应抽成参数 |
| 改需求就重搭一条工作流 | 参数化设计下，改配置 + 回归即可，不必重搭 |

【我的理解】
> （你的用例工作流里，"输出维度"（功能/异常/边界…）应该写成"参数"还是"写死进 prompt"？为什么？）
