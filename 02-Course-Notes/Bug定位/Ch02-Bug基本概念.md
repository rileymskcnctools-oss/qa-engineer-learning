## 一、Bug 的定义

### 知识点1：什么是 Bug

【课程原话/定义】
Bug 就是一个电脑程序里的错误。早期计算机是大型机器，有一天机器出故障，排查发现是虫子爬进主机内部引起短路导致故障。所以后来大家把程序故障统称为 Bug。

【为什么？】
这个故事不只是有趣——它揭示了 Bug 的本质：**任何导致程序不按预期运行的因素，都叫 Bug。** 虫子钻进机器是物理 Bug，代码写错是逻辑 Bug，需求理解错是设计 Bug。Bug 的来源可以是代码、需求、环境、数据——不限于程序员的编码错误。

【必须掌握】
- Bug = 程序不按预期运行的任何现象
- Bug 来源不限于代码：需求、设计、环境、数据都可以是 Bug 的来源
- Bug 词源：物理虫子 → 泛指所有程序故障

【企业场景】
> 生产环境突然报 500 错误，你第一反应是"开发改了什么代码"。排查后发现是运维改了数据库配置，代码完全没问题。这个"配置错误"就是 Bug。Bug 不一定是代码写错了——谁改了什么导致系统不正常，谁就引入了 Bug。

【易错点】

| 常见误解        | 正确理解                                  |
| ----------- | ------------------------------------- |
| Bug = 代码写错了 | Bug = 实际结果 ≠ 预期结果，原因可以是代码/需求/配置/数据/环境 |
| Bug 是开发的事   | 测试负责发现和报告，开发负责修复，PM 负责判定              |

### 知识点2：Bug 和缺陷的区别

【课程原话/定义】
严谨地说，Bug 和缺陷还是有区别的。一般来说 Bug 是现象，而缺陷是引起这些现象的原因。比如说因为程序中存在缺陷，所以才出现了 Bug。不过在实际工作当中不会这么严格区分，更多用 Bug 来统称软件设计问题和故障。

【为什么？】
这个区分在理论上成立但在实践中模糊。理解它的意义不在于"用对词"，而在于理解**Bug 分析的两个层次**：
- **现象层**（Bug）：用户看到了什么？（支付金额显示错误）
- **原因层**（缺陷）：代码里哪里出了问题？（汇率换算函数用了错误的精度类型）

实际工作中说"提 Bug"而不说"提缺陷"，但当你写 Bug 报告时，好的报告既描述现象也推测原因。

【必须掌握】
- Bug = 现象（用户看到的错误），缺陷 = 原因（代码/设计里的错）
- 工作日常：统称 Bug，不做严格区分
- 面试时：能说出两者的理论区别 + 补充"实际工作中不区分"

## 二、Bug 判定标准

### 知识点3：4 条判定标准

【课程原话/定义】
只要符合以下标准之一，就可以断定是 Bug：
1. 软件未达到客户需求文档的功能和性能
2. 软件出现客户需求不能容忍的错误
3. 软件的使用未能符合客户的习惯和工作环境
4. 软件超出需求文档的范围

【为什么？**
这 4 条标准从严格到宽松层层递进，覆盖了不同类型的 Bug：

- 标准 1 是最硬的依据：PRD 写了 → 没做到 → Bug。没争议。
- 标准 2 是兜底条款：PRD 没写但后果严重 → 也是 Bug。比如没写"支付金额不能为负"，但你输入负数系统崩了——这算 Bug。
- 标准 3 是体验类 Bug：PRD 没要求但用户体验极差。比如删除按钮和无障碍操作冲突。
- 标准 4 是范围溢出：开发自作主张加的功能，哪怕功能本身没问题，也算 Bug（因为没有需求依据）。

【必须掌握】
- 能默写 4 条标准
- 理解 4 条的优先级：标准 1 > 标准 2 > 标准 3 > 标准 4
- 面试核心："需求文档没写清楚能不能提 Bug？"——能，用标准 2 或 3。

【企业场景】
> 你测一个表单，发现"提交"按钮在页面最底部，用户要滚动 3 屏才能看到。需求文档没写按钮位置。你能提 Bug 吗？——能。用标准 3："软件的使用未能符合客户的习惯和工作环境"。正常用户预期提交按钮在可视范围内，这就是体验 Bug。

【面试考察】
面试官问："如果需求文档没写某个功能的具体表现，你测出来觉得不合理，能提 Bug 吗？"
参考回答：能，但要区分情况：
- 如果是严重影响使用的（标准 2：客户不能容忍的错误）→ 提 Bug，拉 PM 确认
- 如果是体验问题（标准 3：不符合使用习惯）→ 提建议类 Bug，让 PM 判断优先级
- 如果是你自己不确定的场景 → 先沟通再提，不要凭感觉

【易错点】

| 常见错误 | 正确做法 |
|----------|----------|
| "PRD 没写 = 不是 Bug" | PRD 没写但后果严重（标准2）或体验差（标准3）照样提 |
| "我看起来不对 = Bug" | 需要客观依据：PRD/竞品/行业惯例/用户反馈 |
| 超出需求范围的一定是好事 | 开发自行加的功能也可能引入安全隐患或和已有功能冲突 |

## 三、经典面试题：开发说不是 Bug

### 知识点4：开发不认 Bug 怎么办

【课程原话/定义】
这个问题考察的是对 Bug 有没有自己的判断，以及工作中的软实力——处理问题的思路。

【为什么？**
这道题几乎必考，因为它能同时考察：
- 你的专业判断力（能不能区分真 Bug 和误报）
- 你的沟通能力（能不能有理有据地说服别人）
- 你的情绪管理（不因为开发一句话就上头或退缩）

【必须掌握】4 种场景 + 对应策略：

| 场景       | 根因             | 你的策略                          |
| -------- | -------------- | ----------------------------- |
| 描述不清晰    | 开发没看懂你的 Bug 报告 | 提高自己：补充复现步骤、截图、log、环境信息       |
| 难以复现     | 偶发 Bug，开发重现不了  | 保留证据：录屏、抓 log、记录触发条件和频率       |
| 有争议（建议类） | 你说要改，开发觉得没必要   | 升级决策：拉 PM/PO 一起开会讨论，看需求优先级    |
| 需求理解不一致  | 你和开发对 PRD 理解不同 | 拿证据：截图 PRD 原文 + 设计文档 + 需求评审记录 |

【企业场景】
> 你提了一个 Bug："用户不登录就能看到支付页面，应该拦截"。开发回复："需求没说要拦截，不是 Bug"。你翻出 PRD 安全需求章节，截图回复："PRD 第 3.2 节明确要求'支付功能需要登录态校验'"。开发说——"哦，漏了，我加个中间件。"

> 关键：Bug 争论的唯一裁判是需求文档。没有文档 → 找 PM 确认。别陷入"我觉得 vs 你觉得"。

【面试考察】
面试官问："开发认为你提交的 Bug 不是 Bug，你怎么办？"
参考回答框架：
1. 先自查：我的 Bug 描述清楚吗？复现步骤完整吗？有截图/log 吗？
2. 再沟通：和开发当面聊，了解他为什么认为不是 Bug（理解不一致？还是需求不明确？）
3. 找依据：翻 PRD、设计文档、需求评审记录——用文档说话
4. 升级：僵持不下 → 拉 PM 拍板。PM 说不是 Bug → 关闭，更新需求说明

【我的理解】

## 四、Bug 严重程度

### 知识点5：4 级严重程度

【课程原话/定义】
严重程度的判断应从软件最终用户的观点出发，考虑缺陷对用户使用造成的恶劣后果。

| 等级     | 定义                 | 典型例子                         |
| ------ | ------------------ | ---------------------------- |
| **致命** | 系统停止运行、崩溃、关键部件无法运行 | 支付后订单未生成；登录后直接 500；数据丢失      |
| **严重** | 严重影响基本功能，且没有变通办法   | 主要功能无法使用但系统未崩溃；搜索结果为空但数据库有数据 |
| **一般** | 功能可用但有限影响          | 响应变慢；中间结果错误但不影响最终结果；非核心功能异常  |
| **建议** | 不影响功能但体验不佳         | 界面拼写错误；按钮位置不合理；提示文案不友好       |

【为什么？**
严重程度从"用户能不能用"这个角度分级——这是用户视角，不是开发视角。比如"首页 Logo 加载失败"技术上是个小问题，但如果首页是电商入口，用户第一眼看到破图就关掉——用户视角这就是严重问题。

严重程度不是主观感觉，要基于两个维度判断：
1. **影响范围**：影响所有用户还是极少数用户？
2. **是否有变通办法**：用户能不能绕过这个问题继续使用？

【必须掌握】
- 4 级名称和定义能默写
- 判断依据：影响范围 + 是否有变通办法
- 面试必考：给场景判断严重程度

【面试考察】
面试官问："用户注册页面，验证码刷新按钮偶尔点击无反应（概率约 5%），严重程度定几级？"
参考回答：定"一般"。原因：① 用户可刷新页面绕过（有变通办法）；② 不影响已登录用户（影响范围有限）；③ 概率 5% 不是必现。但如果验证码完全无法刷新导致无法注册 → 定"严重"。

【易错点】

| 容易混淆 | 致命 | 严重 |
|----------|------|------|
| 系统状态 | 崩溃/停止运行 | 能运行但核心功能坏了 |
| 举例 | 支付后系统 500 | 能打开支付页但无法选择支付方式 |
| 是否有变通办法 | 通常没有 | 有时有（重启/换浏览器） |

## 五、Bug 优先级

### 知识点6：优先级定义

【课程原话/定义】
优先级是表示处理和修正软件缺陷的先后顺序的指标，即哪些缺陷需要优先修正，哪些缺陷可以稍后修正。

【为什么？**
优先级 ≠ 严重程度。严重程度回答"这个 Bug 有多严重"，优先级回答"这个 Bug 应该什么时候修"。

优先级是谁定的？——不是测试，是 PM/PO 定的。因为优先级涉及"这个功能和那个功能哪个更急"，这是业务决策，不是技术决策。

【必须掌握】
- 优先级 = 修复顺序
- 决定者：PM/PO（不是测试）
- 常见划分：P0（立刻修）、P1（本迭代）、P2（下迭代）、P3（backlog）

### 知识点7：严重程度 vs 优先级的关系

【课程原话/定义】
- 一般地，严重程度高的 Bug 具有较高优先级
- 有时候严重程度高的 Bug，优先级不一定高，甚至不需要处理
- 有时候严重程度低的 Bug 却需要及时处理，具有较高优先级

【为什么？**
这是面试中最容易被追问的点。核心理解：**严重程度是技术判断，优先级是业务判断。**

经典反例：
- 严重高 + 优先级低：用户协议页面第 37 页第 3 段有个错别字，严格说是 Bug——但实际上几乎没人会看到。Severity=建议，Priority=P3。
- 严重低 + 优先级高：首页 Banner 上 CEO 的名字拼错了。技术上是"建议"级（不影响功能），但业务上必须立刻修——因为影响公司形象。Severity=建议，Priority=P0。

【必须掌握】
- 一句话金句（面试必背）：**"Severity 高 Priority 不一定高。一个严重影响用户体验但只出现在特定机型上的 Bug，Severity 高但 Priority 可能低。反之，一个文案错误出现在首页，Severity 低但 Priority 高。"**
- 判断 Priority 的核心：影响范围 × 业务重要度

【企业场景】
> 双十一前夜，你发现一个 Bug：订单列表的排序在某些条件下会乱。功能上属于"一般"（中间结果出错但不影响下单和支付）。但 PM 在群里说"P0 立刻修"——因为 12 小时后百万用户涌入，订单列表是最高频访问的页面。Severity=一般，Priority=P0。

【面试考察】
面试官问："什么时候 Severity 高但 Priority 低？什么时候反过来？"
参考回答：
- Severity 高 Priority 低：只在极罕见条件下触发的严重 Bug（如特定型号手机+特定系统版本才崩溃），影响面极小
- Severity 低 Priority 高：影响面大的体验问题（首页文案错误、CEO 名字写错、品牌 Logo 错误）
