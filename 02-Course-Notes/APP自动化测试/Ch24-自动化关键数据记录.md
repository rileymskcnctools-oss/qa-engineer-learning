# Ch24 - 自动化关键数据记录

## 课程来源
- 学习日期：

> 本章是工程化的第一块地基：**失败留证**。日志、截图、页面源码三件套，是"用例挂了之后能快速定位根因"的关键——没有它们，自动化跑出来的失败就只是一句"assert 失败"，无法追溯当时页面长什么样。

---

## 一、关键数据是什么

### 知识点 1：日志 / 截图 / 页面源码三件套

【课程原话/定义】

关键性数据：测试执行期间用于判断测试成功或失败的重要信息，通常是测试过程中获取的——日志信息、截图、页面源码等。

使用场景：帮助脚本发现问题后，辅助分析错误原因，更快定位和解决问题。

【为什么？】

1. 自动化用例失败时，光看"assert False"根本不知道当时页面处于什么状态、元素为什么没找到——关键数据就是"案发现场的照片和笔录"。
2. 日志回答"执行到哪一步、发生了什么"；截图回答"当时页面长什么样"；page_source 回答"当时 DOM/控件树里有什么"。
3. 三者配合才能从"知道失败了"推进到"知道为什么失败"——这是失败留证的完整闭环。

【必须掌握】

- 关键数据三件套：日志（过程）/ 截图（画面）/ page_source（结构）
- 它们的统一用途：失败后辅助定位根因

【企业场景】

你在企业里，用例在 CI 半夜跑挂了，第二天早上不可能复现（App 状态、网络都变了）。这时候唯一的线索就是用例失败时自动保存的日志 + 截图 + 页面源码。没做留证的用例，挂了基本等于白跑。

【面试考察】

面试官："自动化用例失败后，你靠什么排查问题？"

参考回答框架：靠三件套留证——日志（记录执行到哪一步、异常堆栈）、截图（失败瞬间页面画面）、page_source（失败瞬间控件树/DOM 结构）。三者配合能还原失败现场，无需复现。

【易错点】

| 误区 | 纠正 |
|------|------|
| 只在 assert 失败时打印一句错误 | 要留"案发现场"：日志 + 截图 + page_source 三件套 |
| 日志和截图二选一 | 两者互补：日志讲过程、截图讲画面，缺一不可 |

【我的理解】

> （为什么说"日志 + 截图 + page_source"缺一不可？试想只有日志、或只有截图，分别会漏掉什么线索？）

## 二、行为日志——Python

### 知识点 2：logging + RotatingFileHandler + pytest.ini

【课程原话/定义】

Python 用自带 logging 模块：

```python
import logging
import os
from logging.handlers import RotatingFileHandler

logger = logging.getLogger(__name__)
root_path = os.path.dirname(os.path.abspath(__file__))
log_dir_path = os.sep.join([root_path, '..', 'logs'])
if not os.path.isdir(log_dir_path):
    os.mkdir(log_dir_path)

file_log_handler = RotatingFileHandler(
    os.sep.join([log_dir_path, 'log.txt']),
    maxBytes=1024 * 1024, backupCount=10, encoding="utf-8"
)
formatter = logging.Formatter(
    '[%(asctime)s] [%(levelname)s] [%(filename)s]/[line: %(lineno)d]/[%(funcName)s] %(message)s',
    '%Y-%m-%d %H:%M:%S'
)
stream_handler = logging.StreamHandler()
file_log_handler.setFormatter(formatter)
stream_handler.setFormatter(formatter)
logger.addHandler(stream_handler)
logger.addHandler(file_log_handler)
logger.setLevel(level=logging.INFO)
```

pytest.ini 配置日志开关与格式：

```ini
[pytest]
log_cli = true
log_cli_level = info
addopts = --capture=no
log_cli_format = %(asctime)s [%(levelname)s] %(message)s (%(filename)s:%(lineno)s)
log_cli_date_format = %Y-%m-%d %H:%M:%S
log_file = ./log/test.log
log_file_level = info
log_file_format = %(asctime)s [%(levelname)s] %(message)s (%(filename)s:%(lineno)s)
log_file_date_format = %Y-%m-%d %H:%M:%S
```

注意：Windows 系统需去掉 ini 里的中文注释。

【为什么？】

1. RotatingFileHandler 是"滚动日志"：`maxBytes` 单个文件上限、`backupCount` 备份个数，日志写满自动切新文件，避免一个 log.txt 无限膨胀。
2. `getLogger(__name__)` 用模块名作 logger 名，避免用根 logger 污染；formatter 里 `%(filename)s:%(lineno)d:%(funcName)s` 能精确到"哪一行、哪个函数"打的日志。
3. pytest.ini 的 `log_cli`/`log_file` 让 pytest 自带日志能力：控制台 + 文件双输出，`--capture=no` 等价 `-s`，日志实时可见。

【必须掌握】

- RotatingFileHandler 三参数：maxBytes（单文件上限）/ backupCount（备份数）/ encoding
- formatter 格式串 + 两个 handler（文件 + 控制台）
- pytest.ini 的 log_cli / log_file 配置

【企业场景】

你在企业里，框架的 log_utils 通常就是这段代码的封装：统一 logger、滚动文件、控制台同步。用例里 `logger.info(f"搜索框 text：{text}")` 这种"关键节点留痕"，是排错时还原执行路径的依据。

【面试考察】

面试官："RotatingFileHandler 是干什么的？maxBytes 和 backupCount 分别控制什么？"

参考回答框架：RotatingFileHandler 是滚动日志处理器，maxBytes 控制单个日志文件大小上限、backupCount 控制保留的备份文件个数，写满自动轮转，防止日志文件无限增长。

【易错点】

| 误区 | 纠正 |
|------|------|
| 只用 print 不用 logging | logging 带级别/时间/文件行号，可关可配，print 无法分级也无法落盘 |
| 日志文件无限增长 | 用 RotatingFileHandler 滚动，否则 log.txt 会无限膨胀 |
| 源码 `os.sep.join([root_path, '..', f'/logs'])` 里 `f'/logs'` | `f'/logs'` 是笔误（f-string 无占位 + 硬编码 `/` 与 os.sep 冲突），应为 `'logs'` |
| ini 里写中文注释 | Windows 下 ini 中文注释可能乱码/报错，要删掉 |

【我的理解】

> （RotatingFileHandler 的 maxBytes=1MB、backupCount=10 意味着什么？日志总量最多会占用多少磁盘？为什么不能只设一个超大的文件？）

## 三、行为日志——Java

### 知识点 3：java.util.logging + FileHandler

【课程原话/定义】

Java 简单日志用 java.util.logging 标准库；复杂需求用第三方框架（log4j 等）。

```java
FileHandler fileHandler = new FileHandler(logDirPath + "/log.txt", 1024 * 1024, 10, true);
fileHandler.setFormatter(new SimpleFormatter());

ConsoleHandler consoleHandler = new ConsoleHandler();
consoleHandler.setFormatter(new SimpleFormatter());

logger.addHandler(fileHandler);
logger.addHandler(consoleHandler);
logger.setLevel(Level.INFO);
```

【为什么？】

1. FileHandler 的构造参数 `(文件名, 单文件上限, 备份数, 是否追加)` 对应 Python 的 RotatingFileHandler，语义一致（滚动日志）。
2. java.util.logging 是 JDK 自带、零依赖，适合简单场景；复杂需求（异步、按天切分、JSON 格式）再上 log4j/slf4j。
3. 注意企业里 Java 项目更常用 **SLF4J + Logback/Log4j2**（统一门面 + 实现），本课的 java.util.logging 只是入门。

【必须掌握】

- FileHandler 四参数：文件名 / 大小上限 / 备份数 / 是否追加
- java.util.logging 是 JDK 自带；生产多改用 SLF4J + Logback/Log4j2

【企业场景】

你在企业里，Java 端日志优先用 SLF4J 门面（`LoggerFactory.getLogger(...)`）+ Logback 实现，别直接用 java.util.logging（功能弱、配置麻烦）。本课示例只是演示"Java 也能记录日志"这一思想，跟 Python 的 logging 对照理解即可。

【面试考察】

面试官："Java 项目里日志一般怎么选型？"

参考回答框架：简单场景用 JDK 自带 java.util.logging；生产环境多用 SLF4J 统一门面 + Logback/Log4j2 实现，功能强（异步、滚动、格式灵活）、配置灵活。

【易错点】

| 误区 | 纠正 |
|------|------|
| Java 只有 java.util.logging | 还有 log4j、SLF4J+Logback 等，生产多不用 java.util.logging |
| FileHandler 参数顺序记混 | `(文件名, 单文件上限, 备份数, 是否追加)` |

【我的理解】

> （Java 的 FileHandler 和 Python 的 RotatingFileHandler 有哪些对应关系？为什么企业里 Java 不用 java.util.logging 而用 SLF4J+Logback？）

## 四、截图

### 知识点 4：四种截图 API

【课程原话/定义】

| Python | Java | 描述 |
|------|------|------|
| get_screenshot_as_file(filename) | getScreenshotAs(OutputType.FILE) | 保存为 .png，filename 为路径 |
| save_screenshot(filename) | getScreenshotAs(OutputType.FILE) | 保存为 .png |
| get_screenshot_as_png() | getScreenshotAs(OutputType.BYTES) | 二进制格式 |
| get_screenshot_as_base64() | getScreenshotAs(OutputType.BASE64) | base64 格式，常用于 html 报告内嵌 |

【为什么？】

1. 四种 API 区别在"输出形态"：存文件（.png）、拿字节（BYTES）、拿 base64 字符串（BASE64）——不同场景选不同形态。
2. `get_screenshot_as_base64` 返回 base64 字符串，可直接嵌进 HTML 测试报告（`<img src="data:image/png;base64,...">`），Allure 就是这么内嵌截图的。
3. 注意"截图的目录要提前创建好"——save_screenshot 不会自动建目录，目录不存在会报错。

【必须掌握】

- 四种截图 API 与输出形态的对应
- base64 用途：html 报告内嵌
- 截图前要确保目录存在

【企业场景】

你在企业里，失败截图统一封装成 `screenshot()` 方法：内部先 `os.makedirs(dir, exist_ok=True)` 建目录，再 save_screenshot 到带时间戳的路径（避免覆盖），最后返回路径给 allure 附加。base64 版用于把截图直接塞进自研的 HTML 报告里。

【面试考察】

面试官："get_screenshot_as_file 和 get_screenshot_as_base64 有什么区别？base64 有什么用？"

参考回答框架：前者把截图存成 .png 文件、后者返回 base64 字符串；base64 可直接内嵌进 HTML 报告（data URI），无需额外存文件。

【易错点】

| 误区 | 纠正 |
|------|------|
| 截图前不建目录 | save_screenshot 不会自动建目录，目录不存在会报错，要先 mkdir |
| 截图文件名固定、会覆盖 | 加时间戳命名，避免多次失败互相覆盖 |

【我的理解】

> （为什么 base64 格式"常用于 html 里添加截图"？把图片存成文件 vs 存成 base64 字符串，各自适合什么场景？）

## 五、页面源码 + 完整示例

### 知识点 5：page_source + 失败留证闭环

【课程原话/定义】

获取页面源码：Python `driver.page_source` / Java `driver.getPageSource()`。

完整示例（雪球搜索 + 三件套留证）：

```python
result = alibaba_element.is_displayed()
logging.info(result)
if result == True:
    logging.info("搜索成功")
    self.driver.save_screenshot("./image/success_search_result.png")
    logging.info(self.driver.page_source)
else:
    logging.info("搜索失败")
    self.driver.save_screenshot("./image/fail_search_result.png")
    logging.info(self.driver.page_source)
assert result == True
```

【为什么？】

1. page_source 返回当前页面的控件树/DOM 源码字符串——失败时打印它，能还原"当时页面上到底有哪些元素、id 是什么"，是定位失败的终极线索。
2. 完整示例展示了留证的标准姿势：**关键节点记日志 → 成功/失败分支各截图 + 各留 page_source → 最后 assert**。
3. `logging.info(self.driver.page_source)` 把源码写进日志，避免另存文件——但源码很大，生产常改为存文件。

【必须掌握】

- page_source 返回控件树源码字符串
- 失败留证闭环：日志 + 截图 + page_source + assert

【企业场景】

你在企业里，定位失败的用例往往靠 page_source 破案：报"元素找不到"，看 page_source 发现元素 id 变了（版本更新）、或根本在 WebView 里没切上下文。截图告诉你"页面长这样"，page_source 告诉你"结构里到底有什么"。

【面试考察】

面试官："page_source 返回的是什么？失败时留 page_source 有什么用？"

参考回答框架：page_source 返回当前页面的控件树/DOM 源码字符串；失败时打印它，能还原失败瞬间页面结构、元素 id，是定位失败根因的关键线索。

【易错点】

| 误区 | 纠正 |
|------|------|
| page_source 是截图 | page_source 是**源码字符串**（控件树），不是图片 |
| 只断言不记日志 | 断言前后要留日志 + 截图 + page_source，否则失败无据可查 |
| 源码 `logging.info(self.driver.page_source)` 每次都打全量 | 源码很大，生产建议失败才留、或存文件，别每步都打全量 |

【我的理解】

> （报"元素找不到"时，截图和 page_source 分别能帮你看到什么？为什么 page_source 更能定位"id 变了"这类根因？）
