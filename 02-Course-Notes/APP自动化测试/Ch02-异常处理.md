## 一、异常与 try-except

### 知识点 1：用 try/except 捕获异常，避免程序中断

【课程原话/定义】

即使语句语法正确，执行时仍可能触发错误——执行时检测到的错误叫**异常**。大多数异常不被处理，程序会中断并抛出异常信息。如果不想程序被中断，可以用 `try/except` 捕获选定的异常并处理：

```python
file = open("data.txt", "r")
try:
    file.write("写入的数据")     # 以只读模式打开却写入，会触发异常
except IOError as err:
    print("文件不能写入", err)
file.close()
```

【为什么？】

1. **异常 vs 语法错误**：语法错误是"代码写错了，压根跑不起来"；异常是"语法没问题，但运行时环境不满足"（文件不存在、除零、下标越界、类型不匹配……）。前者靠写对，后者只能靠 `try/except` 兜住。
2. **`except IOError as err`** 里的 `err` 是异常对象，`print(err)` 能打印异常信息，方便定位问题。
3. **为什么自动化测试必须懂异常**：测试框架里"失败留证"（截图、存 page_source）就是靠 `try/except` 实现的——执行用例，`except` 里截图 + 记录，再决定是吞掉还是继续抛出。见 [[Web自动化测试/Ch16-异常自动截图]]。

【必须掌握】

- 异常 = 运行时错误（非语法错误），不被处理会中断程序
- `try/except 异常类型 as err` 的基本写法
- 自动化里"失败留证"的本质就是 try/except

【企业场景】

你在企业里跑 App 自动化，用例随时可能因为"元素没找到""网络超时""设备断开"抛异常。裸跑的话一条用例失败就整个进程中断，后面几百条全不跑了。正确做法就是 `try/except` 捕获 + 记录（截图/日志/page_source）——这正是 Ch16 那个 `ui_exception_record` 装饰器的核心。

【面试考察】

面试官："语法错误和异常有什么区别？为什么异常要用 try/except 处理？"

参考回答框架：
1. 语法错误：代码写错，解释器解析阶段就报，程序无法运行。
2. 异常：语法正确，运行时环境不满足（文件不存在/除零等）才报。
3. 用 try/except 捕获并处理，避免一条错误中断整个程序。

【易错点】

| 误区 | 纠正 |
|------|------|
| 把"语法错误"当"异常" | 语法错误在解析阶段就报，try/except 抓不住 |
| 只写 `except:` 不指定类型 | 会吞掉所有异常（含键盘中断），难排查；应尽量指定类型 |
| `except IOError` 在 Python 3 里的位置 | Python 3 中 IOError 是 OSError 的别名，写 `except OSError` 更规范 |

【我的理解】
> （"异常"是"运行时才报"的错误。那为什么"运行时才报"比"编译时就知道"更难处理？想想什么信息只有运行时才拿得到。）

## 二、捕捉多个异常

### 知识点 2：多个 except 分别处理，Exception 兜底放最后

【课程原话/定义】

一段代码可能发生多种异常，可以用多个 `except` 分别捕捉。可以捕捉 `Exception` 类型处理所有异常，但**有多个 except 时，Exception 必须放在最后**，否则其它 except 永远执行不到。

```python
file = open("data.txt", "r")
try:
    print("hello" + 100)      # 会抛 TypeError
except IOError as err:
    print("文件不能写入", err)
except NameError:
    print("标识符没有定义")
except ZeroDivisionError:
    print("除数不能为0")
except IndexError:
    print("下标越界了")
except Exception:
    print("程序运行出错，请检查代码")   # 兜底，放最后
file.close()
```

【为什么？】

1. **异常是继承层级**：`Exception` 是所有内建异常的父类，`IOError`、`TypeError`、`NameError` 等都是它的子类。`except` 是按**从上到下**顺序匹配的，且子类能匹配到父类的 except。所以 `Exception` 放前面会把后面所有 except 都"短路"。
2. **先具体后兜底**：正确的顺序是"越具体越靠前，`Exception` 兜底放最后"——这样具体的异常进具体的分支，其它杂七杂八的异常才落到 `Exception` 兜底。
3. **为什么要兜底**：`Exception` 兜底能保证"任何异常都不让程序崩溃"，但代价是"掩盖了具体错误类型"，所以只用来兜底 + 记录，不能用来替代具体处理。

【必须掌握】

- 异常是继承层级，`Exception` 是所有异常的父类
- 多个 except 从上到下匹配，子类能匹配父类的 except
- `Exception` 兜底必须放最后，否则短路

【企业场景】

你在企业里写"失败留证"装饰器时，就是 `except Exception` 兜底——不管抛的是 NoSuchElementException、TimeoutException 还是别的，统统截图 + 存 page_source + 记录日志，然后决定是否继续抛。但前提是你清楚：兜底是为了"不遗漏任何异常"，不是"忽略异常"。

【面试考察】

面试官："为什么 `except Exception` 必须放在多个 except 的最后？"

参考回答框架：
1. except 按顺序匹配，且子类异常能匹配到父类的 except。
2. Exception 是所有异常的父类，放前面会"接住"所有异常，后面的 except 永远不执行（短路）。
3. 正确顺序：具体异常在前，Exception 兜底在后。

【易错点】

| 误区 | 纠正 |
|------|------|
| `except Exception` 放第一个 | 短路，后面所有 except 失效 |
| 以为 except 是"精确类型匹配" | 实际是"继承匹配"，父类能接住子类 |
| 用 `except Exception` 吞掉异常不处理 | 兜底应记录/重抛，不能静默吞掉（否则测试假绿灯） |

【我的理解】
> （"子类能匹配父类的 except"——反过来，父类的 except 能匹配子类吗？用这个规则解释为什么 Exception 放前面会短路。）

## 三、else 与 finally

### 知识点 3：else 处理"无异常"分支，finally 保证"必执行"

【课程原话/定义】

- `else`：在 try 块**无异常时**执行后续操作。
- `finally`：无论异常是否**发生**，都要执行的代码，一般用来做清理工作。

```python
# else
try:
    n = input("请输入一个数字:")
    num = int(n)
except Exception:
    print("元素无法转换为数字")
else:
    print("转换后成功", num)

# finally
try:
    file = open("data.txt", "r")
except Exception:
    print("文件操作报错")
finally:
    print("文件已关闭")
    file.close()
```

【为什么？】

1. **`else` 的意义是"语义分离"**：把"正常逻辑"和"异常处理"分开。`else` 里的代码只有 try 成功时才跑，比把正常逻辑全塞进 try 里更清晰——try 里只放"可能出错的操作"，else 放"成功后的操作"。
2. **`finally` 的意义是"保证清理"**：不管 try 成功、except 捕获、还是异常没被捕获继续往外抛，`finally` 都一定会执行。所以它专门放"必须执行的收尾"：关文件、关 driver、释放连接。
3. **自动化里的 finally = teardown**：pytest 的 `teardown`/`fixture` 收尾、`driver.quit()` 关浏览器，本质都是"无论用例成败都要清理"——和 finally 是同一个思想。

【必须掌握】

- `else`：try 无异常时才执行（放"成功后的操作"）
- `finally`：无论是否异常都执行（放"清理工作"）
- 自动化 teardown / driver.quit 是 finally 思想的落地

【企业场景】

你在企业里，`finally` 最常见的落地就是"关 driver"：用例可能失败抛异常，但如果不在 finally/fixture 里 `driver.quit()`，失败的用例就会留下僵尸浏览器进程（[[Web自动化测试/Ch04-自动化测试用例结构分析]] 里讲过 quit 必须放 teardown）。这正是 finally "无论成败都要执行"的价值。

【面试考察】

面试官："else 和 finally 有什么区别？各自适合放什么？"

参考回答框架：
1. else：try 无异常时才执行，放"成功后的正常逻辑"。
2. finally：无论是否异常都执行，放"清理/收尾"（关文件、关连接、关 driver）。
3. 一句话：else 是"成功才做"，finally 是"无论如何都做"。

【易错点】

| 误区 | 纠正 |
|------|------|
| 以为 else 在异常时也执行 | else 只在 try 无异常时执行，异常时跳过 |
| finally 里访问可能没定义的变量 | 若 open() 失败，`file` 没定义，`file.close()` 会再抛 NameError（课程示例的隐患） |
| 以为 finally 能"吃掉"异常 | finally 不改变异常传播，只是追加一段必执行代码 |

> 注：课程源码里 finally 示例有个隐患——`file = open(...)` 若失败，`file` 未定义，`finally` 里的 `file.close()` 会抛 `NameError` 掩盖原异常。更稳妥写法是 `with open(...) as file`（上下文管理器自动关闭，见 [[Python/Ch25-文件操作]]）。

【我的理解】
> （"清理工作放 finally"和"清理工作放 else"有什么本质不同？为什么"无论成败都要执行"这个特性，决定了清理只能放 finally？）
