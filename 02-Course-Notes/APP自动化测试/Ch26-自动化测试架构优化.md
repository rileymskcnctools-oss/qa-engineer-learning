# Ch26 - 自动化测试架构优化

## 课程来源
- 学习日期：

> 本章是工程化的第三块：**架构**。把前面散落的"定位/等待/留证/容错"能力，按"框架层 / 基础层 / 业务层 / 用例层"分层组织起来，再补上数据驱动和 Allure 报告——这是从"写脚本"走向"搭框架"的分水岭。

---

## 一、自动化框架应具备的功能

### 知识点 1：八大能力 + 实现对照表

【课程原话/定义】

自动化框架应具备的功能：

1. 管理用例、运行用例
2. 查找/定位元素，对元素/页面进行操作（点击、滑动、输入等）
3. 生成测试报告
4. 功能复用（登录、搜索等）
5. 页面异常弹框的有效处理
6. 用例失败时添加日志、截图等信息到测试报告
7. 多设备并发
8. 平台化

功能与实现对照：

| 功能 | Python | Java |
|------|--------|------|
| 管理/运行用例 | pytest | JUnit |
| 查找/定位元素 | Appium | Appium |
| 测试报告 | Allure | Allure |
| 功能复用 | PO 实现 | PO 实现 |
| 异常弹框 | 编写代码 | 编写代码 |
| 失败日志/截图 | 编写代码 | 编写代码 |

【为什么？】

1. 框架的"应具备功能"是**验收清单**——判断一个自动化框架成不成熟，就看这八项覆盖了没。
2. 前六项是"基本盘"（pytest/JUnit + Appium + Allure + PO），后两项（并发、平台化）是"进阶盘"。
3. "编写代码"出现在异常弹框、失败留证两行，说明这两项框架不提供现成方案，要靠自己封装（正是 Ch24/Ch25 的内容）。

【必须掌握】

- 八大能力 + 各自的技术选型（pytest/JUnit、Appium、Allure、PO）
- 异常弹框 + 失败留证需要"自己写代码"封装

【企业场景】

你在企业里，搭框架前先对着这张表过一遍：用例管理用 pytest、定位用 Appium、报告用 Allure、复用用 PO——这四项是现成轮子；异常弹框和失败留证必须自己封装（Ch25 黑名单 + Ch24 三件套）。并发和平台化按需补。

【面试考察】

面试官："一个成熟的自动化测试框架应该具备哪些能力？"

参考回答框架：用例管理运行（pytest/JUnit）、元素定位操作（Appium）、测试报告（Allure）、功能复用（PO）、异常弹框处理、失败留证（日志/截图）、多设备并发、平台化。前六项是基本盘，后两项是进阶。

【易错点】

| 误区 | 纠正 |
|------|------|
| 以为框架 = 会写用例 | 框架要能"管理用例/复用功能/留证/容错"，用例只是其中一层 |
| 异常弹框/留证有现成库 | 这两项框架不提供现成方案，要自己封装（Ch24/Ch25） |

【我的理解】

> （对照表里"异常弹框""失败留证"两行为什么写"编写代码"而不是某个现成库？这说明框架的哪些能力要自己沉淀？）

## 二、项目结构

### 知识点 2：四层结构（框架层/基础层/业务层/用例层）

【课程原话/定义】

Python 项目结构示例：

```
.
├── base          # 基础层：driver 封装、元素查找封装、操作封装
│   ├── app.py
│   └── base_page.py
├── cases         # 用例层：测试用例集
│   └── test_xxx.py
├── log           # 日志
│   └── test.log
├── datas         # 数据
│   └── xxx.yml
├── page          # 业务层：页面封装
│   ├── main_page.py
│   └── xxx_page.py
├── conftest.py
└── utils         # 公共方法层
    └── log_utils.py
```

四层：**框架层**（异常处理/数据驱动/日志搜集/报告管理）、**基础层**（driver 封装/元素查找/操作）、**业务层**（页面封装）、**用例层**（测试用例集）。

【为什么？】

1. 分层的本质是"职责分离"：用例层只关心"测什么业务"，业务层封装"页面有哪些元素和操作"，基础层封装"怎么找元素/操作 driver"，框架层提供"横切能力"（日志/异常/报告/数据）。
2. 这样改定位器只动业务层、改日志只动框架层，互不影响——降低维护成本。
3. conftest.py 是 pytest 的 fixture 挂载点（driver 的创建/销毁通常放这），datas 放测试数据、utils 放工具函数。

【必须掌握】

- 四层结构：框架层/基础层/业务层/用例层 + 各自职责
- 每个目录放什么（base/page/cases/datas/utils/log）

【企业场景】

你在企业里，接手一个 PO 框架，看目录就能懂架构：base 是 driver+查找封装、page 是页面对象、cases 是测试用例、datas 是数据、utils 是工具。分层清晰，新人上手快、改代码不会互相踩。

【面试考察】

面试官："你们的测试框架分哪几层？各层职责是什么？"

参考回答框架：框架层（异常/数据驱动/日志/报告横切能力）、基础层（driver 封装/元素查找/操作）、业务层（页面封装）、用例层（测试用例集）。分层实现职责分离、降低维护成本。

【易错点】

| 误区 | 纠正 |
|------|------|
| 所有代码堆一个文件 | 按四层拆分，否则定位器/日志/用例耦合，一处改全局崩 |
| 业务逻辑写进用例层 | 用例层只调用业务层方法，不直接写 find_element（那是基础层/业务层的活） |

【我的理解】

> （"改定位器只动业务层、改日志只动框架层"——这句话体现了分层的什么价值？如果不分层会怎样？）

## 三、数据驱动

### 知识点 3：yaml + pytest.mark.parametrize

【课程原话/定义】

数据驱动三步：①参数定义（指定名字）②数据源指定（yaml 等文件）③准备测试数据（线上捞或自建，设计成"读取出来就是参数化所需格式"）。

```yaml
# datas.yaml
datas:
- - name1
  - phone1
- - name2
  - phone2
```

读取 yaml：

```python
class Utils:
    @classmethod
    def get_yaml_data(cls, yaml_path):
        with open(yaml_path, encoding="utf-8") as f:
            datas = yaml.safe_load(f)
        return datas
```

用例参数化：

```python
@pytest.mark.parametrize("name, phonenum", get_datas("datas.yaml"))
def test_xx(self, name, phonenum):
    ...
```

【为什么？】

1. 数据驱动的目的：**同一段测试逻辑，喂不同数据跑多遍**——把"测试逻辑"和"测试数据"分离，加用例 = 加一行数据，不用复制粘贴代码。
2. yaml 结构设计成 `[[name1, phone1], [name2, phone2], ...]`（列表套列表），正好对应 parametrize 的 `[(name, phone), ...]`。
3. `pytest.mark.parametrize("name, phonenum", 数据列表)` 把数据按位置解包到参数。

【必须掌握】

- 数据驱动三步骤 + yaml 数据格式
- get_yaml_data 用 yaml.safe_load
- @pytest.mark.parametrize 参数化

【企业场景】

你在企业里，搜索/登录这类"逻辑相同、数据不同"的用例，都用数据驱动：yaml 里加一条股票名，就跑一个新搜索用例。数据还能从线上/Excel 捞，测试人员维护数据文件即可，不用碰代码。

【面试考察】

面试官："数据驱动怎么实现？yaml 数据格式怎么设计？"

参考回答框架：测试逻辑与测试数据分离，用 yaml 存数据（列表套列表 `[[name,phone],...]`），yaml.safe_load 读出来，pytest.mark.parametrize 按位置解包到用例参数。加用例=加一行数据。

【易错点】

| 误区 | 纠正 |
|------|------|
| 数据逻辑写死在用例里 | 数据驱动要把数据抽到 yaml，用 parametrize 注入 |
| yaml 格式和 parametrize 不匹配 | yaml 设计成 `[[a,b],[a,b]]`，才能直接喂给 parametrize |

【我的理解】

> （为什么说"加用例 = 加一行数据"？对比"复制粘贴一段测试代码"和"往 yaml 加一行"，各自改动的成本和出错风险差在哪？）

## 四、日志搜集 + 报告管理

### 知识点 4：allure.step / feature / story / title + 生成报告

【课程原话/定义】

基类里加步骤描述 + allure.step：

```python
class BasePage:
    @black_wrapper
    def find_ele(self, by, value):
        step_text = f"查找单个元素的定位：{by},{value}"
        logger.info(step_text)
        with allure.step(step_text):
            ele = self.driver.find_element(by, value)
        return ele
```

用例里加描述：

```python
@allure.feature("产品描述")
class TestXXX:
    @allure.story("功能描述")
    @allure.title("用例标题")
    def test_xx(self):
        pass
```

黑名单装饰器里把截图/源码附加到 allure 报告：

```python
allure.attach.file(image_path, name="查找元素异常截图",
                   attachment_type=allure.attachment_type.PNG)
allure.attach.file(pagesource_path, name="page_source",
                   attachment_type=allure.attachment_type.TEXT)
```

生成报告：

```bash
pytest --alluredir=./results --clean-alluredir
allure serve ./results            # 本地服务查看
allure generate --clean ./results -o ./report/html   # 生成静态报告
```

【为什么？】

1. allure.step 把"查找元素"这类底层动作变成报告里的可折叠步骤，失败时报告能展开看到具体哪一步挂了。
2. feature/story/title 是报告的三级组织维度（产品→功能→用例），让报告按业务归类，不是一堆平铺的用例名。
3. allure.attach 把截图/源码塞进报告对应用例，失败点开报告就能看到"现场照片"——这是"失败留证进报告"的闭环。

【必须掌握】

- allure.step（步骤）/ feature（产品）/ story（功能）/ title（用例标题）
- allure.attach.file 附加截图/源码
- 三条命令：--alluredir 收集 / serve 本地看 / generate 静态报告

【企业场景】

你在企业里，Allure 报告是给测试和开发看的"失败说明书"：feature/story 归类业务，step 展开执行路径，失败用例里 attach 了截图和 page_source，开发点开就能定位，不用再找测试复现。

【面试考察】

面试官："Allure 报告里 feature/story/title/step 分别是什么？怎么把失败截图放进报告？"

参考回答框架：feature 产品、story 功能、title 用例标题（三级归类），step 是报告里的执行步骤；失败截图用 allure.attach.file(..., attachment_type=PNG) 附加到用例，配合 --alluredir 收集、allure serve/generate 查看。

【易错点】

| 误区 | 纠正 |
|------|------|
| 只跑 pytest 不收集 allure 结果 | 要 `--alluredir=./results` 收集结果，才有报告 |
| 源码 `allure generate --clean report/html report -o report/html` 参数混乱 | 正确应为 `allure generate --clean ./results -o ./report/html`（结果目录 → 输出目录） |
| feature/story/title 顺序搞混 | feature=产品(大) → story=功能(中) → title=用例(小) |

【我的理解】

> （Allure 报告里 feature/story/title 和 step 分别解决什么？为什么"失败截图 attach 进报告"比"截图存本地文件夹"更有用？）
