## 一、滑动操作的场景

### 知识点 1：三类滑动场景

【课程原话/定义】

移动端用户倾向用滑动与控件交互，滑动是自动化高频动作。三类场景：

- 触摸事件模拟：模拟用户按住、滑动、释放的一系列触摸事件。
- 坐标计算：涉及起始点和终点坐标，坐标相对屏幕或特定元素。
- 惯性滑动：释放手指后继续滑动一段距离，需模拟逐渐减速。

【为什么？】

1. 滑动本质是"触摸事件序列"：pointerDown（按下）→ pointerMove（移动）→ pointerUp（释放），Appium 把这三个事件打包成一次滑动。
2. 坐标是滑动的"语言"：起点终点决定方向和距离；用比例（如 `width*0.5`）而非绝对像素，一套脚本适配不同分辨率。
3. 惯性滑动：真实手指滑动有"松手后还滑一段"的物理惯性，`duration` 参数控制"慢滑"来模拟减速效果。

【必须掌握】

- 滑动 = 触摸事件序列（按下 → 移动 → 释放）
- 坐标用比例计算，适配不同屏幕
- 惯性滑动靠 duration 控制

【企业场景】

你在企业里，App 的列表加载更多、轮播图、抽屉菜单、下拉刷新都是滑动场景。用比例坐标写滑动，一套脚本能跑不同尺寸的模拟器和真机，不用为每个设备写死像素。

【面试考察】

面试官："滑动的本质是什么？坐标为什么要用比例？"

参考回答框架：滑动本质是触摸事件序列（按下→移动→释放）；坐标用比例（屏幕宽高的百分比）而非绝对像素，因为不同设备分辨率不同，比例写法一套脚本多设备通用。

【易错点】

| 误区 | 纠正 |
|------|------|
| 滑动是"瞬移" | 滑动是"按下→移动→释放"事件序列，有过程 |
| 坐标写死像素 | 用比例（width*0.5）适配不同分辨率 |

【我的理解】

> （"滑动 = 触摸事件序列"这句话怎么理解？为什么 duration=2000 的滑动比 duration=0 更像真实手指？）

## 二、swipe 方法

### 知识点 2：坐标滑动（swipe）

【课程原话/定义】

从一个点滑到另一个点，可选择持续时间，有惯性。参数：

- start_x / start_y：起点坐标
- end_x / end_y：终点坐标
- duration（可选）：持续时间，默认 0

Python 示例：

```python
size = self.driver.get_window_size()
height = size.get('height')
width = size.get('width')
self.driver.swipe(
    start_x=width * 0.5, start_y=height * 0.8,
    end_x=width * 0.5, end_y=height * 0.2,
    duration=2000
)
```

Java 无便捷方法，用 W3C Actions 手写：

```java
public void swipe(int startX, int startY, int endX, int endY, Duration duration) {
    PointerInput finger = new PointerInput(PointerInput.Kind.TOUCH, "finger");
    Sequence swipe = new Sequence(finger, 1)
            .addAction(finger.createPointerMove(Duration.ofMillis(0), PointerInput.Origin.viewport(), startX, startY))
            .addAction(finger.createPointerDown(PointerInput.MouseButton.LEFT.asArg()))
            .addAction(finger.createPointerMove(duration, PointerInput.Origin.viewport(), endX, endY))
            .addAction(finger.createPointerUp(PointerInput.MouseButton.LEFT.asArg()));
    driver.perform(Collections.singletonList(swipe));
}
```

【为什么？】

1. swipe 是"纯坐标"滑动：不关心页面上有什么元素，只关心从哪滑到哪，适合列表翻页、上滑加载等"无目标元素"场景。
2. start 用 `height*0.8`（屏幕下方）、end 用 `height*0.2`（屏幕上方）= 手指从下往上滑，即"上滑"。
3. Python 直接有 `swipe` 方法；Java 官方没封装，要用 Selenium W3C 的 `PointerInput`（触摸指针）+ `Sequence`（动作序列）手动拼"移到起点→按下→移到终点→抬起"。

【必须掌握】

- swipe 五个参数 + duration 默认 0
- 上滑 = start_y > end_y（从下往上）
- Java 用 PointerInput + Sequence 手写滑动

【企业场景】

你在企业里，列表页"上滑加载更多"、长页面滚动到底，用 swipe 按比例坐标滑。跨团队时 Java 同学要会手写 W3C Actions（因为 Java 没现成 swipe），这是 Java 和 Python 在 Appium 上的一个明显差异点。

【面试考察】

面试官："swipe 和 scroll 有什么区别？Java 里为什么没有 swipe 便捷方法？"

参考回答框架：swipe 按坐标滑、scroll 按元素滑；Java 客户端没封装 swipe/scroll 便捷方法，要用 Selenium W3C Actions（PointerInput + Sequence）手动拼触摸事件序列实现。

【易错点】

| 误区 | 纠正 |
|------|------|
| 原文 `weight = size.get('width')` | 变量名 weight 是笔误，应为 width（照抄易误导） |
| duration 是"次数" | duration 是持续时间（毫秒），控制滑动快慢/惯性 |
| 上下滑方向搞反 | start_y=0.8、end_y=0.2 是"从下往上滑"（上滑），反了就是下滑 |

【我的理解】

> （start_y=height*0.8、end_y=height*0.2 为什么是"上滑"？如果要"下滑"，start/end 该怎么写？）

## 三、scroll 方法

### 知识点 3：元素间滑动（scroll）

【课程原话/定义】

从一个元素滑到另一个元素，有惯性。参数：

- origin_el：滑动起始元素
- destination_el：滑动结束元素
- duration：持续时间

Python 示例：

```python
image_btn = self.driver.find_element(AppiumBy.ACCESSIBILITY_ID, 'ImageButton')
button = self.driver.find_element(AppiumBy.ACCESSIBILITY_ID, 'Buttons')
self.driver.scroll(image_btn, button, duration=2000)
```

Java（手写，核心是算两个元素中心点）：

```java
int startX = startElement.getLocation().getX() + startElement.getSize().getWidth() / 2;
int startY = startElement.getLocation().getY() + startElement.getSize().getHeight() / 2;
int endX = endElement.getLocation().getX() + endElement.getSize().getWidth() / 2;
int endY = endElement.getLocation().getY() + endElement.getSize().getHeight() / 2;
// 之后用 PointerInput + Sequence 执行滑动
```

【为什么？】

1. scroll 是"元素到元素"：Appium 自动算两个元素的中心点，从起始元素中心滑到结束元素中心，适合"把列表里某个已知元素滚到可见位置"。
2. Java 的 scroll 手写实现里，用 location + size 算中心点（呼应 Ch15 知识点3），再走同一套 PointerInput + Sequence。
3. swipe 和 scroll 本质都是"触摸事件序列"，差别只在"坐标怎么来"：swipe 手给坐标，scroll 自动算元素中心。

【必须掌握】

- scroll 参数：origin_el / destination_el / duration
- scroll = 自动算两元素中心点再滑
- swipe vs scroll 的本质区别（坐标 vs 元素）

【企业场景】

你在企业里，目标元素在长列表下方、需要先滑到它才能点，用 scroll(起始元素, 目标元素) 比 swipe 更稳——不用猜"滑多远"，直接说"从 A 滑到 B"。但 scroll 要求两个元素当前都能定位到（目标元素可能在屏幕外找不到，此时先 swipe 粗滑、再 scroll 精定位）。

【面试考察】

面试官："swipe 和 scroll 的本质区别？各自适用什么场景？"

参考回答框架：swipe 按坐标滑（适合无目标元素的上滑加载/翻页），scroll 按元素滑（自动算两元素中心点，适合把已知元素滚到可见）。本质都是触摸事件序列，差别在坐标来源。

【易错点】

| 误区 | 纠正 |
|------|------|
| 以为 scroll 目标元素可以"屏幕外" | scroll 要先把两元素定位到，屏幕外目标元素可能定位失败，需先 swipe 粗滑 |
| swipe/scroll 是两种不同机制 | 本质相同（触摸事件序列），只是坐标来源不同 |

【我的理解】

> （scroll 为什么能"自动"从 A 滑到 B？它背后算的是什么坐标？（提示：回忆 Ch15 的 location + size））
