## 一、用例结构三原则

### 知识点 1：可读性 / 可维护性 / 可扩展性

【课程原话/定义】

自动化测试用例结构是指为有效执行自动化测试而组织设计的一套规范或布局。良好的结构可提高脚本的可读性、可维护性和可扩展性。

【为什么？】

1. 可读性：脚本是给人看的（别人接手、自己回看），结构清晰才好懂。
2. 可维护性：元素/流程变化时改得少、改得快。
3. 可扩展性：加新用例不破坏旧用例。

【必须掌握】

- 三原则：可读性 / 可维护性 / 可扩展性

【企业场景】

你在企业里，一个用例脚本从"录制出来的面条代码"到"框架化"，本质就是依次满足这三原则：先让别人看得懂，再让改动低成本，最后让新增用例不打架。

【面试考察】

面试官："为什么要注意自动化用例的结构？"

参考回答框架：提升可读性（好懂）、可维护性（好改）、可扩展性（好加）。

【易错点】

| 误区 | 纠正 |
|------|------|
| 能跑就行 | 录制脚本能跑但不可维护，元素一改全挂 |

【我的理解】

> （"能跑"和"可维护"的区别是什么？举一个"能跑但不可维护"的脚本例子。）

## 二、Inspector 录制脚本

### 知识点 2：录制生成用例

【课程原话/定义】

Inspector 录制生成用例脚本：定位元素（OS 按钮、Morse Code 按钮、输入框）→ 调用点击/输入方法 → 返回。

Python 示例（录制版）：

```python
el1 = driver.find_element(by=AppiumBy.ACCESSIBILITY_ID, value="OS")
el1.click()
el2 = driver.find_element(by=AppiumBy.ACCESSIBILITY_ID, value="Morse Code")
el2.click()
el3 = driver.find_element(by=AppiumBy.ID, value="io.appium.android.apis:id/text")
el3.send_keys("ceshiren.com")
driver.back()
driver.back()
```

Java 示例（录制版）：

```java
WebElement el1 = driver.findElement(AppiumBy.accessibilityId("OS"));
el1.click();
WebElement el2 = driver.findElement(AppiumBy.accessibilityId("Morse Code"));
el2.click();
WebElement el3 = driver.findElement(AppiumBy.id("io.appium.android.apis:id/text"));
el3.sendKeys("ceshiren.com");
driver.navigate().back();
driver.navigate().back();
```

【为什么？】

1. Inspector 录制是"拿定位器"的最快方式：自动把元素转成 find_element 代码，不用手写定位。
2. 录制的脚本是"原始版"，通常只包含定位 + 操作，没有 capability、没有 setup/teardown、没有断言——需要后续优化。
3. 定位方式多样（ACCESSIBILITY_ID / ID / XPATH），不同场景选不同方式。

【必须掌握】

- 录制脚本的组成：find_element + 操作（click / send_keys / back）
- 录制脚本是"原始版"，还需优化

【企业场景】

你在企业里，用 Inspector 录制只是"起点"，录出来的脚本要手动改三处：补 capability、补 setup/teardown、补断言。这是从"能跑"到"能自动化回归"的关键一步。

【面试考察】

面试官："Inspector 录制出来的脚本能直接用吗？"

参考回答框架：不能。录制脚本只有定位+操作，缺 capability、缺 setup/teardown、缺断言，要优化后才能进回归。

【易错点】

| 误区 | 纠正 |
|------|------|
| 录制脚本直接上生产 | 缺断言、缺清理，无法真正验证结果 |
| 定位方式只背一种 | ACCESSIBILITY_ID / ID / XPATH 各有适用场景 |

【我的理解】

> （为什么录制脚本"能跑"但还"不能用"？它缺了哪三样东西？）

## 三、Capability 与初始化

### 知识点 3：添加 capability + 初始化 webdriver

【课程原话/定义】

优化第一步：加 Capability 信息 + 初始化 webdriver。

Python 示例：

```python
from appium import webdriver
from appium.options.android import UiAutomator2Options
from appium.webdriver.common.appiumby import AppiumBy

caps = {
    "platformName": "android",              # app 安装的平台
    "appium:automationName": "uiautomator2",# appium 驱动
    "appium:deviceName": "emulator-5554",   # 设备名称
    "appium:appPackage": "io.appium.android.apis",  # app 包名
    "appium:appActivity": ".ApiDemos",      # app 启动页
}
driver = webdriver.Remote(
    "http://localhost:4723",
    options=UiAutomator2Options().load_capabilities(caps)
)
```

Java 示例（关键部分）：

```java
DesiredCapabilities caps = new DesiredCapabilities();
caps.setCapability(MobileCapabilityType.PLATFORM_NAME, "Android");
caps.setCapability(MobileCapabilityType.AUTOMATION_NAME, "UiAutomator2");
caps.setCapability(MobileCapabilityType.DEVICE_NAME, "emulator-5554");
caps.setCapability("appPackage", "io.appium.android.apis");
caps.setCapability("appActivity", ".ApiDemos");
URL remoteUrl = new URL("http://127.0.0.1:4723");
driver = new AndroidDriver(remoteUrl, caps);
```

【为什么？】

1. Capability 是告诉 Server"测什么、怎么测"的键值对：平台、引擎、设备、App 包名/入口 Activity。
2. webdriver.Remote(url, options) 是建立连接的入口：Client 通过它发 POST /session 给 Server（呼应 Ch09 原理）。
3. appPackage + appActivity 决定启动哪个 App 的哪个页面（Activity 是 Android 的页面概念）。

【必须掌握】

- 五个核心 capability：platformName / automationName / deviceName / appPackage / appActivity
- webdriver.Remote 建立连接

【企业场景】

你在企业里，最常改的 capability 是 appPackage 和 appActivity——换被测 App 就改这两个。deviceName 在真机上要填真机 id（adb devices 看），模拟器上填模拟器名（如 emulator-5554）。

【面试考察】

面试官："启动一个 Android App 需要哪些关键 capability？"

参考回答框架：platformName、automationName（uiautomator2）、deviceName、appPackage、appActivity。

【易错点】

| 误区 | 纠正 |
|------|------|
| appPackage/appActivity 填错 | 找不到 App/页面；appActivity 有的要带点号（.ApiDemos） |
| capability 前缀漏写 | Appium 2.x 非标准功能要加 appium: 前缀（如 appium:appPackage）；原文 Java 示例里的 appPackage/appActivity 就漏了前缀 |
| 混淆 shouldTerminateApp 语义 | shouldTerminateApp=true 表示会话结束时终止 App，不是"不重启"（原文注释写反了） |

【我的理解】

> （appPackage 和 appActivity 分别对应 Android 的什么概念？"启动一个 App"为什么两个都要？）

## 四、测试框架优化

### 知识点 4：setup / teardown + 断言

【课程原话/定义】

优化第二步：用测试框架组织用例。Python 用 pytest 的 setup_method / teardown_method，把 driver 初始化放 setup、quit 放 teardown；测试方法里加断言。Java 用 JUnit 的 @BeforeAll / @AfterAll + @Test + assert。

Python 示例（pytest 版）：

```python
class TestApiDemo:
    def setup_method(self):
        caps = {
            "platformName": "android",
            "appium:automationName": "uiautomator2",
            "appium:deviceName": "emulator-5554",
            "appium:appPackage": "io.appium.android.apis",
            "appium:appActivity": ".ApiDemos",
        }
        self.driver = webdriver.Remote(
            "http://localhost:4723",
            options=UiAutomator2Options().load_capabilities(caps)
        )

    def teardown_method(self):
        self.driver.quit()

    def test_api_demo(self):
        el1 = self.driver.find_element(by=AppiumBy.ACCESSIBILITY_ID, value="OS")
        el1.click()
        el2 = self.driver.find_element(by=AppiumBy.ACCESSIBILITY_ID, value="Morse Code")
        el2.click()
        el3 = self.driver.find_element(by=AppiumBy.ID, value="io.appium.android.apis:id/text")
        el3.send_keys("ceshiren.com")
        self.driver.back()
        self.driver.back()
        result = self.driver.find_element(
            AppiumBy.XPATH, "//*[@resource-id='android:id/text1'][1]"
        )
        assert result.text == "Access'ibility"
```

【为什么？】

1. setup/teardown 把"建连接/关连接"抽出来，每个用例自动复用，避免每个方法重复初始化。
2. 断言是自动化测试的"灵魂"：没有断言，脚本只是"操作了一遍"，无法判断对不对。
3. 测试框架提供用例管理（发现/执行/报告），是工程化的基础。

【必须掌握】

- pytest：setup_method（初始化 driver）/ teardown_method（quit）
- 断言 assert 判断结果

【企业场景】

你在企业里，框架化的标准姿势就是：setup_method 建 driver → 测试方法做操作 + 断言 → teardown_method 关 driver。断言写的是"预期文本 == 实际文本"这类判断，这是测试和"演示脚本"的分水岭。

【面试考察】

面试官："为什么要把用例放进测试框架里？"

参考回答框架：setup/teardown 复用初始化与清理、断言判断结果、框架提供用例发现/执行/报告。

【易错点】

| 误区 | 纠正 |
|------|------|
| 没有断言 | 脚本变成"演示操作"，测不出对错 |
| 忘写 teardown 关 driver | 会话不释放，多次运行会残留/报错 |
| 断言只打印不看结果 | 断言要判断"预期 == 实际"，不是 print 了事 |

【我的理解】

> （"没有断言的脚本不算测试"——为什么？setup_method 和 teardown_method 各自解决了什么问题？）
