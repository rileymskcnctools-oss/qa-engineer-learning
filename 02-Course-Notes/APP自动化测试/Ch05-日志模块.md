## 一、为什么要用日志（logging vs print）

### 知识点 1：日志是记录程序运行时信息的机制

【课程原话/定义】

日志是用于记录应用程序运行时的信息，通过日志可以帮助开发者诊断问题、跟踪应用程序的状态以及记录重要的事件。Python 中可以使用 `logging` 模块实现日志的记录。`logging` 提供了丰富的配置选项和灵活性，可以将日志信息输出到不同的位置、设置不同的日志级别等。

【为什么？】

1. `print` 只能打控制台、不能留档、不能分级、不能带时间戳/行号等元信息；上线后没人盯控制台，问题复现时啥都没有。
2. `logging` 能输出到不同位置（文件/控制台/网络）、设置不同级别（决定记录哪些）、自定义格式（时间戳/模块/行号/级别/信息）。
3. 自动化测试里用例失败要"留证"：日志记录每一步的状态，失败时能回溯"卡在哪一步、什么参数、什么报错"。

【必须掌握】

- 日志 vs print 的本质区别：可留档、可分级、可带元信息、可多目的地
- 日志三大用途：诊断问题、跟踪状态、记录重要事件

【企业场景】

你写 App 自动化，一个用例跑了 5 分钟最后失败，如果只靠 `print` 早就被刷屏淹没；而日志文件按时间戳+模块+行号记录了每一步，失败时打开日志就知道卡在哪个元素、哪个接口。日志是"事后排查"的主要依据。

【面试考察】

面试官："print 和 logging 有什么区别？为什么生产代码里都用 logging？"

参考回答框架：
1. print 无级别、无时间戳、只能控制台，且无法统一开关。
2. logging 可分级、可格式化、可多目的地（文件/控制台/网络）、可统一控制。
3. 生产/自动化里日志要留档供事后排查，print 做不到。

【易错点】

| 误区 | 纠正 |
|------|------|
| 只用 print 调试 | 生产/自动化里要留档、分级、带时间戳，用 logging |
| 以为 logging 只能写文件 | 不指定 filename 时默认输出到控制台，还能同时写多个目的地 |

【我的理解】
> （为什么说"日志是自动化测试事后排查的主要依据"？举一个用例失败后你靠日志才能定位问题的具体场景。）

## 二、日志等级

### 知识点 2：DEBUG / INFO / WARNING / ERROR / CRITICAL 五个等级

【课程原话/定义】

| 级别 | 用法 |
|------|------|
| DEBUG | 最低级别，用于调试和记录详细信息，通常用于开发和调试阶段 |
| INFO | 信息性信息，确认程序按预期运行 |
| WARNING | 表示警告，指示已经或即将发生的意外（如磁盘空间不足），程序仍按预期进行 |
| ERROR | 表示错误，由于严重问题，程序的某些功能已不能正常执行 |
| CRITICAL | 最高级别，表示严重错误，程序已不能继续执行 |

【为什么？】

1. 分级的核心是"按严重程度过滤"：设 `level=WARNING` 时，比它低的 DEBUG/INFO 就不记录——生产环境只关心 WARNING 及以上，调试时才放开 DEBUG。
2. 阈值语义是"从该级别往上都记录"：`level=ERROR` 只记录 ERROR 和 CRITICAL。
3. 分级让同一套代码适配不同环境：开发打 DEBUG 全量，生产只打 WARNING+，避免磁盘被海量 DEBUG 打满。

【必须掌握】

- 五级顺序和各自含义
- 阈值语义：设 level 后，低于它的不记录
- 默认 level 是 WARNING（不显式设置时 DEBUG/INFO 不输出）

【企业场景】

你在企业里，开发环境 `level=DEBUG` 全量记录方便定位；上线前改成 `level=INFO` 或 `WARNING`，避免磁盘被海量 DEBUG 日志写满。分级就是"同一份代码，不同环境不同记录量"。

【面试考察】

面试官："logging 的默认级别是什么？设 level=WARNING 后 DEBUG 还会不会被记录？"

参考回答框架：
1. 默认级别是 WARNING。
2. 不会——阈值语义是"只记录 >= WARNING 的"，DEBUG/INFO 被过滤掉。
3. 所以不显式设 level 时，直接 `logging.info()` 什么都看不到，这是新手最常见的坑。

【易错点】

| 误区 | 纠正 |
|------|------|
| 不设 level 就调 logging.info() | 默认 WARNING，INFO/DEBUG 不输出，看不到 |
| 以为 level 是"只记这个级别" | level 是阈值，>= 该级别的都记录 |
| INFO 描述照抄 DEBUG 文案 | 源课程 INFO 行误写"用于调试和记录详细信息，通常用于开发和调试阶段"（这是 DEBUG 的定位）；INFO 正确语义是"确认程序按预期运行、记录正常业务流程" |

【我的理解】
> （"设 level=ERROR 后，WARNING 还记不记录？"——用阈值的语义解释，而不是背结论。）

## 三、logging 四大组件

### 知识点 3：logger / handler / filter / formatter

【课程原话/定义】

- **logger**：日志器，提供程序可使用的接口（负责"产生哪条日志"）。
- **handler**：处理器，用于写入日志文件并输出到指定位置，如文件、控制台或网络等。
- **filter**：过滤器，用于输出符合指定条件的日志记录。
- **formatter**：格式器，决定日志记录的输出格式。

【为什么？】

1. 四大组件把"记录日志"拆成流水线：logger 产生日志 → filter 过滤 → handler 决定往哪写 → formatter 决定长什么样。
2. 一个 logger 可以挂多个 handler（同一份日志同时写文件 + 打控制台 + 发网络），这是 print 做不到的。
3. 组件化让"输出目的地"和"输出格式"解耦：改格式只动 formatter，改目的地只动 handler。

【必须掌握】

- 四组件的职责：logger 产生、handler 输出、filter 过滤、formatter 格式化
- logger 可挂多个 handler，实现"一份日志多目的地"
- 数据流向：logger → filter → handler → formatter

【企业场景】

你在企业里，测试框架通常配"控制台 handler（实时看）+ 文件 handler（留档）"，有时再加"邮件/网络 handler（失败告警）"。一个 logger 同时挂这几个 handler，跑用例时既能在终端看，又能事后翻日志文件。

【面试考察】

面试官："logging 的四大组件分别负责什么？一个 logger 能同时输出到控制台和文件吗？"

参考回答框架：
1. logger 产生日志、handler 决定输出位置、filter 过滤、formatter 决定格式。
2. 能——logger 可以 addHandler 多个 handler，每个 handler 独立配置目的地和格式。

【易错点】

| 误区 | 纠正 |
|------|------|
| handler 和 formatter 分不清 | handler = 往哪写（文件/控制台），formatter = 写成什么样 |
| 以为一个 logger 只能输出一处 | 一个 logger 可挂多个 handler，实现多目的地 |

【我的理解】
> （"logger 产生日志、handler 决定往哪写、formatter 决定长什么样"——如果只想让日志输出到文件，最少需要哪几个组件配合？）

## 四、logging.basicConfig() 与 format

### 知识点 4：basicConfig 参数与 format 格式符

【课程原话/定义】

`logging.basicConfig(filename, filemode, format, level)`

- **filename**：指定将日志记录到文件中，如果不指定，则默认将日志输出到控制台。
- **filemode**：指定文件打开模式，默认为 `'a'`（追加模式）。
- **format**：指定日志记录的格式。
- **level**：指定记录的最低级别，默认为 `logging.WARNING`。

format 格式符：

- `%(asctime)s` 打印日志的时间
- `%(filename)s` 打印当前模块名
- `%(lineno)d` 打印日志当前的行号
- `%(levelname)s` 打印日志级别名称
- `%(message)s` 打印日志信息

示例代码（源课程）：

```python
import logging

# 设置日志输出格式
fmt = "%(asctime)s - %(filename)s [line:%(lineno)d] - %(levelname)s - %(message)s"
# 配置日志
logging.basicConfig(filename="myLog.log", filemode="w", format=fmt, level=logging.NOTSET)
# 调用日志器触发日志信息
logging.debug('This is a debug message')
logging.info('This is an info message')
logging.warning('This is a warning message')
logging.error('This is an error message')
logging.critical('This is a critical message')
```

【为什么？】

1. `basicConfig` 是"全局一次性配置"，通常在程序入口调用一次；它背后创建默认的 root logger 并配好 handler/formatter，让 `logging.debug/info/...` 这些模块级函数能直接工作。
2. `filename` 不指定时默认输出到控制台（root logger 默认挂的 StreamHandler）。
3. `filemode='w'` 是覆盖写（每次运行清空重写），`'a'` 是追加（保留历史）——跑自动化时常用 `'w'` 保证每次结果干净，生产日志则要 `'a'` 保留历史。

【必须掌握】

- 四个参数的含义与默认值
- 不指定 filename → 控制台；filemode 默认 `'a'`
- format 各格式符含义
- basicConfig 是全局一次性配置

【企业场景】

你在企业里，测试框架入口一般有一行统一配置：`logging.basicConfig(filename="logs/run.log", filemode="w", format=fmt, level=logging.INFO)`。所有用例的日志都走这一套格式（时间戳+模块+行号+级别+信息），事后翻日志一眼定位。

【面试考察】

面试官："basicConfig 的 level 默认值是多少？不指定 filename 时日志输出到哪？"

参考回答框架：
1. level 默认 WARNING。
2. filename 不指定时输出到控制台。
3. basicConfig 只需调用一次，第二次调用默认不生效（除非 force=True）。

【易错点】

| 误区 | 纠正 |
|------|------|
| 以为不设 filename 就报错 | 默认输出到控制台，不写文件 |
| filemode 想当然以为是 'w' | 默认 'a'（追加），要覆盖必须显式 'w' |
| %(lineno)s 和 %(lineno)d 混用 | 源课程表格写 `%(lineno)s`、示例代码写 `%(lineno)d`；lineno 是整数，标准写法是 `%(lineno)d`，`%s` 靠 str() 兜底也能出但不够规范 |

【我的理解】
> （`filemode='w'` 和 `filemode='a'` 在"每天跑自动化、想保留最近 N 天日志"的需求下分别会有什么问题？你会选哪个、为什么？）
