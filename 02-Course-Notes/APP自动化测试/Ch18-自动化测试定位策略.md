## 一、App 定位方式全景

### 知识点 1：App 定位方式总表（9+ 种，比 Ch13 更全）

【课程原话/定义】

| 定位策略 | 描述 |
|------|------|
| Accessibility ID | 识别唯一 UI 元素；XCUITest 对应 accessibility-id，Android 对应 content-desc |
| Class name | iOS 以 XCUIElementType 开头；Android 对应 UIAutomator2 的 class（android.widget.TextView） |
| ID | 原生元素标识符；Android=resource-id，iOS=name |
| Name | 元素名称 |
| XPath | 用 xpath 表达式查页面 xml 路径（不推荐，存在性能问题） |
| Image | 通过匹配 base64 编码的图像文件定位元素 |
| Android UiAutomator (UiAutomator2 only) | 用 UiSelector 类定位；Appium 把 Java 代码作为字符串发到服务器执行 |
| Android View Tag (Espresso only) | 用 view tag 定位元素 |
| Android Data Matcher (Espresso only) | 用 Espresso 数据匹配器定位 |
| IOS UIAutomation | 用苹果 instruments 框架查找元素 |

【为什么？】

1. Ch13 讲的是"基础 5 种"（ID / Accessibility ID / Class / Name / XPath），本章是"全景"——补上 Image、UiAutomator、Espresso 专属、iOS UIAutomation 等进阶/引擎专属策略。
2. 标注 "(UiAutomator2 only)" / "(Espresso only)" 很关键：这些策略只在对应引擎下有效，换引擎（如 iOS 用 XCUITest）就用不了。
3. XPath 标"不推荐，性能问题"——和 Ch13 的"兜底"定位一致。

【必须掌握】

- App 定位策略全景（基础 5 + Image + UiAutomator + Espresso 专属）
- 引擎专属策略的边界（only 标注）

【企业场景】

你在企业里，默认用 ID / Accessibility ID；遇到原生 ID 缺失、又是 UiAutomator2 引擎时，用 UiAutomator 的 UiSelector（如 `new UiSelector().text("xxx")`）兜底。Espresso 专属的 View Tag / Data Matcher 只在"项目本来就用 Espresso 做单测"时才可能用到。

【面试考察】

面试官："Appium 支持哪些定位方式？哪些是引擎专属的？"

参考回答框架：通用有 ID / Accessibility ID / Class / Name / XPath / Image；引擎专属有 Android UiAutomator(UiSelector)、Android View Tag / Data Matcher(Espresso)、IOS UIAutomation。专属策略换引擎失效。

【易错点】

| 误区 | 纠正 |
|------|------|
| 以为所有定位方式全平台通用 | UiAutomator / Espresso 专属只对 Android 特定引擎有效，iOS 用不了 |
| 滥用 XPath | XPath 有性能问题且脆，官方标"不推荐"，只兜底 |

【我的理解】

> （"Android UiAutomator (UiAutomator2 only)" 里的 only 是什么意思？为什么不能拿到 iOS 上用？）

## 二、Web 定位方式

### 知识点 2：Web 定位方式总表（8 种）

【课程原话/定义】

| 定位策略 | 描述 |
|------|------|
| class name | 通过 class 属性定位 |
| css selector | 通过匹配 css selector 定位 |
| id | 通过 id 属性匹配 |
| name | 通过 name 属性定位 |
| link text | 通过 text 标签中间的文本定位 |
| partial link text | 通过 text 标签中间文本的部分内容定位 |
| tag name | 通过 tag 名称定位 |
| xpath | 通过 xpath 表达式匹配 |

【为什么？】

1. App 和 Web 定位体系对照：Web 有 css selector、link text / partial link text（浏览器特有），App 有 Accessibility ID、UiAutomator（移动特有）。
2. link text / partial link text 只对 `<a>` 标签有效；css selector 是 Web 端最灵活高效的。
3. 记住对照关系，跨 Web/App 自动化时能快速切换心智。

【必须掌握】

- Web 8 种定位 + css selector / link text 特有
- App vs Web 定位对照

【企业场景】

你在企业里，做 Web 自动化用 css selector（快、稳），做 App 用 ID / Accessibility ID。面试常问"Web 和 App 定位方式有什么区别"，这张对照表就是答案。

【面试考察】

面试官："Web 定位和 App 定位方式有什么异同？"

参考回答框架：共同有 id / name / class / xpath；Web 特有 css selector、link text、partial link text、tag name；App 特有 Accessibility ID、UiAutomator、Image、Espresso 专属。

【易错点】

| 误区 | 纠正 |
|------|------|
| link text 能定位任意元素 | link text / partial link text 只对 `<a>` 标签有效 |
| App 用 css selector | App 没有 css selector，它是 Web 特有 |

【我的理解】

> （为什么 Web 有 css selector 而 App 没有？css selector 定位的本质依赖什么？）

## 三、选择定位器通用原则

### 知识点 3：优先稳定唯一，避免易变

【课程原话/定义】

- 优先使用稳定、唯一的定位方式：Web 端有唯一 id 或 name 最稳；移动端有唯一 Accessibility ID（content-desc）优先。
- 避免易变属性：class name 只在特殊情况下用（多元素共享类名）。
- 使用层级结构定位：XPath、CSS。
- 适当利用文本内容。

【为什么？】

1. 定位策略的稳定性排序：唯一 id > 语义属性（content-desc / accessibility-id）> 文本 > 类名 > 层级 XPath。
2. class name 易变因为"一类元素共享一个类名"，列表项几百个元素都是 android.widget.TextView，定位不唯一。
3. 文本内容（text）直观但随文案/多语言变，只能"适当利用"。

【必须掌握】

- 稳定性排序 + 为什么
- class name 为什么易变

【企业场景】

你在企业里，写定位时脑子里过一遍优先级：这个元素有没有唯一 id？没有就看 content-desc；再没有才考虑 text（且评估文案会不会改）；class name 和 XPath 最后兜底。这条原则能显著降低"用例上线一周就因定位失效而红"的概率。

【面试考察】

面试官："选择定位策略的优先级是什么？为什么 class name 要慎用？"

参考回答框架：稳定唯一优先（id / content-desc），避免易变属性（class name 多元素共享、text 随文案变），层级定位兜底。class name 不唯一所以慎用。

【易错点】

| 误区 | 纠正 |
|------|------|
| 能定位就行，不管稳不稳 | 定位"能跑"不等于"能长期跑"，稳定性是第一原则 |
| class name 当主定位 | class name 多个元素共享，不唯一，只能特殊场景用 |

【我的理解】

> （为什么"能定位到"不等于"定位策略好"？举一个用 text 定位、App 改文案后用例挂掉的例子。）

## 四、元素定位不到的原因和处理

### 知识点 4：定位不到 6 类原因 + 解决方案

【课程原话/定义】

原因：定位信息错误、元素未加载完成、元素隐藏不可见、定位策略不准确、Appium 和 app 版本不兼容、设备连接或设置问题。

| 原因 | 解决方案 |
|------|------|
| 定位不正确 | 在定位工具中先测试定位表达式是否正确 |
| 存在动态 ID | 定位方式使用 css 或 xpath 的相对定位 |
| 页面还没有加载完成 | 添加死等验证，用显式等待或隐式等待优化 |
| 页面有 iframe | 切换到 iframe 后定位 |
| 页面切换 window | 切换到对应窗口后定位 |
| 要定位元素为隐藏元素 | 使用 js 操作该元素 |
| 定位到的元素不唯一 | 用 css/xpath 相对定位（父级/子级/兄弟/索引），或用 find_elements 遍历 |

【为什么？】

1. 定位不到是"结果"，根因分三类：①定位器错（属性名/值写错、动态 ID、不唯一）②时机错（没加载完、还没切 iframe/window）③状态错（隐藏）。
2. 每个解决方案对应一个根因：动态 ID→相对定位；没加载完→等待；iframe/window→切换上下文；隐藏→js。
3. 这套"原因→方案"表是排错地图，避免"定位不到就盲目换定位器"。

【必须掌握】

- 6 类原因 + 解决方案表
- iframe/window 要切换上下文，不是换定位器
- 动态 ID 用相对定位

【企业场景】

你在企业里，遇到定位不到，先别急着换定位方式，按表排查：是不是没等加载（加显式等待）？是不是在 iframe 里（Web）？是不是动态 ID（用相对定位）？多数定位失败是"时机"和"上下文"问题，不是定位器本身错。

【面试考察】

面试官："元素定位不到，你通常怎么排查？"

参考回答框架：先确认定位表达式对不对（工具里验证），再查时机（是否加载完/加等待）、上下文（iframe/window 切换）、动态 ID（相对定位）、隐藏元素（js 操作）。

【易错点】

| 误区 | 纠正 |
|------|------|
| 定位不到就换定位器 | 先定位根因（时机/上下文/动态 ID），很多不是定位器问题 |
| 在 iframe 里直接定位 | 必须先 switch_to frame，否则永远找不到 |

【我的理解】

> （"页面有 iframe"导致定位不到，为什么换定位器没用？必须做什么操作？（提示：Web 端上下文切换））

## 五、等待机制的场景

### 知识点 5：动态出现 / 特定特征 → 隐式 + 显式

【课程原话/定义】

场景：控件动态出现、控件出现特定特征。

解决：元素定位结合隐式等待与显式等待。

【为什么？】

1. 这是 Ch14 三种等待在"定位"场景的落地：元素动态出现（异步加载）→ 不能定位完立即操作，要等。
2. 隐式等待兜底"找得到"，显式等待保证"特定条件满足"（如可点击、文本出现）。
3. 两者结合是标准姿势：全局隐式 + 关键点显式。

【必须掌握】

- 动态出现场景为什么要等
- 隐式 + 显式结合

【企业场景】

你在企业里，凡是"点按钮后异步加载列表/弹窗"的地方，都要在定位目标元素前加显式等待（等元素可点击/可见），否则用例跑得快一点就偶发失败，这种"偶发"最难查。

【面试考察】

面试官："什么时候必须用显式等待？"

参考回答框架：控件动态出现（异步加载）、需等待特定特征（可点击/文本出现）时，用显式等待等具体条件；隐式等待只保证元素"在 DOM 里"，不保证"可交互"。

【易错点】

| 误区 | 纠正 |
|------|------|
| 只靠隐式等待 | 隐式等待只保证找到元素，不保证可交互，动态控件要显式等待 |
| 用 sleep 代替显式等待 | sleep 固定时长，要么浪费要么不够，显式等待按条件自适应 |

【我的理解】

> （"控件动态出现"为什么隐式等待不够？隐式等待和显式等待各保证什么？）

## 六、特殊控件定位

### 知识点 6：alert / toast / 下拉框日期 / 文件上传

【课程原话/定义】

- Web alert 弹框：`driver.switchTo().alert()` 处理。
- App toast 提示框：`driver.page_source` 拿布局结构，分析 toast 组件标签，用 id/text/class + xpath 定位，结合隐式等待。
- 下拉框 / 日期控件（`<input>` 标签组合）：引入 JS 注入技术解决。
- 文件上传（input 标签）：`send_keys()` 直接传文件路径。

【为什么？】

1. 这四类控件"特殊"在：普通 find_element 定位不到或操作不了，需要特殊手段。
2. Web alert 不在 DOM 里，是浏览器原生弹窗，要 switch_to.alert；App toast 短暂显示、无稳定 id，要从 page_source 里抓。
3. 下拉框/日期是 input 组合（readonly 输入框 + 隐藏弹层），用 JS 注入绕过；文件上传是 `<input type=file>`，直接 send_keys 文件路径即可。

【必须掌握】

- Web alert → switch_to.alert
- App toast → page_source + xpath + 隐式等待
- 文件上传 → send_keys 文件路径

【企业场景】

你在企业里，Web 遇到 alert/confirm 弹窗要 switch_to.alert 接受/取消；App 的 toast（"操作成功"）无法直接定位，要从 page_source 抓文本断言；上传附件/头像用 input 直接 send_keys 文件绝对路径，比模拟点击文件选择器省事得多。

【面试考察】

面试官："App 的 toast 提示怎么定位断言？Web 的 alert 怎么处理？"

参考回答框架：toast 从 driver.page_source 拿布局，用 xpath 按 text 定位并结合隐式等待；Web alert 用 driver.switchTo().alert() 切到原生弹窗再 accept/dismiss。

【易错点】

| 误区 | 纠正 |
|------|------|
| 用 find_element 定位 Web alert | alert 是浏览器原生弹窗，不在 DOM，必须 switch_to.alert |
| 以为 toast 有稳定 id | toast 短暂显示、id 不稳定，要从 page_source 抓 |

【我的理解】

> （Web 的 alert 为什么不能用普通定位？App 的 toast 为什么"短暂显示"导致难定位？）
