## 一、显式等待为什么"高级"

### 知识点 1：显式等待的优势

【课程原话/定义】

显式等待：在执行脚本时，显式等待某个特定条件发生或元素可用，确保脚本在合适时机执行。一定时间后判断条件，满足则继续、超时则抛异常。

四大优势：

1. **精准等待**：等某个特定条件发生，测试在最合适的时机执行，提高稳定性。
2. **灵活性**：等待时间可按需调整，适应不同网络/服务器响应。
3. **超时处理**：设置最长等待时间，超时抛异常，及时检测超时。
4. **提高稳定性**：确保页面/元素加载完毕再执行。

【为什么？】

1. 显式等待把"等多久"从"猜一个固定值"升级成"等某个条件成立"——这是它和强制等待（sleep）最本质的差别。
2. "条件"可精确到"元素可点击""文本出现""窗口数量"等业务状态，而不是笼统的"时间到了"。
3. 它是稳定性工程的核心：异步加载、动画、网络响应时间不确定时，显式等待自适应，比 sleep 又快又稳。

【必须掌握】

- 显式等待 = 等"条件"而非等"时间"
- 四大优势：精准 / 灵活 / 超时 / 稳定

【企业场景】

你在企业里，点按钮后异步加载列表、登录后跳转、动画播完才可点——这些"元素最终会就绪但时间不定"的地方，一律用显式等待等具体条件。这是把"偶发失败"消灭在源头的标准做法。

【面试考察】

面试官："显式等待相比强制等待、隐式等待，优势在哪？"

参考回答框架：强制等待是无脑固定睡、隐式等待只全局等"元素存在"；显式等待针对特定元素等特定条件（可点击/可见/文本出现），精准、灵活、可超时处理，稳定性最高。

【易错点】

| 误区 | 纠正 |
|------|------|
| 显式等待 = 高级版 sleep | 显式等待等的是**条件**，条件早满足就早返回，不是固定睡 |
| 只背"比 sleep 好" | 要说清"精准/灵活/超时/稳定"四点的具体含义 |

【我的理解】

> （"等条件"和"等时间"有什么本质区别？元素 0.5 秒就绪时，`sleep(3)` 和 `WebDriverWait(driver,3).until(可点击)` 各浪费了多少时间？）

## 二、WebDriverWait 用法

### 知识点 2：构造参数 + until / until_not

【课程原话/定义】

Python：

```python
WebDriverWait(driver, timeout, poll_frequency=0.5, ignored_exceptions=None)
```

| 参数 | 含义 |
|------|------|
| driver | 浏览器/App 驱动 |
| timeout | 最长超时时间（默认秒） |
| poll_frequency | 检测间隔步长，默认 0.5s |
| ignored_exceptions | 超时后抛出的异常（默认 NoSuchElementException） |

两个核心方法：

- `until(method, message='')`：某元素出现或条件成立则继续执行。
- `until_not(method, message='')`：某元素消失或条件不成立则继续执行。

其中 method 在等待期间每隔 poll_frequency 调用一次，直到返回值不是 False；超时抛 TimeoutException，message 传入异常信息。

【为什么？】

1. poll_frequency 决定"多久查一次"——它让显式等待不是"死等满 timeout"，而是"轮询到条件满足就提前返回"。
2. ignored_exceptions 让你忽略某些异常（如元素暂时还没出现的 NoSuchElement），而不是一抛就失败。
3. until（等成立）和 until_not（等消失/不成立）是两个方向，多数场景用 until。

【必须掌握】

- WebDriverWait 四个构造参数（重点 poll_frequency 轮询）
- until（条件成立继续）/ until_not（条件不成立继续）

【企业场景】

你在企业里，默认用 `WebDriverWait(driver, 10)` 就够了（poll_frequency 用默认 0.5）；要"等某个加载遮罩消失"这类反向场景用 until_not；message 参数填业务描述，超时报错时一眼看出是哪步没等到。

【面试考察】

面试官："WebDriverWait 的 poll_frequency 是什么？until 和 until_not 有什么区别？"

参考回答框架：poll_frequency 是轮询间隔（默认 0.5s），等待期间每隔这么久查一次条件；until 等条件成立、until_not 等条件不成立（如元素消失），超时抛 TimeoutException。

【易错点】

| 误区 | 纠正 |
|------|------|
| 以为显式等待"死等满 timeout" | 它是**轮询**（poll_frequency），条件早满足就提前返回 |
| until / until_not 方向搞反 | until 等"成立/出现"，until_not 等"消失/不成立" |
| 单位：Python timeout 是秒 | Python 秒；Java 用 Duration.ofSeconds(10)，别把毫秒当秒 |

【我的理解】

> （poll_frequency=0.5 意味着什么？如果元素 1.2 秒才就绪，这 1.2 秒里 method 被调用了几次？）

## 三、等待条件 expected_conditions

### 知识点 3：条件大全与选择

【课程原话/定义】

WebDriverWait 配套的 expected_conditions（EC）提供一系列条件，用于等元素的特定状态：

| 条件（Python / Java） | 含义 |
|------|------|
| presence_of_element_located / presenceOfElementLocated | 元素出现在 DOM 树里（不代表可见） |
| visibility_of_element_located / visibilityOfElementLocated | 元素存在于 DOM 且可见（非隐藏、宽高不为 0） |
| element_to_be_clickable / elementToBeClickable | 元素可见且启用，可响应点击 |
| text_to_be_present_in_element / textToBePresentInElement | 元素包含指定文本 |
| number_of_windows_to_be / numberOfWindowsToBe | 打开的窗口数量达到特定值 |
| title_contains / titleContains | 窗口标题包含特定文本 |

【为什么？】

1. "存在"（presence）和"可见"（visibility）是递进关系：presence 只看有没有进 DOM，visibility 还要非隐藏、有宽高——这正是 Ch14 知识点 4"元素在 DOM ≠ 可交互"的官方对应条件。
2. element_to_be_clickable 是最常用的条件，它 = 可见 + 启用，直接对应"我要点这个按钮"。
3. 选对条件 = 表达正确的业务意图：要输入就等 presence，要点击就等 clickable，要断言文案就等 text_to_be_present。

【必须掌握】

- presence（在 DOM）/ visibility（可见）/ clickable（可点击）三者的递进区别
- element_to_be_clickable 最常用
- 其它条件（text/window/title）知道存在即可

【企业场景】

你在企业里，点按钮前用 `element_to_be_clickable`；断言某段文案加载出来用 `text_to_be_present_in_element`；判断元素"是否已从页面消失"用 visibility 的反向 + until_not。条件选错（如该用 clickable 却用 presence）会导致"元素找到了但点不了"。

【面试考察】

面试官："presence_of_element_located 和 visibility_of_element_located 有什么区别？"

参考回答框架：presence 只判断元素进了 DOM 树（不一定可见），visibility 要求元素非隐藏且宽高不为 0（真正可见）。点击前要用 element_to_be_clickable（可见 + 启用），否则可能"找到了但点不了"。

【易错点】

| 误区 | 纠正 |
|------|------|
| presence = 可见 | presence 只代表"在 DOM 树里"，可能隐藏、宽高为 0，≠ 可见 |
| 点击前用 presence 等待 | 应等 element_to_be_clickable（可见且启用），presence 只保证"找得到" |
| 条件对象写错 | until 里要传 expected_conditions 的条件对象（如 element_to_be_clickable((by,值))），注意定位符是**元组** (AppiumBy.xxx, "值") |

【我的理解】

> （Ch14 说过"元素在 DOM ≠ 可交互"，本章的 presence 和 clickable 分别对应这条结论的哪一半？为什么点按钮前必须等 clickable 而不是 presence？）

## 四、lambda 表达式等待

### 知识点 4：lambda 自定义等待条件

【课程原话/定义】

WebDriverWait 可结合 lambda 表达式，直到表达式通过再返回所等待的元素。

Python：

```python
WebDriverWait(driver, time).until(
    lambda x: x.find_element(AppiumBy.ID, "someId")
)
```

Java：

```java
WebElement element = wait.until((driver) -> driver.findElement(By.id("someId")));
```

【为什么？】

1. expected_conditions 是**预置条件**，lambda 让你写**任意自定义条件**——只要函数返回"非 False/非 None"就继续，返回 None/False 就重试。
2. lambda 里的参数 x / driver 就是 WebDriverWait 传入的 driver 实例，所以能直接调 find_element。
3. 适合"EC 没有现成条件"的场景（如自定义的判断逻辑、组合条件），比 EC 更灵活但可读性稍差。

【必须掌握】

- `until(lambda x: x.find_element(...))` 的写法
- lambda 参数是 driver 实例

【企业场景】

你在企业里，遇到 EC 覆盖不了的条件（如"等某个自定义属性变 true""等列表数量 >= N"），用 lambda 写自定义谓词。日常能用 EC 就用 EC（可读性好），EC 不够才上 lambda。

【面试考察】

面试官："显式等待除了 expected_conditions，还能怎么自定义条件？"

参考回答框架：用 lambda 表达式，`until(lambda x: x.find_element(...))`，x 是 driver 实例，返回非空则继续、空则重试；适合 EC 没有现成条件的自定义判断。

【易错点】

| 误区 | 纠正 |
|------|------|
| lambda 参数不是 driver | until 会把 driver 传给 lambda，参数 x 就是 driver，可直接 find_element |
| lambda 返回 WebElement 以为会失败 | 返回元素（非 False/None）就视为"条件成立"，正常返回 |

【我的理解】

> （`until(lambda x: x.find_element(AppiumBy.ID, "someId"))` 里，如果元素一直没出现，这个 lambda 反复返回什么、直到什么时候结束？）
