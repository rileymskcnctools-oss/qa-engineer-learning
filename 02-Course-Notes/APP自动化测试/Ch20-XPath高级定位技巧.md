# Ch20 - XPath 高级定位技巧

## 课程来源

## 一、XPath 高阶定位概览

### 知识点 1：contains() 函数（包含定位）

【课程原话/定义】

XPath 是一种用于在 XML 文档中定位和选择节点的语言，通过路径表达式指定节点位置，并支持各种条件过滤。三种高阶定位方法：

1. **逻辑运算符**（and / or / not）：组合多个条件。
2. **轴定位**：通过预定义轴（子节点、父节点、兄弟节点等）获取相对当前节点的其他节点集合。
3. **contains() 函数**：匹配属性值中包含某字符串的元素。

contains() 使用格式：`//*[contains(@属性, "属性值")]`

> 示例：雪球搜索"阿里"，`//*[contains(@text, "阿里")]` 匹配 text 属性值中包含"阿里"的元素，共 12 个。
> 📷 【截图占位】雪球搜索框输入"阿里"后的界面

【为什么？】

1. 精确匹配 `@text="阿里巴巴"` 要求值**完全相等**；contains() 是**子串包含**，`contains(@text,"阿里")` 能同时命中"阿里""阿里巴巴""阿里健康"等——适合文案不确定、只想"框住一批"的场景。
2. 定位的本质还是"按属性筛节点"，contains() 只是把"等于"换成了"包含"这个更宽松的谓词。
3. **contains() 命中多个是常态不是例外**（例子里 12 个），所以它要么配合其他条件缩小范围，要么用 find_elements 拿列表。

【必须掌握】

- `//*[contains(@属性, "属性值")]` 格式，属性名必须加 `@`
- contains() 是"包含"不是"等于"，很容易命中多个元素

【企业场景】

你在企业里，遇到文案带动态后缀（如"已选 3 件""余额 ¥12.50"）无法精确匹配时，用 `contains(@text,"已选")` 或 `contains(@text,"余额")` 锁定元素。要精确到某一个，再叠加 and 条件（见知识点 4）。

【面试考察】

面试官："contains() 和 `@text='xx'` 有什么区别？contains() 定位到的元素有什么特点？"

参考回答框架：`@text='xx'` 是精确相等，contains() 是子串包含、更宽松；contains() 命中多个元素是常态，需要叠加其他条件或配合 find_elements 使用。

【易错点】

| 误区 | 纠正 |
|------|------|
| contains() 是精确匹配 | 它是**包含**匹配，`contains(@text,"阿里")` 能命中"阿里巴巴"等所有含"阿里"的元素 |
| 属性名不加 @ | contains() 里的属性名必须 `@text` 这样带 @，写成 `contains(text,...)` 无效 |
| 以为 contains() 只返回一个 | 通常返回**多个**，例子里就有 12 个 |

【我的理解】

> （`//*[contains(@text,"阿里")]` 会命中"阿里""阿里巴巴""阿里云"，如果要只命中"阿里巴巴"这一个，该怎么改表达式？（提示：换精确匹配 or 叠加条件））

## 二、XPath 轴定位——父子 / 祖孙关系

### 知识点 2：parent:: / child:: / ancestor:: 轴

【课程原话/定义】

XPath 轴根据节点之间的关系选择节点：通过一个节点，定位到它的兄弟、父节点、祖先节点等。

| 关系 | 表达式 |
|------|--------|
| 父节点 | `/当前节点/..` 或 `/当前节点/parent::*` |
| 子节点 | `/当前节点/child::*` 或 `/当前节点/*` |
| 爷节点（父的父） | `/当前节点/../..` 或 `/当前节点/parent::*/parent::*` |
| 孙节点（子的子） | `/当前节点/child::*/child::*` 或 `/当前节点/*/*` |
| 所有祖先节点 | `/当前节点/ancestor::*` |
| 指定类型的祖先 | `/当前节点/ancestor::android.widget.LinearLayout` |
| 最近的指定祖先 | `/当前节点/ancestor::android.widget.LinearLayout[1]` |

> 示例：定位 text 为"阿里巴巴"元素的父节点 → `//*[@text="阿里巴巴"]/..` 或 `//*[@text="阿里巴巴"]/parent::*`
> 📷 【截图占位】"阿里巴巴"元素的父节点
> 📷 【截图占位】stock_layout 的子节点 / stockName 的爷节点

【为什么？】

1. **不是所有元素都有稳定 id/text**，很多时候唯一能定位的锚点是它的**邻居**——先定位一个能唯一识别的兄弟/子元素，再沿轴"走一步"到目标。
2. `..` 是 `parent::*` 的简写、`*` 是 `child::*` 的简写；`parent::*/parent::*` 就是"向上走两层"。
3. `ancestor::*` 返回**所有**祖先（例子里 9 个），加 `[1]` 取**距离当前节点最近**的那一个——这里的 `[1]` 不是数组下标，而是"向外数一层"。

【必须掌握】

- 父/子/爷/孙/祖先五种轴对应的表达式（`..`、`*`、`parent::`、`child::`、`ancestor::`）
- `ancestor::xxx[1]` 里 `[1]` 的含义（最近一个，不是下标 0 起）

【企业场景】

你在企业里，某个"删除"按钮自己没 id、没 text，但旁边有一行标题文本是唯一的。定位思路就是：`//*[@text="这条标题"]/parent::*/parent::*` 走到整行，再往下找按钮。轴定位让你能"先锚定、再导航"，而不是要求每个目标元素本身可定位。

【面试考察】

面试官："`ancestor::*` 和 `ancestor::xxx[1]` 有什么区别？`[1]` 是什么意思？"

参考回答框架：`ancestor::*` 返回所有祖先节点；加 `[1]` 只取距离当前节点最近的那一个。这里的 `[1]` 表示"从当前元素向外数一层"，不是数组下标。

【易错点】

| 误区 | 纠正 |
|------|------|
| 把 `[1]` 当数组下标（从 0 数） | 轴里的 `[1]` 是"向外/向上一层"，不是取索引 1 |
| `child::*` 和 `*` 分不清谁是谁的简写 | 两者等价，`*` 是 `child::*` 的简写；`..` 是 `parent::*` 的简写 |
| 以为 `ancestor::*` 只返回一个 | 返回**所有**祖先（例子里 9 个 LinearLayout），要精确就加 `[1]` 或指定类名 |

【我的理解】

> （为什么"爷节点"要写 `parent::*/parent::*` 或 `/../..`？能不能直接写一个 `ancestor::*[2]` 取"向上两层"？试试对比这两种思路的区别。）

## 三、XPath 轴定位——兄弟关系

### 知识点 3：following-sibling:: / preceding-sibling::

【课程原话/定义】

- 定位当前节点**之后**的所有兄弟节点：`/当前节点/following-sibling::*`
- 定位当前节点**之前**的所有兄弟节点：`/当前节点/preceding-sibling::*`
- 从多个兄弟中筛一个：加条件过滤
  - `//*[@resource-id=".../stock_layout"]/following-sibling::*[@resource-id=".../price_layout"]`
  - `//*[@resource-id=".../add_attention"]/preceding-sibling::*[@resource-id=".../stock_layout"]`

> 📷 【截图占位】stock_layout 之后的兄弟节点 / add_attention 之前的兄弟节点

【为什么？】

1. 列表项往往**结构相同、属性相同**（每项都有 stock_layout、price_layout），单个元素无法唯一定位；兄弟轴让你"以其中一个为锚，横向找它的兄弟"。
2. following-sibling 是**向后**（文档顺序的下一个），preceding-sibling 是**向前**（上一个），方向别搞反。
3. 兄弟多时直接加 `[@resource-id="..."]` 二次过滤，把"所有兄弟"收窄到"我要的那一个"。

【必须掌握】

- following-sibling（之后）/ preceding-sibling（之前）的方向
- 兄弟轴 + 条件过滤的组合写法

【企业场景】

你在企业里，一条列表有多行"商品卡"，每张卡里"价格""加自选""关注"结构都一样。定位某一行里的价格，就用该行唯一锚点 + `following-sibling::*[@resource-id=".../price_layout"]`，而不是靠 index 数第几个（index 脆弱）。

【面试考察】

面试官："following-sibling 和 preceding-sibling 有什么区别？什么时候用？"

参考回答框架：前者定位当前节点之后（文档顺序下一个）的兄弟，后者定位之前的兄弟。用于列表项结构相同、靠兄弟关系横向定位的场景，加条件可精确到某一个。

【易错点】

| 误区 | 纠正 |
|------|------|
| following / preceding 方向搞反 | following-sibling 是**之后**（下一个），preceding-sibling 是**之前**（上一个） |
| 兄弟轴返回单个 | 返回**多个**兄弟，要精确需叠加 `[@属性]` 条件过滤 |
| 用 index 定位列表第 N 项 | index 脆弱（增删项就错位），优先用唯一锚点 + 兄弟轴 + 属性过滤 |

【我的理解】

> （`//*[@resource-id=".../add_attention"]/preceding-sibling::*[@resource-id=".../stock_layout"]` 这句话，先定位到了谁、然后横向走到了谁？为什么能保证"唯一"？）

## 四、XPath 运算符

### 知识点 4：and / or（交集与并集）

【课程原话/定义】

- **AND**：两个条件都成立才选中，取**交集**。`//*[@resource-id=".../stockName" and @text="阿里巴巴"]`
- **OR**：任一条件成立即选中，取**并集**。`//*[@resource-id=".../stock_layout" or @text="加自选"]`

> 📷 【截图占位】AND 定位的红框元素（stockName 且 text=阿里巴巴）/ OR 定位到的 6 个元素

【为什么？】

1. 单属性定位不唯一时，用 AND 叠加条件收窄范围——"既要 resource-id 是这个、又要 text 是那个"。
2. OR 是"同一类目标一次拿全"（多个候选属性，命中任一都算），适合"元素可能是 A 也可能是 B"的容错定位。
3. 语义和编程里的逻辑运算一致：AND 交集、OR 并集；注意 XPath 里是**小写** `and` / `or`。

【必须掌握】

- `and`（交集，两个条件都满足）/ `or`（并集，任一满足）
- 小写 and / or，属性条件用 `[]` 包裹

【企业场景】

你在企业里，同一页面有多个 stockName（不同股票），要定位"阿里巴巴"那一个，就 `[@resource-id=".../stockName" and @text="阿里巴巴"]` 两个条件收窄到唯一。反过来，某些按钮文案会在"关注"/"加自选"间切换，用 `or` 兼容两种文案，避免文案一改用例就挂。

【面试考察】

面试官："XPath 里的 and 和 or 分别什么语义？什么时候用？"

参考回答框架：and 是两个条件同时满足（交集，用来收窄定位到唯一）；or 是任一满足（并集，用来兼容多个候选文案/属性）。语义与编程逻辑运算一致，注意小写。

【易错点】

| 误区 | 纠正 |
|------|------|
| 大写 AND / OR | XPath 是**小写** `and` / `or`，大写不识别 |
| and 和 or 的并集/交集搞反 | and = 交集（都满足），or = 并集（任一满足） |
| 用 and 代替"或"的场景 | 文案可能变（关注/加自选）要用 or 兼容，用 and 会定位不到 |

【我的理解】

> （"阿里巴巴"页面有 6 个 stockName，为什么 `[@resource-id=".../stockName" and @text="阿里巴巴"]` 能唯一命中？这个 and 各自过滤掉了哪些候选？）
