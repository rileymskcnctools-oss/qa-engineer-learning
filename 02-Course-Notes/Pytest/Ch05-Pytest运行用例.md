## 一、PyCharm 界面化运行

### 知识点1：四种粒度的运行方式

【课程原话/定义】
利用 PyCharm 可以界面化运行：某个/多个用例包、某个/多个用例模块、某个/多个用例类、某个/多个用例方法。

【为什么？】
PyCharm 的界面化运行本质上是 IDE 帮你拼装 pytest 命令行参数。理解四种粒度对应的是 pytest 的路径解析能力——pytest 可以按目录（包）、文件（模块）、类、方法逐级精确定位测试目标。这在企业里意味着你可以快速调试单个失败的用例而不是重跑整个测试套件。

【必须掌握】
- 四种运行粒度：包 → 模块 → 类 → 方法
- PyCharm 右键 → Run 'pytest in xxx' 的操作方式
- 界面运行和命令行运行的对应关系

【企业场景】
你在 CI 流水线中跑了 200 条用例，其中 3 条失败。你不可能重跑全部 200 条来定位问题。这时候你在 PyCharm 中直接右键失败的用例方法，单独运行那一条，30 秒内就能进调试模式看变量状态。四种粒度本质上是从粗到细的筛选漏斗。

【面试考察】
面试官："你平时怎么运行 Pytest 用例？有哪些粒度？"
参考回答框架：① PyCharm 右键运行（开发调试阶段）② 命令行运行（CI/批量回归阶段）③ 四种粒度：包级 `pytest tests/`、模块级 `pytest test_login.py`、类级 `pytest test_login.py::TestLogin`、方法级 `pytest test_login.py::TestLogin::test_valid_login` ④ 每种粒度的适用场景

【易错点】

| 易混淆 | 区别 |
|------|------|
| 运行"包" vs 运行"模块" | 包 = 整个目录递归运行；模块 = 单个 .py 文件 |
| 运行"类" vs 运行"方法" | 类 = 类内所有 test_ 方法；方法 = 精确到一条用例 |
| PyCharm 右键 vs Terminal | PyCharm 本质也是调 pytest 命令，只是帮你拼好了参数 |

## 二、命令行方式运行

### 知识点2：pytest 命令行语法

【课程原话/定义】
- 执行包下所有用例：`pytest 包名`
- 执行单独模块：`pytest 文件名.py`
- 运行类：`pytest 文件名.py::类名`
- 运行方法：`pytest 文件名.py::类名::方法名`

【为什么？】
双冒号 `::` 是 pytest 的路径分隔符，含义类似于 Python 的点号在模块路径中的角色。pytest 用 `::` 而不是 `.` 是因为测试方法本身也叫 test_xxx，用点号会和模块路径混淆。理解 `::` 语法后，你可以用一条命令精确命中任何粒度的用例，这在 Jenkins、GitHub Actions 等 CI 脚本中非常重要。

【必须掌握】
- `pytest 包名` — 递归运行目录下所有 test_*.py / *_test.py
- `pytest 文件名.py` — 运行单个模块
- `pytest 文件名.py::类名` — 运行单个类
- `pytest 文件名.py::类名::方法名` — 运行单个方法
- 双冒号 `::` 的含义和用法

【企业场景】
你在 Jenkins 的构建脚本中写了 `pytest tests/`，每次提交跑全部用例要 15 分钟。后来改成分模块运行：冒烟测试 2 分钟，全量回归晚上跑。Jenkinsfile 里写的是 `pytest tests/smoke/` 和 `pytest tests/regression/`，用包级粒度控制执行范围。

【面试考察】
面试官："`pytest tests/test_user.py::TestUser::test_login` 中 `::` 的作用是什么？"
参考回答框架：① `::` 是 pytest 的测试项路径分隔符 ② 第一个 `::` 分隔文件名和类名 ③ 第二个 `::` 分隔类名和方法名 ④ 与 Python 的 `.` 不同，`::` 避免了模块路径和测试方法名的歧义

【易错点】

| 常见错误 | 正确做法 |
|------|------|
| `pytest 文件名.py.类名.方法名` | 用 `::` 不是 `.` |
| `pytest tests/` 漏了斜杠 | 包名可以带或不带尾部 `/`，但建议保持一致 |
| 方法名不加 `test_` 前缀 | pytest 只识别 `test_` 开头的方法，没加前缀不会被执行 |

## 三、常见运行结果

### 知识点3：五种运行结果的含义与区分

【课程原话/定义】
- **fail**：测试用例未通过（断言失败）
- **error**：代码中有错误、添加不正确断言等
- **pass**：测试用例通过
- **warning**：警告，不影响程序执行
- **deselect**：没有被选中

【为什么？】
区分 fail 和 error 是新手最容易搞混但最关键的概念。fail = 业务逻辑不符合预期（assert 没通过），error = 代码本身崩了（抛了未捕获的异常）。区分这二者直接影响你的 Debug 方向：fail → 查业务逻辑；error → 查代码健壮性。CI 报告中 fail 和 error 的统计也是分开的，error 通常优先级更高。

【必须掌握】
- fail vs error 的本质区别
- 每种结果对应的 pytest 输出标识（F / E / . / W / d）
- deselect 出现的场景（-m 筛选、-k 筛选等）

【企业场景】
你收到 CI 邮件通知："50 tests run, 45 passed, 3 failed, 2 errors"。你先看 2 个 error——可能是数据库连接超时导致 setUp 阶段就挂了，这比业务逻辑错误更紧急。修完 error 后再看 3 个 failed——可能是产品改了字段名导致断言失败。区分优先级是测试工程师的日常。

【面试考察】
面试官："fail 和 error 有什么区别？什么情况下你会优先修 error？"
参考回答框架：① fail = 断言没通过，被测功能不符合预期 ② error = 代码抛异常，测试本身都没跑完 ③ error 更优先，因为 error 可能阻塞后续所有用例（如 fixture 中的数据库连接失败）④ 举例：`assert 1+1==3` 是 fail；`x = 1/0` 是 error

【易错点】

| 结果类型 | pytest 标识 | 含义 | 例子 |
|------|------|------|------|
| pass | `.` | 用例通过 | assert 1+1==2 |
| fail | `F` | 断言失败 | assert add(1,1)==3 |
| error | `E` | 代码异常 | 变量未定义、除零、导入失败 |
| warning | `W` | 警告不阻塞 | 使用了废弃的 API |
| deselect | `d` | 未被选中 | -m 筛选排除了该用例 |
