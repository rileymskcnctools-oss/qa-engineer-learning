## 一、什么是自动化测试策略

### 【课程原话/定义】

> 自动化测试策略（Automation Testing Strategy）是指在软件测试过程中，通过自动化手段来提高测试效率和效果的计划和方法。这些策略通常涵盖：如何选择合适的自动化工具、如何设计和执行测试用例、如何管理测试数据和测试环境等内容。

### 【为什么要有"策略"而不只是"工具"？】

很多人以为自动化测试 = 会写 Selenium/Requests 脚本。但"策略"回答的是更上层的三个问题：

| 问题 | 举例 |
|------|------|
| 选什么工具 | Web 用 Selenium，App 用 Appium，接口用 Requests/RestAssured |
| 怎么设计用例 | 哪些用例值得自动化？怎么组织脚本？ |
| 怎么管数据和环境 | 测试数据怎么造、怎么隔离？测试环境怎么搭（见 [[Ch16-测试环境搭建]]）？ |

> 没有策略，自动化脚本只会越写越乱，最后变成"没人敢动的祖传代码"。

### 【必须掌握】三大价值

| 价值 | 说明 |
|------|------|
| 提高测试效率 | 机器跑得比人快，重复执行不疲劳 |
| 增强测试覆盖率 | 自动化能覆盖更多场景（遍历、参数化、大数据量） |
| 提高测试稳定性 | 脚本执行结果一致，不因人而异、不遗漏步骤 |

### 【我的理解】

> 思考：自动化"提高效率"和"提高覆盖率"是一回事吗？为什么一个团队可能"覆盖率上去了，但效率没上去"？（提示：维护成本）

## 二、用户端测试体系（Android 三层 + 工具）

> [[Ch14-分层测试策略]] 已讲"UI 组件分层测试"的三层概念（单元/集成/UI）。本节给出每一层对应的**具体工具**。

### 【必须掌握】三层测试与工具对应

| 测试层 | 工具 | 特点 |
|--------|------|------|
| 研发单元测试 | JUnit、Robolectric | 不依赖真机/模拟器 |
| 集成测试 | Espresso | 单应用快速集成测试 |
| 验收测试 | Appium、ATX/AirTest、Calabash | 跨应用测试 |

### 【为什么 Robolectric 不依赖真机/模拟器？】

Robolectric 在 JVM 上直接"模拟"了 Android 框架的行为——不需要启动模拟器或真机就能跑单元测试。好处：速度快（秒级）、能进 CI 流水线、不占设备资源。

### 【易错点】四类工具别搞混

| 工具 | 层 | 关键特征 |
|------|-----|---------|
| JUnit | 单元 | Java 最基础的单元测试框架 |
| Robolectric | 单元 | 在 JVM 上模拟 Android，不启动设备 |
| Espresso | 集成 | 单应用内快速验证 UI 交互，白盒（能访问应用内部） |
| Appium/ATX/Calabash | 验收 | 跨应用、黑盒，像真实用户一样操作整个 App |

> 📷 【截图占位】Google Android 测试体系图

### 【面试考察】

> 面试官："Android 自动化测试，JUnit、Robolectric、Espresso、Appium 有什么区别？"

**参考回答框架：** 分三层。单元层用 JUnit/Robolectric——Robolectric 在 JVM 上模拟 Android 框架，不依赖真机，速度快；集成层用 Espresso，在单应用内快速验证 UI 交互；验收层用 Appium/ATX/Calabash，跨应用、黑盒，模拟真实用户操作。选择依据是"离真机越远越快，离用户越近越真实"，从下到上速度递减、真实度递增。

### 【我的理解】

> 思考：Robolectric 和 Espresso 都能测 UI 相关逻辑，为什么一个叫"单元测试"一个叫"集成测试"？它们测的"边界"差在哪？

## 三、工具体系参考

### 3.1 Selenium

#### 【课程原话/定义】

> Selenium 是一个开源的自动化测试工具，用于 Web 应用程序的测试。它允许用户通过脚本控制浏览器的行为，从而自动执行测试用例。支持多种浏览器和操作系统，提供丰富的 API 模拟用户操作。

#### 【必须掌握】

| 维度 | 说明 |
|------|------|
| 适用 | Web 应用自动化 |
| 核心能力 | 脚本驱动浏览器：点击、输入、跳转、断言 |
| 跨平台 | 多种浏览器（Chrome/Firefox/Edge）+ 多操作系统 |

> 📷 【截图占位】Selenium 图示
> 工具对比详见 [[Ch04-测试技术体系]] 第九节工具全景。

### 3.2 Appium

#### 【课程原话/定义】

> Appium 是一个开源的自动化测试框架，用于移动应用程序的测试。支持原生应用、混合应用以及移动网页应用的自动化测试，适用于 iOS 和 Android 平台。

#### 【必须掌握】

| 维度 | 说明 |
|------|------|
| 适用 | 移动端（原生/混合/移动网页）自动化 |
| 跨平台 | iOS + Android 一套脚本 |
| 核心理念 | 基于 WebDriver 协议，跨应用、黑盒 |

> 📷 【截图占位】Appium 图示

### 3.3 智能遍历工具

#### 【必须掌握】主流智能遍历工具

| 工具 | 来源 | 用途 |
|------|------|------|
| SmartMonkey | 百度 | App 智能遍历、稳定性测试 |
| NewMonkey | 腾讯 | App 智能遍历 |
| fastbot | 头条/字节 | App 遍历 + 稳定性测试 |
| Macaca NoSmoke | 支付宝 | App 遍历 |
| Android Monkey / App Crawler | 谷歌官方 | 随机事件遍历 |
| AppCrawler | 霍格沃兹测试开发学社 | 自动遍历 App 并生成测试报告 |
| OWASP-ZAP | OWASP 社区 | Web 漏洞自动探测 |

#### 【为什么需要"智能遍历"而不是"随机乱点"？】

Android 官方的 Monkey 是纯随机事件流——乱点、乱滑，可能卡在某个页面出不来，覆盖率低。智能遍历工具（SmartMonkey、fastbot 等）用算法引导：识别当前页面的可点元素、有策略地探索路径，覆盖率更高、更容易触发崩溃和异常。

#### 【易错点】遍历工具 vs UI 自动化框架

| 维度 | UI 自动化框架（Selenium/Appium） | 智能遍历工具（Monkey/fastbot） |
|------|-------------------------------|------------------------------|
| 用例 | 有明确脚本、断言 | 无脚本，算法自动探索 |
| 目的 | 验证功能对不对 | 找崩溃、卡顿、异常 |
| 结果 | 通过/失败 | 崩溃日志、异常路径 |
| 适用 | 回归、功能验证 | 稳定性测试、兼容性测试 |

### 3.4 稳定性测试体系案例：Fastbot（字节跳动）

#### 【课程原话/定义】

> Fastbot 已广泛应用于字节客户端类产品的稳定性测试与兼容性测试。每日启动任务数超过 1 万次，每月平均发现 5 万个以上的崩溃。借助 Fastbot，发版前就能修复大部分 crash，同时在整个 DevOps 流程中扮演重要的基础服务角色。

#### 【为什么这是"体系"而不只是"工具"？】

Fastbot 不是一次性脚本，而是挂在 DevOps 流水线上的**持续性服务**：每天自动跑上万次任务 → 持续发现崩溃 → 发版前修复。这体现了自动化测试的终极形态——**和流水线结合，持续运行、持续反馈**。

#### 【面试考察】

> 面试官："你们怎么保证 App 的稳定性？"

**参考回答框架：** 三层。开发阶段做单元测试和 Espresso 集成测试；提测后跑智能遍历工具（fastbot/Monkey）做稳定性测试，自动发现崩溃；再结合兼容性测试覆盖不同机型。像字节用 fastbot 每天跑上万次任务、每月发现 5 万个崩溃，发版前修复大部分 crash。关键是把它挂进 DevOps 流水线持续跑，而不是发版前临时跑一次。

## 四、服务端测试体系

### 【必须掌握】服务端测试手段

| 手段 | 说明 |
|------|------|
| 手工测试 | 用 Postman 等工具手动发请求验证 |
| 自动化测试 | 用 Requests/RestAssured 写脚本自动验证 |
| DIFF 测试 | 新旧版本跑同一批输入，对比输出差异 |
| 流量回放 | 录制线上真实流量，在测试环境回放验证 |
| Mock | 用替身隔离依赖，解耦 + 提高覆盖率 |

### 【为什么需要 DIFF 测试和流量回放？】

服务端重构/迁移（比如换框架、换存储）时，最怕"功能看起来没变，但某些边界行为变了"。DIFF 测试和流量回放解决这个问题：

| 手段 | 做法 | 价值 |
|------|------|------|
| DIFF 测试 | 同一批请求同时打到新旧两个版本，对比响应差异 | 精确发现"哪类请求行为变了" |
| 流量回放 | 把线上真实请求录制下来，在测试环境回放 | 用真实数据验证，覆盖手工构造不了的边界 |

### 【易错点】DIFF 测试 vs 流量回放

| 维度 | DIFF 测试 | 流量回放 |
|------|----------|---------|
| 核心 | 新旧版本对比 | 录制线上流量再播放 |
| 数据来源 | 构造/录制均可 | 必须是线上真实流量 |
| 目的 | 发现行为差异 | 用真实场景验证新版本 |
| 适用 | 重构、迁移、升级 | 回归、上线前验证 |

### 【为什么用 Mock 解耦与提高覆盖率？】

> 接口测试课程有详细讲解，这里只讲"为什么"。

Mock 用测试替身（假对象）替代真实依赖（数据库、下游服务、第三方接口）。好处：

| 好处 | 说明 |
|------|------|
| 解耦 | 被测代码不依赖外部服务的可用性，随时能测 |
| 提高覆盖率 | 可以模拟"下游返回异常/超时"等正常环境难构造的场景 |
| 加速 | 不等真实依赖，测试跑得更快 |

> 📷 【截图占位】后端链路调用架构图 / 淘宝核心链路应用拓扑图
> 📷 【截图占位】使用 Mock 解耦与提高覆盖率
> 详见 [[接口测试/README|接口测试]] 课程。

### 【我的理解】

> 思考：如果只允许你用"一个手段"验证"接口重构后行为没变"，你会选 DIFF 测试还是流量回放？为什么？

## 五、接口测试框架

### 【必须掌握】Requests（Python）vs RestAssured（Java）

| 维度 | Requests | RestAssured |
|------|----------|-------------|
| 语言 | Python | Java |
| 定位 | 发 HTTP 请求的库，简单强大 | 测试/验证 RESTful 服务的库 |
| 支持 | GET/POST/PUT/DELETE 等方法 | 简洁的接口测试 DSL |
| 解析 | 结构化解析 JSON/XML 等 | 结构化解析 XML/JSON 等 |
| 特点 | 代码直观，几行搞定 | 链式 DSL，可读性强 |

### 【为什么接口测试首选这两个？】

Requests 是 Python 生态里最流行的 HTTP 库——API 设计"简单而强大"，几行代码就能发请求、拿响应、解析 JSON。RestAssured 是 Java 生态里验证 RESTful 服务的标准选择——链式调用让"请求 + 断言"读起来像一句自然语言。

### 【易错点】Requests 是"库"不是"框架"

| 维度 | 库（Requests） | 框架（RestAssured） |
|------|---------------|-------------------|
| 定位 | 提供 HTTP 能力 | 提供测试 DSL + 断言 |
| 用法 | 需要自己组织用例结构 | 自带 given/when/then 结构 |
| 测试报告 | 需要配 pytest/unittest | 集成 JUnit 报告 |

> 📷 【截图占位】Requests 图示
> 📷 【截图占位】RestAssured 图示
> 工具对比详见 [[Ch04-测试技术体系]] 第九节工具全景。

### 【面试考察】

> 面试官："接口自动化你用什么做的？Requests 和 RestAssured 怎么选？"

**参考回答框架：** 主要看团队技术栈。Python 栈用 Requests（配合 pytest），Java 栈用 RestAssured（配合 JUnit/TestNG）。Requests 是 HTTP 库，几行代码就能发请求解析响应；RestAssured 是测试框架，自带 given/when/then 的 DSL，断言更语义化。两者都支持结构化解析 XML/JSON。

## 六、测试用例自动生成技术：Swagger

### 【课程原话/定义】

> Swagger 是一个广泛使用的工具套件，用于设计、构建、记录和测试 RESTful API。它提供一整套工具帮助开发者创建易于理解和使用的 API 文档。

### 【为什么 Swagger 能"自动生成测试用例"？】

Swagger（OpenAPI）用一份结构化文档描述接口的路径、参数、请求体、响应模型。有了这份"机器可读的接口定义"，就能自动：

| 能力 | 说明 |
|------|------|
| 生成 API 文档 | 交互式文档，直接在线调试 |
| 生成客户端/服务端代码 | 减少手写样板代码 |
| 生成测试用例 | 根据参数 schema 自动生成边界值/必填校验用例 |

### 【易错点】Swagger 是"文档"还是"测试工具"？

| 维度 | 误解 | 真相 |
|------|------|------|
| 定位 | 只是接口文档 | 是接口描述规范（OpenAPI），文档只是其中一种产出 |
| 能力 | 只能看 | 能生成代码、生成测试用例、在线调试 |
| 面试说 | "Swagger 就是写文档的" | "Swagger/OpenAPI 是接口描述规范，文档、代码、用例都能自动生成" |
