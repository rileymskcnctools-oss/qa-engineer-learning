## 一、JIRA 是什么

### 【课程定义】

> JIRA 是 Atlassian 公司出品的项目与事务跟踪工具，被广泛应用于缺陷跟踪、需求收集、流程审批、任务跟踪、项目跟踪和敏捷管理。

### 【为什么测试必须学JIRA？】

Ch05 讲了四大平台，JIRA 在四个里占了两个（用例管理 + Bug管理），再加上项目管理。面试问"你们用什么管测试"，你说JIRA，面试官大概率也用JIRA——接下来就会问"JIRA里你怎么管用例和Bug"。

### 【必须掌握】JIRA七大价值

| 价值       | 对你意味着什么                      |
| -------- | ---------------------------- |
| 提升项目管理能力 | 知道一个迭代从需求→测试→上线的全流程          |
| 增强团队协作   | 测试、开发、PM在同一个工具里协作            |
| 提高问题跟踪效率 | Bug从提交到关闭全程可追溯               |
| 支持持续集成   | JIRA ↔ Jenkins ↔ GitLab 可以打通 |
| 灵活定制     | 每个团队的字段、工作流都可以自己配            |
| 透明可追溯    | 谁在什么时候做了什么，全有记录              |
| 职业竞争力    | 几乎所有互联网公司都用JIRA              |

## 二、JIRA 五大基础概念

> 理解这五个概念，JIRA就入门了。

### 2.1 概念全景

| 概念  | 英文       | 通俗理解            | 类比                       |
| --- | -------- | --------------- | ------------------------ |
| 项目  | Project  | 一个容器，装所有相关Issue | 一个文件夹                    |
| 问题  | Issue    | JIRA的最小工作单元     | 一张待办便签                   |
| 字段  | Field    | Issue的属性        | 便签上的每一项：标题、日期、负责人        |
| 工作流 | Workflow | Issue从生到死的状态流转  | Bug的New→Open→Fixed→Close |
| 视图  | Screen   | 用户看到的界面         | 新建Issue时弹出的表单            |

### 2.2 Project（项目）

#### 【必须掌握】

- 项目是一个顶层容器
- 每个项目代表一个产品/团队/业务
- 项目下可以创建多种类型的Issue（需求、Bug、任务、测试用例）
- 每个项目可以独立配置工作流、字段、权限

#### 【企业场景】

> 你们团队可能有两个JIRA项目：
> - "电商App"项目 → 放所有App相关的需求和Bug
> - "测试自动化"项目 → 专门管理测试用例和测试任务
>
> 或者一个项目管全部，用Issue类型区分。

---

### 2.3 Issue（问题）

#### 【必须掌握】

Issue 是 JIRA 的核心。一切皆 Issue：

| Issue类型     | 用来干什么         | 谁创建   |
| ----------- | ------------- | ----- |
| Story（用户故事） | 描述一个功能需求      | PM    |
| Bug（缺陷）     | 记录一个缺陷        | 测试    |
| Task（任务）    | 技术任务、改进、文档    | 开发/测试 |
| Epic（史诗）    | 大功能，包含多个Story | PM    |
| Test（测试用例）  | Xray插件引入，记录用例 | 测试    |

### 2.4 Field（字段）

#### 【必须掌握】

每个Issue都有字段来描述它：

| 字段类型            | 举例                        | 谁来填      |
| --------------- | ------------------------- | -------- |
| 摘要（Summary）     | "登录页密码错误提示不显示"            | 创建人      |
| 描述（Description） | 详细说明+截图                   | 创建人      |
| 优先级（Priority）   | P0/P1/P2/P3               | 测试/PM    |
| 经办人（Assignee）   | 谁来解决这个问题                  | Leader分配 |
| 报告人（Reporter）   | 谁提出的这个问题                  | 自动       |
| 状态（Status）      | New/Open/In Progress/Done | 工作流自动流转  |
| 版本（Fix Version） | 在哪个版本修复                   | 开发/PM    |

#### 【企业场景】

> 你提Bug时，至少填对四个字段：
> - 摘要写清楚（"登录失败" ✗ → "iOS端微信登录回调无响应" ✓）
> - 优先级写对（影响核心功能=P0，UI对齐问题=P3）
> - 环境写全（iOS 17.2 + App v3.5.1）
> - 复现步骤写全（第一步做啥、第二步做啥、预期结果、实际结果）

---

### 2.5 Workflow（工作流）

#### 【课程定义】

> 工作流定义了Issue从创建到完成的生命周期，是一个状态和转换的流程。

#### 【为什么工作流重要？】

没有工作流 = 状态混乱，Bug到底修了没修不知道。工作流规定了每个状态能流转到哪，谁可以流转。

#### 【必须掌握】标准Bug工作流

```
  [新建] → [进行中] → [已修复] → [已关闭]
    ↑                    ↓
    └── [重新打开] ←──────┘
          ↑
    [不予处理]（Rejected）
```

| 转换            | 含义                | 谁操作   |
| ------------- | ----------------- | ----- |
| 新建 → 进行中      | 开发确认并开始修复         | 开发    |
| 进行中 → 已修复     | 修复完成，等待验证         | 开发    |
| 已修复 → 已关闭     | 测试验证通过            | 测试    |
| 已修复 → 重新打开    | 验证不通过             | 测试    |
| 新建/进行中 → 不予处理 | 不是Bug / 重复 / 无法复现 | 开发/PM |

#### 【企业场景】

> 流水线式工作流：
> 1. 你提Bug → 状态：新建
> 2. 你指派给开发 → 状态：待确认
> 3. 开发确认是Bug → 状态：进行中
> 4. 开发修完 → 状态：已修复，指派回你
> 5. 你验证通过 → 状态：已关闭
> 6. 你验证不通过 → 状态：重新打开，指派回开发
>
> 每一步都有记录：谁在什么时间做了什么操作。出问题直接查JIRA历史。

---

### 2.6 Screen（视图）

#### 【必须掌握】

- Screen = Issue的"表单页面"
- 创建Issue时弹出的是"创建视图"
- 编辑Issue时看到的是"编辑视图"
- 不同Issue类型可以有不同的视图（Bug的视图比Task多出"环境"字段）
- 视图决定了"在这个步骤用户能看到和填写哪些字段"

## 三、JIRA 管理测试用例

### 3.1 完整流程

```
创建测试项目 → 录入用例 → 用例状态流转 → 关联需求 → 执行测试
```

### 3.2 创建测试用例管理项目

| 步骤  | 操作                                         |
| --- | ------------------------------------------ |
| 1   | 创建JIRA项目，类型选"Test Management"（需Xray插件）或自定义 |
| 2   | 配置Issue类型：新增"Test Case"类型                  |
| 3   | 配置Test Case专属字段：测试步骤、预期结果、测试数据、前置条件        |
| 4   | 配置工作流：草稿→待评审→已通过→已废弃                       |

### 3.3 录入用例

在JIRA中创建Test Case类型的Issue：

| 字段   | 填写内容                        |
| ---- | --------------------------- |
| 摘要   | 用例标题，例如"验证正确账号密码登录"         |
| 前置条件 | "已注册账号test@qq.com，密码123456" |
| 测试步骤 | 分步写：1.打开登录页 2.输入账号密码 3.点击登录 |
| 预期结果 | "成功登录，跳转到首页，显示用户名"          |
| 关联需求 | 用JIRA的"关联"功能链接到对应的Story     |
| 优先级  | 核心功能P0，边缘场景P2               |

### 3.4 用例状态流转

```
 [草稿] → [待评审] → [已通过] → [执行中] → [通过]/[失败]
              ↑                      ↓
          [需修改] ←──────────────────┘
```

| 状态  | 含义             |
| --- | -------------- |
| 草稿  | 刚写好，还没人审       |
| 待评审 | 提交给Leader/开发评审 |
| 已通过 | 评审通过，等待执行      |
| 已废弃 | 需求变更，用例作废      |
| 执行中 | 正在测试           |
| 通过  | 执行通过           |
| 失败  | 执行失败，关联Bug     |

## 四、JIRA 管理 Bug

### 4.1 完整流程

```
创建Bug项目 → 从用例关联Bug → 录入Bug → Bug状态流转 → 回归验证
```

### 4.2 从用例关联到Bug

> JIRA 最强大的地方：关联。

| 关联类型   | 含义             | 方向       |
| ------ | -------------- | -------- |
| "测试"关系 | 用例测试了某个需求      | 用例 → 需求  |
| "导致"关系 | Bug是由某个用例失败发现的 | 用例 → Bug |
| "阻塞"关系 | Bug阻塞了某个需求上线   | Bug → 需求 |

#### 【企业场景】

> 用例"CJ-001 验证正确账号登录"执行失败 → 你创建Bug → 选择关联类型"是由 CJ-001 导致的"。
>
> 之后任何人打开这个Bug，都能看到是哪个用例发现了它。打开那个用例，能看到它关联了哪些Bug。打开需求，能看到它的覆盖率和关联Bug数。
>
> 这就是JIRA的"可追溯性"。

### 4.3 录入Bug

| 关键字段 | 填写标准 |
|---------|---------|
| 摘要 | 【模块】简短描述问题，如"【登录】iOS端微信授权后白屏" |
| 描述 | 环境 + 复现步骤 + 预期结果 + 实际结果 + 截图/日志 |
| 严重程度 | S1致命/S2严重/S3一般/S4建议 |
| 优先级 | P0立即/P1本迭代/P2下迭代/P3待排期 |
| 版本 | 发现的版本号 |
| 模块 | 哪个功能模块 |
| 经办人 | 指派给对应开发 |

### 4.4 Bug状态流转

```
 [新建] → [确认] → [修复中] → [已修复] → [已关闭]
                       ↓           ↓
                   [不予处理]   [重新打开]
```

#### 【易错点】Bug流转中最常见的争议

| 场景 | 开发操作 | 你怎么处理 |
|------|---------|-----------|
| 开发说"不是Bug，设计如此" | 标记Rejected | 查需求文档，有依据→Reopen；没依据→找PM |
| 开发说"无法复现" | 标记Cannot Reproduce | 补充复现步骤+录屏→Reopen |
| 相同Bug别人提过了 | 标记Duplicate | 确认后接受，在原Bug上补充信息 |
| 开发说"修了"但你测了没好 | — | Reopen，附上新的截图 |

## 五、JIRA 实战速查：测试工程师的一天

| 时间    | 操作    | JIRA上做什么                           |
| ----- | ----- | ---------------------------------- |
| 9:00  | 站会    | 看自己的JIRA看板，了解昨天+今天的Issue           |
| 9:15  | 接手新需求 | 找到对应Story → 看需求描述 → 创建关联的Test Case |
| 10:00 | 执行测试  | 执行Test Case → 通过标记Pass，失败标记Fail    |
| 11:00 | 提Bug  | Fail的用例 → 创建Bug Issue → 关联用例+需求    |
| 14:00 | 回归验证  | 看自己的Bug列表 → 状态=已修复的 → 逐个验证         |
| 16:00 | 更新用例  | 需求变更 → 更新对应Test Case → 状态变更为"待评审"  |
| 17:00 | 写日报   | 从JIRA Dashboard看自己今天的Issue变化       |
