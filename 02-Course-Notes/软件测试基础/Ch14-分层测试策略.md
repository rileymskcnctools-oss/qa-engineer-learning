## 一、什么是分层测试策略

### 【课程原话/定义】

> 分层测试策略是一种将测试工作按层次分解的策略，旨在通过不同层次的测试来确保软件系统的质量。这种策略有助于有效地组织测试工作，优化测试资源的利用，并提高缺陷发现和修复的效率。

### 【为什么？】

把整个系统当成"黑盒子"从头点到尾（端到端）有两个致命问题：

| 问题  | 后果                                      |
| --- | --------------------------------------- |
| 定位难 | 一个"登录失败"可能是前端、网关、后端、数据库任意一层的问题，逐层排查成本极高 |
| 反馈慢 | 端到端测试要等整个系统联调完成才能跑，缺陷发现越晚，修复成本越高        |

分层测试的核心思想是"**在每一层尽早、独立地验证**"——函数写完就测函数（单元），接口联调就测接口（集成），最后才测整体界面（UI）。越早发现缺陷，修复成本越低。

### 【必须掌握】分层测试策略的两大价值

| 价值维度 | 具体抓手                                      | 为什么重要               |
| ---- | ----------------------------------------- | ------------------- |
| 质量保证 | 需求分析、测试标准确立、测试用例 review、界面覆盖率、接口覆盖率、代码覆盖率 | 把"测没测够"从主观感觉变成可量化指标 |
| 效率提升 | 自动化测试、尽早测试尽快反馈、流水线（CI/CD/DevOps）          | 用机器和流程替代重复劳动，缩短反馈周期 |

### 【我的理解】

> 思考：如果把一个电商下单功能"只做端到端测试"，和"分层测试（单元测函数 + 集成测接口 + UI 测流程）"相比，在**发现 Bug 的速度**上有什么区别？为什么后者能更早暴露缺陷？

## 二、质量保证维度

### 2.1 质量保证的六个抓手

| 抓手 | 说明 | 所处阶段 |
|------|------|---------|
| 需求分析 | 理解被测需求，明确"测什么" | 测试前 |
| 测试标准确立 | 定好"测到什么程度算够"的标尺 | 测试前 |
| 测试用例 review | 用例评审，保证用例本身的质量 | 测试设计 |
| 界面覆盖率 | 页面元素和操作流程被覆盖的比例 | 测试执行 |
| 接口覆盖率 | API 被调用和验证的比例 | 测试执行 |
| 代码覆盖率 | 代码被测试跑到的比例 | 单元测试 |

### 2.2 三个覆盖率（重点）

### 【必须掌握】界面 / 接口 / 代码三个覆盖率

分层测试把"质量保证"拆成了三个可以量化的覆盖率指标，分别对应测试金字塔的三层：

| 覆盖率 | 对应层 | 测什么 | 谁负责 |
|--------|--------|--------|--------|
| 代码覆盖率 | 单元测试 | 函数/方法有没有被测试跑到 | 开发 |
| 接口覆盖率 | 服务/集成测试 | API 有没有被调用和验证 | 测试 + 开发 |
| 界面覆盖率 | UI 测试 | 页面元素和操作流程有没有被覆盖 | 测试 |

### 【为什么三个覆盖率缺一不可？】

| 只有单一覆盖率 | 漏洞 |
|--------------|------|
| 只有界面覆盖率 | 界面点到了，但背后接口逻辑没验证，数据错误发现不了 |
| 只有接口覆盖率 | 接口返回正确，但前端展示/交互可能错位 |
| 只有代码覆盖率 | 代码每行都跑了，但"跑到了 ≠ 跑对了"，业务场景可能漏掉 |

### 【易错点】代码覆盖率 ≠ 质量高

| 误区 | 真相 |
|------|------|
| 代码覆盖率 100% = 没 Bug | 覆盖率只说明"代码被执行过"，不说明"结果被验证过"。一行代码跑了但断言写错，覆盖率照样 100% |
| 覆盖率低 = 一定有问题 | 关键核心逻辑覆盖到位，比"边角代码刷到 100%"更有价值 |

### 【面试考察】

> 面试官："你们团队关注哪些测试覆盖率？怎么用的？"

**参考回答框架：** 三个层面。单元测试看代码覆盖率（JaCoCo / coverage.py），核心模块一般要求 80% 左右，但更看重关键分支是否被覆盖；接口测试看接口覆盖率，保证每个对外 API 都有对应用例；UI 测试看界面覆盖率，保证核心页面和主流程被自动化脚本覆盖。最后强调一句："覆盖率是手段不是目的"，最终目标是缺陷预防。

### 【我的理解】

> 思考：如果一段代码"被测试执行到了，但测试没有断言它的返回值"，代码覆盖率会涨吗？这说明了代码覆盖率指标的什么盲区？

## 三、效率提升维度

### 3.1 人工测试 vs 自动化测试

### 【必须掌握】

| 维度 | 人工测试 | 自动化测试 |
|------|---------|-----------|
| 扩容成本 | 招人、培训，横向纵向扩容都贵 | 加机器、复制脚本，边际成本极低 |
| 稳定性 | 人疲劳会遗漏 | 脚本稳定、不遗漏、可重复 |
| 典型手段 | 手工执行用例 | 自动化测试、自动遍历测试、录制回放测试 |
| 适用场景 | 探索性、一次性、复杂场景 | 回归、遍历、重复执行的用例 |

### 3.2 尽早测试、尽快反馈

| 手段 | 说明 |
|------|------|
| 单元测试 | 代码写完立即跑，秒级反馈 |
| 集成测试 | 模块联调时验证接口，分钟级反馈 |

### 3.3 流水线（CI/CD/DevOps）

> 持续集成 → 持续交付 → DevOps，让"提交代码 → 自动测试 → 自动反馈"变成常态，而不是每次手工触发。

### 【为什么流水线能提升效率？】

手工回归测试的痛点是"每次发版都重复跑一遍同样的用例"。流水线把测试脚本挂到代码提交事件上，开发一提交代码，自动化测试自动跑、结果自动反馈。人只处理"失败的用例"，不再处理"重复的回归"。

### 【我的理解】

> 思考：如果一个团队只有人工测试、没有自动化，当测试用例从 100 条涨到 1000 条时会怎样？为什么说"人工测试无法线性扩容"？

## 四、分层测试理论体系：测试金字塔

### 【课程原话/定义】

> 测试金字塔（Test Pyramid）由 Martin Fowler 提出，是用于帮助开发团队构建更高效、更可靠的自动化测试体系的测试策略模型。它将测试分为三个主要层次：单元测试（Unit）、服务测试（Service）、用户界面测试（UI）。金字塔的形状象征了各层次测试的数量比例。

### 【必须掌握】三层金字塔

```
        ┌──────┐
        │  UI  │  最少   确保界面元素正确 + 用户操作流程正常
        ├──────┤
        │Service│ 中等   确保系统各部分能正确协同工作
        ├──────┤
        │ Unit │  最多   验证单个功能模块的正确性
        └──────┘
```

| 层 | 测什么 | 一句话 |
|----|--------|--------|
| UI | 界面元素正确性、用户操作流程 | 用户看到的、点的对不对 |
| Service | 系统各部分协同工作 | 模块之间接口对不对 |
| Unit | 单个功能模块 | 函数/方法对不对 |

> 📷 【截图占位】Martin Fowler 测试金字塔图示

### 【为什么底层最多、顶层最少？】

> Ch04 已从"四个原则"角度讲过测试金字塔。这里补充 Martin Fowler 原模型的视角：

| 层 | 特点 | 决定数量 |
|----|------|---------|
| Unit | 毫秒级、无外部依赖、最稳定 | 多写（数量最大） |
| Service | 秒级、验证接口协同 | 中等 |
| UI | 分钟级、最脆弱（改个按钮就挂）、维护成本最高 | 少写（数量最少） |

> 三层工具与占比的详细内容见 [[Ch04-测试技术体系]] 第八节"自动化分层测试体系"。

### 【面试考察】

> 面试官："测试金字塔是谁提出的？三层分别测什么？"

**参考回答框架：** Martin Fowler 提出。三层分别是单元测试（Unit，验证单个函数/模块）、服务测试（Service，验证系统各部分协同）、UI 测试（User Interface，验证界面元素和操作流程）。金字塔形状代表数量比例：单元测试最多、服务测试中等、UI 测试最少——因为越往上执行越慢、越不稳定、维护成本越高。

## 五、UI 组件的分层测试（Google Android 体系）

### 【课程原话/定义】

> 在 Google Android 开发中，UI 组件的分层测试通常包括三层：单元测试（Unit Tests）、集成测试（Integration Tests）、用户界面测试（UI Tests）。这三层测试有助于确保应用程序各个部分正常工作，整体功能符合预期。

### 【必须掌握】Android 三层测试

| 层 | 测什么 | 运行环境 | 速度 |
|----|--------|---------|------|
| 单元测试（Unit） | 单个类/方法，如业务逻辑、工具类 | JVM（本地） | 最快 |
| 集成测试（Integration） | 组件之间交互，如和数据库、网络的集成 | JVM 或模拟器 | 中等 |
| UI 测试（UI） | 完整用户流程：点击、滑动、界面跳转 | 模拟器/真机 | 最慢 |

### 【为什么移动端也要分层？】

移动端测试如果"全部跑在真机上"，速度极慢、设备成本高、难以进流水线。分层后：单元测试跑在本地 JVM 上秒级完成，只有真正需要验证界面和系统交互的才跑模拟器/真机。这和测试金字塔"底层多、顶层少"是同一个逻辑在移动端的落地。

> 📷 【截图占位】Google Android 测试体系图

### 【面试考察】

> 面试官："Android 应用的分层测试是怎么分的？"

**参考回答框架：** 三层。单元测试跑在 JVM 上，测单个类和方法，最快；集成测试测组件之间的交互（数据库、网络），跑在 JVM 或模拟器上；UI 测试用 Espresso/Appium 之类在模拟器或真机上验证完整用户流程，最慢。分层目的还是"能快的别慢"——尽量把测试放在底层，减少对真机和模拟器的依赖。

## 六、金字塔模型 vs 沙漏模型

### 【课程原话/定义】

> 金字塔模型：理想自动化测试分布——单元测试占 70%-80%，集成测试占 10%-20%，端到端测试最少。
> 沙漏模型：对金字塔模型的变形，强调更多单元测试和端到端测试，减少集成测试的数量。

### 【必须掌握】两种模型对比

| 维度 | 金字塔模型 | 沙漏模型 |
|------|-----------|---------|
| 单元测试 | 最多（70%-80%） | 更多（同样是主力） |
| 集成测试 | 中等（10%-20%） | 减少（中间被压缩） |
| 端到端测试 | 最少 | 增多（顶部放大） |
| 形状 | 上小下大 | 上下大、中间窄 |

> 📷 【截图占位】金字塔模型图示
> 📷 【截图占位】沙漏模型图示

### 【为什么会出现沙漏模型？】

沙漏模型通常出现在**微服务/分布式架构**下：单个服务本身很小，单元测试好写；服务之间靠 HTTP/RPC 通信，集成测试（mock 掉一堆下游）反而成本高、价值低；而端到端测试能直接验证"用户请求 → 多个服务协同 → 返回结果"的完整链路，价值上升。所以中间（集成）被压缩，两端（单元 + 端到端）被放大。

### 【易错点】金字塔 vs 沙漏：哪个是对的？

| 模型 | 适用场景 | 别搞混 |
|------|---------|--------|
| 金字塔 | 单体/分层清晰的系统，集成测试成本可控 | 是"理想默认"，不是唯一答案 |
| 沙漏 | 微服务/分布式，集成测试成本高、端到端价值高 | 不是"金字塔做错了"，是架构不同导致的变形 |

> 面试时别说"沙漏模型是错的"。正确说法："金字塔是通用理想模型，微服务架构下会向沙漏形演化。"

### 【我的理解】

> 思考：在微服务架构下，为什么"集成测试"会变少、"端到端测试"会变多？试着用自己的话解释"中间被压缩"的原因。

## 七、微服务测试模型

### 【课程原话/定义】

> Martin Fowler 提出的微服务测试模型，把微服务内部拆成以下几层：

| 层 | 职责 |
|----|------|
| Resources | 通过特定协议（HTTP/RPC）对外暴露能力 |
| Service | 负责领域模型的协作（业务编排） |
| Domain | 包含行为和数据的领域对象模型（核心业务逻辑） |
| Repositories | 作用于域实体的集合，通常有持久化支持 |
| Gateway | 与远程服务通讯 |
| Data Mappers | 模型的序列化方案 |

### 【为什么微服务要单独一套测试模型？】

单体应用的测试金字塔（UI/Service/Unit）在微服务下不够用了——微服务内部结构更复杂，一个服务里有"对外接口、业务编排、领域模型、数据访问、远程调用、序列化"这么多层，每一层的测试边界和手段都不一样。所以 Martin Fowler 针对微服务给出了更细的分层。

> 📷 【截图占位】Martin Fowler 微服务测试模型图

### 【易错点】微服务分层 vs 测试金字塔

| 维度 | 测试金字塔 | 微服务测试模型 |
|------|-----------|--------------|
| 视角 | 全系统的测试类型 | 单个微服务内部的分层 |
| 粒度 | UI / Service / Unit 三层 | Resources / Service / Domain / Repository / Gateway / DataMapper 六层 |
| 关系 | 宏观战略 | 微观落地 |

### 【我的理解】

> 思考：微服务模型里的 "Service" 和测试金字塔里的 "Service" 是同一个东西吗？为什么？（提示：一个指"服务层测试类型"，一个指"业务编排组件"）

## 八、微服务测试策略

### 【必须掌握】四种测试类型

| 测试类型 | 测什么 | 一句话 |
|---------|--------|--------|
| 单元测试 | 最小可测试软件，行为是否符合预期 | 单个函数/类 |
| 集成测试 | 组件之间通信路径和交互，检测接口缺陷 | 组件怎么连 |
| 组件测试 | 限制在系统一部分，用内部接口操纵，用测试替身隔离其他组件 | 隔离起来测一部分 |
| 端到端测试 | 验证系统是否满足外部需求，从头到尾测整个系统 | 整个系统跑通 |

### 【为什么"组件测试"容易和"集成测试"混淆？】

| 维度 | 集成测试 | 组件测试 |
|------|---------|---------|
| 关注 | 组件之间的通信路径 | 单个组件/子系统内部 |
| 范围 | 跨组件 | 限定在系统一部分 |
| 隔离手段 | 真实连接（或部分替身） | 用测试替身（Test Double）把被测部分和其他组件隔离 |

> 一句话区分：集成测试测"它们怎么连"，组件测试测"它自己（隔离了别人）怎么工作"。

> 📷 【截图占位】微服务测试策略图示

### 【面试考察】

> 面试官："微服务测试策略包含哪几种测试？组件测试和集成测试有什么区别？"

**参考回答框架：** 四种——单元测试、集成测试、组件测试、端到端测试。单元测试验证最小单元；集成测试验证组件之间的通信路径和接口；组件测试把范围限制在系统的一部分，通过内部代码接口操纵，并用测试替身把其他组件隔离；端到端测试从头到尾验证整个系统是否满足外部需求。区别上，集成测试关注"组件之间怎么通信"，组件测试关注"单个组件隔离掉外部依赖后自身行为对不对"。

### 【我的理解】

> 思考：如果让你给一个微服务的"订单服务"写测试，你会分别用什么手段测它的 Domain 层（业务逻辑）和 Gateway 层（远程调用）？为什么这两层用的测试手段不一样？
