## 一、测试右移定义

### 【课程原话/定义】

> 右移是在实际条件下在生产中执行测试、质量和性能评估的做法。右移方法确保在生产中运行的应用程序可以承受真实的用户负载，同时确保同样高水平的质量。目标是检测和修复在开发环境中难以预料的问题。

### 【为什么需要右移？】

开发/测试环境再完善，也模拟不了真实生产：真实用户行为、真实流量、真实网络、真实数据。右移把测试延伸到生产环境，去发现"开发环境难以预料的问题"。

### 【我的理解】

> 思考：哪些问题在开发/测试环境"几乎不可能发现"，只有上线到生产才会暴露？举两个例子。

## 二、测试右移的六个主要实践

### 【必须掌握】

| 实践                        | 说明                                   |
| ------------------------- | ------------------------------------ |
| 应用监控                      | 上线后实时监控应用指标                          |
| 综合监控 / 质量监控               | Continuous Quality Monitoring，持续质量监控 |
| A/B 测试                    | 线上分流对比不同版本效果                         |
| 金丝雀部署 Canary releases     | 先让少量用户用新版本，验证后再全量                    |
| TIP 线上测试                  | Test In Production，在生产环境做受控测试        |
| 故障注入 / 混沌工程 Chaos testing | 主动注入故障，验证系统韧性                        |

### 【易错点】金丝雀 vs A/B

| 维度   | 金丝雀部署         | A/B 测试       |
| ---- | ------------- | ------------ |
| 目的   | 验证新版本稳定性，安全发布 | 对比不同方案效果，做决策 |
| 对象   | 同一功能的新旧版本     | 两个（或多个）不同方案  |
| 判断依据 | 新版本有没有问题      | 哪个方案数据更好     |

### 【我的理解】

> 思考：混沌工程"主动注入故障"听起来像搞破坏，为什么它反而能"提高系统可靠性"？这和"等故障自然发生"的区别是什么？

## 四、监控系统搭建

### 【必须掌握】为什么要搭监控系统

| 环节     | 说明         |
| ------ | ---------- |
| 测试数据收集 | 从生产采集数据    |
| 测试数据分析 | 分析数据发现异常   |
| 数据可视化  | 用图表呈现，便于定位 |

### 【必须掌握】常用架构 ELK（Elastic Stack）

| 组件 | 作用 |
|------|------|
| Elasticsearch | 数据存储 + 检索 |
| Logstash | 数据采集/同步、转换 |
| Kibana | 数据可视化前端 |

> ELK 用于日志收集、检索、可视化，是测试右移/监控的基础设施。

### 【必须掌握】常见数据存储平台

| 环节 | 工具 |
|------|------|
| 数据同步 | logstash、flume |
| 数据存储 | elasticsearch、influxdb、prometheus |
| 前端展现 | kibana、grafana |

## 六、移动端监控

### 【必须掌握】移动端插桩技术

| 技术 | 说明 |
|------|------|
| 埋点：硬编码 | 直接写死埋点代码 |
| AOP 编程 | 用 AspectJ 切面插入埋点 |
| 插桩框架 | ASM、JavaAssist 字节码插桩 |

### 【必须掌握】数据收集回传

| 组件 | 作用 |
|------|------|
| logstash | 日志采集转换 |
| kafka | 消息队列缓冲 |
| filebeat | 轻量日志采集 |

### 【必须掌握】插桩技术分类

| 类型 | 代表工具 |
|------|---------|
| 编译插桩（植入 SDK） | NewRelic |
| dex 插桩 | Appetizer |
| Hook | XPosed、Frida |

### 【必须掌握】常见质量维度监控类型

| 类型          | 工具/平台          |
| ----------- | -------------- |
| App 崩溃监控    | Bugly          |
| 应用性能监控（APM） | NewRelic、听云等   |
| 业务监控        | TalkingData、友盟 |
| 质量监控        | 目前普遍"缺位"（待建设）  |

### 【我的理解】

> 思考：四种监控类型里，"质量监控"为什么标注"缺位"？质量监控要监控什么指标，为什么比崩溃/性能监控难做？

## 七、更多数据收集与分析

### 【必须掌握】用户反馈分析

| 来源          | 说明               |
| ----------- | ---------------- |
| 核心用户在产品内的反馈 | 站内反馈、投诉          |
| 应用商店评论      | App Store/应用市场评价 |
| 产品反馈        | 汇总分析             |
| 外部平台        | Bugly、友盟、Flurry  |

### 【必须掌握】业务建模与分析

**建模**

| 模型 | 说明 |
|------|------|
| UI 模型 | 页面结构、交互路径 |
| 接口模型 | API 调用关系 |
| 性能数据 | 性能指标趋势 |
| 代码流模型 | 代码变更影响分析 |

**分析**

| 方法 | 说明 |
|------|------|
| 基于规则 | 用规则引擎发现异常 |
| diff 算法 | 对比差异（如新旧版本行为） |
| 机器学习 + AI | 用模型预测风险、智能告警 |

### 【扩展知识】测试行业的数据化趋势

> 过去几十年的测试行业一直没有很好地对测试工作进行有效的数据化建设，在当代数据分析科学蓬勃发展的背景下，测试工作将迎来新机遇，发挥出更大价值。

### 【我的理解】

> 思考："UI 模型 / 接口模型 / 代码流模型"这些建模数据，分别能支撑测试左移还是右移？试着把它们和精准测试、影响分析关联起来。
