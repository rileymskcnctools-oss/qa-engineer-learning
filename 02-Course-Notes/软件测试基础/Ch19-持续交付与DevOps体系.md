## 一、从传统流程到敏捷

### 【为什么传统开发流程不够用？】

传统瀑布式开发：需求 → 设计 → 开发 → 测试 → 上线，每个阶段串行，周期长、反馈慢。敏捷开发体系把大版本拆成小迭代，持续交付价值。而 CI/CD/DevOps 是让"持续交付"落地的工程实践。

> 开发流程的背景详见 [[Ch02-软件开发流程]]（瀑布/敏捷/DevOps）。

### 【我的理解】

> 思考：传统流程"测试阶段"为什么是瓶颈？为什么说"反馈越慢，修复成本越高"？

## 二、持续集成 CI

### 【课程原话/定义】

> 持续集成是一种 DevOps 软件开发实践。采用持续集成时，开发人员会定期将代码变更合并到一个中央存储库中，之后系统会自动运行构建和测试操作。持续集成的主要目标是更快发现并解决缺陷，提高软件质量，并减少验证和发布新软件更新所需的时间。（@亚马逊）

### 【必须掌握】CI 的两个组件

| 组件 | 说明 |
|------|------|
| 自动化组件 | CI/构建服务（如 GitLab CI、Jenkins），自动构建+测试 |
| 文化组件 | 学习频繁地集成（提交要小、要勤） |

### 【必须掌握】GitLab CI 流程

```
提交代码 → 触发流水线 → 构建 → 单元测试 → 集成测试 → 反馈
```

### 【为什么 CI 能"更快发现缺陷"？】

开发每次提交都自动跑构建和测试，问题在提交后几分钟内暴露，而不是等到版本集成时才发现。缺陷发现越早，定位和修复成本越低。

### 【易错点】CI 的"集成"指什么？

| 误解 | 真相 |
|------|------|
| CI = 自动部署 | CI 是"自动构建+测试"，部署是 CD 的事 |
| CI = 只是工具 | CI 需要"自动化组件 + 频繁提交的文化"两者配合 |

## 三、持续交付 CD

### 【课程原话/定义】

> 持续交付是一种软件开发实践，系统可以自动为将代码更改发布到生产环境做好准备。持续交付通过在构建阶段后将所有代码变更部署到测试环境和/或生产环境中，实现对持续集成的扩展。开发人员将始终拥有已通过标准化测试流程的部署就绪构建构件。（@亚马逊）

### 【必须掌握】CD 扩展了 CI 什么？

| 阶段 | 内容 |
|------|------|
| CI（集成） | 构建 + 单元测试 |
| CD（交付） | 在 CI 后，把代码变更部署到测试/生产环境，并自动执行**单元测试以外的测试** |

### 【必须掌握】CD 阶段可能跑的测试类型

UI 测试、负载测试、集成测试、API 可靠性测试等——比 CI 的单元测试更全面，能跨多个维度验证更新。

### 【必须掌握】持续交付流水线

```
代码提交 → 构建 → 单元测试 → 部署到测试环境 → 集成/UI/负载测试 → 部署就绪构件
```

## 四、持续部署 Continuous Deployment

### 【课程原话/定义】

> 通过持续部署，可自动完成从代码提交到生产的全过程。开发与交付阶段之间的触发器是自动的，因此在代码更改获得验证并通过所有测试后，就会立即发布。客户可立即获得新功能。（@microsoft）

### 【必须掌握】CI / CD / 持续部署 三者对比

| 维度 | 持续集成 CI | 持续交付 CD | 持续部署 CD |
|------|------------|------------|------------|
| 自动化到哪 | 构建 + 测试 | 构建 + 测试 + 部署到测试/预发 | 全自动直到生产 |
| 上线动作 | 人工 | 人工点击发布（就绪） | 全自动，无需人工 |
| 关键词 | 集成、构建、测试 | 部署就绪构件 | 自动发布到生产 |

### 【易错点】持续交付 vs 持续部署（易混淆）

| 维度 | 持续交付 | 持续部署 |
|------|---------|---------|
| 最后一步 | 需要**人工确认**才发布到生产 | **自动**发布到生产，无人工干预 |
| 风险 | 低，人可控 | 高，依赖极完善的测试门禁 |

> 面试必考点：持续交付 = "随时可发布，但要人点一下"；持续部署 = "测试过了自动上线，人不用点"。

### 【我的理解】

> 思考：为什么"持续部署"对测试质量的要求比"持续交付"高得多？如果测试没拦住 bug，两种模式各会有什么后果？

## 五、DevOps 体系

### 【必须掌握】DevOps 六要素

| 要素 | 说明 |
|------|------|
| 持续集成 | 频繁合并 + 自动构建测试 |
| 持续交付 | 代码变更自动就绪可发布 |
| 微服务 | 服务拆分，独立部署 |
| 基础设施即代码 | 环境用代码描述，可版本化 |
| 监控和日志记录 | 上线后持续观察 |
| 沟通与合作 | 开发/测试/运维打破壁垒 |

### 【必须掌握】DevOps 相关技能示例

| 角色 | 技能 |
|------|------|
| 开发 | 单元测试、代码评审、版本控制 |
| 测试 | 自动化测试、测试环境管理、性能/安全测试 |
| 运维 | 部署自动化、监控告警、容器编排 |

### 【必须掌握】DevOps 中的左移与右移

| 方向 | 含义 |
|------|------|
| 左移（Shift-left） | 测试提前到开发阶段（详见 [[Ch20-测试左移体系]]） |
| 右移（Shift-right） | 测试延伸到生产环境（详见 [[Ch21-测试右移体系]]） |

### 【面试考察】

> 面试官："说一下 CI、持续交付、持续部署的区别？"

**参考回答框架：** 三者是递进关系。CI 是"频繁合并代码 + 自动构建 + 自动单元测试"；持续交付在 CI 基础上"自动部署到测试/预发环境，跑更全面的测试（UI/负载/集成），产出部署就绪构件，但上线要人工确认"；持续部署则"连上线也全自动，测试全过就自动发布到生产"。区别就是自动化覆盖到哪一步、最后上线要不要人点。

### 【我的理解】

> 思考：一个团队从"没有 CI"到"持续部署"应该怎么分步走？为什么不能一步到位上持续部署？
