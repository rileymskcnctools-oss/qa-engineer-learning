## 一、为什么要做测试左移

### 【课程原话/定义】

> 测试左移（Shift-left）是把测试活动提前到研发阶段的做法，目标是在开发阶段尽早发现 bug，降低沟通成本、提高研发效率。

> 理论依据：Applied Software Measurement, Capers Jones（卡珀斯·琼斯）, 1996 —— 缺陷越早发现，修复成本越低（呈数量级增长）。

### 【为什么左移能省钱？】

| 阶段 | 发现一个 bug 的修复成本 |
|------|----------------------|
| 需求/设计阶段 | 极低（改文档/设计） |
| 开发阶段 | 低（改代码） |
| 测试阶段 | 中（改代码 + 重新测试） |
| 生产环境 | 极高（紧急修复 + 用户流失 + 品牌损失） |

> 微软的左移实践：把测试活动提前到需求评审、设计评审、代码评审阶段。

### 【我的理解】

> 思考：为什么"需求评审发现的问题"比"测试阶段发现的 bug"修复成本低得多？同样是改，区别在哪？

## 二、测试左移的八个主要实践

### 【必须掌握】

| 实践 | 说明 |
|------|------|
| 需求分析与评审 | 测试提前参与需求，从源头发现需求缺陷 |
| 代码评审 | 同行审查代码，早期发现逻辑/设计问题 |
| 代码审计、静态分析 | 用工具扫描代码（如 SonarQube） |
| 自动化测试左移 | 自动化测试提前到开发阶段 |
| 单元测试 | 开发自测，写完即测 |
| 覆盖率统计 | 用覆盖率衡量测试充分性 |
| 应用监控 | 提前埋点，为后续监控做准备 |
| 测试用例生成 | 根据接口定义/数据自动生成用例 |

### 【易错点】"左移"不等于"测试干开发的活"

| 误解              | 真相                                |
| --------------- | --------------------------------- |
| 左移 = 测试工程师写单元测试 | 左移是"测试活动提前"，单元测试仍以开发为主，测试做用例设计/评审 |
| 左移 = 不测了        | 左移是"提前测 + 后面照常测"，不是替代             |

## 三、代码审查 Code Review

### 【课程原话/定义】

> 代码审查是对计算机源代码系统化地审查，常用软件同行评审的方式进行，目的是找出及修正在软件开发初期未发现的错误，提升软件质量及开发者的技术。

### 【必须掌握】开发人员的收益

| 收益 | 说明 |
|------|------|
| 工作认真且始终如一 | 有人审查，写代码更谨慎 |
| 学习最佳实践和新技术 | 从同事代码里学习 |
| 代码库一致性和质量 | 统一风格，减少技术债 |

### 【必须掌握】Code Review 能发现的问题

| 维度 | 审查问题 |
|------|---------|
| 设计 | 代码是否经过精心设计并适合代码库？ |
| 功能 | 代码是否按预期以对用户有益的方式执行？ |
| 复杂性 | 其他开发人员能否理解和使用代码？ |
| 命名 | 变量、类、方法是否有清晰名称？ |
| 注释 | 注释是否具体且完整？ |

### 【必须掌握】Code Review 工具

| 工具 | 说明 |
|------|------|
| Gerrit | Google 的代码审查系统，提交前审查 |
| GitLab Merge Request | GitLab 的 MR 审查流程 |
| SonarQube | 代码审计/静态分析平台，扫描代码质量 + 漏洞 |

### 【为什么 SonarQube 是"代码审计平台"而不是"人工审查"？】

SonarQube 用**静态分析**自动扫描代码（Bug、漏洞、坏味道、覆盖率），人工 Code Review 是**人肉审查逻辑和设计**。两者互补：机器查规则性/重复性问题，人查业务逻辑和设计合理性。

### 【面试考察】

> 面试官："你们团队怎么做代码评审？用什么工具？"

**参考回答框架：** 两层。人工评审用 GitLab Merge Request（或 Gerrit）——提交前同行审查，重点看设计、功能正确性、复杂度、命名、注释；自动审计用 SonarQube 做静态分析，扫描 bug、漏洞、坏味道，并集成覆盖率。人工查逻辑，机器查规则，互补。

### 【我的理解】

> 思考：Code Review 的五个维度里，为什么"设计"和"复杂度"排在最前面？这体现了评审的什么价值取向？

## 四、覆盖率集成

### 【必须掌握】覆盖率与左移的关系

| 环节 | 作用 |
|------|------|
| 单元测试覆盖率 | 衡量开发自测是否充分 |
| 覆盖率统计 | 集成到流水线，低于阈值就阻断 |
| 质量门禁 | 覆盖率不达标不让合并/发布 |

> 典型 bug 案例：覆盖率看似高，但关键分支没测到 → 线上出 bug。覆盖率是"手段不是目的"（呼应 [[Ch14-分层测试策略]] 的覆盖率易错点）。

### 【我的理解】

> 思考：如果把"覆盖率阈值"设成质量门禁，但团队为了过门禁写一堆没断言的测试，会发生什么？这暴露了覆盖率指标的什么盲区？

## 五、总结

### 【必须掌握】测试左移的价值

> 测试左移可以让我们更早更快地发现研发阶段引入的 bug，从而更好地保障产品质量，降低项目沟通成本，提高研发效率。
