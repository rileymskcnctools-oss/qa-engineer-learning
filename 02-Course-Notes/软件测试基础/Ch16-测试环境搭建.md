## 一、什么是测试环境搭建

### 【课程原话/定义】

> 测试环境搭建（Test Environment Setup）是指为软件测试过程创建一个模拟真实运行环境的过程。这个环境应尽可能与实际生产环境相匹配，以确保测试结果的可靠性和准确性。通常包括硬件、软件、网络配置以及必要的测试数据等方面。

### 【为什么环境要"尽量和生产一致"？】

环境不一致 = 测试结果不可信。两个典型翻车场景：

| 场景 | 后果 |
|------|------|
| 测试环境数据库版本比生产旧 | 测试通过的 SQL，生产上因为语法/索引差异报错 |
| 测试环境内存/配置比生产小 | 测试时性能正常，上线后在高负载下崩溃 |

> 核心原则：**测试环境越接近生产，测出来的结果越能代表上线后的真实表现**。

### 【必须掌握】五大价值

| 价值 | 说明 |
|------|------|
| 提高测试质量 | 环境越接近生产，测出的结果越可信 |
| 提升问题定位能力 | 了解环境构成，Bug 定位更快、更准 |
| 增强系统理解 | 亲手搭环境 = 理解系统架构和数据流转 |
| 提高团队协作效率 | 统一环境，减少"我这儿没问题"的扯皮 |
| 提升实际操作能力 | 部署、命令、容器是测试工程师的硬技能 |

> 📷 【截图占位】测试环境搭建概览

### 【我的理解】

> 思考：如果测试环境和生产环境"版本不一致"导致了一个 Bug 只在生产出现，你能说出至少两种"环境差异"的来源吗？

## 二、被测系统 AUT

### 【课程原话/定义】

> AUT（Application Under Test）即"被测系统"，指当前正在被测试的应用程序。测试环境搭建的第一步，就是搞清楚 AUT 长什么样、属于哪一类。

### 【必须掌握】AUT 的两大方向

| 方向 | 说明 | 举例 |
|------|------|------|
| 用户端/移动端测试 | 面向用户的应用 | App、Web 前端 |
| 服务端测试 | 面向接口/数据的服务 | RESTful API、RPC 服务 |

> 📷 【截图占位】被测系统 AUT（用户端/移动端 + 服务端）

### 【为什么先分清 AUT 类型？】

不同类型的 AUT，测试手段和工具完全不同：App 用 Appium、Web 用 Selenium、RESTful 接口用 Requests/RestAssured、RPC 用 dubbo/pb 对应的客户端。**先判断"测的是什么"，再决定"用什么测"**（呼应 [[Ch15-自动化测试策略]] 的"选什么工具"）。

## 三、常见被测系统类型

### 【必须掌握】UI vs Service 两大类型

| 大类      | 具体类型       | 说明                          |
| ------- | ---------- | --------------------------- |
| UI      | Web        | 浏览器应用（Selenium）             |
| UI      | App        | 移动应用（Appium）                |
| UI      | IOT        | 物联网设备界面                     |
| Service | RESTful    | 基于 HTTP 的资源接口，如 Spring Boot |
| Service | webservice | 老式 SOAP/XML Web 服务          |
| Service | RPC        | 远程过程调用，如 dubbo、pb（protobuf） |
| Service | code       | SDK、lib 等库的测试               |

### 【易错点】RESTful vs webservice vs RPC

| 维度   | RESTful        | webservice     | RPC               |
| ---- | -------------- | -------------- | ----------------- |
| 协议   | HTTP           | SOAP over HTTP | 自定义（TCP/HTTP）     |
| 数据格式 | 主要是 JSON       | XML            | 二进制（protobuf）或自定义 |
| 风格   | 资源导向（URL 代表资源） | 操作导向（方法名）      | 像调本地函数一样调远程       |
| 代表   | Spring Boot    | 老式企业系统         | Dubbo、gRPC        |

### 【我的理解】

> 思考：面试官问"你测过什么类型的系统"，如果你只回答"测过接口"，会不会太笼统？试着把"接口"再往下细分一层。

## 四、部署方法总览

### 【必须掌握】三种部署方法

| 部署方法 | 产物                  | 核心工具                   | 特点           |
| ---- | ------------------- | ---------------------- | ------------ |
| 打包部署 | apk/app/ipa/jar/war | gradle/xcode/npm/maven | 打包成可安装/可运行文件 |
| 脚本部署 | 自动化脚本               | bash/python + Jenkins  | 脚本化自动构建与部署   |
| 容器部署 | 容器镜像                | Docker/K8s + Jenkins   | 镜像化，环境一致、可编排 |

### 【为什么部署方法从"打包"演进到"容器"？】

| 演进   | 解决的痛点                                   |
| ---- | --------------------------------------- |
| 打包部署 | 把代码变成可运行产物，但环境还是要手工配                    |
| 脚本部署 | 自动执行构建和部署，减少手工操作                        |
| 容器部署 | 把"代码 + 依赖 + 环境"一起打包成镜像，彻底消除"我这儿能跑你那儿不行" |

## 五、打包部署与打包命令

### 【必须掌握】四种打包方式

| 平台          | 打包工具               | 产物        |
| ----------- | ------------------ | --------- |
| Android     | gradle             | apk       |
| iOS         | xcode / xcodebuild | app / ipa |
| Web（前端）     | nodejs + npm       | 优化后的静态资源  |
| Service（后端） | maven / gradle     | jar / war |

### 【必须掌握】常用打包命令

```bash
# Web（前端）
npm run build

# App（Android，用项目里的 gradlew wrapper）
gradlew tasks              # 查看所有可用任务
gradlew assembleDebug      # 打包 Debug 版本
gradlew assembleRelease    # 打包 Release 版本

# Spring Boot（后端）
mvn clean package          # 清理 + 打包成 jar/war
```


### 【易错点】gradle vs gradlew vs maven

| 概念 | 是什么 | 别搞混 |
|------|--------|--------|
| gradle | 全局安装的构建工具 | 依赖机器上装的版本 |
| gradlew | 项目里的 wrapper 脚本 | 保证团队用同一版本，无需全局安装 |
| maven | Java 的另一套构建工具 | 用 pom.xml 管理依赖，命令是 mvn |

> 面试时能说出"gradlew 是 wrapper，保证构建版本一致"是加分项。

### 【为什么前端要 `npm run build`？】

开发时的前端代码（源码、模块、未压缩）不能直接上线——`npm run build` 会把源码打包成"优化后的版本"（压缩、合并、tree-shaking），供生产环境使用。测试前也要先确认被测版本是"构建后的产物"还是"开发态"，两者行为可能不同。

### 【我的理解】

> 思考：Android 用 gradle、iOS 用 xcode、Web 用 npm、Service 用 maven，为什么"打包"这件事在不同平台要用不同的工具？（提示：各平台语言和运行环境不同）

## 六、自动化脚本部署

### 【必须掌握】

| 手段 | 说明 |
|------|------|
| bash / python 脚本 | 用脚本自动完成构建、拷贝、启动、配置等部署步骤 |
| Jenkins（持续集成平台） | 流程管理：触发构建 → 跑测试 → 自动部署，全链路可视化 |

### 【为什么用脚本部署？】

手工部署每步都要人点、人敲，容易漏、容易错、不可重复。脚本部署把步骤固化下来：同一份脚本，每次部署结果一致、可回滚、可审计。Jenkins 再往上抽象一层——把"脚本"变成"流水线"，定时或提交触发。

### 【易错点】脚本部署 vs 容器部署

| 维度 | 脚本部署 | 容器部署 |
|------|---------|---------|
| 部署对象 | 脚本直接操作机器 | 先构建镜像，再运行容器 |
| 环境一致性 | 依赖目标机器环境 | 镜像自带环境，天然一致 |
| 编排能力 | 弱（脚本自己写逻辑） | 强（K8s 自动调度、扩缩容） |

## 七、容器部署

### 【必须掌握】容器部署四件套

| 环节 | 工具 | 作用 |
|------|------|------|
| 自动化构建 | bash | 打包、触发构建的脚本 |
| 容器构建 | Docker | 把应用 + 依赖打成镜像 |
| 容器编排 | K8s | 镜像的部署、调度、扩缩容 |
| 持续集成 | Jenkins | 串联"构建 → 测试 → 部署"流水线 |

### 【为什么容器部署能"消除环境差异"？】

Docker 把"代码 + 依赖 + 运行环境"一起打进镜像，镜像在任何机器上跑出来的行为一致——"我这儿能跑你那儿不行"的问题被根治。K8s 在这个基础上管理成百上千个容器的部署和调度。

### 【面试考察】

> 面试官："你们测试环境是怎么部署的？"

**参考回答框架：** 分阶段演进。早期是打包部署——开发打好 jar/war/apk，测试手工部署到测试机；后来用脚本部署——bash/python 脚本自动构建部署，Jenkins 管流程；现在很多团队用容器部署——Docker 打成镜像、K8s 编排，环境一致性好，测试环境和生产环境用同一套镜像，减少了"环境差异导致的假 Bug"。

### 【我的理解】

> 思考：为什么"测试环境和生产环境用同一套 Docker 镜像"能减少"只在生产出现的 Bug"？这和第一节"环境要尽量和生产一致"是什么关系？
