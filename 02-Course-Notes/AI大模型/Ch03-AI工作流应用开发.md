## 一、工作流 Workflow 概述

### 知识点 1：什么是工作流

【课程原话/定义】

工作流是为了实现目标而按特定顺序完成的一系列结构化任务或步骤。它概述了从开始到结束的流程，有助于确保效率和清晰度。工作流可简可繁，可用于商业、IT 甚至个人组织。

工作流通过将复杂任务分解成较小的步骤（节点）来降低系统复杂度，减少了对提示词技术和模型推理能力的依赖，提高了 LLM 应用面向复杂任务的性能，提升了系统的可解释性、稳定性和容错性。

【为什么？】

单个大模型面对复杂任务时有两个痛点：
1. **长链条推理容易出错**：让 GPT 一次完成"拆需求 → 设计用例 → 合并结果"整条链路，中间任何一步推理错误都会污染后续
2. **不可解释、不可控**：黑盒输出，无法在中间插入校验或人工干预

工作流的解法是"分而治之"：把复杂任务拆成一个个明确的节点，每个节点只做一件事，节点之间用变量传递数据。这样：
- 每个节点职责单一，提示词更简单
- 中间结果可见、可校验、可容错
- 不依赖模型"一口气做对"，稳定性大幅提升

【必须掌握】

- 工作流 = 按特定顺序排列的结构化任务步骤
- 核心价值：降复杂度、提性能、可解释、稳定、容错
- 工作流是"编排"思想，和程序设计的"函数拆分"同构

【易错点】

| 误区 | 事实 |
|------|------|
| 工作流 = 只是把提示词连起来 | 工作流包含逻辑控制、变量、异常处理，是完整编排 |
| 有工作流就不用写提示词 | 每个大模型节点仍需好的提示词，只是难度降低 |
| 工作流和 Agent 是一回事 | Agent 是自主推理选工具，工作流是固定编排，两者可结合 |

【我的理解】

> 为什么说工作流"减少了对提示词技术和模型推理能力的依赖"？它具体把哪些原本靠模型"硬扛"的负担，转移到了哪里？

## 二、工作流核心要素

### 知识点 2：核心要素

【课程原话/定义】

```
开始 / 结束
状态与变量
条件分支 / 循环迭代
内部工具 / 外部工具 / 工作流工具
```

【为什么？】

这些要素对应了编程的基本结构：
- 开始/结束 → 程序的入口和出口
- 状态与变量 → 数据存储和传递
- 条件分支/循环迭代 → if/for/while 控制流
- 工具 → 函数调用

工作流本质是**"可视化编程"**——把代码逻辑用节点图表达出来，降低非程序员搭建 LLM 应用的难度。

## 三、Dify 工作流节点

### 知识点 3：节点分类

【课程原话/定义】

| 分类    | 节点           | 作用      |
| ----- | ------------ | ------- |
| 基础节点  | 开始、结束、对话回复   | 流程入口/出口 |
| 工具节点  | HTTP请求、代码、工具 | 执行外部操作  |
| 大模型节点 | LLM、知识检索、智能体 | AI 能力   |
| 逻辑控制  | 条件、迭代、循环     | 分支与循环   |
| 异常控制  | 异常处理         | 容错      |

【为什么？】

Dify 把节点分成几类，反映了一个 LLM 应用需要的能力：
1. **AI 能力**（大模型、知识检索、智能体）—— 应用的"大脑"
2. **工具能力**（HTTP、代码、工具）—— 应用的"手脚"，连接外部世界
3. **逻辑编排**（条件、迭代、循环）—— 应用的"神经系统"，控制流程
4. **异常控制** —— 应用的"免疫系统"，容错恢复

【必须掌握】

- 大模型节点：调用 LLM 处理上游输入
- 知识检索节点：从知识库检索相关内容，作为 LLM 的上下文（RAG 实现）
- 智能体节点：让 LLM 自主选择并执行工具（Agent）
- HTTP 请求节点：调外部 API
- 代码节点：运行 Python/NodeJS 做数据转换

---

### 知识点 4：变量

【课程原话/定义】

变量用于串联工作流内前后节点的输入与输出。三类：

| 变量类型 | 作用               | 示例                                              |
| ---- | ---------------- | ----------------------------------------------- |
| 系统变量 | 平台预置，只读          | `sys.user_id`、`sys.files`、`sys.conversation_id` |
| 环境变量 | 存敏感信息，不在代码里      | API 密钥、数据库密码                                    |
| 会话变量 | 同一会话内多轮对话共享的临时信息 | 用户偏好、中间状态                                       |

【为什么？】

- **环境变量**隔离敏感信息：密钥存在工作流配置里而非代码，方便不同环境（开发/测试/生产）共享同一份工作流、注入不同密钥
- **会话变量**解决多轮对话的状态问题：LLM 本身无状态，需要会话变量在 Chatflow 的多轮对话间"记住"信息

【易错点】

| 变量   | 生命周期    | 是否可写  |
| ---- | ------- | ----- |
| 系统变量 | 每次运行固定  | 只读    |
| 环境变量 | 跨运行、跨会话 | 配置时设置 |
| 会话变量 | 单次会话内   | 运行中可写 |

### 知识点 5：逻辑控制节点

【课程原话/定义】

| 节点 | 对应编程结构 | 用途 |
|------|-------------|------|
| 条件（if/else） | if elif else | 按条件分支 |
| 迭代（iteration） | for item in items | 遍历数组，逐个处理 |
| 循环（loop） | while | 满足条件时重复执行 |

【为什么？】

区分"迭代"和"循环"：
- **迭代**：已知集合（如 10 个功能点），逐个遍历处理 → for
- **循环**：未知次数，靠条件退出（如"直到测试用例数量达标"）→ while

实战中"测试用例批量生成"用的就是迭代——拆出 N 个功能点，对每个功能点迭代生成用例。

【企业场景】

> 你要批量生成测试用例：用户输入一个需求，先拆成 5 个功能点，然后"针对每个功能点"生成用例。
>
> 这里用**迭代节点**：`for 功能点 in 功能点列表`，每个迭代里调用大模型节点，为该功能点生成用例，最后合并所有输出。这就是 Dify 工作流实战的核心编排。

---

### 知识点 6：异常控制

【课程原话/定义】

异常处理机制提供多样化的节点错误处理策略，能在局部节点出错时抛出故障信息而不中断主流程。可设置异常时重新执行节点，或通过备用路径继续任务。

【为什么？】

LLM 调用天然不稳定（超时、限流、格式错乱）。如果某个节点报错导致整个工作流失败，用户体验极差。异常控制让工作流具备"容错"能力——重试或走备用路径，保证主流程不中断。

## 四、工作流工具

### 知识点 7：工作流发布为工具

【课程原话/定义】

非对话的工作流可以发布为工具，其他工作流可以以工具节点的方式调用该工作流。

【为什么？】

这体现了"复用"思想：一个复杂的工作流（如"生成测试用例"）可以被封装成工具，在其他工作流里像函数一样调用。工作流之间可以像搭积木一样组合，构建更复杂的应用。

## 五、工作流实战：测试用例批量生成

### 知识点 8：测试用例批量生成工作流

【课程原话/定义】

**基础流程编排：**

```
用户输入需求
    ↓
大模型拆解功能点与测试点
    ↓
迭代功能点 → 针对每个功能点生成测试用例
    ↓
合并测试用例
```

**高级流程编排（递归）：**

```
用户输入需求
    ↓
分层迭代功能点
    ↓
大模型拆解功能点与测试点
    ↓
迭代功能点 → 生成测试用例
    ↓
合并测试用例
```

【为什么？】

为什么"拆解 → 迭代生成 → 合并"比"一次性生成所有用例"效果好？

1. **拆解**让模型聚焦于"识别功能点"这一单一任务，比"识别+生成"混合任务更准
2. **迭代**把每个功能点单独喂给模型，提示词上下文更聚焦，生成的用例更深入
3. **合并**把分散结果汇总成最终输出

这本质上就是"提示词工程五大原则"里的"拆分复杂任务"——用工作流固化了这套最佳实践。

【必须掌握】

- 实战编排：拆解 → 迭代 → 合并
- 用 structured output（JSON Schema）约束模型输出格式

【企业场景】

> 你是测试工程师，每天要为新需求设计测试用例。用 Dify 搭一个"测试用例批量生成"工作流：
> 1. 输入需求（如"百度搜索"）
> 2. 大模型节点用 system prompt 设定角色"你是一名软件测试工程师，擅长测试用例设计"
> 3. 用 JSON Schema 约束输出结构（module/testcase/package）
> 4. 迭代节点遍历功能点，逐个补充更多测试点
> 5. 结束节点合并输出
>
> 这样你每次只需输入需求，工作流自动产出结构化测试用例，再用 Excel/TestRail 导入。

【扩展知识：structured output 的 JSON Schema】

```json
{
  "format": {
    "type": "object",
    "properties": {
      "testcases": {
        "type": "array",
        "items": {
          "type": "object",
          "properties": {
            "module": {"type": "string"},
            "testcase": {"type": "string"},
            "package": {"type": "string"}
          },
          "required": ["module", "testcase"]
        }
      }
    },
    "required": ["testcases"]
  },
  "options": {"temperature": 0.7}
}
```

用 JSON Schema 强约束输出，比"请在输出里用 JSON 格式"这种自然语言提示可靠得多——因为模型会严格对齐 schema，后续代码才能稳定解析。

【易错点】

| 做法 | 问题 | 改进 |
|------|------|------|
| 自然语言要求"输出 JSON" | 模型可能输出不合法 JSON | 用 JSON Schema structured output |
| 一次性生成所有用例 | 用例浅、覆盖不全 | 拆解+迭代 |
| temperature 设太高 | 输出不稳定，格式易乱 | 结构化输出时降低 temperature |
