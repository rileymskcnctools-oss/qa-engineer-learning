### 逐题批改

#### 1. 弃忍区 TPS 为什么下降（Ch01 知识点 8）✅

**你的答案要点**：TPS 下降不是系统"没在工作"，而是系统太忙——大量资源花在"等待 + 重试 + 上下文切换 + 超时处理"上，而不是真正的业务处理。

**✅ 到位**：抓到了本质——**资源被内耗**（不是资源不够），而且把"重试/上下文切换/超时"这几个连锁动作列全了。

**⚠️ 加深点**：还缺两处（面试往下追问就会问到）
- 缺"**GC / 内存回收**"这一项——课程原文的链条里，GC 抢占是压力区往弃忍区滑落的关键推手。
- 缺"**为什么利用率还是 99%**"的收口——资源利用率只反映"忙"，不反映"有效"。

**引导题（写回 Ch01 知识点 8 的【我的理解】）**：
> 既然资源都被"内耗"掉了，为什么资源利用率曲线仍然顶在 99% 而不是掉下来？如果只看利用率，你会把弃忍区误判成什么？

#### 2. 1 分钟讲清为什么选 JMeter（Ch04 知识点 7）✅

**你的结构**：适合接口/服务端性能测试 → 协议支持（HTTP/HTTPS）→ 并发模拟（线程数、Ramp-up）与指标（TPS/RT/错误率）→ 参数化/关联/断言/前置后置处理器串起真实业务流程 → 开源、插件资料丰富、易与 CI/CD 和监控工具结合 → 收口到"我们场景下成本合适"。

**✅ 到位**：没有罗列优点，走的是"能力 → 适配我们的场景"这条主线，最后一句收口非常专业。参数化 + 前后置处理器这条（能串业务流程）是很多人漏掉的点，你讲到了。

**⚠️ 加深点**：缺"**规模**"这一维——高可扩展性/分布式压测没提。

**引导题（写回 Ch04 知识点 7 的【我的理解】）**：
> 面试官追问："你们最大压到多少并发？单机压不上去怎么办？"——请补一段回答（提示：先排除起压机瓶颈，再分布式加机器）。

#### 3. TPS 走平时的定位路径（Ch05 知识点 1）✅✅

**你的答案要点**：JMeter（先确认真的走平：TPS/RT/错误率/活动线程）→ vmstat（r / id / wa / si,so 判断系统资源）→ top（定位哪个进程/线程）。还写了判断条件："线程数继续增加但 TPS 不再增加、RT 越来越高 → 系统已出现处理瓶颈"。

**✅✅ 到位**：这一题的难点是"给出判断条件"而不是"列工具"，你做到了；三层顺序也对（业务 → 系统 → 进程）。

**⚠️ 加深点**：两个缺口
- 缺**压测机侧检查**（TIME_WAIT / 端口 / 起压机 CPU）——不看这一侧，会把"压不上去"误判成"被压系统到顶了"。
- 缺**第四层下钻**（top -H → jstack / 火焰图）——你写到"Java 进程 CPU 高，继续往 JVM"就停了，那一步正是剖析工具（Ch06）的入口。

**引导题（写回 Ch05 知识点 1 的【我的理解】）**：
> 若 JMeter 显示 2000 并发，但 nginx 日志统计出的每秒请求数远低于预期，你会先怀疑哪一侧？给出两个具体的检查项。

#### 4. r=25 那组数据的判断（Ch05 知识点 2）✅

**你的答案**：r=25 → 运行队列长；id=5% → CPU 基本满载；wa=2% → I/O 等待不高；si/so=0 → 无明显 Swap → 优先判断 **CPU 是主要瓶颈**，大量任务在竞争 CPU，下一步用 top 定位进程/线程。

**✅ 到位**：四个字段各对上了瓶颈方向，还给出了下一步动作。这就是"能干活"的答法。

**⚠️ 加深点**：可以再补一句"**结论要落成容量动作**"——不是"CPU 瓶颈"就结束，而是"当前规格的容量上限约为 X，扩容或优化二选一"（这正是 Ch01 知识点 9 的三段式结论）。

**引导题（写回 Ch05 知识点 2 的【我的理解】）**：
> 如果这个数值是在压测中出现的，你会给出"扩容"还是"优化"的建议？判断依据分别是什么？

#### 5. 哪两步最易跳过 + 只保留三步（Ch07 知识点 1）✅✅

**你的答案**：第 2 步（获取当前性能指标）与第 4 步（定义验收标准）最易被跳过——大家都想直接上工具压，却没先搞清楚"系统现在什么水平"和"什么结果算合格"。没有基线无法判断提升/退化，没有标准测出 TPS/RT 也不知道是否达标。若只保留三步：**定义验收标准 + 建立性能基线 + 执行压测并结合监控分析**，分别回答"目标是什么、现状是什么、实际结果怎么样"。

**✅✅ 到位**：把流程抽成三个问题，这是"理解"而不是"背步骤"的标志。顺序上你把"目标"放在"现状"之前，也说得通（先声明目标再取基线同样成立）。

**⚠️ 加深点**：这三问还差**最后一环**——"所以呢？"（结论与建议）。否则报告到"实际结果"就断了，团队拿不到动作。

**引导题（写回 Ch07 知识点 1 的【我的理解】）**：
> 如果流程只到"实际结果"就结束，报告会缺什么？为什么这一环决定了性能测试在团队里有没有话语权？

#### 6. 性能回归为什么用 RPS + 怎么设计（Ch07 知识点 3）✅✅

**你的答案**：回归的核心是比较前后变化 → 必须保证压力一致；并发模式下 RT 变化会让实际请求速率变化、压力不可比；RPS 模式固定请求速率，适合回归。方案：固定环境/数据/脚本，只改代码；固定 100 RPS；优化前预热并建基线（平均 RT、P95、错误率、CPU）；优化后同样 100 RPS 再测；最后对比计算优化幅度，而不是"感觉变快了"。

**✅✅ 到位**：控制变量 + 预热 + 多指标 + 量化表达，这就是标准答案；"不说感觉变快了"这句尤其加分。

**⚠️ 加深点**：再补两点就完美
- **复跑多次取稳定值**（单次结果波动会误导结论）；
- 主动说明"**优化后并发占用会变小**"——同样 100 RPS 下 RT 降低 → 占用系统的并发数减少，这是效率提升而非"压力变了"（面试官爱在这里挖坑）。

**引导题（写回 Ch07 知识点 3 的【我的理解】）**：
> 优化后 RT 从 200ms 降到 120ms，同样是 100 RPS，并发线程数会变多还是变少？这算不算"压力变了"？为什么？
