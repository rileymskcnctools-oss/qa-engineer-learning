### 知识点1：参数化是什么，为什么必须做

【课程原话/定义】
JMeter 使用变量进行参数化测试，是指在 JMeter 测试计划中，通过定义和使用变量来替代硬编码的测试数据，以实现测试数据的动态化和可配置化。这种方法可以极大地提高测试效率和灵活性，特别适用于需要测试大量不同数据或在不同环境下进行重复测试的场景。

课程给出的"使用参数化的优点"（原文 4 条）：
1. **提高测试效率**：一份测试逻辑配多组参数反复运行，不必为每个新输入重复写用例；敏捷开发中让测试跟得上迭代节奏；
2. **增加测试覆盖率和真实性**：轻松覆盖正常值、边界值、异常值，发现更多潜在缺陷；为每个虚拟用户用不同参数，业务更接近真实客户；
3. **易于管理与扩展**：测试数据以表格/文件等结构化方式存储，管理直观、便于扩展；
4. **更好的错误定位**：某个参数化的用例失败时，能知道是**哪个参数组合**导致的失败。

【为什么？】
参数化要解决的是压测里最根本的"**假并发**"问题。如果 500 个虚拟用户登录的是同一个账号、下单的是同一个商品、请求的是同一条数据，那么：
- **缓存全部命中**：第一次请求之后，后面的请求几乎不碰数据库——你压出来的是缓存，不是系统真实能力，TPS 会虚高；
- **锁与顺序被抹平**：同一行数据的行锁、同一账号的限购/防重逻辑根本不会被触发，真实的并发冲突问题一个都测不出来；
- **数据失真**：业务侧的统计（订单量、UV）全被污染，压测数据没法用来做容量判断。

所以参数化的价值不止"少写几份脚本"，而是**让每个虚拟用户成为"不同的用户"**——这也是课程把"增加覆盖率和真实性"单独列一条的原因。另外两条（易管理扩展、错误定位）是工程收益：数据结构化之后，加一个场景＝加几行数据；失败时能指名道姓地说是哪一行数据坏了。

【必须掌握】

| 参数化的 4 类收益（原文） | 具体含义 | 落地动作 |
|---|---|---|
| 提高测试效率 | 一份逻辑 × 多组数据 | 脚本只维护一份，数据放到外部（CSV / 属性 / DB） |
| 增加覆盖率与真实性 | 覆盖正常 / 边界 / 异常值；每用户不同数据 | 准备"正常 + 边界 + 异常"三类数据，账号池按线程分发 |
| 易于管理与扩展 | 数据结构化存储 | 数据落在 CSV 文件里，加场景只加行 |
| 更好的错误定位 | 知道是哪个参数组合失败 | 让每个请求带上可识别的数据（如 `userId`），失败时能回溯到具体行 |

【企业场景】
你压"登录 → 查询订单"链路。用同一个账号压 500 并发：登录接口第一次之后全部命中会话缓存，查询接口全部命中同一份订单缓存，TPS 轻松上到几千——上线后真实用户一来，系统直接雪崩。企业做法：准备 500 行账号（生产脱敏导出）+ 每个账号若干订单号，用 CSV 参数化，压测前先确认"每行数据只用一次"（看 Debug Sampler 里的取值分布和日志中的 userId 去重数量）。**判断压测结论可信的第一问就是"数据是不是真的分开了"。**

【面试考察】
面试官："性能测试为什么要做参数化？不参数化会怎样？"

参考回答框架：
1. 目的：让每个虚拟用户发**不同的数据**，否则测出来的是缓存与顺序执行，不是真实并发；
2. 不参数化的三个后果：缓存命中导致 TPS 虚高、锁/防重逻辑不触发、业务数据被污染；
3. 收益四条：效率（一份逻辑多组数据）、覆盖率与真实性（正常/边界/异常）、易管理扩展（数据结构化）、错误定位（能追到具体参数组合）；
4. 加分：参数化是"关联"之外的另一个基础能力——关联解决"值从响应来"，参数化解决"值从数据源来"。

【易错点】

| 常见错误 | 正确理解 |
|---|---|
| 认为参数化只是"省得改脚本" | 核心目的是**模拟真实用户（数据不同）+ 提高覆盖率**；省事只是附带收益 |
| 用同一个账号 / 同一个商品压全站 | 缓存命中 + 锁不触发 → TPS 虚高、问题测不出来；必须做数据分离 |
| 只准备"正常值"数据 | 面试与实战都要求覆盖**正常 / 边界 / 异常**三类，异常值能暴露参数校验与容错缺陷 |
| 参数化后不看数据是否真的分开了 | 要验证：Debug Sampler 里的取值、日志里 userId 的去重数量、行数是否够线程用 |
| 把"参数化"和"关联"混为一谈 | 关联＝值来自**响应**（后置处理器）；参数化＝值来自**数据源**（CSV / 变量 / 函数） |

【我的理解】引导题（用自己的话回答）：
1. 用"缓存命中"这四个字解释：为什么用同一个账号压 500 并发，TPS 会虚高、结论会错？
2. 课程列的 4 条参数化优点里，哪一条最容易被初学者忽略？它在企业里对应的动作是什么？

### 知识点2：参数化测试的四种类型（原文 4 类 → 选型表）

【课程原话/定义】
课程列出参数化测试的 4 种类型：
1. **用户定义的变量**：适用于那些**不需要在测试计划执行过程中发生变化**的参数（例如应用的 `tid`、`vid`），可以在测试计划开始前定义，并在整个测试计划中使用；
2. **用户参数（User Parameters）**：与用户定义的变量不同，用户参数列表中的参数取值**可以在测试计划执行过程中发生变化**——可以为同一参数设置多组不同的值，并在每次迭代中使用不同的值；
3. **函数助手（Function Helper）**：JMeter 提供丰富的函数助手，帮助生成各种类型的变量值，如随机数、时间戳等；
4. **CSV 数据文件设置（CSV Data Set Config）**：把测试数据存储在 CSV 文件中，在 JMeter 中通过读取 CSV 文件来设置参数值，**特别适用于有大量测试数据的场景**。

【为什么？】
这 4 类的差别只有一句话：**"值从哪来、什么时候变"**——这正好是 [[Ch32-JMeter变量与引用]] 里那张"求值时机"表的应用。把它们放在一起看，选型逻辑就出来了：

| 类型 | 值从哪来 | 什么时候变 | 适合什么 |
|---|---|---|---|
| 用户定义的变量（UDV） | 脚本里人工写 | **测试开始一次** | 环境域名、端口、固定 tid/vid 等**常量** |
| 用户参数（User Parameters，前置处理器） | 脚本里人工写多组 | **同一线程内按迭代/按取样器推进** | 少量、需要"每个虚拟用户一组值"的场景（例如给每个线程分一个固定用户 ID） |
| 函数助手 | 运行时计算 | **每次调用**（`${__Random}`）/ 一次（`${__time}` 视用法） | 随机数、时间戳、唯一序号、线程号 |
| CSV 数据文件设置 | 外部文件 | **每个迭代取一行** | 大量数据（账号池、商品池、订单池）——**企业主力方案** |

为什么官方独推 CSV 处理大数据量？官方原文（CSV Data Set Config 页）给了两条理由：*"It is well suited to handling large numbers of variables"*，以及——*"Generating unique random values at run-time is expensive in terms of CPU and memory, so just create the data in advance of the test."*（运行期生成唯一随机值很耗 CPU 和内存，**不如提前把数据准备好**）。这一句是性能工程师的思维：**别让施压机把资源花在造数据上**，否则施压机自己就成了瓶颈。

【必须掌握】

| 类型 | 元件 / 位置 | 关键参数或写法 | 一句话适用判据 |
|---|---|---|---|
| 用户定义的变量 | 配置元件 User Defined Variables | Name / Value | 值**从头到尾不变** |
| 用户参数 | 前置处理器 User Parameters | Name + 多列 User 值 + `Update Once Per Iteration` | 少量数据、**每个线程一组**、按迭代推进 |
| 函数助手 | 函数面板（Function Helper Dialog） | `${__Random(min,max)}`、`${__time()}`、`${__threadNum}` | 值**需要现算**（唯一、随机、时间） |
| CSV 数据文件设置 | 配置元件 CSV Data Set Config | Filename / Variable Names / Recycle / Sharing mode | 数据量大、**要用文件管理** |

> 【扩展知识】官方对"用户参数（User Parameters）"的定义值得抄下来：*"Allows the user to specify values for User Variables specific to individual threads… For each thread, the variable will be assigned one of the values from the series in sequence. If there are more threads than values, the values get re-used."*（**按线程**依次取一组值，值不够就复用）+ 参数 `Update Once Per Iteration`：勾选＝每次经过父控制器时更新一次；不勾＝作用域内**每个取样请求**都推进一次（官方原文：*"the UP will update the parameters for every sample request made within its scope"*）。**同一个元件，勾不勾选中会差出一个数量级的数据消耗**，这是本节最容易踩错的一处。

【企业场景】
你手上是"50 个账号 × 每个账号 20 个订单"的数据：账号要"每个线程分一个、整轮不变"，订单要"每次请求都换"。企业做法：账号用 **User Parameters**（或用 CSV + `Sharing mode: Current thread`），把 50 个账号按线程分发；订单用 **CSV Data Set Config**（每迭代一行）。如果全部塞进 UDV，账号和订单都会变成固定值；如果全部塞进 CSV 而线程数远大于行数，就会出现"同一个账号被多线程同时使用"——**选型错了，压测数据就废了**。

【面试考察】
面试官："JMeter 里有哪几种参数化方式？各自用在什么场景？"

参考回答框架：
1. 四类：用户定义的变量（UDV，一次性常量）→ 用户参数（User Parameters，按线程分组的少量数据）→ 函数助手（随机/时间/序号，现算）→ CSV Data Set Config（大数据量，每迭代一行）；
2. 选型判据一句话："值变不变、什么时候变、数据量多大"；
3. 大数据量优先 CSV（官方：CSV 适合大量变量；运行期造随机数很耗 CPU/内存）；
4. 加分：User Parameters 的 `Update Once Per Iteration` 决定"按迭代更新"还是"每个取样请求都更新"。

【易错点】

| 常见错误 | 正确理解 |
|---|---|
| 把 UDV 当参数化用（"我有变量了就够了"） | UDV 是**一次性常量**，不能让每轮数据不同；参数化必须用 CSV / User Parameters / 函数 |
| 线程多、数据少，直接用默认 Sharing mode 又没算行数 | 默认 `All threads` 下每个线程取不同行，**行数不够时会按 Recycle 规则复用**——会出现多个线程用同一行数据 |
| 用函数 `__Random` 造大量唯一数据 | 运行期造唯一值很耗 CPU / 内存（官方原文），大数据量应提前生成到 CSV |
| 用户参数（User Parameters）不勾 `Update Once Per Iteration` 却想要"按迭代换值" | 不勾＝作用域内**每个取样请求**都推进一次，数据会被快速耗尽，行为与预期不符 |
| 以为"用户参数"＝"用户定义的变量" | 前者是**前置处理器**、按线程/迭代推进；后者是**配置元件**、测试开始一次 |

【我的理解】引导题（用自己的话回答）：
1. 用"值变不变、什么时候变"这句话，把 UDV / 用户参数 / 函数 / CSV 四类排成一条从"最不变"到"最常变"的线，并各举一个业务例子。
2. 官方为什么说"运行期生成唯一随机值不如提前准备数据"？这句话对**施压机资源**有什么工程含义？

### 知识点3：做法一 —— 用户自定义变量（操作步骤与它做不到的事）

【课程原话/定义】
操作步骤（原文）：
1. 创建线程组；
2. 创建 User Defined Variables（用户自定义变量）元件；
3. 配置元件 User Defined Variables（填 Name / Value）；
4. 在 HTTP 请求里调用变量。

【为什么？】
这一段步骤与 [[Ch32-JMeter变量与引用]] 知识点2 完全同源（站点两页都讲 UDV），所以这里**不要重复背步骤**，而要记"它做不到什么"：UDV 在测试计划开始时一次性求值，因此它**只能做参数化里"最不变"的那一类**——把 tid、vid、域名、端口、固定账号从硬编码里抽出来。课程用 tid/vid 举例非常贴切：这两个值在一次压测里就是不变的。

真正要带走的知识是**判断标准**：如果一个值在一次压测里不变 → UDV 没问题；如果它需要"每个用户不同"或"每轮不同" → 必须换成 用户参数 / CSV / 函数。这一条判断错，压测数据就废了（而且是静默的：脚本不会报错，只是数据重复）。

【必须掌握】

| 步骤 | 做什么 | 检查点 |
|---|---|---|
| 1 | 创建线程组 | 线程数 / Ramp-up / 循环次数先按小样本设（1 线程 1 轮） |
| 2 | 添加配置元件 → User Defined Variables | 位置：线程组下或测试计划下（求值时机都一样） |
| 3 | 填 Name / Value | 名字见名知意（`host` / `tid` / `vid`）；值不要用 `${__Random}` 这类函数 |
| 4 | 在 HTTP 请求里用 `${变量名}` 引用 | 跑完后用 View Results Tree 看**请求里是否真被替换** |

| UDV 能做 / 不能做 | 说明 |
|---|---|
| 能做 | 抽出**恒定**的环境参数与业务常量（域名、端口、tid、vid、固定商户号） |
| 不能做 | 每用户不同（要 User Parameters / CSV）、每轮不同（要 CSV）、每次调用不同（要函数）、取响应值（要后置处理器） |

【企业场景】
你把"内外网域名 + 两个固定业务参数（tid/vid）"做成 UDV，脚本交给同事后：他改一行 `host` 就能跑自己的环境，tid/vid 由业务方一次性给。**这就是 UDV 的正确定位——环境与常量层**；而账号池、商品池一定不要放这里，否则 500 线程全用同一个账号，压出来的数据没人敢用来做容量决策。

【面试考察】
面试官："用户定义的变量能做参数化吗？什么时候该换别的方式？"

参考回答框架：
1. 能，但只能做**不变的那一层**（环境参数、业务常量，如 tid / vid / host）；
2. 判据：值在一次压测里是否恒定——恒定用 UDV；每用户不同用 User Parameters / CSV（Sharing mode）；每轮不同用 CSV；
3. 提醒：UDV 在测试计划开始时一次性处理，不能引用运行期变量、不能放 `__Random` 这类函数（官方原文）；
4. 实操：小样本跑一次，用 View Results Tree 确认 `${变量}` 被替换、Debug Sampler 确认取值。

【易错点】

| 常见错误 | 正确理解 |
|---|---|
| 把账号池放进 UDV | 500 线程会共用同一个账号 → 缓存命中 + 数据重复；账号池要用 CSV / User Parameters |
| 把 `${__Random}` 写进 UDV 当"随机参数" | 只保存第一次结果（官方原文），所有线程都一样 |
| 只配置不验证 | 必须小样本跑一遍并看 View Results Tree 里请求是否被替换（`${tid}` 原样出现就是失败的信号） |
| 认为"放测试计划下"和"放线程组下"效果不同 | 所有 UDV 都在测试开始时处理（官方：no matter where they are），差别只在**同名覆盖顺序**（从上到下） |

【我的理解】引导题（用自己的话回答）：
1. 为什么课程用 tid / vid 举例 UDV？请再举两个"适合放进 UDV"的值和两个"绝对不能放进 UDV"的值。
2. 如果同事把账号池写进了 UDV，你在压测报告里会先看到什么异常现象？（提示：数据重复 + 缓存命中）

### 知识点4：做法二 —— 从 CSV 文件中读取数据（操作步骤，含专页分工）

【课程原话/定义】
操作步骤（原文，从 CSV 文件中读取数据）：
1. 创建线程组；
2. 创建 HTTP 请求；
3. 准备一个 `data.csv` 文件；
4. 创建 CSV Data Set Config 元件；
5. 配置 CSV Data Set Config；
6. 在 HTTP 请求里进行变量引用；
7. 创建 Debug Sampler 和 View Results Tree 元件；
8. 查看结果。

【为什么？】
这 8 步里真正有技术含量的是第 5 步"配置"——而这个站点页**几乎全用截图糊过去了**，所以本笔记把配置项留给专页 [[Ch34-JMeter参数化csv]] 详讲，这里只讲**为什么企业主流方案是 CSV**：

1. **数据与脚本解耦**：数据在文件里，改数据不用动 `.jmx`；一份脚本配多套数据文件 = 多套场景；
2. **支持大数据量**：官方明确 CSV 适合"large numbers of variables"，还能用文本工具/脚本批量生成（如从数据库导出脱敏数据）；
3. **按迭代推进**：每个迭代取下一行，天然实现"每轮换数据"，配合 `Recycle` / `Stop thread on EOF` 精确控制"数据用完怎么办"；
4. **可与关联组合**：CSV 给"入口数据"，后置处理器给"链路数据"，两条数据来源互补。

第 7 步放 **Debug Sampler + View Results Tree** 是这个流程里最该保留的纪律：CSV 的失败同样是**静默**的——文件路径写错、列名对不上、行数不够，脚本都不会报错，只会把空值或 `<EOF>` 发出去。所以"取到值了吗、引用了没"这两件事必须各用一个元件验证（详见知识点5）。

【必须掌握】

| 步骤 | 关键点 | 容易出错的地方 |
|---|---|---|
| 1–2 | 线程组 + HTTP 请求 | 先用 1 线程 1 轮（数据只有几行时最容易看出错） |
| 3 | 准备 `data.csv` | 首行可作列名（Variable Names 留空时）；**编码统一 UTF-8**；列数与变量名个数对应 |
| 4–5 | CSV Data Set Config 配置 | Filename 路径、Variable Names、Delimiter、Recycle、Sharing mode —— 见 [[Ch34-JMeter参数化csv]] |
| 6 | 请求里 `${列名}` 引用 | 变量名与 CSV 列名（或 Variable Names 里写的名字）完全一致，**大小写敏感** |
| 7–8 | Debug Sampler + View Results Tree | 一个看"值取到了吗"，一个看"请求里替换了吗"；正式压测前删掉 |

【企业场景】
你压"订单查询"接口，需要 10 000 个真实订单号。企业做法：从生产库按脱敏规则导出 `orders.csv`（一列 `order_id`），放进脚本同目录，CSV Data Set Config 里 `Filename` 写文件名、`Variable Names` 写 `order_id`、`Recycle on EOF` 设 `False` + `Stop thread on EOF` 设 `True`（数据用完就让线程停下，避免重复压同一条数据）；请求参数写 `${order_id}`。压完检查两点：日志里 `order_id` 去重数量是否≈10 000、有没有线程因为 EOF 提前结束。**这两点决定"压测是否真的覆盖了 10 000 条数据"。**

【面试考察】
面试官："JMeter 里怎么用 CSV 做参数化？数据用完了怎么办？"

参考回答框架：
1. 元件：配置元件 CSV Data Set Config；`Variable Names` 写列名（或在 CSV 首行写表头、把 Variable Names 留空）；
2. 请求里用 `${列名}` 引用；先用 1 线程 1 轮 + Debug Sampler / View Results Tree 验证；
3. 数据用完的两种策略：`Recycle on EOF = true`（回到第一行重读，默认）或 `false` + `Stop thread on EOF = true/false`（停止线程；或不停止则变量被置为 `<EOF>`）；
4. 大数据量时 CSV 是企业主流：数据与脚本解耦、可批量生成、按迭代推进（官方也推荐这种"提前准备数据"的做法）。

【易错点】

| 常见错误 | 正确理解 |
|---|---|
| 只建元件不验证 | CSV 出错是**静默**的（路径错、列名错、行数不够都不报错），必须 Debug Sampler + View Results Tree 双验证 |
| 认为"用 CSV"就等于"做好了参数化" | 还要看行数 vs 线程数、Sharing mode、Recycle 设置——否则会出现多线程共用一行数据 |
| 数据文件编码与脚本不一致（GBK / UTF-8） | 中文数据会乱码或解析错列；统一 UTF-8，必要时用 `File Encoding` 参数指定 |
| 正式压测带着 Debug Sampler / View Results Tree | 会累积每个响应占内存，施压机失真；调通后必须删除 |
| 把 CSV 步骤与本章"做法一（UDV）"混着背 | 两段步骤是**两种不同做法**；本章是总览页，细节看 [[Ch34-JMeter参数化csv]] |

【我的理解】引导题（用自己的话回答）：
1. 为什么课程要求在第 7 步专门建 Debug Sampler 和 View Results Tree？少了它们，CSV 出问题时会看到什么现象？
2. 如果 CSV 只有 100 行数据、你要压 500 个线程，会发生什么？你会怎么改配置？

### 知识点5：参数化的工程纪律（覆盖三类数据 / 可定位失败 / 与关联的分工）

【课程原话/定义】
课程总结（原文）：参数化测试的类型 + 实现参数化测试（两种做法的操作步骤）。

【为什么？】
把本章知识变成可交付的脚本，靠的是三条纪律，而不是"会点元件"：

1. **数据要覆盖三类值**：课程在"增加测试覆盖率"里点明"正常值、边界值、异常值"。企业里这不是功能测试的专属要求——压测脚本也应包含少量异常值与边界值（例如订单号不存在、金额等于上限），用来验证系统在压力下的**容错路径**是否也稳定（异常分支往往比正常分支更容易成为瓶颈）。
2. **每个请求要带可识别的数据**：课程强调"更好的错误定位：知道是哪个参数组合导致了失败"。落地做法是让数据可回溯——请求里带上 `user_id` / `order_id`，日志与结果树里就能定位到具体行；否则你只知道"有 3% 请求失败"，不知道是哪批数据。
3. **参数化与关联各管一摊**：参数化解决"值从**数据源**来"，关联解决"值从**响应**来"。一条真实业务的完整取值链是：CSV 给账号 → 登录响应提取 token（关联）→ 用 token 调业务接口（参数 + 变量混合引用）。两条链路要能分开讲清楚。

【必须掌握】

| 纪律 | 落地做法 | 验收证据 |
|---|---|---|
| 覆盖三类数据 | 正常 / 边界 / 异常值各准备一批（异常值占比小） | 数据文件里有三类的区段或分文件，报告里能看到异常分支的统计 |
| 失败可定位 | 请求参数带业务标识（`user_id` / `order_id`） | 报告 / 日志能追到具体数据行；能回答"失败集中在哪批数据" |
| 参数 vs 关联分工 | CSV/变量负责入口数据；后置处理器负责响应数据 | 口述链路：CSV → 登录 → 提取 token → 业务请求 |
| 小样本先行 | 1 线程 1 轮 + Debug Sampler + View Results Tree | 变量取值与引用替换都确认过；正式压测前删掉调试元件 |
| 资源意识 | 大数据量提前生成到 CSV，不在运行期硬造 | 施压机 CPU / 内存不被造数据占用（官方观点） |

【企业场景】
压测交付评审时，评委最常问的三句话正好对应上面三条纪律："数据是不是真分开了？"（参数化是否正确）、"失败能不能定位到数据？"（可观测性）、"token 是每用户自己登的还是共用的？"（关联与参数的分工）。**你的脚本只要能当场回答这三问，就是可交付的脚本**；回答不出来，报告里的 TPS 数字再漂亮也不可信。

【面试考察】
面试官："你的压测脚本里数据是怎么准备的？失败了怎么定位？"

参考回答框架：
1. 数据来源分层：常量（UDV）/ 每个用户一组（User Parameters 或 CSV `Current thread`）/ 每轮一行（CSV Data Set Config）/ 现算（函数）；
2. 覆盖三类值（正常 / 边界 / 异常），异常值用来验证容错路径；
3. 可定位性：请求带业务标识，失败能回溯到具体数据行；用断言区分"业务失败"与"技术失败"；
4. 纪律：小样本调通 → 双元件验证取值与引用 → 删调试元件 → 正式压测；Token 等链路数据用关联（后置处理器）。

【易错点】

| 常见错误 | 正确理解 |
|---|---|
| 只测正常数据就出结论 | 缺少边界值 / 异常值，容错路径的性能与稳定性没被验证；异常分支也是瓶颈高发区 |
| 失败只看失败率，不看是哪批数据 | 报告要能回答"失败集中在哪些数据行 / 哪些账号"，否则无法定位 |
| 把 token 也做成 CSV | 如果 token 有有效期，写死的数据会过期；token 应由**登录请求 + 关联**在运行期取得（或用属性一次登录全员复用，见 [[Ch32-JMeter变量与引用]] 知识点4） |
| 数据文件放在个人电脑任意目录 | 相对路径要相对脚本位置可解析；换机器/CI 上跑不动是常见交付事故 |
| 压测结束不复盘数据分布 | 复盘要点：数据去重数量、每行使用次数、异常值命中次数——这些决定结论可信度 |

【我的理解】引导题（用自己的话回答）：
1. 用一句话说清"参数化"和"关联"各自解决什么问题，并给出一个"两者同时出现"的业务链路。
2. 评审时有人问你"失败能不能定位到数据"，你会拿出哪两样证据来回答？
