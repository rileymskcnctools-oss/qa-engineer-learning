### 知识点1：JMeter 变量是什么（定义 / 三类来源 / 为什么需要）

【课程原话/定义】
在 JMeter 中，变量是用于存储和引用值的工具，它们允许测试人员灵活地处理测试过程中的数据。这些变量可以是用户定义的，也可以是通过 JMeter 的内置功能（如 CSV Data Set Config、User Defined Variables 等）自动设置的。

课程原文列出的"使用变量的优点"共 9 条：提高测试效率 / 模拟真实场景 / 便于管理和维护 / 数据集中处理 / 环境切换 / 模拟真实场景（重复）/ 传递参数 / 使用变量值（避免硬编码）/ 跨线程传参。

【为什么？】
把值直接写死在脚本里的代价是**这份脚本只能用一次**：换一台被测服务器要改 URL、换一个账号要改参数、换一个环境要改端口——每改一次都要重新保存 `.jmx`、重新走一遍"改脚本 → 回归调试"，而压测脚本动辄上百个请求，手改必然漏。

变量的本质是把脚本的**结构**（发什么请求、按什么顺序发）和**数据**（发什么值）分开，这是所有工程化测试的第一原则：
1. **结构与数据分离**：一套脚本 + 多套数据 = 多个测试场景（多环境、多账号池、多商品池），不必维护多份脚本；
2. **数据集中**：所有可变值收敛到一处（一个元件 / 一个 CSV / 一个属性文件），改数据不用打开每个请求面板逐条翻找；
3. **避免硬编码**：值只在"定义处"出现一次，引用处统一写 `${变量名}`，改定义处即全局生效。

这也解释了课程为什么把"提高测试效率"（写脚本快）和"便于管理和维护"（改脚本快）分开列——压测脚本的寿命通常远长于一次压测，**后者才是企业里真正省时间的部分**。

【必须掌握】

| 变量的三类来源 | 怎么产生 | 典型元件 / 语法 | 求值时机（关键差异） |
|---|---|---|---|
| ① 用户定义的变量（UDV） | 人工在脚本里写死 | User Defined Variables 元件、测试计划的"用户定义的变量" | 测试计划开始时**一次性**求值，之后不再变（知识点2） |
| ② 内置功能自动生成 | 元件按规则在运行期注入 | CSV Data Set Config、Random Variable、Counter、`${__Random()}`、`${__threadNum}` | 运行时**按迭代 / 按每次调用**求值——这正是它能做参数化的原因 |
| ③ 从响应里提取 | 上游请求的响应 → 提取器 → 变量 | JSON / 正则 / XPath 提取器（后置处理器） | 每个取样器**响应之后**求值（关联取参） |

| 课程 9 条优点 → 整理成 4 类（原文有重复） | 归到哪一类 |
|---|---|
| 提高测试效率 / 便于管理和维护 / 数据集中处理 / 使用变量值（避免硬编码） | **① 复用与维护**：结构与数据分离，改数据不改结构 |
| 模拟真实场景 ×2（不同用户行为、请求频率、持续时间） | **② 贴近真实**：让每个虚拟用户发不一样的数据（＝参数化） |
| 环境切换（开发 / 测试 / 生产） | **③ 环境可移植**：一套脚本多环境跑（`${__P(env)}` 等） |
| 传递参数 / 跨线程传参 | **④ 跨请求传值**：关联（Correlation）——⚠️"跨线程"是原文写错的，变量不跨线程，见 知识点4 |

【企业场景】
你接到"给 5 个环境各跑一遍"的需求（dev / test / pre / prod / 灰度）。硬编码的脚本要维护 5 份 `.jmx`，任何请求改动都要改 5 遍。企业做法：脚本里所有环境相关信息（域名、端口、账号、商户号）全写成 `${变量}`，环境相关的值只在**一处**定义（UDV 给默认值 / 属性文件 / 命令行 `-J` 传值），压测时 `jmeter -n -t x.jmx -Jhost=pre.example.com` 指哪个环境就跑哪个环境。**脚本只有一份，这是"能交付给别人用"和"只能自己用"的分界线。**

【面试考察】
面试官："JMeter 里为什么要用变量？变量有哪几种来源？"

参考回答框架：
1. 目的：**结构（请求编排）与数据（具体值）分离**——一套脚本跑多环境、多账号池，改数据不改结构，避免硬编码散落各处；
2. 三类来源：① 用户定义的变量（UDV，人工定义）；② 配置元件 / 函数自动生成（CSV Data Set Config、Random Variable、`${__Random}`、`${__threadNum}`）；③ 后置处理器从响应提取（JSON / 正则 / XPath 提取器 → 关联取参）；
3. 引用统一是 `${变量名}`；
4. 加分点：三类来源的**求值时机不同**，这就决定了它们各自能干什么（UDV 一次性、CSV/函数按迭代或每次调用、提取器按响应）。

【易错点】

| 常见错误 | 正确理解 |
|---|---|
| 认为"变量只是省得手敲一遍" | 变量的价值在**复用 + 集中管理 + 环境可移植**，不是少打几个字；压测脚本寿命长，易改比好写更重要 |
| 把"用户定义的变量"和"CSV Data Set Config"当成同一类 | 前者人工定义、测试计划开始一次性求值；后者运行时**每个迭代**换一行数据——"每轮换一个值"必须用 CSV，不能用 UDV（知识点5） |
| 照着原文理解"变量可以跨线程传参" | 变量**线程私有**；跨线程共享要用属性 `__setProperty` / `${__P()}`（知识点4，已核对官方文档） |
| 把 9 条优点逐条背 | 原文有重复（"模拟真实场景"出现两次、多条目重叠）；记"复用维护 / 贴近真实 / 环境可移植 / 跨请求传值"4 类更清楚 |
| 变量名随手起（`a`、`v1`、`tmp`） | 企业里变量名要见名知意且成体系（`host`、`token`、`sku_id`、`login_user`），Debug Sampler 里一眼能认出来 |

【我的理解】引导题（用自己的话回答）：
1. 请用"结构与数据分离"这句话，解释变量为什么会同时带来"写脚本快"和"改脚本快"两方面的好处。
2. 课程把优点列成 9 条，我整理成 4 类。请你自己再检查一遍：有没有哪一条你觉得**不该合并**（它确实说的是另一件事）？

### 知识点2：User Defined Variables（用户定义的变量）——操作步骤与"什么时候求值"

【课程原话/定义】
操作步骤（原文 7 步）：
1. 建立线程组；
2. 创建 User Defined Variables 元件；
3. 在元件 User Defined Variables 里添加自定义的键值对（Name / Value）；
4. 创建一个 HTTP 请求；
5. 设置 HTTP 请求以及引用先前创建的变量，通过关键字 `${key}` 来引用已存在的变量；
6. 创建结果树；
7. 查看结果，验证是否引用成功。

【为什么？】
UDV 是"人工定义变量"的标准入口，但它有一个**决定性特征**必须记牢——官方原文：*"all the UDV elements in a test plan - no matter where they are - are processed at the start. So you cannot reference variables which are defined as part of a test run, e.g. in a Post-Processor."*（测试计划里所有 UDV 元件，无论放在哪里，都在测试开始时统一处理；因此你无法在其中引用运行期才产生的变量。）

这句话拆开有 4 个后果：
1. **位置无关、时机统一**：UDV 放在线程组下还是测试计划下，都在测试开始前处理，所以它"长得像配置元件"，实际身份是**一次性初始值**。官方补充：*"UDVs are processed in the order they appear in the Plan, from top to bottom."*——同名变量看的是**在计划里出现的先后（从上到下）**，不是嵌套层级。
2. **不能用运行期值**：`${token}`（后置处理器提取的）在 UDV 里引用不到——那时 token 还没产生。要在运行期写变量，只能用前置处理器 / 后置处理器 / CSV 这类运行期元件。
3. **不能用"每次结果都不同"的函数**：官方原文：*"UDVs should not be used with functions that generate different results each time they are called. Only the result of the first function call will be saved in the variable."* ——`${__Random(1,100)}` 写进 UDV 只会拿到**第一次**的随机值，之后所有线程、所有迭代都用同一个数，根本不"随机"。可以安全同用的是 `${__P(host,localhost)}` 这种**取值稳定**的函数（读属性、给默认值）。
4. **每个线程拿到的是"副本"**：官方原文：*"Once the Test Plan and all UDVs have been processed, the resulting set of variables is copied to each thread to provide the initial set of variables."* ——"**copied to each thread**"这半句，就是"变量是线程私有的"官方依据（知识点4）。

【必须掌握】

| UDV 关键点 | 内容 | 实践含义 |
|---|---|---|
| 元件归属 | 配置元件（Config Element） | 添加路径：线程组 / 测试计划 → 添加 → 配置元件 → User Defined Variables |
| 求值时机 | 测试计划开始时**一次性**处理（官方：no matter where they are） | 不要在 UDV 里引用运行期变量；不要用它做"每轮换值" |
| 与函数同用 | 只保存**第一次函数调用的结果**（官方原文） | `${__Random}`、`${__time()}` 之类不要写进 UDV |
| 可以安全同用 | `${__P(属性名,默认值)}` | 给"外部可覆盖的默认值"，命令行 `-J` 可覆盖 |
| 同名覆盖 | 按在计划中出现的顺序，从上到下处理 | 运行期元件（User Parameters / 提取器）写同名变量会**替换** UDV 的初值 |
| 对后续请求的可见性 | 初始变量集会**复制给每个线程** | 同线程内后续请求直接写 `${变量名}` 即可引用 |
| 面板字段 | Name（变量名）/ Value（值）/ Description（注释）+ Add / Delete / Details | Value 里可以引用其他变量和**取值稳定**的函数 |

【企业场景】
你压一个只在内网可达的测试环境，脚本既要能在同事本机跑（`localhost`），又要在 CI 上跑（内网域名）。企业做法：UDV 里写一行 `host` = `${__P(host,localhost)}`——默认 `localhost`，谁要覆盖就在命令行加 `-Jhost=pre.example.com`（CI 把域名当参数传进去）。**这就是"UDV + 属性"的经典组合：UDV 给默认值、属性给外部开关。** 反面例子：把 `${__Random(1000,9999)}` 直接写进 UDV 当"随机用户 ID"，结果 100 个线程用同一个 ID 下单，数据撞在一起、压测结论全错——这类 bug 极其隐蔽，因为脚本不报错。

【面试考察】
面试官："JMeter 的用户定义变量（UDV）是什么时候生效的？能不能在里面用函数？"

参考回答框架：
1. 归属与时机：配置元件；测试计划里**所有** UDV 都在测试开始时统一处理（与摆放位置无关），处理结果**复制给每个线程**作为初始变量；
2. 因此**不能**引用运行期产生的变量（如后置处理器提取的 token）；
3. 函数限制：只保存**第一次调用**的结果 → `__Random` / `__time` 这类不能用；`__P()` 这类取值稳定的可以；
4. 要做"每轮换值"的参数化，应改用 CSV Data Set Config / Random Variable 元件 / User Parameters（前置处理器），而不是 UDV。

【易错点】

| 常见错误 | 正确理解 |
|---|---|
| 在 UDV 里引用后置处理器提取的变量 | UDV 在测试开始就处理完了，那时提取器还没跑过，引用不到（官方原文：cannot reference variables defined as part of a test run） |
| 在 UDV 里用 `${__Random(...)}` / `${__time(...)}` | 只保存第一次结果，之后所有线程 / 迭代都用同一个值（官方原文）；随机化要用 Random Variable 元件或 CSV |
| 认为"UDV 放在线程组下就只对本线程组生效" | 官方：所有 UDV 无论在哪都在测试开始时处理（内容上是全局初始值，值再**复制**给每个线程） |
| 用 UDV 做"每轮换一行测试数据" | 那是 CSV Data Set Config 的职责（按迭代换行）；UDV 只给一个固定值 |
| 同名变量"谁生效"搞不清 | 规则是**从上到下处理**，后处理的覆盖先处理的；运行期元件写同名变量会覆盖 UDV 初值 |

【我的理解】引导题（用自己的话回答）：
1. 用"求值时机"这一个维度解释：为什么 UDV 不能当参数化用，而 CSV Data Set Config 可以？
2. 如果一个同名 UDV 分别写在"测试计划"下和"线程组"下，最终生效的是哪一个？你自己的判断依据是哪条官方规则？

### 知识点3：引用语法 `${变量名}`——引用不是"填空"

【课程原话/定义】
设置 HTTP 请求以及引用先前创建的变量，通过关键字 `${key}` 来引用已存在的变量；创建结果树，查看结果验证引用是否成功。

【为什么？】
引用写法看着只有两个符号，但官方文档里关于 `${}` 的几条规则必须知道，否则排错时会怀疑人生：
1. *"If an undefined function or variable is referenced, JMeter does not report/log an error - the reference is returned unchanged."* ——**引用不存在的变量不报错、不打日志**，原样把 `${foo}` 发出去。所以"请求发出去了、HTTP 200、业务数据全错"的典型原因就是变量名写错了。这也是"必须配 Debug Sampler 验证"的根本理由（知识点5）。
2. *"Variables, functions (and properties) are all case-sensitive."* ——三者都**大小写敏感**，`${Token}` 与 `${token}` 是两个不同的变量。
3. *"JMeter trims spaces from variable names before use."* ——变量名会被去首尾空格，`${ token }` 与 `${token}` 等价（但别依赖这个习惯，容易误读）。
4. 嵌套引用不支持：*"variables cannot currently be nested; i.e. `${Var${N}}` does not work. The `__V` (variable) function can be used to do this: `${__V(Var${N})}`"* ——需要"变量名本身也是变量"时，用 `__V`。

【必须掌握】

| 语法 | 作用 | 例子 |
|---|---|---|
| `${变量名}` | 引用变量 | `${host}`、`${token}` |
| `${__V(变量名表达式)}` | **嵌套**引用（变量名里还有变量） | `${__V(A${N})}`，N=1 时取 A1 的值 |
| `${__P(属性名,默认值)}` | 引用**属性**（跨线程共享的那一类） | `${__P(host,localhost)}` |
| `${__threadNum}` | 当前线程编号 | 给每个虚拟用户造唯一数据 |
| `${__counter(FALSE)}` | 计数器（FALSE＝各线程独立计数） | 造唯一序号 |
| `${__Random(min,max)}` | 随机数（**每次调用**都重新算） | 但不能写进 UDV（知识点2） |
| `${__evalVar(var)}` | 把变量里的内容当表达式再解析一遍 | 从文件读模板串时常用 |
| `${__setProperty(名,值)}` | **写**属性（跨线程共享的唯一正道） | 与 `${__P()}` 配对使用 |

【企业场景】
你压一条下单链路，服务端要求每个虚拟用户用**不同**的用户 ID，否则会把同一账号下成限购错误。做法：请求参数写 `userId=user_${__threadNum}`、订单号写 `order_${__threadNum}_${__counter(FALSE)}`——**不依赖任何外部文件就能造出并发安全的数据**（线程号唯一 + 每线程独立计数）。另一类高频场景是"变量名由变量决定"：你从 CSV 读到列名，想动态拼出 `${data_${colName}}`——直接写不支持，必须写 `${__V(data_${colName})}`（曾经有人因此排查一下午，因为脚本既不报错、值也一直是字面量）。

【面试考察】
面试官："JMeter 里引用不存在的变量会怎样？变量名里想再套一个变量怎么办？"

参考回答框架：
1. 不存在的变量 / 函数：**不报错、不打日志**，原样返回 `${foo}`——所以脚本"看起来正常"但数据错，必须用 Debug Sampler / 断言暴露；
2. 三者（变量、函数、属性）都**大小写敏感**，变量名会被去首尾空格；
3. 嵌套引用**不支持** `${A${N}}`，要用 `${__V(A${N})}`；`__evalVar` 用于把变量内容当表达式再解析一遍；
4. 变量是线程私有的，跨线程取值要用 `${__P(名,默认值)}`（属性）。

【易错点】

| 常见错误 | 正确理解 |
|---|---|
| 以为引用不到变量会报错 | 不报错、原样输出 `${foo}`；典型症状是"HTTP 200、业务全错"（官方原文） |
| `${token}` 写成 `${Token}` 或 `${tokens}` | 变量名大小写敏感，拼错同样静默通过；Debug Sampler 里一比对就现形 |
| 在 JSON 请求体里写 `${变量}` 却没加引号 | 值为字符串时要自己补引号：`{"user":"${user}"}`，否则可能拼出不合法 JSON |
| 需要"变量名里套变量"时直接写 `${A${N}}` | 不支持嵌套；用 `${__V(A${N})}`（官方原文） |
| 把 `${__Random}` 写在 UDV / 测试计划变量里当"随机参数" | 只会保存第一次结果；随机化要靠 Random Variable 元件或 CSV（知识点2） |
| 用 `${__P(名)}` 去读一个普通变量 | `${__P()}` 读的是**属性**；变量直接用 `${名}`（知识点4） |

【我的理解】引导题（用自己的话回答）：
1. 为什么"引用不存在的变量不报错"这一条，反而**加强**了"必须用 Debug Sampler 验证"的必要性？
2. 要给每个线程造唯一订单号，你会怎么组合函数？为什么选 `${__threadNum}` + `${__counter(FALSE)}` 而不是 `${__Random}`？

### 知识点4：变量的作用域——线程私有 vs 属性全 JVM 共享（"跨线程传参"的真相）

【课程原话/定义】
课程原文："跨线程传参：JMeter 中的变量可以跨线程传参，这使得在多线程测试场景中，不同线程之间可以共享和使用相同的变量值。"

⚠️ 这一条**写错了**。（核对来源：JMeter 官方 `usermanual/functions.html`、`usermanual/component_reference.html`）

【为什么？】
官方原文写得很直白：*"Properties are not the same as variables. Variables are local to a thread; properties are common to all threads, and need to be referenced using the `__P` or `__property` function."*（属性 ≠ 变量。**变量是线程私有的**；属性是所有线程共有的，且必须用 `__P` / `__property` 引用。）

再结合 UDV 页的原文：*"the resulting set of variables is copied to each thread to provide the initial set of variables."*——连"全局定义"的 UDV 也是**复制一份给每个线程**。于是有两条推论：
1. 100 个线程可以有 100 个不同的 `${token}`（各自响应里提取的），互不干扰 → **这正是"100 个线程 = 100 个独立并发用户"能成立的物理基础**；
2. 同时意味着：**线程 A 提取到的值，线程 B 看不到。**

那"跨线程传值"到底怎么做？只有**属性（Properties）**这一条正道：

| 目的 | 手段 | 说明 |
|---|---|---|
| 写一个全测试共享的值 | `${__setProperty(名,值)}`，或 BeanShell / JSR223 里 `props.put("名",值)` | 属性存在**同一个 JVM** 里 |
| 读这个值 | `${__P(名)}`（函数面板里也有 `__property`） | 任意线程组、任意线程都能读 |
| 典型用途 | setUp 线程组登录取 token → 写成属性 → 主线程组所有线程读 `${__P(token)}` | 一次登录、全员复用（也常作为"登录只跑 1 次"的节省手法） |

三条边界（【扩展知识】）：
1. **属性是 JVM 级的、但不等于"每次运行都重置"**：本地 GUI 连续运行同一个脚本时，可能读到**上一次运行留下的旧值**（典型坑：第二次运行时 token 已过期）→ 稳妥做法是在 setUp 里先 `${__setProperty(token,)}` 清空，或用断言把过期暴露出来。
2. **分布式压测里属性不跨机器自动同步**：远程机之间、master 与 slave 之间的属性可见性有限；跨节点共享要用 `-G` 传全局属性（`jmeter -G名=值`），不要假设"我写的属性远端的线程也能看到"。
3. **`User Parameters`（前置处理器）不是跨线程工具**：它是"同一线程内按迭代换值"，和属性完全是两件事——名字相近，最容易被混为一谈。

【必须掌握】

| 对比项 | 变量（Variables） | 属性（Properties） |
|---|---|---|
| 作用域 | **线程私有**（每个线程一份） | 全 JVM 共享（同一次运行内所有线程组） |
| 谁写 | UDV / 提取器 / CSV / 函数 | `${__setProperty()}`、`props.put()`、命令行 `-J` / `-G`、`user.properties` 文件 |
| 谁读 | `${变量名}` | `${__P(名[,默认值])}` |
| 跨线程能用吗 | **不能** | 能 |
| 典型用途 | 关联取参（每个用户自己的 token / orderId） | 全局配置（环境域名、端口）；setUp 里取一次、全员复用 |
| 大小写 | 敏感 | 敏感 |

【企业场景】
你压一个需要登录的业务，登录接口有防爆破限制（同一账号频繁登录会被锁）。如果 500 个线程各自登录一次，账号立刻被封、压测直接失败。企业做法：把登录放进 **setUp 线程组**（1 个线程 1 次循环），登录成功后用 `${__setProperty(token,${token})}` 把 token 写成属性，主线程组里所有请求头写 `token: ${__P(token)}`——**一次登录、全员复用**，既绕开防爆破，又省掉 500 次登录的开销。同理，要跨线程组共享"环境域名 / 商户号"，也走属性：`${__setProperty(host,pre.example.com)}` + `${__P(host)}`。

【面试考察】
面试官："JMeter 的变量和属性有什么区别？多线程之间怎么传值？setUp 线程组里取的 token，主线程组能用吗？"

参考回答框架：
1. 官方定义：**变量线程私有；属性全线程共享，且必须用 `${__P()}` 引用**；
2. 所以"变量可以跨线程传参"这个说法不成立——课程原文在这点上写错了；
3. 跨线程 / 跨线程组的正道是**属性**：`${__setProperty(名,值)}` 写 → `${__P(名)}` 读；setUp 登录一次写属性，主线程组全员复用；
4. 加分边界：属性是 JVM 级、有"读到上次运行旧值"的风险；分布式压测下属性跨机器不会自动同步，要用 `-G` 传。

【易错点】

| 常见错误 | 正确理解 |
|---|---|
| 认为"变量可以跨线程传参"（照抄课程原文） | 变量**线程私有**（官方原文）；跨线程共享要用**属性** `__setProperty` / `${__P()}` |
| 用 `${token}` 去读 setUp 线程组写的变量 | 读不到（线程私有），会原样输出 `${token}` 且不报错；要写 `${__P(token)}` |
| 用 `${__P(名)}` 去读一个普通变量 | 属性表里没有这个名字；变量直接用 `${名}` |
| 把属性当"每次运行都会重置的全局常量" | 属性在 JVM 内持续存在，重复运行可能读到**上一次**的旧值；需显式清空或校验 |
| 以为 User Parameters 可以跨线程 | 它只在本线程按迭代换值；跨线程仍要靠属性 |
| 分布式压测里假设属性自动同步 | 属性以 JVM 为单位；跨机器用 `-G` 传全局属性，不要假设自动可见 |

【我的理解】引导题（用自己的话回答）：
1. 既然变量是线程私有的，为什么"500 个虚拟用户各自拿到自己的 token"反而是**好事**？（提示：从"用户独立性"和"问题能否复现"两个角度想）
2. 请把"setUp 只登录一次、主线程组全员复用 token"拆成四步说出来：谁来写 → 写到哪 → 谁来读 → 用什么语法读。

### 知识点5：给变量赋值的四种方式对比 + 实操验证

【课程原话/定义】
课程实操链路（原文）：建线程组 → 建 User Defined Variables 并填键值对 → 建 HTTP 请求并用 `${key}` 引用 → 建结果树 → 查看结果，验证引用成功。

【为什么？】
"变量"这一个概念，在 JMeter 里有**四种赋值入口**。它们语法相同、面板相似，但**求值时机完全不同**——这正是实操与面试里最容易混的地方。把下面这张表记牢，参数化选型就不用背了：判断口诀是 **"这个值要不要变？什么时候变？"**

| 赋值方式 | 元件 / 语法 | 求值时机 | 适合什么数据 |
|---|---|---|---|
| 用户定义 | User Defined Variables / 测试计划的"用户定义的变量" | 测试计划开始**一次性** | 环境域名、端口、固定账号等**常量** |
| 数据驱动 | CSV Data Set Config（配置元件） | 每个**迭代**取下一行（Recycle / Stop 由选项决定） | 账号池、商品池等**每轮换值** |
| 运行时随机 / 自增 | Random Variable / Counter 元件、`${__Random}` / `${__counter}` / `${__threadNum}` | **每次调用** | 造唯一数据、随机数据 |
| 关联提取 | JSON / 正则 / XPath 提取器（后置处理器） | 每个取样器**响应之后** | 上一个请求的返回值（token / orderId） |

验证方式同样有两种，别混：
- **Debug Sampler**：把变量名和值打印进响应（JMeter Variables 一栏），确认"值**取到了没有**"。它本身**不是断言**，不会让脚本失败；
- **View Results Tree**：看 **Request** 面板里 `${变量}` 有没有被替换成真实值，确认"引用**生效了没有**"；
- 顺序永远是：**先用 1 线程 1 次循环把变量调通，再放大并发。**

【必须掌握】

| 验证手段 | 看什么 | 什么时候用 |
|---|---|---|
| Debug Sampler | Response data 里的 **JMeter Variables** 列表（变量名 + 值） | 确认变量**有没有取到**、值对不对 |
| View Results Tree → Request | 请求 URL / 参数 / 请求头里的变量**是否被替换** | 确认引用**有没有生效**（`${token}` 是否原样发出） |
| 断言（JSON / 响应断言） | 业务是否真的成功 | 变量正确 ≠ 业务正确，压测必须配断言 |
| 正式压测前 | **删掉 Debug Sampler 与 View Results Tree** | 它们会把每个响应留在内存里，几轮就能把施压机压垮 |

【企业场景】
你交付一条"登录（setUp，1 次）→ 商品列表 → 商品详情 → 下单（500 线程 × 50 轮）"的脚本。交付前的自检顺序：① 用 1 线程 1 循环 + Debug Sampler，看 `token` / `sku_id` / `order_no` 三个变量的值是否合理；② 用 View Results Tree 看请求体里是不是真的替换成了值（曾有同事把 `${sku_id}` 写成 `${skuId}`，脚本不报错，结果压了 500 个 `NOT FOUND` 商品，整轮数据作废）；③ 给下单接口加 JSON 断言校验业务码；④ 删掉调试元件，再用 500 线程正式压。**这四步是企业里"脚本可以交付"的最低标准。**

【面试考察】
面试官："JMeter 里给变量赋值有哪几种方式？什么场景用哪种？"

参考回答框架：
1. 四类入口 + 求值时机：UDV（开始一次）→ CSV Data Set Config（每迭代）→ Random/Counter 元件与函数（每次调用）→ 后置处理器提取（每次响应后）；
2. 选型口诀："值变不变、什么时候变"；
3. 验证：Debug Sampler 看值、View Results Tree 看引用替换，两者配合才能区分"取值失败"和"引用失败"；
4. 交付纪律：小样本调通 → 加断言 → 删调试元件 → 正式压测。

【易错点】

| 常见错误 | 正确理解 |
|---|---|
| 用 UDV 做"每线程不同"的账号 | UDV 是固定初值；按迭代换行要用 CSV Data Set Config，按线程区分要用 `${__threadNum}` 拼接 |
| 只看 Debug Sampler 变量好看就认为脚本没问题 | 变量取到 ≠ 请求引用正确 ≠ 业务成功；三层都要看（值 → 引用 → 断言） |
| 变量引用失败时靠"HTTP 200"判断成功 | 引用失败不报错，参数会变成 `${xxx}` 或 `NOT FOUND`，HTTP 仍可能 200；必须靠断言 / 看请求体 |
| 正式压测时忘记移除 Debug Sampler / View Results Tree | 会累积响应数据占内存，施压机资源被吃掉 → TPS 结论失真（施压机自己成了瓶颈） |
| 变量名不成体系（`tmp1`、`a`、`data2`） | 企业脚本要一眼可读：`host` / `token` / `sku_id` / `login_user`，排错时才找得到 |

【我的理解】引导题（用自己的话回答）：
1. 用"值变不变、什么时候变"这句口诀，给下面四个值各选一种赋值方式：环境域名 / 登录后拿到的 token / 每轮换一条的用户账号 / 每次请求都要唯一的订单号。
2. 为什么"变量取到了"和"引用生效了"要用两个不同的元件来验证？请从"故障分层"的角度说明。
