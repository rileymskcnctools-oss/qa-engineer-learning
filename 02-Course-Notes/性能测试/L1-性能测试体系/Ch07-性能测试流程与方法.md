## 一、性能测试流程

### 知识点 1：性能测试流程的十二个步骤

【课程原话/定义】
性能测试流程是指在进行性能测试时所遵循的一系列步骤和阶段，以确保对系统的全面测试和评估。**具体步骤可能会因组织、项目和测试需求而有所不同。**
1. **分析现状**：对应用程序或系统进行详细分析，了解当前性能状况、发现性能瓶颈，并确定性能测试的目标
2. **获取当前性能指标**：使用性能剖析工具或监控工具收集应用程序的性能指标，如响应时间、吞吐量、错误率等。这些指标将成为后续测试和优化的**基准**
3. **定义用户场景**：根据实际使用情况，定义一系列典型的用户场景或负载模型，模拟实际用户的行为和请求
4. **定义性能验收标准**：根据用户场景和业务需求，定义一系列性能验收标准，如响应时间的上限、吞吐量的目标等。这些标准将用于**评估性能是否符合预期**
5. **编写测试计划/脚本**：根据用户场景和验收标准编写性能测试计划，包括测试目标、测试场景、测试数据准备等；同时根据场景编写测试脚本，用于自动化执行
6. **准备压力环境**：搭建适合压力测试的环境，包括硬件设备、网络配置、测试环境部署等。确保测试环境的**稳定性、一致性和负载能力**
7. **执行压测**：按照测试计划和脚本，使用性能测试工具模拟并生成负载，对应用程序进行压力测试；可以**逐步增加负载**，直至达到预定的性能验收标准
8. **监控**：在压测过程中使用性能监控工具对性能指标进行实时监测和记录，涵盖各个层面的指标，如服务器资源利用率、请求响应时间、错误率等
9. **收集和分析**：根据压测期间的监控数据收集和分析结果，对性能问题和瓶颈进行**归因分析**，找出瓶颈所在的原因
10. **测试报告**：根据分析结果编写性能测试报告，总结结果、得出结论，并提供可视化图表和建议；报告应包括测试指标、测试环境、测试结果、发现的问题等
11. **改进建议**：根据报告提供的性能问题和瓶颈，给出具体的改进建议（代码优化、配置调整、资源扩容等）
12. **持续测试**：性能测试是一个**持续的过程**，在系统迭代升级或新增功能时需要定期进行，以确保性能稳定性和可扩展性

【为什么？】
为什么这个流程值得逐步背下来？因为它同时是**工作清单**和**面试答题骨架**：
- 作为工作清单：漏掉"获取当前性能指标（基准）"，你就无法回答"优化有没有效果"；漏掉"定义验收标准"，报告就无法判断达标与否；漏掉"持续测试"，性能回归就会在某个版本爆发
- 作为面试骨架：面试官问"你怎么开展性能测试"，答案就是这条链，而且能顺着每一步展开细节（业务量怎么折算、环境怎么搭、指标怎么定、瓶颈怎么定位）

流程里还有一条隐藏主线：**每一步都在为"结论可信"服务**——基准让对比有效，场景让数据贴近真实，验收标准让结论可判定，监控与归因让原因可解释，报告与建议让结果可交付，持续测试让性能不退化。**流程的价值不是走完步骤，而是让结论站得住。**

【必须掌握】

| 阶段        | 核心动作           | 关键交付物      | 常见坑              |
| --------- | -------------- | ---------- | ---------------- |
| 1 分析现状    | 了解现状、发现瓶颈、确定目标 | 测试目标       | 目标含糊（"压一下看看"）    |
| 2 获取当前指标  | 用剖析/监控工具采基线    | 性能基线数据     | 无基线 → 无法对比优化效果   |
| 3 定义用户场景  | 提炼典型场景与负载模型    | 场景清单       | 场景不贴业务（只压单接口）    |
| 4 定义验收标准  | 定 RT 上限、吞吐目标等  | SLA / 验收标准 | 标准拍脑袋、无业务依据      |
| 5 编写计划/脚本 | 计划 + 脚本 + 数据准备 | 压测计划、脚本    | 脚本无参数化/无断言       |
| 6 准备压力环境  | 硬件、网络、部署       | 稳定的压测环境    | 环境与线上差异过大（无参考价值） |
| 7 执行压测    | 逐步增加负载至验收标准    | 压测数据       | 一次性加到顶，拿不到拐点     |
| 8 监控      | 实时监测各层面指标      | 监控数据       | 监控未提前验证          |
| 9 收集和分析   | 归因分析找瓶颈原因      | 瓶颈结论       | 只有数据没有归因         |
| 10 测试报告   | 结论 + 图表 + 建议   | 性能测试报告     | 只有截图没有结论         |
| 11 改进建议   | 代码/配置/扩容建议     | 优化项清单      | 建议不可执行           |
| 12 持续测试   | 迭代与新功能后定期重压    | 性能回归机制     | 压一次就结束           |

【企业场景】
你负责一个版本的性能验收，按流程走下来的实际动作是：从生产日志拿基线（步骤 2）→ 与产品确认"下单 + 支付"两个主场景（步骤 3）→ 定"下单 TP99 ≤ 800ms、错误率 < 0.1%"（步骤 4）→ 写 JMeter 脚本并准备 5000 条测试账号（步骤 5）→ 搭同比 1/2 的压测环境（步骤 6）→ 阶梯加压到 3000 QPS（步骤 7）→ 全程开 Grafana + nmon（步骤 8）→ 归因到"订单库连接池饱和"（步骤 9）→ 出报告并给扩容/调参建议（步骤 10-11）→ 把脚本接入 CI，每版本自动跑一轮（步骤 12）。**这条链在面试里讲一遍，胜过背十个定义。**

【面试考察】
面试官："如何开展性能测试？性能测试的流程是什么？"

参考回答框架：
1. 用"四段式"组织十二步：**准备（1-6）→ 执行（7-8）→ 分析（9）→ 交付与迭代（10-12）**
2. 每一步给一句关键点：现状与基线 → 场景 → 验收标准 → 计划脚本 → 环境 → 加压 → 监控 → 归因 → 报告 → 建议 → 持续
3. 强调两个容易漏的：先取**基线**（否则无法对比）、定义**验收标准**（否则无法判定达标）
4. 加分：说明"持续测试"意味着性能测试要进 CI，性能是会回归的

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 跳过"获取当前性能指标"直接压 | 没有基线的压测无法判断优化效果，也无法证明劣化 |
| 没有验收标准就开始压 | 不知道"多少算达标"，报告无法下结论 |
| 一次把负载加到目标值 | 拿不到拐点与三区域，应阶梯加压，观察曲线变化 |
| 压测环境与线上差异巨大 | 环境要有参考价值（同比 1/2、1/4），否则结论不可迁移 |
| 只做一次压测 | 性能测试是持续过程，迭代/新功能后必须重压 |
| 报告只贴数据不做归因 | 报告要回答"瓶颈在哪、为什么、怎么改" |

【我的理解】
> （用自己的话回答：为什么流程里第 2 步"获取当前性能指标"和第 4 步"定义性能验收标准"经常被跳过，却最容易导致压测白做？如果只能保留流程中的三步，你保留哪三步？）
> 
> 我认为第 2 步和第 4 步特别容易被跳过，因为大家很容易直接上工具压测，却没有先搞清楚系统当前是什么水平，以及什么结果才算合格。没有基线，就无法判断性能到底提升还是退化；没有验收标准，就算测出 TPS、RT，也不知道结果是否达标。所以如果只能保留三步，我会保留**定义验收标准、建立性能基线、执行压测并结合监控分析**。因为这三步分别解决了‘目标是什么、现状是什么、实际结果怎么样’三个核心问题。

## 二、性能测试方法：并发模式与 RPS 模式

### 知识点 2：并发模式（虚拟用户模式）

【课程原话/定义】
**并发模式（虚拟用户模式）**：并发是指虚拟并发用户数，从业务角度，也可以理解为同时在线的用户数。如果需要从**客户端**的角度出发，摸底业务系统各节点能同时承载的在线用户数，可以使用该模式设置**目标并发**。

【为什么？】
并发模式的本质是"**模拟人**"：你设定的是"有多少个虚拟用户同时在操作"，工具负责让每个虚拟用户按脚本循环执行（并可以通过思考时间模拟真实用户的停顿）。它的适用场景是：
- 你要回答的问题形如"**这个系统能同时承载多少在线用户**"（客户端视角、容量摸底）
- 场景是**行为型**的：登录 → 浏览 → 加购 → 下单，每个虚拟用户走的是一段流程
- 你要做**能力验证**（给定硬件能撑多少并发）或**稳定性测试**（固定并发跑长时间）

对应的代价是：并发数与服务端的"每秒请求数"之间隔着平均 RT（并发数 = QPS × RT），所以**同样的并发数，在不同响应时间下产生的压力完全不一样**——这是并发模式在跨系统/跨版本对比时的天然弱点（版本变快后，同样并发会打出更高 QPS）。这也正是 RPS 模式存在的理由。

【必须掌握】

| 项目   | 内容                               |
| ---- | -------------------------------- |
| 视角   | 客户端（模拟用户）                        |
| 设定量  | 目标并发数（虚拟用户数 / 在线用户数）             |
| 适用问题 | "系统能同时承载多少在线用户"                  |
| 适合场景 | 业务流程型场景、容量摸底、能力验证、稳定性测试          |
| 天然弱点 | 并发 → 压力的换算受 RT 影响（版本变快，同样并发压力更大） |

【企业场景】
大促前你要回答业务方的问题："系统能支撑多少用户同时下单？" 这时用并发模式：设 500 / 1000 / 2000 三档并发，每档稳定跑 10 分钟，观察 RT 与 TPS，交付结论"最佳并发约 800（RT 稳定在 230ms）、超过 1500 后 RT 急剧上升"。**业务方能直接理解"多少用户"这个单位**——这是并发模式在沟通上的优势。

【面试考察】
面试官："压测时并发模式怎么用？什么时候用并发模式？"

参考回答框架：
1. 定义：并发模式设定虚拟并发用户数，模拟 N 个用户同时在操作
2. 视角与问题：客户端视角，回答"能承载多少在线用户"
3. 适用：行为型业务场景、容量摸底、能力验证、稳定性测试
4. 注意：并发必须从业务量折算（并发 = QPS × RT），且 RT 变化会让同样并产生不同压力
5. 沟通价值：结论以"用户数"表达，业务方易懂

【易错点】

| 常见错误          | 正确理解                                 |
| ------------- | ------------------------------------ |
| 把并发数当固定压力     | 同样的并发在不同 RT 下压力不同（并发 = QPS × RT）     |
| 用并发模式做跨版本压测对比 | 版本变快后同并发的 QPS 更高，对比不严谨，跨版本建议用 RPS 模式 |
| 设置并发后不加思考时间   | 无思考时间的"死循环请求"会远超真实用户压力强度             |

【我的理解】
> （用自己的话回答：为什么说并发模式"天生不适合跨版本对比"？如果业务方问"能扛多少用户"，你会怎么设计加压档位？）

### 知识点 3：RPS 模式（吞吐量模式）

【课程原话/定义】
**RPS 模式（吞吐量模式）**：RPS（Requests Per Second）是指每秒请求数。RPS 模式即"吞吐量模式"，通过**设置每秒发出的请求数**，从**服务端**的角度出发，直接衡量系统的吞吐能力，**免去并发到 RPS 的繁琐转化，一步到位**。

【为什么？】
RPS 模式的本质是"**模拟流量**"而非"模拟人"：你直接告诉工具"每秒固定发多少请求"，工具负责匀速发出去（不够就加线程，够了就等）。它解决的是并发模式的两个痛点：
1. **免折算**：不用再走"在线用户 → 活跃比例 → QPS → 并发"这条链，直接给定 QPS/RPS 目标
2. **可对比**：每次压测的"入水流量"恒定，优化前后、版本前后的结果**直接可比**（这才是性能回归的正确姿势）

代价是它脱离了"用户数"的直观性，需要你先能算出业务需要的 QPS（这恰好是 [[Ch02-性能测试概念与指标体系|Ch02]] 里业务量折算的用武之地），并且工具端要能支撑"按目标速率发压"（需要足够的线程与稳定的发压能力）。

【必须掌握】

| 项目   | 内容                          |
| ---- | --------------------------- |
| 视角   | 服务端（衡量吞吐能力）                 |
| 设定量  | 每秒请求数（RPS / QPS）            |
| 核心优势 | 免去并发 → RPS 的繁琐转化；流量恒定，结果可对比 |
| 适合场景 | 性能基准测试、优化前后对比、性能回归、容量验证     |
| 前提条件 | 能算出业务目标 QPS（来自业务量折算）        |

| 对比维度  | 并发模式（虚拟用户）            | RPS 模式（吞吐量）    |
| ----- | --------------------- | -------------- |
| 视角    | 客户端（模拟用户）             | 服务端（模拟流量）      |
| 设定量   | 并发用户数                 | 每秒请求数          |
| 回答的问题 | 能承载多少在线用户             | 能承载多少吞吐        |
| 压力稳定性 | 随 RT 变化而变（RT 涨则实际压力降） | 恒定（流量固定）       |
| 跨版本对比 | 不严谨                   | 严谨、可对比         |
| 典型用途  | 容量摸底、业务场景模拟、稳定性测试     | 基准测试、优化对比、性能回归 |

【企业场景】
你把压测脚本接进 CI 做性能回归：每版本用 RPS 模式固定打 1500 QPS 跑 10 分钟，比较 TP99 与错误率。这样"这个版本比上个版本慢了 15%"才是可靠的结论——如果换成并发模式，新版本代码变快后同并发会打出更高 QPS，反而会让报告显示"TPS 变高但 RT 变差"，结论完全失去可比性。

【面试考察】
面试官："压测时你设定的是并发数还是 RPS？为什么？"

参考回答框架：
1. 两种模式都说清：并发模式=模拟用户（客户端视角），RPS 模式=模拟流量（服务端视角）
2. 选择依据：要"承载多少用户"用并发模式；要"吞吐能力/可比性"用 RPS 模式
3. 关键差异：并发模式的实际压力随 RT 变化，RPS 模式压力恒定
4. 实践组合：先用并发模式摸容量与拐点，再用 RPS 模式做基准对比与性能回归
5. 加分：指出性能回归必须用 RPS 模式，否则版本间数据不可比

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 认为 RPS 模式不需要并发设置 | 工具仍需线程承载（按目标 RPS 与 RT 计算所需线程数） |
| 用 RPS 模式做业务场景模拟 | 业务场景是"用户行为"，用并发模式更贴切 |
| 设定的 RPS 超出压测机能力 | 必须先验证起压机能否稳定输出目标 RPS，否则数据失真 |
| 忽视两种模式结论口径不同 | 报告里必须写明本轮用的是哪种模式，避免结论被误读 |

【我的理解】
> （用自己的话回答：为什么"性能回归"必须用 RPS 模式？如果你要做"这个接口优化后提升了多少"的对比，你会怎么设计这轮压测？）
> 
> 性能回归的核心是比较优化前后的性能变化，所以我需要尽量保证两次测试的压力一致。并发模式下，RT 发生变化会影响实际请求速率，因此前后两次的实际压力可能不一样。RPS 模式可以把请求速率固定下来，所以更适合做性能回归。
> 
> 如果让我测试一个接口优化后提升了多少，我会先固定测试环境、测试数据和脚本，只改变接口代码，然后确定一个固定的 RPS，比如 100 RPS。先对优化前版本进行预热并建立基线，记录平均 RT、P95、错误率以及 CPU 等指标；然后上线优化后的版本，在完全相同的 100 RPS 下再次测试。最后对比两次的 RT、P95、错误率和资源消耗，用具体数据计算优化幅度，而不是只说‘感觉变快了’。”
> 
> **性能回归要的是“同样的压力，前后表现有什么变化”，所以要固定 RPS，控制变量。**
>

## 今日课程总结

| 模块 | 核心内容 | 面试权重 |
|------|----------|----------|
| 性能测试流程 | 12 步：分析现状 → 取基线 → 定义场景 → 验收标准 → 计划脚本 → 环境 → 执行 → 监控 → 分析 → 报告 → 建议 → 持续测试 | ★★★★★ |
| 流程的两个易漏点 | 必须先取**基线**、必须定义**验收标准** | ★★★★★ |
| 并发模式 | 客户端视角、设定虚拟并发用户数；答案单位是"用户"；压力随 RT 变化 | ★★★★★ |
| RPS 模式 | 服务端视角、设定每秒请求数；免折算、压力恒定、可比性好 | ★★★★★ |
| 模式选择 | 摸容量/模拟业务用并发模式；基准对比与性能回归用 RPS 模式 | ★★★★★ |
