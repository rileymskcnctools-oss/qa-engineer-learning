## 一、什么是性能测试场景设计

### 知识点 1：场景设计的定义与目标

【课程原话/定义】
性能测试场景设计是指**定义和创建用于评估系统性能的模拟场景**的过程。这些场景通常包括**模拟用户行为、负载模式和使用情况**，以便在实际环境下测量系统的性能表现。

性能测试场景设计的目标是**模拟真实世界中的使用情况**，以便评估系统在不同条件下的**性能、稳定性和可靠性**。

【为什么？】
为什么"设计场景"要单独作为一个主题？因为**场景决定结论的适用范围**：
- 压"单接口 1000 并发"和压"下单链路混合场景 1000 并发"，得到的瓶颈完全不同
- 压"短时高峰"和压"持续 24 小时"，暴露的问题类型完全不同（前者暴露容量、后者暴露泄漏）
- 场景里的**请求比例**（浏览:加购:下单）决定了哪一层会先饱和

换句话说：**压测结论只有配着场景描述才成立。** "系统能撑 3000 QPS"是无效结论，"在'浏览:加购:下单 = 20:5:1'的混合场景下，系统能撑 3000 QPS"才是可用的结论。这也是为什么课程把"常用方法（负载/压力/稳定性/并发/容量）"放在场景设计里讲——**每种方法就是一种场景模板**，选哪种方法，取决于你要回答的是哪个问题。

【必须掌握】

| 要素 | 含义 | 影响 |
|------|------|------|
| 用户行为 | 模拟真实用户的操作路径（登录/浏览/下单） | 决定请求的关联性与参数依赖 |
| 负载模式 | 加压方式（阶梯/恒定/峰值/持续） | 决定能否看到拐点与漂移 |
| 使用情况 | 请求比例、数据分布、时间分布 | 决定哪个节点先饱和 |
| 目标问题 | 能力验证 / 容量规划 / 风险发现 | 决定选哪种测试方法 |

【企业场景】
你为"双十一大促"设计场景时，不是写"压 5000 并发"，而是先拆场景清单：① 日常基线（浏览为主，作为对照）；② 大促峰值混合场景（浏览:加购:下单 = 20:5:1，阶梯加压到预估峰值的 1.2 倍）；③ 秒杀瞬时冲击（单点接口，瞬时高并发）；④ 稳定性场景（按峰值 70% 的负载持续 8 小时）。**四类场景回答四个不同问题**：能不能扛、瓶颈在哪、能不能扛瞬时、长时间会不会崩。

【面试考察】
面试官："性能测试的场景怎么设计？"

参考回答框架：
1. 从业务出发：先梳理用户行为路径与请求比例（来自日志与业务数据）
2. 定负载模式：阶梯加压（找拐点）、恒定负载（看稳定）、瞬时冲击（看峰值）、长时持续（看漂移）
3. 定场景清单：基线场景 + 峰值场景 + 专项场景（秒杀/大文件/报表）+ 稳定性场景
4. 说明每个场景回答什么问题，以及该场景的验收标准
5. 加分：强调结论必须绑定场景描述，否则不可用

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 只压单接口，不压业务链路 | 单接口达标不代表链路达标（依赖、锁、连接池在链路层面才暴露） |
| 场景里不带请求比例 | 比例错了瓶颈组合就错了，结论无法迁移线上 |
| 只设计一个场景 | 不同问题需要不同场景（容量/峰值/稳定性） |
| 场景不写验收标准 | 无法判定该场景是否通过 |

【我的理解】
> （用自己的话回答：为什么"系统能撑 3000 QPS"是一个不完整的结论？如果只允许你设计一个场景，你会怎么设计，并说明它回答什么问题。）

## 二、性能测试的常用方法（五种场景模板）

### 知识点 2：负载测试 / 压力测试 / 稳定性测试 / 并发测试 / 容量测试

【课程原话/定义】
- **负载测试**：通过模拟用户实际使用系统的场景，对系统的性能进行测试。可以模拟并发用户数、访问数量和请求频率等实际使用情况，以评估系统在不同负载下的性能表现。其中的关键是**确保负载测试的设置与实际使用情况相匹配**
- **压力测试**：通过**加大系统资源负载，超过系统设计能力的限制**来检测系统的稳定性和弹性。通过应用程序的高负载和高并发条件，压力测试可以帮助团队了解系统在负载超出预期水平时的表现，并识别系统的**瓶颈和潜在问题**
- **稳定性测试**（极限测试）：用来评估系统或应用程序在**持续负载条件下的稳定性和可靠性**的测试方法。主要关注系统在长时间运行、持续负载下的性能表现，以确定系统是否能够在真实运行环境下保持稳定，并能够长时间持续地工作
- **并发测试**：通过**模拟多个用户同时访问系统**，以测试系统在同时处理多个请求时的性能。主要用于评估系统的并发处理能力和资源利用率，以及检测并发访问引起的潜在问题，如**死锁、竞争条件**等
- **容量测试**：评估系统的**容量和资源利用率**的测试。用于确定系统在预定条件下对资源的使用情况，以及在给定的负载情况下，系统能够处理的并发用户数、事务量等。目的是确定系统的**扩展能力和容错能力**，以支持未来的增长需求

【为什么？】
为什么要区分这五种方法而不是笼统说"压测"？因为它们**回答的问题不同、能暴露的缺陷类型不同**：

| 方法 | 回答的问题 | 典型暴露的缺陷 |
|------|-----------|----------------|
| 负载测试 | 在预期负载下表现如何？ | 性能不达标、资源配比不合理 |
| 压力测试 | 超出设计能力后会怎样？ | 雪崩点、错误处理缺失、恢复能力差 |
| 稳定性测试 | 长时间运行会不会退化？ | 内存/连接泄漏、日志写满磁盘、缓存膨胀 |
| 并发测试 | 并发访问会不会出问题？ | 死锁、竞争条件、数据不一致 |
| 容量测试 | 能撑多少？要多少机器？ | 容量边界不明、扩容无依据 |

一个很实用的判断法：**"要发现什么问题"决定"用哪种方法"**。只想证明"能上线"用负载测试；要"找边界"用压力测试；要"防大促当天跑着跑着崩"用稳定性测试；要"查并发 bug"用并发测试；要"给采购和扩容提供数据"用容量测试。

【必须掌握】

| 方法 | 核心动作 | 关键点 | 关键指标 |
|------|----------|--------|----------|
| 负载测试 | 模拟真实使用负载（并发数/访问量/请求频率） | **设置必须与实际使用情况匹配** | RT、TPS、资源利用率 |
| 压力测试 | 加大负载直到超过设计能力 | 找瓶颈与雪崩点，观察恢复 | 拐点位置、错误率、恢复时间 |
| 稳定性测试 | 持续负载长时间运行 | 极限测试；关注指标漂移 | 内存/连接趋势、GC、错误率 |
| 并发测试 | 多用户同时访问同一资源 | 关注死锁与竞争条件 | 死锁数量、数据一致性、错误率 |
| 容量测试 | 测定容量与资源利用 | 为扩容与规划提供依据 | 可支撑并发/事务量、资源水位 |

【企业场景】
大促备战的标准组合是："先容量测试摸清边界（能撑多少）→ 再压力测试确认超载行为与恢复（会不会雪崩、多久恢复）→ 然后稳定性测试跑 8~24 小时确认不退化（有没有泄漏）→ 最后用负载测试按真实比例做验收（达标与否）"。**这四步的顺序不是随意的：先摸边界，再验极限，再验长时间，最后按真实负载验收。**

【面试考察】
面试官："负载测试和压力测试有什么区别？稳定性测试怎么做？"

参考回答框架：
1. 负载测试：在预期负载下验证表现，负载设置要与实际使用匹配
2. 压力测试：主动超出设计能力，找瓶颈、雪崩点与恢复能力
3. 稳定性测试：持续负载长时间运行（如 8/24 小时），看指标是否漂移（内存、连接、GC）
4. 并发测试：验证并发访问的正确性（死锁、竞争条件、数据一致）
5. 容量测试：测定容量边界与资源利用率，为扩容与规划提供依据
6. 加分：说明"用什么方法取决于要回答什么问题"，并给出大促的测试组合顺序

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 把负载测试和压力测试当成一回事 | 负载测试在能力范围内，压力测试故意超出能力 |
| 稳定性测试用低负载代替 | 稳定性测试要用接近峰值的持续负载，低负载测不出泄漏 |
| 认为压力测试就是"把系统压崩" | 目的是观察超载行为与恢复能力，压崩后要能恢复并记录过程 |
| 忽略并发测试 | 死锁、竞争条件只在并发下暴露，功能测试永远测不出 |
| 容量测试只测一次 | 数据量/代码/依赖变化后容量会变，需定期重测 |

【我的理解】
> （用自己的话回答：为什么稳定性测试不能用低负载代替？如果你要为一个秒杀活动设计测试组合，你会按什么顺序上用这五种方法，各自要拿到什么数据？）

## 三、方法 × 场景对照：不同用途下的场景选择

### 知识点 3：三类用途与对应的方法、特点

【课程原话/定义】

| 用途 | 场景 | 特点 | 常用方法 |
|------|------|------|----------|
| **能力验证** | 给定软硬件条件下，系统预期表现 | 指定 AVG Time 要求，单系统能否撑展开指定量级压力，例如 5000 QPS；① 通常指单机 ② 指定硬件环境 ③ 明确并发和性能指标 | 负载测试 / 压力测试 / 稳定性测试 |
| **容量规划** | 为满足指定需求，需要多少机器，如何部署 | 指定用户量级，例如 50w UV，需要多少台机器；① 通常用于活动、新用户上线部署 ② 不断探测得到系统承载能力 | 负载测试 / 压力测试 / 部署测试 |
| **问题追查风险发现** | 在已有系统上通过一定时间压力，查看资源使用，内存泄漏情况 | 在长时间 24 小时、高 QPS 场景下验证 Full GC < 1s，无内存泄漏；① 长时间发压 ② 关注性能指标 ③ 多次优化重试 | 负载测试 / 压力测试 |

【为什么？】
为什么按"用途"而不是按"工具/方法"来组织测试？因为**用途决定了整个测试的设计与交付物**：
- **能力验证**：输入是"硬件规格 + AVG Time 要求 + 目标量级"，输出是"达标/不达标"的判定 → 通常针对单机，环境要求固定、指标要求明确（这类测试最"干净"，也最常见于发版验收）
- **容量规划**：输入是"用户量级（如 50w UV）"，输出是"需要多少台机器、怎么部署" → 重点是**不断探测**承载能力，并把结果换算成机器数与部署拓扑
- **问题追查 / 风险发现**：输入是"已有系统 + 长时间压力"，输出是"泄漏/劣化/隐患清单" → 特征是长时间发压、关注指标漂移、往往需要**多次优化重试**（这是一种"测试 → 优化 → 再测试"的迭代模式）

一句话记忆：**能力验证回答"行不行"，容量规划回答"要多少"，问题追查回答"会不会慢慢坏"。**

【必须掌握】

| 用途 | 输入 | 输出 | 方法 | 实操要点 |
|------|------|------|------|----------|
| 能力验证 | 软硬件规格 + 指标要求（AVG Time）+ 目标量级（如 5000 QPS） | 达标判定 | 负载 / 压力 / 稳定性测试 | 通常单机、环境固定、指标明确 |
| 容量规划 | 用户量级（如 50w UV）+ 部署条件 | 机器数量与部署方案 | 负载 / 压力测试 + 部署测试 | 不断探测承载能力，用于活动与新用户上线部署 |
| 问题追查 / 风险发现 | 已有系统 + 长时间压力 | 隐患清单（如 Full GC、内存泄漏） | 负载 / 压力测试 | 长时间发压（如 24 小时）+ 关注指标 + 多次优化重试 |

【企业场景】
同一个系统，你会被要求做三种不同的压测，交付物完全不同：
1. **能力验证**（发版验收）："单机 4C8G 在下单场景下能否达到 AVG RT ≤ 200ms、5000 QPS" → 交付达标判定
2. **容量规划**（活动备战）："50 万 UV 的活动，需要多少台机器" → 交付机器数与部署方案
3. **问题追查**（大促前体检）："24 小时高 QPS 下 Full GC < 1s、无内存泄漏" → 交付隐患清单与修复建议

**面试时如果你能主动区分这三类，并说明各自的输入输出，面试官会立刻把你和"只会跑 JMeter 的人"区分开。**

【面试考察】
面试官："你们做性能测试通常包含哪些类型？"

参考回答框架：
1. 按用途分三类：能力验证、容量规划、问题追查与风险发现
2. 每类的输入输出：能力验证（规格+指标 → 达标判定）、容量规划（用户量级 → 机器数与部署）、问题追查（长时间压力 → 隐患清单）
3. 每类侧重的方法与特点：是否单机、是否长时间发压、是否需要多次优化重试
4. 加分：给出一个真实例子（例如大促前用 24 小时稳定性测试发现内存泄漏）

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 三类用途混成"一次压测全搞定" | 目标不同、环境不同、指标不同，需要分别设计 |
| 容量规划只给"能撑多少 QPS" | 要换算成"需要多少台机器、如何部署"（部署测试也是方法之一） |
| 能力验证环境随意（未固定规格） | 能力验证必须明确硬件规格与指标要求，否则结论无意义 |
| 问题追查只跑一次 | 需要"测试 → 优化 → 重试"的迭代，一次压测只能发现问题存在 |
| 把"风险发现"当成一次性任务 | 风险发现要常态化（定期重压），因为风险随时间与版本引入 |

【我的理解】
> （用自己的话回答：为什么同一个系统的三种压测，交付物完全不同？如果业务方说"双十一预计 50 万 UV，你们看看行不行"，你会按哪一类用途来做，并交付什么？）
