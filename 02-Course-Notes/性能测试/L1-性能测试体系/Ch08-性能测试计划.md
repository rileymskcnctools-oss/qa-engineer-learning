## 一、什么是性能测试计划、为什么必须做

### 知识点 1：性能测试计划的定义与七个制定理由

【课程原话/定义】
性能测试计划是在进行软件或系统的性能测试之前制定的**详细计划和指导文件**。它描述了所需性能测试的**目标、范围、测试环境、资源需求、测试策略、测试用例、时间表**等重要信息。

为什么要制定性能测试计划（保证性能测试的有效性和可靠性）：
1. **明确测试目标**：明确定义性能目标，例如响应时间、吞吐量、并发用户数等，有助于确保测试的准确性和一致性，并提供可评估的性能指标
2. **确定测试范围**：明确需要测试的系统或软件范围，包括功能模块、关键业务流程等，避免遗漏关键的性能热点
3. **提供测试环境和配置**：指定测试所需的硬件、软件、操作系统和网络配置，有助于创建与实际生产环境相似的测试环境，确保测试的真实性和准确性
4. **设定测试策略**：定义测试的方法、策略和技术，确定负载模型、测试用例设计方法、测试数据和性能统计指标，确保测试具有**可重现性和可测量性**
5. **资源管理和规划**：列出执行测试所需的人员、工具、时间和预算等资源，有助于合理规划和管理测试过程，避免测试中断或延误
6. **风险评估和应对措施**：识别可能的风险和挑战，并提供相应的风险评估和应对措施，有助于规避潜在的性能问题和系统崩溃
7. **结果分析和报告**：规定测试结果的分析方法和报告格式，有助于准确分析和解释测试结果，向相关方提供清晰、可理解的性能测试报告

总之，性能测试计划提供了一个**全面的框架和指导**，确保性能测试的**有效性、可靠性和可重复性**。

【为什么？】
为什么"可重复性"是性能测试计划的核心价值？因为性能测试的结论只有在**同条件**下才有意义：
- 优化前 vs 优化后（同环境、同数据量、同场景、同加压方式）→ 才能说"提升了 30%"
- 这个版本 vs 上个版本（同 RPS、同数据）→ 才能说"劣化了 15%"

计划的作用就是把"条件"固定下来写成文档：环境规格、数据规模、加压曲线、指标口径。**没有计划的压测，每次测出来的数字都不可比——那只是"测过"，不是"性能测试"。** 这七条理由合起来其实是一句话：**计划让压测从"一次性活动"变成"可复现的工程过程"。**

【必须掌握】

| 理由 | 解决的问题 | 不做的后果 |
|------|------------|-----------|
| 明确测试目标 | 定 RT/吞吐/并发目标 | 不知道压什么、达标与否无法判断 |
| 确定测试范围 | 圈定模块与关键业务流程 | 漏测核心链路，上线后仍崩 |
| 环境和配置 | 规范硬件/软件/网络 | 环境差异大，结论无法迁移线上 |
| 设定测试策略 | 负载模型、用例设计、指标口径 | 结果不可重现、不可测量 |
| 资源管理和规划 | 人员/工具/时间/预算 | 压测中途缺机器缺人，延误或中断 |
| 风险评估和应对 | 识别风险与预案 | 压出事故（例如压到生产） |
| 结果分析和报告 | 规定分析方法与报告格式 | 数据一堆、结论没有 |

【企业场景】
你接手一个"发版前性能验收"，先写的就是这份计划：目标（下单 TP99 ≤ 800ms、3000 QPS 下错误率 < 0.1%）、范围（下单 + 支付两条链路，不含后台管理系统）、环境（同比线上 1/2 的规格，8 台应用机 + 1 主 2 从数据库）、策略（阶梯加压 + 混合场景 + RPS 基准）、资源（2 人 × 3 天，JMeter 集群 + Grafana 看板）、风险（测试数据不足导致缓存命中率虚高；压测环境与线上配置差异）。**这份文档同时是"给领导看的申请"和"给团队执行的标准"，压测过程中所有争议都能回到它来判定。**

【面试考察】
面试官："性能测试计划里都写什么？为什么必须有计划？"

参考回答框架：
1. 内容清单：目标、范围、环境与配置、策略（负载模型/用例/指标口径）、资源（人/工具/时间/预算）、风险预案、结果分析与报告格式
2. 核心价值：保证**有效性、可靠性和可重复性**——尤其是可重复，它决定了优化前后能否对比
3. 业务价值：一份计划既是执行标准，也是向上沟通（资源申请）与风险管理的工具
4. 加分：指出"范围"最常被漏（只压单个接口，没压混合链路）

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 认为计划是走流程的形式 | 计划决定了数据可比性，是结论可信的前提 |
| 只写目标不写范围 | 范围缺失会导致核心链路漏测（如只压下单不压支付） |
| 不写风险预案 | 压测风险包括压到生产、压崩测试环境、数据污染等，需提前声明 |
| 计划一次写完就锁死 | 环境变化、业务量变化时应修订计划并记录版本 |

## 二、性能测试计划的六个阶段

### 知识点 2：计划流程总览

【课程原话/定义】
性能测试计划的流程：
1. **需求分析与测试设计阶段**
2. **环境设计与搭建阶段**
3. **测试数据准备阶段**
4. **性能指标预期设定阶段**
5. **测试执行 & 监控阶段**
6. （发压工具配置及脚本编写阶段穿插其中）
7. **测试报告输出阶段**

【必须掌握】

```mermaid
flowchart LR
    S1["① 需求分析与测试设计<br/>业务数据 / 行为日志 → 业务模型 → 预估 TPS/QPS"] --> S2["② 环境设计与搭建<br/>同比 1/2、1/4 · 起压环境 / 被压环境 / 环境调试"]
    S2 --> S3["③ 测试数据准备<br/>请求参数 / 数据表填充 / 多接口请求比例"]
    S3 --> S4["④ 性能指标预期设定<br/>QPS / RT / 错误率 / 机器性能 / 功能正常"]
    S4 --> S5["⑤ 发压工具配置与脚本编写<br/>选工具 / 安装配置 / 写脚本"]
    S5 --> S6["⑥ 测试执行 & 监控<br/>环境检查 / 起压 / 记录指标"]
    S6 --> S7["⑦ 测试报告输出<br/>分析结果 / 沟通确认 / 邮件发送"]
```

| 阶段 | 一句话目标 | 输出 |
|------|-----------|------|
| ① 需求分析与测试设计 | 搞清楚"要压什么、多大量" | 业务模型 + 预估 TPS/QPS + 场景 |
| ② 环境设计与搭建 | 造一个"有参考价值"的压测环境 | 起压环境 + 被压环境 + 调试通过 |
| ③ 测试数据准备 | 让数据量级与分布贴近真实 | 参数数据 + 库表数据 + 请求比例 |
| ④ 性能指标预期设定 | 明确"多少算达标" | SLA / 验收标准 |
| ⑤ 发压工具配置及脚本编写 | 让压力能被"执行" | 压测脚本 + 工具配置 |
| ⑥ 测试执行 & 监控 | 采集可信数据 | 压测数据 + 监控数据 |
| ⑦ 测试报告输出 | 交付结论与建议 | 性能测试报告 |

【为什么？】
为什么这七个阶段要按这个顺序走？因为它们之间存在**硬依赖**，跳过任何一个都会让后面的阶段失效：
- 没有①需求分析 → 不知道压什么（场景与目标都定不出来）
- 没有②环境 → 数据不可信（结论无法外推）
- 没有③数据 → 压出来的数字虚高（小数据量/单账号导致缓存命中虚高）
- 没有④指标预期 → 无法判定达标（报告无法下结论）
- 没有⑤脚本 → 压力根本发不出来
- 没有⑥执行监控 → 没有数据可分析（压测白做）
- 没有⑦报告 → 结论无法交付，团队不会采取动作

从工程视角看，这七个阶段是"**把业务需求翻译成可执行、可度量、可交付的压测过程**"的完整链条：①②③解决"测什么、在哪测、用什么数据"，④⑤解决"达标线与执行手段"，⑥⑦解决"证据与交付"。

【企业场景】
你在周会上被问"这次压测要多久"，回答就来自阶段划分：需求分析 + 环境（3 天）→ 数据准备（2 天）→ 指标对齐（0.5 天）→ 脚本开发（1.5 天）→ 执行与监控（1 天）→ 报告（1 天），共 9 个工作日左右。**能把压测拆成带工期的阶段，才说明你真的做过**——面试时这个答案比"压测很快的，一两天就行"有说服力得多。

【面试考察】
面试官："性能测试计划包含哪些阶段？哪一步最花时间？"

参考回答框架：
1. 七阶段：需求分析与测试设计 → 环境设计与搭建 → 测试数据准备 → 性能指标预期设定 → 发压工具配置与脚本编写 → 测试执行与监控 → 测试报告输出
2. 各阶段的产出：业务模型与目标 QPS → 可用环境 → 贴近真实的数据 → 验收标准 → 脚本 → 压测与监控数据 → 报告
3. 最花时间/最容易被低估的：**环境搭建 + 数据准备**（尤其是数据量级对齐生产）
4. 加分：说明阶段间是硬依赖，缺一环结论就不可信

### 知识点 3：阶段① 需求分析与测试设计

【课程原话/定义】
**场景 1：对于已经在线上运行的业务或相似业务**
- **收集行为日志**：获取业务运行时的行为日志，包括用户的访问请求、操作行为、响应时间等信息，帮助了解用户行为模式和业务负载情况
- **分析当前业务数据**：通过分析当前业务数据，例如每日活跃用户数（DAU）、每日页面浏览量（PV）、每天的订单量等，获得业务的基本性能指标，如每秒钟的请求量（QPS）或每秒钟的事务处理量（TPS）等
- **建立业务模型**：基于当前业务数据和行为日志的分析结果，建立业务模型，包括各个关键业务场景、用户行为流程、系统组件之间的交互等
- **预估接口 TPS/QPS**：根据业务模型和当前业务数据，预估出每个关键接口或服务的每秒钟事务处理量（TPS）或请求量（QPS），帮助确定性能测试的目标和负载程度

**场景 2：对于新业务或新活动**
- **参考友商经验**：如果有类似的业务已经在线上运行，可以参考其性能测试经验和结果，了解业务模型、性能指标和测试场景，从而为新业务制定性能测试计划提供参考依据
- **产品和运营共同梳理评估**：产品和运营团队可以针对新业务梳理出**核心场景路径、入口及对应的转化率、问题收敛页面**等，然后将这些信息转化为业务模型，进而确定相应的测试场景、数据量级和接口比例

【为什么？】
为什么需求分析要分成"已有业务"和"新业务"两条路？因为它们的**数据来源本质不同**：
- 已有业务：**数据在手**——日志和业务数据是既成事实，工作重点是"提取 + 折算"（DAU/PV/订单量 → QPS/TPS）。这是最可靠的一条路，也必须做（**没有比线上数据更真实的负载模型**）
- 新业务：**没有数据**——只能靠两个替代品：友商的标杆数据（外部参照）和产品运营梳理的场景路径与转化率（内部推演）。这时结论必须写明假设，并在上线后**回采真实流量修正模型**（这也是课程在应用场景里提到的"新产品参考竞品指标"）

一句话总结：**性能测试的输入永远来自业务，而不是来自测试人员的想象。**

【必须掌握】

| 数据来源 | 具体内容 | 折算方式 |
|----------|----------|----------|
| 行为日志 | 访问请求、操作行为、响应时间 | 得到行为模式与请求分布 |
| 业务数据 | DAU、PV、订单量 | 折算 QPS / TPS |
| 业务模型 | 关键场景、用户行为流程、组件交互 | 决定测试场景与请求比例 |
| 友商经验（新业务） | 类似业务的性能指标与场景 | 作为第一版目标参照 |
| 产品运营梳理（新业务） | 核心场景路径、入口、转化率、问题收敛页面 | 转化为数据量级与接口比例 |

【企业场景】
你要压"新增的秒杀活动"，但活动还没上线，没有任何历史数据。你的动作是：先找运营要三样东西——预计参与人数、活动时长、各入口的转化率；再参考同类活动（或竞品）的峰值数据；最后把"活动页 → 商品详情 → 秒杀下单 → 支付"这条路径上的每个接口，按转化率折算成 QPS。**面试时如果你能讲出"新业务怎么从运营的转化率倒推接口 QPS"，这就是区分"做过压测"和"真的会做性能测试"的分水岭。**

【面试考察】
面试官："没有历史数据的新业务，你怎么做性能测试？"

参考回答框架：
1. 数据来源替代：参考友商的量与指标（外部标杆）
2. 内部推演：与产品运营梳理核心场景路径、入口、转化率、收敛页面 → 转成业务模型
3. 折算：按转化率与漏斗把用户量拆到具体接口的 QPS/TPS
4. 留冗余：设定 20%~30% 余量，并在上线后回采真实流量修正模型
5. 加分：明确指出"假设条件"要写进报告，避免结论被当成事实

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 直接用 DAU 当并发数 | 需要用活跃比例、集中度、转化率逐层折算到接口 QPS |
| 新业务不写假设条件 | 推演数据必须标注假设，否则上线后无法复盘偏差 |
| 只看总量不看分布 | 请求比例（浏览:下单）决定了混合场景，漏掉会造成误判 |
| 忽略"问题收敛页面" | 它往往是流量漏斗的瓶颈点，是压测重点 |

### 知识点 4：阶段② 环境设计与搭建

【课程原话/定义】
**设计**：根据需求，结合线上机器部署情况，搭建线下测试环境，要求具有**一定的参考价值，一般同比 1/2、1/4**。
注意：**测试环境无论怎么仿真和模拟，基本都不太可能达到 1 比 1 的效果。**

**环境搭建**
- **起压环境**：压测工具的安装与调试、机器参数记录
- **被压环境**：基础服务的搭建、web 机代码部署及代码改造、机器参数记录
- **环境调试**：查看接口是否正常

【为什么？】
为什么要"同比 1/2、1/4"而不是 1:1？这是一个**成本与可信度的权衡**：
- 1:1 复刻线上环境成本极高（机器、网络、数据量），大多数公司不具备条件
- 同比缩容（两台线上机对一台压测机）保留了**架构与配置的比例关系**，结论可以按比例外推
- 但课程同时提醒：**不可能达到 1:1 的效果**——因为数据量、网络链路、依赖服务的真实压力、线上其他业务的干扰都无法完全复制

所以正确的态度是：**接受环境有偏差，主动记录偏差**。做法就是把"机器参数记录"作为标准动作（起压环境与被压环境都要记），并在报告里写明环境规格与线上差异——**这样别人才知道你的结论能外推多远。**

另外，"web 机代码改造"这一条很关键：压测环境里往往要**关闭验证码、关闭风控、加日志、开调试端口、调整限流阈值**，这些改造本身会影响性能，必须记录在案，避免上线后"压测过了但线上扛不住"。

【必须掌握】

| 项目 | 内容 | 为什么要记录 |
|------|------|--------------|
| 环境设计 | 结合线上部署，同比 1/2、1/4 | 用比例关系把结论外推到线上 |
| 环境局限 | 无法 1:1 仿真 | 主动声明偏差，避免结论被过度采信 |
| 起压环境 | 工具安装调试 + 机器参数记录 | 起压机是瓶颈时会导致假结论 |
| 被压环境 | 基础服务、web 代码部署与改造、机器参数记录 | 明确"改了什么"，避免与线上配置混淆 |
| 环境调试 | 查看接口是否正常 | 环境不通则压测数据无意义 |
| 代码改造 | 关验证码/风控、加日志、调限流等 | 改造会影响性能，必须记录并评估影响 |

【企业场景】
你搭好压测环境后做的第一件事不是敲 JMeter，而是写一份"环境对照表"：线上 16 台应用机 vs 压测 8 台（同比 1/2）、线上数据库 1 主 3 从 vs 压测 1 主 1 从、网络带宽差异、以及压测环境做了哪些改造（关闭了短信验证码、限流阈值调到 10 万、日志级别调成 INFO）。压测结束后，报告里写"按同比 1/2 外推，线上可支撑约 2 倍于本次压测的吞吐"。**没有这张对照表，你的容量结论就是空中楼阁。**

【面试考察】
面试官："压测环境怎么搭？和线上不一致怎么办？"

参考回答框架：
1. 设计原则：结合线上部署结构，同比缩容（1/2、1/4）保证有参考价值
2. 两部分环境：起压环境（工具 + 机器参数）+ 被压环境（服务 + 代码部署与改造 + 机器参数）
3. 必须做环境调试：确认接口连通、链路可用、监控采集正常
4. 偏差处理：明确"不可能 1:1"，记录环境差异与代码改造项，结论按比例外推并标注假设
5. 加分：指出代码改造（关风控/限流）是最容易被忽略的"结论失真源"

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 认为压测环境越接近线上越好、越真 | 目标不是"最真"而是"有参考价值 + 偏差可量化" |
| 不记录机器参数 | 无法复现、无法横向对比、无法外推容量 |
| 忘记记录代码改造项 | 改造会改变性能表现，结论会失真 |
| 忽略起压环境 | 起压机资源不足会伪装成"系统没问题" |
| 环境调试只测连通性 | 还要验证监控采集、测试数据、限流是否被误触发 |

【我的理解】
> （用自己的话回答：为什么压测环境"不可能 1:1"？如果压测环境同比线上 1/4，你的容量结论应该怎么表达才严谨？）

### 知识点 5：阶段③ 测试数据准备

【课程原话/定义】
- **接口请求参数**：自己构造 / 日志获取 / 上下关联
- **数据表的数据填充**：部分业务数据信息可以直接从数据库或缓存数据库获取
- **如果是多接口，则需结合业务场景设计请求比例**

【为什么？】
为什么"数据准备"值得单列一个阶段？因为性能测试的结果对数据**极其敏感**，而且这种敏感性往往被低估：
- **数据量**：空表上的查询与千万级表上的查询不是一个性能问题（有索引时也可能因为回表、排序、深分页而崩）
- **数据分布**：如果所有请求都查同一个商品 ID，缓存与局部性会让结果虚高——真实流量是分散的
- **数据合法性**：压测数据要能走通业务（账号存在、库存充足、余额够），否则测出来的是"业务失败的快速返回"，TPS 虚高、RT 虚低
- **请求比例**：多接口场景必须按业务真实比例混合（浏览:加购:下单 ≈ 20:5:1），否则压出来的瓶颈组合与线上不同

一句话：**数据准备的质量，直接决定压测结论能不能代表线上。**

【必须掌握】

| 数据类别 | 来源/做法 | 关键点 |
|----------|-----------|--------|
| 接口请求参数 | 自己构造 / 日志获取 / 上下关联 | 越接近真实越好；用日志提取真实参数分布 |
| 库表数据填充 | 从数据库或缓存数据库获取、造数 | 数据量级必须是"量级正确"的（千万级不能用几千条代） |
| 多接口请求比例 | 结合业务场景设计 | 比例错了 → 瓶颈组合错了 → 结论错了 |
| 参数化/数据驱动 | 每个虚拟用户用不同数据 | 避免缓存、风控、锁竞争导致的结果失真 |

【企业场景】
你要压商品详情页，先向 DBA 要一份生产库数据量的清单（商品表 800 万行、SKU 表 3000 万行），然后在压测库造同量级数据（用造数脚本按真实分布生成），再用日志里提取的"热门商品 Top 1000 + 长尾商品"的真实访问比例做参数化。**如果跳过这一步（在只有几千条数据的库上压），你得到的"商品详情 50ms"结论在线上可能直接变成 500ms。**

【面试考察】
面试官："压测数据怎么准备？"

参考回答框架：
1. 参数数据：从日志提取或自己构造，注意上下关联（登录态、订单号）
2. 库表数据：量级与分布要对齐生产（空表/小表压测无意义）
3. 请求比例：按业务场景设计多接口混合比例
4. 参数化：用数据驱动让不同虚拟用户使用不同数据，避免缓存/风控污染
5. 加分：说明造数脚本与数据来源，保证压测可复现

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 在小数据量库上压测 | 数据量级直接决定 SQL 性能，必须对齐生产量级 |
| 所有请求用同一账号/同一商品 | 缓存命中与风控会让结论虚高 |
| 忽略请求比例 | 混合场景的比例错了，瓶颈组合就错了 |
| 造的数据走不通业务 | 业务失败快速返回会被误读成"性能很好" |
| 压测后不清理数据 | 数据污染会影响下一次压测的可比性 |

【我的理解】
> （用自己的话回答：为什么"在只有几千条数据的库上压商品查询"会得出乐观的错误结论？如果你要向 DBA 申请造数，你会提出哪些要求？）

### 知识点 6：阶段④ 性能指标预期设定

【课程原话/定义】
- **每秒请求数（QPS）**：基于业务进行拆分，比如业务会提出需要再双十一的时候支持每分钟两万的订单。根据这个需求，再去拆分具体有哪一些接口的请求
- **请求响应时间（最小、最大、平均）**：需要考虑到用户体验，即使后面能够正常响应，但是请求响应时间不能太长。（**通常 C 端不超过 1s，尽量在 200 毫秒内**）
- **错误率**：基于在性能测试过程中，每个请求不可能百分百成功，但是也要有一个上限的阈值，那么这个阈值是多少
- **机器性能**：cpu、memory 无剧烈抖动或者飙升
- **压测过程接口功能是否正常**：不要只关注响应状态码 200，还需要从业务角度来看响应信息是否符合业务需求
- 注意：**不同性能测试方式下指标预期会有差异**

【为什么？】
为什么指标预期必须"分段位 + 分类别"地想清楚？
- **RT 的量化标准**：课程给了很有用的经验值——**C 端不超过 1s、尽量 200ms 内**。这不是拍脑袋：1s 是用户注意力的临界点（超过会觉得卡），200ms 是"感觉是即时的"阈值
- **错误率要设阈值而不是要求 0**：压测中由于网络、限流、数据竞争，极少量失败是正常的；关键是**定义可接受上限**（例如 < 0.1%），否则报告永远"不达标"
- **机器性能要看"抖动"**：CPU 无剧烈抖动或飙升，比"平均 CPU 50%"更严格——**抖动往往意味着 GC、锁竞争或资源争抢**，是大促时雪崩的前兆
- **业务功能正常 ≠ HTTP 200**：压测中必须校验业务码/业务数据，否则"下单失败但返回 200"会被统计成成功，TPS 完全失真
- **不同测试方式指标不同**：稳定性测试看长时间漂移，压力测试看拐点，基准测试看单点指标——一套阈值套所有场景是错的

【必须掌握】

| 指标 | 设定方式 | 经验值 / 注意点 |
|------|----------|-----------------|
| QPS | 从业务需求拆分到接口（如双十一每分钟 2 万订单 → 各接口 QPS） | 拆分要基于真实的请求比例 |
| 响应时间 | 定义最小/最大/平均（建议同时定分位值） | **C 端 ≤ 1s，尽量 ≤ 200ms** |
| 错误率 | 设定可接受上限阈值 | 不要求 0，但要明确上限（如 < 0.1%） |
| 机器性能 | CPU/内存无剧烈抖动或飙升 | 关注抖动（GC/锁/争抢的信号），不只看均值 |
| 功能正确性 | 校验业务响应而非仅状态码 200 | 业务失败但 200 是最常见的假成功 |
| 场景差异 | 不同测试方式（负载/压力/稳定性/容量）指标不同 | 阈值必须绑定测试类型 |

【企业场景】
你写验收标准时是这样落地的：QPS（双十一峰值每分钟 2 万订单 → 下单接口 900 QPS、商品详情 4000 QPS）、RT（C 端下单 TP99 ≤ 800ms、平均 ≤ 200ms）、错误率 < 0.1%、机器性能（压测期间 CPU 波动不超过 ±15%、无 Full GC 超过 1s）、功能（每轮压测后抽检 100 笔订单数据落库正确）。**这份标准让"压测通过"变成可判定的事实，而不是一句主观感受。**

【面试考察】
面试官："压测的验收标准怎么定？"

参考回答框架：
1. 业务驱动：从业务峰值需求（订单量/用户量）拆到接口 QPS
2. 用户体验：RT 定上限（C 端 ≤ 1s，尽量 ≤ 200ms），建议用分位值而非仅均值
3. 稳定性：错误率设可接受上限（不是 0）
4. 资源健康：CPU/内存无剧烈抖动或飙升（抖动比均值更能暴露隐患）
5. 业务正确性：校验业务响应与数据落库，不能只看 200
6. 加分：指标必须绑定测试类型（负载/压力/稳定性/容量各不相同）

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 只定"RT ≤ 1s"，不定分位值 | 应同时定均值与 TP95/TP99，否则长尾被掩盖 |
| 要求错误率 0% | 应设可接受上限阈值（如 < 0.1%） |
| 把 CPU 平均值当健康指标 | 要盯"剧烈抖动/飙升"，抖动是雪崩前兆 |
| 只校验 HTTP 200 | 必须校验业务码与业务数据 |
| 一套阈值套所有场景 | 负载/压力/稳定性/容量测试的指标预期不同 |

【我的理解】
> （用自己的话回答：为什么"CPU 无剧烈抖动"比"CPU 平均 50%"更能反映系统健康？压测中"业务失败但返回 200"为什么是最危险的假成功？）

### 知识点 7：阶段⑤⑥⑦ 工具配置与脚本、执行与监控、报告输出

【课程原话/定义】
**发压工具配置及脚本编写阶段**
- **选择发压工具**：根据需求和系统特点选择适合的发压工具。常用的性能测试工具包括 JMeter、LoadRunner、Gatling 等，需考虑测试目标、可支持的协议和工具的易用性
- **安装和配置发压工具**：根据官方文档下载安装，然后根据具体情况进行配置。配置项可能包括服务器地址、并发用户数、请求协议和频率等，确保工具和测试环境的通信设置正确
- **编写性能测试脚本**：用于定义测试场景，包括模拟并发用户行为、设定请求参数和验证响应等；脚本可以使用工具提供的图形界面或编程语言来编写

**测试执行 & 监控阶段**
- 测试前环境检查：记录机器参数
- 起压：根据被压情况，调节并发量到适合的情况
- 查看记录各项性能指标：nginx 日志查看每秒请求数、查看 nginx 错误请求、查看机器参数（cpu idle、mem 等）、查看 db、cache 等数据是否写入正常、访问接口查看功能是否正常

**测试报告输出阶段**
根据测试过程中记录的各项参数，结合压测工具产生的日志，对测试结果进行分析，并产出测试报告。测试完成后，及时与相关人员沟通，确认是否满足需求，发送测试报告邮件。

【为什么？】
为什么"选择发压工具"要强调"根据需求和系统特点"？因为工具能力直接限定了测试范围：被测对象是 HTTP 接口还是 Dubbo/Kafka？需不需要参数化与断言？要不要分布式？——不同答案对应不同工具（见 [[Ch04-行业流行性能压测工具介绍|Ch04]] 的选型对比表）。**选错工具的代价不是"麻烦"，而是"有些场景根本压不了"。**

而"测试前环境检查：记录机器参数"这一条，是整条流程里最容易被忽略、代价最大的动作：**基线参数不记，压测后就没有对比对象**，"CPU 95%"到底是不是异常、内存增长算不算泄漏，都无从判断。这也是稳定性测试（跑 24 小时）的必备前提。

【必须掌握】

| 环节 | 关键动作 | 检查清单 |
|------|----------|----------|
| 工具选择 | 按测试目标 / 协议支持 / 易用性选（JMeter、LoadRunner、Gatling 等） | 能否覆盖被测协议与场景 |
| 工具配置 | 服务器地址、并发用户数、请求协议与频率 | 通信设置正确、压测机能稳定发压 |
| 脚本编写 | 模拟并发用户行为、设定请求参数、验证响应 | 参数化、断言、关联、思考时间 |
| 执行前检查 | 记录机器参数（基线） | 起压机与被压机的 CPU/内存基线 |
| 起压 | 按被压情况调节并发量 | 阶梯加压，观察曲线 |
| 监控记录 | nginx 每秒请求数、错误请求、CPU idle、内存、DB/缓存写入、接口功能 | 业务与系统双侧数据齐全 |
| 报告输出 | 分析结果 → 产出报告 → 沟通确认 → 发送邮件 | 结论 + 建议 + 是否满足需求 |

【企业场景】
压测执行日的标准动作是：开压前记录所有机器参数基线（CPU/内存/磁盘/连接数）→ 启动 nginx 日志统计、vmstat、nmon 与 Grafana 看板 → 按 500/1000/2000/3000 阶梯加压，每档稳定 10 分钟后记录数据 → 每档压测结束后**访问接口抽检业务数据是否正确落库** → 结束后汇总数据、归因分析、输出报告并邮件发给开发/运维/产品确认。**这套动作的每一步都在回答同一个问题："这份结论能被别人相信吗？"**

【面试考察】
面试官："压测当天你会做哪些事？"

参考回答框架：
1. 压前：确认环境与脚本可用、记录机器参数基线、验证监控采集、确认测试数据
2. 工具侧：确认目标并发/速率能被稳定发出（避免起压机成为瓶颈）
3. 执行：阶梯加压、每档稳定时长、观察曲线与资源
4. 监控：业务侧（每秒请求数、错误请求）与系统侧（CPU/内存/DB/缓存）双侧记录
5. 正确性：校验业务数据落库与接口功能，不只依赖状态码
6. 压后：出报告 + 与相关方沟通确认 + 邮件交付

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 不记录机器参数基线 | 没有基线就无法判断"异常"，结论无法归因 |
| 只盯着 JMeter 的报告 | 必须同时采集 nginx 日志与系统资源数据（交叉验证） |
| 压测结束不校验业务数据 | 状态码正常不代表业务正确（数据可能没写进去） |
| 报告写完不沟通 | 报告要经过与开发/运维/产品的确认闭环，否则问题不会被修 |
| 用"感觉"调并发量 | 应按预设的阶梯档位与判定标准调节 |

【我的理解】
> （用自己的话回答：为什么"记录机器参数基线"是压测执行的第一步？如果你在压测中看到内存持续上升，你会怎么用基线数据判断这是不是泄漏？）

## 三、性能测试中的常用命令（可直接抄用的清单）

### 知识点 8：九组实战命令

【课程原话/定义】
1. **查看 nginx 每秒请求数**：`tail -f access.log | awk '{print $4}' | uniq -c`
   - `tail -f access.log`：实时监视 access.log 内容；`awk '{print $4}'`：提取每行第 4 列；`uniq -c`：去重计数
2. **查看某个接口每秒请求数**：`tail -f access.log | grep p_getorderstatus | awk '{print $4}' | uniq -c`
   - 先用 `grep p_getorderstatus` 过滤出该接口的行，其余同上
3. **查看 cpu idle**：`vmstat 1`
4. **查看内存**：`free -m`
5. **查看 nginx 日志是否有错误请求**：`tail -f access.log | cut -d ' ' -f 10 | grep -v 200`
   - `cut -d ' ' -f 10` 取第 10 列；`grep -v 200` 排除状态码 200 的行
6. **查看进程**：`top` / `ps aux | grep xxx`
7. **查看 nginx 日志某接口访问数量**：`cat access.log.xxxx | grep p_getorderstatus | wc -l`
8. **杀进程**：`kill xxx`（指定进程号）/ `pkill xxx`（指定部分进程名）；自定义特征：`for i in ps aux | grep xxxx | awk '{print $2}'; do kill $i; done` 或 `kill pgrep -f xxxx`
9. **查看 TIME_WAIT 数量**：`ss -s` / `netstat -tnlp | grep TIME_WAIT | wc -l`

【为什么？】
为什么压测工程师必须会这几条命令？因为压测现场的判断是**秒级**的：曲线走平时你要立刻知道"现在实际打进去多少请求（nginx 每秒请求数）、有没有报错（错误请求）、机器还剩多少资源（cpu idle / 内存）、下游写没写进去（DB/缓存）"。这些答案不该等到压测结束再看报告——**现场用命令行看数据，才能及时调整档位、避免"压错了一整轮"**。

另外要注意第 9 条的意义：**TIME_WAIT 数量是压测机侧的经典坑**。短连接大量建立关闭会耗尽本地端口，表现为"压不上去"，容易被误判成"被压系统扛住了"。所以压测中同时看两端（服务端资源 + 压测机 TIME_WAIT）才是完整视角。

【必须掌握】

| 目的 | 命令 | 关键点 |
|------|------|--------|
| nginx 每秒请求数 | `tail -f access.log \| awk '{print $4}' \| uniq -c` | 第 4 列通常是时间；`uniq -c` 只统计**相邻重复**，要精确统计需先 `sort` |
| 某接口每秒请求数 | `tail -f access.log \| grep 接口名 \| awk '{print $4}' \| uniq -c` | 定位单接口流量，验证参数化与场景比例是否生效 |
| CPU 空闲 | `vmstat 1` | 看 `id` 与 `r`、`wa`；采样才看得到毛刺 |
| 内存 | `free -m` | 结合 vmstat 的 si/so 判断是否动用 swap |
| nginx 错误请求 | `tail -f access.log \| cut -d ' ' -f 10 \| grep -v 200` | 排除 200 后剩下的即错误/非 200 响应 |
| 查看进程 | `top` / `ps aux \| grep xxx` | top 看资源，ps 看进程是否存在 |
| 某接口访问总量 | `cat access.log.日期 \| grep 接口名 \| wc -l` | 适合压测后统计总量与校验 |
| 杀进程 | `kill PID` / `pkill 进程名` | 压测收尾清理残留进程 |
| TIME_WAIT 数量 | `ss -s` / `netstat -tnlp \| grep TIME_WAIT \| wc -l` | **压测机端口耗尽的预警指标** |

【课程原文勘误（【易错点】）】
课程原文这几条命令有几处笔误，直接抄会报错，记录如下以便对照原文核对：

| 课程原话 | 问题 | 正确写法 |
|----------|------|----------|
| `for i in ps aux \| grep xxxx \| awk '{print $2}';do kill $i ;done` | `for` 的列表缺少命令替换，会把 `ps` 当字符串 | `for i in $(ps aux \| grep xxxx \| awk '{print $2}'); do kill $i; done` |
| `kill pgrep -f xxxx` | 参数顺序错了，`kill` 不认识 `pgrep` | `kill $(pgrep -f xxxx)` 或直接 `pkill -f xxxx` |
| `- top - ps aux\|grep xxx` | 排版错乱，应为两条独立命令 | `top` 与 `ps aux \| grep xxx` 分开执行 |
| `tail -f access.log \| awk '{print $4}' \| uniq -c` | `uniq -c` 只能合并**相邻**相同的行，日志未按时间排序时统计不准 | 需要精确统计时加 `sort`：`... \| sort \| uniq -c` |

【企业场景】
压测进行到第 3 档（2000 并发）时 TPS 突然走平，你现场敲三条命令：`tail -f access.log | grep p_getorderstatus | awk '{print $4}' | uniq -c` 看实际打进多少、`tail -f access.log | cut -d ' ' -f 10 | grep -v 200` 看错误码、`free -m` + `vmstat 1` 看内存与 swap。三条命令 30 秒内完成，结论是"实际 QPS 只有目标的 60%，且出现 502"——问题不在被压系统，而在**压测机/网关侧**。这个判断如果等到压测结束才做，白跑一整轮。

【面试考察】
面试官："压测过程中你怎么实时看数据？"

参考回答框架：
1. 业务侧：nginx 日志统计每秒请求数与错误请求（`awk` 取时间列 + `uniq -c`；`grep -v 200` 找错误）
2. 系统侧：`vmstat 1` 看 CPU/IO、`free -m` 看内存、`top`/`ps` 看进程
3. 数据侧：确认 DB 与缓存写入正常、接口功能正常
4. 压测机侧：`ss -s` / `netstat | grep TIME_WAIT | wc -l` 防端口耗尽导致的假结论
5. 加分：指出命令行是"现场快照"，正式结论要用监控平台（Prometheus/Grafana）的数据

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 直接抄课程命令（含笔误） | 命令语法要自己验证一遍，尤其是 `for`/`kill`/`pgrep` 三处 |
| 只看压测工具的汇总报告 | 必须用 nginx 日志与系统命令交叉验证（工具数可能与实际不一致） |
| 忽略 TIME_WAIT | 压测机端口耗尽会造成"压不上去"的假象 |
| `uniq -c` 不配 `sort` | 未排序时只能合并相邻重复行，统计结果偏差大 |
| 压测中的日志被限流/切割 | 大流量下要确认日志轮转与磁盘空间，避免压测中途日志写满磁盘 |

【我的理解】
> （用自己的话回答：为什么压测中要同时看"服务端资源"和"nginx 实际请求数"？如果压测工具显示 2000 并发但 nginx 每秒请求数远低于预期，你会先怀疑哪里？）
