## 一、什么是性能剖析

### 知识点 1：性能剖析的定义与四类工作内容

【课程原话/定义】
性能剖析是指**对应用程序或系统进行分析和测量，以确定其性能瓶颈和优化潜力**的过程。它可以帮助开发人员识别和解决应用程序中的性能问题，提高应用程序的响应时间、吞吐量和资源利用率。

性能剖析涉及以下几个方面的内容：
- **性能指标的收集**：性能剖析工具可以收集各种性能指标，如 CPU 使用率、内存占用、网络延迟、磁盘 IO 等，帮助开发人员了解系统的整体性能状况
- **热点分析**：找出应用程序中的**热点**，即耗费大量时间和资源的部分。通过定位热点，开发人员可以确定哪些代码、函数或模块需要优化
- **性能优化建议**：性能剖析工具通常会提供优化建议，指导开发人员如何改进代码或配置来优化系统性能；这些建议基于收集到的数据和分析结果
- **可视化和报告**：提供可视化界面和报告功能，通过图表、图形和详细报告，帮助开发人员直观分析性能数据，快速定位问题并做出优化决策

【为什么？】
为什么监控和剖析要分成两套工具？因为它们的**提问层级不同**：
- 监控回答："什么资源饱和了？哪个进程在吃？"（结果层）
- 剖析回答："**哪段代码、哪个方法、哪一跳调用导致了它？**"（原因层）

在性能测试的分工里，这是**递进的两步**：压测暴露"系统在 800 并发时 TPS 走平" → 监控定位"应用进程 CPU 饱和" → 剖析给出"耗时集中在订单序列化方法的反射调用上"。只有走到剖析这一步，优化建议才是**可执行的**（改哪一行代码、加哪个索引、调哪个参数）。所以课程把剖析放在压测工具、监控工具之后讲，顺序本身就是"造压力 → 看资源 → 找原因"的能力链。

【必须掌握】

| 剖析工作内容 | 做什么                  | 产出             |
| ------ | -------------------- | -------------- |
| 性能指标收集 | 采集 CPU、内存、网络延迟、磁盘 IO | 系统整体性能状况       |
| 热点分析   | 找出耗时/耗资源最多的代码、函数、模块  | 优化目标清单         |
| 优化建议   | 基于数据分析给出改进方向         | 可执行的优化项（代码/配置） |
| 可视化与报告 | 图表、图形、详细报告           | 便于沟通与决策的证据     |

【企业场景】
压测后你拿着三条证据去和开发沟通：JMeter 报告（TPS 从 2000 掉到 1200）、Grafana 看板（应用实例 CPU 95%、GC 时间占比 30%）、VisualVM/火焰图（热点集中在某段 JSON 序列化 + 一个没有缓存的循环查询）。**没有剖析数据时，你说的是"接口慢"；有了剖析数据，你说的是"改这里能提升 40%"** —— 后者的沟通效率和被采纳率完全不在一个量级。

【面试考察】
面试官："性能测试和性能剖析有什么区别？"

参考回答框架：
1. 层级差异：性能测试＝造压力、暴露问题（结果层）；性能剖析＝找原因（原因层）
2. 内容差异：剖析包含指标收集、热点分析、优化建议、可视化报告
3. 工具差异：压测用 JMeter/Locust，剖析用 JConsole/VisualVM/jstack/火焰图/链路追踪
4. 价值：剖析让优化建议变得可执行，是从"发现问题"到"解决问题"的桥梁

【易错点】

| 常见错误        | 正确理解                            |
| ----------- | ------------------------------- |
| 认为监控就是剖析    | 监控看资源与进程，剖析下钻到代码方法与调用链          |
| 只做压测不做剖析    | 报告只能写"慢"，写不出"为什么慢、怎么改"          |
| 把剖析工具当成开发专属 | 测开岗位的加分项正是"能用剖析数据给出优化建议"        |
| 只看 CPU 剖析   | 内存、IO、网络、链路延迟同样需要剖析（不同工具负责不同维度） |

【我的理解】
> （用自己的话回答：为什么说"剖析让优化建议变得可执行"？请按"压测 → 监控 → 剖析"的顺序，讲一遍你自己会怎么走完这条链。）

## 二、JVM 层剖析工具

### 知识点 2：JConsole

【课程原话/定义】
JConsole 是 **Java 提供的图形化的监控和管理工具**，用于监视 Java 虚拟机（JVM）的性能和资源使用情况。它可以实时显示 JVM 的**内存、线程、类加载、GC** 等信息，并提供 CPU 和内存的监测工具。JConsole 还支持**远程连接**到运行中的 Java 进程进行监控。

【为什么？】
JConsole 的价值在于"**零成本开局**"：它是 JDK 自带的（`jconsole`），不用装、不用改代码，能立刻看到 JVM 的六类关键信息。对性能测试来说，它解决的是"**CPU 高到底是业务代码在算，还是 GC 在抢**"这个分叉：
- 看 **内存/GC 曲线**：老年代是否持续上涨、Full GC 是否频繁且耗时长 → GC 是瓶颈
- 看 **线程**：线程数是否持续增长（线程泄漏）、是否有大量 BLOCKED（锁竞争）
- 看 **类加载**：类加载数量异常增长（可能每次请求都生成动态类）

在压测中最典型的用法：压测 30 分钟后，JConsole 上老年代曲线呈"锯齿不断抬高"的形态 → 判定存在**对象生命周期过长/内存泄漏**，这属于稳定性测试必须暴露的问题。

【必须掌握】

| 监视项    | 看什么                              | 性能含义                             |
| ------ | -------------------------------- | -------------------------------- |
| 内存     | 各代使用量、GC 次数与耗时                   | 频繁 Full GC → GC 成为瓶颈；持续上涨 → 泄漏风险 |
| 线程     | 线程数与状态（RUNNABLE/BLOCKED/WAITING） | 线程泄漏或锁竞争                         |
| 类加载    | 已加载类数量                           | 异常增长 → 动态类生成问题                   |
| CPU 占用 | JVM 进程 CPU 与 CPU 时间              | 与 top 的进程视图互相印证                  |
| 远程连接   | 通过 JMX 连接远程 Java 进程              | 压测环境（Linux 被压机）也能连               |

【企业场景】
大促压测时你在本机用 JConsole 远程连到压测环境的 Java 应用（JMX 端口 + 账号密码），一边加压一边看 GC。当发现"每分钟一次 Full GC、每次 1.2s"时，你的报告结论可以精确到："建议先调堆与 GC 参数（或排查大对象），因为 RT 的 P99 毛刺与 Full GC 时间高度吻合。" 这个结论比"服务端 CPU 高"有价值得多。

【面试考察】
面试官："压测时你怎么看 JVM？"

参考回答框架：
1. 第一层：JConsole（JDK 自带）看内存/GC/线程/类加载，判断 GC 是否为瓶颈
2. 第二层：VisualVM 做更深入的分析（CPU/内存剖析、Heap Dump）
3. 第三层：jstack 抓线程堆栈，定位死锁/阻塞/热点方法
4. 证据链：把 GC 时间与 RT 毛刺在时间轴上对齐，形成可执行建议

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 认为 CPU 高就一定是业务代码问题 | 也可能是 GC 抢 CPU，必须看 GC 曲线区分 |
| 只看堆使用量不设队列 | 单次采样无法判断趋势，必须看一段时间的曲线 |
| 忘记开 JMX 远程端口 | 压测环境在远程机器上时，需提前配置 JMX 参数 |
| 用 JConsole 做精细 CPU 剖析 | 它偏监控，深挖 CPU 热点要用 VisualVM/火焰图 |

【我的理解】
> （用自己的话回答：JConsole 上"老年代曲线锯齿式持续抬高"和"每 30 秒一次 Full GC 且耗时 1.5s"分别指向什么问题？两种情况分别该给开发什么建议？）

### 知识点 3：VisualVM

【课程原话/定义】
VisualVM 是 **Java 提供的多合一性能分析工具**。它可以用于分析 Java 应用程序的性能瓶颈，包括 **CPU 使用率、内存使用、线程状况**等。VisualVM 还支持**多种插件**，如 Profiler、Heap Dump Analyzer 等，以帮助开发人员更深入地分析和优化应用程序的性能。

> 【易错点提示】课程原文此处写作 "JVirusalVM"，是拼写错误，正确名称为 **VisualVM**（`jvisualvm`，JDK 1.6~8 自带，JDK 9+ 需单独下载）。学这套笔记时按正确名称记。

【为什么？】
VisualVM 是 JConsole 的"加强版"，关键差别在于它能做 **Profiler（采样/插桩）**：
- **CPU 剖析**：按方法统计耗时占比 → 直接得到"哪个方法最热"，这是从"哪个进程忙"到"哪段代码忙"的关键一跳
- **内存剖析**：按类统计对象分配与存活 → 找出"谁在不停产生对象"
- **Heap Dump 分析**：把堆快照导出来离线分析对象引用关系 → 定位内存泄漏的持有者

要提醒的是性能代价：**插桩式 Profiler 会显著影响性能**（可能让 RT 翻倍）。所以压测里的正确姿势是"**分两步走**"：先用采样方式（低开销）粗定位，再在可接受的范围内插桩细查；绝不要在正式压测出报告的那一轮开着插桩 Profiler。

【必须掌握】

| 能力 | 说明 | 使用注意 |
|------|------|----------|
| CPU 剖析 | 按方法统计 CPU 时间占比，找热点方法 | 插桩开销大，优先用采样模式 |
| 内存剖析 | 对象分配与存活统计 | 用于定位"谁在造对象" |
| Heap Dump 分析 | 堆快照与引用链分析 | 定位泄漏持有者（配合 OOM 场景） |
| 线程分析 | 线程状态与堆栈 | 与 jstack 互为印证 |
| 插件扩展 | Profiler、Heap Dump Analyzer 等 | 按需安装，注意版本兼容 |

【企业场景】
压测发现某接口在高并发下 RT 从 150ms 涨到 900ms，你用 VisualVM 的 CPU 采样看到某序列化方法与一个循环内的数据库查询占据大量时间，于是给出两条可执行建议：① 把循环查询改成批量查询（N+1 → 1 次）；② 换用更高效的序列化配置。开发改完后，你在**同一场景、同一数据量、同一并发**下复压，TPS 提升 38% —— 这份"优化前后对比数据"就是性能测试最有价值的交付物。

【面试考察】
面试官："VisualVM 能做什么？和 JConsole 的区别？"

参考回答框架：
1. VisualVM 是"多合一"工具：CPU/内存剖析、线程、Heap Dump、插件扩展
2. 与 JConsole 的区别：JConsole 偏监控（看曲线），VisualVM 偏剖析（看方法/对象热点）
3. 使用原则：插桩有性能开销，正式压测轮次不开；分两步（采样粗定位 → 必要插桩细查）
4. 落地价值：把"慢"翻译成"具体方法/具体对象"，形成可执行优化项

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 在正式压测时开着插桩 Profiler | 插桩会明显影响性能，导致数据失真 |
| 认为剖析结果就是最终结论 | 剖析定位的是"热点"，是否值得优化还要看业务价值与改动成本 |
| 混淆 VisualVM 与 JConsole | 一个偏剖析、一个偏监控，作用互补 |
| 忽略版本差异 | JDK 9 以后 JVisualVM 不再随 JDK 分发，需单独获取 |

【我的理解】
> （用自己的话回答：为什么"正式压测轮次不能开插桩 Profiler"？如果你在压测中发现 RT 涨了 6 倍，用 VisualVM 的下钻顺序应该是什么？）

### 知识点 4：jstack

【课程原话/定义】
JStack 是 **Java 提供的命令行工具**，用于生成 Java 应用程序中**线程的堆栈跟踪信息**。通过使用 JStack 命令，可以快速定位应用程序中的**死锁、死循环以及其它线程相关的问题**。JStack 的输出可以用于分析线程的状态，了解线程间的**调用关系和等待情况**。

【为什么？】
jstack 的价值在于它回答的是"**线程此刻卡在哪一行代码**"这个问题，而这是曲线和图表都回答不了的。压测里最典型的三个场景：
1. **CPU 高但吞吐不涨**：用 `jstack` 连续抓 3~5 次（间隔几秒），把多次堆栈里**重复出现的方法**找出来 → 那就是热点方法（这也是火焰图的原理：采样聚合）
2. **线程大量 BLOCKED / 请求卡住**：堆栈里会直接显示 `waiting to lock <0x...>` → 锁竞争/死锁定位
3. **死锁**：jstack 会在输出末尾直接打印 `Found one Java-level deadlock` 并给出互相等待的线程 → 一键定位

所以它和 top 是绝配：`top -H -p <pid>` 找到占用最高的线程 ID → 转成十六进制 → 在 jstack 输出里搜这个 ID → 定位到具体代码行。**这套"top -H + jstack"是 Java 性能定位的经典组合拳。**

【必须掌握】

| 场景 | 命令/做法 | 结论 |
|------|-----------|------|
| 导出全部线程堆栈 | `jstack <pid>` | 线程状态与调用栈快照 |
| 找 CPU 热点方法 | 多次 `jstack`（间隔数秒）对比重复出现的方法 | 反复出现在栈顶的方法即热点 |
| 定位高 CPU 线程 | `top -H -p <pid>` 拿线程 ID → 转 16 进制 → 在 jstack 输出里搜索 | 精确定位到代码行 |
| 查死锁 | `jstack <pid>`（输出末尾自动提示） | `Found one Java-level deadlock` |
| 查锁竞争 | 看 BLOCKED 线程的 `waiting to lock` | 定位争用的锁对象与持锁代码 |

【企业场景】
压测中接口响应突然从 200ms 飙到 5s，机器 CPU 只有 50%。你先 `jstack` 抓两次间隔 3 秒的堆栈，发现大量线程都停在同一个 `synchronized` 方法上等待锁 → 结论是**锁竞争导致请求排队**（而不是 CPU 不够）。优化建议很明确：缩小锁粒度或改为无锁/异步。**这类"CPU 不高但很慢"的问题，只有线程堆栈能解释。**

【面试考察】
面试官："线上 CPU 飙高 / 接口卡住，你怎么用 jstack 排查？"

参考回答框架：
1. CPU 飙高：`top -H -p <pid>` 找高占用线程 → 线程 ID 转十六进制 → `jstack <pid>` 中搜索该 nid → 定位到代码行
2. 多次采样：连续抓 3~5 次堆栈，取重复出现的栈顶方法作为热点（采样聚合思路）
3. 接口卡住：jstack 看 BLOCKED/WAITING 的分布 → 有 `waiting to lock` 就是锁竞争/死锁
4. 死锁：jstack 输出末尾会直接报告 Java-level deadlock
5. 组合：jstack 定"线程在等什么"，火焰图定"CPU 花在哪"

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 只抓一次堆栈 | 单次快照可能只是巧合，需要多次采样对比重复项 |
| 线程 ID 不转十六进制 | jstack 输出用的是 nid（十六进制），必须转换才能匹配 |
| 生产环境未用 `-F` 兜底 | 进程无响应时 `jstack -F` 可强制获取（会短暂暂停进程，谨慎使用） |
| 把 WAITING 当异常 | 线程池空闲线程正常处于 WAITING，要看数量与上下文判断 |

【我的理解】
> （用自己的话回答：为什么"多次 jstack 采样取重复方法"能找出 CPU 热点？这套思路和火焰图有什么关系？）

## 三、CPU 火焰图与分布式链路追踪

### 知识点 5：FlameGraph（火焰图）

【课程原话/定义】
FlameGraph 是一个**开源的性能剖析工具**，用于**可视化 CPU 剖析数据**。它通过生成**热图**来展示代码执行路径的**频率和耗时**。FlameGraph 通过图形化展示，帮助开发人员轻松地识别和理解系统中的性能瓶颈，并根据剖析数据调整代码和优化性能。

课程原图（未随消息发送）：

> 📷 【截图占位】FlameGraph 火焰图示例图

【为什么？】
火焰图的威力在于"**一眼看出热点**"：它把成千上万次采样堆栈按调用关系聚合，横轴宽度 = 该调用占用的 CPU 时间比例，因此**最宽的方块就是最热的代码**，而且沿着方形往上一层就是"谁调用了它"——这正好补齐了文本堆栈最难的部分（人眼很难从几百行堆栈里判断哪条路径占比最大）。它带来的实际改变是：
- 讨论性能问题从"我觉得可能是这里"变成"**看，就是这里，占 40%**"
- 优化前后可以对比火焰图，量化收益

需要注意的是：火焰图是**采样可视化**，它只对"CPU 消耗型"问题敏感；如果瓶颈在等待（锁、IO、网络），需要看的是内存火焰图、锁/off-CPU 火焰图或链路追踪（下一知识点）。

【必须掌握】

| 要素 | 含义 |
|------|------|
| 横轴 | 该调用占用的 CPU 时间比例（越宽越热） |
| 纵轴 | 调用栈深度（往下是被调用者，往上追调用者） |
| 颜色 | 通常仅用于区分（随机/按类型），不代表冷热 |
| 数据来源 | 采样（如 perf、JVM 采样器）聚合而成 |
| 适用 | CPU 消耗型瓶颈定位；配合内存/off-CPU 火焰图覆盖等待型问题 |

【企业场景】
你压测时发现服务端 CPU 打满，于是用火焰图工具生成一张图，发现某个日期格式化方法占了 35% 的 CPU（因为每次请求都新建 `SimpleDateFormat` 且没缓存）。报告里附上火焰图截图 + 优化前后对比（CPU 下降、TPS 提升），开发无需争辩就直接排期修复——**火焰图是让性能问题"无法被讨论掉"的证据。**

【面试考察】
面试官："火焰图怎么读？它能解决什么问题？"

参考回答框架：
1. 读法：横轴是 CPU 时间占比（越宽越热），纵轴是调用栈深度（往上找调用者）
2. 原理：对多次采样堆栈做聚合统计（采样，不是插桩）
3. 用途：快速定位 CPU 热点；对比优化前后的收益
4. 边界：只对 CPU 型问题敏感，等待型问题要用内存/off-CPU 火焰图或链路追踪

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 以为颜色代表冷热 | 颜色一般只做区分，热的判断依据是**方块宽度** |
| 用火焰图排查 IO/锁等待问题 | 火焰图擅长 CPU 型问题；等待型问题需 off-CPU/链路追踪 |
| 只看最宽的一块 | 还要沿栈向上看调用者，判断是"定位错方法"还是"上游调用次数过多" |
| 采样时间过短 | 采样时长不足会导致统计不稳定，结论不可信 |

【我的理解】
> （用自己的话回答：火焰图里"最宽的方块"和"最深的调用栈"分别告诉你什么？为什么说火焰图是"让性能问题无法被讨论掉"的证据？）

### 知识点 6：SkyWalking

【课程原话/定义】
SkyWalking 是一个**开源的分布式跟踪系统**，用于监控和诊断分布式系统的性能问题。它能够对分布式应用程序的**服务间通信进行跟踪和诊断**，包括**链路追踪、服务拓扑以及性能指标的收集和可视化**。SkyWalking 通过分布式追踪和监控，帮助开发人员快速定位和解决分布式系统的性能问题。

课程原图（未随消息发送）：

> 📷 【截图占位】SkyWalking 服务拓扑/链路图示例

【为什么？】
在微服务架构里，一个"下单"请求可能要经过网关 → 订单服务 → 商品服务 → 库存服务 → 支付服务，**任何一跳慢，整条链路都慢**。而单机工具（JConsole/jstack/火焰图）只能看到"本进程在做什么"，看不到"我调用的下游有多慢"。SkyWalking 正是补上这块：
- **链路追踪（Trace）**：把一次请求在各服务间的调用串起来，显示每一跳的耗时 → 直接回答"慢在哪一跳"
- **服务拓扑（Topology）**：谁调用谁、谁依赖谁 → 压测时可以按拓扑规划场景范围
- **性能指标 + 可视化**：服务/实例/端点的 RT、错误率、吞吐趋势

它在性能测试中的意义是"**把瓶颈定位从单机升级到全链路**"：当压测出现"整体慢、单机都不忙"时，链路追踪往往是唯一能给出答案的工具。

【必须掌握】

| 能力       | 内容                  | 压测中的作用       |
| -------- | ------------------- | ------------ |
| 链路追踪     | 跨服务的调用链与每一跳耗时       | 定位"慢在哪一跳"    |
| 服务拓扑     | 服务间依赖关系图            | 规划压测范围与影响面分析 |
| 指标收集与可视化 | 服务/实例/端点的 RT、错误率、吞吐 | 与压测曲线对齐定位瓶颈  |
| 诊断       | 异常/慢调用下钻            | 输出可执行的优化目标   |

【企业场景】
全链路压测时，压测流量从网关打到 5 个微服务。压测结果"下单 TP99 = 2.5s"，单看应用服务 CPU 都不到 60%。你打开 SkyWalking 的链路视图，发现 2.5s 里有 1.8s 花在"库存服务 → Redis"这一跳（大量热 key 排队），于是优化方向明确：缓存分片/本地缓存/减少单 key 依赖。**没有链路追踪，这个结论只能靠"猜"和"开发的经验"。**

【面试考察】
面试官："微服务架构下怎么定位性能瓶颈？"

参考回答框架：
1. 先讲难点：一次请求跨多个服务，单机工具无法回答"哪一跳慢"
2. 讲工具：SkyWalking（链路追踪 + 服务拓扑 + 指标可视化）/ Zipkin 收集链路数据
3. 讲流程：压测暴露整体慢 → 链路追踪定位到具体一跳 → 该服务的单机工具（jstack/火焰图/DB 监控）继续下钻
4. 讲价值：把"整体慢"拆成"某一跳慢"，让优化目标可执行

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 只用 SkyWalking 不用单机工具 | 链路给出"哪一跳"，单机工具才能给出"为什么这一跳慢" |
| 忽略埋点/探针的接入成本 | 需接入 Agent 并确认采样率，否则数据不全或开销过大 |
| 认为拓扑图只是展示 | 拓扑决定压测范围与依赖影响面，是场景设计的输入 |

【我的理解】
> （用自己的话回答：为什么微服务架构下"单机工具"不够用？请描述一次"链路追踪 → 单机工具"的下钻流程。）

### 知识点 7：Zipkin

【课程原话/定义】
Zipkin 也是一个**开源的分布式追踪系统**，用于收集、存储和可视化分布式系统之间的**请求路径和延迟情况**。它通过追踪请求在不同服务间的传递情况，帮助开发人员了解分布式系统的性能瓶颈并进行故障排查和性能优化。

课程原图（未随消息发送）：

> 📷 【截图占位】Zipkin 链路查询界面示例图

【为什么？】
Zipkin 与 SkyWalking 定位相近，但侧重不同：Zipkin 是**更纯粹、更轻量的链路数据收集与查询系统**（由 Twitter 开源，是分布式追踪领域的早期标准，很多语言的客户端库都支持）。它的核心概念值得记住，因为它们是链路追踪的通用语言：
- **Trace（一次完整请求的调用树）** 与 **Span（一次调用单元）**：一个 Trace 由多个 Span 组成
- **耗时分布**：每个 Span 的 duration，用来定位慢在哪个环节
- **上下文传播**：通过请求头（如 traceId/spanId）把链路串起来，所以能看到跨进程的完整链路

选型上可以这样记：**要"开箱即用 + 服务拓扑 + 指标看板"选 SkyWalking；要"轻量 + 语言生态广 + 与现有链路标准（OpenTracing/OpenTelemetry）对齐"选 Zipkin。**

【必须掌握】

| 概念 | 说明 |
|------|------|
| Trace | 一次完整请求的调用链路 |
| Span | 链路中的一个调用单元（含开始时间与 duration） |
| 上下文传播 | 通过 traceId / spanId 在服务间传递，串起跨进程链路 |
| 可视化查询 | 按服务/时间/耗时查询链路，定位慢调用 |
| 与 SkyWalking 差异 | Zipkin 轻量、生态广；SkyWalking 功能更全（拓扑 + 指标 + 诊断） |

【企业场景】
你负责的压测环境里已经接了 Zipkin（因为团队用 OpenTelemetry 上报）。压测结束你按"耗时 > 1s"筛出慢链路，导出一批 Trace 做归因，发现 70% 的慢链路都包含同一次下游调用——这就把"偶发变慢"变成了"可复现的专项问题"，后续可以针对该下游做单接口压测与专项优化。

【面试考察】
面试官："SkyWalking 和 Zipkin 有什么区别？"

参考回答框架：
1. 定位相同：都是分布式追踪系统，收集/存储/可视化请求路径与延迟
2. 差异：SkyWalking 功能更全（自动探针、服务拓扑、指标与诊断）；Zipkin 更轻量、语言生态广、与链路标准对齐
3. 共同概念：Trace / Span / 上下文传播，是链路追踪的通用语言
4. 选型：按团队既有技术栈、接入成本、是否需要拓扑与指标下钻来定

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 把 Trace 与 Span 混用 | 一个 Trace 由多个 Span 组成，Span 是单个调用单元 |
| 认为采样率 100% 最好 | 高采样率带来存储与性能开销，需按场景权衡（压测期可临时提高） |
| 忽略埋点/透传 | 上下文不传递（如异步线程、MQ）会造成链路断裂，需专门处理 |

【我的理解】
> （用自己的话回答：Trace 和 Span 的关系是什么？为什么"上下文传播"是链路追踪能跨进程拼接的关键？）

## 四、三类工具的分工（本章小结）

```mermaid
flowchart LR
    A["① 压测工具<br/>JMeter / Locust / AB<br/>造压力：TPS / RT / 错误率"] --> B["② 监控工具<br/>top / vmstat / nmon<br/>Prometheus + Grafana<br/>看资源：CPU / 内存 / IO / 网络"]
    B --> C["③ 剖析工具<br/>JConsole / VisualVM / jstack<br/>FlameGraph / SkyWalking / Zipkin<br/>找原因：方法 / 代码 / 调用链"]
    C --> D["④ 优化与复压<br/>量化收益：TPS↑ RT↓<br/>拐点右移"]
    D --> A

    B -.定位到"哪个节点".-> C
    C -.给出"改哪里".-> D
```

> 一句话总结：**压测负责制造问题，监控负责缩小范围，剖析负责给出结论。** 三者缺一，压测就只能停留在"系统有点慢"。
