## 一、性能压测工具是什么

### 知识点 1：性能压测工具的定义与核心功能

【课程原话/定义】
性能压测工具是用于**模拟大量用户访问、负载和压力条件**的软件工具，以评估系统、应用程序或服务在高负载条件下的性能表现和稳定性。

这些工具通常用于软件开发、测试、部署前的准备以及生产环境中的性能监测和优化。性能压测工具的主要功能包括：**模拟用户行为、生成大量的请求、测量响应时间和系统资源利用率**等。

【为什么？】
为什么性能测试必须依赖工具，而不能手写脚本"发一发请求"？因为压测的本质是**可控地复制真实流量**，这要求三个能力同时具备：
1. **并发能力**：同时发起成千上万个请求（手写脚本用 threads + requests 能勉强做到，但难以维护和扩展）
2. **可控能力**：能精确控制加压曲线（阶梯加压、恒定并发、按 RPS 匀速）
3. **度量能力**：能统计 RT 平均值/分位值、TPS、错误率并出报告

工具的价值不在于"发请求"，而在于**让压力可复现、让数据可比较**。这也解释了一个常见误区：用 Postman 单发一次请求看耗时不是性能测试（见 [[../../接口测试/L1-接口协议与接口测试/Ch07-接口测试价值与体系|接口测试 Ch07]] 的【易错点】）——它没有并发，也产生不了曲线。

【必须掌握】

| 核心功能 | 具体表现 | 交付物 |
|----------|----------|--------|
| 模拟用户行为 | 线程组/VU、思考时间、参数化（不同用户不同数据） | 可复现的压测场景 |
| 生成大量请求 | 并发加压、阶梯加压、持续加压、分布式加压 | 加压曲线 |
| 测量响应时间 | 平均 RT、TP90/95/99、错误率 | 数据表与图表 |
| 测量资源利用率 | 结合监控工具采集服务端资源 | 瓶颈定位证据 |

【企业场景】
你接到"大促前压一遍订单链路"的任务。第一步就是选工具并把场景脚本化：把"登录 → 浏览商品 → 加购 → 下单"录成脚本，参数化用户数据（不同账号、不同商品），设置阶梯加压（500 → 1000 → 2000 → 5000 并发，每档跑 10 分钟），并在每一档记录 TPS/RT/CPU。**选错工具或不做参数化，压出来的数据不可信**——所有下单都用同一个账号，会被风控拦截或被缓存放大，结论直接作废。

【面试考察】
面试官："性能压测工具主要干什么？"

参考回答框架：
1. 定义：模拟大量用户访问与负载，评估系统在高负载下的性能与稳定性
2. 三大功能：模拟用户行为、生成请求、测量 RT 与资源利用率
3. 价值：让压力可复现、数据可比较（可复现性正是"手写脚本压一次"做不到的）
4. 落地：配合监控工具使用，才能把"慢"变成"哪里慢"

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 用单次请求的耗时当成性能测试 | 没有并发就没有压力，单次请求只能算接口调试 |
| 不参数化、全部用同一账号/同一数据 | 缓存与风控会污染结果，压测数据不可信 |
| 只加压不做监控 | 拿不到资源数据，无法定位瓶颈，只能报一个"慢" |
| 认为工具有优劣万能解 | 不同工具适合不同场景（协议、脚本语言、分布式能力），按需选 |

【我的理解】
> （用自己的话回答：为什么说"工具的价值是让压力可复现"？如果一次压测无法复现，会带来什么后果？）

## 二、行业流行压测工具逐个介绍

### 知识点 2：Apache AB（Apache Benchmark）

【课程原话/定义】
Apache AB（Apache Benchmark）是一个**开源的命令行工具**，用于进行基准测试和性能测试。它是 Apache HTTP 服务器项目的一部分，旨在评估服务器的性能和稳定性。

- 特点：简单易用，使用命令行界面，轻量级，快速高效
- 使用方法：用户可以通过命令行参数指定要测试的 URL、请求数量、并发用户数等。Apache AB 会输出每个请求的响应时间、吞吐量等性能指标，并提供汇总报告
- 参数配置：
  - 并发用户数：可以通过 `-c` 参数指定并发用户数
  - 请求数量：可以通过 `-n` 参数指定要发送的请求数量
  - 连接超时时间：可以通过 `-t` 参数指定每个连接的超时时间

【为什么？】
AB 的定位是"**快速基准测试**"，不是完整的性能测试方案。它的价值在于 30 秒内给出一个数量级判断（"这个接口单机大概能扛多少"），适合开发自测和接口基准对比。但它的局限也很明显：
- 只能压**单个 URL**，做不了"登录 → 下单"这种带上下文的多步骤业务流程
- 没有参数化（不能用不同用户数据）、没有断言、没有 GUI 报告
- 不支持分布式，单机压力有上限

所以它是"体检仪"而不是"医疗设备"：快速、便宜，但结论只能用于早期判断。选型时记住一句话——**能用一条命令回答的问题，别上 JMeter；要做业务链路和能力验证，AB 不够用。**

【必须掌握】

| 项目 | 内容 |
|------|------|
| 类型 | 开源、命令行、轻量级 |
| 归属 | Apache HTTP 服务器项目的一部分 |
| 特点 | 简单易用、快速高效 |
| 核心参数 | `-n` 请求总数、`-c` 并发用户数、`-t` 连接超时 |
| 输出 | 每个请求的响应时间、吞吐量、汇总报告 |
| 适用 | 单 URL 基准测试、接口性能快速摸底 |
| 局限 | 单 URL、无参数化/断言、不支持分布式与业务流程 |

【企业场景】
你在开发提交代码后想做一次快速回归：同一个接口改动前后各跑一次 `ab -n 10000 -c 200 http://host/api/detail`，对比 Requests per second 和 Time per request（mean）。这属于"开发自测级的性能对比"，用它证明"这次改动没有让接口变慢"就足够了——但绝不能拿它的结果去回答"大促能不能扛住"，那需要 JMeter 做业务链路压测。

【面试考察】
面试官："你用过哪些压测工具？AB 和 JMeter 什么区别？"

参考回答框架：
1. AB：命令行、单 URL、轻量快速，适合基准测试（`-n` 总数、`-c` 并发、`-t` 超时）
2. JMeter：图形化、多协议、支持参数化/断言/分布式，适合完整压测场景
3. 差异总结：AB 回答"这个接口有多快"，JMeter 回答"这条业务链路在多少并发下会到拐点"
4. 选型逻辑：按"要不要业务流程 / 要不要参数化 / 要不要分布式"来选

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 用 AB 结果作为容量结论 | AB 只压单 URL、无业务上下文，容量结论需 JMeter + 监控验证 |
| 忘记 `-n` 与 `-c` 的配合关系 | `-n` 是总请求数、`-c` 是并发数，总数必须 ≥ 并发数，否则压不满 |
| 认为 AB 能测复杂业务 | AB 不支持多步骤、带登录态的流程 |

【我的理解】
> （用自己的话回答：AB 的三个参数 `-n`、`-c`、`-t` 分别控制什么？如果我把 `-n 100`、`-c 200`，会发生什么？）

### 知识点 3：Apache JMeter

【课程原话/定义】
Apache JMeter 是一个**开源的 Java 框架**，可用于进行**负载测试、性能测试和功能测试**。它支持多种协议，如 HTTP、HTTPS、FTP、JDBC 等，并提供了丰富的图表和报告功能。

- 特点：开源、支持多种协议、可扩展性强、功能丰富
- 使用场景：适用于各种应用类型的负载测试，如 Web 应用、Web 服务、数据库等
- 支持协议：HTTP、HTTPS、FTP、JDBC、JMS、SOAP、SMTP、TCP 等
- 功能：提供图形化界面和可视化报告、支持分布式测试、支持参数化和数据驱动等

【为什么？】
JMeter 为什么能成为行业默认选择？因为它同时满足了三类需求，而其他工具通常只满足其中一两类：
- **对测试人员**：图形化界面 + 元件化设计，不用写代码就能搭出业务场景（HTTP 请求、断言、定时器、监听器）
- **对团队**：开源免费、协议覆盖广（HTTP/JDBC/JMS/TCP/SOAP…），从 Web 到数据库到消息队列一套工具搞定
- **对大规模压测**：支持分布式压测与参数化/数据驱动，能把并发从几百推到万级

代价是它的学习曲线偏陡（元件多、执行顺序有讲究），这也是后续课程要重点解决的部分。

【必须掌握】

| 项目   | 内容                                      |
| ---- | --------------------------------------- |
| 类型   | 开源 Java 框架                              |
| 用途   | 负载测试、性能测试、功能测试                          |
| 支持协议 | HTTP、HTTPS、FTP、JDBC、JMS、SOAP、SMTP、TCP 等 |
| 核心能力 | 图形化界面、可视化报告、分布式测试、参数化与数据驱动              |
| 适用   | Web 应用、Web 服务、数据库等各类应用的负载测试             |

【企业场景】
你负责大促压测，用 JMeter 搭了一套脚本：线程组（并发模型）+ HTTP 请求（业务接口）+ 参数化（CSV 读入几千个账号与商品）+ 断言（校验业务码而不只是 200）+ 定时器（模拟思考时间）+ 聚合报告（TPS/RT/错误率）。这套脚本可复现、可评审、可进 CI——**这正是 JMeter 相比 AB 的质变：从"测一个接口"升级为"测一条业务"。**

【面试考察】
面试官："为什么公司选 JMeter 做压测？"

参考回答框架：
1. 开源免费、社区活跃，成本可控
2. 协议覆盖广（HTTP/JDBC/JMS/TCP…），一套工具覆盖多种被测对象
3. 图形化 + 元件化，方便搭业务流程场景；支持参数化与数据驱动
4. 支持分布式压测，可扩展到大并发
5. 报告与监听器丰富，配合监控工具形成完整的性能分析闭环

【易错点】

| 常见错误               | 正确理解                                    |
| ------------------ | --------------------------------------- |
| 认为 JMeter 只能压 HTTP | 还支持 JDBC/JMS/TCP/SOAP/邮件等，可以做数据库与消息队列压测 |
| 认为图形化界面等于简单        | 元件多、作用域与执行顺序有讲究，脚本结构错了结果就错了             |
| 忽略参数化与断言           | 不做参数化数据会被缓存/风控污染；不做业务断言会把"业务失败"当成功      |

【我的理解】
> （用自己的话回答：JMeter 相比 AB，多出来的最关键的三个能力是什么？为什么这三个能力让它适合做"业务链路压测"？）

### 知识点 4：nGrinder

【课程原话/定义】
nGrinder 是一个**开源的负载测试工具**，用于测试和评估应用程序、Web 服务和服务器的性能。它提供了一个简单而强大的平台，以模拟大量的并发用户，并测量系统在不同负载条件下的性能指标。

- **易于使用**：提供了直观的用户界面，可以帮助用户快速设置测试参数和运行测试
- **分布式测试**：支持分布式测试，可以通过配置多个测试代理机器来模拟大规模的并发用户访问
- **脚本录制与回放**：可以从 Web 浏览器中录制用户行为，并回放这些脚本以模拟真实用户的操作
- **实时监控与报告**：提供实时监控和性能指标报告，方便用户了解测试过程和结果

【为什么？】
nGrinder 的差异点在于**"平台化 + 分布式"**：它由 controller（控制台）与 agent（压测代理）组成，天生是"一台控制台指挥多台施压机"的架构。这带来的实际好处是：
- 并发规模上限高（不是靠单机堆线程，而是横向加 agent）
- 脚本在 Web 界面里管理（Groovy/Jython），团队协作与复用的成本低
- 实时监控面板省去了单独搭监控的成本

代价是部署与维护比 JMeter 重（要维护 controller + agent 集群）。所以它的典型使用场景是"**团队级、常态化的大规模压测平台**"，而不是个人临时压一次。

【必须掌握】

| 项目 | 内容 |
|------|------|
| 类型 | 开源负载测试工具／平台 |
| 架构 | Controller（控制台）+ 多个 Agent（压测代理）→ 分布式 |
| 亮点 | 直观 UI、分布式压测、脚本录制与回放、实时监控与报告 |
| 脚本 | Groovy / Jython，在 Web 界面编写与管理 |
| 适用 | 团队级大规模并发压测、常态化压测平台 |

【企业场景】
你们团队要把压测常态化（每次发版前自动压一轮），于是搭了 nGrinder：controller 部署在一台机器上，agent 部署在 5 台施压机上；每次发版，CI 调用 nGrinder 跑同一套脚本，产出可对比的报告。**团队级的价值在于"口径统一 + 可对比"**——同一套脚本、同一个平台，才能把"这次比上次慢了 15%"变成可靠的结论。

【面试考察】
面试官："nGrinder 和 JMeter 的区别？"

参考回答框架：
1. nGrinder：平台化（controller + agent），分布式能力强，Web UI 管理脚本，自带实时监控与报告
2. JMeter：单机工具为主（分布式需自己配置），图形化客户端，元件化脚本，社区生态最广
3. 选型：要"团队平台、规模化、脚本统一管理"选 nGrinder；要"灵活、协议广、生态多、上手快"选 JMeter
4. 共同点：都支持参数化与分布式，都可以配合监控工具使用

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 认为分布式是 nGrinder 独有 | JMeter 也支持分布式，只是需要自己配置 controller/worker |
| 忽略 agent 机器本身的资源瓶颈 | 分布式压测时 agent 也会成为瓶颈，需单独监控 |
| 用录制脚本直接压测 | 录制脚本通常含冗余请求与固定数据，必须参数化与精简后再压 |

【我的理解】
> （用自己的话回答：nGrinder 的 controller + agent 架构解决了压测里的什么问题？为什么"团队级压测平台"比"个人跑脚本"更有价值？）

### 知识点 5：Locust

【课程原话/定义】
Locust 是一个**基于 Python 的开源负载测试工具**。它使用 Python 代码编写测试脚本，支持 HTTP 和 WebSocket 协议，并提供了可扩展的监控和报告功能。

- 特点：开源、基于 Python、简单易用、可扩展性强
- 使用场景：适用于简单的负载测试场景，如 Web 应用、API 等
- 支持协议：HTTP、WebSockets 等
- 功能：使用 Python 代码编写测试脚本、提供实时监控和报告功能

【为什么？】
Locust 的定位是"**代码即脚本**"：压测场景用 Python 类 + `@task` 装饰器描述，加压力时通过 Web UI 动态调整用户数，并且它的事件模型让"用户行为"可以用代码自由编排（带权重的任务、嵌套流程、自定义断言）。对测试开发来说，这带来两个真实优势：
- **复用已有能力**：Riley 已经会写 Python/Pytest，Locust 的学习成本几乎为 0，而 JMeter 的元件体系需要新学一套概念
- **和自动化框架打通**：可以用同一套接口封装（requests 层）同时支撑功能自动化与压测，维护成本更低

局限也很现实：协议支持不如 JMeter 广、生态与资料相对少、大规模分布式压测的成熟度不如 nGrinder/JMeter。

【必须掌握】

| 项目   | 内容                                      |
| ---- | --------------------------------------- |
| 类型   | 开源、基于 Python 的负载测试工具                    |
| 脚本方式 | 用 Python 代码编写测试脚本（HttpUser / task / 权重） |
| 支持协议 | HTTP、WebSockets 等                       |
| 亮点   | 简单易用、可扩展性强（代码级灵活编排）、实时监控与报告             |
| 适用   | Web 应用、API 等较简单或需高度自定义的负载场景             |

【企业场景】
你们的接口自动化框架已经用 requests 封装好了"登录 → 查询 → 下单"的接口层。要压测时，你直接在 Locust 里 import 这些封装方法，用 `@task(3)`、`@task(1)` 描述用户行为比例（3:1 的比例比 JMeter 里配 N 个线程组更直观），压完在同一套代码里维护。**这就是"测试开发"相比"会用工具的人"的优势：把压测变成工程能力的一部分。**

【面试考察】
面试官："Locust 有什么特点？你为什么选它？"

参考回答框架：
1. 定义：基于 Python 的开源负载测试工具，支持 HTTP/WebSocket
2. 特点：脚本用 Python 编写（代码级灵活）、实时 Web UI 调压、可扩展性强
3. 选型理由：团队技术栈是 Python 时可以复用现有接口封装与断言逻辑，学习成本低
4. 局限与权衡：协议覆盖与生态不如 JMeter；大规模分布式不如 nGrinder/JMeter 成熟

【易错点】

| 常见错误                      | 正确理解                                           |
| ------------------------- | ---------------------------------------------- |
| 认为 Locust 只能做简单场景         | 简单是因为上手快；通过代码可以编排带权重、嵌套、条件分支的复杂场景              |
| 认为 Python 写脚本一定比 JMeter 慢 | 单机压力量级主要由起压机资源与实现方式决定，可通过分布式扩展                 |
| 忽略 Python GIL 的影响         | 单进程多线程受 GIL 限制，Locust 通过 gevent 协程 + 多进程提高加压能力 |

【我的理解】
> （用自己的话回答：对已经有 Python + Pytest 基础的测试开发来说，Locust 的最大优势是什么？它的短板在什么场景下会暴露？）

### 知识点 6：LoadRunner

【课程原话/定义】
LoadRunner 是一款广泛使用的性能测试工具，由 **Micro Focus** 推出。它被用于测试和评估各种应用程序、Web 服务和服务器的性能，以确保系统在不同负载下能够正常工作。

- 特点：商业工具、功能丰富、支持多种协议
- 使用场景：适用于需要全面测试各种应用的性能，如 Web 应用、移动应用等
- 支持协议：HTTP、WebSockets、FTP、数据库等多种协议
- 功能：提供强大的监控、分析和报告功能

【为什么？】
LoadRunner 代表了另一条路线：**商业级、全流程、强监控**。它的核心资产不是"能发请求"，而是：
- **脚本录制与协议覆盖极广**（尤其是一些传统企业系统、C/S 架构、专有协议）
- **强大的监控与分析**（自带系统资源监控、诊断模块，无需额外搭一套监控栈）
- **厂商支持与标准化流程**（大企业/金融/国企常以它作为验收工具）

代价是**授权费用高昂**（按协议数与并发数计费），以及脚本体系较重、上手慢。所以在互联网公司里它出现的频率远低于 JMeter，但在银行、保险、传统行业的性能验收场景里仍然是标配。面试时的正确答案不是"哪个更好"，而是"**按公司技术栈、协议要求与预算选型**"。

【必须掌握】

| 项目 | 内容 |
|------|------|
| 类型 | 商业性能测试工具（Micro Focus 出品） |
| 特点 | 功能丰富、支持多种协议、监控/分析/报告能力强 |
| 支持协议 | HTTP、WebSockets、FTP、数据库等多种协议 |
| 适用 | 需要全面测试各类应用（Web、移动应用等）的性能 |
| 成本 | 商业授权，费用较高 |
| 典型行业 | 金融、保险、传统企业系统，以及需要厂商支持的验收场景 |

【企业场景】
你去一家银行面试，性能测试流程里用的是 LoadRunner：用例由专门团队用 VuGen 录制脚本，Controller 调度施压，Analysis 出报告。面试官问你"会不会 LoadRunner"，诚实且加分的答法是："我用 JMeter 做过完整的压测与瓶颈定位，LoadRunner 的核心概念（脚本录制、场景设计、监控分析）是相通的，我能迁移过去；如果需要，我可以说明两者的对应关系。"**不装会，也不贬低工具，是这类问题的正解。**

【面试考察】
面试官："JMeter 和 LoadRunner 有什么区别？"

参考回答框架：
1. 性质差异：JMeter 开源免费，LoadRunner 商业授权（成本高）
2. 能力差异：LoadRunner 协议覆盖与监控分析更全面、有厂商支持；JMeter 生态广、灵活、上手快
3. 使用现状：互联网公司多选 JMeter/Locust，传统行业与金融场景常见 LoadRunner
4. 迁移能力：核心概念（脚本、场景、加压、监控、分析）相通，工具只是实现手段
5. 加分：按"协议要求 + 预算 + 团队技术栈 + 是否需要厂商支持"给出选型逻辑

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 认为商业工具一定更强 | 能力上更全面，但成本、灵活性、生态上未必适合互联网团队 |
| 面试时硬说"我精通 LoadRunner" | 无真实使用经验会被追问答不上来；应按"概念相通 + 可迁移"诚实回答 |
| 认为所有公司都用 JMeter | 金融/传统企业常见 LoadRunner，按公司和岗位要求准备 |

【我的理解】
> （用自己的话回答：如果面试官问你"我们没有 JMeter，只有 LoadRunner，你能上手吗"，你会怎么回答？请把 JMeter 的元件和 LoadRunner 的组件做一次对应。）

### 知识点 7：为什么用 JMeter 做性能压测（六大优点）

【课程原话/定义】
使用 JMeter 做性能压测的优点：
1. **开源自由**：JMeter 是一款开源工具，可以免费获取和使用。JMeter 开放的社区，提供问题支持
2. **跨平台支持**：可以运行在多种操作系统上，包括 Windows、Linux 和 Mac OS 等
3. **高可扩展性**：支持分布式压测，可以在多台机器上部署并发执行测试。这样可以模拟大规模用户同时访问系统，并更加真实地评估系统的性能
4. **多协议支持**：支持各种协议，包括 HTTP、HTTPS、FTP、SOAP、JDBC 等。适用于测试各种应用程序和服务，无论是基于 Web 的应用还是基于移动设备的应用
5. **灵活的脚本编写**：可以编写灵活的测试脚本，以模拟和排查不同用户行为和负载情况。它支持参数化和变量设置，可以模拟不同的用户数据和行为
6. **强大的报告和分析**：提供了详细的性能指标和报告，可以监测和分析测试结果。用户可以查看请求响应时间、吞吐量、错误率等指标，帮助评估系统的性能并查找潜在的性能瓶颈

总的来说，JMeter 是一个功能强大、灵活易用的性能测试工具，具有开源自由、跨平台支持、高可扩展性、多协议支持、灵活的脚本编写和强大的报告和分析等优点。这些原因使得 JMeter 成为很多开发团队进行性能测试的首选工具。

【为什么？】
为什么这六条优点值得记住，而不是当成营销文案？因为它们**正好对应面试官的三类追问**：
- "为什么选它？" → 开源自由 + 多协议 + 跨平台（成本与覆盖面）
- "能压多大？" → 高可扩展性（分布式压测，横向加机器）
- "结果怎么用？" → 强大的报告与分析 + 灵活脚本（参数化/数据驱动 → 数据可信，报告 → 可交付）

换言之，这六条是"**选型理由的结构化答案**"。能按"成本 → 覆盖面 → 规模 → 结果可用性"的顺序讲出来，就比单纯罗列优点更像工程判断。

【必须掌握】

| 优点       | 具体内容                               | 对应解决的痛点                |
| -------- | ---------------------------------- | ---------------------- |
| 开源自由     | 免费获取使用，社区提供问题支持                    | 成本可控、资料充足              |
| 跨平台支持    | Windows / Linux / Mac OS           | 起压机可以选便宜/合适的 Linux 机器  |
| 高可扩展性    | 支持分布式压测，多机并发施压                     | 单机压不出万级并发              |
| 多协议支持    | HTTP / HTTPS / FTP / SOAP / JDBC 等 | 一套工具覆盖 Web、数据库、消息等多种对象 |
| 灵活的脚本编写  | 支持参数化、变量设置，模拟不同用户行为                | 数据污染、风控、缓存导致结论失真       |
| 强大的报告和分析 | RT / 吞吐量 / 错误率等详细指标与报告             | 结论可交付、可对比、可定位瓶颈        |

【企业场景】
你要在团队里推动"统一压测工具"，申请理由不是"JMeter 好用"，而是按上表逐条对齐：不用买授权（省钱）、可以用 Linux 起压机（资源便宜）、能上分布式（大促万级并发的需求）、能压数据库和消息队列（我们的被测对象不只有 HTTP）、能参数化（避免风控与缓存污染）、报告可直接交付业务方（沟通成本低）。**这套表述方式，就是性能测试岗位"工程化沟通能力"的体现。**

【面试考察】
面试官："说说你们为什么选 JMeter？"

参考回答框架：
1. 成本与生态：开源免费、社区活跃，资料与插件丰富
2. 覆盖面：跨平台 + 多协议，一套工具覆盖多种被测对象
3. 规模：分布式压测满足大并发需求
4. 数据可信：参数化与变量设置，避免固定数据污染结论
5. 结果可用：报告与监听器丰富，能直接支撑瓶颈定位与结论交付

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 只说"开源免费" | 开源是入口，多协议 + 分布式 + 报告能力才是它能做完整压测的原因 |
| 认为开源等于没有支持 | 社区、文档、插件生态本身就是支持体系，但复杂问题仍需团队自建能力 |
| 忽略"起压机也要成本" | 分布式压测需要多台施压机，机器与维护成本要提前规划 |

【我的理解】
> （用自己的话回答：把 JMeter 的六条优点，按"成本 → 覆盖面 → 规模 → 结果可用性"重新组织成一段 1 分钟的面试回答，你能说下来吗？）
> 
> **我们选择 JMeter，主要是因为它比较适合做接口和服务端的性能测试。**
> 
> 第一，它支持 HTTP、HTTPS 等常见协议，做 Web 接口压测比较方便。
> 
> 第二，它可以比较方便地模拟不同并发用户，通过线程数、Ramp-up 等参数控制压力，并且能够观察 TPS、响应时间、错误率等性能指标。
> 
> 第三，它支持参数化、关联、断言、前置处理器和后置处理器，可以把一个真实的业务流程串起来，而不是只能重复发送一个固定请求。
> 
> 另外，JMeter 本身是开源的，插件和资料比较丰富，也比较容易和 CI/CD、命令行以及其他监控工具结合。
> 
> **所以对于我们这种以 HTTP 接口为主、需要模拟并发用户并观察 TPS 和 RT 的性能测试场景，JMeter 的学习和使用成本比较合适。**
>

## 三、压测工具选型对比（本章小结表）

| 工具 | 类型 | 脚本方式 | 协议覆盖 | 分布式 | 适用场景 |
|------|------|----------|----------|--------|----------|
| Apache AB | 开源命令行 | 参数化命令行（`-n`/`-c`/`-t`） | 仅 HTTP | 不支持 | 单接口基准测试、快速摸底 |
| Apache JMeter | 开源（Java） | 图形化元件 + 参数化 | 广（HTTP/JDBC/JMS/TCP/SOAP…） | 支持 | 业务链路压测、企业默认选择 |
| nGrinder | 开源平台 | Web 界面编写（Groovy/Jython） | 以 HTTP 为主 | 强（controller + agent） | 团队级规模化压测平台 |
| Locust | 开源（Python） | Python 代码 | HTTP / WebSocket | 支持（多进程 + 协程） | Python 团队、需高度自定义的场景 |
| LoadRunner | 商业 | VuGen 录制脚本 | 极广（含专有协议） | 支持 | 金融/传统企业、需要厂商支持的验收 |
