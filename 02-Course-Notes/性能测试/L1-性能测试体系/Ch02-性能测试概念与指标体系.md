## 一、性能测试的定义与基础概念

### 知识点 1：性能测试的定义与四个基础概念

【课程原话/定义】
性能测试是软件测试的一种类型，旨在评估系统、应用程序或服务在**特定负载条件下**的性能表现。它涉及模拟真实世界中的用户行为、请求和负载，以便测量系统在不同条件下的响应时间、吞吐量、并发用户数和资源利用率等性能指标。

性能测试相关概念：
- **并发**：并发是指虚拟并发用户数，从业务角度，也可以理解为同时在线的用户数
- **响应时间（Response Time，RT）**：响应时间是系统处理用户请求的时间
- **吞吐量（Throughput）**：系统在单位时间内处理的请求数量，通常以每秒请求数（Requests Per Second，RPS）或每分钟请求数（Requests Per Minute，RPM）来衡量
- **每秒事务数（Transaction per Second，TPS）**：系统每秒处理事务数，单位为 事务数/秒
- **每秒查询数（Query per Second，QPS）**：系统每秒处理查询次数，单位为 查询数/秒

【为什么？】
为什么"并发"这个词必须在压测语境下重新定义一次？因为业务说的"并发"和压测工具里的"并发"不是同一个东西：
- 业务视角的并发 ≈ 同时在线用户数（有多少人在系统里）
- 压测视角的并发 = 虚拟并发用户数（有多少个虚拟用户在**同时施加请求**，即同一时刻正在发请求的线程/用户数）

两者的关系要靠"活跃比例 + 请求集中度"折算。如果你把业务方说的"在线 10 万人"直接当成压测的 10 万并发，得到的压测方案会把系统压出真正的线上事故——**这是性能测试里成本最高的一个概念性错误**。这也是为什么课程在讲指标时，第一句先把"并发"的定义钉死。

【必须掌握】

| 概念 | 定义 | 单位 / 口径 | 关键提醒 |
|------|------|-------------|----------|
| 并发（虚拟并发用户数） | 同一时刻在给系统施加压力的虚拟用户数 | 个（VU） | 业务上的"同时在线人数"需要折算，不能直接当并发用 |
| 响应时间（RT） | 系统处理用户请求的时间 | ms / s | 通常包含 Request Time + Response Time（请求发出到收到完整响应） |
| 吞吐量（Throughput） | 单位时间内处理的请求数量 | RPS（个/秒）或 RPM（个/分钟） | 是"系统产能"的总称，具体到业务与接口层面分别用 TPS / QPS 描述 |
| TPS | 每秒处理的事务数 | 事务数/秒 | 事务可以是数据库事务、网络请求、交易，取决于系统性质 |
| QPS | 每秒处理的查询次数 | 查询数/秒 | 查询可以是网络请求、API 调用、HTTP 请求 |

【企业场景】
你接到业务方需求："我们 App 有 100 万 DAU，峰值时段大概 10% 的人在线，也就是 10 万在线用户，你们按 10 万并发压吧。" 你的回答应该是："10 万在线不等于 10 万并发。按历史日志，峰值时段真正在发请求的活跃比例约 20%，其中下单接口请求集中度最高的是每分钟 3000 次——我先按接口维度折算 QPS，再换算成并发数，最后用阶梯加压验证拐点。" 这句话就是面试里"你怎么定并发数"的标准答案雏形。

【面试考察】
面试官："性能测试里说的'并发'是什么意思？和'在线用户数'有什么区别？"

参考回答框架：
1. 定义：并发 = 虚拟并发用户数 = 同一时刻正在施加请求的用户数
2. 区别：在线用户数只表示"人在系统里"，不一定在发请求；两者要靠活跃比例和请求集中度折算
3. 折算路径：业务量（订单量/DAU）→ 接口 QPS → 并发数 ≈ QPS × 平均 RT
4. 落地方式：折算出来的是"预估"，最终要用阶梯加压找拐点来验证

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 把在线用户数直接当并发用户数 | 在线 ≠ 正在请求，必须用活跃比例折算 |
| 认为 RT 就是"服务器处理时间" | RT 是端到端时间，包含网络传输、排队等待、服务处理、响应传输 |
| 把吞吐量等同于 TPS | 吞吐量是统称，业务链路用 TPS、接口查询用 QPS 更精确 |
| 只盯平均 RT | 必须结合分位值（知识点 5），平均值会掩盖长尾 |

【我的理解】
> （用自己的话回答：为什么业务说的"10 万在线"不能直接写成压测的 10 万并发？如果你要把 10 万在线折算成并发数，你需要向业务方再问哪几个数据？）

## 二、性能指标缩写全景

### 知识点 2：性能指标缩写表（面试高频速查）

【课程原话/定义】

| 简写 | 英文全称 | 含义 |
|------|----------|------|
| RT | Response Time | 响应时间。通常响应时间都包括了 Request Time 和 Response Time |
| HPS | Hits Per Second | 每秒点击数 |
| TPS | Transactions Per Second | 每秒事务数。事务可以是数据库事务、网络请求、交易等，取决于具体系统的性质 |
| QPS | Queries Per Second | 每秒钟处理的查询数量。查询可以是网络请求、API 调用、HTTP 请求等 |
| RPS | Requests Per Second | 每秒请求数 |
| CPS | Codes Per Second | 在 HTTP 协议中，CPS 偶有提及，指的是 HTTP 返回每秒 |
| PV | Page View | 页面浏览量 |
| UV | Unique Visitor | 独立访问者 |
| IP | Internet Protocol | 本意是 IP 地址，在性能中一般指独立 IP 数 |
| Throughput | — | 吞吐量 |
| IOPS | Input/Output Operations Per Second | 通常描述磁盘 |

【为什么？】
为什么要把这些缩写一次列全？因为面试和真实工作里的性能讨论是**用缩写进行的**：监控大盘上写的是 IOPS，压测报告上写的是 TPS，日志统计出来的是 PV/UV，磁盘瓶颈讨论的是 IOPS，链路压测看的是 RPS。听不懂缩写 = 读不懂指标 = 无法参与性能问题的讨论。这张表还有一个隐藏作用：**它揭示了"性能"是多维度体系**——业务量（PV/UV/IP）、请求量（QPS/RPS/HPS）、业务能力（TPS）、用户体验（RT）、硬件能力（IOPS），一个维度翻车都算性能问题。

【必须掌握】

| 缩写分组 | 指标 | 用在什么场景 |
|----------|------|--------------|
| 业务规模 | PV / UV / IP | 业务方提需求、容量规划输入（"日 PV 千万"） |
| 请求量级 | QPS / RPS / HPS / CPS | 压测目标设定、网关与 Nginx 流量统计 |
| 业务能力 | TPS | 业务流程（下单/支付）的端到端处理能力 |
| 用户体验 | RT | SLA 与验收标准（TP99 ≤ 800ms） |
| 系统资源 | IOPS / Throughput | 磁盘、网络带宽的瓶颈分析 |

【企业场景】
你做一次压测前的准备工作，会先画一张"指标口径表"给团队对齐：业务方提的 PV/UV → 折算 QPS → 定每个接口的 RT 目标 → 记录机器侧的 CPU/IOPS 基线。压测结束后，报告里所有的数字都必须能对回这张表——否则就会出现"你说 TPS 5000 达标了，运维说磁盘 IOPS 只有 300 早就爆了"这种各说各话的场面。

【面试考察】
面试官："性能测试关注哪些指标？TPS 和 QPS 有什么区别？"

参考回答框架：
1. 分层说指标：业务量（PV/UV）、请求量（QPS/RPS）、业务能力（TPS）、用户体验（RT）、资源（CPU/IOPS）
2. 讲 TPS vs QPS：TPS 面向"事务/业务流程"，QPS 面向"查询/接口调用"
3. 补一句关系：如果一个业务只对应一个请求连接，则 TPS = QPS（见知识点 3）
4. 加分：说明 RT 必须看分位值，资源指标要看抖动是否剧烈

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| TPS 和 QPS 混用 | TPS 面向业务流程（可能包含多个请求），QPS 面向单次查询/接口调用 |
| 把 HPS 当成 TPS | HPS 是"点击/命中"层面的计数，粒度比事务更细，不等价于业务处理能力 |
| 认为 PV 就是请求数 | 一个页面通常会触发多个接口请求，PV < 请求数是常态 |
| 报告里只写"吞吐量"不写口径 | 同一份报告必须统一口径（并注明是 TPS 还是 QPS），否则数据不可比 |

【我的理解】
> （用自己的话回答：TPS 和 QPS 在什么情况下数值相等、什么情况下差异很大？给你一份"日 PV 1000 万"的业务，你会向业务方再要哪些数据才能算出 QPS？）

## 三、TPS/QPS 的关系与并发数换算

### 知识点 3：TPS 与 QPS 的选用 + 并发数公式

【课程原话/定义】
对于互联网业务中，如果某些业务有且仅有一个请求连接，那么 TPS = QPS；一般情况下用 TPS 来衡量整个业务流程，用 QPS 来衡量接口查询次数。

**并发数 = QPS × 平均响应时间**

【为什么？】
为什么这个公式成立？可以把系统想成一个"服务窗口"：
- 1 秒内系统能处理 QPS 个请求（产能）
- 每个请求平均占用窗口 平均 RT 秒（占用时长）
- 那么同一时刻"正在被服务"的请求数 = QPS × 平均 RT（利特尔法则，Little's Law）

这个公式的工程含义比它的数学形式更重要：
- 想让并发数下降 → 要么降 QPS（限流），要么降 RT（优化性能）
- RT 从 200ms 涨到 2s（10 倍）而 QPS 不变 → 系统里同时占用的请求数暴涨 10 倍，这**正是曲线进入重压力区/弃忍区的数学解释**：RT 上升会让并发堆积，堆积又让 RT 更糟，形成正反馈

【必须掌握】

| 要点 | 内容 |
|------|------|
| TPS = QPS 的条件 | 一个业务（事务）只对应一个请求连接时成立 |
| 什么时候用 TPS | 衡量**整个业务流程**（下单 = 查询商品 + 校验库存 + 扣减 + 支付回调） |
| 什么时候用 QPS | 衡量**接口查询次数**（单个接口/单次 API 调用） |
| 核心公式 | 并发数 = QPS × 平均响应时间 |
| 公式的用途 | 由业务量推算压测并发数；反向用压测结果推算系统容量 |

【企业场景】
你给运维写扩容建议时用到的推算：下单接口 QPS 需要支撑 1000，平均 RT 200ms → 同一时刻占用 1000 × 0.2 = 200 个并发，配 30 个线程的容器实例至少需要 7 个实例（还要留冗余）。反过来，如果压测发现 RT 涨到 800ms，同样的 QPS 就会占用 800 个并发——**这就是为什么"RT 上升"必须当成容量事件而不是体验事件来处理**（"RT 一涨，并发需求就翻几倍"这个连锁反应，是面试里的高分点）。

【面试考察】
面试官："并发数怎么算？TPS 和 QPS 什么时候相等？"

参考回答框架：
1. 先讲公式：并发数 = QPS × 平均响应时间（利特尔法则）
2. 讲 TPS = QPS 的条件：业务与请求是 1:1 关系时
3. 讲差异：一个事务包含多个请求（如支付回调 + 订单查询）时，TPS < QPS
4. 讲用途：正推是"业务量 → 并发数"（定压测目标），反推是"压测结果 → 系统容量"（定扩容方案）
5. 加分：指出 RT 上升会导致并发堆积，这是弃忍区形成的内在机制

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 公式里用最大 RT 而不是平均 RT | 公式使用的是平均 RT，最大 RT 属于长尾，用于 SLA 判断 |
| 认为并发数只由"人数"决定 | 并发数由 QPS 和 RT 共同决定，RT 变化会直接改变并发需求 |
| 单位不统一 | QPS×秒 = 并发个数，计算前必须统一秒/毫秒（200ms = 0.2s） |
| 用折算结果当验收标准 | 折算值只用于设计加压模型，实际容量必须靠压测找拐点验证 |

【我的理解】
> （用自己的话回答：为什么说"RT 上升"同时也是"容量事件"？用 并发数 = QPS × RT 解释一下弃忍区里"TPS 下降但资源依然满"的现象。）

## 四、如何"造"出更大的压力

### 知识点 4：技术上提升压力的方式（多进程 / 多线程 / 混合）

【课程原话/定义】
技术上提升压力的方式：
- **多进程**：启动多个进程，每个进程虽然只有一个线程，但是多个进程可以一起执行多个任务
- **多线程**：启动一个进程，在一个进程的内部启动多个线程，这样多个线程也可以一起执行多个任务
- **多进程 + 多线程**：启动多个进程，每个进程再启动多个线程

对比：

| 维度 | 多进程 | 多线程 | 优劣 |
|------|--------|--------|------|
| 数据共享、同步 | 数据是分开的：共享复杂，需要用 IPC；同步简单 | 多线程共享进程数据：共享简单，同步复杂 | 各有优势 |
| 内存、CPU | 占用内存多，切换复杂，CPU 利用率低 | 占用内存少，切换简单，CPU 利用率高 | 线程占优 |
| 创建销毁、切换 | 复杂，速度慢 | 简单，速度快 | 线程占优 |
| 编程调试 | 编程简单，调试简单 | 编程复杂，调试复杂 | 进程占优 |
| 可靠性 | 进程间不会相互影响 | 一个线程挂掉将导致整个进程挂掉 | 进程占优 |
| 分布式 | 适应于多核、多机分布；一台机器不够，扩展到多台机器比较简单 | 适应于多核分布 | 进程占优 |

【为什么？】
压测工具为什么要讲进程/线程模型？因为**压测机本身也是被压对象**：一台机器能"造"出多少并发，取决于它用进程还是线程、以及模型是否适合分布式。这一点在实操里会直接卡住你——单机 JMeter 用线程模型能压出的并发数受 CPU 和内存限制（默认堆内存下通常只有几百到几千），想再往上就必须**分布式压测**（多台起压机），而分布式扩展恰恰是多进程模型更擅长的场景（进程占优：适应多机分布）。所以"多进程 vs 多线程"不是八股，它决定了你压测方案的规模上限。

【必须掌握】

| 结论 | 依据 | 实践含义 |
|------|------|----------|
| 单机高并发：用多线程 | 内存占用少、切换快、CPU 利用率高 | JMeter/nGrinder 默认线程模型，可以低成本提高单机压力 |
| 大规模并发：必须分布式 | 进程适应多机分布、扩展到多台机器简单 | 分布式压测（起压机集群）才能上到万级并发 |
| 稳定性优先：多进程 | 一个线程挂掉会拖垮整个进程 | 压测机自己崩了会导致压测数据失真，需监控起压机 |
| 调试便利：多进程 | 编程/调试简单 | 写自定义压测脚本（如 Locust/Beanshell）时更容易排查 |

【企业场景】
你要压一个"万级并发"的秒杀场景，单机 JMeter 压不上去，于是搭起压测集群：1 台控制器 + 5 台起压机（多进程部署，每台再开多线程），并用 nGrinder 的分布式能力统一调度。压测过程中你还要盯起压机自己的 CPU/内存——**因为起压机扛不住时会表现为"被压系统看起来没问题"**，这是性能测试里最容易导致结论错误的一类假象（压不出来 ≠ 系统能扛住）。

【面试考察】
面试官："压测并发上不去怎么办？多进程和多线程怎么选？"

参考回答框架：
1. 先判断是谁的问题：起压机（客户端）资源瓶颈 还是 被压系统（服务端）瓶颈——看起压机 CPU/内存/带宽
2. 客户端瓶颈的解法：多线程提高单机压力（内存少、切换快）、参数调优（堆内存/连接数）
3. 还不够就分布式：多台起压机（多进程、多机分布），JMeter/nGrinder 都支持分布式
4. 结论对比：多线程适合单机高并发，多进程在可靠性与分布式扩展上占优，大规模压测通常是"多进程 + 多线程"
5. 加分：强调起压机也要监控，否则会得出"系统能扛"的假结论

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 认为并发上不去就是被压系统扛住了 | 先排除起压机自身瓶颈（CPU/内存/带宽/端口耗尽） |
| 单机无限制提高线程数 | 单机受 CPU/内存/连接数限制，线程过多反而因上下文切换导致压测失真 |
| 忽略压测机的 TIME_WAIT/端口耗尽 | 大量短连接会把本地端口耗尽，需要用长连接或调内核参数 |
| 认为多线程总是优于多进程 | 多线程在可靠性（一个线程挂掉拖垮进程）和分布式扩展上不如多进程 |

【我的理解】
> （用自己的话回答：为什么说"压不上去"时第一步要怀疑压测机自己？对"多线程适合单机高并发、多进程适合多机分布"这句话，你能各举一个真实场景吗？）

## 五、性能指标分位值

### 知识点 5：Mean / P90 / P95 / P99 分位值

【课程原话/定义】
在性能指标中，Mean（均值）、P90、P95 和 P99 是常见的描述性分位数，用于衡量数据分布的不同方面：
- **Mean（均值）**：将所有观测值相加并除以观测值的数量。它表示数据的集中趋势，但**容易受到离群值的影响**；在数据分布对称时很有用，因为它与分布的中心位置相对应
- **P90**：第 90 分位数。表示 90% 的观测值低于该值，仅有 10% 的观测值高于该值。给出了一个较高的观察值，可以用来评估系统在高运行负载条件下的性能
- **P95**：第 95 分位数。表示 95% 的观测值低于该值，仅有 5% 的观测值高于该值。用于衡量系统在绝大部分情况下的性能，可以反映典型的性能水平
- **P99**：第 99 分位数。表示 99% 的观测值低于该值，仅有 1% 的观测值高于该值。用于衡量系统在高负荷或异常情况下的性能，通常代表较高的延迟或较差的响应时间

选择使用哪些分位数取决于具体的需求和关注的性能指标。

【为什么？】
为什么平均值会骗人？假设 100 个请求里 99 个是 100ms、1 个是 10s：平均值 = (99×100 + 10000)/100 = 199ms，看起来"很好"；但那个 10s 的用户已经关掉页面了。更常见的是**长尾分布**：均值被大量快请求拉低，掩盖了少数"卡死"的用户。这就是为什么线上 SLA 通常写成"TP99 ≤ 800ms"而不是"平均 RT ≤ 800ms"——
- 均值衡量"平均水平"，适合看整体趋势
- P90/P95 衡量"大多数情况"，是**典型用户体验** 
- P99 衡量"最差的那 1%"，是**投诉与流失的来源**，也是系统抖动的报警信号

一句话：**均值看趋势，分位值定 SLA。**

【必须掌握】

| 指标 | 含义 | 用来判断什么 | 典型用法 |
|------|------|--------------|----------|
| Mean | 平均值 | 整体趋势、纵向对比（优化前后） | 压测报告的趋势图、监控大盘 |
| P90 | 90% 请求快于此值 | 高负载下的表现 | 内部系统、后台接口的容忍线 |
| P95 | 95% 请求快于此值 | 绝大多数用户的体验 | 通用 SLA 口径 |
| P99 | 99% 请求快于此值 | 最差 1% 的极端体验、系统抖动 | C 端核心接口的 SLA（支付/下单） |

【企业场景】
大促当天你看监控大盘，下单接口的均值 RT 稳定在 180ms、P99 却是 6s——均值告诉你"一切正常"，P99 告诉你"每分钟有几百个用户下单要等 6 秒"。你的动作应该是：先看 P99 的时间分布（是否与某个定时任务/缓存过期重合），再看是否有 Full GC 或慢查询的毛刺。**只看均值，这次事故会以"首页突然出现大量'下单失败'投诉"的形式在第二天找上你。**

【面试考察】
面试官："性能测试看平均值还是分位值？为什么？"

参考回答框架：
1. 都要看，但职责不同：均值看趋势与对比，分位值定 SLA 与报警线
2. 均值的问题：容易被离群值或长尾分布掩盖（举 99×100ms + 1×10s 的例子）
3. 分位值的选择：P90/P95 代表典型体验，P99 代表极端体验与抖动
4. 落地方式：SLA 用"TP99 ≤ X ms"表达，压测报告同时给均值与 TP99 曲线
5. 加分：说明分位值比均值更能反映"用户投诉"的来源

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 只看平均 RT 就下结论 | 必须结合 P95/P99，避免长尾被掩盖 |
| 认为 P99 一定有 1% 的请求是慢的 | 分位值是统计口径的描述，不代表必然存在故障，可用于发现抖动 |
| 把 P90 当成最差值 | P90 之上还有 10% 的请求更慢，P99 才是接近最差的口径 |
| 不同口径混着比 | 优化前后必须用同一分位口径对比，否则结论无效 |
| 认为分位值越高越没用 | P99 是发现抖动和故障的关键证据（大促必看） |

【我的理解】
> （用自己的话回答：为什么线上 SLA 通常写 TP99 而不是平均值？如果一次优化让平均 RT 从 300ms 降到 200ms，但 P99 从 800ms 涨到 1.5s，这次优化算成功吗？为什么？）
