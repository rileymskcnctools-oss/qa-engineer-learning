## 一、监控工具有哪些、为什么要用

### 知识点 1：行业流行性能监控工具全景

【课程原话/定义】
行业流行性能监控工具有：
- **Linux 自带命令 vmstat、top 等**
- **Nmon**
- **Collectd + InfluxDB + Grafana**
- **Prometheus + Grafana**

【为什么？】
为什么压测之外还要专门学一套监控工具？因为**曲线和数据只能告诉你"哪里慢了"，不能告诉你"为什么慢"**：
- 压测工具（JMeter）给出的是**业务视角**的数据：TPS、RT、错误率
- 监控工具给出的是**系统视角**的数据：CPU、内存、磁盘 IO、网络、连接数

一次性能问题定位，本质是把两侧数据在**时间轴上对齐**：14:32 开始 TPS 走平 → 同一时刻 CPU 从 60% 冲到 95% → 结论是"CPU 饱和导致吞吐不再增长"。没有监控数据，这个结论只能靠猜。这四类工具的关系也不是"选一个"，而是**分层共存**：

| 层次 | 工具 | 定位 | 什么时候用 |
|------|------|------|-----------|
| 快速排查 | vmstat / top | Linux 自带、零部署 | 压测中随时敲一条命令看实时状态 |
| 单机采集 | Nmon | 轻量、高采样率、可导出 | 需要单机详细指标与事后分析 |
| 自建监控栈（时序库方案） | Collectd + InfluxDB + Grafana | 采集-存储-可视化 | 需要长期存储与自定义看板 |
| 自建监控栈（主流方案） | Prometheus + Grafana | 拉取式采集 + 强查询 + 告警 | 多机集群监控、告警联动、行业主流 |

【必须掌握】

| 工具 | 类型 | 关键能力 |
|------|------|----------|
| vmstat / top | Linux 自带命令 | 实时看 CPU / 内存 / 进程 / IO 状态，零成本 |
| Nmon | 命令行采集工具 | 低开销、高采样率、多维度指标、输出格式灵活（文本/表格/图表）、支持插件 |
| Collectd + InfluxDB + Grafana | 组合方案 | Collectd 采集 → InfluxDB 时序存储 → Grafana 可视化 |
| Prometheus + Grafana | 组合方案 | Prometheus 多维数据模型 + 查询 + 告警 → Grafana 看板 |

【企业场景】
压测过程中你的排查顺序通常是："先 `top` 看哪台机器忙（10 秒）→ 用 Nmon 在那台机器上采一份完整数据（持续记录）→ 看 Grafana 上集群维度的趋势（找拐点与资源饱和的时间对应关系）"。**命令是急诊，监控平台是病历**：急诊先确定病在哪，病历用来复盘与出报告。

【面试考察】
面试官："你们用什么做性能监控？"

参考回答框架：
1. 分层次回答：临时排查用 Linux 自带命令（top/vmstat），单机采集用 nmon，集群长期监控用 Prometheus + Grafana（或 Collectd + InfluxDB + Grafana）
2. 讲分工：压测工具看业务指标（TPS/RT），监控工具看系统指标（CPU/内存/IO/网络），两者按时间轴对齐才能定位瓶颈
3. 讲落地：压测前先确认监控可用（采集覆盖率、看板、告警），否则数据无法归因

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 认为监控工具与压测工具二选一 | 两者互补：一个造压力，一个测资源，必须同时开 |
| 只用 Linux 命令就下结论 | 命令是瞬时值，无法复盘趋势与出报告，需配合采集与看板 |
| 压测前不验证监控可用性 | 采集不到数据 = 压测白做，提前验证是流程必备步骤 |

【我的理解】
> （用自己的话回答：为什么说"压测工具看业务、监控工具看系统，两者按时间轴对齐才能定位瓶颈"？举一个你自己能说出来的对齐例子。）

## 二、Linux 自带命令：vmstat 与 top

### 知识点 2：vmstat

【课程原话/定义】
vmstat 是一个**命令行工具**，用于报告 Linux 系统的**虚拟内存、进程、CPU 和 IO 状态**。它可以提供实时的系统监控信息。vmstat 命令可以通过指定不同的参数和时间间隔来控制输出的频率和详细程度。它对于监测系统的性能问题和调优非常有用。

课程原图（未随消息发送）：

> 📷 【截图占位】vmstat 命令输出示例图

【为什么？】
为什么 vmstat 是性能排查的"第一眼"工具？因为它**一条命令同时给出三类关键信息**，几秒内就能判断瓶颈在哪一类资源上：
- `r`（运行队列长度）：排队等 CPU 的进程数 → 持续 > CPU 核数说明 **CPU 瓶颈**
- `si/so`（换入换出）：swap 交换 → 非 0 说明**内存不足**，性能会断崖式下跌
- `wa`（IO 等待）：CPU 等磁盘的时间占比 → 偏高说明**磁盘 IO 瓶颈**
- `us/sy/id`：用户态/内核态/空闲占比 → 看 CPU 到底被什么吃掉

`vmstat 1` 表示每秒采样一次——**性能问题往往表现为"毛刺"，不采样就看不到**。这也是压测时"必须开着一条 vmstat"的原因。

【必须掌握】

| 字段/用法 | 含义 | 判断标准 |
|-----------|------|----------|
| `vmstat 1` | 每 1 秒输出一次采样 | 压测期间常驻，捕捉毛刺 |
| r | 运行队列（等待 CPU 的进程数） | > CPU 核数 → CPU 瓶颈 |
| b | 阻塞进程数 | 通常与 IO 等待相关 |
| si / so | 从 swap 换入/换出 | 非 0 → 内存不足 |
| us / sy / id / wa | 用户态 / 内核态 / 空闲 / IO 等待占比 | wa 高 → 磁盘瓶颈；sy 高 → 系统调用/上下文切换过重 |
| free | 空闲内存 | 结合 si/so 判断真实内存压力 |

【企业场景】
压测中 TPS 走平，你在应用机器上敲 `vmstat 1`，看到 `r` 列长期在 20 以上（机器 8 核），`id` 只有 5%——结论立刻明确：**CPU 是瓶颈**，后续动作是看是业务代码 CPU 密集还是 GC 在抢 CPU（这时接 JConsole / VisualVM）。如果看到的是 `wa` 长期 30%~50%，方向就要转向磁盘 IO（日志写太猛、数据库刷盘），排查路径完全不同。**一条命令决定了接下来的排查方向。**

【面试考察】
面试官："压测时怎么快速判断瓶颈在哪？vmstat 你关注哪些列？"

参考回答框架：
1. 命令：`vmstat 1`（每秒采样，抓毛刺）
2. 关注：r（CPU 排队）、si/so（内存是否动用 swap）、wa（IO 等待）、us/sy/id（CPU 构成）
3. 判断逻辑：r > 核数 → CPU 瓶颈；wa 高 → 磁盘瓶颈；si/so 非 0 → 内存不足
4. 下一步：确定方向后再上针对性工具（JVM 工具、IO 工具、数据库监控）

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 只看一次 vmstat 输出 | 瞬时值会骗人，必须加采样间隔看趋势与毛刺 |
| 看到 id 高就认为系统健康 | 还要看 wa 与 r：id 高但 wa 也高，说明请求在等 IO |
| 忽略 si/so | 一旦发生 swap，性能会断崖下跌，是最严重的信号之一 |
| 把 r 理解为"进程总数" | r 是"等待 CPU 的运行队列长度"，反映 CPU 竞争程度 |

【我的理解】
> （用自己的话回答：`vmstat 1` 里的 r、wa、si/so 三个字段分别指向什么瓶颈？如果一台 8 核机器 r=25、wa=2、si/so=0，你的判断是什么？）

### 知识点 3：top

【课程原话/定义】
top 是一个**交互式命令行工具**，用于实时监控系统的**进程和资源使用情况**。它可以按照 CPU、内存、IO 等方面对进程进行排序，并提供实时的统计信息。通过使用不同的命令行选项和交互命令，用户可以在 top 中定制显示的内容和排序方式。top 对于**实时监控系统的状态和了解资源消耗最高的进程**很有帮助。

课程原图（未随消息发送）：

> 📷 【截图占位】top 命令输出示例图

【为什么？】
vmstat 告诉你"哪类资源紧张"，top 告诉你"**哪个进程在吃掉它**"——两者是"症状 → 嫌疑人"的关系。top 的核心价值在于**按资源排序 + 下钻到进程**：
- 系统级概览（load average、CPU 构成、内存/swap）
- 进程级明细（%CPU、%MEM、RES、命令名）
- 交互操作（`P` 按 CPU 排序、`M` 按内存排序、`1` 展开每核、`H` 显示线程）

在压测场景里，"按 CPU 排序发现 Java 进程占 380%"这类信息直接指向 JVM（多线程吃多核），下一步就是 JVM 层面的工具。

【必须掌握】

| 用法 / 字段 | 含义 | 用途 |
|-------------|------|------|
| load average | 1/5/15 分钟平均负载 | 快速判断系统整体压力（> 核数需警惕） |
| `%Cpu(s)` 行 | us/sy/id/wa 等构成 | 看 CPU 被用户态还是内核态吃掉 |
| %CPU / %MEM | 单个进程的 CPU / 内存占用 | 找到资源消耗最高的进程 |
| RES / VIRT | 常驻内存 / 虚拟内存 | 判断是否内存泄漏或超配 |
| `P` / `M` / `1` / `H` | 排序与展开的交互键 | 交互式定位"谁在吃资源" |

【企业场景】
压测中你发现应用机器 CPU 打满，切到 top 按 `P` 排序，看到 PID 12345（java）占 380% CPU 且 RES 持续增长——两个结论同时得到：**CPU 瓶颈在应用进程**，且**存在内存持续增长**（需要在长时间压测中确认是否为泄漏）。这份证据直接写进压测报告，交给开发定位到具体线程/代码。

【面试考察】
面试官："top 和 vmstat 的区别？你怎么用？"

参考回答框架：
1. vmstat：汇总视角，看资源类别的竞争情况（CPU/内存/IO）——判断"哪类资源瓶颈"
2. top：进程视角，按 CPU/内存排序并下钻——判断"哪个进程是元凶"
3. 组合用法：vmstat 定方向 → top 定进程 → 再上专项工具（JVM/DB/IO）
4. 实操细节：`top -H -p <pid>` 看线程级占用，配合 jstack 定位到代码

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 把 load average 当成 CPU 使用率 | 负载包含"等 IO/等 CPU"的进程，LOAD 高而 CPU 不高说明在等 IO |
| 只看 %CPU 总和，不看是哪个核 | 多核机器要用 `1` 展开看热点核与负载均衡情况 |
| 不用线程级视图 | 定位到进程后，需 `top -H -p pid` 才能定位到具体线程 |
| 忽略 RES 随时间的变化 | 内存持续增长是泄漏的典型信号，必须在长时间压测中观察 |

【我的理解】
> （用自己的话回答：为什么排查顺序是"vmstat 定方向 → top 定进程 → 线程级视图定代码"？如果 load average 很高但 CPU 使用率不高，你会怀疑什么？）

## 三、Nmon

### 知识点 4：Nmon

【课程原话/定义】
Nmon 是一种性能监控工具，它用于**实时收集和报告 Linux 系统的性能数据**。Nmon 是一个命令行工具，可以提供关于 CPU、内存、磁盘、网络等各方面的详细信息。

主要特点和功能：
- **低系统开销**：Nmon 是一个轻量级的工具，对系统资源消耗较低。它以非常高的采样率获取性能数据，同时降低对系统性能的影响
- **多方面指标**：能够收集丰富的指标，包括 CPU 使用率、内存使用量、磁盘读写速度、网络流量、进程信息等
- **实时监控**：以实时模式运行，可以提供实时的性能数据。它的命令行界面会显示当前性能数据的摘要，管理员可以随时查看系统的运行状态
- **输出格式灵活**：可以将性能数据以不同的输出格式保存，包括文本、电子表格、图表等，方便分析和可视化
- **可扩展性**：支持插件机制，可以通过加载插件来扩展功能。有许多第三方插件可以提供额外的性能指标和报告

课程原图（未随消息发送）：

> 📷 【截图占位】Nmon 命令行界面示例图

【为什么？】
Nmon 解决的是 vmstat/top 的死穴：**它们是瞬时视图，无法作为证据留存**。而性能测试需要"可复盘、可交付、可对比"的数据，这就要求：
- **持续采集**：一次压测可能持续数小时，需要全程记录而不是靠人盯屏
- **低干扰**：采集工具本身不能明显影响被测系统（Nmon 的低开销正是为此设计）
- **可导出分析**：数据要能转成表格/图表进报告（输出格式灵活）

所以在很多企业的实操里，压测时的标准动作是：**在被压机器上后台启动 Nmon 采集（例如每 10 秒采样），压测结束后把数据导出成表格，用分析工具出图放进报告。** 这条链路正是"用数据说话"的最小落地形态。

【必须掌握】

| 特点 | 具体内容 | 对压测的意义 |
|------|----------|--------------|
| 低系统开销 | 轻量级、高采样率、对被测系统影响小 | 采集不污染结果 |
| 多维度指标 | CPU、内存、磁盘读写、网络流量、进程信息 | 一份数据覆盖多类资源瓶颈 |
| 实时监控 | 命令行界面实时显示摘要 | 压测中可即时观察 |
| 输出格式灵活 | 文本、电子表格、图表 | 数据可进报告、可复盘 |
| 可扩展 | 插件机制，第三方插件补充指标 | 按需扩展监控覆盖 |

【企业场景】
大促全链路压测要跑 2 小时，你在每台被压机器上启动 Nmon 后台采集，压测结束后把 8 台机器的数据汇总成一张资源趋势表，找出"哪台机器先饱和、什么时刻开始饱和"——这种**集群级的资源趋势对比**是报告里最有说服力的证据（也是画压力曲线时"资源利用率曲线"的数据来源）。

【面试考察】
面试官："压测时你怎么采集服务端数据？"

参考回答框架：
1. 临时排查：top / vmstat（瞬时、零部署）
2. 持续采集：nmon 后台采集到文件（低开销、多维度、可导出成表格）
3. 集群监控：Prometheus + Grafana（多机长期趋势与告警）
4. 报告落地：把采集数据导出为图表，与压测的 TPS/RT 按时间轴对齐分析

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 靠人盯屏记录数据 | 必须落地成文件才能复盘、对比、出报告 |
| 采集频率过低 | 采不到毛刺（毛刺往往就是性能拐点的成因） |
| 只采集应用机器 | 分布式架构下 Nginx、DB、缓存、MQ 机器都要采 |

【我的理解】
> （用自己的话回答：为什么压测报告里的"资源利用率曲线"必须以持续采集（Nmon/Prometheus）为前提，而不能用 top 的截图？）

## 四、自建监控栈：Collectd + InfluxDB + Grafana

### 知识点 5：Collectd + InfluxDB + Grafana（采集 / 存储 / 可视化三层）

【课程原话/定义】
Collectd、InfluxDB 和 Grafana 是一套常见的组合，用于构建性能监控和可视化解决方案：
- **Collectd**：开源的**系统统计数据收集守护程序**。它定期收集系统的各种指标，如 CPU 使用率、内存使用量、网络流量等，并将这些数据发送给 InfluxDB 进行存储和查询
- **InfluxDB**：开源的**高性能时间序列数据库**，专门用于存储和查询时序数据。它支持高度可扩展的分布式架构，并提供了强大的查询语言和聚合功能，用于分析和监控时间序列数据
- **Grafana**：流行的开源**数据可视化和仪表板工具**。支持多种数据源（其中包括 InfluxDB），可以连接 InfluxDB 并使用其查询语言和可视化功能，创建实时性能监控仪表板。用户可以自定义仪表板并添加各种图表、图形和警报来展示监控数据

【为什么？】
为什么监控系统要拆成"采集 / 存储 / 可视化"三层？因为这三件事的优化目标是互相冲突的：
- 采集要**轻**（尽量不影响被测系统）→ 只负责定时抓数据并推送
- 存储要**专**（高写入、按时间聚合）→ 时序数据库（InfluxDB）替代表结构数据库，才能扛住秒级写入与降采样查询
- 可视化要**灵活**（改看板不改采集）→ Grafana 独立连接数据源，随时换图、换数据源、加告警

一旦把三者耦合（例如用脚本采集+画图），监控就会变成"改一个指标要动整套代码"。**分层的价值在于：每一层可以独立演进，且数据能被长期留存用于复盘。** 这也是它和 top/nmon 的本质区别——**监控平台是"可持续运行的证据系统"，命令行只是"当前的快照"。**

【必须掌握】

| 组件 | 角色 | 关键能力 | 对应性能测试需求 |
|------|------|----------|------------------|
| Collectd | 采集（守护进程） | 定期收集 CPU/内存/网络等指标并发送 | 持续、低开销地记录压测过程 |
| InfluxDB | 存储（时序数据库） | 高性能写入与查询、聚合、可扩展分布式架构 | 长期留存数据，支持事后分析与对比 |
| Grafana | 可视化（仪表板） | 多数据源、多样图表、自定义看板、告警 | 压测期间实时看板 + 报告出图 |

【企业场景】
你搭好这套栈后，压测期间给团队投一个大屏：左侧是业务指标（JMeter 实时结果或网关 QPS/RT），右侧是系统指标（各机器的 CPU/内存/IO/网络）。**同屏对照的价值在于——当 TPS 走平时，你能立刻指出是哪台机器的哪类资源同时到达饱和点。** 这个画面也是给管理层看"压测在做什么"的最有效沟通工具。

【面试考察】
面试官："你搭过监控系统吗？说说架构。"

参考回答框架：
1. 三层架构：采集（Collectd）→ 存储（InfluxDB 时序库）→ 可视化（Grafana 看板 + 告警）
2. 为什么分层：采集要轻、存储要高写入、可视化要灵活，三者独立演进
3. 在压测中的作用：全程记录资源数据，与 TPS/RT 对齐定位瓶颈，并作为报告证据
4. 对比：命令行工具（top/vmstat/nmon）适合即时与单机，监控栈适合集群与长期

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 用关系型数据库存时序数据 | 秒级写入 + 聚合查询要用时序库（InfluxDB / Prometheus），否则写入会先崩 |
| 采集频率与看板粒度不匹配 | 看板要看的粒度决定了采集间隔（要抓毛刺就采密一些） |
| 只有采集没有告警 | 告警是把"事后分析"变成"事中干预"的关键一环 |
| 认为搭了监控就不用命令行 | 应急排查仍靠 top/vmstat 这类零延迟工具 |

## 五、自建监控栈：Prometheus + Grafana

### 知识点 6：Prometheus + Grafana（行业主流方案）

【课程原话/定义】
Prometheus 和 Grafana 是一对强大的开源工具，用于构建**高度可定制**的监控和可视化解决方案：
- **Prometheus**：开源的**系统和服务监控工具**。它采用**多维数据模型**，可以收集和存储时间序列数据。具有强大的查询语言，可以对收集的数据进行灵活的查询和聚合。它还提供了**告警机制**，可以根据定义的规则触发告警
- **Grafana**：流行的开源数据可视化和仪表板工具，支持多种数据源（其中包括 Prometheus）。允许用户通过直观的界面创建自定义仪表板，并添加图表、图形、警报等来展示监控数据，提供丰富的可视化选项

使用 Prometheus 和 Grafana 可以搭建一个完整的监控和可视化系统：Prometheus 负责**收集、存储和查询**时间序列数据，Grafana 通过连接到 Prometheus 并使用其查询语言和可视化功能，创建定制化的性能监控仪表板。

课程原图（未随消息发送）：

> 📷 【截图占位】Prometheus + Grafana 架构/示意图

【为什么？】
Prometheus 相比 Collectd+InfluxDB 的组合，多出了两个决定性的能力，这也是它成为行业主流的原因：
1. **多维数据模型 + 强查询语言（PromQL）**：指标自带标签（instance、job、path、status…），所以你能回答"**哪个实例的哪个接口的错误率**在上升"这种带维度的问题，而不是只能看"总的错误率"
2. **告警机制内建**：压测与线上监控可以共用一套告警规则（例如"TP99 > 800ms 持续 3 分钟"→ 触发告警），把监控从"看图"升级为"自动发现问题"

再加上生态庞大（Exporter 覆盖 Nginx、MySQL、Redis、JVM、Kafka 等几乎所有中间件），Prometheus + Grafana 就成了分布式系统监控的事实标准。压测时的典型用法是：**用 Exporter 把每一层中间件的指标统一采集进 Prometheus，用 Grafana 拼出一张"全链路看板"，压测过程中盯着它找第一个饱和点。**

【必须掌握】

| 组件 | 角色 | 关键能力 |
|------|------|----------|
| Prometheus | 收集 / 存储 / 查询 | 多维数据模型、时序存储、PromQL 查询与聚合、告警规则 |
| Grafana | 可视化 | 多数据源、自定义仪表板、图表与警报 |
| Exporter | 指标暴露 | 把 Nginx / MySQL / Redis / JVM / Kafka 等指标转成 Prometheus 可采集格式 |

| 对比项 | Collectd + InfluxDB | Prometheus + Grafana |
|--------|---------------------|----------------------|
| 采集方式 | 推（push）为主 | 拉（pull）为主 |
| 数据模型 | 时序点 | 多维（标签）数据模型 |
| 查询 | InfluxQL / Flux | PromQL |
| 告警 | 依赖 Grafana | 内建告警规则 |
| 生态 | 较广 | 极广（Exporter 覆盖主流中间件） |

【企业场景】
压测前你接的就是这套栈的"压测版本"：在 Nginx、MySQL、Redis、应用实例上分别部署 Exporter，搭一张 Grafana 看板（QPS、RT、错误率、各层 CPU/内存/连接数/命中率/队列堆积）。压测中一旦 TPS 走平，看板上"哪个面板先变红"就是瓶颈的位置——**这就是把 Ch03 的架构图真正"变成仪表"的过程。**

【面试考察】
面试官："Prometheus 和 Grafana 分别负责什么？为什么要用它们？"

参考回答框架：
1. 分工：Prometheus 负责采集、存储、查询（PromQL）与告警；Grafana 负责可视化与看板
2. 关键优势：多维数据模型（带标签）能按实例/接口维度下钻；内建告警把监控变成自动发现
3. 生态：Exporter 覆盖 Nginx/MySQL/Redis/JVM/Kafka 等，可实现全链路统一监控
4. 压测用法：与压测工具的时间轴对齐，找第一个饱和节点并作为报告证据
5. 对比：与 Collectd + InfluxDB 相比，拉取模型、标签模型、内建告警是主要差异

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 认为 Grafana 负责采集数据 | Grafana 只做查询与展示，采集由 Prometheus 与 Exporter 完成 |
| 不会用标签下钻 | 多维数据模型的价值在标签过滤与聚合，只看总量会丢失定位线索 |
| 告警规则照抄不调阈值 | 阈值要按 SLA 与业务量设定（如 TP99 > 800ms 持续 3 分钟），否则告警疲劳 |
| 采集间隔设置不当 | 间隔过长采不到尖刺，过短则增加存储与采集压力，需按目标粒度权衡 |

【我的理解】
