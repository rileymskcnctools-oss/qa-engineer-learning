### 知识点1：性能监控系统是什么，它解决什么价值

【课程原话/定义】
性能监控系统是一种用于监测和记录软件、硬件或系统在运行期间的性能指标的工具。通过对这些性能指标进行实时收集和分析，性能监控系统能够帮助用户了解系统的运行状况，识别潜在问题，并及时采取优化措施。

课程给出的"性能监控系统的用处"（原文 4 条）：
1. **提高系统稳定性和可靠性**：及时发现并解决性能瓶颈和资源利用率问题，减少因性能问题导致的宕机、崩溃；
2. **优化资源利用**：追踪并记录 CPU 利用率、内存使用、网络流量等指标，据此合理规划与优化资源使用，降低浪费；
3. **提升用户体验**：跟踪应用响应时间、页面加载速度等，了解用户真实感受，通过优化瓶颈提升速度与满意度；
4. **加强安全保障**：检测分析异常行为、网络攻击等安全事件并及时响应，强化安全与风险管理。

原文收口：性能监控系统在提高稳定性、优化资源利用、提升用户体验、加强安全保障等方面都具有重要价值；对企业而言，可以**降低维护成本、提高业务连续性、增强竞争力**。

【为什么？】
这 4 条价值其实是**同一个能力**的四种说法——**"把不可见的系统状态变成可判断的数据"**：

- 稳定性和可靠性："故障发现得早"——本质是**缩短 MTTR**（平均修复时间），因为你有曲线能定位，而不是靠猜；
- 优化资源利用："钱花在该花的地方"——对应 L1 讲过的降本增效（容量规划 + 调优 = 为老板省钱，[[../L1-性能测试体系/Ch01-性能测试介绍与压力曲线模型|L1 Ch01]]）；
- 提升用户体验："把业务感受翻译成指标"——响应时间、页面加载速度这些就是用户体验的可测量代理；
- 加强安全保障："异常行为也是数据"——同一套采集与告警机制，顺带覆盖了攻击、异常访问的发现。

对**测试开发工程师**来说，这 4 条里最该掌握的是第 1 条和第 3 条：性能测试的交付物从来不是"跑完一轮"，而是"**带数据的结论**"；而"数据"就来自监控系统（或上一章那套采集脚本）。**没有监控的压测，结论只能靠感觉。**

【必须掌握】

| 价值（原文 4 条） | 企业里的可量化形式 | 与压测的关系 |
|---|---|---|
| 提高稳定性与可靠性 | MTTR 下降、故障发现时间缩短、可用性（SLA）达标 | 压测中定位瓶颈、压测后回归监控 |
| 优化资源利用 | 资源利用率曲线、扩容/缩容决策依据、成本下降 | 容量结论"日常区间 / 容量上限 / 扩容红线" |
| 提升用户体验 | RT 分位值（P95/P99）、页面加载时间、错误率 | 压测的验收指标本身就是用户体验指标 |
| 加强安全保障 | 异常流量/异常访问告警 | 压测前的授权与压测中的误报识别（压测流量会被当成攻击） |

【企业场景】
一个真实的管理场景：老板问"我们下个月要不要给订单服务扩容？"——如果你只有压测报告里一个 TPS 数字，没法回答；如果你有监控系统里"过去 90 天订单接口 P99 从 300ms 涨到 650ms、CPU 峰值从 55% 涨到 82%"的曲线，你就能给出"现在是拐点左移、建议扩 30%"的结论。**监控系统的价值就是把"我觉得慢"变成"数据说慢在哪、慢了多少"。**

【面试考察】
面试官："性能监控系统有什么价值？对测试开发岗位意味着什么？"

参考回答框架：
1. 四条价值：稳定性（发现早）、资源优化（省钱）、用户体验（指标化感受）、安全（异常行为发现）；
2. 本质：把不可见的运行状态变成可判断的数据，缩短 MTTR、支撑容量决策；
3. 对测开的意义：压测的交付物是"带数据的结论"，监控（或采集）是数据来源；压测 → 监控 → 剖析是一条链；
4. 收口：能举一个"用监控数据给出容量决策"的例子。

【易错点】

| 常见错误 | 正确理解 |
|---|---|
| 把"监控"等同于"报警" | 监控的核心产出是**可判断的数据（趋势）**；报警只是其中一种消费方式 |
| 认为监控是运维的事，与测试无关 | 压测需要它出证据、定基线、做回归；测开要会用甚至能搭（本模块后半就是搭） |
| 只关注"系统指标"（CPU/内存） | 还要关注**业务指标**（RT/TPS/错误率），两者对齐才能下结论 |
| 压测时忽略"压测流量会被安全监控当成异常" | 事前告知安全团队、加白名单，否则会被误封或误报 |
| 认为"有监控就不需要压测" | 监控是"现在的状态"，压测是"未来的容量"；后者不能被前者替代 |

【我的理解】引导题（用自己的话回答）：
1. 请用"MTTR"这个概念解释"提高稳定性"这条价值到底省了什么。
2. 为什么说"压测流量可能被安全监控误判为攻击"？你会做哪些准备？

### 知识点2：使用场景（生产监控 / 排查调优 / 安全 / 容量规划）

【课程原话/定义】
课程给出的 4 个使用场景（原文）：
1. **生产环境监控**：生产环境的稳定性和性能至关重要，监控系统能够实时监控数据库、应用程序等的性能，及时发现问题，确保生产环境的稳定性和业务连续性；
2. **问题排查与调优**：当系统性能下降或出现异常时，提供详细的性能指标和查询分析，帮助管理员和开发人员快速定位问题并优化；
3. **安全监控**：通过分析网络流量和系统日志，及时发现和预警安全威胁（网络攻击、恶意软件、数据泄露等）；
4. **容量规划**：通过对服务器、存储、网络等资源的监控和分析，了解 IT 基础设施的容量需求和瓶颈，为服务器扩展、存储升级等提供决策依据。

【为什么？】
这 4 个场景可以按"**看不看得到问题**"分成两类，用途完全不同：

| 场景 | 触发方式 | 关键诉求 | 典型指标 |
|---|---|---|---|
| 生产环境监控 | 常驻、实时 | 发现异常、保证连续性 | 可用性、错误率、RT、资源水位 |
| 问题排查与调优 | 事件驱动 | **下钻**到根因 | 调用链、慢查询、线程/GC、资源曲线 |
| 安全监控 | 常驻 + 规则 | 识别异常行为 | 流量突增、异常来源、日志告警 |
| 容量规划 | 周期性（周/月） | **长期趋势** | 历史峰值、增长斜率、拐点位置 |

对压测工作来说，这 4 个场景恰好覆盖了完整闭环：**压测前**看容量规划（目标定多少）、**压测中**用生产监控同款指标（避免"压测指标与线上不可比"）、**压测后**做问题排查与调优、**压测外**保证安全合规。其中最容易被忽略的是第二条里的"**查询分析**"——课程原文用了"详细的性能指标**和查询分析**"，这指的就是 Prometheus 的 PromQL / Grafana 的查询能力（后面章节要学）：**同一个指标，能在任意时间窗口聚合、对比、下钻**，才是监控系统比"一堆日志"强的地方。

【必须掌握】

| 场景 | 谁在用 | 对应本模块章节 |
|---|---|---|
| 生产环境监控 | 运维/OnCall | [[Ch42-Prometheus监控系统部署应用实战]]（Prometheus + Grafana + Node Exporter） |
| 问题排查与调优 | 开发/测试/运维 | [[Ch38-系统性能数据收集（cpu、mem、net、io）]] + [[../L1-服务端统计工具/Ch36-top命令使用|Ch36]] + 剖析工具 |
| 安全监控 | 安全团队 | 同一套指标 + 规则告警（认知即可） |
| 容量规划 | 测试/运维/架构 | [[Ch39-性能监控系统价值]] 趋势分析 + L1 场景设计与压力曲线 |
| 压测实时观测 | 测试 | [[Ch43-jmeter实时压测结果收集]]（JMeter + InfluxDB + Grafana） |

【企业场景】
大促前的标准动作：① 用监控系统看过去一年大促的峰值曲线（容量规划）→ ② 按峰值 + 冗余设计压测目标 → ③ 压测中用与线上一致的监控指标（CPU/RT/P99/错误率）→ ④ 大促当天用同一套看板值班，把"压测时的指标"和"线上的指标"直接对照。**"同一套指标贯穿压测与生产"是高级能力**：它让压测结论真的能预测线上表现，而不是两套体系各说各话。

【面试考察】
面试官："监控系统一般用在哪些场景？压测期间你怎么用它？"

参考回答框架：
1. 四个场景：生产常驻监控、问题排查与调优、安全监控、容量规划；
2. 压测的用法：压前用历史趋势定目标；压中用与生产一致的指标实时观测；压后做下钻与回归对比；
3. 关键点：**指标口径与生产一致**（否则结论不可迁移）；监控要支持查询/下钻（PromQL）；
4. 收口：监控系统 + 压测 = "用数据预测容量"，这也是压测报告里"扩容红线"的来源。

【易错点】

| 常见错误 | 正确理解 |
|---|---|
| 压测用一套指标、生产用另一套 | 指标口径不一致，压测结论无法迁移到线上（最常见的隐性错误） |
| 只把监控当"报警器" | 监控还能做趋势分析（容量规划）与下钻（排查）——后者更值钱 |
| 排查时只看实时、不看历史 | 历史数据才能判断"是这次发布导致的，还是长期劣化" |
| 忽略安全监控对压测的影响 | 压测前与安全团队对齐（白名单/时间窗），避免被当成攻击拦截 |
| 以为容量规划是"看一次就够了" | 容量规划是**周期性**：需要长期趋势（增长斜率）才有意义 |

【我的理解】引导题（用自己的话回答）：
1. 课程原文提到监控要提供"性能指标**和查询分析**"——为什么"能查询"比"能展示"更重要？
2. 请说明"压测指标与生产指标一致"这条纪律能避免什么后果。

### 知识点3：监控体系的选择（Grafana / Prometheus / Zipkin / SkyWalking）

【课程原话/定义】
课程给出的 4 个体系（原文）：
1. **Grafana**：开源监控仪表盘与图形编辑器，广泛用于可视化时间序列数据；基于统计数据展示报表，是跨平台、开源的数据可视化网络应用平台。配置好数据源后，可在浏览器里显示数据图表和警告；
2. **Prometheus**：开源的系统监控报警框架，主要优势是**多维数据模型**（由指标名称和键/值对标签标识的时间序列数据组成）；生态由多个组件组成，其中 **Prometheus Server 作为服务端，用于存储时间序列数据**；
3. **ZipKin（distributed tracing system）**：开源的分布式实时数据追踪系统，主要功能是聚集来自各个异构系统的实时监控数据，帮助用户解决服务架构中的**延迟问题**；
4. **SkyWalking**：优秀的国产开源框架，专为微服务、云原生架构和容器化技术（Docker、Kubernetes）设计的分布式系统应用性能监视工具，也是一款出色的 **APM（Application Performance Management）** 工具。

【为什么？】
课程把这 4 个放在"体系选择"里，但它们**其实不是同类工具**，需要按"看什么数据"来理解（这是本节最该建立的心智模型）：

| 工具 | 数据形态 | 回答的问题 | 在体系中的角色 |
|---|---|---|---|
| **Prometheus** | **指标（Metrics）** 时间序列 | "系统/服务此刻和趋势如何？" | **采集与存储 + 报警**（服务端） |
| **Grafana** | 可视化层（对接各类数据源） | "把这些数据画成我想要的图" | **展示与分析**（不采集数据） |
| **Zipkin** | **链路（Traces）** 一次请求跨服务的调用链 | "**这一次慢请求**慢在哪个服务的哪一段？" | 分布式追踪（延迟定位） |
| **SkyWalking** | 链路 + 指标 + 拓扑（APM） | "微服务整体健康度、调用拓扑、慢在哪" | APM 全家桶（国产、对 K8s 友好） |

用一句话概括分工：**Prometheus 负责"记数"，Grafana 负责"看图"，Zipkin/SkyWalking 负责"追链路"。** 企业里通常是 **Prometheus + Grafana**（指标可视化，本模块后半要搭的就是这套），链路追踪按需叠加（Java 微服务常用 SkyWalking / Zipkin）。**"指标能告诉你哪里不对劲，链路才能告诉你为什么不对劲"**——这句话也是面试里讲监控体系的加分句。

【必须掌握】

| 体系 | 定位 | 优势（原文） | 典型使用场景 |
|---|---|---|---|
| Prometheus | 系统监控 + 报警框架 | **多维数据模型**（metric 名 + 标签）、自带时序存储与 PromQL | 主机/容器/中间件/业务指标采集与告警 |
| Grafana | 数据可视化与仪表盘 | 跨平台开源、多数据源、图表与告警 | 把 Prometheus/InfluxDB/ES 的数据画成看板 |
| Zipkin | 分布式追踪 | 聚集异构系统实时数据、定位延迟问题 | 微服务调用链延迟分析 |
| SkyWalking | APM（链路 + 指标 + 拓扑） | 国产、面向微服务/云原生/K8s | Java 微服务全栈 APM |

| 概念（【扩展知识】） | 说明 |
|---|---|
| 可观测性三支柱 | **Metrics（指标）+ Logs（日志）+ Traces（链路）**——Grafana/Prometheus 覆盖前两者的一部分，Zipkin/SkyWalking 覆盖 Traces |
| 监控 vs 可观测性 | 监控＝预设指标看阈值；可观测性＝事后用维度自由探索（多维标签 + 查询语言） |
| 落地顺序建议 | 先指标（Prometheus + Grafana）→ 再日志（ELK/Loki）→ 再链路（SkyWalking/Zipkin）；顺序反了成本高收益低 |

【企业场景】
线上告警"下单接口 P99 从 400ms 涨到 2s"。你的定位路径完美体现四个工具的分工：**Grafana** 看板确认现象与时间点 → **Prometheus** 查询（PromQL）该时段的 QPS/CPU/错误率，发现是某个下游依赖 RT 上涨 → **SkyWalking / Zipkin** 点开一条具体慢请求的调用链，看到"调用优惠券服务耗时 1.8s"→ 定位到具体下游与接口。**只靠指标你会知道"慢"，只靠链路你会知道"哪一段慢"，两者结合才有完整结论。**

【面试考察】
面试官："你们监控体系用什么？Prometheus 和 Grafana 是什么关系？"

参考回答框架：
1. 分工：Prometheus 采集与存储指标（时序 + 多维标签 + PromQL + 告警），Grafana 做可视化与看板（可接多种数据源）；两者通常组合使用；
2. 链路追踪（Zipkin / SkyWalking）解决"单次请求慢在哪一段"，覆盖分布式调用链，与指标互补；
3. 三支柱：Metrics / Logs / Traces；落地顺序建议先指标后链路；
4. 结合压测：压测实时看板用 JMeter + InfluxDB + Grafana；生产长期用 Prometheus + Grafana（+ Node Exporter）。

【易错点】

| 常见错误 | 正确理解 |
|---|---|
| 认为 Grafana 也是"采集工具" | Grafana **不采集**数据，它只连接数据源做展示与告警 |
| 认为 Prometheus 能替代链路追踪 | 指标能给"哪不对劲"，定位到"哪一段代码/哪个下游"要靠 Traces |
| 把 Zipkin / SkyWalking 当同类 | Zipkin 是链路追踪；SkyWalking 是 APM（含链路 + 指标 + 拓扑，能力更全） |
| 一上来就上全套（指标 + 日志 + 链路） | 成本高、收益递减；按"先指标 → 再日志 → 再链路"推进 |
| 忽略"压测实时看板"与"生产监控"是两套 | 压测看板常用 JMeter + InfluxDB + Grafana（秒级、短周期）；生产用 Prometheus 长周期 |

【我的理解】引导题（用自己的话回答）：
1. 用"记数 / 看图 / 追链路"三个词，把 Prometheus、Grafana、Zipkin 的职责各写一句话。
2. 为什么"指标能告诉你哪里不对劲，链路才能告诉你为什么不对劲"？请用一个慢请求的例子说明。

### 知识点4：从"监控系统价值"到"压测报告证据"（本模块的落点）

【课程原话/定义】
课程总结（原文）：简介 / 性能监控系统的用处 / 使用场景 / 性能监控体系的选择。

【为什么？】
这一章的知识最终会被用于两件事：**（A）搭起监控（后面 4 章）**、**（B）把监控数据变成压测报告里的证据**。第 B 件事是测开岗的差异化能力，它有三个具体动作：

1. **基线化**：压测前采集空载基线（见 [[Ch38-系统性能数据收集（cpu、mem、net、io）]]），报告里写"压测前 CPU 12%"才有参照；
2. **对齐**：业务指标（JMeter TPS/RT/错误率）与资源指标（Prometheus/脚本采集）在同一时间轴；
3. **结论化**：把数据翻译成"瓶颈在哪、能不能扩、红线在哪"——**报告不是数据搬运，而是判断**。

另外要记住一个"监控系统自身"的工程约束：**监控系统不能成为新的单点**。它挂了，你的压测就瞎了。所以生产/压测环境里，监控组件的部署、容量、采集间隔都要提前想清（本模块后面用 Docker 搭，也正因为它轻量、好复制）。

【必须掌握】

| 动作 | 具体做法 | 报告里的呈现 |
|---|---|---|
| 基线化 | 压测前采空载 + 记录机器规格 | "基线 CPU 12%、空载 RT 80ms" |
| 对齐 | 记录压测窗口；业务与资源曲线同轴 | "并发到 300 时 TPS 停止增长，同时 CPU us 达 85%" |
| 结论化 | 从数据到判断（瓶颈层、扩容建议、红线） | "瓶颈在应用 CPU，建议扩 2 核或优化热点方法再压" |
| 兜底 | 监控组件自身可用性（别让它成为单点） | 报告注明"采集方式与工具版本" |

【企业场景】
压测报告的"结论页"如果写成这样，评审会一次通过：**"并发 300 为拐点（TPS 4500 不再增长）；此时被测机 CPU us 85%、wa 3%、内存 available 1.1G、磁盘 %util 22%；施压机资源占用 40%。结论：瓶颈位于应用 CPU（非 IO、非磁盘、非施压机），建议按 CPU 扩容至 2 倍核数可获得约 1.8 倍吞吐，扩容后需回归验证。"** ——它把监控数据的四类指标、施压机侧排除、量化建议全都用上了，**每一句都能追溯到数据**。

【面试考察】
面试官："你压测报告里的容量结论是怎么得出来的？"

参考回答框架：
1. 数据来源：基线（压测前）+ 压测中业务指标（JMeter）+ 资源指标（采集脚本/Prometheus）；
2. 分析方法：时间对齐后找拐点（TPS 走平/RT 抬升的那一刻），看该时刻四类指标的状态，排除施压机与 IO/Disk/网络干扰；
3. 结论形式：瓶颈层 + 量化建议（扩容/优化）+ 红线与触发条件（而不是一个孤立数字）；
4. 复核：保留原始采集文件，结论可追溯；有条件的用监控看板直接展示。

【易错点】

| 常见错误 | 正确理解 |
|---|---|
| 报告只有业务指标（TPS/RT），没有资源数据 | 无法说明瓶颈在哪，"容量结论"站不住 |
| 有资源数据但没基线 | 无法判断高低；"CPU 85%"到底算不算饱和要看业务与机器 |
| 结论只给一个数（"能扛 5000"） | 要给"区间 + 红线 + 触发条件"，否则业务方无法使用 |
| 忘记在报告里注明采集方式 | 结论无法复核；数据来源与工具版本都要写 |
| 假设监控系统永远可用 | 监控自身也要有冗余/降级预案，否则压测会被它拖下水 |

【我的理解】引导题（用自己的话回答）：
1. 请把"基线化 → 对齐 → 结论化"三步，用你自己项目里的一句话举例说明。
2. 为什么"只写 TPS 一个数字"的报告会被评审打回？合格的容量结论应该包含哪三样东西？

### 知识点5：本模块路线图（从价值到落地）

【课程原话/定义】
（原文未涉及；本节整理本模块的组织逻辑，方便按图学习。）

【为什么？】
知道"为什么做"之后，接下来 4 章是一条完整的动手链，顺序不要乱：

| 顺序 | 章节 | 解决的问题 | 产出 |
|---|---|---|---|
| 1 | 本章（性能监控系统价值） | 为什么要有、选什么 | 选型判断（Prometheus + Grafana） |
| 2 | [[Ch40-搭建服务端性能监控系统Prometheus]] | 指标从哪来、存哪 | 可访问的 Prometheus（9090） |
| 3 | [[Ch41-搭建数据分析系统Grafana]] | 怎么看、怎么画 | 可访问的 Grafana（3000）+ 数据源 |
| 4 | [[Ch42-Prometheus监控系统部署应用实战]] | 主机/容器指标怎么进体系 | Node Exporter（9100）+ Grafana 看板 |
| 5 | [[Ch43-jmeter实时压测结果收集]] | **压测结果**怎么实时看 | JMeter + InfluxDB + Grafana 实时看板 |

**这条链的价值**：压完一轮你能拿出"实时看板 + 历史数据 + 结论"，而不是"一张跑了 30 分钟的聚合报告截图"。面试讲"我搭过 Prometheus + Grafana + Node Exporter，并且把 JMeter 结果实时写进 InfluxDB 出看板"——这是能直接写进简历的具体动作。

【必须掌握】

| 组件 | 端口（常见） | 角色 | 一句话 |
|---|---|---|---|
| Prometheus | 9090 | 采集 + 存储 + 查询 + 告警 | 记数与算账的 |
| Node Exporter | 9100 | 暴露主机指标 | 服务器指标的"接口" |
| Grafana | 3000 | 可视化 + 看板 | 画图与盯盘的 |
| InfluxDB | 8086 | 时序数据库（压测实时结果用） | JMeter 结果的"临时账本" |
| JMeter Backend Listener | — | 把压测结果推给 InfluxDB | 压测数据的"出口" |

【企业场景】
把这 5 步组合成一个交付物：**"压测实时观测看板"**——大屏上同时有 TPS/RT 曲线（来自 JMeter → InfluxDB）、被测机 CPU/内存/IO（Node Exporter → Prometheus）、错误率告警线（Grafana Alert）。压测时全组一起盯大屏，问题发生时立刻定位；压完把看板截图 + 数据导出一起放进报告。**这套东西搭一次可以复用所有项目**，是投简历时最能体现"工程化能力"的作品之一。

【面试考察】
面试官："你说你会监控，具体搭过什么？"

参考回答框架：
1. 体系：Prometheus（9090，采集存储查询告警）+ Node Exporter（9100，主机指标）+ Grafana（3000，看板）；
2. 压测侧：JMeter Backend Listener → InfluxDB（8086）→ Grafana 实时看板（TPS/RT/错误率）；
3. 用法：压测中用看板实时判断拐点与瓶颈层，压后归档数据与截图；
4. 加分：能说明采集间隔、数据保留周期、告警阈值设定依据，以及"看板指标与生产口径一致"。

【易错点】

| 常见错误 | 正确理解 |
|---|---|
| 按站点目录顺序跳着学（先学压测收集再学搭建） | 应先有 Prometheus/Grafana（第 2、3 步）再做整合（第 4、5 步），否则无法验证 |
| 组件都跑在同一台被压机器上 | 监控组件自身会占资源，污染被测指标；条件允许应分离部署 |
| 端口/配置随手写，不留记录 | 换机器重建时全靠回忆；应把 `docker run` 命令与配置文件留档 |
| 认为"搭起来就完了" | 数据保留、间隔、告警阈值、权限都要配置，否则看板只是"好看" |
| 不看数据保留周期 | Prometheus/InfluxDB 默认保留期有限，压测历史数据会过期，重要数据要导出 |

【我的理解】引导题（用自己的话回答）：
1. 为什么建议"先搭 Prometheus/Grafana，再做 Node Exporter 与压测看板"？顺序反了会遇到什么麻烦？
2. 请把本模块 5 章的产出各写一句话（每句话都要是一个"可验证的东西"）。
