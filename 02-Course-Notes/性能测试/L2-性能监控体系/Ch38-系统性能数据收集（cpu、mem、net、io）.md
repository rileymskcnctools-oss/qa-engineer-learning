### 知识点1：性能监控是什么，为什么"收集"是监控的前置条件

【课程原话/定义】
Linux 系统提供了许多查看性能属性的命令，掌握这些命令能更好地监控 Linux 系统的运行状况；熟练掌握 Linux 关于性能监控的命令，能让我们更好地掌控 Linux 的运行状况。

性能监控是指对系统、应用程序或网络的运行状态进行实时监测、收集和分析关键性能指标的过程。通过性能监控，可以及时了解系统资源的利用情况、进程调度状态以及性能瓶颈等问题。

通常关注的重要指标：**CPU 利用率、内存利用率、磁盘吞吐量以及网络带宽利用率**。

课程给出的"为什么要监控系统性能"（原文 6 条）：
1. **问题诊断与预防**：定位性能瓶颈、资源瓶颈或系统错误，持续监控可在问题发生前预防；
2. **资源优化**：了解 CPU、内存、磁盘、网络的使用情况，判断资源是否被有效利用、是否需要增减；
3. **容量规划**：分析历史数据预测未来需求，避免资源不足或过剩；
4. **服务质量保证**：监控响应时间、吞吐量等指标，确保满足用户需求；
5. **合规性与安全性**：满足合规要求、发现异常行为与未授权访问；
6. **持续改进**：持续分析比较数据，不断发现改进点。

【为什么？】
注意这几个词的顺序：**"监测、收集、分析"**。课程定义里"收集"排在"分析"之前——**没有持续收集，就没有可用于分析的基线**。这正是 L1（Ch35）与 L2（本章）的分工：

- L1 教会你"敲一条命令、看懂一屏输出"——这是**瞬时快照**；
- 本章/本模块要解决的是"**压测那 30 分钟里，每一步的 CPU/内存/IO/网络是什么样**"——这只能是**时间序列**。

一次压测的价值，90% 体现在"能不能拿出与业务指标对齐的资源曲线"。举例：报告写"TPS 在并发 300 时停止增长"意义有限；写成"**并发 300 时被测机 CPU 的 us 达到 85%、sy 稳定、wa 从 3% 升到 8%，而磁盘 %util 只有 20%——瓶颈在应用 CPU 而非磁盘**"，才是可交付的结论。而这条结论完全依赖"**在正确的时间点、以正确的间隔、收集了正确的指标**"。

所以本页三句原文（问题诊断、容量规划、持续改进）在工程上等价于一句要求：**收集要持续、要可对齐、要能留存**。

【必须掌握】

| 监控意义（原文 6 条） | 对"收集"的具体要求 |
|---|---|
| 问题诊断与预防 | 采集间隔 ≤ 现象时间尺度（RT 抖动是秒级，采集就别用 60s） |
| 资源优化 | 指标要覆盖四类（cpu/mem/io/net），并含饱和度类字段（%util、r、si/so） |
| 容量规划 | 要有**历史数据**（跨压测轮次可比），因此数据要落盘/落库 |
| 服务质量保证 | 业务指标（RT/TPS/错误率）与资源指标**同一时间轴** |
| 合规与安全 | 采集内容与访问范围合规（生产采集要授权、脱敏） |
| 持续改进 | 有基线才有改进；每次压测前记录基线，压完对比 |

| 层次 | 回答的问题 | 工具/形态 |
|---|---|---|
| 瞬时快照（L1） | 现在什么情况？ | `vmstat` / `top` / `iostat` 手动敲 |
| **持续收集（本章）** | **整个压测窗口内怎么变化？** | 脚本定时采集 + 落文件/落库 |
| 系统化监控（L2 后半） | 怎么长期、多机、可视化？ | Prometheus + Node Exporter + Grafana |

【企业场景】
压测前的一个必做动作：**采集基线 + 确认采集链路可用**。做法：压测开始前 10 分钟启动采集脚本（`vmstat 5`、`iostat -x 5`、`free -m`、`ss -s` 各自落文件），确认文件在长、时间戳正常；压测期间不动它；压测结束后立刻停止采集并归档。**很多团队压测后才发现"忘了采数据"，于是只能重压一轮**——采集这件事的价值就在于"它必须提前准备好，而不能事后补"。

【面试考察】
面试官："压测时资源数据你怎么收集？为什么不能事后补？"

参考回答框架：
1. 分层：瞬时排查用 vmstat/top/iostat 手敲；**压测期间必须持续采集**（脚本定时 + 落文件/落库），并与业务指标对齐时间轴；
2. 采集内容：四类指标 + 饱和度字段（r、%util、await、si/so、TIME_WAIT）；
3. 为什么不能事后补：性能现象是瞬时的，事后无法复现；没有基线也无法判断"变化了多少"；
4. 进阶：多机、长期、可视化的采集交给 Prometheus + Node Exporter（本模块后续页），手工采集只用于补充与验证。

【易错点】

| 常见错误 | 正确理解 |
|---|---|
| 压测完才想到要看资源数据 | 采集必须**提前开始、覆盖整个压测窗口**，事后无法补 |
| 采集间隔太大（如 60s） | RT 抖动、瞬时队列是秒级现象；关键指标建议 1~5s |
| 只采平均值、不采峰值字段 | 排队（r）、饱和度（%util）、换页（si/so）才是瓶颈证据，平均值会掩盖它们 |
| 业务指标与资源指标时间不对齐 | 报告里要能说"TPS 掉的那一刻 CPU 在干什么"；时间对齐是分析前提 |
| 在生产环境随意起采集脚本 | 采集有开销且涉及权限/合规，需授权并评估影响（压测机不要用来采集被测机数据以外的负担） |

【我的理解】引导题（用自己的话回答）：
1. 用"瞬时快照 vs 时间序列"解释：为什么 L1 学了命令，L2 还要专门讲"数据收集"？
2. 请说明"采集间隔"应该由什么决定，而不是随手定一个数。

### 知识点2：四条数据链的采集命令（命令清单原文完整保留）

【课程原话/定义】
Linux 系统性能监控命令（原文清单，完整保留）：
- `iostat 1 5` —— 参数 1 5 表示每隔 1s 查询一次，总共查询 5 次；用于监控设备的 IO 负载情况；
- `df -h` —— 列出文件系统的整体磁盘空间使用情况；
- `uptime` —— 用于显示系统总共运行了多长时间和系统的平均负载；
- `cat /proc/cpuinfo` —— 查看 CPU 的配置信息；
- `mpstat -P ALL` —— 在多核 CPU 中查询每个核的性能；
- `cat /proc/cpuinfo` —— 查看 CPU 的配置信息（原文此处重复）；
- `sar -u 1 1` —— Linux 的监控工具，用来监控 CPU 性能；每隔一秒监控一次，总共监控 1 次；
- `cat /proc/meminfo` —— 查看内存相关配置信息；
- `vmstat` —— 用来获得有关进程、内存、虚拟内存、页面交换空间及 CPU 活动等信息；
- `free -g` —— 显示系统使用和空闲内存情况，包括物理内存、交换区内存；`-g` 将单位换算为 G；
- `ping` —— 查询是否和某个地址连通；
- `ifconfig` —— 用于获取网卡配置和网络信息；
- `hostname` —— 显示本地用户信息（⚠️ 勘误：应为**主机名**）；
- `hostname -i` —— 显示本地 IP 地址；
- `netstat -an / -at / -aun / -p` —— 用于显示各种网络相关信息。

【为什么？】
把清单按"四条数据链"重新组织，就能直接变成**采集脚本的字段表**——这是本章把提纲变成可执行资产的方式。每条链回答一个资源问题：

| 数据链 | 采集命令（原始间隔） | 采集到的关键字段 | 一句话用途 |
|---|---|---|---|
| **CPU** | `uptime`、`vmstat 1`、`mpstat -P ALL 1`、`sar -u 1 1`、`cat /proc/cpuinfo` | load average（1/5/15）、`us/sy/id/wa`、每核 `%usr/%sys/%iowait`、`r`、`cs`、核数 | 判断是否 CPU 饱和 / 是否单核打满 / 是否在等 IO |
| **MEM** | `free -m`（原文 `-g`）、`vmstat`、`cat /proc/meminfo` | available、swap used、`si/so`、MemAvailable、Cached | 判断内存是否紧张 / 是否在换页 |
| **IO** | `iostat -x 1`（原文 `iostat 1 5`）、`df -h` | `%util`、`await`、`r/s`、`w/s`、`kB_read/s`、`kB_wrtn/s`、Use% | 判断存储是否饱和 / 空间是否够 |
| **NET** | `ping`、`ifconfig`（或 `ip -s link`）、`hostname -i`、`netstat -antp` / `ss -antp` | 延迟、丢包、收发字节、错包、连接状态计数（ESTABLISHED/TIME_WAIT） | 判断网络质量 / 是否连接数或端口耗尽 |

**采集间隔建议（经验值，非课程内容）**：业务压测窗口内 CPU / 内存 / IO 用 **1~5 秒**；网络连接状态用 **5~10 秒**；`df -h`、`cpuinfo`、`meminfo` 这类"配置/容量"信息**开始时采一次即可**（它们是环境基线，不会在压测中变化）。

【必须掌握】

| 命令 | 采集频率 | 关键字段 | 别忘的坑 |
|---|---|---|---|
| `vmstat 1` | 1s（最常用） | r/b、si/so、us/sy/id/wa、cs/in | 第一行是开机以来均值，分析时跳过 |
| `iostat -x 1` | 1~5s | `%util`、await、r/s、w/s | 同样第一行是历史均值；`svctm` 新版本已废弃 |
| `mpstat -P ALL 1` | 1~5s（按需） | 每核 %usr/%sys/%iowait/%idle | 只在怀疑"单核打满"时开，输出量大 |
| `free -m` | 5~10s | available、Swap used | 看 available 不看 free |
| `sar -u 1` + 历史 | 1s，或直接读 `/var/log/sa` | %user/%system/%iowait | 事后复盘利器（提前开启采集才有历史） |
| `netstat -antp` / `ss -antp` | 5~10s | 各状态连接计数、TIME_WAIT | 大连接数时用 `ss`；`-n` 必加 |
| `uptime` | 5~10s | load average | 与核数（`nproc`）一起记录，否则无法判读 |
| `df -h` / `cat /proc/cpuinfo` / `cat /proc/meminfo` | 开始一次 | 容量、核数、内存总量 | 属于**环境基线**：报告里必须体现"压的是什么配置的机器" |

【企业场景】
一次真实的压测复盘之所以能定位到"GC 导致的停顿"，是因为采集脚本同时落了三份数据：① `vmstat 1` 的 `wa/si/so/r`；② 被测进程的 `top -b -n 1 -p <PID>`（CPU/RES）；③ 应用日志里的 GC 记录。**三份数据时间对齐后**，能看到"GC 日志出现的同一秒，`%Cpu(s)` 的 `sy` 尖刺、`r` 排队上升、RT 出现毛刺"。如果只采了 CPU 使用率（而且是 60 秒平均），这条结论就永远拿不到。

【面试考察】
面试官："压测期间你采集哪些数据？用什么命令、什么间隔？"

参考回答框架：
1. 四条链：CPU（vmstat/mpstat/sar/uptime）、MEM（free/vmstat/meminfo）、IO（iostat -x、df）、NET（ss/netstat、ifconfig、ping）；
2. 间隔：业务指标秒级 → 采集 1~5s；配置类（cpuinfo/meminfo/df）开始采一次当基线；
3. 字段：优先采"饱和度与排队"类（r、%util、await、si/so、TIME_WAIT），平均值会掩盖问题；
4. 纪律：提前启动、全程覆盖、与业务指标时间对齐、结束后归档；多机长期采集交给 Prometheus + Node Exporter。

【易错点】

| 常见错误 | 正确理解 |
|---|---|
| 用 vmstat/iostat 的**第一行**做分析 | 第一行是"自开机以来"的均值，必须跳过或用 `-y` |
| 采集时不记核数 / 内存总量 | 没有基线（几核、多少内存）无法判断 85% 是"快满"还是"正常" |
| `free -g` 只看 free 列 | 看 available；`-g` 粒度太粗，排错用 `-m` |
| `netstat` 不加 `-n`，或在大连接数场景硬用 netstat | 不加 `-n` 会解析且变慢；大连接数用 `ss` 更快更准 |
| 采集窗口与压测窗口不重合 | 结果无法解释；采集要"提前开始、压完再停"并记录时间戳 |

【我的理解】引导题（用自己的话回答）：

### 知识点3：从"人工敲命令"到"系统化采集"（脚本化 / 落库 / 与 Prometheus 衔接）

【课程原话/定义】
（原文未涉及，本节把"数据收集"这件事做完——它正是本页标题的含义。）

【为什么？】
人工敲命令有三个致命限制：**人不能连续 30 分钟每 5 秒敲一次；多台机器无法同时看；输出不成时间序列**。所以"数据收集"必须升级成三种形态，按成本从低到高：

1. **脚本化采集**（最低成本，压测必备）：用一行 shell 把命令按固定间隔写入带时间戳的文件——
   - `vmstat 5 >> vmstat.log`（vmstat 自带间隔，最省事）
   - `while true; do date +%T >> iostat.log; iostat -x 5 1 >> iostat.log; sleep 5; done`（需要自己补时间戳）
   - 被测进程维度：`top -b -n 1 -p <PID> >> proc.log`（见 [[../L1-服务端统计工具/Ch36-top命令使用|Ch36]]）
2. **定时采集 + 落库**（中等成本）：`sar`/`sadc` 本身就是"定时采集落盘"的系统方案（`/var/log/sa`），可以事后按时间段回看；企业里也常用脚本把指标写进 InfluxDB / MySQL，便于画图和对比。
3. **监控系统采集**（推荐长期方案）：**Prometheus 拉取 Node Exporter 暴露的指标**（`localhost:9100/metrics`），四类指标齐全、自带时间序列存储与查询语言，Grafana 出图——这正是本模块后续章节（[[Ch40-搭建服务端性能监控系统Prometheus]]、[[Ch42-Prometheus监控系统部署应用实战]]）的内容。

**为什么压测仍然需要第 1 种（脚本采集）？** 因为压测窗口短、需要"立刻能拿到证据"，而 Prometheus 常见的 15~60s 抓取间隔对某些毛刺不够细；两者配合最好：**Prometheus 看整体趋势，脚本采集抓秒级细节**。这也是官方那句"提前把数据准备好"（见 [[../L2-JMeter参数化与并发/Ch34-JMeter参数化csv|Ch34]]）在监控侧的同一思路——**采集也要提前准备，而不是事发才动手**。

【必须掌握】

| 形态 | 成本 | 优点 | 局限 | 典型工具 |
|---|---|---|---|---|
| 脚本采集 | 极低 | 秒级细节、立刻可得、无需依赖 | 需手工管理、不易多机统一 | `vmstat`/`iostat`/`top -b` + 重定向 |
| 定时采集落盘/落库 | 中 | 可历史回看、可跨轮次对比 | 需配置与维护 | `sar`/`sadc`、采集脚本 + InfluxDB |
| 监控系统 | 中高 | 多机、长期、自带查询与告警、可视化 | 部署成本、抓取间隔较粗 | Prometheus + Node Exporter + Grafana |

| 采集要落到哪个粒度 | 建议 |
|---|---|
| 系统级（整机） | vmstat / iostat / free / ss（脚本或 Node Exporter） |
| 进程级 | `top -b -n 1 -p PID` / `ps`（脚本，秒级） |
| 应用级 | 应用自带的 metrics（JMX / actuator / 日志），与系统指标时间对齐 |
| 中间件/DB | 各自的内置监控（连接数、慢查询、命中率），别只看系统层 |

【企业场景】
一次压测的采集方案（可直接照抄）：压测前 10 分钟，在被测机上启动 3 个后台采集：① `vmstat 5 >> /tmp/perf/vmstat.log`；② `iostat -x 5 >> /tmp/perf/iostat.log`；③ `while true; do date +%T >> /tmp/perf/ss.log; ss -s >> /tmp/perf/ss.log; sleep 10; done`；同时在施压机上开 `top -b -n 1 -p <jmeterPID>` 记录施压机自身负载。压测结束后归档整个 `/tmp/perf/`。**面试里能把这张"采集清单"说出来，比背 10 条命令更有说服力**——因为它体现的是"数据可信度"意识。

【面试考察】
面试官："你会怎么系统地收集压测期间的性能数据？"

参考回答框架：
1. 三层粒度：系统级（vmstat/iostat/free/ss）、进程级（top -b -p PID / ps）、应用级（JMX/actuator/日志）；
2. 三种形态：脚本采集（秒级、压测必备）→ 定时采集落库（如 sar/InfluxDB）→ 监控系统（Prometheus + Node Exporter + Grafana，多机长期）；
3. 关键纪律：提前启动、全程覆盖、时间戳对齐、压完归档；Prometheus 抓取间隔较粗时用脚本补细节；
4. 收口：采集的目的是让报告结论"可追溯、可复核、可对比"。

【易错点】

| 常见错误 | 正确理解 |
|---|---|
| 只靠监控系统（15~60s 间隔）就下"毛刺"结论 | 抓取间隔可能漏掉秒级尖刺；高压场景配秒级脚本采集 |
| 采集脚本没有时间戳 | 无法与业务指标对齐（`vmstat`/`iostat` 首行陷阱同理） |
| 在被测机上同时跑压测工具与采集 | 采集本身有开销，且会污染指标；施压机与被测机分离是基本纪律 |
| 采集输出塞进同一个大文件，事后无法定位 | 按指标分文件；每行带时间戳；记录压测起止时间 |
| 采完不归档、不写进报告 | 数据没有进入交付物，等于没采 |

【我的理解】引导题（用自己的话回答）：
1. 为什么说"Prometheus 抓取间隔较粗"时要补脚本采集？请举一个会被漏掉的场景。
2. 请写出你会用的三条采集命令（含间隔与输出文件），并说明各自覆盖哪条数据链。

### 知识点4：采集纪律——时间对齐、基线、开销与容器视角

【课程原话/定义】
（原文未涉及，本节是"数据收集"的工程约束。）

【为什么？】
采集的产出只有"能对比"才有意义，而"能对比"依赖四个前提，缺一个结论就会被打脸：

1. **时间对齐**：业务侧（JMeter 的 TPS/RT 时间序列）与资源侧必须能对上。**压测开始/结束时间、机器时间是否同步（NTP）都要记录**——两台机器差 3 分钟，曲线就永远对不上，结论会被质疑。
2. **基线**：压测前记录"空载基线"（空闲时的 CPU/内存/连接数）。**没有基线，你说不清"85% 是高还是正常"**——有些服务空载 CPU 就 30%。
3. **采集开销**：采集本身消耗资源（尤其 `mpstat -P ALL`、高频 `top -b`、大连接数下的 `netstat`）。**施压机绝不要兼做高频采集**，否则施压机先瓶颈；被测机上采集也要控制频率。
4. **容器/虚拟化视角**：容器里看到的 CPU/内存是 **cgroup 限制**下的视角，宿主 `free` 有余量也可能被 OOM Kill；虚拟机上 `st`（被宿主抢占）会污染一切指标。**排查前先确认"你在哪一层看数据"**。

【必须掌握】

| 纪律 | 具体动作 | 缺失后果 |
|---|---|---|
| 时间对齐 | 记录压测起止时间；机器对时（NTP）；采集行带时间戳 | 曲线对不上，结论无法成立 |
| 基线 | 压测前采集空载数据；记录机器规格（核数/内存/磁盘类型） | 无法判断指标高低，无法解释变化 |
| 开销控制 | 采集放独立机器或低频率；避免 `mpstat -P ALL` 高频跑 | 采集本身成为瓶颈，指标失真 |
| 层次确认 | 容器（cgroup）、虚拟机（st）、物理机分别看 | 误判容量（如"内存够"却 OOM） |
| 归档与可复核 | 原始文件保留、命令与版本记录 | 报告无法复核，问题无法复盘 |

【企业场景】
一次事故复盘：压测结论是"数据库不是瓶颈"，因为 DB 机器 CPU 只有 20%。复盘时被指出——**DB 跑在容器里且 CPU limit 设得很低**，`docker stats` 显示它长期贴着 limit 跑，宿主机 CPU 却不忙。**容器视角 vs 宿主机视角，直接把结论推翻了。** 这就是"先确认你在哪一层看数据"的价值；也解释了为什么 L2 后面要专门上 Prometheus + Node Exporter：**它按实例采集，视角明确**。

【面试考察】
面试官："你采集的数据凭什么让人相信？"

参考回答框架：
1. 时间对齐：业务与资源指标同一时间轴，机器对时、采集带时间戳、记录压测起止；
2. 基线：空载数据 + 机器规格（核数/内存/盘型），使"高/低"有参照；
3. 开销：采集不污染被测与施压（分离部署、控制频率）；
4. 层次：容器 cgroup 限制、虚拟机 st、物理机区分清楚，避免视角错误；
5. 归档：原始文件留存，结论可复核；多机长期采集用 Prometheus + Node Exporter。

【易错点】

| 常见错误 | 正确理解 |
|---|---|
| 认为"采了数据"就等于"数据可信" | 时间不对齐、无基线、有采集开销、视角错误，都会让数据不可信 |
| 把容器里的 CPU% 当宿主机占用 | 容器看的是 cgroup 视角；宿主可能很空闲，也可能因 limit 早就打满 |
| 在被测机上跑高频采集脚本 | 采集开销会污染指标；高压场景应把采集放独立机器 |
| 忽略 NTP/机器时间 | 跨机曲线对不上；需要记录并校准时间 |
| 只采一次、不留原始文件 | 无法复核；问题复盘时说不清"当时到底是多少" |

【我的理解】引导题（用自己的话回答）：
1. 请用一句话说明"基线"解决了什么问题，并举例（有基线 vs 没基线的两种结论）。
2. 为什么"DB 机器 CPU 只有 20%"不能直接证明"DB 不是瓶颈"？你会补查什么？

### 知识点5：实操——写一份压测采集脚本并验证

【课程原话/定义】
（原文未涉及；本节把本章知识变成可交付动作。）

【为什么？】
本章的知识只有变成**一份能在 5 分钟内启动的采集脚本 + 一份归档目录**，才算真正掌握。以下是可直接使用的骨架（Linux 执行）：

```bash
# 压测采集骨架：四链 + 进程级，全部带时间戳
DIR=/tmp/perf-$(date +%Y%m%d-%H%M); mkdir -p "$DIR"
nproc > "$DIR/baseline.txt"; free -m >> "$DIR/baseline.txt"; df -h >> "$DIR/baseline.txt"
echo "start: $(date +%F' '%T)" > "$DIR/window.txt"

vmstat 5 > "$DIR/vmstat.log" &            # CPU/内存/队列：r b si so us sy id wa cs
iostat -x 5 > "$DIR/iostat.log" &          # 磁盘：%util await r/s w/s
( while true; do date +%T; ss -s; sleep 10; done ) > "$DIR/net.log" &   # 网络连接状态
( while true; do date +%T; top -b -n 1 -p "$TARGET_PID" | tail -12; sleep 5; done ) > "$DIR/proc.log" &
# 压测结束：echo "end: $(date +%F' '%T)" >> "$DIR/window.txt"; kill %1 %2 %3 %4; tar czf "$DIR.tgz" "$DIR"
```

验证要点（做完必须逐条确认）：
1. 四个 `.log` 文件都在增长，且行里有时间戳；
2. `baseline.txt` 里有核数、内存、磁盘容量（后面判读要用）；
3. `window.txt` 的 start/end 与 JMeter 报告的起止时间一致（时间对齐）；
4. 压测中不要开 `mpstat -P ALL` 这类高频命令；
5. 采完立即归档（tar）并复制到压测报告目录。

【必须掌握】

| 动作 | 命令要点 | 产出 |
|---|---|---|
| 记录基线 | `nproc`、`free -m`、`df -h`、`cat /proc/cpuinfo \| head` | baseline.txt（判读参照） |
| 采集四链 | `vmstat 5`、`iostat -x 5`、`ss -s` 循环、`top -b -p PID` 循环 | vmstat.log / iostat.log / net.log / proc.log |
| 标记窗口 | start/end 时间写入 window.txt | 与 JMeter 报告对齐的依据 |
| 采集纪律 | 采集机与被测/施压分离；控制频率 | 数据不被采集自身污染 |
| 归档 | `tar czf` 归档 + 复制进报告 | 可复核的证据链 |

【企业场景】
把这份脚本固化进团队的"压测执行手册"：**每次压测第一件事就是跑它**，压完自动归档到 `报告目录/perf-<时间戳>.tgz`。半年后回看某次性能回归，可以拿两次的 `vmstat.log` 直接对比"同一并发下 wa 从 3% 涨到 12%"——**这就是"持续改进"（原文第 6 条意义）落到实处的样子**：数据留得住，改进才有依据。

【面试考察】
面试官："说说你压测时的数据采集流程。"

参考回答框架：
1. 准备：记录基线（核数/内存/盘型）、确认对时、准备归档目录；
2. 采集：四链脚本（vmstat/iostat/ss/进程级 top）+ 业务指标（JMeter）；
3. 纪律：采集与施压分离、频率适度、全程覆盖、时间对齐；
4. 归档与复用：tar 归档进报告，跨轮次可对比；长期多机交给 Prometheus + Grafana；
5. 收口：能说出"数据怎么支撑结论"，而不只是"我采集了"。

【易错点】

| 常见错误 | 正确理解 |
|---|---|
| 脚本里没有 start/end 时间 | 无法与业务指标对齐，数据等于废纸 |
| 采集写在 `.log` 却不归档 | 临时目录被清理后证据丢失；必须 tar + 复制进报告目录 |
| 忘记录基线（核数/内存/盘型） | 报告无法说明"压的是什么规格的机器"，结论无法复用 |
| 采集与被测服务同机高频运行 | 采集开销污染指标（尤其 CPU/IO 密集命令） |
| 只在压测中途开始采集 | 缺少前段与后段数据，无法观察趋势与回落 |

【我的理解】引导题（用自己的话回答）：
1. 请写出你会在 `window.txt` 里记录的两种时间，并说明它们各自用来对齐什么。
2. 如果团队只允许一处采集（要采施压机还是被测机），你会怎么选？为什么？
