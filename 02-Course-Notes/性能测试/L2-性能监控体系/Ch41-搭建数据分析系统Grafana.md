### 知识点1：Grafana 是什么，它在监控体系里的位置

【课程原话/定义】
Grafana 是一个开源的数据可视化工具，它可以从 **Prometheus 等数据源**中读取数据，并将其展示为各种图表和仪表盘。以其灵活的可视化、强大的报警和通知功能、以及混合数据源的支持等特点，使得它在各种场景中都能够发挥重要的作用。

课程给出的"grafana 应用场景"（原文 7 条）：
1. **服务器监控**：收集 CPU 使用率、内存使用率、磁盘使用情况等并可视化；
2. **应用性能监控**：收集响应时间、错误率、吞吐量等，帮助快速定位性能问题；
3. **物联网设备监控**：传感器数据（温度、湿度、光照）实时展示；
4. **时间序列数据与应用程序分析的可视化**：基础设施可视化、工业传感器、家庭自动化、天气与过程控制等领域；
5. **云产品数据可视化**：配合预置的云产品监控插件，可视化 CVM、云数据库、CKafka、Redis 等组件数据；
6. **全栈监控可视化**：对接云上或自建的 Prometheus，实现从技术架构监控、组件监控到业务自定义监控的全栈监控；
7. **日志数据可视化**：对接 Elasticsearch 与日志服务（CLS），实现日志数据可视化。

【为什么？】
一句话记住 Grafana 的定位：**它是"眼睛"，不是"手"**——Grafana **不采集数据、不存储数据**，它只做一件事：**把别人存好的数据查询出来、画成图、并在达标/越界时告警**。

所以它和 [[Ch40-搭建服务端性能监控系统Prometheus]] 的关系是**分层且解耦**的：

| 层 | 组件 | 职责 |
|---|---|---|
| 采集与存储 | Prometheus（+ Exporter） | 抓指标、存时序、提供 PromQL 查询 |
| 展示与告警 | **Grafana** | 连数据源、出面板/看板、配置阈值告警 |
| 数据源（可多个） | Prometheus / InfluxDB / Elasticsearch / MySQL… | Grafana 的"数据来源"，一个看板可混用多源 |

这种解耦带来两个实际好处，也是原文第 6、7 条（全栈可视化、日志可视化）的由来：
1. **一个看板能混搭多种数据源**：压测场景下最常见的组合就是"**TPS/RT 来自 InfluxDB（JMeter 写入）+ CPU/内存来自 Prometheus**"——同一屏上业务与资源对齐，这在排查时极其关键；
2. **换后端不用换前端**：数据源从 Prometheus 换成其他时序库，看板基本可复用（企业里用到云厂商监控时很实用，对应原文第 5 条）。

【必须掌握】

| Grafana 的能力（原文 7 条场景） | 本质能力 |
|---|---|
| 服务器监控 / 应用性能监控 / 物联网监控 | 时间序列可视化（折线、统计、热图、表格） |
| 时间序列与工业/家庭场景分析 | 通用数据可视化平台（不限运维领域） |
| 云产品数据可视化 | 插件化数据源（云厂商监控插件） |
| 全栈监控可视化 | 多数据源统一看板（指标 / 日志 / 业务） |
| 日志数据可视化 | 对接 ES / Loki 等日志数据源 |

| 关键认知 | 说明 |
|---|---|
| Grafana 不采集也不存储 | 没有 Prometheus/InfluxDB 等数据源，Grafana 就是空壳 |
| 数据源可多个 | 一个看板能混用（压测常用：InfluxDB 业务 + Prometheus 资源） |
| 面板（Panel）是基本单元 | 多个面板组成 Dashboard（看板） |
| 告警（Alerting）在图之外 | 除画图外还能按阈值/规则触发通知 |

【企业场景】
大促值班大屏的构成就是 Grafana 的典型用法：左上角"总 QPS/成功率的**统计图**"、中间"RT 分位值（P95/P99）**折线**"、右侧"应用机 CPU/内存 Top**表格**"、底部"错误率**燃尽图/告警状态**"。其中 RT、QPS 来自 InfluxDB（JMeter 实时写入，见 [[Ch43-jmeter实时压测结果收集]]），CPU/内存来自 Prometheus + Node Exporter（见 [[Ch42-Prometheus监控系统部署应用实战]]）——**一块大屏 = 多数据源 + 多面板类型**，这正是 Grafana 的价值所在。

【面试考察】
面试官："Grafana 是什么？它和 Prometheus 是什么关系？"

参考回答框架：
1. 定位：开源数据可视化与告警平台，**不采集、不存储**，只连接数据源做查询、绘图、告警；
2. 与 Prometheus 的关系：Prometheus 负责采集/存储/查询（PromQL），Grafana 把它作为**数据源**消费；一个看板可混用多个数据源；
3. 常用能力：面板（折线/统计/表格/热图）、变量（筛选实例/接口）、阈值告警；
4. 落地：压测看板常用"Prometheus（资源）+ InfluxDB（JMeter 业务指标）"双源。

【易错点】

| 常见错误 | 正确理解 |
|---|---|
| 以为 Grafana 自带数据采集 | 它不采集、不存储；必须先有 Prometheus/InfluxDB 等数据源 |
| 认为一个看板只能一个数据源 | 一个 Dashboard 可混用多数据源（压测看板的关键用法） |
| 把 Grafana 当"监控系统"整体 | 它只是体系里的展示层；采集与存储要看 Prometheus/Exporter |
| 只画业务指标不画资源指标 | 排查需要"业务 + 资源"对齐；分开看会导致误判 |
| 忽略告警与权限配置 | 生产看板需要告警规则与用户/组织权限，否则只是"好看的图" |

【我的理解】引导题（用自己的话回答）：
1. 用"眼睛与手"的比喻说明 Grafana 与 Prometheus 的分工，并解释为什么这种解耦对压测有利。
2. 为什么压测看板要同时有"业务指标"和"资源指标"？只用其中一类会发生什么？

### 知识点2：核心概念（数据源 / 看板 / 面板 / 查询 / 变量 / 告警）

【课程原话/定义】
（原文未涉及概念体系，本节按 Grafana 通用语义补齐，用于理解下一节的搭建与配置。）

【为什么？】
Grafana 的概念只有 6 个，且是层层包含的——**搞清楚这套结构，你就能自己"造"任何一块看板**，而不是只会导入别人做好的：

1. **Data Source（数据源）**：连接目标（Prometheus、InfluxDB、Elasticsearch…），要填 URL 与认证；
2. **Dashboard（看板）**：一组面板的集合，通常对应"一块大屏"（如"压测实时看板"）；
3. **Panel（面板）**：看板里最小的展示单元，有类型（Time series 折线 / Stat 统计 / Gauge 仪表 / Table 表格 / Heatmap 热图）；
4. **Query（查询）**：面板里的查询语句（PromQL / InfluxQL / SQL），决定"这块图显示什么数"；
5. **Variables（变量）**：看板级参数（如 `$instance`、`$job`），让同一块看板能切换机器/接口——**这是"通用看板"的关键**；
6. **Alerting（告警）**：按阈值/规则触发通知（邮件、钉钉、Webhook 等）。

对这 6 个概念，压测场景下最该重视的是**变量**：一块"压测看板"如果不带变量，你只能固定看一台机器；带上 `$instance` 变量后，下拉框一选就能看任意机器——**从"一次性图"变成"可复用工具"**，这也是企业里看板能沉淀成"资产"的原因。

【必须掌握】

| 概念 | 作用 | 压测场景里的用法 |
|---|---|---|
| Data Source | 连接数据源 | Prometheus（资源）+ InfluxDB（JMeter 结果）双源 |
| Dashboard | 一块看板 | "压测实时看板"：业务 + 资源 + 告警 |
| Panel | 单个图表 | 折线看趋势（TPS/RT）、统计看现值、表格看 Top N |
| Query | 查询语句 | PromQL（`rate(node_cpu_seconds_total...)`）/ InfluxQL |
| Variables | 看板参数 | `$instance`、`$interface`、`$testTitle`（多轮压测切换） |
| Alerting | 阈值告警 | RT P99 > 1s、错误率 > 1%、CPU > 85% 触发通知 |
| 时间范围 | 看板级时间选择器 | 与压测窗口对齐（务必记录压测起止时间） |

【企业场景】
一个"能复用"的压测看板长这样：顶部一排统计面板（当前 TPS、当前 RT P95、错误率、被测机 CPU）、中间两条折线（TPS/RT 与 CPU/内存）、底部一行表格（Top 5 慢接口）。**关键点是变量**：`$instance`（被测机）、`$testTitle`（本轮压测标识，JMeter 写 InfluxDB 时带上，见 [[Ch43-jmeter实时压测结果收集]]），于是这套看板可以被所有项目复用，每次压测只改两个下拉框。**能做到这一步，就等于把"监控能力"产品化了。**

【面试考察】
面试官："你会自己在 Grafana 上做压测看板吗？会放哪些内容？"

参考回答框架：
1. 结构：看板（Dashboard）→ 面板（Panel）→ 查询（Query）；数据源可以是 Prometheus（资源）或 InfluxDB（JMeter 结果）；
2. 内容：TPS/RT（含 P95/P99）/错误率（业务） + CPU/内存/IO/网络（资源） + Top 慢接口表格；
3. 提升可用性：用变量（`$instance`/`$testTitle`）做多机器、多轮切换；时间范围与压测窗口对齐；
4. 告警：RT/错误率/CPU 阈值告警，压测与生产都能用。

【易错点】

| 常见错误 | 正确理解 |
|---|---|
| 面板里写查询不写聚合窗口 | 同一指标不同聚合（最大值/平均/分位）结论不同，必须明确 |
| 看板没有变量，一机一板 | 用 `$instance` 等变量做成通用看板，避免重复劳动 |
| 时间范围随意选 | 与压测窗口对齐；跨轮次对比要用同样的时间跨度 |
| 只做图不做告警 | 告警让看板"会说话"，压测时不必全程盯屏 |
| 混淆"面板类型"的用途 | 趋势用折线、现值用统计/仪表、明细用表格、分布用热图 |

【我的理解】引导题（用自己的话回答）：
1. 为什么"变量"是压测看板能否复用的关键？请举一个你想要的变量。
2. 同一指标用"平均值"和"P99"画出来，会分别掩盖或暴露什么问题？

### 知识点3：搭建步骤（Docker 两条命令 + 验证）

【课程原话/定义】
课程给出的搭建步骤（原文）：
1. 拉取镜像 `docker pull grafana/grafana`；
2. 创建并启动容器 `docker run -d -p 3000:3000 --name jmeterGrafana grafana/grafana`。

（原文无验证与持久化说明，以下为补齐内容。）

【为什么？】
Grafana 的部署确实只有两条命令，但**"能打开页面"与"能长期用"之间差三个参数**：

1. **持久化**：Grafana 的看板、数据源、用户都保存在容器内的 `/var/lib/grafana`——不挂卷，容器一删**配置全丢**。生产/压测环境必须挂载：
   `-v <本地目录>:/var/lib/grafana`
2. **管理员与安全**：默认账号密码是 `admin/admin`，**首次登录会强制改密码**；生产环境要么改掉、要么关掉匿名访问与默认管理员（原文没提，但这是基本安全要求）。
3. **网络连通性**：容器里的 `localhost` 指的是**容器自己**——如果 Prometheus 跑在宿主的 9090，Grafana 里填 `http://localhost:9090` 会连不上（这是新手最常踩的坑）。修法：用宿主 IP、或加 `--add-host=host.docker.internal:host-gateway` 用 `host.docker.internal`、或把 Grafana 与 Prometheus 放进**同一个自定义 docker 网络**用容器名互访。

【必须掌握】

| 步骤 | 命令/动作 | 验证 |
|---|---|---|
| 1 拉镜像 | `docker pull grafana/grafana` | 无报错 |
| 2 起容器 | `docker run -d -p 3000:3000 --name grafana -v <本地目录>:/var/lib/grafana grafana/grafana` | `docker ps` 显示 Up |
| 3 登录 | 浏览器 `http://localhost:3000`，默认 `admin/admin`（会强制改密） | 能进首页 |
| 4 加数据源 | Configuration → Data Sources → Prometheus，URL 填**能被容器访问到的地址** | 页面提示 "Data source is working" |
| 5 建/导看板 | 新建 Dashboard 或导入社区看板（Dashboard → Import，填看板 ID） | 面板有数据 |
| 6 持久化 | 挂 `/var/lib/grafana` | 重建容器后配置仍在 |
| 7 安全（生产） | 改默认密码、按需关闭匿名访问、按角色授权 | 不暴露默认口令 |

【企业场景】
团队里"监控看板重建"是很常见的场景（换环境、清机器、迁移机房）。若当初没挂 `/var/lib/grafana`，你只能**重新手搓一遍所有面板**；挂了卷则是"`docker run` 起来，看板全在"。更稳的做法是把 Grafana 的 provisioning（数据源与看板以 YAML/JSON 文件声明）也纳入 Git——**环境可复制**，这也是本模块反复强调的"可复现"纪律在可视化层的体现。

【面试考察】
面试官："Grafana 怎么部署？怎么保证配置不丢？"

参考回答框架：
1. 部署：`docker pull grafana/grafana` → `docker run -d -p 3000:3000 --name grafana -v <dir>:/var/lib/grafana grafana/grafana` → 浏览器 3000 登录（默认 admin/admin，首次强制改密）；
2. 配置持久化：挂载 `/var/lib/grafana`（看板、数据源、用户都在这里）；进阶用 provisioning 把配置进 Git；
3. 数据源连接：注意**容器内 localhost 指向容器自身**，要用宿主 IP / host.docker.internal / 同网络容器名；
4. 安全：改默认口令、限制访问、按需关闭匿名。

【易错点】

| 常见错误 | 正确理解 |
|---|---|
| 不挂 `/var/lib/grafana` | 容器删除即丢所有看板与数据源配置 |
| 数据源 URL 填 `localhost:9090` | 容器内 localhost＝容器自己；要用宿主地址或同网络容器名 |
| 沿用默认 `admin/admin` 上线 | 首次登录会强制改密；生产要改口令并限制访问 |
| 假设 Grafana 一定有数据 | 它依赖数据源；数据源不通则面板为空 |
| 面板改了不保存/不导出 | 看板应导出 JSON 或走 provisioning 入库，便于复用与回滚 |

【我的理解】引导题（用自己的话回答）：
1. 为什么"不挂载 /var/lib/grafana"在生产里是个严重疏漏？你会怎么补救（除了挂卷）？
2. Grafana 容器里填 `localhost:9090` 为什么连不上 Prometheus？给出两种修法。

### 知识点4：配置数据源与压测看板（落地做法）

【课程原话/定义】
（原文只有"拉镜像 + 起容器"两步；数据源与看板属于后续章节 [[Ch42-Prometheus监控系统部署应用实战]] 里"配置 grafana 数据源"的内容，本节提前把机制讲清。）

【为什么？】
从"Grafana 起来了"到"压测时能看板定位瓶颈"，需要走完这条链，每一步都有具体的坑：

| 环节 | 做法 | 常见坑 |
|---|---|---|
| ① 加数据源 | Configuration → Data Sources → Prometheus，URL 填容器可达地址；Save & Test | 容器内 `localhost` 指向自身；端口未映射；防火墙 |
| ② 加第二个数据源 | 再加 InfluxDB（压测结果源，见 [[Ch43-jmeter实时压测结果收集]]） | InfluxDB 版本（1.x 用 InfluxQL、2.x 用 Flux）与库名要对上 |
| ③ 建看板 | New Dashboard → Add panel → 选数据源 → 写查询 | 查询的**聚合窗口**（`[5m]`）与压测时长不匹配 → 曲线失真 |
| ④ 设变量 | Dashboard Settings → Variables（`$instance`、`$testTitle`） | 变量类型/查询写错导致下拉为空 |
| ⑤ 配阈值与告警 | Panel 阈值线 + Alert rules | 阈值没有依据（应来自 SLA/历史基线） |
| ⑥ 对齐时间 | 看板时间范围选压测窗口；记录起止时间 | 与业务指标跨机不对时 → 曲线对不上 |

**一个非常实用的起步方式**：Grafana 官网有海量社区看板（如 Node Exporter 的经典看板），**导入现成看板（Import → 填 ID/JSON）再按需改**，比从零画面板快十倍。企业里常见做法是"导入社区看板 + 自建业务面板"混合。

【必须掌握】

| 看板必备面板（压测版） | 数据源 | 面板类型 | 观察要点 |
|---|---|---|---|
| TPS / 吞吐量 | InfluxDB（JMeter） | 折线 | 拐点（走平）出现的时间点 |
| RT（平均 + P95/P99） | InfluxDB（JMeter） | 折线 | 分位值抬头＝体验恶化开始 |
| 错误率 | InfluxDB（JMeter） | 折线/统计 | 与 RT 是否同时恶化（判断是过载还是故障） |
| 被测机 CPU | Prometheus（Node Exporter） | 折线 | us/sy/wa 分解；是否单核打满 |
| 内存 / available / swap | Prometheus | 折线 | 是否换页（si/so） |
| 磁盘 %util / await | Prometheus | 折线 | 是否 IO 饱和 |
| 网络带宽 / 连接数 | Prometheus | 折线 | 是否带宽或连接数打满 |
| 施压机资源 | Prometheus | 折线 | **排除假瓶颈**（施压机自己是否吃满） |

【企业场景】
压测现场的真实用法：把上述面板投到会议室大屏，压测开始后每 2 分钟看一次拐点位置；一旦 RT 抬头、错误率上升，立刻在同一个时间点看资源面板——**"业务恶化点 + 资源状态"一起看，就能现场给出瓶颈判断**（CPU？IO？连接数？还是施压机？）。压测结束后把看板时间范围固定到压测窗口，导出截图与数据存档——**这份截图就是报告里最直观的证据**。

【面试考察】
面试官："说说你压测时那块看板上有什么，怎么用它定位问题？"

参考回答框架：
1. 双数据源：InfluxDB（JMeter 的 TPS/RT/错误率）+ Prometheus（CPU/内存/IO/网络/施压机）；
2. 面板设计：折线看趋势、统计看现值、表格看 Top 慢接口；分位值（P95/P99）必看；
3. 定位方法：先在业务曲线找恶化时间点，再对齐资源曲线看该时刻哪类资源异常，排除施压机后得出结论；
4. 效率技巧：变量做多实例/多轮切换；导入社区看板起步；看板时间范围与压测窗口对齐并归档。

【易错点】

| 常见错误 | 正确理解 |
|---|---|
| 数据源添加后不点 "Save & Test" | 必须验证连通性，否则后面所有面板都是空的 |
| 只用平均值看 RT | 平均值会掩盖长尾；必须看 P95/P99（用户体验由分位值决定） |
| 看板没有"施压机资源"面板 | 施压机瓶颈会造出假结论；必须监控施压机自身 |
| 时间范围随手选 | 与压测窗口对齐；跨机时间不对齐会导致"因果看不出" |
| 每次压测都从零手搓看板 | 用变量 + 导入社区看板 + provisioning，把看板做成资产 |

【我的理解】引导题（用自己的话回答）：
1. 请设计"压测实时看板"的 6 个面板（写清数据源与面板类型），并说明各自用来回答什么问题。
2. 为什么要专门给"施压机"留一块面板？没有它会犯什么错？

### 知识点5：Grafana 常见坑清单与压测落地检查

【课程原话/定义】
课程总结（原文）：简介 / grafana 应用场景 / 如何搭建 grafana 系统。

【为什么？】
把 Grafana 用进压测流程后，最容易踩的坑集中在**连通性、数据正确性、时间对齐**三类。把它们列成"上板前检查清单"，能避免几次白压：

| 类别 | 检查项 | 判断标准 |
|---|---|---|
| 连通性 | 数据源 Save & Test 通过 | 提示 "Data source is working"，且能看到指标列表 |
| 连通性 | 容器网络可达（不是 localhost） | 容器内能解析/访问到 Prometheus/InfluxDB 地址 |
| 数据正确性 | 查询的指标名/库名/表名正确 | 面板不是 "No data"，且数值与手工命令（vmstat 等）量级一致 |
| 数据正确性 | 聚合窗口与采样间隔合理 | 例如 5s 采集配 `[1m]` 窗口；窗口过大 → 曲线被抹平 |
| 时间对齐 | 看板时间范围 = 压测窗口 | 能一眼指出"RT 抬起那一刻 CPU 是多少" |
| 持久化 | 卷已挂载、看板可导出 | 容器重建后看板仍在 |
| 权限安全 | 默认口令已改 | 不暴露 admin/admin |
| 归档 | 压测结束导出截图/数据 | 报告中有可复核的证据 |

**另外一个只有压测才会遇到的细节**：Grafana 的面板刷新间隔（Refresh）默认较长，**压测时建议设为 5s/10s**，否则你看到的"实时"曲线其实是几十秒前的（对判断拐点时间点有影响）。

【必须掌握】

| 检查项 | 命令/入口 |
|---|---|
| 数据源连通 | Grafana → Data Sources → Save & Test |
| 指标是否进来 | Prometheus `/targets` 全 UP + `/graph` 能查到 |
| 数值对不对 | 与 `vmstat`/`top` 手工结果对照（量级一致） |
| 时间对齐 | 看板右上时间范围；记录压测起止时间 |
| 刷新频率 | Dashboard → Refresh 调整为 5s/10s（压测期间） |
| 持久化 | `docker inspect` 看挂载；看板 JSON 导出 |
| 归档 | Dashboard → Share → Export/Snapshot；截图存报告目录 |

【企业场景】
一次"看板里的数不对"的排查：同事报告"TPS 曲线有 8000，但 JMeter 聚合报告只有 4000"。原因是 InfluxDB 里存的是**累计计数（count）**，面板没有用 `rate()`/差分，直接把累计值画成了曲线——**看着像 TPS，其实是总量**。教训：**监控看板上的每一个数字，都要能说清它的口径**（是速率还是累计、是平均还是分位、单位是什么）。这也是报告评审时最容易被问倒的地方。

【面试考察】
面试官："看板上的数字和你手工采集的对不上，你会怎么查？"

参考回答框架：
1. 先查口径：指标是速率还是累计？聚合是平均/最大/分位？单位（次/秒、毫秒、字节）是否一致；
2. 再查聚合窗口与采样间隔是否匹配（窗口过大抹平尖刺、过小导致锯齿）；
3. 再查时间对齐（跨机时间差、看板时区）与数据源是否同一实例；
4. 最后手工对照（vmstat/top/iostat）确认量级；
5. 收口：把"口径定义"写进看板描述与报告，避免团队误读。

【易错点】

| 常见错误 | 正确理解 |
|---|---|
| 看板数字与手工命令对不上却直接采信看板 | 先核对**口径与单位**（速率/累计、平均/分位、ms/s） |
| 把累计计数当速率画 | TPS 要用 `rate()`/差分；否则显示的是"总量" |
| 刷新间隔与采集间隔不匹配 | 刷新过慢看不到实时；刷新过快会掩盖趋势（压测建议 5s/10s） |
| 时区/时间范围设错 | 曲线看起来"晚了几小时"，与日志对不上 |
| 不做归档 | 压测结束看板数据过期（保留期），报告失去证据；及时导出 |

【我的理解】引导题（用自己的话回答）：
1. 请写出你会用来交叉验证"看板 TPS 是否正确"的两条手段。
2. 为什么"每个数字都要能说清口径"是监控系统的基础纪律？举一个口径错误的例子。
