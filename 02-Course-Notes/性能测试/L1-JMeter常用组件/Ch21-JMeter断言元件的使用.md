### 知识点1：断言元件（Assertion）是什么，为什么性能脚本也必须断言

【课程原话/定义】
在 JMeter 中，断言元件（Assertion）用于验证测试结果是否符合预期。断言元件可以检查服务器的响应数据，以确保它们符合期望的模式或值，从而验证性能测试脚本的正确性。断言元件通常在每个请求的响应中添加，以确保服务器返回了正确的响应。

常用的 JMeter 断言元件（课程原文列举）：
- Response Assertion（响应断言）
- Size Assertion（大小断言）
- XPath Assertion（XPath 断言）
- JSON Assertion（Json 断言）

添加元件步骤的截图在原文里给出（树形结构的添加路径）。

【为什么？】
因为"压测出来的高 TPS"分两种：**真成功的高 TPS** 和**假成功的高 TPS**，而后者的破坏力更大。JMeter 的 HTTP 取样器默认只看协议层结果——**4xx/5xx 会被判为失败**，但**业务层失败它看不出来**：
1. 返回 HTTP 200 但报文是 `{"code": 500, "msg": "库存不足"}`；
2. 返回 HTTP 200 但内容是风控/验证码拦截页、或者网关的降级提示页；
3. token 过期后接口秒回 401/未登录提示页——**RT 极短、TPS 很高、图形很漂亮**，但这条链路的业务一次也没走通。

断言的作用就是在"协议层成功"之上再加一道**业务层成功**的判定，让最终报告里的**错误率**由这两道关共同定义。这也解释了一个反直觉的事实：**脚本本身的错误（未登录、参数写错、token 失效）不会让压测"报错停下"，而是会让压测结果变得"更好看"**——所以断言不是"用来给脚本做质检的奢侈品"，而是让数据可信的必需品。

【必须掌握】

| 断言元件 | 断言的"实际结果"从哪来 | 典型用途 | 压测脚本中的使用频率 |
|----------|------------------------|----------|----------------------|
| Response Assertion | 响应文本、响应码、响应消息、响应头、请求头、请求数据、URL 样本、Document | 断响应码 + 断业务关键字（最通用） | ★★★★★ |
| Size Assertion | 响应字节数（完整响应/响应头/响应体/响应码/响应消息） | 兜住"返回了空体或错误小报文"的假成功 | ★★★☆☆ |
| XPath Assertion | XML/HTML 中的节点（XPath 表达式） | 老系统 XML、HTML 页面结构校验 | ★★☆☆☆ |
| JSON Assertion | JSON 里的字段（JSON Path 表达式） | RESTful 接口字段值校验 | ★★★★☆ |

【企业场景】
你接下"下单链路压测"的任务，脚本跑完 200 并发，Aggregate Report 显示 TPS 320、错误率 0.2%——看起来非常健康。但你顺手把断言加上重跑，错误率跳到 61%：原因是压测第 30 秒后登录 token 过期，后面所有下单请求都返回 HTTP 200 + `{"code": 401, "msg": "请先登录"}`，服务端因为没做业务处理所以**响应特别快**，TPS 反而被"刷高了"。如果你直接把 320 TPS 写进报告，结论就是"系统能扛 320 TPS"——实际它是"能被踢掉 320 次/秒"。**企业里的做法是：脚本里必须带上响应码断言 + 业务 code 断言，报告里的错误率才有资格作为容量结论的输入。**

【面试考察】
面试官："做性能测试，你会在脚本里写断言吗？断言起什么作用？"

参考回答框架：
1. 断言是"业务层正确性"的判定：HTTP 状态码只能说明协议层通了，业务失败（code≠0、拦截页、降级页）必须靠断言识别
2. 断言直接影响结果可信度：脚本错误（token 过期、参数错）会让 TPS/RT"变好看"，加了断言才能暴露
3. 断言影响报告的指标口径：错误率 = 协议层失败 + 断言失败，是容量结论的前提
4. 工程取舍：压测脚本只保留必要断言（响应码 + 核心业务字段），断言过重会消耗施压机 CPU

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 认为 HTTP 200 就等于业务成功 | 200 只代表服务端应答了；业务成败要断业务 code / 关键字段（断言元件存在的根本原因） |
| 断言写得越多越安全 | 断言要解析响应（正则、JSON、XML），都在消耗施压机 CPU；压测脚本只保留核心断言，否则施压机先到瓶颈（【扩展知识】） |
| 用断言代替监控 | 断言回答"对不对"，"慢在哪 / 为什么慢"要靠监控与剖析工具（见 [[../L1-性能测试体系/Ch05-行业流行性能监控工具介绍|L1 Ch05]]、[[../L1-性能测试体系/Ch06-行业流行性能剖析工具介绍|L1 Ch06]]） |
| 断言失败时先去改/删断言 | 断言失败先看 View Results Tree 里的真实响应：是脚本问题（未登录、参数错）就修脚本，是系统返回异常就是缺陷证据 |
| 断言失败算不算性能问题不区分 | 断言失败会同时进入错误率统计，掩盖真实的服务端错误率，必须结合响应体分析归因 |

【我的理解】引导题（用自己的话回答）：
1. 为什么"脚本写错"会让压测结果看起来**更漂亮**？请用"token 过期 → 服务端不做业务处理 → RT 变短 → TPS 升高"这条链路解释一遍。
2. 如果只能在一个压测脚本里保留**两条**断言，你会保留哪两条？为什么是它们？

### 知识点2：Response Assertion（响应断言）

【课程原话/定义】
用于检查服务器响应的内容是否符合预期，可以基于响应的内容、代码、消息或其他属性进行断言。可以根据响应文本、响应代码、响应消息和其他参数来定义断言条件，并指定断言模式（包含、匹配、不包含等）。

`Apply to` 选项默认即可：Main sample only（仅作用于父节点取样器）。

**测试字段（要检查的项 = 实际结果）**：

| 测试字段 | 含义（课程原文） |
|----------|------------------|
| Text Response | 来自服务器的响应文本 |
| Response Code | 响应的状态码，例如 200 |
| Response Message | 响应的信息，例如 OK |
| Response Headers | 响应头部 |
| Request Headers | 请求头部 |
| Request Data | 请求数据 |
| URL 样本 | 请求 URL |
| Document(text) | 响应的整个文档 |
| 忽略状态 | 忽略返回的响应状态码 |

**模式匹配规则（比较方式 / 校验规则）**：

| 规则 | 含义（课程原文） |
|------|------------------|
| contains（包括） | 文本包含指定的正则表达式 |
| Matches（匹配） | 整个文本匹配指定的正则表达式 |
| Equals（等于） | 整个返回结果的文本等于指定的字符串（区分大小写） |
| Substring | 返回结果的文本包含指定字符串（区分大小写） |
| 否 | 取反 |
| 或者 | 勾选代表逻辑或（只要有一个模式匹配，断言就是 OK）；不勾选代表逻辑与（所有模式都必须匹配，断言才是 OK） |

**测试模式**：预期结果，即填写指定的结果（可填写多个），通过 [添加]、[删除] 按钮管理。

**课程案例**：检查百度首页的请求响应中是否包含 "百度一下，你就知道"。
1. 步骤一：添加百度的 HTTP Request，添加对应的 Response Assertion，添加查看结果树
2. 步骤二：在 Response Assertion 元件中添加对应配置
3. 步骤三：查看结果，断言成功

【为什么？】
Response Assertion 是四个断言里唯一的"通吃型"，因为它的"实际结果"可以取自响应的**任何一个部位**（文本/头部/状态码/请求数据），再用四种匹配规则之一与之比较。真正要理解的是**四种规则的严格程度差异**——它决定了你的断言是"经常误报"还是"经常漏报"：

| 规则 | 匹配语义 | 误报/漏报倾向 |
|------|----------|----------------|
| contains | 部分匹配 + 正则语义（子串命中即通过） | 容易"漏报"（响应整体错但片段还存在） |
| Matches | 全文匹配（相当于自带 `^...$`） | 容易"误报"（多一个空格/换行就失败） |
| Equals | 全文完全相等，区分大小写 | 最严格，适合断极短的固定报文（如 `OK`） |
| Substring | 部分匹配 + 纯字符串包含，区分大小写 | 最贴近人的直觉："有这几个字就算过" |

同时要看清"或者"这个勾选框的真实语义：**勾选 = 多个测试模式之间取或（任一命中即通过），不勾选 = 取与（全部命中才通过）**。它**不是**"否定"。"否"才是取反。

【必须掌握】

| 配置项 | 默认值 | 语义 | 什么时候要改 |
|--------|--------|------|--------------|
| Apply to | Main sample only | 只对父节点的取样器生效 | 有子取样器（如嵌套装请求）且要一并断言时选 Main sample and sub-samples（【扩展知识】） |
| 测试字段 | Text Response | 断言的"实际结果"取自哪里 | 断状态码选 Response Code；断业务文本选 Text Response（最常用） |
| 模式匹配规则 | contains | 比较的严格程度 | 断固定短报文用 Equals；只判断"包含"优先 Substring |
| 测试模式 | 空 | 预期结果，可多条 | 至少写一条，否则断言不具约束力 |
| 忽略状态 | 未勾选 | 勾选后忽略响应状态码判定 | **业务就是要 4xx/5xx 也算成功**（如负向验证）才勾 |

【企业场景】
你给登录接口写断言，链路是"登录 → 取 token → 下单"。登录请求的断言这样配：测试字段 = Response Code，模式 = `200`；再加一条测试字段 = Text Response，模式 = `"code":0`（不勾"或者"，取与）。压测过程中一旦 `token` 拿不到（返回 200 + `{"code":401}`），断言立刻把请求判失败，Aggregate Report 的错误率会同步升高，你就能在 1 分钟内发现"脚本在第 N 分钟开始失效"，而不是等报告写完才发现整段数据作废。反过来，如果你要验证**限流场景**（期望被限流返回 429），就把"忽略状态"勾上，用 Response Message 断言 `Too Many Requests`——这也是"忽略状态"存在的正当用途。

【面试考察】
面试官："JMeter 响应断言里 contains 和 Matches 有什么区别？'或者'勾选框是什么意思？"

参考回答框架：
1. contains 是**部分匹配**（响应文本里包含该模式就算通过），Matches 是**整个文本匹配**（等价于全文正则匹配）
2. 容错性差异：Matches 对多余空格/换行敏感，容易误报；contains 对响应整体异常不敏感，容易漏报
3. "或者"勾选 = 多个测试模式取逻辑或（任一匹配即 OK）；不勾选 = 取逻辑与（全部匹配才 OK）——注意它跟"否"（取反）是两个不同的东西
4. 实践建议：断业务关键字段用 Substring/contains，断固定短报文（OK、200）用 Equals，全文断版本号这类唯一标识才用 Matches

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 以为"或者"勾上是逻辑与 | 原文明确：勾选 = 逻辑或（有一个模式匹配即 OK），不勾选 = 逻辑与（全部匹配才 OK），最易搞反的一项 |
| 用 Matches 去做"包含"校验 | Matches 要求整个文本匹配，响应里任何多余内容都会让它失败；"包含"要用 contains / Substring |
| 随手勾"忽略状态" | 勾上后 4xx/5xx 不再算失败，会掩盖真实错误；只在负向场景（期望 4xx）才勾 |
| 把断言的"测试字段"理解成"我要断什么" | 测试字段是**实际结果的来源**，测试模式才是**预期结果**；两者写反会导致永远失败或永远通过 |
| 用 Text Response 断整个大响应体 | 大响应体上跑正则匹配会显著增加施压机 CPU 开销（【扩展知识】），压测优先断 Response Code + 一个关键片段 |
| 一条断言里塞十几个测试模式 | 断言越复杂，失败时越难定位原因；按"状态码断言 + 业务断言"拆成两条，失败信息更好读 |

【我的理解】引导题（用自己的话回答）：
1. 现在要校验"下单接口返回的 `orderId` 是不是 16 位数字"，你会选哪个匹配规则？为什么不用 Matches？
2. 什么业务场景下"返回 4xx 反而是对的"？这时断言该怎么配才能既不误报又不漏报？

### 知识点3：Size Assertion（大小断言）

【课程原话/定义】
Size Assertion 是一种断言元件，用于验证服务器响应的内容的大小是否符合预期：检查返回的响应数据的大小是否在指定的范围内，以便在性能测试中验证响应的大小是否符合要求。

`Apply to` 选项默认即可：Main sample only（仅作用于父节点取样器）。

**Response Size Field to Test（要测试的响应大小字段）**：

| 选项 | 含义（课程原文） |
|------|------------------|
| Full Response | 完整响应 |
| Response Headers | 响应头 |
| Response Body | 响应的消息体，选择此项判断返回主体数据 Body 的大小 |
| Response Code | 响应代码 |
| Response Message | 响应信息 |

其他参数：`Size to Assert` → `size in bytes`（设置要判断的数值，单位 bytes / kb）；`Type of Comparison`（比较类型，即 =、≠、>、<、≥、≤）。

**课程案例**：检查百度首页的请求响应的内容大小是否大于等于 2381。（步骤一添加 HTTP Request + Size Assertion + 查看结果树 → 步骤二配置 → 步骤三查看结果：断言成功）

【为什么？】
大小断言的价值在于——它是**最省 CPU 的"假成功探测器"**。它不解析正文，只数字节，所以：
1. 服务端在压力下返回精简错误体（如 `{"error":"rate limited"}` 只有几十字节）、返回空数组 `[]`、返回降级页，此时 RT 很短、TPS 很高，肉眼完全看不出异常；
2. 给业务响应体设一个**大小下限**（如 ≥ 2381 字节），这类"缩水响应"会立刻被标记为失败；
3. 反过来，也要警惕**大小上限**：响应体异常膨胀（错误堆栈、全量数据未分页）说明业务逻辑走错了分支，也是缺陷信号。

注意它和"性能指标"的区别：**响应大小不是性能指标（不是 RT/TPS），它是"内容是否合理"的正确性判定**。原文说"在性能测试中验证响应的大小是否符合要求"，落脚点是"内容符合预期"，不要理解成"用大小衡量性能"。

【必须掌握】

| 配置项 | 可选项 | 建议 |
|--------|--------|------|
| Response Size Field to Test | Full Response / Response Headers / Response Body / Response Code / Response Message | 卡业务数据大小用 **Response Body**（不含头部，波动小） |
| Size to Assert | 数值 + 单位（bytes / kb） | 写 2381 就是 2381 字节，不是字符数 |
| Type of Comparison | = / ≠ / > / < / ≥ / ≤ | 生产压测通常用 ≥（设下限兜底），而不是 =（动态页面做不到字节级相等） |
| Apply to | Main sample only（默认） | 有子取样器时按需调整（【扩展知识】） |

【企业场景】
你压一个"商品详情页"接口，页面里有广告位、推荐位、时间戳，所以响应体大小本身会波动，**不能用 = 卡死**。企业做法是：先用 Response Body ≥ 8000 字节设下限（正常详情页大约 12KB 以上，返回 300 字节一定是错误页），同时把"大小断言失败"和"业务 code 断言失败"放在一起看——如果错误率里大量来自大小断言，基本可以直接定位到"压力下服务端返回了降级/限流报文"，这比逐个翻响应体快得多。

【面试考察】
面试官："你怎么保证压测结果里的成功请求是'真成功'？"

参考回答框架：
1. 三层把关：协议层（HTTP 状态码，JMeter 默认 4xx/5xx 判失败）+ 业务层（响应断言断业务 code / 关键字段）+ 内容层（大小断言兜住空体、缩水报文、降级页）
2. 大小断言的优势：不解析正文、几乎不耗 CPU，适合在大并发压测里当"低成本的兜底检查"
3. 使用要点：用 Response Body 而不是 Full Response（头部含 Date/Vary 等波动字段）；比较类型用 ≥ 设下限而非 = 卡等值
4. 归因：错误率升高时区分"来自哪条断言"，能快速判断是限流降级还是逻辑缺陷

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 把 Size Assertion 当成性能指标 | 它是正确性断言（内容是否合理）；RT/TPS 才是性能指标 |
| 用 = 精确卡字节数 | 动态内容（广告、时间戳、GUID）让响应体大小天然波动，用 ≥ / ≤ 设范围 |
| 选 Full Response 卡业务大小 | Full Response 含响应头，头部长度会变；要卡业务数据用 Response Body（原文明确指出 Response Body 是"返回主体数据 Body 的大小"） |
| 单位/字符数混淆 | size in bytes 是字节：一个中文汉字在 UTF-8 下 3 字节，2381 字节 ≈ 不到 800 个汉字（【扩展知识】） |
| 大小断言放在最内层加上一堆正则 | 兜底断言要"轻"；重解析交给核心业务断言，避免施压机 CPU 被吃满 |

【我的理解】引导题（用自己的话回答）：
1. 一个接口在正常情况下返回 12KB 数据，压力下返回 `{"code":500}`（约 15 字节）。为什么这种"缩水响应"会让压测报告的错误率**看起来更低**，而实际是严重的服务端问题？
2. 如果响应体大小天然波动（含广告位），你会怎么设 Size Assertion，才不至于天天误报？

### 知识点4：XPath Assertion（XPath 断言）

【课程原话/定义】
XPath Assertion 用于验证 XML 或 HTML 响应的内容是否符合指定的 XPath 表达式。XPath 是一种用于在 XML 文档中定位和选择元素的语言，通过 XPath Assertion 可以使用 XPath 表达式来验证响应中的特定内容，例如检查特定元素、属性或文本是否存在或符合条件。

**XML Parsing Options（XML 解析选项）**：

| 选项 | 含义（课程原文） |
|------|------------------|
| Use Tidy | 当需要处理的页面是 HTML 格式时，必须选中该选项；如果是 XML 或 XHTML 格式（例如 RSS 返回），则取消选中，默认是 quiet |
| （quiet / Report errors / Show warnings） | Quiet 表示只显示需要的 HTML 页面；Report errors 表示显示响应报错；Show warnings 表示显示警告 |
| Use Namespaces | 如果启用该选项，后续的 XML 解析器将使用命名空间来分辨 |
| Validate XML | 根据页面元素模式进行检查解析 |
| Ignore Whitespace | 忽略空白内容 |
| Fetch external DTDs | 如果选中该项，外部将使用 DTD 规则来获取页面内容 |

**XPath Assertion 文本框**：用于填写 XPath 表达式，点击 `Validate` 验证其正确性；勾选 `True if nothing matches` 表示确认都不匹配，才会断言验证通过。

**课程案例**：检查百度首页的请求响应的内容包含 XPath 表达式 `//input[@id="kw"]`。（步骤一添加 HTTP Request + XPath Assertion + 查看结果树 → 步骤二配置 → 步骤三查看结果：断言成功）

**课程原文勘误**：该页在 XPath Assertion 的参数说明里混入了一段"引用名称：下一个请求要引用的参数名称，如填写 title，则可用 `${var_regexp2}` 引用它"以及关于 XML 属性需要 DTD 声明的括号说明。这段内容属于**后置处理器里的 XPath 提取器 / 正则表达式提取器**的参数，XPath Assertion **没有"引用名称"参数**——断言只输出"通过/失败"，不把值取出来给后续请求用。

【为什么？】
XPath 断言是**结构级校验**：它不问"响应里有没有'登录成功'这几个字"，而问"DOM 结构里有没有这样一个节点"。这个区别很关键——HTML 页面里出现"登录成功"四个字，可能只是标题栏或静态文案；而 `//div[@class="user-info"]` 这种节点的存在，才说明渲染走了登录后的分支。

Use Tidy 的存在理由也是机制层面的：真实 HTML 页面大量标签不闭合（`<br>`、`<img>` 不写 `/`），严格 XML 解析器会直接报错、XPath 根本查不到节点，所以**处理 HTML 必须勾 Use Tidy 让它先做容错修正**；而 XML/XHTML 本身合法，勾上反而可能被 Tidy 改写成非预期结构，所以官方与课程都要求"HTML 勾、XML/XHTML 取消"。

【必须掌握】

| 配置项 | 取值 | 关键提醒 |
|--------|------|----------|
| Use Tidy | 勾 / 不勾 | HTML 页面**必须勾**；XML/XHTML 取消（原文明确） |
| Tidy 模式 | quiet / Report errors / Show warnings | 默认 quiet，排查解析问题时临时切到 Report errors / Show warnings |
| Use Namespaces | 勾 / 不勾 | 报文带 namespace（如 SOAP）时启用 |
| Validate XML | 勾 / 不勾 | 按页面元素模式校验解析结果 |
| Ignore Whitespace | 勾 / 不勾 | 空白敏感的场景（含文本比对）建议勾上以忽略空白 |
| Fetch external DTDs | 勾 / 不勾 | 需要按外部 DTD 规则解析时才勾（会引入外部网络依赖） |
| XPath Assertion | XPath 表达式 | 先点 Validate 验证表达式本身可用，再跑脚本 |
| True if nothing matches | 勾 / 不勾 | 勾上后语义反转：都不匹配才通过（负向校验） |

【企业场景】
你在测一个老金融系统的 XML 报文接口（或一个服务端渲染的 HTML 后台页）。这类响应的特点是：字段名稳定、结构固定，但里面夹着流水号、时间戳这类每次都变的值。用"文本包含"断言不合适（值会变），用 XPath 断言 `//resultCode[text()="0"]` 或 `//div[@id="order-list"]` 就非常稳：它只关心结构和关键节点的存在性。压测时一旦服务端在压力下返回错误页（没有 `order-list` 节点）或 XML 结构变化，断言立即暴露，错误率同步升高。**这类接口如果不写 XPath 断言，很容易在"页面结构变了但文本还在"的情况下漏掉真实错误。**

【面试考察】
面试官："XPath 断言和 JSON 断言分别在什么场景用？Use Tidy 是干什么的？"

参考回答框架：
1. 按响应格式选：JSON 接口用 JSON Assertion，XML / HTML（服务端渲染页）用 XPath Assertion
2. XPath 断言的本质是**结构校验**（节点/属性是否存在），比纯文本包含更精确，能排除静态文案干扰
3. Use Tidy：真实 HTML 标签常不闭合，需要先容错修整才能用 XML 解析器定位节点，所以 HTML 必须勾；XML/XHTML 本身合法，勾上反而可能被改写，所以取消
4. 反向校验用 True if nothing matches（都不匹配才通过），例如校验"登录后的页面不应该再出现登录表单"

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| HTML 页面不勾 Use Tidy | 原文明确：处理 HTML 格式必须勾选；XML/XHTML 才取消 |
| 把 XPath Assertion 当成取值工具 | 断言只判断通过/失败，取不到变量；要"取值给后续请求用"必须用后置处理器的 XPath Extractor（见 [[Ch24-JMeter后置处理器]]） |
| 以为"引用名称"是 XPath Assertion 的参数 | 课程原文这段是从提取器串入的内容（见上面勘误），断言元件没有该参数 |
| 勾了 True if nothing matches 还按"节点存在"理解 | 勾选后语义反转：XPath 查不到任何节点才算通过 |
| 用浏览器 F12 能查到节点，就以为 JMeter 也能查到 | 浏览器会补全 DOM（如自动插入 `tbody`）且执行 JS 渲染；JMeter 只解析**原始响应体**（【扩展知识】） |
| 表达式写错不先 Validate | 表达式语法错误会直接导致断言失败（表现为"永远不通过"），先点 Validate 排除表达式问题 |

【我的理解】引导题（用自己的话回答）：
1. 同样一个"登录后页面"的校验，用 `Text Response contains "退出登录"` 和用 `XPath //a[@id='logout']` 各自的风险是什么？
2. 为什么"XML 返回要取消 Use Tidy"？请从"XML 本身是否合法"的角度解释。

### 知识点5：JSON Assertion（Json 断言）

【课程原话/定义】
JSON Assertion 用于验证 JSON 格式的响应数据是否符合预期。在进行 API 接口性能测试时，通常会返回 JSON 格式的响应数据，通过 JSON Assertion 可以根据预定义的 JSON 断言规则来验证返回的 JSON 数据是否正确。

**参数配置**：

| 参数 | 含义（课程原文） |
|------|------------------|
| Assert JSON Path exists | 用于断言的 JSON 元素的路径（实际结果） |
| Additionally assert value | 如果想要用某个值生成断言，请选择复选框 |
| Match as regular expression | 使用正则表达式断言 |
| Expected Value | 期望值（期望结果） |
| Expect null | 如果希望为空，请选择复选框 |
| Invert assertion (will fail if above conditions met) | 反转断言（如果满足以上条件则失败） |

**课程案例**：检查天气请求响应的 JSON 数据中，city 对应的内容是否为 '北京'。（步骤一添加天气 HTTP Request + JSON Assertion + 查看结果树 → 步骤二配置 → 步骤三查看结果：断言成功）

【为什么？】
现在的接口九成以上返回 JSON，如果用 Response Assertion 去断 JSON 里的某个字段，你只能写正则或子串（`"city":"北京"`）——一旦服务端调整字段顺序、或字段里多了空格（`"city" : "北京"`），断言就误报。JSON Assertion 换了一条思路：**先把响应体按 JSON 解析成对象树，再用 JSON Path 定位字段，最后比较值**。带来的两个好处：
1. **对格式噪声免疫**：字段顺序、缩进、空格、换行都不影响结果，只有"字段的值"会影响结果；
2. **自带"响应合法性"校验**：如果响应根本不是合法 JSON（网关错误页、HTML 超时报错页），解析直接失败，断言随之失败——这本身就是一道很有价值的保护。

它也能表达"反转"语义（Invert assertion）：业务上"期望失败"的场景（限额超限、重复提交、权限不足）配合 Expect null 使用，可以把负向用例也纳入压测统计。

【必须掌握】

| 配置项 | 说明 | 实践建议 |
|--------|------|----------|
| Assert JSON Path exists | JSON Path 表达式（实际结果） | 路径按接口返回结构写，如 `$.weatherinfo.city`；写错路径 → 找不到节点 → 断言失败 |
| Additionally assert value | 勾上后才比较值 | **不勾就只能断"字段存在"**，断不了值 |
| Expected Value | 期望值 | 与 Additionally assert value 配合使用 |
| Match as regular expression | 期望值按正则匹配 | 值动态（如订单号 `\d{16}`）时用 |
| Expect null | 期望字段为空 | 与 Expected Value 二选一，不要同时设 |
| Invert assertion | 满足条件则失败 | 负向校验用（期望被限流、期望无该字段） |

【企业场景】
你压"查询用户余额"接口，断言这样配：JSON Path = `$.data.balance`，勾 Additionally assert value，Expected Value 用正则 `^\d+(\.\d{1,2})?$`（Match as regular expression 勾上）——这样压测跑出来的错误率里，"返回了错误结构 / 余额为空 / 余额格式异常"这三种情况都会被抓出来。另一个常用招式是**先断言"字段存在"再断言"值合法"**：对返回结构复杂的接口，先用只勾 Path 的断言兜住"结构没变"，再加一条带 Expected Value 的断言卡关键值，失败时你能一眼看出是"结构问题"还是"值问题"。

【面试考察】
面试官："压测接口时，怎么校验返回的 JSON 字段值？"

参考回答框架：
1. 元件选择：JMeter 内置 JSON Assertion，用 JSON Path 定位字段（`$.a.b` 这种形式）
2. 必须同时满足两个勾选才校验值：Assert JSON Path exists（路径）+ Additionally assert value（启用值比较）
3. 值动态时勾 Match as regular expression，用正则覆盖（订单号、时间戳、金额）
4. 负向场景用 Expect null / Invert assertion；另外 JSON 解析失败本身也说明响应不是合法 JSON，是一道免费的保护

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 只填 JSON Path 就以为断了值 | 不勾 Additionally assert value 时只断言"字段存在"，值错了也不会失败（原文参数说明） |
| 想用正则却不勾 Match as regular expression | 不勾时 Expected Value 按**普通字符串**比较，`\d{16}` 会被当成字面量 |
| 同时设置 Expected Value 和 Expect null | 语义冲突，二选一（Expect null 表示"希望为空"） |
| 拿 JSON 断言去断 HTML 页面 | 响应不是合法 JSON 时直接失败；这既可能是"保护生效"，也可能是"元件用错了" |
| 结构变化频繁的接口把路径写死 | 接口加了一层 data 包装（`$.city` → `$.data.city`）就会全线失败；接口改版后要同步更新断言（【扩展知识】） |
| 依赖 JSON Path 的"模糊匹配"写法 | `$..city` 这类递归写法能匹配多层，但也会匹配到意外的节点；结构已知时用精确路径更可靠（【扩展知识】） |

【我的理解】引导题（用自己的话回答）：
1. 只勾 `Assert JSON Path exists` 和同时勾 `Additionally assert value`，两者的失败条件分别是什么？举一个"前者通过、后者失败"的例子。
2. 什么业务场景适合用 `Invert assertion`？举一个你熟悉的接口（提示：重复提交、权限不足、限额超限）。

### 知识点6：四种断言怎么选 + 课程原文勘误汇总

【课程原话/定义】
课程总结部分原文：断言元件的介绍、常用的断言元件的使用。（本页四类断言 + 添加元件步骤截图）

【为什么？】
选错断言会导致两种后果：**误报**（断言太严，天天红）和**漏报**（断言太松，错误率永远 0）。判断标准不是"哪个更厉害"，而是"**我的响应用什么方式描述最稳定**"：

| 响应特征 | 应选元件 | 原因 |
|----------|----------|------|
| 业务 code / 短固定报文 | Response Assertion（Response Code、Equals） | 只需一格比较，CPU 开销最低 |
| 响应体是 JSON，要断字段值 | JSON Assertion | 对字段顺序/空格免疫（正则做不到） |
| 响应体是 XML / HTML 结构 | XPath Assertion | 结构级校验，能排除纯文案干扰 |
| 只在意"内容有没有缩水" | Size Assertion | 数字节不解析，大并发下最轻的兜底 |

**课程原文勘误（本页）**：

| 课程原文表述 | 正确理解 |
|--------------|----------|
| XPath Assertion 参数里出现"引用名称：…如填写 title，则可用 ${var_regexp2} 引用它" | 该段属于 XPath 提取器/正则表达式提取器的参数；断言元件没有"引用名称"，不输出变量 |
| "常用的断言原件的使用"（总结处错别字） | 应为"常用的断言元件"（元件 = component） |
| Size Assertion "在性能测试中验证响应的大小是否符合要求" | 它的落脚点是"内容是否合理"的正确性校验，不是性能指标 |
| Response Assertion 的 contains 说明为"文本包含指定的正则表达式"，Substring 说明为"包含指定字符串" | 表述本身正确，但要注意两者差别：contains 带正则语义、Substring 是纯字符串包含（都区分大小写） |

【必须掌握】

| 断言的工程化要点 | 做法 |
|------------------|------|
| 断言放置层级 | 只针对某个请求就用它作为该请求的子节点；要覆盖同级全部请求放在上层（作用域规则见 [[Ch25-JMeter执行顺序]]） |
| 断言数量 | 每个请求 1~2 条：状态码断言 + 核心业务断言（性能脚本不是功能用例，别堆断言） |
| 断言失败后要能查证 | 保留 View Results Tree / Debug Sampler 用于调试，正式压测时关掉（监听器很吃内存，见 [[Ch25-JMeter执行顺序]]） |
| 断言表达式先用小样本验证 | 先用 1 个线程 1 次循环跑通、看断言结果，再放大并发 |
| 断言与结果指标的关系 | 断言失败进入错误率统计；错误率高时先区分是"脚本失效"还是"系统异常"（看响应体） |

【企业场景】
你接手一个已有的压测脚本交接文档，第一步不是直接加压，而是**审查断言**：如果脚本里只有 View Results Tree、没有任何断言，说明这套脚本的数据不可信，你要补上"每个核心请求 + 响应码断言 + 业务 code 断言"，再跑一次基线，然后才敢对外报数字。同时你会关掉所有 View Results Tree / Debug Sampler——**监听器保留在压测计划里会让施压机内存暴涨**，几个回合就能把施压机自己压垮，这在企业里是比断言写错更常见的低级事故。

【面试考察】
面试官："给你一个返回 JSON 的登录接口，压测脚本里你会加哪些断言？"

参考回答框架：
1. 第一层：Response Assertion 断 Response Code = 200（协议层）
2. 第二层：JSON Assertion 断 `$.code` = 0（或断 `$.data.token` 存在），拦截"HTTP 200 但业务失败"
3. 第三层（可选）：Size Assertion 设 Response Body 下限，兜住空体/降级报文
4. 收尾：确认监听器只保留聚合报告类元件，调试用的 View Results Tree 在正式压测前移除

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 每个请求都堆三四个断言"求安心" | 断言要解析响应，直接消耗施压机 CPU；性能脚本每个请求 1~2 条核心断言即可，其余靠小样本功能验证覆盖 |
| 用断言的"测试模式"当成"我要判断的条件" | 测试字段是**实际结果来源**，测试模式是**预期结果**；两者写反会出现"永远通过"或"永远失败" |
| 断言失败就认定系统有缺陷 | 先区分"脚本失效"（未登录、token 过期、参数错）与"系统异常"（看响应体），归因错误会把脚本 bug 报成缺陷 |
| 把调试验证用的元件留在正式压测计划里 | View Results Tree / Debug Sampler 会累积响应数据占内存，正式压测前必须移除（【扩展知识】） |
| 断言写好后不复验就上大并发 | 断言表达式必须先用 1 线程 1 迭代验证通过，再放大；否则错误率虚高，白跑一轮 |

【我的理解】引导题（用自己的话回答）：
1. 如果一个接口同时有"JSON 结构断言"和"大小断言"，当压力下服务端开始返回限流报文时，你预期**哪条断言先失败**？为什么？
2. 为什么"每加一条断言就多消耗一点施压机资源"这个结论，会让你在 5000 并发的压测里改变断言的写法？
