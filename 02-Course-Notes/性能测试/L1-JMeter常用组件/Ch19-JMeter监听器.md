### 知识点1：监听器是什么，以及它在报告链条里的位置

【课程原话/定义】
> JMeter 监听器是用于收集、查看和分析测试结果的重要组件，用于监控性能测试过程中的请求响应数据、断言结果、错误信息等，帮助用户评估应用程序的性能和功能。
>
> JMeter 监听器是用于在性能测试执行期间收集、显示和分析测试结果的组件。它允许用户实时监控测试的执行情况，并以图表、表格或其他形式呈现性能数据。JMeter 监听器提供了丰富的功能，可以帮助用户深入了解系统的性能特征，识别性能瓶颈，并优化系统的性能。

课程给出 **常用的监听器**：
- View Results Tree（查看结果树）
- Aggregate Report（聚合报告）
- Backend Listener（后端监听器）
- Graph Results（图形结果，见「监听器与测试结果」页）

添加路径：`测试计划 → 线程组 → (右键添加) 监听器 → 选择具体监听器`。

【为什么？】
监听器是「**压测数据的出口**」。压测的本质是「施加压力 → 采集响应 → 得出结论」，前两步靠线程组和采样器完成，最后一步完全落在监听器上：它决定你看到的是响应时间分布、吞吐量曲线，还是每条响应的原始报文。这里有个反直觉但极其重要的机制——**监听器自己不产生负载，但会消耗加压机资源**。它接收从采样器传回的 SampleResult 对象，按自身类型做聚合或缓存：查看结果树会缓存完整响应体（内存杀手），聚合报告只做累加统计（开销极小）。所以「选什么监听器」直接决定了你能压到多高的并发而不让加压机先趴下。

【必须掌握】

| 监听器 | 展示形式 | 典型用途 | 资源开销 |
|---|---|---|---|
| View Results Tree | 树形明细（请求/响应全文） | 调试脚本、定位单请求问题 | 高（缓存响应体） |
| Aggregate Report | 表格（聚合统计） | 出结论、做性能分析 | 低 |
| Graph Results | 图表（实时曲线） | 观察趋势、粗略判断稳定性 | 中 |
| Backend Listener | 推送到外部时序库 | 生产级监控、长期观察 | 低 |
| View Results in Table | 表格（逐条明细） | 看单条请求耗时、验证并发是否同时发生 | 中 |

【企业场景】
你负责一次常态化压测，脚本调试阶段和正式加压阶段用的是完全不同的监听器组合。调试阶段你用「查看结果树」加「View Results in Table」，因为要确认响应内容、确认请求参数、确认并发是否真的同时到达；正式加压时你会把这两个全部禁用，只留「聚合报告」或直接用「后端监听器」把数据推到 InfluxDB + Grafana。原因很实在：有一次你忘了关查看结果树，200 并发下加压机内存被响应体撑爆，测试直接中断，白跑了一小时。从那次起，「压测前检查监听器」成了你的检查清单第一条。

【面试考察】
1. **面试官怎么问**：「压测时你一般加哪些监听器？」
   **回答框架**：调试期用查看结果树 + View Results in Table，正式压测只保留聚合报告 / 后端监听器；强调监听器本身耗资源，正式加压要精简。
2. **面试官怎么问**：「监听器会影响压测结果吗？」
   **回答框架**：会。它不是「只看」，而是会缓存数据、消耗内存和 CPU，进而导致加压机先到瓶颈，使 TPS 偏低、耗时偏高。这是必须主动规避的失真源。
3. **面试官怎么问**：「怎么把压测结果持久化下来？」
   **回答框架**：聚合报告「所有数据写入一个文件」写出 jtl/csv，或用后端监听器推送到 InfluxDB/Graphite 做可视化。

【易错点】

| 常见错误 | 正确理解 |
|---|---|
| 认为监听器只是「看结果」，不影响性能 | 监听器会缓存和计算数据，消耗加压机资源，开重型监听器会明显拉低压测结果 |
| 正式压测时仍开着查看结果树 | 查看结果树缓存完整响应体，高并发下极易 OOM，必须禁用或删除 |
| 把监听器加在「测试计划」层级并以为作用域是单个线程组 | 加在测试计划层级的监听器收集所有线程组的数据，加在线程组内只收该线程组 |
| 用禁用（Disable）代替删除，忘记禁用状态也能被误开启 | 删除或明确禁用并在压测前检查，最好把「检查监听器」写进流程清单 |

【我的理解】
1. 「监听器不产生请求，但会影响压测结果」——请你解释这个看似矛盾的结论是怎么成立的？（提示：从加压机资源分配的角度想。）
2. 如果一定要在正式压测中保留明细能力，你会怎么设计，才能既拿到数据又不让加压机成为瓶颈？

> 监听器的字段级细节（查看结果树的三种查看模式与 Sampler result / Request / Response data 三面板、Graph Results 的参数与底部统计含义）**详细字段见 [[Ch31-监听器与测试结果]]**；本知识点只回答"有哪些监听器、各自什么代价、该怎么选"。

### 知识点2：Aggregate Report（聚合报告）—— 出结论靠的就是这张表

【课程原话/定义】
> 用于生成聚合报告，包括各个请求的响应时间、吞吐量、错误率等统计数据，帮助用户全面了解性能测试结果。
>
> 添加 Aggregate Report：测试计划 → 线程组 → (右键添加) 监听器 → Aggregate Report。

课程给出的 **各个参数说明（课程原话逐行）**：

| 参数 | 课程原文说明 |
|---|---|
| Label | 取样器别名，如果勾选 Include group name，则会添加线程组的名称作为前缀 |
| Samples | 取样器运行次数 |
| Average | 请求（事务）的平均响应时间 |
| Median | 中位数 |
| 90% Line | 90% 用户响应时间 |
| 95% Line | 90% 用户响应时间 |
| 99% Line | 90% 用户响应时间 |
| Min | 最小响应时间 |
| Max | 最大响应时间 |
| Error | 错误率 |
| Throughput | 吞吐率 |
| Received KB/sec | 每秒收到的千字节 |
| Sent KB/sec | 每秒收到的千字节 |

> ⚠️ **课程原文勘误**：上表中 90% Line / 95% Line / 99% Line 三行的说明都写成了「90% 用户响应时间」，这是原文笔误。正确含义是分别对应 **90% / 95% / 99% 的百分位响应时间**（即「90%/95%/99% 的用户响应时间不超过该值」）。同时 `Sent KB/sec` 的说明被写成「每秒收到的千字节」，正确应为 **每秒发送的千字节**（Received 才是「收到」）。

【为什么？】
聚合报告是压测的「结论层」。它只做轻量累加统计，开销极小，因此可以放心在正式压测中开启。它存在的根本原因是：**平均响应时间会骗人**。服务端只要有一小部分请求变得很慢（GC、锁竞争、连接池耗尽、慢 SQL），平均值可能纹丝不动，但用户已经明显感到卡顿。所以工业界的验收口径普遍用「百分位 + 错误率 + 吞吐量」三元组，而不用平均值。这也是为什么聚合报告里同时给出了 90/95/99 三条 Line——它们共同刻画出「长尾有多长」。经验上，99% Line 与 Average 的比值越大，说明系统的不稳定性越严重。

【必须掌握】

| 指标 | 含义 | 使用要点 |
|---|---|---|
| Samples | 该 Label 的采样器执行次数 | 用来核对实际压出的请求数是否符合设计 |
| Average | 平均响应时间 | 只做参考，不可单独作为验收依据 |
| Median | 中位数（50% 分位） | 比 Average 更抗极端值干扰，反映「典型用户体验」 |
| 90%/95%/99% Line | 百分位响应时间 | 验收核心指标，常见 SLA 用 P95 或 P99 |
| Min / Max | 最小 / 最大响应时间 | Max 异常大通常意味着有偶发慢请求或超时 |
| Error | 错误率 | 必须结合断言才有意义；无断言的错误率会虚低 |
| Throughput | 吞吐率 | 结合并发数判断系统是否已达到能力上限 |
| Received / Sent KB/sec | 每秒接收 / 发送的千字节 | 判断是否为带宽瓶颈的重要依据 |

【企业场景】
你要给「订单查询」接口出一份验收结论。业务方的要求是「P99 < 800ms，错误率 < 0.1%」。你跑完 30 分钟稳定压测后，聚合报告显示 Average 260ms、Median 210ms、95% Line 520ms、99% Line 1450ms、Error 0.3%。你不能只看 Average 说「通过」——因为 99% Line 是要求值的 1.8 倍，且错误率超标。你的结论应该是「不通过」，并给出定位方向：99% Line 与 P95 差距悬殊，说明存在长尾，需要结合服务端监控排查 GC 或慢 SQL。这份「用百分位说话」的报告才是研发愿意接受、业务方看得懂的输出。

【面试考察】
1. **面试官怎么问**：「聚合报告里你都看哪些指标？为什么不用平均值？」
   **回答框架**：看 Samples / 百分位（95、99）/ Error / Throughput；平均值会被少数极快或极慢的请求拉偏，掩盖长尾，验收要用百分位。
2. **面试官怎么问**：「90% Line 是什么意思？」
   **回答框架**：90% 的样本响应时间不超过该值，即 90 百分位响应时间；同理 95%、99% Line，数值越大覆盖比例越高、越接近最差情况。
3. **面试官怎么问**：「Throughput 该怎么用？」
   **回答框架**：它反映单位时间完成的样本数，是系统处理能力；要结合并发数一起看——并发上升而吞吐不再增长，说明已到拐点。
4. **面试官怎么问**：「错误率怎么算才可信？」
   **回答框架**：必须先给每个请求加响应断言（状态码 + 业务码），否则「请求发出去了」会被算成成功，错误率虚低。

【易错点】

| 常见错误 | 正确理解 |
|---|---|
| 只看 Average 就下结论 | 平均值掩盖长尾；验收必须看 95%/99% Line 与错误率，课程原文把 90%/95%/99% Line 都写成「90% 用户响应时间」属笔误，实际是三个不同百分位 |
| 把 `Sent KB/sec` 也理解成「每秒收到的千字节」 | Received KB/sec 是收到，Sent KB/sec 是发出，方向相反（课程原文此处说明重复，需自行纠正） |
| 认为 Samples 等于「请求数」 | Samples 是该 Label 的采样器执行次数；一个事务包含多个请求时两者不等 |
| 报告里 Label 混乱，分不清哪个是哪个 | 命名要带业务含义；可用 Include group name 加线程组前缀区分同名取样器 |
| 没有断言就看 Error 列，得出「错误率 0，性能完美」 | 没有断言时 4xx/5xx 之外的业务失败不会被识别，错误率不可信 |

【我的理解】
1. 假设两个版本的接口 Average 都是 300ms，但 A 版本 99% Line 是 900ms、B 版本 99% Line 是 2500ms。请你判断哪个版本对用户体验更友好，并说明你会用什么业务语言向产品经理解释这个差异。
2. 课程里 90%/95%/99% Line 的说明都写成了「90% 用户响应时间」。请你自己想清楚：如果三者含义真的一样，聚合报告为什么还要分三行给出？这三行各自的决策价值是什么？

### 知识点3：Backend Listener（后端监听器）—— 把结果推进时序数据库

【课程原话/定义】
> 用于将测试结果发送到指定的后端系统，如 InfluxDB、Graphite 等，实现实时性能监控和结果存储并以图标形式展示各项指标。

课程给出的 **相关参数配置（原文要点）**：

| 参数 | 课程原文说明 |
|---|---|
| Backend Listener implementation | BackendListenerClient 类的实现，Jmeter 默认提供如下两种实现。`org.apache.jmeter.visualizers.backend.graphite.GraphiteBackendListenerClient`：Graphite 作为存储。`org.apache.jmeter.visualizers.backend.graphite.InfluxdbBackendListenerClient`：InfluxDB 作为存储。注：后续只对 InfluxdbBackendListenerClient 进行介绍 |
| Async Queue size | 异步队列大小。队列值包含异步处理时的度量标准。除非有一些特定的性能问题，否则最好不要改动默认的 5000 |

**InfluxdbBackendListenerClient 的配置参数（课程原话）**：

| 参数 | 课程原文说明 |
|---|---|
| influxdbMetricsSender | `org.apache.jmeter.visualizers.backend.influxdb.HttpMetricsSender` |
| influxdbUrl | influx 数据库的 url。example : `http://influxHost:8086/write?db=jmeter` |
| application | 被测试的应用名称。此值也作为名为 “application” 的标记存储在 “events” 中 |
| measurement | 使用默认的 “jmeter” 即可 |
| summaryOnly | 为 ture 的情况下，只推送一个集合结果；为 flase 的情况下，推送每个请求元件的结果，以及集合结果 |
| samplersRegex | 正则表达式将与样本名称匹配并发送到后端。默认匹配所有 |
| percentiles | 要发送到后端的百分位数，多个值已分割 |
| testTitle | 测试名称。默认的设置为 Test name。该值作为名为 “text” 的字段存储在 “事件” 度量中。JMeter 在测试的开始和结束时自动生成一个注释，其值以 'started' 和 'ended' 结尾 |
| eventTags | 自定义标签 |

> ⚠️ **课程原文勘误**：原文把 `InfluxdbBackendListenerClient` 的包路径写成 `org.apache.jmeter.visualizers.backend.graphite.InfluxdbBackendListenerClient`，与 Graphite 实现放在同一个 graphite 包下。实际 InfluxDB 实现位于 `influxdb` 包。另外 `summaryOnly` 的取值原文写作 “ture/flase”，正确拼写为 `true/false`；`percentiles` 的说明「多个值已分割」语义不完整，实际是**多个值以分隔符隔开填写**。

【为什么？】
前面几个监听器都是「本地看」：数据留在 JMeter 进程内存里，压测结束就没了（除非手动写文件），团队其他人看不到实时进展，也无法和历史基线对比。后端监听器的思路完全不同——它把每个样本的指标**异步推送**到外部时序数据库（InfluxDB / Graphite），再由 Grafana 等做可视化。这带来三个质变：**实时**（压测过程中就能看曲线）、**持久**（可长期留存做版本间对比）、**解耦**（加压机只管压，数据展示交给监控栈）。Async Queue size 默认 5000 的意义也在这里：推送是异步的，队列起到缓冲作用，避免网络抖动阻塞压测主流程；除非队列被打满（表现为数据丢失或内存增长），否则不该动它。

【必须掌握】

| 参数 | 建议值 / 要点 |
|---|---|
| implementation | InfluxDB 方案选 `InfluxdbBackendListenerClient` |
| influxdbUrl | `http://<host>:8086/write?db=jmeter`，host 与库名按实际环境替换 |
| application | 填被测应用名，作为 tag 用于多应用区分（Grafana 上做筛选靠它） |
| measurement | 保持默认 `jmeter` |
| summaryOnly | true 只推集合结果（数据量小）；false 推送每请求元件 + 集合结果（细粒度、量大） |
| samplersRegex | 只把关心的样本名推过去，默认全部匹配 |
| percentiles | 需要哪些百分位就填哪些（如 90;95;99），用分隔符隔开 |
| testTitle | 测试名称，用于区分不同轮次压测；JMeter 会自动生成 started/ended 注释 |
| eventTags | 自定义标签，用于给压测打环境/版本标记 |
| Async Queue size | 默认 5000，非特殊性能问题不要改 |

【企业场景】
你所在团队要把压测常态化：每次版本发布前跑一轮基准压测，要求「结果可对比」。你搭的方案是 JMeter（后端监听器）→ InfluxDB → Grafana。每轮压测的 `testTitle` 带上版本号（如 `v2.3.0-baseline`），`application` 填服务名，`eventTags` 标记环境。压测过程中研发同学直接在 Grafana 上看实时曲线，不用等你导出报告；压测结束后，你把本轮的 P95 曲线和上一版本叠加对比，一眼就能看出「这次发布让 P95 整体抬高了 80ms」。这套方案比「跑完发一张聚合报告截图」专业得多，也让性能回归变成可自动化的流程。

【面试考察】
1. **面试官怎么问**：「压测结果怎么做到实时可视化和长期留存？」
   **回答框架**：用 Backend Listener 推到 InfluxDB/Graphite，Grafana 做看板；关键参数是 influxdbUrl、application、testTitle、summaryOnly。
2. **面试官怎么问**：「summaryOnly 什么时候设 true？」
   **回答框架**：只关心总体指标、想减小写入压力时设 true；需要按请求粒度下钻就设 false，但要评估 InfluxDB 写入量。
3. **面试官怎么问**：「怎么保证压测数据不丢？」
   **回答框架**：后端监听器是异步推送，有 Async Queue 缓冲；队列满或网络不通可能丢数据，所以要监控加压机资源与写入情况，必要时降低推送量。

【易错点】

| 常见错误 | 正确理解 |
|---|---|
| 认为后端监听器会拖慢压测主流程 | 它是异步推送 + 队列缓冲；但配置不当（队列打满、网络阻塞）仍会影响加压机 |
| 把 InfluxDB 实现的包路径写成 graphite 包 | 原文此处有误；InfluxDB 实现在 `influxdb` 包下，配置时以实际类路径为准 |
| 忘记填 application / testTitle，多轮压测数据混成一锅 | 这两个字段正是用于区分应用与轮次的 tag，缺失后 Grafana 上无法有效筛选 |
| 随意调大 Async Queue size | 默认 5000 是权衡结果，调大只会增加内存占用，不解决根本问题 |
| 把 summaryOnly 写成 `ture`（照抄原文拼写错误） | 正确值是 `true` / `false` |

【我的理解】
1. 后端监听器把数据推到外部库，为什么课程特别强调 Async Queue size「最好不要改动默认的 5000」？请你自己推演：这个队列在什么情况下会被打满，打满之后会发生什么？
2. `summaryOnly = true` 与 `false` 之间的取舍，本质上是「数据量」和「下钻能力」的权衡。请你自己判断：做一次 8 小时的稳定性压测，你会怎么选？为什么？

### 知识点4：监听器的使用规范 —— 什么时候开、什么时候关

【课程原话/定义】
> JMeter 监听器提供了丰富的功能，可以帮助用户深入了解系统的性能特征，识别性能瓶颈，并优化系统的性能。

原文只讲了「有哪些监听器、怎么配」，**没有给出使用规范**，以下是【扩展知识】，来源于压测工程实践。

【扩展知识】压测前检查清单（监听器部分）：

| 阶段 | 该开什么 | 该关什么 |
|---|---|---|
| 脚本调试（单线程） | 查看结果树、View Results in Table、Debug Sampler | 无需关闭，怎么方便怎么来 |
| 基准测试（小并发） | 聚合报告 + 后端监听器、图形结果 | 关闭查看结果树 |
| 正式加压（高并发） | 后端监听器（推时序库）或聚合报告 | 关闭查看结果树、View Results in Table、图形结果 |
| 长时间稳定性测试 | 后端监听器 + 聚合报告 + 结果写文件 | 全部明细类监听器 |

【为什么？】
监听器违背直觉的地方在于：它不产生负载却消耗资源。查看结果树要为每个样本保存完整响应体（含 HTTP 头），假设单响应 500KB、200 并发、压测 10 分钟、TPS 200，那就是 200×600×500KB ≈ 60GB 的瞬时数据流通量——即使 JMeter 有上限保护，内存压力和 GC 停顿也足以让加压机的表现先劣化。于是你测出来的是「加压机的能力」而不是「被测系统的能力」。这个失真方向很危险：它表现为「TPS 上不去」，容易被误读为「系统性能不行」，从而做出错误的扩容决策。所以规范只有一句话：**明细用来看，聚合用来结论，高并发时只看聚合。**

【必须掌握】

| 原则 | 说明 |
|---|---|
| 调试期尽情报错，加压期尽量精简 | 两阶段用两套监听器组合 |
| 结论类监听器（聚合报告）可以常开 | 它只做累加统计，开销极小 |
| 明细类监听器（查看结果树）必须关 | 它是加压机内存与 CPU 的主要消耗源 |
| 结果落盘要有策略 | 全量 jtl 文件会非常大，可按需选择只记录错误或只记录必要字段 |
| 加压机资源要监控 | CPU、内存、网络带宽，任何一项接近饱和都要怀疑加压能力不足 |

【企业场景】
你负责一次大促前的容量评估，需要压到 3000 并发。你在 JMeter 脚本里配置了后端监听器 + 聚合报告，并把结果按需落盘；加压机是 4 台 8C16G 的机器，压测过程中你同时盯着每台机器的 CPU 和内存。压到 2500 并发时你发现加压机 CPU 都到 85% 以上，你立刻判定「这个数字不能作为系统容量结论」，于是补机器继续升并发。整个过程中你没有开过一次查看结果树——因为一旦开了，你连 2500 并发都压不上去，还很难分清瓶颈在谁身上。

【面试考察】
1. **面试官怎么问**：「你怎么保证压测结果反映的是被测系统而不是加压机？」
   **回答框架**：精简监听器、显式设超时、监控加压机 CPU/内存/网络、必要时分布式加压；如果加压机接近饱和，结论无效。
2. **面试官怎么问**：「压测报告里为什么有大量不认识的 Label？」
   **回答框架**：多来自静态资源和调试期间的监听器产物；正规做法是命名规范 + 正式压测前清理调试元件。
3. **面试官怎么问**：「你的压测流程里，监听器是怎么分阶段使用的？」
   **回答框架**：调试期用明细、正式期只用聚合/后端监听器、稳定性测试加结果落盘并配合时序库做长周期对比。

【易错点】

| 常见错误 | 正确理解 |
|---|---|
| 「监听器又不发请求，开着没事」 | 它不发请求但缓存数据，是加压机瓶颈的头号来源 |
| 压测中途为了看现象临时开启查看结果树 | 中途开启同样会引起内存突增；要看现象就停压、单线程复现 |
| 用图形结果做长时间高并发压测的唯一监控 | 图形结果需要维护曲线数据，长时间高压下也有开销，生产级监控应交给时序库 |
| 结果文件全量落盘且不清理，磁盘写满导致压测中断 | 结果落盘要有容量策略，只记必要字段或只记错误 |

【我的理解】
1. 请你把「明细类监听器」和「聚合类监听器」的开销差异，从「它们各自需要保存什么数据」这个角度解释清楚。这能解释为什么一个能常开、一个必须关。
2. 如果一次压测的 TPS 明显低于预期，你如何快速判断是「被测系统到瓶颈」还是「加压机到瓶颈」？请列出你会看的证据清单。
