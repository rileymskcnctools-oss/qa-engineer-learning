### 知识点1：JMeter 八大组件（课程原文列举）

【课程原话/定义】
课程原文列出 **JMeter 八大组件**：
1. 线程组
2. 配置元件
3. 前置处理器
4. 定时器
5. 取样器
6. 后置处理器
7. 断言
8. 监听器

【为什么？】
八大组件其实就是压测脚本的**"数据流"环节的物理划分**：一条请求从"用户想发"到"结果被记录"，中间必然经过"准备数据 → 组装请求 → 施加节奏 → 发出请求 → 拿回响应 → 判定结果 → 记录数据"七个动作，JMeter 为每个动作提供了一类元件。理解这张表，等于把整个 L2 模块（乃至整个 JMeter 学习）的知识点都挂到一根骨架上：

| # | 组件 | 职责（一句话） | 对应课程章节 |
|---|------|----------------|--------------|
| 1 | 线程组 | 定义"多少个用户、多久跑完、跑几轮"——压力的来源与容器 | L2 后续（参数化与并发） |
| 2 | 配置元件 | 准备配置与数据（请求头、Cookie、缓存策略、CSV 数据），作用域内共享 | [[Ch22-JMeter常用配置元件剖析]] |
| 3 | 前置处理器 | 取样器执行**之前**处理请求（改参数、算签名、造数据、超时兜底） | [[Ch23-JMeter前置处理器]] |
| 4 | 定时器 | 控制请求之间的**节奏/等待**（思考时间、吞吐量控制） | L2 后续 |
| 5 | 取样器 | **真正发起请求**的元件（HTTP Request 等），是执行链的核心 | L2（HTTP 请求元件） |
| 6 | 后置处理器 | 取样器执行**之后**处理响应（提取值存成变量、供后续请求引用） | [[Ch24-JMeter后置处理器]] |
| 7 | 断言 | 判定响应是否符合预期（协议层 + 业务层） | [[Ch21-JMeter断言元件的使用]] |
| 8 | 监听器 | 收集与展示结果（查看结果树、聚合报告等） | L2 后续（报告与监听器） |

【必须掌握】

| 关键认知 | 说明 |
|----------|------|
| 只有取样器"发请求" | 其余组件都是围绕取样器的准备、约束、判定与记录 |
| 线程组是"容器 + 调度者" | 它决定并发数与迭代次数，不是执行链上的一环（【扩展知识】） |
| 七大组件的组合顺序固定 | 见知识点2；记住"取样器在中间"是最省力的记法 |
| 每个组件都有作用域 | 放错层级 = 生效范围错（知识点4） |
| 重复出现的元件类型 | 同一作用域可以出现多个同类元件，按从上到下处理（知识点3） |

【企业场景】
你拿到一份陌生同事写的压测脚本做评审。最有效的读法**不是**从上往下逐个看元件，而是先按"八大组件"给树里的每个节点分类，然后回答三个问题：① 取样器有几个、构成什么业务链路；② 配置元件（头/Cookie/CSV）在谁下面、作用域对不对；③ 有没有断言、监听器是否只留了必要的那几个。**用八大组件给脚本做"分类体检"，通常 3 分钟就能指出问题**——这也是面试中描述"我如何 Review 一个压测脚本"时的标准框架。

【面试考察】
面试官："说说 JMeter 有哪些组件。"

参考回答框架：
1. 念出八类：线程组、配置元件、前置处理器、定时器、取样器、后置处理器、断言、监听器
2. 按数据流解释：准备（配置元件/前置处理器）→ 节奏（定时器）→ 发请求（取样器）→ 取结果（后置处理器）→ 判定（断言）→ 记录（监听器）
3. 强调取样器是唯一真正发起请求的元件，其余都是围绕它的周边能力
4. 关联作用域：所有组件都受"放在哪一层"的影响，放错层级是最常见的脚本缺陷

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 把线程组当成执行链上的一环 | 【扩展知识】线程组是容器与调度者（定并发、迭代），执行链讲的是"在一个取样器周期内元件怎么跑" |
| 认为监听器"越详细越好" | 监听器要保存结果数据，View Results Tree 在大并发下会吃爆内存；正式压测只留聚合类监听器 |
| 把定时器理解成"延时元件可有可无" | 定时器决定请求节奏，直接影响 TPS 与并发模型；它是压力曲线能"可控"的关键之一 |
| 只记组件名不记职责 | 面试真正考的是"哪个组件在什么时机做什么"，而不是背清单 |

【我的理解】引导题（用自己的话回答）：
1. 请用"数据流"复述八大组件：哪些是"请求发出前"的，哪些是"响应回来之后"的？
2. 为什么说"取样器是执行链的核心，其余组件都围绕它"？

### 知识点2：同一作用域内不同元件的执行顺序（课程原文核心结论一）

【课程原话/定义】
课程原文：在同一个作用域（目录/级别/缩进）的不同元件的执行顺序是：
**配置元件 → 前置处理器 → 定时器 → 取样器 → 后置处理器 → 断言 → 监听器**

【为什么？】
这条链不是随意排列的，它严格对应"一次请求的正确处理次序"：
1. **配置元件最先**：它要把请求头、Cookie、缓存策略、CSV 变量都准备好，后面的元件和取样器才有数据可用；
2. **前置处理器第二**：在请求组装完成后、发出之前，做最后改写（算签名、填动态参数）；
3. **定时器第三**：等（思考时间/吞吐量控制）——注意它在取样器**之前**，所以它是在"发请求前先等一下"，而不是"发完后休息"；
4. **取样器第四**：真正发请求；
5. **后置处理器第五**：响应回来立刻取需要的值存成变量（供后续取样器用）；
6. **断言第六**：判断这次响应是否合格——**放在后置处理器之后是有意义的**：断言可以基于"已提取的变量"做判断；
7. **监听器最后**：等结果（含断言结论）都定稿了，才记录与展示，因此报告里的成功/失败已经是最终口径。

一句话记法：**"备好料 → 改请求 → 等一等 → 发出去 → 取回来 → 判对错 → 记下来"**。

【必须掌握】

| 顺序 | 组件 | 什么时候用到（本模块章节） |
|------|------|---------------------------|
| 1 | 配置元件 | 请求头/Cookie/CSV 参数（[[Ch22-JMeter常用配置元件剖析]]） |
| 2 | 前置处理器 | 签名、时间戳、超时兜底（[[Ch23-JMeter前置处理器]]） |
| 3 | 定时器 | 思考时间、吞吐量控制（L2 后续章节） |
| 4 | 取样器 | HTTP Request 等真正发请求的元件 |
| 5 | 后置处理器 | 提取 token/orderId 供后续请求引用（[[Ch24-JMeter后置处理器]]） |
| 6 | 断言 | 协议层 + 业务层判定，进入错误率统计（[[Ch21-JMeter断言元件的使用]]） |
| 7 | 监听器 | 结果树 / 聚合报告，形成最终报告口径（L2 后续章节） |

【企业场景】
你排查一个"变量偶尔取到旧值"的诡异问题：登录链路里 token 依赖上游请求，而报告里偶发 401。按这条顺序检查后发现，同事把"取 token 的提取器"挂成了**同级**元件（放在请求后面而不是里面），于是它的生效范围变成了同作用域的所有取样器——列表请求的响应回来后又用登录的正则跑了一遍，把 `token` 覆盖成了缺省值。**用执行顺序 + 作用域这两把尺子，5 分钟就能定位到"元件挂错层"。**

【面试考察】
面试官："JMeter 里元件的执行顺序是什么？为什么定时器在取样器前面？"

参考回答框架：
1. 背出七步链：配置元件 → 前置处理器 → 定时器 → 取样器 → 后置处理器 → 断言 → 监听器
2. 解释语义：定时器在取样器**之前**，代表"发请求前先等待"（思考时间/限速），不是"发完后休息"
3. 断言在后置处理器之后：可以先提取变量、再做基于变量的判定；监听器最后，保证记录的是最终结论
4. 落地价值：顺序决定"谁能引用谁"（配置元件和前置处理器不能引用本次响应，因为响应还没回来）

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 以为定时器在取样器"之后" | 定时器在取样器**之前**执行（发请求前先等待），这是"思考时间"能生效的前提 |
| 在前置处理器里引用本次响应 | 前置处理器运行时响应还没回来；要引用响应值必须用后置处理器（[[Ch24-JMeter后置处理器]]） |
| 以为断言先于后置处理器 | 断言在后置处理器之后，所以断言里可以引用提取出来的变量 |
| 把"顺序固定"理解成"元件必须按顺序摆放" | 顺序是**执行语义**，摆放位置决定的是作用域；两者是两把不同的尺子 |
| 依赖监听器"实时"看到断言结果 | 监听器最后记录，其数据是最终口径；实时观察要用其 UI 刷新（且大并发下不建议常开） |

【我的理解】引导题（用自己的话回答）：
1. 用"备好料 → 改请求 → 等一等 → 发出去 → 取回来 → 判对错 → 记下来"复述一遍，并说出每一步为什么必须是这个位置。
2. 为什么"在前置处理器里引用请求的响应值"是不可能的？请从时间顺序上解释。

### 知识点3：同一作用域内相同元件的执行顺序（课程原文核心结论二）

【课程原话/定义】
课程原文：在同一个作用域（目录/级别/缩进）的**相同元件**的执行顺序是：**从上到下的顺序依次执行。**

【为什么？】
因为 JMeter 的测试计划是**树**，同一层级的节点按**树中出现的先后顺序**被处理。这条规则的实际后果有三类，必须分清：
1. **顺序执行**：多个同类型元件按从上到下依次处理（如两个 BeanShell 前置处理器，上面的先跑）；
2. **覆盖关系**：如果两个元件写了**同一个变量名或同一个请求头**，后处理的那个会覆盖先处理的（"后面的赢"）；
3. **可预期性**：正因为顺序确定，脚本才可维护——把顺序搞乱（用拖拽改变了元件次序）可能悄悄改变压测行为。

【扩展知识】JMeter 官方文档对这一点的表述是：*"Other test elements are processed according to the scope in which they are found, and the type of test element. [Within a type, elements are processed in the order in which they appear in the tree]"*（在同一类型内，元件按它们在树中出现的顺序被处理），并同时说明 *"Logic Controllers and Samplers are processed in the order in which they appear in the tree"*（逻辑控制器与取样器也按树中顺序处理）。这与课程结论完全一致：**同级同类型，从上到下。**

【必须掌握】

| 场景 | 结果 | 建议 |
|------|------|------|
| 同级两个 HTTP Header Manager 定义不同头 | 都会生效（合并） | 可以接受，但不如集中到一个元件里更清晰 |
| 同级两个元件定义**同名**变量/头 | 后处理者覆盖先处理者 | 企业规范：同一作用域禁止重复定义同名配置 |
| 同级两个同名正则提取器写同一变量 | 后面的覆盖前面的值 | 一变量一处提取，避免"变量被神秘覆盖" |
| 拖拽改变了同级元件次序 | 执行顺序随之改变，行为可能变化 | 改动后重新用 1 线程小样本验证 |
| 逻辑控制器内的取样器 | 按树中顺序执行 | 业务流程顺序 = 树中摆放顺序，别依赖编号命名 |

【企业场景】
你所在团队的压测脚本规范里有一条：**"同一作用域内不得出现两个同名 Header Manager，也不得重复定义同名变量"**。这条规则就是为了消灭"覆盖类"故障——曾有一个线上事故：某同事在调试时复制了一个 Header Manager 改环境参数，忘记删掉旧的，结果两个元件定义同名 `X-Env`，谁生效取决于摆放顺序；脚本在 A 同事机器上是压测试环境，在 B 同事机器上（拖拽子节点后顺序变了）压到了预发环境，压测数据直接作废。**顺序确定 ≠ 你可以随意制造顺序，规则的价值是把"可预测的坑"变成"不允许出现"。**

【面试考察】
面试官："同一层级有多个同类元件，JMeter 怎么处理？"

参考回答框架：
1. 规则：同一类型内按树中出现的顺序（从上到下）依次处理（课程与官方文档一致）
2. 冲突语义：定义同名变量/请求头时，后处理的会覆盖先处理的（"后者生效"）
3. 工程规范：同一作用域避免重复定义同名配置，用集中管理 + 变量区分环境
4. 验证方式：变更元件顺序后，用 1 线程小样本 + Debug Sampler 复验行为，别靠"应该没问题"

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 用"复制粘贴再改"的方式做多环境配置 | 复制品与原件同层会形成覆盖冲突；用变量/属性做环境区分更安全 |
| 以为"顺序"只影响日志显示 | 同名配置的覆盖、变量赋值先后都受顺序影响，可能改变压测结果 |
| 把业务顺序交给"命名编号" | 取样器/控制器的执行顺序由**树中顺序**决定，不看你命名成 01、02 |
| 调整元件顺序后不复验 | 任何顺序调整都是一次"行为变更"，必须小样本复验 |
| 不理解"同级" | 同级 = 同一个父节点下的兄弟节点；跨层级的比较要用作用域规则（知识点4） |

【我的理解】引导题（用自己的话回答）：
1. 两个同级元件都定义变量 `token`，最终 `${token}` 会取到哪个值？为什么？
2. 既然"顺序确定"，为什么企业还要禁止"复制粘贴式"的多环境配置？

### 知识点4：作用域（目录 / 级别 / 缩进）到底指什么（【扩展知识】）

【课程原话/定义】
课程原文在两条结论里都写了限定语：**同一个作用域（目录/级别/缩进）**。也就是说，"执行顺序"的讨论前提是"它们在同一作用域里"。

【为什么？】
因为"执行顺序"这两条结论都带限定语——"同一个作用域"。不先把"作用域"定义清楚，顺序规则就无从谈起：**作用域决定"谁参与这次执行"，顺序决定"参与者按什么次序跑"**。混淆这两件事是最常见的排错误区：很多人把"元件放错层级"（作用域问题）误判为"顺序问题"，于是在树的上下位置上来回拖拽，问题依旧。机制上，JMeter 的测试计划是一棵树，元件的生效范围来自它在树中被**包含**的范围——这就是"目录/级别/缩进"这三个词的真实含义。

【扩展知识】理解"作用域"的三层模型（把前几章的实验结论抽象成规则）：
1. **作用域 = 元件在树中的位置所覆盖的范围**：元件对它**所在层级**及其**子树**内的取样器生效。
2. **三层心智模型**（复习 [[Ch22-JMeter常用配置元件剖析]] 的实验）：
   - 挂在 **Test Plan** 下 → 所有线程组的所有取样器都生效（公共配置）；
   - 挂在**线程组**下 → 该线程组内所有取样器生效（一条业务链路的公共配置）；
   - 挂在**某个取样器之下**（作为它的子节点）→ 只对该取样器生效（单个接口的特殊配置）。
3. **官方口径**（【扩展知识】）：配置元件在其所在作用域的**开始处**被处理（即同一作用域内任何取样器之前）；后置处理器等则**作用于同一作用域内的所有取样器**，要只对某个取样器生效就必须挂到它下面。
4. **元件类型也影响作用域行为**：定时器、断言、前后置处理器"只有在存在可适用的取样器时才被处理"（官方文档），也就是说孤立的元件（作用域内没有取样器）不会做任何事。

【必须掌握】

| 你要的效果 | 放置层级 | 说明 |
|------------|----------|------|
| 全计划生效 | Test Plan 下 | 全局公共头、全局变量 |
| 某线程组生效 | 该线程组下 | 一条链路的公共配置（最常见的正确位置） |
| 只对某请求生效 | 作为该请求的子节点 | 单独接口的特殊头、单独接口的提取器/断言 |
| 只对某段业务生效 | 逻辑控制器（如 Simple/Transaction Controller）下 | 用控制器划分业务片段（【扩展知识】） |
| 元件放错层 | —— | 症状："部分请求少带配置""变量偶发被覆盖""断言永远不触发或到处触发" |

【企业场景】
你同事的脚本里，登录提取器挂在线程组下（而不是登录请求下），现象是"偶尔 401，重跑几次又好了"。这就是典型的**作用域**问题：提取器对同作用域所有取样器生效，登录之后的每个响应都会重新执行一次提取，把 `token` 覆盖成缺省值或错误值；由于响应时序不同，覆盖发生的时机也不同，于是表现为"偶发"。整改动作只有一条：把它移到登录请求下。**"偶发问题查作用域"是性能压测排错的第 0 原则。**

【面试考察】
面试官："如何保证某个配置只对某一个请求生效？"

参考回答框架：
1. 原则：生效范围由元件在测试计划树中的**层级**决定
2. 三种摆法：Test Plan 级（全局）／线程组级（组内全部）／取样器子节点（仅该请求）
3. 官方补充：配置元件在其作用域开始处处理；后置处理器等作用于同作用域所有取样器，因此要"只对某一个生效"必须挂到该取样器下面
4. 排错经验：出现"偶发""部分请求"这类字眼时，第一反应就是查作用域与同名覆盖

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 把"同一个作用域"理解成"同一行/同一屏" | 作用域由**父子层级**决定，与屏幕上的视觉距离无关 |
| 认为元件放下面就不生效 | 生效与否由层级决定（配置元件在作用域开始处即生效，与同级上下位置无关，见 [[Ch22-JMeter常用配置元件剖析]]） |
| 断言/提取器挂在线程组下却希望"只针对一个请求" | 它们作用于同作用域**所有**取样器，必须挂到目标取样器下 |
| 认为孤立的元件也会执行 | 定时器/断言/前后置处理器只有在有可适用的取样器时才被处理（官方口径） |
| 全链路共用一个挂错层的提取器变量 | 同名变量被后处理的取样器响应覆盖，表现为偶发错误 |

【我的理解】引导题（用自己的话回答）：
1. 请分别说出"全局头""链路公共头""单接口特殊头"应该放在哪一层。
2. 为什么"偶发"类问题要优先查作用域，而不是先怀疑服务端？

### 知识点5：一次迭代里，JMeter 到底按什么机制走完这条链（【扩展知识】）

【课程原话/定义】
课程原文只给出两条顺序结论，没有展开机制。（本节为【扩展知识】，用于把结论"讲通"。）

【为什么？】
"背结论"只能应付面试，"懂机制"才能解释现场现象。三条现实问题只有机制能回答：① 为什么加了定时器 TPS 会降（等发生在取样之前）；② 为什么断言失败不会让压测停下（失败只是标记，流程继续）；③ 为什么 5000 个线程不是"同时发出 5000 个请求"（每线程受响应时间与定时器约束，符合利特尔法则：并发数 = QPS × 平均响应时间）。这些正是 [[../L1-性能测试体系/Ch01-性能测试介绍与压力曲线模型|L1 Ch01]] 的压力曲线在工具层面的落地解释。

【扩展知识】JMeter 引擎的执行模型可以概括为：
1. **线程组启动 N 个线程**（线程数 = 并发用户数），每个线程独立、按迭代次数循环；
2. 每一轮迭代，线程从树的根往下遍历：
   - 遇到**逻辑控制器/取样器**，按树中顺序处理（业务顺序 = 摆放顺序）；
   - 遇到**取样器**时，先把当前作用域内的**配置元件**处理好（这就是"配置元件在其作用域开始处被处理"），再执行**前置处理器**，再执行**定时器**（等待），然后真正发出请求；
   - 响应回来后，执行**后置处理器**（提取值）、**断言**（判定）、**监听器**（记录）；
3. **例外条件**（官方口径）：后置处理器、断言、监听器在 **SampleResult 为 null 时不会执行**——也就是说，如果某次取样根本没有产生结果（例如取样器未执行成功到产生结果这一步），后续的判定与记录环节会被跳过；
4. **并发模型提醒**：以上是**单线程内**的顺序；N 个线程之间是并行的，所以报告里的"TPS 随时间变化"是 N 条线程叠加的结果。理解这一点，才能解释"为什么并发数上去后 RT 变长、TPS 不再涨"（见 [[../L1-性能测试体系/Ch01-性能测试介绍与压力曲线模型|L1 Ch01 压力曲线模型]]）。

【必须掌握】

| 机制要点 | 结论 |
|----------|------|
| 单线程内串行 | 同一个线程里，元件严格按七步链顺序执行，没有并行 |
| 迭代循环 | 线程按迭代次数重复整个链路；变量在每个线程内独立维护 |
| 线程之间并行 | 并发来自多线程；压力 = 线程数 × 每线程请求节奏（由定时器控制） |
| 结果判定顺序 | 后置处理器 → 断言 → 监听器，所以报告中的成功/失败是断言后的最终口径 |
| 例外 | SampleResult 为 null 时，后置处理器/断言/监听器不执行（官方口径） |

【企业场景】
你被问到"为什么我加了定时器，TPS 反而上不去？"——因为定时器在取样器**之前**等待，它把每个线程的请求节奏拉慢了：TPS ≈ 线程数 ÷ (单次请求耗时 + 定时等待)。企业里定时器的常见用法有两种：加"思考时间"模拟真实用户（更真实但 TPS 变低），或用吞吐量定时器反向控制目标 TPS（做定量加压）。**搞不清"定时器在取样器之前"这件事，就会算错容量模型**——这是从"会用工具"走向"会设计场景"的分界线。

【面试考察】
面试官："JMeter 是怎么执行一个测试计划的？定时器对 TPS 有什么影响？"

参考回答框架：
1. 执行模型：线程组创建 N 个线程，每个线程按迭代次数循环遍历测试树
2. 单线程内顺序：配置元件 → 前置处理器 → 定时器 → 取样器 → 后置处理器 → 断言 → 监听器
3. 定时器影响：位于取样器之前，等待时间会降低每线程的请求频率，从而压低 TPS（也可用吞吐量定时器定量控制 TPS）
4. 例外与边界：后置处理器/断言/监听器在 SampleResult 为 null 时不执行；线程之间是并行关系

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 用"TPS 变低"直接判定系统变慢 | 先排除定时器与思考时间的影响：它们会拉低 TPS 但不代表系统变慢 |
| 认为断言失败会中断压测 | 断言失败只把该请求标记为失败并计入错误率，脚本继续跑 |
| 认为元件在所有线程间共享状态 | 变量是线程内独立的；跨线程共享需用属性等机制（【扩展知识】） |
| 忽略"SampleResult 为 null 就不执行断言" | 极少数情况下断言没触发，可能是取样未产生结果，而不是断言配错 |
| 把"并发数"理解成"同时发出请求数" | 并发来自多线程，但每线程的请求节奏由响应时间 + 定时器共同决定（利特尔法则） |

【我的理解】引导题（用自己的话回答）：
1. 请解释：为什么加了一个"等待 1 秒"的定时器后，TPS 会降到大约"线程数 ÷ 秒"的量级？
2. 断言失败后，压测会停下来吗？报告里的错误率会怎么变化？

### 知识点6：执行顺序 × 作用域 —— 排错清单（收口实战）

【课程原话/定义】
课程总结（原文）：JMeter 组件执行顺序。（本章两条结论 + 八大组件清单）

【为什么？】
把前面五个知识点合成一张"症状 → 病因"的对照表，就能把"执行顺序/作用域"从知识点变成工具——**因为压测脚本 90% 的诡异问题都落在这两个维度上**：

| 症状 | 常见病因 | 用哪把尺子查 |
|------|----------|--------------|
| 部分请求缺少请求头/鉴权 | 配置元件挂错层级（作用域过窄） | 作用域（知识点4） |
| 变量偶发变成缺省值/错误值 | 提取器挂成同级，对多个响应都执行并覆盖 | 作用域 + 同名覆盖（知识点3、4） |
| 断言"永远不失败" | 断言挂错层级（作用域内没有取样器）／断言配在无关请求下 | 作用域（知识点4） |
| 断言"到处失败" | 断言挂在线程组下，对所有请求都生效 | 作用域（知识点4） |
| 改了配置却不生效 | 同名配置被同级更靠后的元件覆盖 | 顺序（知识点3） |
| 脚本偶发 401/未登录 | token 提取失败或被覆盖；缺省值静默传播 | 顺序 + 后置处理器（[[Ch24-JMeter后置处理器]]） |
| 压测跑一会儿施压机内存暴涨 | 调试用监听器（View Results Tree / Debug Sampler）留在计划里 | 八大组件（知识点1） |
| TPS 比预期低很多 | 定时器在取样器之前等待（思考时间/限速） | 顺序（知识点2、5） |

【必须掌握】

| 检查项 | 通过标准 |
|--------|----------|
| 八大组件是否齐全 | 线程组、配置元件、取样器、断言、监听器（必要项）都在；调试元件已移除 |
| 每个配置元件的作用域 | 明确它"应该影响谁"，并能在树上指出它挂在哪一层 |
| 每个提取器/断言的位置 | 只影响目标请求时，必须是该请求的子节点 |
| 同名冲突 | 同一作用域内无同名变量/同名请求头定义 |
| 顺序敏感点 | 多个同类元件的处理顺序已确认，且小样本复验过 |
| 结果口径 | 监听器里看到的成功/失败已包含断言结论 |

【企业场景】
你以"性能测试脚本评审人"的身份接手一份交接脚本，按上面这张清单逐条走：① 用八大组件给树分类；② 逐个配置元件确认作用域；③ 逐个提取器/断言确认挂载层级；④ 搜索同名变量与同名头；⑤ 移除调试元件；⑥ 1 线程 1 迭代跑通并核对变量与报告口径。整份检查通常 20 分钟以内完成，却能挡掉后续数小时的"疑难排查"。**在企业里，能写出这份评审清单的人，通常已经在带压测项目了**——这也是从"能用 JMeter"走向"能交付可信压测结论"的关键能力。

【面试考察】
面试官："你怎么保证压测脚本是可信的？"

参考回答框架：
1. 结构层面：按八大组件体检脚本（线程组/配置/取样器/断言/监听器是否齐全、调试元件是否移除）
2. 作用域层面：每个配置元件、提取器、断言的作用范围可被准确指出（挂错层级是最常见缺陷）
3. 顺序层面：确认同级同类元件的处理顺序与覆盖关系，避免同名冲突
4. 数据层面：断言覆盖协议层 + 业务层，关键变量设显眼缺省值，先用小样本验证再放大并发

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 出问题先怀疑服务端 | 先按"作用域 → 顺序 → 元件齐全性"自查脚本，再怀疑被测系统 |
| 只删 View Results Tree，忘了 Debug Sampler | 两者都会累积结果数据占内存，正式压测前都要移除 |
| 认为脚本"跑起来没报错"就等于可信 | 无报错只说明没异常；可信需要断言 + 作用域 + 数据口径三重确认 |
| 拿脚本修改后的数据与之前对比 | 顺序/作用域变更属于行为变更，必须重跑基线再对比 |
| 把本清单当一次性检查 | 每次改脚本都要过一遍；脚本变更后先小样本复验再上并发 |

【我的理解】引导题（用自己的话回答）：
1. 从上面的"症状 → 病因"表里挑 3 条，用自己的话说明为什么这两把尺子（作用域、顺序）能定位它们。
2. 如果你要给别人一份"压测脚本评审清单"，你会把哪 5 条放进去？为什么？
