### 知识点1：什么是"使用代理服务器录制请求"

【课程原话/定义】
JMeter 使用代理服务器录制请求是指**通过配置 JMeter 的 HTTP(S) 代理服务器，将浏览器的 HTTP 请求通过代理服务器转发给目标服务器，并同时将这些请求记录下来**，以生成 JMeter 的请求脚本。

具体来说，当把浏览器的代理设置为 JMeter 中配置的代理服务器的主机名和端口时，浏览器发送的所有 HTTP 或 HTTPS 请求将会经由 JMeter 的代理服务器进行转发。在这个过程中，代理服务器会记录下所有的请求信息，包括**请求的 URL、请求方法、请求头、请求体**等。

【为什么？】
"录制"的本质是**把一次真实操作翻译成脚本**，它的原理可以拆成三个动作：

1. **拦截**：浏览器被配置成"所有流量走 JMeter 的代理端口"，于是 JMeter 站在了浏览器与服务器之间——这就是"代理"的全部含义（代理服务器在客户端和目标服务器之间转发请求）。
2. **转发**：JMeter 把请求原样转发给目标服务器，并把响应返回给浏览器。所以录制期间**页面能正常打开**，用户看到的体验与平时一样。
3. **记录**：JMeter 按 HTTP 协议解析流量，把 URL、方法、请求头、请求体逐条抓成 Sampler（取样器）挂在指定的录制控制器下。

这里有一个必须想清楚的推论：**JMeter 只能记录它能"看懂"的协议**。因为 JMeter 需要按 HTTP 语义解析并重建请求，所以浏览器发出的图片、JS、CSS 也会被记成请求（即使你并不需要它们）——**这正是后面"过滤器（Requests Filtering）"存在的根本原因**：录制的信噪比需要人工控制，而不是靠工具自动判断"哪些请求有用"。

【必须掌握】

| 环节 | 课程定义 | 关键技术点 |
|------|----------|-----------|
| 角色 | JMeter 充当浏览器与目标服务器之间的代理 | 浏览器代理指向 JMeter 的 IP + 端口 |
| 协议 | HTTP(S) | HTTPS 需要证书才能解密查看/录制 |
| 记录内容 | URL、请求方法、请求头、请求体 | 逐条生成 Sampler |
| 产物 | JMeter 请求脚本（`.jmx`） | 无需手写每个请求 |
| 前置条件 | 浏览器代理设置 + 证书安装 | 缺证书抓不到 HTTPS 请求 |

【企业场景】
你被安排给"下单主流程"写压测脚本。**最稳的第一步不是打开 JMeter 敲请求，而是先录一遍**：让脚本从"你在浏览器里真下单"这件事里长出来。为什么？因为下单链路里藏着大量你手写时容易漏掉的东西——登录后的 Cookie/Session、埋点接口、签名参数、前端带入的动态 Token。你先录，拿到的是**一份"真实会发生的请求清单"**；然后你再删掉埋点、图片这类噪声，补上参数化（下一章之后的内容），脚本的完整度和可信度远高于"凭文档手写"。这就是"**先录后改**"成为业界标准起手式的原因。

【面试考察】
面试官："JMeter 怎么录制脚本？原理是什么？"

参考回答框架：
1. 原理：JMeter 配置 HTTP(S) 代理服务器，浏览器流量经代理转发并被逐条记录成 Sampler
2. 记录内容：URL、请求方法、请求头、请求体（HTTPS 需安装 JMeter 证书解密）
3. 前提：浏览器代理指向 JMeter 主机 + 端口；被测侧需要能与压测机连通
4. 定位：录制是"快速拿到请求清单"的手段，录制后必须人工裁剪与参数化，不能直接拿录制脚本压测

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 把录制脚本直接当压测脚本用 | 录制出来的脚本包含噪声请求（图片/JS/CSS/埋点），且全部是固定值，必须裁剪＋参数化 |
| 认为录制能自动只记"有用的请求" | 工具只能忠实记录流量，裁剪靠 Requests Filtering 过滤器与人眼 |
| 认为 HTTP 和 HTTPS 录制流程完全一样 | HTTPS 必须安装 JMeter 证书（`ApacheJMeterTemporaryRootCA.crt`）到受信任证书，否则抓不到请求内容 |
| 以为录制期间页面打不开是正常的 | 代理转发必须让页面正常工作；页面打不开说明代理/证书配置有问题 |

【我的理解】
> 引导思考题1：请用"拦截 → 转发 → 记录"三步复述录制原理，并解释为什么"JMeter 只能记录它能看懂的协议"。
>
> 引导思考题2：为什么"先录后改"比"照着接口文档手写"更稳？请举一个录制才能发现、看文档容易漏的东西。

### 知识点2：使用代理服务器录制请求的优点

【课程原话/定义】
通过使用代理服务器录制请求，可以实现以下目的：
- **从真实的用户操作中捕获和记录 HTTP 请求**，以便后续进行性能测试
- **方便地生成 JMeter 的请求脚本，无需手动构建每个请求**
- **能够捕获和录制由浏览器生成的动态参数**，如会话 ID、验证码等，方便后续使用

总体而言，使用 JMeter 的代理服务器录制请求能够**快速、方便地将实际的用户操作转化为 JMeter 的请求脚本**，并为进行性能测试提供便利。

【为什么？】
三条优点恰好对应手写脚本的三个死穴：

| 优点 | 它治的是什么病 |
|------|----------------|
| 从真实操作中捕获请求 | **"漏接口"**：文档往往只写主干接口，前后依赖的接口（登录校验、埋点、验证码）手写时极易漏 |
| 无需手动构建每个请求 | **"慢"**：一条完整业务链可能有几十个请求，手写成本高且易错（头部、编码、格式） |
| 捕获动态参数（会话 ID、验证码） | **"跑不通"**：服务端下发的动态值手写无法预知，录下来才能顺着链路往下走 |

要特别注意第三条的真正含义：录制**不只是拿到请求地址**，它还帮你**看清接口之间的数据依赖**（哪个响应里返回的字段被下一个请求引用）。这些依赖关系正是后续做"参数化 / 关联提取（后置处理器）"时的依据——**录制→关联** 是一条完整的技术链，本节只是第一环。

【必须掌握】

| 优点 | 企业价值 | 后续要补的动作 |
|------|----------|----------------|
| 捕获真实请求 | 脚本完整、贴合真实用户行为 | 裁剪噪声请求 |
| 免手写构建 | 节省脚本编写时间 | 核对请求头/编码/参数是否与文档一致 |
| 捕获动态参数 | 链路能连贯跑通 | 用关联/参数化替换固定值（否则并发时全用同一个 Session） |

【企业场景】
团队要压一条"领券 → 下单 → 支付"的完整链路。你做录制的收获不只是几个请求：你会在录制结果里清楚看到**"领券接口返回的券 ID 被下单接口引用"**这类依赖关系。然后你的动作是：把券 ID 用后置处理器提取成变量、下单接口引用该变量，**这样 500 个虚拟用户才会各自用各自的券**。如果你跳过录制直接手写，最典型的翻车是：所有用户共用一个券 ID/一段 Cookie，结果服务端返回"券已使用"或直接 401，压测数据完全不可用。

【面试考察】
面试官："为什么要用录制而不是直接手写脚本？录完还要做什么？"

参考回答框架：
1. 优点三条：捕获真实请求、免手工构建、捕获浏览器生成的动态参数
2. 价值：保证请求完整性与链路依赖不遗漏，快速得到脚本骨架
3. 局限：会产生噪声请求，且所有参数都是固定值
4. 必做后续：裁剪（过滤器/删除无用元件）→ 参数化（CSV/变量）→ 关联提取（后置处理器）→ 断言与监控

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 认为"录下来就等于脚本写完了" | 录制只给你骨架；参数化、关联、断言、事务才是可压测脚本的必要工序 |
| 忽略录制能暴露接口依赖关系 | 响应中被后续请求引用的字段正是"关联"的依据，录制时要专门看 |
| 共用一套会话数据做并发 | 并发用户必须各自持有独立会话/账号，否则结果会被风控或数据冲突污染 |
| 只把录制当"抄接口地址"的工具 | 它同时也是"梳理业务链路"的工具，价值不止 URL |

【我的理解】

### 知识点3：录制前先定场景（压测对象与用户路径）

【课程原话/定义】
**录制压测脚本的场景**（课程原文）：
- 压测对象：`http://news.baidu.com`
- 压测页面：百度首页，百度新闻
- 步骤：
  1. 访问百度首页
  2. 单击进入"百度新闻"

【为什么？】
为什么课程要在"录制"这一节先写"场景"？因为**录制必须"照着剧本演"**——代理只会忠实记录你做过什么。

- 你在录制期间点了什么、点了多久，决定了脚本里出现哪些请求。**如果你边录边乱点**（刷新、搜索、误点广告），噪声请求就会进脚本，事后还得一条条删。
- 录制的操作顺序，会变成脚本里 Sampler 的**默认执行顺序**，也就是未来业务的执行顺序。顺序错了，压测跑的就不是那条业务链。
- 课程把"压测页面"和"操作步骤"分开写，是提醒你：**一个压测场景 = 明确的入口页面 + 明确的用户动作路径**，这和 L1 里学过的"场景设计"完全一致——只不过 L1 用文字/流程图描述场景，这里用录制把它落成脚本。

换句话说：**录制 = 场景设计的可执行化**。设计阶段想清楚"用户怎么走"，录制阶段才能干净利落，不返工。

【必须掌握】

| 场景要素 | 课程示例 | 你要在生产里补充的 |
|----------|----------|--------------------|
| 压测对象 | `http://news.baidu.com` | 明确环境（测试/预发/生产）与域名/IP |
| 压测页面 | 百度首页、百度新闻 | 明确页面/业务入口（首页、商详、下单页…） |
| 操作路径 | 访问首页 → 单击进入"百度新闻" | 写清每一步动作与等待点，录制时按剧本执行 |
| 录制时长 | 覆盖完整业务链即可 | 控制时长，减少噪声请求 |

【企业场景】
你录"用户注册"这条链路时，会先写下剧本：打开注册页 → 输入手机号 → 点击获取验证码 → 填验证码 → 勾选协议 → 提交注册。然后**你就严格按这六步操作一遍，不多点一个按钮**。这样录出来的脚本天然对应业务步骤，你只需要处理"手机号/验证码"这类动态参数。相反，很多人的习惯是"打开浏览器随手点"，结果录出一堆埋点、轮询、推荐位请求，还分不清哪条是关键链路——**清理的时间比重新录一遍还长**。

【面试考察】
面试官："录制脚本前你会做什么准备？"

参考回答框架：
1. 明确被测环境与入口（域名/IP、环境标识）
2. 写出用户操作剧本（每一步动作与等待点），并覆盖完整业务链
3. 录制中严格按剧本执行、不做无关操作，控制录制时长
4. 录完先做"链路核对"（业务步骤是否都有对应请求），再做裁剪与参数化

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 打开浏览器随意点击，边录边探索 | 噪声请求会大量进入脚本，清理成本远高于重录 |
| 没写剧本就开始录 | 容易漏掉业务关键步骤，脚本不完整 |
| 录制时切换环境/账号 | 录出的请求混了多个环境或身份，链路跑不通 |
| 以为录制时长越长越好 | 录得越久噪声越多，覆盖完整链路即可 |

【我的理解】
> 引导思考题1：为什么说"录制是场景设计的可执行化"？如果把 L1 学的场景设计搬到本节，你会先产出什么文档？
>
> 引导思考题2：课程示例里"访问首页 → 单击进入百度新闻"只有两步，你觉得这个脚本能不能直接用来压测？还缺什么？

### 知识点4：搭建录制元件（代理服务器 + 线程组 + 录制控制器）

【课程原话/定义】
**录制压测脚本的步骤**：
1. **打开 JMeter 的 GUI 界面，新建压测脚本，添加 HTTP 代理服务器组件**：
   步骤：`测试计划(Test Plan)` → `添加(Add)` → `非测试元件(Non-Test Elements)` → `HTTP 代理服务器(HTTP(S) Test Script Recorder)`
2. **添加线程组组件**：
   步骤：`测试计划(Test Plan)` → `添加(Add)` → `线程(Threads)` → `线程组(Thread Group)`
3. **添加录制控制器组件**：
   步骤：`线程组(Thread Group)` → `添加(Add)` → `逻辑控制器(Logic Controller)` → `录制控制器(Recording Controller)`
   **注意：使用录制脚本控制器，可以方便的对录制脚本进行统一清理操作。**

【为什么？】
这三个元件不是"随便凑的"，它们各自解决一个角色问题，缺一不可：

| 元件 | 角色 | 为什么必须要它 |
|------|------|----------------|
| HTTP(S) Test Script Recorder | **代理服务器**（录制引擎） | 它才是真正"监听端口、接收浏览器流量"的元件 |
| 线程组 | **容器**（执行单元） | 录下来的 Sampler 未来必须在某个线程组下运行；JMeter 里"所有元件都必须在某个线程组下"（见 [[Ch15-线程组]]） |
| Recording Controller | **收纳层**（录制的落点） | 让所有新录的请求集中挂在一个控制器下，**便于统一清理**——这正是课程注释的含义 |

课程特别点出 Recording Controller 的"便于统一清理"：因为录制产物是**一批**请求（几十条），如果直接散落在线程组下，将来要删无用请求就得一个个找；把它们集中在一个控制器里，**清理时只操作这一个节点**，删完剩下的就是有效链路。这是一个典型的"用结构换维护成本"的工程技巧。

另外注意路径细节：**代理服务器（HTTP(S) Test Script Recorder）挂在"非测试元件（Non-Test Elements）"下，而不是线程组下**——因为它本身不参与压测执行，它只是"录制工具"，录完就该禁用/删除。这个分类本身就是 JMeter 在告诉你："它不是业务脚本的一部分"。

【必须掌握】

| 元件 | 添加路径 | 归属分类 | 作用 |
|------|----------|----------|------|
| HTTP(S) Test Script Recorder | 测试计划 → 添加 → 非测试元件 → HTTP 代理服务器 | 非测试元件 | 开代理端口、接收并记录浏览器流量 |
| 线程组 Thread Group | 测试计划 → 添加 → 线程 → 线程组 | 测试元件 | 未来执行 Sampler 的容器 |
| 录制控制器 Recording Controller | 线程组 → 添加 → 逻辑控制器 → 录制控制器 | 逻辑控制器 | 集中收纳录制的请求，便于统一清理 |

【企业场景】
你录一条较长的业务链（比如"登录 → 搜索 → 加购 → 下单"），一定会用 Recording Controller 作为落点。原因非常实际：录完之后你要**批量审阅**——把埋点、图片、广告位、重复轮询挑出来删掉，只留业务主干。集中在一个控制器里，你的操作是"展开一个节点 → 从上到下过一遍 → 删掉不需要的"；如果请求散落在树里各处，你就得边找边删，还容易误删已调好的元件。**脚本的可维护性，从录制的第一天就被结构决定了。**

【面试考察】
面试官："JMeter 录制要用到哪些元件？为什么要加 Recording Controller？"

参考回答框架：
1. 三个元件：HTTP(S) Test Script Recorder（代理）、Thread Group（容器）、Recording Controller（落点）
2. 分类：代理服务器属于"非测试元件"，不参与压测执行，用完禁用/删除
3. Recording Controller 的价值：录制结果集中存放，方便统一清理与后续调整结构
4. 结构意识：元件挂载位置决定作用域与可维护性，这是 JMeter 的核心思维方式

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 找不到"HTTP 代理服务器" | 它在 `非测试元件(Non-Test Elements)` 下，不在取样器/线程组里 |
| 忘了先建线程组就录制 | Target Controller 必须指向一个已存在的控制器（通常在线程组内） |
| 把录制结果直接挂在测试计划根下 | 建议挂在 Recording Controller 下，便于统一清理，也让脚本结构清晰 |
| 把代理服务器元件当成"压测的一部分"保留在正式脚本里 | 它是非测试元件；录完应禁用或删除，避免正式压测时又开代理端口 |

【我的理解】
> 引导思考题1：为什么 Recording Controller 能"方便统一清理"？请用"结构 vs 维护成本"的关系解释。
>

### 知识点5：配置 HTTP(S) Test Script Recorder（端口与 Target Controller）

【课程原话/定义】
**配置 HTTP(S) 测试脚本记录器**：
- 打开 `HTTP(S) Test Script Recorder`
- 设定 `Port` 为 **8888**
- 设定 `Target Controller` 为 `Test Plan > Tread Group > Recording Controller`（**指定录制脚本的位置**）

【为什么？】
两个配置项各自解决一个"接线"问题：

1. **Port（8888）= 代理监听的"门牌号"**。JMeter 在这台机器的 8888 端口上"守着"，浏览器被配置成"走这台机器的 8888"，两者才能对接。**端口必须与浏览器代理设置里的端口完全一致**——这是录制失败最高频的原因（一个填 8888、另一个填 8080，谁也找不到谁）。
2. **Target Controller = 录制产物的"落点"**。它指定新记录的 Sampler 挂在树的哪个位置。课程特意标注"（指定录制脚本的位置）"，因为 JMeter 不会替你猜：你录的请求到底属于哪个线程组？属于哪个控制器？——**由这个参数决定**。若没有选中一个具体的控制器，录出来的请求会挂到默认位置，后续清理与结构调整会麻烦。

还有一个隐含前提：Target Controller 的候选对象来自**当前测试计划里已存在的控制器**。这解释了为什么步骤顺序必须是"先加线程组＋Recording Controller，再配置记录器"——**落点不存在，就无法指定落点**。

【必须掌握】

| 配置项 | 课程取值 | 作用 | 排错要点 |
|--------|----------|------|----------|
| Port | 8888 | 代理监听端口 | 必须与浏览器代理端口一致；被占用则换端口 |
| Target Controller | Test Plan > Thread Group > Recording Controller | 指定录制脚本在元件树中的落点 | 必须先建好 Recording Controller |
| 元件归属 | 非测试元件 → HTTP 代理服务器 | 录制工具，不属于业务脚本 | 录完禁用/删除 |
| 配套动作 | 点击 `Start` 开始录制 | 开启代理接收 | 未 Start 则录不到任何东西 |

【企业场景】
在公司环境里录脚本，"端口"常常是你要主动决策的地方：默认 8888 可能已被占用（或公司代理软件占用），此时你会**改成其他空闲端口，并同步改浏览器代理设置**，同时在笔记里记下"本机录制端口 = xxxx"。你还可能遇到"录到一半请求挂不上树"的情况——排错顺序就是回看 Target Controller 是否仍指向你期望的那个控制器（有时你录前不小心点到了别的节点，落点就变了）。**这两个参数的核对，是录制环节 90% 问题的答案。**

【面试考察】
面试官："JMeter 录制为什么抓不到请求？你会怎么排查？"

参考回答框架：
1. 端口链路：JMeter 记录器的 Port 与浏览器代理端口是否一致；端口是否被占用
2. 落点：Target Controller 是否指向已存在的控制器（否则无法指定位置）
3. 证书：HTTPS 抓不到 → 检查 `ApacheJMeterTemporaryRootCA.crt` 是否安装为受信任证书
4. 开关：记录器是否已点击 `Start`；浏览器的代理是否真的生效（可先访问一个 HTTP 站点验证）

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| JMeter 填 8888、浏览器填别的端口 | 两端端口必须完全一致，否则流量根本不进 JMeter |
| 端口被占用仍坚持用默认值 | 换个空闲端口并同步改浏览器代理设置 |
| 没先建 Recording Controller 就去配 Target Controller | 落点必须是已存在的控制器，顺序不能反 |
| 配置完忘了点 `Start` | 记录器未启动时，代理端口不接收流量，自然一条也录不到 |

【我的理解】
> 引导思考题1：把"端口"和"Target Controller"分别对应到"能不能录到"和"录到哪里"，请你说出录制失败的排查顺序（至少 4 步）。
>
> 引导思考题2：如果公司规定 8888 端口被安全软件占用，你会怎么改配置？需要同步改哪些地方？

### 知识点6：Requests Filtering（Include / Exclude 正则过滤器）

【课程原话/定义】
在 `Requests Filtering` 添加 "Include" 与 "Exclude" URL 正则匹配表达式：
- **Include（包含模式）**：`.*\\.(baidu\\.com).*`
- **Exclude（排除模式）**：`.*\\.(js|css|PNG|jpg|ico|png|gif).*`
- **目的：避免录制过多没必要的请求**。

【为什么？】
过滤器解决的是"**信噪比**"问题，而它的机制是**白名单 + 黑名单**：

- **Include（白名单）**：只录**匹配**这个正则的 URL。课程用 `baidu.com` 限定"我只关心百度的请求"，其它第三方域名（统计、广告、CDN）直接不录。
- **Exclude（黑名单）**：**匹配就不录**。课程把 `js、css、PNG、jpg、ico、png、gif` 排除掉——因为这些是**静态资源**，不是业务接口。压测一条业务链时，静态资源通常由 CDN/静态服务器承载，把它们录进脚本只会污染 TPS/RT 统计：你会看到"吞吐量很高"，但其中一大半是图片。

这个组合的工程意义在于：**并发用户数是要用来换业务请求量的**。如果你的脚本里有一半请求是图片，那么"500 并发"实际只产生了 250 个业务请求的并发——**压测目标与实际负载不匹配，结论必然失真**。过滤器就是保证"每一份并发都花在业务接口上"的第一道闸门。

【必须掌握】

| 配置 | 课程正则 | 语义 | 影响 |
|------|----------|------|------|
| Include | `.*\.(baidu\.com).*` | 只录匹配该正则的 URL（白名单） | 过滤掉第三方域名的干扰请求 |
| Exclude | `.*\.(js\|css\|PNG\|jpg\|ico\|png\|gif).*` | 匹配即不录（黑名单） | 过滤静态资源，避免污染吞吐量统计 |
| 配置位置 | `Requests Filtering` 面板 | 记录器内部 | 录制前配置，避免事后清理 |
| 判据 | "是否是业务接口" | 业务接口留、静态资源与埋点删 | 决定并发是否花在刀刃上 |

【企业场景】
你压"商品详情页"场景时会这样配过滤：Include 限定为自己的业务域名（例如 `.*\.(yourdomain\.com).*`），Exclude 排除 `js|css|png|jpg|ico|gif|woff|map` 等静态资源，再加一条排除埋点/监控上报的路径。为什么一定要这么做？因为"商品详情页"的静态资源可能由 CDN 承载、且有缓存，**把它们算进压测会把服务端压力算小、把 TPS 算大**，你给出的"服务端能扛 3000 TPS"就站不住了。**过滤器的本质不是省事，而是保证指标口径正确。**

【面试考察】
面试官："录制时为什么要加 Include/Exclude？不加会怎样？"

参考回答框架：
1. 目的：控制录制信噪比，避免把与业务无关的请求录进脚本
2. 机制：Include 是白名单（只录匹配的），Exclude 是黑名单（匹配的不录）
3. 后果：不加过滤器会录进大量图片/JS/CSS/埋点，导致吞吐量虚高、并发浪费、指标口径失真
4. 实践：按被测域名 + 业务接口路径写正则，静态资源后缀统一排除；必要时用后置手段二次清理

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 只配 Exclude，不限域名 | 第三方统计/广告请求仍会被录进来，脚本依然脏 |
| 把静态资源录进脚本 | 静态资源会放大吞吐量、稀释业务并发，指标口径失真 |
| 正则写成 `.*\\.(baidu\\.com).*`（照抄原文的双反斜杠） | 按正则语义，单个反斜杠 `\.` 才表示"转义的点"；双反斜杠匹配的是"反斜杠＋点"，见下方勘误 |
| 认为过滤器可以代替人工审核 | 过滤器只按 URL 匹配；语义层面的噪声（如埋点接口）仍要人工剔除 |
| 忽略正则大小写敏感 | 原文同时写了 `PNG` 与 `png`，说明存在大小写问题；实际可用忽略大小写写法统一处理 |

【我的理解】
> 引导思考题1：为什么把静态资源录进脚本会让"结论失真"？请分别说明它会怎样影响 TPS 与业务并发。
>
> 引导思考题2：如果被测站点的业务接口和埋点接口在**同一个域名**下，Include 过滤域名就不管用了，你会怎么办？

### 知识点7：浏览器代理配置与执行录制

【课程原话/定义】
**浏览器代理配置**：
打开浏览器，手动修改浏览器的代理服务器，**地址设置为本机的 IP 地址，端口号设置为和 JMeter 设置的端口号一致**，根据上一步骤，浏览器的代理服务器端口号设为 **8888**。

**执行录制**：
点击 `start` 按钮进行录制，即可获得百度新闻界面的请求。

【为什么？】
为什么必须用"本机 IP"而不是 `localhost`？这里有两个实际原因：

1. **JMeter 的 8888 端口监听在本机**，所以浏览器代理要指向"这台跑 JMeter 的机器"。
2. **本机 IP 是更稳妥的写法**：当浏览器、JMeter 可能在不同网络命名空间/虚拟网卡环境（例如 Docker、虚拟机、WSL）时，`localhost` 会各自解析到自己，而本机真实 IP 才指向 JMeter 所在主机。企业里压测机与浏览器通常不在同一台机器上（浏览器在个人电脑、JMeter 在压测机），这时就必须是**压测机的 IP**，并确认防火墙放行该端口。

另外要建立"录制的闭环"意识：录制是**你操作 → 浏览器 → 代理 → JMeter** 的链条。链条上任何一环断了都录不到东西，所以录制前后各做一次验证最省时间——**录制前**先随便访问一个页面，确认代理生效；**录制后**打开 View Results Tree（或录制控制器下的请求）确认请求确实进来了。

【必须掌握】

| 步骤 | 课程做法 | 关键点 |
|------|----------|--------|
| 1 | 打开浏览器，手动修改代理服务器 | 不用插件、不用系统全局代理，直接改浏览器代理 |
| 2 | 地址设为本机 IP | 跨机器时要写压测机 IP，并放行端口 |
| 3 | 端口设为与 JMeter 一致（8888） | 两端端口必须严格一致 |
| 4 | 回到 JMeter 点击 `Start` | 先 Start 再操作浏览器，顺序不能反 |
| 5 | 按剧本操作页面 | 只做剧本内的动作，减少噪声 |

【企业场景】
你在自己电脑上录脚本、JMeter 跑在公司压测机上，这是最常见的组合。此时你的动作顺序是：确认压测机 IP → 在压测机启动记录器（Port 8888）→ 在自己浏览器里把代理设成 `压测机IP:8888` → 确认能访问业务站点（说明代理通了）→ 按剧本操作 → 停止录制。录完后**必须把浏览器代理改回"不使用代理"**——否则你之后所有上网流量都会走公司压测机，既影响你自己，也可能干扰别的同学压测。**这个"收尾"动作是新人最常忘的一步。**

【面试考察】
面试官："录制时浏览器代理怎么设？为什么用 IP 不用 localhost？"

参考回答框架：
1. 设置内容：浏览器代理地址 = 运行 JMeter 的机器 IP，端口 = 记录器 Port（必须一致）
2. 用 IP 的原因：JMeter 与浏览器常不在同一台机器（或不同网络环境），`localhost` 会各自解析
3. 顺序：先 Start 记录器，再操作浏览器；录制期间页面应能正常访问
4. 收尾：录完立刻取消浏览器代理，并禁用/删除代理服务器元件，避免污染环境

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 在浏览器写 `localhost:8888`，但 JMeter 在另一台机器 | 应写运行 JMeter 的机器 IP；`localhost` 会指向浏览器自己 |
| 先操作浏览器再点 `Start` | 顺序反了会漏掉第一批请求；必须先 Start |
| 录完忘记取消浏览器代理 | 之后所有流量都会绕道 JMeter，影响自身与他人压测 |
| 录制期间页面打不开仍继续操作 | 页面打不开说明代理链路已断，先排错再录，否则录出来的链路不完整 |

【我的理解】
> 引导思考题1：请把"浏览器 → 代理 → JMeter → 目标服务器"这条链路画出来，并指出 3 个最可能断掉的位置。
>
> 引导思考题2：为什么录制结束后要立刻取消浏览器代理并处理代理服务器元件？不处理会带来哪些连带问题？

### 知识点8：证书安装（HTTPS 录制的前提）

【课程原话/定义】
**注意**：录制抓取请求之前，**需要安装 JMeter 的证书，否则无法抓取请求**。JMeter 证书位于 `bin` 目录中，证书名为 `ApacheJMeterTemporaryRootCA.crt`，需要将其**安装在受信任的证书中**，才能抓取请求。**证书配置步骤与 Charles 一致。**

【为什么？】
HTTPS 的整个设计目的就是"**中间人不能看懂内容**"。JMeter 要录制 HTTPS 请求，就必须主动当一次"受信任的中间人"，流程是：

1. JMeter 首次启动记录器时，会在 `bin` 目录生成自签名的根证书 `ApacheJMeterTemporaryRootCA.crt`。
2. 你把这个根证书装进浏览器/操作系统的**受信任根证书区**。
3. 之后浏览器访问 HTTPS 站点时，JMeter 用这份证书为每个站点**动态签发一张临时证书**给浏览器。因为根证书已受信任，浏览器不报警，于是"浏览器 ↔ JMeter"这一段的加密由 JMeter 掌握，它就能解析并记录请求内容。
4. 而"JMeter ↔ 真实服务器"这一段仍是正常 TLS——服务器看到的仍然是正常的 HTTPS 客户端。

**这就是"必须装在受信任证书中"的原因**：不装，浏览器会认为是中间人攻击而拒绝（或告警），HTTPS 流量根本解不开，自然录不到。课程说"证书配置步骤与 Charles 一致"，也正因为 Charles/Fiddler 用的是同一套中间人解密原理。

【必须掌握】

| 项目 | 课程原文 | 要点 |
|------|----------|------|
| 证书文件 | `ApacheJMeterTemporaryRootCA.crt` | 位于 JMeter 的 `bin` 目录 |
| 安装位置 | **受信任的证书** | 装成受信任根证书才有效 |
| 生成时机 | 启动 HTTP(S) Test Script Recorder 时生成 | 首次启动记录器后才会出现该文件 |
| 不做会怎样 | "否则无法抓取请求" | HTTPS 请求录不到/内容无法解析 |
| 参考做法 | 证书配置步骤与 Charles 一致 | 同为中间人解密机制 |

【企业场景】
你要录一个全站 HTTPS 的业务系统（现在几乎所有企业站点都是 HTTPS）。你的标准动作是：启动记录器 → 拿到 `bin/ApacheJMeterTemporaryRootCA.crt` → 安装为受信任根证书 → 然后才开始录制。特别注意：**如果录制中发现"HTTP 请求能录到、HTTPS 请求一条都没有"，就是证书没装或没被信任**，这时不要怀疑 JMeter，直接回到证书这一步。另外企业里用完要及时处理这张临时根证书（尤其是共用机器），否则存在被他人利用做中间人攻击的安全隐患——**能解密你 HTTPS 的证书，别人也能用**。

【面试考察】
面试官："JMeter 录制 HTTPS 请求要注意什么？"

参考回答框架：
1. 前提：需要安装 JMeter 生成的 `bin/ApacheJMeterTemporaryRootCA.crt` 到系统/浏览器的受信任根证书区
2. 原理：JMeter 作为中间人代理，用自己的根证书为各站点动态签发证书，浏览器信任根证书后才不拦截
3. 现象判断：HTTP 能录、HTTPS 录不到 → 优先查证书
4. 安全与清理：临时根证书用完应清理，避免他人复用造成中间人风险

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 证书只导入"个人"而不是"受信任的根证书" | 必须装到受信任根证书区，否则浏览器仍会拦截 |
| 还没启动记录器就去找证书文件 | 该证书通常在首次启动 HTTP(S) Test Script Recorder 时生成于 `bin` 目录 |
| HTTPS 录不到就怀疑 JMeter 版本/脚本问题 | 先排查证书（HTTP 能录、HTTPS 不能录＝典型证书问题） |
| 录完不清理临时根证书 | 临时根证书等价于长期中间人能力，共用机器上应清理 |

【我的理解】
> 引导思考题1：请用"中间人"解释为什么 JMeter 必须有自己的根证书才能录制 HTTPS，并说明"受信任"这三个字的作用。
>
> 引导思考题2：为什么课程说"证书配置步骤与 Charles 一致"？它们在原理上共同点是什么？

| 原文写法 | 问题 | 正确理解 |
|----------|------|----------|
| Include 正则写作 `.*\\.(baidu\\.com).*`（双反斜杠） | 双反斜杠在正则里表示"反斜杠字符"，会匹配不到普通 URL | 按需求应为单反斜杠转义：`.*\.(baidu\.com).*`（`\.` 表示字面点号） |
| Exclude 正则里同时出现 `PNG` 与 `png`、`jpg` 与 `gif` 混排 | 说明原文在手工补大小写，正则默认大小写敏感，容易漏 | 建议统一用忽略大小写写法（如 `(?i).*\.(js\|css\|png\|jpg\|jpeg\|ico\|gif).*`） |
| 录制控制器说明写作"使用录制脚本控制器，可以方便的…" | 元件名称前后不一致（前文叫"录制控制器 Records Controller"） | 统一按界面英文名 `Recording Controller`（中文：录制控制器）理解 |
| `Target Controller` 示例写作 `Test Plan > Tread Group > Recording Controller` | `Tread Group` 拼写错误 | 应为 `Thread Group`（线程组） |
