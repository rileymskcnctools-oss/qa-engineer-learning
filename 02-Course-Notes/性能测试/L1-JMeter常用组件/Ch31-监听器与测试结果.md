### 知识点1：View Results Tree（查看结果树）—— 明细调试的第一入口

> 监听器的分类、选型与使用规范见 [[Ch19-JMeter监听器]]；本知识点只展开查看结果树的界面字段与排查用法。

【课程原话/定义】
> 用于详细查看每个请求的响应数据、响应码、响应时间等信息，可查看每个请求的执行细节。
>
> 这一组件类似于抓包工具，可以看到 HTTP 请求的请求与响应数据，便于调试，包括请求头，请求体，响应头，响应体等。

课程给出的 **相关参数说明**：
> 当前默认是 Text 查看模式，可以点倒三角，出现下拉菜单，选择不同查看模式。

| 查看项 | 课程原文说明 |
|---|---|
| Sampler result | 主要是一个 Sampler 测试的总体测试结果，里面的每个返回的参数和参数的值和 View Result in Table 一样，多了响应状态码和响应消息这些字段 |
| Request | 点击切换到 Request，主要实现显示这个 HTTP 请求的一些信息 |
| Response data | HTTP 请求返回的 Response 的消息字段，一般是 json 格式或者 xml，也有 Html 格式，这里默认是 text 格式 |

【为什么？】
查看结果树是「**从并发视角切回单请求视角**」的工具。压测报告告诉你「哪里不对」，查看结果树告诉你「为什么不对」。它保存了每个 SampleResult 的完整快照——请求头、请求体、响应头、响应体、断言结果、耗时分解——所以它能替代抓包工具完成大部分调试工作，而且不需要额外配代理、不会漏掉 HTTPS。课程把它类比成抓包工具是准确的，但要点出关键差异：抓包看到的是**网络层的包**（含 TCP/TLS 细节、重传），查看结果树看到的是**JMeter 视角的请求与响应**（含变量替换后的实际值和断言判定）。做压测调脚本时，后者往往更直接。

【必须掌握】

| 面板 | 看什么 | 排查什么 |
|---|---|---|
| Sampler result | 样本序号、启动时间、耗时、状态、响应码、响应消息、响应大小 | 请求是否成功、耗时花在哪一段 |
| Request | 请求方法、URL（含实际拼接后的参数）、请求头、请求体 | 参数是否拼接正确、变量是否替换成功、Content-Type 是否正确 |
| Response data | 服务端返回的响应体（Text/HTML/JSON/XML 等查看模式） | 业务是否报错、返回结构与预期是否一致 |
| 查看模式下拉 | Text / HTML / JSON / XML / RegExp Tester 等 | 换用合适模式可读性更好；RegExp Tester 可直接验证正则表达式 |

【企业场景】
你压测下单接口，聚合报告显示 30% 的样本失败。你打开查看结果树，按「失败」过滤，逐条看 Sampler result 发现响应码是 200 但业务码是 1001「库存不足」。切到 Request 面板，看到实际的请求体里 `skuId` 是空的——进一步追到上游的提取器写错了 JSON 路径。整个过程你不需要抓包工具，也不需要服务端日志，5 分钟内定位到脚本缺陷。这就是查看结果树在压测调试期的核心价值：把「统计异常」翻译成「具体缺陷」。

【面试考察】
1. **面试官怎么问**：「压测里请求失败了，你怎么定位？」
   **回答框架**：查看结果树按失败筛选 → 看 Sampler result 的响应码/响应消息 → 看 Request 面板确认发出的参数 → 看 Response data 确认业务错误码 → 交叉验证断言配置。
2. **面试官怎么问**：「查看结果树和抓包工具有什么区别？」
   **回答框架**：都能看请求响应，但查看结果树看的是 JMeter 替换变量后的实际请求和断言结果，抓包看的是网络层实况；排查脚本问题优先用查看结果树。
3. **面试官怎么问**：「查看结果树的明文模式有什么用？」
   **回答框架**：Text 模式看报文原文最准，HTTP/JSON 模式便于阅读；调试正则或 JSON 提取时直接在结果树里验证规则命中。

【易错点】

| 常见错误 | 正确理解 |
|---|---|
| 只看 Response data，不看 Request | 高达一半的问题是「发出去的参数就不对」，必须看 Request 面板确认实际请求 |
| 认为查看结果树能看到重定向中间过程（未勾 Follow Redirects 时） | 只有勾选了 Follow Redirects，重定向的每个请求才会被记录 |
| 用查看结果树做正式压测的「实时监控」 | 高并发下它会缓存海量响应体，加压机内存和 GC 先崩，结果也不可信 |
| 看到响应码 200 就判定请求成功 | 业务口径的失败常常是「HTTP 200 + 业务错误码」，必须加响应断言才能识别 |

【我的理解】
1. 课程说 Request 面板「显示这个 HTTP 请求的一些信息」。请你结合实际经验想：为什么压测调试时必须看 Request 面板，而不是只看服务端返回？它到底能帮你排除掉哪一类最容易犯的错误？
2. 如果响应码是 200 但业务失败，查看结果树能帮你发现吗？你还需要补什么组件才能让这类失败在报告里被自动统计出来？

### 知识点2：Graph Results（图形结果）—— 用曲线看稳定性

【课程原话/定义】
> Graph Results 是 JMeter 中一个常用的监听器，用于显示性能测试的图形结果。Graph Results 监听器可以以图表的形式展示请求响应时间、吞吐量、错误率等性能指标，帮助用户更直观地分析测试结果。

> ⚠️ **课程原文勘误**：「监听器与测试结果」页把 Graph Results 括注为「（条件控制器）」，这是原文错误——Graph Results 是「图形结果」监听器，与逻辑控制器中的条件控制器（If Controller）毫无关系，请勿混淆。

课程给出的 **相关参数说明（原文要点）**：

| 参数 | 课程原文说明 |
|---|---|
| Write results to file / Read from file（所有数据写入一个文件） | 可以通过浏览，选择一个文件，这样 jmeter 在执行的过程中，会将所有的信息输出到文件，也支持打开一个结果文件进行浏览 |
| Log/Display Only（显示日志内容） | Errors：仅日志错误，表示只输入报错的日志信息；Successes：仅成功日志，表示只输出正常响应的日志信息；不勾选：表示输出所有的信息 |
| Configuer（配置） | 配置需要输出的内容（建议默认。后续如果加载进此保存的文件可能会不知道啥格式） |
| Graphs to Display（要显示的图形） | 从左到右依次是数据、平均、中值、偏离、吞吐量，要显示哪一指标勾选即可显示出来 |

课程给出的 **底部参数含义**：

| 参数 | 课程原文说明 |
|---|---|
| No of Samples（样本数目） | 总的请求数 |
| Latest Sample（最新样本） | 最后一次请求的响应时间 |
| Average（平均） | 所有请求的平均响应时间 |
| Deviation（偏离） | 响应时间变化、离散程度测量值的大小，也就是数据的分布偏差，值越小越好 |
| Throughput（吞吐量） | 服务器每分钟处理的请求数，相当于 TPS，注意单位是分钟 |
| Median（中值） | 响应时间的 50%百分位的值，也就是有 50% 的请求响应时间小于该值 |

【为什么？】
聚合报告给的是「一个时刻的终局统计」，图形结果给的是「整个过程的时间序列」。为什么这个区别重要？因为**压测是一次持续的行为，系统的表现会随时间变化**：JVM 预热阶段慢、GC 触发时抖、连接池打满后劣化、缓存击穿瞬间翻倍。这些现象在最终的聚合数字里会被「平均」掉，但在曲线上会呈现为明显的尖峰或台阶。Deviation（偏离）这个指标尤其被低估——它衡量的是响应时间的离散程度，值越小说明系统越「稳」。一个 Average 200ms、Deviation 20ms 的系统和 Average 200ms、Deviation 400ms 的系统，对用户的含义完全不同。

【必须掌握】

| 参数 | 要点 |
|---|---|
| Write results to file | 把结果落到文件，便于事后复盘；注意文件会随压测时长持续变大 |
| Log/Display Only | Errors 只记失败样本，适合长时间稳定性测试只看问题时刻；Successes 相反；不勾则全记 |
| Configuer | 建议保持默认，否则输出格式可能与后续加载期望不一致 |
| Graphs to Display | 数据 / 平均 / 中值 / 偏离 / 吞吐量，五个曲线可分别勾选 |
| No of Samples | 总请求数（该监听器收到的样本数） |
| Latest Sample | 最新一个样本的响应时间，用于看实时波动 |
| Deviation | 离散程度，越小越稳定——判断「稳不稳」的关键指标 |
| Throughput（注意单位） | 服务器**每分钟**处理的请求数，与聚合报告的每秒吞吐单位不同 |

【企业场景】
你做完 8 小时稳定性压测，聚合报告看起来一切正常：Average 250ms、Error 0%。但你把图形结果的「偏离」和「吞吐量」曲线打开，发现中间某段 30 分钟里吞吐量曲线出现明显台阶式下跌，同时偏离曲线骤增——说明系统在那段时间出现了明显的性能抖动。你拿着这个时间点去比对服务端监控，发现正好赶上数据库的定时备份任务在抢 I/O。如果没有图形结果，这个问题会被最终的聚合数字完全掩盖，你会在生产环境上再遇到一次。这就是「曲线」不可替代的价值。

【面试考察】
1. **面试官怎么问**：「图形结果和聚合报告的区别是什么？」
   **回答框架**：聚合报告是终局统计（表格），图形结果是过程时间序列（曲线）；前者用于下结论，后者用于发现抖动和趋势。
2. **面试官怎么问**：「Deviation 这个指标有什么意义？」
   **回答框架**：衡量响应时间的离散程度，值越小越稳定；两个平均耗时相同的系统，偏离大的那个体验更差、风险更高。
3. **面试官怎么问**：「Graph Results 里的吞吐量单位是什么？」
   **回答框架**：每分钟处理的请求数——这是最容易踩的坑，和聚合报告的每秒吞吐量单位不同，换算时别搞错。
4. **面试官怎么问**：「长时间稳定性测试怎么留证据？」
   **回答框架**：Write results to file 落盘，必要时配合后端监听器推到时序库；关键是要能在事后按时间点回溯。

【易错点】

| 常见错误 | 正确理解 |
|---|---|
| 把 Graph Results 里的 Throughput 当成每秒吞吐量 | 该页明确指出单位是**每分钟**请求数，与聚合报告的每秒吞吐不同，数值会差 60 倍 |
| 只截终局聚合数字作为压测证据 | 抖动、台阶、周期性劣化只在曲线上可见；稳定性测试必须留过程图 |
| 把 Graph Results 与逻辑控制器里的「条件控制器」混为一谈 | 原文括注「（条件控制器）」是笔误，Graph Results 是图形结果监听器 |
| 认为「不勾选 Log/Display Only」就什么都看不到 | 不勾选是输出全部信息；Errors/Successes 才是只看失败或只看成功 |
| 随意修改 Configuer | 课程建议保持默认，否则保存的结果文件格式可能不符合后续加载预期 |

【我的理解】
1. 课程特意提醒 Graph Results 的吞吐量「单位是分钟」。请你算一下：如果曲线显示吞吐量是 1200，那对应的每秒吞吐大约是多少？这个值该和聚合报告的哪一列对比？
2. 一个系统 Average 200ms、Deviation 很小，另一个 Average 200ms、Deviation 很大。请你自己想：如果是给「实时对账」这类业务做容量规划，你会更在意哪个系统？为什么？
