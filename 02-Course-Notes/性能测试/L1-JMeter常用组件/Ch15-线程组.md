### 知识点1：线程组是测试计划的开始点

【课程原话/定义】
课程站点「线程组」页的开篇定位（要点转述）：**线程组（Thread Group）是测试计划的开始点**——测试计划里的请求（取样器）必须放在线程组之下，一条 JMeter 压测脚本就是从 **测试计划 → 线程组 → 取样器** 这条主干长出来的；线程组决定了"用多少用户、以什么节奏、跑多少轮"去访问被测系统。

【为什么？】
用"开始点"而不是"容器"或"文件夹"，是因为它同时表达了三件事：
1. **它是并发的起点**：整个 JMeter 里"多少用户、多快爬升、跑多久"只在**线程组**上配置（见知识点2、知识点3）。所谓"设置 500 并发"，本质是让线程组创建 500 个线程。
2. **它是作用域的起点**：元件的生效范围由它在测试计划树中的层级决定（收口结论见 [[Ch25-JMeter执行顺序]]）。挂在线程组下的配置元件、定时器、断言只对该线程组生效，所以线程组是脚本里**第一个真正划分作用域的层级**。
3. **它是执行的起点**：取样器不会凭空执行——它必须归属于某个线程组，由线程组创建的线程去驱动。没有线程组的测试计划是一条"跑不起来的脚本"。

一句话记忆：**测试计划管全局，线程组管用户，取样器管请求，监听器管结果。**

【必须掌握】

| 说法 | 含义 | 对脚本设计的影响 |
|------|------|------------------|
| 线程组是测试计划的开始点 | 取样器必须挂在线程组之下，脚本主干是"测试计划 → 线程组 → 取样器" | 新建脚本的第一步是加线程组，不是直接加请求 |
| 线程组＝并发模型 | 线程数 / Ramp-up / 循环次数都在这里配 | 并发数是推导出来的，不是随手写的（见 [[Ch26-JMeter虚拟用户管理]]） |
| 线程组＝作用域起点 | 挂在线程组下的元件只对该线程组生效 | 混合场景要建多个线程组，各自配并发与元件 |
| 线程组＝指标归属单位 | 聚合报告等可按线程组/事务组织数据 | 想"分业务看指标"，就要先把线程组拆开 |
| 线程组的类型 | setUp / Thread Group / tearDown 三类 | 执行顺序由**类型**决定，与摆放位置无关（见 [[Ch26-JMeter虚拟用户管理]]） |

【企业场景】
你接到一条新的压测需求，第一步动作永远是"**先把线程组建出来，再往里放请求**"：新建测试计划 → 添加线程组 → 在它下面加 HTTP Request。反过来，如果把 HTTP Request 直接挂在测试计划上（层级放错），JMeter 不会报错，只会**静默地不执行**——这是新人最常见的"脚本点了运行却没反应"。评审别人的脚本时同理：先看树主干（测试计划下有几个线程组、每个线程组里挂了什么），再看参数面板；主干清楚了，脚本行为基本就清楚了。

【面试考察】
面试官："一条 JMeter 压测脚本的结构是什么样的？"

参考回答框架：
1. 主干：测试计划（全局配置）→ 线程组（并发模型）→ 取样器（发什么请求），监听器负责采集结果
2. 线程组的地位：它是测试计划的开始点——取样器必须挂在它下面，并发的数量与节奏也只在它上面配
3. 层级即作用域：配置元件/定时器/断言/前后置处理器挂在哪一层，就只对那一层生效（详见 [[Ch25-JMeter执行顺序]]）
4. 类型与顺序：setUp / Thread Group / tearDown 三类，执行顺序由类型固定，与摆放位置无关

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 把 HTTP Request 直接挂在测试计划下 | 取样器必须归属于线程组；层级放错不会报错，只是静默不执行 |
| 认为线程组只是"装请求的文件夹" | 它同时定义并发模型、作用域边界与指标归属 |
| 以为线程组只有一种 | 还有 setUp / tearDown 两类特殊线程组，执行时机由类型决定 |
| 把"开始点"理解成"第一个执行的动作" | 它是脚本主干与并发的**起点**（结构含义）；真正的初始化动作应放在 setUp 线程组 |

【我的理解】
> 引导思考题1：请用"测试计划 → 线程组 → 取样器"这条主干，解释为什么"新增脚本的第一步是加线程组"，而不是"直接加请求"。
> 引导思考题2：既然层级决定作用域，那么"混合场景要建多个线程组"这件事，本质上是在解决哪个问题——业务比例表达、指标归因，还是两者都有？

### 知识点2：线程组属性①——取样器执行错误后的动作

【课程原话/定义】
**第一部分：在请求取样器执行错误时需要执行的下一步动作：**
- **Continue（继续）**：继续执行接下来的操作。
- **Start Next Loop（启动下一进程循环）**：忽略错误，执行下一个循环。
- **Stop Thread（停止线程）**：退出该线程（不再进行此线程的任何操作）。
- **Stop Test（停止测试）**：等待当前执行的采样器结束后，结束整个测试。
- **Stop Test Now（立即停止测试）**：直接停止整个测试。

【为什么？】
这个设置回答的是一个极具工程意义的问题：**"一个虚拟用户遇到错误之后，还要不要继续演下去？"**

- **Continue（默认语义）= 最贴近真实用户**：真实用户遇到某个请求失败（比如某次推荐位 404），通常仍然会继续浏览、继续操作。所以**绝大多数压测脚本应该用 Continue**——这样错误率会以统计量的形式体现出来（例如 2% 错误率），而不是让压测"提前停掉"。
- **Start Next Thread Loop = "跳过这一轮，重新来"**：适合"某一轮数据有问题"的场景——例如这一轮下单失败（库存不足），就跳过这一轮剩余步骤，开始下一轮。
- **Stop Thread = "这个用户下线"**：适合"该用户已经无法继续"的场景，例如登录失败、token 失效。让这个线程退出，避免它继续制造无意义失败、污染错误率。
- **Stop Test / Stop Test Now = "全局熔断"**：这是**安全阀**。当被测系统出现严重问题（接口大面积 500、数据库挂掉）时，继续加压只会把系统压得更死、还可能影响共用环境，此时需要立刻停。**区别在于"优雅"还是"立刻"**：Stop Test 会等当前采样器跑完再结束（不会留下半截请求），Stop Test Now 直接中断（更狠，可能留下未完成的连接）。

一句话记忆：**Continue 保真实、Start Next Loop 保轮次、Stop Thread 保单用户、Stop Test 保系统。**

【必须掌握】

| 动作 | 行为 | 适用场景 |
|------|------|----------|
| Continue | 继续执行后续操作 | 默认选择；让错误以统计形式体现，贴近真实用户 |
| Start Next Loop | 忽略错误，执行下一个循环 | 本轮数据不可用（如库存不足），跳过本轮剩余步骤 |
| Stop Thread | 退出该线程，不再执行该线程的任何操作 | 该用户已无法继续（登录失败/token 失效） |
| Stop Test | 等当前采样器结束后结束整个测试 | 系统出现严重异常，需要优雅熔断 |
| Stop Test Now | 直接停止整个测试 | 需要立刻止损（大面积 5xx、环境被打挂风险） |

【企业场景】
你晚上跑一轮大并发压测，中途被测服务的一个依赖（比如缓存）挂了，接口开始大面积超时。如果你用的是 Continue，JMeter 会继续压 2 小时，**把已经出问题的服务压得更惨，甚至影响其他同学共用环境**。所以规范做法是：**先按场景选好错误动作，再配上监控告警**——常规压测用 Continue 保留完整错误率数据；一旦出现"容器重启/大面积 5xx"这类系统级异常，用 Stop Test 或 Stop Test Now 及时熔断。这类"压测熔断策略"在正式压测方案里是要写明的（属于风险管理的一部分，对应 [[../L1-性能测试体系/Ch08-性能测试计划|L1 Ch08-性能测试计划]]）。

【面试考察】
面试官："压测中线程组遇到错误怎么处理？什么情况下要停止测试？"

参考回答框架：
1. 五个选项：Continue / Start Next Thread Loop / Stop Thread / Stop Test / Stop Test Now
2. 语义区别：从"继续演"到"单用户退出"到"全局熔断"，粒度逐渐放大
3. 选择原则：常规压测用 Continue 保留错误率数据；用户级失效用 Stop Thread；系统级异常用 Stop Test（优雅）/ Stop Test Now（立刻）
4. 风险管理：熔断策略应写进压测方案，并配合监控告警，避免把问题环境压得更坏

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 为了"看起来数据漂亮"把所有错误动作设成 Stop Test | 会让压测提前结束、丢失错误率曲线，也无法评估系统在异常下的表现 |
| 分不清 Stop Test 与 Stop Test Now | Stop Test 会等待当前采样器结束（优雅）；Stop Test Now 立即中断 |
| 认为 Start Next Loop 是"重试当前请求" | 它是"忽略错误进入下一轮循环"，不是重试机制；重试要靠逻辑控制器/定时器实现 |
| 不配熔断策略就跑长时间大并发 | 一旦被测系统崩溃会持续加压，扩大影响面，属于压测事故 |

【我的理解】
> 引导思考题1：请把五个错误动作按"影响范围"从小到大排序，并各说一个适用场景。
>
> 引导思考题2：为什么常规压测推荐用 Continue 而不是 Stop Test？这样做的收益与风险分别是什么？

### 知识点3：线程组属性②——线程属性（并发、爬升、循环与生命周期）

【课程原话/定义】
**第二部分：线程属性**
- **Number of Thread (users)**：线程数，模拟的用户数量。
- **Ramp-up Period（seconds）**：达到指定线程数所需要的时间。**举例：线程数设置为 50，此处设置为 5，那么每秒启动的线程数 -> 线程数 50/5 = 10。**
- **Loop Count**：循环次数。**Infinite 为永远**，勾选之后就会一直循环。
- **Same user on each iteration**：每次迭代都用相同的用户，勾选该选项则**不同次迭代之间是串行执行**，不勾选则为并行执行。
- **Delay Thread creation until needed**：当线程需要执行的时候，才会被创建。如果不勾选这个选项，那么，在计划开始的时候，**所有需要的线程就都被创建好了**。
- **Specify Thread lifetime**：定义线程调度时间。勾选之后，即可设置之后的两个属性：
  - **Duration (seconds)**：持续时间（秒），在此选项填入 N，说明这个计划，从某个开始时间算起，执行 N 秒后结束。（会忽略 结束时间 的选项）。使用这个选项时，**循环次数可以勾选"永远"**。
  - **Startup delay (seconds)**：启动延迟（秒），在此选项填入 N，手动点击开始执行计划，然后延迟 N 秒后，计划才真正开始执行。

【为什么？】
这六个参数共同回答"**这些虚拟用户怎么活**"，理解它们之间的配合比死记更有效：

1. **线程数 = 目标并发**。它就是"同时在线的虚拟用户数"。
2. **Ramp-up = 爬升斜率**，决定"压力是瞬间砸下去还是逐步加上来"。课程的例子（50 线程 / 5 秒 = 每秒启动 10 个）说明了它的计算方式。**【扩展知识】**（已按 JMeter 官方文档核对）官方对 Ramp-up 的说明补充了一个关键细节：**第一个线程总是立即启动**，且线程不是"一次性全开再等"，而是**按比例间隔启动**——10 个线程配 100 秒 Ramp-up 时，每个线程与上一个的启动间隔是 10 秒，因此第 10 个线程实际在第 90 秒启动（不是第 100 秒）。这意味着"Ramp-up = 达到满并发所需时间"是工程口径，与"最后一个线程的启动时刻"略有差异，做精细场景设计时要注意。
3. **Loop Count = 每个线程跑几轮**。翻页式理解：一个线程跑完一轮（走完线程组内所有取样器）算一次迭代。"永远"配合 Duration 使用，是**稳定性压测**的标配（跑固定时长而不是固定次数）。
4. **Same user on each iteration = 迭代间是否复用用户上下文**。这里必须纠偏（见课程勘误）：它**不是**"串行/并行"，而是"**是否沿用第一次采样得到的 Cookie 与缓存**"。勾选时，需要全局 Cookie Manager / Cache Manager 支持，后续请求会复用第一轮拿到的 Cookie 与缓存；不勾选时，Cookie/缓存不会在迭代间沿用，**并且迭代之间会重新建立连接**，导致 RT 变长、消耗更多内存与 CPU。工程含义：**如果你要模拟"同一个用户连续操作"（例如同一会话下浏览→加购→下单），就应勾选它**；如果每次迭代都要模拟"新用户"，则不勾选（代价是更多连接开销）。
5. **Delay Thread creation until needed = 线程是否按需创建**。勾选时，线程只会在"轮到它的那部分 Ramp-up 时间"到来时创建；不勾选（原始默认行为）则测试开始时**所有线程一次性创建完毕，然后按比例暂停等待**。适用判断：**Ramp-up 远大于单线程执行时间**（前面的线程早就跑完了后面的还没启动）就适合勾选，能省内存；而"线程在全测试期间大部分时间都活跃"的场景适合不勾选。
6. **Specify Thread lifetime（Duration / Startup delay）= 生命周期**。Duration 让压测"跑固定时长"，此时把 Loop Count 设为"永远"最自然；Startup delay 让压测"延迟 N 秒再真正开始"（便于错峰或者等监控就位）。课程还提到一个历史细节：**设了 Duration 会忽略"结束时间"选项**——这是旧版 JMeter 界面（有开始/结束时间字段）的遗留说明，现行界面上只保留 Duration 与 Startup delay 两个输入框，理解语义即可。

【必须掌握】

| 参数 | 课程原文 | 作用 | 实践要点 |
|------|----------|------|----------|
| Number of Threads (users) | 线程数，模拟的用户数量 | 目标并发 | 应由业务量推导，做阶梯档位 |
| Ramp-up Period (seconds) | 达到指定线程数所需时间（50/5 → 每秒 10 个） | 爬升速度 | 避免"瞬间打满"；官方：第一线程立即启动，10 线程/100 秒时第 10 个在第 90 秒启动 |
| Loop Count | 循环次数；Infinite 为永远 | 迭代轮数 | 稳定性压测用"永远"＋Duration |
| Same user on each iteration | **课程原文写作"勾选＝串行、不勾选＝并行"（错误）** | 迭代间是否复用 Cookie/缓存 | 实际语义：是否沿用第一轮采样的 Cookie 与缓存；不勾选会重新建连、增加 RT 与资源消耗 |
| Delay Thread creation until needed | 勾选＝需要时才创建线程；不勾选＝开始就全部创建 | 线程创建时机 | Ramp-up 远大于单线程耗时→勾选省内存 |
| Specify Thread lifetime | Duration（持续时间） / Startup delay（启动延迟） | 生命周期 | Duration 与"永远"搭配；Startup delay 用于延后启动 |
| 课程提到的"结束时间" | 原文写"会忽略 结束时间 的选项" | 旧版界面残留 | 现行界面只有 Duration 与 Startup delay，按语义理解 |

【企业场景】
你做一次"阶梯加压找拐点"的压测：并发 50 → 100 → 200 → 400，每档跑 5 分钟。落地方式有两种：一是**建 4 个 Thread Group 顺序执行**（用 [[Ch14-测试计划]] 的"独立运行每个线程组"），每个线程组设好并发、Ramp-up（例如 50 并发的 Ramp-up 给 30 秒，避免瞬间冲高）、Loop Count 设"永远"＋Duration 300 秒；二是用插件里的阶梯线程组（后续 L2 内容）。**为什么每档都要 Ramp-up 而不是直接冲？** 因为瞬间把 400 线程砸下去，服务端会先经历一次"冷启动冲击"（连接池、JIT、缓存全空），你测到的其实不是稳态性能；给一个爬升过程，才能得到有意义的稳态指标。这就是 Ramp-up 在生产压测里的真实用法。

【面试考察】
面试官："线程组里 Ramp-up 是什么意思？Same user on each iteration 你了解吗？"

参考回答框架：
1. 三个基础参数：Number of Threads（并发用户数）、Ramp-up（爬升时间，决定压力上升斜率）、Loop Count（迭代次数/永远）
2. Ramp-up 细节：按比例间隔启动线程；官方说明第一个线程立即启动，10 线程/100 秒时第 10 个在第 90 秒启动
3. Same user on each iteration：控制迭代之间是否复用第一轮采样的 Cookie 与缓存；不勾选会重新建连、增加响应时间与资源消耗（注意课程此处解释有误）
4. 生命周期：Specify Thread lifetime 的 Duration 用于定时长压测（常配"永远"），Startup delay 用于延后启动；Delay Thread creation until needed 控制线程按需创建以省内存

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 按课程原文理解 Same user on each iteration（勾选＝串行、不勾选＝并行） | 同一线程内的迭代必然串行；该选项实际控制**迭代间是否复用 Cookie/缓存**，不勾选还会重新建连 |
| 把 Ramp-up 当成"压测持续时间" | 它是"爬到目标并发所需时间"，持续时长由 Loop Count 或 Duration 决定 |
| 认为 Ramp-up = 最后一个线程的启动时刻 | 官方说明第一线程立即启动，10 线程/100 秒时第 10 个在第 90 秒启动 |
| 设了 Duration 却忘了把 Loop Count 设为"永远" | 两者不配套时压测会在循环跑完后提前结束，跑不满时长 |
| 每个档位直接瞬间打满并发 | 会有冷启动冲击，测到的是瞬态而非稳态；应给合理 Ramp-up |
| 以为 "Install-loop"= 重试 | "永远"是持续循环，不是失败重试机制 |

## 课程原文勘误

| 原文写法 | 问题 | 正确理解（已核对 JMeter 官方文档） |
|----------|------|-----------------------------------|
| `Start Next Loop（启动下一进程循环）` | 选项名与官方界面不一致 | 官方标签为 **Start Next Thread Loop**；语义：忽略本次错误，进入下一轮循环 |
| `Same user on each iteration：勾选该选项则不同次迭代之间是串行执行，不勾选则为并行执行` | 解释错误（同一线程内迭代不可能并行） | 该选项控制**迭代之间是否沿用第一轮采样得到的 Cookie 与缓存**（需全局 Cookie/Cache Manager）；不勾选时 Cookie/缓存不沿用，且迭代间会重新建立连接，导致 RT 增加、内存与 CPU 消耗上升 |
| `Specify Thread lifetime ...（会忽略 结束时间 的选项）` | 现行界面（含课程录制版本）中并无"结束时间"字段 | 属于旧版 JMeter 的 Scheduler（有开始/结束时间）残留说明；现行界面只有 **Duration（seconds）** 与 **Startup delay（seconds）** 两项，Duration 用于设定相对结束时间 |
| 线程属性第 1 项写作 `Number of Thread (users)` | 与界面一致但与官方文档常见写法略有差异 | 官方文档写法为 **Number of Threads (users)**，两者指同一参数 |
| `Loop Count：...Infinite 为永远` | 原文未提示"永远"与 Duration 的配套关系 | 使用 Duration 时建议把 Loop Count 设为"永远"，否则可能循环跑完提前结束 |
