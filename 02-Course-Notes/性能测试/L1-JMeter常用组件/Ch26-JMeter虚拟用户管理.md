### 知识点1：虚拟用户与虚拟用户管理

【课程原话/定义】
**JMeter 虚拟用户管理是指在性能测试中模拟和管理多个虚拟用户的过程。** 在性能测试中，**虚拟用户是指由性能测试工具模拟的并发访问系统的用户**，用于模拟实际用户对系统的请求和行为。
通过管理虚拟用户，可以模拟真实世界中的用户行为和负载，评估系统在不同负载条件下的性能特征。

【为什么？】
"虚拟用户（Virtual User，VU）" 是压测里最核心的一个抽象，它的机制可以拆成三句话：

1. **一个虚拟用户 = 一个真实用户的行为脚本**：它不代表一个真人，而是"真人在系统里会做的那串请求"。所以设计虚拟用户的第一步是**设计行为路径**（登录 → 浏览 → 加购 → 下单），而不是先想并发数。
2. **JMeter 的虚拟用户由"线程"承载**：JMeter 是多线程模型，**一个线程 ≈ 一个虚拟用户**。这就是为什么"设置并发"在 JMeter 里体现为"设置 Number of Threads"——这一章的所有参数归根到底都在回答一个问题：**这些线程怎么创建、跑多久、循环几次、出错怎么办。**
3. **"管理"包含三个维度**：**数量**（多少并发）、**节奏**（多快爬升到目标并发）、**生命周期**（跑多久、循环几次、准备与清理）。课程用一整页讲"虚拟用户管理"，本质就是把这三件事讲全。

再往前接一节：L1 学过 `并发数 = QPS × 平均响应时间`（利特尔法则）。这个公式的工程含义是——**并发数不是拍脑袋定的，它由业务量和 RT 反推出来**。而本节要学的，正是"把推导出的并发数落成 JMeter 参数"的那一步。

【必须掌握】

| 概念 | 定义 | 落地到 JMeter |
|------|------|---------------|
| 虚拟用户（VU） | 由工具模拟的并发访问系统的用户 | 一个线程（Thread） |
| 虚拟用户管理 | 模拟与管理多个虚拟用户的过程 | 线程组的四个维度：数量/节奏/循环/生命周期 |
| 模拟目标 | 逼近真实用户行为与负载 | 行为路径（脚本逻辑）＋并发模型（参数） |
| 评估产出 | 不同负载条件下的性能特征 | RT / TPS / 错误率曲线与拐点 |
| 上游依据 | 业务量与 RT 推导并发数 | 由参数（L1）落到参数值（本章） |

【企业场景】
Leader 说"大促首小时预计 30 万次下单，要求 RT 不超过 200ms，压一下看能不能扛住"。你的推导路径是：30 万次/3600 秒 ≈ 83 QPS → 并发数 ≈ 83 × 0.2s ≈ 17 个并发（这是**平均值**）→ 考虑峰值系数与冗余，实际压测要按更高的并发档位（例如 50/100/200）去压，找出拐点。然后你把这个"50/100/200"落到 JMeter 里，就变成**线程组的 Number of Threads**。**注意：虚拟用户数是推导的产物，不是随手写个 500。** 企业里最常被追问的就是"你这个并发数怎么来的"，答不出推导过程的压测方案是过不了评审的。

【面试考察】
面试官："什么是虚拟用户？并发数你是怎么定的？"

参考回答框架：
1. 定义：虚拟用户是压测工具模拟的并发访问用户，用于模拟真实用户的请求与行为
2. JMeter 映射：一个线程约等于一个虚拟用户，由线程组统一管理数量/节奏/循环/生命周期
3. 并发数推导：并发数 = QPS × 平均 RT（利特尔法则）；QPS 由业务量推导，RT 来自目标或基线
4. 工程处理：按峰值系数与冗余放大档位（如 50/100/200），做阶梯加压找拐点，而不是只压一个值

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 拍脑袋定并发数（"就压 500 吧"） | 应由业务量与 RT 推导，再按峰值系数放大做阶梯加压 |
| 认为虚拟用户是"真人账号" | VU 是行为脚本的载体，一个账号可以支撑多个 VU（但业务数据要参数化） |
| 把并发数当成"总共发多少个请求" | 并发数是同时在线的用户数，总请求量 = 并发 × 迭代次数 |
| 只考虑平均 QPS 不看峰值 | 压测必须按峰值时段量级放大，否则得到的容量结论偏乐观 |

【我的理解】
> 引导思考题1：请用自己的话说明"一个虚拟用户"到底代表什么，以及为什么它会被映射成 JMeter 的一个线程。
>
> 引导思考题2：如果业务量是每天 100 万次请求、平均 RT 是 300ms，你会怎么推导并发数？（先算均价量，再想峰值系数）

### 知识点2：三类线程组总览

【课程原话/定义】
常见的线程组（课程原文）：
- **setUp Thread Group**
- **Thread Group**
- **tearDown Thread Group**

【为什么？】
把线程组分成三类，解决的是"**压测的时间轴管理**"问题。一次完整的压测不只是"加压"这一个动作，它有三段：

| 时间段 | 需要做的事 | 对应线程组 |
|--------|-----------|-----------|
| 加压之前 | 准备环境、加载数据、登录获取会话 | setUp Thread Group |
| 加压期间 | 真正模拟用户并发行为 | Thread Group |
| 加压之后 | 关闭资源、清理数据、收尾 | tearDown Thread Group |

为什么要分开？因为**混在一起会污染指标**：

- 造数/登录这类"准备动作"如果放在主线程组里，它的耗时会被算进 RT、它的请求会被算进 TPS——**你交付的指标里混进了压测机自己造的"非业务流量"**。
- 清理动作如果与加压同时发生，会让清理本身成为被测系统的一部分负载，甚至删掉正在被断言的数据（见 [[Ch14-测试计划]] 知识点5）。

所以这三类线程组的分工，本质是**把"准备/加压/清理"在时间上隔离**，让每个阶段的执行目的单一、指标干净。这也解释了课程为什么强调"执行顺序与它们在测试计划中的位置无关"（知识点6）——顺序由**类型**决定，不由摆放位置决定。

【必须掌握】

| 线程组类型 | 阶段 | 目的 | 课程给出的典型内容 |
|------------|------|------|--------------------|
| setUp Thread Group | 主测试之前 | 初始化设置 | 准备测试环境、加载数据、执行其他设置操作 |
| Thread Group | 主测试期间 | 定义并控制线程（虚拟用户）的执行方式和数量，模拟并发访问 | 创建测试场景、设置并发用户数量、循环次数 |
| tearDown Thread Group | 主测试之后 | 清理/收尾 | 关闭资源、清理数据、执行其他收尾工作 |

【企业场景】
你写一条"下单"压测脚本，标准的三段式结构是：**setUp 线程组**里放"登录并提取 token 到全局变量"（这样主线程组里每个用户都能直接带着会话去下单）；**主线程组**里放"浏览 → 加购 → 下单 → 支付"的下单链路；**tearDown 线程组**里放"取消订单/清理测试数据"。为什么要这么分？因为如果不分：登录请求会混进下单链路的 RT 统计（一个登录接口 300ms 会把下单链路平均 RT 拉高）、清理动作又可能与加压打架。**这三段式结构是性能脚本的行业惯例，评审时别人第一眼就看你分没分。**

【面试考察】
面试官："JMeter 有哪几种线程组？分别什么作用？"

参考回答框架：
1. 三类：setUp Thread Group、Thread Group、tearDown Thread Group
2. 分工：前置准备 / 主加压 / 后置清理，分别对应压测时间轴的三段
3. 为什么要分开：避免准备与清理动作混入业务指标，也避免清理与加压互相干扰
4. 执行顺序：setUp → Thread Group → tearDown，与元件在测试计划中的位置无关

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 把所有请求都塞进一个 Thread Group | 准备/清理会污染业务指标；应按 setUp/主/tearDown 三段拆分 |
| 认为 setUp 是"可选的装饰" | 它是前置准备的正规位置，能显著提升脚本可维护性与指标纯净度 |
| 把造数请求写进主线程组的第一个取样器 | 造数属于前置阶段，应放 setUp 线程组 |
| 以为只有 Thread Group 能设置并发 | setUp/tearDown 线程组也各有自己的线程数与循环配置，只是用途不同 |

【我的理解】
> 引导思考题1：为什么"登录"这一步更适合放在 setUp 线程组，而不是放在主线程组的第一个请求？
>
> 引导思考题2：请为一条"领券"压测链路设计三段式结构，写出每个线程组里放什么。

### 知识点3：setUp Thread Group（前置初始化）

【课程原话/定义】
**setUp Thread Group**
- **作用**：setUp Thread Group 是 JMeter 中的一个**特殊元素**，它主要用于**在测试执行之前进行初始化设置**。setUp Thread Group 允许您在执行测试计划之前执行一组请求或操作，例如**准备测试环境、加载数据或执行其他设置操作**。
- **适用场景**：适用于需要在执行主要测试计划之前进行**特定设置或准备工作**的情况。通常与 Thread Group 结合使用，确保在主要测试执行之前执行必要的初始化操作。

【为什么？】
setUp 的机制关键在"**它在时间轴上的位置被强制固定**"：

- 它总是先于所有 Thread Group 执行，**不受它在测试计划树里的摆放位置影响**（课程原文强调了这一点）。这意味着你不必靠"把它拖到最上面"来保证顺序，JMeter 用**类型**而非**位置**来调度。
- 为什么要强制？因为很多压测的前置条件是**强依赖**：没有登录就没有 token，没有 token 下单接口必 401。如果前置和主加压并行跑，主线程组第一批请求会在 token 还没准备好时发出——**你会看到大量 401 失败，然后误判"系统扛不住"**。
- 它的一个实践特性：**setUp 线程组的变量可以被主线程组读取**。所以"在 setUp 里登录 → 把 token 存为变量 → 主线程组用 `${token}`" 是极常见的组合。

**【扩展知识】**：要注意 setUp 线程组本身也是"线程组"，它有线程数与循环次数。**前置造数如果量大（例如要造 1 万个用户），它自己也可能成为一次小压测**——这时可以给它单独设置并发与循环，且要认识到它的执行耗时会让整个压测的"开始时间"往后推。

【必须掌握】

| 项目 | 课程原文 | 工程要点 |
|------|----------|----------|
| 定位 | JMeter 中的特殊元素 | 前置阶段专用线程组 |
| 作用 | 测试执行之前进行初始化设置 | 准备环境、加载数据、执行设置操作 |
| 典型内容 | 准备测试环境、加载数据、其他设置操作 | 登录取 token、造数、准备基础数据 |
| 适用场景 | 需要主测试前做特定准备的情况 | 与 Thread Group 结合使用 |
| 执行时机 | 先于所有 Thread Group（与摆放位置无关） | 保证强依赖前置条件先完成 |
| 变量传递 | — | setUp 中产生的变量可供主线程组引用 |

【企业场景】
你压"支付"链路，支付接口需要一个**登录后的 session** 和一个**已存在的订单号**。你的 setUp 线程组就做两件事：调用登录接口 → 用后置处理器把 token/session 提取成变量；调用下单接口 → 提取订单号成变量。这样主线程组的支付请求直接引用 `${token}`、`${orderId}` 即可。**好处是可复用与可维护**：会话获取逻辑只写一遍；如果登录接口变了（比如加了验证码），你只改 setUp 这一处，主线程组一行不动。

【面试考察】
面试官："setUp Thread Group 有什么作用？什么时候用？"

参考回答框架：
1. 定位：特殊线程组，在主测试执行之前完成初始化设置
2. 用途：准备测试环境、加载数据、登录获取会话、造基础数据等
3. 执行保证：先于所有 Thread Group 执行，且与它在测试计划中的位置无关
4. 实践价值：把前置依赖集中管理，变量可被主线程组引用，接口变更只需改一处

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 把 setUp 放在主线程组后面以为它就后执行 | 执行顺序由类型决定，setUp 永远先执行，跟位置无关 |
| 把 setUp 当"随便放点杂项"的地方 | 它是强依赖前置的正规位置，内容要单一明确（登录/造数/准备） |
| 忽略 setUp 自身也要配置线程数与循环 | 批量造数时 setUp 自身就是一次小压测，耗时会影响整体开始时间 |
| 以为 setUp 里的变量主线程组读不到 | 变量可传递，主线程组可直接引用 setUp 中提取的变量 |

【我的理解】
> 引导思考题1：为什么 setUp 的执行顺序"与它在测试计划中的位置无关"反而是个好设计？
>
> 引导思考题2：如果 setUp 里要造 1 万个用户数据，你会怎么配置它的线程数和循环次数？为什么这会拉长整个压测的准备时间？

### 知识点4：Thread Group（核心加压单元）

【课程原话/定义】
**Thread Group**
- **作用**：Thread Group 是 JMeter 中的**核心元素之一**，用于**定义并控制线程（虚拟用户）的执行方式和数量**，以模拟并发用户访问系统的行为。
- **适用场景**：适用于**创建测试场景、设置并发用户数量、循环次数**等，用于模拟用户在系统中的行为。**大多数 JMeter 测试计划都会包含一个或多个 Thread Group。**

【为什么？】
Thread Group 之所以是"核心"，是因为它承担了三件事，缺一不可：

1. **它是"并发模型"的唯一表达位置**：整个 JMeter 里"多少用户、多快爬升、跑多久"只在 Thread Group 上配。想要 500 并发，本质是让 Thread Group 创建 500 个线程。
2. **它是"作用域"的主要分界线**：挂在某个 Thread Group 下的元件只对它生效。所以**要做多业务混合场景，标准做法是建多个 Thread Group**——每个线程组代表一类用户行为（浏览/搜索/下单），各配各的并发数体现业务比例。
3. **它是"指标归属"的单位**：聚合报告等监听器可以按线程组/事务组织数据，所以线程组划分得清不清，直接决定你能不能"按业务分项看指标"。这就是课程说"大多数测试计划都会包含一个或多个 Thread Group"的实际含义——一个是因为简单场景只需一条链路，多个是因为混合场景必须拆分。

**【扩展知识】**：JMeter 还有 **Concurrency Thread Group**、**Ultimate Thread Group**（插件提供）等增强型线程组，支持阶梯加压、波浪形加压等更真实的负载模型——这正是课程后面 L2「JMeter 参数化与并发」要展开的内容。本节的 Thread Group 是所有加压模型的基础。

【必须掌握】

| 维度 | 课程原文 | 工程含义 |
|------|----------|----------|
| 定位 | JMeter 的核心元素之一 | 并发模型的唯一表达位置 |
| 作用 | 定义并控制线程（虚拟用户）的执行方式和数量 | 设置并发用户数量、循环次数 |
| 目标 | 模拟并发用户访问系统的行为 | 逼近真实用户行为 |
| 适用场景 | 创建测试场景、设置并发、循环次数 | 单链路场景用一个；混合场景用多个体现比例 |
| 常见性 | 大多数测试计划包含一个或多个 | 作用域与指标归属的分界线 |

【企业场景】
你要压"大促首页"的混合流量：60% 浏览商详、30% 搜索、10% 加购。做法是**建三个 Thread Group**，分别设置并发数与循环次数来体现 3:6:1 的比例，并且每个线程组内的请求只写对应业务的动作。这样跑完之后，你能在聚合报告里**按线程组分别读出**浏览/搜索/加购各自的 RT 与 TPS——**这正是"能不能做混合场景压测"的标志**。如果把三条业务链全塞进一个线程组，你就只能得到一个混合后的平均值，无法回答"到底是搜索慢还是加购慢"。

【面试考察】
面试官："Thread Group 的作用是什么？什么时候需要建多个线程组？"

参考回答框架：
1. 定位：JMeter 的核心元素，定义并控制线程（虚拟用户）的数量与执行方式
2. 配置内容：并发用户数、Ramp-up、循环次数、生命周期等（下一知识点展开）
3. 何时多个：需要模拟多业务混合流量时，一个线程组代表一类用户行为，用并发数体现比例
4. 收益：作用域清晰、指标可按业务分项统计，能定位"哪条链路更慢"

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 把所有业务链塞进一个 Thread Group | 混合场景应建多个线程组并配不同并发，才能分业务看指标 |
| 认为线程组只是"放请求的文件夹" | 它同时定义并发模型、作用域边界与指标归属 |
| 一个线程组里配 500 并发 = 每条链路各 500 并发 | 线程组内的请求共享该线程组的线程；链路内部顺序执行才符合真实用户行为 |
| 以为只有一种 Thread Group | 另有 setUp/tearDown 线程组，以及插件提供的并发/阶梯线程组 |

【我的理解】
> 引导思考题1：为什么"混合场景要用多个 Thread Group"？请从"业务比例表达"和"指标归因"两个角度解释。
>
> 引导思考题2：如果一条链路里包含"浏览 → 加购 → 下单"三步，你会把它们放在同一个线程组里顺序执行，还是拆成三个线程组？为什么？

### 知识点5：tearDown Thread Group（后置收尾）

【课程原话/定义】
**tearDown Thread Group**
- **作用**：tearDown Thread Group 也是 JMeter 中的一个**特殊元素**，用于**在测试执行结束后进行清理工作或收尾操作**。tearDown Thread Group 允许在整个测试计划执行完成后执行一组请求或操作，例如**关闭资源、清理数据或执行其他收尾工作**。
- **适用场景**：适用于需要在**整个测试计划执行完成后进行清理或收尾工作**的情况。通常用于执行**最终性的操作**，确保**测试执行完成后系统处于正确状态**。

【为什么？】
tearDown 的价值集中在一句话里：**"确保测试执行完成后系统处于正确状态"**。这句话在生产环境里分量很重：

- **压测是"制造副作用"的过程**：注册会造账号、下单会造订单、上传会造文件、领券会占库存。如果不清理，下一轮压测就在脏数据上跑——数据量变化会让查询变慢、会让缓存命中率变化，**结果不再可比**。
- **tearDown 也是"安全阀"**：典型用法是在后置里把压测期间修改的配置**还原**（打开的功能开关关掉、改过的限流阈值调回），避免压测把环境"留在一个危险状态"。
- **顺序上必须靠后**：它与主线程组的先后关系由 [[Ch14-测试计划]] 的"主线程组运行完成后运行 tearDown 线程组"这个开关控制。为什么必须靠后？因为清理动作本身也是请求，如果与加压并行，它就会变成**额外负载**，污染你正在采集的指标。

**【扩展知识】**：tearDown 里放"关闭资源"时要小心幂等性与失败处理——清理失败不应让整轮压测被判定为失败，实践中常把它们放在独立线程组里单独看结果。

【必须掌握】

| 项目 | 课程原文 | 工程要点 |
|------|----------|----------|
| 定位 | JMeter 的特殊元素 | 后置阶段专用线程组 |
| 作用 | 测试执行结束后进行清理工作或收尾操作 | 关闭资源、清理数据、还原配置 |
| 执行时机 | 整个测试计划执行完成后 | 由"主线程组完成后运行 tearDown"开关保证 |
| 适用场景 | 需要清理/收尾、执行最终性操作 | 保证测试完成后系统处于正确状态 |
| 目标 | 系统处于正确状态 | 保证压测可重复、结果可比、避免残留风险 |

【企业场景】
你压"登录取 token"这条链路，注册/登录会大量写入**会话记录**和**登录日志**。如果每一轮压测都不清理，第三天你会发现数据库里堆了几百万条测试会话——数据库查询开始变慢，于是你误判"系统性能在下降"，其实是你自己留下的垃圾。所以企业里规范的压测脚本一定会配 tearDown：批量失效测试会话、删除测试订单、把压测开关关掉。**"会不会写 tearDown"经常就是区分"能跑脚本"和"能交付压测结论"的分水岭。**

【面试考察】
面试官："压测脚本为什么要有 tearDown？它保证什么？"

参考回答框架：
1. 作用：在测试执行结束后做清理与收尾（关闭资源、清理数据、还原配置）
2. 目的：确保测试完成后系统处于正确状态，避免脏数据影响下一轮压测的可比性
3. 时机：整个测试计划执行完成后执行，由测试计划里的"主线程组完成后运行 tearDown"开关控制
4. 风险意识：后置与加压并行会污染指标；清理逻辑要幂等、失败不应误导压测结论

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 不做清理，反复压同一环境 | 脏数据会改变系统性能表现，后续结果不可比甚至失败 |
| 让 tearDown 与加压并行 | 清理成为额外负载，污染指标并可能误删正在使用的数据 |
| 认为清理失败就代表压测失败 | 清理是收尾动作，其失败应单独看待，避免误判压测结果 |
| 把"重置环境"当成别人的事 | 压测执行者对"压完环境是否干净"负直接责任 |

【我的理解】
> 引导思考题1：请解释"确保测试执行完成后系统处于正确状态"这句话在企业里意味着哪些具体动作。
>
> 引导思考题2：如果 tearDown 里的清理请求失败了，你会把它算入"压测失败率"吗？为什么？

### 知识点6：不同线程组的执行顺序

【课程原话/定义】
**同一个测试计划中的执行顺序：`setUp Thread Group` → `Thread Group` → `tearDown Thread Group`**
**注：执行顺序与他们在测试计划中的位置顺序无关。**

【为什么？】
这条规则看似简单，却定义了 JMeter 的**调度语义**：

1. **顺序由"类型"决定，不由"位置"决定**。你把 tearDown 线程组拖到元件树最上面，它依然最后执行。这对脚本维护是好事：**元件树可以被整理成"好读"的顺序（例如把 setUp 放在最上面方便阅读），而不会改变执行行为**。
2. **多个 Thread Group 之间**（同类型的多个主线程组）则回到 [[Ch14-测试计划]] 的开关：不勾选"独立运行每个线程组"＝并行执行（混合场景）；勾选＝按树中顺序依次执行（分阶段场景）。**所以"顺序"其实是两个层面的规则**：跨类型（setUp/主/tearDown）由类型固定；同类型（多个主线程组）由测试计划开关决定。
3. **为什么要有这条固定顺序？** 因为它把"前置 → 加压 → 后置"的生命周期语义固化下来，用户不用靠拖拽来维护依赖关系——**这是把工程约束做进工具的设计**。

【必须掌握】

| 层面 | 决定因素 | 行为 |
|------|----------|------|
| 跨类型顺序 | setUp / Thread Group / tearDown 的类型 | setUp → 主线程组 → tearDown，固定不变 |
| 位置影响 | — | 与元件在测试计划中的摆放位置**无关** |
| 同类型多线程组 | 测试计划"独立运行每个线程组"开关 | 不勾选＝并行；勾选＝按顺序执行 |
| 元素树的作用 | 可读性 | 可自由整理摆放顺序而不影响执行语义 |

【企业场景】
你在 Code Review 别人的压测脚本时，看到元件树把 tearDown 线程组放在最上面，你**不应该**判定"脚本写错了"——因为位置不影响执行。你要检查的是另外两点：一是**类型用对了没有**（该前置的有没有用 setUp、该清理的有没有用 tearDown）；二是**"独立运行每个线程组"开关有没有按场景勾选**。还有一类高频事故：压测跑完后清理动作没执行，排查发现是"独立运行每个线程组"勾上了、且 tearDown 的时机开关没配对——**这些开关之间的组合关系，是压测脚本最容易出错的地方。**

【面试考察】
面试官："同一个测试计划里，线程组的执行顺序是怎样的？"

参考回答框架：
1. 跨类型：固定为 setUp Thread Group → Thread Group → tearDown Thread Group
2. 位置无关：摆放位置不改变执行顺序（课程原文强调）
3. 同类型多个主线程组：由"独立运行每个线程组"决定——不勾选并行、勾选顺序执行
4. 实践意义：可以自由整理元件树提高可读性，同时依赖固定语义保证前置/后置正确执行

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 通过拖拽位置来控制 setUp/tearDown 的执行时机 | 位置无关，执行顺序由线程组类型决定 |
| 看到 tearDown 放在最上面就认为脚本错了 | 位置不影响执行；应检查类型使用与测试计划开关 |
| 混淆两层顺序规则 | 跨类型顺序固定；多个主线程组之间的先后由"独立运行每个线程组"开关决定 |
| 认为 setUp 会随着"独立运行每个线程组"改变时机 | 无论该开关如何设置，setUp 都在主测试之前、tearDown 都在之后 |

【我的理解】
> 引导思考题1：请分别说出"跨类型顺序"和"同类型线程组顺序"分别由什么决定。
>
> 引导思考题2：既然位置不影响执行，那你在整理元件树时还会在意摆放顺序吗？为什么（可读性 vs 执行语义）？
