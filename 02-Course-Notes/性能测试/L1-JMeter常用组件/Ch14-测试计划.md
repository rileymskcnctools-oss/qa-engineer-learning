### 知识点1：测试计划的定义与地位

【课程原话/定义】
测试计划**用来描述一个压力/性能测试脚本和场景设计的基本运行单元**，使用 JMeter 进行测试的所有内容都是**基于一个测试计划**。

【为什么？】
"基本运行单元"这五个字是理解 JMeter 的关键：

- **测试计划是整棵元件树的根节点**。你打开 JMeter，界面左侧最顶层永远是 `Test Plan`；所有线程组、控制器、取样器、监听器都必须长在它下面。没有测试计划，就没有可执行的东西。
- **它同时是"配置容器"和"执行单元"**：JMeter 执行时的入口是"运行一个测试计划"，测试计划里放什么，跑的就是什么。所以 JMeter 里没有"跑一个线程组"这种独立入口（除非你做特殊配置），**执行粒度就是测试计划**。
- **它是"全局作用域"的边界**：挂在测试计划层级的元件（例如接下来要讲的"用户定义的变量"）对整个脚本生效，挂在某个线程组下的元件只对那个线程组生效。这是 JMeter 元件模型里最重要的一条规则——**位置决定作用域**。
- **它也是"一次压测的交付物本体"**：`.jmx` 文件保存的就是一个测试计划。企业里说的"把脚本发我"，指的就是这一个 `.jmx`。

一句话：**测试计划 = 一次压测运行的容器 + 全局作用域 + 可交付脚本本体。**

【必须掌握】

| 属性 | 课程定义 | 工程含义 |
|------|----------|----------|
| 定位 | 压力/性能测试脚本与场景设计的基本运行单元 | 执行粒度；`.jmx` 文件内容 |
| 位置 | 元件树根节点 | 所有元件都挂在它下面 |
| 作用域 | 挂在其下的元件全局生效 | 位置决定作用域 |
| 组成 | 名称与注释 / 用户定义的变量 / 测试计划设置（三大部分） | 本章知识点 2~7 |
| 交付形态 | 保存为 `.jmx` | 可版本管理、可分发给团队 |

【企业场景】
你接手师兄留下的压测项目，第一件事是打开 `.jmx` **先看测试计划这一层的配置**：有没有在测试计划级定义全局变量（例如压测域名、端口）、有没有勾选"独立运行每个线程组"、有没有勾选函数测试模式。为什么先看这一层？因为它决定了**整个脚本的运行方式和数据来源**——比如域名定义在测试计划级时，你把脚本从测试环境切到预发环境只需要改这一处；而如果域名散落在几十个 HTTP 请求里，切换环境就是灾难。**新人写脚本最容易犯的错，就是把本该全局的东西写死在每个请求里。**

【面试考察】
面试官："JMeter 的测试计划是什么？它有什么作用？"

参考回答框架：
1. 定义：测试计划是 JMeter 中进行测试的基本运行单元，所有测试内容都基于一个测试计划
2. 结构：它是元件树的根，所有线程组与元件都挂在它下面，位置决定作用域
3. 作用：既是配置容器（全局变量等），也是执行单元与交付物（`.jmx` 文件）
4. 实践：全局信息（域名、端口、公共参数）宜定义在测试计划级，便于环境切换

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 认为可以直接运行某个线程组 | 执行粒度是测试计划，界面里的"运行"跑的是整个测试计划 |
| 把全局变量定义在某个线程组里 | 线程组级变量只对那个线程组生效，跨线程组要放在测试计划级 |
| 认为测试计划只是一个"名字" | 它持有全局变量与运行策略，直接决定脚本行为与环境可切换性 |
| 把域名、端口硬编码在每个 HTTP 请求里 | 应抽到测试计划级的用户定义变量，改一处即可切换环境 |

【我的理解】
> 引导思考题1：为什么说 JMeter 里"位置决定作用域"？请用测试计划级变量 vs 线程组级变量举例说明差别。
>
> 引导思考题2：如果要把脚本从测试环境切到预发环境，你会把哪些内容放到测试计划级？（至少写出 3 项）

### 知识点2：第一部分——测试计划的名称和注释

【课程原话/定义】
**第一部分：测试计划的名称和注释**，可以修改测试计划的名称，并加上对应的注释描述内容。

【为什么？】
看起来最"没技术含量"的一项，恰恰是脚本可维护性的起点：

- **名称是脚本的"身份证"**：一个压测项目常常有十几种脚本（登录、下单、支付、全链路…）。名称写清楚了，谁都能一眼认出"这是哪条业务链、哪个环境"。
- **注释是"设计意图的存档"**：压测脚本很难自解释——比如某个线程组为什么是 200 并发、某个参数为什么这么配、这个脚本对应哪条需求单。三个月后连你自己都会忘。注释区就是留给这时候的。
- **它是团队协作的最小成本**：把脚本交接给别人时，对方不需要问你就能看懂设计意图，这在企业里等价于**减少一次沟通成本与一次事故风险**。

**【扩展知识】**：企业实践里，注释区通常固定写四件事——**业务场景、被测环境、脚本作者与日期、关键设计说明（并发模型/数据来源）**。有些团队还会把"脚本对应的需求单号/JIRA 链接"写进去，方便追溯。

【必须掌握】

| 字段 | 作用 | 建议内容 |
|------|------|----------|
| 名称（Name） | 脚本标识 | 业务场景 + 环境 + 版本，如 `下单链路_预发_v2` |
| 注释（Comments） | 设计意图存档 | 业务场景、被测环境、并发模型、数据来源、作者/日期 |
| 维护价值 | 交接与追溯 | 让自己和同事都能读懂脚本设计 |

【企业场景】
你的一次压测结论被质疑"当时到底压的是哪个环境"，你的回答不会是"我记不清了"，而是打开脚本指着测试计划的注释说："这里写着被测环境是预发、并发 500、数据来自 `user_500.csv`、压测日期是 X 月 X 日。"**压测报告的可信度，往往就靠这些"看不出技术含量"的记录撑起来。**养成"新建脚本先改名字、写注释"的习惯，成本 30 秒，收益是长期的。

【面试考察】
面试官："你写压测脚本有什么规范？"

参考回答框架：
1. 命名规范：脚本名包含业务场景 + 环境 + 版本，便于识别与检索
2. 注释规范：在测试计划注释里写清业务场景、被测环境、并发模型、数据来源、作者与日期
3. 结构规范：元件命名清晰（避免一堆 `HTTP Request` 同名），必要时用控制器分层组织
4. 版本管理：`.jmx` 入 Git，脚本变更与需求变更对应，可复现任意历史版本

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 测试计划名一直用默认 `Test Plan` | 名不达意会导致多人协作时拿错脚本、压错环境 |
| 注释区空白 | 注释是设计意图的唯一载体，缺了就无法追溯"为什么这么配" |
| 只在自己电脑上留脚本、不进版本库 | 压测脚本属于交付物，应入 Git 并保留变更历史 |
| 认为命名和注释是"形式主义" | 在压测里，环境与配置的每一次"记不清"都可能让结论作废 |

【我的理解】
> 引导思考题1：如果你要写一个新脚本的测试计划注释，你会固定写哪几项内容？请列出你的模板。
>
> 引导思考题2：半年后你被问"当时这个 500 并发是怎么定的"，你希望从脚本的哪里找到答案？

### 知识点3：第二部分——用户定义的变量（User Defined Variables）

【课程原话/定义】
**第二部分：用户定义的变量**，**在之后的测试脚本中可以使用**。

【为什么？】
"用户定义的变量"是 JMeter 里最容易被低估、也最有价值的功能之一，它的机制可以拆成三点：

1. **它定义的是"全局变量"**：定义在测试计划级，所以**整个脚本都能引用**（包括不同线程组、不同控制器下的取样器）。引用语法是 `${变量名}`。
2. **它把"易变信息"从脚本里抽出来**：域名、端口、路径前缀、公共请求头值、超时时间…这些都是"换个环境就要改"的东西。写在变量里，改一处即可全局切换；写死在几十个 HTTP 请求里，改一次就是一场事故。
3. **它让脚本变成"可配置的资产"**：企业里同一套脚本要在测试/预发/生产（或不同机房）之间切换，靠的就是这种"参数外置"。这也是后面参数化（CSV Data Set Config 等）与 CI 参数化传递的基础。

**【扩展知识】**：要区分两类"变量"，这是面试常见追问点：
- **User Defined Variables（测试计划级）**：脚本启动时**一次性求值**，之后不会再变。适合静态配置（域名、端口、常量）。**它的值不能在同一轮运行中被动态改写后再次生效**。
- **User Parameters / CSV Data Set Config（线程组级、按迭代取值）**：每次迭代/每个线程重新取值，适合"不同用户不同数据"的压测数据（账号、商品 ID）。**做并发压测时，"每个虚拟用户用不同账号"必须靠后者，而不是前者。**

理解这个区别，你就明白为什么"把 500 个账号写进 User Defined Variables"是错的：那 500 个值在同一轮里不会轮换，等于所有用户共用同一批数据。

【必须掌握】

| 维度 | 说明 |
|------|------|
| 位置 | 测试计划（Test Plan）→ 用户定义的变量 |
| 作用域 | 整个测试计划（所有线程组可见） |
| 引用语法 | `${变量名}` |
| 求值时机 | 脚本运行前一次性求值（静态配置用） |
| 适合放什么 | 域名、端口、协议、路径前缀、公共常量、超时时间 |
| 不适合放什么 | 需要"每个用户/每次迭代不同"的业务数据（应走参数化元件） |

【企业场景】
你写的压测脚本要在测试环境和预发环境各跑一遍。做法是：在测试计划里定义 `host`、`port`，所有 HTTP 请求的 Server Name 都写 `${host}`、Port 写 `${port}`；切环境时只改变量值，脚本一行不动。更进一步，接入 CI 后你会用命令行 `-Jhost=xxx` 传入参数覆盖变量，实现**同一份脚本、流水线参数化到不同环境**。如果没有这一层抽象，你会被迫维护两份几乎一样的脚本——这是企业里最常见的技术债。

【面试考察】
面试官："JMeter 里怎么管理不同环境的域名？用户定义的变量和 CSV 参数化有什么区别？"

参考回答框架：
1. 做法：把域名/端口等易变配置放到测试计划级的"用户定义的变量"，请求里用 `${变量名}` 引用
2. 好处：改一处全局生效，脚本可跨环境复用；可结合命令行参数（`-J`）在 CI 中传值
3. 区别：User Defined Variables 是**启动时一次性求值的静态配置**；CSV Data Set Config 等是**按线程/迭代轮换取值的压测数据**
4. 结论：配置用变量、数据用参数化；把业务数据塞进变量会导致并发时数据不轮换

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 把需要轮换的业务数据（账号、订单号）放进用户定义的变量 | 它一次性求值不轮换，并发时会所有用户共用同一份数据；应使用 CSV 等参数化元件 |
| 以为用户定义变量能在线程运行中被动态改写并再次生效 | 它属于启动时求值的静态配置，动态值要用变量/函数/后置处理器另做处理 |
| 请求里直接写死域名和端口 | 应抽为变量，否则切环境要改几十处，易漏改出事故 |
| 变量名随便起（如 a1、tmp） | 变量名要有语义（host、port、apiPrefix），否则脚本无法维护 |

【我的理解】
> 引导思考题1：哪些信息应该放进"用户定义的变量"，哪些不该？请各举 3 例并说明理由。
>
> 引导思考题2：为什么"把 500 个账号写进用户定义的变量"无法实现"每个虚拟用户不同账号"？正确的做法方向是什么？

### 知识点4：第三部分设置①——独立运行每个线程组

【课程原话/定义】
**第三部分：对测试计划的设置**，从上到下的设置为：
**独立运行每个线程组**
- **不勾选**：各个线程组**并行、随机执行**
- **勾选**：线程组**按照前后顺序来执行**

【为什么？】
这个开关决定的是"**多个线程组之间的关系**"，而它直接影响压测的两种根本场景：

- **不勾选（并行）** = 多个线程组**同时加压**。适合"混合场景"：比如 70% 用户在浏览、20% 在加购、10% 在下单——你想让这些行为**同时发生**，逼近真实流量构成。
- **勾选（顺序）** = 线程组**一个接一个执行**。适合"分阶段场景"：比如先跑 5 分钟基准、再跑 10 分钟负载、最后跑 30 分钟稳定性——你需要它们**不能重叠**，否则指标会互相污染，你根本分不清某个时间点的 RT 是谁造成的。

要注意课程用词里的"随机执行"：并行时 JMeter 让各线程组同时启动，调度由线程与操作系统决定，**执行交错的顺序不可控**。这意味着**并行模式下你无法为某个线程组断言"它一定在另一个之前完成"**——如果你有"必须先登录再压业务"这类依赖，就不要指望并行，应该用 setUp 线程组（见 [[Ch15-线程组]]）或勾选顺序执行。

**【扩展知识】**：这也是"混合场景"压测的技术实现方式——把不同业务的比例做成不同权重的线程组，并行加压，从而让服务端承受接近真实的混合流量。

【必须掌握】

| 设置 | 行为 | 适用场景 | 代价 |
|------|------|----------|------|
| 不勾选 | 各线程组并行、交错执行 | 混合场景（多业务同时发生） | 时间线不可控，指标需分线程组看 |
| 勾选 | 线程组按树的先后顺序依次执行 | 分阶段场景（基准→负载→稳定性） | 总时长变长，无法模拟混合流量 |
| 关联元件 | setUp / tearDown 线程组 | 前后置准备与清理 | 见 Ch14 |

【企业场景】
你要压"大促首页混合流量"：浏览商详 60%、搜索 30%、加购 10%。做法是建三个线程组，分别设置并发数与循环次数体现比例，然后**不勾选**"独立运行每个线程组"，让它们并行加压——这样得到的 RT/TPS 才是混合流量下的真实表现。反过来，如果 Leader 要你"先压 500 并发 5 分钟，再压 1000 并发 10 分钟，最后跑 2 小时稳定性"，你就**必须勾选**它，让三档依次执行，否则三档叠在一起，你交不出干净的"每档指标"。

【面试考察】
面试官："如何设计混合场景？多线程组并行还是顺序执行？"

参考回答框架：
1. 并行（不勾选）：用于混合场景，多个业务线程组同时加压，通过线程组数量/并发/循环体现业务比例
2. 顺序（勾选）：用于分阶段场景，基准、负载、稳定性各阶段依次执行，保证每阶段指标干净
3. 判断依据：业务在真实世界是否同时发生（同时→并行；阶段递进→顺序）
4. 注意：并行时执行交错不可控，有先后依赖的操作要用 setUp/tearDown 或顺序执行来保证

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 做混合比例场景时勾选了顺序执行 | 混合场景需要同时发生，应不勾选（并行），否则比例失真 |
| 做分阶段加压时不勾选 | 阶段会重叠，各档指标互相污染，拿不出干净的阶段数据 |
| 认为并行时能控制线程组谁先谁后 | 并行执行交错不可控；需要前后依赖时用 setUp 线程组或顺序模式 |
| 把"线程组顺序"理解为"树里位置决定先后" | 并行模式下位置不代表先后；顺序模式才按顺序执行 |

【我的理解】
> 引导思考题1：请各举一个必须并行、一个必须顺序的真实压测场景，并说明理由。
>
> 引导思考题2：如果业务要求"必须先登录成功，再开始压下单"，而你又需要下单与浏览并行，你会怎么组合设置？（提示：Ch14 的 setUp 线程组）

### 知识点5：第三部分设置②——主线程组运行完成后运行 tearDown 线程组

【课程原话/定义】
**主线程组运行完成之后运行 tearDown 线程组。**

【为什么？】
这是一个"**收尾开关**"：它规定 tearDown Thread Group（拆卸线程组）在什么时机执行。

- **压测不只是"加压"，还要"恢复现场"**：压测过程会造数据（注册的账号、下单的订单、领的券、上传的文件）。如果不清理，下一轮压测就跑在"脏数据"上——数据量越滚越大，正确性会被影响，性能结果也不可比。
- **tearDown 的意义就是"在正确的时机做清理"**：只有当主线程组（真正加压的那些线程组）跑完了，清理才有意义。如果清理与加压同时发生（并行），会出现"边压边删"的情况——**你的清理动作本身会变成被测系统的一部分，污染压测结果**，甚至把正在被读取的数据删掉，导致断言失败。
- 这个开关与"独立运行每个线程组"是一对：**"独立运行"管的是主线程组之间的先后，tearDown 开关管的是主线程组与 tearDown 组之间的先后。**

**【扩展知识】**：JMeter 中与之配套的还有 setUp Thread Group（主测试前执行初始化）。三者关系是：
`setUp Thread Group → Thread Group（主加压）→ tearDown Thread Group`。
课程在这一页只讲了 tearDown 的开关，完整的执行顺序在 [[Ch15-线程组]] 里给出："执行顺序与它们在测试计划中的位置顺序无关"。

【必须掌握】

| 设置 | 含义 | 使用时机 |
|------|------|----------|
| 勾选 | 主线程组跑完后，再执行 tearDown 线程组 | 需要在压测结束后清理数据/关闭资源 |
| 不勾选 | tearDown 不会被安排在主线程组之后执行（不会形成"压完再清理"的顺序） | 只做纯加压、无需收尾的临时脚本 |
| 配套元件 | tearDown Thread Group | 关闭资源、清理数据、还原配置 |
| 上游环节 | setUp Thread Group（前置准备） | 造数、登录、准备环境（见 Ch14） |

【企业场景】
你压"注册"链路时往往需要**前置造数 + 后置清理**：setUp 线程组准备手机号段/初始数据；主线程组压注册；tearDown 线程组把这一轮注册出来的测试账号批量注销或标记（避免污染线上/预发的账号库）。如果清理与加压同时跑，会出现"刚注册的账号被清理脚本删除，导致后面的断言随机失败"——**压测失败率飙升，但你找不到被测系统的毛病，因为是你自己造成的。** 所以企业脚本里，只要有造数/写操作的场景，几乎都会配 tearDown 并把它的执行时机管好。

【面试考察】
面试官："压测脚本为什么要做前置和后置？JMeter 里怎么保证后置在压测之后执行？"

参考回答框架：
1. 必要性：前置准备环境与数据，后置清理数据、关闭资源，保证压测可重复、结果可比
2. 元件：JMeter 用 setUp Thread Group 做前置、tearDown Thread Group 做后置
3. 时机控制：通过"主线程组运行完成后运行 tearDown 线程组"这个测试计划设置，保证后置在主加压之后执行
4. 反面：若后置与加压并行，清理动作会成为额外负载并污染结果，甚至造成误判

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 只加压不清理，反复压同一环境 | 脏数据累积会让结果不可比，甚至让后续压测直接失败 |
| 让清理与加压同时发生 | 清理会成为额外负载/误删数据，污染结果；应保证主线程组跑完再后置 |
| 把"造数"写在主线程组里的取样器上 | 造数属于前置准备，应放 setUp 线程组，避免污染加压指标 |
| 认为 tearDown 是"必须的" | 无写操作的纯只读场景可以不配；有写数据的场景则应配置并管好时机 |

【我的理解】
> 引导思考题1：为什么"压测之后的清理"不能和"压测"同时进行？请从"结果污染"和"数据正确性"两个角度说明。
>
> 引导思考题2：请为一条"领券"压测链路列出你需要的前置动作和后置动作各 2 项。

### 知识点6：第三部分设置③——函数测试模式

【课程原话/定义】
**函数测试模式**，比如保存响应数据或者样本数据，**需要注意的是选择该功能非常占用磁盘空间**。

【为什么？】
"函数测试模式"（Functional Test Mode）的机制是：**让 JMeter 把每个取样器的响应数据（以及相关样本数据）都保存/记录下来**。

- **它解决的问题**：调试脚本时你需要看"服务器到底回了什么"（例如登录接口返回的 JSON 里有哪些字段、有没有报错信息）。这个模式就是为**调试**而生的。
- **它的代价**：课程原文已经点明——**非常占用磁盘空间**。因为每个请求的完整响应体都会被记录；500 并发跑 1 小时产生的数据量是巨大的。
- **更本质的代价（课程未展开）**：记录响应数据需要 CPU 与内存参与，**压测机的资源被消耗**，而压测机一旦成为瓶颈，你得到的 RT/TPS 就失真了。所以这个模式的正确用法是：**调试阶段开、正式压测关**——和 "GUI 调脚本、CLI 跑压测" 是同一条纪律的两种体现。

**【扩展知识】**：企业里更常见的调试替代做法是：正式压测时只保留必要的监听器（如聚合报告/后端监听器），把需要的少量响应信息通过**断言**和**日志**来判定，避免全量响应落盘。

【必须掌握】

| 项目 | 说明 |
|------|------|
| 作用 | 保存响应数据/样本数据，用于调试与结果分析 |
| 代价 | 非常占用磁盘空间（课程原文），并额外消耗压测机 CPU/内存 |
| 正确用法 | 调试阶段开启；正式压测关闭 |
| 替代方案 | 用断言校验结果、只保留轻量监听器，避免全量落盘 |
| 判断标准 | "我需要看响应内容吗？" 需要→调试模式；只关心指标→关闭 |

【企业场景】
你调一个新录的脚本，登录总是失败但看不出原因。这时你会**临时**打开函数测试模式（或用 View Results Tree 逐条看响应），发现服务器返回的是"验证码错误"——于是你知道要处理验证码/关联参数。调通之后，**你务必把它关掉**再跑正式压测，并且把监听器精简掉。为什么必须强调这个动作？因为新人最常见的翻车是"带着调试配置去跑 2 小时稳定性"——结果磁盘被写满、JMeter 崩掉、压测机 CPU 被自身日志吃掉，**整轮压测白跑**。

【面试考察】
面试官："什么情况下会开启函数测试模式？开启后要注意什么？"

参考回答框架：
1. 用途：调试脚本阶段需要查看每个请求的响应内容/样本数据时启用
2. 代价：非常占用磁盘空间，并额外消耗压测机资源，可能影响指标真实性
3. 纪律：调试开、正式压测关；正式压测只保留必要监听器并精简结果输出
4. 替代：用断言判定响应正确性，用轻量监听器（聚合报告/后端监听器）汇总指标

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 带着函数测试模式跑正式压测 | 会大量写磁盘并消耗压测机资源，可能写满磁盘或让结果失真 |
| 认为"多记数据总没坏处" | 压测机是瓶颈就等同于结论失真，多余记录只有代价没有收益 |
| 调试完不改回来 | 应建立"调试配置不许进正式压测"的检查习惯 |
| 用全量响应落盘代替断言 | 结果正确性应由断言保证，而非事后翻日志 |

【我的理解】
> 引导思考题1：函数测试模式为什么会"非常占用磁盘空间"？请从"每个请求都记什么"来解释。
>
> 引导思考题2：除了磁盘，开启它还会通过哪条路径影响压测结论？请把它和"加压机不能成为瓶颈"这条纪律联系起来。

### 知识点7：第三部分设置④——添加文件或者 jar 包

【课程原话/定义】
**添加文件或者 jar 包，常用于外部功能调用。**

【为什么？】
JMeter 的定位是"压测引擎"而不是"万能语言"，当压测需要**自定义逻辑**时，官方给的两条路是：**函数/插件** 或 **jar 包扩展**。

- **jar 包扩展解决的是什么问题？** 典型有三类：
  1. **自定义取样器/协议**：被测系统用私有协议（公司自研 RPC），官方取样器压不了，需要自研取样器 jar。
  2. **自定义函数/工具类**：脚本里要做的加解密、签名计算、特殊格式转换，JMeter 内置函数不够用，就把公司现成的 Java 工具类打进 jar 引用。
  3. **自定义监听器/断言**：需要把结果推送到公司自己的性能平台，或按公司规范输出。
- **"添加到 classpath" 的含义**：测试计划里添加的目录/jar 会被加入 JMeter 的类加载路径，于是脚本（例如 Beanshell 脚本、JSR223 脚本）里就能 `import` 并使用这些类。这就是"常用于外部功能调用"的技术含义。

**【扩展知识】**：这条路正是课程后面 **L3「JMeter 分布式与 Beanshell」和 L5「JMeter 二次开发」** 的入口——从"用别人的 jar"到"自己写取样器/插件"是测开与普通测试的分界线。此外，正式企业实践中，jar 包通常放在 `lib/ext` 目录或用插件管理器安装，而不是每次都手动加到测试计划里；测试计划级的添加更适合"单个脚本临时依赖"。

【必须掌握】

| 用途 | 场景 | 实现方式 |
|------|------|----------|
| 自定义协议取样器 | 私有 RPC / 特殊协议压测 | 自研取样器 jar |
| 外部功能调用 | 加解密、签名、特殊格式计算 | 引入公司工具类 jar，脚本中调用 |
| 自定义函数/断言/监听器 | 满足公司规范或对接自研性能平台 | jar 扩展 |
| 添加位置 | 测试计划 → 添加文件或 jar 包（加入 classpath） | 也可放 `lib/ext`（全局） |
| 能力进阶 | Beanshell/JSR223 调用 → 自研插件 | 见 L3 / L5 |

【企业场景】
你压一个公司自研网关的接口，接口参数需要**私钥签名**（HMAC + 时间戳），而 JMeter 内置函数算不出这种签名。你的做法是：让开发同学提供一个签名工具类（或你按文档自己实现），打成 jar → 加到测试计划（或放进 `lib/ext`）→ 用 JSR223/Beanshell 预处理脚本调用它生成签名 → 把结果传给请求参数。**这就是"测试开发"和"只会用工具"的分水岭**：遇到工具做不到的事，能自己扩出来。同一套能力在 L5 会升级为"写自己的取样器/插件"。

【面试考察】
面试官："JMeter 内置功能不够用怎么办？"

参考回答框架：
1. 分层解决：先用内置函数/插件；不够再引入 jar（外部功能调用）；再不够就自研取样器/插件
2. 常见需求：加解密与签名、私有协议加压、对接公司自研平台
3. 用法：把 jar/目录加入测试计划（classpath），或用插件管理器/`lib/ext` 全局引入，脚本中调用
4. 进阶：Beanshell/JSR223 脚本开发 → 自定义元件开发，这是 JMeter 二次开发的方向

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 遇到内置做不了的功能就放弃或"手工造数据" | JMeter 支持 jar 扩展与二次开发，应走"引入 jar / 自研元件"路线 |
| 把 jar 加在任意位置就以为全局生效 | 测试计划级添加只对该脚本生效；全局生效通常放 `lib/ext` 或用插件管理器 |
| 加 jar 后没重启 JMeter | 类加载路径变化常需要重启 JMeter 才生效（工程实践中的常见坑） |
| 把业务签名逻辑写在取样器里硬编码 | 应封装为可复用工具类/jar，保证与开发实现一致且可维护 |

【我的理解】
> 引导思考题1："添加文件或者 jar 包"解决的是一类什么问题？请举一个压测中必须靠它解决的问题。
>
> 引导思考题2：为什么课程把它写进"测试计划设置"这一层，而不是写在线程组里？这与"作用域"有什么关系？

### 知识点8：辨析——JMeter 的"测试计划" ≠ 性能测试计划（文档）

【课程原话/定义】
本章课程原文只给出两条总结：**什么是测试计划**、**测试计划的组件内容**。

【扩展知识】
这是本课程里唯一一个**同名不同物**的概念，必须分清，否则面试回答会张冠李戴：

| 概念 | 出处 | 是什么 | 产物形态 |
|------|------|--------|----------|
| **JMeter 测试计划（Test Plan）** | 本章 | 一个压测脚本的容器与运行单元 | `.jmx` 脚本文件 |
| **性能测试计划（文档）** | [[../L1-性能测试体系/Ch08-性能测试计划\|L1 Ch08-性能测试计划]] | 项目级压测方案：需求分析、环境、数据、指标预期、工具脚本、执行监控、报告 | Word/在线文档 |

两者关系是 **"文档指导脚本"**：性能测试计划文档里规定的"压测对象、场景、并发数、指标预期、执行策略"，最终都要落成 JMeter 的测试计划（脚本）。所以正确的链路是：**性能测试计划（文档，L1 Ch08）→ 场景设计（L1 Ch10）→ JMeter 测试计划（脚本，本章）→ 执行与报告（L1 Ch09）**。

【为什么？】
为什么会混淆？因为中文都叫"测试计划"。规避方法很简单：**说 JMeter 时带英文名 `Test Plan`（脚本/容器），说项目交付物时说"性能测试方案/计划文档"**。面试时如果面试官问"测试计划怎么写"，你要先反问/确认是哪一层——**这个辨析本身就是专业度的体现**。

【必须掌握】

| 区分维度 | JMeter Test Plan | 性能测试计划文档 |
|----------|------------------|------------------|
| 层面 | 脚本/工具层 | 项目/管理交付层 |
| 内容 | 变量、线程组、元件、设置开关 | 目标、环境、数据、指标、策略、风险 |
| 谁写 | 压测执行人（测试开发/性能测试） | 性能测试负责人，需评审 |
| 交付给谁 | 执行者、CI 流水线 | 项目组、Leader、业务方 |
| 先后关系 | 后者指导前者 | 前者是后者的落地 |

【企业场景】
你在周会上说"测试计划已经写好了"，如果指的是 `.jmx` 脚本，Leader 会以为你已经把方案文档写完了——**这种表述歧义在跨团队沟通里会直接造成误解**。规范说法是："性能测试方案（文档）已评审通过，对应的 JMeter 测试计划（脚本）已调试完成，可以开始执行。"这一句话同时交代了两个层面，也顺带证明你懂整条链路。

【面试考察】
面试官："你说的测试计划是指文档还是脚本？"

参考回答框架：
1. 明确区分：JMeter 的 Test Plan 是脚本容器（`.jmx`）；性能测试计划是项目级方案文档
2. 关系：文档规定目标/场景/指标/策略，脚本是它的技术落地
3. 流程串联：需求分析 → 性能测试计划（文档）→ 场景设计 → JMeter 测试计划（脚本）→ 执行监控 → 报告
4. 表达规范：沟通时带上层面（"方案文档"/"脚本"），避免歧义

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 把 JMeter 的 Test Plan 当成"压测方案文档" | 它只是脚本容器；方案文档是 L1 Ch08 那类项目交付物 |
| 面试说"测试计划里写了指标预期" | 指标预期属于方案文档；JMeter 测试计划里是变量与元件 |
| 认为写了脚本就等于把方案做完了 | 脚本是落地；目标、环境、数据、指标、风险仍需方案文档覆盖 |
| 沟通时省略层面限定 | 必须说清"方案文档"还是"JMeter 脚本"，否则团队理解不一致 |

【我的理解】
> 引导思考题1：请用一句话分别定义"JMeter 测试计划"和"性能测试计划文档"，并说明谁指导谁。
>
> 引导思考题2：如果面试官问"你的测试计划里包含哪些内容"，你会怎么先确认他问的是哪一层？两种答案分别怎么答？
