### 知识点1：配置元件（Configuration Elements）是什么，能干什么

【课程原话/定义】
在 JMeter 中，配置元件（Configuration Elements）用于管理和设置测试计划的配置信息。它们可以帮助配置参数、变量、请求头信息等，并在整个测试计划中共享这些配置信息。

JMeter 常用配置元件（课程原文列举四个）：
- **HTTP Header Manager（HTTP 头管理器）**：用于设置 HTTP 请求的头部信息，例如 `User-Agent`、`Content-Type` 等。通过设置头部信息，可以模拟具有不同头部信息的请求，并更好地测试服务器的响应。
- **HTTP Cookie Manager（HTTP Cookie 管理器）**：用于管理 HTTP 请求中的 Cookie 信息，以便维护会话状态。保持正确的会话状态对于模拟真实用户的行为至关重要；启用后 JMeter 可以自动处理来自服务器的 Cookie，并在后续请求中使用相同的 Cookie 信息，确保会话一致性。
- **HTTP Cache Manager（HTTP 缓存管理器）**：帮助管理 HTTP 请求的缓存信息，以模拟浏览器缓存行为。通过配置可以控制是否启用缓存以及设置缓存的具体属性，以确保测试中的请求响应符合预期。
- **CSV Data Set Config（CSV 数据集配置元件）**：用于从 CSV 文件中读取数据，并将数据应用到测试中的请求中；在配置时可以指定文件路径、字段分隔符、循环次数等参数，以便动态地为测试请求提供不同的数据。

【为什么？】
配置元件的本质是**"给作用域内的取样器统一补默认值"**。它解决三个真实痛点：
1. **重复配置的爆炸**：100 个请求都要带 `token`、`Content-Type`，一个个写进 HTTP Request 会不可维护；配置元件放一次，作用域内全部生效。
2. **会话状态的模拟**：压测要模拟"同一个用户连续操作"，就必须让 Cookie 在多个请求间自动传递；Cookie Manager 是让 RT 曲线变真实的关键之一（不带 Cookie 的链路根本没有登录态，压出来的缓存命中率、数据库压力全都是错的）。
3. **数据参数化**：同一接口用不同账号/不同商品发压，才不会被风控或缓存"放大"成假数据，CSV Data Set Config 承担这件事（[[Ch25-JMeter执行顺序|参数化的完整展开在 L2 后续章节]]——本章只需知道它属于配置元件）。

注意这里有个重要分野：**缓存管理器与 Cookie 管理器影响的是"请求行为"，不是"请求内容"**。它们会改变服务端承受的负载性质（命中缓存的请求根本不落到后端），所以压测时"要不要勾缓存"直接决定你的结论是"压后端"还是"压 CDN"。

【必须掌握】

| 配置元件 | 管什么 | 影响面 | 压测里的必要性 |
|----------|--------|--------|----------------|
| HTTP Header Manager | 请求头（User-Agent、Content-Type、Accept、Token…） | 影响服务端识别、鉴权、内容协商 | 必配（至少 Content-Type 与鉴权头） |
| HTTP Cookie Manager | Cookie 的接收、保存、自动带出 | 决定会话是否连续 | 有登录态的链路必配 |
| HTTP Cache Manager | 请求缓存（模拟浏览器缓存行为） | 影响是否真正打到后端 | 压"后端能力"时通常**不勾**（【扩展知识】） |
| CSV Data Set Config | 从文件读数据 → 变量 | 决定参数化的数据来源 | 多用户/多数据场景必配 |

【企业场景】
你接手一条"登录 → 查询 → 下单"的压测链路。第一步不是加线程数，而是把配置元件配齐：线程组下放一个 HTTP Header Manager（统一 `Content-Type: application/json` + 鉴权头 `token: ${token}`）、一个 HTTP Cookie Manager（保存登录返回的会话 Cookie）、一个 CSV Data Set Config（1000 行 用户名/密码，避免所有线程用同一个账号被风控拦截）。**这三件套没配好，压测数据一定是假的**：Cookie 不共享时每个请求都是"新会话"，服务端会创建海量临时会话，压出来的是"会话创建能力"而不是"业务能力"。

【面试考察】
面试官："JMeter 的配置元件是干什么的？你常用的有哪几个？"

参考回答框架：
1. 定义：管理和设置测试计划的配置信息（参数、变量、请求头等），在作用域内共享
2. 常用四个：HTTP Header Manager（请求头）、HTTP Cookie Manager（会话）、HTTP Cache Manager（缓存行为）、CSV Data Set Config（参数化数据）
3. 价值：把"每个请求都要写一遍"的东西集中一处，保证链路可维护、可复现
4. 提醒：Cookie/Cache 管理器会改变真实负载性质，压后端能力时要想清楚是否启用缓存

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 把配置元件当成"只执行一次的初始化代码" | 它在**所在作用域的每个取样器执行前**都会被处理一次（原文与官方文档均如此），不是启动时跑一遍就完了 |
| 认为不勾 Cookie Manager 也能维持会话 | 不启用时 JMeter 不做 Cookie 管理，请求间不自动带 Cookie，多请求链路会退化成"每次都是新用户" |
| 压后端却勾了 HTTP Cache Manager | 缓存命中会让请求不落到后端，压出来的 TPS 不是服务端能力（【扩展知识】） |
| 全部配置写在一个 HTTP Request 里 | 换域名/换环境时改 100 处；配置元件才是集中管理点 |
| 以为配置元件只对"同级的下方请求"生效 | 作用域按层级，不按上下位置（见知识点6） |

【我的理解】引导题（用自己的话回答）：
1. 如果不配 HTTP Cookie Manager，一条"登录 → 下单"的链路在 JMeter 里会发生什么？为什么这会让压测结论失真？
2. 请用一句话说清"配置元件"和"取样器"的分工。

### 知识点2：HTTP Cache Manager（HTTP 缓存管理器）

【课程原话/定义】
HTTP Cache Manager 帮助管理 HTTP 请求的缓存信息，以模拟浏览器缓存行为。在一些测试场景中，缓存可以显著提高性能并减少服务器负载，因此正确地管理缓存信息很重要。通过配置 HTTP Cache Manager，可以控制是否启用缓存以及设置缓存的具体属性，以确保测试中的请求响应符合预期。

【为什么？】
HTTP 缓存的核心是**用响应头（`Cache-Control`、`Expires`、`ETag`、`Last-Modified`）决定"这次请求要不要真的打到服务端"**。启用缓存管理器后，JMeter 会像浏览器一样：命中新鲜缓存就不发请求（只计一次缓存命中）；拿条件请求（`If-None-Match` / `If-Modified-Since`）去问服务端，服务端回 304 时也只算轻量响应。**这会直接改变你压到的对象**：
- 压"后端服务能力"→ 通常不启用缓存，让每个请求都打到后端，测的是最坏情况的能力；
- 压"用户真实体验（含 CDN/浏览器缓存）"→ 启用缓存，测的是真实用户感知；
- 压"缓存命中后的服务端压力"→ 启用并确认缓存头正确，测的是 CDN/网关承载。

所以课程说"缓存可以显著提高性能并减少服务器负载"——这句话同时是**性能优化的手段**和**压测结论失真的来源**，取决于你想测什么。

【必须掌握】

| 关注点 | 说明 |
|--------|------|
| 是否启用 | 通过是否添加 HTTP Cache Manager 来控制（不添加 = 不模拟缓存行为） |
| 典型影响 | 命中缓存时不发请求（RT 统计与请求数统计都会变"好看"） |
| 适用场景 | 验证缓存策略是否生效、模拟真实浏览器行为、压 CDN/网关层 |
| 不适用场景 | 压后端接口的服务端处理能力（需要最坏情况数据） |
| 与 Cookie 的区别 | Cookie 管会话状态；缓存管"要不要发这个请求、发条件请求还是完整请求" |
| 验证手段 | 看 View Results Tree 里是否出现 304 / 是否真的发出请求（【扩展知识】） |

【企业场景】
大促前你要回答"后端服务能扛多少并发下单"。这时脚本里**不能**放 HTTP Cache Manager，也不能放大量静态资源请求——因为下单接口本身不该被缓存，带上缓存管理器只会让部分请求"没打到后端就结束"，把服务端能力估高。反过来，你要回答"首页在真实用户侧打开有多快"时，就要把 Cache Manager 打开（并保留静态资源请求），否则你压出来的是"每次都回源的极端情况"，与线上真实感受不符。**同一份脚本，两次结论可以差好几倍，差异就来自这一个配置元件。**

【面试考察】
面试官："压测时缓存要不要开？什么时候开？"

参考回答框架：
1. 先明确压测目标：压后端服务能力 vs 模拟真实用户体验，两者的缓存策略相反
2. 压后端能力：不启用缓存管理器（让请求完整打到后端），并避免把静态资源算进核心接口指标
3. 模拟真实用户：启用 HTTP Cache Manager，同时保留 Cookie Manager，让链路最接近浏览器
4. 结论落地：报告里必须写明"本次结果是否包含缓存影响"，否则数字无法被复用和对比

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 无脑启用缓存管理器"让它更快" | 缓存会让请求不到后端，压出来的不是服务端能力（【扩展知识】） |
| 把缓存管理器和 Cookie 管理器混为一谈 | 一个管请求是否发出/条件请求，一个管会话状态，职责不同 |
| 报告里不说明缓存策略 | 不写缓存策略等于数字不可复现；跨版本对比时结论会被推翻 |
| 同时手动加 `If-Modified-Since` 又开缓存管理器 | 两手都做会导致请求头混乱，选一种方式（建议交给管理器）（【扩展知识】） |

【我的理解】引导题（用自己的话回答）：
1. 为什么"开了缓存管理器"会让压测报告的 TPS 变高、但**不能**用来回答"服务端能扛多少并发"？
2. 如果你要验证"服务端缓存策略是否生效"，你会怎么观察（提示：304 状态码、请求数与命中数）？

### 知识点3：CSV Data Set Config（CSV 数据集配置元件）

【课程原话/定义】
CSV Data Set Config 用于从 CSV 文件中读取数据，并将数据应用到测试中的请求中。通过使用 CSV 文件，可以轻松管理和引用大量数据，例如用户凭证、产品信息等。在配置 CSV Data Set Config 时，可以指定文件路径、字段分隔符、循环次数等参数，以便动态地为测试请求提供不同的数据。

【为什么？】
性能测试的"用户"必须是**不同的用户**，否则会出现三类失真：
1. **风控/限流**：同一账号高频请求会触发限流，你压到的是限流器而不是业务；
2. **缓存放大**：同一用户查同一数据，命中用户级缓存，服务端压力被低估；
3. **状态冲突**：同一账号并发下单会出现"库存/余额互相抢占"这类非真实竞争。

CSV 数据集的价值就是**把"数据"从脚本里剥离出来**：脚本描述业务逻辑，数据文件描述用户与业务数据；换环境换数据只改文件，脚本不动。它属于配置元件，所以同样遵守"作用域内共享 + 取样器之前生效"的规则。

【必须掌握】

| 项目 | 说明 |
|------|------|
| 数据来源 | 一个 CSV 文件（列 = 变量，行 = 每条数据） |
| 取值方式 | 每个线程在每轮迭代开始取一行；变量名在脚本里用 `${变量名}` 引用 |
| 行数 vs 线程数 | 行数少于线程数时会出现复用/循环行为，必须提前规划数据量（【扩展知识】：可通过"循环/是否到文件末尾后停止"等设置控制） |
| 编码 | 中文数据用 UTF-8 保存，否则读出乱码（【扩展知识】） |
| 与 Header 变量配合 | CSV 变量可直接用于 HTTP Header Manager（如 `${token}`、`${username}`） |
| 文件路径 | 建议用相对测试计划路径（如 `userdata.csv`），换机器不用改绝对路径（【扩展知识】） |

【企业场景】
你要压"下单"链路，需要 2000 个真实可用的测试账号。做法：把 2000 行 `username,password,sku` 存成 `users.csv`，线程组下挂 CSV Data Set Config 指到该文件，HTTP Request 里用 `${username}` / `${password}` / `${sku}`，Header Manager 里用 `${token}`（token 由登录请求配合后置处理器提取）。**这样才能做到"2000 线程 = 2000 个不同用户"**。如果不做参数化，2000 线程共用 1 个账号，服务端风控会在第几秒开始拦截，你的报告就会显示"错误率飙升"——那是你的脚本问题，不是系统问题。

【面试考察】
面试官："JMeter 参数化怎么做？为什么要参数化？"

参考回答框架：
1. 为什么：避免风控/缓存/状态冲突造成的数据失真，"并发用户数"必须对应"真实不同的用户"
2. 手段：CSV Data Set Config 是最常用的配置元件（文件列 → 变量 → 脚本里 `${}` 引用）；也可用用户定义的变量、函数（如 `${__Random}`）
3. 配套：数据量要 ≥ 线程数 × 迭代数，否则数据被复用；中文注意编码
4. 验证：用 Debug Sampler + View Results Tree 确认每次请求取到的是不同的值

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 数据行数少于线程数 × 迭代数 | 会造成数据复用，风控/缓存问题重现；数据量要提前规划（【扩展知识】） |
| CSV 存成 GBK/Excel 默认编码 | 中文读出来乱码或字面问号，中文数据统一 UTF-8 |
| 用绝对路径 | 换机器/换人执行就找不到文件；用相对测试计划的路径 |
| 在 CSV 里放带分隔符的内容却不加引号 | 分隔符会截断字段，需要按 CSV 规范用双引号包裹（【扩展知识】） |
| 认为 CSV 变量在所有位置都能用 | 变量在迭代开始时定义，个别"配置期就取值"的元件里可能取不到（如部分 JDBC 配置）；HTTP 头/请求参数是安全的 |
| 想用 CSV 却把它放到线程组之外 | 作用域不对会导致取不到或行为不符预期，见知识点6 |

【我的理解】引导题（用自己的话回答）：
1. 为什么"不做参数化"的压测报告在企业里几乎不会被采信？请从风控、缓存、状态冲突三个角度各说一句。
2. 你现在要压一个需要 500 个并发用户的登录链路，CSV 要准备多少行？为什么？

### 知识点4：配置元件的作用范围（最重要的结论）

【课程原话/定义】
课程以 HTTP Header Manager 为例讲解配置元件的作用范围，实验过程如下：
1. 先创建一个线程组，在线程组中创建两个采样器，都是访问百度首页的请求，然后在线程组中添加名为 HTTP Header Manager 的配置元件，最后添加查看结果树。配置元件中做相应配置。
2. **HTTP Header Manager 与 HTTP Request 同级上方时**：点击运行，可以看到**请求 1 与请求 2 的请求头中都包含** HTTP Header Manager 中添加的参数。
3. **HTTP Header Manager 调整到 HTTP Request 2 的目录下**（即成为请求 2 的子节点）时：点击运行，可以看到**只有请求 2 的请求头中包含参数**。

结论（课程原文）：**配置元件的作用范围通常是在与之平级的 HTTP Request 以内的，即配置元件中设置的值将应用到其所在的目录下。**

【为什么？】
JMeter 的测试计划是一棵树，元件的生效范围由**它在树中的位置（层级/缩进）**决定，不是由"它写在上面还是下面"决定：
1. 元件的**子树**（它自己所在层级之下、包含同级后续节点）构成它的作用域；
2. 元件挂在线程组这一层 → 线程组内**所有**取样器都受它影响（案例第 2 步）；
3. 元件挂在某个 HTTP Request 之下（作为它的子节点）→ 只有那个取样器受影响（案例第 3 步），因为作用域被"收窄"到了这个请求。

对照一下子树与作用域的关系会更清楚：

| 元件位置 | 影响的取样器 | 典型用途 |
|----------|--------------|----------|
| 测试计划（Test Plan）级 | 所有线程组的所有取样器 | 全局通用的头、全局 Cookie 管理 |
| 线程组级 | 该线程组内所有取样器 | 一套业务链路的公共头/Cookie |
| 某个 HTTP Request 之下 | 仅该请求（及其子节点） | 只有这个接口需要的特殊头 |

这也是为什么"作用范围随位置变化"——它不是要你背一条规则，而是理解了树结构就自然成立。

【必须掌握】

| 你想要的生效范围 | 元件应该放在哪 |
|------------------|----------------|
| 整个测试计划所有请求 | Test Plan 下（顶层） |
| 某个线程组内所有请求 | 该线程组下（与请求同级） |
| 只有一个请求 | 作为该请求的子节点（挂在请求下面） |
| 只对某个业务片段生效 | 放进事务控制器/Simple Controller 下（同一层级思路）（【扩展知识】） |
| 组件"收窄"后的排错 | 现象是"只有部分请求带上了头" → 先检查该元件在树里的层级 |

【企业场景】
你在维护一个三线程组的压测计划（登录组、查询组、下单组），三段链路的请求头不同：登录要 `Content-Type: application/json`，下单要多一个 `X-Channel: app`。企业做法是：公共头放 Test Plan 级（全局），`X-Channel` 只在"下单组"线程组下加一个 HTTP Header Manager，或者干脆挂到下单请求下面。**这样任何一个新同事改完脚本，跑一次就能用 View Results Tree 逐请求验证——因为"只有该组的请求带上了 X-Channel"这件事，是层级决定的、可预期的。** 反过来，如果把特殊头挂错层级，现象是"线上灰度路由失效，压到的服务不一样"，排查成本极高。

【面试考察】
面试官："JMeter 里配置元件怎么控制生效范围？举个你调过的坑。"

参考回答框架：
1. 作用域由**层级**决定：元件的子树（同级及同级下方延伸的节点）就是它的作用范围
2. 三层心智模型：Test Plan 级 = 全局；线程组级 = 组内全部请求；请求之下 = 仅该请求
3. 现象化验证：同级上方 → 两个请求都带；收窄到请求 2 之下 → 只有请求 2 带（课程案例）
4. 踩坑实例：公共头放在某个请求下，导致其他请求不带鉴权头，错误率高但看不出报错原因（HTTP 200 + 未登录提示）

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 认为"挂在同级下方就不生效" | 生效与否由**层级**决定，跟它在同级里的上下位置无关（下一条知识点会解释为什么下方的也会生效） |
| 把公共头挂在最后一个请求下面 | 作用域被收窄，其他请求立刻失去该头；这类错误常表现为大量"HTTP 200 但业务失败" |
| 用"复制一份配置到每个请求"解决作用域问题 | 失去集中管理的好处，改一次要改 N 处；用层级与变量管理 |
| 只看配置界面就断言"头已生效" | 必须用 View Results Tree 的 Request 面板/Cookie Data 验证真实发出的请求 |
| 在非 HTTP 取样器上期待 HTTP 配置元件生效 | HTTP Header/Cookie/Cache Manager 只对 HTTP 系取样器有意义（【扩展知识】） |

【我的理解】引导题（用自己的话回答）：
1. 用"树"的模型解释：HTTP Header Manager 挂在线程组下 和 挂在请求 2 之下，为什么影响的请求数量不同？
2. 你希望"只有下单接口带 `X-Channel` 头"，除了把 Header Manager 挂到下单请求下面，还有别的实现方式吗？

### 知识点5：配置元件的执行顺序（原文勘误与准确表述）

【课程原话/定义】
课程同样以 HTTP Header Manager 做实验：**将 HTTP Header Manager 调整到所有 HTTP 请求的同级目录下方**，点击运行，可以看到所有请求下都包含配置元件中的参数。

课程结论（原文）：**配置元件的执行顺序与它们在测试计划中的存放位置无关，通常在线程组之前执行。**

【为什么？】
这句话要用**机制**去理解，否则会被误用：
1. **"与存放位置无关"的真实含义**：配置元件属于"准备型"元件，JMeter 在**取样器执行之前**已经把当前作用域内的配置元件收集并合并到取样器上（官方文档的表述是：配置元件在其所在作用域的**开始处**被处理，即同一作用域内任何取样器之前）。所以放在同级的上方或下方**都生效**——这就是原文实验第 4 步"移到下方仍然所有请求都带"的原因。
2. **"通常在线程组之前执行"的准确说法**：不是"线程启动前跑一次就结束"，而是**每个取样器执行前都会重新收集一次作用域内的配置元件**。更准确的表述是"**配置元件在所有取样器之前生效**"。
3. **但顺序在两种情况下仍然重要**：
   - **同一层级、同一类型的多个元件**：日志与合并按**从上到下**的顺序处理；同名键（如两个 Header Manager 都定义 `X-Env`）会出现覆盖关系，具体以哪个为准受顺序影响，**工程上应避免同名冲突**（强建议：一个作用域只留一个同名配置元件）。
   - **元件之间有依赖时**（如 CSV 变量被 Header 引用）：先定义的变量、先读的数据才有值。

所以正确的完整表述是：**配置元件在其所在作用域内、所有取样器之前生效（这与它在同级中的上下位置无关）；同一层级内的元件则按从上到下的顺序被处理。**

【课程原文勘误】

| 课程原文表述 | 更准确的表述 |
|--------------|--------------|
| "配置元件的执行顺序与它们在测试计划中的存放位置无关，通常在线程组之前执行" | ① 它生效的时机是"所在作用域的开始处、任何取样器之前"（官方文档表述），所以放同级上方/下方都生效；② 同一层级内的元件仍按**从上到下**顺序处理；③ 不是"在线程组之前跑一次"，而是**每个取样器之前都会重新收集生效** |
| 实验结论"配置元件的作用范围通常是在与之平级的 HTTP Request 以内的" | 更准确：作用域 = 该元件的**子树**（它所在层级及其下方同级/子级节点）；"以内的"容易让人误以为"只往下不往同级"，实际是同级后续节点也包含在内 |

【必须掌握】

| 问题 | 准确答案 |
|------|----------|
| 配置元件什么时候生效？ | 在其作用域开始处、作用域内任何取样器之前生效 |
| 放在请求上方 vs 下方有区别吗？ | 对"是否生效"没有区别（课程实验已验证） |
| 同一层级多个元件怎么排？ | 从上到下依次处理（与 [[Ch25-JMeter执行顺序]] 的"相同元件从上到下"一致） |
| 有覆盖冲突怎么办？ | 避免同名：一个作用域只保留一个同类元件，用变量/CSV 做差异 |
| 与八大组件顺序的关系？ | 配置元件是执行链的第一环：配置元件 → 前置处理器 → 定时器 → 取样器 → 后置处理器 → 断言 → 监听器 |

【企业场景】
你接手一个"厂商交付"的压测脚本做评审，看到 HTTP Header Manager 被放在了最后一个请求的**下面**、CSV Data Set Config 放在线程组外面。按原文"与位置无关"的说法，前者"应该也能生效"——但你会**要求整改**：一是层级放错会让作用域收窄（这是作用域问题，不是顺序问题），二是同一个脚本里出现两个同名 Header Manager 时，谁覆盖谁只能靠猜。标准交付姿势是：公共配置集中在 Test Plan/线程组层，一个作用域只保留一份同类配置，用变量做差异化。这样任何人对脚本做一次 Review，都能在不运行的情况下预判生效范围。

【面试考察】
面试官："JMeter 配置元件的执行顺序是什么？放在请求下面还生效吗？"

参考回答框架：
1. 生效时机：在它所在作用域的开始处、任何取样器之前被处理（官方文档口径）
2. 位置敏感性：放在同级请求的上方或下方**都生效**（课程用 HTTP Header Manager 做了对照实验）
3. 顺序规则：同一层级内的元件按**从上到下**处理；同名冲突要靠"避免同名"来规避
4. 与八大组件的关系：配置元件是执行链的第一环，后面依次是前置处理器 → 定时器 → 取样器 → 后置处理器 → 断言 → 监听器（见 [[Ch25-JMeter执行顺序]]）

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 以为"生效顺序与位置无关"= 位置随便放 | "是否生效"与同级上下位置无关，但**作用域仍由层级决定**；放到请求下面 = 只对该请求生效 |
| 以为配置元件只在线程组启动时执行一次 | 它在每个取样器执行前都会被收集生效（这也是它总能"先于取样器"的原因） |
| 用两个同名 Header Manager 试"叠加效果" | 同名键的覆盖关系受处理顺序影响，靠猜会导致压测结论不可复现；避免同名 |
| 把"从上到下执行"只记成"配置元件从下到上" | 原文与实验都支持**从上到下**；这条规则对断言、前后置处理器等所有同类元件都成立 |
| 把课程结论当成"配置元件是线程级初始化代码" | 它是"取样器级准备"，与"线程生命周期"不是一回事 |

【我的理解】引导题（用自己的话回答）：
1. 请用自己的话把"配置元件与存放位置无关"和"同一层级元件从上到下执行"这两句看似矛盾的话讲通。
2. 如果你在同一个线程组里放了两个 HTTP Header Manager，各自都定义了 `X-Env`，你会怎么预判最终发出去的请求头？为什么企业里建议直接禁止这种做法？
