### 知识点1：逻辑控制器是什么

【课程原话/定义】
在 JMeter 中，**逻辑控制器是一种测试元素，用于控制测试计划中其他测试元素（如请求、定时器等）的执行顺序和条件**。逻辑控制器**通过逻辑条件来决定是否执行其下面的子元素**，从而**模拟真实用户行为或者特定的测试场景**。

常用的控制器（课程原文）：
- **Transaction Controller（事务控制器）**
- **If Controller（条件控制器）**
- **Loop Controller（循环控制器）**
- **Random Controller（随机控制器）**

**【扩展知识】**：添加元件步骤——在 JMeter 界面中，逻辑控制器是**挂载在网络组或其他控制器之下**的：`线程组（Thread Group）→ 添加（Add）→ 逻辑控制器（Logic Controller）→ 选择具体控制器`（与 [[Ch13-使用代理服务器录制请求]] 中"添加录制控制器"的路径一致）。控制器下还可以继续挂控制器，形成**嵌套结构**——这是后面实现复杂业务分支的基础。

【为什么？】
逻辑控制器存在的根本原因只有一个：**真实用户的行为不是"直线"的**。

- 一个虚拟用户不会永远"打开首页 → 点搜索 → 退出"，他会：**重复**刷新几次（循环）、**根据结果**决定下一步（条件）、**走其中一条分支**（随机/分支）、**把一串动作当成一件事来看**（事务）。
- 如果没有逻辑控制器，JMeter 的脚本就只能"从上到下执行一遍"——那是**接口连通性测试**，不是性能压测。**并发压测的核心价值之一是"压力形状"要像真实用户**，而控制器就是塑造压力形状的元件。
- 更重要的一层：**控制器直接决定指标口径**。比如 Transaction Controller 能把多个请求合并成一个"事务"来统计 RT——于是你才能回答"用户完成一次下单要多久"（端到端耗时），而不是"下单接口本身耗多久"。**这就是性能测试里"事务响应时间"这一常用指标的技术来源。**

一句话：**取样器决定"发什么请求"，控制器决定"请求怎么组织、按什么逻辑执行"——而组织方式决定了你最终能拿出什么口径的指标。**

【必须掌握】

| 维度 | 课程定义 | 工程含义 |
|------|----------|----------|
| 定位 | 一种测试元素（逻辑控制器） | 组织与调度元件，不发请求 |
| 作用对象 | 测试计划中其他测试元素（请求、定时器等） | 控制其**子元素**的执行 |
| 控制方式 | 通过逻辑条件决定是否执行其下面的子元素 | 分支、循环、随机、事务合并 |
| 目的 | 模拟真实用户行为或特定测试场景 | 塑造"压力形状"，贴近真实业务 |
| 常用控制器 | Transaction / If / Loop / Random | 本课重点四个 |
| 挂载位置 | 线程组或其他控制器之下（可嵌套） | 位置＝作用域，嵌套＝复杂逻辑 |

【企业场景】
你录完一条业务链，脚本里是"从上到下 30 个请求"。Leader 问你："用户完成一次下单要多久？" 你如果直接看某个接口的响应时间，答案是不合格的——**用户感知的是"从点下单到支付完成"的端到端耗时**。你的做法是：用 Transaction Controller 把这 30 个请求（或其中属于下单链路的那一段）包成一个事务，然后在聚合报告里读这个事务的 RT 与 TPS。**这一刻你交付的指标口径才和业务方关心的口径对齐了。** 这也是企业里压测报告最常见的指标列——"业务事务响应时间"，而不是"某个接口的响应时间"。

【面试考察】
面试官："JMeter 的逻辑控制器是干什么的？你常用哪些？"

参考回答框架：
1. 定义：逻辑控制器用于控制其下子元素（请求、定时器等）的执行顺序与条件，从而模拟真实用户行为与测试场景
2. 常用四类：Transaction（事务合并）、If（条件分支）、Loop（循环）、Random（随机）
3. 价值：塑造压力形状、贴近真实用户；同时决定指标口径（如事务级 RT）
4. 结构：控制器可嵌套，挂载位置决定作用域

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 以为逻辑控制器自己会"发请求" | 控制器是调度元件，不产生请求；请求只由取样器发出 |
| 把控制器加在线程组之外（如测试计划根下随意放置） | 逻辑控制器应挂在测试计划/线程组/其他控制器下，参与元件树的执行流 |
| 认为控制器只影响"要不要执行" | 它还影响**执行顺序、执行次数、事务边界与指标口径** |
| 只按字面记四个控制器，不理解使用场景 | 面试常问"什么场景用哪个控制器"，要能给出业务例子 |

### 知识点2：Transaction Controller（事务控制器）

【课程原话/定义】
**Transaction Controller（事务控制器）是 JMeter 中一种逻辑控制器，它允许用户将多个 Sampler 组合成一个逻辑事务，表示一个业务流程或用户操作。** Transaction Controller 可以帮助用户**统计和管理这些逻辑事务的性能数据**，例如**请求响应时间、吞吐量、错误率**等指标。

相关配置参数介绍：
- **Generate Parent Sample**：如果选中，事务控制器将作为其他取样器的**父级样本**，否则事务控制器仅作为独立的样本。**一个事务下包含多个请求，如果一个请求失败了，那这个事务就失败了。**
  - **勾选之后只会显示事务控制器的相关指标**
  - **未勾选还会显示每个请求的相关指标**
- **Include duration of timer and pre-post processors in generated sample**：如果选中，在生成的样本中**包括计时器，预处理和后处理的延迟时间**，否则不包含。

以访问百度首页为例展示 Transaction Controller 的使用：
1. **步骤一**：添加线程组，在线程组中配置**并发数为 5**，线程组中添加 Transaction Controller，然后在 Transaction Controller 下添加 **4 个相同的 HTTP Request**（都为请求访问百度首页），最后添加 **Aggregate Report** 查看响应结果。
2. **步骤二**：点击运行查看**勾选 Generate Parent Sample 与否的区别**。

【为什么？】
事务控制器解决的是"**指标口径**"问题，它的机制可以从三层来理解：

1. **什么是"事务"？** 一个事务 = 一个对用户有意义的完整业务流程（例如"下单"包含 加购→提交订单→支付 三个请求）。**用户感知的耗时是事务级耗时**，而不是单个接口耗时。事务控制器就是把这个"感知粒度"告诉 JMeter。
2. **Generate Parent Sample 的机制**：勾选后，事务控制器生成一个"父级样本"，**聚合报告里只显示这条父样本**（事务的 RT/TPS），把子请求的结果"藏"在父样本里面；不勾选时，父样本与子请求样本**都会显示**，你既能看到事务总耗时，也能看到每个请求各自的耗时。
   - **面试/工作判断法**：看"用户视角"用勾选（只看事务）；查"哪一步慢"用不勾选（保留每步明细）。
3. **失败传播**：课程明确指出"**一个事务下包含多个请求，如果一个请求失败了，那这个事务就失败了**"。这是事务语义的关键——**事务是"原子"的**：用户在真实场景里，只要下单链路中任何一步失败，这次下单就是失败的。所以事务级错误率天然是更严格的业务错误率。**企业报压测结果时常用事务级错误率，就是这个原因。**

另外 **Include duration of timer and pre-post processors** 明确了另一个口径问题：**事务耗时里要不要算"思考时间/等待时间"与前后处理脚本的耗时？**
- **勾选**：包含 → 更接近"真实用户体验到的时间"（因为真实用户确实会有停顿、系统确实要跑前后处理）。
- **不勾选**：不包含 → 更接近"服务端处理能力的纯耗时"。
**这是压测方案里必须明确的口径声明**——同一个脚本，两种配置给出的 RT 可能差出数倍，如果不声明口径，结论无法比较。

【必须掌握】

| 参数 | 取值 | 含义 | 使用建议 |
|------|------|------|----------|
| Generate Parent Sample | 勾选 | 事务控制器作为父级样本，**只显示事务指标** | 上报"业务事务 RT/TPS"时用 |
| Generate Parent Sample | 不勾选 | 事务与各请求样本都显示 | 排查"哪一步慢"时用 |
| Include duration of timer and pre-post processors | 勾选 | 事务耗时包含计时器与前后处理延迟 | 想反映真实用户感知耗时 |
| Include duration of timer and pre-post processors | 不勾选 | 不包含计时器与前后处理 | 想反映服务端纯处理耗时 |
| 失败语义 | — | 子请求任一失败 → 事务失败 | 用事务级错误率作为业务错误率 |
| 配套监听器 | — | 课程示例使用 Aggregate Report 查看结果 | 配合结果分析（见后续监听器章节） |

【企业场景】
你压"下单"链路（加购 → 提交订单 → 支付），上报给业务方的指标应该是"**下单事务的 P95 响应时间**"。做法：用 Transaction Controller 包住这三个请求，**勾选 Generate Parent Sample**，跑完后在 Aggregate Report 里读事务级的 95% Line 与 Throughput；同时**为了排查**，你还会跑一次**不勾选**的版本（或在其他监听器里保留子请求明细），看看到底是"提交订单"还是"支付"拖慢的。**这两次配置不是"随便选的"，而是分别回答两个不同问题：对外报口径，对内做定位。** 当你需要在方案里写清指标定义时，还要声明有没有把定时器/前后处理计入事务耗时。

【面试考察】
面试官："事务控制器是干什么的？Generate Parent Sample 勾不勾有什么区别？"

参考回答框架：
1. 作用：把多个 Sampler 组合成一个逻辑事务，统计事务级 RT、吞吐量、错误率
2. 勾选 Generate Parent Sample：只显示事务（父样本）指标，适合对外上报业务事务指标
3. 不勾选：事务与各子请求指标都展示，适合定位"事务内哪一步慢"
4. 失败语义：任一子请求失败即整个事务失败，因此事务错误率是更严格的业务级错误率
5. 计时口径：Include duration of timer and pre-post processors 决定是否计入定时器与前后处理耗时，方案中必须声明口径

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 认为事务控制器会自己发一个请求 | 它只是把子请求合并统计，不额外发请求 |
| 只看单个接口 RT 就向业务方汇报"下单耗时" | 业务关心的是事务级端到端耗时，应由 Transaction Controller 统计 |
| 忘记"任一子请求失败则事务失败"的语义 | 事务错误率是业务级错误率；子请求失败会直接拉高事务错误率 |
| 不声明事务耗时是否包含定时器/前后处理 | 两种口径的 RT 可能差数倍，不声明则结果不可比 |
| 混淆"勾选后看不到子请求指标"是 bug | 这是设计行为：勾选只显示事务指标，看明细需不勾选或换监听器 |

【我的理解】
> 引导思考题1：什么情况下你会上报"事务级 RT"，什么情况下你必须看"单请求 RT"？请各举一个工作场景。
>
> 引导思考题2：如果事务的 RT 很高，但每个子请求的 RT 都不高，你会怀疑哪个参数？（提示：定时器与前后处理是否计入）

### 知识点3：If Controller（条件控制器）

【课程原话/定义】
**If Controller（条件控制器）允许在执行测试计划时根据某个条件来选择是否执行其子元素。例如，可以根据前一个请求的响应结果是否包含某个关键字来决定是否执行下一个请求。**

相关参数配置说明：
- **Condition (evaluated with javascript)**：默认情况下，该条件被解释为返回 `"true"` 或 `"false"` 的 **JavaScript 代码**。
- **Expression (must evaluate to true or false)**：表达式（值必须是 true 或 false）。
- **Interpret Condition as Variable Expression?**：如果选择了这个，那么条件必须是一个计算值为 `"true"` 的表达式。
- **Evaluate for all children?**：
  - **勾选**：表达式会在 if controller 节点下的**每个取样器之前**执行一次，根据表达式结果判断是否执行该取样器。
  - **不勾选**：**只在 if controller 入口处执行一次**，根据结果判断是否执行下面的脚本。

以访问百度首页为例展示 If Controller 的使用：
1. **步骤一**：添加线程组，线程组中添加 HTTP Request 和 If Controller，然后在 If Controller 下添加 HTTP Request，两个请求都为访问百度首页，最后添加 View Results Tree 查看响应结果。
2. **步骤二**：在 If Controller 中进行相关配置。
3. **步骤三**：**当作为条件的请求通过时**，在 View Results Tree 中展示响应结果。
4. **步骤四**：**当作为条件的请求失败时**，在 View Results Tree 中展示响应结果。

【为什么？】
If Controller 解决的是"**分支**"问题——真实用户不会走同一条路。

- 机制上，它**在入口处求值一个真假表达式**，为真才执行其下子元素。表达式的来源通常是**上一个请求的结果**（例如用后置处理器把响应中的字段提取成变量，再在 If 里判断这个变量）。
- **两种参数写法对应两种"条件来源"**：
  - `Condition (evaluated with javascript)`：默认按 **JavaScript 代码**解释，返回 `"true"`/`"false"`。这允许写更复杂的 JS 逻辑，但性能开销更大（每次求值都要走脚本引擎）。
  - 勾选 `Interpret Condition as Variable Expression?`：把条件当作**表达式**求值（值必须是 true/false），开销更小。**【扩展知识】**：JMeter 官方推荐在不需要复杂逻辑时优先用这种写法，因为脚本求值在高并发下会明显消耗压测机资源——**又一次呼应"加压机不能成为瓶颈"这条纪律。**
- **Evaluate for all children?** 决定"条件是一次性判断，还是每个子元素前都判断一次"：
  - **勾选**：每个取样器前都重新求值 → 子元素可以**执行一部分**（比如表达式在第 3 个子元素前变成 false，后面就不执行了）。
  - **不勾选**：只在入口判断一次 → 要么整块执行，要么整块跳过（**全进或全不进**）。
  这两者的差别在业务上很关键："整块执行"适合"条件成立就做完这一套动作"；"逐个判断"适合"过程条件会变化"的流程（例如库存实时变化）。
- 课程的"步骤三/步骤四"演示的正是分支的两个结果：**条件请求通过 → 执行子请求并出现在结果树里；条件请求失败 → 子请求不执行**。这就是"分支"在结果上的可观测证据。

【必须掌握】

| 参数 | 取值 | 含义 | 使用要点 |
|------|------|------|----------|
| Condition (evaluated with javascript) | 默认 | 条件按 JavaScript 代码解释，返回 true/false | 复杂逻辑可用，但开销大 |
| Expression (must evaluate to true or false) | — | 表达式值必须是 true 或 false | 写清真假条件，避免隐式类型问题 |
| Interpret Condition as Variable Expression? | 勾选 | 条件作为表达式求值（值须为 true/false） | 官方推荐：比 JS 求值开销小 |
| Evaluate for all children? | 勾选 | 每个子取样器前都求值 | 子元素可部分执行（过程条件会变化） |
| Evaluate for all children? | 不勾选 | 仅在入口求值一次 | 整块执行或整块跳过 |
| 条件来源 | — | 通常取自上一个请求的结果（提取成变量） | 需配合后置处理器/断言 |

【企业场景】
你压"优惠券"场景，业务规则是"只有黄金会员才走领券接口"。做法：先用正则/JSON 提取器把用户等级从上一个接口的响应里提取为变量 `grade`，然后在 If Controller 里写条件判断 `grade` 是否为黄金；条件成立才执行领券请求。为什么必须这么做？因为**如果无条件压领券接口，会有大量用户拿到"非会员不可领"的失败响应——你的错误率统计直接虚高，业务方会以为系统有缺陷**。反过来，如果你的场景是"100% 都要领券"，就**不该**用 If，而应该直接放请求——用控制器是为了贴合规则，不是为了"看起来高级"。

【面试考察】
面试官："If Controller 怎么用？Interpret Condition as Variable Expression 和 Evaluate for all children 分别什么意思？"

参考回答框架：
1. 作用：按条件决定是否执行其下子元素，用于模拟用户的判断分支行为
2. 条件来源：通常来自前一个请求的响应（提取成变量）或表达式，必须是 true/false
3. Interpret Condition as Variable Expression：勾选后按表达式求值（官方推荐，开销小于 JS 求值）
4. Evaluate for all children：勾选则每个子取样器前都判断一次（可部分执行）；不勾选则只在入口判断一次（全进或全不进）
5. 实践：条件要贴合真实业务规则，否则会制造大量"假失败"污染错误率

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 条件表达式写成非 true/false 的值 | 表达式必须能求值为 true 或 false，否则判断结果不符合预期 |
| 无条件地给接口加上 If Controller | 条件应贴合业务规则；乱加会导致部分用户该发的请求没发（覆盖不足） |
| 需要"逐个判断"时没勾 Evaluate for all children | 不勾选只在入口判断一次，整块进入/跳过，做不到"执行一半" |
| 一直使用 JS 求值（不勾 Variable Expression） | 高并发下 JS 求值开销明显，会成为压测机负担；简单条件应勾选表达式模式 |
| 条件变量没提取到（后置处理器没生效） | 变量为空时条件通常不成立，子请求静默不执行——要先用结果树验证 |

【我的理解】

### 知识点4：Loop Controller（循环控制器）

【课程原话/定义】
**Loop Controller 是 Apache JMeter 中一种循环控制器，用于控制其子元素（如采样器、定时器、逻辑控制器等）的执行次数。** 通过 Loop Controller，可以指定子元素需要被执行的**循环次数**，从而实现对测试逻辑的循环执行。

以访问百度首页为例展示 Loop Controller 的使用：
1. **步骤一**：添加线程组，线程组中添加 Loop Controller，然后在 Loop Controller 下添加访问百度首页的 HTTP Request，然后**设置 Loop Controller 的循环次数为 10**，最后添加 View Results Tree 查看响应结果。
2. **步骤二**：点击运行查看结果。

【为什么？】
循环控制器解决"**重复**"问题，但它的关键价值在于"**循环的层级**"——这是新人最容易搞混的地方：

- **线程组的 Loop Count 是"用户级循环"**：它决定"这个虚拟用户把整个线程组走几遍"。
- **Loop Controller 的循环次数是"局部循环"**：它决定"这一小段动作重复几次"，且**可以嵌套**（循环里还能套循环）。
- 所以当业务是"用户登录一次，然后连续浏览 10 个商品"时，正确的做法是：**线程组控制"登录 + 浏览"整体跑几轮（或跑固定时长），Loop Controller 控制"浏览"这一步跑 10 次**。如果你把"浏览"的重复靠线程组的 Loop Count 实现，登录也会跟着重复 10 次，**行为和指标都错了**（你会多压 9 次登录接口）。
- 另一个要点：**循环控制器里的取样器会产生多条样本**。以课程示例（循环 10 次、并发若干）为例，结果树里会出现 10 倍数量的请求记录——这也意味着**样本量会放大**，做长循环时要留意磁盘与内存开销（呼应 [[Ch14-测试计划]] 的"函数测试模式非常占用磁盘空间"）。

**【扩展知识】**：循环次数除了写死，也可以通过变量/属性引用（如 `${loopTimes}`）或勾选"永远"来动态控制；循环与计数配合（例如配合 Counter 配置元件）能生成递增的数据，用于"每个用户取不同数据"的变体场景。

【必须掌握】

| 项目 | 课程原文 | 工程含义 |
|------|----------|----------|
| 作用 | 控制其子元素（采样器、定时器、逻辑控制器等）的执行次数 | 局部重复 |
| 关键参数 | 循环次数（示例中设为 10） | 可写死、可用变量、可"永远" |
| 与线程组 Loop Count 的区别 | — | 线程组＝整块业务跑几轮；Loop Controller＝局部动作重复几次 |
| 可嵌套 | 子元素可以是逻辑控制器 | 支持"循环里套循环/分支" |
| 结果影响 | 子取样器会产生多倍样本 | 结果树/报告数据量放大，注意资源开销 |

【企业场景】
你压"商品列表翻页"场景：用户进入列表后会**连续翻 10 页**。脚本结构应该是：HTTP 请求（打开列表）→ Loop Controller（循环 10 次）→ HTTP 请求（下一页）。这样每个虚拟用户会看到 10 次翻页请求，脚本行为与真实用户一致。**如果你把这个脚本的循环放在线程组级别**，那"打开列表"也会重复 10 次——你的压测结果里"列表首页"的 TPS 会被放大 10 倍，而真正要压的"翻页"反而只是其中一部分，**瓶颈定位彻底失真**。这就是"循环层级选错会让结论全废"的典型例子。

【面试考察】
面试官："循环控制器和线程组的循环次数有什么区别？"

参考回答框架：
1. Loop Controller：控制其下子元素的局部重复次数，可嵌套（循环里套循环/分支）
2. 线程组 Loop Count：控制整个线程组（该虚拟用户的全部动作）迭代几轮
3. 区别与选择：局部动作重复用 Loop Controller，整体业务轮次用线程组 Loop Count
4. 影响：循环会使子取样器产生多倍样本，放大结果数据量与资源开销，长循环要评估压测机承载

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 用线程组 Loop Count 实现"局部重复" | 会让整块业务（含登录等一次性动作）一起重复，行为与指标都失真 |
| 认为循环控制器只能包取样器 | 它可以包定时器、逻辑控制器等，支持嵌套形成复杂逻辑 |
| 忘记循环会放大样本量 | 循环 N 次 → 子请求样本 ×N，影响结果数据量与压测机资源 |
| 把"循环"与"重试"混为一谈 | 循环是业务语义上的重复行为；失败重试需要额外逻辑（控制器/定时器组合）实现 |

【我的理解】
> 引导思考题1：请各举一个"应该用线程组 Loop Count"和"应该用 Loop Controller"的场景，并说明用错会怎样。
>
> 引导思考题2：如果循环次数是"永远"，你这个脚本什么时候会停？需要配合什么参数？

### 知识点5：Random Controller（随机控制器）

【课程原话/定义】
**Random Controller（随机控制器）是 JMeter 中的一种逻辑控制器，用于在其子元素中随机选择一个进行执行。** 在性能测试中，Random Controller 可以**帮助模拟用户行为的随机性，从而更接近真实场景**。

相关参数配置说明：
- **Ignore sub-controller block（忽略子控制器模块）**：**勾选后，子控制器失效，由随机控制器代替。**

以访问百度首页为例展示 Random Controller 的使用：
1. **步骤一**：添加线程组，**线程组中的并发数设置为 4**，线程组中添加 Random Controller，然后在 Random Controller 下添加**四个访问百度首页的 HTTP Request**，最后添加 View Results Tree 查看响应结果。
2. **步骤二**：点击运行查看结果。

【为什么？】
随机控制器解决的是"**行为多样性**"问题：

- **真实用户不会都做同一件事**。同一个入口页面上，有人点 A 链接、有人点 B 链接。Random Controller 每次执行时**从子元素里随机挑一个**执行，于是不同虚拟用户、不同迭代会走出不同路径——**压力分布因此更接近真实流量**。
- **课程示例的设计很讲究**：并发数设为 4，子元素是 4 个 HTTP Request。**4 个并发 × 每次随机 1 个**，你能在结果树里直观看到"多个请求都被覆盖到、但每次只跑其中一个"。这证明了随机控制器**不是"都跑一遍"**，而是"挑一个跑"。
- **Ignore sub-controller block（忽略子控制器模块）** 是一个嵌套相关的开关：**勾选后，子控制器失效，由随机控制器代替**——也就是说，本来子控制器有自己的执行逻辑（比如一个循环控制器），勾选这个选项后，随机控制器把它整体当作"一个可选块"来随机选择，而不是让子控制器按自己的逻辑展开。**【扩展知识】**：这在"随机挑选一大段业务流程"的场景里很有用（例如随机选择一个模块的整体流程执行）。

**⚠ 一个重要提醒**：随机意味着**结果不可精确复现**——同一脚本两次运行的请求分布可能不同。做"必须可对比"的压测（优化前后对比、版本对比）时，要谨慎使用随机控制器，或者保证样本量足够大让分布趋稳。这是"随机性"与"可复现性"之间的取舍，也是压测方案里要声明的口径。

【必须掌握】

| 参数/特性 | 课程原文 | 工程含义 |
|-----------|----------|----------|
| 作用 | 在其子元素中随机选择一个执行 | 模拟用户行为的随机性 |
| 目的 | 更接近真实场景 | 让压力分布贴近真实流量构成 |
| 示例配置 | 线程组并发 4，Random Controller 下 4 个 HTTP Request | 每次随机执行其中一个 |
| Ignore sub-controller block | 勾选后子控制器失效，由随机控制器代替 | 把子控制器整体当作一个可随机选择的块 |
| 副作用 | — | 结果不可精确复现；对比类压测需谨慎或加大样本量 |

【企业场景】
你压一个"首页推荐位"场景：首页有 4 个推荐位入口（A/B/C/D），真实用户点哪个是随机的。做法是用 Random Controller 包住这 4 个请求，让每个虚拟用户在每次迭代里随机进入一个入口——**这样服务端承受的是接近真实的流量分布**，而不是"所有人只点 A"。同时你要意识到一个风险：如果这 4 个入口背后的服务端处理能力差别很大，那么随机执行会让每次压测的分布略有波动，所以**做优化前后对比时，你更可能选择固定比例的方案（多个线程组并行按比例加压）而不是纯随机**，或者把迭代数放大到足够大，让随机分布趋稳。

【面试考察】
面试官："怎么做更接近真实用户行为的压测？随机控制器有什么用？"

参考回答框架：
1. 随机控制器：在其子元素中随机选择一个执行，模拟用户行为的随机性
2. 组合方式：多元素随机 + 多线程组按比例并行，共同逼近真实流量分布
3. Ignore sub-controller block：勾选后子控制器失效，随机控制器把它作为可选块处理
4. 取舍：随机导致结果不可精确复现；优化前后对比等场景应控制随机性或用足够大样本量使其趋稳

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 以为随机控制器会把子元素都跑一遍 | 每次只随机挑**一个**子元素执行 |
| 在需要严格可对比的场景大量使用随机 | 随机导致分布波动，可能让优化前后的结论不可比；应控制或加大样本量 |
| 不理解 Ignore sub-controller block 的含义 | 勾选后子控制器不再按自己的逻辑执行，而是被随机控制器整体当作一个可选块 |
| 把随机控制器当成"随机数据的生成器" | 它随机的是"执行哪个子元素"，不负责生成随机参数值（数据随机要靠函数/参数化） |

【我的理解】
> 引导思考题1：为什么"随机执行"更接近真实用户？请举一个你熟悉的业务页面来说明。
>
> 引导思考题2：如果你要做"优化前后对比"的压测，你会怎么处理随机性带来的不可复现问题？

### 知识点6：四个控制器的对比与选用

【课程原话/定义】
课程本页的总结是两条：**常见控制器的介绍**、**常见控制器的使用**——也就是说，这一页的考核目标是"认识四个常用控制器，并能跑通课程给的示例"。

【扩展知识】
把四个控制器放在一张表里对比，是形成"选用直觉"的最快方式：

| 控制器 | 解决的业务问题 | 用户视角类比 | 结果里的表现 | 关键参数 |
|--------|----------------|--------------|--------------|----------|
| Transaction | 把一串请求当成"一件事"，统计事务级指标 | 用户感知的"下单用了多久" | 勾选父子样本后只显示事务；不勾选则事务与子请求都显示 | Generate Parent Sample、是否计入定时器/前后处理 |
| If | 按条件决定"是否走这条路" | "会员才能领券" | 条件不成立时子请求不出现 | 条件表达式、Interpret as Variable Expression、Evaluate for all children |
| Loop | 让一段动作重复 N 次 | "连续翻 10 页" | 子请求样本数量 ×N | 循环次数（可"永远"、可用变量） |
| Random | 从若干动作里随机挑一个 | "用户随机点某个入口" | 每轮只出现其中一个子元素 | Ignore sub-controller block |

**选用口诀**：**要口径用事务、要分支用 If、要重复用 Loop、要多样性用 Random。**

**⚠ 课程原文的"结果查看"细节**：课程在 Transaction 与 Loop 的示例里用 **Aggregate Report（聚合报告）** 看结果，在 If 与 Random 的示例里用 **View Results Tree（查看结果树）** 看结果。这不是随意选的：
- **聚合报告**给的是**统计量**（平均/分位 RT、吞吐量、错误率），适合看"事务/请求的整体表现" —— Transaction 与 Loop 的效果是"指标数量级变化"，用聚合报告一眼能看出来。
- **结果树**给的是**逐条明细**（每个请求的响应内容），适合看"某次执行到底走了哪条分支/挑了哪个子元素" —— If 与 Random 的效果是"执行路径差异"，必须逐条看才能验证。

**【扩展知识】**：这两个监听器的参数含义与原文勘误（如聚合报告中 90%/95%/99% Line 的说明、Received/Sent KB/sec 的说明）属于后续"监听器"章节的内容，本章只需先把"看统计用聚合报告、看路径用结果树"的分工记住。

【为什么？】
为什么"选用控制器"值得单独成为一个知识点？因为在真实项目里，**控制器选错不会报错，只会悄悄给你错误的结论**：

- 用 Loop 代替线程组 Loop Count → 一次性动作被重复压（例如登录被压 N 倍），指标失真；
- 用 If 覆盖了本该 100% 执行的请求 → 请求量不足，容量结论偏乐观；
- 该用 Transaction 却直接看单接口 → 交付的指标口径与业务不对齐，报告被退回；
- 该用 Random 却全部固定 → 流量分布不真实，隐藏的瓶颈（某个分支很慢）永远发现不了。

**压测脚本里最贵的错误从来不是"跑不起来"，而是"跑起来了但结论是错的"。**

【必须掌握】

| 判断问题 | 选哪个控制器 |
|----------|--------------|
| 我要报"一个业务流程的端到端耗时" | Transaction Controller |
| 我要按服务端返回的结果决定后续走哪条路 | If Controller |
| 我要让某段动作重复若干次 | Loop Controller |
| 我要模拟用户在不同入口之间随机选择 | Random Controller |
| 我想"某一整块流程"被随机选择一个执行 | Random Controller + 勾选 Ignore sub-controller block |
| 我要看执行路径/分支是否按预期走 | 用 View Results Tree 查看 |
| 我要看事务整体的 RT/TPS/错误率 | 用 Aggregate Report 查看 |

【企业场景】
你在评审一个新人写的脚本时，用上面的"判断问题"逐条过了一遍，发现两处问题：一是"登录"被放在了 Loop Controller 里面，导致登录请求被重复压了 10 倍；二是它把 4 条业务链塞进一个线程组用 Random 随机跑，导致"优化前后对比"的结果每次都不一样，无法出结论。你给出的修改意见是：登录移到循环外（或用 setUp 线程组）、对比类压测改成多个线程组按固定比例并行。**这种"看结构就知道指标会不会失真"的能力，就是这一章真正要练的东西。**

【面试考察】
面试官："给你一个业务场景，你会怎么组织 JMeter 脚本结构？"

参考回答框架：
1. 先定口径：需要业务事务指标 → 用 Transaction Controller 包住业务流程
2. 再定逻辑：有分支规则用 If、有重复动作用 Loop、有多样性需求用 Random
3. 分层组织：前置用 setUp 线程组、整体轮次用线程组 Loop Count、清理用 tearDown 线程组
4. 最后定验证方式：看路径用结果树，看统计用聚合报告；并声明随机性/计时口径等影响可复现性的因素

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 控制器选错但脚本能跑，就以为没问题 | 控制器选错不会报错，只会让指标口径失真，是最危险的错误类型 |
| 用 Random 做优化前后对比 | 随机分布波动会让两次结果不可比；应固定比例或加大样本量 |
| 用结果树去看"事务的整体 RT" | 结果树是逐条明细，整体统计应看聚合报告 |
| 用聚合报告去验证"分支是否走对" | 聚合报告只有统计量，看不出执行路径；路径验证要看结果树 |
| 把控制器当"装饰"，随意嵌套 | 每个控制器都会改变执行次数与口径，嵌套前先想清业务语义 |

【我的理解】
> 引导思考题1：请用"判断问题 → 选控制器"的方式，为一条"会员领券 → 下单 → 支付"的业务链设计控制器结构。
>
> 引导思考题2：为什么说"脚本跑起来了但结论是错的"比"脚本跑不起来"更危险？请结合本章的某个控制器举例。

### 知识点7：逻辑控制器在真实业务场景中的应用

【课程原话/定义】
本章课程原文的正文收敛于四个常用控制器的介绍与使用示例（以访问百度首页为例）；本页的总结是"**常见控制器的介绍、常见控制器的使用**"。

> 📌 **内容缺口提示**：站点把"逻辑控制器如何落到真实业务流程"单独放在另一页（《JMeter 场景逻辑控制技术》），该页给出"用户访问商城购买商品"的应用示例与业务分支流程图。按本仓库的章节安排，那部分内容属于下一个知识页；本节只做指针，不搬运。

**【扩展知识】**：把控制器用起来的通用思路，可以归纳为"**先画业务分支，再落控制器**"三步：
1. **画业务分支图**：把真实用户的可能路径画出来（例如：未登录只刷首页 / 注册登录后购买 / 注册登录后只浏览）。
2. **给每条分支配控制器**：分支判断用 If、重复动作用 Loop、随机选择用 Random、整段业务合并统计用 Transaction。
3. **核对指标口径**：确认每条分支的请求量是否符合业务比例，以及你上报的指标是事务级还是请求级。

这一套思路与 L1 学过的场景设计完全一致：**场景设计决定"压什么"，控制器决定"怎么在 JMeter 里表达出来"**。

【为什么？】
为什么要在本章末尾强调"落回业务"？因为控制器是**最容易"技术上正确、业务上错误"**的元件：

- 你在 JMeter 里写的每一个 If/Loop/Random，都在**断言一个业务规则**（"只有会员能领券""用户会翻 10 页""入口是随机的"）。如果这个业务规则你写错了，压测出来的流量构成就是错的——**服务端承受的负载与真实流量不匹配，容量结论自然不可信**。
- 反过来，**能准确把业务规则翻译成控制器结构，是"会压测"和"会跑 JMeter"的分界线**。面试里考控制器的题，最终都会落到"你会怎么设计这条业务链的脚本结构"。

【必须掌握】

| 步骤 | 动作 | 产出 |
|------|------|------|
| 1. 业务分析 | 找出用户可能的路径与分支条件 | 业务分支清单/流程图 |
| 2. 结构映射 | 分支→If、重复→Loop、随机→Random、业务合并→Transaction | 元件树结构 |
| 3. 容器选择 | 前置→setUp、主加压→Thread Group、清理→tearDown | 三段式脚本 |
| 4. 比例核对 | 各分支请求量是否符合业务比例 | 流量构成说明 |
| 5. 口径声明 | 事务级/请求级指标、是否含定时器与前后处理 | 压测方案中的指标定义 |

【企业场景】
你接到"压一遍商城下单链路"的任务，不会直接打开 JMeter 就录。你会先在纸上画出三条分支：**未登录用户只刷首页**、**登录用户直接购买**、**登录用户只浏览**（这正是站点另一页给出的示例分支）。然后逐一映射：外层用 If 判断登录状态；"购买"分支用 Transaction 把 加购→下单→支付 包成一个事务；"只浏览"分支用 Loop 表示连续浏览若干商品。做完这一步，你的脚本结构**本身就是一份可视化的业务需求说明**——开发、产品、Leader 都能看懂你在压什么。**这就是"控制器结构 = 业务规则的可执行文档"的价值。**

【面试考察】
面试官："给你一条完整业务链，你怎么把它翻译成 JMeter 脚本结构？"

参考回答框架：
1. 业务先行：先画出用户路径与分支（未登录浏览 / 登录购买 / 登录浏览等）
2. 结构映射：分支→If Controller，重复→Loop Controller，随机→Random Controller，业务整体→Transaction Controller
3. 容器分层：setUp 做前置（登录/造数），Thread Group 做加压，tearDown 做清理
4. 指标对齐：事务级指标对业务上报，请求级指标用于内部定位；并声明计时口径与流量比例

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 控制器结构写得出来，但业务规则写错了 | 控制器表达的是业务规则；规则错→流量构成错→容量结论错 |
| 只关注"脚本能不能跑通" | 更要关注"跑出来的流量是否与真实业务比例一致" |
| 把业务分支全写成 100% 执行 | 会造成请求量虚高，容量结论偏乐观；应用 If/比例控制 |
| 不记录流量构成与口径 | 压测报告需要说明并发与请求比例、指标定义，否则无法复用与对比 |

【我的理解】
> 引导思考题1：请把"未登录刷首页 / 登录后购买 / 登录后只浏览"这三条分支，映射成具体的控制器结构。
>
> 引导思考题2：为什么说"控制器结构是一份可执行的业务规则文档"？这给你的脚本可读性带来什么要求？

## 课程原文勘误

| 涉及页面 | 原文写法 | 问题 | 正确理解 |
|----------|----------|------|----------|
| 本章（控制器） | `Ignore sub-controller block（忽略子控制器模块）` | "子控制器模块"表述易误解为"忽略掉子控制器这个元件" | 含义是：勾选后子控制器**不再按自身逻辑执行**，由随机控制器把它整体当作一个可选块来处理 |
| 本章（控制器）示例 | Transaction 示例中"最后添加 Aggregate Report 查看响应结果" | 原文未说明聚合报告各列含义（在监听器页才展开） | 事务示例应重点看 `Label / Samples / Average / 90%·95%·99% Line / Error / Throughput` 与事务级样本是否出现 |
| 监听器页（《JMeter 监听器》） | `90% Line：90%用户响应时间`、`95% Line：90%用户响应时间`、`99% Line：90%用户响应时间` | **三行说明全部写成"90%用户响应时间"，95%/99% 未改** | 95% Line 应为"95% 用户的响应时间小于该值"，99% Line 同理；这三行是不同分位值，不是同一个数 |
| 监听器页（《JMeter 监听器》） | `Received KB/sec：每秒收到的千字节`、`Sent KB/sec：每秒收到的千字节` | **两行说明完全相同，Sent 未改** | Received KB/sec 是**每秒接收**的字节数（服务端返回给客户端），Sent KB/sec 是**每秒发送**的字节数（客户端发给服务端），方向相反 |
| 监听器页（《监听器与测试结果》） | `Graph Results（条件控制器）` | **括注张冠李戴**：把监听器误标成控制器 | Graph Results 是**监听器**（图形结果），与"条件控制器 If Controller"无关 |
| 站点另一页（《JMeter 场景逻辑控制技术》） | 页首 `“Logic Controller”来添加所需的逻辑控制器。` | 句子残缺（缺少前半句，应为"通过 添加 → 逻辑控制器 → 选择 Logic Controller 来添加所需的逻辑控制器"之类） | 该页正文开头少了一句操作前置说明，不影响四个控制器的语义；本仓库在 Ch12/Ch15 知识点1 中补全了正确的添加路径 |
| 本章（控制器） | 术语 `Loo...`（原文省略号处）与各处英文名大小写不统一（如 `Random Controller` / `随机控制器` 混用） | 课程中文名与英文名混排，易导致界面里找不到元件 | 一律以界面英文名为准：Transaction Controller / If Controller / Loop Controller / Random Controller |

## 今日课程总结

| 模块 | 核心内容 | 面试权重 |
|------|----------|----------|
| 逻辑控制器定义 | 控制其下子元素（请求、定时器等）的执行顺序与条件，模拟真实用户行为 | ★★★★★ |
| Transaction Controller | 多个 Sampler 组合成逻辑事务；Generate Parent Sample 决定是否只显示事务；子请求失败即事务失败 | ★★★★★ |
| If Controller | 条件分支；Interpret Condition as Variable Expression；Evaluate for all children 决定"逐个子元素判断"还是"入口判断一次" | ★★★★★ |
| Loop Controller | 控制子元素执行次数（示例 10 次）；与线程组 Loop Count 的层级区别 | ★★★★ |
| Random Controller | 子元素中随机选一个执行；Ignore sub-controller block 使子控制器整体成为可选块 | ★★★★ |
| 选用与口径 | 事务管口径、If 管分支、Loop 管重复、Random 管多样性；看统计用聚合报告、看路径用结果树 | ★★★★★ |
| 落地业务 | 先画业务分支，再映射控制器；控制器结构＝可执行的业务规则文档 | ★★★★ |
