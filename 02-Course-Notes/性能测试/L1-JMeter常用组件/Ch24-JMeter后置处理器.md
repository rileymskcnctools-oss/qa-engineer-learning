### 知识点1：后置处理器（Post-Processor）是什么，与前置处理器如何分工

【课程原话/定义】
在 JMeter 中，后置处理器（Post-Processor）是一种元素，用于在执行 Sampler（采样器）后对响应数据进行处理。后置处理器可以从 Sampler 的响应中提取信息、对数据进行解析或者执行其他定制化操作。后置处理器通常用于从响应数据中提取特定的信息，并将其存储为变量用于后续的请求或脚本逻辑。

常见的后置处理器（课程原文列举）：
- **JSON Extractor（Json 提取器）**
- **Regular Expression Extractor（正则表达式提取器）**
- **XPath Extractor（XPath 提取器）**

添加元件步骤的截图在原文中给出（元件树添加路径）。

【为什么？】
性能测试脚本里**最核心的技术难点**就是"把一次响应的值用到下一次请求上"——登录拿到的 `token` 要给后面的请求用、下单返回的 `orderId` 要用来查询订单状态。这个能力在测试圈有个专门的名字叫**关联（Correlation）**，后置处理器就是 JMeter 里实现关联的元件。它必须是"后置"，因为：
1. 要提取的值**只有当响应回来之后才存在**——JSR223/BeanShell 型的"前置"处理器在请求发出前运行，物理上拿不到响应；
2. 提取出的值写入变量（`vars`）后，**后续请求（下一个取样器）才能引用** `${变量名}`。所以在业务链路里，提取器的位置天然是"上游请求"的子节点。

与前置处理器的分工可以用一句话说清：**前置处理器负责"把请求发出去之前要准备的东西"，后置处理器负责"响应回来之后要拿走的东西"**。两者在同一个取样器上的执行顺序是"前置 → 取样器 → 后置"（完整顺序见 [[Ch25-JMeter执行顺序]]）。

**作用域提醒（【扩展知识】）**：JMeter 官方文档明确说明，后置处理器作用于**同一作用域内的所有取样器**；要让它只对某个取样器生效，必须把它作为**该取样器的子节点**。企业脚本里最常见的低级错误，就是把登录的提取器挂到了线程组下——结果每个请求响应后都会用登录接口的正则去跑一遍，既浪费 CPU，又会让变量被无关响应覆盖成错误值。

【必须掌握】

| 维度 | 前置处理器 | 后置处理器 |
|------|-----------|-----------|
| 运行时点 | 取样器**之前** | 取样器**之后** |
| 输入 | 请求参数、变量 | **响应数据**（文本/JSON/XML/Header） |
| 典型能力 | 改参数、算签名、造数据、超时兜底 | 提取响应值、解析响应、写回变量 |
| 课程常见成员 | Sample Timeout、BeanShell PreProcessor | JSON Extractor、正则表达式提取器、XPath 提取器 |
| 与后续请求的关系 | 无（只影响本请求） | **决定后续请求能否拿到正确的上下文** |

| 后置处理器的能力边界 | 说明 |
|----------------------|------|
| 做 | 从响应里"取值"→ 存成变量 → 供后续请求/脚本引用 |
| 不做 | 判定"值对不对"（那是断言，见 [[Ch21-JMeter断言元件的使用]]） |
| 不做 | 修改已经发出的请求（那只有下一次请求能做） |
| 级别提醒 | 提取失败时会写入**缺省值**并继续跑，脚本不会因此报错——必须另配断言或调试元件才能发现 |

【企业场景】
你压"登录 → 查询用户信息 → 下单"三步链路，服务端要求所有后续请求带 `token`。做法：登录请求下（注意是**它下面**，不是线程组下）挂一个 JSON Extractor，变量名 `token`、JSON Path 取 `$.data.token`，后续两个请求的头里写 `token: ${token}`。压测前先用 1 线程跑一次，确认变量真的被取到且被引用；再放大并发。**在企业里，能不能正确做"关联"，是区分"会点 JMeter 按钮"和"能独立完成压测脚本"的分水岭**——90% 的"脚本跑不通/数据全错"都出在关联这一环。

【面试考察】
面试官："JMeter 里怎么把上一个请求的返回值用到下一个请求？"

参考回答框架：
1. 这叫关联（Correlation），用**后置处理器**实现：JSON Extractor / 正则表达式提取器 / XPath 提取器
2. 机制：把响应中的值提取出来存成 JMeter 变量，后续请求用 `${变量名}` 引用
3. 位置：挂在上游请求**之下**（作为它的子节点），保证只对这个取样器的响应生效
4. 验证：Debug Sampler + View Results Tree 看变量是否取到；避免用缺省值掩盖提取失败

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 提取器挂在线程组下 | 后置处理器作用于同作用域**所有**取样器（官方说明），必须挂到目标取样器下才能只针对它 |
| 认为没取到值脚本会报错 | 取不到时会用**缺省值**继续执行，后续请求带着错值发出去，HTTP 仍可能 200——必须配断言/Debug Sampler 才能发现 |
| 把提取器和断言混用 | 提取器只"取值"，不判断对错；要判断必须另加断言（职责分离才便于排错） |
| 变量名与引用大小写/拼写不一致 | `${Token}` 与 `token` 不匹配时会原样发出字符串，不报错，极难发现 |
| 以为"后置"= 在整条链路结束后执行 | 它是"每个取样器响应之后"立刻执行，不是链路结束才跑 |

【我的理解】引导题（用自己的话回答）：
1. 为什么"取值"这件事必须放在取样器之后，而不能用前置处理器完成？请从"值的生命周期"角度解释。
2. 如果登录接口挂了 CSRF/图形验证码导致登录失败，后续请求会看到什么现象？你靠什么元件发现这个问题？

### 知识点2：JSON Extractor（Json 提取器）

【课程原话/定义】
JSON Extractor 是 JMeter 中的一种后置处理器，用于从 JSON 格式的响应数据中提取特定的值。当发送一个请求并收到一个 JSON 格式的响应时，可以使用 JSON Extractor 来提取其中的数据，并将其存储为 JMeter 变量，以便在后续的请求中使用。

相关参数说明：

| 参数 | 含义（课程原文） |
|------|------------------|
| names of created Variable | 保存的变量名，后面使用 `${变量名}` 引用，如 `${code}` |
| JSON Path expressions | json path 表达式，根据接口返回的 JSON 数据格式去定义，如 `$.udf2` |
| Match No.(0 for Random) | 匹配数字（0 代表随机，1 代表第一个，-1 代表所有） |
| Compute concatenation var(suffix_ALL) | 是否统计所有，即将匹配到的所有值保存，名为"变量名_ALL"；使用场景是需要获取的值有多个、后面需要对这一组数据进行操作 |
| Default Values | 找不到时默认值，一般设置为 `NOT FOUND` |

课程案例：提取 Json 格式响应中的城市名称。
1. 步骤一：添加天气的 HTTP Request，添加对应的 Json 提取器，添加查看结果树和 Debug Sampler
2. 步骤二：在 Json 提取器元件中添加配置——变量名 `city_name`，JSON Path 表达式 `$.weatherinfo.city`
3. 步骤三：查看结果，提取出城市名称并赋值给对应的变量名

【为什么？】
JSON 提取器解决的是"**用结构定位值**"的问题。如果不用它，你只能用正则去啃 JSON 字符串——而 JSON 里字段顺序、空格、转义都可能变，正则的维护成本极高。JSON Extractor 的做法是先解析成对象树，再按 JSON Path 定位，于是天然获得两个好处：
1. **对格式噪声免疫**：字段顺序、缩进、空白不影响提取；
2. **失败可预期**：路径不存在时返回缺省值（课程建议设 `NOT FOUND`），而不是抛错中断脚本。

这里最值得琢磨的是 **`Default Values` 为什么要专门设成 `NOT FOUND`**：因为提取失败**不会中断压测**，它只会悄悄把 `NOT FOUND` 塞进变量，然后下游请求带着 `token=NOT FOUND` 继续发。设一个显眼的缺省值，就是在报告/调试时给自己留一个"一眼可见的异常标记"——**这本身就是一种零成本的断言技巧**（可以再加一条 `Text Response contains NOT FOUND` 之类的负向断言）。

`Match No.` 与 `Compute concatenation var` 则解决"一个响应里有多条匹配"的情况：列表接口返回 10 个商品 ID 时，用 `-1`（全部）配合 `_ALL` 拼接变量，才能把这组数据交给后续请求或脚本。

【必须掌握】

| 参数 | 取值 | 使用要点 |
|------|------|----------|
| names of created Variable | 变量名（如 `city_name`） | 后续用 `${city_name}` 引用；多个变量名用逗号分隔可与多个 JSON Path 一一对应（【扩展知识】） |
| JSON Path expressions | 如 `$.weatherinfo.city`、`$.data.list[0].id` | 路径必须按真实响应结构写；写错 = 取到缺省值 |
| Match No.(0 for Random) | 0 随机 / 1 第一个 / n 第几个 / -1 全部 | 单值场景通常写 1（避免随机导致结果不可复现）（【扩展知识】） |
| Compute concatenation var | 勾 / 不勾 | 勾上后生成 `变量名_ALL`，用于多值场景（原文） |
| Default Values | 建议 `NOT FOUND` | 找不到时的兜底值，也是"提取失败"的可见标记 |

【企业场景】
你压"商品列表 → 取第一个商品 ID → 进详情页"的链路。做法：列表请求下挂 JSON Extractor，变量 `sku_id`，路径 `$.data.list[0].id`，Match No. 写 `1`（取第一个，保证可复现），Default Value 写 `NOT FOUND`；详情请求 URL 写 `/product/${sku_id}`。压测跑完你会在 Debug Sampler / 请求 URL 里直接看到是否有 `NOT FOUND` 进入链路——如果商品列表在压力下开始返回空数组，`sku_id` 就会变成 `NOT FOUND`，你能立刻定位"是列表接口先出问题，而不是详情接口慢"。**这就是利用"缺省值"做链路级健康信号的价值。**

【面试考察】
面试官："JMeter 怎么提取 JSON 响应里的字段？取多个值怎么做？"

参考回答框架：
1. 元件：后置处理器里的 JSON Extractor，用 JSON Path 定位（如 `$.data.token`）
2. 参数三要素：变量名 + JSON Path + 缺省值（建议 `NOT FOUND` 让失败可见）
3. 多值场景：Match No. 用 `-1`（全部）并勾 Compute concatenation var，生成 `变量名_ALL`
4. 验证：配 Debug Sampler 检查变量；下游请求用 `${变量名}` 引用

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| Mock/调试时缺省值留空 | 取不到值时变量为空，下游请求参数变成空串更难排查；建议固定 `NOT FOUND`（原文建议） |
| Match No. 用 0（随机）却要求结果可复现 | 随机取值会让同一份脚本每次压的数据不同，问题无法复现；单值场景用 1 |
| 忘记勾 Compute concatenation var 却想用 `变量名_ALL` | 不勾就不会生成拼接变量（原文参数说明） |
| 只配了提取器就以为链路正确 | 提取失败不报错、会静默传播；必须用 Debug Sampler / 断言验证 |
| 路径写错（多加/少加一层 `data`） | 接口包装结构变化后路径要同步改；表现为"一直取到缺省值" |
| 用 JSON Extractor 提取 HTML 页面里的信息 | 响应不是 JSON 时提取必然失败；HTML/XML 用 XPath 提取器（知识点4） |

【我的理解】引导题（用自己的话回答）：
1. 为什么课程建议把缺省值设成 `NOT FOUND` 而不是留空？它在压测报告与排错中分别带来什么好处？
2. 一个列表接口返回 20 个 ID，你要把它们全部传给后续请求，参数该怎么配（Match No. + 勾选项）？

### 知识点3：Regular Expression Extractor（正则表达式提取器）

【课程原话/定义】
正则表达式提取器（Regular Expression Extractor）是 JMeter 中一种常用的后置处理器，用于从响应数据中提取特定模式的信息。通过使用正则表达式，可以方便地从文本数据中提取所需的内容，如从 HTML、XML、JSON 或普通文本中提取特定信息。

相关参数说明：

| 参数 | 含义（课程原文） |
|------|------------------|
| 引用名称（Name of created variable） | 请求要引用的变量名称，如填写 `result_num` |
| 正则表达式（Regular Expression） | 业务对应的正则表达式 |
| 模板（Template） | 对应正则表达式的组号，从 1 开始；比如：`$1$` 表示取 id 的值，`$2$` 表示取 name 的值，也就是对应到表达式中的第几个括号 |
| 匹配数字（0 代表随机） | 0 代表随机取值，n 取第几个匹配值，-1 匹配所有；比如取 1 表示报文中的第 1 个对象匹配，取 2 表示报文中的第 2 个对象匹配 |
| 缺省值（Default Value） | 如果参数没有取得到值，那默认给一个值 |

课程案例：通过正则表达式提取器提取百度首页标签为 `title` 中的值，将其赋值给变量保存。
1. 步骤一：添加百度的 HTTP Request，添加对应的正则表达式提取器，添加查看结果树和 Debug Sampler
2. 步骤二：在正则表达式提取器元件中添加配置——变量名 `title_ex`，正则表达式 `<title>(.+?)</title>`，设置对应的模板
3. 步骤三：查看结果，提取出 `title` 标签包含的内容并赋值给对应的变量名

【为什么？】
正则表达式提取器是三个提取器里**最通用**的：JSON 提取器只能在 JSON 上工作、XPath 提取器只能在 XML/HTML 上工作，而正则对**任意文本**都有效——这就是为什么它能处理"HTML 里夹着 JSON、JSON 里夹着 HTML 转义"这种脏响应。

但它也是最容易写错的，关键在**模板与括号的对应关系**：
- 正则里的每对括号就是一个捕获组，从 1 开始编号（课程原文强调）；
- 模板 `$1$`/`$2$` 决定"把第几个捕获组的值写进变量"——**不是整段匹配结果**；
- 所以像 `<title>(.+?)</title>` 这种写法，`$1$` 拿到的是 `title` 标签内的文字，而 `$0$` 才是整段 `<title>...</title>`。

`.+?` 里的 `?`（非贪婪）在这里至关重要：没有它，正则会一路吃到**最后一个** `</title>`，在多标题的页面上就会提取出一整段垃圾数据。这也是"为什么教程都写 `(.+?)`"的原因。

【必须掌握】

| 参数 | 说明 | 实践建议 |
|------|------|----------|
| 引用名称 | 提取结果存入的变量名（如 `title_ex`、`result_num`） | 用见名知意的名字，后续 `${title_ex}` 引用 |
| 正则表达式 | 业务对应的正则 | 用 `(.+?)` 非贪婪匹配；`.*?` 用于可有可无的内容（【扩展知识】） |
| 模板 | 捕获组编号，从 1 开始（`$1$`、`$2$`…） | 与括号一一对应；多组可以组合成 `$1$_$2$` 形式拼一个值（【扩展知识】） |
| 匹配数字 | 0 随机 / n 第几个 / -1 所有 | 需要可复现就用 1；需要"全部"才用 -1 |
| 缺省值 | 没取到时的默认值 | 设成显眼的值（如 `NOT FOUND`）便于发现提取失败 |
| 验证方式 | Debug Sampler 看变量；View Results Tree 看响应文本 | 先用 1 线程 1 次循环调通提取器 |

【企业场景】
你压一个老系统的服务端渲染页面：登录后页面里有一行隐藏域 `<input type="hidden" name="csrfToken" value="xxxx">`，后续每个表单提交都要带上它。这种场景 JSON 提取器用不上，企业做法就是用正则提取器：正则 `name="csrfToken" value="(.+?)"`、模板 `$1$`、引用名 `csrf`，后续请求参数里写 `${csrf}`。**换个接口，如果隐藏域的顺序变了、属性顺序变了（`value` 在 `name` 前面），正则就要跟着改**——这也是为什么"能结构化的接口优先用 JSON/XPath 提取器，正则留给非结构化响应"。

【面试考察】
面试官："JMeter 正则表达式提取器的模板 `$1$` 是什么意思？匹配数字怎么选？"

参考回答框架：
1. 模板对应正则里捕获组的编号，从 1 开始：`$1$` = 第 1 个括号的内容，`$2$` = 第 2 个括号
2. 匹配数字：0 随机、n 取第 n 个匹配、-1 取所有匹配（多值场景）
3. 缺省值用于提取失败时兜底，建议设成显眼值便于发现失败
4. 实战要点：用非贪婪 `(.+?)` 避免跨标签匹配；提取器只在必要处挂，避免污染变量

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 模板写成 `$0$` 却以为拿到括号里的值 | `$0$` 是整段匹配结果；括号内的值要用 `$1$` |
| 用贪婪的 `(.+)` 提取多标签页面 | 会跨标签吃到最后一个匹配；用 `(.+?)` 非贪婪 |
| 匹配数字用 0（随机）却需要可复现 | 随机取值使脚本行为不可复现；确定取第几个就写具体数字 |
| 提取失败不设缺省值 | 变量为空会让下游请求参数变空串，问题更难定位 |
| 用正则去啃 JSON | 字段顺序/空格一变就失效；JSON 响应优先用 JSON Extractor |
| 正则写在多个提取器里重复维护 | 同一变量在多个提取器里重复提取会造成覆盖；一处提取、多处引用 |

【我的理解】引导题（用自己的话回答）：
1. 正则 `<title>(.+?)</title>` 中，`$1$` 和 `$0$` 分别得到什么？如果把 `?` 去掉会有什么后果？
2. 什么情况下你会放弃正则提取器、改用 JSON 提取器？请从"响应格式是否稳定"的角度回答。

### 知识点4：XPath Extractor（XPath 提取器）

【课程原话/定义】
XPath 提取器（XPath Extractor）是 JMeter 中的一种后置处理器，用于从 XML 或 HTML 类型的响应数据中提取特定内容。XPath 是一种用于在 XML 或 HTML 文档中导航和选择节点的语言，XPath 提取器允许使用 XPath 表达式来确定需要提取的数据位置，并将其存储为 JMeter 变量以供后续请求使用。

相关参数说明：

| 参数 | 含义（课程原文） |
|------|------------------|
| 引用名称（Name of created variables） | 请求要引用的变量名称，如填写 `result_num` |
| XPath query | 用于提取值的 XPath 表达式 |
| 匹配数字（0 代表随机） | 0 代表随机取值，n 取第几个匹配值，-1 匹配所有；比如取 1 表示报文中的第 1 个对象匹配，取 2 表示报文中的第 2 个对象匹配 |
| 缺省值（Default Value） | 如果参数没取得到值，那默认给一个值 |

课程案例：通过 XPath 提取器提取百度首页标签为 `title` 中的值，将其赋值给变量保存。
1. 步骤一：添加百度的 HTTP Request，添加对应的 XPath 提取器，添加查看结果树和 Debug Sampler
2. 步骤二：在 XPath 提取器元件中添加配置——变量名 `title`，XPath 表达式 `//title`
3. 步骤三：查看结果，提取出对应内容并赋值给对应的变量名

（【扩展知识】XPath 提取器与 XPath 断言所在的元件面板都涉及 XML 解析选项：处理 HTML 页面时需要启用 Tidy 容错解析，XML/XHTML 则不需要——同一个知识点在 [[Ch21-JMeter断言元件的使用]] 的 XPath Assertion 里已详述，提取器侧同理。）

【为什么？】
XPath 提取器适合"**结构稳定、字段位置固定**"的响应，尤其是老系统常见的 XML 报文。它的优势与 XPath 断言一致：无视文本顺序和空白，按节点路径定位。比如 SOAP 报文里 `<soap:Envelope><soap:Body><ns:orderId>10086</ns:orderId>...`，用 `//*[local-name()='orderId']` 就能稳定取到。

但要记住它的定位属于"**解析型提取**"——比正则重（要解析 XML/HTML 树），因此：
1. **能用 JSON 提取器就别用 XPath**（JSON 解析比 HTML 容错解析轻）；
2. 大响应体上挂多个 XPath 提取器会叠加 CPU 开销，施压机压力会上升；
3. 与断言的分工依然成立：**XPath 提取器取"值"，XPath 断言判"存在与否/真伪"**——这也是课程原文里 XPath 断言页误把"引用名称（提取器参数）"写进去的根本原因：两者确实长得像，但一个输出值、一个输出判定结果。

【必须掌握】

| 参数 | 说明 | 实践建议 |
|------|------|----------|
| 引用名称 | 提取结果变量名 | 后续 `${title}` 引用 |
| XPath query | XPath 表达式（如 `//title`） | 先在浏览器/在线 XPath 工具里验证表达式能定位到节点 |
| 匹配数字 | 0 随机 / n 第几个 / -1 所有 | 单节点 `//title` 用 1；多节点列表用 -1 |
| 缺省值 | 未取到时的默认值 | 设 `NOT FOUND` 之类的显眼值 |
| 适用响应 | XML / HTML（服务端渲染页、SOAP） | JSON 响应**不要**用 XPath 提取器 |
| 与 XPath 断言的区分 | 提取器 = 取值（变量）；断言 = 判定（通过/失败） | 需要"既取值又校验"时两个都要挂（【扩展知识】） |

【企业场景】
你压一个银行老系统的 XML 接口：下单请求要带上游返回的 `<tradeNo>`。做法：上游请求下挂 XPath 提取器，表达式 `//tradeNo`（或带命名空间的 `//*[local-name()='tradeNo']`），引用名 `trade_no`，缺省值 `NOT FOUND`；下游请求参数写 `${trade_no}`。同时在上游请求上挂一条 XPath 断言确认 `<tradeNo>` 存在——**取值和判定分开两层，一旦报告出现异常，你能立刻分辨是"取值失败"还是"系统没返回该字段"。**

【面试考察】
面试官："JMeter 三个提取器（JSON / 正则 / XPath）怎么选？"

参考回答框架：
1. 按响应格式选：JSON → JSON Extractor；XML/HTML → XPath Extractor；非结构化文本 → 正则表达式提取器
2. 按稳定性选：结构稳定优先结构化提取（JSON/XPath），格式会漂移的脏文本才用正则
3. 按开销选：正则最轻、XPath 需要解析树稍重、JSON 解析成本可控；大并发下元件数量要克制
4. 通用要点：都要设缺省值、都要用 Debug Sampler 验证、都要挂在上游请求之下

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 用 XPath 提取器处理 JSON 响应 | JSON 不是合法 XML，提取必然失败；JSON 用 JSON Extractor |
| 表达式里有命名空间却不处理 | 带 `soap:`/`ns:` 前缀时需要命名空间兼容写法或用 `local-name()`（【扩展知识】） |
| 把"引用名称"当成断言参数 | 那是提取器的参数；断言元件不产生变量（课程 XPath 断言页原文的串入错误，见 [[Ch21-JMeter断言元件的使用]] 知识点4勘误） |
| 只挂提取器不挂断言 | 提取失败会静默用缺省值继续跑，必须另配断言/调试元件 |
| 大响应体上挂多个提取器 | 每个提取器都要解析一遍响应树，CPU 开销叠加；必要时合并表达式 |
| 用浏览器渲染后的 DOM 结构写 XPath | 浏览器会补全 DOM 并执行 JS；JMeter 只解析原始响应体（【扩展知识】） |

【我的理解】引导题（用自己的话回答）：
1. 请用一个业务例子说明"XPath 提取器 + XPath 断言"为什么要同时挂，而不是只挂一个。
2. 如果同一个 XML 响应里你需要同时取 5 个字段，你会挂 5 个提取器还是 1 个？说说你的取舍依据。

### 知识点5：三种提取器横向对比与变量机制（含调试方法）

【课程原话/定义】
课程总结（原文）：后置处理器简介、常见的后置处理器的使用。三个提取器的参数结构高度相似：**引用名称 + 表达式 + 匹配数字 + 缺省值**（JSON 提取器额外有 `Compute concatenation var(suffix_ALL)`）。

【为什么？】
学完三个提取器要能回答一个问题：**它们的差异到底在哪？** 差异只有一个维度——**"表达式按什么规则定位值"**：正则按字符模式、JSON Path 按 JSON 结构、XPath 按 XML/HTML 结构。而"提取出来之后怎么用"完全一样：都是写进 JMeter 变量，后续请求用 `${变量名}` 引用。

变量的生命周期要讲清（这是排错的地基）：
1. 变量是**线程内**的（每个线程各有一份自己的变量值），所以 100 个线程能各自持有自己的 `token`——这正是并发用户独立的物理基础；
2. 提取器写入的变量**在本线程的后续取样器中可用**，但不能跨线程共享（要跨线程共享需用属性 `props` 等机制）（【扩展知识】）；
3. 变量名大小写敏感，`${token}` 与 `${Token}` 是两个不同的东西，**引用不到时 JMeter 不报错，而是原样把 `${token}` 发出去**——这是最难排查的坑。

【必须掌握】

| 对比项 | JSON Extractor | 正则表达式提取器 | XPath 提取器 |
|--------|----------------|------------------|--------------|
| 适用响应 | JSON | 任意文本（HTML/JSON/XML/纯文本） | XML / HTML |
| 表达式 | JSON Path（`$.data.token`） | 正则（`(.+?)` + 模板 `$1$`） | XPath（`//title`） |
| 变量名参数 | names of created Variable | 引用名称 | 引用名称 |
| 多值支持 | Match No. -1 + Compute concatenation var（`变量名_ALL`） | 匹配数字 -1（【扩展知识】：生成 `变量名_1..n`、`变量名_matchNr` 等） | 匹配数字 -1（同机制） |
| 缺省值 | Default Values | 缺省值 | 缺省值 |
| 维护难度 | 低（结构稳定时最省心） | 高（格式一变就失效） | 中（结构稳定但解析较重） |
| 推荐优先级 | JSON 接口首选 | 兜底最后手段 | XML/HTML 场景首选 |

【企业场景】
你在银行/保险类项目做压测，同一套脚本要处理三种响应：一个 JSON 查询接口、一个返回 HTML 的登录页（需要取隐藏域）、一个返回 XML 的回调通知。企业做法是"**按响应格式分工**"：JSON 用 JSON Extractor、HTML 隐藏域用正则或 XPath（HTML 用 XPath 记得启用 HTML 容错解析）、XML 用 XPath 提取器；全部提取器都挂在**各自的请求之下**，变量名统一命名规范（如 `token`、`csrf`、`trade_no`），并全部设置 `NOT FOUND` 缺省值。调试期统一用 Debug Sampler 观察变量值，**正式压测前删除 Debug Sampler 与 View Results Tree**——它们会把每个响应都留在内存里，几个回合就能把施压机压垮。

【面试考察】
面试官："JMeter 里关联（提取）失败你怎么排查？"

参考回答框架：
1. 第一步看"值有没有被取到"：Debug Sampler 里查变量值是否为缺省值（`NOT FOUND`）
2. 第二步看"引用有没有生效"：View Results Tree 的 Request 面板，确认 `${变量}` 被替换成了真实值
3. 第三步定位原因：表达式与真实响应不匹配（结构变了/格式变了）、提取器挂错层级、变量名大小写不一致、上游请求本身失败
4. 预防：缺省值设显眼值 + 关键变量加断言 + 调试元件在小样本下先验证

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 调试元件留在正式压测计划里 | Debug Sampler / View Results Tree 会累积响应数据占内存，正式压测前必须移除（【扩展知识】） |
| 以为变量能跨线程共享 | 变量是线程内独立的；跨线程需要属性或其他机制（【扩展知识】） |
| 依赖缺省值"兜住"提取失败 | 缺省值只保证脚本不中断，不保证业务正确；失败必须显式暴露（断言/检查报告） |
| 一个变量被多个提取器写入 | 后执行的提取器会覆盖前面的值，排查时容易误判；一变量一处提取 |
| 只看 Debug Sampler 不看请求体 | 变量取到了不等于请求引用正确；两层都要看 |

【我的理解】引导题（用自己的话回答）：
1. 请把三个提取器的差异压缩成一句话（提示：差异只在"表达式按什么规则定位值"）。
2. 为什么"变量是线程内独立的"这件事，是"100 个线程 = 100 个并发用户"能成立的物理基础？
