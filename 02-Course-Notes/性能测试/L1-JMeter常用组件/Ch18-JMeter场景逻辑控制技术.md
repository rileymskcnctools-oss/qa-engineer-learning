### 知识点1：什么是逻辑控制器，以及它的四种使用场景

【课程原话/定义】
> 使用 “Logic Controller” 来添加所需的逻辑控制器。配置逻辑控制器的参数，如条件、循环次数等。在逻辑控制器下添加相应的子元素，如 HTTP 请求、定时器等。

课程给出的 **逻辑控制器的使用场景**（原文四条）：

| 使用场景 | 课程原文描述 | 涉及的控制器 |
|---|---|---|
| 处理动态场景 | 可以根据动态条件来控制测试脚本的执行流程，使得测试更加灵活 | If Controller、Switch Controller |
| 模拟循环场景 | 可以模拟用户的循环操作，例如循环登录、循环浏览等 | While Controller、ForEach Controller |
| 组织事务 | 可以将一系列相关操作组织成一个事务，方便统计和分析 | Transaction Controller |
| 灵活处理异常 | 在逻辑控制器中添加适当的断言，根据条件决定是否执行下一个请求，从而模拟用户在特定情况下的行为 | 断言 + 逻辑控制器组合 |

课程总结一句话：**掌握逻辑控制器在实际场景中的使用。**

【为什么？】
线性录制的脚本是「一条直线」：从上到下每个取样器都无条件执行一次。而真实用户是有判断、有循环、有分支的。JMeter 的元件树天生只能表达「顺序」，逻辑控制器就是给这棵树装上「调度器」——它本身**不发送任何请求**，只决定自己的子节点「执行几次 / 要不要执行 / 按哪个分支执行 / 统计上算不算一个整体」。这就是为什么课程反复强调：逻辑控制器解决的不是「能不能发请求」，而是「请求按什么业务逻辑发」。

【必须掌握】

| 分类 | 控制器 | 一句话作用 |
|---|---|---|
| 条件类 | If Controller | 条件成立才执行子节点 |
| 条件类 | Switch Controller | 按值在多分支中选一个执行 |
| 循环类 | Loop Controller | 按固定次数（或 Forever）重复子节点 |
| 循环类 | While Controller | 条件成立就持续循环 |
| 循环类 | ForEach Controller | 遍历一组变量（如读取 CSV 多行） |
| 事务类 | Transaction Controller | 把一组取样器合并成一个事务统计 |
| 流量分配类 | Throughput Controller / Random Controller / Interleave Controller | 控制子节点执行的比例与顺序 |

添加路径（课程步骤的通用形式）：`测试计划 → 线程组 → (右键) Add → Logic Controller → 选择具体控制器 → 在其下 Add → Sampler/Timer/Assertion`。

【企业场景】
你在真实项目里写压测脚本，第一次做「单接口基准测试」时确实用不到逻辑控制器。但只要需求变成「模拟用户从登录到下单的完整链路」，需求方给你的是一句话业务描述而不是接口清单——你必须自己把这句话翻译成元件树：哪一步可能跳过、哪一步要重复、哪几步要合并成一个事务。这时逻辑控制器就是你的「业务流程图解释器」，缺了它，你只能给每个分支录一套脚本，维护成本会随分支数量指数上升。

【面试考察】
1. **面试官怎么问**：「JMeter 的逻辑控制器有哪些？分别在什么场景下用？」
   **回答框架**：先分类（条件 / 循环 / 事务 / 流量），每类举 1 个代表控制器 + 1 个业务场景，最后补一句「逻辑控制器本身不产生请求，只控制子节点的执行」。
2. **面试官怎么问**：「录制的脚本能直接用吗？」
   **回答框架**：不能。录制出来是线性无分支的，且包含大量无关静态资源请求；需要删减、用逻辑控制器还原业务分支、做参数化和关联。
3. **面试官怎么问**：「你怎么保证压测场景和真实流量分布一致？」
   **回答框架**：业务流程拆分支 → 用逻辑控制器 + 流量分配组件按比例分配（如 3:5:2）→ 用聚合报告验证各分支的 samples 比例是否符合预期。

【易错点】

| 常见错误 | 正确理解 |
|---|---|
| 以为「加了一个逻辑控制器就会多出一个请求」 | 逻辑控制器不发送请求，它只是子节点的调度器；你看到的 samples 全部来自取样器 |
| 认为逻辑控制器加在「测试计划」下面和加在「线程组」下面效果一样 | 加在测试计划层级的逻辑控制器被所有线程组共享，加在线程组内只作用于该线程组；层级决定作用域 |
| 逻辑控制器只对「紧接着的一个请求」生效 | 它对本层级下**所有**子节点生效（可嵌套），作用域是整棵子树 |
| 把定时器、配置元件当成「独立元件」随便放 | 放在逻辑控制器内的定时器/配置元件会作用于该子树，位置变了行为就变了 |

【我的理解】
1. 如果把「逻辑控制器不发送请求」这一点想透，那么你在看聚合报告时，`Samples` 这一列统计的到底是谁的执行次数？你能不能据此反推自己脚本里每个分支实际跑了多少次？
2. 课程说逻辑控制器能「组织事务」，那请你先自己想：不用事务控制器，只靠给取样器改名字，能不能得到一样的事务级指标？为什么？

### 知识点2：If Controller（条件控制器）—— 让脚本按条件走

【课程原话/定义】
> 处理动态场景：使用 If Controller 和 Switch Controller 可以根据动态条件来控制测试脚本的执行流程，使得测试更加灵活。

原文只在「使用场景」里提到 If Controller 的动态条件能力，**没有展开参数细节**，下面的参数说明为【扩展知识】，来源于 JMeter 通用用法。

【扩展知识】If Controller 常用参数：

| 参数 | 含义 |
|---|---|
| Name / Comments | 名称与注释，注释里写清这个分支的业务含义（强烈建议） |
| Expression | 条件表达式，如 `${__jexl3("${token}" != "")}` |
| Interpret Condition as Variable Expression? | 勾选后按变量/表达式求值（推荐）；不勾选则用 JavaScript 引擎求值（慢，新版已弱化 JS 支持） |
| Evaluate for all children? | 勾选则每个子节点执行前都重新求值；不勾选只在进入控制器时求值一次 |

【为什么？】
如果没有条件控制器，你要模拟「有 20% 用户是未登录状态」就只能手工改脚本、跑两次。有了 If Controller，条件可以来自 `${__Random(1,100)}`、`${token}`、上一个请求的提取结果——**脚本的流程由运行时数据驱动，而不是由脚本文件本身写死**。这一点和参数化是同一个思想：把「写死的」变成「运行时决定的」。JMeter 之所以推荐勾选 Interpret Condition as Variable Expression，是因为它走的是变量表达式求值而不是内嵌 JS 解释器，性能开销小得多，在高并发下差异明显。

【必须掌握】

| 写法 | 效果 |
|---|---|
| `${__jexl3(${count} > 3)}` | 数字比较 |
| `${__jexl3("${token}" != "")}` | 字符串判空（最常用：判断业务是否已登录） |
| `${__jexl3(${__Random(1,100)} <= 20)}` | 约 20% 概率进入该分支 |
| `${__groovy(...)}` | 复杂逻辑，可用 Groovy 写多行脚本 |

【企业场景】
你要压测电商的「下单」接口，但登录态有时有效有时失效（服务端有 session 过期策略）。你的做法是：在 If Controller 里判断 `${token}` 是否为空，为空就走「登录 → 提取 token」，不为空就跳过登录直接下单。这样一套脚本能同时覆盖「已登录用户」和「session 过期需重新登录」两种真实情况，而且不会因为 token 失效导致整轮压测大面积 401。

【面试考察】
1. **面试官怎么问**：「JMeter 里怎么实现 if 判断？」
   **回答框架**：用 If Controller，表达式建议勾选 Interpret Condition as Variable Expression 并用 `__jexl3`；举一个「判断 token 是否为空决定是否登录」的例子；补充 Evaluate for all children 的取舍。
2. **面试官怎么问**：「条件依赖于上一个请求的结果，怎么拿到？」
   **回答框架**：先在上游请求上加 JSON 提取器 / 正则提取器把值存成变量，再在 If Controller 里引用该变量比较。
3. **面试官怎么问**：「你怎么在压测里控制某分支的流量占比？」
   **回答框架**：随机数 + If Controller，或用 Throughput Controller 按百分比；注意实际比例会受随机波动影响，要看聚合报告的 samples 数验证。

【易错点】

| 常见错误 | 正确理解 |
|---|---|
| 表达式字符串里忘了加引号，如 `${token} != ""` 直接写 | 变量比较必须靠 `__jexl3`/`__groovy` 包裹，且字符串要带引号：`${__jexl3("${token}" != "")}` |
| 用 `if (${a} == "1")` 这种 JS 语法但不勾选 Interpret Condition as Variable Expression | 不勾选时按 JS 求值，行为与勾选时不同；高版本 JMeter 已默认不推荐 JS，混用极易出错 |
| 用 `${count} >= 3` 但 count 是字符串导致比较结果不符合预期 | JMeter 变量本质是字符串，数字比较要交给 `__jexl3`/`__groovy` 转换后再比 |
| 认为条件不成立时控制器内的定时器/断言也不生效 | 条件不成立时整个子树被跳过，子树内的定时器与断言同样不会执行 |

【我的理解】
1. 如果我用 `${__Random(1,100)} <= 20` 作为条件，希望在压测中「大约 20% 的请求进入分支」，那么在 10000 个样本下，聚合报告里这个分支的 samples 一定会等于 2000 吗？为什么不一定，你打算怎么验证实际比例？
2. 「Evaluate for all children」勾上和不勾上，对「循环 10 次、每次都要重新判断条件」的场景分别意味着什么？请你自己举一个必须勾选它的业务例子。

### 知识点3：循环类控制器（Loop / While / ForEach）—— 模拟重复操作

【课程原话/定义】
> 模拟循环场景：使用 While Controller 和 ForEach Controller 可以模拟用户的循环操作，例如循环登录、循环浏览等。

原文只点出了 While 与 ForEach 的用途，**参数细节为【扩展知识】**。

【扩展知识】三种循环控制器对比：

| 控制器 | 关键参数 | 结束条件 |
|---|---|---|
| Loop Controller | Loop Count（次数）、Forever（无限循环） | 固定次数 |
| While Controller | Condition（条件表达式） | 条件为假时停止；可用 `${__jexl3(...)}`、`${变量}`、`LAST` |
| ForEach Controller | Input variable prefix、Start index、End index、Output variable name、Add "_" before number | 变量集合遍历完 |

`LAST` 是 While Controller 的特殊条件：当循环体内的最后一个取样器失败（或没有子节点）时返回 true，从而结束循环，常用来做「一直重试直到成功」或「翻页直到没有下一页」。

【为什么？】
循环有两层：**线程组的循环**决定「一个虚拟用户完整跑几轮」，**循环控制器**决定「某一组请求在每一轮里重复几次」。两者是乘法关系：线程数 10、线程组循环 5 次、循环控制器 3 次，则该循环体下的取样器总共执行 10×5×3=150 次。很多人算错了总请求数，就是因为漏掉了这个乘法。另外，While + 计数器是 JMeter 里少数能表达「不确定次数」的方式——真实用户的浏览行为本来就是次数不定的。

【必须掌握】

| 需求 | 组件写法 |
|---|---|
| 每个用户连续浏览 5 个商品页 | Loop Controller：Loop Count = 5，内部放「商品详情」请求，路径用 `${__counter(FALSE)}` 参数化 |
| 一直翻页直到没有下一页 | While Controller：Condition = `${__jexl3("${hasNext}" == "true")}`，内部用 JSON 提取器取下一页标记 |
| 把 CSV 里读到的 10 行数据各用一次 | ForEach Controller：Input variable prefix = `product`，Output variable name = `curProduct` |
| 循环登录 3 次（模拟反复登录） | Loop Controller：Loop Count = 3，内部放登录请求 |

【企业场景】
你压测「商品列表翻页」场景，需求方说「真实用户平均翻 3~5 页，少数会一直翻到底」。你的实现是：外层用 While Controller 配合 JSON 提取器读取 `nextPage` 字段（接口返回 null 时结束），内层用 Loop Controller 保证至少执行 1 次翻页。这样每个虚拟用户的翻页深度是数据驱动的，不会出现「脚本固定翻 10 页，压出来的 QPS 比线上高一倍」这种失真。验证阶段你要用聚合报告检查「商品列表」取样器的 samples 数是否与预期翻页总次数吻合。

【面试考察】
1. **面试官怎么问**：「JMeter 里怎么实现循环？有几种方式？」
   **回答框架**：线程组循环次数（整轮重复）、Loop Controller（固定次数）、While Controller（条件驱动）、ForEach Controller（遍历变量）；重点是区分「线程组循环」和「控制器循环」的乘法关系。
2. **面试官怎么问**：「怎么模拟次数不确定的重复操作？」
   **回答框架**：While Controller + 计数器/提取器，条件来自上一个响应；或者用 `LAST` 条件做重试直到成功。
3. **面试官怎么问**：「线程数 10、线程组循环 2 次、Loop Controller 循环 3 次，某个请求总共发多少次？」
   **回答框架**：10×2×3=60 次，如果能顺便说出「再乘上分布式压测的节点数」就更完整。

【易错点】

| 常见错误 | 正确理解 |
|---|---|
| 只改 Loop Controller 的循环次数，忘了线程组本身还有循环次数 | 总次数是「线程数 × 线程组循环 × 控制器循环」的乘积，要联合看待 |
| While Controller 的条件写成死循环（条件恒真） | 必须有能让条件变为假的变量更新（计数器、提取器），否则该线程永远出不来，压测跑不完 |
| 用 ForEach 但变量前缀写错（如实际是 `product_1` 却写 `product`） | 前缀不含下划线，ForEach 会自动拼 `_序号`；序号还要和 Start/End index 对上 |
| 认为 ForEach 能遍历任意多个变量集合 | 一次只遍历一个前缀对应的编号区间，多组数据要么分批、要么换 CSV + 循环 |

【我的理解】
1. 假设你的脚本里有个 While Controller，条件是 `${__jexl3(${counter} < 5)}`，但你把计数器放在了 While 控制器**外面**——结果会怎样？请你自己推演一遍执行过程，再回答「计数器应该放在哪一层」。
2. 「用 ForEach 遍历 CSV 的 10 行数据」和「用 CSV Data Set Config + 线程组循环 10 次」，两者的样本总量一样，但压测的含义有什么本质区别？

### 知识点4：Switch Controller（多分支选择）

【课程原话/定义】
> 处理动态场景：使用 If Controller 和 Switch Controller 可以根据动态条件来控制测试脚本的执行流程，使得测试更加灵活。

原文未展开 Switch Controller 的参数，以下为【扩展知识】。

【扩展知识】

| 参数 | 说明 |
|---|---|
| Switch Value | 数字：按 0 开始的下标选子节点；字符串：按子节点名称匹配；为空时只执行第一个子节点 |
| （子节点顺序） | 数字索引与子节点在树中的顺序强绑定，拖动顺序会改变索引含义 |

对比 If Controller：If 是「二值开关（真/假）」，Switch 是「多路选择器（N 选 1）」。当分支数 > 2 时，用一堆 If 嵌套会非常难维护，Switch 更合适。

【为什么？】
业务里的分支往往是「枚举型」而不是「布尔型」：支付方式（支付宝 / 微信 / 银行卡）、用户等级（普通 / 白银 / 黄金）、渠道（APP / H5 / 小程序）。这类分支如果用 If 表达，需要 N-1 层嵌套，树深、难读、易错。Switch 把这些枚举收平成同一层的 N 个子节点，脚本结构与业务字典一一对应，改一个分支不会影响其他分支。本质上它降低了脚本的**分支复杂度**，而分支复杂度直接决定脚本的可维护性和出错率。

【必须掌握】

| 场景 | Switch Value 写法 | 说明 |
|---|---|---|
| 按支付方式分支 | `${payType}` 且子节点名分别为 `alipay`、`wechat`、`bankcard` | 字符串按名称匹配 |
| 按用户等级分支 | `${__jexl3(${level})}` 或直接 `${level}` 配数字子节点 | 数字按下标匹配，从 0 开始 |
| 兜底分支 | 把最常用的分支放在第 1 个子节点位置 | Switch Value 为空时执行第一个子节点 |

【企业场景】
你压测支付链路，产品说「三种支付方式的流量比是 5:3:2」。你不可能维护三套脚本——切一套、跑一轮、再切一套，每次都要重新准备测试数据和监控。你的做法是：CSV 里准备 `payType` 列，按 5:3:2 的比例重复铺满数据，Switch Controller 挂在支付请求上层，一个脚本、一轮压测就同时压到三种支付通道；跑完看聚合报告里三个分支的 samples 比例，验证是否落在预期区间。发布前用这一套脚本回归，能一次发现「微信通道超时」这类单通道问题。

【面试考察】
1. **面试官怎么问**：「If 和 Switch 怎么选？」
   **回答框架**：二值条件用 If、枚举多分支用 Switch；Switch 用参数化值驱动，避免为每个分支维护独立脚本。
2. **面试官怎么问**：「Switch 的数字索引从几开始？」
   **回答框架**：从 0 开始，对应子节点在树中的顺序，顺序变了索引含义就变——这是最容易踩的坑。
3. **面试官怎么问**：「怎么保证多分支脚本的流量比例符合预期？」
   **回答框架**：数据侧按比例铺 CSV 行 + 聚合报告验证 samples 分布 + 必要时用吞吐量控制器兜底。

【易错点】

| 常见错误 | 正确理解 |
|---|---|
| 以为 Switch 的数字索引从 1 开始 | 从 0 开始，0 代表第一个子节点 |
| 用字符串匹配但子节点名称带空格/大小写不一致 | 默认按名称精确匹配，改名前先确认脚本引用，命名要规范化 |
| 调整了子节点顺序后没意识到数字分支走错了 | 数字索引与树顺序绑定，任何拖拽调整都要重新验证所有分支 |
| 把 Switch 当成「会执行多个子节点」 | Switch 每次只选一个分支执行，它是 N 选 1，不是批量执行 |

【我的理解】
1. 如果业务分支从 3 个增长到 8 个，你更愿意维护「8 个 If Controller 串联」还是「1 个 Switch + 8 个子节点」？请从「改需求时你要动几处脚本」这个角度说明理由。
2. 当 Switch Value 匹配不到任何子节点名称时，JMeter 会怎么做？你打算怎么给这种「兜底」情况做防护？

### 知识点5：Transaction Controller（事务控制器）—— 让统计口径等于业务口径

【课程原话/定义】
> 组织事务：使用 Transaction Controller 可以将一系列相关操作组织成一个事务，方便统计和分析。

【扩展知识】常用参数：

| 参数 | 说明 |
|---|---|
| Generate parent sample | 勾选后聚合报告里只出现一个「父事务」行，子取样器不再单独成行；不勾选则父子都统计 |
| Include duration of timer and pre-post processors in generated sample | 勾选后事务耗时会算上定时器与前/后置处理器，更贴近用户真实等待时间 |

【为什么？】
性能指标必须与业务口径对齐，否则没有意义。用户说的「下单用了 2 秒」指的是从点击按钮到看到结果，中间包含页面跳转、加载等待；而 JMeter 默认只统计单个 HTTP 请求的耗时。如果不用事务控制器，你报给业务方的是「下单接口 200ms」，业务方测出来是「下单 2s」，双方永远对不齐。事务控制器的作用就是把「多个原子请求」聚合成「一个用户可感知的操作」，让 TPS 和响应时间的分子分母与业务定义一致。这也是为什么课程把它归类为「组织事务、方便统计和分析」，而不是归类为流程控制。

【必须掌握】

| 事务定义 | 包含的取样器 | 统计意义 |
|---|---|---|
| 登录事务 | 打开登录页 + 提交账号密码 + 校验登录成功 | 用户感知的「登录」耗时 |
| 下单事务 | 加入购物车 + 提交订单 + 查询订单状态 | 用户感知的「下单」耗时 |
| 支付事务 | 发起支付 + 支付回调 + 支付结果查询 | 用户感知的「支付」耗时 |

注意：事务的响应时间 ≈ 内部各取样器耗时之和（含等待），TPS 按「事务数/时间」计算，而不是按请求数。

【企业场景】
你所在团队要对「下单」做 SLA 承诺：P95 < 500ms。这个数字只能建立在事务口径上。你的做法是：用 Transaction Controller 包住「加购 → 提交订单 → 查订单」，勾选 Generate parent sample，然后看聚合报告里「下单事务」那一行的 95% Line；同时把子请求也保留统计（不勾 Generate parent sample，或另跑一轮），以便定位是哪个子步骤拖慢的。上线后如果只看到「订单接口慢」，你能立刻下钻到子请求；如果只看子请求，你就无法回答「用户到底等了多久」。

【面试考察】
1. **面试官怎么问**：「TPS 怎么统计的？是基于请求还是基于事务？」
   **回答框架**：先说明两者定义不同，再说压测里通常以「业务事务」为准（Transaction Controller 聚合），并强调统计口径必须和业务方对齐。
2. **面试官怎么问**：「事务控制器里的定时器算不算进事务耗时？」
   **回答框架**：取决于 Include duration of timer and pre-post processors 是否勾选；要模拟用户真实等待就勾上，要纯服务端处理耗时就不勾。
3. **面试官怎么问**：「聚合报告里既有父事务又有子请求，会不会重复计数？」
   **回答框架**：会同时出现两行，做 TPS/吞吐统计时要明确用哪一行，避免把父子相加当成总数。

【易错点】

| 常见错误 | 正确理解 |
|---|---|
| 直接用事务的 samples 数当作「请求总数」报出去 | 一个事务包含多个请求，事务数与请求数不是一回事，报告里要写明口径 |
| 勾了 Generate parent sample 后又去看子请求，发现「找不到」就以为请求没发 | 勾选后子取样器不再单独成行，要看明细得关掉该选项或看查看结果树 |
| 认为事务控制器能「加速」或「合并请求」 | 它只是统计上的分组，请求该发几次还是几次，网络开销一点没少 |
| 事务里放了定时器却没勾 Include duration…，然后抱怨事务耗时比实际短 | 默认不含定时器耗时，要贴近用户感知必须显式勾选 |

【我的理解】
1. 如果你把「登录事务」的 P95 报给业务方是 800ms，业务方自己点了一下是 1.5s，你会从哪几个方向去解释这个差异？（提示：静态资源、定时器、口径。）
2. 一个事务里包含了 3 个请求，第 2 个请求失败但事务控制器本身不会失败——你打算怎么让「事务失败」这件事在报告里体现出来？

### 知识点6：实战——商城购买流程三分支场景

【课程原话/定义】
> 利用 JMeter 逻辑控制器实现测试业务流程中的逻辑变化，即模拟实际业务场景。以用户访问商城购买商品为例，流程图如下图所示。该场景可分为三个分支：
> - 用户未登录仅刷新首页。
> - 用户进行注册登录后进行购买。
> - 用户进行注册登录后仅进行浏览动作。

【必须掌握】把课程的业务描述翻译成元件树：

```text
Test Plan
└─ Thread Group（线程数 N，循环 1）
   ├─ Random / 参数化：userType ∈ {未登录, 已登录-购买, 已登录-浏览}
   └─ Switch Controller（Switch Value = ${userType}）   ← 分支总入口
      ├─ 分支1：未登录-仅刷新首页
      │   └─ HTTP 请求：GET /
      ├─ 分支2：注册登录后购买
      │   ├─ If Controller（${__jexl3("${token}" == "")}）
      │   │   ├─ HTTP 请求：提交注册/登录
      │   │   └─ JSON 提取器：提取 token
      │   └─ Transaction Controller（购买事务）
      │       ├─ HTTP 请求：加入购物车
      │       ├─ HTTP 请求：提交订单
      │       └─ HTTP 请求：查询订单状态
      └─ 分支3：注册登录后仅浏览
          ├─ HTTP 请求：搜索商品
          └─ Loop Controller（Loop Count = 3）
              └─ HTTP 请求：商品详情（路径用 ${__counter(FALSE)} 参数化）
```

三层逻辑叠加：**Switch 选分支 → If 判断前置条件（是否已登录）→ Transaction 聚合业务操作 → Loop 控制浏览深度**。这正是课程说的「用逻辑控制器模拟实际业务场景」。

【为什么？】
单一业务流程的压测只能验证「这条链路顶不顶得住」，无法回答「线上混合流量下系统顶不顶得住」。真实系统的压力是多种用户行为叠加的结果：一部分人只刷首页（高 QPS、低资源消耗），一部分人下单（低 QPS、高资源消耗、涉及写库和事务），一部分人只浏览（中等 QPS、涉及缓存和搜索）。如果只压下单链路，数据库压力被高估、缓存压力被低估，压出来的结论会误导容量规划。三分支模型的价值在于**让各链路的压力比例接近线上真实分布**。

【企业场景】
你接到需求「模拟双 11 前的流量高峰」。你没有直接开最高并发跑下单接口，而是先找业务方要到流量分布：首页浏览 : 浏览商品 : 下单 = 5 : 3 : 2。然后你在 CSV 里按这个比例铺 `userType` 数据，用 Switch Controller 分流；压测后你通过聚合报告核对三个分支的 samples 比例，发现「下单」分支只占 12% 而不是 20%，原因是其中 30% 的未登录用户被 If Controller 挡住了——于是你调整了「已登录用户占比」这个上游参数。这套「比例设计 → 分流 → 报告反查 → 修正」的闭环，就是压测场景设计的实际工作内容。

【面试考察】
1. **面试官怎么问**：「你怎么设计一个混合业务场景的压测脚本？」
   **回答框架**：拉取线上流量分布 → 拆分支 → 用 Switch/If 表达业务逻辑 → 用比例参数控制分流 → 聚合报告反查比例是否达标。
2. **面试官怎么问**：「脚本里怎么表达『用户可能已登录也可能未登录』？」
   **回答框架**：If Controller 判断 token 变量是否为空，为空走登录并提取 token，不空直接继续。
3. **面试官怎么问**：「你怎么知道自己的场景设计是对的？」
   **回答框架**：从两个维度验证——样本分布是否符合预期比例；各分支响应时间与线上监控的差距是否可解释。

【易错点】

| 常见错误 | 正确理解 |
|---|---|
| 三个分支的取样器名称都一样，压完报告分不清谁是谁 | 取样器命名要带分支前缀（如 `[购买]加入购物车`），聚合报告按 Label 分组，命名混乱等于报告不可读 |
| 用固定比例的 `__Random` 做分流，但小样本下比例偏差很大 | 样本量小时随机波动明显；要稳定比例就用 CSV 按比例铺数据或用 Throughput Controller |
| 分支里没有断言，请求全部 401 却以为压测成功 | 每个分支都要加响应断言（状态码 + 业务码），否则「压测通过」可能是全失败 |
| 三条分支共用同一个 token 变量，导致未登录分支也被带上登录态 | 变量的作用域与线程绑定，分支间的登录态要显式管理，不能假设互相隔离 |

【我的理解】
1. 课程流程图里的三个分支，哪一个是「不需要登录态」的？如果某个线程在前一轮跑过登录分支，下一轮跑未登录分支，它会不会残留登录态？你打算怎么保证分支之间互不干扰？
2. 如果业务方说「流量比例我们从线上监控拿不准」，你会用什么办法先跑一轮「探针压测」来反推真实比例？

### 知识点7：逻辑控制器的作用域、执行顺序与脚本复用

【课程原话/定义】
> 在逻辑控制器下添加相应的子元素，如 HTTP 请求、定时器等。

课程只讲了「怎么加」，作用域与执行顺序属于**必须自己搞清的隐性知识**，以下为【扩展知识】。

【扩展知识】执行顺序规则：

```text
Test Plan
└─ Thread Group
   ├─ 定时器（作用于其后的所有取样器）      ← 先执行
   ├─ 配置元件（如 CSV Data Set Config）
   ├─ 取样器 / 逻辑控制器（按树中先后顺序）
   └─ 后置处理器（跟随它上层的取样器）
```

| 规则 | 说明 |
|---|---|
| 同类元件按树中顺序执行 | 谁在上面谁先跑，逻辑控制器也不会打乱同层的顺序 |
| 定时器在线程组层级生效于其后所有取样器 | 想让某个定时器只影响一个请求，就把它放进该请求所在的控制器的子树里 |
| 逻辑控制器可嵌套 | 嵌套时内层先执行完，外层才继续；嵌套层数越多越难读，一般不超过三层 |
| 变量的作用域是线程私有 | 每个虚拟线程有独立的变量副本，跨线程共享要用属性（Properties） |

【为什么？】
JMeter 的元件树本质是**深度优先遍历**：进入一个节点就把它的子树跑完，再回到同层的下一个节点。定时器、配置元件之所以「向上就近生效」，是因为它们在遍历时会对**其后同级及其子节点**产生作用。理解了这一点，你就能预判「把定时器移到控制器里面 vs 外面」会带来什么差异，而不是靠试错。这一条也是排查「为什么我的延迟没生效 / 为什么我的 CSV 被读过界」这类问题的根本方法。

【必须掌握】

| 想做什么 | 正确放置位置 |
|---|---|
| 只给「提交订单」加 2s 延迟 | 定时器作为「提交订单」的兄弟节点，且紧挨在它上面 |
| 给整个购买事务加固定思考时间 | 定时器放在 Transaction Controller **内部** |
| 全部请求统一加 500ms 延迟 | 定时器放在线程组第一层 |
| 让某分支用独立的数据文件 | CSV Data Set Config 放在该分支的控制器内部 |

【企业场景】
你压测时发现「加入购物车」接口的 P95 比预期高 300ms，但服务端监控显示接口本身只有 50ms。排查下来是同事把 Constant Timer 放在了线程组第一层，于是每个请求之前都加了 300ms 延迟，而这条链路的统计里就包含了它。你把定时器从线程组顶层挪进「首页分支」的控制器内部，重新跑一轮，事务耗时立刻回到 60ms 左右，与业务方口径一致。这类定位不靠猜，靠的是对作用域规则的理解。

【面试考察】
1. **面试官怎么问**：「定时器放在线程组里和放在请求下面有什么区别？」
   **回答框架**：作用域不同——线程组层级影响其后所有取样器，放在某个请求的兄弟位置上只影响该请求；本质是深度优先遍历决定的「就近生效」。
2. **面试官怎么问**：「为什么我两个线程之间变量互相污染/取不到？」
   **回答框架**：JMeter 变量是线程私有的，跨线程要么用属性、要么用文件，不要假设共享。
3. **面试官怎么问**：「你脚本里的逻辑控制器一般嵌套几层？」
   **回答框架**：尽量不超过三层，并在注释里写清业务含义；层级过深说明场景拆分粒度有问题，可以考虑拆成多个线程组。

【易错点】

| 常见错误 | 正确理解 |
|---|---|
| 把定时器当成「独立元件」放在最上面，以为只影响一个请求 | 同级及以下的所有后继取样器都会受影响 |
| 嵌套四层逻辑控制器后自己都看不懂 | 可读性优先，必要时用注释或拆线程组代替深层嵌套 |
| 认为逻辑控制器里的变量能被其他线程组读到 | 变量线程私有，共享要靠属性或外部存储 |
| 取样器命名随意，最后报告无法定位 | 命名要体现「分支 + 步骤」，这是脚本可维护性的第一要素 |

【我的理解】
1. 请你按照「深度优先遍历」这个模型，自己推演一遍：一个线程组下有「定时器 A → 请求 1 → 事务控制器(请求 2 → 请求 3) → 请求 4」，实际执行顺序是什么？
2. 如果脚本层级已经深到你自己都要画图才能看懂，你会选择「拆成多个线程组」还是「继续嵌套」？各有什么代价？
