### 知识点1：JMeter 的运行环境要求与启动方式

【课程原话/定义】
**JMeter 运行环境要求**：
- **Java 版本**：JMeter 是基于 Java 开发的，所以需要安装 Java 运行环境（JRE）或 Java 开发工具包（JDK）。推荐使用 Java 8 或更新版本。
- **系统要求**：JMeter 可以运行在 Windows、Mac 和 Linux 等操作系统上。具体的要求可以根据 JMeter 官方文档来确定。
- **内存要求**：JMeter 在运行时需要一定的内存空间。**官方建议至少分配 1GB 的内存给 JMeter 使用**。如果要执行大型测试，可能需要更多的内存。

**JMeter 运行方式**：
- Mac 系统：图形界面启动——在安装目录找到 `bin` 文件夹，双击运行 `jmeter.sh`；命令行启动——打开终端 `cd` 到该目录，输入 `./jmeter.sh`
- Windows 系统：图形界面启动——在安装目录找到 `bin` 文件夹，双击运行 `jmeter.bat`；命令行启动——打开命令行窗口，输入 `jmeter` 命令
- 注意：配置环境变量后，就不需进入 `bin` 文件夹下操作，直接打开终端输入 `jmeter` 即可打开

【为什么？】
三条要求（Java、系统、内存）里，**只有内存是"性能"问题而不是"能不能跑"问题**，这是理解 JMeter 压测失真的关键：

- **JMeter 自己也是被测对象**。它要维护 N 个线程的栈、保存每个请求的取样结果、跑聚合计算。并发越高、采样越多，它自身内存压力越大。
- **内存不够会引发两类灾难**：一是 OOM 直接崩掉（脚本白跑）；二是 GC 频繁导致 JMeter 自己变成瓶颈——你看到的 RT 曲线上升，其实是压测机在拖后腿，**结论完全是错的**。所以"加压机不能成为瓶颈"是压测的基本纪律（这也是后面要学分布式加压的根因）。
- **课程说"至少 1GB"，这是底线而不是推荐值**：小脚本调试够用，但几百上千并发、长时间稳定性场景必须调大 JVM 堆（改 `bin/jmeter.bat`/`jmeter.sh` 里的 `HEAP` 参数）。
- **启动方式的选择同样是纪律**：GUI（`jmeter.bat`/`jmeter.sh` 双击）只用来**调试脚本**；正式压测用命令行（配合 `-n`）。课程这里讲的是"怎么启动 GUI"，但你要记住 GUI ≠ 压测模式——"支持 UI 与命令两种操作方式"这个优点的真正用法就在这里。

【必须掌握】

| 维度 | 课程要求 | 工程含义 |
|------|----------|----------|
| Java | JRE 或 JDK，推荐 Java 8 或更新 | 实际部署建议统一 JDK，便于后续 JVM 分析 |
| 操作系统 | Windows / Mac / Linux | 压测机首选 Linux（资源开销低、可远程、便于分布式） |
| 内存 | 官方建议至少 1GB 给 JMeter | 大测试需加大 JVM 堆；加压机不能成为瓶颈 |
| Mac 启动 | `jmeter.sh`（GUI） / `./jmeter.sh`（命令行） | 配好环境变量后直接 `jmeter` |
| Windows 启动 | `jmeter.bat`（GUI） / `jmeter`（命令行） | 同上，环境变量生效后免 `cd bin` |
| 验证 | 能拉起 GUI 并可看到菜单与元件树 | 启动失败先查 Java 环境 |

【企业场景】
你准备跑一次 800 并发的稳定性压测（2 小时）。做法不是"打开 GUI 点运行"，而是：登录 Linux 压测机 → `export JMETER_HOME=/opt/apache-jmeter-5.6.3; export PATH=$JMETER_HOME/bin:$PATH` → 用 `jmeter -n -t order.jmx -l order.jtl` 跑 → 执行期间用 `top`/`free` **同时监控压测机自身的 CPU 与内存**。为什么要盯自己这台机器？因为一旦压测机 CPU 打满或内存告急，你交付的 TPS/RT 数据就已经失真了——**性能测试里，先证明"加压源不是瓶颈"，结论才站得住**。

【面试考察】
面试官："JMeter 运行需要什么环境？为什么正式压测不用 GUI？"

参考回答框架：
1. 环境三要素：Java（8+，JRE/JDK）、主流操作系统（Win/Mac/Linux）、内存（至少 1GB，大测试需更多）
2. 启动方式：Windows 用 `jmeter.bat`、Mac/Linux 用 `jmeter.sh`；配好环境变量后任意目录 `jmeter` 即可
3. GUI vs 命令行：GUI 需要渲染结果与监听器，自身消耗 CPU/内存并影响被测数据；命令行（`-n`）开销小、可脚本化、可进 CI
4. 纪律：压测机不能成为瓶颈，正式压测必须监控加压机自身资源

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 把 GUI 当压测模式，指着界面里的图表当最终报告 | GUI 只用于调试；正式压测走命令行并把结果落盘成 `.jtl` 再分析 |
| 认为"1GB 内存够压任何场景" | 1GB 是官方底线；高并发/长时间场景必须调大 JVM 堆，否则压测机先崩 |
| 只看被测服务的资源，不看压测机自身资源 | 压测机 CPU/内存打满会让 RT 虚高、TPS 虚低，结论直接失真 |
| 在 Mac 用双击 `jmeter.sh` 之后又抱怨命令行 `jmeter` 不生效 | 双击是 GUI 启动；命令行生效的前提是环境变量已配好并重开终端 |

【我的理解】
> 引导思考题1：课程说"官方建议至少 1GB 内存"，请你说出什么情况下 1GB 会明显不够，以及内存不足会怎样污染压测结论。
>
> 引导思考题2：请用自己的话解释"GUI 只用来调脚本"的原因——如果一定要给 GUI 模式加一个适用场景，你会怎么定义它的边界？

### 知识点2：JMeter 主界面功能介绍

【课程原话/定义】
JMeter 主界面大致可以划分为**四个部分**：
1. **常规菜单功能**
   - `File`（文件）：主要是新建、打开和保存文件
   - `Edit`（编辑）：主要是添加元件、保存、打开、禁用等
   - `Search`（查找）：查找和清除查找
   - `Run`（运行）：主要是运行、分布式运行。可以实现压测运行相关：开始运行、停止运行、远程运行、停止远程运行等
   - `Options`（选项）：可以设定界面大小、外观主题、配置语言等
   - `Help`（帮助）：可以点击帮助，查看 JMeter 帮助文档
2. **工具栏**：主要是一些运行、保存、模板、新建等功能按键
3. **测试计划树（课程原文："JMeter 的目录，是用来存放 JMeter 测试项目的项目栏"）**：存放 JMeter 测试项目（元件树）的区域
4. **工作区（课程原文："类似于测试项目的信息填写区域"）**：例如进行 HTTP 测试时，需要填写请求头、请求信息、参数等等，都是在这个界面完成的

【为什么？】
理解这四块分区，是为了建立 JMeter 最重要的一个心智模型：**"树 + 面板"的元件模型**。

- **左树右面板**：左边是**测试计划树**（结构化：测试计划 → 线程组 → 控制器 → 取样器/配置元件/监听器…），右边是**选中节点对应的属性面板**。所以 JMeter 里"配置一个东西"永远是两步：**先在树里选中它（或右键添加它），再到右侧填参数**。
- **树的层级 = 作用域（Scope）**：元件挂在哪个节点下，决定了它"对谁生效"。这是 JMeter 与"写脚本"最大的思维差异，也是后面 Controller（Ch15）、配置元件、断言、定时器全部要围绕的核心规则。
- **菜单里的 `Run` 藏着分布式入口**：课程原文明确列出 `Run` 包含"运行、分布式运行（远程运行/停止远程运行）"。这说明**分布式压测是核心能力而非插件**，后面 L3 的分布式章节就是围绕这个入口展开的。
- **`Options → 语言`**：课程提到"配置语言"，这对中文使用者很实用——但要注意，**界面语言切换只影响显示，不影响脚本（`.jmx` 里存的是元件英文名）**，所以不要在中文界面里记"中文元件名"，面试和排错都用英文名沟通。

【必须掌握】

| 分区 | 内容 | 使用要点 |
|------|------|----------|
| 菜单栏 | File / Edit / Search / Run / Options / Help | `Run` 含开始/停止/远程运行（分布式）；`Options` 可切语言与主题 |
| 工具栏 | 新建、保存、模板、运行等按钮 | 高频操作快捷入口，等价于菜单项 |
| 测试计划树 | 存放测试项目（测试计划及其下元件） | **树结构 = 作用域**，是本课程最核心的思维模型 |
| 工作区/属性面板 | 填写选中元件的信息 | 选中树节点后在此填请求头、参数、路径等 |
| 语言切换 | `Options` 中设置 | 只改显示，`.jmx` 内仍是英文元件名 |
| 分布式入口 | `Run` 菜单中的远程运行 | 分布式加压的 GUI 入口，命令行用 `-R` |

【企业场景】
你接手一个同事留下的 `.jmx` 脚本，打开后界面很"乱"，你的排查顺序一定是：**先看左边的测试计划树**——因为脚本的行为完全由树结构决定。你会按层级检查：测试计划下有几个线程组（是否有 setUp/tearDown）→ 每个线程组下挂了多少取样器 → 哪些元件挂在测试计划级（全局生效，例如"用户定义的变量"）、哪些挂在线程组级（只对该线程组生效）。**只看右侧属性面板是看不出脚本行为的**，这是新人读别人脚本最常见的低效方式；而"读脚本先读树"这个习惯，在整个 JMeter 学习期都适用。

【面试考察】
面试官："JMeter 的界面你熟悉吗？一个测试计划的层级结构是什么样的？"

参考回答框架：
1. 布局：主界面分菜单栏、工具栏、测试计划树、工作区（属性面板）四块
2. 核心模型：左边是元件树，右边是选中元件的属性；配置元件就是"选中 → 填参数"
3. 层级与作用域：测试计划 → 线程组 → 控制器 → 取样器；元件挂载位置决定生效范围
4. 功能入口：File/Edit 管文件与元件，Run 管运行与分布式，Options 管界面与语言

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 在中文界面里背"中文元件名" | `.jmx` 里存的是英文元件名；面试与排错都用英文沟通（Thread Group、Sampler…） |
| 只盯着右侧属性面板读他人脚本 | 先读左边的元件树（结构决定行为），再看属性 |
| 以为"添加元件"只能在菜单里找 | `Edit` 菜单与树节点右键菜单都能添加，实际都用右键 |
| 觉得 `Run` 菜单只是"开始/停止" | 它还包含远程运行等分布式入口，是 L3 分布式加压的起点 |

【我的理解】
> 引导思考题1：请用"树 + 面板"解释：为什么在 JMeter 里配置任何元件都是"先选中、再填参数"两步？
>
> 引导思考题2：课程说工作区是"类似于测试项目的信息填写区域"——请举一个你后面的章节会遇到的例子（提示：HTTP 请求的请求头、参数填写在哪里？）。

### 知识点3：从"装上"到"用起来"——本模块的最小可用脚本

【课程原话/定义】
课程本章的"总结"只有两句：**JMeter 的简介**、**JMeter 的安装**（第二节的总结是 **JMeter 运行方式**、**JMeter 界面功能介绍**）。也就是说，本章的交付标准是"能装、能启、能看到界面"。

【扩展知识】
课程没有在本章串起"最小可用脚本"，但这是学习者自检的最好方式。基于课程后续章节的元件清单，一个**最小可跑的压测脚本**只需要四类东西：**测试计划（容器）→ 线程组（并发模型）→ 取样器（发什么请求）→ 监听器（怎么看结果）**。它们分别在本书 Ch13、Ch14、后续章节、以及监听器章节展开。你现在只需要记住这条主线：**测试计划管全局 → 线程组管用户 → 取样器管请求 → 监听器管结果**。

【为什么？】
把本章当作"安装篇"是错的——**安装动作的每一处都对应后面章节的一个知识点**：

| 安装期的动作 | 后面会变成哪个知识点 |
|--------------|----------------------|
| 装 JDK、`java --version` | JVM 相关监控与剖析（L4/L5） |
| 下载 binary 包、固定版本 | 压测环境基线与结果可比性 |
| 配 `JMETER_HOME`/`PATH` | CI 集成、分布式 slave 启动 |
| 命令行启动 | `jmeter -n -t -l` 无 GUI 压测 |
| 主界面四分区 | 元件树/作用域模型（贯穿全书） |

**这就是"为什么安装篇值得记笔记"的答案：性能测试的结论可信度，是从环境一致性与加压源可控性开始积累的。**

【必须掌握】

| 阶段 | 你要能独立完成 | 自检标准 |
|------|----------------|----------|
| 环境准备 | 装 JDK 并验证、下载解压 JMeter | `java --version`、`jmeter -v` 均有输出 |
| 配置 | 配 `JMETER_HOME` 与 `PATH` | 任意目录执行 `jmeter` 能拉起界面 |
| 启动 | Windows `jmeter.bat` / Mac `jmeter.sh` | 界面四分区齐全，无报错 |
| 认知 | 说清 GUI vs 命令行模式的区别 | 能说出"GUI 调脚本、CLI 跑压测" |
| 记录 | 把版本、路径写进环境说明 | 团队/未来自己都能复现同一环境 |

【企业场景】
新人入职第一周，Leader 通常不会让你直接压测，而是让你"**把压测环境搭起来并写一页环境说明**"。这一页要包含：JDK 版本、JMeter 版本与安装路径、环境变量配置方式、GUI 与命令行两种启动命令、验证输出截图。这份文档的价值在于：**当三个月后压测结论被质疑时，你能拿出"当时的加压环境"**。你越是把安装这一章的每个细节落到文档里，后面的压测报告就越难被推翻。

【面试考察】
面试官："压测环境你是怎么准备的？需要注意什么？"

参考回答框架：
1. 环境基线：JDK 与 JMeter 版本统一并登记，压测机不放个人目录
2. 可变项控制：环境变量系统级配置，保证 CI/服务账号也能执行 `jmeter`
3. 资源准备：按并发规模评估压测机内存（≥1GB 起步）与 CPU，必要时分布式
4. 可复现意识：同一脚本在不同环境跑出的结果不可直接比较，环境变更必须记录

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 装完就以为学完了，不看界面结构 | 四分区与元件树模型是后续所有章节的地基 |
| 环境说明只写"已安装 JMeter" | 必须写清版本、路径、变量、验证方式，才能复现 |
| 换版本不留记录 | 版本变更等价于环境变更，会让历史结果失去可比性 |
| 把"能启动 GUI"当成"能压测" | 能启动只证明环境通了；压测能力要等线程组/取样器章节 |

【我的理解】
> 引导思考题1：把本章的安装动作逐步映射到"后面会用到它的章节"，你能说出几组对应关系？
>
> 引导思考题2：如果三个月后有人质疑你当时的压测结论，你会拿本章的哪些产出（文档/命令/版本）来证明结论可信？
