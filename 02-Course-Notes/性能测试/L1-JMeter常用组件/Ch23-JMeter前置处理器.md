### 知识点1：前置处理器（Pre Processors）是什么，什么时候该用它

【课程原话/定义】
在 JMeter 中，前置处理器（Pre Processors）用于在**每个 Sampler（采样器）执行之前**对请求进行处理。前置处理器允许我们在发送请求之前对请求参数进行修改、添加额外的逻辑验证或其他操作，以确保请求能够正确执行并生成需要的测试数据。

常见的前置处理器（课程原文列举）：**Sample Timeout、BeanShell PreProcessor**。

**课程原文分类勘误**：原文写的是"前置处理器（Pre Processors）是一种**配置元件**"。这个分类表述不严谨——**前置处理器是 JMeter 八大组件中独立的一类**（线程组、配置元件、前置处理器、定时器、取样器、后置处理器、断言、监听器），它**不属于**配置元件。两者有本质差别：

| 维度 | 配置元件 | 前置处理器 |
|------|----------|------------|
| 职责 | 提供配置数据（请求头、Cookie、变量、缓存策略） | 对**即将发出的请求**执行脚本级处理（改参数、加逻辑、算数据） |
| 典型代表 | HTTP Header Manager、CSV Data Set Config | Sample Timeout、BeanShell PreProcessor |
| 与取样器的关系 | 补默认值，取样器读取它 | 在取样器执行前**主动修改**取样器上的内容 |
| 执行位置（同一作用域） | 第 1 位 | 第 2 位（紧跟配置元件之后） |

【为什么？】
性能测试脚本总会遇到"发出去之前必须先做点什么"的问题，例如：
1. **签名/加密**：接口要带 `sign`，而 `sign = md5(参数 + timestamp + secret)`，每次都不同 → 必须在请求发出前用代码算出来（BeanShell/JSR223 PreProcessor）；
2. **动态参数**：时间戳、随机串、流水号、递增 ID → 请求发出前生成；
3. **请求内容依赖上一步结果**：虽然逻辑上更像"后置处理"的产物，但在某些场景里需要在**本请求发出前**做改写（如把上一步的值拼进 body）；
4. **超时兜底**：给取样器加最大等待时间，超时就中断，避免个别请求把整个线程卡死、污染 RT 统计。

这四类需求都有一个共同点：**必须在"请求发出"这个时点之前完成，且与"请求本身要发什么内容/发多久允许"有关**。这也解释了它为什么排在执行链第二位——它在配置元件把所有默认值和变量准备好之后运行，改完之后才轮到定时器与取样器（完整顺序见 [[Ch25-JMeter执行顺序]]）。

【必须掌握】

| 维度 | 内容 |
|------|------|
| 定义 | 在每个 Sampler 执行**之前**对请求进行处理的元件 |
| 能力 | 修改请求参数、添加额外逻辑验证、生成测试数据 |
| 常见成员 | Sample Timeout、BeanShell PreProcessor（原文列举；【扩展知识】：JSR223 PreProcessor、用户参数 User Parameters、JDBC PreProcessor、RegEx User Parameters 等） |
| 执行位置 | 同一作用域内：**配置元件 → 前置处理器** → 定时器 → 取样器 → 后置处理器 → 断言 → 监听器 |
| 作用域 | 与配置元件一样由**层级**决定：挂在线程组下对所有请求生效，挂在请求之下只对该请求生效 |
| 使用原则 | 越"重"的处理（写复杂脚本、做加解密）越要控制规模：它在线程内串行执行，会直接吃掉施压机的 CPU |

【企业场景】
你压一个带签名的开放平台接口，服务端会对每个请求校验 `sign`。脚本里没有签名逻辑，压出来的结果全是 100% 错误（HTTP 200 + `{"code":"SIGN_INVALID"}`），最多能测出"网关的签名校验性能"。企业做法是在该请求下挂一个 BeanShell/JSR223 PreProcessor，用代码按相同规则算出 `sign` 并 `vars.put("sign", ...)`，请求里用 `${sign}` 引用。**前置处理器在企业里最常见的用途就三件事：算签名、造动态数据、加超时兜底。** 它不是"进阶技巧"，而是让加解密类接口的压测从"完全不可做"变成"可做"的必备元件。

【面试考察】
面试官："JMeter 的前置处理器是干什么的？和配置元件有什么区别？"

参考回答框架：
1. 定义：在每个取样器执行前对请求做处理（改参数、算数据、加逻辑校验）
2. 与配置元件的区别：配置元件提供"默认配置/数据"（被动被读取），前置处理器是"主动改写请求"，两者是八大组件中独立的两类，执行顺序上配置元件在前
3. 典型用途：签名/加密参数计算、时间戳与随机数据生成、超时兜底控制
4. 工程提醒：前置处理器里的脚本会在线程内反复执行，复杂度直接吃施压机 CPU，压大并发时要评估施压机能力

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 认为"前置处理器是一种配置元件"（课程原文的表述） | 它是八大组件中独立的一类；配置元件准备数据，前置处理器改写请求/算数据，执行顺序上前者在前 |
| 认为前置处理器"只执行一次" | 它在**每个取样器执行前**都会运行（每个线程、每轮迭代、每个取样器都会触发） |
| 把加解密脚本写得很重 | 脚本开销会计入施压机 CPU，可能让施压机先于服务端到瓶颈——压出来的"RT 升高"其实是施压机自己的问题 |
| 用前置处理器去"断言" | 断言是取样器**之后**的判定；前置处理器只管准备阶段。"添加额外的逻辑验证"指的是发起请求前的条件判断（如参数非法就不发），不是替代断言 |
| 挂错层级导致只对部分请求生效 | 作用域按层级：放线程组 = 全组生效，放请求下 = 只该请求生效 |

【我的理解】引导题（用自己的话回答）：
1. 用一句话区分"配置元件"和"前置处理器"：一个是"___"，一个是"___"。
2. 为什么"算签名"这件事必须放在请求发出之前（前置处理器），而不能放在断言里？

### 知识点2：Sample Timeout（采样超时）

【课程原话/定义】
在 JMeter 中，Sample Timeout 是一个针对每个 Sampler（采样器）的设置，用于定义在等待响应时允许的最大超时时间。如果超过了设置的 Sample Timeout 时间，JMeter 将放弃该请求，并将其标记为超时。这个设置可以帮助在进行性能测试时控制请求的最大响应时间，并识别潜在的性能问题。

参数配置：`Sample timeout (in milliseconds)`——采样超时时间，单位是毫秒。

课程案例：检查百度首页发送请求的时间是否小于 10 毫秒。
- 步骤一：添加百度的 HTTP Request，添加对应的 Sample timeout，添加查看结果树
- 步骤二：查看结果，**断言失败**——预期结果为 10 毫秒，而实际结果为 11 毫秒

**课程原文勘误（重要）**：
1. 案例把 Sample Timeout 当成"断言"，说结果是"断言失败"。准确说，**Sample Timeout 不是断言元件**，它的作用是"给取样器设置最大等待时间，超时则中断该请求并把结果标记为超时/失败"。案例的效果是"把超过 10ms 的请求标记为超时"，是一种**超时门槛控制**，不是断言（断言判定通过/失败但请求本身仍会跑完；Sample Timeout 会真的中断取样）。
2. 【扩展知识】Sample Timeout 虽然功能上偏向"超时控制"，但 JMeter 官方组件手册确实把它归在 **Pre Processors（前置处理器）** 一节，其实现方式是"调度一个定时任务，在取样执行过久时中断该取样"，并且**要求取样器实现 Interruptible 接口才生效**（官方列出支持者包括 AJP、BeanShell、FTP、HTTP 等）。所以它"挂在前置处理器下"是分类事实，但不要把它当断言用——职责说清：**它是超时控制的兜底。**

【为什么？】
压测现场最怕两件事，Sample Timeout 正好治其中一件：
1. **个别请求长期挂起**：某个请求因为服务端没回、TCP 层没断，会把线程一直占着，导致这条线程在整段时间内几乎不产生请求 → 实际并发数远低于设定值 → 你以为是"服务端能扛 500 并发"，其实是"只有 50 个线程在工作"；
2. **统计被污染**：如果没有超时中断，这些请求最终可能以极长的 RT 出现在报告里（拉高平均 RT / 99 线），或者干脆卡到测试结束。

**机制上要特别注意**：Sample Timeout 是"中断取样"，**超时的请求会被标记为失败/超时，进入错误率统计**。所以设一个很紧的阈值（如 10ms）会让你得到一个"错误率 99%"的报告——这不是系统的错，是阈值不合理。企业里的用法是把它设成**"业务可接受上限的兜底"**（如接口承诺 P99 < 2s，就把超时设在 3~5s），用来兜住"卡死型"请求，而不是用它做精确的响应时间门槛判断（那是断言的活）。

【必须掌握】

| 项目 | 内容 |
|------|------|
| 作用 | 给取样器设最大等待时间，超过则放弃该请求并标记为超时 |
| 参数 | `Sample timeout (in milliseconds)`，单位毫秒 |
| 生效前提 | 【扩展知识】取样器需实现 Interruptible（官方列出 AJP/BeanShell/FTP/HTTP 等），因此对 HTTP 请求有效 |
| 合理取值 | 兜底型：设成"业务承诺上限"的 1.5~3 倍；不要设成精确的期望值（如 10ms） |
| 超时后果 | 线程被释放可继续下一轮（避免线程被卡死）、该请求计入错误率 |
| 与断言的区别 | Sample Timeout = 超时中断（控制等待上限）；断言 = 结果判定（通过/失败） |
| 与 HTTP 超时设置的关系 | 【扩展知识】HTTP Request 自身也有连接/响应超时设置；两者层级与语义不同，压测脚本里要注意别互相冲突 |

【企业场景】
你压一个第三方支付回调接口，服务端依赖外部渠道，个别请求会因为对端不响应而挂起 30 秒以上。跑 20 分钟稳定性测试时，Aggregate Report 里出现十几条 RT = 30000ms 的请求，把 99 线拉得很难看，同时你的有效并发数掉了一截。企业做法：给这类**外部依赖型接口**加 Sample Timeout（比如 5000ms），让卡住的请求被及时中断释放线程，报告里把它们集中体现为"超时错误"，再单独分析——**要看的是"有多少请求超时"，而不是让它们悄悄拉高平均 RT。** 同时也会去监控端（下游服务、网络）确认这是下游问题还是本级问题。

【面试考察】
面试官："压测时个别请求一直不返回怎么处理？Sample Timeout 是断言吗？"

参考回答框架：
1. 先定性：多数情况下是"外部依赖慢/卡"，少数是连接未正常关闭
2. 处理手段：给取样器加 Sample Timeout（或设置 HTTP 超时），超时即中断取样并标记失败，避免线程被长期占用、避免污染 RT 统计
3. 明确它不是断言：断言是"结果对不对"的判定；Sample Timeout 是"允许等多久"的控制，超时会被计入错误率
4. 阈值策略：按业务承诺上限的倍数设兜底值，别用精确期望值（否则错误率虚高，结论失真）

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 把 Sample Timeout 当断言用（原文案例称"断言失败"） | 它是超时控制，超时即中断并计失败；要做响应时间门槛校验用断言（如 Duration Assertion / 响应断言），两者机制不同 |
| 阈值设得极小（如 10ms） | 结果是"错误率虚高"，反映的是阈值不合理，不是系统性能差 |
| 认为它是"前端处理器里的普通配置" | 它属于前置处理器分类下的超时控制元件；官方要求取样器实现 Interruptible 才生效 |
| 以为超时的请求不算失败 | 超时会进入错误率统计；分析报告时必须区分"业务错误"与"超时错误" |
| 给所有请求都加同一个超时值 | 不同接口的合理上限不同（查询类 < 下单类），一刀切会让慢接口被大量误判 |

【我的理解】引导题（用自己的话回答）：
1. 为什么"把 Sample Timeout 设成 10ms"会让报告变得毫无价值？请从"错误率"和"施压机有效并发数"两个角度解释。
2. 请说清 Sample Timeout 与断言在机制上的差别：一个请求超时被中断后，断言还会执行吗？为什么？

### 知识点3：BeanShell PreProcessor（BeanShell 前置处理器）

【课程原话/定义】
在 JMeter 中，BeanShell PreProcessor 是一种前置处理器，可以使用 BeanShell 脚本语言编写逻辑，用于在执行每个 Sampler（采样器）之前进行自定义处理操作。BeanShell PreProcessor 允许用户编写灵活的代码来操作请求参数、处理数据或执行其他任何自定义操作，以满足特定的测试需求。

常用参数配置：
- **Script file**：包含要运行的 BeanShell 脚本的文件，文件名存储在变量 `FileName` 中；**添加了脚本文件后，就只会运行添加的脚本文件，Script 部分的脚本代码不会运行了**。
- **Script**：要运行的 BeanShell 脚本，**返回值如果不为 null，就存储为采样器结果**。

课程案例：通过程序生成当前时间戳，将时间戳值赋值给变量，然后传递给后续的请求样本。
- 步骤一：添加百度的 HTTP Request，添加对应的 BeanShell PreProcessor，添加查看结果树和 Debug Sampler
- 步骤二：在 BeanShell PreProcessor 元件中添加对应脚本获取当前时间戳
- 步骤三：查看结果，时间戳添加在请求参数中

【为什么？】
BeanShell PreProcessor 是把 JMeter 从"配置型工具"变成"可编程工具"的关键之一。它的三个核心机制必须懂：
1. **脚本在取样器前、线程内运行**：每个线程、每一轮迭代、每个挂载点都会执行一次；所以脚本里写"睡眠/循环/大对象"会成倍放大施压机开销。
2. **与 JMeter 变量系统交互**：脚本里通过 `vars`（JMeterVariables）读写变量——`vars.put("ts", value)` 写、`vars.get("token")` 读；写进去的变量可以用 `${ts}` 被请求参数、请求头引用。这就是"生成时间戳并传给请求"的原理。
3. **Script file 与 Script 是二选一**（原文明确）：一旦填了 Script file，界面里的 Script 代码**不会执行**——这是最典型的"我改了界面里的脚本怎么不生效"问题来源。
4. 关于"返回值不为 null 就存储为采样器结果"：BeanShell PreProcessor 的 Script 返回值会被作为结果处理（也正因为如此，脚本里随手的最后一行表达式可能带来非预期行为，建议显式控制）。

【必须掌握】

| 配置项 | 说明 |
|--------|------|
| Script file | 外部脚本文件路径（文件名存入变量 `FileName`）；**启用后 Script 区代码不再运行**（原文明确） |
| Script | 内联脚本；返回值不为 null 会存储为采样器结果（原文明确） |
| 内置对象 | `vars`（JMeter 变量读写）、`props`（JMeter 属性）、`ctx`（上下文）、`prev`（上一个取样结果）等（【扩展知识】） |
| 变量写回 | `vars.put("ts", value)` → 请求里用 `${ts}` 引用 |
| 层级 | 放在请求下 = 只影响该请求；放线程组下 = 该组所有请求前都执行（作用域规则） |
| 验证手段 | 配 Debug Sampler + View Results Tree，确认变量真的被写进去、真的被请求引用了 |

【企业场景】
你压的接口需要带 `timestamp` 和 `sign`，且服务端要求"时间戳与服务器时间差不超过 5 分钟"。做法：在该请求下挂 BeanShell PreProcessor，脚本里取当前时间戳写入变量 `ts`，再按约定拼接参数算出 `sign` 写入变量；HTTP Request 的参数用 `${ts}`、`${sign}`。压测前先用 1 线程 1 次循环验证（Debug Sampler 里能看到变量值），再放大并发。**这类脚本一定要先小样本验证再放大**——因为它一旦写错，压出来的是"签名校验失败"的错误率，而不是系统性能。

【面试考察】
面试官："JMeter 里怎么做签名/加解密接口的压测？"

参考回答框架：
1. 元件：在请求下挂脚本类前置处理器（BeanShell PreProcessor 或 JSR223 PreProcessor）
2. 机制：脚本在取样器前执行，用 `vars.put(...)` 把算出的 `sign`/`timestamp` 写回变量，请求参数用 `${sign}` 引用
3. 验证：先在 1 线程 1 迭代下用 Debug Sampler + View Results Tree 确认变量与请求正确，再放大并发
4. 性能提醒：脚本会消耗施压机 CPU（BeanShell 是解释执行，性能弱于 JSR223 + Groovy），大并发下优先考虑轻量实现或分布式加压

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 填了 Script file 后又在 Script 区改代码 | 原文明确：添加脚本文件后只运行该文件，Script 部分不执行——改界面不生效就是这个原因 |
| 变量名写错 / 大小写不一致 | `${Ts}` 与 `vars.put("ts", ...)` 不匹配时，请求里会原样发出 `${Ts}`，不报错；必须看 View Results Tree 的请求内容 |
| 把签名脚本放在线程组外层以为"只算一次" | 前置处理器在每个取样器前都执行；频率高、开销大，别做重计算 |
| 用 BeanShell 做复杂逻辑（循环、大量字符串拼接） | BeanShell 解释执行较慢；【扩展知识】建议改用 JSR223 PreProcessor + Groovy（编译缓存后性能明显更好） |
| 不配 Debug Sampler 就上并发 | 变量到底写没写进去无从验证；调试期必须配 Debug Sampler，正式压测前移除（监听器吃资源） |
| 脚本里未处理异常 | 脚本报错会让前置处理失效甚至影响取样，建议脚本内 try/catch 并把错误信息写入变量便于排查 |

【我的理解】引导题（用自己的话回答）：
1. 请写出"生成时间戳 → 写入变量 → 请求引用"这条链路里，三个环节分别由谁完成（元件/代码/引用语法）。
2. 为什么"填了 Script file 后 Script 区改代码没反应"是新手最容易踩的坑？你以后会怎么避免（提示：先看哪个字段有值）？

### 知识点4：其他常见前置处理器与使用原则（【扩展知识】）

【课程原话/定义】
课程原文只列举了 Sample Timeout 与 BeanShell PreProcessor 两个常见前置处理器（"常见的前置处理器"小节）。

以下为【扩展知识】——JMeter 组件手册中同属前置处理器分类的其他成员，了解它们的用途有助于选型：
- **User Parameters（用户参数）**：为每个线程/每次迭代提供一组参数值，适合"少量固定用户数据"的简单参数化。
- **JSR223 PreProcessor**：与 BeanShell 定位相同，但用 JSR223 支持的语言（常用 Groovy），性能更好，是官方推荐的脚本方向。
- **HTML Link Parser / HTTP URL Re-writing Modifier**：从响应 HTML 中解析链接、自动改写 URL（会话 ID 重写），用于早期的 HTML 页面压测。
- **RegEx User Parameters**：从上一个响应中用正则取参数名/值，做动态参数传递。
- **JDBC PreProcessor**：请求前查数据库取数据。

【为什么？】
前置处理器的选型逻辑只有一条：**"这件事能不能用更轻的方式做？"** 顺序是：
1. 能用**配置元件**（CSV、用户定义的变量、HTTP Header Manager）做的，不要用脚本——配置元件几乎零 CPU 开销；
2. 需要**少量变化的数据**用**函数**（如 `${__Random}`、`${__time()}`，JMeter 内置函数是编译好的，比脚本轻）；
3. 只有**确实需要编程逻辑**（签名、加解密、条件分支）才用脚本类前置处理器，且优先 **JSR223 + Groovy** 而不是 BeanShell（Groovy 有编译缓存，反复执行开销明显更低）；
4. 【扩展知识】无论选谁，都要评估**施压机 CPU 余量**：压测时施压机 CPU 长期 > 80% 时，报告里的 RT/TPS 就不可全信了（可能是施压机自己成了瓶颈）。

【必须掌握】

| 需求 | 优先方案 | 理由 |
|------|----------|------|
| 固定配置（头、Cookie、缓存策略） | 配置元件 | 零脚本开销，集中管理 |
| 大量不同用户/数据 | CSV Data Set Config | 数据在文件里，读取开销低 |
| 简单动态值（时间戳、随机数） | JMeter 函数（`${__time()}`、`${__Random}` 等） | 内置实现，比脚本轻（【扩展知识】） |
| 签名/加解密/复杂分支 | JSR223 PreProcessor（Groovy）优先，BeanShell 次之 | 可编程；Groovy 性能优于 BeanShell（【扩展知识】） |
| 请求前需查库取数 | JDBC PreProcessor | 属前置处理器分类的一员（【扩展知识】） |
| 超时兜底 | Sample Timeout | 控制等待上限，避免线程被卡死 |

【企业场景】
你评审一个同事的压测脚本，发现他用 BeanShell PreProcessor 生成了一个随机数。你会建议改成 `${__Random(1,1000)}` 函数——**功能一样，但施压机 CPU 开销差一个量级**。反过来，如果需求是"根据上游接口返回的动态密钥做 AES 加密"，那就必须上脚本（JSR223 + Groovy），并且要提前算好：单次加密耗时 × 每秒请求数 = 施压机需要的额外 CPU，必要时增加施压机或上分布式加压（[[Ch25-JMeter执行顺序|分布式在 L3 展开]]）。**"用最轻的手段满足需求"是压测脚本评审的第一原则。**

【面试考察】
面试官："JMeter 里做参数化/动态数据有哪几种方式？怎么选？"

参考回答框架：
1. 分层回答：配置元件（CSV、用户定义变量）→ 函数（`__time`、`__Random`）→ 脚本前置处理器（BeanShell/JSR223）
2. 选择原则：能不用脚本就不用脚本，因为脚本开销直接落在施压机上，会影响压测结果可信度
3. 脚本场景：签名、加解密、复杂条件逻辑；优先 JSR223 + Groovy（有编译缓存）
4. 兜底建设：压测期间同时监控施压机自身 CPU/内存，避免"施压机瓶颈"被误判为"服务端瓶颈"

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 见动态数据就上脚本 | 先想配置元件和函数；脚本是最后手段（CPU 开销最大） |
| BeanShell 与 JSR223 混用无差别 | 【扩展知识】JSR223 + Groovy 通常性能更好，是官方推荐方向；BeanShell 仍在用但不建议做重逻辑 |
| 不监控施压机资源 | 施压机 CPU 打满时 RT/TPS 数据失真；压测要同时看施压机与服务端 |
| 认为前置处理器能替代断言/后置处理器 | 三者职责不同：前置 = 发请求前准备；后置 = 取样后取值；断言 = 结果判定 |

【我的理解】引导题（用自己的话回答）：
1. 你要为 1000 个线程生成随机手机号，会选哪种方式？为什么不用 BeanShell 写一行 `Math.random()`？
2. 如果压测时施压机 CPU 到了 95%，你会怎么判断报告里的"RT 升高"是服务端的问题还是施压机的问题？
