### 知识点1：HTTP 请求属性 —— 重定向、KeepAlive 与 multipart

【课程原话/定义】

| 选项 | 课程原文说明 |
|---|---|
| Redirect Automatically（自动重定向） | 如果选中该选项，当发送 HTTP 请求后得到的响应是 302/301 时，JMeter 会自动重定向到新的页面，但是 Jmeter 是不记录重定向的过程内容 |
| Follow Redirects（跟随重定向） | Http Request 取样器的默认选项，当响应 code 是 3xx 时，自动跳转到目标地址。与自动重定向不同，Jmeter 会记录重定向过程中的所有请求响应，在查看结果树时可以看到服务器返回的内容，如有多个跳转则多个请求都会被记录下来，此为默认选项 |
| Use KeepAlive | 当该选项被选中时，jmeter 和目标服务器之间使用 KeepAlive 方式进行 HTTP 通信，默认选中 |
| Use multipart/form-data | 对 post 使用 multipart/from-data：当发送 POST 请求时，使用 multipart/from-data 方法或者 application/x-www-form-urlencoded 方法发送，默认不选中 |
| Browser-compatible headers（与浏览器兼容的头） | 当勾选 multipart/form-data 时，勾选此项会截掉 http 请求头中的 Content-Type 和 Content-Transfer-Encoding，而只发送 Content-Disposition 部分 |

【扩展知识】Redirect Automatically 与 Follow Redirects 是互斥的：两者都不勾时，3xx 响应会被当作最终结果直接返回给脚本（状态码 302、内容为跳转页），这时你才能自己用断言判断跳转地址。

【为什么？】
这几个选项全部围绕「**让 JMeter 的行为和浏览器/真实客户端一致**」。

- **重定向**：真实用户遇到 302 会自动跳到新页面并完成后续交互。如果压测脚本不跟重定向，那么登录后拿不到 session、下单请求打在旧地址上，压出来的全是 302。这也是为什么课程强调 Follow Redirects 是默认项——它更贴近真实用户。
- **KeepAlive**：浏览器复用 TCP 连接，省掉三次握手和慢启动开销。如果压测不复用连接，测出的响应时间会明显高于真实用户感受，且加压机会因为频繁建连而先到瓶颈。所以「模拟真实用户」这个目标决定了 KeepAlive 默认勾选。
- **multipart/form-data**：文件上传这类请求体的格式与普通表单不同，勾选后 JMeter 会按 multipart 规范拼装请求体（并能配合「文件上传」参数类型）；`Browser-compatible headers` 则是进一步模拟某些浏览器不发 Content-Type 的怪异行为。

【必须掌握】

| 场景 | Redirect Automatically | Follow Redirects | 说明 |
|---|---|---|---|
| 模拟真实用户浏览/登录 | 不勾 | ✅ 勾选（默认） | 能看到完整跳转链路，贴近用户行为 |
| 只想看首次响应的状态码 | 不勾 | 不勾 | 3xx 直接作为结果返回，便于断言跳转 |
| 压测接口（无重定向） | 不勾 | 不勾或保持默认 | 对结果无影响，清晰优先 |

| 场景 | Use KeepAlive | Use multipart/form-data |
|---|---|---|
| 普通接口压测 | ✅ 保持默认勾选 | 不勾 |
| 模拟上传文件 | ✅ 保持默认勾选 | ✅ 勾选，且「文件上传」参数类型要填对 |
| 表单提交（普通 POST） | ✅ 保持默认勾选 | 不勾，用参数表 + application/x-www-form-urlencoded |

【企业场景】
你压测「登录 → 跳转到工作台」的流程，同事写的脚本里只发了一个登录 POST 请求，结果聚合报告里「登录」的响应时间只有 30ms，业务方却说真实用户点登录要等 1 秒多。排查发现：登录接口返回 302 之后，浏览器还要请求工作台页面和若干静态资源，这些时间在脚本里全被省掉了。修复方式是勾上 `Follow Redirects`（默认已勾，同事手动取消了）并在断言里检查最终落地的页面。同时你确认 `Use KeepAlive` 保持勾选，因为线上网关是支持长连接的，关掉它会凭空制造出建连开销。修完之后压出来的数字才和真实用户体验对得上。

【面试考察】
1. **面试官怎么问**：「自动重定向和跟随重定向有什么区别？你选哪个？」
   **回答框架**：自动重定向只记录最终结果、不记录过程；跟随重定向记录每一次跳转的请求与响应；模拟真实用户用跟随，只想看首次状态码用都不勾。
2. **面试官怎么问**：「KeepAlive 要不要开？」
   **回答框架**：默认开、且应该开——浏览器就是这么做的；关掉会失真并加大加压机建连开销，只有专门测「短连接场景」时才关。
3. **面试官怎么问**：「文件上传/图片上传接口怎么压？」
   **回答框架**：POST + 勾选 Use multipart/form-data + 参数类型选「文件上传」并填 MIME Type；必要时配合 Browser-compatible headers。

【易错点】

| 常见错误 | 正确理解 |
|---|---|
| 手工把 Follow Redirects 取消，然后发现登录后拿不到会话 | 默认勾选是有意为之，取消后 3xx 会直接结束该采样器，后续流程必然失败 |
| 同时勾上 Redirect Automatically 和 Follow Redirects | 二者语义冲突（一个记录一个不记录），按需求二选一 |
| 上传文件时忘记勾 multipart/form-data，服务端报 400 | 上传必须用 multipart 编码，勾选后还要把「文件上传」的 MIME Type 填正确 |
| 为了「省压力」把 KeepAlive 关掉 | 关掉后每次请求都新建 TCP 连接，加压机开销反而更大，结果也会失真 |

【我的理解】
1. 课程说「不勾自动重定向时 JMeter 不记录重定向过程内容」——请你结合「用户真实体验」这个标准，判断这两种模式分别适合什么样的压测目标。
2. KeepAlive 的开启会影响响应时间，那它在「验证服务端性能」和「模拟真实用户」这两个目标下，结论会不会不一样？请你自己给出判断依据。

### 知识点2：三种参数类型 —— 参数 / 消息体数据 / 文件上传

【课程原话/定义】

| 参数类型 | 课程原文说明 |
|---|---|
| 参数 | 可以将 URL 中所有参数设置在本表中，表中的每一行是一个参数值对，此时编码这个选项设置为 UTF-8 并勾选最好，防止参数值内含有 ASCII Control Chars 或者 Non-ASCII characters 或者其他符号导致乱码问题 |
| 消息体数据 | 同请求一起发送的数据信息，这里可以支持多种数据格式，json、xml 等 |
| 文件上传 | 同请求一起发送的文件信息，参数名称就是发送文件对应的参数，MIME Type 为资源媒体类型 |

课程的实操验证（以访问百度首页为例）：

| 类型 | 步骤 | 结果 |
|---|---|---|
| 参数 | 步骤一：请求方式为 GET，添加两个参数 `username=user1`、`password=123456` | 步骤二：设置的参数被拼接在请求地址的后面，不同参数之间用 `&` 连接 |
| 消息体数据 | 步骤一：请求方式为 POST，添加 POST data 数据为 `{"username":"user2","password":"123"}` | 步骤二：设置的消息体数据被存放在请求体的 POST data 中 |

【为什么？】
这三种类型对应 HTTP 协议里「客户端能把数据放在哪儿」的全部三个位置：**URL query string**（参数）、**request body**（消息体数据）、**multipart body 的某个 part**（文件上传）。选错位置的后果不是「报错」，而是「静默不生效或服务端解析不到」——因为 HTTP 层完全合法，只是业务层读不到。另外一个关键点是编码：参数表里的值会参与 URL 编码，中文、特殊符号、空格都可能在编码/解码环节被破坏，所以课程专门提醒「编码设置为 UTF-8 并勾选」。而消息体数据是**原样发送**的，不做 URL 编码——这既是它能承载 JSON 的原因，也是它容易因为转义、换行、变量拼接出错的原因。

【必须掌握】

| 场景 | 用哪种 | 注意事项 |
|---|---|---|
| GET 查询（分页、筛选） | 参数 | 会拼到 URL 后用 `&` 连接；中文要勾编码并设 UTF-8 |
| POST 表单提交 | 参数 | 走 application/x-www-form-urlencoded；与 multipart 二选一 |
| POST JSON 接口 | 消息体数据 | 需在 HTTP 信息头管理器里设 `Content-Type: application/json` |
| POST XML 接口 | 消息体数据 | 注意 XML 里的 `<`、`>` 不要被转义 |
| 上传图片/文件 | 文件上传（+ 勾 multipart/form-data） | 参数名与 MIME Type 要与接口文档一致；文件路径要可参数化 |

【企业场景】
你压测一个 JSON 接口，把 `{"username":"user2","password":"123"}` 直接填进了「参数」表——结果服务端返回 400。因为参数表会把内容做 URL 编码并拼成 `username=%7B%22username%22...` 这种形式，服务端按 JSON 解析自然失败。你的修正是：清空参数表，把 JSON 放进「消息体数据」，并在 HTTP 信息头管理器加一条 `Content-Type: application/json`。同时你把里面的用户名密码改成 `${username}`、`${password}` 变量，接 CSV 数据实现参数化——这样一套脚本就能支持上万个不同用户的登录压测。这几步是所有接口压测脚本的通用模板，务必形成肌肉记忆。

【面试考察】
1. **面试官怎么问**：「POST JSON 请求在 JMeter 里怎么配？」
   **回答框架**：消息体数据放 JSON + HTTP 信息头管理器设 Content-Type: application/json（必要时加 charset）+ 断言校验业务码。
2. **面试官怎么问**：「参数表和消息体数据的区别是什么？」
   **回答框架**：参数表会做 URL 编码并拼到 URL 或表单体；消息体数据原样放在 request body，适合 JSON/XML。
3. **面试官怎么问**：「怎么压测文件上传接口？」
   **回答框架**：勾 multipart/form-data + 参数类型选文件上传 + 正确填写参数名与 MIME Type，必要时用变量参数化文件路径。

【易错点】

| 常见错误 | 正确理解 |
|---|---|
| 把 JSON 字符串填进「参数」表 | 参数表会做 URL 编码并拼接，JSON 必须放「消息体数据」 |
| 用了消息体数据但没设 Content-Type 请求头 | 服务端可能按表单解析而报错；JSON 接口通常必须显式声明头 |
| 中文参数不设 UTF-8、不勾编码，出现乱码 | 编码字段要填 utf-8，参数表按需勾选编码，两端编码要一致 |
| 文件上传时 MIME Type 留空或写错 | MIME Type（课程原文写作 “MINE Type”，属笔误）决定服务端如何识别资源类型，必须按接口文档填写 |
| 以为「参数」和「消息体数据」可以混用 | 同一请求的请求体格式只有一个，混用会导致请求体与声明的内容类型不匹配 |

【我的理解】
1. 课程用「参数被拼在请求地址后面、用 & 连接」来描述 GET 参数的行为。请你据此推演：如果把 `<script>` 这类特殊字符直接写进参数表且不勾编码，会发生什么？这又说明了为什么「勾选编码」是必要的？
2. 「消息体数据原样发送」这个特性，对你在压测中做参数化（把变量拼进 JSON）提出了什么额外要求？你打算怎么保证拼出来的 JSON 永远合法？
