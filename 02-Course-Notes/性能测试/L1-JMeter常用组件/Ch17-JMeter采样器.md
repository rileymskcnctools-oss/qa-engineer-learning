### 知识点1：什么是采样器（Sampler），它在元件体系里的位置

【课程原话/定义】
> 采样器（Sampler）是用来模拟用户请求发送到目标服务器的组件。采样器的作用是模拟不同类型的用户操作或请求，以测试目标服务器的性能和稳定性。通过采样器可以模拟大量用户同时访问服务器的情况，从而评估服务器的性能表现。

课程给出 **常用的采样器**：
- HTTP Request Sampler
- Debug Sampler
- BeanShell Sampler

【为什么？】
JMeter 元件可以按「是否发请求」分成两类：**采样器**是唯一真正产生网络请求的元件；定时器、断言、前置/后置处理器、配置元件、监听器都只是围绕采样器服务的「辅助件」。这个区分极其重要，因为它解释了一连串报告现象：聚合报告里的 `Samples` 数只统计采样器执行次数；逻辑控制器多加了不会多一个样本；断言失败会把样本标红但不会多一个样本。理解了「只有采样器发请求」，你看报告时就能立刻判断每个数字的来源。

【必须掌握】

| 元件类别 | 是否发请求 | 在报告中的体现 |
|---|---|---|
| Sampler 采样器 | ✅ 发请求 | 每个采样器一次执行 = 1 个 Sample |
| Logic Controller 逻辑控制器 | ❌ 不发 | 不产生样本，只改变子节点执行次数 |
| Timer 定时器 | ❌ 不发 | 影响样本耗时，不产生样本 |
| Assertion 断言 | ❌ 不发 | 改变样本的成功/失败标记 |
| Pre/Post Processor | ❌ 不发 | 改变请求数据或提取响应数据 |
| Config Element 配置元件 | ❌ 不发 | 提供变量、默认值，覆盖范围决定生效范围 |
| Listener 监听器 | ❌ 不发 | 收集/展示样本，本身也是性能开销来源 |

【企业场景】
你第一次带队做压测，同事报过来一张聚合报告截图问「为什么 Samples 是 3000 而不是我说的一万人」。你只需要问两个问题就能定位：一是线程数 × 循环次数是多少，二是脚本里有没有逻辑控制器导致部分请求被跳过了。因为你清楚 Samples 的分子只有采样器，排查方向就收敛得很快——而不是去怀疑 JMeter「统计丢数」。

【面试考察】
1. **面试官怎么问**：「JMeter 里哪些元件会产生请求？」
   **回答框架**：只有采样器会发请求，其余元件都是辅助；顺带说出这个结论对读报告的意义（Samples / 断言 / 耗时分别由谁决定）。
2. **面试官怎么问**：「你常用的采样器有哪些？」
   **回答框架**：HTTP Request（Web 与接口压测核心）、Debug Sampler（调试变量）、BeanShell/JSR223 Sampler（写脚本扩展逻辑），再补一句「其他协议的采样器按需选用，如 JDBC Request」。
3. **面试官怎么问**：「压测跑出来的请求数和预期不一致，你怎么查？」
   **回答框架**：先核对线程数与循环次数，再检查逻辑控制器跳过、断言失败、CSV 数据用尽等可能，最后看聚合报告各 Label 的 samples 分布。

【易错点】

| 常见错误 | 正确理解 |
|---|---|
| 以为加了定时器、监听器会让请求数变多 | 它们都不发请求；只有采样器产生样本，请求数只由采样器 × 执行次数决定 |
| 把「监听器」误当成「采样器」写进脚本结构里 | 监听器只负责收集展示，与是否发请求无关 |
| 认为 Debug Sampler 也是发请求去调后端 | Debug Sampler 不向服务器发请求，只把调试信息输出到结果树 |
| 用「请求数」和「样本数」两个词混着说 | 一个采样器执行一次 = 一个样本；严格来说「样本数」才是 JMeter 的统计口径 |

【我的理解】
1. 「只有采样器发请求」这个结论，能不能解释「我加了一个事务控制器，但聚合报告里的 Samples 没变」？请你自己捋一遍因果。
2. 如果监听器本身也是性能开销来源，那么在真正的加压机上你该怎么处理监听器？先自己想，再看 [[Ch19-JMeter监听器]]。

### 知识点2：HTTP Request Sampler —— 压测的核心组件

【课程原话/定义】
> HTTP Request Sampler 是 Apache JMeter 中最常用的一种采样器，用于模拟发送 HTTP 请求到服务器，并获取响应结果。通过 HTTP Request Sampler，可以模拟测试各种 Web 应用程序、Web 服务和接口的性能和功能，是 JMeter 进行 Web 测试的核心组件之一。

课程的四个步骤：

| 步骤 | 操作路径 |
|---|---|
| 步骤一：添加线程组 | 右击 Test Plan(测试计划) → Add(添加) → Threads(线程（用户）) → Thread Group(线程组) |
| 步骤二：添加 HTTP 请求 | 右击创建的线程组 → Add(添加) → Sampler(取样器) → HTTP Request(HTTP 请求) |
| 步骤三：添加查看结果树 | 在取样器上右击 → Add(添加) → Listener(监听器) → View Results Tree(察看结果树) |
| 步骤四：点击运行 | 点击菜单栏中的三角图标开始运行，然后点击察看结果树，显示响应状态码为 200，代表请求成功 |

【为什么？】
这三步路径之所以固定，是因为 JMeter 的元件有**严格的父子层级要求**：线程组必须在测试计划下（它决定并发模型），采样器必须在线程组下（它决定被压的是什么），监听器必须在线程组或测试计划下（它决定看什么）。JMeter 用树形结构而不是配置文件来表达压测方案，好处是「思维模型即结构」——你的场景设计怎么想，树就怎么长。坏处是层级放错不会报错，只会静默地不生效，所以入门时必须把这几个路径记成肌肉记忆。

【必须掌握】

| 字段 | 含义 | 课程原文要点 |
|---|---|---|
| 协议 | 发送 HTTP 请求时的协议 | 可以是 http 或者是 https 或者 File，默认为 http |
| 服务器名称或 IP | 请求发送的目标服务器名称或 IP 地址 | 可以填域名或 IP |
| 端口号 | 目标服务器端口 | 默认为 80，https 的端口为 443 |
| http 请求 | 请求方法 | 可用方法包括 GET、POST 等 |
| 路径 | 目标 URL 路径 | 不包括服务器地址和端口；也可以写完整路径，但不规范 |
| 内容编码 | 内容编码方式 | 默认值为 iso8859；一般都填入 utf-8 |

【企业场景】
你要压测公司内网的一个订单查询接口。你新建线程组 → 加 HTTP 请求，服务器名称填测试环境域名、端口填 8080、方法选 GET、路径填 `/api/order/query`、内容编码填 `utf-8`。要点是**一定先把单请求跑通再谈并发**：点运行后看察看结果树是不是 200、响应体是不是正常的业务 JSON。很多新人一上来就把线程数调到 500，结果只是把「域名写错」这个错误放大了 500 倍，排查成本反而更高。

【面试考察】
1. **面试官怎么问**：「HTTP 请求采样器里哪些字段是必填的？」
   **回答框架**：服务器名称/IP 是必填，路径按需，协议与端口有默认值（http/80，https/443）；强调「内容编码建议显式填 utf-8」。
2. **面试官怎么问**：「路径能不能写完整 URL？」
   **回答框架**：能，但不规范——会绕过「服务器名称」字段的复用价值，参数化环境时到处要改；规范做法是 host/port/路径分开。
3. **面试官怎么问**：「怎么确认一个压测脚本是能跑通的？」
   **回答框架**：先用单线程跑通看 200 和业务响应，再逐步加并发；同时加响应断言，避免「全 4xx 也算通过」。

【易错点】

| 常见错误 | 正确理解 |
|---|---|
| 内容编码不填，中文参数乱码，以为是服务端问题 | 默认 iso8859，中文场景必须显式改成 utf-8 |
| 把 https 的地址配了 80 端口 | https 默认端口 443，配置要成对，否则连接超时或 4xx |
| 路径里重复写上了 host 和端口 | 路径字段只写 URL path；写成完整地址虽然能跑但不规范，环境切换时会很痛苦 |
| 只看到「运行结束」就认为压测成功 | 必须看响应状态码与业务响应内容；没有断言的压测结果不可信 |

【我的理解】
1. 为什么课程说「在路径里写完整 URL 不规范」？请你从「三个环境（测试/预发/生产）都要跑同一套脚本」这个角度解释一遍。
2. 如果内容编码填错导致响应乱码，你会优先怀疑是「请求编码」还是「响应编码」问题？打算怎么用察看结果树区分？

### 知识点3：Debug Sampler —— 不发请求的调试利器

【课程原话/定义】
> Debug Sampler 是 Apache JMeter 提供的一种特殊的采样器，其作用是在测试执行过程中插入一些调试信息，以便检查测试计划的执行过程和结果。Debug Sampler 并不发送实际请求到服务器，而是用于输出调试信息到 JMeter 的结果树中，以便于后续分析和调试。

课程步骤：添加线程组 → 添加 HTTP 请求 → 添加 Debug Sampler（右击创建的线程组 → Add → Sampler → Debug Sampler）→ 添加察看结果树，点击运行。

课程给出的 **基本界面选项**：

| 选项 | 说明 |
|---|---|
| JMeter Properties | 是否查看 JMeter 属性，默认为 False |
| JMeter Variables | 是否查看运行时变量，默认为 True |
| System Properties | 是否查看系统属性，默认为 False |

【为什么？】
压测脚本里最难的 Bug 不是「请求发不出去」，而是「变量取值不对」——关联提取出来的 token 是空的、CSV 读到了错行的数据、`__counter` 计数不符合预期。这些问题在 HTTP 请求的响应里看不出来，因为请求本身可能返回 200（只是带着错的参数）。Debug Sampler 的价值在于把 JMeter 内部的**变量状态快照**输出到结果树：你在关键节点插一个 Debug Sampler，就能看到「此刻这个线程里所有变量的值」。它不发请求、不占带宽、不影响被测系统，是最低成本的定位手段。默认只开 JMeter Variables 也是刻意的：变量才是你关心的，属性列表又长又无用。

【必须掌握】

| 使用时机 | 目的 |
|---|---|
| 关联请求之后 | 确认 token/订单号等提取结果是否正确、是否为空 |
| 参数化请求之前 | 确认 CSV 取到的每一列值是否符合预期 |
| 循环/条件控制器内部 | 确认计数器与分支判断依据的实际取值 |
| 脚本整体跑不通时 | 逐段插桩，二分定位是哪一步开始出问题 |

【企业场景】
你写的下单脚本在本地单线程跑得好好的，一放到加压机上跑 200 并发就出现大量「订单号为空」的失败。你把 Debug Sampler 插在「提交订单」前面，跑 1 个线程 2 个循环，看结果树发现第二轮循环里 token 变量还是第一轮的旧值——原因是 token 的提取器放在了一个被 If Controller 跳过的分支里。定位到根因后，你把提取器移到每次都会执行的层级，问题解决。整个排查过程 5 分钟，靠的就是 Debug Sampler 提供的「变量快照」。

【面试考察】
1. **面试官怎么问**：「脚本里的变量取值不对，你怎么排查？」
   **回答框架**：用 Debug Sampler 输出 JMeter Variables，插在可疑位置前后对比；配合察看结果树的 Response data 交叉验证。
2. **面试官怎么问**：「Debug Sampler 会不会影响压测结果？」
   **回答框架**：不发请求，对被测系统无影响；但它会产生样本并可能被监听器记录，压测正式跑时建议删掉或用「禁用」而不是留着。
3. **面试官怎么问**：「Debug Sampler 和加一个断言有什么区别？」
   **回答框架**：断言判对错，Debug Sampler 看取值；前者回答「成功还是失败」，后者回答「值到底是什么」，定位根因时要靠后者。

【易错点】

| 常见错误 | 正确理解 |
|---|---|
| 认为 Debug Sampler 会向服务端发一个调试请求 | 它完全不发请求，只是把 JMeter 内部信息输出到结果树 |
| 把 JMeter Properties 也打开，结果树被上万行属性刷屏 | 默认只看 JMeter Variables 就够了，属性表几乎用不上 |
| 正式压测时忘了关掉 Debug Sampler，导致结果里多了一堆样本 | 压测前要把它禁用或删除，否则统计口径被污染 |
| 用 Debug Sampler 却去看 Response data 找变量 | 变量值要看 Response data 里的 JMeterVariables 段，位置容易看漏 |

【我的理解】
1. 为什么 Debug Sampler 的默认设置是「JMeter Variables = True，其余为 False」？请你自己想一下这个默认值体现了设计者希望你关注什么。
2. 如果 Debug Sampler 也会产生样本，那它会不会污染聚合报告？你打算怎么既用它调试又不影响最终统计？

### 知识点4：BeanShell Sampler —— 用脚本扩展 JMeter 的能力

【课程原话/定义】
> BeanShell Sampler 是 Apache JMeter 提供的一种采样器，用于在测试计划中执行 BeanShell 脚本。BeanShell 是一种可嵌入 Java 代码的解释器，可以在运行时动态执行 Java 代码，因此 BeanShell Sampler 提供了一种非常灵活和强大的方式来扩展 JMeter 的功能和定制测试逻辑。

课程步骤：
1. 步骤一：添加 BeanShell Sampler 采样器——创建线程组，在线程组中添加 Debug Sampler，添加 BeanShell Sampler 采样器和 View Results Tree。
2. 步骤二：添加脚本增加功能——在 BeanShell Sampler 中添加 Java 脚本增加功能。
3. 步骤三：添加察看结果树，点击运行。

【为什么？】
JMeter 的图形化元件能覆盖 80% 的常规压测需求，剩下 20% 是「奇怪但必须做」的事：要按某种自定义规则生成签名、要拼装 Java 对象作为请求体、要从文件里按业务规则挑数据、要在压测过程中写自定义日志。这些用元件组合做不出来，用 Java 脚本却只要几行。BeanShell Sampler 给的就是这个逃生出口。同时要注意代价：脚本执行是 **CPU 密集**的，且加压机本身就是全流程瓶颈高发区，脚本越重，能压出的并发越低——所以它是「能不用就不用，用就要可控」的工具。现代 JMeter 更推荐用 JSR223 Sampler + Groovy（有编译缓存，性能远好于 BeanShell），这是【扩展知识】层面的选型建议。

【必须掌握】

| 维度 | BeanShell Sampler | 【扩展知识】JSR223 Sampler + Groovy |
|---|---|---|
| 语言 | BeanShell（Java 语法的解释器） | Groovy / Java / JS 等 |
| 执行方式 | 逐行解释 | 可编译并缓存编译结果 |
| 性能 | 较慢，高并发下开销明显 | 明显更快，官方推荐 |
| 适用 | 少量简单调试脚本 | 正式压测中的脚本逻辑 |

【企业场景】
你压测一个需要签名的开放接口，签名规则是 `md5(appId + timestamp + secret)`。这套规则没有现成元件可以直接生成，于是你用脚本采样器写几行代码算出签名并存入变量，后续 HTTP 请求直接引用 `${sign}`。另一个典型场景是造数据：你需要在压测过程中生成一批符合业务规则的手机号、身份证号并写入 CSV，用脚本采样器几行代码就能完成，比手工准备数据省掉大量时间。

【面试考察】
1. **面试官怎么问**：「JMeter 能自定义逻辑吗？怎么做？」
   **回答框架**：可以用 BeanShell / JSR223 Sampler 写脚本，也可以用前置/后置处理器；补一句新版本推荐 JSR223 + Groovy，因为有编译缓存。
2. **面试官怎么问**：「脚本采样器会不会影响性能测试结果？」
   **回答框架**：会。脚本执行消耗加压机 CPU，尤其在分布式压测时要评估加压机余量；重逻辑建议前置生成或打桩，别放在高压路径上。
3. **面试官怎么问**：「签名、加密这类场景怎么处理？」
   **回答框架**：脚本采样器/前置处理器生成变量，HTTP 请求引用；或直接调用被测团队提供的工具类打成 jar 放到 lib/ext。

【易错点】

| 常见错误 | 正确理解 |
|---|---|
| 把上百行的复杂业务逻辑塞进脚本采样器 | 脚本越重、加压机越容易成为瓶颈；能前置就前置，能参数化就参数化 |
| 认为脚本采样器一定不会发请求 | 它默认不发请求，但脚本里可以主动发起调用；它的「不请求」只是默认行为 |
| 在脚本里抛异常却不检查结果，导致后续变量为空 | 脚本异常会让样本失败但流程可能继续，必须看结果树或加断言确认 |
| 高并发场景用 BeanShell 而不是 JSR223+Groovy | 正式压测优先选有编译缓存的实现，避免加压机 CPU 被脚本吃掉 |

【我的理解】
1. 脚本采样器能极大提升灵活性，但也会把加压机变成瓶颈。请你设想一个场景，说明「灵活性」和「压测准确性」为什么会冲突，并给出你的取舍方案。
2. 如果同一个签名逻辑要在 5 个脚本里复用，你会怎么做？写在每个脚本里、做成 jar 包，还是别的方案？各自的维护成本如何？
