### 知识点1：JMeter 是什么（简介）

【课程原话/定义】
Apache JMeter 是一个**开源的 Java 应用程序**，用于进行**性能测试和负载测试**。它可以模拟多种协议的负载，被广泛用于测试 **Web 应用程序、Web 服务、数据库和其他网络服务**的性能。

【为什么？】
要理解 JMeter 的能力边界，只要抓住它的三个身份：

1. **它是"Java 应用程序"而不是"网站/云服务"** —— 所以它跑在 JVM 上，本机装好 JDK 就能启动（这也解释了为什么安装前提是 Java 环境）；同时也意味着它的资源消耗与 JVM 内存参数强相关（见知识点6的内存要求）。
2. **它的负载模型是"多线程"** —— JMeter 里一个线程 ≈ 一个虚拟用户（虚拟用户 = 由工具模拟的并发访问用户）。这是后面「线程组」一章全部参数的起点：所谓"设置 500 并发"，本质是让 JMeter 开 500 个线程。
3. **它靠 Sampler（取样器）扩展协议** —— 核心只自带 HTTP/HTTPS、FTP、JDBC、JMS、SOAP 等常用取样器，其他协议（Dubbo、Kafka、MQTT、gRPC…）通过**插件或二次开发**补。这就是"可模拟多种协议的负载"的实现方式，也预告了本课程 L4「JMeter 微服务压测」和 L5「JMeter 二次开发」为什么存在。

一句话：**JMeter 是一个"用线程模拟用户、用取样器模拟协议、用元件树组织脚本"的开源压测引擎。**

【必须掌握】

| 维度 | 课程定义 | 关键含义 |
|------|----------|----------|
| 形态 | 开源的 Java 应用程序 | 需 JDK/JRE 环境；跨平台 |
| 用途 | 性能测试、负载测试 | 与 L1 学过的负载/压力/稳定性场景直接对应 |
| 能力 | 可模拟多种协议负载 | 协议支持靠取样器＋插件扩展，不是内置万物 |
| 对象 | Web 应用、Web 服务、数据库、其他网络服务 | 不仅测 HTTP 接口，也能直压 DB（JDBC） |
| 负载手段 | 模拟多种协议的负载 | 本质是多线程（虚拟用户）并发 |

【企业场景】
你入职后第一次接压测任务，Leader 说"接口压测用 JMeter"。你要做的第一件事不是打开界面，而是**确认自己机器上的 Java 环境和 JMeter 版本**——因为 JMeter 是 Java 应用，JDK 缺失或版本过低会直接启动失败；同时你要清楚这台机器上 JMeter 能不能压到目标协议：如果被测服务是 HTTP 接口（最常见），自带取样器就够；如果 Leader 让你压的是公司内部的 Dubbo 服务，你要立刻意识到**默认 JMeter 压不了，得先确认有没有对应的插件/自定义取样器**，否则脚本写到一半才发现缺取样器，时间全浪费。

【面试考察】
面试官："JMeter 是什么？它能做什么？"

参考回答框架：
1. 定义：Apache JMeter 是开源的 Java 压测工具，用于性能测试和负载测试
2. 负载模型：以多线程模拟虚拟用户并发访问，可对服务器/网络/对象施加巨大负载
3. 协议能力：核心支持 Web、Web 服务、数据库等；其他协议靠插件/二次开发扩展
4. 工程价值：开源免费、跨平台、支持分布式加压、支持 GUI 和命令行两种模式，是当前国内市场占有率最高的开源压测工具

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 把 JMeter 当成"只能压 HTTP 接口的工具" | 自带取样器覆盖 HTTP/FTP/JDBC/JMS/SOAP 等，其他协议可通过插件扩展 |
| 认为压测工具就是"发请求" | 压测工具的核心是"并发 + 可控 + 可度量"，发请求只是表象 |
| 以为装了 JMeter 就能压所有协议 | 协议支持取决于是否有对应取样器/插件，Dubbo、Kafka 等需要额外扩展 |
| 把 JMeter 的"线程"当成操作系统线程去理解调优 | JMeter 线程是虚拟用户（VU）的载体，调优重点是并发模型与资源占用，不是 JVM 线程池调参 |

【我的理解】
> 引导思考题1：课程说 JMeter 是"Java 应用程序"——请你说出这个事实至少带来 2 个后果（提示：安装前提、运行资源、跨平台、界面风格）。
>
> 引导思考题2：如果 Leader 让你压一个 Dubbo 服务，而 JMeter 默认没有 Dubbo 取样器，你会怎么解决？（先回答方向，L4 会给出完整答案。自己先想一遍。）

### 知识点2：JMeter 的优点（为什么压测圈都选它）

【课程原话/定义】
JMeter 的优点（课程原文条目）：
- **纯 Java 程序，跨平台性强**：Windows、Mac、Linux
- **开源免费**
- **高可扩展性**：支持插件和扩展
- **可对服务器、网络或对象模拟巨大的负载**，进行压力测试
- **可以用于接口测试**
- **支持分布式、多节点部署**
- **支持 UI 以及命令两种操作方式**

【为什么？】
这七条不是并列的"优点罗列"，它们各自解决了压测落地中的一个具体障碍：

| 优点 | 解决的现实障碍 |
|------|----------------|
| 纯 Java 跨平台 | 团队里 macOS / Windows / Linux 混用，脚本要能互相拿来即跑 |
| 开源免费 | LoadRunner 商业授权昂贵，中小团队与个人学习没有成本 |
| 高可扩展性 | 各家协议/自定义鉴权千差万别，插件机制让"压不了"变成"加个插件" |
| 可模拟巨大负载 | 压测的目的就是找到系统拐点（L1 压力曲线模型），负载上不去就测不出拐点 |
| 可用于接口测试 | 一套工具两用：既能做接口功能调试（断言），也能做性能压测 |
| 支持分布式多节点 | 单机线程上限有限（受本机 CPU/内存/端口限制），大并发必须多机并行加压 |
| UI + 命令两种模式 | GUI 只用于调试脚本，真正压测必须用命令行（GUI 本身耗资源、会干扰结果） |

特别注意最后一条——它是**工程纪律**而不是"便利性优点"：GUI 模式下 JMeter 要实时渲染结果树/图表，这部分开销会算在你自己的机器上，同时也会扭曲 RT 数据。所以企业里公认的做法是 "**GUI 调脚本，CLI 跑压测**"，这也解释了为什么后面的分布式与 CI 集成章节全在讲命令行参数（`-n -t -l -e -o`）。

【必须掌握】

| 优点 | 一句话记忆 | 企业里的具体体现 |
|------|-----------|------------------|
| 纯 Java 跨平台 | 装了 JDK 就能跑 | Win/Mac/Linux 共用一份 `.jmx` 脚本 |
| 开源免费 | 零授权成本 | 团队人人都能装，不用申请 License |
| 高可扩展性 | 插件＋自定义元件 | 装插件管理器补充协议、自研函数/取样器 |
| 模拟巨大负载 | 多线程＋分布式 | 单机不够就多机并行加压 |
| 可用于接口测试 | 断言＋结果树 | 接口调试与压测共用一套脚本 |
| 分布式多节点 | master-slave 加压 | 大促前压全链路需要多台压测机 |
| UI＋命令双模式 | GUI 调试 / CLI 执行 | `jmeter -n -t xx.jmx -l result.jtl` 进 CI |

【企业场景】
你排大促压测计划时，要把"工具选型"写进方案里并说明理由：被测是 HTTP + RPC 混合链路、团队没有采购预算、需要压到 5000 并发、脚本要能在 Jenkins 里每天自动跑。这时候你会写出这样一段话——"选用 JMeter：开源免授权；HTTP 场景用自带取样器，RPC 场景通过插件扩展；5000 并发单机压不动，采用 1 master + 3 slave 分布式加压；执行阶段统一走命令行模式并接入 CI，避免 GUI 开销污染指标"。**这段话的每一句，都能在上面的优点表里找到对应项**——面试和工作汇报时都要能这样"优点 → 落地动作"地答出来。

【面试考察】
面试官："JMeter 和 LoadRunner 有什么区别？为什么你们用 JMeter？"

参考回答框架：
1. 授权与成本：JMeter 开源免费；LoadRunner 商业授权，成本高
2. 平台与脚本：JMeter 纯 Java 跨平台、脚本是 XML（`.jmx`）便于版本管理；LoadRunner 偏 Windows、脚本格式封闭
3. 扩展与生态：JMeter 插件生态活跃，可二次开发；LoadRunner 依赖官方版本迭代
4. 能力侧重：LoadRunner 在协议覆盖、录制回放、企业级报表上更成熟；JMeter 在开源生态、CI 集成、接口测试复用上更强——**选型要看预算、协议、团队技能和是否要进流水线**

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| "GUI 界面跑压测更方便，就用 GUI 压" | GUI 只适合调试脚本；正式压测必须 `-n` 命令行模式，否则 GUI 渲染开销会污染结果 |
| 认为开源＝功能弱 | 开源只是授权模型，JMeter 的功能与协议覆盖可以通过插件持续扩张 |
| 认为单机线程数想开多少开多少 | 单机并发受 CPU/内存/端口/操作系统的实际限制，超大并发必须分布式 |
| 把"可以用于接口测试"理解成能替代 Postman | JMeter 能发请求+断言，但接口调试体验不如 Postman；它的主场是压测与批量化 |

【我的理解】
> 引导思考题1：七条优点里，哪一条最容易被新人忽略、但在企业里是**纪律性要求**？为什么它会直接决定压测数据的可信度？
>
> 引导思考题2：如果公司预算充足、被测协议非常偏门（比如自研私有协议 + 硬件网关），你会怎么说服 Leader 依然选/不选 JMeter？请列出你的判断依据。

### 知识点3：安装前提——Java 环境

【课程原话/定义】
**注意：JMeter 需要 Java 8+ 环境，因此前提是本地已安装 JDK。** 安装 Java 可以参考 Java 安装教程贴进行安装。
环境验证命令：
```
java --version
```

【为什么？】
为什么必须是 **JDK**，而不是只要有 JRE 就行？这是新手最容易踩的坑：

- **JRE 只能"运行"Java 程序，JDK 才能"开发/分析"Java 程序**。JMeter 本身只需要运行，但一旦进入真实工作——你要采样 JVM 数据、要读 GC 日志、要用 `jvisualvm`/`jstack` 分析被测服务的 JVM（这些属于 L4/L5 内容）——本机没有 JDK 就只能干瞪眼。企业压测机统一装 JDK 是惯例。
- **版本决定兼容性**：课程说 JMeter 需要 Java 8+，是因为 JMeter 5.x 系列在 Java 8 上可运行；而**越新的 JMeter 版本对 JDK 下限要求越高**（例如 JMeter 5.6.x 已要求 Java 8+，而更高版本要求 Java 17+）。这句话的工程含义是：**装 JMeter 之前先确认 JDK 版本，装完之后用 `java --version` 亲自验证**，不要相信"我装过 Java"的记忆。
- **环境变量 PATH 决定命令能不能直接用**：`java --version` 能打印出版本号，说明 JDK 的 `bin` 已在 PATH 中——这也是后面知识点5配置 JMeter 环境变量时要重复一遍的动作。

【必须掌握】

| 项目 | 要求 | 验证方式 |
|------|------|----------|
| Java 版本 | Java 8+（课程原文口径） | `java --version` |
| 安装类型 | JDK（而非仅 JRE） | `javac -version` 能出版本即说明是 JDK |
| 环境变量 | `JAVA_HOME` 指向 JDK 根目录，`bin` 加入 PATH | 任意目录下执行 `java --version` 有输出 |
| 顺序 | **先装 Java，再装 JMeter** | 反了的话 JMeter 启动会报找不到 Java 环境 |

【企业场景】
你拿到一台新的压测机（或虚拟机），要做的第一件事是**固化环境基线**：执行 `java --version` 记录 JDK 版本，再执行 `java -version` 对比，把结果写进压测环境的"环境说明"里。为什么必须记录？因为压测结果是要拿来做结论的——如果同一套脚本上周 RT 是 200ms、这周是 400ms，第一件事就是核对 JDK 与 JMeter 版本是否被人换过（版本差异会改变 JMeter 自身的性能表现）。**在性能测试里，环境变更就等于结论变更。**

【面试考察】
面试官："JMeter 运行需要什么环境？你部署过压测机吗？"

参考回答框架：
1. 语言环境：JMeter 是 Java 应用，需要 JDK/JRE，课程口径为 Java 8+（新版本要求更高）
2. 操作系统：Windows / Mac / Linux 均可，压测机通常选 Linux（资源占用低、可远程管理）
3. 内存：官方建议至少分配 1GB 给 JMeter，大型测试需要更多（受 JVM 堆参数影响）
4. 验证动作：`java --version` 与 `jmeter -v` 双验证，并把版本写入环境说明，保证压测可复现

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 只装 JRE 就装 JMeter | 课程明确要求 JDK；后续 JVM 剖析也需要 JDK 工具，企业统一装 JDK |
| 凭记忆认为"我装过 Java" | 必须在终端执行 `java --version` 看到实际版本号才算验证通过 |
| 把 `java --version` 和 `java -version` 当同一个东西 | 两者都能输出版本，习惯上一个看完整版本串、一个看简要；关键是**确实执行并核对**，别想当然 |
| 先装 JMeter 再装 Java | 顺序反了会导致 JMeter 启动报 Java 环境错误，新手机器最容易犯 |

【我的理解】
> 引导思考题1：为什么企业要求压测机"统一装 JDK 而不是 JRE"？请把答案和你后面要学的 JVM 剖析/GC 日志分析联系起来想。
>
> 引导思考题2：如果 `java --version` 报 "command not found"，但 Java 明明安装过了，你会按什么顺序排查？（提示：安装路径 → 环境变量 → 终端是否重开）

### 知识点4：下载 JMeter

【课程原话/定义】
下载渠道（课程原文）：
- **官网下载地址**：JMeter 官网下载
- 找到 **binary 可运行文件包**，选择想要下载的 JMeter 版本，可以选择 **zip 或 tgz 格式**
- **微盘下载地址**：JMeter 微盘下载（课程提供的国内镜像/网盘渠道）

【为什么？】
为什么强调"找 **binary** 包"而不是别的包？

- 官网下载页上的产物有三类：**binary（可运行包）**、**source（源码包）**、以及各类校验/插件文件。压测使用只需要 binary 包——**source 包是给二次开发者的**（要编译、要改源码），它不是"更完整的版本"。
- **zip 与 tgz 的选择规则**：Windows 习惯用 `zip`，Linux/macOS 习惯用 `tgz`（tar.gz）。本质是压缩格式差异，解压后目录结构完全一致。
- **课程保留网盘渠道的原因**：官网在海外，公司内网或国内网络下载慢/失败很常见。**企业里更规范的做法是把安装包放到内网制品库或共享目录**（附带版本号与校验值），保证全组用的是同一版本——这和"压测环境基线"是同一件事。

【必须掌握】

| 下载项 | 说明 | 注意 |
|--------|------|------|
| binary 包 | 可直接运行的发行包 | 压测只用这个 |
| source 包 | 源码包 | 二次开发/看实现时才需要，不是必需 |
| 格式 | zip（Windows）/ tgz（Linux、macOS） | 解压后目录结构一致 |
| 版本 | 选择稳定版本并**固定**版本 | 团队内统一版本，避免结果不可比 |
| 产物 | 解压后得到 `apache-jmeter-x.y.z` 目录 | 内含 `bin/`、`lib/`、`ext/` 等 |

【企业场景】
你要给团队搭建压测环境，正确的做法是：从官网（或内网制品库）下载指定版本的 binary 包 → 解压到统一路径（例如 Linux 下的 `/opt/apache-jmeter-5.6.3`，不要放在个人目录）→ 把版本号登记到"环境说明"文档 → 让所有压测机用同一个包。**如果每个人的 JMeter 版本不一样，两个人跑出来的 TPS 会不一样**，而 TPS 是你们向业务方交付的结论数据，这种偏差是要背责任的。

【面试考察】
面试官："JMeter 怎么安装？你会在生产/压测环境怎么放？"

参考回答框架：
1. 下载：官网下载 binary 包（zip/tgz），也可用内网镜像加速
2. 解压：解压到统一目录（Linux 常放 `/opt`），不使用个人目录
3. 版本管理：固定版本号并登记，团队统一，保证结果可比
4. 后续：配置环境变量（下一知识点），用 `jmeter -v` 验证

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 下载了 source 源码包 | 压测只需要 binary 包；source 是给二次开发的 |
| 团队各人用不同 JMeter 版本 | 版本差异会造成 TPS/RT 口径偏差，必须统一并登记 |
| 解压到个人目录/桌面 | 压测机应放统一路径（如 `/opt`），便于多用户、多任务复用 |
| 以为 zip 和 tgz 解压出来的内容不同 | 只是压缩格式不同，解压后目录结构一致 |

【我的理解】

### 知识点5：环境配置（把 `bin` 配进环境变量）

【课程原话/定义】
解压 JMeter 压缩包后，**将 JMeter 的 `bin` 目录配置到环境变量中**（Windows 系统配置环境变量 / macOS 系统配置环境变量）。
macOS 系统配置环境变量：编辑 `.bash_profile`
```
# JMeter
JMETER_HOME = /Users/feier/apache-jmeter-5.6.3
export JMETER_HOME
export PATH = $JMETER_HOME /bin: $PATH
```
注：配置环境变量后，在任意目录下打开终端输入 `jmeter` 都可以打开 JMeter。

【为什么？】
为什么要多此一举配置环境变量？本质是**让"命令"与"安装位置"解耦**：

- 不配环境变量，你每次都得 `cd` 到 `bin` 目录再敲 `./jmeter`；一旦机器上有多个版本、或者要在 CI 脚本里执行压测，写死路径就是灾难。
- 配了环境变量后，`jmeter` 就是一个"全局命令"，**任何目录、任何脚本、任何用户都能调用**——这正是后面 CI 集成、分布式压测（slave 上也要能起 `jmeter-server`）的必要前提。
- `JMETER_HOME` 的意义在于"单一事实来源"：路径只写一次，`PATH` 从它派生，将来升级版本只改一行。

> **课程原文勘误（重要）**：课程给出的 shell 代码存在语法错误——赋值语句的 `=` 两边不能有空格，`export PATH = ...` 也写成了一串带空格的伪代码。正确的写法应为：
> ```bash
> # JMeter
> JMETER_HOME=/Users/feier/apache-jmeter-5.6.3
> export JMETER_HOME
> export PATH=$JMETER_HOME/bin:$PATH
> ```

【必须掌握】

| 系统 | 配置文件/入口 | 关键动作 |
|------|---------------|----------|
| macOS | `~/.bash_profile`（或 `.zshrc`） | `JMETER_HOME=...` → `export JMETER_HOME` → `export PATH=$JMETER_HOME/bin:$PATH` |
| Windows | 系统属性 → 环境变量（Path 追加 `bin` 目录） | 新建 `JMETER_HOME`，并在 `Path` 中追加 `%JMETER_HOME%\bin` |
| 生效方式 | 重开终端 / `source ~/.bash_profile` | 环境变量不生效多半是没重开终端 |
| 验证 | 任意目录执行 `jmeter -v`（或直接 `jmeter` 启动 GUI） | 能打印版本/拉起界面即配置成功 |
| 路径变量 | `JMETER_HOME` = JMeter 解压根目录 | 注意是根目录，`PATH` 里才补 `bin` |

【企业场景】
你负责把 JMeter 压测接进 Jenkins。流水线（agent 机上的 shell 步骤）要能直接执行 `jmeter -n -t script.jmx -l result.jtl`——这要求 **Jenkins 运行账号** 的环境变量里有 `JMETER_HOME` 与 `PATH`。常见坑是"我在自己终端能跑，Jenkins 上却报 `jmeter: command not found`"，原因就是环境变量配在了你自己的 shell 配置里，而不是系统级/服务账号级。你的做法应该是：系统级配置 JDK 与 JMeter 的 `PATH`，或在流水线脚本里显式 `export JMETER_HOME=... && export PATH=$JMETER_HOME/bin:$PATH`，并写入环境说明文档。

【面试考察】
面试官："JMeter 装好后为什么要配置环境变量？你是怎么配的？"

参考回答框架：
1. 目的：让 `jmeter` 成为全局命令，任何目录/脚本/用户都能调用（CI、分布式都依赖这一点）
2. 做法：定义 `JMETER_HOME` 指向解压根目录 → 把 `$JMETER_HOME/bin` 追加进 `PATH`
3. 验证：重开终端后任意目录执行 `jmeter -v`，能出版本即成功
4. 踩坑经验：变量配在个人 shell 里，Jenkins/其他账号执行时报 command not found——应在系统级或流水线内显式导出

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 按课程原文照抄 `JMETER_HOME = /path`（等号带空格） | shell 赋值等号两侧**不能有空格**，否则被解析成命令而报错 |
| `PATH` 里配的是 JMeter 根目录而不是 `bin` | 根目录下没有可执行文件；必须配 `$JMETER_HOME/bin` |
| 改完配置文件不重开终端 | 环境变量只在新的 shell 会话里生效，需 `source` 或重开 |
| 只在个人用户下配，忽略 CI/服务账号 | 流水线要以运行账号的视角验证 `jmeter -v`，否则上 CI 必挂 |
| 覆盖 `PATH`（写成 `PATH=$JMETER_HOME/bin`） | 必须**追加**（`:$PATH`），直接覆盖会让系统命令全部失效 |

【我的理解】
> 引导思考题1：课程原文的 shell 代码为什么是错的？请你自己写出正确版本，并说明"等号两边不能有空格"属于哪一类 shell 语法规则。
>
> 引导思考题2：为什么"我在本地终端能跑，Jenkins 上跑不了"是环境变量配错而不是 JMeter 装错了？你的排查顺序是什么？
