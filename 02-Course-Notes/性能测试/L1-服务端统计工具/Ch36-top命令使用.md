### 知识点1：top 是什么，为什么它是压测排错的主力工具

【课程原话/定义】
在 Linux 中，top 命令是一个**动态显示系统状态的监视工具**，可以实时显示系统中各个进程的资源占用状况，类似于 Windows 的任务管理器。top 命令可以定期更新和显示系统中最活跃进程的信息，包括 CPU 使用率、内存占用、进程状态等。

课程给出的"top 命令的作用"（原文 6 条）：
1. **实时性能监控**：提供实时的系统状态视图，快速识别和解决性能问题；
2. **资源使用情况**：查看各进程的 CPU 使用率、内存占用、虚拟内存使用量等关键指标；
3. **进程管理**：不仅显示资源使用，还提供交互功能，如按 PID 杀进程、改变进程优先级；
4. **系统状态概览**：显示总体状态（总 CPU 使用率、内存使用、负载平均值）；
5. **动态更新**：定期刷新信息，便于观察长期趋势与性能变化；
6. **易于使用**：命令行工具，按键操作简单直观。

【为什么？】
[[Ch35-性能分析系统级别指标io cpu mem net]] 解决的是"**哪一类资源**有问题"，但要落地成动作，你还得回答"**是哪个进程、哪个线程**"。top 的价值就在这个位置——它是**从"系统级"过渡到"进程级"的那一步**，也是唯一一个"一边看整体、一边看进程、还能现场操作"的工具（课程原文把它比作 Windows 任务管理器，非常贴切）。

对压测工程师来说，top 有 3 个不可替代的用法：
1. **看整体状态分解**：`%Cpu(s)` 里的 `us / sy / wa / id` 一眼告诉你"CPU 忙的是用户代码还是内核、还是在等 IO"；
2. **定位进程**：找出**谁的 %CPU / %MEM 最高**——压测时通常是被测服务（Java/Python 进程），确认它是它，再看它的占用；
3. **接着往下钻井**：`top -H -p <PID>` 看**线程**级占用，再配 `jstack` / 火焰图看代码（这一环是 [[../L1-性能测试体系/Ch06-行业流行性能剖析工具介绍|L1 Ch06-行业流行性能剖析工具介绍]] 里"压测 → 监控 → 剖析"链条的中间一步）。

【必须掌握】

| top 的作用（原文 6 条） | 压测里的具体用法 |
|---|---|
| 实时性能监控 | 压测中持续盯 `%Cpu(s)` 的 wa/id 与负载 |
| 资源使用情况 | 看被测进程的 %CPU / %MEM / RES |
| 进程管理 | 现场 `k` 结束异常进程、`r` 调优先级（慎用） |
| 系统状态概览 | load average、内存/交换概览 |
| 动态更新 | 观察指标随时间的变化趋势（而不是一个瞬时值） |
| 易于使用 | 按键交互（排序、展开每核、显示线程） |

| top 在排查链条中的位置 | 上游 | 本章 | 下游 |
|---|---|---|---|
| 问题 | 哪类资源有问题（vmstat / iostat / free） | **哪个进程占用高、状态如何** | 哪个线程、哪段代码（jstack / 火焰图 / 慢查询） |

【企业场景】
压测中服务 RT 抖动、TPS 掉。你 ssh 到被测服务器敲 `top`：`%Cpu(s)` 显示 `wa 35%`、`us 20%`——**CPU 大部分时间在等 IO**；再按 `M` 按内存排序，发现被测 Java 进程 RES 一路涨到极限且 `si/so` 非 0（配合 `vmstat` 确认）→ 结论是"内存压力导致换页，进而拖慢整体"。**如果没有 top 的进程级视角，你只知道"机器在等 IO"，不知道该改哪个进程或服务。** 另一个高频用法是压测中现场确认"施压机上是不是 JMeter 自己把 CPU 吃满了"——这决定了你的容量结论是否可信。

【面试考察】
面试官："压测中怎么用 top 定位问题？top 和 vmstat 有什么区别？"

参考回答框架：
1. 定位链条：vmstat/iostat 等回答"哪类资源异常"，top 回答"哪个进程/线程占用高"；
2. top 读法：先看 `%Cpu(s)`（us 用户态、sy 内核态、wa 等 IO、id 空闲）与 load average；再按 `P`（CPU）/`M`（内存）排序找头号进程；确认是被测服务还是施压机进程；
3. 下钻：`top -H -p <PID>` 看线程 → jstack / 火焰图看代码；
4. 分工：vmstat 更适合"每秒一行"的持续采集与脚本化判断；top 更适合"人在现场交互式排查"。

【易错点】

| 常见错误 | 正确理解 |
|---|---|
| 只看 %CPU 最高的进程就下结论 | 需要结合 `%Cpu(s)` 的状态分解（us/sy/wa）与内存指标；有时"最忙的进程"只是受害者 |
| 忘记确认施压机自身的负载 | 施压机（JMeter）CPU 打满会让指标失真 → 假瓶颈；压测时施压机也要被监控 |
| 把 top 的瞬时值当结论 | top 是**动态**工具，要观察一段时间的趋势（尤其内存增长、wa 波动） |
| 在生产机器上随手 `k` 杀进程 | 交互键确实能杀进程，但生产环境必须走变更流程；压测机上也应谨慎 |
| 觉得"top 能替代 vmstat/iostat" | top 的强项是"进程视角"；磁盘饱和（%util）等要看 iostat，纯 CPU 队列看 vmstat 更直观 |

【我的理解】引导题（用自己的话回答）：
1. 为什么说 top 是"系统级指标"与"代码级剖析"之间的那座桥？请用一条排查链把三者的关系说清楚。
2. 压测报告里的 TPS 明显偏低，你会怎么用 top 判断"是不是施压机自己成了瓶颈"？

### 知识点2：三段输出怎么读（负载 / CPU 状态分解 / 内存 / 进程表）

【课程原话/定义】
（原文"用法"部分只有三句话：生成一个持续监控的性能视图、展示了 CPU 的运行情况、展示了内存空间的使用情况、展现了哪些应用程序正在运行。字段含义原文未给出。）

【为什么？】
top 一屏分四块，**每块回答一个问题**，按这个顺序读就不会乱：

1. **第 1 行：系统概览**——当前时间、已运行时长、登录用户数、`load average: 1m 5m 15m`。判断"系统压力"的第一眼。
2. **第 2 行：进程统计**——total 进程数 / running / sleeping / stopped / zombie。**zombie 不为 0 值得注意**（父进程未回收子进程）。
3. **第 3 行：`%Cpu(s)` 状态分解**——这是 top 最有价值的一行：`us`（用户态，业务代码）、`sy`（内核态，系统调用/网络栈）、`ni`（nice 调整过的）、`id`（空闲）、`wa`（等 IO）、`hi`/`si`（硬/软中断）、`st`（被虚拟化偷走的时间，虚拟机里出现说明宿主竞争）。
4. **第 4-5 行：内存与交换**——`MiB Mem`（total/free/used/buff/cache）与 `MiB Swap`（total/free/used）。**Swap 的 used 在压测中持续上涨＝危险信号**。
5. **进程表**——PID / USER / PR / NI / VIRT / RES / S / %CPU / %MEM / TIME+ / COMMAND，其中 `RES` 是进程实际占用的物理内存（排内存问题看它），`TIME+` 是累计 CPU 时间（`TIME+` 很高说明这个进程长期在烧 CPU，与"瞬时 %CPU 高"不同）。

【必须掌握】

| 位置 | 字段 | 含义与判读 |
|---|---|---|
| 第一行 | load average 1m/5m/15m | 与核数比；趋势判断突发 vs 持续（同 [[Ch35-性能分析系统级别指标io cpu mem net]]） |
| 第二行 | Tasks: total / running / sleeping / zombie | `zombie` 非 0 → 有未回收的子进程；`running` 长期大于核数 → CPU 排队 |
| 第三行 | `us / sy / ni / id / wa / hi / si / st` | us 高＝业务代码耗 CPU；sy 高＝内核态（系统调用/切换）；wa 高＝等 IO；st 高＝虚拟化被抢占 |
| 第四行 | MiB Mem: total/free/used/**buff/cache** | free 小是正常的（缓存）；关注 used 与 cache 的关系 |
| 第五行 | MiB Swap: used | **used 持续上涨＝内存压力**，与 `vmstat` 的 si/so 互相印证 |
| 进程表 | RES / VIRT / SHR | RES＝实际物理内存（排错看它）；VIRT 含未占用地址空间，不代表真实占用 |
| 进程表 | S（状态）/ %CPU / %MEM / TIME+ | 状态字母：R 运行、S 睡眠、D 不可中断（IO）、Z 僵尸、T 停止；TIME+＝累计 CPU 时间 |

【企业场景】
你压测时发现接口 RT 偶发 3 秒。top 一屏读出三条线索：`%Cpu(s)` 里 `wa 30%`、`si 1%`（内存换页）、Java 进程 `S` 列频繁出现 `D`（不可中断睡眠＝等磁盘/IO，且不可被打断，这类进程多说明 IO 是瓶颈）。**三条线索指向同一结论：IO/内存压力**。接着 `iostat -x 1` 验证 `%util`，再 `top -H -p PID` 找线程——一条"从三行概览到具体线程"的排查路就打通了。

【面试考察】
面试官："top 输出里你最关注哪几处？%Cpu(s) 的 wa 高说明什么？"

参考回答框架：
1. 关注 load average（与核数比）、`%Cpu(s)` 状态分解、Swap used 趋势、进程表里的 %CPU/%MEM/RES 与 `S` 状态；
2. `wa` 高 = CPU 空闲但在等 IO（磁盘/网络文件系统），瓶颈不在 CPU 而可能在磁盘；配合 `si/so` 排除换页；
3. `sy` 高 = 内核态开销大（系统调用多、上下文切换频繁、网络包多）；
4. `st` 高（虚拟机上）= 宿主 CPU 被其他虚拟机抢占，属于"环境问题"，要在报告里单列。

【易错点】

| 常见错误 | 正确理解 |
|---|---|
| 把 `wa` 高当成 CPU 瓶颈 | `wa` 是"等 IO"的时间，瓶颈在磁盘/存储或内存换页 |
| 用 VIRT 判断进程占用内存 | VIRT 包含未实际使用的地址空间；看 **RES**（+ SHR） |
| 忽略 `zombie` | 僵尸进程本身不耗 CPU，但说明父进程没正确回收子进程；数量增长要查代码/服务管理 |
| 把 `st` 忽略 | 虚拟机上 `st` 高是"宿主机抢走了 CPU"，会造成无法通过优化应用解决的问题 |
| 只看 free 不看 Swap | 压测中 Swap used 持续上涨是最早的恶化信号之一（配合 si/so） |

【我的理解】引导题（用自己的话回答）：
1. 请把 top 的前五行各自"能回答什么问题"写成一句话。
2. 进程状态里的 `D` 与 `S` 有什么本质区别？为什么"一堆 D 状态进程"意味着 IO 问题？

### 知识点3：交互按键与命令行参数（P / M / 1 / H / -b / -n / -p）

【课程原话/定义】
（原文未给按键与参数，只提到"提供了交互功能，如按进程 ID 杀死进程、改变进程的优先级"。）

【为什么？】
top 真正的效率来自"**键盘操作 + 参数化调用**"这两件事。压测排查时最常用的只有几个，记住它们就够了：

**交互按键（运行中按）**：
- `P` 按 CPU 使用率排序、`M` 按内存排序、`T` 按累计 CPU 时间排序 —— 三个排序键，快速找"头号嫌疑进程"；
- `1` 展开/收起**每颗核**的占用 —— 判断"单核打满"（串行/锁问题）的关键；
- `c` 显示完整命令行 —— 同一台机器跑多个 Java 进程时，用它区分是哪个服务；
- `H` 显示线程 —— 或命令行 `top -H`，把视角从进程降到线程；
- `k` 结束进程、`r` 调整优先级（renice） —— 管理与急救用，生产上要谨慎；
- `h` 帮助、`q` 退出、`z` 彩色、`d`/`s` 改刷新间隔。

**命令行参数（用于采集与脚本化）**：
- `top -d 5` 每 5 秒刷新、`top -n 3` 只刷新 3 次后退出；
- **`top -b -n 1`（批处理模式）**：不做全屏刷新、直接输出文本，**可以重定向到文件或管道**——这是"用 top 做数据采集/记录证据"的标准姿势（压测过程留痕、写报告贴证据）；
- `top -p <PID>` 只看指定进程、`top -u <user>` 只看某用户的进程。

【必须掌握】

| 用法 | 作用 | 压测/排错场景 |
|---|---|---|
| `P` / `M` / `T` | 按 CPU / 内存 / 累计 CPU 时间排序 | 快速定位头号进程（先确认是不是被测服务） |
| `1` | 展开每颗核 | 判断"整体不高但一颗核满"（串行/锁） |
| `c` | 显示完整命令行 | 一台机器上多个同类进程时区分服务 |
| `H` / `top -H` | 显示线程 | 进程 → 线程级下钻（再接 jstack / 火焰图） |
| `k` / `r` | 杀进程 / 调优先级 | 现场急救；生产须走变更流程 |
| `top -b -n 1` | 批处理输出（可重定向） | **留痕与采集**：把压测时的资源证据存成文件 |
| `top -d 5` / `-n 3` | 刷新间隔 / 次数 | 控制采样频率，避免日志过大 |
| `top -p PID` / `-u user` | 只看指定进程 / 用户 | 排除干扰，聚焦被测服务 |

【企业场景】
压测报告需要"资源证据"：你在压测窗口内定时执行 `top -b -n 1 -p <被测服务PID> >> top_evidence.log`（配合 `vmstat 5` 的输出一起留档），压完把关键片段贴进报告。**比截图更专业的是"可复制的文本证据 + 时间戳"**——面试时讲"我用 top -b 采集了压测期间的服务进程资源曲线"比"我看了下 top"高一个层次。现场排查时则用交互模式（`P` 排序、`1` 展开、`H` 看线程）快速定位。

【面试考察】
面试官："top 你常用哪些操作？怎么做压测期间的资源记录？"

参考回答框架：
1. 交互：`P`/`M`/`T` 排序、`1` 展开每核、`c` 看完整命令、`H` 看线程、`k` 杀进程（谨慎）；
2. 参数：`-d` 间隔、`-n` 次数、`-p` 指定进程、`-u` 指定用户；
3. **采集**：`top -b -n 1` 批处理输出可重定向，配合 `vmstat`/`iostat` 定期采集，形成压测期间的可追溯证据；
4. 端到端：top 找进程 → `top -H` 找线程 → 应用级工具（jstack/火焰图/慢日志）定位代码。

【易错点】

| 常见错误 | 正确理解 |
|---|---|
| 在非交互环境（脚本/CI）里直接跑 `top` | 全屏刷新在管道里会输出乱码；脚本里用 **`-b`** 批处理模式 |
| 用 `top` 的输出做长时间采样却不加 `-n` | 不加次数会一直跑；采集时用 `-n` 限定次数 + `-d` 控制间隔 |
| 用 `%CPU` 排序后就断言"它就是根因" | 先确认它是被测服务（`c` 看命令行），再看它高在 us 还是 sy、是否在等 IO |
| 在生产上随手 `k` | 交互键能杀进程，但生产改动用变更流程；压测机上也应留记录 |
| 只截屏不留文本 | 报告证据用 `top -b -n 1` 的文本输出更可追溯（可 diff、可贴、可归档） |

【我的理解】引导题（用自己的话回答）：
1. 如果压测脚本跑在 CI 上（没有交互终端），你会怎么用 top 采集证据？写出你用的命令。
2. `1`（展开每核）这个按键，能帮你发现哪一类"看起来不是问题的问题"？

### 知识点4：压测场景下的 top 排错套路（与 vmstat / iostat / jstack 串起来）

【课程原话/定义】
（原文未涉及，本节是本章知识的落地用法。）

【为什么？】
把 top 用出价值的关键，是把它放进一条**固定的排查路径**里，而不是"想起来就敲一下"。推荐的四步套路：

1. **确认现象**：JMeter 侧看 TPS / RT / 错误率 / 活动线程数，先排除"脚本或施压机"的问题；
2. **top 定性**：`%Cpu(s)` 看 us / sy / wa → 决定方向；load average 与核数比 → 判断是否过载；Swap used → 排除内存；
3. **top 定量**：`P` 排序找头号进程 → 确认是被测服务（`c` 看命令行）→ `top -H -p PID` 找头号线程；
4. **交叉验证 + 下钻**：wa 高 → `iostat -x 1`；CS 高/线程多 → 线程池与锁；线程确定后 → `jstack` 取栈、火焰图看热点（[[../L1-性能测试体系/Ch06-行业流行性能剖析工具介绍|L1 Ch06-行业流行性能剖析工具介绍]]）。

这套套路的好处是**每一步都有"进入下一步的条件"**（wa 高才查磁盘，sy 高才查系统调用），而不是把所有命令敲一遍碰运气。

【必须掌握】

| 观察到的现象 | 指向的瓶颈 | 下一步命令 |
|---|---|---|
| `us` 高、`id` 低 | 业务代码消耗 CPU | `top -H` 找线程 → jstack / 火焰图 |
| `sy` 高、`cs` 高 | 内核态/上下文切换/网络栈 | vmstat 看 cs、检查线程数与系统调用 |
| `wa` 高、`si/so` ≈ 0 | 磁盘或存储 IO | `iostat -x 1` 看 `%util` / `await` |
| `wa` 高、`si/so` > 0 | 内存不足在换页 | `free -m` 看 available、查内存泄漏/调堆 |
| load 高但 `%CPU` 不高 | 大量进程在 D 状态（等 IO） | `ps -eo stat,pid,comm` 找 D 状态进程（见 [[Ch37-ps命令]]） |
| 一台机器多个 Java 进程 | 需确认被测服务 | top 里按 `c` 看完整命令行 |
| `st` 明显 | 虚拟化宿主抢占 | 报给运维/云平台，属环境问题 |

**【企业场景】**
排查复盘会上，你被要求"证明瓶颈在数据库而不是应用"。你的取证链：top（应用进程 RES 稳定、%CPU 正常、wa 20%）→ `iostat`（应用机磁盘不饱和）→ vmstat（应用机无换页）→ 结论："应用机侧资源正常，RT 变化跟随数据库响应"→ 于是把结论指向 DB。**排查的产出不只是"找到瓶颈"，而是"用数据排除掉其他可能"**——这也正是面试官想听的思维过程。

【面试考察】
面试官："给你一台已经出现性能问题的服务器，你按什么顺序用命令定位？"

参考回答框架：
1. 定现象：先确认是哪一端（施压机 / 应用 / 中间件 / DB），JMeter 侧指标 + 服务端日志；
2. 定方向：`top`（%Cpu(s) 分解 + load + Swap）或 `vmstat 1`（r/b/si/so/wa/cs）；
3. 定对象：`top` 按 `P`/`M` 排序 + `c` 确认进程 → `top -H -p` 看线程；
4. 交叉验证：磁盘 → `iostat -x`；内存 → `free`/`meminfo`；网络/连接 → `ss`、`netstat`；
5. 下钻到代码：jstack / 火焰图 / 慢日志，并保持"排除法"的思路（把不是瓶颈的层显式排除）。

【易错点】

| 常见错误 | 正确理解 |
|---|---|
| 跳到"猜原因"而不是"逐层排除" | 排查的价值在于**用数据排除**其他可能，最终结论才有说服力 |
| 在同一台机器上同时压测又排查（施压机与被测同机） | 会互相污染指标；压测机与被测机分离是基本纪律（或被压目标另置） |
| 只看被测服务不看中间件/DB | 三层的指标要同时看，否则容易把"上游慢导致的等待"当成"本机瓶颈" |
| 拿到结论不记录证据 | 报告要能给"数据 + 时间窗口 + 命令"；否则结论无法复盘 |
| 忽略虚拟化层的 st | 云主机/虚拟机上的 st 高属于环境问题，不是应用能解决的 |

【我的理解】引导题（用自己的话回答）：
1. 请按"进入下一步的条件"重新表达下面这句话：看到 wa 高就去查磁盘。为什么要带上条件？
2. 如果 top 显示 load average 很高，但 %CPU 的 id 还有 60%，你会怀疑哪一类进程？用什么命令验证？
