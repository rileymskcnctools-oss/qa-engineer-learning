### 知识点1：ps 是什么，它解决什么问题

【课程原话/定义】
在 Linux 系统中，`ps` 命令是一个非常常用的工具，用于查看当前正在运行的进程信息。它基于 `/proc` 文件系统，通过读取 `/proc` 目录下的进程信息文件来获取进程的详细信息，如 PID（进程 ID）、CPU 利用率、内存占用等。这些信息对于系统管理员和开发者来说是很有用的，可以帮助他们了解系统的运行状况，识别和解决性能问题，以及管理和优化进程。

课程给出的"PS 的应用场景"（原文 7 条）：
1. **监控进程状态**：实时显示各进程的状态、PID/PPID、CPU 与内存使用、启动时间、运行状态，便于发现异常或僵死进程；
2. **查找特定进程**：按名称、用户或 PID 查找（如 `ps -u username`）；
3. **分析系统负载**：提供各进程的 CPU 和内存使用情况，定期分析可指导优化或扩容；
4. **调试程序**：查看程序运行时的进程状态，包括命令行参数、环境变量；
5. **管理系统服务**：先确定服务进程状态与 PID，再结合 `kill` 等命令管理服务；
6. **自定义输出格式**：可选择显示的列与顺序，输出更灵活易读；
7. **结合其他命令使用**：通过管道交给 `grep` 过滤，或交给 `awk`/`sed` 进一步处理分析。

【为什么？】
`ps` 和 [[Ch36-top命令使用]] 的关系，可以用一句话概括：**top 是"录像"，ps 是"照片"**。

- **top 是动态刷新**：适合"人在现场盯变化"——但它会一直占用一个终端、输出不断刷新，**不适合放进脚本、不适合留证据**；
- **ps 是一次性快照**：执行完立刻返回，输出是**纯文本**，因此可以 `grep` 过滤、`wc -l` 统计、重定向到文件、写进巡检脚本——这让它成为**自动化与留痕的默认工具**（压测前后各取一次快照就是最省事的"资源证据"）。

它"基于 `/proc` 文件系统"这一点也很重要：`/proc/<PID>/` 下每个进程都有目录（`cmdline`、`status`、`environ` 等），`ps` 本质是在读这些文件并格式化。理解了这一点，就明白为什么 `ps` 能看到**命令行参数、环境变量、父子关系**——这些在 top 的默认视图里是看不到的。

【必须掌握】

| 应用场景（原文 7 条） | 落地命令示例 |
|---|---|
| 监控进程状态 | `ps aux --sort=-%cpu \| head`（按 CPU 降序看头几个） |
| 查找特定进程 | `ps -ef \| grep java`、`pgrep -f xxx` |
| 分析系统负载 | `ps aux --sort=-%mem \| head`（谁在吃内存） |
| 调试程序 | `ps -p <PID> -o pid,ppid,cmd,lstart`（命令行、启动时间） |
| 管理系统服务 | 先 `ps -ef \| grep 服务名` 拿 PID，再 `kill` |
| 自定义输出格式 | `ps -eo pid,ppid,%cpu,%mem,stat,cmd` |
| 结合其他命令 | `ps aux \| awk '$3>50 {print $2,$3,$11}'`（筛出 CPU>50% 的进程） |

| 对比项 | top | ps |
|---|---|---|
| 输出方式 | 动态刷新（录像） | 一次性快照（照片） |
| 适合 | 现场交互排查 | 脚本、统计、留证据 |
| 交互能力 | 排序/杀进程/展开核 | 无（靠参数与管道） |
| 能看到 | 实时占用、状态分布 | 命令行参数、环境变量、父子关系 |

【企业场景】
你要写一个"压测前/压测后环境基线巡检脚本"：用 `ps -eo pid,ppid,%cpu,%mem,stat,cmd --sort=-%cpu | head -20 > before.txt`，压测后再跑一次存成 `after.txt`，然后 `diff` 两份快照——**有没有新的进程在吃 CPU、有没有进程在压测后没被清理（残留的压测工具/连接池）**，一眼可见。这类"快照 + 对比"的用法，就是 `ps` 在企业里最日常的价值。

【面试考察】
面试官："ps 和 top 有什么区别？你什么时候用 ps？"

参考回答框架：
1. 定位：top 动态刷新（现场排查），ps 一次性快照（脚本、统计、留痕）；
2. ps 基于 `/proc` 读取进程信息，能看到命令行参数、环境变量、父子关系（PPID），便于定位"谁拉起了谁"；
3. 常用姿势：`ps aux`（BSD 风格，看 %CPU/%MEM）、`ps -ef`（UNIX 风格，看 PPID）、`ps -eo ...`（自定义列）、配合 `grep`/`awk`/`--sort` 做筛选与排序；
4. 典型用途：压测前后快照对比、查僵死/残留进程、由 PID 提供服务管理（kill/重启）的依据。

【易错点】

| 常见错误 | 正确理解 |
|---|---|
| 认为 ps 能"实时监控" | ps 是**快照**；实时看用 top（或 `watch -n 1 ps ...`） |
| 查进程只用 `ps -ef \| grep java` 就完事 | 该组合会包含 **grep 自身**；用 `grep java \| grep -v grep` 或 `pgrep -f` |
| 只看 %CPU 不看 %MEM | 压测中两类瓶颈都会出现；两个维度都要排序看一遍 |
| 忽略 PPID 与父子关系 | `ps -ef` 的 PPID 能揭示"谁启动了它"（排查异常拉起、容器 init 关系必需） |
| 在生产上执行 `ps` 却不定格输出 | 长命令行会换行；用 `ps -eo ... -w` 或指定列，避免输出错乱 |

【我的理解】引导题（用自己的话回答）：
1. 用"录像 / 照片"这个比喻，说明 top 与 ps 各自不可替代的场景。
2. 为什么 `ps -ef | grep java` 的结果里常有一条"多余的"记录？你会怎么处理？

### 知识点2：三种常用写法与选项（ps / ps aux / ps -ef）+ 两种风格

【课程原话/定义】
- `ps` —— 用于显示当前系统的进程状态；
- `ps -aux` —— `ps` 命令本身用于报告当前系统的进程状态；`-a` 显示所有终端下的进程（包括其他用户的进程）；`-u` 显示用户/拥有者信息；`-x` 显示没有控制终端的进程；
- `ps-ef`（原文写法，缺空格）—— `ps` 表示 "process status"；`e` 显示所有进程；`f` 使用全格式显示进程信息。

【为什么？】
这条知识点的重点不是背选项，而是搞清 **BSD 风格**与 **UNIX 风格**这两套语法——它们的**列不同、用途也不同**：

| 写法 | 风格 | 典型输出列 | 最适合回答的问题 |
|---|---|---|---|
| `ps` | 默认（当前终端+当前用户） | PID TTY TIME CMD | "我这个终端在跑什么" |
| `ps aux` | **BSD 风格**（选项不带横杠） | USER PID %CPU %MEM VSZ RSS TTY STAT START TIME COMMAND | **谁最吃 CPU / 内存** |
| `ps -ef` | **UNIX 风格**（带横杠） | UID PID PPID C STIME TTY TIME CMD | **父子关系（PPID）、启动时间、完整启动命令** |

所以选择标准很简单：**想按资源占用排序找"头号嫌疑"→ 用 `ps aux`；想看"谁拉起了谁、启动命令是什么"→ 用 `ps -ef`。** 课程原文把 `ps -aux`（混合风格）当 BSD 风格用，语义上应写 `ps aux`——这一点在真实排错里影响不大（多数版本能跑），但属于**写规范的细节**，面试里能说明白风格差异是加分项。

另外要记住 `ps aux` 里三个"看不出来但很关键"的状态：`STAT` 列里的 **D（不可中断睡眠，通常在等 IO）** 是关键信号——大量 D 状态进程＝IO 瓶颈（这与 [[Ch36-top命令使用]] 里提到的 D 状态一脉相承）。

【必须掌握】

| 选项 | 含义 | 备注 |
|---|---|---|
| `-e` / `-A` / `aux` 的 `a`+`x` | 显示所有进程（`-e` 含所有；BSD 风格用 `a`+`x` 组合） | `-e` 与 `aux` 都能"看全部"，但输出列不同 |
| `-f` | 全格式（含 UID、PPID、STIME、CMD 全路径） | 想看父子关系必加 |
| `-l` / `-u user` | 长格式 / 指定用户的进程 | `ps -u username`（原文示例）查某人起了什么 |
| `-p PID` | 只看指定 PID | 已知 PID 时精确定位 |
| `-o 列名` | 自定义输出列（原文"自定义输出格式"） | 如 `-o pid,ppid,%cpu,%mem,stat,cmd` |
| `--sort` | 排序（`-` 表示降序） | `ps aux --sort=-%cpu` |
| `-w` | 加宽输出，避免命令行被截断 | 排查长命令行参数时必加 |
| `STAT` 字母 | R 运行、S 睡眠、D 不可中断（IO）、Z 僵尸、T 停止、s 会话首进程、l 多线程、+ 前台进程组 | D 多 → IO 压力；Z 多 → 父进程未回收 |

【企业场景】
压测中 RT 抖动，你在被测机上执行 `ps -eo pid,ppid,stat,%cpu,%mem,cmd --sort=-%cpu | head -15`：发现被测服务进程下有 **大量 `D` 状态**的线程/进程、`%cpu` 不高但 `wa` 高——立刻把方向定到 IO（接着 `iostat -x 1` 验证）。**如果只看 %CPU 排序，这类"在等 IO 的进程"会被忽略**（它们不烧 CPU）。这就是为什么 `ps` 的 `STAT` 列必须会读。

【面试考察】
面试官："`ps aux` 和 `ps -ef` 有什么区别？怎么找出 CPU 占用最高的进程？"

参考回答框架：
1. 风格不同：`ps aux` 是 BSD 风格（选项无横杠），列含 %CPU/%MEM/VSZ/RSS/STAT；`ps -ef` 是 UNIX 风格，列含 PPID/STIME/CMD，看父子关系与启动命令；
2. 找 CPU 最高：`ps aux --sort=-%cpu | head`（或用 `top` 按 `P`）；
3. 找内存最高：`ps aux --sort=-%mem | head`；
4. 加分：`STAT` 里的 `D` 表示不可中断睡眠（多在等 IO），大量 D 状态提示 IO 瓶颈；`Z` 是僵尸进程（父进程未回收）；查进程建议配合 `-w` 防止命令行截断。

【易错点】

| 常见错误 | 正确理解 |
|---|---|
| 把 `ps -aux` 与 `ps aux` 当完全等价的两种写法随便用 | BSD 风格应写 `ps aux`（无横杠）；UNIX 风格用 `ps -ef`；混写不规范 |
| 只看 %CPU 忽略 STAT | **D 状态（等 IO）的进程 %CPU 很低**，但它们是 IO 瓶颈的直接证据 |
| `ps -ef \| grep xxx` 结果里混入 grep 自身 | 加 `grep -v grep`，或用 `pgrep -f xxx` |
| 命令行太长被截断，误判启动参数 | 加 `-w`（`ps -eo cmd -w`）或 `ps -efww` |
| 把 `Z`（僵尸）当成"占资源的进程" | 僵尸几乎不耗资源，问题是**父进程没有回收**；要查父进程逻辑 |

【我的理解】引导题（用自己的话回答）：
1. 你要回答"是谁启动了 nginx"，用 `ps aux` 还是 `ps -ef`？为什么？
2. 为什么"大量 D 状态进程"是 IO 瓶颈的证据，而不是 CPU 瓶颈的证据？

### 知识点3：输出列怎么读（USER / PID / PPID / %CPU / %MEM / VSZ / RSS / STAT / TIME / COMMAND）

【课程原话/定义】
（原文只说明了选项含义，未解释输出列。）

【为什么？】
`ps` 的输出列是"取证的字段表"，每一列都可能成为排查结论的依据。需要重点区分的是**内存三兄弟**与**时间两个维度**：

- **VSZ（虚拟内存）/ RSS（常驻内存）/ %MEM**：**VSZ 是"进程申请的地址空间"（含未真正使用的部分），RSS 才是实际占用的物理内存**。用 VSZ 判断内存占用会严重高估（尤其 Java 进程）。
- **%CPU / TIME**：`%CPU` 是"自进程启动以来的 CPU 时间占比"（**注意：不是瞬时值**，这点与 top 不同！），`TIME` 是累计 CPU 时间。所以 `ps aux` 里 %CPU 高的进程不一定是**此刻**在烧 CPU——排查瞬时热点要用 top。

另外 `PPID`（父进程 ID）是 `ps` 独有的宝：**进程树的关系就在这里**。服务被异常重启、容器里的进程归属、脚本拉起了什么，全靠 PPID 顺藤摸瓜。

【必须掌握】

| 列 | 含义 | 判读/陷阱 |
|---|---|---|
| USER / UID | 进程所属用户 | 判断"是不是以 root 跑的"（安全与权限问题） |
| PID / PPID | 进程号 / 父进程号 | PPID 追"谁启动了它"；PPID=1 通常表示已被 init 接管 |
| %CPU | **自启动以来的 CPU 占用比例** | 不是瞬时值！瞬时热点用 top |
| %MEM / RSS | 物理内存占比 / 实际常驻内存(KB) | 判断内存占用看 **RSS**，别用 VSZ |
| VSZ | 虚拟内存大小(KB) | 含未实际使用的地址空间，会大幅高估 |
| STAT | 进程状态（R/S/D/Z/T…） | D 多＝IO 压力；Z＝僵尸 |
| START / STIME | 进程启动时间/日期 | 判断是否"最近被重启过"（配合报警时间） |
| TIME | 累计 CPU 时间 | 与 %CPU 一起看：TIME 很大＝长期烧 CPU |
| COMMAND / CMD | 启动命令（含参数） | 用 `-w` 防截断；同机多实例时靠它区分 |

【企业场景】
线上告警说"某服务内存飙高"。你执行 `ps -p <PID> -o pid,etime,rss,vsz,%mem,cmd`：发现 `RSS` 只有 1.2G，而 `VSZ` 高达 12G——**虚惊一场：VSZ 大是 JVM 预留地址空间的正常表现**，真正的物理占用看 RSS。反过来，如果 RSS 持续上涨且不回落（配合 [[Ch35-性能分析系统级别指标io cpu mem net]] 的 si/so 与 `free -m`），那才是内存泄漏的实证。**"VSZ 吓人、RSS 淡定"是最常见的一次误报。**

【面试考察】
面试官："ps 输出里 VSZ 和 RSS 有什么区别？%CPU 是瞬时值吗？"

参考回答框架：
1. VSZ＝虚拟内存（含未使用的地址空间，Java/大堆进程会很大）；RSS＝实际占用的物理内存；判断占用用 RSS（+ %MEM）；
2. `ps` 的 %CPU 是**自进程启动以来的平均值**，不是瞬时值——瞬时要看 top（更严谨的说法：top 显示的是自上次刷新以来的占用）；
3. 其他关键列：PPID（父子关系）、STAT（D＝等 IO、Z＝僵尸）、TIME（累计 CPU 时间）、START/STIME（启动时间）；
4. 实践：查进程用 `-o` 指定需要的列 + `-w` 防止截断，输出更适合贴报告。

【易错点】

| 常见错误 | 正确理解 |
|---|---|
| 用 VSZ 判断内存占用（"它占了 12G！"） | VSZ 含未使用地址空间；看 **RSS / %MEM** |
| 把 ps 的 %CPU 当瞬时值 | 它是**自启动以来**的占比；瞬时热点用 top |
| 忽略 STAT 中的 D / Z | D 多＝IO 压力；Z 多＝父进程没回收子进程 |
| 不看 PPID | 少了"谁拉起了谁"的关键线索（排查异常重启、容器进程树必需） |
| 命令行被截断还照抄启动参数 | 加 `-w`；长参数被截断会导致误判（如少了一个关键 JVM 参数） |

【我的理解】引导题（用自己的话回答）：
1. 为什么"VSZ 很大"通常不是问题？判断一个进程真实占用内存应该看哪两列？
2. 你用 ps 看到某进程 %CPU 是 300%，这代表什么？（提示：多核/多线程与"自启动以来"的定义）

### 知识点4：组合用法与自定义输出（grep / awk / --sort / -eo / pgrep）

【课程原话/定义】
- 查找特定进程：通过 `ps` 命令结合不同的选项和参数，可以轻松查找特定名称、用户或 PID 的进程，例如 `ps -u username` 查找指定用户启动的所有进程；
- 结合其他命令使用：将 `ps` 的输出通过管道传递给 `grep` 过滤，或通过 `awk`、`sed` 等文本处理工具进一步分析；
- 自定义输出格式：`ps` 支持自定义输出格式，用户可以选择显示的列与列的顺序。

【为什么？】
`ps` 本身只提供"原材料"，**真正的效率来自"过滤 + 聚合 + 排序"**——这也是它能在脚本/巡检里承担角色的原因。三个最常用的组合模式：

1. **过滤**：`ps -ef | grep java | grep -v grep`，或直接用 `pgrep -f <关键字>`（只输出 PID，最干净）；
2. **聚合**：`ps -eo comm,%cpu | awk '{a[$1]+=$2} END{for(k in a) print a[k],k}' | sort -rn | head` —— 按**进程名**汇总 CPU（同名多进程场景，如多个 Java 实例）；同理可用 `wc -l` 统计"某类进程有几个"；
3. **排序取头部**：`ps aux --sort=-%cpu | head -10`（找 CPU 头名）、`--sort=-rss`（找内存头名）。

一个很实用的排查片段：**统计某个服务的进程数并告警**——`ps -ef | grep -c "[j]ava"`（`[j]ava` 这种写法天然排除了 grep 自身）。压测时"进程数异常增长"往往意味着连接池/线程模型出了问题。

【必须掌握】

| 组合 | 命令 | 用途 |
|---|---|---|
| 精确查进程 | `pgrep -af <关键字>` | 输出 PID + 完整命令行，且不含 grep 自身 |
| 排除 grep 自身 | `ps -ef \| grep -c "[j]ava"` | 计数/统计的首选写法 |
| 排序找头名 | `ps aux --sort=-%cpu \| head`、`--sort=-rss` | CPU / 内存头号进程 |
| 自定义列 | `ps -eo pid,ppid,stat,%cpu,%mem,etime,cmd -w` | 输出可直接贴进报告 |
| 按名聚合 | `ps -eo comm,%cpu --no-headers \| awk '{a[$1]+=$2} END{for(k in a) print a[k],k}' \| sort -rn \| head` | 多实例场景汇总 |
| 只看某用户 | `ps -u <user> -o pid,%cpu,%mem,cmd` | 区分"谁起的进程" |
| 快照留证 | `ps aux > before.txt` | 压测前后对比 |

【企业场景】
压测中出现"连接数暴涨但 TPS 下降"。你执行 `ps -eo pid,ppid,etimes,stat,cmd | grep -v grep | grep <服务名>`：发现该服务被拉起了 **3 个实例**（有人手工多起了一份），三个实例在抢同一份资源（同一端口或同一份数据表锁），于是 TPS 被稀释。**"多实例/多进程"这类问题只能靠 ps 的进程列表发现**——top 只会把它们的 CPU 加总显示，看不出"重复启动了"。排查完记得把"进程数与预期不符"写进报告，这是很有价值的一类发现。

【面试考察】
面试官："怎么快速统计某类进程的数量和资源占用？为什么 `grep xxx` 会带出多余结果？"

参考回答框架：
1. 统计数量：`ps -ef | grep -c "[j]ava"`（方括号技巧排除 grep 自身）或 `pgrep -c -f java`；
2. 资源占用：`ps -eo comm,%cpu,%mem --sort=-%cpu | head`；多实例聚合用 `awk` 按 `comm` 求和；
3. `grep xxx` 多余结果的原因：管道里 grep 自己也是一个进程，且关键字出现在命令行中；用 `grep -v grep`、`[x]xx` 写法或 `pgrep`；
4. 场景：压测前后快照对比、发现"重复启动/残留进程"、按 PID 定位服务再决定是否需要重启。

【易错点】

| 常见错误 | 正确理解 |
|---|---|
| 脚本里用 `ps aux \| grep java` 判断"服务是否在跑" | 可能匹配到 grep 自身或其他含 java 的命令行；用 `pgrep -f` 或 `[j]ava` 写法更可靠 |
| 用 `ps` 统计"进程数"时混入短命进程 | ps 是快照，短命进程可能捕捉不到；要统计启动次数得靠监控/日志 |
| 聚合时用 `%cpu` 求和当作总占用 | `%CPU` 是"自启动以来均值"，求和只能作粗略比较；精确瞬时值用 top/vmstat |
| 自定义列时忘了 `-w`，导致 cmd 被截断 | 排查参数问题时必须加宽输出 |
| 巡检脚本直接解析 `ps` 的人类可读输出 | 列宽会随终端变化；脚本里用 `-eo` 明确列 + `--no-headers`，输出更稳定 |

【我的理解】引导题（用自己的话回答）：
1. `grep -c "[j]ava"` 里的方括号起了什么作用？不用它会出现什么结果？
2. 如果压测报告显示"服务被启动了 3 个实例"，你会给出什么结论和动作？

### 知识点5：企业排错场景与"进程取证"清单（与 top 配合）

【课程原话/定义】
（原文未涉及，本节把本章知识落到排查动作里。）

【为什么？】
`ps` 在企业里的角色是**取证与留痕**：top 让你"看到现象"，ps 让你"留下证据、写进报告、交给别人复核"。压测与线上排错中，它主要出现在 5 个场景：

1. **确认被测服务是谁**：`ps -ef | grep -v grep | grep <服务名>`（含 JVM 参数、启动脚本）；
2. **压测前后基线对比**：`ps aux --sort=-%cpu > before/after.txt` + `diff`；
3. **发现残留/重复进程**：压测结束有没有留下 JMeter/压测节点、服务是否被重复拉起；
4. **确认资源占用与泄漏**：`RSS` 与 `%MEM` 的时间序列（配合定时采样）；
5. **配合 top 下钻**：top 找到 PID → `ps -p PID -o pid,ppid,stat,cmd -w` 取完整信息 → `top -H -p PID` / jstack 看线程。

【必须掌握】

| 场景 | 命令 | 产出 |
|---|---|---|
| 确认服务进程与启动参数 | `ps -ef \| grep -v grep \| grep <服务名>` | 完整启动命令、PID、PPID |
| 压测前后对比 | `ps aux --sort=-%cpu > before.txt`（压后同） | 差异清单：新增/消失/占用变化 |
| 找头号 CPU / 内存 | `ps aux --sort=-%cpu \| head`、`--sort=-rss \| head` | 头号嫌疑进程 |
| 查残留/重复实例 | `ps -ef \| grep -c "[服]务名"` | 进程数是否与预期一致 |
| 与 top 衔接 | `ps -p PID -o ... -w` → `top -H -p PID` | 从进程到线程的证据链 |

【企业场景】
压测收尾时的一个标准动作：核对"压测环境是否回到基线"——`ps aux` 快照与压测前对比，确认：被测服务进程没被重启过（PID 不变）、没有残留的压测工具进程、没有异常的外部连接进程。**很多"压测报告数据不可信"的根因，就是压测期间服务被重启过（PID 变了）而没人发现**——ps 的快照对比能直接给出证据。

【面试考察】
面试官："压测前后你会怎么核实环境没变？"

参考回答框架：
1. 压测前采集基线：进程快照（`ps aux`）、资源基线（进程数、内存、打开文件数）；
2. 压测中持续记录：top/vmstat 采集 + 应用日志；
3. 压测后核对：进程 PID 是否变化（是否被重启）、有无残留/重复进程、资源是否回落；
4. 与 top 配合形成"现象 → 进程 → 线程"的完整证据链，并把证据写进报告。

【易错点】

| 常见错误 | 正确理解 |
|---|---|
| 压测前后不做快照 | 无法证明"环境未变"，结论可被质疑（服务重启会让结果不可比） |
| 只看服务进程，不看残留进程 | 压测工具/代理/临时进程残留会持续占用资源，影响后续测试 |
| 把"进程还在"当成"服务正常" | 进程存在 ≠ 服务可用（可能卡死/僵死）；要结合端口、健康检查、业务断言 |
| 用 PID 判断服务身份而不看启动命令 | 同机多实例/多版本时，必须看 `cmd` 与 PPID 才能确定是哪一个 |
| 采集脚本用人类可读的列宽 | 脚本里固定列（`-eo`）更稳，避免终端宽度导致的解析错误 |

【我的理解】引导题（用自己的话回答）：
1. 为什么"压测期间服务被重启过"会让整轮压测数据不可信？你能用哪条命令给出证据？
2. 请设计一份"压测环境基线快照"清单（至少 4 项），并说明每一项要证明什么。
