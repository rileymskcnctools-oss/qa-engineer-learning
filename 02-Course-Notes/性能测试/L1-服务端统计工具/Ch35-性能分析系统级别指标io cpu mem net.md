### 知识点1：什么是性能监控，为什么要监控（六条意义 → 四类指标）

【课程原话/定义】
Linux 系统提供了许多查看性能属性的命令，掌握这些命令能更好地监控 Linux 系统的运行状况。

性能监控是指对系统、应用程序或网络的运行状态进行实时监测、收集和分析关键性能指标的过程。通过性能监控，可以及时了解系统资源的利用情况、进程调度状态以及性能瓶颈等问题。

在性能监控中，通常关注一些重要的指标，如 **CPU 利用率、内存利用率、磁盘吞吐量以及网络带宽利用率**等。

课程给出的"为什么要监控系统性能"（原文 6 条）：
1. **问题诊断与预防**：定位性能/资源瓶颈或系统错误，在问题发生前预防；
2. **资源优化**：了解 CPU、内存、磁盘、网络的使用情况，决定增/减资源以及资源是否被有效利用；
3. **容量规划**：分析历史数据预测未来需求，避免资源不足或过剩；
4. **服务质量保证**：监控响应时间、吞吐量等，确保满足用户需求；
5. **合规性与安全性**：满足合规要求、发现异常行为与未授权访问；
6. **持续改进**：持续分析比较数据，不断发现改进点。

【为什么？】
这 6 条里，**对性能测试工程师最关键的是第 1 条和第 3 条**——它们正好对应压测的两个交付物：

1. **压测中定位瓶颈**（问题诊断）：TPS 上不去、RT 变长时，你必须能回答"瓶颈在 CPU、内存、磁盘 IO 还是网络"。这一步靠的是"**分层看指标**"：先用全局命令（`uptime`/`vmstat`）判断方向，再用专项命令（`mpstat`/`iostat`/`sar`/`netstat`）钻到具体资源，最后用进程级工具（`top`/`ps`，见 [[Ch36-top命令使用]]、[[Ch37-ps命令]]）落到具体进程。
2. **压测后给容量结论**（容量规划）：报告里的"日常区间 / 容量上限 / 扩容红线"必须有资源数据支撑——"CPU 到 85% 时 TPS 开始走平"才叫结论，"TPS 3000"只是数字。

而"四类指标"（io / cpu / mem / net）是**同一件事的四个视角**，也是排错的主干：CPU 高不一定是代码慢（可能在等 IO 或 swap）；内存不够会表现为 CPU 与 IO 同时异常（swap 换入换出）；磁盘 IO 打满会把 RT 拉长；网络打满会让一切都变慢。**只盯一个指标，几乎一定会误判。**

【必须掌握】

| 监控意义（原文 6 条） | 压测场景里的具体用法 |
|---|---|
| 问题诊断与预防 | 压测中分层定位瓶颈（全局 → 资源 → 进程） |
| 资源优化 | 判断某资源是否成为瓶颈（如 CPU 单核打满、磁盘 %util 100%） |
| 容量规划 | 给出容量结论与扩容红线（报告的数据支撑） |
| 服务质量保证 | 用 RT / 吞吐量验证 SLA，而不是只看"服务没崩" |
| 合规性与安全性 | 发现异常访问/连接暴涨（也用于排查异常流量） |
| 持续改进 | 历史数据对比：性能回归时判断"哪一层退化了" |

| 四类指标 | 关键子指标 | 常见命令 |
|---|---|---|
| **CPU** | 使用率（us/sy/id/wa）、负载（load average）、运行队列（r）、上下文切换（cs） | `uptime`、`vmstat`、`mpstat`、`sar -u` |
| **内存** | 可用内存（available）、缓存、swap 使用、换入换出（si/so） | `free`、`vmstat`、`cat /proc/meminfo` |
| **磁盘 IO** | 使用率（%util）、等待（await）、吞吐（kB_read/s、kB_wrtn/s）、空间 | `iostat`、`df -h` |
| **网络** | 带宽、连接数、TIME_WAIT、丢包/延迟 | `ping`、`ifconfig`/`ip`、`netstat`/`ss` |

【企业场景】
压测进行到第 20 分钟，TPS 走平、RT 从 200ms 涨到 800ms。你的排查顺序：① `uptime`（load average 是否超过核数）→ ② `vmstat 1`（r 高＝CPU 排队；si/so > 0＝在换页；wa 高＝在等 IO）→ ③ 按 vmstat 的指向钻到 `mpstat -P ALL 1`（哪颗核）、`iostat -x 1`（哪块盘）或 `netstat -an | grep TIME_WAIT | wc -l`（端口/连接是否耗尽）。**每一步只为回答一个问题，而不是把所有命令都敲一遍。** 这套"从全局到局部"的走法，是面试里问"你怎么定位瓶颈"时的标准答案骨架。

【面试考察】
面试官："压测中发现 TPS 上不去，你怎么用 Linux 命令分层定位？"

参考回答框架：
1. 先确认现象：JMeter 侧看 TPS / RT / 错误率 / 活动线程数，排除施压机自身瓶颈；
2. 全局判断：`uptime`（负载）、`vmstat 1`（r 运行队列、si/so 换页、wa IO 等待、cs 上下文切换）；
3. 按方向下钻：CPU → `mpstat -P ALL`、`sar -u`；内存 → `free -m`（看 available）、`/proc/meminfo`；磁盘 → `iostat -x`（%util、await）；网络 → `ss`/`netstat`、`ifconfig`；
4. 落到进程：`top` / `ps` 定位进程与线程，再结合应用层工具（jstack/火焰图）看代码；
5. 收口：把数据落成结论（哪一层是瓶颈、扩容还是优化、红线在哪）。

【易错点】

| 常见错误 | 正确理解 |
|---|---|
| 只盯 CPU 使用率 | CPU 高可能是"在等 IO/在换页"（wa 高、si/so 不为 0）；只盯 CPU 会误判根源 |
| 把所有命令都敲一遍收集数据 | 排查是"带着假设下钻"：先用全局命令定向，再用专项命令验证 |
| 用 `free` 的 "free" 列判断内存够不够 | Linux 会把空闲内存用于缓存，看 **available**（可用）才有意义；free 很小不等于内存不足 |
| 把 `load average` 与 CPU 使用率混为一谈 | load 包含**运行 + 不可中断等待**（含 IO 等待）的进程数；高 load 也可能是磁盘 IO 造成 |
| 以为"命令输出会告诉你结论" | 命令只给数字，结论要靠"基线对比 + 阈值判断"（压测前先记录一组基线） |

【我的理解】引导题（用自己的话回答）：
1. 为什么"CPU 使用率很高"不能直接得出"CPU 是瓶颈"？请给出至少两种相反的真相。
2. 请把课程 6 条监控意义里，你认为**对压测工作最没直接关系**的一条挑出来，并说明它在什么场景下仍然有用。

### 知识点2：CPU 相关命令与判读（cpuinfo / mpstat / sar / uptime / vmstat）

【课程原话/定义】
- `cat /proc/cpuinfo` —— 查看 CPU 的配置信息；
- `mpstat -P ALL` —— 在多核 CPU 中查询每个核的性能；
- `sar -u 1 1` —— Linux 的监控工具，用来监控 CPU 性能；每隔一秒监控一次，总共监控 1 次；
- `uptime` —— 用于显示系统总共运行了多长时间和系统的平均负载；
- `vmstat` —— 用来获得有关进程、内存、虚拟内存、页面交换空间及 CPU 活动等信息。

【为什么？】
CPU 排查要抓住"**三个视角**"，命令只是入口：

1. **配置视角**（有多少核）：`cat /proc/cpuinfo`（或 `lscpu`、`nproc`）——不知道核数就没法判断负载高低。**load average = 5 在 4 核机器上已经过载，在 32 核机器上很清闲。**
2. **全局视角**（整体忙不忙、忙在什么状态）：`uptime` 的 load average（1/5/15 分钟）、`vmstat` 的 `us/sy/id/wa` 与 `r`（运行队列）、`cs`（上下文切换）。
3. **单核视角**（是不是"一颗核打满"）：`mpstat -P ALL 1`、`top` 里按 `1` 展开每核——**多核机器上"整体 25% 使用率"完全可能是"一颗核 100%"+其他核空闲**，这通常意味着代码里有串行/锁竞争，扩容核数没用。

`wa`（iowait）这个字段最容易被误读：它统计的是 **CPU 空闲、但有任务在等磁盘 IO** 的时间占比。所以 `wa` 高说明**瓶颈不在 CPU，而在磁盘**——这时候去优化代码或加 CPU 是白费力气。同理 `sy`（system）高说明内核态消耗大（大量系统调用、上下文切换、网络栈处理），常见于频繁 IO、海量小包、频繁线程切换。

【必须掌握】

| 命令 | 看什么 | 判读要点 |
|---|---|---|
| `cat /proc/cpuinfo` | 每颗逻辑核的型号、主频、core id | 数逻辑核数（= 可并行度），对照 load 判断是否过载 |
| `mpstat -P ALL 1` | 每颗核的 `%usr / %sys / %iowait / %idle` | 单核打满 → 串行/锁问题；全体均衡 → 真并发瓶颈或资源饱和 |
| `sar -u 1 1` | `%user / %system / %iowait / %idle` | 与 mpstat 同类；**sar 支持回看历史**（sadc 定时采集），事后复盘必备（【扩展知识】） |
| `uptime` | `load average: 1min / 5min / 15min` | 与核数比较：接近核数＝接近饱和；1min 高 15min 低＝突发；1min 低 15min 高＝已回稳 |
| `vmstat` | `r` 运行队列、`b` 阻塞、`cs` 上下文切换、`in` 中断、`us/sy/id/wa` | `r > 核数` 表示 CPU 排队；`cs` 暴涨常伴锁竞争/线程过多 |

【企业场景】
压测时 TPS 卡在 1 200 上不去、CPU 总使用率只有 30%。你敲 `mpstat -P ALL 1`：发现只有 1 颗核 100%（`%usr`），其余全空闲；结合应用日志看到线程池只有 1 个线程在处理某个串行环节——**结论：不是机器不够，是代码串行**（扩容无效，必须改代码或调线程池）。反过来，如果 `%sys` 与 `cs` 同时暴涨，就要怀疑线程数过多导致上下文切换开销吞掉 CPU。**这两种现象在"只看总 CPU 使用率"时长得一模一样**，所以必须看单核与状态分解。

【面试考察】
面试官："load average 怎么判读？多核机器上 CPU 使用率不高但 TPS 上不去，你怎么查？"

参考回答框架：
1. load average：1/5/15 分钟的平均"运行 + 不可中断等待"进程数；**要和核数比**（`nproc`），接近或超过核数＝饱和；趋势（1m vs 15m）判断是突发还是持续；
2. 使用率不高但慢：可能"一颗核打满"（串行/锁）→ `mpstat -P ALL` 或 `top` 按 `1`；可能在等 IO → 看 `wa`、`iostat`；可能在等外部依赖（DB/下游）；
3. 再看上下文切换 `cs` 与 `sy`：过高说明切换开销大（线程过多）；
4. 收口：给结论 + 给动作（改代码/调参数/扩容/加机器），并说明依据。

【易错点】

| 常见错误 | 正确理解 |
|---|---|
| 用 load average 判断 CPU 忙不忙，不看核数 | load 是"排队长度"，必须除以核数看；4 核 load=5 已过载 |
| 把 `%iowait` 高当成 CPU 瓶颈 | `wa` 是"CPU 在等 IO"，瓶颈在磁盘；优化方向是 IO 而不是 CPU |
| 只看总 CPU 使用率 | 单核打满在多核机器上会被平均数掩盖（串行/锁问题的典型特征） |
| 认为 `sar` 只是"另一个 mpstat" | `sar` 的独门本事是**读历史数据**（`/var/log/sa`），可事后复盘压测时间段（【扩展知识】） |
| 把 `vmstat` 只当内存命令 | `vmstat` 一屏覆盖 r/b、si/so、us/sy/id/wa、cs/in——它是"全局定向"的首选命令 |

【我的理解】引导题（用自己的话回答）：
1. `load average: 5.2` 在 4 核与 32 核机器上分别意味着什么？你会分别给出什么建议？
2. `%iowait` 很高时，为什么"加 CPU"是错的？正确的下一步命令是什么？

### 知识点3：内存相关命令与判读（meminfo / free -g / vmstat 的 si·so）

【课程原话/定义】
- `cat /proc/meminfo` —— 查看内存相关配置信息；
- `free -g` —— 显示系统使用和空闲内存情况，包括物理内存、交换区内存；`-g` 将单位换算为 G；
- `vmstat` —— 用来获得有关进程、内存、虚拟内存、页面交换空间及 CPU 活动等信息。

【为什么？】
内存判读有一条**反直觉但极其重要**的规则：**Linux 会主动把空闲内存用作文件缓存，所以 `free` 很小是正常的、甚至是好事**（缓存能加速读取）。因此判断"内存够不够"要看两个更真实的信号：

1. **`available`**：系统"还能拿出多少内存给新进程"的估算值（`free -m` 里的 available 列）。它把可回收的缓存算进去了——**available 才是"剩余可用"，free 不是。**
2. **`si` / `so`（swap in / swap out）**：`vmstat` 里这两列是**内存不足的铁证**。物理内存不足时，内核把页换到 swap，需要时再换回来：`si/so` 长期非 0 → 内存压力大；换页本身还要读写磁盘，于是 **CPU 的 wa 也会升高**，表现为"CPU 在等 IO"，很容易被误判成磁盘问题。

所以内存不足的典型"三连症"是：`available` 很小 + `si/so` 持续非 0 + `wa` 升高。**看到这组信号，第一动作是确认是不是内存问题（而不是去优化磁盘）**——因为 swap 一旦开始频繁使用，整个系统的响应时间会成倍恶化，压测数据也就没意义了。

【必须掌握】

| 命令 | 关键字段 | 判读要点 |
|---|---|---|
| `free -g`（`-m` 更常用） | total / used / free / shared / buff/cache / **available**、Swap 区 | 看 **available**；Swap 的 used 长期增长＝有换页压力 |
| `cat /proc/meminfo` | MemTotal / MemFree / MemAvailable / Buffers / Cached / SwapTotal / SwapFree | 精读细项（如 Buffers 与 Cached 的构成）时用；脚本采集常用它 |
| `vmstat` | `si`（换入）、`so`（换出）、`swpd` | `si/so` 持续 > 0 ＝内存不足；`swpd` 大但 si/so 为 0 ＝曾换过但现在稳定 |
| 关联信号 | `wa`（iowait） | 换页引起磁盘读 → wa 升高，**别把内存问题误判成磁盘瓶颈** |

【企业场景】
压测 30 分钟后 RT 突然翻倍、TPS 掉一半。你敲 `vmstat 1 5`：`si/so` 从 0 变成几千、`wa` 从 2 涨到 30、`free -m` 里 available 只剩 200MB。**结论：JVM/应用堆把物理内存吃满、开始换页**。处理动作三类：调小堆或修内存泄漏（代码侧）、加内存（资源侧）、把 swap 关掉或调低 `swappiness` 让问题尽快暴露而不是"慢慢变慢"。**关键认知：swap 不是"缓冲区"，它是性能悬崖的缓冲区——一旦常年使用，性能数据就不可信了。**

【面试考察】
面试官："怎么判断 Linux 内存是否不足？free 很小是不是就代表内存不够？"

参考回答框架：
1. 不是：Linux 用空闲内存做缓存，`free` 小是正常的；要看 **available**（可回收估算）；
2. 真正的信号是 `vmstat` 的 **si/so 持续非 0**（在换页），伴随 `wa` 升高；
3. 细分：`/proc/meminfo` 看 MemAvailable / Cached / SwapFree；`free -m` 看 Swap used 趋势；
4. 影响与动作：换页会显著拉长 RT → 定位到是内存问题后，选择调堆/修泄漏/加内存/调 swappiness，而不是去优化磁盘。

【易错点】

| 常见错误 | 正确理解 |
|---|---|
| 看 `free` 列很小就断言"内存不足" | Linux 缓存占用属正常；判断依据是 **available** 与 si/so |
| 看到 `wa` 高就认定磁盘瓶颈 | 换页（si/so 非 0）也会推高 wa；先排除内存问题 |
| 认为 swap 是"内存不够时的正常补充" | swap 是磁盘，速度远低于内存；频繁换页＝性能断崖，压测数据失真 |
| 只压一次就下内存结论 | 内存问题常随时间累积（泄漏）；稳定性测试（数小时）才能暴露 |
| 忽略容器/虚拟机的内存上限 | 容器有 cgroup 限制，宿主 free 有余量也可能被 OOM Kill（【扩展知识】） |

【我的理解】引导题（用自己的话回答）：
1. 为什么"free 很小"反而可能是健康的表现？判断内存是否紧张应该看哪两处证据？
2. 请解释"内存不足"和"磁盘 IO 高"为什么会在指标上互相伪装。

### 知识点4：磁盘与 IO 相关命令与判读（iostat 1 5 / df -h）

【课程原话/定义】
- `iostat 1 5` —— 参数 1 5 表示每隔 1s 查询一次，总共查询 5 次；用于监控设备的 IO 负载情况；
- `df -h` —— 列出文件系统的整体磁盘空间使用情况。

【为什么？】
磁盘排查要分清两件事：**"空间够不够"（容量）** 与 **"忙不忙"（性能）**——它们是完全不同的问题，用的命令也不同：

- **空间 → `df -h`**：看各挂载点的已用/可用百分比。空间满（100%）会直接导致写入失败、日志写不进、数据库报错——这是"功能级"故障，不是"慢"。
- **性能 → `iostat`**：看设备层面的吞吐与饱和。核心三个字段：
  - **`%util`**：设备有 IO 请求的时间占比，接近 100% ＝该设备**已饱和**（这是"磁盘是瓶颈"最直接的证据）；
  - **`await`**：平均每次 IO 的等待 + 服务时间（毫秒）。它升高说明**请求在排队**（磁盘跟不上上层压力）；
  - **`kB_read/s` / `kB_wrtn/s`、`r/s` / `w/s`**：吞吐量与每秒 IO 次数。**同样的吞吐下 IOPS（r/s+w/s）越高，说明每个请求越小、效率越低**——小随机 IO 是磁盘最怕的形态。

还有两个"看数前必须知道"的坑：① **第一行输出是"自开机以来的平均值"**，不是当前值——所以至少要跑两次以上（`-y` 可跳过第一行）；② 新版 sysstat（12+）里 **`svctm` 已被标记废弃**（常显示 0.00），不要拿它当判断依据，要看 `await` 与 `%util`。

【必须掌握】

| 命令 | 关键输出 | 判读要点 |
|---|---|---|
| `iostat 1 5` | `tps`、`kB_read/s`、`kB_wrtn/s`、`kB_read`、`kB_wrtn` | 吞吐视角；第一行是开机以来均值，要看后续行 |
| `iostat -x 1` | `%util`、`await`、`r_await`/`w_await`、`aqu-sz`、`r/s`、`w/s` | **`%util` 接近 100% ＝设备饱和；`await` 升高＝排队**（排查首选） |
| `df -h` | Filesystem / Size / Used / Avail / Use% / Mounted on | 空间容量；关注 Use% 与"哪个挂载点快满" |
| `df -i` | Inodes 使用率 | **空间没满却写不进去**时查 inode 是否耗尽（【扩展知识】） |
| 关联信号 | `vmstat` 的 `wa`、`b` | wa 高 + `iostat %util` 高 → 磁盘瓶颈坐实；wa 高但 %util 不高 → 可能是内存换页或网络文件系统 |

【企业场景】
压测中 RT 抖动严重，TPS 忽高忽低。`iostat -x 1` 显示某块盘 `%util` 长期 95%~100%、`await` 从 2ms 涨到 60ms。**结论：磁盘饱和、请求在排队**。动作按性价比排序：① 业务层减少随机小 IO（批量写、合并日志）；② 把日志/临时文件挪到独立盘；③ 上 SSD/NVMe 或提升 IOPS 上限；④ 检查是不是某个慢查询在刷盘。**注意 `df -h` 只回答"空间够不够"，不能用来判断"磁盘是否成为瓶颈"**——这是初学者最常混的一对。

【面试考察】
面试官："怎么判断磁盘是性能瓶颈？df 和 iostat 分别回答什么问题？"

参考回答框架：
1. 分工：`df` 回答**空间**（容量是否够、哪个挂载点满、inode 是否耗尽）；`iostat` 回答**性能**（吞吐、IOPS、是否饱和）；
2. 性能判读三件套：`%util`（接近 100% ＝饱和）、`await`（排队/延迟）、`r/s`+`w/s`（IO 形态是小随机还是大顺序）；
3. 注意：iostat 第一行是开机以来均值（至少看两次，或用 `-y`）；新版 `svctm` 已废弃，看 `await`；
4. 与上层指标合看：`vmstat` 的 `wa`/`b`、应用 RT 抖动、DB 慢查询日志，形成完整证据链。

【易错点】

| 常见错误 | 正确理解 |
|---|---|
| 用 `df -h` 判断"磁盘是否成为瓶颈" | `df` 只回答空间；瓶颈看 `iostat` 的 `%util` 与 `await` |
| 只看 iostat 第一行就下结论 | 第一行是**自开机以来的平均**（历史被摊平），要看后续行或用 `-y` |
| 用已废弃的 `svctm` 判断磁盘性能 | 新版 sysstat 里 `svctm` 已废弃；用 `await` / `%util` |
| 认为"空间没满就没磁盘问题" | 可能 inode 耗尽（`df -i`）、可能 IO 饱和（性能问题）、可能单盘打满而其他盘空闲 |
| 忽略 IO 形态 | 同样 100MB/s，**小随机 IO** 的 IOPS 高得多、对磁盘压力大得多，不能只看带宽 |

【我的理解】引导题（用自己的话回答）：
1. `df -h` 显示 40% 使用率，`iostat -x` 显示 `%util` 98%——这两句分别说明了什么？会被拿来下什么不同的结论？
2. 为什么"第一行是开机以来均值"这件事会让你误判磁盘性能？

### 知识点5：网络相关命令与判读（ping / ifconfig / hostname / netstat）

【课程原话/定义】
- `ping` —— 查询是否和某个地址连通；
- `ifconfig` —— 用于获取网卡配置和网络信息；
- `hostname` —— 显示本地用户信息（⚠️ 原文勘误，见文首：`hostname` 显示**主机名**）；
- `hostname -i` —— 显示本地 IP 地址；
- `netstat -an / -at / -aun / -p` —— 用于显示各种网络相关信息。

【为什么？】
网络在压测里的两个角色容易被忽略：

1. **它是被测链路的一部分**：带宽打满、连接数打满时，所有接口都会变慢，与"应用代码慢"的现象无法区分——所以必须能用 `ifconfig`/`ip` 看**收发流量与错包**、用 `ping` 看**延迟与丢包**。
2. **施压机侧的网络问题会造成"假瓶颈"**：这是压测专属的坑。施压机对被测服务发起大量短连接时，会产生海量 `TIME_WAIT`（主动关闭方状态），**端口被占满后新连接建立失败**，于是报错率上升、TPS 上不去——你以为是服务端不行，其实是施压机自己的端口耗尽。排查命令就是 `netstat` / 更快的 `ss`：`ss -ant | awk '{print $1}' | sort | uniq -c` 看各状态连接数，`netstat -nat | grep TIME_WAIT | wc -l` 看总量。

`netstat` 的选项组合要会读：`-a` 全部（含监听）、`-t` TCP、`-u` UDP、`-n` 直接显示数字（不解析服务名与域名，更快更准）、`-p` 显示所属进程（需要权限）。**`-n` 在压测排错时几乎必加**：不加的话每条连接都要做反向解析，既慢又可能卡在 DNS 上。

【必须掌握】

| 命令 | 用途 | 判读要点 / 建议 |
|---|---|---|
| `ping <地址>` | 连通性与延迟 | `-c 5` 指定次数；看平均延迟与丢包率；**ping 通不代表服务可用**（端口/服务可能没起） |
| `ifconfig`（或 `ip addr` / `ip -s link`） | 网卡配置、地址、收发与错包统计 | 看 errors/dropped 是否增长；现代发行版建议用 `ip` 命令（【扩展知识】） |
| `hostname` | 显示**主机名** | ⚠️ 不是用户信息；查当前用户用 `whoami` / `who` |
| `hostname -i` / `hostname -I` | 显示本机 IP | `-i` 依赖解析（可能返回 `127.0.1.1`），`-I` 列出所有地址更直观（【扩展知识】） |
| `netstat -an` / `-at` / `-aun` / `-p` | 网络连接、监听端口、协议状态、进程归属 | `-n` 必加（不解析）；`-p` 看进程；关注 `TIME_WAIT`、`CLOSE_WAIT`、`ESTABLISHED` 数量 |
| `ss -antp`（推荐替代） | 同 netstat，更快 | 大连接数场景优先用 `ss`（【扩展知识】） |

【企业场景】
压测压到 800 并发时错误率陡增，服务端日志却没有异常。你第一件事是在**施压机上**执行 `ss -s` / `netstat -nat | awk '{print $6}' | sort | uniq -c`：发现 `TIME_WAIT` 有 5 万多条、`ESTABLISHED` 上不去——**施压机可用端口/连接表被耗尽**（短连接 + 默认 60s TIME_WAIT）。处理：脚本改长连接（KeepAlive）、调大 `net.ipv4.ip_local_port_range`、开启 `tcp_tw_reuse`（内核参数），而不是去"优化服务端"。**这个坑几乎每个压测工程师都会踩一次，能现场识别它的人不多。**

【面试考察】
面试官："压测时服务端一切正常但错误率很高，你怎么排查？netstat 你会看哪些状态？"

参考回答框架：
1. 先分侧：确认是服务端问题还是**施压机/网络侧**问题（这是压测特有的盲区）；
2. 网络连通与质量：`ping`（延迟/丢包）、`ifconfig`/`ip -s link`（错包、带宽）；
3. 连接状态：`ss -antp` / `netstat -nat` 看 `TIME_WAIT`、`CLOSE_WAIT`、`ESTABLISHED`；TIME_WAIT 暴涨＋端口耗尽 → 施压机短连接问题（改 KeepAlive、调内核参数）；
4. 服务端侧对照：看两端同时段的连接数、错误日志，确认瓶颈到底在哪一侧；
5. 收口：把结论写进报告（含"假瓶颈"说明），避免把施压机问题当成被测系统容量结论。

【易错点】

| 常见错误 | 正确理解 |
|---|---|
| 只看服务端，忽略施压机侧网络 | TIME_WAIT/端口耗尽会让施压机成为瓶颈，造出**假瓶颈** |
| `netstat` 不加 `-n`，解析耗时且可能卡 DNS | 排错时用 `-n`；`-p` 需要权限，容器里常看不到宿主机进程 |
| 用 ping 通判断"服务正常" | ping 只证明网络可达；服务是否可用要看端口/业务（curl 或直接压） |
| 把 `TIME_WAIT` 当异常 | TIME_WAIT 是正常状态（主动关闭方等待 2MSL）；**数量暴涨 + 端口耗尽**才是问题 |
| 认为 `hostname` 显示用户信息（照抄原文） | 它显示主机名；用户信息用 `whoami` / `who` / `id` |
| 在容器里用 `ifconfig` 看宿主网络 | 容器网络命名空间独立，看到的可能只是容器网卡；需要进宿主或用监控系统 |

【我的理解】引导题（用自己的话回答）：
1. 为什么"压测中服务端没异常、但错误率高"这件事，第一反应应该是查**施压机**？给出两个可能的施压机侧原因。
2. `netstat` 输出里 `TIME_WAIT` 很多一定是故障吗？什么情况下才算故障？
