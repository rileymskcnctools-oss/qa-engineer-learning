## 一、TCP 协议接口测试概述

### 知识点 1：TCP 协议接口测试（上层协议）

【课程原话/定义】
针对 TCP 协议进行接口测试，是指基于 TCP 协议的上层协议——比如 Http、串口、网口、Socket 等。这些协议与 Http 测试方法类似，但测试过程中需要做些调整。

【为什么？**
为什么要单独讲"TCP 上层协议的接口测试"？因为不是所有接口都是 HTTP——很多底层系统（物联网设备、嵌入式、内核通信、游戏）用的是 Socket、串口、网口这些"基于 TCP 但非 HTTP"的协议。这些接口没有 HTTP 的"URL + 方法 + header"结构，而是"原始字节流"，所以测试工具和方法都要调整：不能再用 Postman 发 JSON，而要收发原始 socket 数据。理解这一点，你就知道接口测试不只有 HTTP 一种形态。

【必须掌握】
- TCP 上层协议：Http、Socket、串口、网口等
- 这些协议与 HTTP 测试类似，但需要调整工具和方法
- 非 HTTP 协议收发的是"原始字节流"，不是 URL+JSON
- 测试这类接口需要"收发 socket 数据的能力"或"代理 socket 的能力"

【企业场景】
你在公司测一个物联网设备的接口，它走的是 Socket 协议（不是 HTTP），用 Postman 根本测不了。你需要写 Python socket 客户端去收发数据，或者用代理工具拦截 socket 流量。这就是"非 HTTP 协议接口测试"的真实场景——测试方法要跟着协议变。

【面试考察】
面试官："接口测试只有 HTTP 吗？还有哪些协议？怎么测？"

参考回答框架：
1. 不只有 HTTP，还有 Socket、串口、网口、RPC 等基于 TCP 的上层协议
2. 这些协议收发原始字节流，不能用 Postman 直接测
3. 需要写 socket 客户端/服务端，或用代理工具拦截 socket 流量
4. 测试思路与 HTTP 类似（构造输入、校验输出），但工具要换

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 接口测试 = HTTP 测试 | 还有 Socket/串口/网口/RPC 等非 HTTP 协议 |
| 用 Postman 测 Socket | Socket 是字节流，需写 socket 客户端或用代理 |
| 认为非 HTTP 协议测不了 | 有 socket 收发能力或代理能力就能测 |

【我的理解】
> （为什么 Postman 测不了 Socket 协议？Socket 接口和 HTTP 接口在"数据形态"上有什么本质区别？）

## 二、Socket 协议测试

### 知识点 2：Socket 协议测试（客户端/服务端 + 配置文件走代理）

【课程原话/定义】
Socket（套接字）：进程通过套接字进行网络通信。适合对传输速度和安全性有严格要求的应用（如手机内核与外界传输测试数据）。测试 Socket 协议，需要有**收发 Socket 数据**的能力或**代理 Socket**的能力。

Python Socket 客户端/服务端示例（客户端连接 127.0.0.1:12345，服务端监听并回"收到信息"）。关键点：要能通过**配置文件**配置 host 和 port（用 yaml 读取），应用才能走 Socket 代理。

【为什么？**
为什么测试 Socket 协议的关键是"配置文件可改 host/port"？因为代理的原理就是"把流量引到代理工具上"——如果 socket 的地址（host/port）硬编码在代码里，就无法把流量引到代理（代理就是另一个 host:port）。所以测试 Socket 接口的第一步，往往是要开发把 socket 地址改成可配置（config 文件），这样测试才能插一个代理进去。这也解释了为什么"提可测性需求"是接口测试工程师的重要工作。

【必须掌握】
- Socket = 套接字，进程间网络通信的接口
- 测试 Socket：写 socket 客户端收发数据，或用代理拦截
- 关键前提：应用支持通过配置文件改 host/port（否则无法走代理）
- Python socket 客户端/服务端是基础收发能力

【企业场景】
你在公司测一个走 Socket 的设备，第一步不是写测试，而是找开发确认"socket 地址能不能配"——如果能配，你就用 mitmproxy 或自写代理把流量引过来拦截分析；如果不能配，就要提"可测性改造"需求（把 host/port 抽成配置）。这是测非 HTTP 协议接口的前置工作。

【面试考察】
面试官："怎么测试 Socket 协议的接口？"

参考回答框架：
1. 写 socket 客户端直接收发数据验证（Python socket）
2. 或用代理工具（mitmproxy/自写）拦截 socket 流量分析
3. 前提：应用支持配置文件改 host/port，才能走代理
4. 测试思路同 HTTP：构造输入 → 校验输出

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| socket 地址硬编码还硬测 | 硬编码无法走代理，需先做可配置改造 |
| 用 HTTP 工具测 Socket | Socket 是字节流，用 socket 客户端或代理 |
| 忽略"提可测性需求" | 让开发把 host/port 抽成配置是测试前置工作 |

【我的理解】
> （为什么"socket 地址可配置"是走代理的前提？如果地址硬编码，代理插不进去会怎样？）

### 知识点 3：其他协议（串口/网口/visa）+ 自写代理

【课程原话/定义】
其他协议（串口、网口、visa 等）与 Socket 测试模式类似，但更冷门、无合适的代理工具。需测试人员**自己写代理**：开两个监听服务（监听服务 A 监听端口 123，透传/改数据给端口 456，监听服务 B 同理），实现 mock。

注意：自写代理会增加数据传输时间，过分注重性能的场景慎用。且需让应用支持端口修改（与开发交流提需求）。

【为什么？**
为什么冷门协议要"自写代理"？因为串口/网口这类协议没有现成的抓包/代理工具（不像 HTTP 有 Charles），测试人员只能自己写一个"中间人"：监听真实端口、转发到虚拟端口（中间可加 mock 逻辑）。核心思想还是 Ch16 讲的"中间人代理"，只是没有现成工具，得自己实现。这也体现了"测试开发"的能力边界——工具没有的，就自己写。

【必须掌握】
- 串口/网口/visa 等协议与 Socket 类似，但无现成代理工具
- 需自写代理：两个监听服务，A 透传/改数据给 B（实现 mock）
- 缺点：增加传输时间，性能敏感场景慎用
- 前提：应用支持端口修改（提需求给开发）

【企业场景】
你在公司测一个串口设备，没有现成抓包工具，就自己写一个串口代理：监听真实串口，把数据透传（或加 mock 篡改）到虚拟串口，从而观察和修改设备通信。这是"测试开发工程师"和"普通测试"的差距——普通测试只能等设备，测试开发能自己写代理解耦测试。

【面试考察】
面试官："没有现成工具的协议（如串口）怎么测？"

参考回答框架：
1. 自写代理：两个监听服务，A 接收 → 透传/改数据 → B 转发
2. 中间可加 mock 逻辑（篡改数据）
3. 前提：应用支持端口修改
4. 缺点：增加传输延迟，性能敏感场景慎用

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 找现成工具测串口 | 串口无现成代理，需自写 |
| 自写代理不考虑性能损耗 | 代理增加传输时间，性能场景慎用 |
| 忽略"应用支持端口修改" | 不支持就堵死代理道路，需提前提需求 |

【扩展知识】
自写代理的核心思想（回顾 [[Ch16-常用代理工具与代理模式]]）：中间人模式——客户端 → 代理 → 真实服务，代理在中间可以"透传"（原样转发）或"篡改"（mock）。Charles/Fiddler 是 HTTP 的现成中间人，串口/网口则要自己实现这个中间人。

【我的理解】
