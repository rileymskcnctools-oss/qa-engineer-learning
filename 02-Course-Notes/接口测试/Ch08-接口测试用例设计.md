## 一、接口测试流程与质量目标

### 知识点 1：接口测试流程与质量目标

【课程原话/定义】
接口测试在**需求分析完成之后**即可设计对应的测试用例，然后根据用例进行接口测试。接口测试用例设计需要用到黑盒测试用例设计方法（和功能测试用例设计方法类似），同时增加与接口特性相关的测试用例。

接口测试的质量目标：**功能、性能、安全、兼容、健壮性、高可用性（中间件）**。

【为什么？】
为什么接口测试在"需求分析完成之后"就能开始？因为接口测试不依赖 UI——只要需求文档里定义了接口的输入输出，测试人员就能据此设计用例，不必等前端页面做完。这就是接口测试"能更早介入"的底层原因。质量目标里除了"功能"之外还有性能/安全/健壮性/高可用，是因为接口是系统对外服务的通道，只测功能正确远远不够。

【必须掌握】
- 接口测试从需求分析完成后即可开始，早于 UI 测试
- 用例设计方法 = 黑盒方法（等价类/边界值/判定表/场景法）+ 接口特性用例
- 六项质量目标：功能、性能、安全、兼容、健壮性、高可用性
- 高可用性关注的是中间件（如 Redis、数据库、消息队列）故障时的表现

【企业场景】
你在公司拿到一个"用户登录接口"的需求，不用等前端登录页做完，就能立刻设计用例：正确账号密码（功能）、密码错误/账号不存在（异常）、密码连续错 5 次（健壮性）、并发登录（性能）、SQL 注入和越权（安全）、老版本 App 调用（兼容）、Redis 挂了还能不能登录（高可用）。这就是"需求分析完就能测"的体现。

【面试考察】
面试官："接口测试的质量目标有哪些？"

参考回答框架：
1. 功能：输入正确参数返回正确结果
2. 性能：高并发下响应时间、吞吐量满足要求
3. 安全：鉴权、越权、加密、防注入
4. 兼容：新老版本、不同客户端都能正常调用
5. 健壮性：异常输入、异常场景下不崩溃、有合理报错
6. 高可用：依赖的中间件（Redis/DB/MQ）故障时能降级、不雪崩

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 接口测试=功能测试的翻版 | 接口测试还要额外覆盖幂等、并发、故障注入等接口特有维度 |
| 等到前端页面做完才测接口 | 需求分析完就能测，这是接口测试早介入的优势 |
| 高可用=服务不宕机 | 高可用还包括中间件故障时降级、故障转移、多活等 |

【我的理解】
> （为什么接口测试能在"需求分析完成之后"就开始，而 UI 测试不行？这个时间差对项目有什么价值？）

### 知识点 2：协议分析方法（抓包工具）

【课程原话/定义】
协议分析方法——网络监听：TcpDump、WireShark、代理 Proxy。
推荐工具：手工测试 Charles（全平台）、安全测试 BurpSuite（全平台 Java）；自动化测试 mitmproxy；其他代理 Fiddler（仅 Windows）、AnyProxy（全平台）。

【为什么？】
为什么要"抓包"？因为接口测试的第一步是**搞清楚接口到底长什么样**——真实的请求方法、请求头、参数、返回结构。有时接口文档不全或过时，就得靠抓包从真实流量里还原接口的真实协议。Charles/BurpSuite/mitmproxy 都是"中间人代理"：让客户端和服务器之间的流量经过自己，就能看到、甚至篡改请求和响应。

【必须掌握】
- 抓包的本质：客户端 ↔ 代理（抓包工具）↔ 服务器，流量经过代理被记录
- TcpDump/WireShark：底层抓包（网络层），适合看 TCP/IP 细节
- 代理工具：Charles（全平台，最常用）、Fiddler（仅 Windows）、BurpSuite（安全测试）、mitmproxy（自动化/命令行）
- HTTPS 抓包需要安装并信任代理的证书（见后续抓包证书配置章节）

【企业场景】
你在公司要测一个 App 的接口，但后端没给完整文档，或者文档和实际对不上。你会用 Charles 抓包：手机设代理 → 在 App 里点几个操作 → 从 Charles 里看到 App 实际请求了哪些接口、传了什么参数、返回了什么。这就是"用抓包还原接口真相"，也是接口测试用例设计的前置动作。

【面试考察】
面试官："Charles 和 Fiddler 有什么区别？抓包原理是什么？"

参考回答框架：
1. 都是 HTTP 代理抓包工具，原理是"中间人代理"
2. Charles 全平台（Windows/Mac/Linux），Fiddler 仅 Windows
3. Charles 界面友好、弱网模拟和断点好用；Fiddler 在 Windows 上功能强大
4. HTTPS 抓包需要安装代理证书并信任，否则只能看到乱码
5. mitmproxy 支持命令行和脚本，适合集成到自动化

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 抓包=偷看数据 | 抓包是合法测试手段，用于还原接口协议、排查问题 |
| 不装证书也能抓 HTTPS | HTTPS 加密，不装证书只能看到握手，看不到明文内容 |
| WireShark 和 Charles 是同类 | WireShark 抓网络层所有协议；Charles 主要抓 HTTP/HTTPS 应用层 |

【我的理解】
> （为什么 HTTPS 抓包必须装证书？如果不装证书，Charles 抓到的是什么？这个"中间人"机制和网络安全有什么关系？）

## 二、接口测试用例设计方法

### 知识点 3：基本功能流程测试（冒烟测试）

【课程原话/定义】
基本功能流程测试：先执行**冒烟测试**，把最基本的功能流程走通。冒烟测试决定提测是否成功——通过才进入详细测试阶段；不通过则打回开发修改后重新提测。冒烟通过后，进行**正常流程覆盖测试**，粒度更细，覆盖一些分支业务逻辑。

【为什么？】
为什么要先冒烟？因为如果最基本的主流程都不通，那详细的用例测试就是浪费时间——你会在一个"地基都塌了"的系统上测一堆细节，最后全是无效 bug。冒烟测试是一道"门槛"：用最少的用例（通常是核心主链路）快速判断"这个版本能不能测"，不能测就退回，节省整个团队的时间。

【必须掌握】
- 冒烟测试：用最少的核心用例验证主流程是否打通
- 冒烟 = 提测门槛：通过才进入详细测试，不通过打回开发
- 正常流程覆盖：比冒烟更细，覆盖分支业务逻辑
- 冒烟关注"通不通"，详细测试关注"对不对"

【企业场景】
你在公司每天接到开发提测，第一件事不是跑全套用例，而是跑冒烟：登录、下单主流程、核心查询接口，各跑一遍。如果登录接口都 500 了，直接打回开发，不用继续测。冒烟过了，才跑详细的用例（各种分支、边界、异常）。这能避免"测了一整天发现主流程根本跑不通"的浪费。

【面试考察】
面试官："冒烟测试和详细测试有什么区别？冒烟测试的价值是什么？"

参考回答框架：
1. 冒烟测试：少量核心用例，验证主流程是否通，决定提测是否成功
2. 详细测试：覆盖分支逻辑、边界、异常，验证正确性
3. 价值：快速拦截"不能测"的版本，节省测试成本
4. 顺序：冒烟 → 详细测试，冒烟不通过直接打回

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 冒烟测试=把全部用例跑一遍 | 冒烟只跑少量核心主流程用例 |
| 冒烟通过=质量没问题 | 冒烟只证明"能测"，不证明"没 bug" |
| 冒烟失败继续往下测 | 冒烟失败应打回开发，继续测是浪费 |

【我的理解】
> （一个电商系统的接口冒烟测试，你会选哪几个接口作为冒烟用例？为什么选它们而不是别的？）

### 知识点 4：基于输入域的测试（参数类用例）

【课程原话/定义】
接口请求需要携带参数，所以基于输入域的测试是接口用例设计的核心。包括：
- **边界值测试**：对范围要求的参数，综合等价类和边界值，选上点和离点，覆盖有效/无效等价类
- **特殊字符校验**：对要求不能含特殊字符的字段，设计含特殊字符的用例
- **参数类型校验**：对类型有要求的字段（只能英文数字/整数等），设计反向用例
- **必选参数校验**：每个必填参数都要设计一条"不传"的用例
- **组合参数校验**：对选填参数，用判定表设计必填+不同选填的组合场景

【为什么？】
为什么接口测试特别强调"参数类用例"？因为接口的输入是参数，参数就是攻击面和 bug 高发区。一个字段漏校验（比如金额字段传了负数、字符串类型传了对象、必填字段没传），轻则数据脏，重则服务崩溃或产生资损。设计思路和功能测试的黑盒方法一脉相承（等价类/边界值/判定表），但聚焦在"每个参数"上。

【必须掌握】
- 边界值：范围参数取上点/离点，覆盖有效+无效等价类
- 特殊字符：要求"不能含特殊字符"的字段，设计注入特殊字符的反向用例
- 参数类型：字段有类型要求时，设计"传错类型"的反向用例
- 必选参数：每个必填字段设计一条"不传"的用例
- 组合参数：用判定表覆盖"只传必填"和"必填+不同选填"的组合

【企业场景】
你在公司测一个"创建订单"接口，参数有：`userId`（必填）、`amount`（必填、0<金额<100000）、`couponCode`（选填、字母数字）、`remark`（选填、不能含 `<script>` 等特殊字符）。你会设计：amount 传 0.01/99999/0/100000/负数（边界值）、couponCode 传中文/超长（类型）、不传 userId（必填）、remark 传 `<script>alert(1)</script>`（特殊字符）、只传必填 + 加一个选填 + 加两个选填（组合）。这就是"基于输入域"的完整用例矩阵。

【面试考察】
面试官："一个接口有多个参数，你怎么设计测试用例？"

参考回答框架：
1. 先识别每个参数：必填/选填、类型、取值范围、是否允许特殊字符
2. 边界值 + 等价类：有效等价类、无效等价类、边界上下点
3. 必填校验：每个必填参数都测"不传"
4. 类型校验：传错类型的反向用例
5. 特殊字符：注入类反向用例
6. 组合：用判定表覆盖参数组合（正交/判定表控制用例数量）

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 只测"参数正确"的用例 | 反向用例（不传/传错/特殊字符）才是 bug 高发区 |
| 边界值只测上点和下点 | 还要测离点（边界外一点）和等价类内点 |
| 组合参数穷举所有组合 | 用判定表/正交法精简组合，避免用例爆炸 |

【我的理解】
> （一个字段要求"0 < 金额 < 100000"，请写出它的边界值测试用例（上点、离点、内点），并说明每个点为什么选它。）

### 知识点 5：排重逻辑与接口幂等性

【课程原话/定义】
**排重逻辑**：字段要求不能重复时，重复请求相同参数，验证服务端处理是否正确。
**接口幂等性**：幂等 = 任意多次执行产生的影响与一次执行相同。涉及资金的系统（银行、电商）尤其重要。用户重复提交、网络重发、系统重试等场景，都需要保证幂等。幂等测试：多次发送同一参数的请求，验证服务端响应**只有一次是成功的**。

【为什么？】
为什么幂等对"资金系统"至关重要？想象用户点了两次"支付"按钮，或者网络超时后客户端自动重试了一次——如果接口不幂等，可能扣两次款。幂等不是"返回一样的结果"，而是"**产生一样的副作用**"（副作用次数相同）。排重逻辑（如用户名唯一）和幂等（如重复下单只成功一次）都是为了防止"重复操作造成重复效果"。

【必须掌握】
- 幂等：多次执行 = 一次执行的影响（副作用次数一致）
- 排重：重复字段（如用户名）重复提交时服务端能正确拒绝/提示
- 幂等测试：多次发同一请求，只有一次成功（或多次结果一致）
- 场景：用户重复点击、网络重发、系统自动重试
- 资金系统（银行/电商）必须保证幂等

【企业场景】
你在公司测"支付接口"，会专门设计幂等用例：同一个订单号连续提交两次支付请求，断言只有第一次成功、第二次返回"订单已支付"（或结果一致），绝不能扣两次钱。这就是幂等测试——它防的不是"功能错"，而是"重复操作造成重复扣款"这种致命 bug。

【面试考察】
面试官："什么是接口幂等性？怎么保证和测试幂等性？"

参考回答框架：
1. 幂等：同一请求执行 N 次和执行 1 次，副作用相同
2. 保证手段：唯一请求号 + 数据库唯一索引、token 机制、状态机（已支付就不再处理）
3. 测试：同一参数重复请求 N 次，断言只有一次成功/结果一致
4. 典型场景：重复提交订单、网络重试、支付重复扣款

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 幂等=返回结果相同 | 幂等是"副作用相同"，返回体可以不同（如第二次返回提示） |
| 幂等和排重是一回事 | 排重是"不允许重复数据"，幂等是"重复操作不产生重复效果"，相关但不同 |
| 只有资金系统才需要幂等 | 任何"写操作"接口都应考虑，只是资金系统要求最严 |

【扩展知识】
实现幂等的常见方案：
1. **唯一请求号 + 唯一索引**：每次请求带 requestId，数据库对 requestId 建唯一索引，重复插入失败
2. **Token 机制**：先申请 token，提交时校验并删除 token，重复提交因 token 已失效而失败
3. **状态机**：订单状态"待支付→已支付"单向流转，已支付状态不再处理重复请求

【我的理解】
> （用户在网络卡顿时连续点击了 3 次"下单"按钮，如果接口幂等和不幂等，分别会发生什么？为什么说幂等防的是"重复副作用"而不是"重复请求"？）

### 知识点 6：线程安全测试（并发与分布式）

【课程原话/定义】
线程安全测试包含**并发测试**和**分布式测试**。
- 分布式：解决单台物理服务器容量和性能瓶颈的优化手段。两种形式：**水平扩展**（加机器，流量平分）、**垂直拆分**（不同需求分发到不同机器）
- 高并发：重点是测试"同时有多少量"（如在线直播上万人观看）。高并发可通过分布式、缓存、多线程等手段解决
- 并发测试：多个相同参数的请求，只有一条成功，其他失败
- 分布式测试：分布式环境中并发相同参数的请求，只有一条成功，其他失败

【为什么？】
为什么要测"并发相同参数只有一条成功"？因为这测的是**线程安全**和**资源竞争**。典型 bug：秒杀商品库存只剩 1 件，100 个人同时下单，如果代码没有锁/原子操作，可能 100 人都下单成功（超卖）。并发测试就是要暴露这种"多线程同时操作共享数据"导致的错误。分布式是并发的一种规模化形式——多台机器同时处理，同样要保证"同一个资源只被成功操作一次"。

【必须掌握】
- 并发测试：同一参数多请求并发，验证只有一条成功（资源竞争/线程安全）
- 分布式：水平扩展（加机器平分流量）+ 垂直拆分（按需求分发到不同机器）
- 高并发：测试"同时能扛多少量"，可用分布式/缓存/多线程解决
- 典型场景：秒杀、抢购、库存扣减、注册抢号

【企业场景】
你在公司测"秒杀接口"，会用压测工具（JMeter/Locust）模拟 1000 个用户同时请求同一个商品（库存 1 件），断言最终只有 1 个请求成功、库存不为负、其他请求收到"已抢完"的明确提示。如果发现超卖（库存变负数），就是严重的线程安全 bug，要提给开发加锁或原子操作。

【面试考察】
面试官："怎么测试一个秒杀接口？并发测试关注什么？"

参考回答框架：
1. 用压测工具模拟大量用户并发请求同一资源
2. 断言：只有符合库存数量的请求成功，其余失败且提示明确
3. 关注：是否超卖、库存是否负数、是否有死锁、响应时间是否退化
4. 背后考察：线程安全、原子操作、锁机制、分布式一致性

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 并发测试=性能测试 | 并发测试关注"正确性"（超卖/竞争），性能测试关注"快不快" |
| 水平扩展和垂直拆分是一回事 | 水平=加机器均分流量；垂直=按功能拆到不同机器 |
| 分布式一定更快 | 分布式引入网络开销和一致性问题，不是简单"变快" |

【扩展知识】
高并发的常见优化手段（面试高频）：
1. **缓存**（Redis）：热点数据放缓存，减少 DB 压力
2. **多线程/异步**：非核心逻辑异步化（如发短信、写日志）
3. **消息队列**（MQ）：削峰填谷，把突发流量缓冲起来
4. **读写分离**：读走从库、写走主库

【我的理解】
> （秒杀库存 1 件、100 人同时下单，如果不做并发控制会发生什么？"超卖"的本质是什么？为什么加个 Redis 扣减就能解决？）

### 知识点 7：故障注入（健壮性测试）

【课程原话/定义】
故障注入测试：故意制造故障场景，保证系统健壮性。
- **Redis 故障**：清空 Redis → 发请求击穿缓存 → 从 DB 获取正常数据并回写 Redis；恢复 Redis → 从 Redis 获取正确数据；制造 Redis 崩溃 → 降级从 DB 获取正常数据
- **数据库故障**：数据丢失 → 数据恢复策略；数据库崩溃 → 多活策略（保证功能不受影响）
- **接口故障**：服务重启 → 集群自动重启实例、请求无异常；集群崩溃 → 返回错误信息、内部有重试机制

【为什么？】
为什么要故意制造故障？因为线上环境"依赖一定会挂"——Redis、数据库、下游接口总有一天会出问题。健壮性测试就是提前演练：当这些依赖挂掉时，系统能不能优雅降级（用 DB 兜底、返回友好错误、自动重试），而不是直接雪崩、整个系统崩溃。这测的是系统的"抗打击能力"。

【必须掌握】
- 故障注入 = 故意制造故障，验证系统降级/容错能力
- Redis 故障：缓存击穿（清空缓存）、缓存崩溃（降级读 DB）
- 数据库故障：数据丢失（恢复）、崩溃（多活/主备切换）
- 接口故障：服务重启（自动拉起）、集群崩溃（重试+错误提示）
- 核心：故障发生时，系统不雪崩、能降级、能恢复

【企业场景】
你在公司做故障演练（Chaos Engineering）：配合开发把 Redis 停掉，然后发请求，验证接口能否自动降级到直接查 DB 并且把数据回写到缓存；再配合开发把数据库主库停掉，验证从库能否自动顶上（多活）。这些测试平时不做，但一旦线上真出故障，就是保命的能力。

【面试考察】
面试官："Redis 挂了，接口还能正常工作吗？你怎么测？"

参考回答框架：
1. 这是健壮性/故障注入测试，验证降级能力
2. 制造 Redis 崩溃 → 发请求 → 断言降级读 DB、返回正常数据
3. 制造 Redis 数据清空 → 断言缓存击穿后能回源 DB 并回写缓存
4. 同理测数据库故障（多活切换）、下游接口故障（重试机制）

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 故障注入是"搞破坏" | 是"有目的的演练"，验证系统在故障下的降级/容错能力 |
| 降级=功能变差 | 降级是"用兜底方案保证核心功能可用"，可能牺牲非核心功能 |
| 故障注入只在测试环境随便测 | 要开发配合、在受控环境进行，避免影响生产 |

【扩展知识】
缓存击穿/穿透/雪崩（面试高频，和 Redis 故障强相关）：
- **击穿**：某个热点 key 过期瞬间大量请求打到 DB
- **穿透**：请求不存在的 key（如 id=-1），缓存和 DB 都没有，恶意/异常流量直击 DB
- **雪崩**：大量 key 同时过期，请求集中打到 DB，压垮后端

【我的理解】
> （"缓存击穿"和"缓存雪崩"有什么区别？为什么清空 Redis 后再发请求，能测出系统是否做了"击穿保护"？）

### 知识点 8：接口测试用例要素

【课程原话/定义】
接口测试用例要素：**模块、测试标题、优先级、前置条件、请求方法、请求参数、预期结果、实际结果**。

【为什么？】
为什么要定义"用例要素"？因为用例是团队的沟通载体和执行的依据——一个要素不全的用例，别人看不懂、执行时对不上、出问题时无法追溯。接口测试用例比功能测试用例多了"请求方法、请求参数"这些接口特有的字段，少了"操作步骤"这种 UI 特有的描述。要素统一，用例才能沉淀成资产。

【必须掌握】
- 模块：接口所属的业务模块（如"用户模块"）
- 测试标题：一句话说明测什么
- 优先级：P0/P1/P2，决定执行顺序
- 前置条件：测试前需要满足的状态（如"已有测试账号"）
- 请求方法 + 请求参数：GET/POST 等 + 具体参数值
- 预期结果：状态码 + 响应字段的期望值
- 实际结果：执行后填写，与预期对比

【企业场景】
你在公司用 Excel/Jira/测试平台维护接口用例，每条用例都按这 8 个要素填写。比如："模块=订单，标题=创建订单成功，优先级=P0，前置条件=已登录+有可用库存，方法=POST，参数={userId, amount...}，预期=200 且返回 orderId，实际=（执行后填）"。要素齐全，新人照着就能执行，回归时也能快速定位。

【面试考察】
面试官："接口测试用例一般包含哪些字段？和功能测试用例有什么不同？"

参考回答框架：
1. 字段：模块、标题、优先级、前置条件、请求方法、请求参数、预期结果、实际结果
2. 接口用例强调请求方法 + 请求参数 + 预期响应（状态码/字段）
3. 功能用例强调操作步骤 + 界面表现
4. 接口用例的"预期结果"包含状态码、响应头、响应体字段校验

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 用例不写前置条件 | 缺前置条件会导致用例无法复现或执行失败 |
| 预期结果只写"返回成功" | 应写清楚：状态码 + 关键字段 + 字段值 |
| 请求参数写成"见文档" | 应写具体参数值，保证用例可独立执行 |

【我的理解】
> （为什么接口用例的"预期结果"要写清状态码和响应字段，而不能只写"返回成功"？一个只有"返回成功"的用例，遇到 bug 时能定位问题吗？）
