## 一、抓包分析与测试集

### 知识点 1：LiteMall 搜索接口抓包分析（har 导入）

【课程原话/定义】
LiteMall 商城：`http://litemall.hogwarts.ceshiren.com/vue/index.html#/`，用浏览器开发者工具抓包。

抓包流程：访问 LiteMall 页面 → 打开开发者工具 Network → 搜索框输入"抱枕"回车 → 抓到请求 → 找到 `list` 接口 → 查看 Headers 里的 URL、请求方法、请求头。

搜索接口：`GET /wx/goods/list?keyword=抱枕&page=1&limit=10&categoryId=0`，请求头里有个特殊的 `X-Litemall-Token`（登录后拿到的 token）。把接口信息保存为 **har** 格式，导入 Postman。

【为什么？】
为什么要"抓包 + 存 har + 导入 Postman"？因为手动在 Postman 里重建一个请求（URL、方法、几十个 header、参数）既慢又容易漏，而 har 是浏览器抓包的标准导出格式，直接"原样"导入 Postman，连请求头都带过来了。这就是"从真实流量还原请求"的最高效方式——比手填准，比看文档快。

【必须掌握】
- 抓包入口：浏览器 F12 → Network，操作后找到目标接口
- 搜索接口：GET /wx/goods/list，参数 keyword/page/limit/categoryId
- `X-Litemall-Token`：登录后拿到的 token，放在请求头
- har 是浏览器抓包导出格式，可导入 Postman 还原请求
- 导入后请求头、参数、方法都自动带过来

【企业场景】
你在公司要测一个线上接口，最快的起步方式不是找开发要文档，而是自己打开浏览器抓包：F12 → Network → 操作页面 → 找到接口 → 右键 Copy as cURL 或保存 har → 导入 Postman。这样你拿到的请求是"真实、完整、带鉴权头"的，直接就能调通。

【面试考察】
面试官："接口文档不全时，你怎么快速拿到接口信息？"

参考回答框架：
1. 用浏览器开发者工具（F12）或 Charles 抓包
2. 操作页面，找到目标接口的请求
3. 查看 URL、请求方法、请求头、参数
4. 保存为 har / 复制 cURL，导入 Postman 直接复用

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 手动重建请求漏了 header | 用 har 导入，请求头自动带过来 |
| 忽略 X-Litemall-Token | 没 token 请求会被拒绝（未登录/鉴权失败） |
| 抓包抓错接口 | 用关键字/URL 过滤 Network，定位真正的业务接口 |

【我的理解】
> （为什么"har 导入 Postman"比"手动填请求"更靠谱？手动填最容易漏掉什么？）

### 知识点 2：创建测试集 + 添加断言

【课程原话/定义】
创建测试集：新建 Collection「LiteMall」→ 把导入的 `list` 接口"另存为"到新测试集 → 设置变量（URL 引用 `{{baseURL}}`）→ 请求成功。

添加断言（Tests 面板）：
```javascript
pm.test("响应状态码为 200", function () {
    pm.response.to.have.status(200);
});
pm.test("响应体中包含【抱枕】", function () {
    pm.expect(pm.response.text()).to.include("抱枕");
});
```

【为什么？】
为什么要把接口"另存为"到自己的测试集？因为导入的 har 是一个"独立请求"，不属于任何测试集，无法批量管理、无法共享变量。另存到 Collection 后，它才成为"可复用、可批量运行"的测试资产。而断言（状态码 200 + 响应包含"抱枕"）把"肉眼看结果"变成了"自动化判定"——搜索"抱枕"就应该返回含"抱枕"的数据。

【必须掌握】
- 导入的 har 请求要"另存为"到自己的 Collection
- Collection 内用 `{{baseURL}}` 变量管理接口地址
- 断言：状态码 200 + 响应体包含关键词
- 断言让测试从"肉眼看"变成"自动 PASS/FAIL"

【企业场景】
你在公司把抓包来的接口导入 Postman 后，不是直接用，而是先建一个"订单模块"测试集，把接口存进去、把 baseURL 抽成变量、写好断言。这样以后回归点 Run 就行，新同事也能直接复用这套测试集。

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 导入的 har 请求不存测试集 | 无法批量运行、无法共享变量 |
| URL 硬编码不抽 baseURL | 换环境要逐个改，抽变量后只改一处 |
| 只断言状态码不断言内容 | 状态码 200 不代表返回了正确数据，要断内容 |

【我的理解】
> （为什么断言要"状态码 + 内容"两层？只断言状态码 200 会漏掉什么问题？）

## 二、数据驱动

### 知识点 3：数据驱动测试（CSV / JSON）

【课程原话/定义】
数据驱动：准备 CSV 或 JSON 数据，第一行是表头（对应变量名），下面是具体数据。修改请求参数为变量引用，断言用 `data.xxx` 调用字段。

CSV 示例（表头 keyword,page,limit,categoryId,statusCode,expect）：
```csv
keyword,page,limit,categoryId,statusCode,expect
,1,10,0,200,list
全棉羽丝绒抱枕芯...,1,10,0,200,list
^{}`[],1,100,0,400,HTTP Status 400
```

断言改用 data 变量：
```javascript
pm.test("响应状态码符合预期", function () {
    pm.response.to.have.status(data.statusCode);
});
pm.test("响应中包含预期内容", function () {
    pm.expect(pm.response.text()).to.include(data.expect);
});
```

运行：Run 页面点 Select File 选 CSV → 迭代次数自动=数据组数（如 4）→ 可 Preview 预览 → Run。

【为什么？】
为什么要数据驱动？因为"一个用例配一组数据"会让用例爆炸，而数据驱动把"逻辑（断言脚本）"和"数据（CSV/JSON）"分离——同一套请求+断言，喂不同数据就能跑出多组用例（正常关键词、空值、超长、特殊字符），覆盖等价类和边界。这既是测试用例设计的落地，也是接口自动化的基本盘。`data` 变量优先级最高，运行时会覆盖测试集里的同名变量。

【必须掌握】
- 数据驱动 = 逻辑与数据分离，一份脚本 + 多组数据
- CSV 首行是表头（变量名），JSON 是对象数组
- 断言用 `data.字段` 引用当前迭代的数据
- Run 时 Select File 导入数据，迭代次数 = 数据组数
- `data` 优先级最高（见 [[Ch10-Postman实战练习]] 变量优先级）

【企业场景】
你在公司测搜索接口，不可能为"空关键词/正常关键词/超长关键词/特殊字符"各写一个用例。你用数据驱动：一个 list 请求 + 断言，CSV 里放 4 组关键词（空、正常、超长、`^{}[]` 特殊字符），Run 一次跑 4 条用例，分别验证返回 200/400。这就是"加数据不加代码"。

【面试考察】
面试官："Postman 怎么做数据驱动测试？"

参考回答框架：
1. 准备 CSV（首行表头）或 JSON（对象数组）数据
2. 请求参数和断言里用 `{{变量}}` / `data.字段` 引用
3. Run 时 Select File 导入数据，迭代次数=数据组数
4. 每轮迭代用一组数据，data 变量优先级最高

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| CSV 首行不是表头 | 首行被当作变量名，数据少一组 |
| 断言里写死期望值 | 应用 `data.expect`，让期望也随数据变化 |
| 忘了 Select File 就 Run | 没导入数据，`data.xxx` 全部为红/报错 |

【我的理解】
> （为什么"数据驱动"比"一个用例一组数据"更好？它的核心思想是什么？）

## 三、鉴权与参数传递

### 知识点 4：Cookies 与鉴权方式

【课程原话/定义】
**Cookie**：存储在客户端浏览器中的一小段文本，用于标识和认证一个用户（如购买接口要先验证是否登录）。Postman 会自动把请求中产生的 Cookie 收集到 Cookie 管理器里，后续接口调用时自动携带，不用手动复制。

**鉴权**：身份认证，验证是否有权限从服务器访问/操作数据（门禁比喻：进门必须验证身份）。

Postman 支持的鉴权方式（逐个说明）：
- **Inherit auth from parent**：从父级继承身份验证，是每个请求的默认选择
- **No Auth**：不需要身份认证
- **API Key**：自定义认证方式，在请求头里加认证字段（如 `X-Litemall-Token: xxx`）
- **Bearer Token**：承载令牌，Authorization 头里 `Bearer <token>`
- **Basic Auth**：基础验证，提供用户名 + 密码（Base64 编码后放 Authorization 头）
- **Digest Auth**：摘要式认证，比 Basic 安全（密码不直接明文传输）
- **OAuth / OAuth 2.0**：第三方身份认证，不公开密码的情况下授权访问第三方 API
- **Hawk Authentication**：消息码认证算法（HMAC 签名）
- **AWS Signature**：针对亚马逊 AWS 公有云用户的签名认证
- **NTLM**：微软的局域网管理认证协议
- **Akamai EdgeGrid**：Akamai 的专属认证协议

**最常用：API Key、Basic Auth、OAuth 2.0、Bearer Token。**

【为什么？】
为什么要理解鉴权？因为现代接口几乎都"要登录才能调"——token/cookie 就是"门禁卡"。测试时，你发请求必须带上正确的鉴权信息，否则服务端返回 401/403，连接口都调不通，更别说测了。Postman 把这些鉴权方式做成选项，是为了让你不用手动拼鉴权头——选对方式、填对值，Postman 自动帮你加头。

【必须掌握】
- Cookie：客户端文本，标识/认证用户（登录态）；Postman 会自动收集并携带 Cookie，无需手动复制
- 鉴权：验证是否有权限访问数据
- 常用鉴权：API key（自定义头）、Basic（用户名密码）、OAuth2（第三方授权）、Bearer Token
- Inherit auth from parent 是默认，从父级继承

【企业场景】
你在公司测接口，登录后拿到 token，在请求的 Authorization 里选 API Key，key 填 `X-Litemall-Token`、value 填 token 值，Postman 就会自动在请求头里带上这个字段。之后所有需要登录态的接口都能直接调通，不用手动复制粘贴 token。

【面试考察】
面试官："接口测试中，Cookie 和 Token 的区别是什么？常用的鉴权方式有哪些？"

参考回答框架：
1. Cookie：服务端下发的会话标识，浏览器自动携带，有状态
2. Token：无状态鉴权凭证，通常放 Authorization 头
3. 常用鉴权：API key、Basic Auth、Bearer Token、OAuth2
4. 测试时：拿到 token/cookie 填入鉴权，才能访问受保护接口

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 分不清鉴权和加密 | 鉴权是"验身份"，加密是"防偷看"，两回事 |
| API Key 和 Bearer Token 混用 | API Key 是自定义头（如 X-Token: xxx），Bearer 是 Authorization: Bearer xxx |
| 所有接口都手动加 token 头 | 可在 Collection 层配鉴权，子请求继承 |

【我的理解】
> （Cookie 和 Token 都是"证明身份"，它们的工作方式有什么本质区别？为什么现代 API 更倾向用 Token？）

### 知识点 5：参数传递（token 关联）+ 请求前脚本

【课程原话/定义】
参数传递：登录接口获取 token，传递到其他接口的请求头。LiteMall 登录接口：`POST http://litemall.hogwarts.ceshiren.com/wx/auth/login`，JSON 参数 `{"username":"user123","password":"user123"}`。

登录接口返回的完整响应结构（token 在 data 下）：
```json
{
    "errno": 0,
    "data": {
        "userInfo": { "nickName": "user123", "avatarUrl": "" },
        "token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9..."
    },
    "errmsg": "成功"
}
```

第一步：在登录接口的 Tests 里提取 token 并存入测试集变量：
```javascript
var jsonData = pm.response.json();          // 获取响应 json 对象
var token = jsonData.data.token;            // 从 data 里提取 token
pm.collectionVariables.set("token", token); // 存为测试集变量
```

第二步：设置鉴权。进入搜索冒烟用例，Authorization 选 API Key，key 填 `X-Litemall-Token`，value 填 `{{token}}`（引用测试集变量），并删掉请求头里原来写死的 `X-Litemall-Token`。send 后请求头里会自动带上 `X-Litemall-Token: <token 值>`。

第三步（更优）：请求前脚本（Pre-request Script）里发登录请求并保存 token，让用例自包含：
```javascript
const loginRequest = {
    url: 'http://litemall.hogwarts.ceshiren.com/wx/auth/login',
    method: "POST",
    header: 'Content-Type: application/json',
    body: { mode: 'raw', raw: JSON.stringify({'username': 'user123', "password": "user123"}) }
};
pm.sendRequest(loginRequest, function (err, response) {
    if (err) {
        console.log(err);               // 调试：打印错误
    } else {
        console.log(response.json());   // 调试：console 面板确认返回结构
        pm.collectionVariables.set("token", response.json().data.token);
    }
});
```
调试技巧：打开 console 面板，运行测试集，即可看到登录接口返回的完整 JSON，确认 `data.token` 就是要提取的值。

【为什么？】
为什么要做"token 关联"？因为接口测试不是单接口——是"登录 → 拿 token → 带 token 调业务接口"的链路。token 是登录接口的动态产物，不能写死（会过期），必须"提取 → 存变量 → 复用"。放在 Tests 里是"请求后提取"，放在 Pre-request Script 里是"每次请求前先登录再拿 token"，后者能让用例**自包含**——不依赖你先手动跑一次登录。这就是接口自动化里"接口间数据关联"的核心技巧。

【必须掌握】
- token 关联三步：登录拿 token → `pm.collectionVariables.set` 存变量 → 其他接口 `{{token}}` 引用
- 提取 token：`pm.response.json().data.token`
- 设置鉴权：API Key + `X-Litemall-Token` + `{{token}}`
- Pre-request Script 里用 `pm.sendRequest` 先登录，让用例自包含
- token 是动态产物，不能写死（会过期）

【企业场景】
你在公司做接口自动化，把"登录拿 token"放到 Collection 的 Pre-request Script 里，这样每次跑测试集都自动先登录、拿到最新 token，再带着 token 调业务接口。token 过期了也不用改用例——因为它每次都是现取的。这就是"自包含"的接口自动化用例。

【面试考察】
面试官："接口测试中，怎么把登录接口的 token 传给其他接口？"

参考回答框架：
1. 登录接口返回 token，在 Tests 里用 `pm.collectionVariables.set("token", ...)` 提取保存
2. 其他接口在请求头/鉴权里用 `{{token}}` 引用
3. 更优：在 Collection 的 Pre-request Script 里用 pm.sendRequest 自动登录
4. 这样 token 每次现取，不过期、用例自包含

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| token 写死成固定值 | token 会过期，应动态提取 |
| 只跑业务接口不先登录 | 没 token 鉴权失败（401） |
| 提取 token 时路径写错 | 要看清响应结构，是 `data.token` 还是别的层级 |

【我的理解】
> （为什么 token 不能写死？"放在 Tests 里提取"和"放在 Pre-request Script 里登录"有什么区别？哪种更能让用例"自包含"？）

### 知识点 6：测试集导入导出与导出代码

【课程原话/定义】
测试集导入导出：测试集既可以导出也可以导入。导出：测试集更多按钮（⋯）→ 选择 Export → 保持默认选择 → 点 Export 按钮，把测试集导出为 json 格式数据。使用时直接 Import 导入该 json 即可复用。

导出代码：接口页面右侧边栏 `</>` 按钮 → 进入 code 页面 → 选择脚本语言和类库，把 Postman 设置转为自动化代码。

【为什么？】
为什么要"导出代码"？因为 Postman 适合调试和轻量回归，但长期自动化还是要落到代码（pytest/requests）里——能进 CI、能版本管理、能自由扩展。`</>` 导出代码就是"从手动到自动化"的桥：你在 Postman 里调通的请求，一键转成 Python/Java 代码，作为自动化脚本的起点。测试集导出 json 则是团队协作/备份的手段。

【必须掌握】
- Collection 可 Export/Import（json 格式）
- 导出代码：`</>` 按钮 → 选语言（Python/Java 等）和类库（requests/http.client 等）
- 导出代码是"手动 → 自动化"的桥，作为 pytest 脚本起点
- 测试集 json 用于团队分享和备份

【企业场景】
你在公司用 Postman 调通了一套接口后，点击 `</>` 把登录+搜索导出成 Python（requests）代码，然后在这个基础上改成 pytest 用例、加参数化、加断言，进 CI 跑回归。Postman 负责"探索和调试"，代码负责"长期自动化"，两者衔接的关键就是导出代码。

【面试考察】
面试官："Postman 调通后，怎么转成自动化脚本？"

参考回答框架：
1. 点 `</>` 导出代码，选语言和类库（如 Python + requests）
2. 得到可运行的代码片段
3. 在此基础上改造：封装成 pytest 用例、加断言、加数据驱动
4. 集成进 CI，实现长期自动化回归

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 认为导出代码就是完整自动化 | 导出的只是"请求代码"，还要自己加断言/参数化/框架 |
| 测试集只存本地不导出备份 | 导出 json 便于分享和备份，防止丢失 |
| 导出代码选错类库 | 不同类库代码风格不同，选团队统一的（如 requests） |

【我的理解】
> （为什么说 Postman 的 `</>` 导出代码是"手动 → 自动化"的桥，而不是终点？导出的代码离真正的自动化还差什么？）
