## 一、抓包原理与应用场景

### 知识点 1：抓包原理（中间人）

【课程原话/定义】
没有代理工具时，客户端直接向服务端发起请求，服务端把响应数据返回给客户端。有了 Charles，就相当于在客户端和服务端之间加了一个**中间人**——客户端的请求先发到 Charles，Charles 再转发到服务端；服务端的响应也先发到 Charles，再由 Charles 发回客户端。

【为什么？】
为什么"中间人"能抓到包？关键在"流量经过我"。只要请求和响应都从 Charles 这"过一道"，Charles 就能记录、查看、甚至篡改这些数据。这是所有抓包工具（Charles/Fiddler/mitmproxy）的共性原理。理解这个模型，你就理解了抓包工具能做的一切：看包（记录）、改包（篡改）、重发包（转发）、断点（拦截）——都是"中间人"这个位置的延伸能力。

【必须掌握】
- 无代理：客户端 ↔ 服务端 直连
- 有代理：客户端 → Charles → 服务端（双向都经过 Charles）
- Charles 是"中间人"，所以能看、能改、能重发
- 这是抓包、改包、断点、mock 的共同原理基础

【企业场景】
你在公司测 App 接口时，先把 Charles 设成手机代理，App 的所有流量就都"路过"Charles。你看到的每个请求，本质都是"App → Charles → 服务器"这条链上的数据。理解了这条链，你就知道为什么 Charles 能同时看到请求（出去的数据）和响应（回来的数据）。

【面试考察】
面试官："说说抓包工具的工作原理。"

参考回答框架：
1. 抓包工具把自己设为代理，插在客户端和服务端之间
2. 客户端请求先发到工具，工具转发给服务端
3. 服务端响应也先到工具，工具再转回客户端
4. 因为流量经过工具，所以能记录、查看、修改、重发

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 认为抓包工具"破解了加密" | 它没有破解，而是用证书做中间人，两边各自加密 |
| 认为抓包只发生在"请求"方向 | 响应也会经过工具，所以能同时看请求和响应 |
| 把"代理"理解成"拦截阻断" | 代理是"转发 + 记录"，正常情况不阻断（除非设断点） |

【我的理解】
> （用自己的话画出"客户端 → Charles → 服务端"的链路，并说明：为什么 Charles 能"改包"？改包改的是哪个方向的数据？）

### 知识点 2：常用应用场景

【课程原话/定义】
常用应用场景：
1. **移动端接口测试**：查看发送请求的 url、携带的参数是否正确
2. **分析 bug**：遇到页面展示错误的问题，看接口请求数据是否正确、返回的数据是否正确
3. **解决传参错误问题**：前端界面发的请求能成功，但脚本/Postman 发的请求失败，大多是因为缺少必要参数——前端会自动加上一些符合要求的请求头（user-agent、host、cookie 等），自己发的时候漏掉了
4. **mock 测试**：对不容易构造、不容易获取的对象，用虚拟对象替代，通过代理工具完成数据的篡改和构造

【为什么？】
这四种场景其实是一条"排错链"：页面错了 → 抓包看接口传参和返回对不对（分析 bug）→ 如果是"前端能过、脚本不能过"，抓包对比前端请求和脚本请求的差异（缺了哪个 header）→ 需要隔离外部依赖时用 mock。抓包不是"看个热闹"，而是**还原真相**：接口到底发了什么、返回了什么、和我脚本发的差在哪。

【必须掌握】
- 移动端接口测试：抓包看真实 url + 参数是否正确
- 分析 bug：页面错了，先抓包看接口请求/响应，定位是"传错"还是"返回错"
- 传参错误排查：前端能过、工具失败 → 对比请求头，多半漏了 user-agent/host/cookie
- mock 测试：用代理工具篡改/构造数据，模拟难获取的对象

【企业场景】
你在公司遇到一个典型问题：浏览器页面功能正常，但你写的自动化脚本调同一个接口总是失败。你用 Charles 抓前端页面的请求，和脚本的请求一对比，发现前端多带了一个 `X-Client-Type` 头、你的脚本没带——补上就通了。这就是"抓包对比"在传参排查里的实战价值。

【面试考察】
面试官："接口测试中，脚本请求失败但前端正常，你怎么排查？"

参考回答框架：
1. 用抓包工具抓前端的真实请求，记录完整的 url + 请求头 + 参数
2. 对比脚本请求和前端请求，找出差异
3. 通常是漏了必要的请求头（user-agent/host/cookie/token）
4. 补齐差异参数后重试

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 脚本失败就怀疑接口坏了 | 先对比前端请求，多半是脚本漏了 header/参数 |
| 分析 bug 只看页面报错信息 | 抓包看接口请求和返回，才能定位是前端还是后端问题 |
| 把 mock 理解成"造假数据骗测试" | mock 是隔离外部依赖、构造难获取数据，是正规测试手段 |

【我的理解】
> （"前端能过、脚本不能过"最常见的根因是什么？为什么抓包对比是定位这个问题的最高效手段？）

## 二、接口抓包分析实战

### 知识点 3：过滤、重发、修改请求、断点

【课程原话/定义】
接口抓包分析实战的四个操作：
1. **过滤**：Filter → Focus / Recording Settings → Include
2. **重发**：右键 → Repeat（简单重发）；右键 → Repeat Advanced（简单压力）
3. **修改请求**：右键 → Compose（选择接口 → 点击小钢笔图标）
4. **断点（BreakPoint）**：右键 → Breakpoint；Proxy → Breakpoint settings 设置断点；确定是请求断点还是响应断点；重新发送请求 → 进入断点修改状态 → 修改内容 → 点击 Execute

【为什么？】
这四个操作是抓包工具的"实战四件套"，各有用途：
- **过滤**：抓包时流量太多，先 Focus 到目标域名，避免大海捞针
- **重发**：Repeat 快速复现一个请求；Repeat Advanced 设置并发/次数，做简单压力测试
- **修改请求（Compose）**：改参数再发，验证边界/异常，不用重新在 App 里操作
- **断点**：拦截请求或响应、当场改数据再放行——这是"篡改数据做 mock"的核心手段（改响应 = 伪造服务端返回）

【必须掌握】
- 过滤：Filter/Focus/Recording Settings→Include 聚焦目标请求
- 重发：Repeat（单次复现）、Repeat Advanced（并发/次数，简单压力）
- 修改请求：Compose（小钢笔）改参数后重发
- 断点：Breakpoint 拦截请求或响应，修改后 Execute 放行
- 请求断点改"发出去的数据"，响应断点改"返回来的数据"

【企业场景】
你在公司测一个下单接口：想验证"金额传 0"会怎样，不用反复在 App 里操作，直接对抓到的下单请求右键 Compose，把金额改成 0 再发；想模拟"库存为 0"的场景，对响应设断点，把返回的库存字段改成 0 再放行。这就是改请求（Compose）和改响应（断点）的典型分工。

【面试考察】
面试官："Charles 怎么模拟服务端返回特定数据（比如让接口返回失败）？"

参考回答框架：
1. 用断点（Breakpoint）拦截响应
2. 在断点里修改响应体/状态码
3. Execute 放行，客户端就收到被篡改的响应
4. 这是"响应断点改返回"；请求断点则是改"发出去的数据"

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 请求断点和响应断点分不清 | 请求断点改"发出去的参数"，响应断点改"返回来的数据" |
| Repeat Advanced 当成功能测试 | 它是"简单压力"（并发/次数），不是完整性能测试 |
| 断点后忘了 Execute | 请求会一直卡在断点状态，客户端收不到响应 |

【扩展知识】
"改响应"是实现轻量 mock 的常用手段：拦截响应 → 把返回字段改成你想要的值 → 放行，客户端看到的就是"伪造"的数据。相比专门的 mock 工具，这种方式更快，但只适合临时验证，不适合大规模 mock 管理。

【我的理解】
> （"请求断点"和"响应断点"分别能改什么？如果要模拟"服务器返回 500 错误"，应该用哪种断点、改哪里？）
