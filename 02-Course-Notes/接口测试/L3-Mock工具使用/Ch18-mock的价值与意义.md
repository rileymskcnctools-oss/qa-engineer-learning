## 一、什么是 Mock

### 知识点 1：Mock 的概念

【课程原话/定义】
做测试的过程中，对于一些**不容易构造、不容易获取**的对象，用一个虚拟的对象来替代它，达到相同的效果，这个虚拟对象就是 Mock。当后端某些接口还不成熟、依赖的接口不稳定或是第三方接口、构造依赖数据太复杂时，可以用 Mock 先虚拟这些接口返回，代替真正的接口返回，从而提高工作效率。

【为什么？】
为什么需要 Mock？核心是"**解除依赖**"——被测对象往往依赖外部服务（第三方支付、短信、还没开发好的后端接口），这些依赖要么不可控、要么要花钱、要么还没开发完。Mock 用一个"假替身"顶替这些依赖，让你能独立、快速、重复地测试被测对象，不被外部因素阻塞。这也解释了为什么 Mock 是接口测试的必备进阶技能。

【必须掌握】
- Mock = 用虚拟对象替代"不容易构造/获取"的真实对象
- 典型场景：后端接口未成熟、依赖接口不稳定、第三方接口、构造数据太复杂
- 核心价值：解除对外部依赖的阻塞，提高测试效率
- Mock 是"替身"，不是"造假数据骗测试"，是正规测试手段

【企业场景】
你在公司测一个"下单"功能，它依赖支付接口（第三方）、短信接口（第三方）、库存服务（还没开发完）。如果等这些都就绪，测试根本没法开展。你用 Mock 把这些依赖的返回都模拟出来（支付成功/失败、短信发送成功、库存充足），就能独立、快速地测下单逻辑。这就是 Mock 在真实工作中的价值——"不等别人，自己先测"。

【面试考察】
面试官："什么是 Mock？为什么要用 Mock？"

参考回答框架：
1. Mock 是用虚拟对象替代不容易构造/获取的依赖对象
2. 场景：后端未就绪、第三方接口、依赖不稳定、数据构造复杂
3. 价值：解除依赖阻塞、提高测试效率、节省联调成本
4. Mock 让测试可以"不依赖外部、独立、重复"地开展

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| Mock 是"造假数据骗测试" | Mock 是模拟依赖的替身，是正规测试手段 |
| Mock 只能替代第三方接口 | 还能替代未开发完的后端、硬件设备、复杂数据 |
| Mock 后就不用测真实接口了 | Mock 用于隔离依赖，真实联调测试仍要做 |

【我的理解】
> （"Mock 是替身，不是造假"——用自己的话解释这句话。为什么说 Mock 反而让测试"更真实"（更聚焦被测对象本身）？）

### 知识点 2：Mock 测试的场景与价值

【课程原话/定义】
Mock 测试的场景：**前后端数据交互、第三方系统数据交互、硬件设备解耦**。
Mock 测试的价值与意义：**不依赖第三方数据、节省工作量、节省联调**。

【为什么？**
为什么 Mock 的三大场景对应三大价值？因为这三类依赖是测试最常见的"阻塞源"：
- 前后端交互 → 前端要等后端接口（Mock 让前后端并行开发）
- 第三方交互 → 第三方不可控/收费/不稳定（Mock 隔离第三方）
- 硬件设备 → 设备昂贵/难获取（Mock 解耦硬件）

三大价值正好一一对应：不依赖第三方数据（第三方场景）、节省工作量（前后端并行）、节省联调（不用等所有人就绪再联调）。

【必须掌握】
- 三大场景：前后端数据交互、第三方系统交互、硬件设备解耦
- 三大价值：不依赖第三方数据、节省工作量、节省联调
- Mock 的核心目标：让测试不被外部依赖阻塞，可以并行、独立开展

【企业场景】
你在公司遇到三类典型阻塞：① 前端催着要联调，但后端接口还没写好 → Mock 后端返回，前端先测；② 测试要调第三方支付，但第三方要真实扣款、收费 → Mock 支付返回；③ 测试要驱动一台几万块的硬件设备，设备还没到货 → Mock 设备返回数据。Mock 解决了这三类"等别人"的阻塞，让你能按自己的节奏推进测试。

【面试考察】
面试官："什么场景下会用 Mock？Mock 能带来什么价值？"

参考回答框架：
1. 场景：前后端并行开发、第三方系统依赖、硬件设备解耦
2. 价值：不依赖第三方数据、节省工作量、节省联调时间
3. 本质：解除对外部依赖的阻塞，让测试独立、并行、可重复

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 认为 Mock 只用于接口测试 | Mock 也用于前端、硬件、第三方等各类依赖隔离 |
| Mock 的价值只是"省时间" | 更深层是"解除阻塞 + 并行开发 + 可重复测试" |
| 前后端交互只能用真实联调 | 前端先 Mock 数据画页面，和后端并行开发 |

【我的理解】
> （这三大场景，哪一个在你之前的工作/学习中已经遇到过？当时没有 Mock 你是怎么处理的？）

## 二、Mock 核心要素

### 知识点 3：Mock 的两个核心要素（匹配规则 + 模拟响应）

【课程原话/定义】
Mock 核心要素：
1. **匹配规则**：确定要对哪个接口、哪些数据进行修改（哪里的数据要修改）
2. **模拟响应**：接口符合匹配规则后，把匹配上的内容做篡改（篡改成什么样子，根据测试用例设计，如等价类/边界值设计不同展示内容）

【为什么？**
为什么 Mock 就这两件事？因为 Mock 的本质是"**找到要改的 + 改成什么样**"：
- 匹配规则 = "找到要改的"：哪个 URL、哪个字段、什么条件下触发（类似编程里的 if 条件）
- 模拟响应 = "改成什么样"：把匹配到的数据篡改成测试需要的值（等价类/边界值决定的期望数据）

理解了这两要素，任何 Mock 工具（Charles 的 Rewrite/MapLocal、mitmproxy 的脚本、Wiremock 的规则）本质都是"定义匹配规则 + 定义模拟响应"，只是配置方式不同。

【必须掌握】
- 匹配规则：确定对哪个接口/哪些数据做修改
- 模拟响应：匹配后把内容篡改成测试需要的值
- 模拟响应要根据测试用例（等价类/边界值）设计
- 任何 Mock 工具本质都是"匹配规则 + 模拟响应"两件事

【企业场景】
你在公司用 Charles 做 Mock：匹配规则 = 指定某个接口 URL（如雪球行情接口），模拟响应 = 把返回里的"股票名称"字段改成测试要的值。要测"超长名称"就把名称改成 200 字超长串（边界值），要测"空名称"就改成空。这就是"匹配规则 + 模拟响应"在实操中的对应。

【面试考察】
面试官："Mock 的核心要素是什么？"

参考回答框架：
1. 匹配规则：确定对哪个接口、哪些字段做修改
2. 模拟响应：匹配后把内容篡改成什么
3. 模拟响应要根据测试用例设计（等价类/边界值）
4. 任何 Mock 工具都围绕这两件事展开

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 只关注"改成什么"，忽略"匹配哪个" | 匹配规则不准确会误改其他接口的数据 |
| 模拟响应随意造数据 | 应根据等价类/边界值设计测试数据 |
| 认为 Mock 工具千差万别 | 本质都是"匹配规则 + 模拟响应"，只是配置方式不同 |

【我的理解】
> （"匹配规则 + 模拟响应"——如果匹配规则写得太宽（比如匹配所有请求），会发生什么？为什么匹配规则要精确？）
