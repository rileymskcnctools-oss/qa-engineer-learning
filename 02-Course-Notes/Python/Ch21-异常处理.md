## 一、异常是什么

### 知识点 1：异常 vs 语法错误

【课程原话/定义】
语法错误是代码写错了格式，程序根本跑不起来（如少写冒号、括号不匹配）。异常是语法正确但在**运行时**触发的错误（如除以零、文件不存在、类型不匹配）。大多数异常不处理会导致程序中断。

【为什么？】
区分语法错误和异常很重要：语法错误→改代码就能解决；异常→改代码不一定能解决，因为异常往往依赖外部条件（用户输入、文件存在性、网络状态）。后者需要程序**在运行时**自己处理。

Python 不像 Java 那样强制你处理所有可能的异常，这是双刃剑：好处是代码简洁，坏处是新手容易漏掉异常处理，导致生产环境崩溃。

【必须掌握】
- 语法错误 = 写错了（程序无法启动）
- 异常 = 运行中出错（程序可启动但在执行中出问题）
- 常见异常类型见下文

> （用自己的话区分语法错误和异常，各举一个例子）

## 二、try-except 基本用法

### 知识点 2：try-except 捕获异常

【课程原话/定义】
`try-except` 用于检测 try 块中的异常，由 except 捕获并处理，防止程序中断。

```python
file = open("data.txt", "r")
try:
    file.write("写入的数据")    # 只读模式打开，写入会报 IOError
except IOError as err:
    print("文件不能写入", err)  # 异常被捕获，程序不会崩溃
file.close()
```

【为什么？】
try-except 的设计哲学是"你预料到这段代码可能出错，你告诉 Python 出错了怎么办"。Python 不会自动帮你处理异常——你必须显式地圈出"危险区"并给出"应急方案"。

注意 try 块中的代码：一旦某行抛异常，**该行之后的 try 块代码不再执行**，直接跳到 except。这意味着 try 块应该只包住"可能出错的代码"，而不是整个函数。包得太大有两个问题：①你不知道具体哪行出错 ②正常代码被异常"连坐"跳过。

【必须掌握】
- `try:` 包住可能出错的代码
- `except 异常类型 as 变量:` 捕获并处理
- try 块中报错行之后的代码不会执行
- try 块越小越好——只包真正可能出错的部分

【企业场景】
你在做接口自动化测试，发送请求时可能遇到网络超时：
```python
import requests

def call_api(url):
    try:
        response = requests.get(url, timeout=5)
        return response.json()
    except requests.Timeout:
        print(f"请求超时: {url}")
        return None    # 不崩溃，返回 None 让调用者决定怎么处理
```
如果不捕获 Timeout，一条请求超时整个测试批量就崩了。

【面试考察】
面试官："try 块中某行代码抛异常后，后面的代码还会执行吗？"

参考回答框架：
1. 不会执行——立即跳到 except
2. 因此 try 块应该只包"有风险"的代码
3. 无风险的代码放在 try 外面或 else 子句中

【易错点】

| 常见错误 | 错误原因 | 正确做法 |
|---------|---------|---------|
| try 块包了整个函数 | 异常导致无辜代码被跳过 | 只包可能出错的那几行 |
| 裸 `except:` 不加类型 | 连 KeyboardInterrupt（Ctrl+C）都捕获 | 至少用 `except Exception` |
| except 后 pass | 吞掉异常，bug 被隐藏 | 至少打印日志或记录异常 |

【我的理解】
> （手写一个 try-except：打开不存在的文件，捕获 FileNotFoundError，打印友好提示。对比不加异常处理的结果）

### 知识点 3：捕获多个异常

【课程原话/定义】
一段代码可能抛出多种异常，用多个 `except` 分别捕获。`Exception` 是所有内置异常的基类，能捕获大部分异常，**必须放在最后**，否则其他 except 永远不会被执行。

```python
try:
    # file.write("写入的数据")     # IOError
    # print(a)                     # NameError
    # print(3 / 0)                 # ZeroDivisionError
    # print([][10])                # IndexError
    print("hello" + 100)           # TypeError
except IOError as err:
    print("文件不能写入", err)
except NameError:
    print("标识符没有定义")
except ZeroDivisionError:
    print("除数不能为0")
except IndexError:
    print("下标越界了")
except Exception:
    print("程序运行出错，请检查代码")   # 兜底，放最后
```

【为什么？】
Python 按 except 的书写顺序从上到下匹配异常。`Exception` 是大多数异常的父类，如果在第一个 except 就写 `except Exception`，后面的 `except IOError` 永远不会被触发——因为 IOError 也是 Exception 的子类，已经被第一个捕获了。

这就像安检：先过具体检查（金属探测），再过通用检查（全身扫描）。反过来的话具体检查就废了。

【必须掌握】
- 多个 except 按"具体→通用"顺序排列
- `except Exception` 是兜底，必须放最后
- 可以用元组一次捕获多种：`except (IOError, OSError)`
- 不捕获的异常会继续向上传播

【企业场景】
你的文件处理函数可能遇到多种问题，分别处理：
```python
def read_config(path):
    try:
        with open(path, "r") as f:
            return f.read()
    except FileNotFoundError:
        print(f"配置文件不存在: {path}，使用默认配置")
        return DEFAULT_CONFIG
    except PermissionError:
        print(f"无权限读取: {path}")
        raise   # 权限问题不能忽略，向上抛出
    except Exception as e:
        print(f"未知错误: {e}")
        raise
```
对不同异常采取不同策略：不存在→兜底；无权限→向上抛（让上层决定）；未知→记录日志后也向上抛。

【面试考察】
面试官："多个 except 的捕获顺序有什么讲究？为什么？"

参考回答框架：
1. 顺序：具体异常在前，通用异常在后
2. Python 从上到下匹配，匹配到一个就停止
3. Exception 放最后做兜底
4. 反例：Exception 放第一个，后面所有 except 永远不执行

【易错点】

| 常见错误 | 错误原因 | 正确做法 |
|---------|---------|---------|
| Exception 写在第一个 except | 后面具体异常永远不会捕获 | Exception 永远放最后 |
| 用多个 except 但行为一样 | 代码冗余 | 用元组合并：`except (A, B, C)` |
| 未知异常被 Exception 兜底后 pass | 异常被静默吞掉 | 至少记录日志 |

【我的理解】
> （写一个 try 块，故意让它可能触发 3 种不同异常。按正确顺序写多个 except，分别验证每种异常是否能正确捕获）

### 知识点 4：else 子句

【课程原话/定义】
`else` 在 try 块**没有发生任何异常**时执行。用于处理"一切正常"的后续逻辑。

```python
try:
    n = input("请输入一个数字:")
    num = int(n)
except Exception:
    print("元素无法转换为数字")
else:
    print("转换后成功", num)    # 只有转换成功才执行
```

【为什么？】
`else` 解决了一个微妙的问题：把"正常逻辑"放在 try 块里还是 try 块外？

如果放在 try 块里：正常逻辑如果抛异常，会被当成"预期内的异常"捕获——但你可能不想捕获它的异常。
如果放在 try 块外：如果 try 块里的异常没被捕获，正常逻辑也会执行——但此时前面已经失败了。

`else` 完美解决：只有 try 块**完全成功**，才执行 else。这样正常逻辑的异常不会被误捕获，也不会在前置失败时执行。

【必须掌握】
- else 在 try 无异常时执行
- else 中的异常不会被前面的 except 捕获
- 适用场景：try 做校验，else 做后续处理
- else 是可选的

【企业场景】
接口测试中，请求成功后才做断言：
```python
try:
    response = requests.get(url, timeout=5)
    response.raise_for_status()       # 非 200 抛异常
except requests.Timeout:
    print("请求超时")
except requests.HTTPError:
    print(f"HTTP 错误: {response.status_code}")
else:
    # 只有请求成功才做断言
    data = response.json()
    assert data["status"] == "ok"
```
把断言放在 else 里，确保只在请求成功时执行——超时或 HTTP 错误时直接跳过断言。

【面试考察】
面试官："try-except 中的 else 什么时候执行？有什么用？"

参考回答框架：
1. else 在 try 块无异常时执行
2. 作用：分离正常逻辑和异常处理
3. 好处：else 中的异常不会被 try 的 except 误捕获
4. 对比：把正常逻辑放 try 里 vs 放 else 里的区别

【易错点】

| 常见错误 | 错误原因 | 正确做法 |
|---------|---------|---------|
| 把正常逻辑全放 try 里 | 不清楚 else 的作用 | 危险代码放 try，正常后续放 else |
| else 中又包了一层 try | 过度嵌套 | else 本身就表示"一切正常"，不需要再套 |

【我的理解】
> （写一个 try-except-else 的完整例子：输入转数字，成功输出平方，失败提示。对比把正常逻辑放 try 里 vs else 里的不同）

### 知识点 5：finally 子句

【课程原话/定义】
`finally` 无论是否发生异常都执行，常用于清理工作（关闭文件、释放资源）。

```python
try:
    file = open("data.txt", "r")
    # file.write("A")    # 可能报异常
except Exception:
    print("文件操作报错")
finally:
    print("文件已关闭")
    file.close()          # 无论是否异常，确保文件关闭
```

【为什么？】
`finally` 是"承诺制"——无论前面发生什么（正常、异常、return、break），finally 块一定会执行。这解决了资源泄漏的经典问题：你打开了文件/连接/驱动，中间抛异常导致 close() 被跳过，资源永远不释放。

**即使 try 中有 return，finally 也会在 return 之前执行。** 这是面试高频题。

但 `with` 语句（上下文管理器）可以替代大部分 finally 的场景——`with open(...)` 自动帮你关闭文件。finally 现在更多用于自定义资源的清理、测试环境的 tearDown。

【必须掌握】
- finally 无论是否异常都执行
- 即使 try 中有 return，finally 也执行（在 return 之前）
- 主要用于释放资源：文件、网络连接、数据库连接、浏览器驱动
- 可以利用 `with` 语句减少 finally 的使用

【企业场景】
UI 自动化测试中，确保浏览器驱动一定关闭：
```python
from selenium import webdriver

driver = webdriver.Chrome()
try:
    driver.get("https://example.com")
    element = driver.find_element("id", "login-btn")
    element.click()
except Exception as e:
    print(f"测试失败: {e}")
finally:
    driver.quit()   # 无论测试成败，一定关闭浏览器
```
如果不用 finally，测试失败时浏览器窗口不关闭，跑 50 个用例就开 50 个浏览器窗口。

【面试考察】
面试官："try 里有 return，finally 还执行吗？执行顺序是怎样的？"

参考回答框架：
1. 执行！finally 始终执行
2. 流程：try 中准备 return → 先执行 finally → 再真正 return
3. 如果 finally 中也有 return，会覆盖 try 的 return（不推荐）
4. 这是确保资源释放的最后一道防线

【易错点】

| 常见错误 | 错误原因 | 正确做法 |
|---------|---------|---------|
| 以为 try 中 return 后 finally 不执行 | 不理解 Python 的退出机制 | finally 就是"无论如何都执行" |
| 在 finally 中写 return | 会覆盖 try 的返回值和异常 | finally 只做清理，不做业务逻辑 |
| 用 finally 替代 with 语句 | 代码冗长且容易出错 | 文件操作用 `with open(...)` |

【我的理解】
