## 一、读懂报错信息

### 知识点 1：报错信息的 5 个关键部分

【课程原话/定义】
程序报错后，错误信息包含 5 个关键部分：

| 序号 | 内容 | 说明 |
|------|------|------|
| 1 | 错误所在文件 | 哪个 `.py` 文件出的错 |
| 2 | 错误所在行号 | 第几行触发 |
| 3 | 错误代码 | 出错的那一行代码内容 |
| 4 | 错误类型 | 如 `TypeError`、`NameError`、`ValueError` |
| 5 | 错误原因描述 | 人类可读的解释 |

**阅读 Traceback 的正确方式：从下往上看。** 最后一行是最终错误，往上是调用链。

```
Traceback (most recent call last):
  File "main.py", line 15, in <module>       ← 调用链：谁调用了出错函数
    outputData(n, msg)
  File "main.py", line 9, in outputData      ← 实际出错位置
    for i in range(n):
TypeError: 'str' object cannot be interpreted as an integer   ← 错误类型+原因
```

【为什么？】
报错信息是 Python 给你的诊断报告，不是惩罚通知。初学者看到一大段红色就慌，但 Traceback 是帮你省时间的——它告诉你"在哪"、"为什么"、"谁导致的"。

Traceback 从上往下是调用栈（调用链），从下往上是出错路径。从下往上看的意思是：先看最后一行（错误类型+原因），再看上面找到自己写的代码行。这样不需要读完整个 Traceback 就能定位。

【必须掌握】
- 5 个关键部分：文件、行号、代码、错误类型、描述
- 从下往上看 Traceback：先看错误类型，再溯源
- 不要只看最后一行——有时根源在调用链上方
- 常见错误类型：`TypeError`（类型错）、`NameError`（变量未定义）、`ValueError`（值不合法）、`IndexError`（索引越界）、`KeyError`（键不存在）

【企业场景】
你在跑自动化测试，控制台输出了一大段红色报错。新手 panic，老手直接翻到最下面看 `AssertionError: expected 200, got 500`——定位到：接口返回了 500。

然后再往上看 Traceback，找到是哪个测试用例的哪一行请求触发的。整个过程不超过 10 秒。

【面试考察】
面试官："Python 报错后你怎么定位问题？Traceback 怎么看？"

参考回答框架：
1. 先看最后一行：错误类型 + 描述（知道"出了什么错"）
2. 往上看找到自己代码的行号（知道"在哪出的错"）
3. 如果根源不在这一行，继续往上看调用链（知道"谁传的错误数据"）
4. 常见错误类型应该能一眼认出

【易错点】

| 常见错误 | 错误原因 | 正确做法 |
|---------|---------|---------|
| 只看报错行，不看调用链 | 以为报错行就是根源 | 往 Traceback 上方看调用链，找到自己的代码 |
| 忽略错误类型描述 | 只盯着行号，不看错误原因 | 先读 Type + 描述，再找位置 |
| Traceback 太长就放弃 | 觉得看不懂就不看了 | 只找自己写的文件名和行号，库文件的行跳过 |

【我的理解】
> （做一个小练习：故意写一段会报错的代码，然后对照 Traceback 找出 5 个要素。截图或抄写 Traceback 内容）

### 知识点 2：报错行 ≠ 根源行

【课程原话/定义】
有时报错信息指向的行并不是真正的 bug 位置。需要结合 Traceback 的调用链和上下文逻辑分析真正的错误原因。

示例场景：
```python
def getInputData():
    n = input("请输入一个数字:")    # 根源！这里应该 int(input(...))
    msg = input("请输入一个数据:")
    return n, msg

def outputData(n, msg):
    for i in range(n):             # 报错这里！n 是字符串
        print(msg)
```
报错在第 7 行 `range(n)`，但真正的 bug 在第 2 行——`input()` 返回字符串，没有转成 int。

【为什么？】
Python 是动态类型语言，参数类型不匹配的错误通常不在"传参的时候"暴露，而在"真正使用的时候"暴露。`range("5")` 报错不代表 range 函数有问题，而是调用者传错了类型。

这就像你在餐厅点菜，服务员把你说的"鱼香肉丝"写成了"鱼香rose"，厨师做不出来时锅在厨师头上，但问题根源在前台。Traceback 告诉你"厨师做不出来"，你需要溯源到"谁点的菜"。

【必须掌握】
- 报错行只是症状的位置，不一定是病因的位置
- 溯源方法：沿 Traceback 往上找自己的代码 → 检查传入的数据类型和值
- 类型错误（TypeError、ValueError）尤其容易"报在其他行"
- 诀窍：看到 `range(x)` 报类型错误 → 立刻检查 x 是谁传的、有没有做类型转换

【企业场景】
你在测试中遇到：
```python
# test_utils.py
def divide(a, b):
    return a / b       # 报错：ZeroDivisionError

# test_case.py
result = divide(100, 0)   # 根源在这！有人传了 0
```
报错在 divide 函数，但 bug 在调用者——测试数据里有个分母为 0。修复不是改 divide 函数（加 try/except 掩盖），而是修正测试数据源头。

【面试考察】
面试官："Traceback 指向的代码行一定是 bug 吗？举一个不是的例子。"

参考回答框架：
1. 不一定，报错行只是"症状位置"
2. 典型例子：函数内 `range(str_param)` 报 TypeError，但 str_param 是调用者传的
3. 解决方案：沿着 Traceback 找到你自己传参的行，修复类型转换

【易错点】

| 常见错误 | 错误原因 | 正确做法 |
|---------|---------|---------|
| 在报错行改代码而不是在根源改 | 头痛医头 | 溯源调用链，在最上游修复 |
| 用 try-except 掩盖而不是修复 | 偷懒 | try-except 用于"预期内的可恢复错误"，不是掩盖 bug |

【我的理解】
> （复现课程中的例子：故意在 input 后不做 int 转换，观察 Traceback。然后修复，验证）

## 二、print 调试法

### 知识点 3：用 print 定位问题

【课程原话/定义】
在代码中插入 `print()` 语句输出中间状态，通过观察哪些 print 输出了、哪些没有，来定位错误发生的区间。

```python
def getInputData():
    print("input run")                      # 标记：进入函数
    n = input("请输入一个数字:")
    msg = input("请输入一个数据:")
    return n, msg

def outputData(n, msg):
    print("output run")                     # 标记：进入函数
    for i in range(n):
        print("output forin run")           # 标记：进入循环
        print(msg)
```
运行结果中 `output forin run` 没输出 → 错误在它之前、`output run` 之后 → 锁定 `for i in range(n)`。

【为什么？】
print 调试法是最古老也最通用的调试手段。它的核心思想是"二分定位"：在怀疑的代码段前后插 print，看程序执行到哪一步死的。

优势：不需要任何工具、任何 IDE，SSH 到服务器上也能用。
劣势：每次调试要改代码、跑完要删，效率低。而且 print 只能展示"值"，不能暂停、不能单步。

在企业里，print 调试是应急手段，PyCharm debug 是常规手段。但 print 有一项不可替代的优势——当你需要观察一个循环里变量的变化趋势时，打日志比一步步 debug 更快。

【必须掌握】
- 在关键位置插入 `print()` 检查程序是否执行到
- 通过"哪个 print 没输出"锁定错误区间
- 调试完必须删除或注释掉调试用的 print
- 更高阶的替代：`logging` 模块（可以控制级别，不用删除）

【企业场景】
你在远程服务器上跑定时任务，没有图形界面，没法用 PyCharm debug。任务偶尔崩溃，你加了 print 输出关键变量值：
```python
print(f"[DEBUG] processing item {idx}: {data}")
result = risky_operation(data)
print(f"[DEBUG] result: {result}")
```
第二天看日志，发现崩溃时 `data` 是 `None`，定位到数据源有空值。

【面试考察】
面试官："你平时怎么调试代码？print 和 IDE debug 各有什么优劣？"

参考回答框架：
1. print：简单通用，适合快速定位、远程环境；但需反复改代码、效率低
2. IDE debug：可以单步执行、查看所有变量、条件断点；但需要 IDE 支持
3. 日常用 debug，print 做补充

【易错点】

| 常见错误 | 错误原因 | 正确做法 |
|---------|---------|---------|
| 调试完忘记删 print | 代码里残留调试信息 | 调试完立刻搜 `print` 并删除 |
| 每个语句都加 print | 信息过载，反而难定位 | 只在你怀疑的关键节点插 print |
| 用 print 替代 logging | print 不能区分级别，不能关 | 生产环境用 logging 模块 |

【我的理解】
> （在你的代码中实践一次 print 调试：制造一个 bug，用 print 二分定位。记录你插了几个 print、定位用了多久）

## 三、PyCharm Debug 调试

### 知识点 4：断点

【课程原话/定义】
断点是在代码行号旁边点击添加的标记。debug 模式下程序运行到断点处会**暂停**，此时可以查看变量值、控制程序单步执行。

设置方法：在 PyCharm 中点击行号右侧空白区域，出现红色圆点即为断点。

【为什么？】
断点让你在"我怀疑这里有问题"的地方按下暂停键。没有断点的 debug 就像看视频没有暂停键——你只能看到最终结果，看不到中间过程。

好的断点策略：
- 在怀疑的代码段**开头**打一个，确认程序走到了这里
- 在关键变量**赋值后**打一个，查看值对不对
- 在条件分支**入口**打一个，确认走了哪个分支

【必须掌握】
- 在行号右侧点击添加/删除断点
- 断点 = 程序暂停点，只在 debug 模式生效
- 不打断点直接 debug = 程序跑完不停
- 可以打多个断点

【企业场景】
你的测试用例报错但不知道哪里出问题，在测试函数第一行打断点，debug 运行，然后一步步往下走，观察每个中间变量——发现某个接口返回的 JSON 结构和预期不一致。

【我的理解】
> （在 PyCharm 中打开一个 .py 文件，练习：添加断点、删除断点、批量查看所有断点）

### 知识点 5：Debug 控制按钮

【课程原话/定义】
程序在断点处暂停后，通过控制按钮决定下一步怎么执行：

| 按钮                      | 中文    | 作用                | 口诀             |
| ----------------------- | ----- | ----------------- | -------------- |
| **Step Over**           | 步过    | 执行当前行，不进入函数内部     | "这行函数我信任，直接过"  |
| **Step Into**           | 步入    | 进入当前行调用的函数内部      | "这函数是我写的，进去看看" |
| **Step Into My Code**   | 步入自定义 | 只进自己写的函数，不进系统/库函数 | "只进我的代码"       |
| **Step Out**            | 步出    | 跳出当前函数，回到调用处      | "这函数看完了，回去"    |
| **Run to Cursor**       | 跑到光标  | 直接执行到光标所在行暂停      | "中间的不想看，跳到这"   |
| **Resume Program**      | 继续    | 执行到下一个断点或程序结束     | "放行！"          |
| **Evaluate Expression** | 计算表达式 | 临时查看任意表达式的值       | "我想看看 n 的类型"   |

【为什么？】
这几个按钮是 PyCharm debug 的核心操作。搞混 Step Over 和 Step Into 是最常见的入门坑——看到函数就想 Step Into，结果进了 `print()`、`range()`、`len()` 等内置函数，里面全是 C 代码，浪费时间。

记住一条铁律：**自己的函数 Step Into，别人的函数 Step Over。**

Evaluate Expression 是被低估的神器。debug 时你想知道 `type(n)`、`len(data)`、`n + 5` 的结果——不需要改代码加 print，直接在 Evaluate 里输入表达式就能看到结果。这比 print 调试快一个数量级。

【必须掌握】
- Step Over：执行整行，不进函数（用于库函数、内置函数）
- Step Into：进入函数内部逐行执行（用于自己写的函数）
- Step Out：跳出当前函数回到调用处（"我看够了"）
- Run to Cursor：跳过中间代码，跳到目标行
- Resume：继续运行到下一个断点或结束
- Evaluate Expression：随时查看/计算表达式值

【企业场景】
调试一个复杂的测试流程：
1. 在 `run_test_suite()` 打第一个断点 → 确认参数正确传入
2. Step Over 跳过初始化 → 快速通过不关心的代码
3. `execute_case(case)` → Step Into → 进入业务逻辑逐行看
4. 发现一个循环跑了 100 次 → Run to Cursor 跳到循环后面
5. 查看返回值 → Evaluate Expression 输入 `result.status`

整个过程不用改一行代码、不用插一个 print。

【面试考察】
面试官："你用过 PyCharm 的 debug 功能吗？Step Over 和 Step Into 的区别？"

参考回答框架：
1. Step Over：把当前行当整体执行，不进入函数内部
2. Step Into：如果当前行有函数调用，进入函数内部逐行执行
3. 使用原则：自己写的函数用 Step Into，库函数用 Step Over
4. 补充：Evaluate Expression 是 debug 时看中间值的利器

【易错点】

| 常见错误 | 错误原因 | 正确做法 |
|---------|---------|---------|
| 看到函数就 Step Into | 进了 `print()` / `range()` 等内置函数 | 只进自己写的函数 |
| 不打断点直接 debug | 程序不停，不知道 debug 有啥用 | 先打至少一个断点 |
| 用 print 替代 debug 看中间变量 | 不知道 Evaluate Expression 功能 | debug 暂停时用 Evaluate 看任意表达式 |
| 忘记清理断点 | 残留断点影响后续调试 | 用 View Breakpoints 查看和清理 |

【我的理解】
> （实际在 PyCharm 中做一遍：打一个断点，debug 运行，依次尝试 Step Over、Step Into、Step Out、Evaluate Expression。描述每个按钮做了什么）
