## 一、标准的用例结构

### 知识点 1：手工用例的五要素

【课程原话/定义】
在自动化测试中，**自动化用例结构**指的是测试用例的组织方式，它确保测试脚本的**可读性、可维护性和可扩展性**。

标准的用例结构：

1. 用例标题
2. 前提条件
3. 用例步骤
4. 预期结果
5. 实际结果

课程示例（搜狗搜索功能）：

| 用例标题 | 类型 | 前提条件 | 用例步骤 | 预期结果 | 实际结果 |
|---------|------|---------|---------|---------|---------|
| 搜狗搜索功能 | 正例 | 进入搜狗首页 | 1. 输入搜索关键词<br>2. 按下回车键 | 1. 搜索成功<br>2. 搜索结果列表包含关键字 | （执行时填写） |

【为什么？】
这五要素不是"表格模板"，而是一条**可验证的逻辑链**：

```
前提条件（环境确定）→ 用例步骤（唯一变量）→ 预期结果（事先定义）
                                          ↕ 比对
                                        实际结果
```

缺任何一环，用例就失去判定能力：
- 缺**前提条件** → 换个环境/账号就跑不通，别人复现不了
- 缺**预期结果** → 执行完不知道算通过还是失败（这是最致命的，等价于自动化脚本里没有断言）
- 缺**实际结果** → 出问题无法举证，开发会说"我这没问题"

自动化只是把这条链从"人来走"换成"代码来走"，**结构一模一样**。所以能写好手工用例的人，写自动化用例天然占优；反过来，不理解用例结构就直接写代码，写出来的往往是"能跑的脚本"而不是"能判定的测试"。

【必须掌握】
- 五要素：用例标题 / 前提条件 / 用例步骤 / 预期结果 / 实际结果
- 预期结果必须**事先定义**，不能执行完了再倒推
- 用例结构的目标：可读、可维护、可扩展（三者都是长期成本问题）
- 自动化用例 = 用代码表达的同一套结构

【企业场景】
你在评审一份自动化脚本的 PR，看到方法名叫 `test_01`、里面没注释、最后 `print(res)` 结束。你会提三条：①标题（方法名）没有表达测试意图，别人无法从名字判断它测什么 ②前提条件（登录态、测试数据）藏在代码里没有显式声明 ③没有断言，所以它不是用例。这三条恰好对应五要素里的标题、前提、预期结果。

【面试考察】
面试官："一条测试用例应该包含哪些要素？自动化用例和手工用例的结构一样吗？"

参考回答框架：
1. 五要素：标题、前提条件、步骤、预期结果、实际结果（外加优先级/类型等管理字段）
2. 结构完全一致，只是**载体不同**：手工用例写在用例管理平台，自动化用例写成代码
3. 对应关系：标题→类名/方法名，前提→setup，步骤→测试方法体，预期 vs 实际→assert，清理→teardown
4. 强调：**没有预期结果的用例不是用例**，对应自动化里"没有断言的脚本不是测试"

【易错点】

| 误区 | 问题 | 纠正 |
|------|------|------|
| 用例标题写成"测试登录" | 无法区分正例反例、测什么条件 | "登录-密码错误-提示密码错误" |
| 前提条件写"打开浏览器" | 那是执行环境，不是业务前提 | 前提应是"已注册用户 A 且未登录" |
| 预期结果写"页面正常" | 不可判定，各人理解不同 | "标题包含关键词 且 结果列表数 > 0" |
| 实际结果不记录 | 缺陷无法举证 | 自动化里靠日志 + 失败截图留证 |

【我的理解】
> （拿你手工写过的一条用例，把五要素逐项对照检查：哪一项当时写得最含糊？为什么含糊的那项最容易引发争议？）

### 知识点 2：手工用例 → 自动化用例的结构映射

【课程原话/定义】

| 自动化测试用例 | 对应实现 | 作用 |
|--------------|---------|------|
| 用例标题 | 测试包、文件、类、方法名称 | 用例的唯一标识 |
| 前提条件 | `setup`、`setup_class`（Pytest）；`@BeforeEach`、`@BeforeAll`（JUnit） | 测试用例前的准备动作，比如读取数据或者 driver 的初始化 |
| 用例步骤 | 测试方法内的代码逻辑 | 测试用例具体的步骤行为 |
| 预期结果 | `assert 实际结果 == 预期结果` | 断言，印证用例是否执行成功 |
| 实际结果 | `assert 实际结果 == 预期结果` | 断言，印证用例是否执行成功 |
| 后置动作 | `teardown`、`teardown_class`（Pytest）；`@AfterEach`、`@AfterAll`（JUnit） | 脏数据清理、关闭 driver 进程 |

【为什么？】
注意表里多出来的一行 —— **后置动作**。手工用例的五要素里没有它，但自动化用例**必须有**，原因是：人做完测试会顺手关掉浏览器、删掉测试数据，机器不会。不写 teardown 的后果是累积性的：

| 不清理什么 | 累积后果 |
|-----------|---------|
| driver 进程 | 僵尸 chromedriver 越攒越多，机器内存耗尽（Ch02 讲过） |
| 测试数据 | 数据库里堆满"测试用户1、测试用户2…"，还可能让后面的用例断言失败 |
| 登录态 / cookie | 上一条用例的状态污染下一条，出现"单跑通过、连跑失败" |

再看**标题**这一行的深意：标题不是一个字段，而是"包 → 文件 → 类 → 方法"四级命名共同构成的**唯一标识**。这也是 Pytest 能用 `文件::类::方法` 精确运行单条用例的基础（`pytest test_search.py::TestSearch::test_keyword`）。所以方法名不是随便起的 `test_01`，它就是用例标题。

【必须掌握】
- 六项映射：标题→包/文件/类/方法名，前提→setup，步骤→方法体，预期/实际→assert，后置→teardown
- **自动化多一项"后置动作"**，用于关 driver + 清脏数据
- 方法级 vs 类级：`setup_method`/`teardown_method` 每条用例各执行一次；`setup_class`/`teardown_class` 整个类各执行一次
- Pytest 与 JUnit 是同一套思想的两种写法（@BeforeEach ↔ setup_method）

【企业场景】
一个下单流程的自动化用例，标准结构长这样：

```python
class TestOrder:
    def setup_class(self):
        """类级前提：整个测试类只登录一次，拿到登录态（贵操作只做一次）"""
        self.driver = webdriver.Chrome()
        self.driver.implicitly_wait(5)
        login(self.driver, "test_user", "123456")

    def setup_method(self):
        """方法级前提：每条用例前把购物车清空，保证用例互不影响"""
        clear_cart(self.driver)

    def test_place_order(self):
        # 用例步骤
        add_to_cart(self.driver, sku="10086")
        submit_order(self.driver)
        # 预期 vs 实际
        assert "下单成功" in self.driver.page_source

    def teardown_method(self):
        """方法级后置：删掉本条用例产生的订单，避免脏数据"""
        delete_test_orders(self.driver)

    def teardown_class(self):
        """类级后置：关浏览器"""
        self.driver.quit()
```

分层的判断标准：**贵且可复用的放类级（登录、启浏览器），会互相污染的放方法级（购物车、订单数据）。**

【面试考察】
面试官："setup_method 和 setup_class 有什么区别？你项目里 driver 放在哪一级？"

参考回答框架：
1. `setup_method` 每条用例前执行一次；`setup_class` 整个类只执行一次
2. driver 放哪级是**用例独立性 vs 执行速度**的权衡：
   - 方法级：每条用例新开浏览器，隔离最好、最稳，但慢（启动浏览器 2-3 秒 × N 条）
   - 类级：共享浏览器，快，但上一条的 cookie/弹窗/页面状态会污染下一条
3. 实践：driver 放类级或 session 级（复用），**状态清理放方法级**（每条用例前回首页/清 cookie）
4. 加分：Pytest 里更推荐用 fixture + scope 控制（function/class/module/session），比 setup/teardown 灵活，还能依赖注入

【易错点】

| 误区 | 后果 | 纠正 |
|------|------|------|
| 只写 setup 不写 teardown | 僵尸进程 + 脏数据累积 | 成对出现，teardown 必须关 driver |
| 把断言写在 teardown 里 | 断言失败时归因混乱，报告显示 error 而非 fail | 断言只写在测试方法里 |
| 用例之间靠执行顺序传递状态 | 单跑就失败，无法并行、无法只跑一条 | 每条用例自带前提，互相独立 |
| 方法名 `test_01`、`test_a` | 报告里看不出测什么，失败无法定位业务 | 方法名即用例标题，写清业务意图 |

【扩展知识】
Pytest 里 setup/teardown 的"进化版"是 fixture：

```python
@pytest.fixture(scope="class")
def driver():
    d = webdriver.Chrome()
    d.implicitly_wait(5)
    yield d          # yield 之前 = setup，之后 = teardown
    d.quit()
```

优势：①一个函数写完前置+后置 ②可通过 scope 控制粒度 ③可被多个测试类**依赖注入**复用 ④异常时也保证执行 teardown。详见 [[Pytest/README|Pytest]] Ch07-Ch09。

【我的理解】
> （为什么"用例之间不能靠执行顺序传递状态"？想想如果只跑第 3 条用例、或者用 pytest-xdist 并行跑会发生什么）

## 二、IDE 录制脚本与优化

### 知识点 3：录制脚本分析（搜狗搜索）

【课程原话/定义】
脚本步骤：访问搜狗网站 → 搜索框输入"霍格沃兹测试开发" → 点击搜索按钮。

录制导出的 Python 脚本：

```python
# Generated by Selenium IDE
import pytest
import time
import json
from selenium import webdriver
from selenium.webdriver.common.by import By
from selenium.webdriver.common.action_chains import ActionChains
from selenium.webdriver.support import expected_conditions
from selenium.webdriver.support.wait import WebDriverWait
from selenium.webdriver.common.keys import Keys
from selenium.webdriver.common.desired_capabilities import DesiredCapabilities


class Test():
    def setup_method(self, method):
        self.driver = webdriver.Chrome()
        self.vars = {}

    def teardown_method(self, method):
        self.driver.quit()

    def test_sougou(self):
        # 打开网页，设置窗口
        self.driver.get("https://www.sogou.com/")
        self.driver.set_window_size(1235, 693)
        # 输入搜索信息
        self.driver.find_element(By.ID, "query").click()
        self.driver.find_element(By.ID, "query").send_keys("霍格沃兹测试开发")
        # 点击搜索
        self.driver.find_element(By.ID, "stb").click()
        element = self.driver.find_element(By.ID, "stb")
        actions = ActionChains(self.driver)
        actions.move_to_element(element).perform()
```

【为什么？】
这段脚本恰好演示了"**结构对了，内容不合格**"：setup/teardown 的骨架是标准的（对应知识点 2 的映射），但用例本体有 5 个问题：

| 问题 | 具体表现 | 为什么是问题 |
|------|---------|------------|
| ❌ **没有断言** | 只有操作，最后是 `move_to_element` | 无法判定通过与否，永远绿灯 —— 违反五要素里的"预期结果" |
| ❌ 冗余动作 | `find_element(By.ID,"query").click()` 后又 `send_keys` | 录制器把"人点了一下输入框"也记下来了，输入不需要先点 |
| ❌ 无意义收尾 | `ActionChains.move_to_element(element)` | 录制器把鼠标滑过按钮的动作也记了，对测试毫无意义 |
| ❌ 重复定位 | `find_element(By.ID,"query")` 出现两次 | 每次都重新查 DOM，慢且冗余，应存变量 |
| 🟡 无等待策略 | 全靠录制回放的默认速度 | 页面稍慢就 `NoSuchElementException` |
| 🟡 一堆无用 import | json、Keys、DesiredCapabilities 都没用到 | 录制器模板化输出，`DesiredCapabilities` 在 Selenium 4 已废弃 |

一句话：**录制器记录的是"你的鼠标轨迹"，不是"你的测试意图"。** 鼠标轨迹里包含大量与验证无关的噪声，而最关键的"我期望看到什么"它完全不知道 —— 因为你只是看了一眼屏幕，没有点击任何东西。

【必须掌握】
- 录制脚本可留：`setup_method` / `teardown_method` 结构、基本定位与操作
- 录制脚本必删：无用 import、`ActionChains` 冗余滑动、输入前的多余 `click()`
- 录制脚本必加：**断言**、等待策略、元素复用
- `set_window_size` 建议保留或改成 `maximize_window()`（窗口太小会导致元素不可见、被折叠菜单藏起来）

【企业场景】
新人把这段录制脚本原样提 PR，跑起来是绿的。你在 review 时问一句："如果搜狗把搜索功能改坏了，返回一个空白结果页，你这条用例会失败吗？"答案是不会 —— 它照样绿。这一问就让人明白**没有断言的脚本等于零覆盖**，比讲十分钟理论有效。

【面试考察】
面试官："录制生成的脚本你会怎么改造？"

参考回答框架：
1. 先看结构：setup/teardown 可保留（driver 初始化 + quit）
2. 删噪声：无用 import、鼠标悬停等无关动作、输入前多余的 click
3. 加断言：明确预期结果（结果标题/列表包含关键词）
4. 加等待：删掉靠速度碰运气的做法，改显式等待（次选隐式等待）
5. 提炼：定位器抽到 PO 层，数据抽到参数化，避免硬编码
6. 结论：**录制给的是操作路径，不是可维护的测试用例**

【易错点】

| 误区 | 纠正 |
|------|------|
| 录制脚本能跑通就提交 | 能跑 ≠ 能验证，先补断言 |
| 保留 `ActionChains` 收尾动作 | 无验证价值，删掉；ActionChains 只在真的需要悬停/拖拽时才用 |
| 保留 `DesiredCapabilities` import | Selenium 4 已废弃，用 `Options` 替代 |
| 输入前必须先 click 输入框 | 不必要，`send_keys` 本身会聚焦；某些前端有遮罩时才需要 |

【我的理解】
> （"如果被测功能坏了，我这条用例会失败吗？"—— 用这个问题检查你写过的每条脚本。为什么它比"脚本能不能跑通"更重要？）

### 知识点 4：Python 脚本优化（课程重点）

【课程原话/定义】
优化后的脚本（改用百度做示例）：

```python
import pytest
import time
from selenium import webdriver
from selenium.webdriver.common.by import By


class TestDemo01():
    def setup_method(self, method):
        # 实例化 chromedriver
        self.driver = webdriver.Chrome()
        # 添加全局隐式等待
        self.driver.implicitly_wait(5)

    def teardown_method(self, method):
        # 关闭 driver
        self.driver.quit()

    def test_demo01(self):
        # 访问网站
        self.driver.get("https://www.baidu.com/")
        # 设置窗口
        self.driver.set_window_size(1330, 718)
        # 点击输入框
        self.driver.find_element(By.ID, "kw").click()
        # 输入框输入信息
        self.driver.find_element(By.ID, "kw").send_keys("霍格沃兹测试开发")
        # 点击搜索按钮
        self.driver.find_element(By.ID, "su").click()
        # 等待界面加载
        time.sleep(5)
        # 元素定位后获取文本信息
        res = self.driver.find_element(By.XPATH, "//*[@id='1']/h3/a").get_attribute("text")
        # 打印文本信息
        print(res)
        # 添加断言
        assert "霍格沃兹测试开发" in res
        # 查看界面展示
        time.sleep(5)
```

【为什么？】
优化做对了**三件关键事**，也留了**两个待改进点**——两者都要看懂：

✅ 做对的：

1. **加了隐式等待 `implicitly_wait(5)`**：全局生效，之后每次 `find_element` 找不到元素时会在 5 秒内不断重试，而不是立刻抛异常。这一行解决了 80% 的"元素找不到"偶发失败。
2. **加了断言**：`assert "霍格沃兹测试开发" in res` —— 用例从"操作脚本"变成了"测试用例"。而且用 `in`（包含）而不是 `==`（相等），这是有意为之：搜索结果标题往往带后缀（"霍格沃兹测试开发 - 官网"），用相等一定挂。
3. **取到了真实结果做验证**：`find_element(...).get_attribute("text")` 从结果列表第一条拿到标题文本，这才是"实际结果"。

🟡 待改进的：

1. **`time.sleep(5)` 是强制等待**：不管页面 0.5 秒还是 8 秒加载完，都固定死等 5 秒。快了浪费时间（100 条用例白等 500 秒），慢了照样失败。应换显式等待（见知识点 5）。最后那句 `time.sleep(5)`（"查看界面展示"）纯粹是给人眼看的，**正式代码必须删掉**。
2. **`//*[@id='1']/h3/a` 是脆弱定位**：`id='1'` 是百度结果条目的序号，属于随页面结构变化的属性，且绝对层级 `/h3/a` 一改版就废。这是 Ch03 讲的"定位器优先级"里的低分选项。

另外一个高频困惑点：`get_attribute("text")` 和 `.text` 有什么区别？

| 写法 | 取什么 | 何时用 |
|------|-------|-------|
| `element.text` | 浏览器**渲染后的可见文本**（不可见元素返回空串） | 默认首选，最贴近用户所见 |
| `element.get_attribute("text")` | DOM 属性 / innerText（`<a>` 标签有 text 属性） | 元素被遮挡/不可见但需取值时 |
| `element.get_attribute("textContent")` | 包括隐藏内容的全部文本 | 元素隐藏时的兜底方案 |
| `element.get_attribute("value")` | 输入框里的**当前值** | 断言输入框内容（`.text` 对 input 取不到） |

课程用 `get_attribute("text")` 能取到值，但更通用的写法是 `.text`；断言输入框内容时必须用 `get_attribute("value")`——这是面试常考的小坑。

【必须掌握】
- 优化三要素：**加等待、加断言、取真实结果**
- `implicitly_wait(n)` 设置一次全局生效，只对**元素查找**生效
- 断言优先用 `in`（包含）而非 `==`（相等），前者对文案变化更健壮
- `.text`（可见文本）vs `get_attribute("value")`（输入框值）vs `get_attribute("textContent")`（含隐藏）
- 正式代码里不留 `time.sleep`，尤其不留"给人看"的 sleep

【企业场景】
你把这条用例交给团队 review，会被要求再改三处：

```python
import pytest
from selenium import webdriver
from selenium.webdriver.common.by import By
from selenium.webdriver.support.wait import WebDriverWait
from selenium.webdriver.support import expected_conditions as EC


class TestBaiduSearch:
    def setup_method(self):
        self.driver = webdriver.Chrome()
        self.driver.maximize_window()          # ① 最大化，避免元素被折叠/遮挡
        self.driver.implicitly_wait(5)
        self.wait = WebDriverWait(self.driver, 10)

    def teardown_method(self):
        self.driver.quit()

    def test_search_keyword(self):
        self.driver.get("https://www.baidu.com/")
        self.driver.find_element(By.ID, "kw").send_keys("霍格沃兹测试开发")
        self.driver.find_element(By.ID, "su").click()
        # ② 显式等待结果区域出现，替代 time.sleep(5)
        first = self.wait.until(
            EC.visibility_of_element_located((By.CSS_SELECTOR, "#content_left h3 a"))
        )
        # ③ 断言用包含匹配，且断言前把实际值记进日志便于排查
        res = first.text
        print(f"[实际结果] {res}")
        assert "霍格沃兹测试开发" in res
```

改动收益：单条用例从固定 10 秒（两个 sleep(5)）降到 1-2 秒，且慢环境下不会假失败 —— 这就是显式等待"更快又更稳"的原因。

【面试考察】
面试官："你写的自动化用例里，怎么保证拿到的结果是真的加载出来了？"

参考回答框架：
1. 不用 `time.sleep` 碰运气，用**显式等待**等待明确条件（元素可见/可点击/文本出现）
2. 全局兜底加隐式等待，但主要靠显式等待处理关键节点
3. 取值区分场景：可见文本 `.text`、输入框 `get_attribute("value")`、隐藏内容 `textContent`
4. 断言用包含匹配 + 失败时输出实际值/截图，方便快速判断是元素变了还是功能坏了

【易错点】

| 错误写法 | 后果 | 正确做法 |
|---------|------|---------|
| `time.sleep(5)` 等页面 | 慢环境仍失败、快环境白等 | `WebDriverWait` + `expected_conditions` |
| `assert res == "霍格沃兹测试开发"` | 标题带后缀就挂 | 用 `in` 包含匹配 |
| 用 `.text` 断言输入框内容 | 永远是空串 | `get_attribute("value")` |
| `//*[@id='1']/h3/a` 这类定位 | 改版即失效 | 用语义化区域 + 相对定位（`#content_left h3 a`） |
| 留一个 sleep "方便观察" | 全量执行时间翻倍 | 调试时用断点，代码里不留 |

【我的理解】
> （这条用例里 `time.sleep(5)` 出现了两次，各自的目的不同。分别说说它们该被什么替代？第二个是不是根本不该存在？）

### 知识点 5：三种等待方式（面试必考）

【课程原话/定义】
课程在 Python 与 Java 优化中都提到"**添加全局隐式等待**"：`implicitly_wait(5)` / `driver.manage().timeouts().implicitlyWait(Duration.ofSeconds(10))`，并注明"隐式等待（了解即可）"。

【为什么？】
UI 自动化最大的敌人是**时序**：代码执行速度是毫秒级，页面渲染和接口返回是百毫秒到秒级。三种等待就是三种应对策略：

| 类型 | 写法 | 机制 | 优点 | 缺点 |
|------|------|------|------|------|
| **强制等待** | `time.sleep(5)` | 无条件死等 5 秒 | 简单 | 快了浪费、慢了失败，是"赌博" |
| **隐式等待** | `driver.implicitly_wait(5)` | 全局生效：**find_element 找不到时**轮询重试，最多 5 秒 | 一行搞定全局兜底 | ①只对"元素存在"生效，对"可点击/文本变化/元素消失"无效 ②设置一次影响全局，不好局部调整 |
| **显式等待** | `WebDriverWait(driver,10).until(EC.xxx)` | 针对**某个明确条件**轮询（默认 0.5s 一次），条件成立立刻返回 | 精确、最快、最稳，条件丰富 | 代码稍长，需要选对条件 |

关键结论（面试答这句就到位）：**显式等待是主力，隐式等待做全局兜底，强制等待只在调试时临时用。**

为什么"隐式等待"课程说"了解即可"？因为它有个隐蔽陷阱：它只解决"元素还没出现在 DOM 里"，而 UI 失败更多是"元素在 DOM 里但还不能点"（被遮罩层挡住、动画还在进行、按钮 disabled）。这种情况隐式等待直接放行，然后 `click()` 报 `ElementClickInterceptedException` / `ElementNotInteractableException` —— 显式等待的 `element_to_be_clickable` 才是对症的解法。

另外：**隐式等待和显式等待混用可能导致等待时间不可预期地叠加**（不同 driver 实现行为不一致），所以团队规范通常是"隐式等待设一个小值（3-5s）兜底，关键节点全用显式等待"。

常用 `expected_conditions`（记住这 5 个够用）：

| 条件 | 含义 | 典型场景 |
|------|------|---------|
| `presence_of_element_located` | 元素出现在 DOM | 只需要取值，不点击 |
| `visibility_of_element_located` | 元素可见（有宽高、不隐藏） | 断言文本、截图 |
| `element_to_be_clickable` | 可见且可点击 | 点按钮/链接（最常用） |
| `text_to_be_present_in_element` | 元素内出现指定文本 | 等异步结果刷新 |
| `invisibility_of_element_located` | 元素消失 | 等 loading 遮罩消失 |

【必须掌握】
- 三种等待的机制、优缺点与适用场景（能画上面那张表）
- 隐式等待：全局一次、只对元素查找生效
- 显式等待：`WebDriverWait(driver, timeout).until(EC.条件((By.X, "locator")))`
- 5 个高频 `expected_conditions`
- 规范：显式等待为主 + 隐式等待兜底 + 不留 sleep

【企业场景】
夜间构建有 6 条用例偶发失败，报错都是 `ElementClickInterceptedException: element click intercepted: Other element would receive the click`。排查发现页面有个 loading 遮罩，隐式等待认为"按钮已在 DOM 中"就放行，结果点在了遮罩上。修法两步：先 `EC.invisibility_of_element_located(遮罩)` 等遮罩消失，再 `EC.element_to_be_clickable(按钮)` 点击。改完偶发失败归零 —— 这类"Flaky 治理"是自动化工程师的核心价值之一。

【面试考察】
面试官："Selenium 有几种等待方式？区别是什么？你项目里怎么用的？"

参考回答框架：
1. 三种：强制等待（sleep）、隐式等待（implicitly_wait）、显式等待（WebDriverWait）
2. 强制等待是死等，不用于正式代码；隐式等待全局兜底、只作用于元素查找；显式等待针对具体条件、条件满足即返回
3. 项目实践：隐式等待设 3-5 秒兜底 + 关键交互全部显式等待（`element_to_be_clickable`、等 loading 消失）
4. 加分：说清"元素在 DOM ≠ 可交互"，举 `ElementClickInterceptedException` 的例子；提一句显隐式混用可能叠加超时，所以隐式值要小
5. 再加分：Playwright 自带 auto-waiting，所以更省心，但 Selenium 需要自己管

【易错点】

| 误区 | 纠正 |
|------|------|
| 有了隐式等待就不用显式等待 | 隐式只管"元素存在"，管不了可点击/文本变化/元素消失 |
| 显式等待写成 `WebDriverWait(driver,10).until(driver.find_element(...))` | `until` 里要传**可调用条件**，直接传结果会立即执行导致报错 |
| 用 sleep 兜底所有偶发失败 | 掩盖问题、拖慢执行；先定位真实原因 |
| 超时时间设很大（如 60s） | 真失败时要等 60 秒才报错，反馈变慢；10s 左右合适 |

【扩展知识】
显式等待的自定义条件（了解）：`until` 接受任何 callable，可传 lambda 实现自定义判断：

```python
# 等列表条目数量大于 5
WebDriverWait(driver, 10).until(
    lambda d: len(d.find_elements(By.CSS_SELECTOR, "#content_left h3")) > 5
)
```

【我的理解】
> （"元素已经在 DOM 里"和"元素可以被点击"是两件事——举一个你在网页上见过的真实例子，说明为什么隐式等待救不了这种情况）

## 三、Java 版本对照

### 知识点 6：Java（JUnit）实现与 pom 依赖【扩展知识】

【课程原话/定义】
Java 录制脚本使用 JUnit 注解组织结构：

```java
public class TestSogouTest {
    private WebDriver driver;

    @Before                       // 前提条件（每个测试方法前）
    public void setUp() {
        driver = new ChromeDriver();
        // 全局隐式等待
        driver.manage().timeouts().implicitlyWait(Duration.ofSeconds(10));
    }

    @After                        // 后置动作
    public void tearDown() {
        driver.quit();
    }

    @Test                         // 测试方法 = 用例步骤
    public void testSogou() {
        driver.get("https://www.sogou.com/");
        driver.manage().window().setSize(new Dimension(1671, 1417));
        driver.findElement(By.id("query")).sendKeys("霍格沃兹测试开发");
        driver.findElement(By.id("query")).sendKeys(Keys.ENTER);   // 回车搜索
        String text = driver.findElement(By.cssSelector("#sogou_vr_30000000_0 > em")).getText();
        assertEquals("霍格沃兹测试开发", text);    // 断言
    }
}
```

Maven `pom.xml` 关键依赖：`selenium-java 4.2.1`、`junit-jupiter-engine 5.8.2`、`slf4j` + `logback`（日志）；插件 `maven-compiler-plugin`（Java 11）、`maven-surefire-plugin`（`**/*Test.java` 才会被执行）。

【为什么？】
Python 方向的同学为什么也要看懂 Java 版？三个现实理由：

1. **面试**：面试官常问"你了解 JUnit 吗"或"Pytest 和 JUnit 有什么区别"，答"完全不知道"会显得视野窄。
2. **接手存量项目**：很多公司（尤其银行、传统企业、Android 团队）自动化用 Java 栈，你至少要能读。
3. **理解框架共性**：注解和 fixture 只是语法差异，**"前置-步骤-断言-后置"的结构完全一致** —— 看懂对照表，等于确认自己抓住的是本质而不是 API。

对照表（面试直接用）：

| 能力 | Pytest（Python） | JUnit 5（Java） |
|------|-----------------|----------------|
| 方法级前置/后置 | `setup_method` / `teardown_method`（或 fixture scope=function） | `@BeforeEach` / `@AfterEach`（旧版 `@Before`/`@After`） |
| 类级前置/后置 | `setup_class` / `teardown_class`（fixture scope=class） | `@BeforeAll` / `@AfterAll` |
| 标识测试方法 | 函数名以 `test_` 开头（约定） | `@Test` 注解（显式） |
| 断言 | 原生 `assert`（失败信息自动增强） | `assertEquals` / `assertTrue`（JUnit 断言方法） |
| 参数化 | `@pytest.mark.parametrize` | `@ParameterizedTest` + `@ValueSource/@CsvSource` |
| 依赖管理 | `pyproject.toml` / `requirements.txt` | `pom.xml`（Maven）/ `build.gradle` |
| 执行器 | `pytest` 命令 | `mvn test`（surefire 插件按 `*Test.java` 匹配） |
| 前置复用机制 | **fixture 依赖注入**（更灵活） | 注解 + 继承 / `@ExtendWith` |

一个值得注意的差异：Java 需要在 pom 里**手动声明 selenium 版本**（`4.2.1`），而 Python 靠 `pip install -U selenium`；Maven 的 surefire 插件还规定了"类名必须匹配 `*Test.java` 才会被执行"—— 这解释了新人常问的"我写了 @Test 为什么 mvn test 不跑"。Pytest 里对应的坑是"文件名必须 `test_*.py`、类名必须 `Test*`、方法必须 `test_*`"，本质是同一类**命名约定问题**。

【必须掌握】
- Pytest ↔ JUnit 结构对照（能说出 4 组对应关系）
- Java 断言 `assertEquals(期望, 实际)`：**期望值在前**（Python 的 assert 无此顺序问题）
- 命名约定决定用例能否被发现：surefire 的 `*Test.java` ↔ pytest 的 `test_*.py` / `Test*` / `test_*`
- 本节标记【扩展知识】：Python 方向以看懂为目标，不要求会写 Java

【企业场景】
你面试一家银行的测试开发岗，对方项目是 Java + Selenium + JUnit + Maven。你答："我主用 Python + Pytest，但结构是通的——你们的 `@BeforeEach` 对应我们的 setup_method 或 function 级 fixture，`@ParameterizedTest` 对应 `@pytest.mark.parametrize`，surefire 的用例匹配规则对应 pytest 的命名约定。读你们的脚本没问题，上手写需要一两周熟悉 Maven 和语法。" 这个回答比"我不会 Java"强得多，也比"我都会"更可信。

【面试考察】
面试官："Pytest 和 JUnit 的区别？你只会 Python，我们项目是 Java 栈能适应吗？"

参考回答框架：
1. 结构一致：前置/步骤/断言/后置四段式，只是注解 vs 函数约定的差异
2. 具体对应：`@BeforeEach`↔`setup_method`、`@BeforeAll`↔`setup_class`、`@Test`↔`test_` 前缀、`assertEquals`↔原生 `assert`、`@ParameterizedTest`↔`parametrize`
3. Pytest 的独特优势：fixture 依赖注入 + scope 控制，比注解继承更灵活；原生 assert 失败信息更友好
4. 迁移态度：语言是工具，**分层设计（PO）、等待策略、用例独立性这些能力是通用的**，语法一两周补齐

【易错点】

| 误区 | 纠正 |
|------|------|
| `assertEquals(实际, 期望)` 参数顺序写反 | JUnit 是 `assertEquals(期望, 实际)`，写反后失败信息会误导 |
| Java 里也用 `sendKeys` 前先 click | 同 Python，多余动作 |
| 写了 `@Test` 但 `mvn test` 不执行 | 类名不匹配 surefire 的 `**/*Test.java` 规则 |
| 认为换语言就要重学自动化 | 变的是 API，不变的是用例结构、等待策略、分层设计 |

【我的理解】
> （用"前置-步骤-断言-后置"四段式，把课程给的 Java 用例和 Python 用例各自的行号标出来对照一遍。你发现这两段代码的差异，本质上只是语法吗？）
