## 一、Web 自动化测试是什么

### 知识点 1：定义与目标

【课程原话/定义】
Web 自动化测试是一种通过**编写脚本或使用工具来模拟用户在 Web 应用程序中的操作**，从而自动执行测试用例并验证应用的功能、性能和稳定性的方法。它是现代软件开发中重要的一部分，有助于提高开发效率和保证软件质量。

目标：确保 Web 应用在各种条件下都能按预期工作。自动化测试旨在**减少手动测试的工作量**，提高测试的效率和准确性，以及**支持持续集成和持续交付流程**。

【为什么？】
定义里有两个词决定了它的一切：**模拟用户** 和 **验证**。

- "模拟用户"决定了它的**技术路径**：不调接口、不查数据库，而是像人一样点、输、滑、跳转 —— 所以它是最接近真实用户体验的一层测试，也是最慢、最脆弱的一层（页面一改就可能失效）。
- "验证"决定了它的**价值边界**：只会操作不会断言的脚本不是测试，是"自动点击器"。跑完全绿但什么都没校验，是自动化最常见的假象。

再往深一层：为什么企业愿意为它投人力？因为手工回归的成本随版本次数**线性增长**（发 10 次版就测 10 遍），而自动化的成本是**一次性投入 + 边际成本趋零**。版本迭代越快，这笔账越划算——这也是它必须绑定 CI/CD 的根本原因。

【必须掌握】
- Web 自动化 = 脚本/工具模拟用户操作 + 自动验证结果
- 验证对象：功能、性能、稳定性（重点是功能回归）
- 核心目标：减少手工回归工作量 + 支撑 CI/CD
- 没有断言的自动化脚本不算测试

【企业场景】
你所在团队两周一个迭代，每次发版前有一份 300 条的核心回归清单，3 个人手工点 2 天。上了 Web 自动化后，把其中 120 条稳定的核心流程做成脚本，挂在 Jenkins 上每晚跑一遍，早上看报告。人只需要覆盖新功能和探索性测试，回归时间从 2 天压到半天。

【面试考察】
面试官："你怎么理解 Web 自动化测试？它解决什么问题？"

参考回答框架：
1. 本质：用脚本模拟真实用户在浏览器上的操作，并对结果做断言
2. 解决的问题：**重复回归**成本高、人工易漏易错、发版频率上不去
3. 定位：它是分层测试金字塔的**顶层**（UI 层），慢而贵，只覆盖核心流程
4. 关键前提：必须有断言、必须进 CI，否则等于没做

【易错点】

| 误区 | 纠正 |
|------|------|
| 自动化测试用来"发现新 bug" | 主要价值是**回归**（守住已通过的功能），发现新 bug 是手工/探索测试更强 |
| 自动化能替代手工测试 | 替代不了。UI 美观、交互体验、易用性、新功能首轮测试仍靠人 |
| 覆盖率越高越好 | UI 层追求高覆盖率 = 维护地狱，核心流程覆盖到就够 |
| 脚本跑完不报错就是通过 | 没断言的脚本永远不报错，是最危险的"绿色" |

【我的理解】
> （用你自己手工测试的经历举例：哪一批用例你已经点得想吐了？它们具备哪些共同特征？）

### 知识点 2：五大价值

【课程原话/定义】

1. **提高测试覆盖率**：自动化测试可以执行大量测试用例，涵盖不同的功能和场景，确保更全面的测试覆盖。
2. **节省时间和资源**：自动化测试可以在没有人工干预的情况下运行，从而节省测试团队的时间和资源。
3. **快速反馈**：自动化测试提供迅速的测试结果，有助于开发团队及时发现和修复问题，加速开发周期。
4. **减少人为错误**：自动化测试脚本可以避免人为疏忽和错误，提高测试的一致性和准确性。
5. **支持持续集成**：自动化测试是持续集成和持续交付流程中的关键环节，确保代码提交后自动运行测试。

【为什么？】
这五条不是并列的，它们有**因果链**：

```
脚本可无人值守重复执行
   ├─→ 节省人力（同样的用例不用人点第二遍）
   ├─→ 提高覆盖（人力省下来可以跑更多组合数据）
   ├─→ 一致性高（人会累会漏，脚本每次动作完全相同）
   └─→ 可挂 CI ─→ 每次提交自动跑 ─→ 快速反馈 ─→ 缺陷发现左移，修复成本降低
```

真正的"杀手价值"是最后一条链路：**缺陷越早发现，修复成本越低**（需求阶段发现 1 倍成本，上线后 100 倍）。自动化的意义不只是"省了几个人天"，而是把回归从"发版前的一次性动作"变成"每次提交后的持续动作"。

面试时只答"省时间"会显得很浅，答到"支撑 CI、让反馈提前"才是测试开发的视角。

【必须掌握】
- 五大价值：覆盖率、省时省力、快速反馈、减少人为错误、支持持续集成
- 价值排序（测试开发视角）：支持 CI ＞ 快速反馈 ＞ 省人力 ＞ 一致性 ＞ 覆盖率
- 一致性 = 每次执行动作完全相同，人做不到

【企业场景】
你把 60 条核心 Web 用例接进 GitLab CI：开发提 MR 后自动触发，10 分钟出结果，失败自动在 MR 上评论并@提交人。上线三个月后统计：发版前的"回归阻塞"从平均 1.5 天降到 0，且有 4 次拦住了开发把登录逻辑改坏的提交——如果等到发版前手工回归才发现，开发已经在做下一个需求了，切回来改的成本高得多。

【面试考察】
面试官："自动化测试到底带来了什么收益？你们怎么衡量？"

参考回答框架：
1. 先说可量化的：回归耗时（人天）下降 X%、每晚可执行用例数、缺陷平均发现时间提前
2. 再说结构性的：从"发版前集中回归"变成"每次提交持续回归"，缺陷左移
3. 提一条真实拦截案例（比如自动化拦住了登录/支付主流程被改坏）
4. 诚实说局限：维护成本、脚本不稳（Flaky）需要治理

【易错点】

| 说法 | 问题 |
|------|------|
| "自动化能提升测试覆盖率" | 指的是**执行覆盖的数据/场景组合变多**，不是自动化天生覆盖更全 |
| "自动化省钱" | 前期投入（框架、脚本、维护）不便宜，只有**重复执行次数够多**才回本 |
| "跑得快就是价值" | 跑得快但不稳定（一半失败要人工复查）反而增加成本 |
| 只关注写脚本，不关注接 CI | 不进 CI 的自动化＝一个没人跑的玩具 |

【扩展知识】
自动化的投入产出比可以粗算：

```
收益 = （单次手工回归耗时 - 单次自动化耗时）× 执行次数
成本 = 脚本开发时间 + 维护时间 × 版本数
```

结论：**执行次数少、UI 变动频繁的项目不该做 UI 自动化**。这直接解释了下面知识点 4 的适用场景。

【我的理解】
> （如果领导问你"投三个月做 Web 自动化，能给我省多少钱"，你会用哪几个数字回答？）

所以"会用 Selenium"只是入场券，**能设计一套别人也能维护的框架**才是招聘方真正付钱买的东西。

【必须掌握】
- 语言（Python）＞ 工具（Selenium）＞ 框架（Pytest）＞ 设计（PO）＞ 工程化（CI/Allure）
- 简历上"熟悉 Selenium"必须能配一个项目讲清：多少条用例、怎么分层、怎么进 CI、怎么处理不稳定
- 面试重点从来不是 API 记忆，而是设计和踩坑经验

【企业场景】
面试官看到简历写"使用 Selenium 完成 Web 自动化测试"，一定会追问三件事：①用例怎么组织（有没有 PO）②元素定位不稳怎么解决（等待策略）③怎么跑起来的（本地还是 CI）。答不上后两个，会被判定为"只跟着教程写过 demo"。

【面试考察】
面试官："介绍一下你做过的 Web 自动化项目。"

参考回答框架（STAR + 技术栈）：
1. 背景：什么系统、迭代频率、回归痛点
2. 方案：Python + Selenium + Pytest + PO + Allure，多少条用例覆盖哪些核心流程
3. 落地：Jenkins 每晚定时跑 + MR 触发，失败自动通知
4. 难点与解法：元素定位不稳 → 显式等待 + 稳定属性；数据污染 → 前置数据初始化 fixture
5. 结果：回归耗时下降、拦截过哪些线上问题

【易错点】

| 简历/回答写法 | 问题 | 改法 |
|-------------|------|------|
| "精通 Selenium" | 一定被深挖到答不上 | 写"熟悉"，并准备 3 个踩坑故事 |
| 只讲工具不讲设计 | 显得是脚本搬砖 | 讲清分层与复用 |
| 说不出用例数量和覆盖范围 | 像没做过 | 记住量级数字 |

### 知识点 4：UI 自动化测试的流程

【课程原话/定义】
课程用 UML 图给出 UI 自动化测试的标准流程，同时给出了功能测试场景图作对照。

> 📷 【截图占位】功能测试场景 UML 图
> 📷 【截图占位】UI 自动化测试流程 UML 图

标准流程可以概括为：

```
需求/用例分析 → 挑选适合自动化的用例 → 搭建环境与框架
    → 编写脚本（定位元素 → 操作 → 断言）→ 本地调试通过
    → 接入 CI 持续执行 → 生成报告 → 分析失败（真 bug / 脚本问题）
    → 维护更新脚本
```

【为什么？】
注意流程里两个容易被跳过、但决定成败的环节：

1. **"挑选适合自动化的用例"在写脚本之前**。新手的做法是把手工用例全量翻译成脚本，结果 60% 的脚本三个月后没人维护。自动化用例是**筛选出来的**，不是全量搬运。
2. **"分析失败"是闭环的关键**。自动化跑红有两种原因：真 bug 和脚本自身问题（元素变了、等待不够、数据脏了）。如果失败没人分析、没人修，团队很快就会集体忽略红灯 —— 自动化就死了。

流程的终点不是"脚本写完"，而是"每天有人看结果并且结果可信"。

【必须掌握】
- 流程六步：选用例 → 搭环境 → 写脚本（定位/操作/断言）→ 调试 → 接 CI → 分析并维护
- 脚本三要素：**元素定位、元素操作、结果断言**
- 失败分析必须区分"产品 bug"和"脚本问题"
- 维护是长期成本，不是一次性工作

【企业场景】
你的夜间构建早上显示 12 条失败。逐条看：8 条是因为前端把按钮 class 从 `btn-submit` 改成了 `btn-primary`（脚本问题，改定位器）；3 条是测试数据被别人跑接口用例删掉了（环境问题，加数据初始化 fixture）；1 条是优惠券金额算错（**真 bug，提单**）。这个"12 → 1"的分诊过程，就是自动化工程师每天的核心工作，也是面试的高频提问点。

【面试考察】
面试官："自动化用例执行失败了，你怎么排查？"

参考回答框架：
1. 先看报告/日志/失败截图，定位失败步骤
2. 分类：定位失败（元素变了/等待不足）、数据问题、环境问题、真 bug
3. 真 bug → 提单并附截图日志；脚本问题 → 修脚本（优先换稳定定位、加显式等待）
4. 治理：同一条用例反复不稳（Flaky）要标记并专项修，不能靠"重跑一次就过"糊过去
5. 沉淀：把这次的定位方式改成不依赖易变属性，避免同类再犯

【易错点】

| 做法 | 问题 |
|------|------|
| 把全部手工用例翻译成脚本 | 维护成本爆炸，多数脚本会烂掉 |
| 失败就重跑，过了就算通过 | 掩盖真 bug，也掩盖 Flaky 问题 |
| 脚本没有断言只有操作 | 永远绿灯，形同虚设 |
| 只在本地跑，不接 CI | 没人看的自动化没有价值 |

【我的理解】
> （为什么"挑选用例"这一步要放在"写脚本"之前？如果跳过它会发生什么？）

### 知识点 5：UI 自动化的适用场景

【课程原话/定义】
UI 自动化应用场景：

- 业务流程**不频繁改动**
- UI 元素**不频繁改动**
- **需要频繁回归**的场景
- **核心场景**等

【为什么？】
这四条其实是同一个判断标准的四个侧面：**收益 ÷ 维护成本**。

- 业务/UI 频繁改动 → 分母（维护成本）巨大 → 不划算
- 需要频繁回归 → 分子（收益）大 → 划算
- 核心场景 → 出问题损失大 → 即使贵也值得

所以判断一条用例该不该自动化，问三个问题：
1. 这个功能三个月内会大改吗？（会 → 先别做）
2. 这条用例每个版本都要测吗？（是 → 值得做）
3. 它坏了会不会阻塞用户/造成资损？（是 → 优先做）

反例也要记住：**新功能首轮测试、UI 视觉/体验验证、只跑一次的用例、需要人工判断的场景（验证码、图片美观度）不适合 UI 自动化。**

【必须掌握】
- 该做：稳定的、要频繁回归的、核心的（登录、下单、支付主流程）
- 不该做：需求频繁变动的新功能、一次性用例、UI 视觉与体验、依赖人工判断的场景
- 判断依据：收益（回归次数 × 单次耗时）vs 成本（开发 + 维护）
- 优先级：核心流程 > 高频回归 > 数据组合多的场景

【企业场景】
产品要在两周内上线一个还在反复改版的活动页。测试组长决定：活动页**不做** UI 自动化（UI 每天在变，脚本写完就废），只做接口层自动化保证优惠计算正确；同时把已经稳定一年的登录 + 下单 + 支付主流程做成 UI 自动化每晚跑。这个决策就是知识点 5 的直接应用。

【面试考察】
面试官："哪些用例适合做 UI 自动化？哪些不适合？为什么？"

参考回答框架：
1. 适合：稳定 + 高频回归 + 核心业务（举例：登录、下单、支付）
2. 不适合：需求/UI 频繁变动、只执行一次、视觉与体验类、需人工判断
3. 判断标准：收益（回归次数）÷ 维护成本
4. 加分：能优先用接口自动化覆盖的逻辑就不要用 UI 做（分层原则，见 [[软件测试基础/README\|软件测试基础]] Ch15）

【易错点】

| 误判 | 正确判断 |
|------|---------|
| 新功能马上做 UI 自动化 | 等需求稳定后再做，否则脚本反复重写 |
| 什么校验都用 UI 做 | 能在接口/单元层验证的下沉一层，UI 只验流程 |
| 认为"核心场景"= 全部主要功能 | 核心 = 坏了会阻塞用户或造成资损的那几条 |
| 把偶发不稳的用例留在 CI 里 | 要么修好，要么移出主流水线 |

【扩展知识】
分层测试原则（测试金字塔）与本章的关系：UI 自动化处在金字塔**顶层**——数量最少、最慢、最贵。同一个校验点如果能在接口层做，就不该放到 UI 层。详见 [[软件测试基础/README|软件测试基础]] 的 Ch14 分层测试策略、Ch15 自动化测试策略。

【我的理解】
> （挑你手工测过的 5 条用例，按"该不该做 UI 自动化"分类，并写出每条的理由）

## 三、技术体系与学习路线

### 知识点 6：Web 自动化测试相关技术

【课程原话/定义】

- **Python**：自动化测试主流开发语言
- **Selenium**：企业事实标准，课程重点
- **Playwright**：新一代 Web 自动化框架
- **Pytest**：测试框架、Fixture、参数化
- **Page Object（PO）**：企业级项目设计模式
- **Allure**：自动化测试报告

【为什么？】
这六项不是"六个工具"，而是**一个框架的六层职责**，各自解决一个明确的问题：

| 技术 | 解决什么问题 | 没有它会怎样 |
|------|------------|------------|
| Python | 写逻辑、处理数据 | 无法编程实现任何自动化 |
| Selenium / Playwright | 驱动浏览器（定位、点击、输入） | 只能人工点 |
| Pytest | 组织用例、前后置、参数化、批量执行 | 用例散落成一堆 main 函数，无法批量跑和统计 |
| Page Object | 页面元素与用例逻辑解耦 | 页面一改要改几十个脚本 |
| Allure | 结果可视化、失败截图、给团队看 | 只有控制台日志，没人看得懂结果 |
| CI（Jenkins/GitLab CI） | 持续、无人执行 | 靠人记得跑，很快就不跑了 |

Selenium 与 Playwright 的关系：Selenium 是**事实标准**（存量项目多、招聘要求多、生态成熟），Playwright 是新一代（自带等待、速度快、API 更现代）。学习顺序上先 Selenium——它的元素定位、等待、多窗口等概念是通用的，迁到 Playwright 只是换 API。

【必须掌握】
- 完整技术栈：Python + Selenium + Pytest + PO + Allure + CI
- 每层的职责（面试常问"为什么要用 PO"、"Pytest 在里面起什么作用"）
- Selenium 是就业事实标准，Playwright 是趋势，概念可迁移
- 工具会换，**分层设计思想不换**

【企业场景】
你搭一个新项目的 Web 自动化框架，目录大致长这样：

```
project/
├── pages/          # PO：每个页面一个类，只放元素定位 + 页面动作
├── testcases/      # 用例：只写业务步骤 + 断言，不出现定位器
├── conftest.py     # Pytest fixture：启动/关闭浏览器、登录态、测试数据
├── data/           # 测试数据（yaml/csv）→ 用到 [[Python/Ch25-文件操作|文件操作]]
├── utils/          # 封装：等待、截图、日志
└── report/         # Allure 结果
```

面试时能画出这张图并解释每层职责，比背 100 个 Selenium API 都有用。

【面试考察】
面试官："你们的 Web 自动化框架是怎么设计的？各部分用什么技术？"

参考回答框架：
1. 语言 Python，驱动 Selenium 4，用例框架 Pytest
2. 分层：PO 层（元素+页面动作）/ 用例层（业务+断言）/ 数据层（yaml/csv）/ 工具层（等待、截图、日志）
3. 报告 Allure（含失败截图），执行 Jenkins 定时 + MR 触发
4. 设计原则：定位器只出现在 PO 层，用例层不碰元素；数据与代码分离
5. 追问 Playwright：知道它自带自动等待、更快，但存量项目和招聘以 Selenium 为主

【易错点】

| 误区 | 纠正 |
|------|------|
| Selenium 就是测试框架 | Selenium 只是**浏览器驱动库**，测试框架是 Pytest/JUnit |
| PO 是"把元素写到一个文件里" | PO 是**页面对象**：元素 + 该页面的行为方法，且要能返回下一个页面对象 |
| Allure 只是好看 | 它承载失败截图/步骤/附件，是团队协作和定责的依据 |
| 学了 Selenium 就不用学 Playwright | 概念通用，趋势要跟；但先把一个学透 |

【我的理解】

### 知识点 7：学习路线

【课程原话/定义】
Web 自动化测试学习路线三原则：

- **由浅入深**
- **掌握核心和重点**
- **理论结合实践**

> 📷 【截图占位】web 自动化学习路线图

【为什么？】
"掌握核心和重点"这一条最值钱，因为 Selenium 的 API 有几百个，**面试和工作只反复用其中 20%**：

| 优先级 | 内容 | 说明 |
|--------|------|------|
| 🔴 必须精通 | 八大元素定位（尤其 XPath / CSS）、click/send_keys/text、显式等待、断言 | 每天都用，面试必问 |
| 🔴 必须精通 | Pytest 组织 + PO 分层 | 决定框架能不能维护 |
| 🟡 需要会用 | 多窗口/frame/弹窗、下拉框、上传、鼠标键盘操作、截图 | 遇到就要会查会写 |
| 🟢 了解即可 | IDE 录制、Selenium Grid、无头模式细节、CDP | 知道存在和适用场景 |

"理论结合实践"的落地方式是：**每学一个 API 立刻在真实网站上跑通一遍**（课程用 ceshiren.com 论坛作练习站点）。只看不写的自动化学习几乎等于零——因为 90% 的坑（元素找不到、点不到、时机不对）只有跑起来才会遇到。

【必须掌握】
- 路线：环境 → 第一个脚本 → 元素定位 → 元素操作 → 等待机制 → 复杂场景 → Pytest 组织 → PO 设计 → 报告 → CI
- 20% 的核心 API 覆盖 80% 的工作
- 学一个练一个，坑必须自己踩

【企业场景】
新人入职做 Web 自动化，前两周的典型任务：把已有框架跑起来 → 读 3 个现成用例 → 照着写 2 条新用例 → 修 5 条因页面改版失效的脚本。整个过程用到的正是"定位 + 操作 + 等待 + 断言 + PO"这几项核心，几乎不涉及冷门 API。

【面试考察】
面试官："如果让你从零学 Selenium，你会怎么安排？"（考学习方法与技术判断）

参考回答框架：
1. 先跑通环境和第一个脚本，建立正反馈
2. 攻核心：元素定位（八大策略、XPath/CSS 优先）→ 常用操作 → 等待机制（显式等待为主）
3. 攻工程化：Pytest 组织 + PO 分层 + Allure 报告 + CI
4. 复杂场景按需补（frame、多窗口、上传）
5. 全程在真实站点练手，边写边记踩坑

【易错点】

| 学习误区 | 后果 | 正确做法 |
|---------|------|---------|
| 追求背完所有 API | 记不住也用不上 | 掌握核心 20%，其余会查文档 |
| 只看视频不动手 | 一遇报错就卡住 | 每个知识点都跑一遍 |
| 一上来就学 Grid/分布式 | 基础不牢，面试也不问这些 | 先把定位和等待打透 |
| 跳过 Pytest 直接写脚本 | 用例无法批量执行和统计 | Pytest 与 Selenium 同等重要 |

【扩展知识】
本章内容与 [[软件测试基础/README|软件测试基础]] 的 Ch15（自动化测试策略）有交叉，但**视角不同**，不要混淆：

| 对比项 | 软件测试基础 Ch15 | 本章（Web 自动化 Ch01） |
|--------|------------------|----------------------|
| 视角 | 管理/策略视角：整体自动化体系（用户端 + 服务端 + 稳定性） | 落地/技术视角：Web 端怎么做 |
| 覆盖范围 | Selenium / Appium / 智能遍历 / Fastbot / 服务端手段 | 只聚焦 Web（Selenium 主线） |
| 关键产出 | 该不该自动化、分层怎么分、工具怎么选 | 技术栈怎么搭、脚本怎么写、路线怎么走 |
| 面试用法 | 回答"你们自动化策略是什么" | 回答"你的 Web 框架怎么设计" |

一句话记：**Ch15 决定"做不做、做哪层"，本章决定"Web 这层怎么做"。**
