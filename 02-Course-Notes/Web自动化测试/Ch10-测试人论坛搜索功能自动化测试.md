## 一、产品分析与测试用例分析

### 知识点 1：从产品到用例

【课程原话/定义】
- 产品：测试人论坛
- 功能：搜索
- 地址：https://ceshiren.com

测试用例：

| 用例标题 | 前提条件 | 用例步骤 | 预期结果 | 实际结果 |
|----------|----------|----------|----------|----------|
| 测试人搜索功能 | 进入测试人论坛首页 | 1. 点击搜索按钮<br>2. 输入搜索关键词<br>3. 点击搜索按钮 | 1. 搜索成功<br>2. 搜索结果列表包含关键字 | （执行时填写） |

【为什么？】
这是 Ch04"五要素"的**第一次完整落地**。注意这条用例的两个细节：

1. **步骤里有两次"点击搜索按钮"**——第一次点开搜索框（页面右上角是折叠的，要先点开），第二次才是真正触发搜索。这提醒我们：**用例步骤要跟着真实页面交互走**，不能想当然地简写成"输入→搜索"。
2. **预期结果有两条**：一条是"搜索成功"（过程），一条是"结果列表包含关键字"（可验证的结果）。第二条才是真正能被断言抓住的——它直接对应脚本里的 `assert "关键字" in 结果文本`。

【必须掌握】
- 写脚本前先有"产品分析（测什么）+ 用例分析（怎么验）"，不是上来就写代码
- 预期结果要落到"可断言的文本/属性"上，否则脚本无法判定
- 用例步骤要还原真实页面交互（本例：先点开搜索框，再点搜索）

【企业场景】
你在企业里接一个自动化需求，第一件事不是开 IDE，而是先把手工用例表拿出来，确认"前提、步骤、预期"这三栏清不清晰。预期结果如果写着"搜索成功"这种不可判定的词，你得先回头和用例作者对齐成"结果列表包含关键字 X"，否则脚本写完没有东西可断言。

【面试考察】
面试官："给你一个搜索功能，说说你怎么把它变成自动化用例？"

参考回答框架：
1. 先产品分析：确认被测对象、功能、URL、前置数据
2. 再用例分析：把手工用例的五要素（标题/前提/步骤/预期）逐条落到可执行、可断言的粒度
3. 关键：预期结果必须"可判定"（能变成 assert），不能是"成功/正常"这种模糊词
4. 最后才是写脚本：结构（前置后置）+ 操作 + 断言

【易错点】

| 误区 | 纠正 |
|------|------|
| 拿到需求直接写代码 | 先产品分析 + 用例分析，明确"验什么" |
| 预期结果写"搜索成功" | 不可判定，要写成"结果列表包含关键字" |
| 步骤漏掉"点开搜索框" | 跟着真实页面交互走，折叠的输入框要先点开 |

【我的理解】
> （这条用例步骤里为什么有两次"点击搜索按钮"？如果少写第一次，脚本会怎样？）

## 二、编写脚本

### 知识点 2：初版脚本与它的缺陷

【课程原话/定义】
Python 版本（初版）：

```python
from selenium import webdriver
from selenium.webdriver.common.by import By


class TestCeShiRen:
    def test_search(self):
        driver = webdriver.Chrome()
        driver.get("https://www.ceshiren.com")
        driver.find_element(By.ID, "search-button").click()           # 点开搜索框
        driver.find_element(By.ID, "search-term").send_keys("appium") # 输入关键词
        driver.find_element(By.CSS_SELECTOR, ".show-advanced-search").click()  # 点搜索
```

Java 版本（初版）：

```java
@Test
void search() throws InterruptedException {
    driver = new ChromeDriver();
    driver.get("https://ceshiren.com/");
    driver.findElement(By.id("search-button")).click();
    driver.findElement(By.id("search-term")).sendKeys("appium");
    driver.findElement(By.cssSelector(".show-advanced-search")).click();
    Thread.sleep(3000);
}
```

【为什么？】
这段初版脚本"能跑"，但对照 Ch04 的用例结构，它有**三个致命缺陷**：

| 缺陷 | 表现 | 后果 |
|------|------|------|
| ❌ 无前置/后置 | driver 直接 new 在用例里，用完没 quit | 僵尸 chromedriver 进程累积（Ch02/Ch04 讲过） |
| ❌ 无断言 | 做完操作就结束 | 无法判定搜索到底成没成功，永远绿灯 |
| 🟡 有 Thread.sleep(3000) | Java 版硬睡 3 秒 | 拖慢执行、慢环境仍可能失败（Ch07 讲过） |

一句话：**这是"能跑的脚本"，不是"能判定的测试"**。接下来两节就是把它补成完整用例的过程。

【必须掌握】
- 初版脚本三缺陷：无前置后置、无断言、（Java）有 sleep
- "能跑" ≠ "能验证"，缺断言就是零覆盖（Ch04 反复强调）

【企业场景】
你 review 新人提的 PR，看到的就是这个初版样子：`test_search` 里 new driver、操作完就结束、没有 quit 没有 assert。你让他自己回答一个问题："如果搜索功能坏了，返回空结果，这条用例会失败吗？"——答案是不会，这比直接批评更有效。

【面试考察】
面试官："这段脚本你 review 会提什么问题？"

参考回答框架：
1. driver 没有前置后置管理，用完没 quit → 僵尸进程
2. 没有断言 → 不是测试用例，无法判定结果
3. sleep 应换显式等待（Java 版）
4. 定位器用了 id 和 CSS，本身没问题，但可以收进 PO 层

【易错点】

| 误区 | 纠正 |
|------|------|
| 初版能跑就交付 | 缺断言 = 零覆盖，缺 quit = 僵尸进程 |
| 靠 Thread.sleep 等结果 | 换显式等待等结果出现 |

【我的理解】
> （对照 Ch04 的六项映射，这段初版脚本少了哪几项？哪一项的缺失最致命？）

## 三、脚本优化

### 知识点 3：优化一 · 加前置与后置

【课程原话/定义】
Python 版本：

```python
class TestCeShiRen:
    def setup_class(self):
        self.driver = webdriver.Chrome()          # 前置：初始化 WebDriver

    def teardown_class(self):
        self.driver.quit()                       # 后置：退出浏览器

    def test_search(self):
        self.driver.get("https://www.ceshiren.com")
        self.driver.find_element(By.ID, "search-button").click()
        self.driver.find_element(By.ID, "search-term").send_keys("appium")
        self.driver.find_element(By.CSS_SELECTOR, ".show-advanced-search").click()
```

Java 版本（前置 BeforeAll - 初始化驱动；后置 AfterAll - 关闭浏览器）：

```java
public class CeshirenTest {
    public static WebDriver driver;

    @BeforeAll
    static void setUpClass(){
        driver = new ChromeDriver();
        driver.get("https://ceshiren.com/");
    }
    @AfterAll
    static void tearDownClass(){
        driver.quit();
    }
    // @Test search() 里本应只留"操作步骤"，见【易错点】
}
```

【为什么？】
这一步把 Ch04 讲的"**自动化比手工多一项后置动作**"落到了实处：

- `setup_class` / `@BeforeAll`：整个类只执行一次，driver 初始化在这里（贵操作只做一次）
- `teardown_class` / `@AfterAll`：类结束只执行一次，保证 `quit()` 一定执行，不留僵尸进程

选 `class` 级而不是 `method` 级，是因为"启浏览器"是**贵且可复用**的操作（Ch04 知识点2 的分层判断标准）。

【必须掌握】
- 前置初始化 driver、后置 quit，两者**成对出现**
- `setup_class`/`@BeforeAll` 类级只执行一次（driver 复用）
- 后置写在 teardown 里，用例失败也会执行（不会攒僵尸进程）

【企业场景】
你把 driver 的生命周期交给 setup/teardown 管理后，团队 50 条用例共享一个 driver（类级），执行时间大幅下降，也不会再出现"跑一晚上、机器上多出几十个 chromedriver 进程"的问题。

【面试考察】
面试官："driver 初始化应该放 setup_class 还是 setup_method？"

参考回答框架：
1. 类级（setup_class）：driver 复用，快，但要注意用例间状态污染
2. 方法级（setup_method）：每条新开浏览器，隔离最好但慢
3. 实践：driver 放类级，状态清理（cookie/数据）放方法级（Ch04 的结论）

【易错点】

| 误区 | 纠正 |
|------|------|
| Java 版 search() 里仍写 `driver = new ChromeDriver()` | setUpClass 已初始化，用例里重复 new 会覆盖掉前置建的 driver（课程 bug） |
| 只写 setup 不写 teardown | quit 不执行 → 僵尸进程累积 |
| driver 放方法级导致慢 | 类级复用更合理，除非用例间强隔离需求 |

【我的理解】
> （Java 版优化后，`@Test search()` 方法体里那一行 `driver = new ChromeDriver();` 还在吗？它应该还在吗？为什么？）

### 知识点 4：优化二 · 添加断言

【课程原话/定义】
Python 版本：

```python
def test_search(self):
    self.driver.get("https://www.ceshiren.com")
    self.driver.find_element(By.ID, "search-button").click()
    self.driver.find_element(By.ID, "search-term").send_keys("appium")
    self.driver.find_element(By.CSS_SELECTOR, ".show-advanced-search").click()
    time.sleep(2)                                    # 等结果加载
    web_ele = self.driver.find_element(By.CSS_SELECTOR, ".topic-title")
    title_text = web_ele.text                        # 取结果标题文本
    assert "appium" in title_text                    # 断言包含关键字
```

Java 版本（assertThat 语句）：

```java
WebElement title = driver.findElement(By.cssSelector(".topic-title"));
String title_text = title.getText();
assertThat(title_text, containsString("selenium"));   // Hamcrest 断言
```

【为什么？】
这一步是**从"脚本"到"测试"的质变**，做了两件关键事：

1. **取真实结果**：`.topic-title` 定位到搜索结果第一条标题，`.text` 拿到文本（Ch08 讲的取值）
2. **断言用包含匹配**：`assert "appium" in title_text` 用 `in` 而不是 `==`——因为标题常带前后缀（"appium 入门教程"），用相等一定挂（Ch04 知识点4 反复强调）

Java 侧用 `assertThat(actual, containsString(expected))`，是 Hamcrest 风格的"包含"断言，等价于 Python 的 `in`。

⚠️ 两个待改进点（Ch07 已讲）：
- `time.sleep(2)` 又是强制等待，应换成**显式等待**等 `.topic-title` 出现
- Python 加断言版本用了 `time.sleep(2)` 但文件头没 `import time`（课程漏 import）

【必须掌握】
- 断言三要素：取真实结果（`.text`）→ 包含匹配（`in` / `containsString`）→ 失败时能看到实际值
- Java 的 `assertThat(actual, containsString(x))` 等价 Python 的 `x in actual`
- `time.sleep` 应换显式等待

【企业场景】
你在 review 时把这条用例的 `time.sleep(2)` 圈出来，改成：

```python
from selenium.webdriver.support.wait import WebDriverWait
from selenium.webdriver.support import expected_conditions as EC

title = WebDriverWait(self.driver, 10).until(
    EC.visibility_of_element_located((By.CSS_SELECTOR, ".topic-title"))
)
assert "appium" in title.text
```

慢环境不再假失败，快环境不白等 2 秒。这就是"更快又更稳"（Ch07 的原话）。

【面试考察】
面试官："这条搜索用例你最终会怎么断言？"

参考回答框架：
1. 等结果区域出现（显式等待，不用 sleep）
2. 取结果标题 `.text`
3. 用包含匹配 `assert "关键字" in title_text`（标题常带前后缀）
4. 失败时打印实际值 + 截图，方便判断是"没搜到"还是"定位变了"

【易错点】

| 误区 | 纠正 |
|------|------|
| `assert title_text == "appium"` | 标题带前后缀一定挂，用 `in` 包含匹配 |
| 用 sleep 等结果 | 换显式等待等 `.topic-title` 可见 |
| 加断言版漏 `import time` | 用了 `time.sleep` 却忘了 import（课程笔误） |
| Java 版同时 import 了 assertEquals 又用 assertThat | 二选一，别混（课程 import 冗余） |

【扩展知识】
Java 侧两种断言风格：
- JUnit 原生：`assertEquals(expected, actual)`（**期望在前**，顺序坑，Ch04 讲过）
- Hamcrest：`assertThat(actual, containsString(x))`（**实际在前**，可读性更好）

课程 Java 版用的是 Hamcrest 的 `assertThat` + `containsString`，同时 import 了 `assertEquals` 但没用——这是"复制模板没删干净"的痕迹，实际写一个即可。

【我的理解】
> （这条用例最终能被判定"通过/失败"的关键是哪一行？如果把它删掉，这条用例还剩下什么价值？）

| 模块 | 核心内容 | 面试权重 |
|------|----------|----------|
| 产品分析 | 产品/功能/URL，先明确"测什么" | ★★☆☆☆ |
