## 一、异常截图场景与实现原理

### 知识点 1：为什么要"异常自动截图" + 装饰器是什么

【课程原话/定义】

**场景：**
- 增加自动化测试代码的可测性
- 丰富报告

**实现原理：**
- 装饰器
- 自动化关键数据记录：截图 / 日志 / page_source

【为什么？】
这一章是 Ch13「失败证据链」的**自动化落地**。Ch13 讲清了"失败要留证"（日志回答"做到哪"、截图回答"长什么样"、page_source 回答"元素在哪"），但那里是**手动在代码里加**。本章要解决的是：**怎么让"留证"这件事自动发生，且不污染每一条用例。**

答案就是**装饰器（decorator）**。装饰器是 Python 的语法糖：

```python
@ui_exception_record
def test_web(self):
    ...

# 等价于
def test_web(self):
    ...
test_web = ui_exception_record(test_web)
```

装饰器"接收一个函数、返回一个新函数"，在调用原函数的**前后或异常时**插入额外逻辑。"异常自动留证"就是一个典型的**横切关注点**——它和"这条用例具体测什么"无关，是所有用例共用的能力。用装饰器可以零侵入地套在任意用例上，而不用在每条用例里复制粘贴 try/except。

【必须掌握】
- 两个目标：增加可测性（失败可观测）+ 丰富报告（证据进 Allure）
- 装饰器本质：`@decorator` = `func = decorator(func)`，在函数调用前后/异常时插入逻辑
- "异常留证"是横切关注点 → 用装饰器统一处理，避免每条用例重复

【企业场景】
你在框架里定义了一个 `@ui_exception_record` 装饰器，团队所有 UI 用例在方法上挂这个装饰器即可。CI 上任何一条用例抛异常，框架自动留日志 + 截图 + page_source 并挂进 Allure 报告，测试同学打开报告就能看到失败现场——这就是"可测性"和"丰富报告"的落地：不用手动重跑复现，不用翻服务器日志。

【面试考察】
面试官："怎么实现'用例失败自动截图'？"

参考回答框架：
1. 用装饰器：`@decorator` 包裹测试方法，在 try/except 里捕获异常
2. 捕获后做三件事：打日志 + 截图 + 存 page_source，再挂进 Allure
3. 关键：记录完必须 `raise e` 重新抛出，否则用例会"假通过"
4. 好处：横切关注点统一处理，用例代码零侵入、不重复

【易错点】

| 误区 | 纠正 |
|------|------|
| 在每条用例里复制 try/except 留证 | 用装饰器统一处理，横切关注点抽离 |
| 以为装饰器是"调用时自动执行" | 装饰器在**定义时**执行一次，把函数替换成新函数 |

【我的理解】
> （"异常留证"为什么是"横切关注点"？如果不用装饰器、每条用例里都写 try/except 截图，会带来什么维护问题？）

## 二、装饰器实现代码拆解

### 知识点 2：ui_exception_record 装饰器逐行拆解

【课程原话/定义】

```python
def ui_exception_record(func):
    def run(*args, **kwargs):
        self = args[0]
        try:
            return func(*args, **kwargs)
        except Exception as e:
            # 日志
            logger.warning("执行过程中发生异常")
            # page_source
            timestamp = int(time.time())
            image_path = f"./images/image_{timestamp}.PNG"
            page_source_path = f"./page_source/{timestamp}_page_source.html"
            with open(page_source_path, "w", encoding="u8") as f:
                f.write(self.driver.page_source)
            # 截图
            self.driver.save_screenshot(image_path)
            # 挂进 Allure 报告
            allure.attach.file(image_path, name="image",
                               attachment_type=allure.attachment_type.PNG)
            allure.attach.file(page_source_path, name="page_source",
                               attachment_type=allure.attachment_type.TEXT)
            raise e
    return run


# 错误的用例（故意找不存在的元素 su11）
class TestWeb:
    def setup_class(self):
        self.driver = webdriver.Chrome()

    @ui_exception_record
    def test_web(self):
        self.driver.get("https://www.baidu.com/")
        self.driver.find_element(By.ID, "su11")   # 这里会抛 NoSuchElementException

    def teardown_class(self):
        self.driver.quit()
```

【为什么？】
逐行拆解四个关键点：

1. **`def run(*args, **kwargs)` 是"包装函数"**：装饰器返回它，以后调用 `test_web` 实际是调用 `run`。`*args, **kwargs` 原样透传，保证装饰器对任何签名的方法都通用。

2. **`self = args[0]` 是拿被测实例**：被装饰的是实例方法 `test_web(self)`，Python 调用时第一个参数自动传 `self`，所以 `args[0]` 就是 `TestWeb` 实例。通过它才能拿到 `self.driver` 去做截图、取 page_source。这是"装饰器套在方法上"的关键技巧，也是脆弱点（见知识点 3）。

3. **`try: return func(...)`**：正常时直接执行原方法并返回，装饰器"透明"不干扰。

4. **`except Exception as e` 里记录，最后 `raise e`**：捕获异常后先留证（日志→page_source→截图→挂 Allure），再 `raise e` **重新抛出**。这一行最关键——如果不 `raise`，异常被吞掉，用例会变成"绿"（假通过），自动化就失去了意义。

【必须掌握】
- `run(*args, **kwargs)` 包装函数 + 原样透传
- `self = args[0]`：装饰实例方法时，第一个参数是 self
- `try/except` + 三件套（日志/page_source/截图）+ Allure attach
- **`raise e` 重新抛出**：记录完仍要失败，否则用例假通过

【企业场景】
你在框架里写这个装饰器时，最容易被新人问的一句是"为什么 except 里最后还要 raise e"。答案：装饰器只负责"留证"，不负责"判对错"——用例该失败还是失败。留证是给排查用的，不是把失败洗成通过。这条规矩一旦破了（忘记 raise），整个自动化会静默变成"全绿"，比没有自动化还危险。

【面试考察】
面试官："这个装饰器里 `self = args[0]` 是什么意思？为什么最后要 `raise e`？"

参考回答框架：
1. `self = args[0]`：装饰器套在实例方法上，`*args` 第一个元素就是实例 self，靠它拿 driver
2. `raise e`：记录完证据后重新抛出异常，保证用例仍然失败
3. 不 raise 的后果：异常被吞，用例"假通过"，自动化失效
4. 留证 vs 判定分离：装饰器只留证，判定交给测试框架

【易错点】

| 误区 | 纠正 |
|------|------|
| except 里只留证、忘了 `raise e` | 用例假通过，自动化静默失效，最危险 |
| 以为 `self = args[0]` 对任何函数都成立 | 只在"装饰实例方法"时成立（见知识点 3） |
| `encoding="u8"`（课程写法） | 应为 `"utf-8"`；u8 是可用别名但不规范 |

【我的理解】
> （为什么"忘记 raise e"比"不写这个装饰器"更危险？从"自动化测试的信任度"角度想。）

## 三、关键细节与坑

### 知识点 3：目录、attach 类型、self 假设三个坑

【为什么？】
这段代码有三个容易被忽略的坑，都是实战里会真实踩到的：

**坑 1：目录没建 → FileNotFoundError**
`save_screenshot(image_path)` 和 `open(page_source_path, "w")` 都要求**目录已存在**。课程代码里 `./images` 和 `./page_source` 目录并没有提前创建，直接跑会报 `FileNotFoundError`。这是 Ch13 讲过的同一个坑——截图前要 `os.makedirs(exist_ok=True)` 建目录，或者框架初始化时统一建好。

**坑 2：page_source 用 TEXT 还是 HTML 类型 attach**
`allure.attachment_type` 决定了报告里怎么展示附件。page_source 本质是 HTML，用 `HTML` 类型 attach 能在报告里**渲染成页面**；课程注释掉了 HTML 版、改用了 `TEXT`，报告里就只能看到一堆 HTML 源码文本。两者都能留证，但 HTML 类型更适合"看页面结构"。

**坑 3：`self = args[0]` 是脆弱假设**
这个写法只在"装饰器直接套在实例方法上"时成立。如果把 `@ui_exception_record` 挂到 `@staticmethod` 或普通函数上，`args[0]` 就不是 self，代码会崩。更稳的写法是显式接收 self（如 `def run(self, *args, **kwargs)`），但通用性会下降——这里需要权衡"通用"和"明确"。

【必须掌握】
- 截图/写文件前先确保目录存在（`os.makedirs(exist_ok=True)`）
- `allure.attachment_type.HTML`（可渲染）vs `TEXT`（纯文本），page_source 用 HTML 更合适
- `self = args[0]` 只在装饰实例方法时成立，是脆弱假设

【企业场景】
你在框架里把 `@ui_exception_record` 写好后，第一次跑 CI 全报 `FileNotFoundError`——因为 images 和 page_source 目录在干净的 CI 机器上不存在。教训：留证目录要在框架启动时（conftest.py 或装饰器内部）统一 `os.makedirs(exist_ok=True)`，不能假设目录已经在。这类"本地能跑、CI 上崩"的环境差异，是自动化上线的典型坑。

【面试考察】
面试官："这个装饰器在生产环境会遇到什么问题？"

参考回答框架：
1. 目录问题：CI 干净环境没有 images/page_source 目录，save_screenshot 报错 → 统一 os.makedirs
2. attach 类型：page_source 用 HTML 能渲染、TEXT 只是源码文本
3. self 假设：装饰器只适用于实例方法，挂错地方会崩
4. 环境差异：本地能跑 ≠ CI 能跑，留证逻辑要做健壮性处理

【易错点】

| 误区 | 纠正 |
|------|------|
| 假设 images/page_source 目录已存在 | 用 `os.makedirs(exist_ok=True)` 统一建目录 |
| page_source 用 TEXT 类型 attach | 用 HTML 类型才能在报告里渲染成页面 |
| 装饰器套在 staticmethod/普通函数上 | `self = args[0]` 不再成立，会崩 |

【扩展知识】
装饰器还有个细节：`run` 没加 `functools.wraps(func)`，会丢失原函数的 `__name__`、`__doc__` 等元信息（pytest 取用例名、allure 显示标题时可能受影响）。规范的写法是在 `run` 上加 `@functools.wraps(func)`。

【我的理解】
> （三个坑里，"目录没建"和"本地能跑、CI 崩"是什么关系？为什么"留证逻辑本身报错"会让排查更麻烦？）

## 四、两种"失败自动留证"方式对比

### 知识点 4：装饰器 vs fixture teardown

【为什么？】
Ch13 讲的是在 **pytest fixture 的 teardown 里**判断用例失败就截图，本章用**装饰器**实现。这是"失败自动留证"的两种主流做法，各有适用场景：

| 维度 | 装饰器（本章） | fixture teardown（Ch13） |
|------|---------------|--------------------------|
| 依赖 | 只依赖 Python 装饰器，**不绑框架** | 依赖 pytest 的 fixture / request |
| 触发点 | 方法抛异常时（try/except） | 用例结束后，teardown 阶段查结果 |
| 判失败方式 | 捕获 Exception | `request.node` 查用例结果 |
| 适用 | 想脱离 pytest 复用、挂任意方法 | 已在 pytest 生态里，用 fixture 统一收口 |
| 侵入性 | 用例方法上挂 `@` 一行 | 用例方法零改动，conftest 统一配 |

一句话选型：**在 pytest 项目里，fixture teardown 更"原生"（用例零侵入）；装饰器更"通用"（不绑框架，可挂任意函数）**。两者本质一样——都是把"失败留证"这个横切关注点抽离出来，只是挂载点不同。

【必须掌握】
- 两种方式：装饰器（try/except 捕获）vs fixture teardown（用例结束查结果）
- 选型：pytest 项目 fixture 更原生，跨框架/通用场景装饰器更灵活
- 共同本质：把"失败留证"横切关注点从用例里抽离

【企业场景】
你在一个纯 pytest 项目里，通常会选 fixture teardown（conftest.py 统一配，用例零改动）；但如果公司框架不基于 pytest（或要复用到接口测试、脚本任务），装饰器更合适。面试时能说出"两种方式 + 各自的适用场景 + 共同本质"，比只会一种更能体现框架设计能力。

【面试考察】
面试官："失败自动截图，除了装饰器还有别的方式吗？"

参考回答框架：
1. 两种：装饰器（try/except）和 fixture teardown（pytest 用例结束查结果）
2. fixture teardown 更 pytest 原生，用例零改动；装饰器不绑框架更通用
3. 两者本质相同：抽离"失败留证"横切关注点
4. 项目里按"是否绑定 pytest / 是否要复用"来选

【易错点】

| 误区 | 纠正 |
|------|------|
| 只知道一种方式 | 两种都要会，面试问"还有别的方式吗"能接上 |
| 以为装饰器只能在 pytest 里用 | 装饰器不绑框架，普通脚本也能用 |

【我的理解】
> （"装饰器"和"fixture teardown"两种方式，本质相同的点是什么？如果你们项目要同时跑 UI 和接口自动化，你会选哪种方式统一留证？为什么？）
