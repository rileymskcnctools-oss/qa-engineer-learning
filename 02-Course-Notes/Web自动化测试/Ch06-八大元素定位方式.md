## 一、为什么定位是核心

### 知识点 1：定位的定义与四个学习理由

【课程原话/定义】
在 Web 自动化测试中，**定位**是指在测试过程中定位网页上的元素位置，例如按钮、文本框、下拉菜单等，以便进行后续操作。定位是自动化测试中**至关重要**的步骤，它使测试工具能够准确找到并与页面上的元素进行交互，从而模拟用户的实际行为。

为什么要学习定位：

1. **与页面元素交互**：测试脚本需要与页面上的元素进行交互，如点击按钮、输入文本等
2. **验证应用程序行为**：定位方式的准确性直接影响测试脚本对页面元素的操作
3. **提高测试效率**：Web 页面结构可能随时更改（ID、Class Name 可能变化），掌握不同定位方式可以在属性变化时灵活修改脚本而不影响稳定性
4. **提高测试脚本的可维护性**：如果只依赖一种定位方式，页面结构变化时脚本可能失效；多掌握定位方式可以按情况选择最合适的

【为什么？】
把这四条读透，会发现它们其实在说同一件事：**定位器质量 = 脚本寿命**。

UI 自动化脚本"腐烂"的原因几乎从来不是逻辑写错了，而是定位器失效。一条脚本的生命周期通常是：

```
写完能跑（第 1 天）→ 前端改了个 class（第 30 天）→ 脚本失败
   → 有人修 or 没人修 → 没人修就被注释掉 → 整个套件慢慢死掉
```

所以定位这一章的真正目标不是"记住八种写法"（那是 10 分钟的事），而是**建立选择标准**：面对一个元素，能判断哪种定位方式最不容易坏。这个判断力是 Ch03 里提过的定位器优先级，本章要把它落到八种方式上。

另外一个认知：Selenium 的 API 只有两大类——`driver.xxx()` 操作浏览器（Ch05），`element.xxx()` 操作元素。而 `find_element` 是这两类之间**唯一的桥**。桥没搭好，后面全废。

【必须掌握】
- 定位 = 找到页面元素，是"操作元素"和"断言元素"的前提
- 定位器质量决定脚本寿命，是 UI 自动化维护成本的主要来源
- 学多种定位方式的目的：页面变化时能换一种稳定的写法
- `find_element` 是"浏览器操作"与"元素操作"之间的桥梁

【企业场景】
你接手一个"半死"的自动化项目：120 条用例只有 40 条能跑。逐条排查发现 70% 的失败是 `NoSuchElementException`，因为前端半年内做了两次改版，脚本里大量 `class_name="btn btn-primary"` 和绝对 XPath 全失效。你的整改方案不是"逐条修"，而是：①把定位器统一收进 PO 层 ②按优先级换成稳定定位 ③推动前端为关键元素加 `data-test-id`。三步下来，下次改版只需改 PO 层一处。

【面试考察】
面试官："UI 自动化最难维护的地方在哪？你怎么解决？"

参考回答框架：
1. 最难在**元素定位失效**：前端改版、动态 id、结构调整都会让脚本失败
2. 治标：选稳定定位器（语义 id / data-test-id > name > 相对 CSS > 文本）
3. 治本（工程化）：定位器集中在 PO 层，改一处生效全局
4. 治根（协作）：推动前端为关键元素补 `data-test-id`，把定位契约化
5. 兜底：失败自动截图 + 保存 page_source，快速区分"元素变了"和"功能坏了"

【易错点】

| 误区            | 纠正                             |
| ------------- | ------------------------------ |
| 定位就是"能找到元素就行" | 还要"下次改版还能找到"，稳定性才是重点           |
| 会 XPath 就够了   | XPath 万能但不一定最稳，优先用 id/name/CSS |
| 定位失败就加 sleep  | 先区分"没出现"（等待问题）和"找错了"（定位问题）     |

【我的理解】
> （为什么说"定位器质量 = 脚本寿命"？回想 Ch03 里那个 `#ember77`，它会在什么时候失效？）

### 知识点 2：Selenium 八大定位方式

【课程原话/定义】

| 定位方式                   | 描述                                    |
| ---------------------- | ------------------------------------- |
| `class name`           | class 属性对应的值                          |
| `css selector`（**重点**） | css 表达式                               |
| `id`（**重点**）           | id 属性对应的值                             |
| `name`（**重点**）         | name 属性对应的值                           |
| `link text`            | 查找其可见文本与搜索值匹配的锚元素（`<a>`）              |
| `partial link text`    | 查找其可见文本**包含**搜索值的锚元素；如果多个元素匹配，只会选择第一个 |
| `tag name`             | 标签名称                                  |
| `xpath`（**重点**）        | xpath 表达式                             |

课程标注四个重点：**css selector、id、name、xpath**。

统一写法：

```python
# Python
driver.find_element(By.CLASS_NAME, "information")

// Java
driver.findElement(By.className("information"));
```

【为什么？】
八种为什么偏偏这四个是重点？因为它们的**唯一性和稳定性**最好：

| 定位方式 | 唯一性 | 稳定性 | 结论 |
|---------|--------|--------|------|
| `id` | 规范上页面唯一 | 取决于是否语义化（`login-btn` 稳 / `ember77` 不稳） | 🥇 首选（语义化 id） |
| `name` | 表单元素内基本唯一 | 与后端字段绑定，很少改 | 🥈 表单首选 |
| `css selector` | 可组合到唯一 | 相对定位可控，写法简洁、执行快 | 🥉 通用主力 |
| `xpath` | 可组合到唯一 | 能力最强（支持文本、父级、轴） | ✅ 复杂场景兜底 |
| `class name` | 常常**不唯一**（一个页面几十个相同 class） | 组件库 class 频繁变（`el-input__inner`） | ⚠️ 谨慎 |
| `tag name` | 几乎不唯一（一页几十个 `<a>`、`<div>`） | —— | ❌ 只用于批量取元素 |
| `link text` | 文本唯一时可用，只对 `<a>` 生效 | 文案/多语言一改就失效 | ⚠️ 直观但脆弱 |
| `partial link text` | 更容易命中多个（取第一个） | 同上，且更模糊 | ⚠️ 少用 |

关键点：**`class name` 和 `tag name` 之所以危险，不是因为"找不到"，而是因为"找到了错的那个"**。Selenium 在多个匹配时**静默返回第一个**，不报错——于是你的脚本点在了错误的按钮上，还显示"通过"。这类问题比报错难查十倍。

`link text` / `partial link text` 还有一个硬限制：**只能定位 `<a>` 标签**（锚元素）。用它去找按钮 `<button>` 永远找不到，新手常在这里卡半天。

【必须掌握】
- 八种方式名称与含义（面试直接问"Selenium 八大定位方式"）
- 四个重点：`id`、`name`、`css selector`、`xpath`
- `link text` / `partial link text` **只对 `<a>` 标签生效**
- 多个元素匹配时 `find_element` **返回第一个且不报错**（隐蔽坑）
- `class name` 传的是**单个 class 值**，不能传 `"btn btn-primary"` 这种复合值（会报 invalid selector）

【企业场景】
一个后台管理系统用 Element UI，页面上所有输入框都是 `class="el-input__inner"`，一页十几个。用 `By.CLASS_NAME, "el-input__inner"` 定位"手机号"输入框，脚本不报错，但填的是页面第一个输入框（用户名）——断言在后面才失败，排查时一头雾水。正确做法是用 CSS 从**语义化的父级**往下定位：

```python
driver.find_element(By.CSS_SELECTOR, "#phone-form .el-input__inner")   # 限定父级作用域
# 或者用 XPath 借助 label 文本锚定
driver.find_element(By.XPATH, "//label[text()='手机号']/following::input[1]")
```

【面试考察】
面试官："Selenium 有哪几种定位方式？你最常用哪个？为什么？"

参考回答框架：
1. 八种：id、name、class name、tag name、link text、partial link text、css selector、xpath
2. 常用：优先 id（语义化）/ name，通用场景用 css selector，复杂场景（要匹配文本、找父级）用 xpath
3. 少用 class name / tag name：不唯一，容易匹配到错误元素且**不报错**
4. link text 只能定位 `<a>`，且文案变更就失效
5. 加分：定位器要写进 PO 层集中管理；最理想是推动前端加 `data-test-id`

【易错点】

| 误区 | 后果 | 纠正 |
|------|------|------|
| `By.CLASS_NAME, "btn btn-primary"` | `InvalidSelectorException` | 复合 class 用 CSS：`.btn.btn-primary` |
| 用 `link text` 找按钮 | 永远找不到 | 只对 `<a>` 有效，按钮用 CSS/XPath |
| 用 `class name` / `tag name` 定位唯一元素 | 静默点错元素 | 加父级限定或换 id/CSS |
| 以为多个匹配会报错 | 静默取第一个，假通过 | 用 `find_elements` 确认数量 |
| `partial link text` 图省事 | 命中多个只取第一个 | 尽量用完整文本或 CSS |

【我的理解】
> （为什么"找到了错的元素"比"报错找不到元素"更可怕？想想哪种问题排查更花时间）

## 二、对照 HTML 逐个练

### 知识点 3：课程 HTML 示例与八种写法

【课程原话/定义】
课程给出一段 HTML 用来练习定位（简化后的关键部分）：

```html
<h2>Contact Selenium</h2>
<form action="/action_page.php">
  <input type="radio" name="gender" value="m" />Male
  <input type="radio" name="gender" value="f" />Female

  <label for="fname">First name:</label>
  <input class="information" type="text" id="fname" name="fname" value="Jane" />

  <label for="lname">Last name:</label>
  <input class="information" type="text" id="lname" name="lname" value="Doe" />

  <label for="newsletter">Newsletter:</label>
  <input type="checkbox" name="newsletter" value="1" />

  <input type="submit" value="Submit" />
</form>

<p>
  To know more about Selenium, visit the official page
  <a href="www.selenium.dev">Selenium Official Page</a>
</p>
```

课程给出的八种写法：

```python
driver.find_element(By.ID, "lname")                                  # id：Last name 输入框
driver.find_element(By.CLASS_NAME, "information")                    # class：两个输入框都匹配 → 取第一个
driver.find_element(By.CSS_SELECTOR, "#fname")                       # css：First name 输入框
driver.find_element(By.NAME, "newsletter")                           # name：复选框
driver.find_element(By.LINK_TEXT, "Selenium Official Page")          # 完整链接文本
driver.find_element(By.PARTIAL_LINK_TEXT, "Official Page")           # 部分链接文本
driver.find_element(By.TAG_NAME, "a")                                # 标签名：页面第一个 <a>
driver.find_element(By.XPATH, "//input[@value='f']")                 # xpath：Female 单选框
```

> ⚠️ **课程原文有两处笔误，要注意**：
> 1. ID 小节写的是 `driver.find_element(By.ID, "information")`，但 `information` 是 **class 值**不是 id。按上文"使用 id 来识别姓氏（Last Name）字段"的描述，正确写法应为 `By.ID, "lname"`。
> 2. 表格里的 `link test` / `partial link test` 应为 `link text` / `partial link text`。

【为什么？】
逐个对照这段 HTML，能看出每种定位方式的**适用边界**：

| 目标元素 | 最佳定位 | 为什么不用别的 |
|---------|---------|--------------|
| Last name 输入框 | `By.ID, "lname"` | 有唯一 id，直接用最稳 |
| First name 输入框 | `By.ID, "fname"` 或 `By.CSS_SELECTOR, "#fname"` | 两者等价，CSS 更通用 |
| Newsletter 复选框 | `By.NAME, "newsletter"` | **它没有 id**，只有 name → name 是唯一选择 |
| Female 单选框 | `By.XPATH, "//input[@value='f']"` | 两个单选框 name 都是 `gender`，**必须靠 value 区分** → 用 name 会取到 Male |
| Submit 按钮 | `By.CSS_SELECTOR, "input[type='submit']"` | 它没有 id/name，只能靠属性组合 |
| 官网链接 | `By.LINK_TEXT, "Selenium Official Page"` | 它是 `<a>`，文本唯一，link text 最直观 |
| 两个 information 输入框 | `find_elements(By.CLASS_NAME, "information")` | 目标是**两个**元素，要用复数方法 |

最值得琢磨的是 **Female 单选框**：`name="gender"` 在 Male 和 Female 上是**相同的**（这是单选按钮的规范——同组同 name）。这说明"用 name 定位"在单选/复选组里天然会撞车，必须叠加 value 或结合父级。这就是"没有一种定位方式万能"的最好例证。

同样值得注意的是 `By.CLASS_NAME, "information"`：它匹配 **fname 和 lname 两个输入框**，`find_element` 只返回第一个（fname）。如果你的意图是 lname，就会静默填错框。

【必须掌握】
- 看 HTML 就能选定位：有唯一 id → id；无 id 有 name → name；都没有 → CSS 属性组合 / XPath
- 单选/复选组同 name，必须叠加 `value` 区分
- `find_element` 单数 → 返回**第一个** WebElement，找不到抛 `NoSuchElementException`
- `find_elements` 复数 → 返回**列表**，找不到返回**空列表 `[]`**（不报错）
- CSS 的 `#id` = id 定位，`.class` = class 定位（CSS 能覆盖 id/class/name/属性）

【企业场景】
测一个注册表单，一次填完所有字段。这是"看 HTML 选定位"的真实练习：

```python
def test_register_form(driver, wait):
    driver.get("https://example.com/register")
    driver.find_element(By.ID, "fname").send_keys("张")                       # 有 id
    driver.find_element(By.ID, "lname").send_keys("三")
    driver.find_element(By.XPATH, "//input[@name='gender'][@value='f']").click()   # 组内靠 value 区分
    driver.find_element(By.NAME, "newsletter").click()                        # 只有 name
    driver.find_element(By.CSS_SELECTOR, "input[type='submit']").click()      # 靠属性组合

    # 断言：输入框的值要用 get_attribute("value")，不是 .text（Ch04 知识点 4）
    assert driver.find_element(By.ID, "fname").get_attribute("value") == "张"
```

顺手记一个校验技巧：**在 Chrome F12 的 Elements 面板按 Ctrl+F，可以直接输入 CSS 或 XPath 表达式验证**，右侧会显示 "1 of 3" 这样的匹配计数。写定位器时先在这里确认**匹配数是 1**，再写进代码 —— 这一步能消灭大部分"点错元素"的问题。

【面试考察】
面试官："给你一个没有 id、没有 name 的按钮，你怎么定位？"

参考回答框架：
1. 先看有没有其他稳定属性：`type`、`data-*`、`aria-label` → CSS 属性选择器 `button[data-test-id='submit']`
2. 再看有没有稳定的文本 → XPath 文本定位 `//button[text()='提交']`（注意文案变更风险）
3. 再考虑从**语义化父级**往下限定作用域：`#order-form button.primary`
4. 绝对不用：整条绝对 XPath（`/html/body/div[3]/...`）、动态生成的 id
5. 最优解是推动前端加 `data-test-id`，把定位变成前后端约定

【易错点】

| 误区 | 后果 | 纠正 |
|------|------|------|
| 单选组用 `By.NAME, "gender"` | 永远选中第一个（Male） | 叠加 value：`//input[@name='gender'][@value='f']` |
| 用 `find_element` 找一组元素 | 只拿到第一个 | 要多个用 `find_elements` |
| 用 `find_elements` 后直接 `[0]` 不判空 | 空列表 → `IndexError` | 先判断 `len(...) > 0` 或改用 `find_element` |
| 写完定位器直接跑脚本试 | 反复失败、浪费时间 | 先在 F12 Ctrl+F 里验证匹配数为 1 |
| 断言输入框用 `.text` | 空字符串 | `get_attribute("value")` |

【扩展知识】
`find_element` vs `find_elements` 完整对比（面试常问）：

| 对比项 | `find_element`（单数） | `find_elements`（复数） |
|--------|---------------------|----------------------|
| 返回值 | 一个 WebElement | list[WebElement] |
| 找不到 | 抛 `NoSuchElementException` | 返回 `[]`，**不报错** |
| 多个匹配 | 静默返回第一个 | 全部返回 |
| 典型用途 | 操作单个元素 | 统计数量、遍历列表、**判断元素是否存在** |

由此得到一个实用技巧——**判断元素是否存在不要用 try/except，用 find_elements**：

```python
# 笨写法：靠异常控制流程
try:
    driver.find_element(By.ID, "popup")
    exists = True
except NoSuchElementException:
    exists = False

# 好写法：靠列表长度（更快、更清晰）
exists = len(driver.find_elements(By.ID, "popup")) > 0
```

【我的理解】
> （课程 HTML 里的 Female 单选框，为什么不能只用 `By.NAME, "gender"` 定位？这个例子说明了什么普适规律？）

### 知识点 4：定位器优先级与验证方法

【课程原话/定义】
课程标注 `id`、`name`、`css selector`、`xpath` 为重点，并在"为什么要学习定位"中强调：页面结构可能随时更改（ID、Class Name 可能变化），掌握多种定位方式可以在属性变化时灵活修改脚本而**不影响稳定性**。

【为什么？】
把 Ch03 的定位器优先级和本章八大方式合并，形成一张**可直接用于工作的决策表**：

| 优先级 | 定位写法 | 例子 | 适用条件 |
|--------|---------|------|---------|
| 1️⃣ | `data-test-id` 等测试专用属性（CSS） | `[data-test-id='submit-btn']` | 前端愿意配合加（最理想） |
| 2️⃣ | 语义化 `id` | `By.ID, "login-btn"` | id 是人写的、有含义、不含随机串 |
| 3️⃣ | `name` | `By.NAME, "username"` | 表单元素，与后端字段绑定 |
| 4️⃣ | CSS 属性/相对组合 | `#login-form input[type='password']` | 有稳定父级或属性 |
| 5️⃣ | XPath 文本定位 | `//button[text()='登录']` | 无属性可用，但文案可能变 |
| 6️⃣ | class name（单个语义化 class） | `.login-submit` | class 是业务语义而非样式框架生成 |
| ❌ | 动态 id / 绝对 XPath / tag name | `#ember77`、`/html/body/div[3]/a`、`By.TAG_NAME,"div"` | **永远不要用** |

判断一个 id 是否"语义化"的土办法：**读一遍能不能猜出它是什么**。`login-btn`、`fname`、`submit` 可以；`ember77`、`react-select-3-input`、`el-id-8532-2` 不行——后者一定是框架运行时生成的。

写完定位器**必须验证**，三种方法从快到慢：

| 方法 | 操作 | 优点 |
|------|------|------|
| F12 Elements → Ctrl+F | 直接粘贴 CSS 或 XPath，看匹配计数 | 最快，能看到"1 of N" |
| F12 Console | `document.querySelectorAll("选择器").length` | 精确拿到 CSS 匹配数 |
| F12 Console（XPath） | `$x("//input[@name='gender']").length` | 验证 XPath 匹配数 |

**匹配数必须是 1**，如果是 2 以上，说明定位器不够精确 —— 这时脚本虽然能跑，但随时可能操作到错误元素。

【必须掌握】
- 决策顺序：data-test-id > 语义 id > name > CSS 相对组合 > XPath 文本 > 语义 class > ❌ 动态 id/绝对路径
- 判断 id 是否可靠：能不能读懂它的含义
- 写完必须验证匹配数为 1（F12 Ctrl+F / `$x()` / `querySelectorAll`）
- 定位器要集中放在 PO 层，不要散落在用例里

【企业场景】
你在项目里定了一条 code review 规则："**PR 里出现绝对 XPath 或含数字后缀的 id，一律打回**"。同时在 PO 层写成常量：

```python
class LoginPage:
    # 定位器集中定义：改版只改这里
    USERNAME = (By.CSS_SELECTOR, "[data-test-id='username']")
    PASSWORD = (By.CSS_SELECTOR, "[data-test-id='password']")
    SUBMIT = (By.CSS_SELECTOR, "[data-test-id='login-submit']")

    def login(self, user, pwd):
        self.driver.find_element(*self.USERNAME).send_keys(user)
        self.driver.find_element(*self.PASSWORD).send_keys(pwd)
        self.driver.find_element(*self.SUBMIT).click()
        return HomePage(self.driver)          # 返回下一个页面对象
```

这就是 PO 模式的雏形：**定位器与用例逻辑解耦**。以后前端改了登录页，只需改这三行常量，所有用到登录的用例自动生效。

【面试考察】
面试官："你怎么写一个不容易失效的定位器？写完怎么验证？"

参考回答框架：
1. 优先级：测试专用属性（data-test-id）→ 语义 id → name → 相对 CSS → XPath 文本
2. 绝不用：框架生成的动态 id、绝对 XPath、纯 tag name
3. 验证：F12 Ctrl+F 粘表达式看匹配数必须为 1；或 Console 里 `$x()` / `querySelectorAll().length`
4. 工程化：定位器集中在 PO 层，改版只改一处
5. 协作：关键元素推动前端加 `data-test-id`，把定位变成契约

【易错点】

| 误区 | 后果 | 纠正 |
|------|------|------|
| 从 F12 "Copy full XPath" 直接粘贴 | 绝对路径，结构一变就废 | 自己写相对 CSS/XPath |
| 定位器写在用例里，多处重复 | 改版要改几十处 | 抽到 PO 层常量 |
| 定位器匹配到多个也不管 | 隐蔽的"点错元素" | 验证匹配数为 1 |
| 认为 XPath 最强所以全用 XPath | 可读性差、部分场景性能略低 | 能用 CSS 就用 CSS，XPath 留给文本/父级场景 |

【扩展知识】
> 本章是"方法层"；选型原则（七条）+ 特殊场景（alert/日期控件/文件上传）的"策略层"专章见 [[Ch09-自动化测试定位策略]]。

1. **CSS 与 XPath 的能力边界**（后续章节会专门展开）：CSS 简洁、执行快，但**不能按文本内容匹配**、不能往父级找；XPath 能按文本（`text()`）、能找父级和兄弟（轴），是复杂场景的兜底。所以"CSS 为主、XPath 补位"是常见规范。
2. **Selenium 4 的相对定位器**（Relative Locators，新特性）：按视觉位置定位，适合"某个 label 右边的输入框"这种描述。

```python
from selenium.webdriver.support.relative_locator import locate_with

password_input = driver.find_element(
    locate_with(By.TAG_NAME, "input").below({By.ID: "username"})
)
```

可用方法：`above` / `below` / `to_left_of` / `to_right_of` / `near`。它依赖渲染位置，页面布局大改时也会失效，属于"实在没有属性可用"时的选项。

## 今日课程总结

| 模块 | 核心内容 | 面试权重 |
|------|----------|----------|
| 定位的价值 | 定位器质量 = 脚本寿命；UI 自动化维护成本主要来自定位失效 | ★★★★☆ |
| 八大定位方式 | id / name / class name / tag name / link text / partial link text / css selector / xpath | ★★★★★ |
| 四个重点 | **id、name、css selector、xpath** | ★★★★★ |
| link text 限制 | 只对 `<a>` 标签生效；文案/多语言变更即失效 | ★★★☆☆ |
