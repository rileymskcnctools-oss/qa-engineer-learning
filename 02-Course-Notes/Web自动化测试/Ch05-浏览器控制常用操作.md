## 一、浏览器控制总览

### 知识点 1：六个核心浏览器控制方法

【课程原话/定义】
在 Web 自动化测试中，经常需要模拟用户在浏览器中的操作来完成一些测试任务，通过编程方式操作和控制浏览器的行为，以便自动化执行各种操作。

| 方法                      | 操作          | 使用场景         |
| ----------------------- | ----------- | ------------ |
| `get()`                 | 打开浏览器（访问网址） | web 自动化测试第一步 |
| `refresh()`             | 浏览器刷新       | 模拟浏览器刷新      |
| `back()`                | 浏览器退回       | 模拟退回步骤       |
| `maximize_window()`     | 最大化浏览器      | 模拟浏览器最大化     |
| `minimize_window()`     | 最小化浏览器      | 模拟浏览器最小化     |
| `set_window_size(宽, 高)` | 设置浏览器宽和高    | 指定分辨率下测试     |

【为什么？】
先建立一个分类认知，否则这六个方法会记成一盘散沙。它们其实分两类，**用途完全不同**：

| 分类              | 方法                                                          | 本质                 | 是不是测试步骤                |
| --------------- | ----------------------------------------------------------- | ------------------ | ---------------------- |
| **导航类**（改变页面内容） | `get()`、`refresh()`、`back()`、`forward()`                    | 操作浏览器的**地址与历史栈**   | ✅ 是，属于用例步骤             |
| **窗口类**（改变显示形态） | `maximize_window()`、`minimize_window()`、`set_window_size()` | 操作**窗口尺寸**，不改变页面内容 | ❌ 多数不是，属于环境准备（放 setup） |

这个区分很实用：导航类写在测试方法里（它们是业务步骤），窗口类基本都写在 `setup` 里（它们是执行环境的一部分）。新手常把 `maximize_window()` 写在用例中间，其实那不是被测行为。

另一个认知：这些方法都挂在 `driver` 上，属于**"对浏览器"的操作**；而下一章的 `find_element` 是**"对页面元素"的操作**。Selenium 的 API 就是这两大类，先分清层级再记方法。

【必须掌握】
- 六个方法及其分类（导航类 vs 窗口类）
- 导航类写在用例步骤里，窗口类写在 setup 里
- `driver.xxx()` = 操作浏览器；`element.xxx()` = 操作元素（下一章）
- Selenium 4 里还有 `forward()`（前进）与 `driver.title` / `driver.current_url`（读状态）

【企业场景】
一个标准的项目 `conftest.py`：窗口类操作全部集中在 fixture 里，用例里只出现导航和业务操作。

```python
@pytest.fixture
def driver():
    options = webdriver.ChromeOptions()
    d = webdriver.Chrome(options=options)
    d.maximize_window()          # 环境准备，不是测试步骤
    d.implicitly_wait(5)
    yield d
    d.quit()
```

这样写的好处：新增用例时不需要每次重复窗口设置，而且**改分辨率只改一处**（比如后来要求所有用例在 1920×1080 下跑，只动 fixture）。

【面试考察】
面试官："Selenium 里操作浏览器的常用方法有哪些？"

参考回答框架：
1. 导航：`get()` 打开、`refresh()` 刷新、`back()`/`forward()` 后退前进
2. 窗口：`maximize_window()`、`minimize_window()`、`set_window_size(w,h)`
3. 读状态：`driver.title`、`driver.current_url`、`driver.page_source`
4. 结束：`close()` 关当前窗口、`quit()` 关全部并结束会话
5. 补一句实践：窗口设置放 setup 统一管理，用例里只写业务步骤

【易错点】

| 误区 | 纠正 |
|------|------|
| 把 `maximize_window()` 当测试步骤写在用例中间 | 它是环境准备，放 setup / fixture |
| 以为 `set_window_size` 能替代 `maximize_window` | 前者是固定像素，后者跟随屏幕；无头模式下必须用前者 |
| 只会 `get()`，不知道 `back()`/`refresh()` | 这三个是"页面状态类"用例的基础（下面知识点会讲场景） |

【我的理解】
> （为什么"最大化窗口"不算测试步骤？如果把它写进用例，会带来什么维护问题？）

## 二、导航类操作

### 知识点 2：get() 打开网页

【课程原话/定义】

```python
from selenium import webdriver


def window_start():
    # 创建 Chrome 浏览器的选项对象
    options = webdriver.ChromeOptions()
    # 初始化 Chrome 浏览器驱动
    driver = webdriver.Chrome(options=options)
    # 打开网页
    driver.get('https://www.ceshiren.com')
    # 关闭浏览器
    driver.quit()


if __name__ == '__main__':
    window_start()
```

Java 示例：`WebDriver driver = new ChromeDriver(); driver.get("https://ceshiren.com"); driver.quit();`

【为什么？】
这段代码比 Ch02 的 5 行版多了一个东西：**`options = webdriver.ChromeOptions()`**。虽然这里是空的（没加任何参数），但它是通往所有浏览器配置的入口，实际项目里几乎必写：

```python
options = webdriver.ChromeOptions()
options.add_argument("--headless=new")             # 无头模式（CI 必需）
options.add_argument("--window-size=1920,1080")    # 无头下设分辨率
options.add_argument("--start-maximized")          # 启动即最大化
options.add_argument("--disable-gpu")              # 老环境兼容
options.add_argument("--no-sandbox")               # Docker/Linux root 下必需
options.add_experimental_option("detach", True)    # 脚本结束不自动关浏览器（调试用）
driver = webdriver.Chrome(options=options)
```

关于 `get()` 本身有一个关键认知：**它会等待页面的 load 事件完成才返回**，但"load 完成"不等于"你要的内容出来了"——现在的页面大量内容是 Ajax 异步加载的，`get()` 返回后接口可能还在飞。所以 `get()` 之后**紧跟一个显式等待**是标准姿势，而不是假设页面已就绪。

【必须掌握】
- `driver.get(url)`：URL 必须带协议（`https://`），否则 `InvalidArgumentException`
- `ChromeOptions` 是浏览器配置入口，无头/分辨率/沙箱参数都从这里加
- `get()` 等 load 事件完成，但**不保证异步内容已渲染** → 后面接显式等待
- 重复调用 `get()` 会产生历史记录（这是 `back()` 能生效的前提）

【企业场景】
同一套用例要在本地（有头，方便看）和 CI（无头，没图形界面）都能跑，靠环境变量切换：

```python
import os


def build_options():
    options = webdriver.ChromeOptions()
    if os.getenv("CI"):                                  # CI 环境
        options.add_argument("--headless=new")
        options.add_argument("--window-size=1920,1080")  # 无头必须显式设，否则默认 800x600
        options.add_argument("--no-sandbox")             # 容器里 root 运行必需
    else:
        options.add_argument("--start-maximized")        # 本地调试看得清
    return options
```

这段代码解决了一个高频事故：**无头模式默认窗口只有 800×600**，很多元素在这个宽度下被折叠进汉堡菜单，于是"本地过、CI 失败"。不是代码错，是分辨率不同导致页面布局不同。

【面试考察】
面试官："自动化在 CI 上跑和本地跑有什么不同？要注意什么？"

参考回答框架：
1. CI 没有图形界面 → 必须无头模式 `--headless=new`
2. 无头默认分辨率小（800×600）→ 显式 `--window-size=1920,1080`，否则响应式布局变化导致元素找不到
3. 容器里以 root 运行 → 需要 `--no-sandbox`（视镜像而定）
4. 失败排查更难 → 必须加失败截图 + 保存 page_source
5. 环境隔离 → driver 版本与浏览器版本锁定（Ch02 的环境漂移问题）

【易错点】

| 误区 | 后果 | 纠正 |
|------|------|------|
| `driver.get("ceshiren.com")` | `InvalidArgumentException` | 带上 `https://` |
| 认为 `get()` 返回就万事俱备 | 异步内容还没到，元素找不到 | 后接显式等待 |
| 无头模式不设窗口大小 | 默认 800×600，元素被折叠 → CI 专属失败 | `--window-size=1920,1080` |
| 每条用例都 `get()` 同一个首页，靠它"重置状态" | cookie/登录态并不会被清掉 | 需要 `delete_all_cookies()` 或新建会话 |

【我的理解】
> （"本地能跑、CI 失败"你已经见过两个原因了：driver 版本不匹配（Ch02）和无头分辨率（本章）。这两类问题的共同点是什么？）

### 知识点 3：refresh() 刷新页面

【课程原话/定义】

```python
driver.get('https://www.ceshiren.com')
time.sleep(1)
driver.refresh()      # 刷新页面
time.sleep(1)
driver.quit()
```

Java：`driver.navigate().refresh();`

【为什么？】
"刷新"看起来是个鸡毛蒜皮的操作，但它是**一类测试场景的核心动作**——验证"数据到底存下来了没有"：

| 场景 | 为什么必须刷新 |
|------|--------------|
| 提交表单后验证持久化 | 不刷新时页面上的数据可能只存在前端内存里，刷新后还在才说明真的入库了 |
| 验证列表实时更新 | 新增一条数据后刷新，确认列表里出现 |
| 验证缓存/登录态 | 刷新后仍处于登录状态，说明 token/cookie 正确 |
| 复现前端状态 bug | 刷新后页面状态错乱（如筛选条件丢失）是常见前端 bug |

所以"提交 → 刷新 → 再断言"是一个非常有价值的用例模式，能抓到"前端假成功、后端没保存"这类最容易漏的 bug。手工测试里资深测试也会这么干。

一个关键副作用：**刷新后页面上所有元素对象都失效了**。之前用 `find_element` 拿到的变量指向的是旧 DOM 节点，刷新后再用它会抛 `StaleElementReferenceException`（元素引用过期）。这是 UI 自动化第二高频的异常，必须重新定位。

【必须掌握】
- `driver.refresh()` 刷新当前页面
- Java 里刷新/回退/前进都在 `driver.navigate()` 下（Python 直接挂 driver）
- **刷新后必须重新定位元素**，旧引用会 `StaleElementReferenceException`
- 典型用法：提交数据 → 刷新 → 断言数据仍存在（验证真正落库）

【企业场景】
测一个"保存草稿"功能，弱的写法和强的写法差别巨大：

```python
# 弱：只验证前端提示（前端可能只是弹了个 toast，后端并没保存）
save_button.click()
assert "保存成功" in driver.page_source

# 强：刷新后再验证内容还在（证明真的持久化了）
save_button.click()
wait.until(EC.visibility_of_element_located((By.CSS_SELECTOR, ".toast-success")))
driver.refresh()                                    # 关键一步
content = driver.find_element(By.ID, "draft-content").get_attribute("value")   # 必须重新定位
assert content == "我的草稿内容"
```

这个"刷新再断言"的思路，在面试里说出来会明显加分——它说明你知道**前端提示 ≠ 数据落库**。

【面试考察】
面试官："你会怎么验证一个提交功能真的成功了？"

参考回答框架：
1. 第一层：验证前端提示/跳转（最弱，只能证明前端有反应）
2. 第二层：**刷新页面后数据仍在**（证明持久化）
3. 第三层：查数据库/调接口核对（最强，见 [[SQL/README|SQL]] Ch05 Python 操作 MySQL）
4. 说明取舍：UI 层做到第二层通常够用，关键业务（支付/订单）做到第三层
5. 提醒坑：刷新后元素引用失效，必须重新定位

【易错点】

| 误区 | 后果 | 纠正 |
|------|------|------|
| 刷新后继续用旧元素变量 | `StaleElementReferenceException` | 刷新后重新 `find_element` |
| 用 `get(当前URL)` 代替 `refresh()` | 多一条历史记录，且不完全等价（不重发 POST） | 刷新就用 `refresh()` |
| 刷新后立刻断言 | 页面还没加载完 | 刷新后加显式等待 |
| 只验证前端提示就认为通过 | 漏掉"前端假成功"类 bug | 刷新再断言 / 查库核对 |

【扩展知识】
`StaleElementReferenceException` 的三个触发场景（面试常问"什么情况会遇到"）：①页面刷新 ②页面跳转 ③前端局部重渲染（React/Vue 更新了这个节点）。通用解法：**重新定位**，或把"定位 + 操作"封装成一个方法每次重新查（这也是 PO 模式里"属性方法化"的原因）。

【我的理解】
> （为什么"刷新后再断言"比"看到成功提示就断言"更强？你手工测试时有没有做过这个动作？）

### 知识点 4：back() 回退

【课程原话/定义】

```python
driver.get('https://www.ceshiren.com')
driver.find_element(By.XPATH, "//*[text()='类别']").click()
time.sleep(1)
driver.back()          # 回退到上一个界面
time.sleep(1)
driver.quit()
```

Java 示例演示了另一种造历史的方式：连续两次 `driver.get()` 打开不同页面，再 `driver.navigate().back()` 回到第一个页面。

【为什么？】
`back()` 操作的是**浏览器的历史栈**，所以它有个前提：**必须先有历史**。第一次 `get()` 之后直接 `back()` 什么也不会发生（栈里没有上一页）。历史记录的产生方式有两种：多次 `get()`、或者点击链接/按钮发生了页面跳转。

`back()` 的测试价值在于它是**用户真实行为里最容易暴露 bug 的动作**：

| 回退相关的经典 bug | 说明 |
|-----------------|------|
| 回退后表单数据丢失 | 用户填了一半点返回再回来，内容清空 |
| 回退后仍显示登录态 | 退出登录后按返回键，居然还能看到个人信息（**安全漏洞**） |
| 回退后购物车/筛选条件错乱 | 状态管理没处理浏览器历史 |
| 回退导致重复提交 | 返回到支付页再次提交，产生重复订单（资损风险） |

所以"退出登录后点返回，看能否访问隐私页面"是面试里回答"你测过什么有价值的 bug"的绝佳素材——它属于**安全 + 状态管理**交叉的坑，也是业务测试里的常规必测项。

同样注意：回退后页面变了，**元素引用同样失效**，且需要等待新页面加载完成。

【必须掌握】
- `driver.back()` 后退、`driver.forward()` 前进（依赖浏览器历史栈）
- 没有历史时 `back()` 无效果（不报错，静默无操作）—— 容易误判为"代码没生效"
- 产生历史的两种方式：多次 `get()`、页面跳转
- 回退后必须重新定位元素 + 等待加载
- 高价值场景：退出登录后回退、表单填写中回退、支付后回退

【企业场景】
一条真实的安全类用例：

```python
def test_logout_then_back_cannot_access_profile(driver, wait):
    login(driver, "user", "pwd")
    driver.get("https://example.com/profile")            # 访问个人中心
    logout(driver)                                        # 退出登录
    driver.back()                                         # 用户按返回键
    # 断言：应该被拦到登录页，而不是还能看到个人信息
    wait.until(EC.url_contains("/login"))
    assert "手机号" not in driver.page_source
```

这条用例抓到的 bug 属于"高危"级别（未授权访问），而它只用到了本章的一个 `back()`。**API 简单不代表用例价值低——价值来自你设计的场景。**

【面试考察】
面试官："你在自动化里怎么测浏览器回退相关的问题？"

参考回答框架：
1. 先造历史：多次导航或页面跳转，再 `back()`/`forward()`
2. 关注四类场景：登录态失效后回退（安全）、表单数据保留、列表状态/筛选条件、重复提交
3. 技术注意点：回退后元素引用失效需重新定位、要等新页面加载完、无历史时 back 静默无效
4. 加分：这类用例价值高但手工容易漏（因为要额外操作步骤），非常适合自动化固化下来

【易错点】

| 误区 | 后果 | 纠正 |
|------|------|------|
| 首次 `get()` 后直接 `back()` | 无任何反应，误以为代码有问题 | 先制造历史 |
| `back()` 后立刻操作元素 | 页面未加载完 / 元素失效 | 加显式等待 + 重新定位 |
| 用 `get(上一个URL)` 模拟回退 | 不等价：不携带历史状态、表单缓存、滚动位置 | 用 `back()` |
| 认为 `back()` 一定回到上一个 URL | SPA 里可能只是路由变化，页面不整体刷新 | 断言要基于内容/URL 判断而非假设 |

【我的理解】
> （"退出登录后按返回键还能看到个人信息"——这条 bug 属于功能问题还是安全问题？为什么它经常被手工测试漏掉？）

## 三、窗口类操作

### 知识点 5：maximize / minimize / set_window_size

【课程原话/定义】

```python
driver.maximize_window()        # 最大化
driver.minimize_window()        # 最小化
driver.set_window_size(500, 500)  # 设置宽和高
```

课程 `set_window_size` 示例里还用了启动参数：

```python
options = webdriver.ChromeOptions()
options.add_argument("--start-maximized")     # 启动即最大化
driver = webdriver.Chrome(options=options)
driver.get('https://www.ceshiren.com')
driver.set_window_size(500, 500)              # 之后又改成 500x500（后者生效）
```

Java：`driver.manage().window().maximize() / minimize() / setSize(new Dimension(800, 600))`

【为什么？】
窗口尺寸不是"美观问题"，而是**直接决定元素能不能被找到**的问题。原因是现代网页普遍用**响应式布局（Responsive Design）**：

| 窗口宽度 | 页面形态 | 对自动化的影响 |
|---------|---------|--------------|
| ≥1200px（桌面） | 导航栏完全展开 | 能直接定位到"类别""登录"等链接 |
| 768-1200px（平板） | 部分菜单折叠 | 某些元素进了下拉菜单，需先点展开 |
| <768px（手机） | 汉堡菜单 ☰ | 顶层菜单元素**根本不在可见 DOM 结构里**，定位必失败 |

所以 `maximize_window()` 在 setup 里几乎是**默认最佳实践**：它把窗口拉到最大，让页面处于桌面布局，元素最容易定位、最不容易被遮挡。反过来，`set_window_size(500, 500)` 会让页面变成移动端形态——除非你**故意**要测响应式布局，否则会凭空制造一堆定位失败。

三者的选择标准：

| 方法 | 什么时候用 |
|------|-----------|
| `maximize_window()` | 默认选择（有头模式），跟随屏幕分辨率 |
| `--window-size=1920,1080` 启动参数 | **无头模式**必须用（maximize 在无头下行为不可靠） |
| `set_window_size(w, h)` | **故意**测响应式布局（不同分辨率下的显示） |
| `minimize_window()` | 极少用；仅演示或让出屏幕 |

关于 `minimize_window()` 要澄清一个常见误解：最小化后 WebDriver **仍然能操作页面**（它通过 driver 协议操作 DOM，不依赖窗口可见），但**截图会拿到异常结果、部分依赖可见性的点击可能失败**。想"不占屏幕地跑"，正确做法是无头模式，不是最小化。

【必须掌握】
- `maximize_window()` 是有头模式的默认最佳实践，放 setup
- 无头模式用 `--window-size=1920,1080`，不要指望 maximize
- `set_window_size` 只在**故意测响应式**时用
- 窗口小 → 响应式布局变化 → 元素被折叠 → 定位失败（"本地过 CI 失败"的常见原因之一）
- 想后台跑用无头，不要用最小化
- 课程示例里 `--start-maximized` 与随后的 `set_window_size(500,500)` 冲突，**后设置的生效**

【企业场景】
产品要求"页面在 1366×768 的老笔记本上不能出现横向滚动条"。这是一条**响应式测试**用例，正是 `set_window_size` 的正当用途：

```python
@pytest.mark.parametrize("width,height", [(1920, 1080), (1366, 768), (768, 1024), (375, 812)])
def test_no_horizontal_scrollbar(driver, width, height):
    driver.set_window_size(width, height)
    driver.get("https://example.com")
    # 页面实际宽度不应超过窗口宽度（否则出现横向滚动条）
    scroll_width = driver.execute_script("return document.documentElement.scrollWidth")
    client_width = driver.execute_script("return document.documentElement.clientWidth")
    assert scroll_width <= client_width, f"{width}x{height} 下出现横向滚动条"
```

参数化 + set_window_size 一次覆盖四种分辨率 —— 手工测这个要开四次窗口拖尺寸，自动化 3 秒跑完。这是 UI 自动化少有的"比手工强很多"的场景（因为可精确控制像素）。

【面试考察】
面试官："为什么很多人建议 Selenium 脚本一开始就最大化窗口？"

参考回答框架：
1. 现代页面是响应式的，窗口宽度变化会改变 DOM 结构（菜单折叠成汉堡菜单）
2. 窗口太小会导致元素不在可见结构里 / 被遮挡 → `NoSuchElementException`、`ElementClickInterceptedException`
3. 最大化让页面处于桌面布局，定位最稳定，所以放在 setup 统一执行
4. 无头模式下改用 `--window-size` 显式指定分辨率（默认 800×600 会踩同样的坑）
5. 反向补充：真要测响应式就用 `set_window_size` + 参数化多分辨率

【易错点】

| 误区 | 后果 | 纠正 |
|------|------|------|
| 无头模式靠 `maximize_window()` | 行为不可靠，实际可能仍是 800×600 | 用 `--window-size=1920,1080` |
| 随手 `set_window_size(500,500)` | 页面变移动端布局，一堆元素定位失败 | 默认最大化，只有测响应式才设小 |
| 用 `minimize_window()` 让脚本"后台跑" | 截图异常、部分操作不稳 | 用无头模式 |
| 窗口设置写在用例里 | 每条用例重复，改分辨率要改多处 | 放 setup / fixture |
| 同时用 `--start-maximized` 和 `set_window_size` | 相互覆盖，结果取后者，容易困惑 | 只保留一种策略 |

【扩展知识】
读取窗口信息与位置控制（了解即可）：`driver.get_window_size()` 返回 `{'width':…, 'height':…}`，`driver.get_window_position()` / `set_window_position(x, y)` 控制窗口在屏幕上的位置（多屏调试时有用）。移动端仿真更彻底的做法是 ChromeOptions 的设备仿真：

```python
options.add_experimental_option("mobileEmulation", {"deviceName": "iPhone 12 Pro"})
```

这会连 User-Agent、触摸事件一起模拟，比单纯改窗口尺寸更接近真机（但真机兼容性测试仍需 Appium / 云真机平台）。

【我的理解】
> （为什么"窗口太小"会导致元素找不到，而不只是"看不见"？想想响应式页面在小宽度下 DOM 到底发生了什么变化）

### 知识点 6：Python 与 Java 写法对照【扩展知识】

【课程原话/定义】
课程每个操作都给了 Java 对照代码。归纳如下：

| 操作 | Python | Java |
|------|--------|------|
| 打开网页 | `driver.get(url)` | `driver.get(url)` |
| 刷新 | `driver.refresh()` | `driver.navigate().refresh()` |
| 回退 | `driver.back()` | `driver.navigate().back()` |
| 前进 | `driver.forward()` | `driver.navigate().forward()` |
| 最大化 | `driver.maximize_window()` | `driver.manage().window().maximize()` |
| 最小化 | `driver.minimize_window()` | `driver.manage().window().minimize()` |
| 设置尺寸 | `driver.set_window_size(800, 600)` | `driver.manage().window().setSize(new Dimension(800, 600))` |
| 等待（课程示例） | `time.sleep(1)` | `Thread.sleep(2000)`（毫秒，需抛 `InterruptedException`） |
| 关闭 | `driver.quit()` | `driver.quit()` |

【为什么？】
差异不是随意的，而是设计风格不同：**Java 版把 API 按职责分组**（`navigate()` 管导航、`manage()` 管浏览器管理如窗口/超时/cookie），**Python 版把常用方法直接平铺在 driver 上**（更简洁）。

理解这个分组反而有好处——它提示你 Java 的 `driver.manage()` 下面还有 `timeouts()`（隐式等待，Ch04 见过）和 `getCookies()`。也就是说"窗口、超时、cookie"在 Selenium 的模型里属于同一类：**浏览器级管理**，不是页面内容。

另外注意 Java 的 `Thread.sleep(2000)` 单位是**毫秒**，Python 的 `time.sleep(1)` 单位是**秒**——面试写代码时搞错单位会闹笑话。当然两者都属于强制等待，正式代码都该换显式等待（Ch04 知识点 5）。

【必须掌握】
- Java 导航类在 `driver.navigate()`，窗口/超时/cookie 在 `driver.manage()`
- `Thread.sleep()` 毫秒 vs `time.sleep()` 秒
- Python 方向以**看懂**为目标；能说出"结构一致、分组不同"即可
- 两边共同点：`get()`、`quit()` 写法完全一样

【企业场景】
你要给 Java 项目的同事解释一个 Python 脚本的逻辑，只需做这层翻译：`driver.refresh()` = 他们的 `driver.navigate().refresh()`。跨栈沟通时，能做这种映射的人省掉大量解释成本。

【面试考察】
（本节属扩展，面试基本不问细节）若被问到"Java 版 Selenium 你熟悉吗"：

参考回答：结构一致、API 分组不同——Java 把导航放 `navigate()`、窗口/超时/cookie 放 `manage()`，Python 直接挂在 driver 上；核心概念（会话、定位、等待、断言）完全相通，读写没有障碍。

【易错点】

| 误区 | 纠正 |
|------|------|
| Java 里写 `driver.refresh()` | 编译不过，要 `driver.navigate().refresh()` |
| `Thread.sleep(2)` 以为是 2 秒 | 是 2 毫秒，Java 单位是毫秒 |
| 认为两套 API 要分别学 | 概念相同，只需记住分组差异 |

【我的理解】
> （Java 把窗口控制放在 `manage()` 下、和超时/cookie 归为一类——这个分组说明 Selenium 认为这三者有什么共同点？）

## 今日课程总结

| 模块 | 核心内容 | 面试权重 |
|------|----------|----------|
| 方法分类 | 导航类（get/refresh/back/forward）写用例；窗口类（maximize/minimize/set_size）放 setup | ★★★★☆ |
| `get()` | URL 必带协议；等 load 完成但不等异步内容；ChromeOptions 是配置入口 | ★★★★★ |
| 无头与分辨率 | 无头默认 800×600 → 必须 `--window-size`，否则 CI 专属失败 | ★★★★★ |
| `refresh()` | "提交 → 刷新 → 再断言"验证真正落库；刷新后元素引用失效 | ★★★★☆ |
| `back()` | 依赖历史栈，无历史静默无效；高价值场景：退出登录后回退（安全类 bug） | ★★★★☆ |
| 窗口控制 | 最大化是默认最佳实践（响应式布局会改 DOM）；set_window_size 用于测响应式 | ★★★★★ |
| StaleElement | 刷新/跳转/局部重渲染后旧元素引用失效 → 重新定位 | ★★★★★ |
| Java 对照 | 导航在 `navigate()`、窗口在 `manage()`；`Thread.sleep` 是毫秒 | ★★☆☆☆ |
