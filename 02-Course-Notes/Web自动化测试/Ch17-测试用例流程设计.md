## 一、现有测试用例的问题

### 知识点 1：为什么要"用例设计"——现有用例的三大毛病

【课程原话/定义】

现有测试用例的问题分两大维度：

| 维度 | 具体表现 |
|------|---------|
| 可维护性不高 | 低模块化性、高耦合性、缺乏可复用性、可读性较差、命名不清晰、缺乏注释和文档、不符合代码风格指南 |
| 稳定性较差 | 未处理异常、断言不足、依赖不清晰 |

【为什么？】
这一章（Ch17）是 Web 自动化测试的"工程化收尾"：前几章学会了写用例（Ch04）、定位元素（Ch06）、组织用例（Ch15 PO 模式），但**会写 ≠ 写得能长期维护、稳定运行**。衡量一份自动化用例的质量，就是两把尺子：

- **可维护性 = 改起来贵不贵**。低模块化、高耦合意味着"改一个按钮定位要动 5 个文件"；命名不清晰、没注释意味着"三个月后自己都看不懂"。自动化脚本的寿命以年计，可维护性差 = 每次业务变更都是一次大改。
- **稳定性 = 跑起来稳不稳**。没处理异常 = 一个弹窗就整条用例挂；断言不足 = 用例"假通过"（没真验证业务）；依赖不清晰 = 用例 A 没跑，用例 B 就报错，排错时根本找不到根因。

这两把尺子是本章所有设计原则的出发点：后面讲的编排、生命周期、数据清理、项目结构，本质都是在"提升可维护性 + 稳定性"。

【必须掌握】
- 两大维度：可维护性（改起来贵不贵）、稳定性（跑起来稳不稳）
- 可维护性的 7 个表现、稳定性的 3 个表现，能对号入座

【企业场景】
你接手一份离职同事留下的自动化代码，发现用例名叫 `test1`、`test2`、`aaa`，一个 `driver` 全局变量在 8 个文件里传来传去，改一处崩三处——这就是"可维护性不高"的现场还原。老板问"这份自动化还能不能用"，你按可维护性 + 稳定性两条给出评估，而不是凭感觉说"写得乱"。

【面试考察】
面试官："你怎么评价一份自动化测试用例写得好不好？"

参考回答框架：
1. 用两把尺子：可维护性（模块化/耦合/复用/可读/命名/注释/风格）和稳定性（异常处理/断言/依赖）
2. 可维护性决定"改起来贵不贵"，稳定性决定"跑起来稳不稳"
3. 举例：命名不清晰 + 没注释 = 三个月后没人敢改；断言不足 = 假通过，自动化形同虚设
4. 结论：好的用例 = 可维护 + 稳定，而不是"能跑"

【易错点】

| 误区 | 纠正 |
|------|------|
| "用例能跑通过 = 写得好" | 能跑只是及格线，可维护性 + 稳定性才决定用例能活多久 |
| 把"可维护性"和"稳定性"混为一谈 | 一个是"改"的代价，一个是"跑"的质量，两把独立的尺子 |

【我的理解】
> （为什么"断言不足"会被归到"稳定性"而不是"可维护性"？一条没有断言的用例，跑起来是"绿"的，它到底"稳不稳"？从"假通过"的角度想想。）

## 二、用例结构设计

### 知识点 2：测试用例的编排（一条用例拆成哪些零件）

【课程原话/定义】

测试用例的编排包含 7 个要素：

1. 测试用例组织
2. 测试步骤
3. 前置条件
4. 测试数据
5. 操作和期望结果
6. 清理操作
7. 参数化测试

【为什么？】
"编排"回答的是**一条用例应该由哪些零件构成**。这正是 Ch04「用例结构分析」的延续——Ch04 讲了"标题/前提/步骤/预期/后置"的骨架，本章把它扩展成 7 个要素，其中三个最容易被初学者漏掉：

- **测试数据**：把数据从用例代码里抽出来（外置到变量/YAML/参数化），而不是硬编码在 `find_element` 里。数据一变，只改数据不动逻辑。
- **清理操作**：用例跑完把脏数据、登录态还原，否则下一条用例在"被污染的环境"里跑，会产生"今天过明天挂"的幽灵失败。
- **参数化测试**：同一套步骤用多组数据跑（pytest 的 `@pytest.mark.parametrize`），把"重复的 10 条用例"压缩成"1 条用例 + 10 组数据"，直接提升可维护性。

【必须掌握】
- 7 个要素各自对应代码里的什么
- 重点理解"测试数据""清理操作""参数化"这三个易漏项的价值

【企业场景】
你在写登录功能用例时，把用户名/密码硬编码在每一条 `test_login_xxx` 里；后来产品要求改测试账号，你改了 12 个文件。正确做法是：测试数据抽到 `conftest.py` 或数据文件，用例只引用变量——账号变更只改一处。这就是"测试数据"要素的落地。

【面试考察】
面试官："一条完整的自动化用例由哪些部分构成？"

参考回答框架：
1. 7 要素：组织、步骤、前置条件、测试数据、操作+期望、清理、参数化
2. 特别强调三个易漏项：数据外置、清理操作、参数化
3. 举例：参数化把"10 条重复用例"变"1 条用例 + 10 组数据"，维护成本骤降

【易错点】

| 误区 | 纠正 |
|------|------|
| 只写"步骤 + 断言"，漏了数据/清理/参数化 | 完整编排 7 要素，漏"清理"会污染后续用例，漏"参数化"会复制粘贴爆炸 |
| 测试数据硬编码在用例里 | 数据外置（变量/文件/fixture），业务变更只改数据不动逻辑 |

【我的理解】
> （"清理操作"和"参数化测试"这两个要素，分别对应了知识点 1 里哪一把尺子？清理操作是为了"稳"，参数化是为了"好维护"——这样一一对应想一遍，就能把本章串起来。）

### 知识点 3：测试用例的项目结构（项目级六大件）

【课程原话/定义】

测试用例的项目结构包含 6 个方面：

1. 测试套件
2. 目录结构
3. 共享资源
4. 报告和日志
5. 版本控制
6. 测试框架集成

【为什么？】
知识点 2 讲"一条用例"的编排，知识点 3 上升到"**一整个项目**"的组织。单条用例写得再好，没有项目级的结构支撑，几十上百条用例就会失控：

- **测试套件（suite）**：把用例按模块/冒烟/回归分组，决定"跑哪些、按什么顺序"，是 CI 的入口。
- **目录结构**：按职责分层（页面对象/用例/工具/日志），对应知识点 8 会展开讲。
- **共享资源**：公共的 driver 实例、测试数据、环境配置（URL/账号）集中管理，避免每个文件复制一份。
- **报告和日志**：Allure 报告 + 日志，失败留证（呼应 Ch13、Ch16）。
- **版本控制**：Git，自动化代码也要随业务代码进版本管理。
- **测试框架集成**：pytest/JUnit 的配置（pytest.ini、markers、conftest），把框架能力接进项目。

【必须掌握】
- 6 个方面，能解释每个"管什么"
- 知道"测试套件"和"共享资源"为什么是项目级而非用例级

【企业场景】
你新建一个 UI 自动化项目，第一件事不是写用例，而是搭结构：`pytest.ini` 注册 marker、`conftest.py` 放共享 driver fixture、`cases/` 和 `pages/` 分层、Allure 挂进报告。结构搭好后，别人加用例只需往 `cases/` 里塞文件——这就是"项目结构"先行的价值。

【面试考察】
面试官："如果让你从零搭一个 UI 自动化框架，你会考虑哪些方面？"

参考回答框架：
1. 先搭项目结构：目录分层 + 测试套件 + 共享资源
2. 再配框架：pytest.ini / conftest / marker 注册
3. 报告日志 + 版本控制（Git）+ CI 集成
4. 强调"结构先行"，不是上来就写用例

【易错点】

| 误区 | 纠正 |
|------|------|
| 项目结构 = 随便建几个文件夹 | 结构承载职责分层（page/case/util/log），是工程化的骨架 |
| 共享资源（driver/配置）在每个用例里各 new 一份 | 集中到 conftest/fixture，一处定义处处复用 |

【我的理解】
> （"测试套件"和"共享资源"这两项，为什么放在"项目结构"里而不是"用例编排"里？一个用例用不上"套件"这个词——想清楚"用例级 vs 项目级"的边界。）

## 三、测试框架生命周期回顾

### 知识点 4：Pytest / JUnit4 / TestNG / JUnit5 的 setup/teardown 对照

【课程原话/定义】

各框架的测试生命周期钩子：

| 框架 | 类/模块级前置 | 方法级前置 | 备注 |
|------|--------------|-----------|------|
| Pytest | setup_class / setup_module | setup_method | 另有更灵活的 fixture（function/class/module/session 四级作用域） |
| JUnit4 | @BeforeClass / @AfterClass | @Before / @After | 类级方法是 static |
| TestNG | @BeforeSuite / @BeforeGroup / @BeforeClass | @BeforeMethod | 粒度最细（Suite→Test→Group→Class→Method） |
| JUnit5 | @BeforeAll / @AfterAll | @BeforeEach / @AfterEach | 类级方法是 static |

> 📷 【截图占位】各测试框架生命周期时序图（Pytest / JUnit4 / TestNG / JUnit5）

【为什么？】
"生命周期钩子"是框架帮你执行**用例前后**的时机点，是"前置/后置"这个概念的框架级实现。回顾它们是为了给知识点 5 打底：Web 自动化用例的"前置准备、后置清理"最终要落到这些钩子上。

关键理解两点：

1. **粒度分层**：所有框架都分"类级（整个类跑一次）"和"方法级（每条用例跑一次）"。TestNG 最细，多出 Suite/Test/Group 三级。粒度越细，越能精确控制"哪些东西只初始化一次、哪些每次重置"。

2. **Pytest 的 fixture 是"加强版钩子"**：setup_method 只认"方法级"，而 fixture 靠 `scope` 参数可以指定 function/class/module/session 四级作用域，还能做依赖注入、返回值、yield 前后置——这是 Pytest 相比 JUnit 系的核心优势，也是 Ch04 里"driver 放类级、状态清理放方法级"的实现手段。

【必须掌握】
- 四框架的前置/后置钩子对照，能背出"方法级"和"类级"各叫什么
- Pytest 的 fixture 作用域四级：function / class / module / session

【企业场景】
你在写 Pytest 用例时，driver 的初始化放在 `setup_class`（整个类只开一次浏览器，省时间），每条用例的"回到首页"放在 `setup_method`（每条重置状态）——这就是用"类级 + 方法级"两层钩子平衡"效率"和"隔离"。换到 Java 项目，同样的思路映射到 @BeforeAll + @BeforeEach。

【面试考察】
面试官："Pytest 的 setup/teardown 和 JUnit 的 @Before/@After 有什么区别？"

参考回答框架：
1. 概念一致：都是生命周期钩子，分方法级和类级
2. 命名对照：setup_method↔@BeforeEach、setup_class↔@BeforeAll（JUnit4 是 @BeforeClass）
3. Pytest 更强的地方：fixture 有四级作用域 + yield 前后置 + 依赖注入，比 JUnit 的注解更灵活
4. TestNG 粒度最细，多出 Suite/Test/Group 三级

【易错点】

| 误区 | 纠正 |
|------|------|
| JUnit5 类级写成 @BeforeClass | @BeforeClass 是 JUnit4 的；JUnit5 类级是 @BeforeAll / @AfterAll（且方法要 static）。课程原文"Junit5：@BeforeClass"是笔误 |
| 以为 setup_class 每条用例都跑 | setup_class 整个类只跑一次；每条用例跑的是 setup_method |
| 只认识 setup_method，不知道 fixture | fixture 是 Pytest 更灵活的钩子，作用域四级，是主流写法 |

【扩展知识】
TestNG 的完整生命周期顺序（从大到小）：`@BeforeSuite → @BeforeTest → @BeforeGroup → @BeforeClass → @BeforeMethod → 用例 → @AfterMethod → @AfterClass → @AfterGroup → @AfterTest → @AfterSuite`。适合需要"按测试套件/分组"批量控制的大型 Java 项目；Python 生态里 Pytest 的 session/module scope fixture 起到类似作用。

【我的理解】
> （"类级钩子"和"方法级钩子"各适合放什么？为什么 driver 初始化适合放类级、而"恢复初始状态"适合放方法级？结合 Ch04 的"粒度权衡"想一想。）

## 四、Web 自动化用例设计

### 知识点 5：前置与后置的职责分工（四象限）

【课程原话/定义】

Web 自动化用例的前置/后置职责分工：

| 阶段 | 框架对应 | 作用 |
|------|---------|------|
| 前置（类级） | setup_class / BeforeAll | 准备测试数据 |
| 前置（方法级） | setup / BeforeEach | 恢复用例初始状态、数据清理 |
| 后置（类级） | teardown_class / AfterAll | driver 进程退出 |
| 后置（方法级） | teardown / AfterEach | 恢复用例初始状态、数据清理 |

> 📷 【截图占位】Web 自动化用例前置/后置流程

【为什么？】
这张表是 Ch04「用例结构映射」的细化落地，核心是一个**粒度权衡**：

- **"贵"的操作放类级，只做一次**：driver 的启动（`setup_class`）和退出（`teardown_class`）成本高——开一个浏览器要几秒，所以整个测试类只开一次、最后只关一次。准备测试数据也放类级（一类用例共享一份数据）。
- **"便宜"的操作放方法级，每条重置**："恢复初始状态"和"数据清理"必须每条用例做，否则上一条用例改了状态（新增了数据、跳到了别的页面），下一条用例就在脏环境里跑。

一句话：**类级管"一次性的重活"（起 driver、备数据），方法级管"每次的复位"（回状态、清数据）**。这正是知识点 4 里"粒度分层"在 Web 自动化里的具体应用。

注意课程原文把"实例的初始化 setup/BeforeEach"单独列了一行，它和方法级前置是同一个东西——setup（方法级前置）的别名而已，不必当成独立的第三种。

【必须掌握】
- 四个象限的职责：类级前置备数据、方法级前置回状态、类级后置退 driver、方法级后置清数据
- "贵操作放类级、便宜操作放方法级"的粒度权衡原则

【企业场景】
你在写一个"商品管理"测试类：`setup_class` 里启动 driver + 登录 + 造一批测试商品；每条用例 `setup` 里 `driver.get(首页)` 回到初始页；`teardown` 里清掉这条用例产生的脏数据；`teardown_class` 里 `driver.quit()`。这样 20 条用例只开一次浏览器，跑得快，又互不污染。

【面试考察】
面试官："driver 应该在哪里初始化、在哪里退出？为什么？"

参考回答框架：
1. driver 初始化放 setup_class（类级），退出放 teardown_class——只开一次，省时间
2. 状态复位 + 数据清理放 setup/teardown（方法级）——每条用例独立
3. 原则：贵的操作（起浏览器）类级做一次，便宜的操作（回首页）方法级每次做
4. 反例：每条用例 new 一个 driver 会慢到无法接受

【易错点】

| 误区 | 纠正 |
|------|------|
| driver 初始化放 setup_method（每条都开浏览器） | 慢；应放 setup_class，整个类共享一个 driver |
| 数据清理放 teardown_class（只清一次） | 每条用例的脏数据要方法级清理，否则相互污染 |
| 把"setup/BeforeEach"当成和 setup_class 并列的第三种前置 | 它就是方法级前置，跟 setup_method 同一个东西 |

【我的理解】
> （为什么"准备测试数据"放类级、而"数据清理"放方法级？同样是"数据"，一个类级一个方法级——它们的区别在哪？想想"数据是共享的初始条件"vs"数据是每条用例产生的脏东西"。）

## 五、恢复用例初始状态

### 知识点 6：quit() 保状态 vs 封装"回到首页"提效率

【课程原话/定义】

- 每条用例执行完成都 `quit()`，虽然能确保初始状态，但可能影响执行效率。
- 可以封装一个方法，在每条用例执行完成后调用，实现"回到首页"，以优化上述问题。

> 📷 【截图占位】恢复用例初始状态流程

【为什么？】
这是"用例隔离"的一个经典效率优化。要保证"每条用例都从干净的初始状态开始"，有两种极端做法：

1. **每条用例结束就 `quit()`（重启大法）**：彻底——浏览器进程整个杀掉，下一条用例重开，天然回到初始状态；但慢——每次重启浏览器 + 重新登录 + 重新加载页面，20 条用例就是 20 次冷启动，suite 跑得巨慢。
2. **封装"回到首页"方法（轻量复位）**：保留浏览器会话，只在用例结束调用一个 `go_home()`（比如 `driver.get(首页URL)` 或点 logo 回首页），把状态拨回初始。快得多，但要求你明确"初始状态"是什么（一般是回到首页 + 清登录态/清临时数据）。

权衡点：**`quit()` 保的是"绝对的干净"，代价是效率；"回到首页"保的是"够用的干净"，换来效率**。所以工程上默认用"回到首页"，只在状态实在无法可靠复位时（比如残留了不可逆的弹窗/本地存储）才退回 `quit()`。

【必须掌握】
- `quit()` = 重启，绝对干净但慢；"回到首页" = 轻量复位，快但要求状态可复位
- 默认用"回到首页"封装方法，效率优先

【企业场景】
你发现团队的 UI 用例套件越跑越慢，一查是每个用例 `teardown` 里都 `driver.quit()`，50 条用例 = 50 次浏览器冷启动，跑完要 40 分钟。你封装了一个 `go_home()` 方法（回到首页 + 必要时清缓存），`teardown` 里改调它，`quit()` 只放到 `teardown_class` 最后关一次——suite 时间从 40 分钟掉到 12 分钟。

【面试考察】
面试官："怎么保证每条用例之间互不影响？"

参考回答框架：
1. 两种方式：每条 quit()（重启，绝对干净）或封装"回到首页"（轻量复位，高效）
2. quit() 保绝对干净但慢，每条冷启动拖垮 suite 效率
3. 工程上默认"回到首页"，quit() 只在整个类跑完（teardown_class）用一次
4. 只有在状态无法可靠复位时，才退回每条 quit()

【易错点】

| 误区 | 纠正 |
|------|------|
| "每条用例都 quit() 最稳妥" | quit() 是效率杀手，50 条 = 50 次冷启动；能用"回到首页"就别重启 |
| "回到首页"只是点一下首页按钮 | 要明确"初始状态"的完整定义（回首页 + 清登录态/临时数据），否则复位不彻底 |

【我的理解】
> （"回到首页"比 quit() 快，但它有一个前提——"初始状态"能被一个动作恢复。如果某条用例留下的状态没法靠"回首页"清掉（比如改了系统配置），你该怎么办？这时 quit() 是不是又从"低效"变回了"必要"？）

## 六、数据清理

### 知识点 7：三种数据清理方式及取舍

【课程原话/定义】

1. **调用业务接口**：通常高效，能确保以业务逻辑为基础的数据清理。
2. **通过 UI 自动化方式操作**：模拟用户界面操作，适用于需要还原用户界面状态的情况。
3. **连接数据库执行 SQL**：不推荐。

【为什么？】
测试会产生"脏数据"（下单测试留下一堆订单、注册测试留下一堆账号），不清理就会污染后续运行甚至污染测试环境。三种清理方式的取舍核心是**效率 vs 真实性 vs 风险**：

1. **调业务接口**：最推荐。业务系统本身就提供"删除订单/删除用户"的接口，直接调它等于用"官方通道"清理，快且符合业务规则（接口内部会做级联清理、校验、日志）。本质是"让业务自己清自己的数据"。
2. **UI 操作清理**：用自动化去点"删除"按钮，模拟真实用户。最真实，但慢（要驱动浏览器走一遍界面），而且只能清理"界面上能删的东西"。适合"顺便还原界面状态"的场景。
3. **直连数据库 SQL**：不推荐。虽然"最彻底"（一条 DELETE 全清），但风险大——绕过业务逻辑直接动库，可能破坏外键约束、漏掉关联表、触发不了业务级联逻辑，还要求测试有生产/测试库的写权限，容易误删。属于"能不用就不用"。

【必须掌握】
- 三种方式 + 各自适用场景
- 为什么"调业务接口"高效、"直连 SQL"不推荐

【企业场景】
你的"订单管理"用例每天在测试环境产生上百条脏订单。你选择在 teardown 里调用后端"取消订单"接口来清理——快，而且走的是业务自己的逻辑（库存回滚、状态流转都对）。而不是写个 SQL 去 `DELETE FROM orders`，那会漏掉订单明细表、状态流水表，还可能要 DBA 开权限。

【面试考察】
面试官："自动化测试产生的脏数据，你一般怎么清理？"

参考回答框架：
1. 首选调业务接口：快、走业务逻辑、级联清理正确
2. 次选 UI 操作：真实，适合还原界面状态，但慢
3. 不推荐直连 SQL：绕过业务、破坏约束/漏关联表、要数据库写权限、有误删风险
4. 按场景选：批量删用接口，还原界面用 UI，SQL 基本不用

【易错点】

| 误区 | 纠正 |
|------|------|
| "连接数据库 DELETE 最干净" | 直连 SQL 绕过业务逻辑，漏级联表、破坏约束、要写权限，不推荐 |
| 用 UI 操作清理所有脏数据 | 慢且只能清界面能删的；批量清理优先用业务接口 |
| 测试完不清理脏数据 | 脏数据污染后续运行、污染测试环境，必须在 teardown 里清理 |

【扩展知识】
数据清理的"业务接口"方式，其实就是**接口测试能力在 UI 自动化里的复用**——UI 测的是界面，清理却可以走接口（更快更稳）。这也是"分层测试"的一个交叉点：UI 层负责"看"，接口层负责"清"，两者配合。参见 [[接口测试/README|接口测试]]。

【我的理解】
> （"调业务接口"和"直连 SQL"都能删数据，为什么前者推荐、后者不推荐？关键区别是"走不走业务逻辑"——想一个直连 SQL 会漏掉什么、破坏什么的例子。）

## 七、Web 自动化项目结构

### 知识点 8：Python 与 Java 项目的目录分层

【课程原话/定义】

Python 项目：

```
- page:      页面对象
- testcases: 测试用例
- utils:     公共工具
- log:       日志信息
```

Java 项目：

```
- main/java
    - com.xxx.page:  页面对象
    - com.xxx.utils: 公共工具
    - resources:     日志配置
- test/java
    - com.xxx:       测试用例
```

【为什么？】
这是 Ch15「PageObject 设计模式」的**工程化落地目录**。分层的目的只有一个：**让"页面变了"时，只改一处**。

- **page（页面对象）**：把每个页面的元素定位 + 操作封装成类。页面 UI 一变，只改对应 page 类，testcases 里的用例逻辑不动。
- **testcases（用例）**：只写业务流程（"登录 → 搜索 → 断言"），不碰元素定位。定位全在 page 层。
- **utils（工具）**：跨页面复用的能力（读配置、日志、截图、driver 工厂）。
- **log（日志）**：运行日志，配合报告留证。

Java 的差异在于语言规范：`main/java` 放"生产代码"（page/utils 这些可复用的框架代码），`test/java` 放"测试代码"（用例），`resources` 放配置文件（日志 log4j/logback 配置等）。这种 main/test 分离是 Java/Maven/Gradle 的标准结构，Python 项目不强制，但职责分层的思路完全一致。

【必须掌握】
- Python 四目录：page / testcases / utils / log 各自放什么
- Java 的 main/test 分离 + resources 放配置
- 分层本质：页面变化只改 page 层，用例逻辑稳定

【企业场景】
你入职一家公司的 UI 自动化项目，第一眼看目录就知道它成不成熟：如果只有一个 `test.py` 把所有用例和定位都堆一起，那是脚本不是框架；如果 `pages/`、`testcases/`、`utils/`、`logs/` 分得清清楚楚，说明是按 PO 模式工程化过的，页面改版时定位只改 pages 层。你写新用例时，也只需在 pages 里加页面类、在 testcases 里写流程。

【面试考察】
面试官："UI 自动化框架的目录怎么组织？为什么这样分？"

参考回答框架：
1. Python：page（页面对象）/ testcases（用例）/ utils（工具）/ log（日志）
2. Java：main/java（page+utils+resources）/ test/java（用例）
3. 分层目的：页面 UI 变化只改 page 层，用例逻辑稳定；可维护性（呼应知识点 1）
4. 这是 PO 设计模式（Ch15）的落地

【易错点】

| 误区 | 纠正 |
|------|------|
| 所有代码堆在 testcases 里 | 元素定位放 page 层，用例只写流程，否则页面一改全崩 |
| Python 项目照搬 Java 的 main/test 结构 | main/test 是 Maven/Gradle 规范，Python 用四目录即可，职责一致但不必强套 |
| log 目录可有可无 | 日志是失败留证的一环（Ch13/Ch16），是框架标配不是可选项 |

【我的理解】
> （"页面对象"这一层，为什么能把"页面改版"的影响限制在 page 目录内？如果定位器散落在每个用例里，页面改一个按钮会波及多少文件？对比一下 PO 分层前后的维护成本。）
