## 一、为什么需要 PO（传统 UI 自动化的问题 + PO 的优势）

### 知识点 1：传统 UI 自动化三大问题 → PO 三大优势

【课程原话/定义】
> 📷 【截图占位】Martin Fowler 个人博客（PageObject 模式出处）
> 📷 【截图占位】Selenium 官网 Page Object 实践推荐页

**传统 UI 自动化的三个问题：**
1. 无法适应 UI 频繁变化
2. 无法清晰表达业务用例场景
3. 大量的样板代码（driver / find / click）

**PageObject 模式的优势：**
1. 降低 UI 变化导致的测试用例脆弱性问题
2. 让用例清晰明朗，与具体实现无关
3. 减少样板代码、提升复用

【为什么？】
这三个问题不是三个独立毛病，而是**同一个根因的三种表现**：定位器和操作细节直接散落在用例里。

```
传统写法：用例 = 业务步骤 + 元素定位 + 操作细节（全混在一起）
         ↓ UI 改版
       定位器变了 → 每一条用例都要改（脆弱）
       满屏 driver.find_element(...).click() → 读不出业务意图（不清晰）
       每条用例重复写同样的定位和操作 → 样板代码爆炸（不可维护）
```

Page Object 的本质，就是把这个"混在一起"的结构**拆成两层**：

```
PO 写法：  用例层 = 业务步骤（调 login()、search_stock()）
          页面层 = 元素定位 + 操作细节（封装在 PageObject 类里）
```

一旦分层，UI 改版只改页面层一处（优势1）、用例只剩业务语言（优势2）、定位和操作集中复用（优势3）。这正是 Ch14 结尾抛出的两个问题（重复代码 + 业务场景不清晰）的答案。

【必须掌握】
- 传统三大问题：UI 变化脆弱 / 业务场景不清晰 / 样板代码多
- PO 三大优势：降低脆弱性 / 用例清晰与实现无关 / 减少样板代码复用
- PO 本质：把"元素定位 + 操作"从用例中抽离，封装到页面类，形成"用例层 / 页面层"两层结构
- PO 出处：Martin Fowler 2013 年博客提出，Selenium 官方列为推荐实践

【企业场景】
你在企业里接手一个跑了半年的 UI 自动化框架，前端一次改版（把按钮 class 从 `btn-primary` 改成 `el-button--primary`），如果用例里硬编码了定位器，几十条用例全部飘红，你得一条条去改。引入 PO 后，这个按钮的定位只在"对应页面类"里声明一次，改一处，全部用例恢复绿色——这就是"降低 UI 变化导致的脆弱性"最直接的体感。

【面试考察】
面试官："为什么要用 Page Object 设计模式？"

参考回答框架：
1. 传统线性脚本三大问题：UI 一变全崩、读不出业务、driver/find/click 样板代码重复
2. PO 把元素定位 + 操作封装到页面类，用例只写业务步骤
3. 三个好处：UI 变化只改页面层 / 用例清晰与实现解耦 / 定位操作集中复用
4. 一句总结：PO 是 UI 自动化从"能跑"到"可维护"的分层标准

【易错点】

| 误区 | 纠正 |
|------|------|
| 以为 PO 只是"把代码挪到另一个文件" | PO 是分层思想：页面层封装定位+操作，用例层只写业务 |
| 以为"样板代码"只指重复的 import | 更核心的是"定位器 + 操作"在每条用例里重复写 |
| 以为 PO 能解决一切 | PO 解决的是"可维护性"，不是"写得快"——初期反而要写更多类 |

【我的理解】
> （传统三大问题为什么是"同一个根因的三种表现"？如果只解决"重复代码"（抽公共方法），但不动"分层"，剩下两个问题会消失吗？）

## 二、PO 建模六大原则（总览）

### 知识点 2：6 大原则分两类——字段意义 + 方法意义

【课程原话/定义】
PO 设计模式 6 大原则：

| 分类 | 原则 | 一句话 |
|------|------|--------|
| 字段意义（元素怎么放） | 1. 不要暴露页面内部元素给外部 | 元素是私有属性 |
| | 2. 不需要建模 UI 内的所有元素 | 只建模用到的 |
| 方法意义（方法怎么写） | 3. 用公共方法代表 UI 所提供的功能 | 方法=业务动作 |
| | 4. 方法返回其他 PageObject 或断言数据 | 返回值有讲究 |
| | 5. 同样行为不同结果建模为不同方法 | 一方法一结果 |
| | 6. 不要在方法内加断言 | 断言放用例层 |

【为什么？】
6 大原则看起来多，其实只回答两个问题：**"元素怎么放"（字段）和"方法怎么写"（方法）**。

- 前 2 条管"字段"：元素是页面的**内部实现**，所以①藏起来（私有）②只建需要的（不铺张）
- 后 4 条管"方法"：方法是页面的**对外接口**，所以③按业务动作命名 ④有返回值 ⑤一方法一结果 ⑥不掺断言

这一层"字段=内部、方法=接口"的理解，是所有原则的根。字段对应"怎么做"（实现），方法对应"做什么"（契约）。PO 的封装，本质就是"对外暴露契约、对内隐藏实现"。

【必须掌握】
- 6 大原则能默写，并分成"字段意义（2 条）+ 方法意义（4 条）"两类
- 核心心法：字段=内部实现（私有、按需），方法=对外接口（业务化、有返回值、不掺断言）

【企业场景】
你在团队里写 PO 编码规范时，就是把 6 大原则翻译成几条硬规则：元素定位器一律私有属性声明、方法名用业务动词（login/search/add_coupon）、方法不写 assert、跳页方法返回下一个页面对象。新同事 review 代码时，照这 6 条一条条对。

【面试考察】
面试官："PO 设计模式有哪些原则？"

参考回答框架：
1. 先说分两类：字段意义 2 条 + 方法意义 4 条
2. 字段：不暴露内部元素（私有）、不建模所有元素（按需）
3. 方法：公共方法代表功能、返回 PageObject 或断言数据、同行为不同结果分方法、不加断言
4. 心法一句：字段是内部实现，方法是对外契约

【易错点】

| 误区 | 纠正 |
|------|------|
| 6 原则死记硬背、串不起来 | 先记"字段 2 + 方法 4"的分类骨架 |
| 把原则 3 和原则 6 混为一谈 | 原则 3 是"方法做什么"（业务动作），原则 6 是"方法里不能有什么"（断言） |

【我的理解】
> （为什么"字段=内部实现、方法=对外接口"是 6 大原则的根？你能用这句话把 6 条原则各归到"实现"或"契约"一侧吗？）

## 三、字段意义的两条原则

### 知识点 3：原则 1（不暴露内部元素）+ 原则 2（不建模所有元素）

【课程原话/定义】

**原则 1：不暴露页面内部元素给外部。**
不要暴露很多细节——方法内部可以有细节，但方法本身一定是"接口"的形式。网页元素抽象成 PageObject 的属性，Python 里设为内部属性，属性名前加一个或两个下划线表示非公开属性。

**原则 2：不需要建模 UI 内的所有元素。**
页面可能有几千上万个元素，全部建模会非常繁琐、不现实。要学会挑重点，只为重要的元素建模。

【为什么？】

原则 1 的"为什么"是**封装（信息隐藏）**：元素定位器是"实现细节"，页面一改版就变。如果暴露给用例层，用例就依赖了"易变的东西"——这就是脆弱性的来源。用私有属性 `__INPUT_SEARCH = (By.NAME, "q")` 把它藏起来，外部只能通过 `search_stock()` 这个"接口"来用，改版时只改 PageObject 内部。

原则 2 的"为什么"是**成本/收益**：建模是有维护成本的，每多建一个元素就多一处"改版时要跟着改"的地方。页面几百个元素里，测试真正用到的可能就十几个，只建这十几个，就是 YAGNI（你不会用到它）原则——不为"可能用到"买单。

两个原则合起来 = "**藏起来，且只藏必要的**"。

【必须掌握】
- 原则 1：定位器用私有属性声明（单下划线 `_` 约定私有 / 双下划线 `__` 强私有触发 name mangling）
- 原则 2：只建模测试用到的元素，不铺张
- 二者关系：元素是内部实现 → 私有；只建需要的 → 精简

【企业场景】
你在一个电商后台的"订单列表页"建 PageObject，页面 DOM 里有两百多个元素（表头、筛选、分页、按钮……），但你的用例只用"搜索框、搜索按钮、订单号列"三个，那就只建这三个，其余一概不管。等哪天用例需要"导出按钮"了，再补一个。这样页面对象始终小而清晰。

【面试考察】
面试官："PO 里元素定位器为什么用私有属性？是不是页面所有元素都要建模？"

参考回答框架：
1. 私有属性是"信息隐藏"：定位器是易变的实现细节，藏起来避免用例层依赖它
2. 不建模所有元素：建模有成本，只为测试用到的元素建模（YAGNI）
3. 双下划线 `__` 触发 name mangling，比单下划线更严格地隐藏

【易错点】

| 误区 | 纠正 |
|------|------|
| 以为单下划线 `_` 和双下划线 `__` 一样 | `_x` 是约定（外部仍可访问）；`__x` 触发 name mangling（类外变 `_ClassName__x`），更严格 |
| 把页面所有元素都建模 | 维护成本爆炸，只建测试用到的 |
| 定位器直接写在用例里（没私有化） | UI 一改版，所有用例跟着改 |

【扩展知识】
Python 私有属性机制：`_x`（单下划线）是"约定俗成"的弱私有，解释器不阻止外部访问；`__x`（双下划线）会触发 name mangling，类外访问需写成 `_ClassName__x`，是"尽量阻止误用"的强私有。PO 里定位器通常用 `__` 双下划线。

【我的理解】
> （为什么"元素定位器是易变的实现细节"这一句，就能同时解释原则 1（藏起来）和原则 2（只建必要的）？）

## 四、方法意义的前两条原则

### 知识点 4：原则 3（公共方法代表功能）+ 原则 4（返回值有讲究）

【课程原话/定义】

**原则 3：用公共方法代表 UI 所提供的功能。**
公共方法应该代替一个页面的服务。以登录页为例：需要填用户名、密码、点登录，甚至填验证码。只需让登录页提供一个 `login()` 方法，把"输入用户名、输密码、点登录"的动作封装进去，外部调用 `login()` 即可。

**原则 4：方法应返回其他 PageObject，或返回用于断言的数据。**
Web 自动化里，页面操作后常跳转到另一个页面（登录成功 → 首页）。这时方法应返回"跳转后的页面对象"。如果场景已结束，需要拿页面反馈信息判断展示是否正确，则暴露一个"返回元素信息的方法"——这就是"返回用于断言的数据"。

【为什么？】

原则 3 解决的是 Ch14 说的"无法清晰表达业务场景"：方法应该用**业务动词**命名（`login`、`search_stock`、`add_coupon`），而不是技术动作（`find_input_and_click`）。用例层调用 `login()` 时，读到的就是"登录"这个业务，而不是"找用户名框、找密码框、点按钮"。

原则 4 解决的是"**方法要有返回值，返回值表达'操作之后的状态'**"：
- 跳转场景 → 返回**下一个 PageObject**，这样用例可以**链式调用**：`LoginPage().login(...).search(...)`
- 结束场景 → 返回**断言用的数据**（一段文本、一个元素），用例层拿它做 assert

没有返回值的方法，用例层"操作完就断了"，既没法继续下一步，也没法验证结果。

【必须掌握】
- 原则 3：方法名 = 业务动作（login / search / add），封装完整操作序列
- 原则 4：方法返回两类东西——PageObject（支持链式跳转）/ 断言数据（支持验证）
- 链式调用：`PageA().action().action2()`，靠"返回 PageObject"实现

【企业场景】
你在写电商下单自动化：`LoginPage().login("user","pwd")` 返回 `HomePage`，`HomePage().search_goods("手机")` 返回 `SearchResultPage`，`SearchResultPage().add_to_cart()` 返回 `CartPage`……整个用例是一串"业务步骤"的链式调用，像在读手工用例，而不是在读一堆 driver.find_element。这就是"用例清晰明朗、与实现无关"。

【面试考察】
面试官："PO 方法的返回值有什么讲究？"

参考回答框架：
1. 两类返回：跳页 → 返回下一个 PageObject（链式调用）；结束 → 返回断言数据
2. 例：login() 成功后返回 HomePage，让用例继续操作
3. 例：search_stock() 返回股票名文本，用例层拿它 assert
4. 核心：返回值表达"操作后的状态"，让用例能继续或能验证

【易错点】

| 误区 | 纠正 |
|------|------|
| 方法返回 None，用例层操作完就断 | 要么返回 PageObject 继续，要么返回数据做断言 |
| 方法名用技术动作（click_submit） | 用业务动词（login / submit_order），用例层才读得懂 |
| 把"返回数据"和"返回 PageObject"混用在一个方法里 | 一个方法表达一种确定的"操作后状态" |

【我的理解】
> （`login()` 返回 `HomePage` 对象，和 `search_stock()` 返回股票名文本，分别对应什么使用场景？如果 `login()` 什么都不返回，用例层会卡在哪？）

## 五、方法意义的后两条原则

### 知识点 5：原则 5（同行为不同结果分方法）+ 原则 6（不加断言）

【课程原话/定义】

**原则 5：同样的行为、不同的结果，可以建模为不同的方法。**
还是登录为例：有时测登录成功，有时测登录失败，就要封装成两个方法，分别代表登录成功和登录失败，而不是写在一个方法里。**一个方法只代表一种特定结果。**

**原则 6：不要在方法内加断言。**
这个原则要求把页面功能和测试用例解耦。断言是测试用例该做的事，一定要和业务逻辑分开，不能写在一起。

【为什么？】

原则 5 的"为什么"是**单一职责 + 可读性**：一个方法只对应一种确定的结果。如果写成 `login(expect_success=True)` 这种带分支的方法，方法内部就会充满 if/else，调用方还得猜"传 True 是什么意思"。拆成 `login_success()` 和 `login_fail()`，方法名即语义，用例层一眼看清测的是哪种场景。

原则 6 的"为什么"是**解耦**：PO 层负责"操作 + 取值"，用例层负责"断言 + 判定"。如果在 PO 方法里写 assert，这个页面对象就和"某一条测试的预期"绑死了——换个场景断言变了，PO 就得改，失去了复用性。**断言是"测试"的事，不是"页面"的事。**

原则 5 和原则 6 常被一起讨论，但它们管的是两个不同维度：原则 5 管"方法怎么拆"（按结果拆），原则 6 管"方法里能不能有断言"（不能）。

【必须掌握】
- 原则 5：`login_success()` / `login_fail()` 分开，一个方法一种结果，不要 `login(expect=...)` 带分支
- 原则 6：断言只在用例层，PO 方法只负责操作和取值
- 二者区别：原则 5 是"方法拆分粒度"，原则 6 是"方法内容边界"

【企业场景】
你在 review 一个新人写的 PO 类，发现 `login()` 方法末尾有一句 `assert "欢迎" in driver.page_source`，你会指出：这违反了原则 6——`login()` 应该返回"登录后是否成功"的数据（或跳转后的页面对象），把"验证是否成功"交给用例层的 assert。否则下次要测"登录失败"时，这个 `login()` 里写死的成功断言就成了绊脚石。

【面试考察】
面试官："为什么 PO 方法里不能加断言？断言应该放哪？"

参考回答框架：
1. 加断言 = 把页面功能和特定测试预期绑死，PO 失去复用性
2. 正确分工：PO 负责操作 + 取值，用例层负责 assert
3. 例：search_stock() 返回文本，用例层 `assert "X" == text`
4. 原则 5 呼应：同行为不同结果拆方法，避免一个方法里塞 if/else

【易错点】

| 误区 | 纠正 |
|------|------|
| `login(expect_success=True)` 一个方法带分支 | 拆成 login_success() / login_fail() |
| PO 方法里写 assert | 断言上移到用例层，PO 只操作 + 取值 |
| 把原则 5（拆方法）和原则 6（去断言）混为一谈 | 5 管"按结果拆"，6 管"内容边界" |

【我的理解】
> （如果一个 PO 方法里写了 assert，为什么说它"和某一条测试绑死了、失去复用性"？你能举一个"换场景就要改 PO"的具体例子吗？）

## 六、搜索场景实战：线性脚本 vs POM

### 知识点 6：同一个搜索场景的两种写法对比

【课程原话/定义】

**传统线性脚本（test_search.py）：**

```python
from selenium import webdriver
from selenium.webdriver.common.by import By


class TestSearch:
    def test_search(self):
        self.driver = webdriver.Chrome()
        self.driver.get("https://xueqiu.com/")
        self.driver.implicitly_wait(3)
        # 输入搜索关键词
        self.driver.find_element(By.NAME, "q").send_keys("阿里巴巴-SW")
        # 点击搜索按钮
        self.driver.find_element(By.CSS_SELECTOR, "i.search").click()
        # 获取搜索结果
        name = self.driver.find_element(By.XPATH, "//table//strong").text
        # 断言
        assert name == "阿里巴巴-SW"
```

**POM 脚本 —— 股票页面 PageObject（search_page.py）：**

```python
from selenium import webdriver
from selenium.webdriver.common.by import By


class SearchPage:

    __INPUT_SEARCH = (By.NAME, "q")
    __BUTTON_SEARCH = (By.CSS_SELECTOR, "i.search")
    __SPAN_STOCK = (By.XPATH, "//table//strong")

    def __init__(self):
        self.driver = webdriver.Chrome()
        self.driver.implicitly_wait(3)
        self.driver.get("https://xueqiu.com/")

    def search_stock(self, stock_name: str):
        self.driver.find_element(*self.__INPUT_SEARCH).send_keys(stock_name)
        self.driver.find_element(*self.__BUTTON_SEARCH).click()
        name = self.driver.find_element(By.XPATH, "//table//strong").text
        return name
```

**POM 测试用例（test_search.py）：**

```python
from onSelenium.fei.page_objects.search_page import SearchPage


class TestSearch:
    def test_search(self):
        text = SearchPage().search_stock("阿里巴巴-SW")
        # 断言
        assert "阿里巴巴-SW" == text
```

【为什么？】
对比三种写法，看 PO 的分层效果：

| 维度 | 线性脚本 | POM 脚本 |
|------|----------|----------|
| 定位器在哪 | 散落在用例里 | 集中在 `SearchPage` 类的私有属性 |
| 用例层看到什么 | driver.find_element 一堆 | 一行 `search_stock("...")` |
| UI 改版时 | 每条用例改定位器 | 只改 `SearchPage` 一处 |
| 断言在哪 | 用例层（正确） | 用例层（`assert "..." == text`，正确） |

两个技术细节值得注意：

1. **`__INPUT_SEARCH = (By.NAME, "q")`**：把"定位方式 + 定位值"打包成一个**元组**，作为类的私有属性（双下划线）。这就是原则 1 的落地——定位器藏进页面类。

2. **`find_element(*self.__INPUT_SEARCH)` 的 `*`**：Python 的**解包**。`find_element` 需要两个参数 `(by, value)`，而 `self.__INPUT_SEARCH` 是一个元组 `(By.NAME, "q")`，加 `*` 把它拆成两个参数传进去。去掉 `*` 会报错（把整个元组当成了第一个参数）。

【必须掌握】
- 定位器元组：`__X = (By.NAME, "q")`，私有属性声明
- 解包调用：`find_element(*self.__X)`，`*` 把元组拆成 `(by, value)`
- POM 用例层：`SearchPage().search_stock("...")` 一行，断言在用例层
- 线性 vs POM 的四维度对比（定位器位置 / 用例可读性 / 改版影响面 / 断言位置）

【企业场景】
你在企业里做一次 PO 重构：把 50 条线性用例里的定位器全部抽到对应的页面类，用例层从"满屏 find_element"变成"一行业务方法调用"。重构后前端改版，你只动了页面类，50 条用例零改动——这就是这次重构的 ROI。

【面试考察】
面试官："这段 POM 代码里 `*self.__INPUT_SEARCH` 的 `*` 是什么意思？为什么定位器要写成元组？"

参考回答框架：
1. `self.__INPUT_SEARCH = (By.NAME, "q")` 是把定位方式 + 定位值打包成元组
2. `find_element` 签名是 `find_element(by, value)`，需要两个参数
3. `*` 是解包，把元组 `(By.NAME, "q")` 拆成两个参数传进去
4. 好处：定位器集中声明、统一管理，符合原则 1（私有、隐藏）

【易错点】

| 误区 | 纠正 |
|------|------|
| `find_element(self.__INPUT_SEARCH)` 忘写 `*` | 把整个元组当第一个参数，报参数错误 |
| 定位器直接写在用例里 | 违反原则 1，应私有属性声明在页面类 |
| 断言写进 `search_stock()` 里 | 违反原则 6，应返回 name 由用例层 assert |
| 用例层 `assert "阿里巴巴-SW" == text`（期望在前） | 课程习惯写法；Python 惯例是 `assert text == "..."`（实际在前），两者都能跑 |

【扩展知识】
课程里 `search_stock` 里又写了一遍 `self.driver.find_element(By.XPATH, "//table//strong")` 而不是用已声明的 `self.__SPAN_STOCK`——这是课程示例的一个小疏忽，按原则 1 应该统一用 `self.__SPAN_STOCK`。注意到这一点，说明你已经理解"定位器集中声明"的意义了。

## 七、总结

### 知识点 7：PO 模式的价值与下一步

【课程原话/定义】
总的来说，使用 Page Object 模式的测试用例具有**更高的可读性、可维护性和代码复用性**。

【为什么？】
这三性对应开头的三大问题，形成闭环：

| 传统问题 | PO 优势 | 落到"三性" |
|----------|---------|-----------|
| UI 频繁变化 → 脆弱 | 定位器集中一处 | 可维护性 |
| 业务场景不清晰 | 方法 = 业务动作 | 可读性 |
| 样板代码多 | 页面类复用 | 代码复用性 |

所以 PO 不是"另一种写法"，而是**把 UI 自动化的可维护性结构性地做出来**。它回答了 Ch14 结尾的问题：重复代码 → 定位器进页面类、业务场景不清晰 → 方法代表业务动作。

【必须掌握】
- PO 三性：可读性 / 可维护性 / 代码复用性，与三大问题一一对应
- PO 与 Ch14 的关系：Ch14 抛出问题（重复代码、业务不清晰），Ch15 给出解法（分层）

【企业场景】
你在项目里推动 UI 自动化落地，PO 是"能不能长期维护"的分水岭：没有 PO 的脚本，三个月后没人敢改；有 PO 的框架，新人照着页面类就能写用例。面试和简历上，"用 PO 模式搭建过 UI 自动化框架"是一个明确的加分项。

【面试考察】
面试官："你的项目里 PO 是怎么落地的？分层结构长什么样？"

参考回答框架：
1. 分层：页面层（PageObject 类，定位器 + 操作方法）+ 用例层（Pytest 用例，只调业务方法 + 断言）
2. 页面类遵循 6 原则：定位器私有、方法业务化、返回 PageObject/数据、不加断言
3. 用例层：链式调用 + assert，像读手工用例
4. 效果：前端改版只改页面层，用例零改动

【易错点】

| 误区 | 纠正 |
|------|------|
| 学完 PO 只在笔记里"懂了" | 必须动手把 Ch14 的 litemall 脚本重构成分层结构 |
| 以为 PO 是"银弹" | PO 增加初期代码量，收益在"用例变多 + UI 改版"时才显现 |

【我的理解】
