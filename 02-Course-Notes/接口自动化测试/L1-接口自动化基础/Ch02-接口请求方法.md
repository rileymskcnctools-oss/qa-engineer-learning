## 一、HTTP 请求方法概述

### 知识点 1：GET / POST / PUT / DELETE 四种核心方法

【课程原话/定义】
接口请求方法是指在进行 API 通信时使用的 HTTP 方法，HTTP 方法定义了客户端与服务器之间通信的目的和操作类型。常见四种：
- **GET（获取）**：从服务器获取资源
- **POST（提交）**：将数据提交到服务器，创建新资源
- **PUT（更新）**：更新服务器上的资源，或创建新资源（如果不存在）
- **DELETE（删除）**：请求服务器删除指定资源

【为什么？】
为什么 HTTP 要区分这么多"方法"？因为"方法"表达的是**语义**——同一个 URL，用不同方法表示不同操作意图（对 `/user` 发 GET 是"查用户"，发 POST 是"建用户"，发 DELETE 是"删用户"）。这就是 REST 风格接口的核心思想：URL 定位资源，方法表达操作。测试时理解这个对应关系，才能判断"这个接口该用什么方法、该返回什么"。

【必须掌握】
- GET=获取、POST=创建、PUT=更新、DELETE=删除
- 方法表达操作语义，URL 定位资源（REST 思想）
- 对应 CRUD：Create→POST、Read→GET、Update→PUT、Delete→DELETE

【企业场景】
你在公司测一个用户模块的接口，看到文档写 `DELETE /api/user/123`，就知道这是"删除 id 为 123 的用户"，不用看具体实现。反过来，如果开发把"删除用户"做成了 `GET /api/user/delete?id=123`，你就知道这不符合 REST 规范（GET 不该有副作用），可以在评审时提出来。

【面试考察】
面试官："HTTP 常用的请求方法有哪些？分别什么语义？"

参考回答框架：
1. GET 获取资源、POST 创建、PUT 更新、DELETE 删除
2. 对应数据库 CRUD
3. 方法表达"操作意图"，URL 定位"资源"（REST 风格）
4. 补充：还有 HEAD/PATCH/OPTIONS 等，但核心是这四种

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 认为 POST 和 PUT 可以互换 | POST=创建（新增），PUT=更新（或存在则创建），语义不同 |
| 用 GET 做删除/更新 | GET 应是无副作用的"获取"，有副作用的操作不该用 GET |
| 分不清"方法"和"URL" | 方法表达操作，URL 表达资源，两者组合才是完整请求 |

【我的理解】
> （为什么"删除用户"要用 DELETE 方法而不是 `GET /user/delete?id=1`？从"方法语义"和"无副作用"两个角度解释。）

## 二、Requests 构造请求方法

### 知识点 2：requests 的 get / post / put / delete / request

【课程原话/定义】
Requests 提供的构造方法（演练环境：https://httpbin.ceshiren.com/ ）：

| 方法 | 说明 |
|------|------|
| requests.request() | 构造请求的基础方法，支撑以下各方法 |
| requests.get() | 构造 GET 请求 |
| requests.post() | 构造 POST 请求 |
| requests.put() | 构造 PUT 请求 |
| requests.delete() | 构造 DELETE 请求 |

GET 格式：`requests.get(url, params=None, **kwargs)`，params 是拼接在 URL 的请求参数。
POST 格式：`requests.post(url, data=None, json=None, **kwargs)`，data 是表单体，json 是 JSON 体。

```python
import requests
def get():
    url = "https://httpbin.ceshiren.com/get"
    r = requests.get(url)
    print(r.text)        # 响应内容的字符串形式
    print(r.status_code) # 响应状态码
get()
```

【为什么？】
为什么 requests 要把五种方法都包成 `requests.get()`、`requests.post()` 这种"方法同名"的函数？因为这样最直观——看到 `requests.get(url)` 就知道是发 GET 请求，代码即文档。而 `requests.request()` 是它们的"总入口"，五个快捷方法内部其实都调它。记住 `get/post` 是"语法糖"，`request()` 才是底层，这能帮你理解为什么参数（params/data/json）在所有方法里是通用的。

【必须掌握】
- requests.get/post/put/delete 五个快捷方法
- GET 用 params（拼 URL），POST 用 data（表单）或 json（JSON 体）
- `r.text` 拿响应字符串，`r.status_code` 拿状态码
- 演练环境 httpbin.ceshiren.com（镜像了 httpbin.org，可随意练习）

【企业场景】
你在公司写接口自动化，最常用的两个就是 `requests.get()` 和 `requests.post()`——查询类接口用 get，提交类接口用 post。httpbin 这种"回声服务"（你发什么它返回什么）特别适合练手和验证参数是否正确传过去了，因为它会把你的请求原样回显。

【面试考察】
面试官："Requests 怎么发 GET 和 POST 请求？"

参考回答框架：
1. GET：requests.get(url, params=...)，参数拼在 URL
2. POST：requests.post(url, data=... 或 json=...)，data 是表单、json 是 JSON 体
3. 返回值 r，用 r.text/r.json() 拿内容，r.status_code 拿状态码
4. 还有 put/delete，以及通用的 request()

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| POST 传参数用 params | POST 的"请求体"用 data/json，params 是拼 URL 的查询参数 |
| 混淆 data 和 json | data=表单（form-urlencoded），json=JSON 体（自动设 Content-Type） |
| 忘记 import requests | 每个脚本开头都要 import requests |

【我的理解】
> （POST 请求里，`data` 和 `json` 都是"往请求体里放数据"，它们到底差在哪？服务器收到的 Content-Type 会是什么？）

## 三、通用请求方法与底层参数

### 知识点 3：requests.request() 的底层参数全景

【课程原话/定义】
通用方法格式：`requests.request(method, url, **kwargs)`，method 支持 GET/OPTIONS/HEAD/POST/PUT/PATCH/DELETE。

底层参数说明：

| 参数 | 应用场景 |
|------|----------|
| method | 请求方法 |
| url | 请求 URL |
| params | URL 查询参数 |
| data | 请求体（默认表单） |
| json | json 格式请求体 |
| headers | 头信息 |
| cookies | cookies |
| files | 文件格式请求体 |
| auth | 认证信息 |
| timeout | 超时时间 |
| allow_redirects | 是否允许重定向 |
| proxies | 代理 |
| verify | 是否校验 TLS 证书 |
| cert | ssl 客户端证书 |

【为什么？】
为什么要把这一堆参数都列出来？因为真实接口测试里，光会 `requests.get(url)` 远远不够——你要带 header（登录态）、带 cookies（会话）、传文件（上传接口）、设超时（防卡死）、走代理（抓包/跨网）。这些参数就是 Requests 的"全家桶"，理解它们在什么场景用，遇到复杂接口才不会抓瞎。`requests.request()` 的文档签名（method/params/data/json/headers/...）是这份参数表最权威的来源。

【必须掌握】
- 通用方法 requests.request(method, url, **kwargs)
- 高频参数：params（URL 参数）、data/json（请求体）、headers（头）、timeout（超时）、verify（证书校验）
- 每个参数对应一个真实测试场景（带 token=headers、上传=files、防卡死=timeout）

【企业场景】
你在公司调一个需要登录态的接口，光 `requests.get(url)` 会返回 401。你要加上 `headers={"Authorization": "Bearer xxx"}`；如果这个接口还慢，再加 `timeout=10` 防止脚本无限等；如果要走公司代理才能访问内网，再加 `proxies={...}`。一个真实的接口请求，往往是"基础 URL + 好几个 kwargs"的组合。

【面试考察】
面试官："Requests 常用的底层参数有哪些？timeout 和 verify 分别是干什么的？"

参考回答框架：
1. params（URL 参数）、data/json（请求体）、headers（头）、cookies（会话）
2. files（上传）、auth（认证）、proxies（代理）
3. timeout：设置超时，防止请求卡死导致脚本挂起
4. verify：是否校验服务端 TLS 证书（默认 True，抓包/自签名场景常设 False）

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 不设 timeout | 接口慢/挂起时脚本会无限等，生产环境必设 timeout |
| 抓包时报 SSL 证书错误 | verify=False 跳过证书校验（或传入 CA 路径） |
| 不知道 files 参数 | 上传文件用 files=，不是 data/json |

【我的理解】
> （为什么"超时时间"timeout 在接口自动化里这么重要？如果不设 timeout，一个卡死的接口会让你的回归脚本发生什么？）
