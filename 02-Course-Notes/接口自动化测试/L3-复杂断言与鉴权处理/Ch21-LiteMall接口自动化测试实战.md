## 一、ApiObject 设计模式搭建框架

### 知识点 1：从线性结构到 ApiObject 模式

【课程原话/定义】
场景：为 LiteMall 后台管理系统接口实现自动化测试，项目周期紧张、手工执行耗时久。团队决定引入接口自动化框架，用 **ApiObject 设计模式**搭建，提高代码可维护性和可复用性。

任务：
1. 编写新增商品、更新商品、删除商品接口的**线性**自动化用例
2. 分析线性代码，识别重复部分和不易维护的代码
3. 用 ApiObject 模式解决：减少代码重复、分离"接口信息"与"操作逻辑"
4. 目标：提高代码复用率、降低维护成本、提升可扩展性

框架搭建步骤：
- 明确框架结构和类图
- 封装接口信息（ApiObject 层），迁移原有代码
- 拼接测试场景，完成断言

代码优化：日志记录 + Allure 报告；数据驱动测试、参数化用例。

【为什么？】
为什么要从"线性结构"升级到"ApiObject 模式"？因为线性代码（每个接口写一遍完整请求）会大量重复——同一个接口的 URL、方法、参数结构在多个用例里反复出现，接口一改就要改 N 处。ApiObject 模式（借鉴 PageObject 思想）的解法是：把"接口信息"（URL、方法、参数、返回值提取）封装成独立的 ApiObject 类，测试用例只"调用"这些 ApiObject 来拼接场景。这样接口定义只在一处，改了 ApiObject 一处，所有用例自动生效。核心是"分离接口定义与测试逻辑"——这也是接口自动化框架"可维护"的关键设计。

【必须掌握】
- ApiObject 模式：封装接口信息，分离接口定义与测试逻辑
- 线性结构的问题：接口信息重复、改一处要改 N 处
- ApiObject 价值：减少重复、提高复用率、降低维护成本
- 框架搭建：封装接口信息 → 拼接场景 → 断言
- 配套：日志 + allure 报告 + 数据驱动参数化

【企业场景】
你在公司搭接口自动化框架，把每个接口封装成 ApiObject（如 GoodsApi，含新增/更新/删除商品的方法），测试用例只调用 GoodsApi 的方法拼场景。接口地址、参数结构变了，只改 GoodsApi 一处，几十个用例不用动。这就是"接口定义与用例逻辑解耦"。

【面试考察】
面试官：「接口自动化的 ApiObject 模式是什么？为什么用它？」

参考回答框架：
1. ApiObject 封装接口信息（URL/方法/参数/提取）
2. 借鉴 PageObject 思想，分离接口定义与测试逻辑
3. 解决线性代码的重复和维护难
4. 价值：减少重复、提高复用率、降低维护成本

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 每个用例重复写接口信息 | 封装成 ApiObject，接口定义只在一处 |
| ApiObject 里写断言 | ApiObject 管接口信息，断言在用例里 |
| 只写线性代码不重构 | 接口多了要升级 ApiObject 模式 |

【扩展知识】
ApiObject 是"PageObject"思想在接口测试的迁移：Web 自动化用 PageObject 分离"页面元素与操作"，接口自动化用 ApiObject 分离"接口信息与业务逻辑"。它们都遵循"封装变化、分离关注点"的设计原则，是自动化框架"可维护性"的核心。
