## 一、MQTT 发布/订阅协议

### 知识点 1：Broker 中心化 + QoS + 测试维度

【课程原话/定义】
MQTT（Message Queuing Telemetry Transport）是轻量级、基于发布/订阅模式的消息协议，适合弱网络、低带宽、物联网场景（智能家居、车联网、IoT 网关）。

通信模式：Publish / Subscribe
- **Broker**：消息中心（EMQX、Mosquitto）
- **Client**：发布者或订阅者（可同时两者）
- 基于 TCP（可选 TLS），长连接 + 心跳保活

**QoS 三级**：
| 级别 | 描述 | 场景 |
|------|------|------|
| QoS 0 | 最多一次（不确保送达） | 传感器数据、日志 |
| QoS 1 | 至少一次（可能重复） | 支付消息、设备状态 |
| QoS 2 | 只有一次（严格送达） | 金融、医疗 |

测试维度：功能（建连/订阅/发布/取消/断开）、可靠性（QoS/丢包/重复）、安全（TLS/权限/Topic 访问控制）、性能（并发/TPS/延迟）、异常（掉线重连/消息堆积/Broker 故障）。

工具：MQTTX（GUI）、Mosquitto CLI、JMeter + MQTT Plugin（压测）、Python paho-mqtt（自动化）。

【为什么？】
为什么要了解 MQTT 测试？因为物联网的普及让 MQTT 成为 IoT 通信的主流协议，而它和 HTTP 完全不同——不是请求-响应，而是"发布/订阅 + Broker 转发 + 长连接"。测试的重点也随之变化：HTTP 测"发请求收响应"，MQTT 测"建连、订阅、发布、消息送达（QoS）、掉线重连"。特别是 QoS 是 MQTT 独有的可靠性保证——QoS 0/1/2 分别对应"不保证/可能重复/严格一次"，测试要验证消息是否按协议承诺送达。理解这些，才知道"非 HTTP 协议怎么测"。

【必须掌握】
- MQTT = 发布/订阅消息协议（IoT 场景）
- Broker 中心化：客户端通过 Broker 转发，不直接通信
- QoS 0/1/2：最多一次/至少一次/只有一次
- 测试维度：功能/可靠(QoS)/安全/性能/异常(重连)
- 工具：MQTTX、paho-mqtt、JMeter

【企业场景】
你在公司测 IoT 设备接口（智能家居），设备通过 MQTT 上报数据。测试要验证：设备能连 Broker、订阅正确 Topic、发布消息能送达（QoS 级别符合预期）、掉线能重连。这些是 HTTP 接口测试没有的维度。

【面试考察】
面试官：「MQTT 和 HTTP 有什么区别？怎么测 MQTT？」

参考回答框架：
1. MQTT 发布/订阅 + Broker 转发，HTTP 请求-响应
2. Broker 中心化，客户端不直接通信
3. QoS 三级：0/1/2 不同送达保证
4. 测试：建连/订阅/发布 + QoS 验证 + 掉线重连

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 用 HTTP 思维测 MQTT | MQTT 是长连接发布/订阅，不是请求-响应 |
| 忽略 QoS 验证 | QoS 是 MQTT 核心可靠性，要验证送达保证 |
| 不测掉线重连 | 长连接要测断网恢复、心跳保活 |

【我的理解】
> （MQTT 的"Broker 中心化"和 HTTP 的"点对点请求"有什么本质区别？为什么 IoT 场景更适合发布/订阅而不是请求-响应？）
