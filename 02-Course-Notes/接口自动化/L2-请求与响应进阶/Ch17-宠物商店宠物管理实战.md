## 一、宠物管理业务流程

### 知识点 1：增删改查业务场景 + 复杂断言

【课程原话/定义】
被测产品 PetStore 宠物商城，宠物管理业务场景：添加宠物 → 查询宠物 → 修改宠物 → 删除宠物。

接口（https://petstore.swagger.io/v2/pet）：
- 添加：POST /pet（JSON 请求体，含 id/category/name/photoUrls/tags/status）
- 查询：GET /pet/findByStatus?status=available
- 修改：PUT /pet（JSON 请求体，改 name）
- 删除：DELETE /pet/{petId}

【为什么？】
为什么 Ch08 只测"查询"，这里要测完整的"增删改查"？因为单接口测试（Ch08 的查询）只验证一个接口，而真实业务是"一连串接口协作"——新增宠物后要能查到它、改完名字要查到新名字、删掉后要查不到它。这是**接口间数据关联**的完整链路测试，比单接口更接近真实业务，也更能暴露"接口之间数据没串起来"的问题。

【必须掌握】
- 宠物管理业务链：增 → 查 → 改 → 查 → 删 → 查（验证）
- 四个接口：POST/PUT/DELETE 用 JSON 请求体，GET 用 params
- 业务断言：新增后 id 在列表里、改后新名字在列表里、删后 id 不在列表里
- 用 JSONPath（$..id / $..name）提取多层嵌套响应做断言

【企业场景】
你在公司测"用户管理"模块，不是单独测"新增用户""删除用户"，而是串起来测：新增用户 → 查询确认新增成功 → 修改用户名 → 查询确认改了 → 删除 → 查询确认删了。这种"业务链路"测试才能真正验证"这些接口配合起来对不对"，而不是各自孤立地"能用"。

【面试考察】
面试官："接口自动化里，怎么测试一组有业务关联的接口（如增删改查）？"

参考回答框架：
1. 按业务流程串联：增 → 查（验证）→ 改 → 查（验证）→ 删 → 查（验证）
2. 用 setup_class 准备测试数据（pet_id、请求体等）
3. 每个步骤断言：状态码 + 业务结果（用 JSONPath 提取字段验证）
4. 数据关联：新增的 id 要能在查询结果里找到，删掉后要查不到

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 只测单个接口不串业务 | 业务链测试才能验证接口间的数据关联 |
| 增删改查数据不关联 | 新增的 id 要用于后续查询/修改/删除 |
| 删除后不验证 | 删除后要查一次，确认真的删掉了 |

【我的理解】
> （为什么"单独测每个接口都通过"不等于"业务链路没问题"？举一个"单个接口正常但业务串联出错"的例子。）

## 二、脚本优化

### 知识点 2：代理 + 日志 + JSONPath 断言 + Allure 报告

【课程原话/定义】
脚本优化四步：
1. **配置代理**：proxies 指向抓包工具，抓包查看脚本真实请求/响应
2. **添加日志**：logging + RotatingFileHandler，替换 print，带时间/级别/行号
3. **JSONPath 断言**：`jsonpath.jsonpath(r.json(), "$..id")` 提取多层嵌套字段做断言
4. **生成报告**：@allure.feature/story/step 标注，allure serve 查看

```python
@allure.feature("宠物管理业务场景测试")
class TestPetclinicPetmanager:
    @allure.story("宠物增删改查场景测试")
    def test_pet_manager(self):
        with allure.step("新增宠物"):
            add_r = requests.post(self.base_url, json=self.pet_info, proxies=self.proxy, verify=False)
            assert add_r.status_code == 200
            search_r = requests.get(self.search_url, params=self.search_param, ...)
            assert self.pet_id in jsonpath.jsonpath(search_r.json(), "$..id")
        # ... 修改、删除同理
```

【为什么？】
为什么这个实战要把代理、日志、JSONPath、Allure 全用上？因为这是 L2 的"综合验收"——把本层学过的能力（代理抓包 Ch15、JSONPath Ch16、日志、报告）串成一个"生产级"的自动化用例。一个合格的接口自动化用例，光"能跑通"不够，还要：能排查（代理+日志）、能精准断言（JSONPath）、能汇报（Allure）。这四步优化就是"从 demo 脚本到生产用例"的差距。

【必须掌握】
- 代理：proxies 参数 + verify=False（抓包看真实请求）
- 日志：logging + RotatingFileHandler（替换 print，带格式）
- JSONPath 断言：$..id / $..name 提取嵌套字段，in 断言
- Allure：@allure.feature（大类）/story（场景）/step（步骤）标注
- 报告命令：pytest --alluredir + allure serve

【企业场景】
你在公司交付接口自动化，脚本要过评审：能抓包排查（代理）、失败能定位（日志）、断言精准（JSONPath）、结果能汇报（Allure 报告）。这四项是"能上 CI 的自动化用例"的标准配置，缺一项都会在真实使用中被吐槽。

【面试考察】
面试官："一个完整的接口自动化用例，除了发请求和断言，还需要哪些工程化能力？"

参考回答框架：
1. 日志：logging 记录请求/响应，失败时定位问题
2. 代理：配抓包工具，排查请求数据对不对
3. 报告：Allure 生成可视化报告，便于汇报
4. 断言：JSONPath 处理复杂嵌套响应

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 用 print 代替 logging | logging 带时间/级别/行号，失败定位快 |
| JSONPath 提取结果当标量 | 返回 list，用 in 判断 |
| 报告缺 feature/story 标注 | 报告没有分类结构，可读性差 |

【我的理解】
> （日志、代理、报告、JSONPath 断言这四件事，分别解决接口自动化里的什么"痛点"？为什么说它们是"生产级用例"的标配？）
