## 一、Response 对象

### 知识点 1：响应对象包含哪些信息

【课程原话/定义】
接口响应断言是在接口测试时验证接口返回结果的方法，用于检查期望条件是否满足。Requests 的响应对象（r）包含：

| 属性 | 含义 |
|------|------|
| r.status_code | HTTP 响应状态码 |
| r.headers | 字典，响应头的所有信息 |
| r.text | 响应内容（字符串） |
| r.url | 编码后的请求 URL |
| r.content | 响应内容（字节流） |
| r.raw | 响应的原始内容 |
| r.json() | 若响应是 JSON，解析成 Python 对象 |

【为什么？】
为什么断言之前要先搞清楚"响应对象里有什么"？因为接口测试的断言本质是"从响应里取信息，和预期对比"。你不知道响应对象有哪些属性，就不知道能断言什么：状态码用 status_code、返回内容用 text/json()、响应头用 headers。理解 Response 对象，等于拿到了"断言的材料清单"。

【必须掌握】
- r.status_code 状态码、r.text 字符串内容、r.json() 解析 JSON
- r.headers 响应头、r.content 字节流、r.url 请求 URL
- 断言前先想清楚"从响应的哪个字段取信息"

【企业场景】
你在公司断言一个接口：先 `assert r.status_code == 200` 确认请求成功，再 `r.json()` 拿到返回数据、校验关键字段。如果你连 r.json() 和 r.text 的区别都不清楚（一个是解析后的对象、一个是原始字符串），断言就无从下手。

【面试考察】
面试官："Requests 的响应对象有哪些常用属性？r.text 和 r.json() 有什么区别？"

参考回答框架：
1. status_code（状态码）、headers（响应头）、url（请求 URL）
2. text（字符串内容）、content（字节流）、raw（原始内容）
3. r.json()：把 JSON 响应解析成 Python 对象（dict/list）
4. r.text：未解析的原始字符串

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| r.text 和 r.json() 混用 | text 是字符串，json() 是解析后的对象（dict/list） |
| 非 JSON 响应调 r.json() | 会抛异常，先确认响应是 JSON 格式 |
| 断言只看 status_code | 状态码 200 不代表数据对，还要断言内容 |

【我的理解】
> （`r.text` 返回的是字符串，`r.json()` 返回的是 dict/list——为什么断言字段时要用 `r.json()` 而不是在 `r.text` 字符串里查找？）

## 二、状态码断言

### 知识点 2：Python assert 与 Java statusCode() 断言

【课程原话/定义】
断言用 assert 关键字，把预期结果和实际结果对比：

| 断言 | 含义 |
|------|------|
| assert xx | 判断 xx 为真 |
| assert not xx | 判断 xx 不为真 |
| assert a in b | 判断 b 包含 a |
| assert a == b | 判断 a 等于 b |
| assert a != b | 判断 a 不等于 b |

状态码断言（Python）：
```python
import requests
def req():
    r = requests.get("https://httpbin.ceshiren.com/get")
    assert r.status_code == 200   # 判断返回状态码是否为 200
```

Java（REST-assured）状态码断言：
```java
given().when().get("https://httpbin.ceshiren.com/get")
.then().log().all().statusCode(200);
```

【为什么？】
为什么断言是接口自动化的"灵魂"？因为接口自动化区别于"手工点一遍"的地方就在于：**自动判定结果对不对**。没有断言，脚本跑完你也不知道过没过；有了 assert，脚本能自动告诉你 PASS/FAIL。断言的核心是"预期 vs 实际"——状态码 200 是"预期"，r.status_code 是"实际"，两者相等才算过。

【必须掌握】
- assert 关键字做断言：==、!=、in、not
- 状态码断言：assert r.status_code == 200（Python）
- Java：then().statusCode(200)
- 断言 = 预期 vs 实际对比，是自动化"自动判定"的核心

【企业场景】
你在公司写接口用例，每条用例最后都要有断言：状态码是不是 200、返回里有没有关键字段、值对不对。没有断言的用例等于"只发请求不检查结果"，跑一万遍也不知道接口有没有坏。断言让"人肉看结果"变成"机器自动判定"。

【面试考察】
面试官："接口自动化里为什么要写断言？常用的断言方式有哪些？"

参考回答框架：
1. 断言让脚本自动判定结果对不对（PASS/FAIL），而不是肉眼看
2. 常见：状态码断言（200/400）、内容断言（包含某字段/值）
3. Python 用 assert，Java 用 then().statusCode()/body()
4. 断言是"预期 vs 实际"的对比

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 只断状态码 200 | 200 只说明请求成功，数据对不对还要断内容 |
| 断言写在请求前 | 断言是对"响应"的判断，必须在请求之后 |
| 用 print 代替 assert | print 只是打印，不会判定 PASS/FAIL |

【我的理解】
> （为什么"只断言状态码 200"不够？举一个"状态码 200 但数据错了"的具体例子，说明为什么还要断内容。）
