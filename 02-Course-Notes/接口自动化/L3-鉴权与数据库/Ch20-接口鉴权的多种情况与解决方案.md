## 一、常见鉴权方式

### 知识点 1：Basic / token / session+cookie / OAuth2 四种鉴权

【课程原话/定义】
接口鉴权是验证请求方身份的机制，确保接口安全和合法性。常见鉴权方式：
- **HTTP Basic Auth**：HTTP 协议基本认证，浏览器弹窗输账号密码，Base64 编码后放 Authorization 头
- **token 鉴权**：登录拿 token，后续请求带 token，服务端校验合法性（常用 JWT）
- **session + cookie 鉴权**：服务端建 session，返回 sid，客户端存 cookie，后续带 sid 请求
- **OAuth2.0**：第三方授权（如微信/QQ 登录）

【为什么？】
为什么要系统理解这几种鉴权？因为接口测试里，绝大多数"访问受限"的接口都需要先解决鉴权问题——不搞懂鉴权，连接口都调不通。而不同鉴权方式的"凭证传递方式"完全不同：Basic 是 Authorization 头（Base64 编码的账密）、token 是 Authorization 头（Bearer token）、session 是靠 Cookie 里的 sid。测试时你得知道"这个接口用哪种鉴权、凭证放哪"，才能正确构造请求。

【必须掌握】
- 四种鉴权：Basic Auth、token、session+cookie、OAuth2.0
- Basic：账密 Base64 编码放 Authorization 头
- token：登录拿 token，请求头携带（JWT 常见）
- session+cookie：服务端 session + 客户端 cookie 存 sid
- 一般公司用 token 或 session+cookie，具体看文档或问开发

【企业场景】
你在公司调接口总 401，第一件事是搞清楚这个系统用哪种鉴权：是 Basic Auth（要账密）、token（要登录拿 token）、还是 session+cookie（要登录态）。不同鉴权对应不同的"获取凭证 + 传递凭证"方式，搞错了就一直 401。这是接口测试的"入门门槛"——过了鉴权这道坎，才能真正测业务。

【面试考察】
面试官："接口测试中常见的鉴权方式有哪些？"

参考回答框架：
1. Basic Auth：账密 Base64 编码放 Authorization
2. token：登录拿 token，请求携带，JWT 常见
3. session+cookie：服务端 session，客户端 cookie 存 sid
4. OAuth2.0：第三方授权
5. 实际项目常用 token 或 session+cookie

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 分不清鉴权和加密 | 鉴权是"验身份"，加密是"防偷看"，两回事 |
| token 和 session+cookie 混为一谈 | token 无状态（凭证本身含信息），session 有状态（服务端存） |
| Basic Auth 密码明文传 | Basic 是 Base64 编码（可逆），不是加密，要配合 HTTPS |

【我的理解】
> （Basic Auth 的账密是 Base64 编码放 Authorization 头，为什么说这"不是加密"？Base64 编码和加密的本质区别是什么？）

## 二、token 与 session+cookie 的区别

### 知识点 2：为什么 token 越来越主流

【课程原话/定义】
**token 鉴权流程**：账密登录 → 服务端验证 → 生成 token 返回 → 客户端存储（cookie/LocalStorage）→ 每次请求带 token → 服务端校验（失败返回 401）。

**session+cookie 流程**：客户端首次访问 → 服务端建 session（内存/redis）→ 生成 sid 返回 → 客户端存 cookie → 后续请求带 sid → 服务端查 session 判断合法。

**两者的核心区别**：
| 维度 | session+cookie | token |
|------|----------------|-------|
| 登录状态 | sid 只是标识，状态存服务端 | token 本身含登录状态 |
| 依赖 Cookie | 是（只有浏览器解析 cookie） | 否（可存 storage/内存，适用 App） |
| 时效性 | sid 登录到登出不变 | 可动态改变 |
| 可扩展性 | 弱 | 强（可做统一鉴权服务，JWT） |

【为什么？】
为什么现代 API 越来越倾向 token 而非 session+cookie？关键在"状态存哪"和"依赖什么"：
- session+cookie 把登录状态存在服务端（session），客户端只存个 sid，且必须依赖浏览器解析 cookie——App、小程序、跨域场景就麻烦
- token 把登录状态"打包"进 token 本身（JWT），服务端无状态、无需存 session，客户端可以放任何地方（cookie/storage/内存），不依赖浏览器

所以 token 更"无状态、更灵活、可扩展"，天然适配移动端和微服务。理解这个区别，是"为什么用 token"这类面试题的答案核心。

【必须掌握】
- token 流程：登录 → 拿 token → 请求带 token → 校验
- session+cookie 流程：建 session → 下发 sid → cookie 带 sid → 查 session
- 核心区别：token 状态在客户端（无状态），session 状态在服务端（有状态）
- token 不依赖 cookie，适用 App/跨域；session+cookie 依赖浏览器

【企业场景】
你在公司测一个"手机 App + 网页"都要用的接口，团队用 token（JWT）鉴权——因为 App 没有浏览器那套 cookie 机制，token 可以放内存/存储里，两边通用。如果团队用 session+cookie，App 端就很难处理登录态。这就是"token 比 session+cookie 更灵活"在真实项目里的体现。

【面试考察】
面试官（高频）：「token 和 session+cookie 有什么区别？为什么现代 API 用 token？」

参考回答框架：
1. session+cookie：状态存服务端（session），客户端只存 sid，依赖浏览器 cookie
2. token：状态含在 token 本身（无状态），不依赖 cookie
3. token 更灵活：适配 App/跨域，可做统一鉴权服务（JWT）
4. session+cookie：服务端要维护 session，扩展性弱

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 认为 token 也要服务端存 session | token 无状态，服务端只校验合法性，不存 |
| 认为 session+cookie 能用于 App | 依赖浏览器解析 cookie，App 场景不便 |
| 分不清 JWT 和 token | JWT 是 token 的一种实现（JSON 结构加密），不是独立概念 |

【扩展知识】
JWT（JSON Web Token）是 token 鉴权的主流实现：把用户信息（JSON）加密成三段式 token（header.payload.signature），服务端无需存储、只需用密钥校验签名即可。它体现了"无状态鉴权"的核心思想——服务端"算"得出合法性，而不是"查"session。这也是微服务架构下能做"统一鉴权服务"的基础。

【我的理解】
> （"token 无状态、session 有状态"——具体区别在哪？如果服务端重启，token 和 session 分别会发生什么？）

## 三、Basic Auth 实战与 OAuth2 流程

### 知识点 3：Basic Auth 代码 + OAuth2 授权流程

【课程原话/定义】
Basic Auth 实战（Python / Java）：
```python
from requests.auth import HTTPBasicAuth
r = requests.get(url="https://httpbin.ceshiren.com/basic-auth/ad/123",
                 auth=HTTPBasicAuth("ad", "123"))
assert r.json()["user"] == 'ad'
```
```java
given().auth().basic("ad", "123").when().get("/basic-auth/ad/123")
    .then().statusCode(200).body("user", equalTo("ad"));
```

OAuth2 授权流程：
1. 用户点第三方登录入口，跳转第三方授权页
2. 用户授权登录，授权服务器生成凭证（code）
3. 第三方应用用 code 换 Access Token
4. 授权服务器返回 Access Token
5. 第三方应用用 Access Token 请求资源，资源服务器验证后返回

【为什么？】
为什么要单独讲 Basic Auth 和 OAuth2？因为它们是两种"典型形态"：Basic Auth 是最简单的"账密直传"（Base64 编码），适合内部接口、快速验证；OAuth2 是最复杂的"第三方授权"（用户密码不暴露给第三方应用），适合开放平台、第三方登录。理解这两个极端，中间的各种鉴权（token、session）就都能理解了——本质都是"用某种凭证证明身份"，只是凭证的获取和传递方式不同。

【必须掌握】
- Basic Auth：requests 的 auth=HTTPBasicAuth(user, pwd)，Java 的 auth().basic()
- OAuth2 五步：授权 → code → 换 Access Token → 拿 Token → 请求资源
- OAuth2 核心价值：第三方应用不接触用户密码
- 凭证方式对比：Basic=账密、token=凭证、session=sid、OAuth2=授权码换 token

【企业场景】
你在公司测内部接口，用 Basic Auth（账密 Base64）快速验证；测第三方登录（微信/QQ），走 OAuth2 流程拿 Access Token。理解"内部接口常用 Basic/token，开放接口常用 OAuth2"这个规律，遇到不同的鉴权需求就知道该用哪种、凭证怎么拿。

【面试考察】
面试官：「OAuth2 的授权流程是怎样的？它解决了什么问题？」

参考回答框架：
1. 五步：授权 → code → 换 Access Token → 拿 Token → 请求资源
2. 核心：用户密码不暴露给第三方应用，用"授权码 + token"代替
3. 适用：第三方登录、开放平台
4. 对比 Basic：Basic 是账密直传，OAuth2 是授权令牌

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| OAuth2 和 token 鉴权混为一谈 | OAuth2 是授权协议（拿 token 的过程），token 是鉴权凭证 |
| Basic Auth 密码当加密 | Base64 可逆，不是加密，需配合 HTTPS |
| 忘了 auth 参数 | requests 用 auth= 传认证信息，不是 headers |

【我的理解】
> （OAuth2 为什么能"不暴露用户密码"？和 Basic Auth 直接传账密相比，OAuth2 多了哪一层"凭证"让密码不用直接给第三方？）
