## 一、需求分析与用例设计

### 知识点 1：从 Swagger 文档到测试用例

【课程原话/定义】
被测产品 PetStore（宠物商城）：一个在线小型商城，提供增删查改等操作接口，结合 Swagger 实现接口管理。接口文档：https://petstore.swagger.io/

需求：完成"宠物查询功能"接口自动化测试——编写自动化测试脚本 + 完成断言。

查询接口：`GET /v2/pet/findByStatus`，参数 `status`（取值 available/pending/sold）。

【为什么？】
为什么实战要从"需求分析 + 用例设计"开始，而不是直接写代码？因为自动化测试的本质是"把测试用例翻译成代码"。用例设计阶段想清楚"测什么、怎么算通过"，写代码才有方向。这一章串起了 Ch02-Ch07 全部知识：请求方法（GET）、请求参数（params）、响应断言（状态码 + 内容）、JSONPath（取字段）——是 L1 的"综合验收"。

【必须掌握】
- 被测系统：PetStore（Swagger 管理的宠物商城）
- 查询接口：GET /v2/pet/findByStatus?status=xxx
- 需求分析 → 用例设计 → 写脚本 → 断言，是完整流程
- Swagger 是接口文档/管理工具，从这里获取接口信息

【企业场景】
你在公司接到一个接口自动化任务，第一步不是写代码，而是先看 Swagger/接口文档搞清楚"接口是什么、参数有哪些、返回什么"，再设计用例（正常场景 + 异常场景），最后才写脚本。跳过早两步直接写代码，往往会漏测边界、断言不全。

【面试考察】
面试官："拿到一个接口自动化需求，你的完整流程是什么？"

参考回答框架：
1. 需求分析：看接口文档（Swagger），搞清 URL/方法/参数/返回
2. 用例设计：正常场景 + 异常场景，明确断言点
3. 写脚本：发请求 + 断言
4. 优化：日志、参数化、异常覆盖、生成报告

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 跳过需求分析直接写代码 | 先搞清接口再写，否则方向错、漏场景 |
| 只测正常场景 | 还要覆盖异常值、空参数、错误参数 |
| 不看接口文档凭空猜 | 以 Swagger/文档为准，别猜参数和返回 |

【我的理解】
> （为什么说"用例设计"是写自动化脚本的前置？如果跳过用例设计直接写代码，最可能漏掉什么？）

## 二、编写与优化测试脚本

### 知识点 2：基础脚本 → 日志 → 断言 → 参数化 → 异常覆盖

【课程原话/定义】
基础脚本：
```python
class TestPetstorePetsearch:
    def setup_class(self):
        self.base_url = "https://petstore.swagger.io/v2/pet"
        self.search_url = self.base_url + "/findByStatus"

    def test_search_pet(self):
        params = {"status": "available"}
        r = requests.get(self.search_url, params=params)
        assert r.status_code == 200        # 状态断言
        assert r.json() != []               # 业务断言
        assert "id" in r.json()[0]          # 响应元素断言
```

参数化（pytest.mark.parametrize）：
```python
@pytest.mark.parametrize("status", ["available", "pending", "sold"],
                         ids=["available_pets", "pending_pets", "sold_pets"])
def test_search_pet_by_param(self, status):
    r = requests.get(self.search_url, params={"status": status})
    assert r.status_code == 200
    assert r.json() != []
```

异常场景覆盖：错误值（"petstatus"）、空字符串、数字 12345、不传参数、错误参数名等，断言返回空列表 `[]`。

【为什么？】
为什么基础脚本写出来后还要"优化"？因为一个能跑的脚本和"一个合格的自动化用例"是两回事。优化解决四个问题：
- **日志**：print 会淹没在输出里，logging 能带时间/级别/行号，排查问题快
- **断言**：从"只断 200"到"断内容 + 断关键字段"，才真正验了数据
- **参数化**：一份脚本跑多组数据（available/pending/sold），不用复制三份
- **异常覆盖**：测"错误输入返回空"这类边界，比只测正常值更完整

【必须掌握】
- setup_class 里定义 URL（复用）
- 断言分层：状态码 + 业务（非空）+ 关键字段（id）
- parametrize 参数化：一份用例跑多组数据
- 异常场景：错误值/空串/数字/缺参数/错参数，断言返回 []
- 日志用 logging（带时间/级别/行号），替换 print

【企业场景】
你在公司写宠物查询的自动化：基础脚本先跑通，然后加 logging 日志（方便失败时定位），加 parametrize 把 available/pending/sold 三种状态参数化（一份代码覆盖三种情况），再加异常场景（传错误值返回空）。这样才是能进回归的"合格用例"，而不是"只能跑一次的 demo 脚本"。

【面试考察】
面试官："接口自动化脚本为什么要参数化？异常场景怎么覆盖？"

参考回答框架：
1. 参数化（parametrize）让一份脚本跑多组数据，减少重复代码
2. 正常场景测 available/pending/sold 等合法值
3. 异常场景测错误值、空值、非法类型、缺参数
4. 异常场景通常断言返回空列表或错误码

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 每种状态复制一份脚本 | 用 parametrize 参数化，一份脚本多组数据 |
| 只断 status_code==200 | 还要断内容（非空、关键字段） |
| 异常场景断言也断 200 | 异常场景返回可能是 200 + 空列表，要看清实际行为 |

【我的理解】
> （"参数化"解决的是什么问题？如果不用 parametrize，测 3 种宠物状态你要写几份几乎一样的代码？）

## 三、生成测试报告

### 知识点 3：Allure 测试报告

【课程原话/定义】
生成 Allure 报告：
1. 安装 allure 相关依赖
2. 给测试脚本添加描述信息：`@allure.feature("宠物搜索接口")`、`@allure.story("冒烟用例")`
3. 执行生成报告：
```bash
pytest -vs test_petclinic_petsearch.py --alluredir=./report --clean-alluredir
allure serve ./report/
```

【为什么？】
为什么自动化测试要生成报告？因为测试跑完，你要向团队/领导汇报"测了什么、过了几条、挂了几条"。Allure 把 pytest 的执行结果可视化：按 feature/story 分类、展示每条用例的 PASS/FAIL、失败用例的详细日志。它把"一堆命令行输出"变成"一张能给人看的报告"。`@allure.feature/story` 注解则是给用例打标签，让报告有结构。

【必须掌握】
- Allure 是测试报告工具，和 pytest 配合
- @allure.feature 大类、@allure.story 子类（给用例打标签）
- --alluredir 生成报告数据，allure serve 查看
- 报告价值：可视化 PASS/FAIL、按 feature/story 分类、便于汇报

【企业场景】
你在公司跑完接口回归，用 Allure 生成一份报告，按"宠物搜索接口"这个 feature、"冒烟用例/异常用例"这些 story 分类，领导一眼能看出"总共几条、过了几条、失败原因"。没有报告，你只能贴一堆终端输出，没人看得懂。

【面试考察】
面试官："接口自动化怎么生成测试报告？Allure 的 feature 和 story 是什么？"

参考回答框架：
1. 用 Allure + pytest 生成报告
2. @allure.feature 标注大功能模块，@allure.story 标注具体场景
3. --alluredir 生成报告数据，allure serve 可视化查看
4. 报告展示每条用例 PASS/FAIL 和失败详情

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 只跑 pytest 不看报告 | 报告是自动化成果的呈现，缺了没法汇报 |
| feature 和 story 不区分 | feature 是大类（模块），story 是子类（具体场景） |
| 忘记 --clean-alluredir | 多次跑报告数据会累积，要清理旧数据 |

【我的理解】
> （为什么自动化测试"跑完不算完"，还要生成报告？报告最终是给谁看、解决什么沟通问题？）
