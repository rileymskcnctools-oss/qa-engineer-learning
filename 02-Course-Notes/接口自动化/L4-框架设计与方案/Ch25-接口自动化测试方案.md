## 一、自动化测试方案设计

### 知识点 1：从需求到技术选型

【课程原话/定义】
接口自动化测试常考的面试题：
- 写接口自动化用例用了什么库、用到哪些功能？
- 接口自动化实现思路？
- 接口垃圾数据如何清理？
- 响应值嵌套深、获取不方便怎么办？
- 返回字段特别多、结构复杂，如何断言？

《Google 测试之道》对自动化的观点：
1. 每个测试之间相互独立，能以任意顺序执行
2. 测试不做数据持久化，离开环境时保证环境状态与开始前一致
3. 自动化不只是写程序，还要考虑编译、执行、分析、存储、报告

接口自动化在通用自动化需求之上，还需处理：请求发送、断言处理、鉴权处理、用例设计。

技术选型：
| 需求 | 框架 | 原因 |
|------|------|------|
| 用例独立性 | pytest | 前置后置结合数据准备与清理 |
| 用例执行过程 | pytest | mark 标签做分类与筛选 |
| 结果报告 | pytest + allure | 统计清晰 + 报告美观 |
| 测试数据管理 | pytest + 数据工具 | |
| 请求发送 | requests | 简单、上手快 |
| 断言处理 | jsonpath + jsonschema | 应用简单 |
| 鉴权处理 | requests | 简单、上手快 |

【为什么？】
为什么要专门学"测试方案设计"？因为这是"从写脚本到搭框架"的分水岭。前面 Ch01-Ch24 教的是"怎么写对单个请求/断言"，而这一章回答的是"一个完整的接口自动化框架该有哪些组件、为什么选这些组件"。这也是面试的高频区——面试官问"你的接口自动化实现思路"，其实是在考察你有没有"框架设计"的全局视角，而不是只会写几个请求脚本。

【必须掌握】
- 面试高频题：实现思路、用啥库、垃圾数据清理、复杂断言
- Google 三原则：用例独立、数据还原（不持久化）、结果报告
- 接口自动化四需求：请求发送、断言、鉴权、用例设计
- 技术选型：pytest（用例管理）+ requests（请求/鉴权）+ jsonpath/jsonschema（断言）+ allure（报告）

【企业场景】
你在公司搭接口自动化框架，方案汇报时要说清：pytest 管用例（独立性、标签分类、前后置做数据准备清理）、requests 管请求和鉴权、jsonpath/jsonschema 管断言（嵌套深、字段多的应对）、allure 管报告。这套"选型 + 理由"是面试和晋升答辩的标配答案。

【面试考察】
面试官（高频）：「说说你的接口自动化测试方案/实现思路？」

参考回答框架：
1. 用例管理：pytest（独立性 + mark 标签 + 前后置数据准备清理）
2. 请求发送 + 鉴权：requests（简单、支持各种鉴权）
3. 断言：jsonpath（嵌套深）、jsonschema（字段多）
4. 报告：pytest + allure
5. 数据管理：前后置做数据还原，保证用例独立

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 只会写脚本不会说方案 | 面试考"框架设计思路"，不是"会不会发请求" |
| 用例之间互相依赖 | Google 原则：用例要独立、任意顺序可执行 |
| 测试数据不清理 | 离开环境要还原，否则脏数据污染后续用例 |

【扩展知识】
这一章是整个"接口自动化"课程的"收口"——它把 L1-L4 学过的所有组件（requests 发请求、jsonpath/jsonschema 断言、鉴权、代理、环境配置、日志、报告）串成一张"框架技术选型表"。理解这张表，你就知道"接口自动化框架"不是玄学，而是这些具体组件按需求组合的结果。

【我的理解】
> （为什么"用例独立性"是自动化测试的第一原则？如果用例之间互相依赖（必须先跑 A 才能跑 B），会遇到什么问题？）
