## 一、什么是 Web 兼容性测试策略

### 【课程原话/定义】

> Web 兼容性测试策略是在不同的浏览器、操作系统和设备上确保 Web 应用程序正常运行的一系列计划和方法。由于不同浏览器（Chrome、Firefox、Safari、Edge 等）以及不同操作系统和设备可能存在兼容性差异，因此制定一套全面的兼容性测试策略非常重要。

### 【为什么？】

Ch09 和 Ch10 都提到了兼容性问题——布局错乱、JS 报错——但只说了"要测"，没讲"怎么定策略"。兼容性测试最大的陷阱是**试图测所有组合**：5 个浏览器 × 3 个 OS × 4 种分辨率 = 60 种组合，全测一遍不现实。**策略的价值不是"全测"，而是"用最小成本覆盖最大风险"。** 本节回答三个问题：测哪些浏览器？测哪些 OS？测哪些分辨率？

### 【必须掌握】

兼容性测试的三维矩阵（浏览器×OS×分辨率）和选择优先级策略。

### 【面试考察】

> "你怎么制定兼容性测试策略？"
>
> 参考回答：分三步——① 看用户数据定浏览器优先级（埋点分析用户浏览器分布）；② 按渲染引擎分类覆盖（Blink/Gecko/WebKit 各至少覆盖一个）；③ 按风险分层：高风险组合（主流浏览器+主流OS+主流分辨率）全量测，低风险组合（<1% 占比）抽检。

### 【易错点】

| 误区 | 正解 |
|------|------|
| 兼容性 = 只测浏览器 | 三维：浏览器 + 操作系统 + 分辨率，缺一不可 |
| 所有浏览器平权测试 | 按用户占比排优先级——占 80% 的 Chrome 全量测，占 0.5% 的 IE 只测主流程 |

## 二、浏览器兼容

### 【课程原话/定义】

> 选择浏览器的关键是要覆盖不同的浏览器渲染引擎（浏览器内核）。渲染引擎负责对网页的标记内容（HTML、XML、JavaScript、图片等）和格式化的信息（CSS、XSL 等）的语法解释并渲染显示网页。不同的浏览器内核对网页编写语法的解释有不同，因此同一网页在不同内核的浏览器里渲染效果可能不同。

> 图片位置（浏览器内核对比示例）

### 【为什么？】

浏览器兼容的本质是**渲染引擎兼容**。市面上几十种浏览器，但内核只有 4 个主流家族。覆盖内核 = 覆盖一类浏览器，比逐个测浏览器高效得多。

### 【必须掌握】

4 大浏览器内核及其代表性浏览器：

| 内核 | 代表浏览器 | 市场地位 |
|------|-----------|---------|
| **Blink** | Chrome、Edge（新版）、Opera、360极速、QQ浏览器 | 绝对主流（~80%） |
| **WebKit** | Safari（macOS/iOS 独占） | 苹果生态必测 |
| **Gecko** | Firefox | 开发者群体占比高 |
| **Trident / EdgeHTML（旧）** | IE11、旧版 Edge | 政企/教育行业仍有存量 |

### 【企业场景】

> 你在 Chrome 上测试全部通过。产品说"客户用的是 360 浏览器"。你用 360 打开——页面布局全乱了。查一下：360 浏览器有"兼容模式"（IE 内核）和"极速模式"（Blink 内核）。客户切换到了兼容模式，等于在用 IE 渲染你的页面。**国内浏览器（360/QQ/搜狗）的双核切换是兼容测试里最容易踩的坑。**

### 【面试考察】

> "为什么要按浏览器内核分类测试，而不是按浏览器品牌？"
>
> 参考回答：同一个内核的浏览器渲染行为基本一致。比如 Chrome 和 Edge（新版）都用 Blink 内核，测 Chrome 基本等于测 Edge。但不同内核之间差异大——比如 Safari（WebKit）对某些 CSS Grid 属性的支持和 Chrome（Blink）不完全相同。按内核分类 = 用最小测试数量覆盖最大差异面。

### 【易错点】

| 常见遗漏 | 补充 |
|---------|------|
| 只测最新版本 | 用户不会全部第一时间升级浏览器——至少覆盖最新版 + 前一个大版本 |
| 国产浏览器只测极速模式 | 360/QQ/搜狗浏览器用户可能切成兼容模式（IE 内核）——必须两种模式都测 |
| 移动端浏览器当桌面端缩小版 | 移动端 Safari（iOS）和 Chrome（Android）行为差异很大，必须真机/模拟器测试 |

## 三、操作系统兼容

### 【课程原话/定义】

> Web 操作系统兼容性指的是确保 Web 应用程序在不同操作系统上的正常运行和一致性展示。由于不同操作系统可能存在不同的浏览器、系统字体、文件系统等差异，因此需要特别关注。

> 图片位置（不同操作系统对比示例）

### 【为什么？**

同一个浏览器（比如 Chrome），在 Windows 和 macOS 上的表现也可能不同——原因不是浏览器代码不同，而是**操作系统底层差异**：系统字体（Windows 用微软雅黑、macOS 用苹方）、文件路径分隔符、滚动条样式、快捷键行为、甚至系统时间格式。**只测 Windows 就以为全平台通过 = 给自己埋雷。**

### 【必须掌握**

操作系统兼容的 4 个差异维度：

| 差异维度 | Windows | macOS | 可能引发的问题 |
|---------|---------|-------|-------------|
| 系统字体 | 微软雅黑、宋体 | 苹方、SF Pro | 字体回退方案不同，排版可能错位 |
| 滚动条 | 始终显示 | 默认隐藏，滚动时才显示 | 内容宽度计算不同（有无滚动条占位） |
| 文件系统 | `C:\path\to\file` | `/Users/path/to/file` | 文件上传/下载路径处理 |
| 快捷键 | Ctrl+C/V | ⌘+C/V | 快捷键提示文案需要适配 |

### 【企业场景】

> 设计师给你一个 Figma 标注：标题字体 PingFang SC 24px。Windows 上没有 PingFang SC——浏览器回退到微软雅黑，行高不一样，标题区域比设计稿矮了 8px，下面的内容跟着往上跑了。你提 Bug："建议 font-family 增加 Windows 回退字体栈：`PingFang SC, Microsoft YaHei, sans-serif`。"

### 【面试考察】

> "Windows 和 macOS 上的 Web 兼容问题，你遇到过哪些？"
>
> 参考回答：① 字体渲染差异（macOS 字体普遍比 Windows 粗）；② 滚动条差异（macOS 滚动条不影响布局宽度，Windows 会占位）；③ input/button 原生样式不同（macOS 的按钮圆角和阴影和 Windows 完全不一样）；④ DatePicker 等原生组件行为差异。

### 【易错点】

| 易忽视 | 正确做法 |
|--------|---------|
| 只测桌面操作系统 | 还要考虑移动端 OS——iOS Safari 和 Android Chrome 是最主要的两个移动端覆盖目标 |
| 字体用 `font-family: "PingFang SC"` 不加回退 | 必须提供完整的字体栈：macOS 字体 → Windows 字体 → 通用字体族 |
| 不考虑 Linux | 如果目标用户包含开发者群体，Linux（Ubuntu）也要验证 |

## 四、分辨率兼容

### 【课程原话/定义】

> 分辨率兼容可以确保应用程序在不同屏幕分辨率下能够正常运行和呈现。

### 【为什么？】

用户可能在 27 寸 4K 显示器上看你的页面，也可能在 13 寸笔记本（1366×768）上，或者在手机上竖屏（375px 宽）。**分辨率兼容 ≠ "缩小了还能看"——而是布局自适应、内容不丢失、功能可操作。** CSS 响应式布局的断点值就是为这个设计的。

### 【必须掌握】

分辨率测试的标准断点：

| 断点 | 分辨率 | 代表设备 |
|------|--------|---------|
| 大桌面 | 1920×1080 | 标准显示器 |
| 小桌面 | 1366×768 | 笔记本（最常见的低分辨率） |
| 平板 | 768×1024（竖） | iPad |
| 手机 | 375×667 | iPhone 6/7/8 |
| 小手机 | 320×568 | iPhone SE、老旧安卓 |

### 【企业场景】

> 产品经理说"咱们的页面在笔记本上看着还行"。你用 1366×768 打开——发现页面右侧的"客服悬浮按钮"被切掉一半，因为设计师是按 1920 宽做的，`position: fixed; right: 0` 在窄屏幕上直接溢出了。**1366×768 是全球最普遍的笔记本分辨率——这是分辨率兼容测试的底线。**

### 【面试考察】

> "响应式设计怎么测？用什么工具？"
>
> 参考回答：① Chrome DevTools → Toggle device toolbar → 切换预设设备或手动拖拽调整宽度；② 关注断点——拖拽时观察布局在哪个宽度发生突变（这是 CSS media query 的断点位置，最容易出问题）；③ 不只是缩小——也要放大到 2560px（4K），看是否有内容过度拉伸。

### 【易错点】

| 误区 | 正解 |
|------|------|
| 用 DevTools 调宽度就算测了 | 真机测试也要做——DevTools 模拟不了触摸交互、虚拟键盘弹出、iOS 底部安全区 |
| 只测宽不测高 | 有些页面内容多，在小屏笔记本上需要纵向滚动——确认关键操作按钮在"首屏"可见 |
| Retina 屏（2x/3x）不单独测 | 高 DPI 下图片模糊、图标发虚——确认使用了 2x 图或 SVG |

## 五、兼容测试工具

### 【课程原话/定义】

> - **IETester**：可以方便地解决 IE 浏览器的兼容问题
> - **Browsershots**：一个在线测试工具，支持很多浏览器
> - **开发者工具 - Toggle device toolbar**：模拟移动设备界面、自定义设备、旋转屏幕、生成页面快照、显示标尺、缩放视图、限制网络流量和 CPU 占用率

### 5.1 IETester

#### 【为什么？】

虽然 IE 已经退役，但政企、教育、医疗行业仍有大量 IE-only 的内网系统。IETester 让你在一台电脑上模拟 IE5.5~IE11 多个版本的渲染效果——不用装虚拟机跑各个版本的 IE。

#### 【必须掌握】

适用场景：面向政企/银行/医院等传统行业的 Web 项目。不适用：现代互联网 toC 产品（IE 用户占比 < 1% 可直接放弃）。

#### 【易错点】

| 注意 | 说明 |
|------|------|
| IETester 是模拟，不是真正的 IE | 某些 JS 行为可能与真实 IE 有差异——关键验证仍需真实 IE 环境 |
| IE 兼容的第一件事 | 检查是否用了 IE 不支持的 API（如 `fetch`、`Promise`、CSS Grid） |

---

### 5.2 Browsershots

#### 【为什么？】

Browsershots 是一个在线服务——你把 URL 发过去，它在远程的多台真实机器上（各种浏览器+OS 组合）截图返回给你。免去本地搭建兼容测试环境的成本。

#### 【必须掌握】

适用场景：需要快速验证某个页面在 10+ 种浏览器上的表现时，截图对比即可。局限：只能看静态渲染效果，无法做交互测试。

#### 【易错点】

| 局限 | 说明 |
|------|------|
| 只能截图，不能交互 | 登录态、表单提交、弹窗、动态加载的内容测不了 |
| 免费版速度慢 | 免费队列可能要等几分钟到几小时——不适合紧急验证 |

---

### 5.3 开发者工具 - Toggle device toolbar

#### 【课程原话/定义】

> Chrome DevTools 的设备工具栏功能：
> - 模拟移动设备界面
> - 自定义设备
> - 旋转屏幕
> - 生成页面快照
> - 显示标尺
> - 缩放视图
> - 限制网络流量和 CPU 占用率

#### 【为什么？】

这是兼容测试中**最常用、最方便**的工具。不需要真机农场，不需要装模拟器，一个面板就能完成 80% 的响应式和移动端兼容验证。每个功能都解决一个具体测试需求。

#### 【必须掌握**

Toggle device toolbar 7 大功能及对应测试场景：

| 功能 | 操作 | 测试场景 |
|------|------|---------|
| 模拟移动设备 | 顶部下拉选预设设备（iPhone/Pixel/iPad） | 快速验证移动端布局 |
| 自定义设备 | 下拉→Edit→Add custom device | 测试特定分辨率（如客户提供的平板尺寸） |
| 旋转屏幕 | 点击旋转图标 | 竖屏→横屏布局是否自适应 |
| 生成页面快照 | 右侧菜单→Capture screenshot | 兼容测试报告中的截图证据 |
| 显示标尺 | 右侧菜单→Show rulers | 精确测量元素尺寸 |
| 缩放视图 | 顶部缩放百分比 | 模拟不同 DPI 的显示效果 |
| 限制网络/CPU | 顶部 Performance 面板 → 节流 | 弱网 + 低性能设备组合测试 |

#### 【企业场景】

> 产品经理："手机上看效果怎么样？"你打开 DevTools → Toggle device toolbar → 选择 iPhone 12 Pro → 截图（Capture screenshot）→ 发现底部按钮被 iOS Safari 的底部导航栏遮挡。提 Bug："iPhone Safari 底部固定按钮被安全区域遮挡，需增加 `padding-bottom: env(safe-area-inset-bottom)`。"附带截图，无需真机。

#### 【面试考察】

> "DevTools 设备模拟和真机测试有什么区别？什么时候必须用真机？"
>
> 参考回答：DevTools 模拟的是分辨率和 UserAgent，但模拟不了——① 真实的触摸事件（如 swipe、长按、双指缩放）；② iOS Safari 特有的渲染行为（如 `position: fixed` 在键盘弹出时的表现）；③ 真实设备性能和内存限制。涉及手势交互、支付流程、相机/定位调用时，必须真机验证。

#### 【易错点】

| 误区 | 正解 |
|------|------|
| DevTools 模拟 = 真机效果 | 只是近似的——字体渲染、触摸交互、虚拟键盘、iOS 安全区等差异模拟不了 |
| 只用 DevTools 截图就交给产品 | 截图可以用于初步沟通，但上线前至少真机走一遍 P0 用例 |
| 不测横屏 | 很多 App 横屏布局是后来补的，最容易出 Bug |

### 【我的理解】

## 六、兼容测试三维矩阵 + 策略总结

### 三维矩阵

```
           浏览器内核
          /    |    \
       Blink  WebKit  Gecko
       /       |        \
    操作系统  操作系统   操作系统
    / | \    / | \     / | \
   W  M  L  W  M  L   W  M  L
  /|\ /|\ /|\ /|\ /|\ /|\ /|\ /|\
 分辨率  分辨率  分辨率 ...
```

### 分层测试策略

| 层级 | 覆盖范围 | 测试深度 | 方法 |
|------|---------|---------|------|
| **L1 全量** | 主流组合（Blink+Win+1920/1366/375） | 全部用例 | 手工 + 自动化 |
| **L2 核心** | 次主流组合（Blink+Mac+1920/375、WebKit+iOS） | P0+P1 用例 | 手工 |
| **L3 抽检** | 小众组合（Gecko+Linux、IE+Win） | 冒烟测试 | 手工快速过 |
| **L4 按需** | 客户特定环境 | 按客户要求 | 搭建专用环境 |

### 选浏览器/OS/分辨率的决策流程

```
用户埋点数据（用户用什么）→ 按内核归类 → 按占比排序 → 确定L1/L2/L3 → 选工具执行
```
