## 一、什么是分层测试策略

### 【课程定义】

> 分层测试策略是将测试工作按层次分解的策略，通过不同层次的测试来确保软件系统质量，优化测试资源利用，提高缺陷发现和修复效率。

### 【为什么需要分层？】

不分层的后果：

| 问题 | 分层怎么解决 |
|------|------------|
| 不知道测什么、测多少 | 每层有明确的测试目标和范围 |
| 全用UI测试 → 慢、不稳定 | 底层多测（单元）、上层少测（UI） |
| 测试资源分配不合理 | 金字塔比例告诉你每层投入多少 |
| 自动化不知道从哪开始 | 从底层开始，性价比最高 |

### 【必须掌握】六大价值

| 价值         | 说明                    |
| ---------- | --------------------- |
| 质量保证       | 层层把关，不遗漏              |
| 需求分析       | 每层对应不同的需求验证           |
| 测试标准确立     | 每层有明确的"通过标准"          |
| 测试用例Review | 分层后更容易评审              |
| 覆盖率量化      | 界面覆盖率 / 接口覆盖率 / 代码覆盖率 |
| 效率提升       | 人工→自动化→尽早测试→流水线       |

## 二、效率提升四阶梯

### 【必须掌握】从人工到DevOps

```
人工测试 → 自动化测试 → 尽早测试 → 持续集成/交付
```

| 阶段    | 方式              | 效果             |
| ----- | --------------- | -------------- |
| 人工测试  | 招人、培训、手工执行      | 横向/纵向扩容成本大     |
| 自动化测试 | 自动化脚本、自动遍历、录制回放 | 重复工作交给机器       |
| 尽早测试  | 单元测试、集成测试       | 开发阶段就发现问题      |
| 流水线   | CI/CD/DevOps    | 提交→构建→测试→部署全自动 |

## 三、测试金字塔（回顾+深化）

> Ch04已学过基础，此处深化策略视角。

> 图片位置

### 【必须掌握】三层职责

| 层级           | 占比  | 测什么     | 核心价值       |
| ------------ | --- | ------- | ---------- |
| Unit 单元测试    | 70% | 单个函数/方法 | 验证最小功能单元   |
| Service 服务测试 | 20% | 模块间协作   | 验证各部分协同工作  |
| UI 界面测试      | 10% | 用户操作流程  | 验证用户视角的正确性 |

### 【为什么是这个比例？】

| 理由   | 说明                     |
| ---- | ---------------------- |
| 底层快  | 单元测试毫秒级，UI测试分钟级        |
| 底层稳  | 单元测试不依赖环境，UI测试换个分辨率就挂  |
| 底层准  | 单元测试定位到行，UI测试只知道"页面不对" |
| 底层便宜 | 写单元测试成本低，UI自动化维护成本高    |

## 四、UI组件的分层测试（Google Android）

> 图片位置

### 【必须掌握】Android三层测试体系

| 层级   | 范围     | 工具                     |
| ---- | ------ | ---------------------- |
| 单元测试 | 单个类/方法 | JUnit, Mockito         |
| 集成测试 | 组件间交互  | Robolectric, Espresso  |
| UI测试 | 完整用户流程 | Espresso, UI Automator |

### 【面试考察】

> 面试官："Android App测试怎么分层？"

**参考回答框架：** Google推荐三层：单元测试用JUnit+Mockito，测单个类和方法；集成测试用Robolectric模拟Android环境，测组件交互；UI测试用Espresso，测完整用户操作流程。比例上单元测试占大头，UI测试只覆盖核心用户路径。

## 五、金字塔模型 vs 沙漏模型

### 5.1 金字塔模型

> 图片位置

| 层级    | 占比      | 特征     |
| ----- | ------- | ------ |
| 单元测试  | 70%-80% | 最多，最底层 |
| 集成测试  | 10%-20% | 中等     |
| 端到端测试 | 最少      | 最少，最顶层 |

**理念：** 底层便宜→多写，上层贵→少写。

### 5.2 沙漏模型

> 图片位置

| 层级    | 占比    | 特征         |
| ----- | ----- | ---------- |
| 单元测试  | 多     | 和金字塔一样，底层多 |
| 集成测试  | **少** | 比金字塔少      |
| 端到端测试 | **多** | 比金字塔多      |

**理念：** 集成测试维护成本高 → 减少集成测试，用单元测试 + 端到端测试覆盖。

### 【易错点】金字塔 vs 沙漏

| 维度    | 金字塔模型   | 沙漏模型        |
| ----- | ------- | ----------- |
| 集成测试  | 中等比例    | 减少          |
| 端到端测试 | 最少      | 增多          |
| 适用场景  | 服务端接口稳定 | 微服务多、集成复杂度高 |
| 风险    | 端到端覆盖不足 | 端到端慢、不稳定    |

### 【面试考察】

> 面试官："金字塔模型和沙漏模型有什么区别？什么时候用沙漏？"

**参考回答框架：** 金字塔强调底层多上层少，沙漏是金字塔的变种——减少了中间层（集成测试），增加了端到端测试。沙漏适用于微服务架构：服务间接口已经通过契约测试保障，做大量集成测试性价比低，不如把精力放在端到端的用户场景验证上。但端到端测试慢且不稳定，需要控制数量，所以沙漏不是"随便多写端到端"，而是"精选核心链路的端到端"。

## 六、微服务测试模型

> 图片位置

### 【必须掌握】微服务六层架构

| 层级    | 英文           | 职责                  | 怎么测       |
| ----- | ------------ | ------------------- | --------- |
| 资源层   | Resources    | 通过协议暴露能力（REST/gRPC） | 接口测试      |
| 服务层   | Service      | 领域模型的协作编排           | 集成测试      |
| 领域层   | Domain       | 行为和数据的领域对象          | 单元测试      |
| 仓储层   | Repositories | 持久化领域实体             | 集成测试+数据验证 |
| 网关层   | Gateway      | 与远程服务通信             | Mock测试    |
| 数据映射层 | Data Mappers | 模型的序列化              | 单元测试      |

### 【为什么微服务需要专门的测试模型？】

单体架构：一个进程，测试简单。
微服务架构：几十个服务互相调用，任何一个服务挂了都可能导致全链路故障。

微服务测试的核心挑战：**服务间的依赖和通信。** 所以Gateway层和Service层是微服务测试的重灾区。

## 七、微服务测试策略

> 图片位置

### 【必须掌握】四层策略

| 层级 | 测什么 | 怎么测 | 特点 |
|------|--------|--------|------|
| 单元测试 | 最小可测试单元 | 纯代码，无外部依赖 | 最快，最稳定 |
| 集成测试 | 组件间通信和交互 | 用Test Double隔离外部 | 检测接口缺陷 |
| 组件测试 | 系统的一部分 | 通过内部接口操控，隔离其他组件 | 范围可控 |
| 端到端测试 | 整个系统从头到尾 | 真实环境，全链路 | 最贵，最慢 |

### 【易错点】集成测试 vs 组件测试

| 维度 | 集成测试 | 组件测试 |
|------|---------|---------|
| 范围 | 两个组件之间的交互 | 一个组件完整行为 |
| 依赖 | 可能Mock外部 | 用Test Double替代所有外部 |
| 目的 | 验证"连接对不对" | 验证"组件行为对不对" |
