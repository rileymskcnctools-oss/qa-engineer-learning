## 一、什么是 Web 测试设计思路

### 【课程原话/定义】

> Web 测试设计思路是针对 Web 应用的各个功能模块，将测试点按 UI、搜索、表单、输入域、分页、交互、链接等维度分类整理，形成可复用的测试检查清单。

### 【为什么？】

Ch14 讲了"测试流程的 9 个阶段"，但流程只告诉你"什么时候做什么"，没告诉你"具体怎么测"。测试设计思路填补了这个空白——把 Web 项目中反复出现的测试场景（表单、搜索、分页、链接……）提炼成标准化检查项。**新手和老手的区别就在这：新手每测一个功能从零想测试点，老手脑子里有一份现成的检查清单直接套。**

### 【必须掌握】

7 大测试维度的核心检查项，能拿到一个 Web 页面立刻列出覆盖清单。

### 【企业场景】

> 你入职第二周，leader 说"这个用户管理页面前端刚改完，你过一下"。没人给你写用例，也没时间写——你打开这份检查清单：UI 维度 6 项、表单维度 9 项、输入域 6 项、分页 5 项……20 分钟跑完，发现 3 个 Bug，leader 对你的第一印象直接拉满。

### 【面试考察】

> "给你一个 Web 页面，你怎么设计测试？从哪些维度考虑？"
>
> 参考回答框架：先讲 7 个维度（UI/搜索/表单/输入域/分页/交互/链接），每维度挑 2 个具体检查项举例，然后说"我会优先从用户最常用的路径开始测试"——体现优先级意识。

### 【易错点】

| 易混淆 | 区别 |
|--------|------|
| 测试流程 vs 测试设计思路 | 流程是"先做什么后做什么"（时序框架）；设计思路是"每类功能怎么测"（检查清单） |
| 测试设计思路 vs 测试用例 | 设计思路是维度级的检查方向（"表单要测重复提交"）；用例是步骤级的操作指令（"第 3 步：点击提交按钮 2 次"） |

### 【我的理解】

## 二、7 大测试维度

### 维度 1：UI 测试

#### 【课程原话/定义】

> - 界面风格统一，与 UI 设计原型图一致
> - 界面文案正确
> - 提示、警告或错误说明描述准确
> - 切换窗口大小，将窗口缩小后，页面是否按比例缩小或出现滚动条，页面是否正确显示
> - 所有的图片是否都被正确装载
> - 在不同的浏览器、分辨率下图片是否能正确显示

#### 【为什么？】

UI 是用户对产品的第一印象。一个按钮没对齐、一句提示有错别字，用户不会觉得"这是个 Bug"，用户会觉得"这产品不专业"。**UI 测试的成本很低（肉眼过一遍），但 UI Bug 的信任损失很高。**

#### 【必须掌握】

UI 测试 6 项核心检查 + 响应式测试的断点选择（1920 / 1366 / 768 / 375）。

#### 【企业场景】

> UI 设计师出了原型图（Figma/Sketch），你的任务不是"看看像不像"——而是把原型图和实际页面并排对比，像素级检查：颜色值、字号、间距、图标样式。企业里常见的问题是开发"凭感觉"调样式，结果和设计稿差 2px——你不指出来，上线后设计师第一个找你。

#### 【面试考察】

> "UI 测试你一般关注哪些方面？"
>
> 参考回答：① 文案准确性（错别字是 P2，但误导性提示是 P0）；② 响应式适配（不只是缩小，还要看内容是否被截断）；③ 图片加载（不只是"能显示"，还要看加载失败时的占位图/alt 文本）。

#### 【易错点】

| 误区 | 正解 |
|------|------|
| UI 测试 = 看看好不好看 | "好不好看"是设计评审的事；测试关注的是"和设计稿一不一致"、"功能上有没有歧义" |
| 缩小窗口能显示就行 | 还要检查：文字是否重叠、按钮是否被挤出可视区域、横向滚动条是否合理出现 |

#### 【我的理解】

### 维度 2：搜索测试

#### 【课程原话/定义】

> - 如果支持模糊查询，搜索名称中任意一个字符是否能搜索到
> - 比较长的名称是否能查到
> - 输入系统中不存在的与之匹配的条件
> - 不同查询条件之间来回选择，是否出现页面错误
> - 查询条件的组合测试

#### 【为什么？】

搜索是 Web 应用最高频的功能之一。搜索 Bug 的伤害面极大——一个查询条件组合出错，影响的是所有使用该条件的用户。搜索测试的核心不是"能不能搜到"，而是**边界和组合**：模糊匹配的边界在哪？条件叠加后 SQL 拼接是否正确？

#### 【必须掌握】

搜索测试 5 类场景：精确/模糊匹配、超长输入、无结果、条件切换、条件组合。

#### 【企业场景】

> 你测一个订单搜索功能，条件有"订单号、客户名、日期范围、状态"。你测了每个单独条件都正常，但组合"客户名 + 日期范围 + 状态"时页面报 500——因为后端 SQL 拼接时忘了加括号导致优先级错误。**单独条件通过 ≠ 组合条件通过，搜索测试必须做笛卡尔积式的条件排列。**

#### 【面试考察】

> "搜索功能的测试，你从哪些方面设计用例？"
>
> 参考回答：按搜索流程拆——① 输入环节（空输入、特殊字符、超长、SQL 注入关键字）；② 匹配环节（精确/模糊、大小写、全角半角）；③ 结果环节（有结果、无结果、结果过多时的分页）；④ 组合环节（多条件 AND/OR 逻辑）。

#### 【易错点】

| 常见遗漏 | 补充 |
|---------|------|
| 只测"搜得到"的情况 | "搜不到"同样要验证——无结果时的提示文案、页面是否空白、是否有推荐搜索 |
| 忽略条件切换 | 选条件A→搜→换成条件B→搜，如果页面缓存了上一次结果就是 Bug |

### 维度 3：表单测试

#### 【课程原话/定义】

> - 表单按钮功能正常实现
> - 下拉列表数据完整、正确，可以正常选择，是否支持模糊匹配
> - 文件上传大小、尺寸、格式、数量、文件内容规则验证
> - 表单提交，删除，修改后是否有提示信息
> - 浏览器的前进、后退、刷新按钮，是否会造成数据重现或页面报错
> - 提交表单是否支持回车键和 Tab 键
> - 数据重复检验
> - 提交的数据是否能正确保存到数据库中

#### 【为什么？】

表单是 Web 应用的数据入口。用户在表单里填的数据最终要进数据库——如果表单校验漏了，脏数据进了库，后续所有报表、分析、业务逻辑全乱了。**表单测试 = 数据质量的第一道防线。**

#### 【必须掌握】

表单 8 类测试点，尤其重点：文件上传规则、浏览器导航影响、数据库落库验证。

#### 【企业场景】

> 你测一个"新增客户"表单，所有字段填对了提交成功。但你点浏览器的"后退"按钮，页面回到表单页，再点"前进"，结果又提交了一次——数据库里出现两条一模一样的客户记录。这是典型的"重复提交"漏洞，解决方式：前端按钮置灰 + 后端 Token 防重。

#### 【面试考察】

> "表单测试有哪些易遗漏的点？"
>
> 参考回答：① 浏览器前进/后退/刷新是否导致重复提交；② Tab 键跳转顺序是否符合用户习惯；③ 文件上传——不只是大小限制，还有空文件、损坏文件、文件名含特殊字符；④ 下拉列表数据源是否实时更新（还是缓存了旧数据）。

#### 【易错点】

| 易遗漏场景 | 为什么重要 |
|-----------|-----------|
| 浏览器刷新导致重复提交 | 用户习惯性 F5，不做防重 = 生产事故 |
| 文件上传"0 字节文件" | 很多校验只检查大小上限，不检查下限 |
| 下拉列表数据不完整 | 可能是数据源更新了但前端缓存了，也可能是接口分页没取全 |
| 表单"回车提交" | 用户在最后一个输入框按回车应触发提交，而不是页面刷新 |

#### 【我的理解】

### 维度 4：输入域测试

#### 【课程原话/定义】

> - 输入类型检验
> - 输入长度检验
> - 必填项检验
> - 重复性检验
> - 空格检查
> - 安全性检查

#### 【为什么？】

输入域是用户和系统的"对话窗口"，也是攻击者最常利用的入口。输入域测试的本质是回答一个问题：**系统能正确处理"所有可能的输入"吗？** 正常输入谁都会测，但空格、超长、特殊字符、脚本注入——这些边缘输入才是 Bug 和漏洞的高发区。

#### 【必须掌握】

6 类输入域测试维度，能立即应用到任何输入框。

#### 【企业场景】

> 你测一个"用户昵称"输入框，需求只写"不超过 20 个字符"。你要测的不止是 21 个字符能不能提交——还有：纯空格算不算？前后空格要不要自动 trim？emoji 表情算几个字符？输入 `<script>alert(1)</script>` 会不会被执行？保存后显示时是否被转义？

#### 【面试考察】

> "输入框的测试，你的检查清单是什么？"
>
> 参考回答：① 类型（数字框输入字母、邮箱框不输@）；② 长度（最小值、最大值、超长截断还是报错）；③ 必填（空值、纯空格）；④ 重复（唯一性约束是否有后端校验）；⑤ 空格（前中后空格的处理策略）；⑥ 安全（XSS、SQL注入关键字）。

#### 【易错点】

| 常见 Bug | 根因 |
|---------|------|
| 前端限制了长度但后端没限制 | 抓包改参数直接绕过前端校验 |
| 必填校验只在 JS 做 | 禁用 JS 后直接提交空数据 |
| trim 处理不一致 | 前端 trim 了，后端没 trim，"abc "和"abc"被认为是不同记录 |

#### 【我的理解】

>

### 维度 5：分页测试

#### 【课程原话/定义】

> - 没有数据时界面展示情况
> - 翻页后数据展示情况
> - 分页的总页数及当前页数显示是否正确
> - 是否能正确跳转到指定的页数

#### 【为什么？】

分页看着简单，但因为涉及"前端展示 + 后端查询"的配合，出问题往往是数据级别的事故——比如第 3 页展示的数据和第 2 页有重复，或者"总页数 5 页"但翻到第 5 页是空的。**分页 Bug 的破坏力在于用户会质疑"数据是不是丢了"。**

#### 【必须掌握】

分页测试 4 场景 + 边界页码（第 1 页、最后一页、超出总页数的页码）。

#### 【企业场景】

> 你测一个订单列表，共 100 条，每页 10 条，总共 10 页。你翻到第 5 页发现有一条订单和第 4 页最后一条重复——原因是后端 SQL 的 OFFSET 计算在并发写入时有偏移。分页测试要特别关注"数据一致性"：翻页过程中是否有新增/删除数据导致内容重复或遗漏。

#### 【面试考察】

> "分页功能怎么测？"
>
> 参考回答：① 边界：第 1 页、最后一页、输入 0 或负数页码、输入超大页码（如 99999）；② 数据一致性：翻页时不重复不遗漏；③ 空状态：无数据时的展示；④ 动态数据：翻页过程中有新数据写入时的表现。

#### 【易错点】

| 易忽略 | 补充 |
|--------|------|
| 只有 1 页数据时分页组件怎么显示 | 应该隐藏分页组件或显示"1/1 页"，而不是显示"0/0"或报错 |
| 跳页输入框输入非数字 | 输入"abc"或"-1"，应做输入过滤 |
| 数据刚好是页大小的整数倍 | 最后一页应该完整显示，而不是多出一个空页 |

#### 【我的理解】

### 维度 6：交互性数据测试

#### 【课程原话/定义】

> - 前台的数据操作是否对后台产生相应正确的影响
> - 用户的权限，是否随着授权而变化

#### 【为什么？】

Web 应用的特点是"前台操作 → 后台响应 → 数据变化"。交互性测试验证的是这个链条的完整性。**最致命的 Bug 不是系统报错，而是前台显示"操作成功"但后台数据根本没变——用户以为搞定了，其实没有。**

#### 【必须掌握】

前台操作后的后端数据验证方法（直接查数据库或通过 API 回查），以及权限变更的即时生效验证。

#### 【企业场景】

> 你测一个"修改用户角色"功能：管理员把用户 A 从"普通用户"改成"管理员"。你不仅要看前台提示"修改成功"，还要做两件事：① 查数据库 role 字段是否真的变了；② 用 A 的账号重新登录，看管理员的菜单权限是否立刻生效（还是需要重新登录才生效——涉及 Session/Token 刷新策略）。

#### 【面试考察】

> "你如何验证前端操作真正影响了后端数据？"
>
> 参考回答：三步验证——① 看前端反馈（提示信息是否正确）；② 查 API 返回（Network 面板看接口响应体）；③ 查数据库或通过另一个查询接口回读数据（如改完用户名后，去用户列表页搜索确认新名字出现了）。三层交叉验证才能真正确认。

#### 【易错点】

| 常见遗漏 | 正确做法 |
|---------|---------|
| 只验证了"前台提示成功" | 必须验证数据库实际变更——前端提示可能是 hardcode 的 |
| 权限变更后不测"即时生效" | 有些系统权限在登录时写入 Session，中途改权限不生效 |
| 不验证"反向操作" | 改了 → 验证改对了 → 再改回来 → 验证能改回来 |

#### 【我的理解】

>

### 维度 7：链接测试

#### 【课程原话/定义】

> - 是否能够直接链接查看
> - 是否有权限控制
> - 是否直接执行，并返回相应结果页

#### 【为什么？】

Web 的核心是超链接——一个电商网站可能有几千个链接。链接测试的三个层次层层递进：能不能访问（404？）、该不该访问（越权？）、访问后对不对（跳转目标正确？）。**链接测试最怕的是"知道 URL 就能绕过登录直接访问"——这是 P0 级安全漏洞。**

#### 【必须掌握】

链接测试 3 层：可访问性 → 权限校验 → 跳转正确性。

#### 【企业场景】

> 你拿到一个后台管理系统的 URL 清单。你在未登录状态下直接访问 `/admin/user/list`——如果能打开，这是严重越权漏洞。更隐蔽的情况：普通用户登录后，把 URL 里的 `id` 参数从自己的改成别人的，看到了不该看的数据——这是水平越权。

#### 【面试考察】

> "链接测试怎么做？重点测什么？"
>
> 参考回答：① 死链接检查（工具扫描 + 手工抽查关键路径）；② 权限链接（未登录直接访问需登录页面 → 应跳到登录页）；③ 越权链接（低权限用户访问高权限 URL）；④ 外链（跳转到外部站点的链接是否安全、是否加 noopener）。

#### 【易错点】

| 常见遗漏 | 补充 |
|---------|------|
| 只测站内链接 | 外链也要测——外链失效、外链被劫持、外链跳转后无法返回 |
| 权限校验只用"未登录"测 | 登录后还要测角色权限——普通用户 vs 管理员 vs 超级管理员 |
| 不测链接的 HTTP 方法 | 有些链接是 GET（安全），有些是 GET 但有副作用（如 `GET /delete?id=1` — 危险！） |

## 三、7 大维度全景总结

```
UI测试 → 搜索测试 → 表单测试 → 输入域测试 → 分页测试 → 交互性测试 → 链接测试
  (1)       (2)        (3)         (4)         (5)         (6)         (7)
```

| 维度    | 核心关注           | 最易遗漏                |
| ----- | -------------- | ------------------- |
| UI 测试 | 一致性、响应式、图片     | 响应式下文字重叠/按钮溢出       |
| 搜索测试  | 模糊匹配、条件组合      | 条件切换后缓存未清理          |
| 表单测试  | 提交、文件上传、浏览器导航  | 刷新重复提交、0字节文件        |
| 输入域测试 | 类型/长度/必填/空格/安全 | 前端校验绕过（抓包改参）        |
| 分页测试  | 边界页、数据一致性、跳页   | 动态数据导致重复/遗漏         |
| 交互性测试 | 前后端数据一致性、权限生效  | 前台提示成功 ≠ 数据库真变了     |
| 链接测试  | 可访问性、权限、跳转     | 水平越权（改 URL 参数看别人数据） |
