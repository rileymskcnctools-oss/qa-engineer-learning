## 一、什么是浏览器开发者工具

### 【课程原话/定义】

> 浏览器开发者工具（Browser Developer Tools）是现代 Web 开发中非常重要的工具，提供了许多强大的功能，用于调试、分析和优化 Web 应用程序。每个主流浏览器都提供了自己的开发者工具。

### 【为什么？】

对测试人员来说，开发者工具不是"开发才用的东西"——它是你看穿 Web 页面表层、直到底层数据和网络请求的"X 光机"。**不用 DevTools 的测试 = 盲测：页面报错了不知道是前端还是后端，数据不对不知道是接口没返回还是前端没渲染。** Ch16 学了很多 Bug 类型，那些 Bug 的定位入口几乎全是 DevTools。

### 【必须掌握】

三种打开方式：F12 / 右键→审查元素 / 浏览器菜单→开发者工具。Elements 和 Network 两大面板的核心操作。

### 【企业场景】

> 开发跟你说"这个 Bug 我复现不了"。你打开 DevTools → Console，把红色报错截图 + Network 里那个返回 500 的接口截图一起发过去，开发秒回"知道了，后端字段名改了"。**DevTools 就是测试人员和开发之间的共同语言——截图比描述有力，数据比感觉可靠。**

### 【面试考察】

> "你在测试中怎么使用浏览器的开发者工具？"
>
> 参考回答：先说 3 个最常用的面板（Elements / Network / Console）各自做什么 → 举一个实际场景（比如定位接口报错、查看 DOM 元素隐藏属性、验证前端传参是否正确）——让面试官知道你不是"会用"，而是"在工作中用"。

### 【易错点】

| 误区 | 正解 |
|------|------|
| DevTools 是开发用的，测试不用学 | 测试用 DevTools 定位问题可以大幅减少沟通成本——"页面显示不对" vs "接口 /api/xxx 返回 500"，后者开发直接动手修 |
| 只用 Chrome DevTools | Firefox、Edge、Safari 的 DevTools 也要大概了解——兼容性测试时可能需要在特定浏览器里排查 |

### 【我的理解】

## 二、开发者工具打开方式

### 【课程原话/定义】

> - 浏览器菜单 → 开发者工具
> - 右击页面任何位置 → 审查元素
> - F12

### 【为什么？】

三种方式各有适用场景：F12 最快（键盘党）、右键→审查用于"想定位某个具体元素"、菜单入口用于"不知道快捷键时"。**注意：右键的"审查元素"会直接跳到 Elements 面板并高亮点击的元素——这是测试中最常用的打开方式。**

### 【必须掌握】

三种打开方式 + "审查元素"自动定位到被点击 DOM 节点的特性。

## 三、Elements 面板

### 【课程原话/定义】

> - 定位元素
> - 查看元素源码
> - 查看元素样式
> - 页面跳转到元素面板指定的元素：Scroll into view

### 【为什么？】

Elements 面板让你看到页面的"骨头"——HTML 结构 + CSS 样式。测试人员用它做三件事：① **确认元素是否存在**（比如某个按钮的 class 或 id，自动化测试要用来定位）；② **查看隐藏信息**（data-* 属性、被 CSS 隐藏的内容）；③ **临时修改验证**（改一个 CSS 属性值看是不是这个问题导致显示异常）。

### 【必须掌握】

Elements 面板的 4 个核心操作：

| 操作               | 怎么做                          | 测试场景                        |
| ---------------- | ---------------------------- | --------------------------- |
| 定位元素             | 右键→审查，或 Ctrl+Shift+C 点击页面元素  | 想知道"这个按钮的 class/id 是什么"     |
| 查看源码             | 右侧查看 HTML 层级结构               | 确认 DOM 是否正确渲染（比如下拉选项是否全部生成） |
| 查看样式             | 右侧 Styles 面板，看应用了哪些 CSS      | 排查布局错乱——哪个 CSS 属性被覆盖了       |
| Scroll into view | 右键 DOM 节点 → Scroll into view | 页面太长时快速滚动到目标元素              |

### 【企业场景】

> 你写自动化脚本，需要定位"提交订单"按钮。右键→审查，发现这个按钮没有 id，class 是 `btn-submit primary large`。你记下 `class="btn-submit"` 作为定位器。但你又注意到这个 class 动态变化——每次刷新 class 后面跟了一串随机数。你改为用 `button[type='submit']` 定位。**先 Elements 看一眼 DOM 结构再写自动化，少踩 80% 的定位坑。**

### 【面试考察】

> "Elements 面板你测试中怎么用？"
>
> 参考回答：① 元素定位——为自动化脚本找独一无二的定位器；② 样式调试——临时改 CSS 验证布局 Bug 的原因；③ DOM 结构验证——确认前端是否正确渲染了数据（比如列表是否渲染了 10 行而不是 9 行）；④ 查看 data-* 属性——验证前端绑定的隐藏数据是否正确。

### 【易错点】

| 易遗漏 | 补充 |
|--------|------|
| 只看 Elements，不看右侧 Styles | Styles 面板能看到最终生效的样式（覆盖链），是排查 UI Bug 的关键 |
| DevTools 里改了 CSS 就认为问题找到了 | 刷新就没了——找到根因后要在源码里确认，不只是临时改一下 |

### 【我的理解】

## 四、Network 面板

### 4.1 记录网络活动

#### 【课程原话/定义】

> - 停止记录网络请求
> - 清除记录
> - 保存跨页面加载的请求

#### 【为什么？】

Network 面板记录了页面加载过程中**每一个** HTTP 请求的完整信息——URL、方法、状态码、耗时、请求参数、响应内容。测试人员用它回答最核心的问题：**"数据对不对？数据从哪来？为什么这么慢？"**

#### 【必须掌握】

Network 面板的基本操作：开始/停止录制、清除、Preserve log（保留跨页面请求）。

- **Preserve log**（保存跨页面加载的请求）：勾选后，页面跳转不会清空请求记录——排查登录→跳转→主页这整条链路时必开。

#### 【易错点】

| 误区 | 正解 |
|------|------|
| 页面加载完再看 Network | 必须先打开 DevTools → Network 面板，再刷新页面/触发操作——否则之前的请求不会被记录 |
| Preserve log 不勾选 | 页面跳转后之前的请求全丢了——排查登录流程、支付流程时必须勾选 |

#### 【我的理解】

### 4.2 清除缓存

#### 【课程原话/定义】

> - 禁用浏览器缓存
> - 手动清除浏览器缓存
> - 清空缓存并硬性重新加载

#### 【为什么？**

浏览器缓存是测试的"障眼法"——你改了数据，页面显示的还是旧的；开发修了 Bug，你看到的还是错误页面。**清除缓存不是"偶尔做一下"的操作，而是每次验证前的标准动作。** 最常用的是 DevTools → Network → Disable cache（只对当前标签页生效，不影响其他标签页）。

#### 【必须掌握】

三种清除方式的区别：

| 方式 | 怎么做 | 适用场景 |
|------|--------|---------|
| Disable cache | Network 面板勾选 "Disable cache" | 日常测试，开发阶段（DevTools 打开时生效） |
| 手动清除缓存 | 浏览器设置→清除浏览数据 | 需要清除 Cookie/Storage 时 |
| 清空缓存并硬性重新加载 | F12 打开后长按刷新按钮→第三个选项 | 改了 CSS/JS 但页面没更新时 |

#### 【企业场景】

> 开发说"修好了你再看"。你刷新页面——还是老样子。开发说"我明明改了"。你打开 DevTools → Network → 勾选 Disable cache → 再刷新——Bug 修复了。你回复开发："修好了，之前是缓存问题。"**2 秒钟的操作，省了 10 分钟的来回扯皮。**

#### 【易错点】

| 常见 Bug | 后果 |
|---------|------|
| 验证 Bug 修复时忘了关缓存 | 看到旧页面以为没修好 → 重复提 Bug → 开发对你不信任 |
| 只在 DevTools 禁用缓存，发布后用户有缓存 | 测试过程中也至少有一次"不关缓存"的验证——模拟真实用户首次访问 |

#### 【我的理解】

### 4.3 模拟网络

#### 【课程原话/定义】

> - 离线模拟
> - 慢速网络模拟

#### 【为什么？**

你不能让用户都装千兆光纤——弱网环境下的表现是 Web 应用质量的重要维度。Network 面板的 throttling 让你在测试机上就能模拟 3G/4G/离线，不用真的跑到电梯里去测。

#### 【必须掌握】

Network 面板 → "No throttling" 下拉 → 选择预设（Slow 3G / Fast 3G / Slow 4G / Offline），或添加自定义配置。离线模拟用于测试：断网提示、离线缓存、PWA 离线功能。

#### 【企业场景】

> 用户投诉"在地铁上用流量打开页面要等 10 秒"。你在工位上，Network 面板选 "Slow 3G"，刷新页面——加载 12 秒。你发现首屏有一个 3MB 的未压缩大图。提 Bug："弱网环境首屏加载超 10 秒，建议压缩首屏图片 + 懒加载非首屏资源。"

#### 【面试考察】

> "你怎么测试弱网环境下的表现？"
>
> 参考回答：Chrome DevTools → Network → Throttling → Slow 3G。重点测：① 加载时间是否在可接受范围；② loading 状态是否有提示（不是白屏）；③ 超时是否有友好提示而非报错；④ 断网后恢复网络，页面是否能正常恢复。

#### 【易错点】

| 误区 | 正解 |
|------|------|
| 只测 Slow 3G | 还要测上网→断网→恢复的切换——用户进电梯断网、出电梯恢复，页面不应该崩 |
| Throttling 只限制下载速度 | 还要关注上传——文件上传功能在弱网下的超时和重试机制 |

### 4.4 查看网络数据

#### 【课程原话/定义】

> - Name：资源名称以及 URL 路径
> - Status：HTTP 状态码
> - Type：请求资源的类型
> - Initiator：解释请求是怎么发起的
> - Size：服务器响应头 + 响应主体的总大小
> - Time：从请求开始到响应结束的总持续时间
> - Waterfall：每个请求活动的可视细分

#### 【为什么？**

这 7 列是 Network 面板的核心数据，每列都回答一个关键问题：

| 列名 | 回答的问题 |
|------|-----------|
| Name | 请求的是什么 |
| Status | 请求成功还是失败（200/404/500） |
| Type | 是接口、JS、图片还是 CSS |
| Initiator | 谁触发的这个请求（哪个 JS 文件哪一行） |
| Size | 传输了多少数据 |
| Time | 花费了多长时间 |
| Waterfall | 时间花在哪个阶段（DNS/连接/等待/下载） |

#### 【必须掌握】

7 列的含义 + 点击单条请求查看 Headers/Preview/Response/Timing 详情。

- **Headers**：请求头/响应头（检查 Token、Content-Type、CORS）
- **Preview**：格式化预览 JSON 数据
- **Response**：原始响应内容
- **Timing**：耗时分解（DNS Lookup → TCP → SSL → Request → Response）

#### 【企业场景】

> 你测一个列表页，显示数据不对。打开 Network → 找到 `/api/list` 这个 XHR 请求 → 点 Response，看到返回的 JSON 里价格字段是 `null`。截 Response 图发给开发："接口返回 price 字段为 null，前端无法渲染价格。"开发立刻定位到后端数据清洗漏了。**不看 Response 你永远不知道是前端渲染错了还是后端数据就错了。**

#### 【面试考察】

> "怎么通过 Network 面板定位一个接口问题？"
>
> 参考回答：① 找到目标 XHR 请求 → 看 Status（非 200 直接定位到后端问题）；② 看 Response 内容是否正确（Status 200 但数据不对也是 Bug）；③ 看 Headers 的 Request Payload → 前端传参是否正确；④ 看 Timing → 如果 Waiting (TTFB) 特别长，说明后端处理慢。

#### 【易错点】

| 常见遗漏 | 正确做法 |
|---------|---------|
| 只看 Status 不看 Response | Status 200 + Response 空数组/错误数据 = 仍然有 Bug |
| 不看 Request Payload | 前端传参多了/少了/错了——开发会说是前端的问题 |

#### 【我的理解】

### 4.5 筛选资源

#### 【课程原话/定义】

> - 显示过滤器
> - 按资源类型筛选

#### 【为什么？**

一个页面可能发出 50~200 个请求——全混在一起找不到你关心的那个。筛选功能让你只看 XHR/Fetch（接口请求）、只看 JS、只看 CSS、只看图片、只看失败的请求。**最常用的筛选是 XHR + 只看非 200 状态码。**

#### 【必须掌握】

资源类型筛选按钮：XHR（接口请求）、JS、CSS、Img、Media、Font、Doc、WS。过滤器输入框支持按名称/URL 模糊搜索。还可以按状态码过滤（如 `status-code:500`）。

#### 【企业场景】

> 页面报错了，但 Console 里有 3 个红色报错、Network 有 87 个请求。你点 XHR 筛选 → 只剩 12 个接口请求 → 看到一个红字的 500。点开看 Response——`{"error": "Database connection timeout"}`。30 秒定位问题，把这条请求的截图 + Response 发给开发。

## 五、Elements + Network 联动实战场景

### 【企业场景】

以下是一个完整的 Bug 定位流程，展示 Elements 和 Network 如何配合：

> **用户反馈**：商品详情页价格显示为 ¥0.00。
>
> **你的排查**：
> 1. 打开 DevTools → Network → 勾选 Disable cache → 刷新页面
> 2. 筛选 XHR → 找到 `/api/product/detail?id=123` → Status 200 ✓
> 3. 点 Response → `"price": 99.00` → 后端数据正确 ✓
> 4. 切到 Elements → Ctrl+Shift+C 点击价格位置 → `<span class="price">¥0.00</span>` 
> 5. 查看右侧 Styles → 发现 `content: "¥0.00"` 是 CSS ::after 伪元素写死的
> 6. **结论**：前端没有正确渲染后端返回的价格，CSS 伪元素覆盖了真实数据
>
> 提 Bug 单：附带 Network Response 截图 + Elements 截图 + 定位结论。
