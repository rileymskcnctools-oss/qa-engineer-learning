## 一、蓝图概述

### 知识点 1：什么是蓝图（Blueprint）

【课程原话/定义】

Flask 中的蓝图是一种**组织和管理应用程序路由与视图的机制**。它允许开发者将相关功能的路由和视图进行分组，从而实现模块化开发。蓝图可以极大地简化大型应用并为扩展提供集中的注册入口。

一个项目可以有多个蓝图。但蓝图不是一个完整的应用，它**不能独立运行**，必须注册到 Flask 应用对象中。

【为什么？】

随着项目变大，所有路由堆在一个文件里会出现三个问题：

1. **单文件爆炸**：100 个路由塞在 `app.py`，滚动查找都困难
2. **命名冲突**：多个模块都定义了 `/list` 路由，互相覆盖
3. **团队协作冲突**：多人同时改同一个 `app.py`，Git 合并天天打架

蓝图解决的不是"能不能写"的问题，而是**"能不能维护"**的问题。就像你不会把公司所有部门的文件堆在一个柜子里——蓝图就是给路由分类归档的文件夹。

【必须掌握】

- 蓝图是什么：路由分组管理机制
- 蓝图不能独立运行，必须 `register_blueprint()` 注册
- 一个应用可以有多个蓝图
- 蓝图适合项目变大、路由增多时使用

【企业场景】

> 你参与一个电商后台开发。系统有商品管理（30+ 接口）、订单管理（20+ 接口）、用户管理（15+ 接口）、数据报表（10+ 接口）。如果全部写在 `app.py`，文件至少 2000 行。
>
> 用蓝图后：
> ```
> app.py              ← 只负责创建 app + 注册蓝图
> goods/
>   __init__.py       ← goods_router = Blueprint(...)
>   views.py          ← 商品相关路由
> order/
>   __init__.py
>   views.py          ← 订单相关路由
> user/
>   __init__.py
>   views.py
> ```
>
> 每个模块独立开发、独立测试，互不干扰。

【面试考察】

> 面试官："Flask 的蓝图是什么？为什么要用？"

**参考回答框架：**

1. 蓝图是 Flask 提供的路由分组管理机制，本质是一个"可插拔的路由集合"
2. 核心作用：模块化（分模块管理路由）、URL 前缀隔离（`url_prefix`）、可复用（同一个蓝图可以注册到不同应用）
3. 和 Django 的 `app` 概念类似，但 Flask 的蓝图更轻量
4. 使用三步：创建 Blueprint 对象 → 定义路由 → `app.register_blueprint()`

【易错点】

| 易混淆 | 正确理解 |
|--------|---------|
| 蓝图 = 独立应用 | 蓝图不是应用，不能单独 `run()`，必须注册到 Flask app |
| `Blueprint(name, __name__)` | 两个参数都是必填的，缺一不可 |
| 蓝图路由不加 `/` 前缀 | 蓝图路由必须用 `/` 开头，否则 Flask 报错 |
| 蓝图层和 Flask 层的路由函数混用 `url_for` | 蓝图中的 `url_for` 需要加蓝图名前缀：`url_for('goods.index')` |

【我的理解】

> 用自己的话解释：为什么单文件管理路由在项目变大时会出问题？蓝图具体解决了哪几个问题？

## 二、蓝图的基本使用

### 知识点 2：创建蓝图对象 + 定义路由 + 注册

【课程原话/定义】

**第一步：创建蓝图对象**

```python
from flask import Blueprint

goods_router = Blueprint(name="goods", import_name=__name__)
```

参数说明：
- `name`：蓝图名称（字符串，必填）
- `import_name`：蓝图所在模块，一般写 `__name__`（必填）

**第二步：定义路由**

路由必须以 `/` 开头。方法和普通 Flask 路由一样：

```python
@goods_router.route("/")
def index():
    return {"code": 0, "msg": "get success", "data": []}

@goods_router.route("/add", methods=["POST"])
def add_goods():
    return {"code": 0, "msg": "add success"}
```

**第三步：注册蓝图**

```python
from flask import Flask

app = Flask(__name__)

if __name__ == '__main__':
    app.register_blueprint(goods_router)
    app.run(port=5055, debug=True)
```

【为什么？】

`import_name` 参数看起来总是写 `__name__`，为什么还要求必须传？

这是 Flask 的设计惯例——Flask 用它来定位蓝图相关的资源（模板文件夹、静态文件夹）。虽然大多数场景填 `__name__` 就行，但当你把蓝图定义在包的不同层级时，`import_name` 决定了 Flask 从哪里找关联文件。

【必须掌握】

- 三步流程：创建 → 定义路由 → 注册
- `Blueprint(name, import_name)` 两个参数必填
- `register_blueprint()` 必须在 `app.run()` 之前调用
- 蓝图路由以 `/` 开头

【企业场景】

> 你在测试一个微服务项目，后端用 Flask 蓝图管理。开发说"加了一个新接口 `/api/v2/users/export`"。
>
> 你应该能根据项目结构猜测：这个路由大概率在 `user` 蓝图下的某个 views 文件里，路由装饰器是 `@user_router.route("/export")`，注册时加了 `url_prefix="/api/v2/users"`。这样你定位测试目标的速度比盲目搜索 `app.py` 快得多。

【面试考察】

> 面试官："`register_blueprint()` 是在 `app.run()` 之前还是之后调用？为什么？"

**参考回答框架：**

- 必须在 `app.run()` 之前
- 因为 `app.run()` 启动后，Flask 的路由表已经固化，不会再扫描新的路由
- 注册蓝图的本质是把蓝图中的路由"复制"到 Flask 应用的路由映射表中，这个过程只在启动前发生

【易错点】

| 易错 | 原因 |
|------|------|
| 蓝图定义了路由但 404 | 忘了 `register_blueprint()` |
| `register_blueprint()` 放在 `app.run()` 后面 | 路由表已锁定，注册无效 |
| 蓝图路由忘了 `/` 开头 | Flask 的路由规则强制要求 |

【我的理解】

> 用伪代码画出创建蓝图到注册的完整调用链：`Blueprint()` → `@router.route()` → `register_blueprint()`。每一步分别做了什么？

## 三、URL 前缀

### 知识点 3：url_prefix 参数

【课程原话/定义】

注册蓝图时可以指定 `url_prefix` 参数，它是在蓝图上注册的所有路由 URL 自动加上的前缀。

```python
user_router = Blueprint("user", __name__, url_prefix="/user")

@user_router.route("")           # 实际 URL: /user
def user_list():
    return {"code": 0}

@user_router.route("/login", methods=["POST"])  # 实际 URL: /user/login
def login():
    return {"code": 0, "msg": "login success"}

# 注册
app.register_blueprint(user_router)
```

规则：
- `url_prefix` 必须是 `/` 开头的字符串
- 如果路由直接使用前缀值（如只访问 `/user`），`route()` 中传空字符串 `""`
- 如果要在前缀后加子路由，`route()` 中以 `/` 开头

【为什么？】

`url_prefix` 解决的是**不同蓝图之间的 URL 冲突**问题。设想：商品蓝图和订单蓝图都定义了 `/list` 路由。没有前缀时，后注册的会覆盖先注册的。有了前缀：
- 商品模块：`/goods/list`
- 订单模块：`/order/list`

互不冲突。这本质上是**命名空间隔离**——和 Python 的 `import goods` vs `import order` 是同一个思路。

【必须掌握】

- `url_prefix` 在 `Blueprint()` 构造时定义，或以 `register_blueprint(router, url_prefix="/xxx")` 方式传入
- 前缀必须以 `/` 开头
- `route("")` + `url_prefix="/user"` = 访问 `/user`
- `route("/login")` + `url_prefix="/user"` = 访问 `/user/login`

【企业场景】

> 你接手一个老项目的接口测试。API 文档写着：
> - `GET /api/v1/products`
> - `POST /api/v1/products`
> - `GET /api/v1/orders`
>
> 看代码发现三个蓝图：`product_router`、`order_router`、`user_router`，注册时都加了 `url_prefix="/api/v1"`。
>
> 这种设计的优势：版本升级时，只要把 `v1` 改成 `v2`，整个模块的路由同时生效，不需要逐个改路由装饰器。

【面试考察】

> 面试官："有两个蓝图都定义了 `/list` 路由，会发生什么？怎么解决？"

**参考回答框架：**

1. 如果不加 `url_prefix`，后注册的蓝图会覆盖先注册的同名路由，先注册的那个变成"死路由"（永远不会被匹配）
2. 解决方案：给两个蓝图分别设置不同的 `url_prefix`，如 `/goods` 和 `/order`
3. 如果已经有前缀还冲突 → 说明前缀设得不够细，需要增加层级

【易错点】

| 场景 | 错误写法 | 正确写法 |
|------|---------|---------|
| 访问 `/user` | `route("/")` | `route("")` |
| 访问 `/user/login` | `route("login")` | `route("/login")` |
| `url_prefix` 没加 `/` | `url_prefix="user"` | `url_prefix="/user"` |

> 重点记忆：`route("")` 代表"和前缀完全一致"，`route("/xxx")` 代表"前缀 + `/xxx`"。

【扩展知识】

`url_prefix` 还可以在注册时覆盖：

```python
# Blueprint 创建时不设 url_prefix
goods_router = Blueprint("goods", __name__)

# 注册时指定
app.register_blueprint(goods_router, url_prefix="/goods")
```

两种方式的区别：
- 构造时定义：前缀和蓝图绑定，无论注册到哪里前缀都不变
- 注册时定义：同一个蓝图可以注册多次，每次用不同前缀（如 `/v1/goods` 和 `/v2/goods`）

【我的理解】

> 如果不用 `url_prefix`，而是每个路由装饰器里手动写完整路径（如 `@router.route("/user/login")`），会有什么问题？

## 四、蓝图架构总结

### 知识点 4：单文件 vs 蓝图架构对比

【课程原话/定义】

一个项目可以有多个蓝图。蓝图不能独立运行，必须注册到 Flask 应用中。

应用一旦创建后，只有销毁整个应用对象才能注销蓝图——这意味着蓝图的生命周期和 Flask app 是绑定的。

【为什么？】

蓝图是在 `app.run()` 之前的初始化阶段完成的，Flask 把蓝图路由合并到全局路由映射表中。一旦应用跑起来，这个映射表就固定了。这是 Flask 的设计选择——简单、性能好（不需要运行时查表），代价是动态增减蓝图需要重启应用。

| | 单文件 | 蓝图 |
|---|---|---|
| 路由数量 < 10 | 够用，简单直接 | 过度设计，增加复杂度 |
| 路由数量 > 30 | 维护困难，单文件过长 | 适合，模块清晰 |
| 多人协作 | Git 冲突频繁 | 每人维护自己的蓝图文件 |
| 接口版本管理 | 每个路由改装饰器 | 改一个 `url_prefix` |
| 代码复用 | 路由无法复用 | 蓝图可以跨项目复用 |

【必须掌握】

- 蓝图适合中大型项目（20+ 路由或多模块）
- 小项目（5 个路由以内）用单文件反而更清晰——不要为了用蓝图而用蓝图
- 蓝图生命周期绑定 Flask app，不支持运行时动态注销

【企业场景】

> 你在测试一个 Flask 微服务。CI 流程中，每次部署要跑回归测试。开发告诉你"路由都是蓝图管理的，每个蓝图对应一个微服务模块"。
>
> 你可以怎么做？对应每个蓝图写一个测试文件：
> ```
> tests/
> ├── test_goods.py      ← 测试 /goods/* 的所有接口
> ├── test_order.py      ← 测试 /order/* 的所有接口
> └── test_user.py       ← 测试 /user/* 的所有接口
> ```
>
> 测试结构和蓝图结构一一对应，维护起来一目了然。

【面试考察】

> 面试官："什么时候该用蓝图，什么时候不该用？"

**参考回答框架：**

1. 该用蓝图：项目路由 > 20 条、多人协作、需要 URL 版本前缀、需要跨项目复用路由模块
2. 不该用蓝图：Demo/原型（5 条路由以内）、个人学习项目且路由不复杂、过度设计反而增加理解成本
3. 关键判断标准：看"路由映射表"能不能一眼看清——如果 `app.py` 的路由列表需要滚动才能看完，就该拆蓝图了

【易错点】

| 误区 | 事实 |
|------|------|
| "蓝图就是 Flask 的微服务" | 蓝图只是路由分组，不涉及进程隔离、独立部署，和微服务是两回事 |
| "每个接口都要一个蓝图" | 蓝图按业务模块分，不是按接口分 |
| "蓝图可以随时增删" | 蓝图只能在应用启动前注册，运行中不能动态增删 |

【我的理解】

> 给你的学生管理系统（`03_platform_backend`）设计一个蓝图重构方案。你会拆成哪几个蓝图？每个蓝图负责哪些路由？`url_prefix` 怎么设？
