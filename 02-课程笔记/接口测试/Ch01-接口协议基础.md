## 一、网络模型基础

### 知识点 1：OSI 七层模型 vs TCP/IP 四层模型

【课程原话/定义】
三种网络模型：OSI 七层模型、TCP/IP 四层模型、五层体系结构（OSI 和 TCP/IP 的综合）。OSI 是概念性框架（不是标准），TCP/IP 四层是互联网基础通信架构，五层是两者的折中——实际应用中还是 TCP/IP 四层为主。

【为什么？】
为什么要分层？——每一层只关注自己的职责，层与层之间通过标准接口通信。类比快递：你写地址（应用层）→ 快递员打包（传输层）→ 分拣中心路由（网络层）→ 货车运输（链路层/物理层）。任何一层出问题只影响那一层，不会全盘崩溃。

OSI 七层过于理想化（会话层、表示层在实际网络中几乎没有独立实现），所以被更务实的 TCP/IP 四层取代。**面试常考的是能说出每一层代表协议**。

【必须掌握】

| 层级  | OSI 七层 | TCP/IP 四层 | 代表协议                 |
| --- | ------ | --------- | -------------------- |
| 7   | 应用层    | 应用层       | HTTP, FTP, SMTP, DNS |
| 6   | 表示层    | ↑         | （并入应用层）              |
| 5   | 会话层    | ↑         | （并入应用层）              |
| 4   | 传输层    | 传输层       | TCP, UDP             |
| 3   | 网络层    | 网络层       | IP, ICMP, ARP        |
| 2   | 数据链路层  | 网络接口层     | Ethernet, Wi-Fi      |
| 1   | 物理层    | ↑         | 网线、光纤、无线电            |

【企业场景】
你在公司排查"接口为什么超时"：先 ping（网络层 ICMP），再 telnet 端口（传输层 TCP），最后 curl 接口（应用层 HTTP）。这是自底向上的排查思路——对应四层模型的逆向验证。

【面试考察】
面试官："OSI 七层模型和 TCP/IP 四层模型有什么区别？"

参考回答框架：
1. OSI 七层是理论模型，TCP/IP 四层是实际使用的协议栈
2. OSI 多了表示层和会话层，TCP/IP 把它们合并到应用层
3. OSI 先有模型后有协议，TCP/IP 先有协议后有模型
4. 实际工作中按 TCP/IP 四层来理解即可

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 把 HTTP 说成传输层协议 | HTTP 是应用层协议，依赖传输层的 TCP |
| 认为七层比四层"更先进" | 七层是理论模型，过度设计；四层是工程实践的产物 |
| 混淆"协议"和"模型" | 模型是框架（怎么分层），协议是实现（每层用什么通信规则） |

【我的理解】
> （用自己的话画出四层模型，每层标注一个你认识的协议。为什么 TCP/IP 四层比 OSI 七层更实用？）

## 二、传输层协议

### 知识点 2：TCP 协议

【课程原话/定义】
TCP（Transmission Control Protocol）是传输层中**面向连接、可靠、基于字节流**的协议。建立连接需要"三次握手"，终止连接需要"四次挥手"。

【为什么？】
TCP 的可靠性来自三个核心机制：

1. **三次握手** — 确认双方收发能力正常后才传输数据（类比：打电话——"喂？""听得到""好的开始聊"）
2. **错误重传** — 数据丢了自动重发
3. **拥塞控制** — 网络堵了就降速

这些机制让 TCP 成为互联网最基础的可靠传输协议。代价是：慢（握手开销）+ 重（头部 20 字节+）。

三次握手和四次挥手的具体过程在后续章节详讲，这里先记住结论。

【必须掌握】
- TCP 是面向连接的：通信前必须建立连接
- TCP 是可靠的：有确认、重传、排序机制
- 三次握手建立连接，四次挥手断开连接
- 适用场景：对数据完整性要求高的场景（用户登录、支付、文件传输）

【企业场景】
你在测一个登录接口——底层走的必然是 TCP（因为 HTTP 基于 TCP）。如果登录请求超时，可能是 TCP 握手阶段就失败了（防火墙拦截端口、服务器不响应 SYN）。排查时先 `telnet ip port` 验证 TCP 连接是否通。

【面试考察】
面试官："为什么 TCP 是可靠的？UDP 是不可靠的？"

参考回答框架：
1. TCP 面向连接（三次握手），UDP 无连接直接发
2. TCP 有序号和确认机制（ACK），丢包会重传；UDP 发出就不管
3. TCP 有流量控制和拥塞控制；UDP 没有
4. 结论：TCP 保证数据完整到达，UDP 保证速度

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 认为 TCP 一定比 UDP 好 | 没有哪个更好——看场景。可靠性→TCP，实时性→UDP |
| "TCP 是安全的" | TCP 保证可靠传输 ≠ 安全（加密是 TLS/SSL 的事，在应用层） |
| 混淆三次握手和四次挥手 | 握手是建连接（3步），挥手是断连接（4步），挥手多一步是因为 TCP 半关闭状态 |

### 知识点 3：UDP 协议

【课程原话/定义】
UDP（User Datagram Protocol）一旦把数据发出去就不保留备份，仅在 IP 包头部加入复用和数据校验字段。UDP 常被认为是**不可靠**的数据包协议。

【为什么？】
UDP 把"快"做到了极致：不需要建立连接 → 零延迟；不重传丢失的数据 → 不阻塞后续数据。代价是：数据可能丢、可能乱序、可能重复。

类比：TCP = 挂号信（签收确认、丢了补发）；UDP = 明信片（扔邮筒就不管了，丢了就丢了）。

【必须掌握】
- UDP 无连接：发送前不需要建立连接
- UDP 不可靠：不保证送达、不保证顺序
- UDP 头部仅 8 字节（TCP 是 20 字节+），开销极小
- 适用场景：实时音视频、在线游戏、DNS 查询、直播

【企业场景】
测试直播接口时，视频流走的是 UDP（或基于 UDP 的 QUIC）。如果你发现画面卡顿、花屏——这可能不是"bug"，而是 UDP 丢包的正常表现。测试策略应关注：丢包率阈值、重连机制、降级策略。

【易错点】

| | TCP | UDP |
|------|-----|-----|
| 连接 | 面向连接 | 无连接 |
| 可靠性 | 可靠（确认+重传） | 不可靠 |
| 速度 | 慢 | 快 |
| 头部开销 | 20-60 字节 | 8 字节 |
| 适用 | HTTP、FTP、邮件 | 视频、游戏、DNS |
| 面试关键词 | 三次握手、四次挥手 | 尽力而为、无状态 |

【我的理解】
> （找一个你常用的 app，猜想它的哪些功能走 TCP、哪些走 UDP？为什么？）

## 三、RPC 协议

### 知识点 4：RPC — 像调本地函数一样调远程服务

【课程原话/定义】
RPC（Remote Procedure Call）：以本地代码调用的方式实现远程执行。主要用于**公司内部**的服务调用。优势：传输效率更高、性能损耗更低、自带负载均衡、更好的服务治理能力。

常见 RPC 协议：Dubbo（Java）、gRPC（Google，基于 Protocol Buffers）、Thrift（Apache）、JSON-RPC。

【为什么？】
RPC 解决的核心问题：微服务架构下，服务 A 调用服务 B 的函数，如果走 HTTP + JSON，每次都要序列化/反序列化 JSON（慢、带宽大）。RPC 用二进制协议（如 Protobuf），体积小、解析快，性能通常是 HTTP+JSON 的 3-10 倍。

类比：HTTP = 寄一封中文信（人类可读，但翻译慢）；RPC = 发电报（机器码，人看不懂但极快）。

【必须掌握】
- RPC 的核心思想：调用远程方法像调用本地方法
- RPC 主要用于内网微服务间通信
- gRPC 使用 Protocol Buffers 作为序列化格式
- RPC vs HTTP：RPC 更快但耦合更强；HTTP 更通用但开销更大

【企业场景】
公司的微服务架构：用户服务（Java/Dubbo）→ 订单服务（Go/gRPC）。你在测订单接口时，如果订单服务内部又调了用户服务走 RPC——那你测的 HTTP 接口只是最外层。排查深层次 bug 需要理解整个调用链。

【面试考察】
面试官："RPC 和 HTTP 有什么区别？什么时候用 RPC、什么时候用 HTTP？"

参考回答框架：
1. RPC 是远程过程调用，HTTP 是超文本传输协议——不是同一层级的概念
2. RPC 可以基于 HTTP 实现（如 gRPC 基于 HTTP/2），也可以基于 TCP
3. RPC 优势：性能高、自带服务治理；HTTP 优势：通用、跨语言、可调试
4. 内部服务间调用 → RPC；对外暴露 API → HTTP RESTful

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| "RPC 和 HTTP 是对立的" | gRPC 底层用的就是 HTTP/2，不是对立关系 |
| "RPC 只能用二进制" | JSON-RPC 就用 JSON，也是 RPC |
| "学接口测试不需要了解 RPC" | 被测系统内部可能走 RPC，理解全链路才能定位问题 |

【扩展知识】
Protocol Buffers（Protobuf）是 Google 的数据序列化框架——定义 `.proto` 文件来描述数据结构，编译后生成各语言的代码。相比 JSON：体积小 3-10 倍、解析快 20-100 倍、有强类型校验。

【我的理解】
> 
> （HTTP 和 RPC 各自的核心取舍是什么？为什么公司内部用 RPC、对外用 HTTP？用自己的话总结。）

## 四、HTTP 协议

### 知识点 5：HTTP 请求与响应

【课程原话/定义】
HTTP（HyperText Transfer Protocol）是接口测试中最常见的协议，是万维网数据通信的基础。客户端发送 HTTP 请求，服务端返回 HTTP 响应。

**请求报文结构：**
- 请求行：`GET /api/user HTTP/1.1`
- 请求头：Host, User-Agent, Cookie, Content-Type 等
- 空行（分隔头与体）
- 请求体（GET 通常为空，POST 携带数据）

**响应报文结构：**
- 状态行：`HTTP/1.1 200 OK`
- 响应头：Server, Content-Type, Content-Length 等
- 空行
- 响应体（HTML / JSON / XML 等）

【为什么？】
理解 HTTP 报文结构 = 理解接口测试的"输入和输出"。每一个测试断言，本质上都是在校验响应报文的某个部分：状态码（状态行）、Content-Type（响应头）、返回数据（响应体）。

类比：寄快递。请求 = 快递单（地址+收件人）+ 包裹内容。响应 = 回执单（签收状态）+ 回寄物品。

【必须掌握】
- 请求行三要素：方法 + URL + 协议版本
- 常见请求头：Host, Content-Type, Cookie, Authorization, User-Agent
- 响应状态行：协议版本 + 状态码 + 状态描述
- 常见响应头：Content-Type, Content-Length, Set-Cookie
- 请求体和响应体可以是 JSON、XML、Form、Binary 等格式

【企业场景】
调试接口时用浏览器 DevTools → Network 面板，点开任意请求，对照看 Request Headers / Response Headers / Preview——这跟你写自动化脚本里的 `response.status_code`、`response.headers`、`response.json()` 是一一对应的。

【面试考察】
面试官："一个 HTTP 请求从客户端发出到收到响应，经历了哪些步骤？"

参考回答框架：
1. DNS 解析域名 → IP 地址
2. TCP 三次握手建立连接
3. （HTTPS）TLS 握手
4. 发送 HTTP 请求报文
5. 服务器处理并返回 HTTP 响应报文
6. 浏览器/客户端解析响应
7. TCP 四次挥手断开连接

【易错点】

| 常见错误              | 正确理解                                 |
| ----------------- | ------------------------------------ |
| 把请求头和请求体搞混        | 头是元信息（描述数据），体是实际数据                   |
| 认为 GET 请求一定有 body | GET 通常没有 body（虽然 HTTP 规范不禁止，但实践中极少用） |
| 以为 Cookie 只存在响应中  | 请求也可以带 Cookie（浏览器自动附加）               |

【我的理解】
> （打开浏览器 F12 → Network，随便点一个请求，用手写出它的请求行、2个请求头、响应状态行、1个响应头。）

### 知识点 6：URI 和 URL

【课程原话/定义】
URI（Uniform Resource Identifier）：统一资源标识符，唯一标识一个资源。URL（Uniform Resource Locator）：统一资源定位符，是 URI 的一种——不仅标识资源，还告诉你怎么找到它。

URL 结构：`https://www.baidu.com:443/s?wd=霍格沃兹&rsv_spt=1`

| 组成部分 | 示例值               | 说明                    |
| ---- | ----------------- | --------------------- |
| 协议   | https             | 非必须，默认 http           |
| 域名   | www.baidu.com     |                       |
| 端口   | 443               | 跟在域名后，`:` 分隔；省略则用默认端口 |
| 路径   | /s                | 资源在服务器上的路径            |
| 查询参数 | wd=霍格沃兹&rsv_spt=1 | `?` 开头，`&` 分隔多个参数     |

【为什么？】
URI 和 URL 的区别是面试经典题。"所有的 URL 都是 URI，但不是所有的 URI 都是 URL"——URN（统一资源名称，如 `urn:isbn:0451450523`）是 URI 但不是 URL，因为它只标识资源，不告诉你哪里获取。

【必须掌握】
- URI ⊇ URL：URL 是 URI 的子集
- URL 包含定位信息（协议+域名+路径）
- 端口省略时：HTTP 默认 80，HTTPS 默认 443
- 查询参数格式：`?key1=value1&key2=value2`

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 说 URI 和 URL 是同一个东西 | URL 是 URI 的一种，URN 也是 URI |
| 认为端口可以随便省略 | 只有用默认端口时才能省略 |

【我的理解】
> （URL 和 URI 的区别用一句话怎么说？为什么面试官爱问这个？）

### 知识点 7：HTTP 状态码

【课程原话/定义】
HTTP 响应状态码由三位数字组成，第一位表示响应类别：

| 类别  | 含义            | 常见状态码                                                                       |
| --- | ------------- | --------------------------------------------------------------------------- |
| 1xx | 信息，请求已收到，继续处理 | 100 Continue                                                                |
| 2xx | 成功            | **200** OK, 201 Created, 204 No Content                                     |
| 3xx | 重定向           | **301** 永久移动, **302** 临时移动, 304 Not Modified                                |
| 4xx | 客户端错误         | 400 Bad Request, **401** Unauthorized, **403** Forbidden, **404** Not Found |
| 5xx | 服务端错误         | **500** Internal Server Error, 502 Bad Gateway, **503** Service Unavailable |

【为什么？】
状态码是接口测试断言的"第一道防线"。一个接口不管返回了什么数据，先看状态码——如果是 500，后面的断言都不用跑了（服务端已经崩了）。

【必须掌握】
- **301 vs 302**：301 永久移动（浏览器会缓存，下次直接跳），302 临时移动（每次都问服务器）
- **401 vs 403**：401 是"你没登录/没token"（身份验证失败），403 是"你登录了但权限不够"（授权失败）
- **500 vs 502 vs 503**：500 是服务器代码崩了，502 是网关/代理从上游收到无效响应，503 是服务器暂时不可用（过载/维护）
- **304**：资源没变，用缓存（配合 If-Modified-Since / ETag 头使用）

【企业场景】
写自动化测试时，断言模式通常是：`assert response.status_code == 200`。但一个健壮的测试要考虑各种状态码：正常登录 → 200；密码错误 → 401；无权限访问 → 403；不存在的接口 → 404；传了非法参数 → 400。

【面试考察】
面试官："301 和 302 有什么区别？401 和 403 呢？"

参考回答框架：
1. 301 永久重定向 → 搜索引擎会更新索引，浏览器会缓存跳转
2. 302 临时重定向 → 不缓存，每次都请求原地址
3. 401 = 未认证（没带 token / token 过期）
4. 403 = 未授权（有身份但没权限）

【易错点】

| 常见错误 | 正确理解 |
|----------|----------|
| 把 401 和 403 搞反 | 记法：401 → 你是谁？(Unauthenticated)；403 → 你不能看 (Forbidden) |
| 把 500 和 503 混为一谈 | 500 → 代码bug；503 → 服务器忙/挂了 |
| 以为 2xx 都是 200 | 201 创建成功，204 成功但无返回体 |

【我的理解】
> （设计一个测试用例矩阵：同一个登录接口，分别输入正确密码、错误密码、不传 token、传入过期 token——各自期望返回什么状态码？为什么？）

## 五、RESTful 架构

### 知识点 8：RESTful 是什么

【课程原话/定义】
RESTful 是 Roy Fielding 博士 2000 年提出的万维网软件架构风格。一句话概括：**用 URL 定位资源，用 HTTP 动词描述操作**。

| 方法     | 含义    |
| ------ | ----- |
| GET    | 获取资源  |
| POST   | 新增或更新 |
| PUT    | 更新资源  |
| DELETE | 删除资源  |

注意：不同公司在使用 RESTful 时存在部分差别。

【为什么？】
在 RESTful 之前，很多接口设计是这样的：`/getUser?id=1`、`/deleteUser?id=1`、`/updateUser`——动词在 URL 里。RESTful 把动词统一到 HTTP Method，URL 只表示资源：`GET /users/1`、`DELETE /users/1`、`PUT /users/1`。好处：URL 结构一致、语义清晰、便于理解和维护。

【必须掌握】
- URL 表示资源（名词），HTTP Method 表示操作（动词）
- GET 是安全且幂等的（多次调用结果相同，不改变服务端数据）
- PUT 是幂等的（多次更新同一数据结果一样）
- POST 不是幂等的（多次调用可能创建多条记录）
- DELETE 是幂等的（删一次和删多次效果一样——资源不存在了）

【企业场景】
80% 以上的现代 Web API 都声称"遵循 RESTful 风格"。你在写接口测试用例时，第一步就是理解接口的 RESTful 语义：这是 GET（查）还是 POST（增）？如果文档说用 GET 但实际产生了数据变更——那就是设计问题，值得提 bug。

【面试考察】
面试官："你怎么判断一个 API 设计是否符合 RESTful 风格？"

参考回答框架：
1. URL 是否只用名词（资源名），不用动词
2. 是否正确使用 HTTP Method（GET/POST/PUT/DELETE）
3. 是否有合理的状态码返回
4. 是否无状态（每个请求包含所有必要信息，不依赖服务端 session）

【易错点】

| 常见错误                   | 正确理解                    |
| ---------------------- | ----------------------- |
| `POST /users/1/delete` | 应该是 `DELETE /users/1`   |
| `GET /getUserList`     | 应该是 `GET /users`        |
| 用 POST 做所有写操作          | PUT 用于全量更新，PATCH 用于部分更新 |
| 认为 RESTful 是标准/协议      | 它是一种风格/约定，不是强制标准        |

【我的理解】
> （把以下 URL 改成 RESTful 风格：`/api/getOrderById?id=100`、`/api/createUser`、`/api/removeProduct?pid=5`）

### 知识点 9：GET 与 POST 的区别

【课程原话/定义】
GET 和 POST 是 HTTP 中使用最多的两种请求方法。两者的核心区别不只是"GET 参数在 URL 里，POST 在 body 里"。

【为什么？】
面试官问"GET 和 POST 的区别"不是要你背八股文——是要考察你是否理解 HTTP 协议的设计哲学。

| 维度   | GET                 | POST             |
| ---- | ------------------- | ---------------- |
| 参数位置 | URL 查询字符串           | 请求体              |
| 安全性  | 参数暴露在 URL 中         | 参数在 body 中（相对隐蔽） |
| 长度限制 | URL 长度受浏览器限制（约 2KB） | 理论上无限制           |
| 缓存   | 可缓存                 | 默认不缓存            |
| 幂等性  | 幂等（多次请求结果相同）        | 非幂等              |
| 书签   | 可收藏                 | 不可收藏             |
| 语义   | 获取数据                | 提交数据             |

【必须掌握】
- GET 用于查询操作，不应对服务端数据产生变更
- POST 用于创建/更新操作
- GET 参数暴露在 URL，不适合传敏感信息（密码、token）
- POST 可以传 JSON、XML、Form、文件等多种格式
- GET 可被缓存，POST 默认不缓存

【企业场景】
在写自动化测试时：
- 获取用例列表 → GET，断言只需验证返回数据
- 创建新用例 → POST，断言需要验证状态码 201 + 返回的 ID + 数据是否真的入库（再 GET 一次验证）
- 登录接口 → POST（涉及密码，不能在 URL 里暴露）

【面试考察】
面试官："GET 和 POST 的本质区别是什么？"

参考回答框架：
1. 语义不同：GET = 获取，POST = 提交
2. 参数位置不同：URL vs Body
3. 幂等性不同：GET 幂等，POST 非幂等
4. 缓存策略不同
5. （进阶）TCP 层面：GET 产生一个 TCP 数据包（header+data 一起发），POST 产生两个（先发 header，服务器 100 Continue 后再发 body）——但这不是绝对的，取决于具体实现

【易错点】

| 常见错误                  | 正确理解                                          |
| --------------------- | --------------------------------------------- |
| "GET 比 POST 更安全"      | 恰恰相反——GET 参数暴露在 URL 里、存在浏览器历史记录里              |
| "POST 一定不会被缓存"        | HTTP 规范说 POST 默认不缓存，但可以通过 Cache-Control 头强制缓存 |
| "GET 的长度限制是 HTTP 协议的" | 是浏览器和服务器的限制，HTTP 协议本身没限制 URL 长度               |

【我的理解】
> （除了参数位置不同，GET 和 POST 最本质的区别是什么？为什么说 GET 是"安全且幂等"的而 POST 不是？用自己的话解释幂等性的含义。）
