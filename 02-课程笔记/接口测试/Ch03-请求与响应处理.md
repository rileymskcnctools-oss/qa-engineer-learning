## 一、处理请求数据 — request 对象

### 知识点 1：request 对象概述

【课程原话/定义】
浏览器访问地址时，HTTP 协议会向后台传递一个请求对象，包含请求头、请求参数、请求方式。Flask 通过 `request` 对象提供访问这些数据的方法。

| 属性/方法             | 说明                    |
| ----------------- | --------------------- |
| `request.args`    | 查询参数（URL 中 `?` 后面的部分） |
| `request.json`    | JSON 格式的请求体           |
| `request.files`   | 上传的文件                 |
| `request.form`    | 表单数据                  |
| `request.method`  | HTTP 请求方法             |
| `request.url`     | 完整的请求 URL             |
| `request.host`    | 请求的域名                 |
| `request.headers` | 请求头信息                 |

【为什么？】
`request` 是 Flask 的全局请求代理对象。关键理解：它不是"一个全局变量被所有请求共享"——而是 Flask 内部通过"请求上下文"（Request Context）机制，在每个请求到达时自动创建对应的 request 对象，请求结束后销毁。所以你在视图函数里直接 `from flask import request` 就能用，而且不同请求之间互不干扰。底层原理类似线程局部变量（thread-local）。

【必须掌握】
- `from flask import request` 导入
- 每个属性对应 HTTP 请求的不同部分
- request 是请求级别的代理，不是真正的全局变量

【企业场景】
接口测试中写 Mock 服务时，你需要根据请求参数返回不同响应。比如同一个 `/api/users`：
- 带了 `?status=active` → 返回活跃用户列表
- 带了 `?status=inactive` → 返回非活跃用户列表
- 什么都不带 → 返回全部用户

request 对象让你能读取这些参数做分支判断，一个路由 Mock 多种场景。

【面试考察】
面试官："Flask 的 request 对象是全局的，为什么多个并发请求不会互相干扰？"

参考回答框架：
1. request 不是真正的全局变量，而是 Flask 的"请求上下文"机制
2. 每个请求到达时，Flask 创建独立的 Request Context，把 request 绑定到当前请求
3. 底层用类似线程局部变量的机制隔离不同请求
4. 请求结束后上下文自动销毁

【易错点】

| 常见错误 | 正确做法 |
|----------|----------|
| 在视图函数外面使用 `request.args` | request 只在请求上下文中有效，函数外访问会报 `RuntimeError: Working outside of request context` |
| 认为 request 是全局单例 | 每个请求有独立的 request 对象，Flask 自动切换 |

【我的理解】
> （Flask 的 request 对象底层返回 `ImmutableMultiDict` 类型，跟你之前学的 Python dict 有什么不同？提示：普通 dict 一个 key 只能对应一个 value，ImmutableMultiDict 呢？什么时候会出现一个 key 对应多个 value？）

### 知识点 2：普通请求参数 — request.args

【课程原话/定义】
GET 请求中 URL 拼接的查询参数（`?key=value`），使用 `request.args` 获取。`request.args` 是一个 `ImmutableMultiDict` 对象，可以通过 `.get()` 方法安全取值。

```python
@app.route('/user')
def get_user():
    url_param = request.args
    # ImmutableMultiDict — 行为类似 dict，但不可修改
    username = url_param.get('username')
    return f'Hello, {username}!'
```

访问 `/user?username=John` → 返回 `'Hello, John!'`。

【为什么？】
查询参数是 Web 中最常见的传参方式。为什么用 `.get()` 而不是 `['key']`？
- `request.args['key']` — key 不存在时抛出 KeyError → 500
- `request.args.get('key')` — key 不存在时返回 None，不会崩溃
- `request.args.get('key', '默认值')` — 可以设置默认值

测试接口时，用户可能漏传参数——`.get()` 让你优雅处理，不会让 Mock 服务崩溃。另外 `ImmutableMultiDict` 支持同一个 key 出现多次（如 `?tag=python&tag=flask`），用 `.getlist('tag')` 拿到 `['python', 'flask']`。

【必须掌握】
- `request.args` 获取 URL 查询参数（`?` 后面部分）
- 返回值类型：`ImmutableMultiDict`，不可修改
- 用 `.get('key', default)` 安全取值
- `.getlist('key')` 获取同一 key 的多个值

【企业场景】
Mock 一个分页查询接口——后端接口通常还没开发好，你用它让前端先联调：

```python
@app.route('/api/users')
def list_users():
    page = request.args.get('page', 1, type=int)    # 默认第 1 页，自动转 int
    size = request.args.get('size', 20, type=int)    # 默认每页 20 条
    keyword = request.args.get('q', '')               # 搜索关键词
    # 根据参数返回不同数据——Mock 的核心能力
    return {
        "page": page,
        "size": size,
        "keyword": keyword,
        "data": [f"user_{i}" for i in range(size)]
    }
```

你的前端同事可以用不同 page/size/q 测试分页和搜索，而不需要真实后端。

【面试考察】
面试官："`request.args.get('key')` 和 `request.args['key']` 有什么区别？哪个更好？"

参考回答框架：
1. `.get('key')` 在 key 不存在时返回 None，不会抛异常
2. `['key']` 在 key 不存在时抛出 KeyError → 500 错误
3. 接口测试中推荐 `.get()`，因为你可以处理缺失参数的情况，返回友好的 400 错误而非 500
4. `.get('key', default)` 还可以设置默认值

【易错点】

| 常见错误 | 正确做法 |
|----------|----------|
| `request.args['key']` 取值，用户不传就 500 | 用 `.get('key')` 或 `.get('key', default)` |
| 认为 `request.args` 是普通 dict | 它是 `ImmutableMultiDict`，不可修改，同一 key 可以有多个值 |
| 多个值场景用 `.get()` 只拿到第一个 | 用 `.getlist('key')` 获取全部值列表 |

【我的理解】
> （写一个路由 `/search`，接收 `q`（关键词）和 `category`（分类）两个查询参数。分别测试：传了所有参数、不传任何参数、传了相同的 key 两次（`?tag=python&tag=flask`）三种情况。用 `.getlist('tag')` 看看拿到了什么。）

### 知识点 3：JSON 请求体 — request.json

【课程原话/定义】
POST/PUT 请求携带 JSON 格式数据时，使用 `request.json` 获取。它会解析请求的 JSON 数据并返回一个字典。

```python
@app.route('/data', methods=['POST'])
def process_data():
    data = request.json
    name = data.get('name')
    age = data.get('age')
    return f'Name: {name}, Age: {age}'
```

【为什么？】
JSON 是前后端分离时代的事实标准。关键点：

1. `request.json` 能工作有两个前提：
   - 请求的 `Content-Type` 必须是 `application/json`
   - 请求体必须是合法的 JSON 字符串
2. 如果 Content-Type 不对（比如 `text/plain`），`request.json` 返回 None——这是最常见的坑
3. Flask 内部用 `request.get_json()` 实现，`request.json` 是其快捷属性

【必须掌握】
- `request.json` 解析 JSON 请求体，返回 Python dict 或 None
- 请求必须带 `Content-Type: application/json`
- 同样用 `.get()` 安全取值
- JSON 解析失败时 `request.json` 返回 None

【企业场景】
Mock 创建用户的接口——这是最常用的 Mock 场景之一：

```python
@app.route('/api/user', methods=['POST'])
def create_user():
    data = request.json
    # 必填字段校验
    if not data or not data.get('username'):
        return {"error": "username is required"}, 400
    if not data.get('email'):
        return {"error": "email is required"}, 400
    # 模拟创建成功
    return {"id": 1001, "username": data['username'], "email": data['email']}, 201
```

测试时可以验证：
1. 正常数据 → 201 + 返回用户 ID
2. 缺少字段 → 400 + 错误信息
3. Content-Type 错误 → `request.json` 为 None

【面试考察】
面试官："前端发了一个 POST 请求但 `request.json` 返回 None，可能是什么原因？"

参考回答框架：
1. 请求的 Content-Type 不是 `application/json`（最常见原因）
2. 请求体不是合法的 JSON 格式（比如用了单引号、有 trailing comma）
3. 请求体为空
4. 排查方法：打印 `request.data` 看原始请求体，打印 `request.content_type` 看 Content-Type

【易错点】

| 常见错误 | 正确做法 |
|----------|----------|
| POST 请求 `request.json` 返回 None | 检查 Content-Type 是否为 `application/json` |
| 用 `request.json` 接收 form 表单 | form 用 `request.form`，json 用 `request.json`，二者根据 Content-Type 互斥 |
| JSON body 中有中文，解析乱码 | Flask 自动处理 UTF-8，无需额外设置 |
| `data['key']` 直接取值 | 用 `data.get('key')` 防止 KeyError |

【我的理解】
> （用 curl 发一个 POST 请求带 JSON body 到你的 Flask 接口。试试 Content-Type 写成 `text/plain` 时 `request.json` 返回什么。再试试请求体写成不合法的 JSON（如单引号 `{'name':'test'}`）会发生什么。）

### 知识点 4：表单请求体 — request.form

【课程原话/定义】
POST 请求携带 form 表单格式数据时，使用 `request.form` 获取。它是一个字典，可以通过键名获取表单字段的值。

```python
@app.route('/login', methods=['POST'])
def login():
    user_info = request.form
    username = user_info.get('username')
    password = user_info.get('password')
    return f'Welcome, {username}!'
```

【为什么？】
虽然现在大部分 API 用 JSON，但以下场景仍然用表单格式：
- 传统 HTML `<form>` 提交
- OAuth2 的 token 请求（`grant_type=password&username=xxx`）
- 老系统接口兼容

底层原理：`request.form` 由 Flask 自动解析 `application/x-www-form-urlencoded` 或 `multipart/form-data` 格式的请求体。关键区别——`request.json` 和 `request.form` 在同一请求中互斥，取决于 Content-Type。

【必须掌握】
- `request.form` 获取表单数据
- 对应 Content-Type: `application/x-www-form-urlencoded`
- `.form` 和 `.json` 互斥——同一个请求只会填充其中一个
- 文件上传场景下，文字字段也在 `request.form` 中

【企业场景】
CI/CD 流水线中，有些老系统的 webhook 回调是表单格式。比如 Jenkins 的构建通知 webhook 是 `application/x-www-form-urlencoded` 格式。测试这类回调接口时，Mock 服务必须用 `request.form` 接收。

```python
@app.route('/webhook/jenkins', methods=['POST'])
def jenkins_webhook():
    # Jenkins webhook 是表单格式
    build_status = request.form.get('build_status')
    project = request.form.get('project')
    return f"Received: {project} build {build_status}"
```

【面试考察】
面试官："`request.form` 和 `request.json` 有什么区别？同一个请求能同时拿到两个吗？"

参考回答框架：
1. `request.form` 用于 `application/x-www-form-urlencoded` 或 `multipart/form-data` 格式
2. `request.json` 用于 `application/json` 格式
3. 不能同时拿到——Flask 根据 Content-Type 决定解析哪个
4. JSON 支持嵌套结构（对象、数组），form 只能平铺 key-value；JSON 适合复杂数据，form 适合简单键值对

【易错点】

| 常见错误 | 正确做法 |
|----------|----------|
| 用 `request.json` 接收 HTML 表单提交 | 表单用 `request.form`，JSON 用 `request.json` |
| 认为 form 只能用于登录场景 | OAuth2 token 申请、webhook 回调、文件上传的文字字段都在 form 中 |

【扩展知识】

| 对比维度 | `request.json` | `request.form` |
|----------|---------------|----------------|
| Content-Type | `application/json` | `application/x-www-form-urlencoded` |
| 请求体格式 | `{"key": "value"}` | `key=value&key2=value2` |
| 嵌套结构 | 支持（对象、数组） | 不支持（只能平铺 key-value） |
| 使用场景 | RESTful API、前后端分离 | 传统表单提交、OAuth2 |
| 数据获取 | `request.json.get('key')` | `request.form.get('key')` |

【我的理解】
> （分别用 curl 发 JSON 格式和表单格式的 POST 请求到同一个 Flask 路由。在视图函数里同时打印 `request.json`、`request.form` 和 `request.content_type`，观察哪个有值哪个是 None。你能根据 `request.content_type` 写一个同时兼容两种格式的路由吗？）

### 知识点 5：文件上传 — request.files + secure_filename()

【课程原话/定义】
上传文件使用 `request.files`，它是一个字典，每个上传的文件都存储在这里。通过 `.get('key')` 获取文件对象。文件对象有 `.save()` 方法保存到服务器，有 `.filename` 属性获取原始文件名。`secure_filename()` 用于过滤文件名中的危险字符。

```python
from werkzeug.utils import secure_filename

@app.route('/upload', methods=['POST'])
def upload_file():
    file = request.files.get("file")
    file.save('./uploads/' + secure_filename(file.filename))
    return f'File {file.filename} is saved!'
```

【为什么？】
`secure_filename()` 存在的根本原因：**永远不要信任用户输入的文件名**。攻击者可以上传名为 `../../../etc/passwd` 的文件，如果不加处理直接拼接路径保存，就会覆盖系统关键文件（路径穿越攻击）。`secure_filename()` 做了三件事：
1. 去掉路径分隔符（`/`、`\`），防止路径穿越
2. 只保留字母、数字、点、下划线、连字符
3. 去掉连续的点（防止 `..` 穿越）

此外，`.filename` 来自客户端，可以伪造——不要用它的值做业务判断（比如判断文件类型）。文件类型应该通过读取文件内容（magic bytes）来判断。

【必须掌握】
- `request.files.get('key')` 获取文件对象
- `.filename` 获取原始文件名（客户端的，可伪造，不要信任）
- `.save(path)` 保存文件到服务器
- `secure_filename()` 过滤危险字符，防止路径穿越攻击
- 保存前需要先创建目标目录

【企业场景】
测试文件上传接口时，你需要覆盖这些场景：

| 测试场景 | 预期结果 |
|----------|----------|
| 上传正常图片（jpg, 500KB） | 201 成功，文件保存到 uploads/ |
| 上传超大文件（50MB） | 413 或自定义大小限制报错 |
| 上传 .exe 文件 | 类型校验拒绝 |
| 文件名：`../../../etc/hosts` | `secure_filename` 过滤后变成 `etc_hosts` |
| 不传文件 | 400 缺少必填字段 |

Mock 一个文件上传接口让你能在文件功能还没开发完时就开始写测试用例。

```python
import os
from werkzeug.utils import secure_filename

@app.route('/api/upload', methods=['POST'])
def mock_upload():
    f = request.files.get('file')
    if not f:
        return {"error": "no file provided"}, 400
    if f.filename == '':
        return {"error": "empty filename"}, 400

    safe_name = secure_filename(f.filename)
    os.makedirs('uploads', exist_ok=True)  # 自动创建目录
    f.save(os.path.join('uploads', safe_name))
    return {"filename": safe_name, "status": "uploaded"}, 201
```

【面试考察】
面试官："为什么要用 `secure_filename()`？不用它会有什么安全问题？"

参考回答框架：
1. 防止路径穿越攻击（Path Traversal）——用户可能上传文件名为 `../../../etc/passwd`
2. `secure_filename()` 过滤掉路径分隔符和特殊字符，只保留安全的字母数字
3. 不用它的话，攻击者可以把文件保存到服务器任意位置，覆盖系统文件
4. 同时要注意：`.filename` 是客户端提供的，可以伪造，不能用来判断真实文件类型

【易错点】

| 常见错误 | 正确做法 |
|----------|----------|
| 拼接路径时直接使用 `f.filename` | 必须用 `secure_filename()` 过滤 |
| 信任 `.filename` 的扩展名判断文件类型 | 文件类型应通过读取文件内容（magic bytes）判断 |
| 保存文件前不检查目录是否存在 | 用 `os.makedirs('dir', exist_ok=True)` 自动创建 |
| 忘记处理 `request.files.get('file')` 返回 None | 判断 `if not f:` 处理未上传文件的情况 |

【扩展知识】
`secure_filename()` 对中文文件名的处理：会把中文字符过滤掉，只保留字母数字。如果你的应用需要保留中文文件名，可以用 UUID 重命名：
```python
import uuid
ext = f.filename.rsplit('.', 1)[-1] if '.' in f.filename else ''
safe_name = f"{uuid.uuid4()}.{ext}"
```

【我的理解】
> （实现一个文件上传接口，分别上传：① 一个正常的 jpg 图片 ② 一个文件名为 `../../../etc/hosts` 的文件。对比使用和不使用 `secure_filename()` 的结果差异。用 curl 的 `-F` 参数上传文件，格式是什么？）

### 知识点 6：其他请求信息 — url, host, headers, method

【课程原话/定义】
业务处理时可能需要根据不同的 URL、域名、请求头或请求方法做判断。使用 `request.url`、`request.host`、`request.headers`、`request.method` 获取。

```python
@app.route('/upload', methods=['GET', 'POST'])
def upload_file():
    r_url = request.url          # 完整 URL
    r_host = request.host        # 域名:端口
    r_headers = request.headers  # 请求头（类字典）
    r_method = request.method    # 请求方法

    if r_method == 'POST':
        if r_headers.get('My-Header') == "hogwarts":
            f = request.files.get("file")
            f.save('./uploads/' + secure_filename(f.filename))
            return f'File {f.filename} is saved!'
        return "My-Header is missing!"
    return "Method is wrong!"
```

【为什么？】
同一个路由同时支持 GET 和 POST 是 RESTful 设计的核心——`/resource` 用 GET 查列表、POST 新增。`request.method` 让你在一个视图函数里分支处理。请求头校验的典型场景：
- `Authorization` → token 鉴权
- `Content-Type` → 判断请求体格式
- `User-Agent` → 判断客户端类型
- 自定义 Header → 传递额外元数据

【必须掌握】
- `request.method` 获取当前请求的 HTTP 方法（GET/POST/PUT/DELETE 等）
- `request.headers` 是类字典对象，用 `.get()` 取值
- `request.url` 返回完整 URL（含协议、域名、端口、路径、查询参数）
- `request.host` 返回 `域名:端口`，不含协议

【企业场景】
写接口自动化测试时，Mock 服务需要模拟鉴权逻辑：

```python
@app.route('/api/users')
def get_users():
    # 模拟 token 鉴权
    auth = request.headers.get('Authorization')
    if not auth or not auth.startswith('Bearer '):
        return {"error": "unauthorized"}, 401
    token = auth.split(' ')[1]
    if token != 'valid-token-123':
        return {"error": "invalid token"}, 403
    return {"data": [...]}, 200
```

你的测试用例可以：
1. 不带 token → 验证返回 401
2. 带错误 token → 验证返回 403
3. 带正确 token → 验证返回 200 + 数据

一个 Mock 服务覆盖了鉴权的所有分支。

【面试考察】
面试官："`request.method` 和 `request.headers` 在什么场景下会用到？"

参考回答框架：
1. `request.method`：同一路由处理多种 HTTP 方法时用于分支判断
2. `request.headers`：鉴权（Authorization）、内容类型判断（Content-Type）、版本控制、来源校验
3. 接口测试中 Mock 鉴权接口必备

【易错点】

| 常见错误 | 正确做法 |
|----------|----------|
| 用 `request.headers['key']` 取值 | 用 `.get('key')` 防止 KeyError |
| 混淆 `request.url` 和 `request.host` | url = 完整地址含参数，host = 仅域名:端口 |
| 在 GET 路由中试图获取 JSON body | GET 请求没有请求体，`request.json` 永远是 None |

【我的理解】
> （写一个路由同时支持 GET 和 POST。GET 返回 `{"method": "GET", "url": ...}`，POST 返回 `{"method": "POST", "url": ...}`。用 `request.method` 区分逻辑。用 curl 分别发 GET 和 POST 测试。再试试打印 `request.url` 和 `request.host`，理解它们的区别。）

## 二、处理响应信息

### 知识点 7：返回文本类型

【课程原话/定义】
最简单的响应：视图函数直接 return 字符串。Flask 自动封装成 HTTP 响应，`Content-Type` 为 `text/html; charset=utf-8`。

```python
@app.route('/text')
def text_res():
    return '返回文本'
```

【为什么？】
Flask 内部对返回值的处理逻辑：
1. 返回字符串 → 自动包装为 Response 对象，Content-Type 设为 `text/html`
2. 返回 dict → Flask 1.1+ 自动调用 `jsonify()`，Content-Type 设为 `application/json`
3. 返回元组 → 按 `(body, status, headers)` 规则解析
4. 返回 Response 对象 → 直接使用

理解这个"自动装箱"机制，你就理解了 Flask 响应处理的全部逻辑。

【必须掌握】
- 直接返回字符串 = 最简单的响应
- 默认 Content-Type: `text/html; charset=utf-8`
- Flask 自动将返回值包装成合法的 HTTP 响应

【我的理解】
> （创建一个返回纯文本的路由，用浏览器和 curl -v 各访问一次。对比两者的输出——curl -v 能看到完整的 HTTP 响应报文（状态行 + 响应头 + 空行 + 响应体），浏览器开发者工具 Network 面板也能看到同样的信息。你能在 curl -v 输出中找到 Content-Type 头吗？）

### 知识点 8：返回元组类型

【课程原话/定义】
Flask 视图函数可以返回元组，包含 2-3 个元素：`(response_body, status_code, headers)`。

```python
# 3 个元素：响应体 + 状态码 + 响应头
@app.route('/tuple')
def tuple_res():
    return "你好呀", 200, {"hogwarts": "Harry"}

# 2 个元素：响应体 + 状态码
@app.route('/not-found')
def not_found():
    return "页面不存在", 404

# 2 个元素：响应体 + 响应头
@app.route('/custom-header')
def custom_header():
    return "OK", {"X-Custom": "value"}
```

【为什么？】
元组返回是对 HTTP 协议最直观的编程映射：
- HTTP 响应 = 状态行（`HTTP/1.1 200 OK`）+ 响应头 + 响应体
- 元组 `(body, status, headers)` 三者一一对应

这种设计让你无需额外学习 Response 对象的 API 就能控制 HTTP 状态码和响应头——这在 Mock 测试中是核心需求。

【必须掌握】
- 元组三个位置的对应关系：`(响应体, 状态码, 响应头)`
- 可以只传两个：`(body, status)` 或 `(body, headers)`
- 状态码必须是整数
- 响应头必须是字典

【企业场景】
Mock 接口测试中，控制状态码是最常见的需求：

```python
@app.route('/api/user/<int:uid>')
def mock_user(uid):
    if uid == 0:
        return {"error": "not found"}, 404       # 用户不存在
    if uid < 0:
        return {"error": "invalid id"}, 400      # 非法 ID
    if uid > 10000:
        return {"error": "server error"}, 500    # 模拟服务器错误
    return {"id": uid, "name": f"user_{uid}"}, 200  # 正常
```

你的测试用例可以用不同 uid 验证客户端对各种 HTTP 状态码的容错处理是否正确。

【面试考察】
面试官："Flask 视图函数返回元组时，两个元素和三个元素分别怎么解析？"

参考回答框架：
1. 三元组：`(body, status, headers)` → 一一对应
2. 二元组 `(body, status)` → 第一个是 body，第二个是整数→认定为 status
3. 二元组 `(body, headers)` → 第二个是字典→认定为 headers
4. Flask 根据第二个元素的类型自动判断是 status 还是 headers

【易错点】

| 常见错误 | 正确做法 |
|----------|----------|
| 状态码写成字符串 `"200"` | 必须是整数：`200` |
| 元组元素顺序搞反 | 记牢：body → status → headers，从左到右 |
| `("OK", {"key": "val"})` 行为不确定 | 当第二个元素既不是 int 也不是 dict 时可能出错 |

【我的理解】
> （创建 3 个路由，分别返回 200 "成功"、404 "未找到"、500 "服务器错误"。用 curl -v 查看完整的响应状态行（第一行）。对比三者的状态行有什么不同。）

### 知识点 9：返回 JSON

【课程原话/定义】
返回 JSON 有两种方式：
1. `jsonify()` — Flask 内置方法，支持传字典或关键字参数
2. 直接 return dict — Flask 1.1+ 自动调用 `jsonify()`

```python
# 方式一：jsonify（传关键字参数）
from flask import jsonify
@app.route('/json')
def get_json():
    return jsonify(status=1, name="lily", age=20)

# 方式二：jsonify（传字典）
@app.route('/json2')
def get_json2():
    return jsonify({"status": 1, "name": "lily"})

# 方式三：直接返回字典（Flask 1.1+）
@app.route('/dict')
def get_dict():
    return {'status': 0}
```

三种方式的 `Content-Type` 都是 `application/json`。

【为什么？】
`jsonify()` 和 Python 标准库 `json.dumps()` 的关键区别：

| 对比 | `jsonify()` | `json.dumps()` |
|------|------------|----------------|
| 返回值 | Response 对象 | 字符串 |
| Content-Type | 自动设 `application/json` | 需要手动设 |
| 中文处理 | 自动处理 UTF-8 | `ensure_ascii=False` |
| JSONP 支持 | 内置 | 无 |
| 适用场景 | Flask 视图函数 | 任何需要 JSON 字符串的场景 |

如果视图函数 return `json.dumps(dict)` 而不是 `jsonify(dict)`，Content-Type 会变成 `text/html`，前端可能解析失败。Flask 1.1+ 的改进（直接 return dict）就是为了减少这个坑。

【必须掌握】
- `jsonify()` 返回 Response 对象，Content-Type 自动设为 `application/json`
- Flask 1.1+ 直接 return dict 效果等同于 jsonify
- 参数可以传字典，也可以传关键字参数
- `json.dumps()` 返回的是字符串，不是 HTTP 响应——不要直接 return

【企业场景】
Mock 接口几乎 100% 返回 JSON：

```python
@app.route('/api/user/<int:uid>')
def mock_user(uid):
    return {
        "code": 0,
        "message": "success",
        "data": {
            "id": uid,
            "name": f"user_{uid}",
            "created_at": "2026-01-01T00:00:00Z"
        }
    }
```

你的测试用例断言 `response.json()['code'] == 0` 或 `response.json()['data']['name']` 来验证业务逻辑。

【面试考察】
面试官："`jsonify()` 和 Python 的 `json.dumps()` 有什么区别？Flask 视图函数应该 return 哪个？"

参考回答框架：
1. `jsonify()` 返回 Flask Response 对象，自动设置 `Content-Type: application/json`
2. `json.dumps()` 返回普通字符串，不设置 Content-Type
3. 视图函数应 return `jsonify(dict)` 或直接 return dict（Flask 1.1+），不能用 `json.dumps()`
4. `jsonify()` 还能正确处理中文（不会变成 `\uXXXX`）

【易错点】

| 常见错误 | 正确做法 |
|----------|----------|
| `return json.dumps({"name": "张三"})` | 返回的是字符串，Content-Type 变成了 text/html |
| 认为三种方式完全等价 | 直接 return dict 最简单（Flask 1.1+），jsonify 兼容老版本 |
| 在 return dict 时手动加状态码 | `return {"error": "xxx"}, 400` 是合法的（Flask 会把 dict + 状态码正确包装） |

【我的理解】
> （分别用 `jsonify(dict)`、`json.dumps(dict)`、直接 return dict 三种方式返回 `{"name": "测试", "score": 95}`。用 curl -v 查看三种响应的 Content-Type 头有何不同。哪种方式最"标准"？哪种会出问题？）

### 知识点 10：返回 HTML

【课程原话/定义】
返回 HTML 使用 `render_template()` 方法，传入 HTML 文件名。HTML 文件必须放在项目根目录的 `templates/` 目录下。

```python
from flask import render_template

@app.route('/html')
def get_html():
    return render_template('demo.html')
```

目录结构：
```
application.py          # Flask 主程序
templates/              # 模板目录（Flask 默认查找位置）
    demo.html
```

【为什么？】
Flask 使用 Jinja2 模板引擎渲染 HTML。`render_template()` 不只是读取文件——它支持模板语法（变量插值、循环、条件判断），可以在 HTML 中嵌入动态数据。接口测试中不常用，但了解它有助于理解：Flask 可以同时做 API（返回 JSON）和页面渲染（返回 HTML），两者的视图函数写法完全不同。

【必须掌握】
- `render_template('文件名.html')` 渲染模板
- HTML 文件必须放在 `templates/` 目录下
- Flask 默认在当前目录查找 `templates/` 文件夹
- 模板引擎是 Jinja2，支持变量、循环、条件等语法

【扩展知识】
详细的 Jinja2 模板语法（`{{ }}` / `{% %}`、if/for、继承 extends、导入 include）见 [[Ch04-Jinja2模板技术]]。

【我的理解】
> （在项目中创建 `templates/` 目录和 `hello.html`，写一个简单的 HTML 页面包含 `<h1>{{ title }}</h1>`。用 `render_template('hello.html', title='我的页面')` 渲染。理解模板渲染的基本流程：Flask 读取 HTML 文件 → Jinja2 把 `{{ title }}` 替换成 `'我的页面'` → 返回完整 HTML。）

### 知识点 11：返回额外数据 — make_response()

【课程原话/定义】
当需要同时设置响应体、响应头、Cookie 等额外信息时，使用 `make_response()` 构造完整的 Response 对象。

```python
from flask import make_response, render_template

@app.route('/')
def index():
    resp = make_response(render_template('demo.html'))
    # 设置 Cookie
    resp.set_cookie('username', 'the username')
    # 设置自定义响应头
    resp.headers["hogwarts"] = "Hary"
    return resp
```

【为什么？】
简单的 return 只能控制响应体。`make_response()` 是"完全控制权"——它返回一个可修改的 Response 对象，你可以：
- 用 `.set_cookie()` 设置 Cookie（本质是添加 `Set-Cookie` 响应头）
- 用 `.headers['key'] = 'value'` 添加自定义响应头
- 用 `.status_code = 201` 修改状态码
- 用 `.delete_cookie()` 删除 Cookie

Cookie 的 `Set-Cookie` 响应头是一个特殊的 header——浏览器收到后会自动存储，后续请求自动带上。这就是"登录后保持会话"的底层机制。

【必须掌握】
- `make_response(body)` 将任意内容包装成 Response 对象
- `.set_cookie(key, value)` 设置 Cookie
- `.headers[key] = value` 添加自定义响应头
- Cookie 通过 `Set-Cookie` 响应头实现

【企业场景】
Mock 登录接口——这是 Mock 中最复杂的场景之一：

```python
@app.route('/api/login', methods=['POST'])
def mock_login():
    data = request.json
    username = data.get('username', '')
    password = data.get('password', '')

    if not username or not password:
        return {"error": "username and password required"}, 400

    if username == 'admin' and password == '123456':
        # 登录成功 → 返回 token + 设置 cookie
        resp = make_response({"code": 0, "message": "login success"}, 200)
        resp.set_cookie('session_id', 'mock-session-abc123', httponly=True, max_age=3600)
        resp.headers['X-Auth-Token'] = 'mock-token-xyz'
        return resp
    else:
        return {"code": 1, "message": "invalid credentials"}, 401
```

测试时可以验证：
1. 正确账号密码 → 200 + Cookie + Token header
2. 错误密码 → 401
3. 缺少字段 → 400
4. Cookie 有 `httponly=True`（JavaScript 读不到，防 XSS）

【面试考察】
面试官："什么时候需要用到 `make_response()`？直接 return 不行吗？"

参考回答框架：
1. 直接 return 只能控制响应体（body），无法同时操作 Cookie 和自定义 Header
2. `make_response()` 返回 Response 对象，可以链式操作：设置 Cookie、添加 Header、修改状态码
3. 典型场景：登录接口需要同时返回 JSON body + Session Cookie + 自定义 Header
4. `make_response()` 也可以用于文件下载（设置 `Content-Disposition` header）

【易错点】

| 常见错误 | 正确做法 |
|----------|----------|
| 想设 Cookie 但只用 `return jsonify(...)` | 必须用 `resp = make_response(...)` 然后 `resp.set_cookie(...)` |
| `set_cookie()` 参数写错 | 常用参数：`value`, `max_age`（秒）, `httponly`, `secure`, `path` |
| 忘记 import `make_response` | `from flask import make_response` |

【扩展知识】
`make_response()` 的三种传参方式：
```python
# 1. 传字符串
resp = make_response("Hello")

# 2. 传元组（和视图函数返回元组规则一样）
resp = make_response(("Hello", 200, {"X-Key": "val"}))

# 3. 传另一个 Response 对象（复制）
resp2 = make_response(resp)
```

【我的理解】
> （写一个 `/login` Mock 接口，用 `make_response()` 同时返回 JSON body + Cookie + 自定义 Header。用 curl -v 查看响应，你能在输出中找到 `Set-Cookie` 和你的自定义 Header 吗？再试试用浏览器访问，打开开发者工具 Application → Cookies，能看到你设置的 Cookie 吗？）

## 三、测试平台环境配置

### 知识点 12：host — 监听主机

【课程原话/定义】
`app.run()` 的 `host` 参数指定监听的主机地址：

```python
app.run(host="127.0.0.1")   # 只能本机访问（默认）
app.run(host="0.0.0.0")     # 监听所有网络接口，局域网可访问
app.run(host="192.168.1.100")  # 绑定指定 IP
```

【为什么？】
`127.0.0.1` 和 `0.0.0.0` 的底层区别：
- `127.0.0.1`：绑定到回环接口（lo）——只接受本机发起的连接
- `0.0.0.0`：绑定到所有网络接口——接受来自任何 IP 的连接
- 指定具体 IP（如 `192.168.1.100`）：只绑定到该网卡——只有通过该 IP 的请求被接受

安全考虑：`0.0.0.0` 让同一局域网内的任何人都能访问你的 Flask 服务。在生产环境中，最好不要裸跑 Flask，前面应加 nginx 等反向代理——Flask 的开发服务器（Werkzeug）不是为生产设计的。

【必须掌握】
- 默认 `host="127.0.0.1"`，只有本机能访问
- `host="0.0.0.0"` 允许局域网内其他设备通过你的 IP 访问
- 开发服务器不适合生产——需要配合 gunicorn/uWSGI + nginx

【企业场景】
联调时常见的问题：后端在服务器上起了 Flask 用默认 `127.0.0.1`，你的 Postman 在另一台电脑上连不过去。排查步骤：
1. `netstat -an | grep 5000` → 看是 `127.0.0.1:5000` 还是 `0.0.0.0:5000`
2. 如果是 `127.0.0.1` → 改成 `0.0.0.0` 重启
3. 如果还是不通 → 检查防火墙是否拦截了端口

【面试考察】
面试官："Flask 的 `host="0.0.0.0"` 有什么安全风险？生产环境应该怎么部署？"

参考回答框架：
1. `0.0.0.0` 会让服务暴露给所有网络接口，同一局域网任何人都能访问
2. Flask 自带的开发服务器（Werkzeug）不是为生产设计的——单线程、性能差、不安全
3. 生产环境应该用 gunicorn/uWSGI 等 WSGI 服务器 + nginx 反向代理
4. nginx 负责处理静态文件、负载均衡、SSL 终端等

【易错点】

| 常见错误 | 正确做法 |
|----------|----------|
| `host="127.0.0.1"` 然后让别人访问你的 IP | 改为 `host="0.0.0.0"` |
| 生产环境直接 `app.run(host="0.0.0.0")` | 用 gunicorn/uWSGI + nginx |
| 端口被占用不报错（Windows） | 换一个端口或用 `netstat` 查谁占了 5000 |

### 知识点 13：port — 监听端口

【课程原话/定义】
`app.run()` 的 `port` 参数指定端口号，默认为 5000。

```python
app.run(port=5000)   # 默认
app.run(port=5050)   # 自定义
app.run(port=80)     # HTTP 标准端口（需要管理员权限）
```

【为什么？】
端口号的范围和约定：
- 0-1023：知名端口（HTTP=80, HTTPS=443, SSH=22），绑定需要管理员权限
- 1024-49151：注册端口，常用服务的默认端口
- 49152-65535：动态/私有端口，临时使用

Flask 默认 5000 是因为开发服务器通常用高端口号避免权限问题（80 端口需要 root/管理员）。同一台机器上多个 Flask 实例需要不同端口——Flask 不允许多个进程绑定同一个端口（会报 `Address already in use`）。

【必须掌握】
- 默认端口 5000
- 端口范围：建议 1024-65535
- 端口冲突时 Flask 报 `OSError: [Errno 98] Address already in use`
- macOS 的 AirPlay Receiver 默认占用 5000 端口——如果冲突需要换端口

【我的理解】
> （同时启动两个 Flask 应用，一个用端口 5000，一个用 5050。用浏览器分别访问 `localhost:5000` 和 `localhost:5050`，确认两个服务同时工作。再试试让第二个也用 5000——会发生什么？）

### 知识点 14：Debug 模式

【课程原话/定义】
`app.run()` 设置 `debug=True` 开启调试模式。默认是 `False`（生产模式）。

```python
app.run(debug=True)   # 开启调试模式
app.run(debug=False)  # 关闭（默认）
```

调试模式的三大功能：
1. **详细错误信息**：浏览器中显示完整的 Python 错误堆栈跟踪
2. **自动重载代码**：修改代码保存后 Flask 自动重启，无需手动操作
3. **在线调试器**：错误页面中可以打开交互式 Python 调试器（在浏览器中执行 Python 代码）

【为什么？】
debug 模式的每个功能都有对应的安全风险：

| 功能 | 开发收益 | 生产风险 |
|------|----------|----------|
| 错误堆栈 | 快速定位 bug | 暴露代码路径、数据库表名、内部逻辑 |
| 自动重载 | 改代码不重启 | 监控文件变化的机制可能被利用加载恶意代码 |
| 在线调试器 | 浏览器中执行 Python | 攻击者获得服务器完整 Python shell——等于拿到服务器权限 |

**真实案例**：曾有公司把 Flask debug 模式开到线上，攻击者访问了一个不存在的路由触发 404 调试页面，打开在线调试器，执行了 `import os; os.system('rm -rf /')`——直接删库。这不是玩笑，调试器的 PIN 码保护在早期版本中可以被暴力破解。

除了安全风险，还有性能问题：
- 自动重载的监控机制消耗 CPU
- 错误页面生成消耗内存
- 单线程开发服务器无法处理并发请求

【必须掌握】
- `debug=True` 开发用，生产必须关
- 三大功能：错误详情 + 自动重载 + 在线调试器
- 生产环境的三重风险：信息泄露 + 代码注入 + 性能问题
- 生产部署用 gunicorn/uWSGI + nginx，不用 `app.run()`

【企业场景】
测试环境中的 debug 模式使用原则：
1. 本地开发：`debug=True`，提高效率
2. 内网测试环境：按需开启（团队成员调试时），但加上 PIN 码保护
3. 公网测试环境：**永远不开** debug
4. CI/CD 中的 Flask 进程：不开 debug（用 logging 代替 print 调试）

配置管理的正确姿势——不要把 `debug=True` 写死在代码里：
```python
import os
app.run(debug=os.environ.get('FLASK_DEBUG', '0') == '1')
```
通过环境变量控制，不同环境用不同配置，避免"改代码上线"的灾难。

【面试考察】
面试官："Flask 的 debug 模式有哪些功能？为什么生产环境绝对不能开？"

参考回答框架：
1. 三大功能：详细错误堆栈、自动代码重载、在线 Python 调试器
2. 安全风险：错误堆栈暴露内部代码路径；调试器允许在浏览器中执行任意 Python 代码（等于服务器权限沦陷）
3. 性能风险：自动重载的文件监控消耗资源；单线程开发服务器无法处理并发
4. 生产环境应该用 WSGI 服务器 + 反向代理，配置通过环境变量管理

【易错点】

| 常见错误                    | 正确做法                                     |
| ----------------------- | ---------------------------------------- |
| `debug=True` 写死在代码里上线   | 通过环境变量控制：`os.environ.get('FLASK_DEBUG')` |
| 以为 debug 模式只是"多打印日志"    | 它开放了在线 Python 调试器——极度危险                  |
| 测试环境随意开 debug 且不加 PIN 码 | 内网也要加 PIN，防止内部人员误操作                      |
| `debug=True` 下改了代码没自动重启 | 可能是改的不是 `.py` 文件（模板、静态文件不触发重载）           |

【扩展知识】
`debug=True` 和 `FLASK_ENV=development` 的关系：
- `debug=True` 等价于 `FLASK_DEBUG=1`
- `FLASK_ENV=development` 会自动设置 `FLASK_DEBUG=1`（Flask 2.2 之前）
- Flask 2.3+ 推荐只使用 `FLASK_DEBUG` 环境变量
- `flask run --debug` 是命令行等效方式

**实战案例**：PyCharm 下 `app.run(debug=True)` 不生效的排查 → [[../../05-Bug记录/BUG-001-Flask启动配置异常]]（PyCharm Flask Run 模式跳过 app.run()）

【我的理解】
> （分别用 `debug=True` 和 `debug=False` 启动 Flask。在代码里故意写 `1/0` 制造错误，访问路由。对比两种模式下浏览器显示的页面：debug 开启时能看到完整的 Python 堆栈跟踪吗？能看到在线调试器的入口（一个终端图标）吗？关掉 debug 后页面显示什么？）
