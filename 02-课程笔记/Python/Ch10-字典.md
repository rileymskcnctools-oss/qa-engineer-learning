## 一、什么是字典

### 知识点 1：字典的定义与特点

【课程原话/定义】
字典是 Python 中的容器数据类型，用于存储键值对（key-value）的数据集合。通过一个 key 对应一个确定唯一的值。字典是可变的，且可以存储任意类型的元素。使用花括号 `{}` 定义。

【为什么？】
如果你的数据需要"按名字找"，而不是"按位置找"，字典就是正解。接口返回的 JSON 本质就是嵌套字典——`response["data"]["user"]["name"]`。列表用数字索引，字典用有意义的 key，代码可读性天差地别。`user_list[0][2]` 是什么意思？没人知道。`user["age"]` 一目了然。

【必须掌握】
- 字面量定义：`d = {"name": "Alice", "age": 25}`
- 构造方法定义：`dict(one=1, two=2)`、`dict([("a", 1), ("b", 2)])`、`dict(zip(keys, values))`
- key 具有唯一性：同 key 后写的覆盖前写的

【企业场景】
> 接口测试中，你写的每一个请求体都是字典：`{"username": "admin", "password": "123456"}`。接口返回的 JSON 解析后也是字典：`{"code": 200, "data": {"items": [...]}}`。字典是你和 API 对话的语言。

【面试考察】
> 面试官："`d = {}` 和 `d = dict()` 有什么区别？"
> 参考回答：效果相同，`{}` 比 `dict()` 稍快（不需要函数调用开销）。但 `dict(key=value)` 适合 key 是合法 Python 标识符的场景，`dict(zip(keys, values))` 适合从两个列表批量构造。

【易错点】

| 写法 | 结果 | 原因 |
|------|------|------|
| `d = {}` | 空字典 | 合法 |
| `d = {[]: "a"}` | `TypeError: unhashable type: 'list'` | 列表不可哈希 |
| `d = {(1,2): "a"}` | `{(1,2): 'a'}` | 元组可哈希 |
| `d = {"a": 1, "a": 2}` | `{"a": 2}` | 后值覆盖前值 |

【我的理解】


### 知识点 2：key 的可哈希要求

【课程原话/定义】
key 必须是可哈希（hashable）的对象。不可变对象数据都可以得到哈希值。一般情况下，字符串类型做 key 最常见。列表不可哈希，元组（元素全可哈希）可哈希。在一次程序运行中，相同数据的 `hash()` 结果不变。

【为什么？】
字典底层是哈希表——key 先算哈希值，再映射到内存槽位。如果 key 可变（比如列表），内容变了哈希值跟着变，字典就找不到原来存的值了。这就是"列表不能做 key"的深层原因：不是 Python 故意限制你，是哈希表的数据结构决定了 key 必须稳定。

打个比方：你搬了家但不通知邮局，快递就丢了——可变 key 的哈希值就是"地址"，内容变了等于偷偷搬家。

【必须掌握】
- `hash("abc")` → 可用；`hash([1,2,3])` → `TypeError: unhashable type: 'list'`
- 元组中如果包含列表，整个元组也不可哈希：`hash((1,2,[3]))` → TypeError
- 同一程序中同一数据的 hash 不变，不同程序运行可能不同（Python 3.3+ 默认启用 hash randomization）

【企业场景】
> 你用请求参数构建缓存 key：`cache_key = (method, url, frozenset(headers.items()))`——元组可哈希所以能做二级字典的 key。如果用列表做 key，程序直接崩溃。另外 JSON 标准规定 key 必须是字符串，所以你从接口收到的所有 key 天然都是字符串——这不是巧合。

【面试考察】
> 面试官："为什么列表不能做字典的 key？底层原因是什么？"
> 参考回答：字典底层是哈希表，依赖哈希值定位。列表可变→哈希值会变→插入后内容改变再查找时哈希值对不上→找不到。从数据结构层面讲，哈希表的 key 必须满足"相等性不变"——可变对象破坏了这个前提。

【易错点】

| 数据类型 | 可哈希？ | 能做字典 key？ | 举例 |
|----------|---------|--------------|------|
| int | ✅ | ✅ | `d[1] = "a"` |
| str | ✅ | ✅ | `d["name"] = "Tom"` |
| tuple（纯不可变）| ✅ | ✅ | `d[(1,2)] = "point"` |
| list | ❌ | ❌ | `d[[1,2]]` → TypeError |
| tuple（含list）| ❌ | ❌ | `d[(1,[2])]` → TypeError |
| bool | ✅ | ✅ | `d[True] = "yes"`（注意 True==1） |
| None | ✅ | ✅ | `d[None] = "null"` |

【我的理解】

## 二、字典的基本操作

### 知识点 3：数据访问

【课程原话/定义】
字典使用 key 来获取对应的值，格式：`字典对象[key]`。key 可以理解为自定义的下标索引。

【为什么？】
`d[key]` 的设计和列表 `l[index]` 保持了一致的中括号语法，降低学习成本。但 key 不存在时抛 `KeyError` 而非返回 None——Python 的设计哲学是"找不到就是异常，不应默默吞掉"，这和列表 `IndexError` 思路一致。

【必须掌握】
- key 不存在时，`d[key]` 抛出 `KeyError`
- key 可以是变量：`k = "name"; d[k]`

【企业场景】
> 解析接口响应：`user_name = response["data"]["user"]["name"]`——三层嵌套取值。如果中间任何一层 key 不存在，`KeyError` 会让整个测试崩溃。更安全的写法是链式 `get()`：`response.get("data", {}).get("user", {}).get("name")`——但链式 get 也有盲区：如果 `data` 不是 dict 而是 list，`.get()` 会抛 AttributeError。

【面试考察】
> 面试官："`d[key]` 和 `d.get(key)` 什么时候选哪个？"
> 参考回答：确定 key 一定存在时用 `d[key]`（更直接，报错反而是好事——暴露数据异常）；不确定时用 `d.get(key, default)`（防御性编程）。测试断言中推荐用 `d[key]`，让异常直接暴露接口数据缺失问题，而不是静默通过。

【我的理解】


### 知识点 4：元素添加与修改

【课程原话/定义】
`字典对象[key] = value`。如果 key 不存在 → 添加新键值对；如果 key 已存在 → 更新 value。

【为什么？】
添加和修改用同一语法——Python 的"简洁"哲学：你不必关心 key 存不存在，直接赋值就行。这个设计也意味着"字典不允许重复 key"，key 是唯一标识符，后写的值覆盖先写的。

【必须掌握】
- 同 key 后写覆盖前写
- 不能通过不存在的 key 访问，但可以通过不存在的 key 赋值（添加）

【企业场景】
> 构建请求参数：先创建空字典 `params = {}`，动态添加：`params["page"] = 1; params["size"] = 20`。修改已有配置：`config["timeout"] = 30` 覆盖默认值。接口测试中这是最频繁的操作——几乎每个 test case 都在拼接参数。

【面试考察】
> 面试官："怎么判断 `d[key] = value` 是新增还是覆盖？"
> 参考回答：用 `in` 提前检查：`if key in d: print("覆盖") else: print("新增")`。实际编码中通常不关心——直接赋值就行。

【我的理解】


### 知识点 5：删除元素 — del

【课程原话/定义】
`del 字典对象[key]`，删除整个键值对。key 不存在时抛出 `KeyError`。

【为什么？】
`del` 是 Python 关键字，不只适用于字典——能删变量、列表元素、字典键值对、对象属性。和 `pop()` 的选择：如果你不在乎被删的值，用 `del`；如果你需要"取出再用"，用 `pop()`。

【必须掌握】
- `del d[key]` 删除键值对，key 不存在 → `KeyError`

【企业场景】
> 接口要求某些内部字段不能传给服务端：`del request_body["internal_id"]`。清理日志中的敏感信息：`del log_entry["password"]`。测试数据脱敏时逐字段删除比创建新字典更高效。

【易错点】

| 对比       | 删除 list 元素     | 删除 dict 元素   |
| -------- | -------------- | ------------ |
| 语法       | `del l[index]` | `del d[key]` |
| 依据       | 数字索引           | key 名称       |
| 不存在时报什么错 | `IndexError`   | `KeyError`   |

【我的理解】


### 知识点 6：字典的有序性（Python 3.7+）

【课程原话/定义】
Python 3.7+ 字典保持键值对的添加顺序。Python 3.6 及更早版本字典无序，需用 `collections.OrderedDict`。

【为什么？】
Python 3.6 重新设计了 dict 的底层实现（compact dict），用更少内存的同时顺便实现了有序。3.7 正式将其纳入语言规范。这个改动让字典可以替代大部分 OrderedDict 的使用场景，并且让 JSON 序列化结果更可读——字段顺序和代码中定义顺序一致。

【必须掌握】
- 3.7+ 字典有序，遍历顺序 = 插入顺序
- `d.popitem()` 删除最后插入的键值对（LIFO）
- 旧项目可能还是 3.6，要注意兼容

【企业场景】
> 构建有序的 JSON 响应：先 `code`、再 `message`、最后 `data`——按这个顺序插入字典，打印出来可读性更好，调试时不用在一堆字段里找错误码。如果你用 Python 3.6 写测试脚本跑在 3.6 服务器上，别依赖字典顺序。

【面试考察】
> 面试官："Python 字典从什么时候开始有序的？为什么之前无序？"
> 参考回答：3.7 正式保证有序（3.6 CPython 实现级有序）。之前无序是因为旧实现用纯哈希表+开放寻址，不维护插入顺序。3.6 起用紧凑字典+索引数组，顺带记录了顺序，内存反而更省。

【我的理解】

## 三、字典方法分类详解

### 知识点 7：获取类 — keys / values / items / get

【课程原话/定义】
- `d.keys()` → 所有 key，返回 `dict_keys` 类型
- `d.values()` → 所有 value，返回 `dict_values` 类型
- `d.items()` → 所有键值对（每个是元组），返回 `dict_items` 类型
- `d.get(key, default)` → 获取 key 对应的值，key 不存在返回 default（默认 None），不报错

【为什么？】
`keys/values/items` 返回的是**视图对象**而非列表——它们动态反映字典的后续修改（字典变了视图也变），且不占额外内存。这是 Python 3 的重要改进（Python 2 返回列表副本）。`get()` 是为"不确定 key 存不存在"的场景设计的，避免了 try/except 的冗余。

【必须掌握】
- 视图对象可迭代、可做成员检查（`"key" in d.keys()`），但不支持索引
- 需要独立列表时用 `list(d.keys())`
- `d.get(key)` key 不存在返回 `None`，不会抛异常

【企业场景】
> 验证接口返回字段完整性：`assert set(response.keys()) >= {"code", "data", "message"}`——用集合运算检查必填字段。遍历所有字段打印日志：`for k, v in response.items(): print(f"{k}: {v}")`。取嵌套字段带默认值：`user_name = data.get("user", {}).get("name", "未知用户")`。

【面试考察】
> 面试官："`d.keys()` 返回的是列表吗？和 Python 2 有什么不同？"
> 参考回答：不是，是 `dict_keys` 视图对象，动态反映字典变化，不占额外内存。Python 2 返回列表副本——如果字典很大，浪费内存。需要列表时用 `list(d.keys())`。

【易错点】

| 取值方式 | key 存在 | key 不存在 | 推荐场景 |
|----------|---------|-----------|---------|
| `d[key]` | 返回 value | `KeyError` | 确定 key 存在时 |
| `d.get(key)` | 返回 value | 返回 `None` | 不确定时，不需要特殊默认值 |
| `d.get(key, default)` | 返回 value | 返回 default | 需要自定义默认值时（如 0、[]、"N/A"） |

```python
# 动手验证：
d = {"name": "Tom", "age": 23}

print(d.get("hobby"))   # None，不报错
print(d["hobby"])       # KeyError: 'hobby'
```

【我的理解】


### 知识点 8：添加更新类 — setdefault / fromkeys / update

【课程原话/定义】
- `d.setdefault(key, default)` — key 不存在时添加默认值并返回该值；key 已存在时返回现有值，不修改
- `dict.fromkeys(keys, val)` — 静态方法，用 keys 序列创建新字典，所有值初始为 val（默认 None）
- `d.update(dict | iterable)` — 用参数中的数据更新字典：存在的 key 覆盖，不存在的 key 新增

【为什么？】
`setdefault` 解决了一个常见模式："如果没有这个 key 就初始化为默认值，然后操作它"。不用 setdefault 需要写 3 行（if + 赋值 + 操作），用它 1 行搞定。`fromkeys` 适合批量初始化——比如给一组字段设默认值。`update` 相当于批量赋值，是合并两个字典的标准方式（`{**d1, **d2}` 是 3.5+ 的更简洁写法）。

【必须掌握】
- `setdefault` 会修改字典，`get` 不会——这是本质区别
- `fromkeys` 是静态方法，必须用 `dict.fromkeys()` 调用，不能用实例
- `fromkeys` 所有 key 共享同一个 value 对象——value 是列表时小心（改一个全变）

【企业场景】
> `setdefault`：统计接口返回数据中各 HTTP 状态出现次数——`status_count.setdefault(code, 0); status_count[code] += 1`。`update`：合并默认配置和用户自定义配置——`config = default_config.copy(); config.update(user_config)`。`fromkeys`：初始化一批监控指标，默认值全为 0——`metrics = dict.fromkeys(["cpu", "mem", "disk"], 0)`。

【面试考察】
> 面试官："`setdefault()` 和 `get()` 的本质区别？"
> 参考回答：`setdefault` 会修改字典（key 不存在时插入默认值），`get` 只读不写。调用 `setdefault` 后字典已经变了——这是很多人的盲区：他们以为 setdefault 和 get 一样只是取值，结果字典被悄悄塞了值。

【易错点】

| 方法 | 修改原字典？ | 返回值是什么 | key 已存在时的行为 |
|------|-----------|------------|-----------------|
| `setdefault(key, val)` | 可能修改 | 返回 key 对应的值（新或旧） | 返回旧值，不修改 |
| `get(key, val)` | 不修改 | 返回 key 对应的值或默认值 | 返回旧值 |
| `update(other)` | 修改 | 返回 `None` | 覆盖旧值 |
| `dict.fromkeys(keys, val)` | 创建新字典 | 新字典 | 不适用（创建新字典） |

```python
# 动手验证 setdefault 的坑：
d = {"name": "Tom"}
result = d.setdefault("name", "Jack")
print(result)   # ?
print(d)        # ?
```

【我的理解】


### 知识点 9：删除类 — popitem / pop / clear

【课程原话/定义】
- `d.popitem()` — 取出并删除最后一个键值对，返回元组 `(key, value)`，空字典时抛 `KeyError`
- `d.pop(key)` — 取出并删除指定 key 的键值对，返回 value，key 不存在抛 `KeyError`
- `d.clear()` — 清空所有键值对

【为什么？】
`pop` 有返回值而 `del` 没有——这是"我需要被删的那个值"和"我只要删掉它"的场景区分。`popitem()` 在 3.7+ 删最后一个（LIFO），在 3.6 以前随机删——它的原始目的是高效地"逐个销毁"字典（不需要维护删除顺序），3.7+ 变为有序是附带效果。

【必须掌握】
- `d.pop(key)` 可以带默认值：`d.pop(key, None)`——找不到时返回 None 而不报错
- `d.popitem()` 空字典抛 `KeyError`
- 列表没有 `popitem()` 方法——这是字典独有的

【企业场景】
> `pop`：从请求参数中提取并移除分页 token——`next_token = params.pop("page_token", None)`。`popitem`：按后进先出处理任务栈——`while task_stack: task_name, task_fn = task_stack.popitem(); task_fn()`。`clear`：测试 tearDown 中清空全局缓存数据——`cache.clear()`。

【面试考察】
> 面试官："`pop()` 和 `popitem()` 的区别？"
> 参考回答：`pop(key)` 指定 key 删除，`popitem()` 删最后一个（3.7+ LIFO）。`pop` 可带默认值避免 KeyError，`popitem` 不能。列表的 `pop()` 按索引删，字典的 `pop()` 按 key 删——同名不同行为。

【易错点】

| 方法 | 按什么删除 | 返回值 | 空字典/不存在时 | 列表有对应方法？ |
|------|----------|--------|---------------|----------------|
| `d.pop(key)` | key | value | KeyError（可设默认值避免） | `l.pop(index)` |
| `d.popitem()` | 最后一个 | `(key, value)` | KeyError | 无 |
| `del d[key]` | key | 无 | KeyError | `del l[i]` |
| `d.clear()` | 全部 | 无 | 安全（空也不报错） | `l.clear()` |

【我的理解】

## 四、列表 vs 字典对比总结

| 对比维度 | 列表 list | 字典 dict |
|----------|----------|----------|
| 访问方式 | 数字索引 `l[0]` | key `d["name"]` |
| 元素形式 | 单个值 | 键值对 |
| 是否有序 | 有序 | 3.7+ 有序 |
| 是否可变 | 可变 | 可变 |
| 越界/缺失行为 | `IndexError` | `KeyError` |
| 安全取值方法 | 先 `if index < len(l)` | `d.get(key, default)` |
| 典型测试场景 | 用例列表、结果集、日志行 | 请求参数、响应 JSON、配置项 |
