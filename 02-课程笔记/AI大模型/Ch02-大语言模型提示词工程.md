## 一、提示词 Prompt 介绍

### 知识点 1：什么是提示词工程

【课程原话/定义】

- **对于普通人**：提示词是和 AI 沟通的桥梁，提示词的好坏决定了返回结果是否准确。
- **对于开发者**：提示工程（Prompt Engineering）是一种相对较新的学科，专门用于开发和优化提示，以高效地使用语言模型来处理各种应用和研究主题。

【为什么？】

GPT 是"生成式"模型，它根据你给的输入"续写"最可能的下文。它没有读心术，也不会主动澄清模糊需求——你给什么输入，它就朝什么方向生成。所以提示词质量直接决定输出质量，这就像：
- 你问同事"帮我看看这个"，同事会懵
- 你问同事"帮我 review 这段登录代码，重点看有没有 SQL 注入"，同事就能精准工作

提示工程就是研究"怎么问，AI 才能答得好"的方法论。

【必须掌握】

- Prompt：你发给模型的输入文本
- 提示工程：开发 + 优化提示词的学科
- 核心认知：GPT 不会读心，需求越具体，输出越准

【易错点】

| 误区 | 事实 |
|------|------|
| "提示词就是随便打字问" | 提示词是精心设计的输入，有方法可循 |
| "AI 能理解我的潜台词" | GPT 只基于字面输入续写，模糊输入=模糊输出 |
| "提示工程没技术含量" | 它是影响大模型效果的关键变量，有系统方法 |

【我的理解】

> 用你自己的话解释：为什么"帮我写个测试用例"得到的回答，通常比"帮我为'登录功能'设计 5 条等价类划分的测试用例，包含正常、异常场景，用表格输出"得到的回答差很多？

## 二、提示词的原则与技巧

### 知识点 2：五大原则

【课程原话/定义】

| 原则 | 原因 |
|------|------|
| 写清楚需求 | GPT 无法读懂想法，需具体：包含详细信息、要求角色、用定界符划分输入 |
| 提供参考文本 | 提供相似示例，让模型了解你要什么 |
| 复杂任务拆成简单子任务 | 拆小后模型更容易理解，结果更准 |
| 角色扮演 | 告诉 ChatGPT 扮演特定角色，模拟真实场景 |
| 系统地测试变化 | 改动提示词时系统测试，找出最有效的改动 |

【为什么？】

这五条原则背后是同一个底层逻辑：**降低模型的"猜测空间"**。

- 写清楚需求 → 减少语义歧义
- 提供参考文本 → 给出格式和内容的锚点（few-shot）
- 拆分任务 → 每一步的难度更低，减少长链条推理出错
- 角色扮演 → 激活模型训练数据中对应角色的语料分布
- 系统测试 → 提示词也是"代码"，需要版本化迭代

【必须掌握】

- 五大原则：写清楚、给参考、拆任务、角色扮演、系统测试
- 定界符技巧：用 `###`、`"""`、`<标签>` 等把不同部分分开

【企业场景】

> 你要用 GPT 生成接口测试用例。对比两种提示词：
>
> ❌ 差："帮我写测试用例"
> ✅ 好：
> ```
> 你是一名资深测试工程师。请为下面的接口设计测试用例。
> 
> 接口信息（定界符包裹）：
> ###
> POST /login
> 参数：username(必填), password(必填)
> ###
> 
> 参考格式（few-shot）：
> 1. 用例标题：登录成功
>    输入：username=admin, password=123456
>    预期：返回200，token非空
> 
> 请输出：等价类划分的正常用例3条 + 异常用例5条，用表格呈现。
> ```
>
> 第二条同时用到了"角色扮演 + 写清楚需求 + 定界符 + 参考文本 + 拆分子任务"，输出质量天差地别。

【面试考察】

> 面试官："说说提示词工程的核心原则，你在实际工作中怎么用？"

**参考回答框架：**

1. 核心原则：写清楚需求、提供参考（few-shot）、拆分子任务、角色扮演、系统测试
2. 我常用技巧：定界符隔离输入、给 few-shot 示例固定输出格式、让模型先"分析再回答"（思维链）
3. 落地案例：用角色扮演 + few-shot 让 GPT 按固定模板生成测试用例，再人工审核
4. 认知：提示词要像代码一样版本化、系统测试，不是一次写死的

### 知识点 3：拆解五大原则的实操技巧

【扩展知识】

**1. 写清楚需求（三个具体手段）**

- **包含详细信息**：不要问"写个爬虫"，要问"写一个 Python 爬虫，爬取某网站前3页新闻标题，用 requests + BeautifulSoup，处理反爬"
- **要求模型采用角色**：`你是一名拥有10年经验的测试架构师`
- **使用定界符**：用 `###`、`"""` 或 `<text>` 把"指令"和"待处理内容"隔开，防止注入混淆

**2. 提供参考文本（few-shot）**

```markdown
请把下面的句子翻译成英文，格式参考示例：

示例1：你好 → Hello
示例2：谢谢 → Thank you

待翻译：再见
```

**3. 复杂任务拆分**

不要一次性让模型"从零写一个完整的自动化测试框架"，而是：
1. 先让模型设计框架目录结构
2. 再让模型逐个实现模块（配置文件 → 请求封装 → 断言封装 → 报告）
3. 最后让模型写集成示例

**4. 角色扮演**

`你现在是资深测试工程师，正在面试一个初级测试候选人，请问我5个关于接口测试的问题，并根据我的回答评估水平`

**5. 系统测试变化**

每次只改一个变量（比如只改角色设定，其他不变），对比输出差异，确定哪个改动有效。
