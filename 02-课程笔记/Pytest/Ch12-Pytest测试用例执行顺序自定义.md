## 一、pytest-order 基础

### 知识点1：为什么需要控制执行顺序

【课程原话/定义】
pytest-order 是一个可自定义测试用例执行顺序的插件。对于集成测试中具有上下文依赖关系的用例（登录→创建订单→支付→查询），需要按顺序执行。

【为什么？】
pytest 默认按字母序/代码行序执行用例，这是为单元测试设计的——单元测试间不应有依赖。但集成测试天然有步骤依赖：不登录怎么下单？不下单怎么支付？强行保持用例独立会让代码变得臃肿（每个用例都写登录逻辑）。pytest-order 承认了"集成测试有依赖是现实"，用最小的代价管理这种依赖——一个装饰器标注顺序。

【必须掌握】
- pytest 默认执行顺序：从上到下（同文件）、字母序（跨文件）
- pytest-order 的定位：不是鼓励依赖，而是管理不可避免的依赖
- 使用场景：集成测试 > E2E 测试 > 有上下文依赖的场景
- 不适合：纯单元测试（单元测试应保持独立）

【企业场景】
你的支付系统集成测试有 4 步：登录 → 创建订单 → 支付 → 查订单状态。用 pytest-order 标记 order(1) 到 order(4)，确保即使 CI 随机分配用例执行顺序，这 4 步也严格按序执行。如果某一步失败，pytest 会标记后续依赖步骤为 error，你一眼就知道根因在第一步。

【面试考察】
面试官："pytest 默认按什么顺序执行用例？如果有依赖关系怎么办？"
参考回答框架：① pytest 默认：同一文件从上到下，跨文件按字母序 ② 理想情况：测试用例应保持独立，不应有依赖 ③ 现实情况：集成测试/E2E 测试有天然步骤依赖 ④ 解决方案：pytest-order 插件，用 `@pytest.mark.order(n)` 控制 ⑤ 原则：尽量少用，只在不可避免的依赖场景用

【易错点】

| 误区 | 正解 |
|------|------|
| 所有测试都加 order | 只在有步骤依赖的集成测试用；单元测试保持独立 |
| order 越大越先执行 | order 值**越小**优先级越高，越先执行 |
| pytest-order 解决所有依赖问题 | 它只控制顺序，不保证前面用例的状态传递给后面用例（传数据用 fixture） |

## 二、基本使用

### 知识点2：@pytest.mark.order 语法

【课程原话/定义】
- 安装：`pip install pytest-order`
- 使用：`@pytest.mark.order(数字)`，order 值越小优先级越高
- 特殊值：`"first"` 最先执行，`"last"` 最后执行
- 未标记的用例按默认顺序（代码行序）执行

【为什么？】
order 的值设计成"越小越先"而不是"越大越先"，是为了直觉：`order(1)` = 第一步，`order(2)` = 第二步。如果用"越大越先"，`order(10)` 是第一步会让人困惑。"first" 和 "last" 是语法糖，替代 `order(0)` 和 `order(9999)`，语义更清晰。

【必须掌握】
- `@pytest.mark.order(n)` — n 越小越先执行
- `@pytest.mark.order("first")` — 在所有标记用例中最先
- `@pytest.mark.order("last")` — 在所有标记用例中最后
- 未标记 order 的用例排在最后，按默认顺序执行
- 验证命令：`pytest -vs` 查看执行顺序

【企业场景】
你写了一条冒烟测试用例（验证服务是否存活），这条必须在所有用例之前跑——如果服务挂了，后面的 500 条都是浪费时间。标记 `@pytest.mark.order("first")`，配合 `pytest -x`（首次失败停止），服务挂了就立即中断，不浪费 CI 资源。

【面试考察】
面试官："`@pytest.mark.order(1)` 和 `@pytest.mark.order(3)` 哪个先执行？`"first"` 和 `order(1)` 呢？"
参考回答框架：① order 值越小越先 → order(1) 先于 order(3) ② `"first"` 在所有数字之前（可以理解为 order 最小值）③ 执行顺序：first → order(1) → order(2) → order(3) → 无标记用例（默认顺序）→ last

【易错点】

| 常见错误 | 正确做法 |
|------|------|
| `order(3)` 在 `order(1)` 之前执行 | order 越小越先，`order(1)` > `order(3)` |
| 以为 `"first"` 和 `order(1)` 冲突 | `"first"` 比所有数字 order 更先 |
| 不给有依赖的用例加 order，靠文件名排序 | 不同 CI 环境的文件系统排序可能不同，应用 order 显式控制 |
| `@pytest.mark.order` 忘了括号 | 必须是 `@pytest.mark.order(1)` 而不是 `@pytest.mark.order` |

## 三、实战与注意事项

### 知识点3：集成测试场景与最佳实践

【课程原话/定义】
适用场景：登录 → 创建订单 → 支付 → 查询订单，这 4 个步骤需要按顺序执行。order 更适合集成测试，不适合完全独立的单元测试。

【为什么？】
"不建议大量依赖执行顺序"不是为了否定 pytest-order，而是在提醒：如果你给 100 条用例都加 order，说明你的测试设计有问题——它们可能共享了可变状态，一条失败会导致连锁反应。好的测试策略是：单元测试独立（无 order），集成测试步骤化（用 order），E2E 测试场景化（用 order）。

【必须掌握】
- 适合：集成测试、E2E 测试的步骤化场景
- 不适合：独立单元测试
- 原则：尽量少用，只在确实有步骤依赖时使用
- 传入数据（如登录后的 token）应通过 fixture 而非依赖执行顺序

【企业场景】
你的团队开始大量使用 pytest-order 后，一条测试数据污染了数据库，后面 20 条用例全部失败。你复盘发现：order 控制了顺序，但没有控制数据隔离。改进方案：order 只管步骤顺序（登录→操作），数据隔离靠 fixture 的 scope=function 保证每条用例干净的数据环境。两个维度各司其职。

【面试考察】
面试官："你提到 pytest-order 不适合单元测试，为什么？"
参考回答框架：① 单元测试的原则是每个测试独立、可单独运行 ② 如果单元测试有执行顺序依赖，说明测试之间有共享可变状态——这本身就是设计问题 ③ 加 order 只是掩盖了问题，没有解决问题 ④ 正确做法：用 fixture（scope=function）保证数据隔离，让每个单测自给自足

【易错点】

| 场景 | 该不该用 order | 原因 |
|------|------|------|
| 单元测试：加法函数 | ❌ | 完全独立，不需要顺序 |
| 集成测试：下单流程 | ✅ | 登录→下单→支付有天然步骤 |
| 想让某条先用例先跑因为慢 | ❌ | 执行速度不是 order 的理由，用 pytest-xdist 并发 |
| E2E：用户注册→登录→发帖→登出 | ✅ | 完整用户旅程，步骤有上下文 |
