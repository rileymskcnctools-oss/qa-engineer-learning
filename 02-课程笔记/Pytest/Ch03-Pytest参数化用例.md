## 一、什么是参数化

### 知识点1：参数化的定义与核心思想

【课程原话/定义】
Pytest 中的参数化是通过参数的方式传递数据，从而实现数据和脚本分离。允许在同一个测试函数上多次运行相同的测试，使用不同的输入数据进而生成多个测试用例。

【为什么？】
没有参数化时，测试 10 组数据就要写 10 个几乎一样的测试函数——复制粘贴 10 次，改 10 个地方的数据。一旦测试逻辑要改（比如加一个断言），就要改 10 个函数，漏掉一个就是 Bug。参数化解决的核心矛盾：**测试逻辑相同，但测试数据不同**——把数据和逻辑分离，逻辑写一次，数据通过参数注入。这也是"数据驱动测试（DDT）"思想的落地实现。

【必须掌握】
- `@pytest.mark.parametrize(argnames, argvalues, ids)` 三个参数的含义
- 单参数：`argnames="name"`，argvalues 是一维列表
- 多参数：`argnames="a,b"`，argvalues 是列表嵌套元组（每个元组对应一组参数）
- 笛卡尔积：两个 `@parametrize` 装饰器叠加，用例数 = 参数A数量 × 参数B数量

【企业场景】
> 你在写接口自动化测试，登录接口要测 20 种用户名+密码组合（合法/非法/边界/空值）。没有参数化，20 个测试函数 = 200 行代码；有了参数化，1 个函数 + 20 行数据 = 30 行代码。更重要的是，当登录逻辑变了（比如增加验证码字段），你改 1 个函数就够了，不是改 20 个。

【面试考察】
面试官："你们自动化测试怎么做数据驱动的？"
参考回答框架：① 我们使用 Pytest 的 `@parametrize` 装饰器 ② 测试数据可以写死在装饰器里（简单场景）或从外部 JSON/YAML/Excel 读取（复杂场景）③ 这样测试逻辑和测试数据分离，新增用例只加数据不改代码。

【易错点】

| 易混淆                                  | 区别                                              |
| ------------------------------------ | ----------------------------------------------- |
| `@parametrize("a,b", [(1,2),(3,4)])` | 两组参数，生成 2 条用例                                   |
| 两个 `@parametrize` 叠加                 | 笛卡尔积，A×B 条用例                                    |
| `ids` 传列表                            | 别名数量必须等于用例数量，否则报错                               |
| 参数化 ≠ 循环                             | 参数化每一条是独立用例（单独 PASS/FAIL 统计），循环里 assert 失败整条函数停 |

【我的理解】

### 知识点2：参数化的优点

【课程原话/定义】
1. 简化测试代码：单个测试函数覆盖多种测试情况，避免重复代码
2. 减少维护成本：修改测试逻辑只需改一处

【为什么？】
这和"函数封装"是同一个道理——把变化的部分（数据）抽出来当参数，不变的部分（逻辑）留在函数体内。代码量从 O(n) 降到 O(1)，维护成本同理。

【必须掌握】
- 参数化的本质是 DDT（Data-Driven Testing）：数据驱动测试
- 和写循环的区别：参数化每一条独立统计 PASS/FAIL

【扩展知识】
数据文件驱动：数据量很大时（比如 100+ 条），`argvalues` 可以从外部读取：
```python
import json
with open("test_data.json") as f:
    data = json.load(f)
@pytest.mark.parametrize("username,password,expected", data)
```

【我的理解】

## 二、参数化使用方法

### 知识点3：单参数

【课程原话/定义】
单参数时，将数据放在列表或元组中。

【为什么？】
最简单的参数化形式，一个变量对应一个值列表。每个值生成一条测试用例。

【必须掌握】
```python
search_list = ['appium', 'selenium', 'pytest']

@pytest.mark.parametrize('name', search_list)
def test_search(name):
    assert name in search_list
```
每个 `name` 值对应一条独立的测试用例。

【易错点】
- 变量名 `'name'` 必须和函数参数 `name` 一致
- 拼写不一致会报 `fixture 'xxx' not found`

【我的理解】
>把逻辑相同的测试工作简化，只需动态替代数据，便可用简短代码实现多条测试用例，提高代码复用性。

---

### 知识点4：多参数

【课程原话/定义】
将数据放在列表嵌套元组或列表中。元组中参数的顺序要和 `argnames` 声明的顺序一一对应。

【为什么？】
现实中大多数测试场景都有多个输入参数（用户名+密码、输入+预期输出）。多参数把一组相关的输入打包成一个元组，逻辑清晰。

【必须掌握】
```python
# 数据放在元组中
@pytest.mark.parametrize(
    "test_input,expected",
    [
        ("3+5", 8),
        ("2+5", 7),
        ("7+5", 12)
    ]
)
def test_mark_more(test_input, expected):
    assert eval(test_input) == expected
```
- `"test_input,expected"` 字符串中用逗号分隔参数名
- 每个元组 `("3+5", 8)` 对应一组 (输入, 期望)
- 也可以用列表代替元组：`["3+5", 8]`

【企业场景】
> 接口测试中，一个接口的测试数据通常是一组键值对。比如登录接口：`[("admin","123456",200), ("","",400), ("admin","wrong",401)]`。每组包含 (用户名, 密码, 期望HTTP状态码)。

【面试考察】
面试官："怎么设计接口测试的参数化数据？"
参考回答：① 按测试场景分组（正向/异常/边界）② 每组数据包含：输入参数 + 期望结果 ③ 用 `ids` 给每条用例命名，方便报告定位

【易错点】

| 易错写法                     | 正确写法                    | 原因                       |
| ------------------------ | ----------------------- | ------------------------ |
| `"test_input, expected"` | `"test_input,expected"` | 空格会被当作参数名的一部分            |
| 元组 `(3+5, 8)`            | `("3+5", 8)`            | `3+5` 会被计算成 `8`，丢掉了原始表达式 |

【我的理解】
>

### 知识点5：用例重命名 — ids 参数

【课程原话/定义】
通过 `ids` 参数给每条测试用例起别名。`ids` 列表的个数必须与参数值个数一致。

【为什么？】
默认生成的用例名是 `test_func[value1-value2]`，可读性差。当用例数量多（10+）且失败时，你靠 `test_login[admin-123456]` 一眼能找到问题，比 `test_login[arg0-arg1]` 快 10 倍。团队协作时，好的用例名 = 好的文档。

【必须掌握】
```python
@pytest.mark.parametrize(
    "test_input,expected",
    [("3+5", 8), ("2+5", 7), ("7+5", 12)],
    ids=['add_3+5=8', 'add_2+5=7', 'add_3+5=12']
)
```
- `ids` 长度必须等于用例数量
- 中文 `ids` 在终端显示为 unicode 编码（需要 `conftest.py` 中配置解决）

【企业场景】
> 测试报告（如 Allure）中，用例名就是 `ids` 的值。如果 100 条用例全叫 `test_login[0]`、`test_login[1]`……出了 Bug 你根本不知道是哪条数据。好的 `ids` 命名规范：`[场景]_[输入]_[期望]`，如 `正向_合法邮箱_返回True`。

【扩展知识】
解决中文 `ids` unicode 显示问题：在 `conftest.py` 添加：
```python
def pytest_collection_modifyitems(items):
    for item in items:
        item.name = item.name.encode('utf-8').decode('unicode_escape')
        item._nodeid = item.nodeid.encode('utf-8').decode('unicode_escape')
```

【我的理解】

### 知识点6：笛卡尔积参数化

【课程原话/定义】
两组数据通过两个 `@pytest.mark.parametrize` 装饰器叠加，生成所有可能的组合。用例总数 = 参数A数量 × 参数B数量。

【为什么？】
很多测试场景需要组合覆盖。比如：测试一个搜索功能，浏览器（Chrome/Firefox/Edge）× 关键词类型（中文/英文/数字/特殊字符）= 3×4=12 条用例。笛卡尔积让你用两组独立数据自动生成全部组合——你只需要维护两组数据，不用手动列举 12 种组合。

【必须掌握】
```python
@pytest.mark.parametrize("b", ["a", "b", "c"])   # 第二个装饰器 → 内层变量
@pytest.mark.parametrize("a", [1, 2, 3])          # 第一个装饰器 → 外层变量
def test_param(a, b):
    print(f"a={a}, b={b}")
```
生成 9 条用例：(1,a)(1,b)(1,c)(2,a)(2,b)(2,c)(3,a)(3,b)(3,c)

**执行顺序**：最靠近函数的装饰器是先变化的（外层），越远的越稳定（内层）。上面例子：a 每变一次，b 走完一轮。

【企业场景】
> 兼容性测试矩阵：操作系统（Win/Mac/Linux）× 浏览器（Chrome/Firefox/Edge/）→ 笛卡尔积自动生成完整矩阵。如果产品说"我们只支持 Chrome+Win 和 Safari+Mac"，那用多参数（不用笛卡尔积）手动列出组合即可。

【面试考察】
面试官："笛卡尔积参数化和普通多参数有什么区别？什么时候用哪个？"
参考回答：① 多参数：手动指定每一组组合，适合非全组合场景（如只测特定搭配）② 笛卡尔积：自动生成全组合，适合矩阵型测试（如兼容性测试）③ 使用原则：如果组合之间有"互斥"（某些组合不可能出现），用多参数手动列；如果能全排列，用笛卡尔积省事

【易错点】

| 场景 | 用例数计算 |
|------|-----------|
| 1 个 parametrize，3 个值 | 3 条 |
| 2 个 parametrize，各 3 个值 | 3×3=9 条 |
| 3 个 parametrize，各 N/M/K 个值 | N×M×K 条（容易组合爆炸！） |

【我的理解】
