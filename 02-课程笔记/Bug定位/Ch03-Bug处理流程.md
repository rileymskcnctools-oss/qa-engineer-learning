## 一、不同角色对 Bug 的职责

### 知识点1：谁对 Bug 负责什么

【课程原话/定义】
Bug 处理流程涉及多个角色，每个角色有不同职责。

【为什么？**
很多人以为 Bug 就是"测试提交 → 开发修复 → 测试关闭"一条线。实际上一条 Bug 从生到死涉及至少 4 个角色：

| 角色          | 职责      | 关键动作                   |
| ----------- | ------- | ---------------------- |
| **测试人员**    | 发现 & 验证 | 提交 Bug、回归验证、关闭 Bug     |
| **开发人员**    | 分析 & 修复 | 确认 Bug、修复代码、标记 Fixed   |
| **项目经理/PM** | 仲裁 & 排期 | 分配 Bug、确认优先级、裁决争议      |
| **产品经理/PO** | 需求判定    | 确认是否为 Bug（需求层面）、决定是否修改 |

理解角色分工的意义：Bug 流转不是"你推给我、我推给你"——每个角色在流程中都有明确的入口和出口。

【必须掌握】
- 测试：提交 + 回归验证 + 关闭
- 开发：确认 + 修复
- PM/组长：分配 + 排期
- PO：需求层判定（By Design / Won't Fix 需要 PO 确认）

【企业场景】
> 你提了一个 Bug 给开发，开发说"By Design"。你不是直接关掉——需要 PO 确认"需求设计就是这样吗？"如果 PO 点头 → 关掉。如果 PO 说"这不是我设计的，应该要改"→ Reopen 给开发。

## 二、Bug 生命周期（Bug 处理流程）

### 知识点2：Bug 的 6 个核心状态

【课程原话/定义】
Bug 处理流程就是 Bug 的生命周期，从测试人员提交 Bug 到最终解决问题的一系列步骤。

【为什么？**
Bug 生命周期是你每天在 Jira/禅道中操作的核心界面——你的每一次状态流转都在走这个流程。理解流程图 = 知道每个状态下你能做什么操作、下一步该流转给谁。

**标准 6 状态流转：**

```
测试提交 Bug
     ↓
  [New] 新建 ——————→ [Rejected] 开发拒绝（非Bug/无法复现）
     ↓                       ↓
  开发确认                   测试确认
     ↓                       ↓
  [Open] 打开/确认        [Closed] 关闭（确实不是Bug）
     ↓
  开发修复
     ↓
  [Fixed] 已修复
     ↓
  测试回归验证
     ↓
[Closed] 关闭 ←——→ [Reopen] 重新打开（验证不通过）
```

【必须掌握】
- 6 个状态能默写：New → Open → Fixed → Closed，以及两个分支：Rejected 和 Reopen
- 每个状态的"谁操作"要清楚

| 状态       | 含义         | 谁操作 | 下一步      |
| -------- | ---------- | --- | -------- |
| New      | 测试刚提交      | 测试  | → 开发确认   |
| Open     | 开发确认是 Bug  | 开发  | → 开发修复   |
| Fixed    | 开发已修复，待验证  | 开发  | → 测试回归   |
| Closed   | 测试验证通过，关闭  | 测试  | 终点       |
| Rejected | 开发认为不是 Bug | 开发  | → 测试确认   |
| Reopen   | 回归不通过，重新打开 | 测试  | → 开发重新修复 |

【面试考察】
面试官问："Bug 从提交到关闭，经历了哪些状态流转？"
参考回答：New（测试提交）→ Open（开发确认）→ Fixed（开发修复）→ Closed（测试验证通过关闭）。如果开发认为是非 Bug → Rejected（测试确认后可能是 Closed）。如果回归验证不通过 → Reopen（重新进入 Open→Fixed→Closed 循环）。

【易错点】

| 常见错误 | 正确做法 |
|----------|----------|
| 开发直接关 Bug | 只有测试有权关闭 Bug（测试是 Bug 的提交者，也是最终确认者） |
| 测试直接改开发的状态 | 测试只能操作 New/Reopen/Closed，不能操作 Open/Fixed |
| Reopen 后不走确认直接修复 | Reopen → Open（开发重新确认）→ Fixed（修复）→ 回归 |

### 知识点3：Bug 流程的 6 个详细步骤

【课程原话/定义】
Bug 处理流程包含：提交缺陷 → 指派缺陷 → 确认缺陷 → 推迟处理 → 处理缺陷 → 回归缺陷 → 关闭缺陷。

【为什么？**
6 状态是简化的逻辑视图，7 步骤是操作视图——每一步对应一个具体动作。

| 步骤     | 做什么            | 关键细节                                       |
| ------ | -------------- | ------------------------------------------ |
| ① 提交缺陷 | 测试填写 Bug 报告并提交 | 先查重，确认没人提过；描述尽可能详细                         |
| ② 指派缺陷 | 分配给对应的开发       | 清楚开发分工 → 直接指派；不清楚 → 指派给组长转交                |
| ③ 确认缺陷 | 开发分析并重现        | 能重现 → 确认；不能重现 → 退回测试补充信息；不是 Bug → Rejected |
| ④ 推迟处理 | 判断是否要现在修       | 极端场景/架构改动大/优先级低 → Postponed                |
| ⑤ 处理缺陷 | 开发修复代码         | 修复后标记 Fixed，附修复说明                          |
| ⑥ 回归缺陷 | 测试验证           | 三种情况：确认非缺陷→关闭；确认修复→关闭；修复不通过→Reopen         |
| ⑦ 关闭缺陷 | 测试最终关闭         | 只有验证通过才能关                                  |

【企业场景】
> 步骤 ④"推迟处理"是最容易出分歧的环节。开发说"这个问题要改架构，下个版本再做"，你作为测试需要评估：这个 Bug 的影响面多大？如果影响核心流程，你不能接受 Postponed——拉 PM 讨论优先级。如果不是核心流程，接受 Postponed 但记到 backlog，下个迭代跟踪。

### 知识点4：回归缺陷的 3 种情况

【课程原话/定义】
回归缺陷对测试人员非常重要，有 3 种情况：
1. 确认非缺陷：开发说不是 Bug → 测试再次确认 → 确实不是就关闭，确实就是补充信息重新转给开发
2. 确认修复：开发修了 → 测试验证 → 通过就关闭，不通过就 Reopen
3. 确认遗留：定期回顾 Postponed 的 Bug → 版本更新后已不存在就关闭，仍然存在且变紧急就 Reopen

【为什么？**
回归验证是测试工作中占比最高的活动——据统计，测试工程师约 40% 的时间花在回归上。这 3 种情况的处理方式不同，搞混了会导致：
- 该关的没关 → Bug 列表膨胀，无法分辨哪些是活跃 Bug
- 该 Reopen 的关了 → Bug 遗留到线上

【必须掌握】
- 回归的 3 种类型和各自的处理路径
- 核心原则：测试是 Bug 状态的最终把关者

【企业场景】
> 你回归一个 3 个月前 Postponed 的 Bug，发现新版本已经不存在这个问题了（可能是关联模块重构间接修复的）。你的正确操作：在 Bug 单上备注"新版本验证已不存在，关闭"，然后 Closed。不要默默关——留记录让团队知道这个 Bug 是怎么消失的。

## 三、Bug 处理意见

### 知识点5：7 种处理意见

【课程原话/定义】
Bug 最终的处理方式有 7 种。

【为什么？**
提交 Bug 后，不是只有"修了"和"没修"两种结果。7 种处理意见覆盖了所有可能的走向——理解每种的含义，才能在 Jira/禅道中正确流转。

| 处理意见 | 英文 | 含义 | 什么时候用 |
|----------|------|------|------------|
| 可修改 | Fixable | Bug 可被修复 | 正常情况，开发确认后修复 |
| 重复 | Duplicated | 已被其他人提过 | 同现象、同根因的 Bug 已存在 |
| 延后 | Postponed | 本版不做，延到后续版本 | 极端场景、架构改动大、优先级低 |
| 设计如此 | By Design | 产品就是这么设计的 | 需求和测试理解不一致，PO 确认后 |
| 不可复现 | Can't Reproduce | 开发环境中无法重现 | 偶发 Bug，测试补充信息后再试 |
| 不是问题 | Not Error | 不是 Bug | 测试理解有误或环境问题导致 |
| 不值得修 | Won't Fix | 是 Bug 但影响太小 | 理论上对、但修复成本 > 收益 |

【必须掌握】
- 7 种意见能默写（至少能说出 Fixable / Duplicated / Postponed / By Design / Can't Reproduce）
- Postponed vs Won't Fix：Postponed = 延后但会修；Won't Fix = 决定不修
- By Design vs Not Error：By Design = 是功能特性不是 Bug；Not Error = 不是问题（如环境配置问题）

【面试考察】
面试官问："Postponed 和 Won't Fix 有什么区别？"
参考回答：Postponed = "这是个 Bug，但现在来不及修，下个版本修"——Bug 的严重性是认可的，只是排期延后。Won't Fix = "这是个 Bug，但影响太小不值得修"——Bug 本身被定性为不修。Postponed 的 Bug 会在 backlog 里，Won't Fix 的直接关。

【易错点】

| 容易混淆 | Postponed | Won't Fix | By Design |
|----------|-----------|-----------|-----------|
| 是不是 Bug | ✅ 是 | ✅ 是 | ❌ 不是 |
| 修不修 | 以后修 | 不修 | 不适用 |
| 谁决定 | PM 排期 | PM + 开发 | PO 确认需求 |

## 四、Bug 报告

### 知识点6：Bug 报告的 11 个要素

【课程原话/定义】
Bug 报告需要包含以下要素：Bug 编号、所属产品、发现的版本、所属模块、提交人、错误类型、复现概率、严重级别、优先级、标题、内容描述（测试环境、前提条件、复现步骤、预期结果、实际结果）、附件（截图、log、测试数据）。

【为什么？**
Bug 报告是你和开发之间唯一的沟通载体。开发没有坐在你旁边看你操作，他只能通过报告来理解问题。一份好的 Bug 报告让开发 5 分钟定位问题；一份差的报告让开发花 2 小时也复现不了 → 被退回 → 你再补充 → 时间翻倍。

【必须掌握】11 个要素按重要性排序：

| 要素 | 为什么重要 | 常见错误 |
|------|-----------|----------|
| **标题** | 开发第一眼看到的东西，决定了会不会优先看你的 Bug | "支付有问题" ← 太模糊；"iOS端微信支付成功后订单状态未更新" ← 清晰 |
| **复现步骤** | 开发照着操作就能重现 | 跳步、缺少前提条件、没写具体数据 |
| **预期结果 vs 实际结果** | 这是 Bug 判定的核心 | 只写实际没写预期，开发不知道你想要什么 |
| **测试环境** | 不同环境表现不同 | 没写浏览器版本/操作系统/APP版本 |
| **附件** | 一图胜千言 | 没截图就没法证明 Bug 真的存在 |
| 复现概率 | 必现 vs 偶发 处理优先级不同 | 偶发 Bug 不标概率，开发直接退回 |
| 严重级别/优先级 | 决定修复顺序 | 标错等级（见 Ch02） |

【企业场景】
> 好的 Bug 标题 = 开发看到标题就知道大概在哪改。对比：
> - 差的："首页加载慢"
> - 好的："Android端首页Banner图加载耗时超过5s，WiFi和4G均复现"
>
> 差的标题让开发猜，好的标题让开发直接定位。标题写得好，Bug 被优先处理的概率高 50%。

【面试考察】
面试官问："一份好的 Bug 报告应该怎么写？"
参考回答：7 字口诀——**"别人能看懂，自己能复现"**。具体来说：
1. 标题：模块 + 场景 + 现象（"iOS-微信支付-成功后订单未更新"）
2. 环境：设备型号 + OS版本 + APP版本 + 网络环境
3. 前提条件：需要什么前置状态（已登录、已加购、有余额）
4. 复现步骤：1→2→3，每一步可操作
5. 预期结果 vs 实际结果：对比写
6. 附件：截图/录屏/抓包/log

### 知识点7：Bug 报告的协作价值

【课程原话/定义】
好的 Bug 报告可以提高研发修改缺陷的速度、提高测试部门的信用度、增强测试和研发部门的协作。Bug 报告写的好，测试人员信誉度和产品贡献度也会很好提升。

【为什么？**
Bug 报告不只是工具——它是测试工程师的"专业名片"。开发通过你的 Bug 报告判断你的水平：
- 报告清晰、证据完整 → "这个测试靠谱，她提的 Bug 我优先看"
- 报告模糊、没有截图 → "又是她，上次提的那个我复现不了，等有空再看"

测试工程师的专业度，一半体现在用例设计，一半体现在 Bug 报告。

【必须掌握】
- Bug 报告 = 你的专业名片
- 核心标准：别人能独立复现，不依赖你的口头解释
