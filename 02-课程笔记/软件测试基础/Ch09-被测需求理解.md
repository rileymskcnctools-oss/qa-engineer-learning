## 一、什么是被测需求理解

### 【课程定义】

> 被测需求理解是对软件系统需求的深入分析和理解，确保测试团队对系统需求有清晰且一致的认识，从而设计出有效的测试用例和策略。

### 【为什么需求理解是测试的起点？】

测试的本质是"对比实际结果和预期结果"。预期结果从哪来？需求文档。

需求理解错了 → 预期结果就错了 → 所有测试白做。这是测试的第一个环节，也是最重要的环节——后面的所有工作（写用例、执行、提Bug）都建立在需求理解之上。

### 【必须掌握】五大价值

| 价值 | 对你的意义 |
|------|-----------|
| 提高测试质量 | 需求理解到位，用例才能写到点子上 |
| 避免需求遗漏 | PM没写的、写模糊的，你来发现 |
| 增强需求追踪性 | 每个用例都能追溯到需求文档的哪一条 |
| 减少沟通成本 | 需求评审时一次性搞清楚，比测到一半再问强 |
| 提高项目成功率 | 需求阶段发现的问题修复成本最低 |

> 图片位置

### 2.5 第四章：非功能性需求

> 面试中容易被忽略的板块。测试只关注功能 = 不专业。

| 需求类型 | 内容 | 测试对应做什么 |
|---------|------|--------------|
| 性能需求 | 响应时间、并发量 | "500人同时下单，响应时间<2秒" → 压测 |
| 测试环境需求 | 硬件、软件、网络条件 | 环境不满足 → 有些测试做不了 |
| 数据统计需求 | 埋点、报表 | 数据统计的准确性测试 |
| 安全性需求 | 权限控制、数据加密 | SQL注入、XSS、越权测试 |
| 兼容性需求 | OS、浏览器、分辨率 | "支持iOS 14+，Android 10+" |

> 图片位置 × 5（性能、环境、数据统计、安全、兼容性各一）

#### 【面试考察】

> 面试官："除了功能测试，你们还关注哪些方面？"

**参考回答框架：** 根据需求的非功能性部分，我们还会做性能测试（并发场景下的响应时间）、兼容性测试（不同OS/浏览器）、安全测试（权限校验、数据加密）。这些测试的依据同样是需求文档——需求写了"支持500并发"就要测到500，写了"兼容iOS14+"就要在iOS14上测。

## 三、需求评审

### 【课程定义】

> 需求评审是团队成员的集体审查，识别和修复需求文档中的问题，确保需求准确、清晰、完整、可行。

> ![[02-课程笔记/软件测试基础/images/Pasted image 20260702153520.png]]

### 【为什么测试必须参加需求评审？】

不参加需求评审 = PM写什么你测什么。问题是PM可能写漏、写错、写模糊。你在评审时提一个问题，可能省掉开发3天返工 + 测试2天重测。

### 【必须掌握】测试在需求评审中的三个关注点

| 关注点 | 问什么 | 举例 |
|--------|--------|------|
| 完整性 | 有没有遗漏的场景？ | "微信登录失败的回调处理写了，支付宝登录失败的呢？" |
| 清晰性 | 有没有模糊的表述？ | "'系统响应快'——快是多快？能给出具体数值吗？" |
| 可测试性 | 能不能测试？ | "'推荐算法应智能推荐'——什么叫智能？怎么验证？" |

### 【企业场景】

> 需求评审会上，PM说"用户可以邀请好友加入团队"。
>
> 你举手问：
> 1. 被邀请的人需要注册吗？
> 2. 邀请链接有效期多久？过期了怎么办？
> 3. 已经在一个团队的人能被邀请到另一个吗？
> 4. 最多邀请多少人？
>
> 这4个问题PM当场答不出来 → 需求回去改。如果评审时你没问，开发做完了你来测，发现一堆undefined behavior → 你和开发吵架 → 找PM → PM说"嗯...这个场景没考虑过" → 返工。

## 四、需求分析（测试视角）

> 需求评审是审文档，需求分析是把文档变成你的测试策略。

### 【必须掌握】六大分析维度

| 维度 | 做什么 | 产出 |
|------|--------|------|
| 明确测试范围 | 圈定哪些需求要测、哪些不测 | 测试范围列表 |
| 明确功能点 | 拆解每个需求包含哪些功能点 | 功能点清单 |
| 明确业务流程 | 梳理正常流程+分支流程+异常流程 | 业务流程图/脑图 |
| 明确输出结果 | 每个操作的预期结果是什么 | 预期结果列表 |
| 分析异常流程 | 出错了怎么办？超时了怎么办？ | 异常场景清单 |
| 预估时间和资源 | 测完需要多少人、多长时间 | 测试工作量评估 |

### 4.1 明确测试范围

| 问自己 | 举例 |
|--------|------|
| 本次迭代改了哪些模块？ | "本期改登录、支付，不动商品模块" |
| 哪些是核心功能必须测？ | "支付是核心链路，100%覆盖" |
| 哪些可以少测或不测？ | "帮助中心文案修改，看一眼就行" |

### 4.2 明确功能点

不要看一遍需求就觉得自己理解了。拿笔拆：

```
需求："用户可以查看订单列表"
拆解：
  - 有订单时显示订单列表
  - 无订单时显示空状态
  - 订单按时间倒序排列
  - 支持分页加载
  - 支持按状态筛选（待支付/已支付/已取消）
  - 网络异常时显示错误提示
```

一个需求拆出6个功能点 → 6个测试场景。

### 4.3 明确业务流程

画流程图，标注每个节点的测试场景：

```
[开始] → [选择商品] → [加入购物车] → [去结算]
                                            ↓
                              ┌─ 正常支付成功 → [订单页]
                              │
                   [选择支付方式] ── 支付超时 → [订单待支付]
                              │
                              └─ 余额不足 → [提示充值]
```

分支 = 测试场景。一个分支没测 = 漏测。

### 4.4 明确输出结果

每个操作必须对应一个明确的预期结果：

| 操作 | 预期结果 |
|------|---------|
| 正确账号+正确密码 | 登录成功，跳转首页 |
| 正确账号+错误密码 | 提示"密码错误"，留在登录页 |
| 空账号+任意密码 | 提示"请输入账号" |
| 连续输错5次 | 账号锁定15分钟 |

预期结果不明确 = 无法判断对错 = 这个用例没意义。

### 4.5 分析异常流程

> 面试高发题："你怎么设计异常场景的测试用例？"

| 异常类型 | 举例 |
|---------|------|
| 网络异常 | 提交订单时断网 |
| 服务超时 | 支付接口超时30秒 |
| 数据异常 | 商品库存突然变成负数 |
| 并发冲突 | 最后一件库存，两个人同时下单 |
| 用户异常操作 | 支付过程中按返回键、切后台、杀进程 |

### 4.6 预估时间和资源

| 考虑 | 问题 |
|------|------|
| 人力 | 几个测试？全职还是兼职？ |
| 时间 | 开发几天提测？留给测试几天？ |
| 环境 | 测试环境够不够？需要额外申请吗？ |
| 数据 | 测试数据准备好了吗？需要开发配合造数据吗？ |
