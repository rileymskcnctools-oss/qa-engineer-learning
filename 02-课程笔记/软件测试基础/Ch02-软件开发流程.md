## 一、什么是软件

### 课程定义

> 与计算机系统操作有关的计算机程序、可能有的文件、文档及数据。

### 【为什么测试要理解软件的定义？】

软件 ≠ 代码。软件 = 程序 + 文档 + 数据。这意味着：

- 文档错了也是Bug（你在Ch01已经学过了）
- 数据错了也是Bug
- 不只是测程序，文档和数据也要测

## 二、软件开发流程的演变

> 📷 课程截图：开发流程演变图

### 【必须掌握】三种模型一句话对比

| 模型 | 核心理念 | 一句话理解 |
|------|----------|-----------|
| 瀑布模型 | 线性顺序，做完一步再做下一步 | "全部想好了再做" |
| 敏捷模型 | 迭代增量，小步快跑 | "想一点做一点，边做边改" |
| DevOps | 开发运维一体化，持续交付 | "做好了立刻上线" |

### 【面试考察】

> 面试官："说一下瀑布和敏捷的区别？"

**参考回答框架：** 瀑布是线性的，需求→设计→编码→测试→维护，每个阶段完成后进入下一阶段，适合需求稳定的项目。敏捷是迭代的，把大项目拆成多个小迭代，每个迭代都交付可运行的软件，适合需求频繁变化的项目。关键区别：瀑布里测试是独立的后期阶段，敏捷里测试贯穿每个迭代。

## 三、瀑布模型（Waterfall Model）

### 课程定义

> 开发过程通过设计一系列阶段顺序展开，从系统需求分析开始直到产品发布和维护。每个阶段产生循环反馈，项目开发进程从一个阶段"流动"到下一个阶段，就像瀑布一样。

> 📷 课程截图：瀑布模型阶段图

### 【必须掌握】瀑布模型的7个阶段

```
需求分析 → 设计 → 编码 → 实现 → 软件测试 → 完成 → 维护
```

| 阶段 | 做什么 | 产出 | 谁的职责 |
|------|--------|------|----------|
| 需求分析 | 收集用户需求，明确功能和性能 | 需求规格说明书（SRS） | 产品经理 + 需求分析师 |
| 设计 | 系统架构、模块设计、UI设计 | 系统设计文档、详细设计文档 | 架构师 + 设计师 |
| 编码 | 按设计写代码，完成单元测试 | 代码 + 单元测试文档 | 开发工程师 |
| 实现 | 集成各模块，部署到测试环境，集成测试 | 集成测试文档、配置文档 | 开发 + 测试 |
| 软件测试 | 多维度测试，发现和修复缺陷 | 测试计划、测试用例、缺陷报告 | 测试工程师 |
| 完成 | 交付给用户，提供文档和培训 | 用户手册、部署手册、培训材料 | 全员 |
| 维护 | 修复线上Bug，优化性能，版本迭代 | 维护日志、需求变更说明书 | 运维 + 开发 |

### 【为什么瀑布叫"瀑布"？】

水从高处往下流，不会倒流。瀑布模型也一样——做完需求才能设计，做完设计才能编码，不能跳步，也很难回头。

### 【必须掌握】瀑布模型的优缺点

| 优点 | 缺点 |
|------|------|
| 阶段清晰，分工明确 | 线性开发，风险高 |
| 强调早期计划和需求 | 早期错误到后期才能发现 |
| 适合需求稳定的项目 | 不适合需求频繁变化的项目 |

### 【企业场景】什么时候还用瀑布？

不是所有公司都用敏捷。以下场景瀑布仍然常见：

- 政府项目（需求在合同里写死了，不能变）
- 银行核心系统（稳定压倒一切，不允许"迭代试错"）
- 嵌入式/硬件相关（硬件变更成本巨高，必须前期定死需求）

### 【易错点】瀑布模型中测试的位置

瀑布模型里测试在编码之后才正式介入。这导致一个致命问题：需求阶段的Bug，到了编码阶段才发现，返工成本是发现阶段的500倍。

**这就是为什么后面出现了V模型、敏捷模型——都是为了解决"测试介入太晚"的问题。**

## 四、敏捷开发模型（Agile）

### 核心理念

> 以用户的需求进化为核心，采用迭代、循序渐进的方法。把一个大项目分为多个相互联系又可独立运行的小项目，分别完成。软件一直处于可使用状态。

### 【为什么会有敏捷？】

瀑布的问题：需求定死了 → 开发了半年 → 做出来用户说"不是我想要的" → 全白干。

敏捷的解法：每两周交付一个能用的版本 → 给用户看 → 用户说"这里不对" → 下个迭代改 → 方向始终不会跑偏。

### 4.1 XP - 极限编程（Extreme Programming）

> 1996年 Kent Beck 提出，适用于小团队开发。

> 📷 课程截图：XP实践全景图

### 【必须掌握】XP四大实践领域

#### 领域一：编程方法

| 实践 | 含义 | 测试工程师要关注什么 |
|------|------|-------------------|
| 简单设计 | 只实现当前需要的功能，不做过度设计 | 过度设计 = 多余代码 = 多余测试工作量 |
| 结对编程 | 两人共写一份代码，一人写一人审 | 审查本身就是在做"静态测试" |
| 测试驱动开发（TDD） | 先写测试，再写代码 | **这是测试工程师的核心技能之一** |
| 重构 | 持续优化代码结构，消除重复 | 重构后必须回归测试，确认功能没被破坏 |

#### 领域二：小组实践

| 实践 | 含义 |
|------|------|
| 代码集体所有 | 任何人都可以修改任何代码，不做知识孤岛 |
| 编码标准 | 统一编码规范，代码像一个人写的 |
| 稳定高速的步伐 | 保持节奏，避免996式赶工 |
| 持续集成 | 频繁合并代码，每次合并自动构建+测试 |
| 隐喻 | 用比喻让非技术人员理解系统（比如"购物车"就是隐喻） |

#### 领域三：交付与管理

| 实践 | 含义 |
|------|------|
| 小规模发布 | 频繁发布增量版本，降低单次发布风险 |
| 计划游戏 | 分发布计划（长期）和迭代计划（短期）|
| 完整的团队 | 开发+测试+设计+客户代表，所有角色在一个团队 |
| 现场客户 | 客户持续参与，随时获取反馈 |

### 【面试考察】

> 面试官："TDD是什么？你在项目中用过吗？"

**参考回答框架：** TDD = Test-Driven Development，测试驱动开发。流程是：先写一个失败的测试 → 写最少的代码让测试通过 → 重构代码。核心思想是用测试来驱动代码设计，而不是先写代码再补测试。TDD保证每一个功能都有对应的测试覆盖。

### 4.2 SCRUM

> Scrum 是迭代式增量软件开发过程，是敏捷方法论中最常用的框架。

> 📷 课程截图：SCRUM循环迭代流程图

### 【必须掌握】SCRUM三大角色

| 角色 | 英文 | 职责 | 不等于 |
|------|------|------|--------|
| 产品负责人 | Product Owner（PO） | 定义需求、排优先级、接受/拒绝交付 | 不是老板 |
| Scrum主管 | Scrum Master（SM） | 保障Scrum流程、清除障碍、保护团队 | 不是项目经理 |
| 开发团队 | Development Team | 自组织完成开发+测试+交付 | 包含测试工程师 |

### 【必须掌握】SCRUM迭代流程

```
产品BACKLOG → Sprint计划会议 → Sprint BACKLOG → 迭代执行 → 迭代评审 → 迭代回顾 → 下一迭代
```

| 环节 | 做什么 | 频率 |
|------|--------|------|
| 产品BACKLOG | PO维护需求清单，排优先级 | 持续更新 |
| Sprint计划会议 | PO+团队确定本次迭代目标和待办项 | 每次迭代开始时 |
| Sprint BACKLOG | 本次迭代的具体任务清单 | 一次迭代 |
| 迭代执行 | 团队自组织完成开发+测试（通常1-4周） | 每天站会同步 |
| 迭代评审 | 演示完成的功能，收集反馈 | 每次迭代结束时 |
| 迭代回顾 | 团队反思：什么做得好、什么可以改进 | 每次迭代结束时 |

### 【企业场景】测试工程师在SCRUM中的一天

```
09:00  每日站会（15分钟）：
      "昨天测了登录模块，发现2个Bug已提交。
       今天计划测支付模块，阻塞项是无测试环境账号。"

09:15  拉开发对齐Bug
10:00  执行测试用例
14:00  Sprint Backlog上认领新的测试任务
16:00  写自动化脚本（为下次迭代做准备）
17:30  更新Bug状态
```

### 【敏捷总结】

| 核心 | 一句话 |
|------|--------|
| 增量迭代 | 每次只做一点，持续交付 |
| 小步快跑 | 两周一个版本，快速验证想法 |

## 五、DevOps

### 课程定义

> DevOps = Development + Operations，将开发、运维与测试结合，形成一体化的软件开发管理模式。

> 📷 课程截图：DevOps生命周期图

### 【为什么会有DevOps？】

传统模式的问题：

```
开发写完代码 → 丢给测试 → 测试完丢给运维 → 运维部署
```

每个环节之间是"扔过墙"式的交接。运维说"你代码有问题"、开发说"是你环境配错了"——互相扯皮。

DevOps解法：开发+测试+运维在同一个流程里，用自动化工具串联，没人能推卸责任。

### 【必须掌握】DevOps生命周期的5个持续

| 阶段 | 做什么 | 测试在哪 |
|------|--------|----------|
| 持续开发 | 持续编写和提交代码 | 代码提交时触发静态分析 |
| 持续测试 | 每个阶段自动化测试 | **测试工程师的核心战场** |
| 持续集成 | 代码合并后自动构建+测试 | 自动化测试脚本在这里跑 |
| 持续部署 | 测试通过后自动部署到生产环境 | 测试不通过 = 部署阻塞 |
| 持续监控 | 实时监控线上系统 | 线上Bug通过监控发现，反馈给开发 |

> 📷 课程截图：DevOps对发布的影响

### 【企业场景】DevOps对测试的3个变化

| 传统测试 | DevOps中的测试 |
|----------|---------------|
| 测试是独立阶段 | 测试是持续活动 |
| 手工测试为主 | 自动化测试为主 |
| 测试只对开发阶段的代码负责 | 测试对从提交到上线的全过程负责 |

### 【面试考察】

> 面试官："DevOps中测试工程师的角色有什么变化？"

**参考回答框架：** 在传统模式中，测试是独立阶段，等开发完成了才开始测。DevOps中测试贯穿整个流程：提交代码时自动跑单元测试、合并代码时自动跑集成测试、部署前跑端到端测试、上线后做线上监控和回归。测试工程师的产出从"测试报告"变成了"自动化测试流水线"。

## 六、CI/CD

### 【必须掌握】CI 和 CD 的定义

| 概念 | 全称 | 含义 | 通俗理解 |
|------|------|------|----------|
| CI | 持续集成（Continuous Integration） | 频繁合并代码，自动构建和测试 | "代码合进来先自动跑一遍测试，跑不过不让合" |
| CD | 持续交付（Continuous Delivery） | 让软件随时可以发布 | "任何时候点一个按钮就能上线" |

### CI/CD 流程（企业标准）

```
开发提交代码 → 自动构建 → 自动跑单元测试 → 自动跑集成测试 → 部署到测试环境
                                                              ↓
                                                    人工确认 → 部署到生产环境
```

### 【易错点】CI ≠ 每天合代码就可以了

很多人以为 CI 就是"代码经常合并"。真正的 CI 要求：

1. 每次合并触发自动构建
2. 构建后自动跑测试
3. 测试不通过 → 阻止合并 → 通知开发 → 立刻修复

**没有自动化测试的 CI 是假 CI。**

### 【必须掌握】CD 与 DevOps 的关系

| | CD（持续交付） | DevOps |
|------|------|------|
| 范围 | 自动化交付手段 | 整个软件交付的文化和协作方式 |
| 关注点 | 构建→测试→部署自动化 | 开发+测试+运维协作 |
| 关系 | CD 是 DevOps 的自动化实现 | DevOps 是 CD 的上层理念 |

> DevOps 是"道"，CD 是"术"。
