## 一、什么是测试流程体系

### 【课程定义】

> 测试流程体系是在软件开发生命周期中，为确保软件质量而定义的一系列系统化和标准化的测试活动、方法、工具和管理流程。

### 【为什么需要流程体系？】

没有流程的测试 = 想到什么测什么 = 漏测。流程体系解决三个问题：

| 问题      | 流程怎么解决             |
| ------- | ------------------ |
| 不知道测什么  | 需求分析 → 测试计划 → 明确范围 |
| 不知道怎么测  | 测试设计 → 测试用例 → 有章可循 |
| 测完不知道结果 | Bug管理 → 测试报告 → 可追溯 |

### 【必须掌握】测试流程体系五大价值

| 价值      | 一句话            |
| ------- | -------------- |
| 提高软件质量  | 规范流程 → 减少漏测    |
| 降低开发成本  | 早发现Bug → 修复成本低 |
| 提高开发效率  | 有流程 → 不返工、不扯皮  |
| 提升团队能力  | 流程标准化 → 新人上手快  |
| 提高客户满意度 | 质量稳定 → 用户信任    |

### 【我的理解】

## 二、软件测试模型：V → W → H

> 三个模型不是孤立的，是一个演进过程——每一步解决前一步的问题。

### 2.1 V模型

#### 【课程定义】

> V模型是瀑布模型的改进，左右两边组成V字形。左边是开发阶段（需求分析→概要设计→详细设计→编码），右边是对应的测试阶段（单元测试→集成测试→系统测试→验收测试）。每个开发阶段对应一个测试阶段。
![[02-课程笔记/软件测试基础/images/Pasted image 20260702114258.png]]
#### 【为什么V模型比瀑布好？】

瀑布里测试是开发的最后一个环节。V模型的改进：**把测试提前到和开发并行**——需求分析时就在准备验收测试，详细设计时就在准备单元测试。不是"开发完了再测"，而是"一边开发一边准备测试"。

#### 【必须掌握】V模型阶段对应关系

```
开发侧（左）              测试侧（右）
需求分析      ←————————→  验收测试
概要设计      ←————————→  系统测试
详细设计      ←————————→  集成测试
编码         ←————————→  单元测试
```

| 开发阶段 | 做什么        | 对应测试阶段 | 测试做什么      |
| ---- | ---------- | ------ | ---------- |
| 需求分析 | 收集需求，产出SRS | 验收测试   | 验证是否满足用户需求 |
| 概要设计 | 系统架构，模块划分  | 系统测试   | 验证整个系统功能   |
| 详细设计 | 模块内部逻辑、接口  | 集成测试   | 验证模块间交互    |
| 编码   | 写代码        | 单元测试   | 验证单个模块/函数  |

#### 【必须掌握】V模型优缺点

| 优点            | 缺点                |
| ------------- | ----------------- |
| 底层测试+高层测试都有覆盖 | 容易误解为"测试在开发之后"    |
| 开发阶段清楚，便于控制过程 | 编码完成后发现的Bug难以定位根源 |
| 每个阶段有明确产出     | 需求变更大时返工量大        |

#### 【易错点】V模型 ≠ 测试在开发之后

V模型强调的是**对应关系**，不是顺序关系。但实际执行中，很多人把它用成了"开发全部完成 → 然后从单元测到验收"——这就退化成了瀑布。

### 2.2 W模型

#### 【课程定义】

> W模型是V模型的扩展，由两个V组成（开发V + 测试V），明确表示测试与开发的并行关系。测试贯穿整个软件生命周期，测试对象不只是程序，需求和设计同样要测试。
![[02-课程笔记/软件测试基础/images/Pasted image 20260702114236.png]]
#### 【为什么需要W模型？】

V模型的问题：虽然测试对应了开发阶段，但实际测试活动还是在开发完成之后才执行。W模型的解法：**开发活动进行的同时，测试活动也在同步进行**——需求分析的同时测试就在做需求评审，设计的同时测试就在做设计评审。

#### 【必须掌握】W模型的"双V"结构

```
开发V：需求分析 → 概要设计 → 详细设计 → 编码
         ↑                        ↑
测试V：需求评审 → 概要设计评审 → 详细设计评审 → 单元测试
         ↓                        ↓
      系统测试设计              集成测试设计
```

#### 【必须掌握】W模型优缺点

| 优点                | 缺点                  |
| ----------------- | ------------------- |
| 测试贯穿整个生命周期，不只是测代码 | 不支持迭代开发模型           |
| 更早介入，更早发现缺陷       | 对没有文档的项目无法使用        |
| 测试与开发独立并行         | 对需求/设计的测试技术要求高，实践困难 |

#### 【易错点】W模型 vs V模型一句话区分

| V模型          | W模型           |
| ------------ | ------------- |
| 测试**对应**开发阶段 | 测试**和**开发同步进行 |
| 测试在开发完成后再执行  | 测试在开发过程中就执行   |

#### 【我的理解】

### 2.3 H模型

#### 【课程定义】

> H模型将测试活动完全独立出来，形成独立的流程。将测试准备活动和测试执行活动清晰分离。测试在该模式下完成三部分工作：测试前期准备、测试就绪点预判、测试执行。

#### 【为什么需要H模型？】

V和W都假设开发和测试是分阶段串行的。现实中，需求、设计、编码是交叉迭代的。H模型的解法：**测试不依赖开发阶段，什么时候条件满足了什么时候开始测。**
![[02-课程笔记/软件测试基础/images/Pasted image 20260702114415.png]]
#### 【必须掌握】H模型三个核心工作

| 阶段      | 做什么                 | 举例                 |
| ------- | ------------------- | ------------------ |
| 测试前期准备  | 写测试计划、设计测试用例、准备测试数据 | 需求评审结束就开始写用例       |
| 测试就绪点预判 | 判断什么时候可以开始测         | "接口文档已发布→可以开始接口测试" |
| 测试执行    | 执行测试、提交Bug、回归验证     | 条件满足立刻执行，不等"测试阶段"  |

#### 【必须掌握】H模型优缺点

| 优点               | 缺点        |
| ---------------- | --------- |
| 测试完全独立，与其他流程并发   | 测试就绪点分析困难 |
| 可尽早准备、尽早执行，灵活性最强 | 对团队人员要求高  |

#### 【面试考察】三模型对比

> 面试官："说一下V模型、W模型、H模型的区别和演进逻辑？"

**参考回答框架：**

| 维度     | V模型    | W模型         | H模型       |
| ------ | ------ | ----------- | --------- |
| 核心理念   | 测试对应开发 | 测试并行开发      | 测试独立于开发   |
| 测试介入时机 | 开发完成后  | 开发过程中       | 条件满足就介入   |
| 灵活性    | 低      | 中           | 高         |
| 演进解决什么 | 瀑布测试太晚 | V模型测试还在开发之后 | W模型假设阶段串行 |

#### 【我的理解】

## 三、传统测试流程：6个阶段

> 从开发到上线，测试工作依次经过6个阶段。每个阶段的目标、执行人、关注点不同。

### 【必须掌握】6阶段全览

| 阶段 | 英文 | 测什么 | 谁来做 | 目标 |
|------|------|--------|--------|------|
| 单元测试 | Unit Test | 单个函数/方法 | 开发工程师 | 验证独立功能正确 |
| 集成测试 | Integration Test | 模块间接口和交互 | 开发 + 测试 | 发现集成问题 |
| 冒烟测试 | Smoke Test | 核心基本功能 | 测试工程师 | 确认版本是否可测 |
| 系统测试 | System Test | 整个系统全面测试 | 测试工程师 | 验证满足需求 |
| 回归测试 | Regression Test | 修改影响范围 | 测试工程师 | 确保修改不引入新Bug |
| 验收测试 | Acceptance Test | 业务需求 | 用户/客户 | 确认可交付 |

### 【为什么是这个顺序？】

```
单元测试（最小粒度，确保零件合格）
  → 集成测试（组装，确保零件能配合）
    → 冒烟测试（快速检查核心功能，不合格就打回）
      → 系统测试（全面深入测试）
        → 回归测试（改了代码后确认没坏原来好的）
          → 验收测试（用户说OK才上线）
```

每一层是下一层的基础。单元都没过就做系统测试 = 浪费时间。

---

### 3.1 单元测试

#### 【必须掌握】

- 测试最小可测单元（一个函数/方法）
- 由开发人员编写和执行
- 使用框架：JUnit / pytest / unittest
- 通常是自动化测试

### 3.2 集成测试

#### 【必须掌握】

- 测试模块之间的接口和交互
- 两种策略：增量集成（逐步加模块） vs 大爆炸集成（一次全加）
- 企业中通常是测试和开发共同负责

#### 【易错点】增量集成 vs 大爆炸集成

| 策略 | 方法 | 优点 | 缺点 |
|------|------|------|------|
| 增量集成 | 逐个模块加入测试 | 问题好定位 | 速度慢 |
| 大爆炸集成 | 所有模块一次集成 | 速度快 | 出问题难定位 |

### 3.3 冒烟测试

#### 【必须掌握】

- 每次构建后的第一轮测试
- 只测核心功能，范围小
- 目标：快速确认版本是否稳定（"通电不冒烟"）
- 冒烟不通过 → 版本打回，不做后续测试

#### 【企业场景】

> 你每天早上来，CI已经跑完了昨天的代码提交。第一件事：跑一遍冒烟用例（登录、下单、支付三个核心流程，10分钟）。通过了——今天可以测新功能。没通过——群里@开发，版本打回。

### 3.4 系统测试

#### 【必须掌握】

- 在整个系统上做全面测试
- 包括：功能测试、性能测试、安全测试、兼容性测试
- 是测试工程师最核心的工作阶段
- 在所有测试类型中覆盖面最广

### 3.5 回归测试

#### 【必须掌握】

- 软件修改/更新后执行
- 确认新版本没有引入新缺陷
- 确认之前修复的问题没有重新出现
- 通常使用自动化测试工具
- 覆盖面要广，不能只测修改的部分

#### 【易错点】冒烟测试 vs 回归测试

| 维度 | 冒烟测试 | 回归测试 |
|------|---------|---------|
| 时机 | 每次构建后 | 每次代码修改后 |
| 范围 | 核心功能，范围小 | 影响范围+关联功能，范围大 |
| 深度 | 浅，快速验证 | 深入验证 |
| 目的 | 确认"能不能测" | 确认"有没有坏" |
| 频率 | 每日多次 | 每次发版/修复后 |

### 3.6 验收测试

#### 【必须掌握】

- 由最终用户/客户执行
- 验证是否满足业务需求
- 两种形式：
  - Alpha测试：内部用户，可控环境
  - Beta测试：外部用户，真实环境
- 是开发和测试的最后阶段

#### 【易错点】Alpha vs Beta 测试

| 维度 | Alpha测试 | Beta测试 |
|------|----------|----------|
| 谁测 | 内部用户 | 外部真实用户 |
| 环境 | 开发/测试环境 | 生产环境 |
| 可控性 | 高 | 低 |
| 目的 | 发现明显缺陷 | 收集真实使用反馈 |

#### 【我的理解】

>

## 四、系统测试流程：从需求到发布

> 这是你在企业中最常参与的完整测试工作流程。

### 【必须掌握】7个环节

| 环节 | 做什么 | 产出 | 你的职责 |
|------|--------|------|---------|
| 需求分析 | 理解需求，明确测试范围 | 需求分析文档 | 参与需求评审，提出测试关注点 |
| 测试计划 | 制定测试策略、分派任务 | 测试计划文档 | 明确"测什么、怎么测、谁测、多久" |
| 测试设计 | 编写测试用例、准备数据 | 测试用例文档、测试数据 | 写用例、准备环境 |
| 用例评审 | 评审测试用例 | 评审记录 | 和开发/PM确认用例合理 |
| 测试执行 | 执行用例，记录结果 | 测试结果、Bug报告 | 执行测试、提交Bug |
| Bug管理 | 跟踪和验证缺陷 | Bug状态记录 | 跟踪修复、回归验证 |
| 发布维护 | 上线、监控、收集反馈 | 发布文档 | 确认上线质量 |

#### 【企业场景】

> 入职后你接手的第一个需求，大概率是：
> 1. 产品发你PRD → 你读需求（需求分析）
> 2. 你写测试用例 → 拉开发评审（测试设计 → 用例评审）
> 3. 开发提测 → 你执行用例（测试执行）
> 4. 发现Bug → 提交Jira（Bug管理）
> 5. 开发修复 → 你回归验证（Bug管理循环）
> 6. 上线 → 你在线上做一轮验证（发布维护）

## 五、Bug管理流程

### 【必须掌握】Bug生命周期

```
     测试发现Bug
         ↓
    [New] 新建
         ↓ 开发确认
    [Open] 打开/确认
         ↓ 开发修复
    [Fixed] 已修复
         ↓ 测试回归验证
    [Close] 关闭     或    [Reopen] 重新打开（验证不通过）
```

| 状态 | 含义 | 谁操作 |
|------|------|--------|
| New | 测试刚提交的Bug | 测试工程师 |
| Open | 开发确认确实是Bug | 开发工程师 |
| Fixed | 开发已修复，等待验证 | 开发工程师 |
| Close | 测试验证通过，关闭 | 测试工程师 |
| Reopen | 验证不通过，重新打开 | 测试工程师 |
| Rejected | 开发认为不是Bug | 开发工程师 |

#### 【企业场景】Rejected 怎么处理？

> 开发把Bug标记为Rejected，理由是"需求就是这样设计的"。你不是直接Reopen，而是：
> 1. 查需求文档——有依据就截图回复
> 2. 拉PM确认——需求文档没写清楚就找PM
> 3. 依据明确 → Reopen。依据不明 → 接受Rejected，更新需求文档
>
> Bug争论的唯一裁判是需求文档，不是"我觉得"。

#### 【易错点】Severity vs Priority

> 面试高频题，必背！

| 维度 | Severity（严重程度） | Priority（优先级） |
|------|---------------------|-------------------|
| 关注什么 | Bug对系统的影响有多大 | Bug应该多快被修复 |
| 谁来定 | 测试工程师 | PM/PO + 测试 |
| 级别 | S1-致命, S2-严重, S3-一般, S4-建议 | P0-立刻修, P1-本迭代, P2-下迭代, P3- backlog |
| 举例 | 支付金额算错（S1致命） | 按钮颜色不对但功能正常（P3） |

面试金句：**"Severity高 Priority不一定高。一个严重影响用户体验但只出现在特定机型上的Bug，Severity高但Priority可能低。反之，一个文案错误出现在首页，Severity低但Priority高。"**

## 六、测试左移 & 测试右移

### 【为什么会有左右移？】

传统测试的困局：测试只在开发完成后的那个阶段 → Bug发现晚 → 修复成本高 → 线上还是出问题。

左移：往前挪 → 在Bug还没产生的时候就预防它。
右移：往后挪 → 上线了继续监控，出问题立刻知道。

### 【必须掌握】左移 vs 右移

| 维度 | 测试左移 | 测试右移 |
|------|---------|---------|
| 方向 | 往开发阶段移 | 往上线之后移 |
| 时机 | 开发早期就介入 | 产品上线后继续监控 |
| 核心思维 | 从"发现Bug"到"预防Bug" | 从"测完不管"到"线上追踪" |
| 目标 | 尽早发现问题 | 及时发现线上问题 |

### 【必须掌握】左移的5种质量保障手段

| 手段 | 谁来做 | 做什么 |
|------|--------|--------|
| 代码评审（Code Review） | 开发 | 检查代码质量、逻辑、规范 |
| 代码审计 | 独立团队/工具 | 检查安全漏洞、性能、合规 |
| 单元测试 | 开发 | 自动化验证每个函数 |
| 自动化冒烟测试 | 测试 | CI中每次提交自动跑核心用例 |
| 研发自测 | 开发 | 提交前自测功能 |

### 【必须掌握】右移的监控手段

| 手段 | 目的 |
|------|------|
| 线上问题闭环 | 发现→反馈→修复→验证的完整流程 |
| 日志回传 | 线上出问题能快速定位 |
| 业务监控 | 例如短信发送成功率、支付成功率 |
| 关键指标每日监控 | 服务器CPU、内存、QPS |
| 生产数据监控 | 异常数据自动告警 |

#### 【面试考察】

> 面试官："说一下测试左移和测试右移？你们项目里怎么做的？"

**参考回答框架：** 左移是把测试活动提前到开发阶段，目的是预防Bug。我们项目里通过Code Review、研发自测、CI自动跑冒烟用例来实现。右移是上线后继续监控，通过日志监控、业务指标告警来发现线上问题，形成发现-反馈-修复的闭环。传统的测试边界在"开发完成→上线"这个区间，左移右移把边界扩展到了整个软件生命周期。
