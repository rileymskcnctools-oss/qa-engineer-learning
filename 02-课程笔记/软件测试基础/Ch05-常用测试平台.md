## 一、什么是测试平台

### 【课程定义】

> 软件测试平台是为测试阶段提供支持的工具和环境，可以自动化测试过程、管理测试用例、跟踪缺陷、生成测试报告。

### 【为什么需要测试平台？】

没有平台 = 用例写在Excel里、Bug用嘴说、代码不知道谁改了。平台解决四个问题：

| 没有平台         | 有平台          |
| ------------ | ------------ |
| 用例散落各人电脑     | 统一管理，谁都能看    |
| Bug口头传达，忘了就没 | 系统追踪，有状态有记录  |
| 不知道改了哪些代码    | 版本管理，每次变更可追溯 |
| 手工重复操作       | CI自动构建+自动测试  |

### 【必须掌握】测试平台五大价值

| 价值 | 一句话 |
|------|--------|
| 提高测试效率 | 自动化替代重复劳动 |
| 提升测试质量 | 不遗漏、可追溯 |
| 降低成本 | Bug早发现 = 修复成本低 |
| 提高协作 | 开发+测试+PM在同一平台沟通 |
| 保障进度 | 任务状态透明，谁在做什么一目了然 |

## 二、四大平台全景图

> 企业里测试工程师每天打交道的四类平台。

| 平台类型   | 管什么         | 核心工具               | 面试怎么问        |
| ------ | ----------- | ------------------ | ------------ |
| 测试用例管理 | 用例的创建、执行、追踪 | Jira, TestLink, 禅道 | "你们用什么管用例？"  |
| Bug管理  | 缺陷的生命周期     | Jira, Redmine, 禅道  | 和用例平台通常一致    |
| 代码管理   | 源代码版本控制     | GitLab, GitHub     | "用过Git吗？"    |
| 持续集成   | 自动构建+自动测试   | Jenkins, GitLab CI | "CI/CD怎么配的？" |

#### 【企业场景】

> 你入职新公司第一天，leader给你开四个账号：Jira（管用例+Bug）+ GitLab（看代码）+ Jenkins（看CI流水线）+ 钉钉/飞书（沟通）。这四个平台就是你的工作台。

## 三、测试用例管理平台

### 3.1 主流方案对比

| 平台                | 特点                  | 适合场景       |
| ----------------- | ------------------- | ---------- |
| **Jira + Xray**   | 最强方案，定制性强，与项目管理无缝集成 | 中大型公司，标准选择 |
| **Redmine**       | 开源免费，功能全面           | 中小团队，预算有限  |
| **TestLink**      | 老牌用例管理，开源           | 传统测试团队     |
| **禅道**            | 国产，项目管理+测试一体化       | 国内中小公司     |
| **TAPD / 云效**     | 腾讯/阿里出品             | 互联网公司      |
| **GitLab Issues** | 代码和Issue一体          | 技术驱动的团队    |
| **Excel / 思维导图**  | 无协作要求时使用            | 个人/小团队快速上手 |

---

### 3.2 Jira + Xray（重点）

#### 【为什么Jira是行业标准？】

Jira本是一个问题追踪工具（Issue Tracker）。测试用例、Bug、需求——在Jira里都是Issue。Xray插件把"测试用例"也变成一种Issue类型，测试和开发在同一个平台协作，不需要切换工具。

#### 【必须掌握】Xray三大能力

| 能力                       | 做什么                  | 面试怎么说                   |
| ------------------------ | -------------------- | ----------------------- |
| Manage Tests as Issues   | 用例=Bug=需求=Issue，统一管理 | "我们用Jira的Issue类型管理测试用例" |
| Plan, Execute, Integrate | 测试计划+执行+集成CI/CD      | "写好用例→关联到测试计划→CI触发执行"   |
| Reports & Coverage       | 需求覆盖率报告、执行进度         | "每个迭代结束跑需求覆盖率分析"        |

#### 【企业场景】

> 一个迭代的标准Jira+Xray流程：
> 1. PM创建需求（Story类型的Issue）
> 2. 你创建测试用例（Test类型的Issue），关联到需求
> 3. 测试计划（Test Plan）里纳入所有用例
> 4. 执行用例（Test Execution），通过→标记Pass，失败→创建Bug Issue
> 5. 迭代结束→跑需求覆盖率报告，看看哪个需求没测到

---

### 3.3 Redmine

#### 【必须掌握】

- 开源项目管理平台，Ruby on Rails开发
- 不只是测试工具，是项目管理+Wiki+文档+讨论+时间追踪一体的平台
- 通过"项目（Project）"组织成员、任务、文档
- 可集成SVN、Git等版本管理工具

---

### 3.4 TestLink

#### 【必须掌握】

- 专注测试管理的开源平台
- 覆盖：测试需求→测试设计→测试执行→结果统计
- 功能专一但界面较老旧
- 老牌工具，部分传统企业仍在使用

#### 【易错点】TestLink vs Jira+Xray

| 维度 | TestLink | Jira + Xray |
|------|----------|------------|
| 定位 | 纯测试管理 | 测试+项目管理 |
| 与开发协作 | 需要切工具 | 同一平台 |
| 学习成本 | 低 | 中 |
| 目前趋势 | 越来越少 | 行业主流 |

## 四、Bug管理平台

#### 【必须掌握】Bug管理 = 用例管理

企业中Bug管理平台通常和用例管理是同一套。原因很简单：

- Bug和用例在Jira里都是Issue，可以互相引用
- 一个用例执行失败 → 直接创建关联Bug
- Bug修复后 → 回归测试同一个用例

#### 【核心能力】

| 能力 | 说明 |
|------|------|
| Issue表达 | 用例和Bug都用统一的Issue格式 |
| 关联关系 | Bug关联到用例，用例关联到需求 |
| 属性定制 | Severity、Priority、环境、复现步骤等字段 |

## 五、代码管理平台

### 5.1 主流方案对比

| 平台                  | 特点               | 现状            |
| ------------------- | ---------------- | ------------- |
| **GitLab**          | 可本地部署，CI/CD内置    | **企业首选，推荐方案** |
| **GitHub**          | 开源社区最大           | 开源项目首选        |
| **Bitbucket**       | 与Jira同属Atlassian | 配合Jira使用      |
| **SVN（Subversion）** | 集中式版本管理          | 已过时，但老项目可能碰到  |

### 5.2 GitLab（重点）

#### 【必须掌握】

| 概念          | 说明                   |
| ----------- | -------------------- |
| Group（群组）   | 管理多个项目，一个部门一个Group   |
| Project（项目） | 一个代码仓库               |
| Branch（分支）  | 主分支开发，特性分支独立开发，完成后合并 |

#### 【为什么测试要了解GitLab？】

1. 看代码变更：开发改了哪些文件 → 判断测试范围
2. CI/CD触发：GitLab Runner + .gitlab-ci.yml → 提交代码自动跑测试
3. Issue管理：有些团队直接用GitLab Issues替代Jira
4. Code Review：开发提MR，测试也要会看

## 六、持续集成管理平台

### 6.1 主流方案对比

| 平台 | 特点 | 适合 |
|------|------|------|
| **Jenkins** | 最老牌，插件生态极大，Java开发 | 所有场景 |
| **GitLab Runner** | 与GitLab深度集成 | 用GitLab的团队 |
| **GitHub Actions** | 与GitHub深度集成 | 开源项目 |
| **自建DevOps平台** | 企业定制（TAPD/云效等） | 大厂 |

### 6.2 Jenkins（重点）

#### 【课程定义】

> Jenkins是基于Java开发的开源持续集成工具，用于监控持续重复的工作，使软件项目可以进行持续集成。

#### 【必须掌握】Jenkins四大角色

| 角色     | 在Jenkins中做什么            |
| ------ | ----------------------- |
| **研发** | 触发构建、跑单元测试、代码覆盖率分析、代码审计 |
| **运维** | 配置自动化部署                 |
| **测试** | 跑接口测试、UI自动化、性能测试、安全测试   |
| **全员** | 构建失败 → 邮件/IM通知 → 谁提交谁修  |

#### 【企业场景】

> 每天的工作从Jenkins开始：
> 1. 打开Jenkins → 看昨晚的构建结果
> 2. 构建是蓝色（成功）→ 开始今天的工作
> 3. 构建是红色（失败）→ 看是谁的提交导致的 → 看测试报告 → 提交Bug
>
> 你写的自动化测试脚本最终都要接入Jenkins，不是在你电脑上跑一遍就完事。

---

### 6.3 CI/CD 各平台核心实践

| 实践    | Jenkins     | GitLab Runner  | GitHub Actions          |
| ----- | ----------- | -------------- | ----------------------- |
| 触发方式  | 定时/Webhook  | .gitlab-ci.yml | .github/workflows/*.yml |
| 配置文件  | Jenkinsfile | .gitlab-ci.yml | YAML                    |
| 插件/市场 | 极丰富         | 内置             | 内置+Marketplace          |
| 学习门槛  | 中高          | 低              | 低                       |

#### 【面试考察】

> 面试官："你们项目用的是什么CI/CD平台？Jenkins是怎么配置的？"

**参考回答框架：** 我们用Jenkins做持续集成。开发提交代码到GitLab → GitLab Webhook触发Jenkins → Jenkins拉代码→构建→跑单元测试→跑接口自动化→生成测试报告→通知结果。配置文件用Jenkinsfile，放在代码仓库根目录，Pipeline分阶段执行。测试的自动化脚本在"Test"阶段执行，失败了会阻塞后续部署。
