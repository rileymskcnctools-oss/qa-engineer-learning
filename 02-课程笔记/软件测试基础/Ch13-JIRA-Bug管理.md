## 一、JIRA 管理 Bug 的基础配置

### 知识点1：Bug 管理需要配置什么

【课程原话/定义】
想要在 JIRA 中对 Bug 进行管理，需要有 Bug 管理项目，关联 Bug 相关的工作流、界面，界面中包含 Bug 的专有字段。

【为什么？**
JIRA 不是"开箱即用"的 Bug 管理工具——需要先配置再使用。这和 Ch12 的测试用例管理是同一个逻辑：JIRA 的定制性意味着你需要先"搭台"再"唱戏"。

**Bug 管理的 4 个配置要素：**

| 配置项          | 作用                  | Bug 管理场景                                       |
| ------------ | ------------------- | ---------------------------------------------- |
| **Bug 管理项目** | Issue 的容器           | 可以单独建 Bug 项目，也可以和开发项目共用                        |
| **Bug 工作流**  | Bug 的状态流转           | New → Open → Fixed → Closed（+ Rejected/Reopen） |
| **Bug 界面**   | 创建/编辑/查看 Bug 时看到的字段 | 新建 Bug 时需要看到"严重级别""复现概率"等字段                    |
| **Bug 专有字段** | Bug 特有的属性           | 复现概率、严重级别、测试环境、复现步骤、预期/实际结果                    |

【必须掌握】
- 4 个配置要素缺一不可
- Bug 专有字段 = Bug 不同于其他 Issue 类型的字段（测试用例不需要"复现概率"）

【关联】
Bug 工作流的状态流转 = Ch03-Bug处理流程 中讲的 6 状态生命周期，JIRA 把这套流程配置成了 Workflow。

【我的理解】

## 二、在 JIRA 中提 Bug

### 知识点2：Bug 创建的两个入口

【课程原话/定义】
Bug 创建入口有两种：① 从测试用例创建关联问题；② 直接在 Bug 管理项目中提 Bug。

【为什么？**
两种入口对应两种工作场景：

| 入口 | 场景 | 优势 |
|------|------|------|
| **从测试用例创建** | 执行用例时发现 Bug | Bug 自动关联到用例，追溯链条完整 |
| **直接在 Bug 项目提** | 探索式测试/用户反馈/偶发发现 | 快速提交，不依赖用例 |

企业中最常见的是入口①——你正在 JIRA 中执行测试用例，发现结果和预期不一致 → 直接在用例上点"创建关联问题" → 选 Bug 类型 → 自动关联。

【必须掌握】
- 两种入口和使用场景
- 从用例创建 = 自动关联 = 可追溯（推荐）

【企业场景】
> 你在 JIRA 中执行用例 TEST-001"验证支付成功后订单状态更新"，实际结果是订单状态未更新。你点击用例详情页的"关联 Issue"→ 创建 Bug → 系统自动把 Bug 关联到 TEST-001。后续开发修复后，你可以从用例直接看到关联的 Bug 状态——一条完整的追溯链。

【我的理解】

## 三、Bug 报告编写（JIRA 实操版）

> 这部分是 Ch03-Bug处理流程 中"Bug 报告 11 要素"的 JIRA 实操落地。

### 知识点3：Bug 标题格式

【课程原话/定义】
Bug 标题格式：**执行完 A 之后，发生 B**。简明扼要地对 Bug 进行概述，让人看了就知道大概出了什么问题。标题必须简短且描述和传达出准确的信息。

【为什么？**
标题是开发在 Bug 列表中唯一能看到的东西（不点进去的话）。好的标题 = 开发 2 秒判断优先级和归属。

**标题公式：`[模块] 操作 + 现象`**

| 差的标题    | 好的标题                       | 差在哪            |
| ------- | -------------------------- | -------------- |
| "支付有问题" | "微信支付成功后订单状态仍为待支付"         | 没说哪个支付方式、什么现象  |
| "登录报错"  | "iOS端手机号+验证码登录后白屏"         | 没说平台、登录方式、现象   |
| "首页加载慢" | "Android端首页Banner图加载耗时>5s" | 没说平台、哪个元素、量化数据 |

【必须掌握】
- 标题公式：`[平台/模块] 操作 + 具体现象`
- 标题 = 一句话说清楚"在什么情况下发生了什么问题"
- 关键词要精炼，不啰嗦

【企业场景】
> 开发 Leader 每天早上看团队 Bug 列表："今天有 30 个新 Bug，我先扫标题"。你的 Bug 标题是"支付有问题"——他不知道是不是自己模块的，跳过。另一个测试写的是"退款接口-支付宝渠道返回签名错误"——他立刻点进去分配给自己。标题决定了你的 Bug 是被优先处理还是排在最后。

【我的理解】

>

### 知识点4：Bug 属性字段

【课程原话/定义】
Bug 属性：复现概率、严重级别。

【为什么？**
JIRA 中 Bug Issue 有专有字段，这两个是最影响开发排期的：

| 属性 | 为什么重要 | 选项示例 |
|------|-----------|----------|
| **复现概率** | 必现 vs 偶发，处理优先级完全不同 | 必现 / 高(>50%) / 中(20-50%) / 低(<20%) / 仅一次 |
| **严重级别** | 决定了修复紧急度（见 Ch02） | 致命 / 严重 / 一般 / 建议 |

复现概率决定了开发的信心——必现 Bug 开发敢直接修，偶发 Bug 开发会犹豫"是不是环境问题？"

【必须掌握】
- 提交时必填复现概率和严重级别
- 严重级别判断标准见 Ch02-Bug基本概念

【我的理解】

>

### 知识点5：Bug 内容四要素

【课程原话/定义】
Bug 内容：测试环境、复现步骤、预期结果、实际结果。

【为什么？**
这四要素是 Bug 报告的核心——缺任何一个，开发都无法独立复现：

```
测试环境：你用什么测的？
    ↓
复现步骤：你怎么操作的？（1→2→3）
    ↓
预期结果：应该发生什么？
    ↓
实际结果：实际发生了什么？
```

**模板范例（JIRA 中直接复制这个结构）：**

```
【测试环境】
- 设备：iPhone 15 / iOS 18.1
- APP版本：v3.2.1 (build 20260701)
- 网络：WiFi / 中国移动4G
- 账号：test_user_001（已实名认证）

【前提条件】
- 已登录，账户余额 100 元
- 购物车中有 1 件商品（金额 50 元）

【复现步骤】
1. 进入购物车页面
2. 点击"结算"按钮
3. 选择"微信支付"
4. 点击"确认支付"
5. 输入支付密码

【预期结果】
支付成功后，订单状态更新为"待发货"，页面跳转到订单详情

【实际结果】
支付成功（微信扣款成功），但订单状态仍显示"待支付"，页面未跳转
```

【必须掌握】
- 四要素能默写
- 复现步骤用编号 1→2→3，不能跳步
- 预期和实际必须对比写

【企业场景】
> 你写 Bug 报告时的黄金法则：**让一个完全不熟悉这个模块的开发，照着你的步骤能 100% 复现**。如果你自己照着步骤操作一遍都无法复现——说明报告不合格。

【我的理解】

## 四、提 Bug 的注意事项

### 知识点6：提 Bug 的三个原则

【课程原话/定义】
1. **一个 Bug 报告只能描述一个 Bug**：将几个问题写在一个报告中，开发很难发现自己的问题并解决
2. **Bug 的唯一性**：提交前确认这个 Bug 是否已经被其他人发现并报告（搜索功能）
3. **复现**：容易复现的要写全步骤，不能复现的要提供尽可能多的信息（截图、日志、抓包）

【为什么？**
这三条每一条都对应一个常见错误：

| 原则 | 违反的后果 | 你见过的新人错误 |
|------|-----------|-----------------|
| 一个报告一个 Bug | 开发只修了其中 1 个，其他 2 个被忽略 | "提了一个 Bug 说登录页有三个问题" |
| 先查重 | 重复 Bug 浪费开发时间确认 | "没搜直接提，被标记 Duplicated" |
| 尽量复现 | 不可复现 = 开发大概率退回 | "偶发，没截图没 log，开发说 Can't Reproduce" |

【必须掌握】
- 三个原则能默写
- 提 Bug 前的操作顺序：① 查重 → ② 确认能复现 → ③ 截图/录屏 → ④ 提交

【企业场景】
> 你发现一个 Bug，截图+录屏+抓包全搞定，打开 JIRA 准备提交——停！先搜一下。在搜索框输入关键词，发现 3 天前另一个测试已经提过同一个问题，状态是 Open。你不用提了，在已有 Bug 下评论补充你的复现信息。这就是专业测试和业余测试的区别。

【我的理解】

>

### 知识点7：Bug 报告的语言规范

【课程原话/定义】
报告 Bug 时要使用中性语言，不要带有感情色彩。不要带有幽默也不要带有任何不满情绪，尽量考虑研发的情绪。

【为什么？**
Bug 报告不是你发泄情绪的地方。对比：

| ❌ 不应该写 | ✅ 应该写 |
|------------|----------|
| "这个功能又挂了，开发能不能认真点？" | "支付接口返回 500，疑似空指针异常" |
| "这么明显的 Bug 都没发现？" | "预期结果和实际结果不一致，详见下方对比" |
| "终于修好了？呵呵" | "v3.2.2 验证通过，关闭" |

Bug 报告是**技术文档**，不是聊天记录。保持客观、准确、中性——这既是专业度，也是保护你自己（不会因为语气问题引发不必要的冲突）。

【必须掌握】
- Bug 报告 = 技术文档，不是情绪表达
- 只描述事实，不评价人
- Bug 报告中的"你"只能指代操作步骤，不能指代开发人员

【面试考察】
面试官问："Bug 报告中应该注意什么语言规范？"
参考回答：客观描述事实，不带感情色彩。只写"实际结果和预期结果不一致"，不写"开发写错了"。Bug 报告的核心目的是帮助开发快速定位问题，任何情绪化表达都会降低沟通效率。

【我的理解】
