## 一、什么是软件技术体系

### 【课程定义】

> 软件技术体系是在软件开发过程中所使用的各种技术和工具的组合。包括编程语言、开发框架、数据库、服务器、版本控制工具、开发工具以及测试工具等。

### 【为什么测试要了解技术体系？】

你不需要精通所有技术，但需要知道每个环节用什么工具、测试怎么介入：

| 技术栈层级 | 举例                       | 测试关注什么    |
| ----- | ------------------------ | --------- |
| 编程语言  | Python / Java            | 用什么写单元测试  |
| 开发框架  | Spring Boot / Django     | 接口测试怎么调   |
| 数据库   | MySQL / Redis            | 数据怎么验证    |
| 服务器   | Linux / Docker           | 测试环境怎么部署  |
| 版本控制  | Git                      | 代码变更怎么跟踪  |
| CI/CD | Jenkins / GitHub Actions | 自动化测试怎么触发 |

### 【必须掌握】技术体系四大价值

| 价值      | 对你的意义               |
| ------- | ------------------- |
| 提高测试效率  | 选对工具，10分钟做完手工1小时的事  |
| 提高测试质量  | 自动化比人更稳定，不遗漏        |
| 促进团队协作  | 和开发说同一种技术语言         |
| 提高就业竞争力 | 面试不问你"会不会测"，问"用什么测" |

## 三、按开发阶段分类

> Ch03 已经学过，此处只做速查。重点在下面的"系统测试"和"验收测试"子类。

| 阶段   | 测什么   | 谁来做     |
| ---- | ----- | ------- |
| 单元测试 | 函数/方法 | 开发      |
| 集成测试 | 模块间接口 | 开发 + 测试 |
| 系统测试 | 整个系统  | 测试工程师   |
| 验收测试 | 业务需求  | 用户/客户   |

---

### 3.1 系统测试子类（重点）

> 系统测试不只是"功能测试"。面试说"系统测试就是测功能" = 减分。

| 子类    | 测什么            | 面试关键词            |
| ----- | -------------- | ---------------- |
| 功能测试  | 功能是否按需求运行      | 最基本的测试类型         |
| 兼容性测试 | 不同OS/浏览器/设备    | "你们的App适配了多少机型？" |
| 性能测试  | 响应时间、吞吐量、资源使用  | "怎么做压测？"         |
| 安全测试  | SQL注入、XSS、权限漏洞 | "测试怎么保障安全？"      |

#### 【企业场景】

> 功能测试全过了 ≠ 可以上线。你还要回答：
> - "iPhone 8 和 iPhone 15 都测过了吗？"（兼容性）
> - "1000个人同时下单，系统撑得住吗？"（性能）
> - "普通用户能不能访问管理员的功能？"（安全）

### 3.2 验收测试子类

| 子类         | 谁测     | 环境   | 目的       |
| ---------- | ------ | ---- | -------- |
| Alpha（α）测试 | 内部人员   | 开发环境 | 早期发现明显缺陷 |
| Beta（β）测试  | 真实外部用户 | 生产环境 | 收集真实使用反馈 |

#### 【易错点】Alpha vs Beta

| 维度 | Alpha | Beta |
|------|-------|------|
| 用户 | 内部可控 | 外部不可控 |
| 环境 | 测试环境 | 真实环境 |
| 反馈 | 直接和技术沟通 | 通过渠道收集 |
| 风险 | 低 | 高 |

## 四、按是否查看代码分类

> 面试必考三人组：黑盒、白盒、灰盒。

### 4.1 黑盒测试

#### 【课程定义】

> 又称数据驱动测试。完全不考虑程序内部结构和内部特性，只关注输入和输出。测试用例基于需求和功能规格设计。

#### 【为什么叫黑盒？】

把程序当成一个黑色盒子——你看不见里面，只能从外面看：给什么输入 → 出什么输出。

#### 【必须掌握】

| 维度     | 说明                 |
| ------ | ------------------ |
| 关注什么   | 功能需求，不关注代码         |
| 怎么设计用例 | 基于需求文档，等价类、边界值、场景法 |
| 谁来做    | 主要是测试工程师           |
| 属于什么测试 | 系统测试、验收测试通常是黑盒     |

#### 【企业场景】

> 你是测试，开发给了你一个登录页面。你不知道里面的代码怎么写的，你只需要验证：
> - 正确账号密码 → 登录成功
> - 错误密码 → 提示"密码错误"
> - 空账号 → 提示"请输入账号"
>
> 你关注的是"行为对不对"，不是"代码怎么写"。

---

### 4.2 白盒测试

#### 【课程定义】

> 研究产品内部的源代码和程序结构。单元测试就是白盒测试的一种。

#### 【为什么叫白盒？】

盒子是透明的——你看得见里面的代码逻辑，可以针对每个分支、每个路径设计测试。

#### 【必须掌握】

| 维度 | 说明 |
|------|------|
| 关注什么 | 代码内部逻辑、路径覆盖 |
| 怎么设计用例 | 基于代码结构：语句覆盖、分支覆盖、路径覆盖 |
| 谁来做 | 主要是开发工程师 |
| 属于什么测试 | 单元测试通常是白盒 |

#### 【企业场景】

> 开发写了一个计算折扣的函数：VIP用户打8折，普通用户满100打9折。白盒测试要验证：
> - VIP → 能否走到8折分支
> - 普通+满100 → 能否走到9折分支
> - 普通+不满100 → 能否走到原价分支
>
> 你在代码里看到3个if分支，就要确保3条路都走过。

---

### 4.3 灰盒测试

#### 【课程定义】

> 结合黑盒和白盒的方法，了解部分代码内部结构，但主要关注输入和输出。

#### 【为什么有灰盒？】

纯黑盒可能漏掉关键路径，纯白盒成本太高。灰盒是折中——知道大概结构，但不用逐行读代码。

---

### 【面试考察】黑盒 vs 白盒 vs 灰盒

> 面试官："黑盒测试和白盒测试的区别？各举一个例子。"

**参考回答框架：**

| 维度     | 黑盒        | 白盒         | 灰盒              |
| ------ | --------- | ---------- | --------------- |
| 关注点    | 功能（做什么）   | 代码（怎么做）    | 两者结合            |
| 谁来做    | 测试工程师     | 开发工程师      | 测试 + 开发         |
| 基于什么设计 | 需求文档      | 代码结构       | 需求 + 部分代码       |
| 举例     | 测登录功能是否正确 | 测某个函数的分支覆盖 | 测API接口，看返回+查数据库 |

## 五、按执行方式分类

### 【必须掌握】静态测试 vs 动态测试

| 维度     | 静态测试              | 动态测试           |
| ------ | ----------------- | -------------- |
| 是否运行代码 | 不运行               | 运行             |
| 测什么    | 代码、文档、设计          | 功能、性能          |
| 方法     | 代码审查、静态分析、走查、技术评审 | 单元测试、集成测试、系统测试 |
| 发现什么   | 逻辑错误、规范问题、设计缺陷    | 运行时Bug、性能问题    |
| 时机     | 编码阶段              | 编码完成后          |

#### 【企业场景】

> 代码审查（Code Review）就是静态测试的典型应用。开发提交代码前，另一个开发看一遍："你这个if条件漏了空值判断"——这就是在运行代码之前发现了Bug，成本极低。

#### 【易错点】

很多人以为"测试 = 运行程序"。静态测试不需要运行——审查文档、审查代码也是测试，而且成本更低。

## 六、按是否手工执行分类

### 【必须掌握】手工测试 vs 自动化测试

| 维度   | 手工测试             | 自动化测试              |
| ---- | ---------------- | ------------------ |
| 执行者  | 人                | 脚本/工具              |
| 适合场景 | 探索性测试、复杂场景、一次性测试 | 重复性高、回归测试、数据驱动     |
| 优点   | 灵活，能发现意想不到的问题    | 快、稳定、不遗漏、可重复       |
| 缺点   | 慢、易疲劳、易遗漏        | 开发成本高、维护成本高、不适合新功能 |

#### 【易错点】自动化 ≠ 替代手工

自动化做的是"已知场景的重复验证"，手工做的是"未知场景的探索发现"。两者互补，不是替代。

## 七、其他测试分类

> 这些分类在 Ch03 已经学过，此处做对比速查。

| 类型    | 一句话      | 和谁容易混淆 |
| ----- | -------- | ------ |
| 冒烟测试  | 版本能不能用   | 回归测试   |
| 回归测试  | 改了有没有坏   | 冒烟测试   |
| 随机测试  | 随便点，看哪里炸 | 探索性测试  |
| 探索性测试 | 边测边想新用例  | 随机测试   |

### 【易错点】随机测试 vs 探索性测试

| 维度 | 随机测试 | 探索性测试 |
|------|---------|-----------|
| 有策略吗 | 无，随机点 | 有，凭经验和直觉 |
| 有记录吗 | 通常没有 | 有，边测边记 |
| 目的是什么 | 看会不会崩溃 | 发现隐藏的复杂缺陷 |
| 面试怎么说 | "就是乱点"（✗） | "基于经验设计即时测试策略"（✓） |

## 八、自动化分层测试体系（测试金字塔）

> 面试高频。不止要能画出金字塔，还要能解释为什么是这样分层。

### 【必须掌握】三层金字塔

```
        ┌──────┐
        │  UI  │  10%   用户界面测试（Selenium, Appium）
        ├──────┤
        │ 服务  │  20%   接口测试/服务测试（Postman, Requests）
        ├──────┤
        │ 单元  │  70%   单元测试（JUnit, pytest）
        └──────┘
```

### 【为什么是金字塔形状？】

不是随便画的。四个原则决定：

| 原则   | 含义                       |
| ---- | ------------------------ |
| 低层高频 | 单元测试跑得快、成本低 → 多写         |
| 早期测试 | 代码写完立刻跑单元测试 → 尽早发现问题     |
| 全面覆盖 | 每层各司其职，UI测交互、服务测逻辑、单元测函数 |
| 独立原则 | 单元测试不依赖数据库/UI，服务测试不依赖UI  |

### 【必须掌握】三层对比

| 层级   | 占比  | 测什么   | 工具（Python）           | 工具（Java）                | 执行速度 |
| ---- | --- | ----- | -------------------- | ----------------------- | ---- |
| 单元测试 | 70% | 函数/方法 | pytest, unittest     | JUnit, TestNG           | 毫秒级  |
| 服务测试 | 20% | API接口 | Requests, HttpRunner | RestAssured, HttpClient | 秒级   |
| UI测试 | 10% | 用户界面  | Selenium, Appium     | Selenium, Appium        | 分钟级  |

### 【面试考察】

> 面试官："说一下测试金字塔？为什么UI测试最少？"

**参考回答框架：** 测试金字塔从底到顶是单元测试→服务测试→UI测试，比例是7:2:1。UI测试最少的原因是：UI测试最慢、最不稳定（换个按钮就挂了）、维护成本最高。所以要把大部分测试放在最底层（单元测试），跑得最快、最稳定。越往上越少——不是UI不重要，而是用底层的性价比更高。

## 九、三层测试工具全景

### 9.1 单元测试工具

| 语言     | 框架       | 一句话                 |
| ------ | -------- | ------------------- |
| Java   | JUnit    | 最流行的Java单元测试框架      |
| Java   | TestNG   | 功能更强，支持集成测试         |
| Python | unittest | 内建框架，类似JUnit        |
| Python | pytest   | 语法简洁，插件丰富，**面试最常提** |

### 9.2 接口测试工具

| 工具                  | 类型  | 用途                      |
| ------------------- | --- | ----------------------- |
| Postman             | GUI | 设计、测试、文档化API，**新手入门必学** |
| Charles             | 代理  | HTTP流量监控、抓包调试           |
| Fiddler             | 代理  | HTTP调试代理，抓包分析           |
| Jmeter              | 开源  | 接口测试 + 性能测试             |
| LoadRunner          | 企业级 | 性能测试和负载测试               |
| Requests (Python)   | 代码库 | 发HTTP请求，自动化接口测试         |
| HttpRunner (Python) | 框架  | 接口测试 + 自动化              |
| RestAssured (Java)  | 代码库 | RESTful接口测试             |
| HttpClient (Java)   | 代码库 | HTTP请求                  |

### 9.3 UI测试工具

| 工具       | 适用  | 用途                |
| -------- | --- | ----------------- |
| Selenium | Web | 浏览器自动化，**面试最常提**  |
| Appium   | App | Android/iOS移动端自动化 |
