## 一、JIRA 为什么流行

### 知识点1：JIRA 的核心竞争力

【课程原话/定义】
JIRA 是目前比较流行的测试管理系统，大厂更爱用 JIRA，因为它的定制性非常强——可以自己定义流程、界面、字段。各种插件也非常丰富。测试工作中的测试用例和 Bug 都可以用 JIRA 去跟踪管理。

【为什么？**
JIRA 不是专门的测试工具，是通用项目管理工具。但正是因为它"通用 + 可定制"，反而比专用测试平台更灵活：
- 禅道：固定流程，适合中小企业
- JIRA：自定义流程，适合大厂的复杂业务

大厂选择 JIRA 的核心原因就一个词：**定制性**。每个团队的工作流不一样，JIRA 允许你配出自己的流程，而不是让团队去适应工具。

【必须掌握】
- JIRA 的优势：定制性强（流程/字段/界面/插件）
- JIRA ≠ 测试工具，JIRA = 通用项目管理工具 + 测试用例管理 + Bug 管理

【企业场景】
> 你们团队的测试流程是"需求评审 → 用例设计 → 用例评审 → 执行 → Bug 跟踪"，另一个团队是"直接写用例 → 执行 → 提 Bug"。两个团队在 JIRA 里可以配两套完全不同的 Workflow——同一工具，不同流程。这就是 JIRA 被大厂选中的原因。

【关联】
Ch06 已覆盖 JIRA 的五大价值和基础概念全览，本章聚焦**测试用例管理**实操。

## 二、JIRA 使用者与角色

### 知识点2：谁在用 JIRA

【课程原话/定义】
凡是参与到项目中的人都可以使用 JIRA，不同角色使用的功能有差异，可以通过设置权限去分别。角色包括：管理者、项目经理、产品、开发、测试。

【为什么？**
理解角色分工的意义：JIRA 是一个跨角色的协作平台，不是测试的专属工具。

| 角色 | 在 JIRA 中主要做什么 |
|------|---------------------|
| **测试** | 创建测试用例 Issue、执行用例、提交 Bug、跟踪 Bug 状态 |
| **开发** | 查看分配给自己的 Bug、标记修复状态、关联代码提交 |
| **产品/PM** | 创建需求 Issue、排优先级、确认 Bug 处理意见 |
| **项目经理** | 配置项目、定义 Workflow、分配任务、看进度报表 |
| **管理者** | 查看全局报表、资源分配、流程审批 |

【必须掌握】
- JIRA 是跨角色协作平台
- 测试在 JIRA 中的核心操作：用例管理 + Bug 管理

## 三、JIRA 五大基础概念

> 以下概念在 Ch06 中已详细展开，这里聚焦**与测试用例管理相关的部分**。

### 知识点3：Project（项目）

【课程原话/定义】
Project 项目是 Issue 问题的容器。

【为什么？**
在 JIRA 中做测试用例管理，第一步是创建项目。项目类型决定了默认的 Workflow 和 Issue 类型。

**测试用例管理通常的做法：**
- 创建独立的"测试用例管理"项目，和"开发项目"分开
- 或者在开发项目中启用"测试用例"类型的 Issue

【必须掌握】
- 项目 = 顶层容器，所有 Issue 都在项目里
- 创建项目时选择类型 → 决定了默认 Workflow

【我的理解】

### 知识点4：Issue（问题）

【课程原话/定义】
Issue 是 JIRA 核心中的核心，用来管理各项事务。可以直接使用系统内置的 Issue 类型，也可以自己创建新的问题类型。

【为什么？**
在 JIRA 中，测试用例也是一种 Issue。你可以创建自定义 Issue 类型叫"测试用例"——和 Bug、Task、Story 平级。

**常见的 Issue 类型：**
| Issue 类型 | 用途 |
|------------|------|
| Epic | 大功能模块 |
| Story | 用户故事（需求） |
| Task | 开发任务 |
| Bug | 缺陷 |
| **Test Case** | **测试用例（自定义）** |
| Sub-task | 子任务 |

【企业场景】
> 你的团队在 JIRA 中这样用 Issue 类型：PM 创建 Story → 开发创建 Task 关联到 Story → 测试创建 Test Case 关联到 Story → 发现 Bug 就创建 Bug Issue 关联到 Story 或 Test Case。所有东西都在一个项目里，关联关系清晰可追溯。

### 知识点5：Field（字段）

【课程原话/定义】
要描述一个问题，会通过各种属性来进行：名称、详细描述、提交人、提交时间、优先级、状态等等。这些属性就是 Field 字段。系统已定义好常用字段，也可以创建自定义字段。

【为什么？**
测试用例在 JIRA 中需要哪些字段？——比普通 Issue 更多：

| 字段   | 说明          |
| ---- | ----------- |
| 标题   | 用例名称        |
| 描述   | 前置条件 + 测试步骤 |
| 预期结果 | 期望的输出       |
| 优先级  | 用例优先级       |
| 所属模块 | 功能模块        |
| 测试数据 | 需要的测试数据     |
| 关联需求 | 链接到 Story   |

这些字段大部分是**自定义字段**——这是 JIRA 定制性的体现。

【我的理解】

>

### 知识点6：Workflow（工作流）

【课程原话/定义】
Workflow 工作流描述 Issue 的状态和状态转换。由两部分组成：**Status（状态）** 和 **Transition（转换动作）**。从一种状态切换到另一种状态必须借助 Transition。JIRA 提供方便的配置项，可以自动生成 Transition。

【为什么？**
这是 JIRA 最强大的功能——你可以自定义测试用例的"生命周期"。

**测试用例的典型 Workflow：**
```
[Draft] 草稿 —→ [Ready] 待评审 —→ [Approved] 已通过 —→ [Executed] 已执行
                                                    ↓
                                              [Deprecated] 已废弃
```

Status = 节点（如 Draft/Ready/Approved）
Transition = 节点间的连线（如"提交评审"是从 Draft 到 Ready 的 Transition）

【面试考察】
面试官问："JIRA 的 Workflow 由什么组成？"
参考回答：由 Status（状态）和 Transition（转换动作）两部分组成。Status 是 Issue 所处的阶段（如待办、进行中、已完成），Transition 是连接两个 Status 的动作（如"开始处理"是从待办到进行中的 Transition）。

【易错点】

| 容易混淆 | Status（状态） | Transition（转换） |
|----------|:----------:|:----------:|
| 是什么 | Issue 当前所处的阶段 | 连接两个阶段的操作 |
| 类比 | 地铁站 | 地铁线路 |
| 举例 | 待办、进行中、已完成 | 开始处理、提交评审、关闭 |

【我的理解】

### 知识点7：Screen（界面/视图）

【课程原话/定义】
Screen 视图用来展示 Issue 的字段。对于一个 Issue，新建、编辑、查看详情时需要看到不同的字段。所以通过"新建视图"、"编辑视图"、"详情视图"三种视图分别展示。不同的问题类型可以自定义不同视图。

【为什么？**
测试用例的创建视图和 Bug 的创建视图应该不同——测试用例需要"前置条件"和"测试步骤"字段，而 Bug 需要"复现步骤"和"实际结果"字段。JIRA 允许你为不同 Issue 类型配置不同 Screen，这正是定制性的体现。

| 视图类型 | 什么时候出现 | 测试用例场景 |
|----------|-------------|-------------|
| 新建视图 | 创建 Issue 时 | 填写用例标题、步骤、预期结果 |
| 编辑视图 | 修改 Issue 时 | 更新用例内容 |
| 详情视图 | 查看 Issue 时 | 查看完整用例信息 + 执行记录 |

## 四、JIRA 管理测试用例实操

### 知识点8：完整流程 5 步骤

【课程原话/定义】
流程：创建测试用例管理项目 → 设置测试用例管理项目 → 进入项目 → 填写测试用例内容 → 执行测试用例。

【为什么？**
这 5 步是 JIRA 测试用例管理的最小闭环。每一步对应一个具体操作：

| 步骤     | 操作                             | 关键配置                           |
| ------ | ------------------------------ | ------------------------------ |
| ① 创建项目 | 新建 Project，选择"测试用例管理"类型        | 项目名称、Key（如 TEST）               |
| ② 设置项目 | 配置 Issue 类型、Workflow、字段、Screen | 自定义 Test Case 类型 + Workflow    |
| ③ 进入项目 | 进入项目主页，看到 Issue 列表             | 按模块/版本筛选                       |
| ④ 填写用例 | 创建 Test Case Issue，填写各字段       | 标题、步骤、预期结果、优先级、模块              |
| ⑤ 执行用例 | 执行后更新 Issue 状态 + 记录结果          | 通过 → 标记完成；失败 → 创建 Bug Issue 关联 |

【企业场景】
> 入职第一周，mentor 说："在 JIRA 的 TEST 项目里创建一个 Test Case，关联到 Story-1234，写完发我 review。"你打开 JIRA → 进 TEST 项目 → 点 Create → 选 Issue Type = Test Case → 填标题/步骤/预期结果 → Link 到 Story-1234 → 状态 Draft → 指派给 mentor。这就是你每天要做的事。

### 知识点9：项目设置详解

【课程原话/定义】
项目设置包含：详情、问题类型、工作流、版本、模块、界面、域。

【为什么？**
这些设置项是项目经理/管理员配置的，但测试需要理解每个配置的含义——因为你的工作流是这些配置驱动的。

| 设置项 | 作用 | 对测试的影响 |
|--------|------|-------------|
| 问题类型 | 项目中有哪些 Issue 类型 | 你能创建 Test Case / Bug / Task |
| 工作流 | Issue 状态的流转规则 | 你的用例从 Draft 到 Done 必须走哪些状态 |
| 版本 | 软件版本号 | 用例关联到哪个版本 |
| 模块 | 系统功能模块 | 用例归属于哪个模块 |
| 界面 | 不同 Issue 类型的展示字段 | 创建用例时看到哪些输入框 |
| 域 | 自定义字段 | 用例是否需要额外字段（如"测试数据"） |
