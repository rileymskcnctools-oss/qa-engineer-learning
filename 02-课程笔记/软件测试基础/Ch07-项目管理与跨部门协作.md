## 一、为什么测试要学项目管理？

### 【课程定义】

> 软件工程项目管理是对软件开发项目进行规划、组织、指导和控制，以实现项目目标的过程。跨部门沟通协作涉及开发、测试、产品、运营等不同部门之间的有效沟通和协调。

### 【为什么？】

测试不是孤立的技术活。你是项目中的一环，需要：

- 知道项目走到哪一步了（需求？开发？提测？）
- 知道什么时候该做什么事（需求阶段你就该看文档了，不是等提测）
- 知道和谁沟通（产品管需求、开发管实现、运维管环境）
- 知道怎么推动问题解决（Bug不是提了就完了，要跟进到关闭）

不懂项目管理的测试 = 只会执行用例的工具人。懂项目管理的测试 = 能独立负责一个迭代的测试Owner。

### 【必须掌握】十大价值速查

| 价值      | 对你的意义                  |
| ------- | ---------------------- |
| 提高项目成功率 | 测试介入越早，项目越不容易延期        |
| 优化资源使用  | 知道什么时候忙什么时候闲，提前安排      |
| 增强决策能力  | 敢于说"这个版本质量达不到上线标准"     |
| 提升团队协作  | 和产品、开发不是对立关系           |
| 促进信息共享  | 你发现的Bug信息，开发要知道，PM也要知道 |
| 提高工作效率  | 按流程走，不返工               |
| 解决冲突    | Bug是需求还是缺陷？知道找谁裁决      |
| 增强协调性   | 上下游测试环境、数据、接口对齐        |
| 提升个人能力  | 从执行者→测试Owner的跃迁        |

## 二、软件项目全流程

### 【必须掌握】七大阶段

```
项目立项 → 产品定义 → 软件开发 → 软件测试 → 内部验收 → 用户验收 → 系统维护
```

| 阶段   | 做什么           | 测试在做什么        | 产出         |
| ---- | ------------- | ------------- | ---------- |
| 项目立项 | 确定目标，可行性研究，批准 | 了解项目背景        | 项目章程       |
| 产品定义 | 收集需求，编写SRS    | 参与需求评审，提测试关注点 | 需求规格说明书    |
| 软件开发 | 设计→编码→单元测试    | 写测试计划、测试用例    | 代码 + 单元测试  |
| 软件测试 | 执行测试，发现和修复缺陷  | **你的主场**      | 测试报告、Bug记录 |
| 内部验收 | 内部评审，确认达标     | 参与评审，提供测试数据   | 评审报告       |
| 用户验收 | 用户培训，验收测试     | 协助用户验收        | 验收报告       |
| 系统维护 | 处理线上故障，升级，监控  | 线上问题复现、回归测试   | 维护日志       |

#### 【企业场景】

> 你接手一个全新的需求，心里要有这张时间线：
>
> 需求评审时 → 你在，挑需求漏洞
> 开发写代码时 → 你在，写测试用例
> 开发提测时 → 你是主力，执行测试
> 上线前 → 你出测试报告，说能不能上
> 上线后 → 你监控，出问题第一个排查
>
> 不是你只在"软件测试"阶段才上班。前面的Ch03学的测试左移就是这个意思。

## 三、软件项目开发的五个核心阶段

> 每个阶段都有"门"，测试是守门人之一。

### 3.1 需求分析阶段

| 角色     | 做什么                |
| ------ | ------------------ |
| PM     | 收集需求，写PRD          |
| 开发     | 评估技术可行性            |
| **测试** | 理解需求、识别漏洞、提出可测试性建议 |

#### 【测试在需求阶段的核心价值】

> 需求说"用户可以修改个人信息"，你没问"哪些信息可以改？修改后是否需要验证？"——等到开发做完了，你说这不对，返工成本100倍。

### 3.2 设计阶段

| 角色 | 做什么 |
|------|--------|
| 架构师/开发 | 系统架构、接口设计、数据库设计 |
| **测试** | 审接口文档、确认测试策略、准备测试数据 |

### 3.3 开发阶段

| 角色 | 做什么 |
|------|--------|
| 开发 | 编码 + 单元测试 |
| **测试** | 编写测试用例、准备测试环境、写自动化脚本 |

### 3.4 集成测试阶段

| 角色 | 做什么 |
|------|--------|
| 开发 + 测试 | 模块联调、接口测试、集成测试 |
| **测试** | 验证模块间交互、提交Bug |

### 3.5 系统测试阶段

| 角色     | 做什么                |
| ------ | ------------------ |
| **测试** | 功能、性能、兼容性、安全——全面测试 |
| 开发     | 修复Bug              |

## 四、项目管理方法四步法

### 【必须掌握】

```
制定计划 → 执行监控 → 风险应对 → 项目收尾
```

| 步骤 | 核心动作 | 测试要做什么 |
|------|---------|------------|
| 制定计划 | 定义目标、时间表、资源 | 评估测试工作量："这个需求我需要3天测完" |
| 执行监控 | 跟踪进度，调整计划 | 每天更新测试进度，发现阻塞立刻上报 |
| 风险应对 | 识别风险，制定策略 | "提测时间可能延期2天，测试时间被压缩"→提前预警 |
| 项目收尾 | 交付、验收、归档、总结经验 | 出测试报告、归档用例、总结踩过的坑 |

#### 【面试考察】

> 面试官："项目延期了，测试时间被压缩了一半，你怎么办？"

**参考回答框架：** 第一步做风险评估——哪些功能必须测、哪些可以降级。第二步和PM/开发沟通——明确上线范围，高风险模块优先保障。第三步调整测试策略——核心功能全量测试，边缘功能做冒烟，非关键UI做抽查。第四步上线后加强监控——被砍掉的测试在上线后用线上监控补。

## 五、跨部门沟通协作

> 这部分是面试中的"软技能"考核重点。技术可以学，沟通能力是区分初级和高级测试的分水岭。

### 5.1 与产品（PM）沟通

#### 【四个阶段，四个沟通重点】

| 阶段 | 沟通什么 | 典型对话 |
|------|---------|---------|
| 需求评审会 | 确认需求、排优先级 | "这个功能的异常流程需求里没写，用户输错了怎么办？" |
| 分析需求阶段 | 深挖业务逻辑、识别漏洞 | "这个优惠券可以和满减叠加吗？需求里没说" |
| 用例编写阶段 | 确认用例覆盖 | "这三个场景我写了用例，你看看有没有遗漏的？" |
| 测试过程中 | 同步Bug，确认修复方案 | "支付失败这个Bug，产品你觉得优先级怎么定？" |

#### 【为什么产品是测试的盟友？】

开发和测试容易对立（你找Bug=你挑他毛病）。但有PM在中间：Bug的裁判不是你觉得也不是开发觉得，是需求文档。PM是需求文档的作者，他是最终裁判。

---

### 5.2 与研发（开发）沟通

#### 【四个阶段，四个沟通重点】

| 阶段 | 沟通什么 | 典型对话 |
|------|---------|---------|
| 需求分析阶段 | 技术可行性、实现细节 | "这个功能后端接口什么时候能给？我这边需要提前准备测试数据" |
| 用例编写阶段 | 确认测试重点 | "这个支付模块你最担心哪个环节？我重点测" |
| 测试过程中 | 提交Bug、复现步骤 | "你这个Bug我录了屏，步骤在描述里，你看看能复现吗" |
| 线上发现Bug | 紧急通知、协助定位 | "线上支付回调超时，日志我发你了，帮我看看是不是刚才那个发布引起的" |

#### 【企业场景】和开发沟通的三个坑

| 坑 | 错误做法 | 正确做法 |
|----|---------|---------|
| 提Bug像吵架 | "你写的什么垃圾代码" | "发现一个问题，具体现象是XX，步骤是XX，你帮忙看看" |
| Bug说不清楚 | "登录有问题" | "iOS Safari下，微信授权登录后白屏，录屏附件" |
| 被Rejected就放弃 | "哦好的" | 查需求文档→有依据就Reopen→没依据找PM |

---

### 5.3 上下游测试配合

#### 【三大维度】

| 维度     | 做什么          | 为什么重要                      |
| ------ | ------------ | -------------------------- |
| 测试计划沟通 | 对齐时间、范围、目标   | 避免上游测完了下游还没开始，或者重复测同一块     |
| 环境对接   | 协调测试环境，数据同步  | 环境不一致=你的Bug开发复现不了=白测       |
| 熟悉业务   | 了解上下游系统的业务逻辑 | 你测下单，但支付是另一个系统，你得知道支付的回调逻辑 |

#### 【企业场景】

> 你在测电商App的下单功能。下单后要调支付系统、库存系统、物流系统。你只测了下单没测支付回调 → 上线后支付成功了但订单状态还是"待付款" → 线上事故。
>
> 这就是上下游测试配合：你知道支付系统怎么回调、库存系统怎么扣减，你才能写出覆盖全链路的测试用例。

---

### 5.4 跨部门协作速查矩阵

| 问题 | 找谁 | 什么阶段 |
|------|------|---------|
| 需求不清楚 | PM | 需求分析/测试执行 |
| 需求前后矛盾 | PM | 需求评审 |
| 代码逻辑问题 | 开发 | 测试执行 |
| Bug无法复现 | 开发 | 测试执行 |
| 环境问题 | 运维/开发 | 测试执行 |
| 上线标准 | PM + 开发Leader | 测试收尾 |
| 线上故障 | 开发 + 运维 | 上线后 |
| 上下游数据不一致 | 上下游测试 | 集成测试 |

## 六、项目实例（实战框架）

> 课程给了项目实例截图，这里整理成一个通用框架，任何项目都能套。

### 一个标准迭代的测试工作全景

| 时间节点 | 阶段 | 测试做什么 | 和谁协作 |
|---------|------|-----------|---------|
| D-5 | 需求评审 | 审PRD，提问题 | PM |
| D-3 | 需求确认 | 理解业务逻辑，评估测试工时 | PM + 开发 |
| D-1 | 用例编写 | 写测试用例，准备测试数据 | PM 确认用例 |
| D-Day | 开发启动 | 开始写自动化脚本 | 开发对齐接口 |
| D+5 | 用例评审 | 拉开发/PM评审用例 | 开发 + PM |
| D+10 | 开发提测 | 跑冒烟，确认版本可测 | 开发 |
| D+10~15 | 测试执行 | 执行用例，提交Bug，回归 | 开发修Bug |
| D+16 | 测试报告 | 出测试报告，判断是否可上线 | PM + 开发Leader |
| D+17 | 上线 | 线上验证 + 监控 | 运维 + 开发 |
| D+18~ | 线上监控 | 关注用户反馈和告警 | 开发 + 运维 |
