## 一、Web 端 Bug 分类全貌

### 【课程原话/定义】

> Web 端测试中发现的 Bug 包含页面布局方面、页面元素方面、功能方面等等。

### 【为什么？】

Bug 分类不只是为了归档——分类决定了你的**测试优先级和排查方向**。布局 Bug 通常是 CSS 问题（前端改），功能 Bug 可能是前后端交互问题（需要联调），JS 报错需要区分是网络、代码还是兼容性。**见到 Bug 不急着提，先分类 → 再定位 → 然后才提缺陷单。分类能力是测试人员从执行者到分析者的分水岭。**

### 【必须掌握】

4 大类 Bug 的识别和初步定位方法。

### 【面试考察】

> "你在 Web 测试中最常遇到哪几类 Bug？怎么区分优先级？"
>
> 参考回答：按 4 类回答（布局/元素/功能/其他），每类举例 + 说明什么情况下是 Blocker（如功能主流程不通）、什么情况下是 Minor（如 UI 文字偏了 1px）。

### 【易错点】

| 易混淆 | 区别 |
|--------|------|
| 布局 Bug vs 兼容性 Bug | 布局 Bug 是"所有浏览器都错乱"（代码问题）；兼容性 Bug 是"Chrome 正常 IE 错乱"（浏览器差异） |
| 前端 JS 报错 vs 后端报错 | JS 报错看浏览器 Console；后端报错看 Network 面板的响应状态码和 Response Body |

## 二、页面布局方面 Bug

### 2.1 页面内容超长展示错乱

#### 【课程原话/定义】

> 页面一行内容超长展示错乱。这种情况一般是需要自己造数据进行验证的。前面学习用例设计的时候就说过，页面展示的时候需要根据长度的边界值去设计用例进行验证。如果出现问题——出现滚动条、内容被遮盖——需要修改，比如折行展示或超出部分用"..."。

> 图片位置（超长内容导致布局错乱示例）

#### 【为什么？】

开发自测时通常用"正常长度"的数据（比如"张三"、"测试商品"），但真实用户会输入各种长度的内容——有人昵称 20 个字，有人商品标题 100 个字。**布局 Bug 的根源是开发只考虑了"理想数据"，没考虑"极端数据"。**

#### 【必须掌握】

超长内容的 3 种处理方案及各自的测试验证点：
- **折行**：折行后行高是否正常、是否影响相邻元素
- **截断 + "..."**：hover 是否有 title/tooltip 显示完整内容
- **滚动条**：滚动条是否只在必要区域出现、是否影响整体页面布局

#### 【企业场景】

> 你测一个商品列表页，商品名称需求说"不超过 50 个字符"。你用 50 个"哈"造了一条数据——发现商品名称把价格和"加入购物车"按钮挤到屏幕外面了。开发说"谁会起这么长的名字"。你回："运营导入第三方商品数据时，供应商就起了这么长。"——测试就是用极端数据帮开发看见盲区。

#### 【易错点】

| 常见遗漏 | 补充 |
|---------|------|
| 只测中文超长 | 英文超长（无空格长单词如 supercalifragilisticexpialidocious）比中文更容易撑破布局 |
| 超长内容在响应式布局下 | 桌面端正常 + 缩小到手机端后超长内容是否仍然正常 |

### 2.2 更换设备布局错乱

#### 【课程原话/定义】

> 这一类问题一般出现在兼容测试中。Web 产品需要在各种系统的各种版本的不同浏览器上运行。PC 端、手机端、Win/Mac/Linux/Android/iOS，这些设备上各种版本的浏览器内核和特性有区别，导致页面展示错乱。

> 图片位置（页面右侧显示不全示例）

#### 【为什么？】

不同浏览器的渲染引擎不同：Chrome 用 Blink、Firefox 用 Gecko、Safari 用 WebKit、IE 用 Trident。同一个 CSS 属性在不同引擎中的默认值、支持程度可能不同。**兼容性 Bug 不是"测不测"的问题，而是"测哪些"的问题——资源有限，必须按用户数据排优先级。**

#### 【必须掌握】

兼容性 Bug 的排查步骤：① 确认浏览器版本；② F12 看 Console 是否有 CSS 相关报错；③ 检查是否使用了该浏览器不支持的 CSS 属性（caniuse.com 查询）。

#### 【企业场景】

> 老板说"咱们页面在客户那显示不对"。你问"客户用什么浏览器？"——"不知道"。你先查线上埋点数据：用户浏览器分布 Chrome 78%、Safari 12%、Firefox 6%、IE 2%、其他 2%。你在 IE 上复现了问题，评估了修复成本和受影响用户量（2%），把决策权交给产品经理：修还是不修？

#### 【易错点】

| 误区 | 正解 |
|------|------|
| 每个浏览器版本都测一遍 | 数据驱动——优先测用户占比最高的浏览器和版本 |
| CSS 前缀只写 -webkit- | 有些属性还需要 -moz-（Firefox）、-ms-（IE/旧 Edge） |
| 手机端用 Chrome 模拟器测了就完 | 模拟器 ≠ 真机。iOS Safari 和 Chrome 的行为差异模拟器不一定能还原 |

## 三、页面元素方面 Bug

### 3.1 输入域提示信息不明确

#### 【课程原话/定义】

> 属于界面方面的问题。比如注册界面，注册密码的要求没有明确说明，用户全部输入完成后点击注册，才得到密码不符合要求的提示，用户体验很差。输入框需要先说明清楚输入内容的规则。

> 图片位置（注册界面密码要求不明确示例）

#### 【为什么？】

这不是"功能错了"——功能逻辑上"校验不通过"是对的——但**信息呈现的时机和方式错了**。用户填了 5 分钟表单点提交，弹一个"密码必须包含大小写字母"——这种体验叫"惩罚性设计"。正确的做法是**事前告知 + 实时校验**。

#### 【必须掌握】

输入域提示的 3 个设计原则：① 事前说明规则（placeholder 或输入框旁文字）；② 实时校验反馈（输入时即校验，不要等提交）；③ 错误提示明确具体（不是"输入不合法"，而是"密码需包含至少 1 个大写字母"）。

#### 【企业场景】

> 你测一个注册页，密码要求是"8-16 位，含大小写字母+数字"。界面上没有任何提示。你提 Bug："用户体验缺陷——密码规则未在界面展示，建议在输入框下方灰字标注规则，并在用户输入时实时显示满足条件的状态（长度✅、大写❌、数字✅）。

#### 【面试考察】

> "你发现一个界面提示信息不清晰，应该怎么提 Bug？"
>
> 参考回答：① 描述现状（当前提示是什么、出现在什么时机）；② 描述影响（用户会怎么误解、可能导致什么操作错误）；③ 给建议方案（不强制，但体现你的产品思维）。重点：这是用户体验类 Bug，严重程度一般是 Minor-Major，不是 Blocker。

#### 【易错点】

| 常见误区 | 正确认知 |
|---------|---------|
| "提示不清晰"不是 Bug 是建议 | 如果提示信息误导用户执行了错误操作，就是 Bug（如"删除后不可恢复"写成了"删除后可恢复"） |
| 只提问题不给建议 | 提示类 Bug 给建议说明你理解用户视角，面试加分 |

### 3.2 输入框包含 HTML 字符时出现异常

#### 【课程原话/定义】

> Web 页面本身就是 HTML 写的，输入框中输入 HTML 语言片段，如果没有进行处理，页面可能会有报错信息。

> 图片位置（输入 HTML 字符导致页面异常示例）

#### 【为什么？】

这是经典的 XSS 漏洞的"温和版本"——还没到注入攻击的程度，但已经暴露了"输入未转义"的问题。如果 `<b>test</b>` 被当成 HTML 渲染成了粗体而不是原文显示，说明后端/前端没有对用户输入做转义处理。**同样的漏洞，输入换成 `<script>alert(document.cookie)</script>` 就变成安全事件了。**

#### 【必须掌握】

输入 HTML 特殊字符的测试方法 + 3 个需要转义的字符：`<` → `&lt;`、`>` → `&gt;`、`&` → `&amp;`。

#### 【企业场景】

> 你在用户昵称输入框输入 `<h1>管理员</h1>`，保存后在用户列表页这个昵称显示成了超大标题——说明前端渲染时没有转义。你提 Bug 时标注"存在 XSS 隐患"，安全等级直接拉高。开发修完你再验证：输入 `<script>alert(1)</script>` 是否被转义为纯文本显示。

#### 【面试考察】

> "输入 HTML 标签导致页面异常，这是什么类型的问题？"
>
> 参考回答：表面是"输入校验缺失"，本质是"输出未转义"。这是 OWASP Top 10 中 XSS 漏洞的前兆——测试人员应该标记为安全相关 Bug，而非普通功能 Bug。正常输入 `<b>test</b>` 应原样显示或过滤掉标签。

#### 【易错点】

| 易忽略 | 补充 |
|--------|------|
| 只测输入框 | 任何用户可控的输入都要测——URL 参数、Cookie、HTTP Header、文件上传的文件名 |
| 前端转义了就安全 | 后端也要转义——攻击者可以绕过前端直接发请求 |

#### 【我的理解】

## 四、功能方面 Bug

### 4.1 功能不符合需求

#### 【课程原话/定义】

> 功能方面 Bug 是平常工作中最常见的。核心就是功能没有符合需求当中的要求。

> 图片位置（搜索无结果示例）

#### 【为什么？】

功能不符合需求是最直接的 Bug 类型，但"不符合需求"有不同的层次——可能是没实现、可能是实现错了、可能是实现了但缺了边界处理。**定位到哪个层次，决定了 Bug 的严重程度和修复成本。**

#### 【必须掌握】

功能不符的 3 个层次：
- **未实现**：需求写了但功能不存在 → Blocker
- **实现错误**：功能存在但逻辑与需求相反/不同 → Critical/Major
- **实现不完整**：主流程对但边界情况未处理 → Major/Minor

#### 【企业场景】

> 需求："用户输入关键词后，展示匹配结果，无结果时显示'未找到相关内容'"。开发实现了搜索，但无结果时页面空白。你提 Bug 的依据不是"我觉得不好"，而是"需求文档第 3 页第 2 段明确写了'无结果时显示未找到相关内容'"。**需求文档是测试人员的武器——没写的不叫 Bug，写了的没实现就叫 Bug。**

#### 【面试考察】

> "你怎么判断一个现象算不算 Bug？"
>
> 参考回答：三条判断标准——① 需求文档明确写了但没实现 = Bug；② 需求没写但常识性预期不满足（如点击"删除"没弹确认框）= 建议/优化；③ 需求没写且无常识性预期的=和产品确认后再决定。

#### 【易错点】

| 误区 | 正解 |
|------|------|
| "我觉得不好用"就当 Bug 提 | Bug 的依据是需求文档，不是个人感受。个人感受可以提"建议"，但要和 Bug 分开 |
| 需求和实际情况冲突时不敢说 | 需求也可能错——如果按需求实现后明显不合理，提出来和产品讨论，这叫"需求缺陷" |

### 4.2 提示信息错误

#### 【课程原话/定义】

> 提示信息中带了一些错误码之类的内容，这些内容是不应该暴露给用户的。给用户的应该就是明确的中文提示。

> 图片位置（错误提示中包含错误码示例）

#### 【为什么？】

提示信息暴露内部错误细节，属于**信息泄露类安全漏洞**。用户看到 `SQLException: Duplicate entry 'admin' for key 'PRIMARY'`，不仅体验差，还泄露了数据库类型（MySQL）、表结构（有 PRIMARY KEY）、甚至数据内容（admin 已存在）。**错误信息要做两层处理：面向用户 → 友好提示；面向开发 → 日志记录。**

#### 【必须掌握】

错误提示的检查点：① 是否暴露了技术栈（如"Tomcat"、"nginx"、"MySQL"）；② 是否暴露了代码路径（如 `/var/www/app/controller/user.php`）；③ 是否暴露了数据库信息（表名、字段名）；④ 对用户是否可理解（中文 vs 英文/乱码）。

#### 【企业场景】

> 你测一个文件上传功能，上传超大的文件，页面显示 `413 Request Entity Too Large nginx/1.18.0`。你提 Bug：① 前端应该在上传前校验文件大小给出友好提示；② 后端 nginx 的错误页应自定义，不要暴露服务器软件和版本号。这个 Bug 属于安全+体验双重问题。

#### 【面试考察】

> "接口返回的错误信息直接展示给用户，你怎么看？"
>
> 参考回答：分两层——① 前端应对错误码做映射（如 500→"系统繁忙，请稍后重试"，401→"登录已过期，请重新登录"）；② 后端原始错误信息写入日志供开发排查，不返回给前端。面试时可以提"前后端分离的错误处理策略"加分。

#### 【易错点】

| 常见遗漏 | 正确做法 |
|---------|---------|
| 只检查正常流程的提示 | 异常流程的提示更关键——4xx/5xx 错误页面是否自定义 |
| 开发说"调试用，上线就关" | 验证上线后确实关了。很多线上事故就是因为"调试开关忘关了" |

#### 【我的理解】

### 4.3 JS 报错

#### 【课程原话/定义】

> JS 脚本报错。遇到这种情况得先区分原因：网速过慢导致代码不完整、网页设计错误导致部分代码不能执行、浏览器不兼容、浏览器缓存出错、服务器超负载。

#### 【为什么？】

JS 报错是"症状"不是"病因"。测试人员的价值不是报告"页面报错了"，而是**初步定位是哪种原因**，让开发拿到 Bug 单就能直接往那个方向排查。**错误定位能力 = 测试效率的倍增器。**

#### 【必须掌握】

JS 报错的 5 种原因 + F12 Console 面板的基本使用。

| 原因 | 排查方法 | 典型表现 |
|------|---------|---------|
| 网速过慢/代码未完全加载 | 刷新后是否复现？不复现 = 偶发网络问题 | 页面加载一半就报错 |
| 网页代码错误 | 复现概率 100%，同一操作必报错 | Console 有明确的错误行号 |
| 浏览器不兼容 | 换浏览器后正常，只有特定浏览器报错 | 通常涉及不支持的 API |
| 浏览器缓存 | 清除缓存后正常 | 更新代码后仍报旧错误 |
| 服务器超负载 | 刷新几次后有时正常有时报错 | 高峰期复现 |

#### 【企业场景】

> 测试环境页面突然 JS 报错，你 F12 打开 Console，看到 `Uncaught TypeError: Cannot read property 'name' of null at user.js:42`。你先刷新——还报错（排除网络）。换 Chrome 无痕模式——还报错（排除缓存）。查 Network——有一个 API 返回了 500。你把 Console 报错 + Network 截图 + "API /api/user/info 返回 500 导致 JS 解析 null 对象报错"一起发给开发——开发 3 分钟定位到后端改了返回字段名。

#### 【面试考察】

> "页面 JS 报错你怎么排查？"
>
> 参考回答：三步法——① F12 Console 看报错信息和行号（判断是哪个功能模块）；② Network 看接口返回（判断是否后端数据异常导致前端报错）；③ 交叉验证（换浏览器、清缓存、刷新），区分是代码 Bug 还是环境问题。把定位结果写在 Bug 单里，不只是"页面报错"。

#### 【易错点】

| 误区 | 正解 |
|------|------|
| 看到 JS 报错就提 Bug | 先确认是否可复现——不可复现的报错可能是环境/网络问题，标注"偶发" |
| Console 里的 Warning 不当回事 | 有些 Warning 是未来版本废弃的 API，可能导致浏览器升级后功能不可用 |

#### 【我的理解】

### 4.4 更改不同步

#### 【课程原话/定义】

> - **登录后打开多个页面**：在一个页面中操作修改内容，在另一个页面中查看，已经修改过的内容在另一个页面上没有体现。
> - **登录状态不同步**：打开多个页面，其中一个页面登录成功，另一个页面刷新，没有同步为登录状态。

#### 【为什么？】

这是 Web 应用多标签页场景下的经典问题。Web 是无状态协议，状态靠 Cookie/Session/Token 维护——但**多个标签页之间共享同一个 Session，却不共享同一个页面状态**。用户天然认为"同一个网站的所有标签页是同步的"，这不是 bug 也是 bug。

#### 【必须掌握】

多标签页一致性测试的 3 个场景：
- **数据同步**：Tab A 修改数据 → Tab B 刷新，是否看到最新数据
- **登录同步**：Tab A 登录 → Tab B 刷新/操作，是否同步登录态
- **登出同步**：Tab A 登出 → Tab B 操作，是否正确拦截

#### 【企业场景】

> 你在浏览器打开两个标签页，都用同一个账号登录后台。Tab A 把订单 1001 的状态从"待发货"改成"已发货"。切到 Tab B，订单 1001 还是显示"待发货"——刷新后仍然是。开发说"刷新就会重新请求数据"。你继续追问：那用户在 Tab B 基于旧状态又操作了一次（比如取消订单），后端怎么处理？结果发现后端没有乐观锁——Tab B 的取消操作覆盖了 Tab A 的发货操作。

#### 【面试考察】

> "多标签页场景下数据不同步，你怎么测？"
>
> 参考回答：模拟真实用户行为——① 打开两个标签页（同一 URL）；② A 修改 → B 查看（无刷新 + 刷新 + 操作）；③ 验证后端数据最终一致性。重点不是"刷新后显示对不对"，而是"并发操作时数据有没有被错误覆盖"。

#### 【易错点】

| 易遗漏 | 补充 |
|--------|------|
| 只测同一浏览器多 Tab | 也要测不同浏览器同时登录（Chrome + Firefox） |
| 只测修改同步 | 删除同步更深——A 删了一条数据，B 还在操作这条数据 |
| 登录同步只测"未登录→登录" | 还有"A 登出→B 操作"、"A 修改密码→B 是否被踢出" |

## 五、其他 Bug

### 5.1 页面请求失败

#### 【课程原话/定义】

> 涉及网络请求，可以到开发者工具的 Network 面板中查看请求发送的状态。通过响应状态码可以简单定位是前端还是服务端出了问题。

> 图片位置（Network 面板请求失败示例）

#### 【为什么？】

页面请求失败不等于"功能坏了"——可能是网络问题、后端挂了、接口超时、跨域被拦截。测试人员的价值在于**用状态码和 Network 面板把问题收敛到"前端还是后端"**，而不是把"页面打不开"的模糊描述丢给开发。

#### 【必须掌握】

HTTP 状态码快速定位表：

| 状态码范围 | 含义 | 谁的问题 |
|-----------|------|---------|
| 4xx | 客户端请求错误 | 前端居多（参数错误、未授权、无权限） |
| 5xx | 服务端错误 | 后端（代码异常、数据库挂了、超时） |
| 无状态码/CORS 报错 | 跨域被拦截 | 后端没配 CORS 或配置错误 |
| (failed) / net::ERR | 网络不通 | 检查域名解析、防火墙、代理 |

#### 【企业场景】

> 前端页面白屏，你打开 F12 → Network，看到 `/api/product/list` 返回 502 Bad Gateway。截图 + "502 说明后端网关/负载均衡找不到上游服务，建议检查后端服务是否正常启动"——开发 1 分钟确认是测试环境后端容器挂了。如果你只写"产品列表页打不开"，开发要从头排查，浪费 15 分钟。

#### 【易错点】

| 常见遗漏 | 正确做法 |
|---------|---------|
| Network 过滤了只看 XHR/Fetch | 也要看 All——JS/CSS/图片加载失败同样会导致页面异常 |
| 只看失败的请求 | 成功的请求也要抽查——返回数据内容是否正确（比如返回空数组但页面没报错就是漏了） |

### 5.2 加载时间太长

#### 【课程原话/定义】

> 需要排查是网络问题还是网页性能问题。如果是性能问题，需要针对性优化。

#### 【为什么？**

用户对页面加载的容忍度极低——3 秒以上，53% 的移动用户会离开。加载慢不一定是 Bug（功能正常），但**测试人员有责任量化它**：是 2 秒还是 20 秒？慢在哪个环节？有数据才有优化依据。

#### 【必须掌握】

Performance 排查三要素：① 总加载时间（Network 底部 Load 时间）；② 最慢的资源（按 Duration 排序）；③ 是否是首屏渲染慢（看 DOMContentLoaded vs Load 的差距）。

#### 【企业场景】

> 用户反馈"订单页加载慢"。你打开 Network → 勾选 Disable cache → 刷新，看到加载时间 8.2 秒。按 Duration 排序，发现一张 4MB 的 PNG 图片加载了 6 秒——这就是慢的根因。你提 Bug："订单页 banner 图 4MB，加载时间 6 秒，建议压缩至 200KB 以内或使用 WebP 格式。"附带 Network 截图。这个 Bug 有理有据，开发没法说"我这不卡"。

#### 【面试考察】

> "页面加载慢怎么排查？"
>
> 参考回答：① F12 Network 看总加载时间和瓶颈资源；② 区分网络问题（资源加载慢）vs 渲染问题（DOMContentLoaded 快但交互慢）；③ 如果用 Lighthouse/PageSpeed 跑分更专业（加分项）。

#### 【易错点】

| 误区 | 正解 |
|------|------|
| 本地/测试环境不慢就觉得没问题 | 生产环境网络条件不同——用 Chrome DevTools 的 Network Throttling 模拟 3G/4G |
| 只看图片/JS 大小 | 接口响应时间也关键——一个慢 SQL 导致接口 5 秒才返回，前端的 loading 转圈转到用户关页面 |

## 六、Web 端 Bug 分类全景总结

```
              ┌── 页面布局方面 ──┬── 超长内容展示错乱
              │                 └── 更换设备布局错乱
              │
              ├── 页面元素方面 ──┬── 输入域提示不明确
              │                 └── HTML字符输入异常
              │
Web端常见Bug ─┼── 功能方面 ────┬── 功能不符合需求
              │                ├── 提示信息错误
              │                ├── JS 报错（5种原因）
              │                └── 更改不同步（多标签页）
              │
              └── 其他Bug ────┬── 页面请求失败（状态码定位）
                               └── 加载时间太长（性能排查）
```

| Bug 类型 | 排查工具 | 典型严重程度 |
|----------|---------|------------|
| 布局错乱 | 肉眼 + 不同浏览器 | Minor ~ Major |
| 输入提示不明确 | 肉眼 + 需求文档 | Minor |
| HTML 字符异常 | F12 Console + 输入特殊字符 | Major（含安全隐患） |
| 功能不符合需求 | 需求文档比对 | Blocker ~ Major |
| 提示信息暴露错误码 | F12 Network + Response | Major（信息泄露） |
| JS 报错 | F12 Console + Network | 取决于影响范围 |
| 多标签页不同步 | 手工多 Tab 操作 | Major |
| 页面请求失败 | F12 Network → 状态码 | Blocker ~ Major |
| 加载太慢 | F12 Network → Duration / Performance | Major |
