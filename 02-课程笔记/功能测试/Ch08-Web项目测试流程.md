## 一、什么是 Web 项目测试流程

### 【课程原话/定义】

> Web 项目测试流程是指在开发和发布 Web 应用程序时，测试团队采用的一系列测试活动和步骤。目标是确保 Web 应用程序符合规格说明、满足用户需求，并具有高质量的性能、可用性和安全性。

### 【为什么？】

Web 项目与桌面软件不同——部署在服务端、通过浏览器访问、用户环境千差万别（不同浏览器、操作系统、屏幕分辨率、网络环境）。如果测试流程不覆盖这些差异，上线后用户用 IE 打不开、手机端错位、并发一大就崩，修复成本远超测试投入。**Web 测试流程的核心价值不是"按步骤执行"，而是"用流程保证不遗漏 Web 特有的风险点"。**

### 【必须掌握】

Web 测试流程的 9 个阶段顺序及每个阶段的产出物。

### 【企业场景】

> 你入职一家电商公司，第一天 leader 扔给你一个需求文档："新功能——用户收藏夹改版，下周三上线。"你不可能上来就对着页面瞎点——先做需求分析理解改了什么，再写测试计划定范围，然后设计用例、执行、回归、兼容性检查……最后写完测试报告才能上线。这就是流程给你的"安全感"——每一环都有据可查。

### 【面试考察】

> "说说你对 Web 项目测试流程的理解？"
>
> 参考回答框架：先讲 9 阶段全貌 → 挑 3 个关键阶段展开说明为什么重要 → 用一句话总结流程的本质（不是机械执行，是风险覆盖）。

### 【易错点】

| 易混淆概念 | 区别 |
|-----------|------|
| 测试流程 vs 开发流程 | 开发流程面向"怎么把代码写出来"（需求→设计→编码→测试→部署）；测试流程面向"怎么保证质量"（分析→计划→设计→执行→回归→报告） |
| 测试流程 vs 测试策略 | 流程是"先做什么后做什么"（时序）；策略是"用什么方法测"（方法选择，如手工/自动化、黑盒/白盒） |
| 测试计划 vs 测试方案 | 计划侧重"管理"（时间、人员、资源）；方案侧重"技术"（测什么、怎么测、用什么工具） |

## 二、Web 测试流程 9 个阶段

### 阶段 1：需求分析

#### 【课程原话/定义】

> 理解业务需求，明确测试范围，识别需求中的模糊点和潜在风险。

#### 【为什么？】

测试人员最怕的不是 Bug 多，而是"测完了才发现理解偏了"。需求分析阶段花 1 小时澄清一个模糊点，能避免执行阶段 10 小时的无用功。

#### 【必须掌握】

需求分析的三步：读需求文档 → 梳理业务流程 → 标出模糊点与产品/开发沟通确认。

#### 【企业场景】

> 你拿到 PRD（产品需求文档），写着"用户可以在购物车修改商品数量"。你马上要追问：数量上限是多少？库存不足时怎么提示？修改数量后优惠券是否重新计算？批量修改时并发怎么处理？这些 PRD 可能都没写，但你不问，上线后全是 Bug。

#### 【面试考察】

> "需求分析阶段测试人员主要做什么？"
>
> 参考回答：不是"验收需求写没写对"（那是产品的事），而是从可测试性角度审视需求——有没有不可验证的描述（如"系统响应快"——多快？）、有没有遗漏异常分支（网络断开、数据为空）、有没有隐含的业务规则没写清楚。

#### 【易错点】

| 误区 | 正确做法 |
|------|---------|
| 需求分析就是读一遍 PRD | 带着"我怎么测这个需求"的视角去读，边读边列测试点 |
| 需求有问题等产品改了再说 | 越早反馈成本越低，需求阶段改一行字 vs 上线后改代码+数据库+回归，代价差 100 倍 |

### 阶段 2：测试计划编写

#### 【课程原话/定义】

> 制定测试范围、资源分配、时间安排、风险评估和测试策略。

#### 【为什么？】

没有计划的测试是一场赌博。测试计划回答三个核心问题：测什么（范围）、测多久（排期）、用什么测（资源）。Leader 看计划判断你能不能按时交付，开发看计划知道自己什么时候要配合修 Bug。

#### 【必须掌握】

测试计划的核心要素：测试范围、测试策略、资源分配、时间安排、风险识别、准入/准出标准。

#### 【企业场景】

> 下周三上线的功能，leader 问你要几天测完。你不能拍脑袋说"三天"。你得拆：需求分析半天、用例设计半天、执行两天、回归半天——总共三天半。和 leader 说清楚每段时间花在哪，这叫专业。

#### 【面试考察】

> "测试计划包含哪些内容？准入准出标准是什么？"
>
> 参考回答：准入标准 = 什么条件下可以开始测试（如开发提测、冒烟通过）；准出标准 = 什么条件下可以结束测试（如用例 100% 执行、严重 Bug 清零、遗留 Bug 已评审）。

#### 【易错点】

| 易错 | 正解 |
|------|------|
| 计划就是排期表 | 计划 = 范围 + 策略 + 资源 + 风险 + 准入准出，排期只是其中一项 |
| 计划写完了就不用改 | 计划是动态的——需求变了、人员请假、Bug 比预期多，都要调整计划 |

### 阶段 3：测试用例设计

#### 【课程原话/定义】

> 基于需求文档和测试计划，设计具体的测试用例，覆盖功能、界面、性能、安全等方面。

#### 【为什么？】

用例是测试人员的"操作手册"——没有用例的测试叫"随机点点"，随机点点的结果不可重复、不可追溯、不可量化。一份好的用例 = 任何人（包括三个月后的你）拿着它都能复现同样的测试。

#### 【必须掌握】

用例设计的核心方法：等价类划分、边界值分析、场景法、判定表法。Web 项目额外关注：浏览器兼容性用例、页面跳转流程用例、异常网络断联用例。

#### 【企业场景】

> 你设计"登录功能"的用例时，不能只写"输入正确账号密码能登录"。你还得考虑：密码错误 3 次是否锁定？验证码过期怎么办？第三方登录（微信/支付宝）回调失败怎么处理？记住密码的 cookie 过期时长？这些才是 Web 登录的真考验。

#### 【面试考察】

> "Web 项目测试用例设计有哪些特殊考虑？"
>
> 参考回答：① 多浏览器兼容性（Chrome/Firefox/Edge/Safari）；② 多分辨率响应式；③ 网络异常场景（超时、断网、弱网）；④ Cookie/Session/Token 过期；⑤ 前端 JS 报错后的页面降级。

#### 【易错点】

| 常见遗漏 | 补充 |
|---------|------|
| 只写正常流程 | 异常流程（网络断开、数据为空、超时、接口 500）往往 Bug 更多 |
| 只测前端 | Web 项目的 Bug 可能在前后端交互——前端校验绕过、接口参数篡改、Token 伪造 |

#### 【我的理解】

### 阶段 4：用例执行

#### 【课程原话/定义】

> 按照测试用例逐步执行测试，记录测试结果和发现的缺陷。

#### 【为什么？】

执行阶段是测试人员的主战场。但"执行"不等于"一条条跑用例"——执行中会遇到用例没覆盖的场景，需要随机应变做探索性测试。执行阶段的产出物是缺陷报告，直接决定开发修不修、怎么修。

#### 【必须掌握】

执行顺序：冒烟测试 → 功能测试 → 异常测试 → 探索性测试。每轮执行后更新用例执行状态（Pass/Fail/Block）。

#### 【企业场景】

> 开发说"提测了"，你不能上来就全量跑用例。先做冒烟——主流程跑通没？主流程不通直接打回，别浪费时间。冒烟过了再按优先级执行：P0（核心功能）→ P1（重要功能）→ P2（边缘场景）→ P3（UI 细节）。

#### 【面试考察】

> "测试执行中你如何管理缺陷？优先级怎么定？"
>
> 参考回答：按严重程度（Blocker/Critical/Major/Minor/Trivial）× 发生概率排序。Blocker 阻塞测试必须立即修，Trivial 文字拼写可以下版本改。同时关注缺陷聚类——某个模块 Bug 密集说明代码质量差，需要扩大测试范围。

#### 【易错点】

| 易错 | 正解 |
|------|------|
| 执行 = 机械跑用例 | 执行中要保持"测试嗅觉"——感觉哪里不对就深挖，最好的 Bug 往往是"用例之外的偶然发现" |
| 发现 Bug 就停 | 发现一个 Bug 后继续执行（先记下来），不要花 30 分钟深入研究根因而耽误进度 |

#### 【我的理解】

### 阶段 5：回归测试

#### 【课程原话/定义】

> 在 Bug 修复或代码变更后，重新执行测试以保证原有功能不受影响。

#### 【为什么？】

"修好一个 Bug，引入三个新 Bug"是软件开发的基本定律。回归测试就是防止这种"修复副作用"的安全网。Web 项目尤其容易出这类问题——前端改了 JS，后端接口没配合，整条链路就断了。

#### 【必须掌握】

回归范围的选择策略：① 全量回归（大版本/核心模块改动）；② 选择性回归（只回归受影响模块+关联模块）；③ 自动化回归（用脚本跑高频用例，节省人力）。

#### 【企业场景】

> 开发告诉你"只改了一行代码，不用回归"。千万别信。哪怕改了一行 CSS，都可能导致页面布局错乱。你至少要把该页面的核心功能走一遍。企业里通常有回归用例集——每次上线前必跑的 50~100 条核心用例，手工跑 2 小时，自动化 15 分钟。

#### 【面试考察】

> "回归测试怎么选范围？时间不够怎么办？"
>
> 参考回答：基于风险选择——改了什么模块？关联哪些模块？线上用户高频使用的功能必回归。时间不够时优先跑自动化回归 + P0 用例，和 leader 说明风险后签字确认。

#### 【易错点】

| 误区 | 正解 |
|------|------|
| 回归 = 把全部用例再跑一遍 | 时间不允许。良好的回归策略 = 自动化覆盖核心 + 手工覆盖变更影响区域 |
| 开发说"改动小不用回归"就真的不回归 | 测试人员自己评估风险，不能被开发带节奏 |

#### 【我的理解】

### 阶段 6：兼容性测试

#### 【课程原话/定义】

> 验证 Web 应用在不同浏览器、操作系统、设备和网络环境下的表现一致性。

#### 【为什么？】

Web 项目的天然特性：用户端不可控。你用的是 Chrome 最新版，用户可能在用 IE11、360 浏览器、手机自带浏览器。兼容性问题往往是上线后用户投诉的第一来源。**兼容性测试 = 用测试成本换取用户覆盖。**

#### 【必须掌握】

兼容性测试矩阵的三个维度：
- **浏览器**：Chrome（最新版+近3个大版本）、Firefox、Edge、Safari
- **操作系统**：Windows、macOS、移动端（iOS Safari + Android Chrome）
- **分辨率**：1920×1080、1366×768（笔记本）、375×667（iPhone）

#### 【企业场景】

> 公司主要用户是政府/国企，他们电脑清一色 Windows 7 + IE11。产品经理说"我们只支持 Chrome"，但上线后客服每天接 50 个投诉电话。所以兼容性测试的范围一定要根据用户画像来定——先看埋点数据知道用户用什么浏览器，再决定测哪些。

#### 【面试考察】

> "如何确定兼容性测试的范围？"
>
> 参考回答：① 查看线上用户数据分析（Google Analytics/百度统计）—用户浏览器分布；② 产品定位（toC 覆盖面广 vs toB 可控环境）；③ 时间和资源约束下的优先级排序。

#### 【易错点】

| 常见误区 | 正解 |
|---------|------|
| 所有浏览器都装一遍测 | 数据驱动——用户占比 < 1% 的浏览器可以不做深度测试，只确认基本可访问 |
| 兼容性测试放在最后 | 越晚发现兼容性问题修改成本越高——至少 P0 用例要在开发阶段就交叉浏览器验证 |

#### 【我的理解】

### 阶段 7：安全测试

#### 【课程原话/定义】

> 检测 Web 应用的安全漏洞，包括但不限于 XSS、SQL 注入、CSRF、敏感信息泄露、权限越权等。

#### 【为什么？】

Web 应用暴露在公网，任何人输入 URL 就能访问。安全漏洞不只是技术问题——数据泄露 = 法律风险 + 品牌损失 + 用户流失。测试人员不要求成为安全专家，但必须能识别最常见的 Web 漏洞。

#### 【必须掌握】

Web 测试人员必知的安全检查项：
- **XSS（跨站脚本）**：输入框输入 `<script>alert(1)</script>` 是否被执行
- **SQL 注入**：输入框输入 `' OR '1'='1` 是否被拼接进 SQL
- **CSRF**：是否验证 referer / 使用 CSRF token
- **越权**：修改 URL 参数中的 ID 是否能访问他人数据（水平越权）；普通用户是否能访问管理员接口（垂直越权）
- **敏感信息**：密码是否明文传输/存储；报错页面是否泄露数据库结构

#### 【企业场景】

> 你测一个查询订单页面，URL 是 `/order?id=10001`。你把 id 改成 10002，如果能看到别人的订单——这就是水平越权，P0 级别 Bug。企业里安全测试通常有专门的安全团队，但基础的安全检查是每个测试人员的必修课。

#### 【面试考察】

> "你在测试中如何做安全测试？列举几个你关注的点。"
>
> 参考回答：列举 3~5 个 OWASP Top 10 中的漏洞类型 + 你在测试中怎么检查 + 一个你实际发现过的安全问题（没有就说"如果有 XX 情况我会怎么处理"）。

#### 【易错点】

| 误区 | 正解 |
|------|------|
| 安全测试是安全团队的事 | 基本安全检查（XSS、SQL注入、越权、敏感信息泄露）是功能测试的一部分 |
| 用自动化工具扫一遍就完了 | 工具扫不出业务逻辑层面的越权，必须手工验证 |

#### 【我的理解】

### 阶段 8：走查验收

#### 【课程原话/定义】

> 在产品上线前，组织相关干系人（产品、开发、测试、运营）进行最终检查，确认所有需求已实现、已知缺陷已处理、达到上线标准。

#### 【为什么？】

走查验收不是"再测一遍"，而是"换一个视角过一遍"——产品看需求是否全部满足，开发看是否有遗漏的技术债务，运营看业务流程是否跑通。这是上线的最后一道关卡，也是测试人员的"免责声明"——验收通过后上线出问题，决策记录在案。

#### 【必须掌握】

验收检查清单：
- 所有需求是否已实现且测试通过
- P0/P1 Bug 是否全部关闭
- 遗留 Bug 是否已评审并明确责任人
- 回归测试是否通过
- 上线回滚方案是否准备

#### 【企业场景】

> 上线前的验收会议上，产品经理突然说"这个按钮的颜色应该用品牌色"，开发说"文档里没写啊"。你拿出需求文档——"第 3 页第 2 段，写的确实是蓝色"。这就是验收走查的价值：把争议在上线前解决，不要等用户来"验收"。

#### 【面试考察】

> "验收测试和功能测试有什么区别？"
>
> 参考回答：功能测试是测试人员的验证活动（是否符合需求）；验收测试是干系人（产品/用户）的确认活动（是否满足业务目标）。测试人员做的是"验证"（Verification），产品做的是"确认"（Validation）。

#### 【易错点】

| 易混淆 | 区别 |
|--------|------|
| 测试人员的验收 ≠ 产品的验收 | 测试验收看"有没有 Bug"；产品验收看"是不是我要的东西" |
| 验收 = 再跑一遍用例 | 验收重点是业务流程端到端走通 + 需求核对，不是重新执行全部用例 |

### 阶段 9：测试总结报告

#### 【课程原话/定义】

> 汇总整个测试过程的数据和发现，评估产品质量，总结经验教训，为后续项目提供参考。

#### 【为什么？】

测试报告 = 测试的"交付物"。如果没有报告，测试做得好不好没有证据，Bug 分布没有统计，经验没有沉淀。测试报告不仅给领导看，也是你自己的复盘材料——"这次项目我在哪个阶段最耗时？下次怎么优化？"

#### 【必须掌握】

测试报告的核心内容：
1. **测试概况**：测试范围、时间、人员、环境
2. **用例统计**：总用例数、执行数、通过率
3. **缺陷分析**：Bug 总数、按严重程度/模块分布、修复率、遗留 Bug
4. **质量评估**：是否达到准出标准、风险评估
5. **经验总结**：做得好的、可以改进的、下次注意的

#### 【企业场景】

> 项目上线后，leader 让你发测试报告。你不能写"测完了，可以上线"。你要给数据：本次测试设计用例 86 条，执行 86 条，通过率 97.7%，发现 Bug 23 个（2 个 Blocker 已修、3 个 Major 遗留经评审同意），回归 2 轮，兼容性覆盖 Chrome/Firefox/Edge/Safari。**有数据的报告才叫专业。**

#### 【面试考察】

> "测试报告怎么写？你有什么模板吗？"
>
> 参考回答：列出 5 大板块 + 每板块重点内容，强调"数据说话"——不是感觉没问题，是用例通过率、Bug 关闭率这些可量化指标。

#### 【易错点】

| 误区 | 正解 |
|------|------|
| 报告是给领导看的，随便写写 | 报告首先是给你自己看的——哪类 Bug 最多说明哪类需求最容易出问题，下次测试时重点覆盖 |
| 只写数字不写结论 | 数字是原材料，结论才是价值——"因为 XX 模块 Bug 密度高，建议开发做代码评审" |

## 三、Web 测试流程全景总结

```
需求分析 → 测试计划 → 用例设计 → 用例执行 → 回归测试 → 兼容性测试 → 安全测试 → 走查验收 → 测试总结
  (1)        (2)        (3)        (4)        (5)         (6)         (7)        (8)        (9)
```

| 阶段    | 核心产出         | 谁参与          |
| ----- | ------------ | ------------ |
| 需求分析  | 需求问题清单、测试点列表 | 测试 + 产品      |
| 测试计划  | 测试计划文档       | 测试           |
| 用例设计  | 测试用例库        | 测试           |
| 用例执行  | 缺陷报告、执行记录    | 测试 + 开发      |
| 回归测试  | 回归测试结果       | 测试           |
| 兼容性测试 | 兼容性测试报告      | 测试           |
| 安全测试  | 安全测试报告       | 测试（+安全团队）    |
| 走查验收  | 验收签核         | 测试 + 产品 + 开发 |
| 测试总结  | 测试总结报告       | 测试           |
