## 一、Web 是什么

### 【课程定义】

> Web（World Wide Web，万维网）是一种基于超文本和 HTTP 的跨平台分布式图形信息系统。从技术视角看，它包含网页布局设计、代码编写、数据库建立、网络平台选择等；从用户视角看，就是我们用浏览器上网时所浏览的网页。

### 【为什么？】

理解 Web 本质 = 理解你在测什么。Web 不是"一个软件"，而是**一堆技术的组合体**：

```
用户看到    →  网页（HTML + CSS + JS）
数据传输    →  HTTP/HTTPS 协议
业务处理    →  后端服务 + 数据库
域名解析    →  DNS
文件托管    →  Web 服务器
```

测试工程师如果不理解这些组件各自干什么，看到一个 Bug 时根本不知道往哪个方向排查。

### 【必须掌握】

- Web 的技术定义和用户定义
- 超文本的含义：通过超链接组织不同空间的文字信息
- Web 是"网络使用环境 + 相关技术的总称"

### 【企业场景】

> 开发说"这个 Bug 是前端的"，前端说"是后端接口的问题"，后端说"是数据库数据不对"。你作为 QA 要能判断到底是谁的问题，靠的就是对 Web 各层技术的基本理解。谁都不懂就会被推来推去。

### 【面试考察】

> 面试官：简单介绍一下 Web 是什么？

参考回答框架：
1. 定义：基于超文本和 HTTP 的全球广域网
2. 两个视角：技术视角（HTML/CSS/JS/数据库/服务器）+ 用户视角（浏览器上网）
3. 核心特点：跨平台、分布式、超链接组织信息

### 【易错点】

| 易混淆 | 区别 |
|--------|------|
| Web = 互联网？ | 互联网是基础设施（网络层），Web 是互联网上的一个应用（应用层） |
| Web = 网站？ | 网站是 Web 的具体实例，Web 是技术体系的总称 |

## 二、系统架构：B/S vs C/S

### 【课程定义】

> B/S（Browser/Server）：通过浏览器查看的应用程序。C/S（Client/Server）：需要额外安装客户端的应用程序。Web 属于 B/S 架构，App 属于 C/S 架构。

### 【为什么？】

架构不同，测试重点完全不同：

| 测试维度 | B/S（Web） | C/S（App） |
|----------|-----------|-----------|
| 兼容性测试 | 浏览器兼容（Chrome/Firefox/Safari/Edge） | 操作系统兼容（iOS/Android/Windows） |
| 安装测试 | 不需要 | 安装/升级/卸载/覆盖安装 |
| 升级方式 | 服务端更新，用户无感 | 用户需下载更新包 |
| 网络依赖 | 必须有网络 | 部分可离线使用 |
| 性能关注 | 页面加载速度、首屏时间 | 启动速度、内存占用 |

### 【必须掌握】

- B/S 和 C/S 的定义和区别
- B/S 的测试重点：浏览器兼容性
- C/S 的测试重点：安装/升级/卸载、平台兼容

### 【企业场景】

> 你测一个 B/S 架构的后台管理系统，上线前必须过 Chrome、Firefox、Edge 三轮兼容测试。后来公司出了 App 版（C/S），你又多了 iOS/Android 安装测试、升级测试、不同手机分辨率的适配测试。这就是为什么架构决定测试策略。

### 【面试考察】

> 面试官：B/S 和 C/S 架构的测试有什么区别？

参考回答框架：
1. 定义区分：B/S 浏览器访问 vs C/S 安装客户端
2. 测试重点不同：兼容性方向不同（浏览器 vs 操作系统）
3. 升级方式不同：服务端无感更新 vs 客户端版本管理
4. 各举一个例子

### 【我的理解】

## 三、Web 的三层架构

### 【课程定义】

> B/S 架构内部通常分为 3 层：
> - **界面层（表示层）**：Web 前端界面，用户看到的网页
> - **业务逻辑层**：服务端的接口和处理逻辑
> - **数据访问层**：SQL 和数据库存储

### 【为什么？】

三层架构不是理论，它是你日常排查 Bug 的导航图：

```
用户反馈：下单按钮点不了
     ↓
① 界面层排查：F12 Console 有没有 JS 报错？按钮元素存在吗？
     ↓
② 业务逻辑层排查：接口有没有返回？返回码是什么？参数对不对？
     ↓
③ 数据访问层排查：数据库订单表有没有写入？数据对不对？
```

**分层排查 = 快速定位问题的核心方法论。**

### 【必须掌握】

- 三层架构各自负责什么
- 每层的典型技术：界面层（HTML/CSS/JS）、业务逻辑层（Java/Python/Go + API）、数据访问层（SQL + MySQL/Redis）
- 测试视角下如何分层验证

### 【企业场景】

> 你做功能测试时，不要只测界面"能不能点"。一个完整的测试应该覆盖三层：界面显示对不对→接口返回对不对→数据库写入对不对。这叫"端到端验证"。很多新人只测了第一层，漏了下面两层，线上出数据问题。

### 【面试考察】

> 面试官：Web 应用通常分几层？测试时怎么覆盖每一层？

参考回答框架：
1. 三层：界面层 + 业务逻辑层 + 数据访问层
2. 界面层：UI 自动化 / 手工验证显示和交互
3. 业务逻辑层：接口测试，验证请求/响应
4. 数据访问层：数据库校验，验证数据正确落库

### 【易错点】

| 误区 | 正解 |
|------|------|
| 测试就是测界面 | 三层都要验证，界面只是冰山一角 |
| 三层必须独立测试 | 实际工作中先端到端跑通，再逐层深入 |

### 【我的理解】

## 四、静态网页 vs 动态网页

### 【课程定义】

> - **静态网页**：和服务器没有数据交互，内容固定
> - **动态网页**：网页数据可以和服务器进行数据交互，内容随请求变化

### 【为什么？】

静态和动态不是指页面有没有动画，而是**数据从哪来**：

| 特征    | 静态网页       | 动态网页                             |
| ----- | ---------- | -------------------------------- |
| 数据来源  | 写死在 HTML 里 | 从数据库/接口获取                        |
| 内容变化  | 改代码才能变     | 数据变页面就变                          |
| 典型文件  | .html      | .php / .jsp / .aspx / 前后端分离的 SPA |
| 测试关注点 | 页面展示正确     | 数据绑定正确 + 接口正常                    |

### 【必须掌握】

- 能判断一个网页是静态还是动态
- 动态网页的测试比静态网页复杂，因为涉及数据流

### 【企业场景】

> 公司官网首页是静态的，改了就能上线，测试只要看页面展示。但用户中心页面是动态的，显示用户名、订单数、积分余额，这些都是从数据库取出来的。测试时你要验证：数据库改了 → 接口返回变了 → 页面显示变了，整个链路通不通。

## 五、URL 与 URI

### 【课程定义】

> **URL**：Uniform Resource Locator，统一资源定位符，通过描述"哪个主机上哪个路径的文件"来定位资源。
> 
> 格式：`schema://host[:port]/path[?query][#fragment]`
> 
> **URI**：Uniform Resource Identifier，统一资源标识符，在某一规则下唯一标识一个资源。URL 是 URI 的一种实现方式（通过定位来实现标识）。

### 【为什么？】

测试工作中每天都在和 URL 打交道：

```
https://www.baidu.com/s?wd=hogwarts&rsv_spt=1
└─┬─┘ └──────┬──────┘└┬┘└───────┬──────────────┘
 schema    host      path    query string
```

- 接口测试 = 拼 URL + 发请求
- 安全测试 = 改 URL 参数看看会不会越权
- 兼容测试 = 换不同 host（测试环境/预发布/生产）

### 【必须掌握】

- URL 的 5 个组成部分：协议、主机、端口、路径、查询参数
- URI 和 URL 的关系：URL ⊆ URI
- 能拆解任意一个 URL

### 【面试考察】

> 面试官：URI 和 URL 有什么区别？

参考回答框架：
1. URI 是统一资源标识符，URL 是统一资源定位符
2. URL 是 URI 的子集，通过"位置"来标识
3. 举例：身份证号是 URI 但不是 URL（不描述位置），家庭住址既是 URI 也是 URL

### 【易错点】

| 易混淆 | 辨析 |
|--------|------|
| URI 和 URL 是一个东西？ | URL 是 URI 的一种，URN 也是（通过名字标识） |
| URL 就是网址？ | 网址是通俗说法，技术面试说 URL |

### 【我的理解】

## 六、HTTP 协议

### 【课程定义】

> HTTP（HyperText Transfer Protocol，超文本传输协议）是用来传输超文本到本地浏览器的传送协议。它由请求和响应构成，本身是一个**无状态**的协议——每次请求之间都是独立的，客户端和服务器都不记录彼此过去的行为。

### 【为什么？】

HTTP 是 Web 世界的高速公路。所有前后端交互都跑在这条路上。

**三个关键特性必须理解：**

| 特性         | 含义             | 测试影响                          |
| ---------- | -------------- | ----------------------------- |
| 请求-响应模型    | 客户端发请求，服务端返回响应 | 测试 = 构造请求 + 验证响应              |
| 无状态        | 每次请求独立，不记历史    | 需要 Cookie/Session/Token 维持登录态 |
| 明文传输（HTTP） | 数据不加密          | HTTPS 才是加密的，安全测试要关注           |

### 【必须掌握】

- HTTP 的请求-响应模型
- "无状态"的含义
- HTTP 和 HTTPS 的区别（加密）
- HTTP 在 Web 测试中的角色：接口测试的基础

### 【企业场景】

> 你在测试一个登录功能。输入用户名密码点登录 → 浏览器发 HTTP POST 请求到 `/api/login` → 服务端验证 → 返回成功 + Set-Cookie → 浏览器存下 Cookie → 后续请求自动带上 Cookie 证明"我已经登录了"。这就是 HTTP 无状态 + Cookie 维持状态的工作方式。如果 Cookie 丢了，用户就得重新登录——你测登录时就要测这个。

### 【面试考察】

> 面试官：HTTP 协议有什么特点？什么是无状态？

参考回答框架：
1. 基于请求-响应模型
2. 无状态：每次请求独立，不保留上下文
3. 无状态的好处：简单、可扩展
4. 无状态的解决方案：Cookie / Session / Token
5. HTTP vs HTTPS：加密层

### 【我的理解】

## 七、浏览器工作原理

### 【课程定义】

> 浏览器访问网页的流程：
> 1. 用户访问网址，发送请求到服务器
> 2. 服务器解析请求，查询数据库
> 3. 数据库返回结果给服务器
> 4. 服务器生成 HTML，放入 HTTP Response 返回
> 5. 浏览器解析 HTML，创建 DOM 树
> 6. 下载 CSS，对 DOM 树渲染
> 7. 下载 JS，执行 JS 程序
> 8. 浏览器显示最终页面

### 【为什么？】

这是面试高频题，也是理解"页面为什么白屏/加载慢/样式错乱"的基础：

```
请求阶段（1-4）：    网络问题 → 白屏 / 超时
DOM 构建（5）：       HTML 结构错误 → 元素缺失
CSS 渲染（6）：       样式加载失败 → 页面乱掉
JS 执行（7）：        脚本报错 → 交互失效
```

**知道每一步干什么 = 知道去哪看、怎么定位。**

### 【必须掌握】

- 从输入 URL 到页面显示，浏览器干了什么（8 步流程）
- DOM 树是什么：浏览器把 HTML 解析成的树形结构
- CSS 和 JS 的加载和渲染顺序

### 【面试考察】

> 面试官：从输入 URL 到页面显示，发生了什么？

参考回答框架：
1. DNS 解析：域名 → IP
2. TCP 连接：三次握手
3. 发送 HTTP 请求
4. 服务器处理并返回响应
5. 浏览器解析 HTML → DOM 树
6. 解析 CSS → CSSOM 树 → 合并为渲染树
7. 布局 + 绘制
8. 执行 JS（可能修改 DOM）

### 【易错点】

| 误区 | 正解 |
|------|------|
| "页面显示完才执行 JS" | JS 可能在 DOM 构建过程中就执行，会阻塞渲染 |
| CSS 加载失败不影响内容？ | CSS 加载失败 → 页面无样式，用户体验极差 |
| DOM 树 = 渲染树？ | 渲染树 = DOM + CSSOM 合并后，包含可见元素 |

## 八、DNS 解析

### 【课程定义】

> DNS（Domain Name System，域名系统）是把域名和 IP 地址相互映射的分布式数据库。通过域名得到 IP 地址的过程叫域名解析。

### 【为什么？】

你测的是 `https://test.example.com`，开发说"改下 hosts 指向测试环境"，你不懂 DNS 就懵了。

DNS 解析顺序：
```
① 浏览器缓存
② 本机 hosts 文件  ← C:\Windows\System32\drivers\etc\hosts
③ 本地 DNS 服务器
④ 根域名服务器 → 逐级向下查询
```

### 【必须掌握】

- DNS 的作用：域名 ↔ IP 映射
- 解析顺序（4 步）
- hosts 文件的位置和作用（测试环境切换常用）

### 【企业场景】

> 测试环境还没配域名，开发让你在 hosts 文件里加一行 `192.168.1.100 test.example.com`，这样你访问 `test.example.com` 时实际指向测试服务器。这就是通过 DNS 机制绕过正式域名解析。你改完 hosts 发现不生效？可能浏览器有 DNS 缓存，清一下缓存或用隐身窗口。

### 【面试考察】

> 面试官：DNS 的解析过程是怎样的？

参考回答框架：
1. 浏览器缓存 → hosts 文件 → 本地 DNS → 根域名服务器
2. 递归查询：逐级向下直到找到
3. 根域名服务器全球 13 组（主根在美国，辅根分布各国）

## 九、常见 Web 服务器

### 【课程定义】

> Web 服务器是处理浏览器请求并返回响应的软件。主流的有 Apache、Nginx、Tomcat、IIS。

### 【为什么？】

知道服务器类型 → 知道日志在哪看 → 出问题时能自己查而不是等开发。

| 服务器    | 特点              | 常见场景          |
| ------ | --------------- | ------------- |
| Apache | 开源，跨平台，市场占有率高   | PHP 项目（LAMP）  |
| Nginx  | 轻量高效，反向代理/负载均衡强 | 前后端分离、微服务网关   |
| Tomcat | Java 应用服务器      | Java Web 项目   |
| IIS    | 微软出品，Windows 集成 | .NET / 企业内部系统 |

### 【必须掌握】

- 4 种主流 Web 服务器的名字和典型用途
- Nginx 的"反向代理"概念（面试高频）
- 测试时要会看服务器日志定位问题

### 【企业场景】

> 你测接口时发现请求超时，开发说"你看下 Nginx 日志"。你在服务器上 `tail -f /var/log/nginx/access.log`，发现请求已经到了 Nginx 但转发给后端时超时了。问题不在前端也不在 Nginx，是后端服务挂了。看日志定位 = QA 的进阶能力。
