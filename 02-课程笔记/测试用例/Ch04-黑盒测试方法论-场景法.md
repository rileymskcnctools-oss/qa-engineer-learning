## 一、什么是场景法

### 知识点1：场景法的定义与核心思想

【课程原话/定义】
场景法就是模拟用户操作软件时的场景，主要用于测试系统的业务流程。现在的产品几乎都是由事件触发来控制流程的，事件触发时的情景便形成了场景。而同一事件不同的触发顺序和处理结果形成事件流。

当拿到一个测试任务时，不能只关注某个控件的边界值、等价类是否满足要求，也要关注它的主要功能和业务流程是否正确实现。

【为什么？】
前面学的等价类、边界值、判定表都在测试**单个功能点**的正确性。但用户使用软件时不是"测完按钮A再测输入框B"，而是走一条**完整的操作路径**。这条路线上任何一个节点断了，即便每个节点单独都正确，用户也无法完成任务。

本质区别：
- 等价类/边界值/判定表 → 测"部件"（单个控件、单个规则）
- 场景法 → 测"装配体"（部件串联后能不能跑通一条完整的用户路径）

场景法的核心思想来自软件工程中的**用例（Use Case）**概念——一个用例描述用户和系统之间的一次完整交互。测试中的场景法就是用例的测试版。

【必须掌握】
- 场景法 = 模拟用户操作流程，端到端验证业务流程
- 基本流 = 正确的、期望的主路径
- 备选流 = 异常分支、错误处理路径
- 事件流 = 同一个流程中不同事件触发顺序和处理结果的组合

【企业场景】
> 你在测试一个报销系统，每个单点功能都测过了：金额输入框边界值OK、审批按钮能点、上传附件正常。但上线后用户投诉："我填完报销单点提交，系统提示审批人不存在，之前填的所有内容都丢了！"——问题出在流程上：提交失败 → 页面刷新 → 数据丢失。等价类和边界值不覆盖这种端到端流程，只有场景法能发现。

【面试考察】
> 面试官："什么是场景法？和等价类/边界值有什么本质区别？"
**参考回答框架：**
1. 场景法模拟用户操作路径，测试端到端业务流程
2. 等价类/边界值/判定表测试的是单点功能（输入框、按钮、规则）
3. 场景法测试的是流程（多个单点串联后的完整路径）
4. 比喻：单点测试 = 检测每个零件的质量；场景测试 = 检测装配好的机器能不能运转

【易错点】

| ❌ 错误理解       | ✅ 正确理解                                   |
| ------------ | ---------------------------------------- |
| 场景法就是随便点点流程  | 场景法需要系统化地识别基本流和所有备选流，每条路径都要有明确的测试用例      |
| 场景法不需要关注输入值  | 场景法中的每个步骤仍需要合理的测试数据——只是更关注流程走向而不是单个字段的精度 |
| 场景法替代等价类和边界值 | 先单点验证，再场景验证——两者顺序不能颠倒，否则流程测通了但单点有 bug    |

## 二、基本流与备选流

### 知识点2：场景法的两大核心概念

【课程原话/定义】
- **基本流**：按照正确的业务流程来实现的一条操作路径（主成功场景）
- **备选流**：导致程序出现错误的操作流程（异常分支、扩展场景）

使用场景法设计测试用例时，需要覆盖主成功场景和扩展场景，并适当补充各种正反面的测试用例和考虑异常场景的情形。

【为什么？】
基本流和备选流的划分来自用例建模中的**主成功场景（Main Success Scenario）**和**扩展（Extensions）**概念：

- 基本流 = 一切顺利时的理想路径，用户从起点走到终点，中间没有任何阻碍
- 备选流 = 过程中每个可能"出岔子"的节点——登录失败、余额不足、网络超时、中途退出...

**关键认知**：基本流只有一条，但备选流有很多条。而且备选流不一定是"彻底失败"——有些备选流是"绕路后回到基本流"（如未登录 → 登录 → 继续购物）。测试用例 = 基本流 + 备选流的各种组合路径。

【必须掌握】
- 基本流 = "欢乐路径"（Happy Path），只有一个
- 备选流 = 每个步骤可能出现的异常分支
- 一个场景 = 基本流（或部分基本流）+ 若干备选流
- 覆盖率要求：每个备选流至少被一个场景覆盖

【企业场景】
> 你在测试一个在线选座购票系统。基本流：选电影 → 选场次 → 选座位 → 支付 → 出票。备选流包括：① 电影已下架 ② 场次已满座 ③ 座位被锁定（并发）④ 余额不足 ⑤ 支付超时 ⑥ 选座中途退出 ⑦ 已购票再次购买同一场次。你设计 8 个场景（1 个基本流 + 7 个各含一条备选流），上线后发现 ③（并发锁座）仍然有 bug——说明"座位被锁定"这条备选流需要进一步细分（别人锁 vs 自己锁 vs 超时释放后重新锁）。

【面试考察】
> 面试官："基本流和备选流有什么区别？怎么保证备选流覆盖完整？"
**参考回答框架：**
1. 基本流是最理想的用户路径，备选流是过程中的任何异常/分支
2. 识别备选流的方法：对基本流中的每一步问"如果这一步出错了会怎样？"
3. 覆盖保证：基本流中每个步骤至少考虑 2-3 种异常情况，列出所有备选流
4. 每个备选流设计一个场景（可以与基本流组合），确保所有备选流都被触发过

【易错点】

| ❌ 错误理解       | ✅ 正确理解                                     |
| ------------ | ------------------------------------------ |
| 备选流就是失败路径    | 备选流包括"绕路后继续"（未登录→登录→继续）和"彻底失败"（支付失败结束）两种情况 |
| 基本流只有一条所以不重要 | 基本流是企业最核心的业务路径——如果基本流挂了，用户什么也做不了，优先级最高     |
| 每个备选流单独测就行   | 备选流需要和基本流组合——因为用户是在某个步骤触发备选流，然后可能回到基本流     |

【我的理解】

## 三、场景法的优缺点

### 知识点3：场景法的适用范围和局限

【课程原话/定义】
- **优点**：涉及业务流程的业务需求适合用场景法
- **缺点**：只验证业务流程，不验证单点功能。一般先采用等价类、边界值、错误推断、判定表等方法对单点功能进行验证，验证通过后再采用场景法进行业务流程验证

【为什么？】
这个"缺点"其实是正确的工程顺序——不是场景法不行，而是：

1. 场景法测的是**依赖链**：流程中 A→B→C，如果 A 本身是坏的，B 和 C 的场景测试没意义
2. 单点功能是场景的**基本面**：先确认每个步骤单独正常，再串联测流程——否则 debug 成本极高（你不知道是哪个步骤出了问题）
3. 所以场景法**必须排在等价类/边界值/判定表之后**，这是测试执行的依赖顺序，不是"重要性"的排序

【必须掌握】
- 场景法的优势：端到端验证业务流程，发现单点测试无法发现的流程性缺陷
- 场景法的局限：不覆盖单点细节，需要前置方法配合
- 正确的测试顺序：单点验证 → 场景验证（先局部后整体）

【企业场景】
> 你测试一个贷款申请系统。如果你先跑场景法（注册→认证→申请→审批→放款），过程中审批失败，你不知道是因为"身份证号输入框的边界值问题"还是"审批逻辑的判定表问题"——定位成本太高。正确顺序：先用等价类+边界值验证每个输入框，再用判定表验证审批规则，最后用场景法跑通整个流程。

【面试考察】
> 面试官："场景法有什么局限性？实际项目中如何和其他方法配合？"
**参考回答框架：**
1. 场景法只验证流程，不验证单点功能的细节（如输入框的边界值）
2. 配合顺序：先等价类+边界值（单点输入）→ 判定表（多条件规则）→ 场景法（端到端流程）
3. 场景法中每个步骤的数据仍用等价类/边界值的设计思路选取
4. 比喻：单点是零件质检，场景是整机测试——先质检零件，再测试整机

【易错点】

| ❌ 错误理解 | ✅ 正确理解 |
|------------|------------|
| 场景法比等价类/边界值"高级" | 没有高级低级之分，只是测试维度不同——不能跳过单点测试直接做场景测试 |
| 先做场景法更高效 | 如果单点有 bug，场景测试大量失败且难以定位根因，反而低效 |
| 场景法不需要测试数据 | 场景法中每个步骤仍需要输入数据，只是数据选取不必穷举（用等价类代表值即可） |

【我的理解】

## 四、场景法设计步骤（6步）

### 知识点4：从流程图到测试用例的完整流程

【课程原话/定义】
1. 根据需求规格说明，画出功能模块流程图
2. 根据流程图，描述出程序的基本流及备选流
3. 根据基本流和备选流生成不同的场景，构造场景列表
4. 对每一个场景生成相应的测试用例
5. 对生成的所有测试用例重新复审，去掉多余的测试用例
6. 测试用例确定后，为每一个测试用例确定测试数据值

【为什么？】
6 步的背后逻辑是层层递进：

- 第 1 步（流程图）→ 可视化业务流程，不画流程图直接写场景一定会漏
- 第 2 步（基本流+备选流）→ 从图中提取文本化的路径描述
- 第 3 步（场景列表）→ 组合基本流和备选流，形成"测试目标"
- 第 4 步（测试用例）→ 将场景落地为可执行的用例（含步骤、预期结果）
- 第 5 步（复审去重）→ 识别重复覆盖的场景，删减
- 第 6 步（测试数据）→ 为用例填充具体数据

这是从抽象到具体、从全貌到细节的逐层细化过程。

【必须掌握】
- 6 步顺序和每步的目的
- 第 1 步画流程图是基础——不画图直接写场景是常见错误
- 第 5 步去重是效率关键——多个场景可能本质上是同一条路径
- 第 6 步的数据确定——场景法不穷举数据，只取代表性数据

【企业场景】
> 你接到一个"用户注册-实名认证-绑定银行卡"的测试任务。你按 6 步来：先画流程图（确认分支点：手机验证失败→重试/换号，实名认证驳回→补充材料，绑卡失败→换卡），再列基本流和 9 个备选流，组合出 12 个场景，去重后剩 9 个，最后填数据。PM 看了你的场景列表说"原来用户绑卡失败后没有引导去帮助中心，这是需求漏了"——场景法不仅发现了测试点，还反哺了需求。

【面试考察】
> 面试官："拿到一个新需求，你用场景法设计测试用例的完整步骤是什么？"
**参考回答框架：**
1. 第一步：画业务流程图（关键！不画图会漏）
2. 第二步：标出基本流（一条主线）+ 每个节点的备选流
3. 第三步：组合场景（1 个纯基本流 + N 个基本流+某个备选流）
4. 第四步：为每个场景写用例（前置条件、步骤、预期结果）
5. 第五步：复审去重（合并路径相同的场景）
6. 第六步：为每条用例确定测试数据

【易错点】

| ❌ 错误理解 | ✅ 正确理解 |
|------------|------------|
| 第 1 步画流程图多余，直接写场景更快 | 流程图帮你识别隐藏的分支和循环——不画图直接写，遗漏率非常高 |
| 第 5 步去重 = 尽量删减用例 | 去重是去掉"路径完全相同"的场景——如果两条场景走的路径一样但数据不同，保留一条即可 |
| 第 6 步数据随便填一个就行 | 数据仍需考虑等价类和边界值——只是不需要穷举每条等价类的所有代表值 |

【我的理解】

## 五、场景法实战：淘宝购物流程

### 知识点5：淘宝购物流程的场景法分析

> ![[Pasted image 20260706155353.png|542]]
> ![[Pasted image 20260706155250.png|514]]

【课程原话/定义】

**基本流（主成功路径）：**
1. 进入淘宝首页
2. 浏览商品
3. 进入单品页
4. 选择商品规格和数量
5. 加入购物车
6. 前往购物车
7. 选择商品
8. 结算，进入确认订单页
9. 提交订单
10. 付款成功
11. 等待收货
12. 确认收货

**备选流（异常分支）：**

| 编号 | 触发时机 | 描述 | 处理方式 |
|------|---------|------|---------|
| 备选流1 | 步骤4 | 不选择商品规格和型号就添加购物车 | 回到步骤4 |
| 备选流2 | 步骤4 | 商品库存不足 | 回到步骤4 |
| 备选流3 | 步骤5 | 未登录 | 登录后回到步骤3 |
| 备选流4 | 步骤5 | 加入购物车后继续选购 | 回到步骤4 |
| 备选流5 | 步骤8 | 购物车中未选择商品，直接结算 | 回到步骤7 |
| 备选流6 | 步骤10 | 支付失败 | 回到步骤8 |
| 备选流7 | 步骤5 | 没有添加任何商品，退出 | 结束 |

**场景列表（8个）：**

| 场景 | 描述 | 涉及流 |
|------|------|--------|
| 场景1 | 登录后成功购物 | 基本流 |
| 场景2 | 未选规格就添加购物车 | 基本流 + 备选流1 |
| 场景3 | 商品库存不足 | 基本流 + 备选流2 |
| 场景4 | 未登录添加购物车 | 基本流 + 备选流3 |
| 场景5 | 添加购物车后继续选购 | 基本流 + 备选流4 |
| 场景6 | 未选商品直接结算 | 基本流 + 备选流5 |
| 场景7 | 支付过程出错 | 基本流 + 备选流6 |
| 场景8 | 没有添加商品到购物车 | 基本流 + 备选流7 |

【为什么？】
淘宝购物流程是场景法教学的经典案例，因为它有以下特点：

1. **流程足够长**（12步基本流）→ 能展示场景法的覆盖策略
2. **备选流多样化**：有"回到上一步继续"（备选流1/2/5）、有"跳转登录后返回"（备选流3）、有"彻底结束"（备选流7）、有"支付失败"（备选流6）
3. **备选流的处理方式不同**：有的需要重试（选规格），有的需要外部操作（登录），有的是系统状态问题（库存不足）
4. **场景 = 基本流 + 某个备选流**这个组合模式是场景法的标准范式

注意：课程中每个场景只组合了一个备选流。真实项目中可能有"多个备选流同时触发"的复杂场景（如既库存不足又未登录），但教学上先掌握单备选流组合。

【必须掌握】
- 能独立完成一个中等复杂度流程的场景法分析
- 能从基本流中每个步骤反向推导备选流
- 场景组合的范式：基本流 + 0/1/N 个备选流
- 备选流不一定意味着"失败"，可能是"绕路"或"触发额外操作"

【企业场景】
> 你在测试一个外卖下单系统，基本流 8 步。你按淘宝购物流程的模式分析出 12 个备选流：超出配送范围、店铺已打烊、优惠券过期、地址不完整、支付密码错误、余额不足、取消订单后重新下单...设计 13 个场景，PM 追问"如果用户支付成功后商家取消订单呢？"——这是你没考虑到的备选流！好在你及时发现并补充，否则这就是线上的一个漏测。

【面试考察】
> 面试官："给你一个登录→搜索→加入购物车→下单的流程，用场景法设计测试场景。"
**参考回答框架：**
1. 先画流程图，标出 4 个主要步骤和每个步骤的分支
2. 基本流：正常登录→搜索成功→加入购物车→下单成功
3. 备选流：登录失败（密码错/账号不存在/验证码错）、搜索结果为空、商品已下架、库存不足、购物车为空、地址无效、支付失败...
4. 组合场景：基本流 × 1 + 每个备选流 × 1 = 约 10-15 个场景
5. 保证每个备选流至少被覆盖一次

【易错点】

| ❌ 错误理解 | ✅ 正确理解 |
|------------|------------|
| 场景法分析完 12 步基本流就完了 | 核心工作是识别备选流——每个步骤问"如果这步出问题会怎样？" |
| 备选流越多越好 | 备选流要从需求和系统交互中识别，不是凭空想象——过度设计会增加不必要的工作量 |
| 场景数 = 基本流1条 + 备选流N条 | 有时需要多备选流组合（如登录失败后重试又失败），这种复杂场景也要覆盖 1-2 条 |

【我的理解】

## 六、场景法与其他黑盒方法的关系总结

### 知识点6：四种方法的协作模式

【课程原话/定义】
（综合前面四节课程的隐含逻辑）

场景法只验证业务流程，不验证单点功能——一般先用等价类、边界值、错误推断、判定表等方法对单点功能进行验证，验证通过后再采用场景法进行业务流程验证。

【为什么？】
到这里，四种黑盒测试方法形成了完整的测试维度金字塔：

```
           /\
          / 场景法 \        ← 端到端流程（业务流程正确性）
         /----------\
        /  判定表法  \       ← 多条件组合（逻辑规则正确性）
       /--------------\
      / 边界值分析法   \     ← 边界精度（范围边界正确性）
     /------------------\
    /  等价类划分法      \   ← 输入覆盖（类型/分类正确性）
   /----------------------\
```

- 等价类和边界值 = 底层，每个输入框的"基本功"
- 判定表 = 中层，多个输入条件的"组合逻辑"
- 场景法 = 顶层，整个业务流程的"端到端"

四种方法不是选择关系，是**叠加关系**——一个完整的功能测试通常四种都用。

【必须掌握】
- 四种方法各自解决什么问题，面试能讲清楚区别
- 测试执行顺序：等价类/边界值（单点）→ 判定表（组合）→ 场景法（流程）
- 不是说"等价类测完就完了"——场景法中每个步骤的数据仍然要用等价类+边界值思路来选

【企业场景】
> 你写一个电商系统的测试计划，测试经理问"你计划用什么方法？"你的回答：
> - "对注册表单的每个输入框，用等价类+边界值覆盖单个字段"
> - "对运费计算规则、优惠券叠加规则，用判定表覆盖多条件组合"
> - "对整个下单→支付→发货→收货流程，用场景法覆盖端到端业务"
> 这个回答展示了完整的测试方法论体系，比只说"我会好好测"高出一个级别。

【面试考察】
> 面试官："等价类、边界值、判定表、场景法，四种方法分别在什么时候用？"
**参考回答框架：**
1. 等价类 → 任何有输入的地方，先做分类覆盖
2. 边界值 → 输入有范围/个数限制时，在等价类基础上补充边界精度
3. 判定表 → 多个输入条件存在逻辑组合关系，不同组合产生不同输出
4. 场景法 → 有明确的用户操作流程，端到端验证业务闭环
5. 实际项目 = 四种方法的叠加使用，不是四选一

【易错点】

| ❌ 错误理解 | ✅ 正确理解 |
|------------|------------|
| 场景法最重要，其他三种可以省 | 没有单点质量保证，场景流程再完整也不可靠——流程中任何一个节点崩了，场景就断了 |
| 学了场景法就不用判定表了 | 场景法中某个步骤可能涉及规则判断（如"是否符合优惠条件"），这个子步骤仍需要判定表 |
| 四种方法是四个独立工具，选一个用 | 四种方法是同一个测试策略的不同层次，上层依赖下层的结果 |
