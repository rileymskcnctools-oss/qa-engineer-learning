## 一、设计方法的选择

### 知识点1：5 种方法的选用规则

【课程原话/定义】
前面学过的黑盒测试方法不止一种，设计测试用例时需要综合考虑和选择：

| 条件              | 选用方法                      |
| --------------- | ------------------------- |
| 任何情况下           | **等价类划分法** —— 将无限测试变成有限测试 |
| 规定了数据范围         | **边界值分析法** —— 必须采用        |
| 关注业务流程、业务逻辑是否正确 | **场景法**                   |
| 含有输入条件的组合       | **因果图 / 判定表法**            |
| 补充遗漏            | **错误推断法** —— 基于经验追加用例     |

【为什么？】
方法不是越多越好，而是**看需求特征匹配方法**：

- **等价类是底线**：没有任何输入能穷举，等价类让"不可穷举"变成"有限代表"——所以任何情况都要用
- **边界值是经验法则**：开发写 `if age >= 18` 最容易在 `age=18` 这个边界写错（写成 `>` 或 `>=`）——所以有范围就必须测边界
- **场景法是业务流程的翻译**：用户不会单独测"输入密码"，他走的是"打开页面→输入账号→输入密码→点登录"一整条路径——场景法模拟的是**真实用户行为**
- **判定表是组合爆炸的克星**：当输入条件互相影响（如"会员等级 × 优惠券 × 满减"），不画判定表一定会漏测组合

【必须掌握】
- 等价类：任何情况都用（底线）
- 边界值：有数据范围必须用
- 场景法：管业务流程
- 判定表/因果图：管条件组合
- 错误推断：管补充（经验驱动）

【企业场景】
> 你拿到一份新需求：用户注册功能，包含手机号（11位）、密码（8-12位数字+英文）、验证码（6位数字）、勾选用户协议。你先用等价类划分有效/无效手机号、有效/无效密码；发现手机号有范围（11位）和密码有长度范围，补充边界值；然后画出正常注册的整个流程（场景法）；再考虑密码格式是"数字+英文"的组合条件，补判定表；最后凭经验追加：不勾协议点注册会怎样、验证码过期、验证码错误3次——这5种方法不是孤立的，是**叠加使用**的。

【面试考察】
> 面试官："等价类和边界值什么关系？为什么说两者要一起用？"
**参考回答框架：**
1. 等价类先分类（有效类、无效类），边界值再从每类的边界处取数据
2. 等价类让你不遗漏分类，边界值让你在分类内选对数据点
3. 举例：年龄 18-60 → 等价类划分：有效（18-60）、无效（<18）、无效（>60）；边界值取：17, 18, 60, 61

【易错点】

| ❌ 错误理解 | ✅ 正确理解 |
|------------|------------|
| 每个需求只用一种方法就够了 | 一个需求通常需要 2-4 种方法叠加——等价类+边界值几乎永远一起用 |
| 错误推断法是乱猜 | 错误推断基于经验——如"空文件上传"、"超长字符"、"并发点击"——是有方向的推测 |
| 有输入组合就必须用判定表 | 条件 ≤3 个时可以用判定表，条件太多（>5）时判定表会爆炸，改用正交实验法 |

【我的理解】

## 二、测试用例编写步骤

### 知识点2：5 步编写流程

【课程原话/定义】
测试用例编写的标准 5 步：

```
Step 1: 划分功能模块 → 用思维导图拆分大功能里的小功能点
Step 2: 正向功能验证 → 先把正向操作走通（相当于冒烟测试）
Step 3: 单个功能项验证 → 每个小功能点单独验证
Step 4: 功能之间交互验证 → 验证场景级用例
Step 5: 隐形需求 → 产品特性验证 + 特殊业务场景验证
```

【为什么？】
这 5 步的顺序不能乱，因为：

1. **先拆分再验证**：不拆分就写用例 = 凭感觉测，一定会漏
2. **先正向再异常**：正向是主路径，正向都跑不通，测异常没有意义
3. **先单点再交互**：单点 Bug 没解决就去测交互场景，出了问题无法定位
4. **最后补隐形需求**：产品文档不会写"这个按钮应该在3秒内响应"，但用户期望它快——这些是隐形需求，必须单独一轮思考

这就像盖房子：先画图纸（拆分）→ 先建主体（正向）→ 检查每个房间（单点）→ 检查水电连通（交互）→ 看看住着舒不舒服（隐性需求）。

【必须掌握】
- 5 步顺序和每步产出
- Step 2 正向 = 冒烟测试，先保证主流程通
- Step 5 隐性需求 = 产品没写但用户期望的行为

【企业场景】
> 你拿到一个新功能开始写用例。你直接开始想各种异常情况——"密码为空"、"密码太短"、"账号不存在"。写完 20 条异常用例后执行，发现一个都没法跑：因为正常的登录流程压根没走通——登录按钮点了没反应，是前端 JS 报错。你浪费了 30 分钟写异常用例，而实际上第一步应该是"先看看正常登录能不能走通"。

【面试考察】
> 面试官："你设计测试用例的流程是怎样的？"
**参考回答框架：**
1. 先分析需求，用导图拆分功能模块
2. 设计正向用例（冒烟级别），保证主流程能跑通
3. 逐个子功能点设计单点用例
4. 设计跨功能的场景交互用例
5. 补充隐性需求和异常场景

【易错点】

| ❌ 错误理解     | ✅ 正确理解                                |
| ---------- | ------------------------------------- |
| 5 步做完就完事了  | 5 步是一轮，需求变更后需要重新走一轮（回归用例更新）           |
| 隐性需求可以不做   | 隐性需求往往是用户投诉的来源——"虽然没说，但你就应该这样"        |
| 正向验证就是一条用例 | 一个功能可能有多条正向路径——如登录可以手机号+密码，也可以手机号+验证码 |

【我的理解】

## 三、需求分析实例（登录页）

### 知识点3：从需求文档提取测试点

【课程原话/定义】
需求原文：
- 帐号是手机号
- 手机号仅限制为国内常用的号段
- 密码必须为 数字+英文 的形式，字段为 8-12 个字符
- 账号密码都为空时，登录按钮置灰不可点击
- 点击登录按钮，发起登录请求
- 请求成功，跳转到首页
- 点击忘记密码跳转到找回密码页

【为什么？】
这个简单的 7 条需求，隐藏了大量测试点。测试工程师的价值就是把这些"简洁的需求"翻译成"可验证的测试点"：

| 需求            | 表面含义          | 需要测什么（展开）                           |
| ------------- | ------------- | ----------------------------------- |
| 账号是手机号        | 输入框只接受手机号     | 空、非手机号格式、含空格、含特殊字符、境外号段             |
| 国内常用号段        | 13x/15x/18x 等 | 非国内号段能不能注册？联通/移动/电信号段是否都支持？         |
| 密码数字+英文，8-12位 | 格式+长度双重约束     | 纯数字、纯英文、含中文、含特殊字符、7位、13位、8位边界、12位边界 |
| 都为空时按钮置灰      | 按钮状态联动        | 一个空一个有值 → 按钮亮不亮？输入后删除到空 → 按钮变灰？     |
| 点击登录发起请求      | 触发网络请求        | 弱网环境？请求超时？服务器返回 500？连续快速点击？         |
| 请求成功跳转首页      | 成功后的行为        | 跳转后按返回键会不会回到登录页？token 是否存储？         |
| 忘记密码跳转        | 页面跳转          | 跳转后按返回键？如果已登录状态点忘记密码？               |

【必须掌握】
- 能从一条需求展开出 3-5 个测试方向
- 需求中的"隐含条件"（如"8-12位"意味着要测 7 位和 13 位）

【企业场景】
> PM 给你需求文档："登录页，输入账号密码，点登录，成功进首页。" 一共一句话。如果你只按这一句话写用例，3 条就写完了。但实际这个页面涉及 30+ 条用例：各种格式的账号、边界值密码、网络异常、并发、安全（SQL注入/XSS）。PM 不会写这些，但测试必须想到——这就是测试的价值。

【面试考察】
> 面试官："给你一个登录页面的需求，说说你会设计哪些测试用例？"
**参考回答框架：**
1. UI 层：页面元素展示、按钮置灰逻辑、密码掩码
2. 功能层：正确登录、各种错误组合（账号错/密码错/都错/空）
3. 边界层：密码长度 7/8/12/13、手机号格式边界
4. 安全层：SQL注入、XSS、密码传输加密、错误次数限制
5. 体验层：弱网提示、loading状态、返回键行为

【易错点】

| ❌ 错误理解 | ✅ 正确理解 |
|------------|------------|
| 需求没写的就不用测 | 需求没写但用户会做的必须测——如连续点登录按钮 10 次 |
| 拿到需求就开始写用例 | 先充分分析需求中的隐藏条件（如"8-12位"隐含了边界）再动笔 |
| 登录页很简单不用太细 | 登录是系统的门——门坏了，里面装修再好也进不去。P0 中的 P0 |

【我的理解】

## 四、测试用例的粒度

### 知识点4：粗细权衡

【课程原话/定义】
测试用例可以写得简单，也可以写得复杂：

- **太简单**：只覆盖正向功能，异常场景全漏 → 保证不了健壮性，发现问题的能力差
- **太复杂**：写用例费时间、执行费时间、维护成本高 → 投入产出比低
- **太详细**：留给执行者的思考空间少，容易限制测试人员的思维

**结论**：在场景覆盖完整的情况下尽量精简，平衡投入产出比。同时遵守公司规范。

【为什么？】
这个问题的本质是**测试用例是一种"沟通文档"**，不是学术论文：

| 维度 | 太粗 | 太细 |
|------|------|------|
| 写用例时间 | 快，但质量差 | 慢，3 天写 50 条 |
| 执行效率 | 执行者要自己脑补步骤 | 执行者像机器人一步一步走 |
| Bug 发现率 | 低——异常场景没设计 | 可能也低——限制了探索性思维 |
| 维护成本 | 低——条目少 | 高——需求变更后要改 500 条 |
| 交接友好度 | 差——新人看不懂 | 中——新人能执行但会变呆 |

**最佳平衡点**：一个好的用例应该让执行者知道"测什么 + 怎么操作 + 什么算对"，但**不需要写到点击坐标级别**。

【必须掌握】
- 太粗的后果：异常场景漏测、发现 Bug 能力差
- 太细的后果：效率低、维护成本高、限制思维
- 判断标准：场景覆盖完整 + 尽量精简 + 遵守公司规范

【企业场景】
> 你入职新公司，拿到上一任留下的 2000 条用例。你花了一周熟悉后，发现 2000 条里 800 条是重复的（同一个功能分了 5 条用例，每条只差一个参数），300 条过时了（需求早就改了），真正有效的只有 900 条。现在每次需求变更，你得维护 2000 条——这就是"太细"的代价。

【面试考察】
> 面试官："测试用例写到什么粒度合适？"
**参考回答框架：**
1. 没有统一标准，取决于公司规范 + 项目阶段 + 团队水平
2. 基本原则：场景覆盖完整 + 步骤清晰 + 预期结果可验证
3. 不写到"点击坐标"级别，但要写到"输入什么 + 预期看到什么"
4. 新人多的团队用例要写得稍详细；老手团队可以偏概要
5. 核心功能（P0/P1）要详细，边缘功能（P3）可以精简

【易错点】

| ❌ 错误理解 | ✅ 正确理解 |
|------------|------------|
| 用例越详细越专业 | 过度详细的用例是在"编程"而不是"测试"——执行者变成了人工脚本执行器 |
| 简明用例 = 不专业 | 用 20 个字说清一条用例，比用 200 个字更有水平 |
| 有模板就行，不用想粒度 | 模板是框架，粒度是策略——两个层面的问题 |

【我的理解】

## 五、测试用例评审

### 知识点5：评审的 8 个检查维度

【课程原话/定义】
用例评审时检查以下方面：

1. 用例描述是否清晰，是否存在二义性
2. 用例内容是否正确，是否与需求目标一致
3. 期望结果是否确定、唯一
4. 是否覆盖了所有需求
5. 是否具有可执行性
6. 是否从用户层面设计使用场景和业务流程
7. 场景用例是否覆盖最复杂的业务流程
8. 是否包含正面和反面的用例

【为什么？】
这 8 条背后是三个核心问题：

- **清晰性（1, 3, 5）**："别人能看懂、能执行吗？"——用例是写给执行者的，不是写给自己看的
- **完整性（4, 6, 7, 8）**："测全了吗？"——正向+反向+复杂场景+所有需求点
- **正确性（2）**："和需求对得上吗？"——需求改了用例没改 = 测试在验证过时的预期

评审不是挑刺，是**集体防漏**——一个人一定会漏，三个人一起看能补上很多盲区。

【必须掌握】
- 8 个检查维度的名称和含义
- 最核心的 3 条：清晰（1/3）、完整（4/8）、正确（2）

【企业场景】
> 用例评审会上，你写了 50 条用例投屏。同事看了 5 分钟说："第 23 条，预期结果写'登录成功'——但到底是跳到首页还是停留在当前页弹 toast？" 你发现确实没写清楚。另一同事："安全相关的用例一条都没有？SQL 注入、XSS、暴力破解？" 你愣住——完全没想到。如果没有评审会，这些漏测就直接上线了。

【面试考察】
> 面试官："你参加过用例评审吗？评审时主要看什么？"
**参考回答框架：**
1. 参加过。用例评审是测试团队+开发+产品的联合会议
2. 主要看：描述是否清晰无歧义、是否覆盖所有需求、正向反向是否都覆盖、期望结果是否可验证
3. 还会关注：是否有遗漏的业务场景、边界条件是否覆盖
4. 评审的价值：提前发现遗漏，减少执行阶段返工和线上事故

【易错点】

| ❌ 错误理解 | ✅ 正确理解 |
|------------|------------|
| 评审就是走形式 | 评审是最后一道防线——用例阶段发现遗漏的成本远低于执行后补测 |
| 评审只让测试同事看 | 产品看是否覆盖需求，开发看是否理解技术边界——多方参与才能补全视角 |
| 用例通过评审就不用改了 | 需求变更后用例要重新评审——评审不是一次性的 |

【我的理解】
