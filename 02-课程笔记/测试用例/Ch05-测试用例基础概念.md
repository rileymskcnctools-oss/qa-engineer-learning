## 一、什么是测试用例

### 知识点1：测试用例的定义与本质

【课程原话/定义】
测试用例（Test Case）是为特定的目的而设计的一组测试输入、执行条件和预期的结果的文档。有了这个文档之后，就算是不太了解这个系统的人，也可以按照测试步骤的指引，一步一步去操作。最后把实际结果和预期结果做对比：一致标注 Pass，不一致标注 Fail，然后提 Bug 让开发修改。

【为什么？】
测试用例的本质是**一组可复现、可验证的指令**。它的核心价值不在于"测了什么"，而在于：

1. **可复现**：换一个人，换一个时间，按同一个用例操作，得到的结果应该可复现
2. **可传递**：测试知识不绑定在某个人的大脑里，而是固化在文档中
3. **可追溯**：每条用例对应需求中的某个点，出问题时能回溯到"哪个需求没被满足"
4. **可度量**：通过 Pass/Fail 统计，量化测试进度和质量

如果不写用例，只凭感觉"点点点"——这叫**探索性测试**，不是不可以，但无法沉淀、无法复用、无法证明你测完了。

【必须掌握】
- 测试用例 = 输入 + 执行条件 + 预期结果 + 实际结果对比
- 核心目标：让任何人按用例操作都能得到一致结果
- 实际结果 ≠ 预期结果 → Fail → 提 Bug

【企业场景】
> 周一你请假了，测试经理让新同事执行你写的用例。他完全不了解这个系统，但按你用例里的步骤一步步操作，最后对比预期结果，发现 3 条 Fail，提了 3 个 Bug。周二你回来，经理说"你写的用例质量不错，新人也能执行"——这就是好的测试用例：不依赖个人经验，任何人拿到都能执行。

【面试考察】
> 面试官："什么是测试用例？为什么要写测试用例？"
**参考回答框架：**
1. 定义：一组包含输入、执行条件、预期结果的文档，用于验证系统是否满足需求
2. 为什么要写：
   - 确保测试的可复现性和一致性
   - 测试知识沉淀，不依赖个人记忆
   - 覆盖度可衡量（写了多少条，覆盖了多少需求点）
   - 新人/交接时的执行指南
3. 好的用例标准：其他人不看需求文档，只看用例就能独立执行

【易错点】

| ❌ 错误理解 | ✅ 正确理解 |
|------------|------------|
| 测试用例就是操作步骤 | 操作步骤只是用例的一部分——没有预期结果的用例是残废的，因为你不知道"对"长什么样 |
| 测试用例写完就不用改了 | 需求变更时用例必须同步更新，否则过时的预期结果会导致误判 |
| 用例越详细越好 | 过于冗长的用例反而没人看——关键是步骤清晰、预期结果明确，不是字数多 |

## 二、测试用例的组成要素

### 知识点2：测试用例的 8 个组成部分

> ![[Pasted image 20260706155917.png]]

【课程原话/定义】
测试用例应包含以下要素（部分非必须）：

| 要素 | 说明 | 是否必须 |
|------|------|---------|
| **用例编号** | 唯一标识，如 TC-LOGIN-001 | 必须 |
| **模块** | 所属功能模块，如"登录模块" | 必须 |
| **测试点（测试标题）** | 简要描述这条用例测什么 | 必须 |
| **优先级** | P0/P1/P2/P3 | 必须 |
| **前提条件** | 执行前需要满足的条件（如"已有注册账号"） | 非必须 |
| **测试步骤** | 逐步操作描述 | 必须 |
| **期望结果** | 每一步操作后系统应有的响应 | 必须 |
| **实际结果** | 执行后填写，Pass/Fail + 备注 | 执行时填 |

【为什么？】
8 个要素不是随便列的，每个都有不可替代的工程价值：

- **用例编号**：唯一标识 → 便于引用（"执行 TC-LOGIN-001 到 TC-LOGIN-020"）、便于缺陷关联（"Bug #42 在 TC-003 中被发现"）
- **模块**：分类维度 → 按模块统计覆盖率和缺陷密度，定位薄弱模块
- **测试点**：一句话描述 → 快速浏览时不用读全部步骤就知道这条测什么
- **优先级**：执行顺序 → 时间不够时先跑 P0/P1
- **前提条件**：环境依赖 → 避免"咦你怎么没先创建用户？"的无效执行
- **测试步骤**：操作路径 → 可复现性的核心
- **期望结果**：判断标准 → 没有它，执行者不知道"对还是错"
- **实际结果**：执行记录 → 测试的证据链

【必须掌握】
- 8 个要素名称和作用，面试可能让列举
- "前提条件"和"实际结果"不是每次都要填，但要理解为什么可以留空
- 用例编号、模块、测试点、优先级、测试步骤、期望结果是最核心的

【企业场景】
> 你写了 50 条用例给测试经理 review。经理扫了一眼说："你这些用例都没有预期结果，执行的人怎么知道你写的是对的还是错的？"你赶紧补上。另一件事：同事执行你的用例时反复来问你"这个数据要先准备什么？"——因为你忘了写前提条件。这两件事说明 8 个要素各有各的价值，缺一个就会给后续环节添麻烦。

【面试考察】
> 面试官："一个完整的测试用例包含哪些要素？"
**参考回答框架：**
1. 必须要素：用例编号、模块、测试标题、优先级、测试步骤、期望结果
2. 非必须但重要：前提条件、实际结果
3. 每个要素的作用要能说清楚（如"用例编号是为了唯一标识和缺陷关联"）
4. 加分项：提到不同公司可能用不同模板，但核心要素基本一致

【易错点】

| ❌ 错误理解 | ✅ 正确理解 |
|------------|------------|
| 预期结果写"功能正常"就够了 | "功能正常"太模糊——应该写具体的系统行为，如"页面跳转到首页，右上角显示用户名" |
| 测试步骤写得越细越好 | 步骤要精确但不过度——"输入用户名 admin"够了，不需要写"将光标移到输入框，单击左键..." |
| 实际结果是必填项 | 实际结果在执行用例时填写，写用例时留空。另外，实际结果应包括 Pass/Fail + 截图/Bug ID |

## 三、测试用例的优先级

### 知识点3：P0-P3 四级优先级体系

【课程原话/定义】
测试用例根据重要性分成 4 个等级（不同公司可能略有差异，但大同小异）：

| 等级 | 定义 | 典型场景 |
|------|------|---------|
| **P0** | 核心功能测试用例 | 阻断性问题——系统崩溃、核心流程不通、登录失败 |
| **P1** | 高优先级测试用例 | 主要功能异常——重要模块报错、数据错误 |
| **P2** | 中优先级测试用例 | 非核心功能、边界条件、兼容性问题 |
| **P3** | 低优先级测试用例 | UI 文案、易用性建议、低频操作路径 |

【为什么？】
优先级不是拍脑袋决定的，背后的逻辑是 **风险 × 影响**：

- **P0 = 阻塞性**：这个问题不解决，系统没法用。如登录挂了 → 所有功能都无法访问
- **P1 = 主流程**：核心业务路径上的问题。如支付成功但订单未生成
- **P2 = 次要功能**：影响用户体验但不阻塞主流程。如搜索筛选功能异常
- **P3 = 锦上添花**：不影响功能正确性。如按钮颜色偏差、提示文案不够友好

**时间不够时的执行策略**：P0 全部执行 → P1 全部执行 → P2 尽可能 → P3 看情况。这叫**基于风险的测试**。

【必须掌握】
- 四级优先级的定义和典型场景，面试可能问"你怎么确定一条用例的优先级？"
- P0 的核心判断标准：这个功能挂了，系统还能用吗？
- 优先级可以动态调整——原本 P2 的用例，如果开发说这块代码改动很大，可以升级为 P1

【企业场景】
> 周五下午 5 点，测试经理说"下周一上线，今天必须跑完"。你手里 200 条用例，时间只够跑 80 条。怎么办？按优先级：P0（15条）→ 全部跑完；P1（35条）→ 全部跑完；P2（80条）→ 挑最近改动的跑 30 条；P3（70条）→ 来不及了。周一上线后没有 P0/P1 级别的线上事故——这就是优先级管理的价值。

【面试考察】
> 面试官："测试用例的优先级怎么划分？为什么 P0 最高？"
**参考回答框架：**
1. 一般分 P0-P3 或 Blocker/Critical/Major/Minor
2. 划分依据：功能重要性 × 失效影响范围
3. P0 = 核心功能 + 阻断性影响（登录失败、支付失败、数据丢失）
4. 优先级作用：指导测试执行顺序，确保有限时间下先测最重要的
5. 不同公司定义可能不同，但核心逻辑一致

【易错点】

| ❌ 错误理解 | ✅ 正确理解 |
|------------|------------|
| P0 就是需求文档里标注"重要"的功能 | P0 需要判断"失效后的影响"——一个功能可能很重要但即使挂了也不影响主流程 |
| 一条用例的优先级固定不变 | 上线前回归阶段，核心流程的 P2 可能升为 P1；新功能第一次测，P1 可以降为 P2 |
| P3 的用例可以不做 | P3 不是"不用做"，而是"资源不足时可以最后做"——有些 P3 的易用性问题长期积累会影响用户留存 |

【我的理解】

## 四、测试用例设计工具

### 知识点4：思维导图 vs 表格形式

> 图片位置（思维导图形式的测试用例）
> 图片位置（表格形式的测试用例）

【课程原话/定义】
测试用例的两种常见承载形式：

- **思维导图**：用 XMind 等工具画出功能模块→测试点→用例的树状结构，直观展示测试覆盖范围
- **表格形式**：用 Excel/在线文档，按 8 要素逐行填写，适合正式执行和归档

【为什么？】
两种形式不是二选一，而是**不同阶段用不同工具**：

| 阶段 | 推荐工具 | 原因 |
|------|---------|------|
| 用例设计/评审 | 思维导图 | 可视化覆盖度，一眼看出哪个分支测得多哪个分支没测 |
| 用例执行 | 表格（Excel） | 逐行执行、记录结果、统计 Pass/Fail |
| 归档/交接 | 表格/用例管理平台 | 标准的 8 要素格式，便于检索和复用 |

思维导图帮你"不遗漏"，表格帮你"可执行"。实际项目中最常见的组合：用 XMind 评审覆盖度 → 通过后导出/转录为 Excel → 导入 TAPD/JIRA 等用例管理平台 → 执行时逐条标记。

【必须掌握】
- 思维导图适合设计阶段（快速梳理、展示覆盖度）
- 表格形式适合执行阶段（逐条对照、记录结果）
- 两者可以转换——思维导图可以导出为表格
- 企业常用的用例管理平台：TAPD、JIRA + Zephyr、TestLink、飞书多维表格

【企业场景】
> 需求评审会上，你用 XMind 画了一张思维导图投屏：登录模块→正常登录/异常登录→密码错误/账号不存在/验证码错误/连续错误锁定。PM 一眼看出"连续错误锁定这个场景你没细分——锁定 30 分钟和永久锁定是两种处理"。你用 5 秒钟在导图上加了两个子节点。如果是 Excel 表格，你得翻 50 行才能发现自己漏了什么。这就是思维导图在评审阶段不可替代的原因。

【面试考察】
> 面试官："你平时用什么工具写测试用例？思维导图和表格各有什么优缺点？"
**参考回答框架：**
1. 思维导图（XMind/MindManager）：
   - 优点：可视化覆盖度、快速梳理、评审直观
   - 缺点：不方便逐条执行和记录结果
2. 表格（Excel/在线表格）：
   - 优点：标准格式、便于执行跟踪、统计方便
   - 缺点：不太直观、评审时不易看出遗漏
3. 企业实践：设计阶段用导图评审 → 执行阶段用表格 → 归档到用例管理平台
4. 加分项：提到具体的用例管理平台（TAPD/JIRA/TestLink）

【易错点】

| ❌ 错误理解 | ✅ 正确理解 |
|------------|------------|
| 思维导图就是"画个脑图"，不是正式用例 | 思维导图是正式的用例设计方法之一——很多大厂要求用例评审必须用导图展示覆盖度 |
| 用 Excel 就够了，不需要导图 | Excel 是线性结构，不利于展示"遗漏"——评审时别人很难从 200 行表格中发现你漏测了什么 |
| 用上了用例管理平台就万事大吉 | 平台只是载体——如果用例本身的逻辑有问题，什么平台都救不了 |

【我的理解】

## 五、测试用例的完整示例

### 知识点5：一个完整的测试用例应该长什么样

> 图片位置（完整测试用例示例表格）

【课程原话/定义】
以下为一个完整的测试用例示例（登录功能）：

| 要素   | 内容                                                |
| ---- | ------------------------------------------------- |
| 用例编号 | TC-LOGIN-001                                      |
| 模块   | 用户登录                                              |
| 测试点  | 输入正确的用户名和密码，验证登录成功                                |
| 优先级  | P0                                                |
| 前提条件 | 已注册账号：admin / 123456                              |
| 测试步骤 | 1. 打开登录页面 2. 输入用户名 admin 3. 输入密码 123456 4. 点击登录按钮 |
| 期望结果 | 登录成功，页面跳转到首页，右上角显示用户名"admin"                      |
| 实际结果 | Pass                                              |

【为什么？】
这个示例展示了"一条好用例"的标准：

1. **编号规范**：TC-模块-序号，一眼知道是哪里的第几条
2. **测试点明确**：读标题就知道测的是"正确账号密码登录成功"，不需要往下翻
3. **前提条件完备**：告诉了执行者"用哪个账号"——避免执行者随意注册新号导致数据污染
4. **步骤可操作**：每步一个动作，不是"登录一下"这种模糊描述
5. **预期结果具体**：不只是"登录成功"，而是"跳转到首页 + 显示用户名"——两个验证点

【必须掌握】
- 能独立写出符合 8 要素的完整用例
- 用例编号要有规范（如 TC-模块-序号）
- 预期结果要具体、可验证，不只写"成功"或"正常"

【企业场景】
> 你写了一条用例：测试点"验证登录功能正常"，步骤"登录系统"，预期结果"登录成功"。同事执行后问你"怎么才算登录成功？跳转到哪个页面？用户名显示在哪？"你发现自己的用例根本没法执行——因为预期结果太模糊。改写成"页面跳转到首页，右上角显示用户名，左侧菜单栏展开"——这才是一条可执行的用例。

【面试考察】
> 面试官："给你一个登录功能，写一条完整的测试用例。"
**参考回答框架：**
1. 用例编号：TC-LOGIN-001
2. 模块：登录模块
3. 测试点：正确用户名密码登录
4. 优先级：P0
5. 前提条件：已有测试账号 testuser / Test@123
6. 测试步骤：①打开登录页 ②输入 testuser ③输入 Test@123 ④点击登录
7. 期望结果：登录成功，跳转到首页，右上角显示"testuser"，左侧菜单可见
8. 实际结果：（执行后填写）

【易错点】

| ❌ 错误理解 | ✅ 正确理解 |
|------------|------------|
| 预期结果写"和需求一致" | 预期结果是给执行者看的，执行者可能不看需求文档——必须写清楚具体表现 |
| 测试步骤写"操作成功后进入下一步" | 步骤要有明确的动作——"操作成功"是什么操作？按哪个按钮？ |
| 一条用例只测一个验证点 | 一条用例可以包含多个验证点（跳转 + 显示用户名 + 菜单），但都属于同一个用户操作场景 |
