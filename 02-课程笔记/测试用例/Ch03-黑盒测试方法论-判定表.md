## 一、什么是判定表

### 知识点1：判定表的定义与定位

【课程原话/定义】
判定表是一种用于表示决策逻辑的表格形式。它以清晰的方式描述各种输入条件和相应输出结果之间的关系，使得决策逻辑更易理解和管理。因果图只是辅助工具，通过分析最终得到判定表，再通过判定表编写测试用例——有时画因果图非常麻烦，可以直接写判定表。

【为什么？】
等价类和边界值解决的是"**单个输入域**"的测试问题。但现实中的业务逻辑几乎都是"**多条件组合决策**"——多个输入条件共同决定一个输出。判定表要解决的核心问题是：

- 多个条件有 True/False 两种取值（N 个条件 = 2^N 种组合），如何**不重不漏**地覆盖所有组合？
- 如何识别出"某些条件在某些情况下无关"从而**精简用例**？

判定表的本质是**穷举所有条件组合 → 精简无关组合**，它是多条件决策场景下唯一能保证逻辑完备性的方法。

> 因果图（Cause-Effect Graph）是判定表的"前身"——用图形化方式推导条件与结果的逻辑关系，再转化为判定表。实践中因果图画起来耗时且容易出错，多数测试工程师直接从需求推导判定表。

【必须掌握】
- 判定表解决的核心问题：多条件组合决策
- 定位：等价类/边界值管"单个输入"，判定表管"多个条件的交叉组合"
- 因果图 → 判定表 → 测试用例，但因果图可跳过

【企业场景】
> 你在测试一个贷款审批系统，审批规则："① 信用分≥600，② 月收入≥5000，③ 有稳定工作。三个条件全满足→通过；满足任意两个→人工审核；只满足一个或不满足→拒绝"。如果用等价类单独测每个条件，你会漏掉"信用分700但月收入3000有稳定工作"这种组合。判定表列出 2^3=8 种组合，确保每个决策路径都被覆盖。

【面试考察】
> 面试官："什么时候用判定表法？和等价类/边界值有什么不同？"
**参考回答框架：**
1. 判定表适用于：多个输入条件之间存在逻辑组合关系，不同组合产生不同输出
2. 等价类/边界值关注单个输入域，判定表关注多条件之间的交叉决策
3. 典型场景：业务规则引擎、权限判断、费率计算、审批流程
4. 判定表的优势：穷举所有条件组合，不会遗漏任何决策路径

【易错点】

| ❌ 错误理解 | ✅ 正确理解 |
|------------|------------|
| 判定表替代等价类/边界值 | 三种方法解决不同维度的问题——等价类管分类、边界值管精度、判定表管组合 |
| 只有 True/False 的条件才能用判定表 | 条件可以有多个取值（如"会员等级：普通/银/金/钻石"），规则数 = 各条件取值数的乘积 |
| 因果图必须先画才能写判定表 | 因果图是可选步骤，对简单场景直接从需求推导判定表更高效 |

【我的理解】

## 二、判定表的四个组成要素

### 知识点2：条件桩、动作桩、条件项、动作项

【课程原话/定义】

| 要素      | 定义                  | 位置    |
| ------- | ------------------- | ----- |
| **条件桩** | 问题的所有条件（输入）         | 表格左上角 |
| **动作桩** | 问题的所有输出/动作          | 表格左下角 |
| **条件项** | 针对条件桩的取值（Y/N 或 0/1） | 表格右上角 |
| **动作项** | 各条件组合下的输出结果         | 表格右下角 |

【为什么？】
这个四象限结构并非随意设计：

- **桩（Stub）** = 列举"有哪些"——条件桩列举所有输入因素，动作桩列举所有可能结果
- **项（Entry）** = 填写"是什么"——条件项填每个规则下各条件的取值，动作项填该规则对应的输出

把"因素列表"（桩）和"组合矩阵"（项）分开，是为了让表格既能清晰展示有哪些条件，又能系统化地穷举组合。如果你把条件和取值混在一起写，遇到 5 个条件（32 条规则）时就会乱成一团。

【必须掌握】
- 四要素的定义和位置，面试可能直接问"判定表由哪几部分组成"
- 条件桩 = 有哪些输入条件，动作桩 = 有哪些可能输出
- 条件项 = 每种组合下条件取什么值，动作项 = 对应输出是什么

【企业场景】
> 你在测试一个电商运费计算规则："① 订单金额≥99 免运费，② VIP 会员免运费，③ 偏远地区加收 10 元"。你先列出条件桩（金额≥99?、VIP?、偏远地区?），再列出动作桩（免运费、收 10 元、收 20 元），然后填条件项（2^3=8 列），最后逐列填动作项。这个表格往开发面前一放，开发立刻就看出自己代码里"VIP+偏远地区"的组合逻辑有问题。

【面试考察】
> 面试官："判定表由哪几部分组成？各有什么作用？"
**参考回答框架：**
1. 四部分：条件桩（输入条件列表）、动作桩（输出结果列表）、条件项（各条件的取值组合）、动作项（各组合对应的输出）
2. 桩 = 列出"有哪些"，项 = 填写"是什么"
3. 四者关系：条件桩 × 条件项 = 每个规则下的条件状态；动作桩 × 动作项 = 每个规则下的输出

【易错点】

| ❌ 错误理解 | ✅ 正确理解 |
|------------|------------|
| 条件桩和条件项是一回事 | 条件桩 = 有哪些条件（表头），条件项 = 每个规则下条件的值（表体） |
| 动作桩就是"通过/不通过"两个 | 动作桩是所有可能的输出——有多少种不同的结果就有多少个动作桩 |
| 条件项只填 Y/N | 也可以填具体数值，如"金额区间：<99 / 99-500 / >500" |

【我的理解】

## 三、判定表设计步骤（5步）

### 知识点3：从需求到判定表的完整流程

【课程原话/定义】
1. 列出所有的条件桩和动作桩
2. 确定规则数：有 N 个条件，每个条件 2 个取值 → 规则数 = 2^N
3. 填入条件项
4. 填入动作项，得到初始判定表
5. 简化判定表（合并规则）

【为什么？】
这 5 步背后是"**先穷举，再精简**"的工程思路：

- 第 1-4 步确保逻辑完备——不遗漏任何条件组合。穷举本身没有技术含量，但**系统性穷举不遗漏**是有技术含量的（第 3 步的填写技巧）
- 第 5 步是判定表最有价值的一步——合并"某个条件不影响结果"的规则，本质上是识别条件之间的**独立性**

如果不做第 5 步（简化），N=5 时 32 条规则全部写成用例，冗余严重；简化后可能只剩 10-15 条。所以判定表的精髓在简化这一步。

【必须掌握】
- 5 个步骤的顺序和每步的目的
- 规则数公式：2^N（二值条件）或 各条件取值数之积（多值条件）
- 条件项填写技巧：C1 填半数0半数1、C2 填一半的一半...依次类推

【企业场景】
> 你测试一个保险理赔判断系统，6 个条件（事故类型、责任认定、保险类型、是否在保期内、是否首报、金额是否超额）。2^6=64 条规则。你按 5 步流程：先穷举 64 条填好初始表，然后发现"保险类型=交强险"时，"金额是否超额"这个条件不影响结果——合并后只剩 28 条有效规则。如果不简化，你会多写 36 条无意义的用例。

【面试考察】
> 面试官："判定表设计用例的步骤是什么？规则数怎么算？"
**参考回答框架：**
1. 五步：列条件桩+动作桩 → 算规则数 → 填条件项 → 填动作项 → 简化
2. 规则数 = 2^条件数（二值条件），或多值条件时 = 各条件取值数的乘积
3. 条件项填写有技巧：第一个条件一半0一半1，第二个条件一半的一半...依次折半
4. 简化原则：两条规则的动作相同且只有一个条件取值不同 → 该条件可合并（无关条件）

【易错点】

| ❌ 错误理解 | ✅ 正确理解 |
|------------|------------|
| 规则数就是最终用例数 | 规则数是初始值，简化后的有效规则通常远少于 2^N |
| 条件项可以随便填 | 必须用"折半法"系统填写，否则会遗漏或重复 |
| 简化就是随便删几条 | 简化有严格条件：只有当一个条件在所有组合中都对结果无影响时，该条件才可删除 |

【我的理解】

## 四、判定表实战：三角形判断

### 知识点4：三角形问题的完整判定表设计

>![[02-课程笔记/测试用例/images/Pasted image 20260706151512.png]]
> ![[02-课程笔记/测试用例/images/Pasted image 20260706153619.png]]

【课程原话/定义】

**确定条件桩（4个）：**
- C1：a, b, c 能否构成三角形？（a < b+c 且 b < a+c 且 c < a+b）
- C2：a = b ?
- C3：a = c ?
- C4：b = c ?

**确定动作桩（5个）：**
- A1：非三角形
- A2：一般三角形（不等边）
- A3：等腰三角形
- A4：等边三角形
- A5：不可能（逻辑矛盾）

**规则数：** 2^4 = 16 条

**条件项填写规律：**
- C1：前 8 列 N，后 8 列 Y
- C2：4N, 4Y, 4N, 4Y
- C3：2N, 2Y, 2N, 2Y, 2N, 2Y, 2N, 2Y
- C4：N, Y, N, Y, N, Y, N, Y...（交替）

**简化：** C1=N 时，无论 C2/C3/C4 取什么值，结果都是"非三角形"——前 8 条规则合并为 1 条。

【为什么？】
三角形问题是测试领域的"Hello World"——它在教学中的价值和经典性：

1. **条件之间有依赖关系**：C2/C3/C4 只在 C1=Y 时才有意义，这种"前置条件"是企业业务规则中最常见的模式（如"先判断是否登录，再判断权限"）
2. **存在逻辑矛盾**：C1=Y 且 C2=Y 且 C3=Y 但 C4=N（a=b=c 时 b≠c 是不可能的），这种"条件内在矛盾"对应企业场景中的业务规则互斥
3. **条件项填写规律（折半法）** 是判定表系统化的核心技巧——第一个条件 N:Y=8:8，第二个 4:4:4:4，第三个 2:2:2:2:2:2:2:2，第四个 1:1:1:1...——这种规律保证了 16 条规则不重不漏

【必须掌握】
- 能独立完成三角形问题的完整判定表（面试高频题）
- 理解"折半法"填写条件项的规律
- 理解简化：C1=N 时整个表的前半部分合并为一条
- 理解"不可能"的动作桩——对应业务规则中的逻辑矛盾

【企业场景】
> 你在测试一个订单系统的退款逻辑："① 订单已支付？② 订单未发货？③ 在退款时效内？④ 用户未超过退款次数限制？"——4 个条件，2^4=16 条规则。和三角形问题一样，条件①是否定（未支付）时，后面三个条件都没有意义，直接合并为"不可退款"。这种"前置条件"的简化模式，在业务流程测试中几乎每次都会遇到。

【面试考察】
> 面试官："请用判定表法解决三角形判断问题，并说明如何简化。"
**参考回答框架：**
1. 条件桩：构成三角形? / a=b? / a=c? / b=c?
2. 动作桩：非三角形 / 一般三角形 / 等腰 / 等边 / 不可能
3. 规则数 2^4=16 条，用折半法填写
4. 简化：
   - C1=N：前 8 条合并为"非三角形"
   - 逻辑矛盾需要剔除（如 a=b=c 但 b≠c）
5. 最终有效规则约 6-7 条

【易错点】

| ❌ 错误理解 | ✅ 正确理解 |
|------------|------------|
| C1 的"非三角形"条件就是"两边之和小于第三边" | 只需覆盖每个变量的"不满足"，即 a≥b+c 或 b≥a+c 或 c≥a+b |
| 简化后"非三角形"只需测 1 条用例 | "非三角形"有三种不同的原因（a 太大 / b 太大 / c 太大），每种都要覆盖，需要在测试用例层面补充 |
| "不可能"的规则可以删掉不管 | "不可能"代表逻辑矛盾，在测试中可以作为负面测试（验证系统确实不会产生这种状态） |

【我的理解】

## 五、条件项填写的系统化技巧（折半法）

### 知识点5：折半法——保证不重不漏

【课程原话/定义】
条件项的填写规律：
- C1：前一半 N，后一半 Y（8N, 8Y）
- C2：前一半的一半 N，再一半 Y，重复（4N, 4Y, 4N, 4Y）
- C3：2N, 2Y, 2N, 2Y, 2N, 2Y, 2N, 2Y
- C4：N, Y, N, Y（交替）

通用规律：第 i 个条件，以 2^(N-i) 为周期交替取值。

【为什么？】
这个看似机械的填写方法背后是**二进制全组合**的思想：

把 N/Y 映射为 0/1，那么 N 个条件的所有组合就是从 0 到 2^N-1 的二进制数。折半法实际上是在按位逐列写出从 0 到 15 的二进制表示：

- C1 = 最高位（第3位）：0×(8列) + 1×(8列)
- C2 = 第2位：0×(4列), 1×(4列), 0×(4列), 1×(4列)
- C3 = 第1位：0×(2列), 1×(2列), ...
- C4 = 最低位（第0位）：0, 1, 0, 1...

这种方法保证了**机械化操作就能穷举所有组合**，不需要动脑推理"还有没有漏掉的组合？"

【必须掌握】
- 折半法的规律：第 i 个条件以 2^(N-i) 为周期交替
- 面试时能当场手写出 3-4 个条件的条件项
- 这是"保证逻辑完备"的技术手段

【企业场景】
> 你在测试一个权限系统，"① 已登录？② 是管理员？③ 有编辑权限？④ 资源是自己的？"——4 个条件 16 种组合。用折半法填条件项，5 分钟填完初始表，然后逐列判断动作项，10 分钟完成整个判定表。如果不按折半法而是"想到哪列填哪列"，你一定会漏掉至少 2-3 种组合。

【面试考察】
> 面试官："有 3 个条件，请用折半法写出所有条件项组合。"
**参考回答框架：**
- C1：4N, 4Y
- C2：2N, 2Y, 2N, 2Y
- C3：N, Y, N, Y, N, Y, N, Y
- 共 8 列（2^3），覆盖所有组合

【易错点】

| ❌ 错误理解 | ✅ 正确理解 |
|------------|------------|
| 折半法只适用于 N/Y 条件 | 多值条件（如"支付方式：微信/支付宝/银行卡"）用乘法原理，但填入时也要系统化排列 |
| 4 个条件以上折半法太麻烦，直接写代码生成 | 面试时手写 4-5 个条件的判定表是常见要求，折半法必须熟练 |
| 条件顺序可以随意换 | 条件桩的排列顺序影响折半法结果——把最重要的/有依赖关系的条件放前面（如 C1 放前置条件） |

【我的理解】
>

## 六、判定表简化原则

### 知识点6：如何正确简化判定表

> 图片位置（判定表简化前后对比）

【课程原话/定义】
简化判定表的核心原则：如果两条或多条规则中，某个条件的取值不同但动作结果相同，说明这个条件在当前情况下不影响结果——这些规则可以合并，该条件标记为"无关"（用 `—` 表示）。

以三角形问题为例：C1 = N 时，不论 C2/C3/C4 取什么值，结果都是"非三角形"——8 条规则合并为 1 条。

【为什么？】
简化的本质是**识别条件之间的独立性**：

- 如果 C1=N → 结果确定，C2/C3/C4 对结果无影响 → 合并
- 这意味着 C1 是"C2/C3/C4"的**前置条件**，在 C1 不满足时，后续条件不需要判断

这种"前置条件"模式在企业系统中极其常见：未登录→不判断权限、未支付→不判断发货状态、非会员→不判断会员等级优惠...

简化后判定表从 16 条变成 6-7 条有效规则，但要注意：**简化的是判定表，不是测试用例**——合并后的一条规则可能需要在测试用例层面拆成多条来覆盖不同情况。

【必须掌握】
- 合并条件：两条规则动作相同 + 只有一个条件取值不同 → 该条件可标记为无关
- 简化后判定表 ≠ 最终测试用例数——需根据实际情况拆解
- 前置条件 → 大量合并，这是判定表最核心的简化模式

【企业场景】
> 你在测试一个折扣计算："① 是否会员？② 订单金额≥200？③ 是否首单？④ 是否促销期？"初始 16 条规则。简化后：非会员→只有一种折扣（不管其他条件）→合并后 4 条。但"非会员+其他条件任意"这一条，在测试用例层面你可能还是要测 2-3 个不同金额来验证。判定表简化节省的是逻辑分析时间，不是测试执行时间。

【面试考察】
> 面试官："什么条件下可以简化判定表中的规则？简化后用例数一定减少吗？"
**参考回答框架：**
1. 简化条件：两条规则只有一个条件取值不同，且动作/输出完全相同
2. 简化的是判定表的逻辑规则数，但测试用例数不一定等比减少
3. 合并后的"无关条件"在用例中仍可能需要覆盖——只是不需要穷举所有组合
4. 举例：三角形问题简化后从 16 条变成约 6 条有效规则

【易错点】

| ❌ 错误理解 | ✅ 正确理解 |
|------------|------------|
| 简化后规则数 = 最终用例数 | 简化后"非三角形"只有 1 条规则，但应该写 3 条用例（分别覆盖 a 太大、b 太大、c 太大） |
| 合并时只看动作是否相同 | 还必须满足"只有一个条件取值不同"——如果两个条件都不同，即使动作相同也不能合并 |
| 简化就是优化，做得越多越好 | 过度简化会丢失信息——如果两条规则动作恰好相同但逻辑上不相关，不应强行合并 |
