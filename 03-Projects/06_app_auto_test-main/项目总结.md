# 企业微信 App UI 自动化测试框架 — 项目总结

> 用于课程学习重点把握与后续复习。

---

## 项目总览

**企业微信 Android App UI 自动化测试框架**，用 Appium + Pytest + Page Object 模式实现。

**核心目标**：自动化测试企业微信"添加成员"流程，展示 PO 模式 + 数据驱动 + 异常处理的完整实践。

---

## 一、分层架构

```
tests（用例层）
  ↓ 依赖
pages（页面对象层）
  ↓ 依赖
utils（工具层）
```

| 层次 | 文件 | 作用 |
|------|------|------|
| utils | file_util.py / log_util.py | YAML读写、日志配置 |
| pages/base_page.py | BasePage | 封装定位/等待/滑动/截图等通用方法 |
| pages/wework_app.py | WeworkApp | App 启动入口，创建 WebDriver |
| pages/main_page.py | MainPage | 首页（通讯录入口） |
| pages/contact_page.py | ContactPage | 通讯录页（添加成员入口） |
| pages/add_member_page.py | AddMemberPage | 添加成员页（手动输入入口 + Toast校验） |
| pages/manual_add_page.py | ManualAddPage | 手动录入页（姓名/手机号输入 + 保存） |
| pages/err_handle.py | black_wrapper | 弹窗异常处理装饰器 |

## 二、核心知识点

### 1. BasePage — 通用方法封装（重点）

`base_page.py` 封装了 Appium 操作的通用方法：

| 方法 | 作用 |
|------|------|
| `find_ele(by, value)` | 查找单个元素 |
| `find_eles(by, value)` | 查找多个元素 |
| `find_and_click(by, value)` | 查找并点击 |
| `find_and_sendkeys(by, value, text)` | 查找并输入 |
| `set_implicitly_wait(time)` | 设置隐式等待 |
| `wait_ele_located(by, value, timeout)` | 显式等待元素可定位 |
| `wait_ele_click(by, value, timeout)` | 显式等待元素可点击 |
| `wait_for_text(text, timeout)` | 等待文本出现 |
| `swipe_window()` | 滑动界面（从底部80%到顶部20%） |
| `swipe_find(text, max_num)` | 滑动查找元素（最多滑5次） |
| `screenshot()` | 截图 |
| `save_page_source()` | 保存页面源码 |

**面试考点**：
- 隐式等待 vs 显式等待的区别？
  - 隐式等待：全局生效，找不到元素就一直等
  - 显式等待：针对特定条件，超时即抛异常
- `swipe_find` 为什么先设 `implicitly_wait(1)`？→ 加快滑动查找速度，避免每次查找都等很久

### 2. WeworkApp — App 启动与 Capability 配置

`wework_app.py` 的 `start()` 方法：

```python
caps = {
    "platformName": "Android",
    "appium:automationName": "uiautomator2",
    "appium:deviceName": "emulator-5554",
    "appium:appPackage": "com.tencent.wework",
    "appium:appActivity": ".launch.LaunchSplashActivity",
    "appium:noReset": True,
    "appium:forceAppLaunch": True,
}
```

**面试考点**：
- `appPackage` 和 `appActivity` 怎么获取？→ `adb shell dumpsys activity top`
- `noReset=True` 的作用？→ 不清空 App 数据，加速测试
- `uiautomator2` 是什么？→ Google 的 UI 自动化框架，Appium 的驱动后端

### 3. Page Object 模式 — 页面对象链式调用

每个页面类继承 `BasePage`，封装该页面的元素和操作：

```
WeworkApp.start()
  → goto_main() → MainPage
    → goto_contact() → ContactPage
      → goto_add_member() → AddMemberPage
        → goto_manual_add() → ManualAddPage
          → success_add_info(name, phone) → AddMemberPage
            → get_tips() → "添加成功"
```

**设计亮点**：
- 每个 `goto_xxx()` 返回下一个页面对象，实现链式调用
- 元素定位器定义为类常量 `__CONTACT = (AppiumBy.XPATH, "...")`
- 用 `*` 解包元组：`self.find_and_click(*self.__CONTACT)`

### 4. 弹窗异常处理装饰器（亮点）

`err_handle.py` 的 `black_wrapper` 装饰器：

```python
@black_wrapper
def find_ele(self, by, value):
    ...
```

**工作原理**：
1. 查找元素失败时捕获异常
2. 自动截图 + 保存页面源码（附加到 Allure 报告）
3. 遍历黑名单弹窗（"确定"/"取消"），点击关闭
4. 重新执行原方法
5. 仍失败则抛出原始异常

**面试考点**：
- 为什么用装饰器？→ 解耦异常处理逻辑，所有方法自动生效
- 黑名单弹窗怎么来的？→ 企业微信常见弹窗：权限提示、确认框等

### 5. 测试用例 — 三种写法对比

**写法一：test_by_po.py — PO 模式 + Faker 随机数据**
- 用 `Faker("zh_CN")` 生成随机姓名和手机号
- `setup_class` 生成一次数据，`setup_method` 每次启动 App
- 链式调用：`main.goto_contact().goto_add_member()...`

**写法二：test_by_param.py — PO 模式 + YAML 数据驱动**
- 数据从 `datas/data.yaml` 读取
- `@pytest.mark.parametrize("name, phonenum", get_member_datas())`
- 每组数据一条用例

**写法三：test_contact.py — 直写测试（教学对比）**
- 直接在用例里写 `find_element`，不封装页面对象
- 展示 PO 模式前后的对比
- **面试考点**：PO 模式的好处？→ 元素定位与用例分离，UI 变了只改页面对象

### 6. conftest.py — 中文乱码修复

```python
def pytest_collection_modifyitems(session, config, items):
    for item in items:
        item.name = item.name.encode('utf-8').decode('unicode-escape')
        item._nodeid = item.nodeid.encode('utf-8').decode('unicode-escape')
```

**作用**：修复 Windows 下 pytest 中文用例名乱码问题。

## 三、Appium 核心概念

| 概念 | 说明 |
|------|------|
| WebDriver | Appium 的驱动对象，提供 find_element、click、send_keys 等方法 |
| AppiumBy | 元素定位方式（ID、XPATH、ACCESSIBILITY_ID 等） |
| Capability | 启动 App 的配置参数（平台、包名、Activity 等） |
| 隐式等待 | `driver.implicitly_wait(10)`，全局生效 |
| 显式等待 | `WebDriverWait(driver, timeout).until(condition)` |
| Toast | 短暂提示框，`android.widget.Toast`，用 XPATH 定位 |
| Page Source | 页面源码 XML，用于分析元素结构 |

## 四、高频面试题

1. **Page Object 模式是什么？有什么好处？**
   - 参考回答框架：每个页面封装为一个类，元素定位和操作封装在方法中。好处：元素定位与用例分离、可维护性高、代码复用。

2. **隐式等待和显式等待的区别？**
   - 参考回答框架：隐式等待是全局的、固定时长；显式等待是局部的、针对特定条件、可自定义超时。

3. **Appium 怎么定位元素？**
   - 参考回答框架：XPATH（文本匹配）、ID（resource-id）、ACCESSIBILITY_ID（content-desc）、CLASS_NAME 等。

4. **black_wrapper 装饰器的工作原理？**
   - 参考回答框架：捕获元素查找异常 → 截图+保存源码 → 点击弹窗 → 重试 → 仍失败抛异常。

5. **swipe_find 为什么先设隐式等待为 1？**
   - 参考回答框架：滑动查找需要频繁尝试，默认 15 秒太慢，临时设为 1 秒加速，找到后恢复。

6. **Appium 和 requests 自动化测试的区别？**
   - 参考回答框架：requests 测接口（HTTP层），Appium 测 UI（设备层）。接口测试快、稳定；UI 测试覆盖用户真实操作路径。
