## 我的理解（最重要）

> Flask 的 `request` 对象是"请求的代言人"——浏览器发过来的所有信息（URL 参数、请求体、文件、请求头、方法）都能通过它拿到。`request.args`、`.json`、`.form`、`.files` 四个属性分别对应 HTTP 请求中四种不同的数据承载方式，它们的核心区别在于 Content-Type 头。响应侧，Flask 的灵活之处在于视图函数可以返回字符串、字典、元组、Response 对象——Flask 内部会根据返回类型自动构造合法的 HTTP 响应。`make_response()` 是"完全控制权"：当你需要同时操作 Cookie、Header、状态码时，它是唯一选择。环境配置中 `debug=True` 是最危险的"便利"——自动重载和在线调试器在生产环境等于给攻击者开了一扇任意代码执行的大门。

## 企业真实场景

> Mock 是测试工程师的日常。你需要模拟登录接口返回 session cookie——用 `make_response()` + `set_cookie()` 10 行搞定。你需要测试客户端对 404/500 的处理——用元组返回不同状态码。前端上传文件接口还没开发完——用 `request.files` + `save()` 搭一个接收端先开始写测试用例。Flask 让测试工程师不再受制于"后端还没开发完"的阻塞——自己搭 Mock，自己控数据，自己定状态码。这就是学 Flask 的核心价值。

## 收获

1. `request` 对象的四个核心属性（args/json/form/files）覆盖了 99% 的请求数据获取场景
2. JSON 响应有两种方式：`jsonify()` 和直接 return dict——区别在 Content-Type 头的自动设置
3. `make_response()` 是构造复杂响应的终极工具——cookie、自定义 header、状态码一把抓
4. `debug=True` 是双刃剑：开发神器，生产毒药——理解其安全风险是工程师的基本素养
