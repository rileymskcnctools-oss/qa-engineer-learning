# 架构分析：从请求到数据库的完整生命周期

> 以本项目的学生管理系统为模型，理解一个 Web 系统从用户点击到数据库读写的完整过程。

---

## 一、项目整体架构

```
             用户
              |
              |
          浏览器页面
              |
        HTTP请求(GET/POST)
              |
              ↓
       Flask路由层(server.py)
              |
              |
       业务逻辑处理
              |
              ↓
       数据访问层(db.py)
              |
              |
            SQL
              |
              ↓
          MySQL数据库
```

### 【为什么？】要这样分层？

如果所有代码写在一个文件里，例如在一个 `@app.route("/add")` 函数中：连接数据库、创建游标、执行 SQL、校验数据、返回页面——全部耦合在一起。

带来的问题：

1. 代码越来越长，难以维护
2. 数据库连接代码在每个路由里重复出现
3. 改一个 SQL 可能影响多个地方
4. 无法单独测试数据库层或业务层

所以拆分为两层：

| 文件 | 职责 | 类比 |
|------|------|------|
| `server.py` | 接收 HTTP 请求，处理业务逻辑，决定"做什么" | 餐厅服务员（接单、传菜） |
| `db.py` | 封装所有数据库操作，决定"怎么做" | 后厨（只管做菜） |

这种设计叫 **分层设计思想**（Separation of Concerns），是 MVC 模式的雏形。

## 二、程序启动流程

### 第一步：创建 Flask 应用

```python
app = Flask(__name__)
```

创建一个 Flask 应用对象，相当于启动了一个 Web 服务器程序的容器。此时服务器还没有开始监听请求，但框架已经就绪。

### 第二步：加载路由映射

```python
@app.route("/")
def index(): ...

@app.route("/add", methods=["GET", "POST"])
def add(): ...

@app.route("/change/<int:sid>", methods=["GET", "POST"])
def change(sid): ...

@app.route("/delete/<int:sid>", methods=["DELETE", "POST"])
def delete(sid): ...
```

Flask 在内部维护一张 **路由映射表**：

```
URL                        函数           方法

/                   -->    index()        GET
/add                -->    add()          GET, POST
/change/<sid>       -->    change(sid)    GET, POST
/delete/<sid>       -->    delete(sid)    DELETE, POST
```

### 第三步：启动服务器

```python
if __name__ == '__main__':
    app.run()
```

执行后，Flask 内置的 Werkzeug 开发服务器开始监听：

```
127.0.0.1:5000
```

此时浏览器访问 `http://127.0.0.1:5000` 即可触发请求。

### 【面试考察】

> 面试官："`if __name__ == '__main__'` 是干什么的？为什么需要它？"

**参考回答框架：**

- 这是一个 Python 惯用法，区分"直接运行"和"被导入"
- 当 `python server.py` 直接运行时，`__name__` 的值是 `'__main__'`，条件成立，执行 `app.run()`
- 当这个文件被 `import` 导入时（例如测试代码 `from server import app`），`__name__` 是模块名 `'server'`，条件不成立，不会启动服务器
- 这样保证了：测试时可以导入 app 对象做单元测试，而不会意外启动一个 Web 服务器

## 三、一次完整请求流程（以查询首页为例）

用户输入 `http://127.0.0.1:5000/`，回车。

```
浏览器 → HTTP GET / → Flask 路由匹配 → index() → db.query_all() → MySQL → 数据返回 → render_template() → HTML 响应 → 浏览器渲染
```

| 步骤 | 位置 | 发生了什么 |
|------|------|-----------|
| 1 | 浏览器 | 发送 HTTP `GET /` 请求 |
| 2 | Flask | 查找路由表，`GET /` 匹配到 `index()` |
| 3 | server.py:index() | 调用 `db.query_all("SELECT ...")` |
| 4 | db.py:query_all() | `get_connect()` 创建 MySQL 连接 |
| 5 | db.py:query_all() | `conn.cursor(DictCursor)` 创建游标 |
| 6 | db.py:query_all() | `cursor.execute(sql)` 执行 SQL |
| 7 | MySQL | 执行 `SELECT sid,name,age,gender FROM student_0802` |
| 8 | MySQL → Python | 返回结果集，例如 `[{"sid":1, "name":"张三", ...}]` |
| 9 | db.py:query_all() | `cursor.close()` 关闭游标，`conn.close()` 关闭连接 |
| 10 | server.py:index() | `render_template("index.html", students=students)` 渲染模板 |
| 11 | Flask → 浏览器 | 返回完整 HTML 页面 |
| 12 | 浏览器 | 渲染表格，用户看到学生列表 |

### 【为什么？】要先关游标再关连接？

游标（Cursor）依赖于连接（Connection）——游标是通过连接创建的。如果先关连接再关游标，就会在已断开的连接上操作，引发异常。正确的关闭顺序：**先创建的后关闭**（游标 → 连接），和打开顺序相反。

## 四、添加学生完整流程（最重要的流程）

添加学生涉及 **写数据库**，包含数据校验 → 参数化 SQL → 事务提交，是理解 Web 安全的关键流程。

用户填写表单：姓名=张三，年龄=18，性别=男，点击提交。

```
浏览器 POST /add → Flask 进入 add() POST 分支 → 获取表单参数 → 数据校验 → db.execute(INSERT) → conn.commit() → redirect("/")
```

### 详细步骤

| 步骤 | 代码位置 | 操作 |
|------|---------|------|
| 1 | 浏览器 | POST `/add`，携带表单数据 `name=张三&age=18&gender=男` |
| 2 | Flask | 路由匹配 `POST /add` → `add()` |
| 3 | server.py:20 | `request.form.get("name")` 获取参数 |
| 4 | server.py:24-32 | **数据校验**：姓名非空、年龄是数字且在 0-150 范围、性别必须是"男"/"女" |
| 5 | server.py:34 | 调用 `db.execute("INSERT INTO ... VALUES (%s,%s,%s)", (name, age, gender))` |
| 6 | db.py:execute() | `get_connect()` 创建连接 |
| 7 | db.py:execute() | 创建游标，`cursor.execute(sql, params)` 执行参数化 INSERT |
| 8 | db.py:execute() | `conn.commit()` 提交事务 |
| 9 | db.py:execute() | 关闭游标和连接 |
| 10 | server.py:36 | `redirect(url_for("index"))` 重定向到首页 |

### 【为什么？】需要 `conn.commit()`？

数据库默认开启了事务。INSERT/UPDATE/DELETE 操作执行后，数据先暂存在事务缓冲区中，并没有真正写入磁盘。只有执行 `commit()`，数据库才将修改持久化。这保证了 **原子性**——如果中途出错可以 `rollback()` 回滚。

### 【为什么？】校验放在 server.py 而不是 db.py？

- **业务校验**（年龄范围、性别合法性）是业务规则，属于业务层职责
- **数据库层**只负责执行 SQL，不应该关心"什么年龄算合法"
- 如果校验放在 db.py，换一个业务场景时校验规则可能不同，会导致 db.py 难以复用

### 【为什么？】添加成功后用 redirect 而不是直接返回首页？

`redirect("/")` 会触发浏览器发起一个新的 `GET /` 请求，重新走 `index()` → `db.query_all()` 流程。这样：
- 用户看到的是最新的数据（包含刚添加的学生）
- 浏览器地址栏显示的是 `/` 而不是 `/add`
- 用户刷新页面时不会重复提交表单（POST 重复提交问题）

这叫 **PRG 模式**（Post-Redirect-Get），是 Web 开发的经典实践。

### 【企业场景】

> 你负责测试添加学生接口。产品经理说："如果有人用 curl 直接发请求，提交了一个 3000 岁的'学生'，系统会怎么处理？"

你需要在测试用例中覆盖：
- 年龄 = `"abc"`（非数字）→ 应返回 400 "年龄必须为数字"
- 年龄 = `-5` → 应返回 400 "年龄超出范围"
- 年龄 = `300` → 应返回 400 "年龄超出范围"
- 性别 = `"未知"` → 应返回 400 "性别必须是男或者女"
- 姓名为空 → 应返回 400 "姓名不能为空"
- 正常数据 → 200，数据库中新增一条记录

## 五、修改功能流程

修改功能体现了 **GET/POST 同路由不同行为** 的 RESTful 设计思想。

```
GET  /change/1  → 查询旧数据 → 页面回显
POST /change/1  → 获取新数据 → 校验 → UPDATE → redirect
```

| 步骤 | 方法 | 操作 |
|------|------|------|
| 1 | GET `/change/1` | 从 URL 提取 `sid=1`，调用 `db.query_one("...WHERE sid=%s", (1,))` |
| 2 | GET | 查询返回 `{"sid":1, "name":"张三", "age":18, "gender":"男"}` |
| 3 | GET | `render_template("change.html", student=student)` 回显到表单 |
| 4 | POST `/change/1` | 用户修改年龄为 20，提交表单 |
| 5 | POST | 数据校验（与添加相同的校验规则） |
| 6 | POST | `db.execute("UPDATE student_0802 SET ... WHERE sid=%s", (...))` |
| 7 | POST | `conn.commit()` 提交 |
| 8 | POST | `redirect("/")` 返回首页，看到更新后的数据 |

### 【为什么？】GET 和 POST 共用同一个 URL？

这是 RESTful 风格的设计：
- **同一个资源**（学生 sid=1）用一个 URL 标识：`/change/1`
- **GET** 表示"读取当前状态"（获取修改前的数据）
- **POST** 表示"更新状态"（提交修改后的数据）

这样做的好处：URL 结构清晰，前端只需要知道一个地址。

## 六、删除流程

用户点击"删除"按钮 → 表单 POST `/delete/1` → Flask 执行 DELETE SQL → 重定向首页。

### 【为什么？】删除用的是 POST 而不是 GET？

HTML 的 `<a>` 标签只能发 GET 请求。如果用 GET 删除：
- 搜索引擎爬虫可能无意中触发删除（Googlebot 访问 `/delete/1`）
- 用户可能误点或浏览器预加载触发删除

所以用一个隐藏的 `<form method="POST">` 包裹删除按钮，确保删除是显式的、带 method 的请求。

### 【为什么？】路由还支持 DELETE 方法？

```python
@app.route("/delete/<int:sid>", methods=["DELETE", "POST"])
```

虽然浏览器端 HTML 表单只支持 GET 和 POST，但 API 测试中可以使用 DELETE 方法（例如 `requests.delete()`）。这为以后做接口自动化测试预留了入口。

## 七、核心设计思想总结

### 1. 请求-响应模型

Web 程序的本质：

```
请求 (Request)
     ↓
处理 (Process)
     ↓
响应 (Response)
```

每一轮交互都是 **无状态** 的——服务器处理完一个请求后不会记住之前发生了什么。这是 HTTP 协议的核心特征。

### 2. 分层架构

```
展示层（HTML templates）
    ↕ Jinja2 模板引擎
业务层（server.py）
    ↕ 函数调用
数据层（db.py）
    ↕ PyMySQL
数据库（MySQL）
```

每一层只和相邻层打交道，修改一层不影响其他层。

### 3. 封装

`db.py` 把数据库的细节（连接、游标、关闭）封装在三个函数中：

| 函数 | 用途 | 返回 |
|------|------|------|
| `query_all(sql, params)` | 查询多条 | `list[dict]` |
| `query_one(sql, params)` | 查询单条 | `dict` 或 `None` |
| `execute(sql, params)` | 增删改 | 影响行数 |

`server.py` 只需要调用这些函数，不用关心连接和游标的生命周期。

### 4. SQL 参数化（防注入）

```python
# ✅ 正确：参数化查询
db.execute("INSERT INTO student_0802 (name,age,gender) VALUES (%s,%s,%s)", (name, age, gender))

# ❌ 错误：字符串拼接（SQL 注入风险！）
db.execute(f"INSERT INTO student_0802 (name,age,gender) VALUES ('{name}',{age},'{gender}')")
```

`%s` 是占位符，PyMySQL 会将参数值安全地转义后填入，杜绝 SQL 注入。

### 【企业场景】

> 你是测试工程师，代码审查时发现同事用了 f-string 拼接 SQL。你需要指出风险并推动修改。

**测试验证方法**：在姓名字段输入 `张三'); DROP TABLE student_0802; --`，观察：
- 参数化版本：这条恶意输入会被当作普通学生姓名存入数据库，数据库安全
- 字符串拼接版本：SQL 被拆成两条语句执行，整张表被删除

### 5. 事务控制

```python
# db.py:execute()
try:
    cursor.execute(sql, params)
    conn.commit()    # 成功 → 持久化
except Exception:
    conn.rollback()  # 失败 → 回滚
    raise
```

保证数据一致性——要么全部成功，要么全部撤销。

## 八、从测试角度理解这个项目

测试不是逐行看代码，而是沿着请求流程找风险点：

```
用户输入 → Flask 接收 → 参数校验 → 数据库操作 → 页面响应
   ↓           ↓           ↓           ↓           ↓
 参数化测试   接口测试    边界值测试   数据验证     UI验证
```

| 流程节点 | 风险 | 测试类型 | 具体测试点 |
|---------|------|---------|-----------|
| 用户输入 | 非法数据绕过前端校验 | 参数校验测试 | 空值、超长、特殊字符、SQL 注入 payload |
| Flask 接收 | 路由错误、方法不允许 | 接口测试 | 错误的方法、不存在的路由、URL 参数类型错误 |
| 参数校验 | 校验逻辑有漏洞 | 功能测试 | 边界值（0, 1, 149, 150, 151）、等价类划分 |
| 数据库操作 | SQL 执行失败、数据不一致 | 数据验证 | 查询结果是否正确、事务是否回滚 |
| 页面响应 | 状态码错误、响应内容异常 | 响应验证 | 200/400/500、重定向是否生效、模板渲染是否正确 |
| 异常场景 | 程序崩溃 | 异常测试 | 数据库断连、超时、并发写入 |

### 【面试考察】

> 面试官："你测试的系统和这个学生管理系统类似，你如何设计测试用例？"

**参考回答框架：**

1. **正向用例**：合法的姓名+年龄+性别 → 200，数据入库，页面显示正确
2. **参数校验**：每一种非法输入（空、非数字、越界）→ 400 + 错误提示
3. **边界值**：年龄 0、1、149、150
4. **SQL 注入**：在输入框填入恶意 SQL → 应被参数化查询防御
5. **重定向验证**：POST 提交后检查是否 302 跳转到 `/`
6. **数据一致性**：添加后查询数据库，确认所有字段值与输入一致
7. **幂等性**：连续两次删除同一个 sid，第二次应如何处理？

## 九、技术栈清单

| 层级 | 技术 | 作用 |
|------|------|------|
| Web 框架 | Flask 3.x | 路由分发、请求处理、模板渲染 |
| 模板引擎 | Jinja2 | 将数据填入 HTML 模板，生成动态页面 |

| 前端 | HTML + CSS | 页面结构与样式 |
| 包管理 | uv | 依赖管理与虚拟环境 |
