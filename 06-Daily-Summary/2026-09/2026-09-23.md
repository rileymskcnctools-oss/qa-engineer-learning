## 学习任务

### 任务 1：亲手画出三条曲线（45 分钟）
用 Python + matplotlib 造一组模拟数据（并发 10→1000），画 RT（基本平稳 → 走平 → 陡增）、TPS（上升 → 走平 → 回落）、资源利用率（上升 → 饱和）三条曲线，画在一张图上，并手动标出：两个拐点、三个区域名。目的：把课程里的文字描述变成自己的图，而不是背"轻压力区/重压力区/弃忍区"三个词。（Ch01 知识点 7 / 8）

### 任务 2：一次完整的容量推导（40 分钟）
拿这个设定做一遍推导并写出计算过程：某电商 App 日订单 10 万单，峰值时段（20:00-21:00）占全天订单的 30%，下单接口平均 RT 200ms。要求算出：① 峰值 QPS；② 按 二八原则 / 峰值系数 换算的瞬时并发数；③ 如果 SLA 定"TP99 ≤ 800ms"，你会怎么设计阶梯加压（从多少并发加到多少）。目的：练"业务量 → 并发模型 → SLA"这条链，这是面试里最能体现工程素养的推导。（Ch01 知识点 3）

### 任务 3：三区域对号入座（30 分钟）
给下面三组现象判断各自处于哪个区域，并各写一句"该给业务什么结论"：
- A：CPU 45%，TPS 随并发线性上升，RT 稳定在 120ms
- B：CPU 88%，TPS 已走平，RT 从 200ms 涨到 600ms
- C：CPU 99%，TPS 从高点回落，RT 涨到 3s
目的：训练"看三线给结论"的反射，而不是只看 TPS。（Ch01 知识点 8 / 9）

### 任务 4：口述三道面试题（20 分钟）
不看笔记口述：① 什么是性能测试，和功能测试的区别是什么？② 最佳并发用户数和最大并发用户数的区别，压测压到哪个点？③ 你怎么确定压测的并发数？目的：把知识点转成能说出口的话，说卡壳的地方就是没吃透的地方。（Ch01 知识点 1 / 3 / 8）

### 任务 5：大促超容量的应对推演（25 分钟）
设定"业务方预估峰值 6000 QPS，你的压测结论是最大并发对应 4500 QPS"，按顺序写出你的四步应对方案（扩容 / 限流降级 / 降级开关清单 / 大促当天监控看板），并说明每一步的触发条件。目的：练习"不给单点数字、给区间 + 红线 + 触发条件"的表达方式。（Ch01 知识点 9）

### 任务 6：指标口径默写（25 分钟）
默写并解释：① 并发 vs 在线用户数的区别；② TPS 与 QPS 何时相等；③ 并发数 = QPS × 平均 RT 的推导（利特尔法则）；④ 用 P90/P95/P99 各说一句"它代表谁的体验"。目的：指标口径是性能测试的语言，面试第一问就考这里。（Ch02）

### 任务 7：画一张自己的架构巡检图（40 分钟）
对着 Ch03 的 Mermaid 架构图，自己手画一遍（Nginx → 应用集群 → DB/缓存/MQ → K8s/Docker → Prometheus/Grafana/Alert），并给每个方框写 1~2 个"压测时要盯的指标"。目的：把架构图变成自己的排查清单。（Ch03）

### 任务 8：给业务方写一段工具选型理由（30 分钟）
用 JMeter 的六大优点，按"成本 → 覆盖面 → 规模 → 结果可用性"顺序，写一段 1 分钟能讲完的选型理由；再补一张 AB / JMeter / nGrinder / Locust / LoadRunner 的对比表（含各自不适用的场景）。目的：练"工程化沟通"。（Ch04）

### 任务 9：写一份"压测当天执行清单"（45 分钟）
把 Ch07 的 12 步流程 + Ch08 的七阶段 + 九组命令揉成一张可执行清单（压前检查 / 压中监控 / 压后交付），每步写清"谁做、用什么工具、产出什么"。要求至少包含：记录机器参数基线、nginx 每秒请求数、错误请求、vmstat、free -m、TIME_WAIT、业务数据落库校验。目的：把流程变成可执行的清单，这是简历上"性能测试实战"最实在的素材。（Ch07 / Ch08）

### 任务 10：设计一次完整的场景方案（50 分钟）
设定："电商 App 双十一预计 50 万 UV，商品详情 + 下单两条链路。" 要求写出：① 这属于哪一类用途（能力验证 / 容量规划 / 问题追查）；② 选哪几种测试方法及顺序；③ 三类场景的请求比例与加压方式；④ 每类场景的验收标准（QPS / RT 分位值 / 错误率 / 资源抖动）。目的：练"从业务量推导到场景与验收标准"的完整链。（Ch10 + Ch02 + Ch08）

任务 1、3 必做（曲线模型是这门课的地基，图形化之后后面的章节才有落脚点）；任务 2 建议做（这是简历/面试里的"杀手锏"材料）；任务 5 是面试中区分"会跑工具"和"能对系统性能负责"的分水岭。

## 我的理解（最重要）

> 用自己的话回答：
> 1. 为什么说"抛开负载谈性能是没有意义的"？如果一个接口平均 RT 是 100ms，你能说它性能好吗？还需要补问哪些信息？（Ch01 知识点 1）——关键词：负载条件、TP99 长尾、资源成本
> 2. 如果线上监控已经能看到慢接口，为什么还要专门做性能测试？"发现瓶颈"和"评估系统能力"分别对应公司里哪些决策？（Ch01 知识点 2）——关键词：主动 vs 被动、容量边界
> 3. 为什么"微博明星公开恋情"和"12306 抢票"都是高并发，压测重点却完全不同？给新功能定压测目标时你会先问哪几个问题？（Ch01 知识点 3）——关键词：流量形态、弹性 vs 排队、一致性
> 4. 性能测试的价值为什么能被写进公司的成本账单？"容量规划"和"性能调优"分别是怎么省钱的？（Ch01 知识点 4）——关键词：不超配 / 不欠配、同硬件多扛流量
> 5. 知识体系四大模块里，为什么"性能调优"最难？它比前三块多需要什么？（Ch01 知识点 5 / 6）——关键词：暴露问题 vs 解决问题、跨栈定位
> 6. 如果只给你 TPS 一条曲线，你可能得出什么错误结论？为什么必须把 RT 曲线叠在一起看才能判断"系统能不能上线"？（Ch01 知识点 7）——关键词：过载误读、产能 / 成本 / 体验三合一
> 7. 为什么过了第二个拐点之后 TPS 反而会下降？"资源都被占满了，为什么处理能力却变弱了"？（Ch01 知识点 8）——关键词：排队、超时重试、上下文切换、GC 内耗
> 8. 为什么给业务方的结论应该是"区间 + 红线 + 触发条件"，而不是"系统能扛 400 并发"？（Ch01 知识点 9）——关键词：日常区间 / 容量上限 / 扩容触发

## 面试可能怎么问

Q1：什么是性能测试？它和功能测试的区别是什么？
→ 参照 Ch01 知识点 1 的四层框架：定义（不同负载下衡量 RT / TPS / 资源利用率 / 稳定性 / 可扩展性）→ 关注点差异（输出是否正确 vs 在多少并发下仍然正确及时）→ 判定差异（二元通过/不通过 vs 量化的"什么负载达到什么指标"）→ 时机差异（贯穿全程 vs 版本稳定后 + 上线前）。

Q2：什么是最佳并发用户数和最大并发用户数？压测应该压到哪个点？
→ 参照 Ch01 知识点 8：两个拐点的位置（轻/重压力区交界、重/弃忍区交界）+ 三个区域的指标走势 + 压测目标（摸容量红线 or 压到 RT 触及 SLA）+ 加分点"为什么压崩不是目的"。

Q3：你怎么确定压测的并发数？
→ 参照 Ch01 知识点 3：业务峰值量 → 转化率折算接口 QPS → 峰值系数换算瞬时并发（并发 ≈ QPS × RT）→ 历史监控校准 + 20%~30% 冗余 → 用阶梯加压找拐点验证。

## 企业真实场景

> 这个知识点在企业里什么时候会用到？

- **大促 / 活动备战**：业务方给预估订单量，你要把它折算成接口 QPS、定 SLA、设计压测场景，最后输出容量结论与扩容建议——这就是"业务量 → 并发模型 → SLA"这条链的真实使用场景。
- **季度云成本优化会**：运维要缩容，能不能缩、缩到多少，拿的就是你压测出的最佳并发数和容量红线（对应降本增效的省钱公式）。
- **上线前的性能验收**：新功能或架构改造上线前，用曲线判断"当前规格能支撑到多少"，并给运维一个三段式结论（日常区间 / 可容忍区间 / 扩容红线）。
- **线上性能劣化回归**：定期重压，观察拐点是否左移——拐点左移就等于容量缩水，是代码 / 依赖 / 数据量变化的报警信号。
- **面试与简历**：性能测试是测开岗的精华加分项，"发现瓶颈 → 定位到具体层 → 优化后量化收益"这条故事线，是区别于"只会写脚本"的候选人的关键材料。

## 收获

1. 性能测试的完整定义必须带两个限定词——**现实场景**和**不同负载条件**；产出不是"通过/不通过"，而是"在什么负载下达到什么指标"（五大指标：RT / TPS / 资源利用率 / 稳定性 / 可扩展性）。
2. **性能压力曲线模型**是整门课的地基：三条曲线（RT / TPS / 利用率）、三个区域（Light Load / Heavy Load / Buckle Zone）、两个拐点（最佳并发用户数 / 最大并发用户数）；核心读法是"三线一起看"——单看 TPS 会把过载误读成正常。
3. 性能测试的价值可以被写成成本账单：**良好的容量规划能力 + 性能调优能力 = 为老板省钱**；容量评估要给"日常区间 + 容量上限 + 扩容红线"三段式结论，而不是一个数字。

## 反思

> 本节是总览课，概念多、图表多，最可能的偏浅处有三个：
> 1. **把"三个区域"当名词背下来** —— 能不能自己画出曲线、标出拐点，才是真掌握；如果只记得"轻压力区/重压力区/弃忍区"这三个名字，做任务 1 时会明显吃力。
> 2. **弃忍区 TPS 下降的原因只记结论** —— 这一条几乎必被深挖（面试官会问"资源都满了为什么处理能力变弱"），必须能讲到"排队 → 超时重试 / 上下文切换 / GC 抢占 → 资源内耗"这一层。
> 3. **应用场景与并发推导割裂** —— 场景不是背景故事，它的作用就是产出并发数这个输入参数。如果做题时还需要回头翻笔记找"怎么从订单量算 QPS"，说明这条链还没内化。
