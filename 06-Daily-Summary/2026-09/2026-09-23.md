## 面试可能怎么问

Q1：什么是性能测试？它和功能测试的区别是什么？
→ 参照 Ch01 知识点 1 的四层框架：定义（不同负载下衡量 RT / TPS / 资源利用率 / 稳定性 / 可扩展性）→ 关注点差异（输出是否正确 vs 在多少并发下仍然正确及时）→ 判定差异（二元通过/不通过 vs 量化的"什么负载达到什么指标"）→ 时机差异（贯穿全程 vs 版本稳定后 + 上线前）。

Q2：什么是最佳并发用户数和最大并发用户数？压测应该压到哪个点？
→ 参照 Ch01 知识点 8：两个拐点的位置（轻/重压力区交界、重/弃忍区交界）+ 三个区域的指标走势 + 压测目标（摸容量红线 or 压到 RT 触及 SLA）+ 加分点"为什么压崩不是目的"。

Q3：你怎么确定压测的并发数？
→ 参照 Ch01 知识点 3：业务峰值量 → 转化率折算接口 QPS → 峰值系数换算瞬时并发（并发 ≈ QPS × RT）→ 历史监控校准 + 20%~30% 冗余 → 用阶梯加压找拐点验证。

## 企业真实场景

> 这个知识点在企业里什么时候会用到？

- **大促 / 活动备战**：业务方给预估订单量，你要把它折算成接口 QPS、定 SLA、设计压测场景，最后输出容量结论与扩容建议——这就是"业务量 → 并发模型 → SLA"这条链的真实使用场景。
- **季度云成本优化会**：运维要缩容，能不能缩、缩到多少，拿的就是你压测出的最佳并发数和容量红线（对应降本增效的省钱公式）。
- **上线前的性能验收**：新功能或架构改造上线前，用曲线判断"当前规格能支撑到多少"，并给运维一个三段式结论（日常区间 / 可容忍区间 / 扩容红线）。
- **线上性能劣化回归**：定期重压，观察拐点是否左移——拐点左移就等于容量缩水，是代码 / 依赖 / 数据量变化的报警信号。
- **面试与简历**：性能测试是测开岗的精华加分项，"发现瓶颈 → 定位到具体层 → 优化后量化收益"这条故事线，是区别于"只会写脚本"的候选人的关键材料。

## 收获

1. 性能测试的完整定义必须带两个限定词——**现实场景**和**不同负载条件**；产出不是"通过/不通过"，而是"在什么负载下达到什么指标"（五大指标：RT / TPS / 资源利用率 / 稳定性 / 可扩展性）。
2. **性能压力曲线模型**是整门课的地基：三条曲线（RT / TPS / 利用率）、三个区域（Light Load / Heavy Load / Buckle Zone）、两个拐点（最佳并发用户数 / 最大并发用户数）；核心读法是"三线一起看"——单看 TPS 会把过载误读成正常。
3. 性能测试的价值可以被写成成本账单：**良好的容量规划能力 + 性能调优能力 = 为老板省钱**；容量评估要给"日常区间 + 容量上限 + 扩容红线"三段式结论，而不是一个数字。

## 反思

> 结合今天的 6 题答卷，原先预判的偏浅处有一处被推翻、两处被证实，另新增一处：
> 1. ~~把"三个区域"当名词背~~ —— **已不成立**：弃忍区一题说清了内耗机制（等待/重试/上下文切换/超时处理），说明不是背名词。
> 2. **下钻动作断在"进程"这一层** —— 定位路径能走到"top 看哪个进程"，但没走到"哪个线程、哪段代码"（top -H → jstack → 火焰图）。这是本阶段最该补的一环，也是面试最容易追问的地方。
> 3. **"规模"与"压测机侧"是盲区** —— 讲 JMeter 选型时没提分布式；排查瓶颈时没考虑压测机/网关侧（TIME_WAIT、端口、起压机资源）导致的假瓶颈。两处都属于"只在单机视角思考"的表现。
> 4. **流程理解已经体系化，但要补最后一环** —— 把流程抽象成"目标/现状/实际"三问很到位，只是少了"结论与建议"（否则报告到结果就断，团队拿不到动作）。
> 5. **动手环节尚未开始** —— 到今天为止全部是"读 + 想"，还没跑过一次真实压测。**下一段的关键是从"会说"推进到"会做"**（JMeter 最小可用 + vmstat/top 实证）。
