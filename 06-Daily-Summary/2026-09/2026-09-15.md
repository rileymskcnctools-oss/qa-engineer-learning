## 企业真实场景

1. **前后端并行开发**：前端 mock、后端写接口，接口是两边"对接标准"，你测接口就是验这个契约。（Ch07）
2. **发版回归**：新版本上线前，把接口用例存进 Collection 点 Run，几十条一次跑完看通过率。（Ch09/Ch10）
3. **接口文档不全/过期**：用 Charles 抓包，从真实流量还原接口的真实参数和返回。（Ch08）
4. **资金类接口**：订单/支付接口专门测幂等，防用户重复点击扣两次钱。（Ch08）
5. **秒杀/抢购**：压测工具模拟高并发，断言库存不为负、无超卖。（Ch08）
6. **故障演练**：配合开发停掉 Redis/数据库，验证接口能否降级、不雪崩。（Ch08）
7. **多环境切换**：baseURL 放 Environment，切 test/stage 环境，一套用例复用。（Ch09/Ch10）
8. **接口间数据关联**：新增宠物返回的 id 存进 Collection 变量，删除接口 `{{petId}}` 引用，实现增删联动。（Ch10）

## 收获

1. **接口 = 契约**：后端预定义的函数，约定输入输出；接口测试验的是"通信与数据交换"是否准确可靠。
2. **分层测试金字塔（马丁福勒）**：单元→接口→UI，越往上发现 bug 越晚、成本越高，所以测试重心要下沉到接口层。
3. **接口测试早介入**：需求分析完就能测，不依赖 UI，这是它比 UI 测试更快更便宜的根本原因。
4. **用例设计六维度**：边界值/特殊字符/类型/必填/组合（输入域）+ 排重/幂等 + 并发/分布式 + 故障注入，是接口特有于功能测试的部分。
5. **幂等防重复副作用**：多次执行=一次执行的"副作用"，资金系统必测；实现靠唯一请求号/状态机/唯一索引。
6. **故障注入测健壮性**：故意制造 Redis/DB/接口故障，验证降级、多活、重试，防止线上雪崩。
7. **Postman 四种 body**：form-data（键值对+文件）、urlencoded（纯表单）、raw（JSON 最常用）、binary（纯二进制），必须和 Content-Type 匹配。
8. **断言让测试可回归**：pm.test + status/include/eql/header/below，预期 vs 实际自动化比较，PASS/FAIL 一目了然。
9. **变量作用域 + 优先级**：Data→Environment→Collection→Global→Local，用于参数化（复用值）和关联（接口间传值）。
10. **常见的接口协议 = Ch01**：本次"常见的接口协议"一节与 Ch01-接口协议基础 完全重合，未重复造章。

## 反思
> Ch07 是接口测试的"世界观"——最容易被当成"背概念"带过，但真正的抓手是"为什么要分层、为什么 UI 测试不够了"。要能把"后端复杂 + 快速迭代 → 传统测试跟不上 → 分层 + 自动化"这条因果链用自己的话讲出来，测试金字塔才不是一张死图。Ch08 是本章最重的一章，幂等（知识点 5）、并发/秒杀（知识点 6）、故障注入（知识点 7）是接口测试区别于功能测试的"特有维度"，面试必问，别只停留在"知道名词"，要能说清"怎么测、为什么测"。Ch09-Ch10 是工具落地，最容易学浅的是只点按钮不写断言——Postman 的价值在"断言 + Collection Run + 变量关联"这三个工程化能力，单个 Send 只是调试。务必亲手把任务 5 的宠物商店 CRUD 跑通，你才会真正理解"从调试到回归"的分水岭在哪里。
