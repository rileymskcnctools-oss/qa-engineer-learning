## 企业真实场景

1. **文案带动态内容**：余额/件数等文案用 `contains(@text,"余额")` 或 UiSelector 的 textContains 定位，不精确匹配。（Ch20/Ch21）
2. **目标元素无 id、靠邻居定位**：唯一标题文本做锚点，`/parent::*/following-sibling::*` 横向走到目标按钮。（Ch20）
3. **长列表屏幕外元素**：UiScrollable 的 scrollIntoView 滚到可见再定位，比手动 swipe 循环稳。（Ch21）
4. **点按钮后异步加载**：显式等待 element_to_be_clickable，等"可点击"而不是等"存在"。（Ch22）
5. **"操作成功/失败"提示断言**：封装 Toast 通用方法，显式等待 + contains 抓 text 断言。（Ch23）

## 收获

1. **XPath 三层高阶**：contains（包含）、轴定位（父子/祖孙/兄弟）、and/or（交集/并集），定位不唯一时靠它们兜底。
2. **轴定位核心思想**："先锚定唯一元素、再沿轴导航到目标"，不要求目标本身可定位；`[1]` 是"向外一层"不是数组下标。
3. **UiSelector 是原生首选**：链式多属性（等价 AND）+ 模糊匹配（contains/StartsWith/Matches）+ 层级（fromParent/childSelector），比 XPath 快且不依赖 XML。
4. **CSS 定位原理**：解析后映射成原生定位，多一层开销，所以 App 端多推荐 XPath 或原生定位；App id 特殊字符要转义。
5. **显式等待进阶**：等"条件"非等"时间"；presence/visibility/clickable 递进；lambda 可自定义条件。
6. **Toast 三件套**：page_source 看结构 + class `android.widget.Toast`/XPath 定位 + 显式等待；短暂显示是难定位的根因。
7. **多处课程源笔误**：`load_capabilities(cpas)` 变量名笔误（应为 caps）、Java 父子示例末尾多引号、`fromParent(text("Text"))` 缺 `new UiSelector().`、`:contains` 非标准 CSS、`shouldTerminateApp` 注释"不重启"写反（Ch11 已标）。

## 反思
> Ch20 轴定位是最容易被"背表达式"带偏的一章——真正要抓住的是"先锚定、再导航"这个思想，`..`/`*`/`[1]` 只是简写符号，背下来不理解"为什么能唯一"等于没学。Ch21 的 UiSelector 和 CSS 是一组对比：一个原生快、一个多一层解析慢，面试最爱问"为什么推荐原生/CSS 区别在哪"，要能说清"映射"这条原理链路。Ch22 的显式等待务必和 Ch14 的"元素在 DOM ≠ 可交互"串起来——presence/clickable 正是那条结论的官方条件化表达。Ch23 Toast 是"特殊控件"的第一个实战，核心不是背 XML 结构，而是理解"短暂显示 → 必须等待 + 抓 text"这个因果。这四章共同把定位和等待从"基础会用"推到"高阶兜底"，是后续 PO 框架和 Pytest 用例的硬基础。
