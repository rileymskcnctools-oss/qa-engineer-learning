> 整理过程中**逐条核对官方文档**并抓到 **8 处课程原文问题**，最值钱的六处：
> ① **"JMeter 变量可以跨线程传参"是错的**（官方：*Variables are local to a thread; properties are common to all threads*）——跨线程/跨线程组共享必须用 `${__setProperty()}` + `${__P()}`（Ch32）；

> ④ `hostname` 被解释成"显示本地用户信息"（实际是**主机名**，用户信息是 `whoami`/`who`），命令清单里 `cat /proc/cpuinfo` **重复出现两次**（Ch35、Ch38）；
> ⑤ `ps-ef` 缺空格、`ps -aux` 混用 BSD/UNIX 两种风格（Ch37）；

## 面试可能怎么问

Q1：JMeter 里变量和属性有什么区别？多线程之间怎么传值？
→ 参照 Ch32 知识点4：官方定义（变量线程私有 / 属性全 JVM 共享且必须 `${__P()}` 引用）→ 因此"变量跨线程传参"不成立（原文此处写错）→ 跨线程正道 `${__setProperty(名,值)}` 写 + `${__P(名)}` 读 → 典型用法"setUp 登录一次写属性、主线程组全员复用" → 边界：属性是 JVM 级（可能读到上次运行的旧值）、分布式下要 `-G` 传。

Q2：JMeter 参数化怎么做？数据用完了会怎样？
→ 参照 Ch34：四种方式（UDV 常量 / 用户参数按线程 / 函数现算 / CSV 每迭代一行）→ CSV Data Set Config 9 个参数（Variable Names 留空＝首行表头、Delimiter `\t`、Allow quoted data）→ 行与线程分配（默认 All threads、分配顺序不保证、`test${__threadNum}.csv` + Current thread）→ 数据用完：Recycle=true 重读；false + Stop thread on EOF=false → 变量变 `<EOF>`；true → 线程停止。

Q3：给你一台已经出现性能问题的服务器，你按什么顺序定位？
→ 参照 Ch35/Ch36/Ch37：① 定现象（施压机 / 应用 / 中间件 / DB，先排除施压机假瓶颈）② 定方向（`uptime` load 与核数比、`vmstat 1` 的 r/b/si·so/wa/cs）③ 定对象（`top` 按 `P`/`M` 排序 → `c` 确认进程 → `top -H -p PID` 找线程）④ 交叉验证（`iostat -x` 的 %util/await、`free -m` 的 available、`ss` 的 TIME_WAIT）⑤ 下钻代码（jstack / 火焰图 / 慢查询），并显式排除其他层。

Q4：压测结果怎么实时看？为什么不是压完看聚合报告？
→ 参照 Ch43：JMeter Backend Listener → InfluxDB（时序库）→ Grafana 实时看板 + 告警；优点是压测中秒级发现拐点、可现场调整、多轮可对比；与机器指标（Ch42 的 Prometheus + Node Exporter）同板对齐才能定位瓶颈层；报告里要注意 TPS 与 QPS 的口径。

Q5：你怎么保证压测数据可信？
→ 参照 Ch38 / Ch42：① 监控链路三层验证（9100 → 9090 → 3000）；② 采集间隔按压测需要（5s）并提前启动采集脚本；③ 业务与机器指标同一时间轴；④ 采基线、压中实时、压后归档；⑤ Prometheus 不部署在被测机上；⑥ 数据文件与脚本解耦、`testTitle` 命名可追溯。

## 企业真实场景

> 这个知识点在企业里什么时候会用到？

- **多环境一套脚本**：域名/端口/账号全部变量化，`${__P(host,localhost)}` + `-Jhost=...` 切环境，脚本只有一份 → 这是"能交给同事和 CI 用"的前提（Ch32）。
- **压测数据不撞车**：500 虚拟用户各自的账号/商品/订单号，靠 CSV 账号池 + `${__threadNum}`/`${__counter}` 造唯一值；`testTitle` 按"项目-场景-日期-轮次"命名，多轮数据可叠加对比、量化优化收益（Ch33 / Ch34）。
- **线上性能问题定位**：`vmstat` 定方向 → `iostat`/`free`/`ss` 定量 → `top -H` + jstack 落到线程与代码；排查产出不只是"找到瓶颈"，而是"用数据排除其他可能"（Ch35~Ch37）。
- **大促值班与容量决策**：Grafana 大屏（Prometheus + Node Exporter 看机器 + InfluxDB 看业务），压测前用历史趋势定目标、压测中盯板找拐点、压测后归档写报告——"同一套指标贯穿压测与生产"（Ch39 / Ch41 / Ch42）。
- **压测现场止损**：实时看板发现 RT 抬头、错误率上升 → 当场停止加压、记录拐点并发作为容量结论，省下"盲压一轮再重压"的时间与人力（Ch43）。
- **简历与面试**："用 Docker 部署 Prometheus + Node Exporter + Grafana，并把 JMeter 结果实时写入 InfluxDB 出实时看板，压测中定位到 CPU/IO/连接数瓶颈"——每个动作都真实做过、可追问（本模块全部章节）。

## 收获

1. **变量 vs 属性是 JMeter 的分水岭**：变量线程私有（UDV 也只是"测试开始时复制给每个线程的初始集"），属性全 JVM 共享（`${__setProperty()}` 写 / `${__P()}` 读）；课程原文"变量可以跨线程传参"是错的，而这恰好是面试最爱追问的点。
2. **求值时机决定用途，"静默失败"是共同特征**：UDV 一次、CSV 每迭代、函数每次调用、提取器每次响应后；引用不存在的变量/CSV 读错列/数据用完变成 `<EOF>`/Backend Listener 参数名写错——**全都不报错**，只能靠"Debug Sampler 看值 + View Results Tree 看引用 + 断言看业务"三层验证兜住。
3. **性能排查有固定方向链**：`uptime`/`vmstat` 定性 → `mpstat`/`iostat`/`free`/`ss` 定量 → `top`/`ps` 落到进程与线程；三个最易误读的信号是 `wa` 高（等 IO）、`available` 小 + `si/so` 非 0（内存不足，会伪装成磁盘问题）、`load` 高但 CPU 不高（一堆进程卡在 `D` 状态）。
4. **监控体系的骨架是"采集 → 存储 → 展示 + 告警"**：9100（Node Exporter）→ 9090（Prometheus，pull + 多维标签 + PromQL）→ 3000（Grafana，不采集不存储）；压测结果走另一条 push 链路（JMeter Backend Listener → InfluxDB 8086 → Grafana）；**两条链路的指标落在同一块看板上，才算闭环**。
5. **口径与纪律决定数据可信度**：`*_total` 必须 `rate()`、内存看 `MemAvailable`、RT 看 P95/P99、TPS 与 QPS 报数必须说明口径；采集要提前启动并覆盖全程、与业务指标时间对齐、压后归档；Prometheus 不与被测服务同机。
