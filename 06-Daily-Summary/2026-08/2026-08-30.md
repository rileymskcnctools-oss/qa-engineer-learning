## 学习任务

### 任务 1：验证生命周期钩子执行顺序（30 分钟）
写一个 Pytest 类，在 `setup_class` / `setup_method` / `teardown_method` / `teardown_class` 各打一行 `print`，跑 2 条用例，确认：①setup_class 只跑 1 次 ②setup_method 每条跑 1 次 ③执行顺序是 setup_class → setup_method → 用例 → teardown_method → teardown_class。把 `print` 换成 `driver` 的启停，观察 2 条用例是不是只开一次浏览器。

### 任务 2：封装"回到首页"对比 quit()（30 分钟）
写两条用例：一条 teardown 里 `driver.quit()`，另一条 teardown 里调封装的 `go_home()`（`driver.get(首页URL)`）。分别计时，体会"每条 quit()"和"回到首页 + teardown_class 才 quit()"的效率差。思考：什么状态下"回到首页"不足以复位，必须退回 quit()。

### 任务 3：数据清理走业务接口（20 分钟）
找一个有删除接口的测试对象，在 teardown 里用 `requests` 调业务删除接口清理脏数据，对比"用 UI 点删除按钮"的耗时。写一句注释说明为什么不用 SQL 直连数据库。

### 任务 4：搭一个最小 PO 项目结构（30 分钟）
在 `homework05-selenium-basic/` 建四目录骨架：`page/`（放一个 `BasePage` 或空页面类）、`testcases/`（放一条用例）、`utils/`（放 driver 工厂或配置读取）、`log/`（放日志初始化）。对照 Ch17 知识点 8，说明每个目录"放什么、为什么分层"。

### 任务 5：口述四框架钩子对照（15 分钟）

## 企业真实场景

1. **接手遗留自动化代码**：用"可维护性 + 稳定性"两把尺子评估它的现状和改造优先级，而不是凭感觉说"写得乱"。（知识点 1）
2. **suite 越跑越慢的排查**：发现每个用例 teardown 都 `driver.quit()` → 50 条用例 50 次冷启动；改成"回到首页 + teardown_class 才 quit()"，suite 时间大幅下降。（知识点 6）
3. **脏数据污染测试环境**：每天上百条脏订单，选择在 teardown 调后端"取消订单"接口清理，走业务自己的级联逻辑，而不是写 SQL 去 `DELETE FROM orders` 漏掉明细表和状态流水。（知识点 7）
4. **页面改版只改一处**：目录按 page/testcases/utils/log 分层后，前端改一个按钮只动 page 类，几十条用例零改动。（知识点 8）

## 收获

1. **两把尺子衡量用例质量**：可维护性（低模块化/高耦合/无复用/差可读/命名乱/无注释/不合规范）+ 稳定性（未处理异常/断言不足/依赖不清），是评价一切自动化代码的通用标准。
2. **生命周期钩子四框架对照**：Pytest `setup_class`/`setup_method`/fixture、JUnit4 `@BeforeClass`/`@Before`、TestNG 五级粒度、JUnit5 `@BeforeAll`/`@BeforeEach`；Pytest 的 fixture 作用域四级（function/class/module/session）是它的核心优势。
3. **粒度权衡原则**：贵的操作（起 driver、备数据）放类级做一次，便宜的操作（回状态、清数据）放方法级每次做——这是用例隔离与效率的平衡点。
4. **恢复初始状态两派**：quit() 重启（绝对干净但慢）vs 回到首页（轻量复位但要求状态可复位），工程默认后者、quit() 收敛到 teardown_class。
5. **数据清理三选**：业务接口（推荐，走业务逻辑）> UI 操作（真实但慢）> 直连 SQL（不推荐，绕过业务有风险）。
6. **项目目录分层**：Python page/testcases/utils/log，Java main/test 分离 + resources，本质都是"页面变化只改 page 层"。
