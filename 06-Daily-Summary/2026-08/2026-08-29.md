## 企业真实场景

1. **后台 CRUD 自动化**：登录态 + 多级菜单 + 复杂表单 + 列表断言，是管理后台自动化最典型的四件套，litemall 优惠券 = 这套的标准样板。
2. **数据依赖治理**：先增后删的用例，用 fixture 造数据 + teardown 清理 + 唯一标识（时间戳）避免冲突，是"用例可重复执行"的底线。
3. **脆弱定位识别**：`.el-table_1_column_2`、`eles[1]` 这种"跑得通但一改版就崩"的定位，正是 review 新人代码时重点圈的地方。
4. **日志滚动**：长期运行的框架日志会膨胀到几个 G，`RotatingFileHandler` 是"别把 CI 磁盘写爆"的标准答案。
5. **Allure 报告**：CI 每次回归生成可视化报告，产品/负责人不看代码就能判断"这轮健不健康"，是自动化"最后一公里"。
6. **PO 分层的必要性**：200 条用例硬编码 XPath，前端改一个 class 要改 200 处；PO 把定位集中一处，改一处全生效。

## 收获

1. **完整实战链路**：产品分析→用例分析→前置后置→脚本→优化→日志/截图→报告→反思，一条后台功能从 0 到自动化报告的完整路径。
2. **两段式断言**：通知提示（"成功" + 具体文案）是过程断言，列表状态（在顶部 / 不在列表）是结果断言，缺一不可。
3. **类级 vs 方法级 fixture**：driver + 登录放类级（复用、快），数据清理放方法级（防污染）。
4. **三个工程化升级**：`time.sleep`→显式等待、`basicConfig`→`RotatingFileHandler`、截图→`allure.attach` 进报告。
5. **Allure 三步 + 一个关键区分**：装程序/装插件 → `--alluredir` 出 JSON 中间数据 → `serve` 渲染报告。跑 `--alluredir` 不等于有报告。
6. **PO 是"承上启下"的分水岭**：本章结尾的两大缺陷（重复代码 + 业务场景不清晰）正是 PO 要解决的，下一章从"能跑"跨到"可维护"。

## 反思
> 本章是"从能跑 → 会优化 → 引出工程化"的转折点。脚本本身不难，难的是**看懂它哪里脆弱**：`time.sleep` 为什么该换、`eles[1]` 为什么一改版就崩、`.el-table_1_column_2` 为什么是动态 class。这些"脆弱点识别"能力，比"能把脚本跑通"更接近真实工作——企业里接手的多半是别人写的第一版脚本，你的价值在于能指出问题并分层重构。最可验证的结果是三个：任务 2（换显式等待后观察速度/稳定性）、任务 6（`--alluredir` 目录里看到的是 JSON 不是报告）、任务 7（能口头说出 3 处脆弱点的"崩溃条件"）。别停留在"我会写优惠券脚本"，务必跑出报告 + 圈出脆弱点。
