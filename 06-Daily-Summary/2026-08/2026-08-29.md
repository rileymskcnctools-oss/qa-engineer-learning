## 企业真实场景

1. **后台 CRUD 自动化**：登录态 + 多级菜单 + 复杂表单 + 列表断言，是管理后台自动化最典型的四件套。（Ch14）
2. **脆弱定位识别**：`.el-table_1_column_2`、`eles[1]` 这种"跑得通但一改版就崩"的定位，是 review 新人代码时重点圈的地方。（Ch14）
3. **日志滚动 + 截图进报告**：`RotatingFileHandler` 防磁盘写爆；`allure.attach` 让失败截图直接出现在报告里，负责人不看代码就判断"这轮健不健康"。（Ch14）
4. **PO 分层重构的 ROI**：把 50 条线性用例的定位器抽到页面类，前端改版只动页面类一处、50 条用例零改动。（Ch15）
5. **定位器私有化**：定位器是"易变的实现细节"，私有属性隐藏它，团队 review 时照 6 原则一条条对。（Ch15）
6. **链式调用读起来像手工用例**：`LoginPage().login(...)` → `HomePage().search(...)`，产品/测试负责人也能看懂自动化在测什么。（Ch15）
7. **失败自动留证装饰器**：所有 UI 用例挂 `@ui_exception_record`，CI 上任何失败都自动留日志 + 截图 + page_source 进报告，测试同学打开报告就能看失败现场，不用重跑复现。（Ch16）

## 收获

1. **完整实战链路**：产品分析→用例分析→前置后置→脚本→优化→日志/截图→报告→反思，一条后台功能从 0 到自动化报告的完整路径。（Ch14）
2. **两段式断言 + 类级 fixture**：通知提示（过程）+ 列表状态（结果）缺一不可；driver + 登录放类级，数据清理放方法级。（Ch14）
3. **三个工程化升级 + Allure 三步**：`time.sleep`→显式等待、`basicConfig`→`RotatingFileHandler`、截图→`allure.attach`；装程序/装插件→`--alluredir` 出 JSON→`serve` 渲染报告。（Ch14）
4. **PO 是"从能跑到可维护"的分水岭**：传统三大问题（脆弱/不清晰/样板代码）↔ PO 三大优势（可维护/可读/复用），本质是"用例层 / 页面层"两层结构。（Ch15）
5. **6 大原则一分为二记**：字段意义 2 条（私有隐藏 + 只建必要）管"元素怎么放"，方法意义 4 条（业务方法 + 返回值 + 一方法一结果 + 不加断言）管"方法怎么写"。（Ch15）
6. **两个 Python 细节**：定位器元组 `(By.NAME, "q")` + `find_element(*locator)` 解包；`__` 双下划线触发 name mangling。（Ch15）
7. **异常自动留证 = 装饰器 + 三件套**：`try/except` 里记日志 + 截图 + page_source 挂 Allure，最后 `raise e` 保证用例仍失败；这是 Ch13 三件套的"自动化落地"。（Ch16）
